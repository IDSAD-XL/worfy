# Ночной прогон: red → green → мутации → сведение

Один вызов — несколько модулей, каждый в своём worktree и своём агенте `auction-implementer`.
Готовый модуль вливается в ветку ночи `overnight/<дата>`. В `main` ночью не вливается ничего:
джоба `deploy` в `.github/workflows/ci.yml` идёт на push в `main` и катит прод, поэтому
последний мерж — утреннее решение человека.

Параллельно не больше трёх модулей `apps/api` (каждый прогон тестов поднимает свой Postgres в
Testcontainers); модули `apps/web` и `packages/shared` идут сверх этого, но всего не больше пяти
агентов разом. Модули берутся очередью: освободилось место — взят следующий, и так до бюджета
времени (по умолчанию шесть часов от старта, иначе аргумент вида `до 06:30`). Невзятые модули
идут в утренний отчёт строкой «не начат». Главная сессия — оркестратор: раздаёт модули, вливает
их ветки, пишет утренний отчёт. Вопрос пользователю ночью — запись в `FAILURE.md` и остановка модуля.

Файлы прогона — в scratchpad-каталоге сессии (путь даёт сессия): `<scratchpad>/overnight/<имя>/PR.md`,
там же `FAILURE.md`, `<scratchpad>/OVERNIGHT-REPORT.md`. Внутри worktree их держать нельзя: в
`.gitignore` их нет, а 1b и 1d коммитят `git add -A` — файлы уехали бы в коммит модуля.

## 0. Ветка ночи и выбор модулей

Ветка сведения — одна на прогон, от свежего `origin/main`:

```bash
git fetch origin --prune
NIGHT=overnight/$(date +%F)          # ветка уже есть (перезапуск, вторая сессия) — переиспользовать
git rev-parse --verify --quiet "origin/$NIGHT" \
  || { git branch "$NIGHT" origin/main && git push -u origin "$NIGHT"; }
```

Модуль — каталог второго уровня в `apps/*/src` или `packages/shared/src` (`apps/api/src/auctions`);
в `apps/web/src/app` — каталог маршрута на уровень глубже (`apps/web/src/app/lots`); файлы в корне
пакета (`apps/api/src/main.ts`) модуля не образуют. Имя модуля — последний сегмент пути
(`auctions`, `lots`; `packages/shared/src` → `shared`), при совпадении имён — с префиксом
приложения (`api-catalog`, `web-catalog`). Если список не дан — самые изменяемые за 30 дней:

```bash
git log origin/main --since=30.days --name-only --pretty=format: -- apps/api/src apps/web/src packages/shared/src \
  | awk -F/ 'NF==0 || /\/(drizzle|dist)\// {next} NF==4 && $1=="apps" {next}
             $3=="src" && $4=="app" {if (NF>5) print $1"/"$2"/"$3"/"$4"/"$5; next}
             NF>4 {print $1"/"$2"/"$3"/"$4; next} {print $1"/"$2"/"$3}' \
  | sort | uniq -c | sort -rn | head -8
```

Дерево модулю — от ветки ночи; чужие деревья держат другие сессии, их не трогать. Имя ветки
модуля не может начинаться с `overnight/<дата>/`: git не заводит ветку внутри уже занятого имени,
поэтому разделитель — дефис.

```bash
git worktree add .claude/worktrees/overnight-<имя> -b overnight/<дата>-<имя> overnight/<дата> \
  && pnpm install -C .claude/worktrees/overnight-<имя>
```

Перед 1a — `auction-scout` по модулю: входные точки, цепочка вызовов, таблицы, которые читают
`apps/web/e2e`. Карта идёт в бриф исполнителя.

## 1. Цикл по модулю — агент `auction-implementer`, один на модуль

Агент привязан к тикетам (`.scratch/<эпик>/issues`, `claim`, JSON с `ticket`, шаги ship-ticket).
В брифе явно: тикета нет, `claim` не делать, порядок — шаги 1a–1g этого скилла, отчёт — по
форме ниже, не JSON тикета. Дать: путь worktree, имя и каталог модуля, имя ветки ночи, карту от
`auction-scout`, «Классы ошибок», пути `PR.md` и `FAILURE.md`. Назад — ≤30 строк: тесты, коды
возврата каждого прогона, строка мутаций «до → после», вердикт ревьюера 1e («чисто» или находки
списком), номер PR или путь `FAILURE.md`; без пересказа хода работы. Без вердикта 1e оркестратор
мерж не делает.

Правки — только внутри следа модуля: его каталог и его новый файл тестов. Правка вне следа нужна
для зелёного — это `FAILURE.md`, не расширение следа. Код возврата печатать рядом с каждым прогоном;
фильтр длинного вывода — только `set -o pipefail; <команда> | tail -n 20` (без него хук
`guard.mjs` откажет в трубе, стоящей после проверочной команды).

### 1a. Тесты модуля, точки мутаций и база «до»

Существующие spec-файлы модуль читает, но не правит: в `apps/api/test` из 121 файла 90 импортируют
больше одного модуля, и два параллельных агента столкнулись бы в одном файле. Новые тесты — всегда
в новый файл, свой у каждого модуля:

| Workspace | Файл новых тестов |
|---|---|
| `apps/api` | `apps/api/test/<имя>.hardening.spec.ts` |
| `apps/web` | рядом с модулем: `<каталог модуля>/<имя>.hardening.test.ts` |
| `packages/shared` | `packages/shared/test/<имя>.hardening.spec.ts` |

Список тестов модуля для мутационного тестирования — существующие spec-файлы, импортирующие
каталог модуля, плюс новый файл. Команда идёт из каталога workspace; каталоги перечислять те, что
там есть (`apps/api` — `test src`, `apps/web` — только `src`, `packages/shared` — `test src`):

```bash
grep -rslE "/<имя>(/|')" --include='*.spec.ts' --include='*.test.ts*' test src   # код 1 при пустом ответе — не ошибка
```

Список фиксируется здесь и без изменений используется в 1d.

Прочитать модуль, выбрать не меньше пяти точек мутации (см. «Что ломать»); подходящих мест меньше
пяти — взять все и записать их число. По каждой: сломать, прогнать тесты модуля, записать
красный/зелёный, вернуть файл `git checkout -- <файл>`. Итог — «до: красных X из N».

### 1b. Враждебные тесты — RED, закоммичены

Написать тесты по «Классам ошибок» ниже — то, что в проекте уже ломалось. Условие завершения:
`typecheck` workspace зелёный, прицельный прогон новых тестов красный по утверждению
(assertion), не по ошибке компиляции.

```bash
pnpm --filter @auction/api typecheck; echo "КОД=$?"
pnpm --filter @auction/api exec vitest run test/<имя>.hardening.spec.ts; echo "КОД=$?"
git add -A && git commit -m "test(<имя>): red — <что проверяется>"
```

Модуль `shared` — перед `typecheck` один раз `pnpm --filter @auction/shared build` (причина в 1f).

С этого коммита текст тестов заморожен: ожидание, изменённое ради зелёного, — `FAILURE.md`.
Новые тесты зелены с первого прогона — переписать утверждение строже; зелены и во второй раз —
закрыть модуль строкой отчёта «нечего укреплять», PR не открывать.

### 1c. Правка до зелёного — не больше 15 итераций

После каждого изменения — весь набор того workspace, где правка, голым:
`pnpm --filter @auction/api test; echo "КОД=$?"`. Пятнадцатая итерация красная — остановиться,
написать `FAILURE.md`: какой тест красный, что пробовали, на чём стоит. Модуль закрыт, PR не открывать.

### 1d. Мутационное тестирование

Сначала коммит: восстановление после мутации сносит незакоммиченное. Те же точки и тот же
список тестов, что в 1a, по одной: сломать → прогон тестов модуля → ожидается красный →
`git checkout -- <файл>` (один путь; `checkout -- .` хук откажет). Итог «после: красных Y из N».

Порог — 80 % убитых. Ниже порога: на каждую выжившую мутацию добавить тест, повторить 1c
один раз, прогнать мутации снова. Второй недобор — `FAILURE.md` с перечнем выживших, PR не открывать.

### 1e. Ревью — агент `auction-reviewer`, линза «корректность и след по файлам»

Отчёт исполнителя — заявление, не факт: ревьюер сам повторяет каждую проверочную команду и вставляет
коды возврата. Контракт: находки только, `file:line`, ≤30 строк, явное «чисто». Каждую ссылку перечитать.

Есть находки — вернуться в 1c и закрыть их, потом ревью заново, один раз. Второй раз не «чисто» —
`FAILURE.md` с находками, PR не открывать. Вердикт идёт в отчёт исполнителя.

### 1f. Гейт

Гейт — `gate.sh fast`: lint корня плюс `typecheck` и `test` изменённых workspace, код 2 на
красном; красный гейт — `FAILURE.md`, не PR. Правил `packages/shared` — перед гейтом один раз
`pnpm --filter @auction/shared build`: vitest читает `src` (алиас в `apps/*/vitest.config.ts`),
а `typecheck` api, `pnpm dev` и `pnpm build` — `dist` (`moduleResolution: node` не читает
`exports`; трассировка tsc резолвит `@auction/shared` в `packages/shared/dist/index.d.ts`).
Поэтому после каждой мутации пересборка не нужна, а перед typecheck и гейтом — обязательна.

```bash
bash ~/.claude/hooks/gate.sh fast </dev/null; echo "КОД=$?"   # stdin закрыт, иначе скрипт ждёт на cat вечно
```

### 1g. PR в ветку ночи

```bash
gh auth status                      # активен не IDSAD-XL → gh auth switch -u IDSAD-XL
git push -u origin overnight/<дата>-<имя>
gh pr create --base overnight/<дата> --title "overnight(<имя>): <что укреплено>" \
  --body-file <scratchpad>/overnight/<имя>/PR.md
```

В теле: тесты списком, «мутации: до X из N → после Y из N», код гейта. Агент модуля здесь
заканчивает: вливает оркестратор.

### 1h. Мерж модуля — делает оркестратор

Проверки и мерж — тремя отдельными командами, без трубы между ними:

```bash
gh pr checks <N> --watch --fail-fast; echo "КОД=$?"
gh pr view <N> --json mergeStateStatus -q .mergeStateStatus   # CLEAN — вливать
gh pr merge <N> --squash --delete-branch
```

Условие мержа — все три сразу: зелёный CI, `CLEAN` и «чисто» от ревьюера 1e. Иначе:

- `DIRTY` — перебазировать ветку модуля на ветку ночи, прогнать гейт заново, дождаться
  проверок, влить. Второй конфликт — `FAILURE.md`, PR остаётся открытым.
- Красные проверки (ненулевой код `gh pr checks`) или любое другое состояние
  (`BLOCKED`, `UNSTABLE`, `BEHIND`) — `FAILURE.md` с именем упавшей джобы, PR остаётся
  открытым, модуль из ночи выпадает. Чинить ночью CI, зелёный локально, значит править вслепую.

Ветка ночи после мержа сдвинулась: следующий модуль это не задевает, следы модулей и файлы
тестов не пересекаются.

## Классы ошибок — что проверять враждебным тестом

Тест на каждый применимый пункт, не на выдуманное. Первые три — из отчёта по стенограммам
сессий за сентябрь 2026; в HANDOFF, ADR и `.scratch` их нет.

- Дата и часовой пояс, вычисленные в Node вместо базы; граница суток по Киеву.
- Регулярное выражение на `CRLF` против `LF`.
- Планировщик за один проход делает два перехода состояния (предупредить и закрыть в
  одном тике) — тест на ровно один переход за проход.
- Разбор статуса из строки: регистр, пробелы, незнакомое значение.
- Тип `$onUpdate` в drizzle: SQL-выражение туда не проходит, запись падает.
- E2E читают базу мимо схемы drizzle (`apps/web/e2e/dev-doors.ts`, `apps/web/e2e/actors.ts`):
  модуль, чьи таблицы они читают, проверяется и там.
- Код возврата, съеденный трубой, — для скриптов модуля, если они есть.

## Что ломать — точки мутаций

Инвертировать условие ветвления; сдвинуть границу (`<` ↔ `<=`); убрать `await`; поменять
статус в переходе на соседний; вернуть константу вместо вычисления; убрать одну ветку
`switch`. Одна мутация — одно место — один прогон.

## Ночью не делать

Мерж в `main` и любой выкат прода; миграции и любые изменения схемы; правки вне следа модуля;
правку чужих spec-файлов; контрактные тесты (`test:contract`); `push --force`; изменения ADR,
`HANDOFF.md`, `CLAUDE.md`. Нужное из этого списка — запись в `FAILURE.md` и утренний отчёт,
работа модуля останавливается.

## 2. Сведение ночи — один PR в `main`, открытый до утра

Очередь пуста или вышел бюджет времени — сначала написать `OVERNIGHT-REPORT.md` (раздел 3), он же
идёт телом PR; затем открыть PR ветки ночи и дождаться проверок:

```bash
gh pr create --base main --head overnight/<дата> --title "overnight <дата>: модулей <K>" \
  --body-file <scratchpad>/OVERNIGHT-REPORT.md
gh pr checks <N> --watch --fail-fast; echo "КОД=$?"
```

PR остаётся открытым. Красные проверки сведения — строка в отчёте с номером PR и упавшей джобой,
разбор утром: чинить ночью то, что зелено помодульно, а красно вместе, значит править вслепую.

## 3. Утренний отчёт

`OVERNIGHT-REPORT.md` в scratchpad-каталоге сессии: таблица по модулям, затем блок статуса.
В таблицу — только PR с кодом гейта и `FAILURE.md` с причиной.

| Модуль | Тестов добавлено | Мутации до → после | PR | Влит | FAILURE |
|---|---|---|---|---|---|
| `auctions` | 7 | 1 из 5 → 5 из 5 | #NNN | да | — |

Человеку остаётся подтвердить выкат. После его «да» — две команды подряд, затем проверка прода:

```bash
gh pr merge <N> --merge --delete-branch      # коммиты модулей раздельны; --squash, если нужен один
sha=$(gh pr view <N> --json mergeCommit -q .mergeCommit.oid)
id=$(gh run list --branch main --limit 10 --json databaseId,headSha \
       -q "[.[] | select(.headSha==\"$sha\")][0].databaseId")
gh run watch "$id" --exit-status; echo "КОД=$?"      # в этом прогоне джоба deploy
curl -s https://<api>/version | jq -r .commit        # должен совпасть с $sha
```

    — Этап: вне эпиков (ночной прогон)
    — Сейчас: <модулей влито в ветку ночи, сколько в FAILURE, состояние PR сведения>
    — Дальше: подтвердить выкат PR #<N>
    — Жду: «да» на мерж в main или разбор FAILURE

## Запуск без терминала (не проверено)

Без человека у терминала любой запрос разрешения останавливает `-p`, а `--permission-mode dontAsk` отвечает
на него отказом — тот же стоп; поэтому `--dangerously-skip-permissions`. Потолок — деньгами: флага на число ходов у `claude` нет.

```bash
claude -p "/overnight-fix-loop apps/api/src/auctions apps/api/src/scheduler до 06:30" \
  --dangerously-skip-permissions --max-budget-usd 40
```
