# Провести волну эпика

`ship-ticket` ведёт один тикет; здесь — раздача, гейт, мерж. Волна — тикеты одного эпика
(`.scratch/<эпик>/`), не блокирующие друг друга: код пишут агенты-исполнители параллельно.

## 1. Предполёт

```bash
~/.claude/bin/preflight --epic <эпик>; echo "КОД=$?"
~/.claude/bin/epic-status --json | jq '.tickets[] | select(.epic=="<эпик>")'
gh pr list --state open --json number,headRefName,mergeStateStatus,files
```

`preflight` делает `git fetch`, меряет отставание локального `main`, спрашивает
`worktree-lock status`, ищет дубли и старший номер ADR на `origin/main`, во всех ветках
`origin/*` и в локальных, последнюю миграцию там же, сверяет активный аккаунт gh с
владельцем remote, печатает открытые PR и строку `epic-status`.
Последняя строка — `GO` или `BLOCKED: <причины>`, код 1 при BLOCKED. Строка
`origin/main: <sha> …` — база для брифов раздачи. `gh pr list` с `files` нужен отдельно:
`docs/adr/*` в чужих PR — занятые номера.

`epic-status --json` не принимает имя эпика (`epic-status <эпик> --json` печатает
человеческую строку) и отдаёт `{ref, epics, tickets[]}` по всем эпикам — отсюда фильтр.
`state` принимает `open|work|blocked|done|none`; слово «claimed» лежит в `statusRaw`.

Исходы: `BLOCKED` от `preflight` (fetch не удался, чужая живая сессия в дереве волны, дубль
номера ADR на `origin/main`, HEAD на `main`, отставшем от `origin/main`, неизвестный эпик) —
стоп с сообщением; отставание локального `main` из ветки — только предупреждение,
исполнители ветвятся от `origin/main`; открытый PR на ветке
`<эпик>/<NN>` — тикет возобновляется (раздел «Как возобновить»), не раздаётся заново;
остальное — строки таблицы плана (`docs/adr/*` в чужих PR — занятые номера).

В волну входят тикеты со `state: "open"`, `blockedParsed: true` и каждым номером из
`blockedNums` в состоянии `done`; при `blockedParsed: false` сначала поправить `Blocked by`.

Один вызов `qmd` (скилл `qmd`: `vec` вопросом, `lex` основами слов, `hyde` ожидаемым
ответом) по теме эпика — до плана: принятое ADR или оплаченный урок меняют брифы.

След по файлам берётся из `## Где в коде` тикета. Неполный след (нет теста, точки входа,
e2e при правке схемы) до раздачи дополняет `auction-scout`: карта тикета с `file:line`.

План волны — таблица, и она же итог предполёта:

| Тикет | След по файлам | ADR / миграция | Кто |
|---|---|---|---|
| 05 | apps/api/src/moderation/*.ts, test/moderation.spec.ts | ADR-0061 | impl-05 |
| 07 | apps/web/app/lots/[id]/page.tsx | — | impl-07 |

Два тикета с общим файлом в следе идут последовательно: второй стартует после мержа
первого. Номера ADR раздаются в плане по одному, следующие за старшим на `origin/main`;
исполнитель пушит заглушку с занятым номером в первые минуты, чтобы заявка была видна
в `gh pr list` другим сессиям. Миграция — только `pnpm db:generate` поверх `origin/main`.
Таблица готова — раздача сразу, без ожидания подтверждения.

## 2. Раздача

Один агент на тикет, все в одном сообщении (`Agent`, тип `auction-implementer`, имя
`impl-<NN>`, фоном): шаги 1–8 `ship-ticket` до открытого PR с зелёным CI, мерж остаётся
оркестратору. Порядок работы и формат отчёта заданы в определении агента, бриф их не повторяет:

```
Цель: <одна фраза из тикета>
Тикет: .scratch/<эпик>/issues/<NN>-<slug>.md; spec.md рядом
Дерево: git worktree add .claude/worktrees/<NN>-<slug> -b <эпик>/<NN>-<slug> origin/main
След по файлам: <точный список>
Номера: ADR-<NNNN> — создай docs/adr/<NNNN>-<slug>.md, сначала заглушкой;
        миграция — pnpm db:generate поверх origin/main
Следы соседей по волне (не трогать): <NN>: <файлы>; <NN>: <файлы>
```

Вопрос вместо отчёта (спорная спецификация, конфликт, который не разводится механически,
CI, красный после двух попыток) решается ответом через `SendMessage` тому же агенту.

## 3. Проверочный гейт

На каждый вернувшийся отчёт — `auction-reviewer` (имя `verify-<NN>`, линза «отчёт
исполнителя»). Дерево исполнителя к этому моменту простаивает, и проверяющий в нём один —
поэтому оно же; второго агента в это дерево не запускать, а мутации гонять только на
копиях в scratchpad (16 сентября второй ревьюер в общем дереве принял мутанта за
нестабильный тест). Отчёт — заявка; проверяющий читает `not_verified` первым и добывает
доказательства сам:

```bash
cd .claude/worktrees/<NN>-<slug>
git diff --name-only origin/main...HEAD                       # сверить с files_changed
bash ~/.claude/hooks/gate.sh fast </dev/null; echo "КОД=$?"   # зелёный: см. ниже
gh pr checks <N>                                              # отдельной командой, без пайпа
gh pr view <N> --json mergeStateStatus,headRefOid
```

Гейт зелёный только при `КОД=0` **и** строке `[gate] зелено (fast): …` в выводе: код 0
без неё значит «ничего не прогналось» или «окружение недоступно», и это не проверка.
Дальше проверяющий перечитывает каждую `file:line` из `claims`, сверяет `exit_code` из
`commands` со своим прогоном и ищет опровержение самой сильной фразе отчёта (тест проходил
и до правки). Вердикт — первая строка ответа: `VERIFIED` или `REJECTED` со списком
неподтверждённых утверждений; ≤30 строк, `file:line`. Каждый вердикт — комментарием в
PR, чтобы счёт кругов пережил перерыв сессии:

```bash
gh pr comment <N> --body "VERIFIED"            # или "REJECTED: <список>"
gh pr view <N> --json comments --jq '[.comments[].body | select(startswith("REJECTED"))] | length'
```

`REJECTED` уходит тому же исполнителю через `SendMessage` с этим списком — ровно один
круг доработки, после него гейт заново. Второй `REJECTED` выводит тикет из волны: строка
`blocked` в таблице отчёта, `ticket block` — в документном PR (раздел 4, пункт 4).
Гейт закрыт, когда у каждого тикета волны есть вердикт.

## 4. Мерж по политике

Каждый шаг — статус и мерж двумя командами; «no checks reported» — вывод `gh pr checks`
при конфликте, не значение `mergeStateStatus`:

```bash
gh pr view <N> --json mergeStateStatus   # CLEAN — мерж; DIRTY — конфликт; BLOCKED, UNSTABLE, BEHIND — ждать
gh pr merge <N> --squash
```

1. Обычные PR с кодом — подряд, по мере вердиктов `VERIFIED`.
2. PR с миграцией или правкой выката (`apps/api/drizzle/`, `scripts/verify-deploy.sh`,
   `.github/workflows/`) — по одному: следующий после зелёного прогона `main` по предыдущему.
3. Проверка прода — один раз, после последнего мержа кода. `scripts/verify-deploy.sh`
   локально не запускать (ему нужны `API_URL WEB_URL BASIC_AUTH_USER BASIC_AUTH_PASSWORD`);
   дымовые проверки делает джоба `deploy` прогона `main` по этому коммиту:

```bash
sha=$(gh pr view <N> --json mergeCommit --jq .mergeCommit.oid)
gh run list --branch main --json headSha,status,conclusion,url --jq ".[] | select(.headSha==\"$sha\")"   # completed, success
curl -fsS -u "$BASIC_AUTH_USER:$BASIC_AUTH_PASSWORD" "$API_URL/version" | jq -r .commit   # = $sha; без этой строки в отчёте прод «не проверен»
```

4. Документный PR — последним, после проверенного прода. `ticket` правит `.scratch` в дереве,
   где запущен, поэтому статусы волны и одна правка `HANDOFF.md` на волну — в его ветке.
   HANDOFF переписывается как снимок (ADR-0085, скилл ship-ticket), рассказ о волне идёт в
   описание документного PR, обобщаемые уроки — в `docs/lessons/<тема>.md`;
   `node scripts/check-handoff.mjs` перед push:

```bash
~/.claude/bin/ticket done <эпик> <NN> --pr <N>                          # на каждый влитый тикет
~/.claude/bin/ticket block <эпик> <NN> «отклонён проверкой: <причина>»   # на каждый выведенный
```

Конфликт с `main` на любом шаге: исполнитель делает rebase на `origin/main` в своём
дереве (миграцию перегенерировать, а не разрешать руками), затем гейт заново, затем мерж.
Следующий PR берётся после того, как предыдущий влит: CI идёт по свежему merge-коммиту.

## 5. Отчёт

Таблица по волне, потом четыре строки статуса: «Этап» — вывод `~/.claude/bin/epic-status
<эпик>` после fast-forward `main`; «Сейчас» — только подтверждённое гейтом и живым адресом;
«Жду» — решение по `blocked`-тикету или «ничего». `file:line` из ответа проверяющего
перед цитированием перечитать самому.

| Тикет | PR | Гейт | Доработка | Прод |
|---|---|---|---|---|
| 07 | #341 | REJECTED → VERIFIED | 1 круг | 1a2b3c4 |
| 09 | — | REJECTED ×2 | blocked | — |

## Как возобновить волну

`ticket claim` выполняется в дереве исполнителя, и статус живёт в его ветке: `epic-status`
по локальному `main` его не видит. Состояние волны читается из веток, PR и деревьев:

```bash
~/.claude/bin/preflight --epic <эпик>; echo "КОД=$?"   # fetch, lock, открытые PR, номера ADR и миграций
for b in $(git for-each-ref --format='%(refname:short)' "refs/heads/<эпик>/*" "refs/remotes/origin/<эпик>/*"); do
  ~/.claude/bin/epic-status --json --ref "$b" | jq -c '.tickets[] | select(.epic=="<эпик>" and .state!="open")'
done                                            # или ~/.claude/bin/epic-board — снимок по всем веткам
ls .claude/worktrees/
```

Тикет `state: "work"` без дерева — исполнитель не стартовал: раздать заново. Дерево без
PR — исполнитель остановился до шага 8: продолжить `ship-ticket` в этом дереве. Открытый
PR — тикет стоит перед гейтом (раздел 3); круги доработки считать по комментариям PR.
Влитый PR при `state` не `done` — документный PR ещё впереди (раздел 4, пункт 4). Дальше —
с раздела 1: предполёт идемпотентен.
