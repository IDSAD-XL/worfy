## 4. k, n и интервал Wilson по каждому case-у

Code: `scripts/eval-history.mjs:28-52` · key lines: 36, 37, 38

```js
export function caseRows(report, tag, chosen) {
  const cases = Array.isArray(report?.cases) ? report.cases : []
  const rows = []
  for (const name of chosen) {
    const entry = cases.find((one) => one?.name === name)
    if (!entry) continue
    // `--ablation none`: every run is in the arm `with`.
    const runs = Array.isArray(entry.arms?.with) ? entry.arms.with.map(object) : []
    const n = runs.length
    const k = runs.filter((run) => run.passed === true).length
    const { low, high } = wilson(k, n)
    const score = object(entry.aggregates).score
    rows.push({
      name,
      tag,
      k,
      n,
      score: typeof score === 'number' ? score : null,
      wilson: { low, high },
      costUsd: sum(runs.map((run) => run.costUsd)),
      judgeCostUsd: sum(runs.map((run) => run.judgeCostUsd)),
    })
  }
  return rows
}
```

- Что делает: из `aggregate-result.json` вызова берёт только выбранные им case-ы. n — число run-ов в arm `with`,
  k — run-ы с `passed: true`, интервал — из готовой `wilson` (`scripts/eval-outcome-stats.mjs`), цена — сумма
  `costUsd` run-ов и отдельно `judgeCostUsd`.
- Почему здесь: модуль отдельный, потому что `eval-harness.mjs` запускает прогон при импорте (так же вынесен
  `eval-harness-coverage.mjs`). Ticket требует `wilson` «только импорт», critic 2026-11-24 — готовую функцию.
- Без него: «k из n» по-прежнему нигде бы не писалось; один упавший run из трёх не виден за средним баллом.
- Требование: [Что строить, п. 2](../issues/03-история-прогонов-k-из-n-потолок-100.md#что-строить)
- Риски и пробелы test-ов: форма `arms.with[].passed` взята из настоящего отчёта `claude plugin eval` 2.1.289;
  test-ы идут на отчётах stub-а той же формы. Run с `error` считается неудачным run-ом в n.

## 5. Сравнение только с записью тех же моделей

Code: `scripts/eval-history.mjs:115-129` · key lines: 117, 126

```js
export function compareWithEarlier(record, earlier) {
  const same = earlier
    .filter(({ record: other }) => other.models?.agent === record.models.agent && other.models?.judge === record.models.judge && other.startedAt < record.startedAt)
    .sort((a, b) => (a.record.startedAt < b.record.startedAt ? -1 : 1))
  const previous = same.at(-1)
  if (!previous) return { with: null, fell: [] }
  const fell = []
  for (const now of record.cases) {
    const before = previous.record.cases.find((one) => one?.name === now.name)
    if (!before || !(before.n > 0) || !(now.n > 0)) continue
    // k/n < kb/nb, without division.
    if (now.k * before.n < before.k * now.n) fell.push({ name: now.name, before: { k: before.k, n: before.n }, now: { k: now.k, n: now.n } })
  }
  return { with: previous.file, fell }
}
```

- Что делает: берёт последнюю более раннюю запись с теми же моделями агента и judge и называет case-ы, у которых
  доля k/n стала ниже. Записи других моделей не сравниваются: так прогоны до точки отсчёта (Ticket 05) не
  сравниваются с ней.
- Почему здесь: spec, «Решено советником»: «Точка отсчёта — первый полный прогон после смены моделей. Прогоны до неё
  с ней не сравниваются». Модели берутся из `suite.modelOverride` и `suite.judgeModel` отчёта, а не из констант
  `eval-run-env.mjs` (их делит Ticket 02); константы — только запасной вариант.
- Без него: сводка сравнила бы прогон на новом judge со старым, и все оценки «упали» бы из-за смены judge.
- Требование: [Что строить, п. 4](../issues/03-история-прогонов-k-из-n-потолок-100.md#что-строить)
- Риски и пробелы test-ов: сравнение по доле: 2 из 3 против 3 из 4 считается падением, хотя интервалы почти
  совпадают; правило провала с двумя прогонами подряд — Ticket 18, не этот.

- Что делает: после всех вызовов собирает запланированные вызовы с их отчётами. Вызов, который не стартовал
  (потолок, сигнал) или не оставил отчёта, получает `report: null`, и запись помечается `partial`

  case-а; такие case-ы перечислены в поле `missing` и в строке сводки `Not in the reports`. Порог в записи —
  `suite.threshold` отчёта, так что `--threshold` пользователя учтён; 0.8 из `COMMON` — только запасной вариант. Файлы — `evals-history/<время>-<commit>.json` и `.md` рядом с
  проверяемым Harness-ом (`dirname(SOURCE)`): без `HARNESS_DIR` это корень репозитория.
- Почему здесь: Ticket: «частичный run пишет запись с пометкой `partial`»; место вне `harness/evals/` — из Ticket-а
  (там любая папка с `prompt.md` — case, а правка там требует платного `--changed`). Commit берётся в начале прогона
  (`scripts/eval-harness.mjs:426-427`), с пометкой о незакоммиченных правках в `harness/`.
- Без него: частичный прогон выглядел бы как полный, и упавшие на потолке case-ы пропадали бы молча.
- Требование: [Что строить, п. 5](../issues/03-история-прогонов-k-из-n-потолок-100.md#что-строить)
- Риски и пробелы test-ов: запись не меняет exit code; закоммитить её — дело того, кто запускал (Ticket 05). С
  `HARNESS_DIR` запись ложится рядом с копией, а не в этот репозиторий — так test-ы со stub-ом не пишут в checkout.
