## Что происходит

Фриз — движение мыши, обработка которого дольше 50 ms (long task). Его даёт поиск свободного места
при перетаскивании группы или крупного Node-а.

- На каждое движение мыши `onNodeDrag` (`src/renderer/canvas/Canvas.tsx:336-345`) вызывает
  `planDrag` (`src/renderer/canvas/snapping.ts:242`, вызов на `Canvas.tsx:319`). `planDrag` отдаёт в
  `freeShift` всю выделенную группу (`snapping.ts:253`). Той же функцией main поправляет каждую
  операцию Layout (`src/main/layout/store.ts:76`, ADR-0038).
- `freeShift` (`src/shared/layout/free-place.ts:75-111`) берёт кандидатов по 2·k·n на ось, где k —
  размер группы, n — число Layout Node-ов рядом (`:91-98`). Каждую пару кандидатов проверяет
  `isClear` за O(k·n) (`:43-49`). Область поиска — до самого правого obstacle (`:79-82`), поэтому
  «рядом» — почти все Node-ы. Худший случай O(k³·n³).
- Замер `freeShift` на одно движение, сетка из 250 Node-ов (20 колонок, шаг 360×280, разброс ±20 px,
  seed 7; через один 300×220 и 220×120), путь — синусоида поперёк сетки:

  | Что тащат | Среднее | Худшее |
  |---|---|---|
  | один Note 220×120 | 0.5 ms | — |
  | один Card 300×220 | 4.8 ms | 14.5 ms |
  | рамка 1200×900 | 5.5 ms | — |
  | 3 выделенных Note | 18 ms | 53 ms |
  | 10 выделенных Note | 62 ms | 168 ms |
  | 20 выделенных Note | 155 ms | 369 ms |

- Перетаскивание одного Note на той же сетке в приложении держит 120 fps без long tasks: этот путь
  самый дешёвый, рядом с Note есть свободные места.
- Вторая, меньшая цена — рамка Epic-а. Ticket Node-ы — дочерние Node-ы рамки (`parentId`,
  `src/renderer/canvas/sources/epics.ts:256`). При drag рамки каждый получает новый
  `positionAbsolute`, и `memo` по умолчанию не спасает ни Ticket Node (`TicketNode.tsx:152`), ни
  рамку (`EpicFrameNode.tsx:126`). Оба читают только `data` (`TicketNode.tsx:81`,
  `EpicFrameNode.tsx:38`). Вместе с ними на каждое движение заново считаются состояния кнопок
  Run wave и Autopilot (`src/renderer/canvas/actions/gates.ts:32-37` → `readyWave` и `cycles` по
  всем Ticket-ам Epic-а): 44 ms за 3 s drag при 47 Ticket-ах на экране.

## Что делаем

1. **`freeShift` без перебора всех пар.** Перебирать пары (dx, dy) в порядке `better`
   (`free-place.ts:52-59`) — куча или ленивое слияние двух отсортированных списков — до первой
   свободной. `isClear` смотрит obstacles через сеточный индекс, построенный в начале вызова, а не
   все подряд. Результат — бит-в-бит тот же Shift, что сейчас: той же функцией пользуется main
   (ADR-0038).
2. **Ticket Node и рамка не перерисовываются от смены позиции.** `memo` с comparator-ом
   `a.data === b.data` для `TicketNode` и `EpicFrameNode`. Кольцо выделения рисует обёртка React
   Flow (`.react-flow__node.selected`), поэтому prop `selected` им не нужен. Пересчёт Run wave и
   Autopilot уходит вместе с перерисовкой; `gates.ts` не меняется.
3. **e2e-сценарий, на котором текущий код падает:** drag группы из 10 выделенных Note и одного Card
   поверх 250 Layout Node-ов, критерий — ни одного long task.

Чего не делаем и почему (проверено скептиком диагноза):

- Не откладываем `planDrag` до `requestAnimationFrame`. React Flow вызывает `onNodesChange` и
  `onNodeDrag` синхронно в одном mousemove (`@xyflow/system`, `dist/esm/index.mjs:2209` и `:2217`).
  Отложенный расчёт на один кадр показал бы сырую позицию, потом snapped: Node дёргался бы.
- Не трогаем `SelectionToolbar` и второй `setNodes` в `onNodeDrag`: тащимый Node выделен, toolbar
  перерисуется всё равно; второй `setNodes` попадает в тот же batch.
- Не ставим CSS `contain`: React Flow двигает Node через `transform` (`@xyflow/react`,
  `dist/esm/index.js:2361`), layout соседей и так не задет, а `contain: paint` обрезал бы ручки
  NodeResizer на краю Node-а.
- Упрощённую отрисовку Node-ов при zoom < 0.4 не делаем. Она меняет вид отдалённого Canvas.
  **Решено без владельца, подтверждено владельцем 2026-10-12** (вернуться, когда Ticket 14 снова в работе). Если после этого Ticket-а фризы останутся, следующий шаг —
  trace (`devtools.timeline`) на реальном Canvas владельца и новый Ticket.

**Что сделано.**
- `src/shared/layout/free-place.ts`, `freeShift`: те же кандидаты, тот же отбор obstacles рядом и тот же
  порядок `better`. Пары (dx, dy) идут из кучи — по одному списку на каждый dx и сторону от нуля (dy ≥ 0 и
  dy < 0) — до первой свободной, без перебора всех пар. Пара, которую остановил obstacle, пропускает в
  своём списке следующие dy, которые тот же obstacle держит (та же проверка по y, что в `crowds`, бинарный
  поиск). Сравнение с obstacles — через сеточный индекс, построенный в начале вызова. Новый необязательный
  четвёртый параметр `onChecks(pairs)` — сколько пар прямоугольников сравнено; вызовы в `snapping.ts`,
  `store.ts`, `upgrade.ts` и `removeOverlaps` не менялись.
- `TicketNode.tsx`, `EpicFrameNode.tsx`: `memo` с comparator-ом `before.data === after.data`.
- Test эквивалентности дополнен по сравнению с черновиком: каждая 20-я раскладка — ещё две рамки
  (1200×900 и 3000×1400) и Node далеко слева (x = −10 000 000), чтобы пройти путь индекса с крупными
  ячейками и с obstacles на много ячеек; сверка бит-в-бит через `Object.is` (`toEqual` не отличает −0 от 0).

**Mutation testing `freeShift`** (в своём worktree, восстановление из копии): убитые мутанты — lookup
