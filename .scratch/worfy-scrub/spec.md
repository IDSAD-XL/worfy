## Цель

Репозиторий worfy публичный. В текущих файлах осталось много личного: имена других проектов владельца, домашний
путь с именем пользователя, имя владельца в прозе, имя хоста, адрес tailnet и адрес Tailscale, имя личного
аккаунта GitHub с именем работодателя внутри. Epic убирает это из текущего дерева `main` и ставит проверку, которая
не даёт личному вернуться. Историю git Epic не трогает (Q7).

Что не цель: спрятать то, что уже есть в старых commit-ах; убрать аккаунт репозитория там, где он работает как
адрес репозитория или его читает код (Q1).

## Как работает

### Guard личных строк (Ticket-ы 01, 06)

Скрипт Node `scripts/check-personal.mjs` (имя — предложение) читает список tracked-файлов (`git ls-files`) и ищет
личное в путях и в тексте. Два вида правил:

1. **Общие правила** — из `harness/lib/privacy.cjs`, он только читается (`findings`, `mask`): `home-path`, `host`,
   `tailscale-ip`, `email`, `token`. Правило `uuid` выключено: id в fixture-ах не личные. Stand-in-ы fixture-ов
   (Q6) guard узнаёт сам, своим списком в `scripts/`: вымышленный хост, хосты вида `<host>.example.ts.net`, адрес
   quad-100 DNS-сервера самого Tailscale. Домашний путь `/Users/someone` `privacy.cjs` уже считает stand-in-ом.
2. **Хэш-список запрещённых слов.** Файл в `scripts/` хранит SHA-256 от запрещённых слов в нижнем регистре, без
   открытого текста. Guard режет путь и текст на слова (`[^a-z0-9]+` после перевода в нижний регистр), хэширует каждое
   слово и склейки соседних слов через `-` до трёх подряд и сверяет с файлом. Открытый список живёт только на машине
   владельца: это `<Harness home>/user/privacy.json`, тот же личный список, что читает `evidence-check`. Хэш-файл
   строит команда guard-а из этого списка (`--hash-from <file>`), она печатает только хэши.

Вывод guard-а — `путь:строка: правило: маска`, маска — `privacy.mask` (первые два знака и длина). Значение целиком
guard не печатает никогда: лог CI публичный. Картинки и другие двоичные файлы guard проверяет только по имени файла.
Исключения — файл `scripts/` с парами «путь, правило, хэш значения»; каждое исключение нужно, иначе guard называет его
устаревшим (как `plugin-neutral.test.sh`, `:120-121`).

Ticket 01 ставит guard в `pnpm lint` в режиме отчёта (`--report`, exit 0 при находках). Ticket 06 убирает
`--report`: находка — exit 1, `lint-typecheck` в CI красный.

### Чистка (Ticket-ы 02–05)

Каждая строка с личным получает нейтральные слова, смысл не меняется:

- имя другого проекта владельца → «другой проект владельца» или вымышленный проект (в fixture-ах);
- домашний путь с именем пользователя → `~/…`, `<home>/…` или `/Users/someone/…` (в fixture-ах);
- имя владельца в прозе → «владелец»;
- имя хоста и адрес tailnet → «Mac владельца», «ПК», `<host>`, `<tailnet>`; в fixture-ах — stand-in-ы Q6;
- аккаунт репозитория в прозе → «аккаунт репозитория» (Q1); в URL и в коде — остаётся;
- имя личного аккаунта GitHub → «личный аккаунт GitHub».

ADR — по Q2. Имена файлов с личным переименовываются, ссылки на них правятся. Картинки evidence, где личное видно на
самом изображении, агент Ticket-а 02 открывает и смотрит; такую картинку он убирает из дерева, строка evidence
остаётся текстом с пометкой «картинка убрана: личное на изображении».

### Перенос старого Harness (Ticket 04)

`PERSONAL_BIN` становится списком хэшей имён (Q5). Перенос сравнивает SHA-256 имени файла из `~/.claude/bin` в нижнем
регистре со списком: поведение для существующих пользователей то же. Функция сравнения берёт список параметром; test-ы
передают хэши вымышленных имён fixture-а. Что список из кода узнаёт настоящие имена, проверяет один ручной шаг на машине
владельца (имена — из его `privacy.json`), результат — в «Итог» 04.

## Решено без владельца

1. **Guard переиспользует `privacy.cjs`**, а не пишет свои регулярные выражения: одно правило на Harness и на
   репозиторий. `privacy.cjs` Ticket 01 не меняет (иначе PR платформенный); stand-in-ы — в `scripts/`.
2. **Аккаунт репозитория не в хэш-списке.** Он публичен как адрес репозитория и нужен коду. Замену в прозе делают
   Ticket-ы 02–05 по отчёту поиска, guard её не проверяет.
3. **Вывод — только маска** (`privacy.mask`), и в режиме отчёта тоже.
4. **Открытый список — `<Harness home>/user/privacy.json`**, в том формате, который уже читает `evidence-check`; на Mac его пишет orchestrator по списку разведки, владелец просматривает.
5. **Строка о замене в ADR — в разделе `## Amendments`** в конце файла (раздел создаётся, если его нет): так требует
   `rules-adr.md`.
6. **Картинки с личным на изображении убираются из текущего дерева**, не перерисовываются: в истории они всё равно есть.
7. **Тексты в коде и plugin-е — английские** (ADR-0074), документы — русские.

## Риски

1. **Замена ломает test-ы, которые сверяют строку.** Test ждёт путь или имя из fixture-а. Ticket 04 и 05 меняют test
   и fixture вместе; полный `pnpm test` в «Готово, когда».
2. **Guard ловит обычные слова.** Короткое имя проекта может совпасть со словом английского. Защита — исключения с
   хэшем значения и склейки только соседних слов; ложная находка в отчёте Ticket-а 01 — повод убрать слово из списка,
   а не плодить исключения.
3. **Правка ADR против правила неизменности.** Q2: меняются только личные слова, смысл не меняется, строка в
   `## Amendments` говорит об этом (как исключение ADR-0017).
4. **Хэш короткого слова подбирается перебором.** Принято: цель — не дать новым следам попасть в репозиторий, а не
   спрятать историю. Старые commit-ы и так содержат эти строки (Q7).
8. **Пустой отчёт guard-а — не «личного нет».** Guard сверяет целые слова и склейки до трёх, а `privacy.cjs` ищет
   подстроку: имя, склеенное с другим словом без разделителя, или имя во множественном числе guard пропустит.
   Ticket-ы 02–05 ищут ещё и подстрокой по открытому списку на машине владельца (`evidence-check` его читает), а
   не только по отчёту guard-а (возражение 3 критика, Q10).
5. **Перенос перестаёт узнавать личные инструменты.** Ошибка в хэше — и перенос удаляет личный скрипт владельца.
   Защита — ручной шаг Ticket-а 04 на машине владельца, до merge.
6. **Личное на картинках.** Guard видит только имя файла. Ticket 02 открывает каждую картинку из Ticket-ов, где речь
   о других проектах.
7. **Новые следы во время Wave 2.** Чужие PR-ы могут добавить личное, пока guard только сообщает. Ticket 06 начинает
   с нового отчёта по свежему `main`.

## Вопросы владельцу

Каждый вопрос записан так, что ответ «да» принимает рекомендацию.

1. **Q1. Охват.** Убираем всё из таблицы «Что нашла разведка»; аккаунт репозитория остаётся там, где он работает
   (URL, код), в прозе меняется на «аккаунт репозитория». **Рекомендую: да.**
2. **Q2. ADR.** В ADR меняются только личные строки, на нейтральные слова, смысл не меняется; в конце каждого
   тронутого ADR — одна датированная строка в `## Amendments`: «2026-11-xx: личные имена заменены нейтральными
   словами (Epic worfy-scrub), смысл не менялся». **Рекомендую: да.**
3. **Q3. Guard от новых следов.** Проверка всего репозитория в `pnpm lint` и CI без открытого списка: SHA-256 слов
   в нижнем регистре плюс общие правила (домашний путь с именем пользователя, email вне доменов example, хосты
   tailnet, адреса Tailscale); находка по хэшу — exit 1. Список `plugin-neutral.test.sh` переходит на те же хэши.
   Открытый список — только на машине владельца. **Рекомендую: да.**
4. **Q4. Автор plugin-а.** Поле `author` в `harness/.claude-plugin/plugin.json` — имя владельца, сознательная
   публичная подпись. Заменить на имя аккаунта репозитория, чтобы личного не осталось? **Рекомендую: да,
   заменить.** Ответ «нет» оставляет имя и записывает его в исключения guard-а.
5. **Q5. `PERSONAL_BIN` переноса.** Поведение остаётся (личные инструменты существующих пользователей перенос
   узнаёт и не удаляет), но сравнение — по хэшам, без открытых имён. **Рекомендую: да.** Другой путь — убрать
   список совсем, если обе машины владельца перенос уже прошли; тогда новый пользователь со скриптами под теми же
   именами их потеряет.
6. **Q6. Вымышленные имена в fixture-ах.** Вымышленный проект, `/Users/someone` (уже есть в fixture-ах), хост
   `someones-mac`, хосты вида `<host>.example.ts.net`. **Рекомендую: да.**
7. **Q7. История git не переписывается**, как сказал владелец; старые commit-ы по-прежнему содержат эти строки, и
   spec это фиксирует. **Рекомендую: да.**
8. **Q8. Возражение 1 критика.** На каждую переименованную картинку Ticket 02 добавляет строку scrub после того, как
   агент её посмотрел. **Рекомендую: да.**
9. **Q9. Возражение 2 критика.** Ticket 04 оставляет проверку `harness/` не слабее нынешней: аккаунт репозитория — в
   отдельном хэш-списке только для plugin-а, подстрока сохраняется, проверка работает из установленного plugin-а.
   **Рекомендую: да.**
10. **Q10. Возражение 3 критика.** Ticket 01 режет записи списка тем же правилом, что и текст, отказывает на записи,
    которую сверка по словам не поймает; риск 8 записан. **Рекомендую: да.**

**Ответ владельца 2026-11-08: «все да».** Q1–Q10 приняты как рекомендовано; Q4 — `author` заменяется именем аккаунта
