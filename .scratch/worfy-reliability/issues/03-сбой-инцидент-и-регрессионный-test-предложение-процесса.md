## Что происходит

- **Уроки** лежат в `docs/lessons/` по темам (`README.md`: `process.md`, `agents.md`,
  `ci-merge.md`, `testing.md`). README говорит, когда писать урок, но не связывает урок с test-ом:
  урок может описать сбой, который потом ничем не проверяется.
- **Skill `retro`** Harness (`harness/skills/retro/SKILL.md`) записывает урок туда, куда указывает
  поле Profile `lessons` (у worfy — `repo:docs/lessons`). Он не классифицирует причину сбоя.
- **Eval-кейсы Harness** — Ticket-ы 27–29 Epic-а worfy-harness открыты: 27 (платная часть eval) ждёт
  28, 29 — после 27 и 28. Проверить правило prompt-а прогоном eval сейчас нельзя.
- **Причины сбоев бывают разные**, а путь у всех один — урок или правило. Примеры из Project-а:
  - временный сбой машины — `fseventsd` краснил gate full 2026-10-12 (`HANDOFF.md`, «Риски и долги»);
  - регрессия SDK поставщика — повтор вызова tool в Claude Code 2.1.296 (Ticket 01);
  - слабая fixture, нарушение ADR, дефект кода, ошибка правила Harness или prompt-а.

## Что делаем

Документ-предложение и решение владельца. Код, Harness и Profile не меняются.

1. **Классы инцидента**, у каждого — признак и куда идёт вывод:
   - временный сбой (`fseventsd`, сеть, заблокированный экран) — запись в «Риски и долги» или урок
     «как распознать», без нового правила;
   - регрессия SDK поставщика — правило версий (как в Ticket-е 01) и fixture новой версии;
   - слабая fixture — test с fixture, которая воспроизводит сбой;
   - нарушение ADR — test или проверка Gate на это ADR;
   - дефект кода — регрессионный test: красный до правки, зелёный после;
   - правило Harness или prompt-а — eval-кейс (когда 27–29 закрыты) или правка `harness/` через PR.
2. **Шаги процесса:** сбой → запись инцидента со ссылками (PR, «Итог», строка журнала, коммит) →
   дедупликация по корневой причине → класс → детерминированный test (красный до, зелёный после)
   или явное «урока нет» с причиной.
3. **Что процесс не поощряет никогда:** выключить или пометить skip flaky test вместо разбора;
   перевести Ticket из `blocked` в `done` без доказательства; обойти Gate; добавить правило prompt-а
   без проверки, что оно что-то меняет.
4. **Проверка на прошлом.** Прогнать процесс вручную по 3–5 прошлым сбоям из «Итог» и
   `docs/lessons/` и показать, какой класс и какой test вышел бы у каждого.
5. **Куда встроить**, если владелец согласится: `docs/lessons/README.md`, skill `retro`, правило
   Orchestrator-а — варианты с ценой каждого. Сами правки — отдельными Ticket-ами после решения:
   Harness и Profile меняются только через PR в `harness/`.

## Итог

2026-10-15. Документ — [docs/research/2026-10-15-сбой-инцидент-test.md](../../../docs/research/2026-10-15-сбой-инцидент-test.md).
`harness/`, Profile и `src/` не менялись.

**Что предложено.** Сбой → запись «Инцидент» в «Итог» Ticket-а (симптом, ссылки, воспроизведение,
корневая причина, дубликат) → дедупликация по корневой причине → один из шести классов с
подтверждением → детерминированная проверка (красная до, зелёная после; для нестабильного test-а —
число красных из N повторов до и после) или «урока нет: <причина>». Урок получает строку `Проверка:`.

**Разбор пяти прошлых сбоев** (раздел «Проверка на прошлом»): `fseventsd`, Claude Code 2.1.296,
`processState`, `rm -rf` с переменной в пути, e2e «long names». В трёх случаях test уже был или
запланирован; процесс добавил бы связь «урок → test» и числа «после». В случае `rm -rf` текстовое
правило нарушалось ещё четыре раза после записи; процесс заменил бы его отказом hook-а и test-ом hook-а.
Из 33 уроков `docs/lessons/` на файл test-а указывают 2.

**Варианты встраивания с ценой:** В1 — `docs/lessons/README.md`; В2 — `scripts/check-lessons.mjs` с
unit test; В3 — skill `retro`; В4 — правило Orchestrator-а. Рекомендация — В1 и В2 сначала, В3 следом,
В4 только при потере инцидентов после них.

**Решения владельца** (раздел «Решения владельца» документа):

1. Принять ли процесс и шесть классов.
2. Место записи инцидента: «Итог» Ticket-а или отдельный файл в `docs/`.
3. Какие варианты встраивания (В1–В4) брать и в каком порядке.
4. `Проверка:` — только новым урокам или всем 33.
5. Ticket Harness на отказ hook-а для `rm -rf` с маской или переменной.
6. Порог для нестабильного test-а: N повторов и нагрузка.
7. Требовать ли для «временного сбоя» зелёный повтор того же commit-а после лечения.

При «да» — follow-up Ticket-ы из раздела «Follow-up Ticket-ы» документа (шесть кандидатов).

PR только с документами: CI на нём не запускается (`rules.md` Profile-а worfy), вместо зелёного Linux
CI — gate fast с кодом 0 и комментарий в PR.

**Решение владельца 2026-10-16:** процесс принят. По пунктам:

1. Шесть классов — без изменений.
2. Инцидент записывается подразделом «Инцидент» в «Итог» Ticket-а, где случился сбой. Сбой без
   Ticket-а записывается в «Итог» Ticket-а, который чинит его последствия.
3. Встраивание: сначала В1 и В2, затем В3; В4 — только если инциденты продолжают теряться.
4. Строка `Проверка:` дописывается всем существующим урокам вместе с В2 (в отчёте их 33; на main
   `274c7eb` — 34: урок про SDK из Ticket-а 01 добавлен позже). Урок без проверки получает явное
   «проверки нет: <почему>».
5. Кандидат hook-а на `rm -rf` с маской или переменной уже покрыт `worfy-harness` 48 — нового
   Ticket-а нет.
6. Flaky test считается вылеченным после 10 повторов без единого красного под параллельной нагрузкой
   полного `pnpm test` (как в gate full). Прогоны на тихой машине не считаются.
7. Класс «временный сбой машины» ставится только после зелёного повтора того же commit-а, когда
   машину вылечили.
