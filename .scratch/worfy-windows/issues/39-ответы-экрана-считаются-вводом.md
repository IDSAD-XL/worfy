### (а) Автоматический ответ забирает размер pty

- **Правило.** ADR-0053, решение 5: размер pty задаёт экран, где в Terminal последним печатали или
  кликали. `touch()` делает экран владельцем размера (`pty.ts:775-782`) при любых данных.
- **Запущено на Mac**, два reviewer-а: настоящий xterm.js 6.0.0, настоящий `TerminalRegistry`,
  подменный pty; exit code 0. Реестр main и реестр ветки PR #280 дают одно и то же.
  - В kept output — `ESC[c` и `ESC[?1004h`. Первый экран 80×24; второй, 120×40, только открывает
    Terminal. Сразу после `open` размер прежний; когда его xterm.js ответил — `resize(120, 40)`.
  - Хватает одного `ESC[?1004h` в выводе: второй экран шлёт `ESC[O`. На `darwin` то же дают
    `ESC[?1004h … ESC[?1004l` и `ESC[6n`.
  - Вывод без запросов: второй экран не шлёт ничего, `resize` нет. После 300 KiB вывода запросов в
    kept output уже нет — тоже ничего.
- **Test-ы этого не видят.** Правило закреплено на подменном pty, который ничего не печатает
  (`test/contract/terminal.test.ts:735-737`, `:768-770`; `SizePty.onData` — `:703`). Ни один
  test-файл не запускает xterm.js.
- **Эффект узкий:** нужны два экрана на одном Terminal; размер возвращается с первым нажатием или
  кликом на первом экране.
- **Windows на main.** В логе чистого runner-а GitHub (Windows Server 2025, 10.0.26100, код main)
  вывод `powershell.exe` начинается с `ESC[?9001h ESC[?1004h`: консоль системы там сама включает
  focus reports. На модели с такими байтами второй экран забирает размер. На ПК владельца старт
  консоли системы не мерили — ревью PR #280 просит этот замер тем же push-ем.

### (б) View, смонтированный заново, отвечает ещё раз — в ввод оболочки

- **Прочитано.** Новый xterm.js создаётся при каждом монтировании view Terminal: Node ушёл из viewport
  и вернулся (`src/renderer/canvas/Canvas.tsx:532`, `onlyRenderVisibleElements`), focus mode, reload
  окна, смена Project-а, второй экран. View пишет kept output в xterm.js как есть
  (`TerminalNode.tsx:186`) и в том же ходе ставит `attached = true` (`:193`). xterm.js разбирает текст
  позже — его ответы уже уходят в `terminal.input`. `ReplayBuffer` (`pty.ts:104`) запросы не вырезает: он срезает только начало
  сохранённого вывода, если оно попало внутрь OSC-последовательности (`pty.ts:100-102`, `:124`).
- **Запущено на Mac** (та же модель, exit code 0; с реестром main — те же строки). Подменный pty
  печатал старт консоли из пакета node-pty: `ESC[1t ESC[c ESC[?1004h ESC[?9001h`. Второй view и
  view, смонтированный заново, каждый записали в pty `ESC[?1;2c` и `ESC[O`, пока в оболочке шла
  программа. После более чем 256 KB вывода новый view не шлёт ничего.
- **macOS.** Настоящие `/bin/zsh` и `/bin/sh` при старте ничего не запрашивают (запущено). Запросы
  приходят от программ: vim, pager.
- **Windows с PR #280** (оболочки на консоли из пакета node-pty). Замер исполнителя на ПК: OpenConsole
  1.23 передаёт запрос `ESC[c` программы дальше, в терминал. Запросы программ доходят до экранов и там.
- **Что чинит сам PR #280.** Main отвечает на стартовый запрос консоли и убирает его из живого
  вывода и из kept output. До этой правки исполнитель видел на ПК в packaged-сборке: после reload
  prompt читается `PS …> [?1;2c`, следующая команда — ParserError, программа, ждущая одну клавишу,
  получает ESC. Этот Ticket — про остальное: запросы программ и focus reports.
- **Не запускалось ни на одной системе:** что увидит программа от повторного ответа.

## Что делаем

1. **Автоматические ответы экрана не считаются вводом.** До pty они доходят — программа, включившая
   focus reports, их ждёт, — но мимо `touch()`. Варианты ревью: `write` не зовёт `touch()`, когда
   данные — только ответ терминала (`ESC[?…c`, `ESC[I`, `ESC[O`, `ESC[…R`); либо ответы помечает view.
2. **Ответы, рождённые разбором replay, отбрасываются.** View ничего не шлёт, пока xterm.js
   разбирает kept output: `attached = true` — в callback вызова `terminal.write(replay, …)`.
3. **Решить про живой запрос при нескольких view.** Прочитано, не запускалось: каждый подключённый
   view пишет живой вывод в свой xterm.js и шлёт его `onData` (`TerminalNode.tsx:114-117`,
   `:132-134`). На один запрос программы уйдёт столько ответов, сколько view. Решение — в «Итог».

### Пункт 3 «Что делаем»: живой запрос при нескольких view — решение

Оставлено как есть: каждый подключённый view отвечает, на один запрос уходит столько ответов,
сколько view. Причина: main не знает, на каком экране view смонтирован сейчас — подписка живёт у
клиента (окна), а view снимается, когда Node ушёл из viewport. Если отвечать будет один экран
(например, владелец размера), а у него view снят, программа не получит ответа совсем; vim и другие
ждут ответа на `ESC[c`/`ESC[6n`. Лишний ответ — то, что было и до правки. Теперь ответы помечены
(`reply`), и дальше можно сузить: в focus mode отвечает только view, задающий размер в своём окне
(`isLastView`), — оба view одного окна точно смонтированы. Это отдельный Ticket, если нужно. Что
программа делает с повторным ответом — не запускалось.

Изменено во втором круге для `ESC[6n`: на запрос позиции курсора отвечает только main, ответы view
на него main отбрасывает — один ответ при любом числе view (раздел «Круг 2» ниже). Для остальных
запросов (`ESC[c` не на Windows, цвета, режимы) решение выше остаётся.
