## Что происходит

- **Не про Windows.** Дефект есть на main и виден на macOS. Ticket лежит в этом Epic-е, потому что
  это тот же класс, что в Ticket-е 35 (junction на том по GUID на Windows), и чинить их разумно
  одним правилом.
- **Как worfy удаляет папку вне Windows.** `removeTree` — это один вызов
  `rmSync(path, { recursive: true, force: true })` (`src/main/storage/remove.ts:148`). Тот же вызов —
  в трёх копиях функции для скриптов: `scripts/remove-tree.mjs:32`, `scripts/install-stable.mjs` и
  текст скрипта восстановления в `src/main/harness/migrate/restore.ts:115-125`. Обход своими руками
  идёт только на Windows.
- **Точка монтирования — не ссылка.** Том, примонтированный на папку, `lstat` называет папкой.
  Список родителя с `withFileTypes` — тоже папкой. `realpath` отвечает её же путём. Отличается одно:
  `dev` у неё свой, не как у родителя (в замере 16777245 против 16777233; `ino` 2).
- **Замер.** macOS 26.6.1 (Darwin 25.6.0); образ диска 8 MB, HFS+, свой, в пробной папке;
  подключён `hdiutil attach -nobrowse -mountpoint <проба>/card/vol`; на томе три файла-метки.
  `removeTree` — из `scripts/remove-tree.mjs`, main `2a6dfee`. Системный Node 24.19.0 и Node 24.21.0
  из Electron 44.5.1 ответили одинаково.

  | Шаг | Ответ | Файлы-метки на томе |
  |---|---|---|
  | `rmdirSync` точки монтирования, без обхода | `EBUSY`, и для пустого тома тоже | на месте |
  | `renameSync` самой точки монтирования | ok, том виден под новым именем | на месте |
  | `renameSync` папки, в которой она лежит | ok, том виден под новым путём | на месте |
  | `removeTree(папка, в которой лежит точка монтирования)` | бросает `ENOTEMPTY`; папка и том остались | **удалены, все три** |
  | `removeTree(сама точка монтирования)` | бросает «Resource busy», поле `code` пустое; том остался | **удалены, все три** |

- **Что это значит для Trash.** `put` — это `renameSync` папки Card-а (`src/main/layout/trash.ts:208`):
  по замеру он проходит в обоих случаях. `purge` (`:281-290`) зовёт `removeTree` для записи Trash
  старше трёх дней (`TRASH_KEEP_MS`). Идёт он только при старте приложения
  (`src/main/ipc/trash.ts:40-48`). По замеру такой вызов стирает файлы тома и заканчивается ошибкой;
  первая ошибка обрывает цикл `purge`, и более старые записи после неё не стираются. Сам Trash на
  macOS от начала до конца не запускался: измерены его два вызова по отдельности.
- **Кто ещё зовёт `removeTree` в main:** `src/main/harness/migrate/apply.ts`,
  `src/main/mcp/canvas-server.ts`, `src/main/terminal/shell-integration.ts`; скрипт восстановления
  зовёт свою копию (`restore.ts:256`, `:326`). Какие из них могут получить путь с томом внутри, не
  разбиралось.
- **Насколько это вероятно.** Нужен том, примонтированный руками внутрь папки, которую worfy потом
  удаляет, — например, в папку Card-а. Так же ведёт себя `rm -rf`: границу тома он переходит, если
  не дан ключ `-x`. Но worfy удаляет сам, при первом запуске после трёх дней и без вопроса.

## Что делаем

1. **Дождаться правки Ticket-а 35.** Если она идёт по `dev` и для всех систем — этот Ticket
   закрывается её PR, после повтора замера на Mac. Если она только для Windows — пункты 2–4.
2. **Сначала падающий test** на подменной файловой системе (`RemoveFs`). До него — правка самой
   подмены: `RemoveFs.lstatSync` отдаёт ещё и `dev` (`remove.ts:46`, сейчас только `isDirectory`),
   запись модели в `test/unit/remove-tree.test.ts` получает `dev` (`:270`, `:311`), копиям функции
   передаётся ещё `dirname` (`:629`). `rmSync` модели стирает всё по префиксу пути (`:336`) — как
   настоящий по замеру. Сам случай: папка, у ребёнка которой `dev` другой; удаление не читает список
   такого ребёнка и не удаляет в нём ничего.
3. **Правило.** Удаление не входит в папку, `dev` которой отличается от `dev` папки, где она
   найдена; для пути, данного `removeTree`, сравнение идёт с его родителем. Живую точку монтирования
   на macOS удалить нельзя (`EBUSY`), поэтому удаление отвечает понятной ошибкой и том не трогает.
4. **Решить про путь вне Windows.** Сейчас там один `rmSync`. Чтобы проверять `dev`, нужен либо свой
   обход на всех системах (меняется путь каждого удаления на macOS), либо проверка перед `rmSync`
   (один проход по дереву только ради `dev`). Выбор и его цена — в «Итог».
5. **Trash.** Решить и записать в «Итог»: либо `put` отказывает для папки Card-а, которая сама точка
   монтирования или держит её внутри, либо `purge` пропускает такую запись и идёт к следующим
   (сейчас первая ошибка `removeTree` обрывает цикл, `trash.ts:284-288`). Чтобы проверить это без
   настоящего тома, `TrashStore` получает подменную файловую систему через `TrashDeps` (сейчас её
   там нет, `trash.ts:63-75`; `renameSync` взят прямо из `node:fs`, `:21`).

## Риски

- **`dev` — число, которое система даёт тому при подключении.** Два тома с одним `dev` в одной
  папке не встречаются, но правило стоит на одном поле. Вторую проверку на macOS взять неоткуда:
  других отличий замер не показал.
- **Свой обход на macOS — это новый путь для каждого удаления.** `rmSync` там до сих пор не
  подводил; обход, написанный для Windows, на macOS запускался только в test-ах.
