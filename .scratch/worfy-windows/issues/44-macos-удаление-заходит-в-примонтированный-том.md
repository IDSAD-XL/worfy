## Что происходит

- **Не про Windows.** Дефект есть на main и виден на macOS. Ticket лежит в этом Epic-е, потому что
  это тот же класс, что в Ticket-е 35 (junction на том по GUID на Windows; исправлен PR #287 только
  для Windows), и правило для macOS — то же сравнение `dev`.
- **Как worfy удаляет папку вне Windows.** `removeTree` — это один вызов
  `rmSync(path, { recursive: true, force: true })` (`src/main/storage/remove.ts:224`). Тот же вызов —
  в трёх копиях функции для скриптов: `scripts/remove-tree.mjs:40`, `scripts/install-stable.mjs:339`
  и текст скрипта восстановления в `src/main/harness/migrate/restore.ts:118-129`. Свой обход дерева
  идёт только на Windows. Скрипт установки Stable copy вне Windows копию не зовёт: в `installStable`
  стоит свой вызов `rmSync` с `recursive` и `force` (`scripts/install-stable.mjs:467`).
- **Точка монтирования — не ссылка.** Том, примонтированный на папку, `lstat` называет папкой.
  Список родителя с `withFileTypes` — тоже папкой. `realpath` отвечает её же путём. Отличается одно:
  `dev` у неё свой, не как у родителя (в замере 16777245 против 16777233; `ino` 2).
- **Замер.** macOS 26.6.1 (Darwin 25.6.0); образ диска 8 MB, HFS+, свой, в пробной папке;
  подключён `hdiutil attach -nobrowse -mountpoint <проба>/card/vol`; на томе три файла-метки.
  `removeTree` — из `scripts/remove-tree.mjs`, main `2a6dfee`. Системный Node 24.19.0 и Node 24.21.0
  из Electron 44.5.1 ответили одинаково.

  | Шаг | Ответ | Файлы-метки на томе |
  |---|---|---|
  | `rmdirSync` точки монтирования, без обхода | `EBUSY`, и для пустого тома тоже | на месте |
  | `renameSync` самой точки монтирования | ok, том виден под новым именем | на месте |
  | `renameSync` папки, в которой она лежит | ok, том виден под новым путём | на месте |
  | `removeTree(папка, в которой лежит точка монтирования)` | бросает `ENOTEMPTY`; папка и том остались | **удалены, все три** |
  | `removeTree(сама точка монтирования)` | бросает «Resource busy», поле `code` пустое; том остался | **удалены, все три** |

- **Что это значит для Trash.** `put` — это `renameSync` папки Card-а (`src/main/layout/trash.ts:208`):
  по замеру он проходит в обоих случаях. `purge` (`:281-290`) зовёт `removeTree` для записи Trash
  старше трёх дней (`TRASH_KEEP_MS`). Идёт он только при старте приложения
  (`src/main/ipc/trash.ts:40-48`). По замеру такой вызов стирает файлы тома и заканчивается ошибкой;
  первая ошибка обрывает цикл `purge`, и более старые записи после неё не стираются. Сам Trash на
  macOS от начала до конца не запускался: измерены его два вызова по отдельности.
- **Кто ещё зовёт `removeTree` в main:** `src/main/harness/migrate/apply.ts`,
  `src/main/mcp/canvas-server.ts`, `src/main/terminal/shell-integration.ts`; скрипт восстановления
  зовёт свою копию (`restore.ts:288`, `:358`). Какие из них могут получить путь с томом внутри, не
  разбиралось.
- **Насколько это вероятно.** Нужен том, примонтированный руками внутрь папки, которую worfy потом
  удаляет, — например, в папку Card-а. Так же ведёт себя `rm -rf`: границу тома он переходит, если
  не дан ключ `-x`. Но worfy удаляет сам, при первом запуске после трёх дней и без вопроса.

## Что делаем

1. **Правка Ticket-а 35 влита (PR #287) и сделана только для Windows: пункты 2–5 остаются.** На
   Windows обход теперь перечисляет папку по двум правилам. Первое: папку сначала просят уйти одним
   `rmdirSync`, и перечисляется она только после ответа `ENOTEMPTY` (`remove.ts:145-159`, `:193`).
   Второе: папка, `dev` которой не равен `dev` папки, где она лежит, не перечисляется никогда
   (`:187-192`). Вне Windows `removeTree` — по-прежнему один `rmSync` (`:223-226`), поэтому замер из
   «Что происходит» верен и после PR #287. По его таблице `rmdirSync` точки монтирования отвечает
   `EBUSY`, а не `ENOTEMPTY`. Прочитано по коду: точка монтирования из замера — папка с другим
   `dev`, и обход вышел бы по второму правилу (`:187-191`): не перечисляет, повторяет `rmdirSync`,
   пока у удаления есть ожидания (пять на весь вызов), и бросает `EBUSY`. При равном `dev` то же
   сделал бы первый `rmdirSync` (`:150-156`). На macOS с настоящим томом обход не запускался.
2. **Сначала падающий test** на подменной файловой системе (`RemoveFs`). Часть подмены уже есть
   после PR #287: `RemoveFs.lstatSync` отдаёт `isDirectory` и `dev` (`remove.ts:68`); модель в
   `test/unit/remove-tree.test.ts` отдаёт `dev` по пути — всё под `/vol` считается другим томом
   (`:320`, `:329`); в модели есть запись `mount` (`:276`) и деревья с ней (`:383-392`). Родителя
   пути обход спрашивает через `join(path, '..')` и берёт его том, только когда `lstat` называет
   родителя папкой (`remove.ts:181-182`). Копии уже получают `join` (`remove-tree.test.ts:851-853`),
   `dirname` им не нужен. Чего для macOS нет (строки ниже — тоже `remove-tree.test.ts`):
   - запись `mount` описывает junction Windows: `rmdir` модели снимает её как ссылку (`:346-352`).
     Точка монтирования macOS по замеру отвечает на `rmdir` `EBUSY`;
   - `rmSync` модели стирает записи по префиксу пути (`:359`) и за `mount` не идёт: файлы тома
     записаны под `/vol` и остаются. Настоящий `rmSync` на macOS по замеру их удаляет. Test PR #287
     «off Windows nothing of this runs» (`:591-597`) сверяет только список вызовов;
   - нужна запись модели для точки монтирования macOS: `lstat` называет её папкой с другим `dev`,
     её `rmdir` отвечает `EBUSY`, `rmSync` папки-родителя удаляет файлы за ней и бросает `ENOTEMPTY`
     — как в таблице замера.

   Сам случай: папка, у ребёнка которой `dev` другой; удаление не читает список такого ребёнка и не
   удаляет в нём ничего.
3. **Правило.** Удаление не входит в папку, `dev` которой отличается от `dev` папки, где она
   найдена; для пути, данного `removeTree`, сравнение идёт с его родителем. Живую точку монтирования
   на macOS удалить нельзя (`EBUSY`), поэтому удаление отвечает понятной ошибкой и том не трогает.
4. **Решить про путь вне Windows.** Сейчас там один `rmSync`. Чтобы проверять `dev`, нужен либо свой
   обход на всех системах (меняется путь каждого удаления на macOS), либо проверка перед `rmSync`
   (один проход по дереву только ради `dev`). Выбор и его цена — в «Итог». Отдельно решить про
   `rmSync` в `installStable` (`scripts/install-stable.mjs:467`): вне Windows он идёт мимо копии
   `removeTree`, и правило его не коснётся. Либо правило приходит и туда, либо строка уходит в «Вне
   скоупа» с причиной.
5. **Trash.** Решить и записать в «Итог»: либо `put` отказывает для папки Card-а, которая сама точка
   монтирования или держит её внутри, либо `purge` пропускает такую запись и идёт к следующим
   (сейчас первая ошибка `removeTree` обрывает цикл, `trash.ts:284-288`). Чтобы проверить это без
   настоящего тома, `TrashStore` получает подменную файловую систему через `TrashDeps` (сейчас её
   там нет, `trash.ts:63-75`; `renameSync` взят прямо из `node:fs`, `:21`).

## Риски

- **`dev` — число, которое система даёт тому при подключении.** Два тома с одним `dev` в одной
  папке не встречаются, но правило стоит на одном поле. Вторая проверка есть только у своего обхода
  (первый вариант пункта 4): первый `rmdir`, как на Windows после PR #287. По таблице замера точка
  монтирования отвечает на него `EBUSY`, и обход её не перечисляет. У проверки перед `rmSync`
  (второй вариант пункта 4) второй проверки нет.
- **Свой обход на macOS — это новый путь для каждого удаления.** `rmSync` там до сих пор не
  подводил; обход, написанный для Windows, на macOS запускался только в test-ах.
