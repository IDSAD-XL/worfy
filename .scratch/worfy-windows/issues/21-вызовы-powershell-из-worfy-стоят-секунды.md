  первом `agentEnv()` (`:485`), два процесса сразу (`:437`). Новый ли это текст после перезапуска

- **Не на main, сверить при claim.** PR #239 перевёл свой helper на `-Command`, общую функцию не

## Что делаем

1. **Измерить** на ПК внутри приложения (Node из Electron) каждый вызов: новый текст, повтор,
   повтор через 30 s, первый вызов после перезапуска worfy.
2. **Искать причину.** Кандидаты, не факты: AMSI или Defender проверяет новый скрипт; script-block

3. **Сделать каждый вызов дешёвым**; способ выбирает исполнитель, выбор — в «Итог». Варианты:

### Причина

**Дорого стоит не флаг, а декодирование base64 внутри PowerShell — и только когда предок процесса Electron.**

- Скрипт, который PowerShell должен раскодировать из base64, стоит примерно на секунду дольше при первом запуске своего текста в данном процессе-родителе. Это и `-EncodedCommand` (в любом написании: `-enc`, `-e`), и обычный текст через `-Command`, если в нём есть `FromBase64String`: 1,19–1,28 s против 0,25–0,3 s. Самый первый такой вызов процесса стоит около 2,2 s.
- Тот же текст повторно в том же процессе — 0,25–0,3 s. В новом процессе первый вызов снова дорогой: «знакомость» текста не переживает перезапуск worfy.
- Текст через `-Command` без декодирования — 0,25–0,32 s всегда, новый он или нет. Кодирование вывода в base64 (`ToBase64String`) бесплатно.
- Из системного Node разницы нет ни в одном случае — ни под 22.13.0, ни под 24.21.0. Версия Node не причина: тот же Node 24.21.0 внутри Electron даёт 1,3 s, вне Electron — 0,4–0,5 s.

**Исключено замером** (проба из Node в Electron, по три вызова с новым текстом):

| Что проверяли | Результат |
|---|---|
| Написание флага: `-EncodedCommand`, `-enc`, `-e` | 1,18–1,25 s все три |
| Окружение дочернего процесса: только пять переменных | 1,19–1,23 s — не оно |
| Скрытое окно (`windowsHide: false`) | 1,36–1,40 s — не оно |
| `cmd.exe` как прямой родитель PowerShell | 2,21–2,27 s — хуже; решает предок, не прямой родитель |
| Сам длинный base64-аргумент: `cmd /c echo -EncodedCommand <base64>` | 60–66 ms — не он |
| Скрипт через stdin (`-Command -`) | 0,22–0,24 s |
| Политики журналирования PowerShell (ScriptBlockLogging, Transcription, ModuleLogging) | ключей в реестре нет |

**Не доказано, только кандидат:** проверка Defender. На ПК включены защита в реальном времени и поведенческий монитор, облачная проверка включена (MAPS 2); `electron.exe` из `node_modules` не подписан, `node.exe` подписан OpenJS Foundation. Отключить Defender для проверки нельзя — нужны права администратора. Windows 11 Pro 10.0.26200, Defender 4.18.26080.4, Smart App Control выключен.
### Что сделано — вариант (а) вместе с (б)

- **`powershellScriptCommand`** (`src/main/agent/env.ts`) отдаёт скрипт текстом через `-Command`. Данные идут третьим параметром и попадают в переменные окружения дочернего процесса: окружение worfy плюс данные. Скрипт читает их как `$env:ИМЯ`. Флаги, timeout 10 s и `windowsHide` — как были.
- **Реестр:** `REGISTRY_SCRIPT` — один текст для любого ключа. Hive и подключ приходят в `WORFY_REGISTRY_HIVE` и `WORFY_REGISTRY_SUBKEY`; скрипт ничего не декодирует и ничего не вклеивает. Hive проверяется дважды: `registryVars` принимает только HKCU и HKLM, скрипт — только `CurrentUser` и `LocalMachine`. Вывод по-прежнему в base64 от UTF-8, разбор не менялся.
- **Время старта процессов:** `PROCESS_STARTS_SCRIPT` (`src/main/claude-home/registry.ts`) — один текст. pid приходят в `WORFY_PROCESS_IDS` через запятую. В переменную проходят только целые больше нуля; сам скрипт берёт из неё только то, что целиком из цифр.
- **Helper Terminal-а из PR #239 и список процессов в `scripts/install-stable.mjs`** не менялись: оба уже отдают скрипт текстом и base64 не декодируют. Замер ниже.
