## Что делаем

### 1. Код Gate

- **R3-S1. Код выхода после `settle` держит соглашение, а не код.** Обработчик сигнала выходит с
  `settled ? code : stopped` (`gate.mjs:706`), а `code` присваивается, только когда `main` вернулся
  (`:951`). Сегодня ни за одним из пяти вызовов `settle()` (`:314`, `:788`, `:807`, `:838`, `:903`)
  до `return` нет `await`, и сигнал после записи исхода выходит с кодом этого исхода. Мутант,
  который добавляет туда один `await`, делает красный прогон с уже записанным файлом вердикта
  выходом 0, и `gate-verdict.test.sh` остаётся зелёным. Правка: выходить с кодом того исхода, что
  записан (например, `settle(code)` его запоминает), а без него — с 3. Проверка — этот мутант.
- **R3-S2. Исход D не оставляет маркера.** Ошибка Gate, в том числе git, завершённый сигналом в
  одиночку, кончается в `catch` (`gate.mjs:952-963`): код 3, строка, маркера нет. Stop hook ищет
  маркеры (`harness/hooks/stop.sh:96-153`) и в форме hook-а модели ничего не скажет. Резолвер,
  завершённый в одиночку, идёт через `notVerified` (`gate.mjs:313-320`) и маркер `nokey-broken-…`
  оставляет. Тот же пробел у любой ошибки Gate был и на base. Сделать: маркер `nokey-broken-…` и в
  `catch` — либо «не делаем, причина».
- **R3-S3 и R3-REST-5. Шапка `gate.mjs` обещает больше, чем делает код.**
  - Шапка: ошибка Gate — «code 3 and no verdict file» (`gate.mjs:86-87`). Но первые два вызова git —
    `--show-toplevel` и `--git-common-dir` (`gate-paths.mjs:57`, `:72`; зовутся в `gate.mjs:687`,
    `:689`) — идут до обработчика `exit`, который удаляет прошлый файл вердикта (`:697-699`). Git,
    завершённый там в одиночку, даёт код 3, и файл вердикта прошлого прогона остаётся. Base выходил
    в этом случае с 0 молча и файл тоже оставлял.
  - Шапка: Gate ищет сигнал «after each call to git» (`gate.mjs:72-73`). Код проверяет после того
    вызова git, который сигнал завершил (`git()` бросает ошибку — `:223`, `catch` ждёт сигнал —
    `:959`), а не после каждого.
  - Сделать: поправить шапку либо поставить обработчик `exit` раньше первых двух вызовов.
- **R3-S4 и R3-REST-1. Неверные причины в строках Gate.**
  - Резолвер, завершённый сигналом, назван «завершился с кодом 1»: `which.status ?? 1`
    (`gate.mjs:721`, строка — `:725`) и то же у резолвера плана (`:806`, строки — `:808-810`). Нужна
    строка с именем сигнала (`which.signal`, `planned.signal`).
  - Вывод git больше 1 GiB (`GIT_OUTPUT_MAX`, `gate.mjs:124`; `maxBuffer` — `:219`): Node сам
    завершает git сигналом SIGTERM, и Gate пишет «git … was ended by the signal SIGTERM» (`:223`).
    Код 3 — безопасная сторона, но причина неверна. Этого отличия от base не было в списке
    implementer-а. Сделать: отличать `ENOBUFS` (`run.error`) от сигнала извне.

- **Предел 60 s test-а переноса не останавливает Gate**, который ждёт синхронного потомка.

## Риски

- **Проверки сигналов — только POSIX.** На Windows они пропускаются; на Linux сигналы по таймеру
  не запускались ни в одном круге (только CI). SIGHUP и SIGBREAK ревью не посылало.
- **Мутанты — в своём worktree.** В третьем круге два reviewer-а шесть минут делили один worktree
  мутантов; оркестратор перезапускал мутанты того окна. Один agent — один worktree мутантов.
- **Поиск node меняет, какой node запускает Gate** на машине владельца: другая сортировка версий nvm
  может выбрать другую версию. Перед правкой записать в «Итог», какие версии лежат в
  `~/.nvm/versions/node` на Mac владельца и какую берёт `gate.sh` до и после.
- **Каждый merge, который трогает `harness/`, кончается `pnpm install:stable`** вне прогона Autopilot
  (ADR-0047): иначе установленный Harness остаётся прежним.
