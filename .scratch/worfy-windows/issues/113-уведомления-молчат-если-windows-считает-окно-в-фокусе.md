## Что происходит

- worfy показывает системное уведомление («turn завершён», очередь gate), только когда ни одно её окно не в
  фокусе: `focused: () => BrowserWindow.getFocusedWindow() !== null` (`src/main/notify.ts:696` и `:704`).
- Замер Ticket-а 110 на ПК: окно, которое Windows не пустила на передний план при запуске (блокировка
  переднего плана — другое приложение недавно получало ввод), Electron всё равно считает активным в своём
  потоке. `isFocused()` и `getFocusedWindow()` дают «в фокусе», хотя впереди другое приложение. `blur()` и
  `minimize()` этого не снимают, снимает только `hide()`.
- Какое правило блокировки сработало, не установлено. Ticket 110 назвал случай редким; замер этого не
  подтверждает.
- Возможный сценарий у пользователя: запустил worfy и, пока она грузится, кликнул в другое приложение. Если
  блокировка сработала, окно worfy «в фокусе» навсегда, и каждое уведомление молчит, пока человек не
  активирует worfy и не уйдёт из неё. Не проверено на worfy, запущенной вручную.
- Тот же признак — источник ложного «в фокусе» в e2e linked-notify (до #809 — красный в полном прогоне).

## Что делаем

1. **Сначала замер, на worfy, запущенной вручную (Stable или собранная копия, не e2e).** Запуск и клик в
   другое приложение во время загрузки; запуск из другого приложения, которое держит передний план; запуск
   через ярлык. Для каждого случая: `getFocusedWindow()`, `isFocused()`, системный передний план
   (`GetForegroundWindow` с pid) и пришло ли уведомление после turn-а. Результат — в «Итог».
2. **Если случай не воспроизводится** — Ticket закрывается с замером в «Итог», код не меняется.
3. **Если воспроизводится** — `focused` на Windows сверяет окно worfy с системным передним планом (окно
   переднего плана принадлежит процессу worfy), а не только с активным окном потока Electron. macOS и Linux
   без изменений. Unit test на оба ответа, e2e linked-notify без `hide()`-обхода, если он становится не нужен.

## Готово, когда

- [ ] Замер из п. 1 записан в «Итог»: каждый случай, что дали `getFocusedWindow()` и передний план, пришло ли

- Воспроизводится: 3 запуска из 7, оба запуска через ярлык. Клик во время загрузки не нужен: хватает того,
  что Windows не отдала новому окну передний план.
- Не замерено: настоящий клик в другое приложение во время загрузки, настоящий двойной клик по ярлыку,
  настоящее уведомление после turn-а (вывод «молчало бы» — из `focused` в `notify.ts`).
- Решение (Mac, вариант (a)): на Windows, когда Electron говорит «в фокусе», worfy спрашивает систему через
  Windows PowerShell, чей процесс владеет окном переднего плана (`src/main/foreground.ts`). Вызов
  0,68–0,95 с при 97 % CPU, таймаут 2 с; при сбое или таймауте остаётся ответ Electron, первый сбой
  пишется в лог. macOS и Linux без изменений. koffi — только если (a) окажется медленным (решает владелец).
- `hide()`-обход в e2e linked-notify (`unfocusAll`) оставлен: убрать его можно только после прогона e2e на
  Windows, а при нагрузке ПК этого прогона не было. Отдельным тикетом не заводится (правило: low не заводим).
- Известные пределы (review, все low, не исправлены):
  - Две заметки одной Session за доли секунды: показ решает порядок ответов PowerShell, а не порядок событий.
  - Переименование Session (временный id → id SDK), пока ждём ответ: счёт 10 с может уйти на старый id.
  - Очередь gate: пока PR ждёт больше часа, а владелец в окне worfy, PowerShell запускается раз в минуту
    (~1 с CPU).
