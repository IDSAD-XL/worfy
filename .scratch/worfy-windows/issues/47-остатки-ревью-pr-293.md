## Что делаем

### 1. Код: просмотр и путь, данный `removeTree`

Правка просмотра идёт в четыре текста сразу. Как её проверять — в «Тесты» и «Риски».

- **«Пропавшая по ходу» запись не проверяется второй раз** (`remove.ts:269-273`; копии —
  `scripts/remove-tree.mjs:63`, `scripts/install-stable.mjs:357`, `restore.ts:145`). Папка называет запись в
  своём списке. Если `lstat` этой записи отвечает `ENOENT` («ничего нет») или `ENOTDIR` («не папка»),
  просмотр считает запись пропавшей и идёт дальше. В том же `try` стоят `lstat` пути `путь/..`
  (`remove.ts:267`) и список папки (`remove.ts:268`): их `ENOENT` и `ENOTDIR` тоже значат «пропало». Для
  записи и для списка папки это закреплено test-ами с ожидаемым итогом
  (`test/unit/remove-tree-mounted.test.ts:210-220`). Для `путь/..` такого test-а нет. Есть только строка
  сверки копий с модулем (`test/unit/remove-tree.test.ts:763`): она сравнивает модуль с копией и своего
  ожидаемого значения не имеет. Прочитано, первый круг: когда `ENOENT` отвечает `lstat` пути `путь/..`,
  просмотр не сравнивает `dev` данной папки и не читает её список, а `rmSync` после этого идёт. На настоящей
  системе для этого дерево должно измениться между двумя вызовами.
  - **Запущено на Linux** (второй reviewer первого круга; контейнер Docker `node:24-bookworm`, Node 24.21.0,
    без сети, томов не подключали; код head `8939aad7` — первый push PR #293). Папка с именем, которое не
    является верным UTF-8 (байты `FF FE`). `readdir` отдаёт её имя строкой с символом замены U+FFFD. `lstat`
    по этой строке отвечает `ENOENT` при каждом вызове, а не один раз. Копия из `scripts/remove-tree.mjs`
    приняла папку за пропавшую и ни о чём под ней не спросила. `rmSync` после этого удалил дерево целиком —
    с этой папкой и всем, что под ней. Копия с main дала тот же итог одним вызовом `rmSync`.
  - **Не запущено.** Точка монтирования под такой папкой: том никто не подключал. Значит, потеря файлов тома
    за такой папкой не показана. Показано другое: просмотр туда не смотрит, а `rmSync` туда заходит.
    Файловые системы macOS, кроме APFS, не проверялись. На head `cce018f9` запуск не повторялся; с первого
    push изменилась одна строка просмотра: запись спрашивается как `path + '/' + name` (`remove.ts:277`), а
    не через `join`.
  - **Запущено на Mac:** APFS такое имя не принимает — `mkdir` отвечает `EILSEQ`.
  - **Кто может дать такое дерево сегодня.** На macOS — никто, пока дерево лежит на APFS. На Windows просмотр
    не идёт. Остаётся Linux, а для Linux worfy не собирается: в `electron-builder.yml` цели только `mac`
    (`:51-52`) и `win` (`:67-69`); на Linux идёт CI (`README.md:72`) и запуск из checkout-а руками. Нужны три
    вещи сразу: такой запуск, папка с таким именем в дереве, которое удаляют, и том, примонтированный под
    ней. Main ведёт себя так же: PR #293 ничего не ухудшил.
  - **Фраза шапки шире кода:** «what is not seen is not removed» (`remove.ts:65-66`). Этот предел не назван
    в шапке. «Итог» Ticket-а 44 называет его одной строкой среди того, что оставлено следующему Ticket-у:
    «запись, „пропавшая по ходу“, без второго взгляда». Что это имя не в UTF-8 и что это Linux, там не
    сказано.
  - **Сделать одно из трёх.** (а) Когда `lstat` отвечает `ENOENT` на имя из только что прочитанного списка —
    прочитать список ещё раз и закончить ошибкой, если имя там по-прежнему есть. (б) Читать имена как `Buffer`
    (`readdirSync` с `encoding: 'buffer'`, путь для `lstat` — тоже `Buffer`); это меняет `RemoveFs`
    (`remove.ts:102-109`), три копии и модель. (в) «Не делаем, причина» в «Итоге» — и тогда предел дописан в
    шапку, а фраза `remove.ts:65-66` сужена.
- **Точка монтирования с тем же `dev`, что у её папки, не видна.** Предел объявлен: шапка `remove.ts:67-72`,
  test «the limit, written down» (`test/unit/remove-tree-mounted.test.ts:232-237`). `rmSync` в такую папку
  заходит.
  - **Запущено, только чтение** (`lstat` 13 точек монтирования Mac владельца). Кроме корня `/`, тот же
    `dev`, что у своей папки, отвечает одна: `/System/Volumes/Data` — том данных, который система монтирует
    сама. Её `dev` равен `dev` папки `/System/Volumes`.
  - **Второго надёжного признака в `node:fs` для macOS ревью не нашло** (запущено, только чтение): `ino`
    корня тома отличил бы только этот системный том, а числа `statfs` меняются.
  - **Для Linux хватило бы одного чтения `/proc/self/mountinfo`** — файла, где система называет каждую точку
    монтирования процесса (по знанию reviewer-а; не запускалось). bind mount папки той же файловой системы
    на Linux не измерялся.
  - **Кто может дать такой путь сегодня.** Места вызова удаляют записи Trash, папки, которые worfy создал
    сам, выбранные записи `~/.claude` при переносе Harness и Stable copy (прочитано ревью). Том с тем же
    `dev` внутри такой папки должен появиться руками. Способ подключить том так на macOS не найден и не
    искался («Итог» Ticket-а 44).
  - **Сделать.** Правка с test-ом на модели (запись `volume` с `sameDev`, `test/unit/remove-tree-model.ts:36`)
    либо «не делаем, причина». Для macOS сначала нужен признак; если его нет — в «Итог» идёт запись, что
    искали и что не подошло.
- **`dev` сравнивается как Number** (`remove.ts:266-267`; копии — `scripts/remove-tree.mjs:58-59`,
  `scripts/install-stable.mjs:352-353`, `restore.ts:140-141`). `dev` со старшим битом приходит округлённым.
  - **Запущено на Mac, только чтение.** `lstatSync('/dev', { bigint: true }).dev` — `-1896451623`. Без
    `bigint` — `18446744071813100000`. `Number(18446744071813099993) === Number(18446744071813099994)` —
    `true`. Шаг чисел около 2^64 — 2048. Два таких `dev` ближе 2048 друг к другу сравниваются как равные, и
    точка монтирования между ними не видна.
  - **Кто может дать такое сегодня.** Из 13 точек монтирования Mac владельца такой `dev` только у `/dev`
    (devfs). `dev` томов APFS и autofs приходят точными. Нужны два тома с такими `dev`, один примонтирован
    прямо в папку другого. На этом Mac таких нет.
  - **Сделать.** `lstatSync(path, { bigint: true })` в просмотре — тогда `RemoveFs` (`remove.ts:103`) и
    модель несут `bigint`; либо строка в шапке рядом с пределом `remove.ts:67-72`; либо «не делаем, причина».
- **Папка с другим `dev`, которая не точка монтирования: subvolume файловой системы btrfs** (по знанию
  reviewer-ов первого круга; не измерено). У subvolume внутри дерева свой `dev`. Просмотр откажет со словами
  «a volume is mounted there» (`remove.ts:298`), хотя том туда не примонтирован; main такое дерево удаляет.
  Это отказ, а не потеря: не удалено ничего. Касается только Linux на btrfs. Сделать: замер либо «не
  измеряем, причина»; если отказ остаётся — строка в шапке. Для замера нужна файловая система btrfs, то есть
  подключённый том: agent его не подключает («Риски»).
- **Не новое: symlink, данный с разделителем в конце, вне Windows читается как папка за ним.** Main ведёт
  себя так же; PR #293 этого не ухудшил.
  - **Запущено на Mac, по своим папкам из `mkdtemp`** (main и head `8939aad7`): `removeTree('<папка>/link/')`
    опустошил и удалил папку, на которую ведёт symlink; сам symlink остался. **На head `cce018f9` — запущено,
    только чтение** (второй круг; своё дерево, удаляющие вызовы подменены, оба Node): для `link/` просмотр
    спросил ровно о том, что удалил бы `rmSync('link/')`, — о папке, на которую ведёт symlink. Настоящего
    удаления `link/` на этом head в отчётах второго круга нет.
  - **Причина.** Вне Windows `rmSync` получает текст пути таким, как он дан (`remove.ts:300`). Разделитель в
    конце срезает только обход Windows (`trimmed`, `remove.ts:128-131`; вызов — `:303`). Описание
    `removeTree` говорит другое: ссылка по самому пути уходит как ссылка (`remove.ts:285-287`).
  - **Кто может дать такой путь сегодня: никто.** Места вызова строят путь через `join`, `resolve`, `dirname`
    или `mkdtemp`; разделителя в конце они не оставляют (прочитано ревью).
  - **Сделать здесь.** Исправить описание `remove.ts:285-287`: вне Windows путь с разделителем в конце система
    читает как папку за ссылкой. Срезать разделитель вне Windows — значит изменить путь, который получает
    `rmSync`. В этом Ticket-е это не делается («Вне скоупа»). В «Итог» идёт запись, нужен ли на это отдельный
    Ticket.

## Риски

- **Тот же класс потери данных, что в Ticket-ах 35 и 44.** Ticket 35 — на Windows удаление стирало файлы тома
  за junction по GUID. Ticket 44 — на macOS оно стирало файлы тома, примонтированного в папку. Правка
  просмотра может скрыть точку монтирования: тогда `rmSync` зайдёт в том. Поэтому каждая правка просмотра
  идёт с тремя вещами. Первая — test-ы на модели с ожидаемым списком вызовов. Вторая — мутанты, только над
  двумя файлами на модели. Третья — замер на настоящем томе, который делает оркестратор.
- **Том подключает только оркестратор.** Implementer и reviewer-ы не подключают и не отключают ни том, ни
  образ диска — на Mac, в контейнере и где угодно ещё. Замер оркестратора из PR #293 не покрывает два случая
  пункта 1. Том под папкой с именем не в UTF-8: на APFS такое имя создать нельзя (`mkdir` отвечает `EILSEQ`).
  Принимает ли его HFS+ — файловая система образа диска оркестратора — и другие файловые системы macOS, не
  проверялось. Subvolume btrfs: нужен Linux. Кто и как делает эти замеры, решает оркестратор; без этого в
  «Итог» идёт «не измеряем, причина».
- **Пункт 1 меняет код удаления в четырёх местах.** Три копии — один текст между метками. Test
  `test/unit/remove-tree.test.ts:827` сверяет их и запрещает в тексте backquote: копия `restore.ts` лежит в
  template-строке.
- **`Buffer` и `bigint` меняют `RemoveFs` и модель.** Тем же интерфейсом пользуется обход Windows
  (`remove.ts:165-173`, `:204-247`). Ticket 45 в пункте 3 тоже предлагает менять `RemoveFs`. Согласовать
  порядок двух Ticket-ов.
- **`test/unit/trash-mounted.test.ts` идёт на модели только с seam-ом PR #293** (`TrashDeps.fs`,
  `src/main/layout/trash.ts:75-76`). С `trash.ts` до PR #293 тот же файл читает настоящую папку
  `/data/p/trash` (первый круг, reviewer test-ов). На Mac владельца папки `/data` нет. По той же причине
  мутант `purge`, который зовёт удаление мимо `this.fs`, делает этот файл не модельным: такой мутант не

**Пункт 1 — просмотр перед `rmSync`.**
- **Запись, «пропавшая по ходу» — вариант (а).** Когда `lstat` записи из только что прочитанного списка отвечает
  `ENOENT` или `ENOTDIR`, папка читается ещё раз (`listedIn` в `src/main/storage/remove.ts`, тот же код в трёх
  копиях). Имя по-прежнему в списке — удаление кончается ошибкой этого `lstat` (code `ENOENT`, `path` — эта
  запись), не удалено ничего. Имени в списке нет или папки уже нет — просмотр идёт дальше, как раньше. Так
  ловится имя не в UTF-8 на Linux: `lstat` по нему отвечает `ENOENT` при каждом вызове. Цена: такое дерево,
  которое раньше удалял `rmSync`, теперь не удаляется. `ENOENT` у `путь/..` и у списка папки по-прежнему
  значат «пропало»: так отвечает только дерево, которое меняет чужой процесс. Для `путь/..` появился test с
  ожидаемым итогом. Test-ы на модели — `test/unit/remove-tree-mounted.test.ts`: имя не в UTF-8 с томом под ним,
  запись, пропавшая на самом деле, папка, ставшая файлом, второй список с `EACCES`, второй список без папки,
  `путь/..` без папки. Модель для этого умеет правку дерева «чужим процессом» (`removedMeanwhile`), а список
  несуществующего пути отвечает `ENOENT`, список файла — `ENOTDIR`. Мутант «правка убрана» красный в четырёх
  текстах сразу (10 test-ов упали), только в модуле (16) и только в трёх копиях (6).
