## Что происходит

Три e2e падают на ПК в каждом прогоне (пересчёт, два gate full и сравнения с main). Все три — сравнение
размера с целым числом CSS px, а на ПК `devicePixelRatio` = 1.5.

1. `test/e2e/done-stack.spec.ts:139` («the open done stack folds by Collapse in the place of Expand, and by
   Esc once nothing else takes the press»), `:169`:
   ```
   expect(locator).toHaveCSS(expected) failed — getByTestId('done-stack-toggle')
   Expected: "1px"   Received: "0.666667px"
   ```
   0.666667 = 1 / 1.5: рамка в 1 CSS px нарисована одним device px. Вероятно, Chromium округляет ширину
   рамки вниз до целых device px и `getComputedStyle` отдаёт уже округлённое значение. Тогда неверна
   проверка, а не кнопка. Похожий случай — чип Open в [Ticket-е 94](94-чип-open-на-windows-выше-своей-рамки.md).
2. `test/e2e/palette-find.spec.ts:101` («⌘K goes to a Ticket and runs commands as the buttons do; ⌘F finds
   words in a transcript and a Card»), `:193`:
   ```
   Expected { field: 28, input: 28, row: 28 }
   Received { field: 28, input: 28.000003814697266, row: 28.00000762939453 }
   ```
   `field` — `clientHeight` (целое), `input` и `row` — `boundingBox()` (дробное). Разница 2⁻¹⁸ и 2⁻¹⁷ px —
   шум перевода координат при дробном масштабе, меньше одной единицы раскладки Chromium (1/64 px).
   Вероятно, неверна проверка: она сравнивает дробное число точным `toMatchObject`.
3. `test/e2e/window.spec.ts:179` («the window position and size survive a restart»), `:201`:
   ```
   Expected { x: 60, y: 100, width: 900, height: 560 }
   Received { x: 60, y: 100, width: 900, height: 562 }
   ```
   Первый запуск записал верные границы (`window-state.json` равен `wanted`, проверка `:197` прошла). Второй
   запуск открыл окно на 2 px выше. Это похоже на продукт или Electron: в
   [Ticket-е 97](97-browser-layer-правый-край-страницы-не-найден-на-windows.md) окно без рамки 638×410 при
   150 % тоже вышло 638×412, там помог `setContentSize`. 2026-10-21 `window.spec.ts` на ПК был зелёным после
   [Ticket-а 79](79-e2e-window-и-settings-health-на-windows.md), то есть это регрессия.

## Что делаем

Для каждой проверки сначала причина, потом правка. Допуск в test-е — только если неверна сама проверка при
дробном масштабе; в «Итог» для каждой из трёх сказать, что неверно: продукт или проверка.

1. Рамка: замерить на ПК `getComputedStyle(toggle).borderTopWidth` и ширину рамки на снимке в device px.
   Если рамка — ровно 1 device px, а Chromium так округляет любую рамку в 1 CSS px, ожидание — то, что
   Chromium отдаёт при этом масштабе (например, `floor(1 × dpr) / dpr`), а не строка `1px`.
2. Высоты: если разница — шум перевода координат, сравнивать с точностью до единицы раскладки
   (`toBeCloseTo(28, 1)` или округление до 1/64). Если высота поля на самом деле дробная — править CSS.
3. Окно: найти, где второй запуск получает 562: границы из `window-state.json` при создании окна, рамка
   Windows, `setBounds` против `setContentBounds`, минимальный размер. Правка — в продукте, чтобы
   восстановленное окно было ровно сохранённого размера при любом масштабе; test остаётся точным.

## Итог

ПК владельца 2026-10-23, Windows 11 Pro 10.0.26200, масштаб экрана 150 % (`devicePixelRatio` 1.5,
`screen.getPrimaryDisplay().scaleFactor` 1.5), ветка `worfy-windows/109` от main `0c4789b7`, Electron 44.5.1.
До правки на ветке: три spec-а (`--grep-invert @packaged`) — 3 failed, 5 passed, все три падения те, что в
описании. Замеры — временными строками в spec-ах и временным spec-ом-пробой (в commit не вошли).

1. **Рамка `done-stack-toggle` — неверна проверка.** Замер: `getComputedStyle(toggle).borderTopWidth` —
   `0.666667px`. Такой же `div` с `border-top: Npx solid` в той же странице: 0.5px и 0.67px → `0.666667px`,
   1px → `0.666667px`, 1.5px → `1.33333px`, 2px → `2px`, 3px → `2.66667px`, то есть
   `max(1, floor(N × 1.5)) / 1.5`. На снимке `webContents.capturePage` (device px) у `div` с рамкой 1px красного
   цвета на дробной координате (top 20.3333) красная ровно одна строка пикселей. Chromium рисует рамку целым
   числом device px, не меньше одного, и `getComputedStyle` отдаёт уже округлённую ширину; у кнопки рамка
   задана как 1px и нарисована одним device px — продукт верен. Правка: ожидание —
   `max(1, floor(dpr)) / dpr` от `devicePixelRatio` страницы, строкой с 6 значащими цифрами, как её печатает
   Chromium (точное сравнение — после ревью, круг 1); на 100 % и 200 % это по-прежнему `1px`.
2. **Высоты поля и строки палитры — неверна проверка.** Замер в той же точке test-а: в странице
   `getBoundingClientRect().height` у `palette-input` и первой `palette-option` — ровно 28, `clientHeight`
   и `offsetHeight` — 28; `boundingBox()` Playwright — 28.000003814697266 и 28.00000762939453 (верх 60.6667
   и 115.3333). Разница — шум перевода координат: Playwright берёт квадрат элемента по CDP в device px и
   делит обратно. Высота не дробная, CSS править нечего. Правка: `input` и `row` меряются
   `getBoundingClientRect().height` в странице — сравнение осталось точным (`toMatchObject` с 28), без
   допуска. Попутно: у `palette-field` `clientHeight` 28, а `offsetHeight` 29 и высота рамки 28.6667 —
   это нижняя рамка 1px, нарисованная одним device px (как в пункте 1); проверка берёт `clientHeight`
   и не задета.
3. **Окно после перезапуска 562 вместо 560 — неверен продукт (точнее, конструктор Electron).** Замер
   пробой с `window-state.json` = `{60, 100, 900, 560}`: окно приложения после старта — `getBounds()`
   900×562, `getContentBounds()` 886×499. Отдельные `new BrowserWindow({x: 60, y: 100, width: 900,
   height: 560, show: false})` в том же процессе: сразу после конструктора 900×562 — с `minWidth/minHeight`
   и без них, только с одним из минимумов, с `setMinimumSize` после создания; `setBounds` того же
   прямоугольника после конструктора даёт ровно 900×560 (содержимое 886×497), и так же после
   `showInactive()`. Значит, 562 — конструктор при дробном масштабе (внешний размер с рамкой Windows), а
   не рамка, не минимум и не `window-state.json` (в нём 560). Правка — `src/main/window.ts`: после
   `new BrowserWindow` окно читает свои `getBounds()` и, если они не равны запрошенным, один раз зовёт
   `setBounds` с запрошенными (без сохранённого места — место, где его поставила система, и запрошенный
   размер); до подписки на `moved`/`resized`, так что это не запись в `window-state.json`. На macOS
   конструктор точен, вызова нет. Test остался точным.
   Что изменилось с 2026-10-21: в коде создания окна и в версии Electron (44.5.1 и в `85cec301`, ветке
   Ticket-а 79) — ничего, что меняет размер на Windows (с тех пор добавлены только `keepOffPointer` —
   только macOS — и `windowShow`). Замер Ticket-а 79 («5 passed, 12 skipped» на три spec-а) не говорит,
   прошёл ли именно этот test и при каком масштабе экрана; при масштабе 100 % или 125 % (560 × 1.25 = 700)
   ошибки конструктора нет. Вероятнее всего, тогда был другой масштаб; доказать нечем.
4. **Четвёртая причина, спрятанная за пунктом 2.** После правки высот `palette-find.spec.ts` упал в 2 из 3
   повторов на последней проверке «в репозитории ничего не изменилось»: `.git\index` с новым временем
   изменения. Список файлов пропускал `.git` по `path.endsWith('/.git')`, а на Windows `join()` даёт `\`, так
   что `.git` попадал в список, а `git status` самого test-а (следующая строка) перезаписывает индекс.
   Неверна проверка. Правка: `.git` пропускается по имени (`basename(path) === '.git'`).
