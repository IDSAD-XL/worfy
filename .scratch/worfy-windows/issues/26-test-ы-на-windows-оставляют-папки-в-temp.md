## Что происходит

- **`afterEach` чистит временную папку через `fs.rmSync` с `recursive`.** Под Node 24.21.0 из
  Electron 44.5.1 на Windows этот вызов бросает EPERM на файле «только для чтения». Такие файлы —
  объекты git: test создаёт во временной папке репозиторий. Причина та же, что в Ticket-е 23
  (общая функция удаления для `src/main` и `scripts/`). Test-ы вынесены из Ticket-а 23 сюда: его PR
  уже большой, а правка `afterEach` — механическая и проверяется отдельно.
- **Следствие первое: test падает.** Из 681 падения `pnpm test` на Windows у 153 в причинах есть
  этот EPERM, у 68 — только он. По файлам: `harness-migrate` 54, `projects` 24, `docs` 22,
  `projects-connect` 21, `clients` 10, `shell` 10, `harness-drift` 9, `build-version` 2,
  `canvas-tools` 1.
- **Следствие второе: папка остаётся.** Один полный `pnpm test` оставляет около 250 папок `worfy-*`
  в `%TEMP%`. За 2026-10-09 — 2026-10-12 на ПК владельца их набралось 9510 (`worfy-migrate` 2268,
  `worfy-canvas` 1134, `worfy-docs` 959, `worfy-projects` 946 и мельче); объём не замерен.
- **Что уже сделано в PR Ticket-а 23:** в двух файлах `afterEach` зовёт новую функцию удаления.
  `harness-migrate`: 54 падения → 25; `build-version`: 2 → 0. Папок после прогона: 253 → 248.
- **Сколько всего мест.** На main `81930f0` в `test/` — 158 вызовов `rmSync` в 57 файлах (grep).
  Какие из них удаляют папку с репозиторием git, не разбиралось.

- **macOS тоже оставляет папки, по другой причине** (ревью PR #257 на Mac, 2026-10-13).
  `test/contract/canvas-tools.test.ts` после каждого зелёного прогона оставляет 11 папок

### Что сделано

1. **Helper — `test/remove.ts`, функция `removeTestTree(path)`.** Это `removeTree` из `src/main/storage/remove.ts` (Ticket 23) без добавок.
   - **Место.** Прямо в `test/`: его импортируют и `test/unit`, и `test/contract`. Файл добавлен в `tsconfig.test.node.json` отдельной строкой.
   - **Почему обёртка, а не прямой импорт.** Одно имя и одно место для всех test-ов; test-запрет проверяет, что helper зовёт именно функцию приложения.
2. **Все рекурсивные `rmSync` в `test/` заменены: 71 вызов в 54 файлах** (37 в `test/contract`, 17 в `test/unit`), семь файлов из пункта 2 — в их числе. Три файла, которые уже звали `removeTree` напрямую (`harness-migrate`, `build-version`, `shell-integration-dispose`), переведены на helper.
   - Убраны два ручных обхода в `install-stable.test.ts`: снятие «только для чтения» с файлов перед чисткой больше не нужно.
   - Три цикла «сначала ссылки, как ссылки» (`install-stable`, `agent-env`, `trash-junction`) оставлены: они безвредны, комментарий исправлен.
   - `rmSync` без `recursive` (20 вызовов, удаление одного файла как шаг test-а) не тронут: Ticket о рекурсивном.
3. **Отложенное сохранение Layout — причина папок и на macOS, и на Windows.** Хранилище Layout пишет `layout.json` через 250 ms после последнего изменения. Test удалял папку раньше, запись приходила позже и создавала папку заново.
   - В `test/remove.ts` добавлена `saveLayoutNow()`: она зовёт `flushAll()` хранилища. Вызывается перед удалением папки.
   - Вызов добавлен в пять файлов, которые оставляли такие папки на ПК: `canvas-tools` (26 папок за прогон), `trash` (10), `clients` (2), `docs` (1), `layout-store` (1).
4. **Два файла не чистили за собой вовсе:** `app-settings.test.ts` (19 папок `worfy-app-settings-store-*` и одна `worfy-app-settings-*` за прогон) и `projects-hold.test.ts` (одна). Теперь убирают в `afterAll`.
5. **`ShellIntegration.prepare()` на Windows — выбран первый вариант, с поправкой: папка создаётся один раз.**
   - Причина замерена: `ownFolder` проверял биты доступа POSIX (`mode & 0o077`), а на Windows у любой папки Node показывает `0o666`. Проверка не проходила никогда, и каждый `prepare()` делал новую папку; `disposeSync` убирал последнюю.
   - Правка: на `win32` папка, которая не ссылка, принимается. Ссылка под именем папки по-прежнему не используется — на любой системе.
   - «Не создавать вовсе» не выбрано: `prepare()` зовётся только для zsh, и если пользователь Windows запускает zsh, папка ему нужна.
   - **Следствие правки, найденное полным прогоном, и вторая правка.** Раз папка одна, каждый следующий `prepare()` переименовывает новый файл скрипта поверх прежнего. На Windows такое переименование отвергается с EPERM, пока прежний файл кем-то открыт; один полный прогон это поймал (`.zprofile`, два вызова `prepare()` разом; тот же test отдельно, уже с двенадцатью вызовами, пять раз подряд прошёл и без правки — сбой виден только под нагрузкой). Теперь на `win32` переименование повторяется: до 10 попыток через 20 ms, только на EPERM, EACCES и EBUSY. Повторять безопасно: источник — свой временный файл со случайным именем, цель не менялась, отказ ничего не переносит. Предел — 180 ms ожидания на файл, затем прежняя ошибка. На остальных системах — один вызов, как было.
6. **Test против возврата** — в `test/unit/no-rmsync.test.ts`, рядом с запретом Ticket-а 23. Красный, если `rmSync` с `recursive` появится в `test/`; опции на следующих строках вызова тоже читаются.
   - Исключения: два test-файла самой функции удаления (`no-rmsync.test.ts`, `remove-tree.test.ts`) и `test/unit/glob-probe.tsx`. Последний проверяется без типов Node и импортировать helper не может; в его папке только копии и symlink-и, три его строки перечислены в test-е.
   - **Попутно исправлена ошибка поиска из третьего круга PR #257:** вызов, начавшийся на следующей строке, засчитывался и строкам перед ним. Ложно зелёным test от этого не был — только лишние строки в списке.

### Что ещё замечено: приложение и отложенная запись Layout

Проба на настоящем хранилище (`zz-probe-layout-late.test.ts`, один запуск, в репозиторий не вошла):

- **Папку данных Project-а приложение не удаляет нигде.** `projects.remove` правит только список (чтение кода: все места `removeTree` в `src/main` — корзина, папка Card, перенос Harness, папка `ShellIntegration`). Значит, вернуть удалённую папку поздней записью приложение само не может; в test-ах папку удалял test.
- **Если папку данных удалить руками, пока запись отложена,** запись через 250 ms создаёт её заново с `layout.json` — то же, что было в test-ах.
- **Project, убранный из списка, пока запись отложена, теряет последнее изменение Layout.** Замер: первое изменение записано; второе сделано, Project сразу убран из списка — через 750 ms на диске только первое, в лог ушла строка `could not save the Layout … No Project with id …`. `flushAll()`, который приложение зовёт при выходе, даёт ту же ошибку. Теряется то, что изменено за последние 250 ms перед удалением из списка; заметно это, только если тот же Project добавят снова. В этот Ticket не входит.
