## Что делаем

### 1. Потерянное окружение не должно читаться как «все процессы завершены»

- **Что сейчас.** Скрипт времени старта (`PROCESS_STARTS_SCRIPT`,
  `src/main/claude-home/registry.ts:127-128`) читает pid из переменной `WORFY_PROCESS_IDS`. Если
  переменной нет, список пуст: код 0, пустой вывод. `processState` тогда отвечает `gone` для каждого
  pid, и все live Session пропадают из списка без ошибки.
- **Когда это случится.** Если `runFile` (`src/main/agent/env.ts:266`) перестанет передавать
  `options.env` в `execFile`. Сегодня он передаёт.
- **Почему это не заметят.** Вне Windows ни один test не падает: мутант проходит (61 прошёл,
  7 пропущено). Ловят его только test-ы с настоящим `powershell.exe`, а они идут лишь на Windows,
  вручную.
- **Что сделать:**
  - test на всех системах: настоящий `runFile` с `process.execPath` и одной переменной; ожидать её
    в stdout;
  - скрипт отвечает кодом, отличным от 0, когда `WORFY_PROCESS_IDS` нет вовсе. Тогда ответ —
    `unknown`, а не `gone`. Пустой список worfy и так не отправляет (`registry.ts:147-150`).

### 2. Окружение worfy у вызова времени старта не закреплено test-ом

- **Два мутанта выживают:** умолчание `env = {}` в `powershellScriptCommand` (`env.ts:243`) и `{}`,
  переданное из `readWindowsProcessStarts` (`registry.ts:151`). С любым из них PowerShell получил бы
  окружение из одной переменной.
- **Что сделать.** В test-е `test/contract/claude-home-registry.test.ts:459` сравнить `options.env`
  целиком: `{ ...process.env, WORFY_PROCESS_IDS: '7,8' }`. У чтения реестра такая проверка есть
  (`test/unit/agent-env.test.ts:598`).

### 3. Мелкие пробелы в test-ах

- **Ключ с `/`.** `registryVars` с разбиением по обоим слэшам проходит test-ы; `HKCU\a/b` стал бы
  другим ключом. В подключ test-а `test/unit/agent-env.test.ts:578` добавить `/`.
- **Фильтр цифр на Windows** (`test/contract/claude-home-registry.test.ts:523`, смоделировано).
  Элемент ` 12` ничего не доказывает: процесс 12 почти никогда не запущен. Заменить на pid, который
  запущен, с пробелом перед ним — например, ` ${process.ppid}`.
- **Фильтр pid в Node** (`registry.ts:146`) пропускает `1e21` и числа больше диапазона `int`.
  Сейчас это безвредно: скрипт берёт только цифры, а `process.kill` отказывает такому pid раньше.
  Можно сузить до `Number.isSafeInteger(pid) && pid > 0 && pid <= 0x7fffffff` и добавить оба числа
  в test.
- **`test/contract/claude-home-registry.test.ts` вырос за 1000 строк** (957 → 1011); gate
  предупреждает, не блокирует. Вынести блок Windows в свой файл.

### 4. Текст ошибки при `-Command`: `stderrLine` берёт не ту строку

- **Замер Session на Windows-ПК 2026-10-13** (голый вызов `powershell.exe` из Node 24.21.0, скрипт
  `throw 'boom'`):
  - с `-Command` — код 1, stderr простым текстом, 176 знаков, не CLIXML. Первая строка — `boom`,
    последняя — `+ FullyQualifiedErrorId : boom`. Вторая строка (позиция в скрипте) приходит в
    кодировке OEM, не UTF-8;
  - с `-EncodedCommand` — stderr начинается с `#< CLIXML`, 477 знаков, как до Ticket-а 21.
- **Что из этого следует.** `stderrLine` (`src/main/agent/env.ts:288`) берёт у простого текста
  последнюю строку — `+ FullyQualifiedErrorId : …`, а сообщение стоит в первой. Через саму
  `stderrLine` замер не шёл: это замер stderr и чтение кода.
- **Что задето.** Только сбои вне `try` скрипта реестра — ошибка разбора, отказ запуска. Свои
  ошибки скрипт ловит сам и печатает строкой `Error <base64>` в stdout.
- **Что сделать.** Для простого текста брать первую непустую строку; поправить комментарий
  `env.ts:272-277`; test на оба вида stderr.

### 5. Комментарии и текст Ticket-а 21

- `env.ts:217` называет `registryScript` — такой функции больше нет, есть `REGISTRY_SCRIPT`.
- `registry.ts:121-123` говорит, что секунду стоили pid в тексте. По Ticket-у 21 причина —
  декодирование закодированной команды, а не новый текст.
- `env.ts:184` говорит 0,26 s для скрипта текстом; в Ticket-е 21 — 0,25–0,32 s. Строки `:181-183`
  говорят «about a second more» про скрипт с декодированием base64; по Ticket-у самый первый такой
  вызов процесса стоил около 2,2 s.
- `claude-home-registry.test.ts:456` и `agent-env.test.ts:545` подают числа с одного ПК как общий
  факт. Добавить «на ПК владельца».
- **Ticket 21, «Итог»:**
  - строка 100 («из системного Node разницы нет») расходится со строкой таблицы 142;
  - строка 91 называет Node 22.13.0 для всех прогонов, строка 163 — 24.21.0;
  - заголовок «Причина» расходится со строкой 188 («кандидат, не доказана»): измерено условие,
    кандидат — механизм;
