## Что происходит

- **Что видели на ПК** (исполнитель PR #280; node-pty вызывался напрямую, без worfy). 20 вызовов
  `kill()` в одном тике — и процесс завершился с кодом 3221225477 (`0xC0000005`, access violation).
  Один раз с консолью системы и один раз за 24 круга с консолью из пакета node-pty (`useConptyDll`).
  Причину на ПК не разбирали.
- **Прочитано в node-pty 1.1.0**, `node_modules/node-pty/src/win/conpty.cc`:
  - записи о pty лежат в `std::vector` без блокировки (`:52`); mutex в файле нет ни одного;
  - у каждого pty свой поток ожидания (`:93`). Когда оболочка завершилась, он закрывает её handle
    (`:105`) и убирает запись из списка (`:106`; `remove_pty_baton` — `:65-74`) — в своём потоке, до
    вызова callback в главном (`:108`);
  - главный поток ищет в том же списке (`get_pty_baton`, `:55-63`) из connect (`:354`), resize
    (`:475`), clear (`:516`) и kill (`:547`) и дописывает в него при старте pty (`:304`);
  - `remove_if` перемещает `unique_ptr`: ячейка на мгновение пуста, и `ptyHandle->id` в другом
    потоке — это чтение по адресу 0;
  - удаление записи стоит внутри `assert`, но собрано: его текст есть в `conpty.node` prebuild-ов
    `win32-x64` и `win32-arm64` (запущено на Mac: поиск по файлам).
- **На модели, Mac** — две независимые модели ревью; libc++ на macOS, не бинарник node-pty и не
  Windows:
  - эти две функции скопированы; 20 записей, по потоку на запись, главный поток ищет. 24 прогона из
    24 кончились чтением по адресу 0;
  - 20 удалений в один момент без единого `kill()`: падают 300 кругов из 300. С блокировкой вокруг
    каждого вызова — 0 из 300;
  - потоки спят в ядре, как при `WaitForSingleObject`: без `kill()` — 192–194 круга из 200; `kill()`
    с работой в 0, 50 и 500 µs между вызовами — 200, 2 и 0 из 200.
- **Что модель показывает.** Класс ошибки — и что `kill()` для неё не нужен: хватит двух оболочек,
  которые завершились вместе, или одной — пока другой Terminal стартует или меняет размер. Частоты —
  модели, не Windows. **Не показано:** что именно это завершило процесс на ПК.
- **Только с консолью из пакета** (PR #280, ещё не влит): `PtyKill` читает `handle->hShell` (`:563`)
  после закрытия консоли (`:559`). Поток ожидания к этому времени мог закрыть handle и убрать
  запись. Насколько широко это окно, никто не мерил.
- **Где worfy закрывает много Terminal-ов разом** (прочитано, main):
  - выход из приложения — `closeAll` (`src/main/terminal/pty.ts:901-903`) из `will-quit`
    (`src/main/ipc/terminal.ts:192`);
  - Project убран из списка — `closeWhere` (`pty.ts:896-899`, `Promise.all`) из
    `closeRemovedProjects` (`ipc/terminal.ts:132-137`);
  - экран ушёл — `leave` (`pty.ts:790-806`).
  - Перед native `kill()` (`:889`) каждое закрытие ждёт свой helper PowerShell (`endWindowsShell`,
    `:856-870`). Вызовы этим разнесены по времени, но в очередь не выстроены.
- **Что теряется при падении.** При выходе Layout пишется в первом проходе `will-quit`
  (`src/main/ipc/layout.ts:18`), `kill()` идут позже: Layout цел. Вне выхода падение уносит всё
  приложение — идущие Session-ы и Layout, который ещё не записан (запись отложена:
  [Ticket 31](31-изменение-layout-теряется-когда-project-убирают-из-списка.md)).

## Что делаем

### 1. Воспроизвести и измерить на Windows-ПК — до любой правки

1. **Записи Windows о двух прошлых падениях:**
   `Get-WinEvent -FilterHashtable @{LogName='Application'; Id=1000}`, строки с `c0000005`. Модуль
   `conpty.node` в «Faulting module name» — эта гонка; `node.dll`, `electron.exe` или `ntdll.dll` —
   другая причина. `conpty.pdb` лежит в prebuild-е рядом с `conpty.node`.
2. **Без `kill()`.** 20 оболочек PowerShell через node-pty; во все в одном тике напечатать `exit`;
   24 круга. Хотя бы один круг с кодом 3221225477 — значит, `kill()` для падения не нужен.
3. **`kill()` в одном тике против `kill()` с шагом** — один на оборот event loop и один в 5 ms;
   число кругов одинаковое. Если с шагом падений нет, очередь закрытий в реестре помогает.
4. **Когда умирает процесс.** Писать строку через `fs.writeSync` сразу после цикла `kill()` и ещё
   раз через 500 ms: до или после остановки рабочих потоков node-pty на 1000 ms.
5. **Обе консоли** — системная и из пакета (вторая — после вливания PR #280). Число кругов и
   падений по каждому шагу — в «Итог».
6. **Если модуль не назван** — crash dump одного падения. Способ (procdump или настройка WER)
   меняет настройки системы: только с разрешения владельца в чате Session на ПК.

### 2. Решение

- **Очередь в реестре:** native `kill()` идут по одному — следующий после события exit предыдущего
  pty или после границы закрытия. Helper-ы PowerShell остаются параллельными.
- **Сообщить в upstream** (microsoft/node-pty) о списке без блокировки — с номерами строк и замером.
- **Окно, которое worfy закрыть не может:** resize или новый Terminal в момент выхода другой
  оболочки. Записать как ограничение. Выбор и причина — в «Итог».

### Замер: оставляет ли системная консоль conhost.exe (2026-10-18)

Вопрос владельца: на сегодняшнем node-pty 1.1.0 с системной консолью (`useConptyDll: false`) оболочка, которая вышла сама (`exit`), по-прежнему оставляет свой `conhost.exe` жить, пока жив родительский процесс? Это находка Ticket-а 22 (влит в PR #280) и причина, по которой приложение перешло на `useConptyDll: true`. Метод тот же, что в шагах 1–5: каждый круг — свежий процесс `electron.exe` как Node, 20 оболочек `powershell.exe -NoLogo -NoProfile` через node-pty (120×30), ожидание prompt во всех 20, действие, ожидание всех событий exit и ещё 3 s, затем запрос `Win32_Process` (консоли, чей родитель — процесс круга или одна из 20 оболочек), `kill()` каждого pty, через 2 s — второй запрос. Один прогон, 144 круга, 26 мин, без параллельных копий.

| Вариант | Консоль | Круги | Осталось conhost.exe до `kill()` | Через 2 s после `kill()` | Смерти (3221225477) |
|---|---|---|---|---|---|
| A: `exit` во все 20 | системная | 96 | **20 в каждом** из 91 опрошенного круга (1820 из 1820) | те же 20 в каждом (1820) | **5** |
| B: `kill()` всех 20 в одном тике, без `exit` | системная | 24 | 0 | 0 | 0 |
| C: `exit` во все 20 | из пакета | 24 | 0 из 22 опрошенных | 0 | **2** |

- **Ответ: да, без изменений.** Когда оболочка выходит сама, её `conhost.exe` (родитель — процесс, который звал node-pty) остаётся, и последующий `kill()` его не останавливает. Они закончились только с выходом процесса круга. `kill()` первым действием (вариант B) не оставляет ни одного. `OpenConsole.exe` при системной консоли не появлялся; на консоли из пакета не осталось ни `conhost.exe`, ни `OpenConsole.exe`.
- **Системная консоль тоже умирает:** 5 смертей из 96 в варианте A — только `exit`, без `kill()`. В шагах 1–5 у системной консоли было 0 из 96, так что «системная консоль не падает» на ПК не подтверждается. Консоль из пакета — 2 из 24 в варианте C. Все 7 смертей — сразу после действия, до первого события exit (не позже ~400 ms).
- **Что это значит для выбора:** у системной консоли две проблемы — брошенные `conhost.exe` после `exit` (Ticket 22) и те же смерти процесса. Возврат на системную консоль падения не убирает. Остаётся исправление гонки в node-pty (mutex вокруг списка pty в `conpty.cc`) — следующий шаг, сборка и тот же замер на 96 кругов.
- **Побочное:** каждый `kill()` на системной консоли запускает `conpty_console_list_agent.js`; в части кругов он печатал `Error: AttachConsole failed` (оболочки уже нет) и выходил. Процесс круга от этого не умирал, `kill()` исключений не бросал.
- **Чистота:** настоящих выживших после кругов 0. Фильтр по pid и времени создания 9 раз поймал чужие процессы с переиспользованным pid (8 — собственный запрос `Get-CimInstance` замера, 1 — `conhost.exe` уже завершавшегося процесса) и остановил их; все уже заканчивались. Консоли, которые были до прогона, не тронуты.
- **Не сделано:** crash dump для 7 смертей (меняет настройки Windows, решение владельца); ожидание после `kill()` дольше 2 s не мерилось (Ticket 22 видел, что они живут, пока живёт приложение).
- Версии: Windows 11 Pro 10.0.26200.9711, системный `conhost.exe` 10.0.26100.8875, Electron 44.5.1 (Node 24.21.0), node-pty 1.1.0, консоль из пакета 1.23.2510.08001, Windows PowerShell 5.1. Скрипты и сырые результаты — на ПК (`%TEMP%\worfy-01\m40\measure-conhost.mjs`, `results-conhost.md`, `conhost-run/results.jsonl`), в репозиторий не входят.

### Замер: исправление гонки — свой patch и node-pty 1.2.0-beta.15 (2026-10-18)

**Upstream уже исправил падение.** [microsoft/node-pty#921](https://github.com/microsoft/node-pty/issues/921) — то же падение; [#922](https://github.com/microsoft/node-pty/pull/922) «fix(win): use-after-free from unsynchronized access to ptyhandles» влит 2026-05-13: mutex вокруг списка pty. На npm он есть только в beta: тег `beta` — `1.2.0-beta.15` (2026-08-03), `latest` — по-прежнему `1.1.0`. Брошенный `conhost.exe` после `exit` на системной консоли — открытый [microsoft/node-pty#965](https://github.com/microsoft/node-pty/issues/965) (2026-09-08): поток ожидания выхода удаляет запись pty до `kill()`, и `kill()` уже нечего закрывать.

**Что делает свой patch** (`src/win/conpty.cc` node-pty 1.1.0, 126 строк diff, вне репозитория):
- один `std::mutex` вокруг списка pty; записи — `shared_ptr`, поэтому вызов, который нашёл запись, держит её живой;
- поток ожидания выхода только ждёт процесс и сообщает код — запись не удаляет и handle не закрывает (в 1.1.0 удаление стояло внутри `assert(...)`);
- `kill()` закрывает pseudo-console и удаляет запись; handle процесса закрывается с последней ссылкой. Так `kill()` после `exit` закрывает и консоль — это и есть исправление #965.

Сборка на ПК: копия node-pty 1.1.0 во временной папке, `node-gyp rebuild --target=44.5.1` с headers Electron из кэша, без `NoDefaultCurrentDirectoryInExePath`, `SpectreMitigation` выключен в `binding.gyp` (только для этой сборки: библиотек Spectre на ПК нет). Собрались `conpty.node` и `conpty_console_list.node`; winpty не собрался (свой `SpectreMitigation`) — на Windows 10 1809+ он не нужен. Контроль — та же копия без patch-а, собранная так же: исключает разницу toolchain-а. beta.15 — из npm (`npm install --ignore-scripts`) во временную папку, её prebuilds; зависимость в репозитории не менялась.

Метод — тот же, что в замере conhost: свежий процесс круга, 20 `powershell.exe -NoLogo -NoProfile`, действие, запросы `Win32_Process` до и через 2 s после `kill()`. По 144 круга на сборку, прогоны по одному.

| Сборка | `exit`, из пакета (48) | `kill()` в тике, из пакета (48) | `exit`, системная (24) | `kill()` в тике, системная (24) | Всего смертей | conhost.exe через 2 s после `kill()`, `exit` на системной |
|---|---|---|---|---|---|---|
| 1.1.0, своя сборка без patch-а (контроль) | **3** | **3** | **2** | 0 | **8 из 144** | 20 в каждом опрошенном круге (440) |
| 1.1.0 + свой patch | 0 | 0 | 0 | 0 | **0 из 144** | **0** |
| 1.2.0-beta.15 из npm (консоль из пакета 1.25.2603.03002) | 0 | 0 | 0 | 0 | **0 из 144** | 20 в каждом круге (480) |

- **Падение уходит и с patch-ем, и с beta.15:** 0 из 144 против 8 из 144 у контроля. Контроль совпадает с prebuilt 1.1.0 из прежних замеров (5 из 96 и 7 из 144), значит, своя сборка ведёт себя как prebuilt.
- **Брошенный conhost.exe уходит только с patch-ем.** beta.15 оставляет все 20 после `exit` и `kill()` — как 1.1.0 (#965 открыт). Для консоли из пакета брошенных консолей нет ни в одной сборке.
- Выживших процессов после кругов 0 во всех трёх прогонах (2 находки в контроле — собственный запрос `Get-CimInstance` замера с переиспользованным pid).
- **Варианты для решения владельца:** (1) перейти на `node-pty@1.2.0-beta.15` (точная версия: `^1.1.0` beta не возьмёт) — падение уходит, conhost на системной консоли остаётся, но приложение на консоли из пакета, где его нет; (2) свой patch к 1.1.0 — нужна сборка Windows-бинаря в CI (prebuilt из npm его не содержит), и его надо поддерживать до релиза upstream; (3) остаться на 1.1.0 — падение остаётся. Что beta.15 меняет ещё (консоль из пакета 1.25, API, выход на Mac), не проверялось.
