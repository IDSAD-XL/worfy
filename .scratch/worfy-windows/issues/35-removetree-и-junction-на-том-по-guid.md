## Что происходит

- **Как `removeTree` удаляет на Windows** ([Ticket 23](23-рекурсивное-удаление-не-идёт-через-junction.md), PR #257).
  Он обходит дерево сам (`src/main/storage/remove.ts:145-152`). Что лежит по пути, решает один
  вызов — `lstatSync(path).isDirectory()` (`:98-105`). «Не папка» удаляется через `unlinkSync`
  (`:115`). «Папка» перечисляется (`readdirSync`, `:120`), каждая запись удаляется тем же обходом
  (`:127-133`), потом идёт `rmdirSync` (`:135`).
- **Что измерил Ticket 19** (ПК владельца, Windows 11 26200, Node 22.13.0). Junction на том по GUID
  (`mklink /J … \\?\Volume{…}\`): `lstat` Node отвечает «папка, не ссылка», `readlink` — EINVAL,
  `realpath`, `stat` и `readdir` идут по нему. То же записано в `src/main/remote-links.ts:26-28`.
- **Что из этого следует — прочитано, на Windows не запускалось.** Для такого junction обход
  ответит «папка», перечислит том, на который он ведёт, и удалит файлы тома. Так же он решает
  для каждой записи ниже (`remove.ts:129`), то есть и для junction внутри удаляемой папки.
  - **Корзина.** Папка Card — такой junction. Проверка перед переносом видит его через `lstat`
    (`src/main/layout/trash.ts:100-107`), `put` переносит его в корзину (`renameSync`, `:208`).
    Через три дня (`TRASH_KEEP_MS`) `purge` зовёт `removeTree` для папки записи (`:286`). `purge`
    идёт при старте приложения (`src/main/ipc/trash.ts:40-48`).
  - **Папка shell integration.** На win32 `ownFolder` берёт любую папку, которая по `lstat` не
    ссылка (`src/main/terminal/shell-integration.ts:108`); при выходе `disposeSync` зовёт
    `removeTree` (`:175`). Сегодня worfy на Windows сюда не доходит: `prepare()` вызывается только
    для zsh (`src/main/terminal/pty.ts:664-667`), а там запускаются PowerShell и Git Bash.
- **На модели** (Mac, подменённый `RemoveFs`, платформа `win32`). Для записи корзины, чью папку
  `card` `lstat` называет папкой, `removeTree` делает `readdir entry/card`, два `unlink` внутри
  и `rmdir entry/card`. Вызовы те же, что у `remove.ts` из main.
- **Чего не знаем.** Перенесёт ли `renameSync` такой junction в корзину. Если нет, `put` падает
  на `trash.ts:208`, и до `purge` дело не доходит.
- **С какого времени и насколько вероятно.** На main с PR #257. PR #274 (watcher-ы на Windows не
  обращаются по ссылке на share), на ревью которого это нашли, `remove.ts` не менял. Нужен том,
  подключённый руками в папку Card внутри папки данных worfy; checkout такого принести не может.
  Поэтому ревью оценило замечание как low и просило оценить заново после замера.
- **Что не задето** (прочитано вторым reviewer-ом). Откат `create_card` удаляет папку, которую
  сам только что создал (`src/main/mcp/canvas-server.ts:192`, `:197`). Откат `put` сначала
  переносит Card обратно, потом удаляет папку записи (`trash.ts:222-223`).
- **Test-ов и замеров этого случая нет.** Поиск `Volume{`, `GUID`, `mount` в Ticket-ах 23 и 28,
  `remove.ts`, `trash.ts`, `remove-tree.test.ts`, `trash-junction.test.ts` — 0 совпадений (grep ревью).

## Что делаем

### 1. Замер на Windows-ПК — до любой правки

**Правило безопасности.** Шаги ниже удаляют файлы там, куда ведёт junction.

- Junction ведёт только на пустой том, созданный для замера: например, маленький VHD, который
  создаёт и подключает владелец.
- Junction на том с данными не создаётся никогда — ни на `C:`, ни на другой диск владельца.
  В Ticket-е 19 `realpath` такого junction ответил `C:\`: там его только читали.
- GUID тома называет владелец. Session на ПК сверяет его с томом VHD перед `mklink` и перед
  каждым шагом, который удаляет. Сама Session том не выбирает.
- На том кладутся два-три файла-метки. После каждого шага записывается, на месте ли они.
- Разрешение на замер владелец даёт в чате Session на ПК.

**Что измерить** — под Node 24.21.0 из Electron 44.5.1 (под ним работает main process) и под
системным Node. По `remove.ts:5-13` `fs.rmSync` у них ведёт себя по-разному, а Ticket 19 мерил под
Node 22.13.0.

1. `lstat`, `readlink`, `readdir` Node по junction — повтор строки таблицы Ticket-а 19.
2. `renameSync` junction в другую папку того же диска: проходит или падает, с каким кодом. То же
   для обычной папки, внутри которой лежит junction.
3. `rmdirSync` по junction без перечисления: снят ли junction, на месте ли файлы-метки.
4. `removeTree` по junction и по папке, внутри которой он лежит.
5. Корзина на Project-е для замера, два случая: папка Card — junction; junction внутри папки
   Card. `put`, затем `purge` с подменённым временем (`now`, `trash.ts:168`).
6. Чем ответ `lstat` Node для такого junction отличается от ответа для обычной папки.

### 2. Оценка и правка

- `put` и `purge` опустошили том — это потеря данных на main: оценить заново.
- `renameSync` не переносит junction — первый случай корзины не задет. Остаются второй случай и
  `removeTree` по пути, где такой junction уже лежит (шаг 4).
- Если замер подтвердил, правка — один из двух вариантов находок ревью: папку с признаком reparse
  point удалять одним `rmdirSync`, не перечисляя; либо пробовать `rmdirSync` до перечисления. По
  находке `rmdirSync` снимает junction любого вида как ссылку — это не измерено, шаг 3 проверяет.
- Если замер не подтвердил (файлы-метки на месте во всех шагах): записать в шапку `remove.ts`, что
  измерено и под какими Node; код не менять.
- Правка — в `walk` (`remove.ts:111-136`) и в трёх копиях из шапки (`remove.ts:24-26`): скрипт
  восстановления (`src/main/harness/migrate/restore.ts:115`), `scripts/remove-tree.mjs`,
  `scripts/install-stable.mjs`. Копии сравнивает `test/unit/remove-tree.test.ts`.

- **Замер удаляет файлы.** Ошибка в GUID тома — потеря данных. Отсюда правило безопасности.

  даст этот код. Через `patiently` каждая такая папка израсходует ожидания удаления: их пять на
  весь вызов (`:37`).
