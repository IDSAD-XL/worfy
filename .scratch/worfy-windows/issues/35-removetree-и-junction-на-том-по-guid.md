## Что делаем

### 1. Замер на Windows-ПК — до любой правки

**Правило безопасности.** Шаги ниже удаляют файлы там, куда ведёт junction.

- Junction ведёт только на пустой том, созданный для замера: например, маленький VHD, который
  создаёт и подключает владелец.
- Junction на том с данными не создаётся никогда — ни на `C:`, ни на другой диск владельца.
  В Ticket-е 19 `realpath` такого junction ответил `C:\`: там его только читали.
- GUID тома называет владелец. Session на ПК сверяет его с томом VHD перед `mklink` и перед
  каждым шагом, который удаляет. Сама Session том не выбирает.
- На том кладутся два-три файла-метки. После каждого шага записывается, на месте ли они.
- Разрешение на замер владелец даёт в чате Session на ПК.

**Что измерить** — под Node 24.21.0 из Electron 44.5.1 (под ним работает main process) и под
системным Node. По `remove.ts:5-13` `fs.rmSync` у них ведёт себя по-разному, а Ticket 19 мерил под
Node 22.13.0.

1. `lstat`, `readlink`, `readdir` Node по junction — повтор строки таблицы Ticket-а 19.
2. `renameSync` junction в другую папку того же диска: проходит или падает, с каким кодом. То же
   для обычной папки, внутри которой лежит junction.
3. `rmdirSync` по junction без перечисления: снят ли junction, на месте ли файлы-метки.
4. `removeTree` по junction и по папке, внутри которой он лежит.
5. Корзина на Project-е для замера, два случая: папка Card — junction; junction внутри папки
   Card. `put`, затем `purge` с подменённым временем (`now`, `trash.ts:168`).
6. Чем ответ `lstat` Node для такого junction отличается от ответа для обычной папки.

### 2. Оценка и правка

- `put` и `purge` опустошили том — это потеря данных на main: оценить заново.
- `renameSync` не переносит junction — первый случай корзины не задет. Остаются второй случай и
  `removeTree` по пути, где такой junction уже лежит (шаг 4).
- Если замер подтвердил, правка — один из двух вариантов находок ревью: папку с признаком reparse
  point удалять одним `rmdirSync`, не перечисляя; либо пробовать `rmdirSync` до перечисления. По
  находке `rmdirSync` снимает junction любого вида как ссылку — это не измерено, шаг 3 проверяет.
- Если замер не подтвердил (файлы-метки на месте во всех шагах): записать в шапку `remove.ts`, что
  измерено и под какими Node; код не менять.
- Правка — в `walk` (`remove.ts:111-136`) и в трёх копиях из шапки (`remove.ts:24-26`): скрипт
  восстановления (`src/main/harness/migrate/restore.ts:115`), `scripts/remove-tree.mjs`,
  `scripts/install-stable.mjs`. Копии сравнивает `test/unit/remove-tree.test.ts`.

### Оценка

- **Данные теряются на main** на трёх путях: `removeTree` по такому junction; `removeTree` по папке, в которой он лежит на любой глубине; корзина — `put`, затем `purge` при старте приложения через три дня.
- `renameSync` такой junction переносит, поэтому первый случай корзины задет так же, как второй.
- Условие прежнее: том, подключённый руками в папку внутри папки данных worfy. Checkout такого принести не может. Но цена — все файлы тома, поэтому находка больше не уровня low.

### Что отвечает один `rmdirSync`

Замер для правила «перечислять только после ответа „не пусто“». Оба Node, ответы совпали во всех 15 строках.

| Что по пути | `lstat` | `rmdirSync` |
|---|---|---|
| пустая папка | папка | проходит |
| папка с файлом | папка | ENOTEMPTY |
| пустая папка с атрибутом «только для чтения» | папка | проходит |
| папка с файлом и атрибутом «только для чтения» | папка | ENOTEMPTY |
| пустая папка — рабочая папка работающего процесса | папка | EBUSY |
| папка с файлом — рабочая папка работающего процесса | папка | EBUSY |
| папка с файлом, который открыт на запись (тем же процессом) | папка | ENOTEMPTY |
| обычный junction на непустую папку | ссылка | проходит, цель не тронута |
| symlink на непустую папку | ссылка | проходит, цель не тронута |
| junction по GUID на том с файлами | папка | проходит, файлы на месте |
| junction по GUID на пустой том | папка | проходит |
| junction по GUID на папку тома | папка | проходит, файлы на месте |
| junction по GUID, пока он — рабочая папка работающего процесса | папка | проходит, файлы на месте |
| папка с файлом по пути длиной 359 символов | папка | ENOTEMPTY |
| та же папка, пустая | папка | проходит |

- Папка с записями отвечает ENOTEMPTY во всех измеренных состояниях, кроме одного: рабочая папка работающего процесса отвечает EBUSY.
- Такой junction `rmdirSync` снимает во всех измеренных состояниях и файлы за ним не трогает.
- Папки и файлы «только для чтения» (объекты git, Ticket 23) правило не задевает: непустая папка «только для чтения» отвечает ENOTEMPTY и перечисляется, как раньше.

### Правка

Только обход Windows: `walk` в `src/main/storage/remove.ts` и три копии одним текстом — `scripts/remove-tree.mjs`, `scripts/install-stable.mjs`, текст `restore.mjs` в `src/main/harness/migrate/restore.ts`. `RemoveFs.lstatSync` теперь отдаёт и `dev`.

Папка, которую `lstat` называет папкой, перечисляется, только когда выполнены оба условия. Каждое достаточно само по себе для того случая, который оно видит.

1. **Том.** `dev` папки равен `dev` папки, в которой она лежит. Для записи внутри обхода `dev` родителя уже известен; для пути, который дали `removeTree`, спрашивается `lstat` папки-родителя (`путь\..`), и том берётся, только если `lstat` называет родителя папкой (первый круг ревью, ниже). Папка на другом томе не перечисляется никогда: её просят уйти через `rmdirSync`, с обычными ожиданиями, и больше ничего.
2. **Первый `rmdirSync`.** Любую другую папку сначала просят уйти как есть. Прошло — готово: это была пустая папка или ссылка, которую `lstat` не увидел. Ответ ENOTEMPTY — в папке есть записи, только теперь она перечисляется. Ответ «занято» — ожидание и новая попытка, без перечисления. Любой другой ответ бросается.

- **Какой признак что закрывает.** Junction на другой том (4а, 4б, 5а, 5б) закрывают оба признака. Junction по GUID на свой же том (4в) закрывает только второй: `dev` там ничего не говорит.
- **Третий признак не взят:** перечисление родителя с `withFileTypes` (шаг 6). Он потребовал бы сменить вид перечисления в модуле и трёх копиях; два правила закрывают все измеренные случаи.
- **Цена, записана в шапке `remove.ts` и закреплена test-ом.** Папка, которая сама занята (рабочая папка работающего процесса отвечает EBUSY, а не ENOTEMPTY), сохраняет своё содержимое: раньше обход удалял содержимое и падал на самой папке, теперь падает сразу с той же ошибкой. Занятую папку обход теперь ждёт до её записей, а не после: папка, занятая дольше 500 ms, даёт ошибку там, где main, приходивший к ней последним, мог успеть (смоделировано ревью, на ПК не измерялось).
- **Сколько вызовов прибавилось:** один `lstat` папки-родителя на вызов `removeTree` и один `rmdirSync` на каждую непустую папку.
- **Вне Windows ничего не меняется:** там по-прежнему один вызов `fs.rmSync`; test проверяет, что других вызовов нет.
- **Что делает `purge` с такой записью корзины.** Убирает её целиком: junction снят как ссылка, запись удалена, цикл идёт дальше — отказа нет (шаги 5а и 5б после правки). Первая ошибка `removeTree` по-прежнему обрывает цикл `purge` (`src/main/layout/trash.ts:284-288`), и более старые записи после неё остаются до следующего старта; так было и на main. Новых случаев, когда запись нельзя удалить, правка на Windows не добавляет, кроме папки, которая сама занята: её `rmdirSync` падал и раньше, после удаления содержимого. ### Как убрать пробный том (владелец, после merge)

0. Перед запуском с повышением прав посмотреть, что будет выполнено. Скрипт — две команды:
   `select vdisk file="C:\Users\Alexey\AppData\Local\Temp\worfy-01\t35-vhd\worfy-scratch.vhdx"` и `detach vdisk`. Диск назван полным путём своего файла, не номером и не буквой. Какой диск за этим файлом, показывает PowerShell без повышения прав:
   `Get-Disk | Where-Object Location -like '*worfy-scratch.vhdx' | Format-List Number, Location, BusType, Size` — ожидается один диск, `BusType` «File Backed Virtual», 64 MB.
   Сам файл скрипта печатает `Get-Content 'C:\Users\Alexey\AppData\Local\Temp\worfy-01\t35-detach-vhd.txt'` — ожидаются ровно эти две строки и ничего больше (добавлено ревью на Mac, второй круг PR #287).
   Перед шагом 1 спросить Session на ПК, созданы ли папки замера 6 (junction по GUID, том которого потом отключён; Ticket 45, пункт 2) и не нужен ли этот том для замера 7 (`mountvol`, там же): после отключения оба замера требуют нового тома и повышения прав (добавлено ревью на Mac).
1. Отключить виртуальный диск. Нужно повышение прав, появится окно UAC:
   `powershell.exe -NoProfile -Command "Start-Process diskpart -Verb RunAs -Wait -ArgumentList '/s C:\Users\Alexey\AppData\Local\Temp\worfy-01\t35-detach-vhd.txt'"`
   Скрипт состоит из двух команд: `select vdisk file="C:\Users\Alexey\AppData\Local\Temp\worfy-01\t35-vhd\worfy-scratch.vhdx"` и `detach vdisk`.
2. Сказать Session на ПК, что диск отключён. Она проверит, что тома `WORFYSCRATCH` больше нет, и уберёт остатки по полным путям: файл `%TEMP%\worfy-01\t35-vhd\worfy-scratch.vhdx`, папку `%TEMP%\worfy-01\t35-vhd`, два скрипта `diskpart` (`t35-make-vhd.txt`, `t35-detach-vhd.txt`) и рабочую копию ветки `%TEMP%\worfy-01\wt35` (через `git worktree remove`).
3. После перезагрузки ПК диск, подключённый через `diskpart`, обычно уже не подключён (на этом ПК не проверялось). Тогда шаг 1 не нужен, остаётся шаг 2: Session сама увидит, есть ли том.
