# 25 — Ручной job в CI: заданный список test-файлов на `windows-latest`

Type: task
Status: claimed — 2026-10-12
Blocked by: —
Source: решение владельца 2026-10-12: вынести вперёд малую часть Ticket-а [14](14-gate-full-на-windows.md) (gate full на Windows, с ручным job-ом «Windows» в CI). Условие владельца: большие test-ы не должны попасть на runner. Делает агент-implementer на Mac.

## Что происходит

- **Test-ы на Windows идут только руками** на ПК владельца. CI — один файл,
  `.github/workflows/ci.yml`. Job `check` на `ubuntu-latest` идёт на PR и push (`:24-26`). Job
  `full-macos` идёт только на `workflow_dispatch` (`:60-62`). Job-а Windows нет. У
  `workflow_dispatch` нет input-ов (`:15`): каждый ручной запуск гонит `full-macos` целиком.
- **Цена** (Ticket 14, `:80`): минута Windows — $0.010, минута macOS — $0.062.
- **Полный job «Windows»** с e2e и packaging описан в Ticket-е 14, пункт 8 (`:124-130`), и остаётся
  там. Здесь — только unit- и contract-файлы по списку.
- **Полный `pnpm test` на Windows красный:** около 700 упавших test-ов (оценка на 2026-10-12; в
  «Итог» Ticket-а 18 — symlink на share — 636, `:241`). На runner он идти не должен.
- **Как запускается файл.** `pnpm test` — это `node scripts/vitest-electron.mjs` (`package.json:16`);
  аргументы уходят в `vitest run` (`scripts/vitest-electron.mjs:24`). Аргумент vitest — фильтр по
  имени, а не точный путь (`test/contract/vitest-electron.test.ts:16-18`).
- **Правило проекта «агенты не запускают платные прогоны»** — вне репозитория, в
  `~/.claude/worfy-harness/projects/worfy/rules.md:27-28`: полный прогон на macOS — только вручную.

## Что делаем

1. **Job на `windows-latest`.** Все ограничения — внутри job-а:
   - запуск только по `workflow_dispatch`; на push и PR — никогда;
   - input — явный список test-файлов; пустой список — отказ;
   - только файлы под `test/unit/` и `test/contract/`; имя с `e2e`, `packaged` или `acceptance` — отказ;
   - не больше 12 файлов за запуск;
   - команда — `node scripts/vitest-electron.mjs <файлы>`; `pnpm test` в job-е нет;
   - `timeout-minutes: 10`; `matrix` нет.
2. **Список — это файлы, а не фильтры** (добавлено при составлении Ticket-а; следует из строки о
   vitest выше): каждый элемент — существующий файл `*.test.ts` или `*.test.tsx` и не начинается с
   `-`. Иначе элемент сработает как фильтр по многим файлам или как опция vitest.
3. **Проверка списка — первым шагом после checkout**, до `pnpm install`: отказ укладывается в
   минуту. Значение input идёт в шаг через `env`, а не подстановкой `${{ … }}` в текст `run`.
4. **Contract test закрепляет эти свойства:** ослабление любого делает Linux CI красным. Test-а,
   который читает workflow-файл, на main нет (grep по `test/`); ближайший образец читает
   `package.json` (`test/contract/vitest-electron.test.ts:26-28`). YAML-парсера среди зависимостей
   `package.json` нет (grep). Вариант: проверка списка — скрипт на Node, test зовёт его.
5. **Вопрос исполнителю, ответ — в «Итог»:** как не запускать `full-macos`, когда нужен только этот
   job. Отдельный workflow-файл (тогда `ci.yml` не меняется вовсе) или input, который выбирает job
   (так в Ticket-е 14, `:126-128`). Job-ы `check` и `full-macos` ведут себя ровно как сейчас.
6. **Кто запускает.** Владелец разрешил (2026-10-12) Session-оркестратору на Mac запускать этот job
   перед merge PR с кодом для Windows. Это единственное исключение из правила о платных прогонах.
   Записать в комментарии workflow-файла; строку в `rules.md` правит оркестратор, в PR её нет.

## Вне скоупа

- e2e, packaging, acceptance и полный `pnpm test` на Windows — Ticket 14.
- Windows-runner на PR: по решению владельца из Ticket-а 14 его нет. Починка красных test-ов.

## Риски

- **Время установки на runner-е.** Electron скачивается при `pnpm install`; node-pty берёт готовый
  prebuild (`scripts/postinstall.mjs:22-23`). Уложится ли запуск в 10 минут — не проверялось.
- **Test-ы с symlink.** На ПК право на symlink даёт режим разработчика (`README.md:13`). Есть ли оно
  на `windows-latest` — не проверялось.
- **Тяжёлый файл в `test/contract`.** Например, `harness-scripts.test.ts` гонит каждый `.test.sh`
  (Ticket 14, `:47-48`). От него защищает только `timeout-minutes`: потолок — 10 минут, $0.10.
- **Оба ручных job-а в одном workflow-файле:** ошибка в условии запустит macOS за $0.062 в минуту.

## Итог

Сделано на Mac 2026-10-12. На GitHub job не запускался ни разу: платные запуски делает владелец.

**Что добавлено**

- `.github/workflows/windows-tests.yml` — workflow «Windows tests» с одним job-ом `listed-tests`.
- `scripts/windows-test-list.mjs` — проверка списка на Node, без зависимостей.
- `test/contract/windows-tests-workflow.test.ts` — contract test: 8 test-ов на workflow-файл и 47 на
  скрипт.

**Ответ на пункт 5 — отдельный workflow-файл. Решено без владельца, подтвердить.**

- `ci.yml` не тронут вовсе: `git diff origin/main -- .github/workflows/ci.yml` пуст.
- Довод: у отдельного файла один trigger и один job, поэтому его запуск не может запустить
  `full-macos`. Вариант с input-ом в `ci.yml` требует менять условие `if` у `full-macos`, а это уже
  изменение его определения, и ошибка в условии стоит $0.062 в минуту.
- Расхождение с буквой ADR-0056, пункт 3: там ручной job «Windows» назван job-ом в `ci.yml`. Полный
  job «Windows» (e2e, packaging) остаётся за Ticket-ом 14; где ему жить, решит он.

**Формат input-а `files`**

- Пути от корня репозитория, с прямой косой чертой, в том написании, в каком их хранит git.
- Разделители — пробел, запятая, перевод строки, в любом сочетании.
- Пример: `gh workflow run windows-tests.yml --ref <ветка> -f files="test/unit/remote-links.test.ts test/unit/shell-resolve.test.ts"`.
  С `--ref` запуск берёт workflow-файл, скрипт и test-ы из этой ветки.

**Правила проверки списка** (отказ — код выхода 1, причина по каждому элементу в stderr, output
шага не пишется):

1. список пуст — отказ; больше 12 элементов — отказ;
2. элемент начинается с `-` — отказ;
3. в элементе есть символ, кроме латинских букв, цифр, `.`, `_`, `-`, `/` — отказ. Сюда попадают
   обратная косая черта, буква диска (`C:`), `*`, `[`, `=`;
4. элемент не под `test/unit/` и не под `test/contract/` — отказ (абсолютный путь тоже);
5. элемент не кончается на `.test.ts` или `.test.tsx` — отказ;
6. в элементе есть `e2e`, `packaged` или `acceptance` в любом регистре — отказ. Проверяется весь
   путь, а не только имя файла;
7. элемент не совпадает буква в букву с файлом, найденным обходом двух папок, — отказ. Обход не идёт
   по symlink, поэтому отказ получают: файл, которого нет; путь с `..`, `.` или `//`; другой регистр
   букв; папка; symlink на файл и путь через symlink на папку;
8. элемент входит как часть в путь другого test-файла (`pair.test.ts` при живом `pair.test.tsx`) —
   отказ. Причина: vitest сравнивает аргумент как часть пути без учёта регистра
   (`node_modules/vitest/dist/chunks/index.*.js`, `filterFiles`) и запустил бы оба файла. Этого
   правила в Ticket-е не было; оно следует из пункта 2. Сегодня таких пар в репозитории нет.

Правила 2 и 4 перекрываются с другими: элемент с `-` в начале не проходит и правило 4, а файл вне
двух папок — и правило 7. Mutation testing ловит их снятие по тексту причины в stderr, а не по
принятому списку.

**Shell шагов — bash, задан явно** (`shell: bash` у шага проверки и у шага запуска; на
`windows-latest` это Git Bash):

- шаг запуска — `node scripts/vitest-electron.mjs $TEST_FILES` без кавычек: bash делит принятый
  список на аргументы по пробелам. Символов, которые bash раскрыл бы, правило 3 не пропускает;
- в PowerShell, shell по умолчанию на Windows, `$TEST_FILES` — незаданная переменная PowerShell, а не
  переменная окружения: команда запустила бы весь набор test-ов. Поэтому shell закреплён test-ом;
- перед командой стоит `test -n "$TEST_FILES"`: пустой список останавливает шаг;
- шаг запуска берёт список из output шага проверки (`steps.list.outputs.files`), а не из input;
- `pnpm install` идёт в shell по умолчанию, как в `ci.yml`.

**Не проверено — ждёт запуска владельца на GitHub после мержа:**

- есть ли `node` на образе `windows-latest` до `actions/setup-node`: шаг проверки идёт на Node из

- как vitest на Windows сопоставляет путь с прямой косой чертой и укладывается ли install в 10 минут.

**Замечено вне Ticket-а**

- Workflow-файлы не входят в `.gitattributes`: на Windows они могут получить CRLF. Contract test
  читает файл с любым концом строки.
