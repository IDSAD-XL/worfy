## Что делаем

На коммите аудита `b9abc6a7d` главный frame окна worfy может уйти на любой адрес, кроме Card:

- `src/main/window.ts:377-380` вызывает `allowFrameNavigation` в `will-frame-navigate`;
- `src/main/cards/protocol.ts:345` для главного frame отвечает `true` на любой адрес не `worfy-card:`;
- `src/renderer/drop-guard.ts:6` останавливает только drop с файлами, drop ссылки Chromium открывает в окне.

Путь атаки: злонамеренная страница (например, в Browser Node) уговаривает пользователя перетащить ссылку на окно worfy.
Окно загружает чужую страницу с preload. IPC-вызовы `wrap()` отклоняет (`src/main/ipc/index.ts:136-141`), но события
`emit()` (`src/main/ipc/index.ts:209-216`) уходят окну без проверки URL. Страница подписывается через `window.worfy.on`
и читает `agent.event` — содержимое Session — и другие события.

Что меняется: в `installWebPolicy` (`src/main/window.ts:360`) для web contents окна приложения (не `<webview>`)
переход главного frame разрешён только на адрес, который принимает `isAppUrl` (тот же matcher, что у проверки
отправителя IPC). Это покрывает и View ▸ Reload, и перезагрузку dev server. Правила для Card и для guest-страницы
Browser не меняются. Второй рубеж — по желанию: `drop-guard.ts` отменяет drop ссылки (`text/uri-list`) там, где её никто
не принимает.

Границы: `allowFrameNavigation` в `src/main/cards/protocol.ts` не трогаем — его меняет только решение Ticket-а 01.

## Итог

**Исправление.** `installWebPolicy` (`src/main/window.ts`) для web contents окна приложения (не `<webview>`) теперь
пропускает переход главного frame, только если `isAppUrl` принимает адрес назначения — тот же matcher, что у проверки
отправителя IPC. Правило Card (`allowFrameNavigation`) осталось как было и проверяется первым; `src/main/cards/protocol.ts`
не тронут. Загрузки, которые начинает сам main (`loadURL`, View ▸ Reload, первая загрузка dev server), через
`will-frame-navigate` не проходят; переход окна на свой адрес с другими query и hash (смена Project-а на Linked machine,
`useProjects.ts`) `isAppUrl` принимает.

**Drop ссылки.** У Electron `webPreferences.navigateOnDragDrop` по умолчанию `false`, и окно его не включает: drop ссылки
на Canvas не начинал навигацию и до исправления. e2e `test/e2e/window-navigation.spec.ts` проверяет это на настоящем
Electron: drag с `text/uri-list` через CDP `Input.dispatchDragEvent` доходит до страницы, а `will-frame-navigate` окна не
срабатывает ни разу. Второй рубеж в `src/renderer/drop-guard.ts` не добавлен: путь закрыт и в renderer-е (Electron), и в
main (это исправление), а guard для ссылок пришлось бы учить не мешать drop в текстовые поля.

**Что было открыто на самом деле.** Переход, начатый страницей окна (`location.href = …`, ссылка без `target`), до
исправления уводил окно на чужую страницу: первый test того же spec на коде без исправления красный (`allowed <адрес>`,
затем `loaded <адрес>`), с исправлением — `refused <адрес>`, окно остаётся на адресе приложения, Canvas на месте.
