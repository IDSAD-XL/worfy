# Code story — worfy-stuck-agents 01: Цикл Autopilot: лестница продолжений, `set-aside` и `main-red`

Kind: pr · Epic: worfy-stuck-agents · Ticket: 01 · PR: - · Language: ru

## 1. Что было не так

Цикл Run-а (`src/shared/autopilot/cycle.ts`) останавливал весь Run из-за одного Ticket-а в двух местах:
`settle-timeout` давал `wave-unfinished` (Ticket всё ещё в работе через 10 минут после хода), `sameSet` в `evaluate()`
давал `no-progress` (та же Wave снова готова). Счётчика попыток на Ticket не было, и не было способа попросить
Orchestrator-а отложить Ticket. Этот PR даёт циклу лестницу: продолжение → `set-aside` → прежняя остановка. Потолок —
параметр, по умолчанию 0: Run пока не исполняет новые эффекты (это Ticket 05), поэтому поведение main не меняется.

- Требование: [Что происходит](../issues/01-цикл-лестница-продолжений.md#что-происходит)

## 2. Лестница: продолжить, отложить или остановиться

Code: `src/shared/autopilot/cycle.ts:334-351` · key lines: 337, 339, 342, 344, 349

```ts
function ladder(state: CycleState, stuck: readonly number[], cause: ContinuationCause, before: CycleEffect[]): CycleStep {
  const max = state.maxContinuations ?? 0
  const setAside = state.setAside ?? []
  if (max === 0 || stuck.length === 0 || stuck.some((num) => setAside.includes(num))) return stop(state, cause, before)
  const spent = (num: number): number => state.continued?.[num] ?? 0
  const over = stuck.filter((num) => spent(num) >= max)
  if (over.length > 0) {
    const asked: CycleState = { ...state, phase: 'turn', setAside: [...setAside, ...over], asked: { kind: 'set-aside' } }
    return { state: asked, effects: [{ kind: 'set-aside', tickets: over, attempts: max, cause }] }
  }
  const continued = stuck.map((num) => ({ num, attempt: spent(num) + 1 }))
  const counts = { ...state.continued, ...Object.fromEntries(continued.map((each) => [each.num, each.attempt])) }
  const continuation: Continuation = { attempt: Math.max(...continued.map((each) => each.attempt)), of: max, cause }
  return {
    state: { ...state, phase: 'sending', continued: counts, asked: { kind: 'continue', continuation } },
    effects: [...before, { kind: 'continue-tickets', tickets: continued, of: max, cause }],
  }
}
```

- Что делает: одна функция для обоих мест. Потолок 0, пустой список или Ticket, который уже откладывали, — прежняя
  остановка с той же причиной. Есть Ticket без попыток — эффект `set-aside` только для таких Ticket-ов, фаза `turn`
  (один ход Orchestrator-а), Ticket-ы записаны в `setAside`. Иначе — `continue-tickets` с попыткой каждого Ticket-а,
  счётчик в `continued` растёт по номеру Ticket-а, фаза `sending`: продолжение уходит как следующая Wave.
- Почему здесь: Ticket называет `src/shared/autopilot/cycle.ts` в «Где в коде»; spec требует, чтобы решения цикла
  оставались чистыми, а исполнение было в `run.ts` (Ticket 05).
- Без него: Run останавливался бы на первом застрявшем Ticket-е, как сегодня.
- Требование: [Что делаем, пункты 1–3 и 6](../issues/01-цикл-лестница-продолжений.md#что-делаем)
- Риски и пробелы test-ов: при `set-aside` по `no-progress` `wave-finished` не пишется сразу — он придёт после хода
  `set-aside`, один раз (test «the same Wave ready again» это проверяет). Если в одной Wave есть Ticket-ы и с
  попытками, и без, сначала откладываются те, у кого попыток нет; остальные продолжаются только при следующем
  `settle-timeout` — это решение не записано в spec, его выбрал implementer.

## 3. Два места, где раньше был `stop(...)`

Code: `src/shared/autopilot/cycle.ts:358-366` · key lines: 361, 362

```ts
  const holding = state.tickets.filter((num) => tickets.some((ticket) => ticket.epic === state.epic && ticket.num === num && inWork(ticket)))
  if (holding.length > 0) {
    // A Ticket the Orchestrator was asked to set aside still holds the Wave after that turn: the old stop.
    if (holding.some((num) => state.setAside?.includes(num))) return stop(state, 'wave-unfinished')
    return stay({ ...state, phase: 'settling', holding })
  }
  const finished: CycleEffect = { kind: 'wave-finished', wave: state.wave, tickets: state.tickets }
  const next = readyNums(state, tickets)
  if (next.length === 0) return nothingReady(state, tickets, [finished])
```

- Что делает: при уходе в `settling` цикл запоминает, какие Ticket-ы Wave держат её (`holding`), — у события
  `settle-timeout` нет списка Ticket-ов, и без этого лестнице было бы нечего считать. Если после хода `set-aside` Ticket
  всё ещё в работе — сразу `wave-unfinished`. Сам `settle-timeout` теперь зовёт `ladder(state, state.holding ?? [],
  'wave-unfinished', [])`, а `sameSet` — `ladder(state, state.tickets, 'no-progress', [finished])`.
- Почему здесь: место названо в Ticket-е (`cycle.ts:275`, `:328–329`); почему запоминать `holding` в состоянии, а не
  добавить Ticket-ы в событие, — не записано: так `run.ts` (вне этого Ticket-а) не меняется.
- Без него: `settle-timeout` не знал бы, какие Ticket-ы продолжать, а отложенный Ticket получал бы новый `set-aside`
  вместо остановки.
- Требование: [Что делаем, пункт 3](../issues/01-цикл-лестница-продолжений.md#что-делаем)
- Риски и пробелы test-ов: `tasks-timeout` с живыми задачами не тронут и остаётся `background-stalled` — это проверено
  test-ом при потолке 2.

## 4. `main-red` останавливает Run, пока продолжение или `set-aside` ещё не ушли

Code: `src/shared/autopilot/cycle.ts:426-431` · key lines: 427, 431

```ts
    case 'settle-timeout':
      return state.phase === 'settling' ? ladder(state, state.holding ?? [], 'wave-unfinished', []) : stay(state)
    case 'main-red':
      // Read only for an asked continuation or set-aside: then the stuck Ticket waits for a green main, and so does the run.
      // After a graceful Stop the run ends as the user asked, with nothing more sent.
      return state.asked === undefined ? stay(state) : stop(state, state.stopping ? 'user-stop' : 'main-red')
```

- Что делает: событие `main-red` действует только пока в состоянии есть `asked` — его ставит `ladder`, снимают
  `wave-sent` (продолжение ушло как Wave, и `wave-started` несёт `continuation`), `busy` и `turn-ended` (ход
  `set-aside` начался или кончился; `busy` до `wave-sent` продолжения окно не закрывает). Вне этого окна событие
  ничего не меняет. Если до красного main пришёл graceful Stop, Run кончается с `user-stop`, а не `main-red`:
  продолжение или `set-aside` всё равно не уходят, а причину остановки выбрал пользователь.
- Почему здесь: spec, «Красный main — маркер `land`»: Run читает маркер, когда цикл просит продолжение или
  `set-aside`; чтение маркера — дело Ticket-ов 02 и 05.
- Без него: продолжение на красном main гоняло бы агента по тесту, который красный не по его вине.
- Требование: [Что делаем, пункт 4](../issues/01-цикл-лестница-продолжений.md#что-делаем)
- Риски и пробелы test-ов: если Run (Ticket 05) пришлёт `main-red` уже после `wave-sent`, Run не остановится — так
  задумано окном `asked`, но test-а против настоящего Run-а нет.

## Проверить себя

1. Почему при потолке 0 Run ведёт себя так же, как до этого PR, хотя у каждого Ticket-а 0 попыток и `0 >= 0`?
   - Строки: `src/shared/autopilot/cycle.ts:337-339`
   - Ответ: проверка `max === 0` стоит раньше `spent(num) >= max` и сразу даёт прежнюю остановку; без неё каждый
     Ticket сразу шёл бы в `set-aside`.
2. Что остановит Run, если после хода `set-aside` Orchestrator не заблокировал Ticket и тот всё ещё в работе?
   - Строки: `src/shared/autopilot/cycle.ts:359-361`
   - Ответ: `evaluate` видит Ticket из `setAside` среди тех, что держат Wave, и сразу даёт `wave-unfinished`, не
     дожидаясь нового `settle-timeout`.
3. Когда событие `main-red` уже ничего не меняет?
   - Строки: `src/shared/autopilot/cycle.ts:428-431`
   - Ответ: когда в состоянии нет `asked`: продолжение уже ушло как Wave (`wave-sent`) или ход `set-aside` начался
     (`busy`) либо кончился (`turn-ended`).
