# 114 — Сообщение, взятое в идущий ход, пропадает из чата

Type: bug
Status: claimed 2026-11-15T01:11Z
Branch: worfy-polish/114
Blocked by: —
Source: сообщение тестировщика через владельца 2026-11-14, бриф Orchestrator-а 2026-11-15.

## Что происходит

В чате Orchestrator-а под Autopilot (Vendor claude) пропало сообщение пользователя, хотя Session его получила и ответила.
Порядок событий: пользователь пишет, пока Claude Code ещё в ходе; Autopilot начинает Run, Session освобождается, worfy
перезапускает Orchestrator без присмотра и через 2 с шлёт команду `/worfy:epic-wave …`. В транскрипте сообщение
«поставлено в очередь и сразу взято в работу».

## Причина

worfy отдаёт сообщение Claude Code сразу, когда сам не считает Session занятой: после `result`, пока Claude Code ещё
в ходе, который начал task-notification фоновой задачи (`src/main/agent/session.ts:419`, `send` → `deliver`, строка 893).
Claude Code ставит такое сообщение в свою очередь и берёт в идущий ход. В файл транскрипта оно попадает только как
`queue-operation` (`enqueue`) и `attachment` типа `queued_command` с `commandMode: "prompt"` — записи `user` нет
(в транскриптах этого Project-а 695 таких сообщений, ни одно не записано ещё и как `user`).

`src/shared/transcript/parse.ts:273` (`attachmentRecord`) читает `queued_command` как `unknown`: из файла сообщение не
читается вовсе. Живой view показывает его, пока оно есть в живых событиях (`prompt` → `notice` пользователя,
`src/renderer/session/store.ts:163`). Но view Session с транскриптом рисует файл, а после него живые события
(`joinPastAndLive`, `src/renderer/session/SessionView.tsx:171`). Когда Autopilot перезапускает Orchestrator
(`src/main/agent/orchestrator.ts:381` → `relaunch`, строка 844), у view новая живая Session `pending-…` с пустым журналом:
часть разговора с этим сообщением читается из файла, и сообщения нет. Следующей строкой чата стоит команда Autopilot —
отсюда «команда встала на место сообщения». После рестарта worfy сообщение пропадает навсегда по той же причине.

Доказательство — `test/unit/session-queued-message.test.tsx`: до правки красный, «['Run the wave', COMMAND]» вместо
«['Run the wave', TYPED, COMMAND]».

## Что делаем

`attachmentRecord` читает `queued_command` с `commandMode: "prompt"` как запись `user` с тем же содержимым (строка
или блоки, картинки — вложениями, как у обычного сообщения). Task-notification в очереди (`commandMode:
"task-notification"`) не трогаем: их читает `subagents.ts` (ADR-0030).
