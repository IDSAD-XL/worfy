## Question

Пункты «Not yet specified» карты: сколько истории читать и сколько это стоит; проекты с короткой историей; смесь
нескольких ревьюеров; как выглядит предложение при добавлении проекта; как судить о качестве; приватность; как
обновлять; какая структура у сгенерированного skill-а; Codex.

## Answer

Владелец 2026-11-07:

- **Что делает генератор.** Skill-генератор, например `/worfy:human-review-setup`, читает историю PR проекта и пишет
  частный проектный skill ревью.
- **Чей голос — вся команда.** Голос — совокупность всех людей-ревьюеров команды: «как пишет человек из этой
  команды». Одного человека не копировать никогда: это подозрительно и не то, что имелось в виду. Наклоны по области
  кода или репозиторию допустимы, где их показывает история. **Заменяет** пункт «Чей голос» решения
  [01](01-решения-владельца-2026-11-07.md) (выбор одного или нескольких ревьюеров, по умолчанию самый активный).
- **Сколько истории.** Последние 12 месяцев, не больше 500 PR с ревью. Боты и комментарии автора к своему PR
  отбрасываются. До запуска — сколько PR и комментариев будет прочитано и оценка токенов.
- **Мало истории.** Меньше 30 содержательных комментариев людей — честно сказать, что голос не собрать, и предложить
  обычный `/worfy:code-review`, настроенный только на стандарты репозитория. Репозиторий worfy — такой случай.
- **Предложение при добавлении проекта.** Есть GitHub с историей ревью — одна строка «Собрать ревьюера в стиле вашей
  команды?» с «Собрать» / «Позже». «Позже» больше никогда не спрашивает; кнопка остаётся в настройках проекта. Без
  истории — строки нет.
- **Проверка качества.** После генерации — прогон нового skill-а на 5 старых PR, где уже было ревью людей; черновик и
  настоящие комментарии рядом; человек оставляет skill или собирает заново. Число совпавших замечаний — грубая мера.
- **Обновление.** Без самообновления. Раз в месяц или по кнопке — перечитать новые PR и показать, что поменялось в
  правилах. **Заменяет** пункт «Обновление» решения 01 (повторный запуск генератора).
- **Где лежит.** В сгенерированном skill-е слова коллег, поэтому он хранится только на машине пользователя, в папке
  Profile-а проекта; никогда в репозитории проекта и никогда в репозитории worfy.
- **Только черновик.** На GitHub ничего не уходит без явного «да» человека.
- **Структура сгенерированного skill-а.** У владельца есть частный рабочий пример для другого проекта; его не читать
  и не называть. Шаблон — его структура:
  1. Загрузить PR.
  2. Triage: какие PR команда одобряет молча (bump-ы, backport-ы, сгенерированные файлы, мелкие правки текстов) и
     какие читает целиком. «Маленький — не значит безопасный»: назвать исключения, которые показывает история.
     Большой или смешанный PR — попросить разделить.
  3. Checklist по областям или репозиториям — что команда действительно ловит, из истории.
  4. Проверить каждого кандидата на head commit; непроверенный становится вопросом. Уровни: let go / nit / question
     / heads-up / followup / argued / blocker. Список «не трогать» — на что команда возражает или что игнорирует.
  5. Голос по уровню: длина, типичные обороты, регистр (оговорки, смягчения), наклоны по областям.
     `voice-examples.md` — настоящие комментарии по уровням, со ссылками. Совпадать по длине и температуре, не по
     словам.
  6. Правила состояния ревью: по умолчанию approve с nit-ами; когда comment; когда request changes.
  7. Черновик как payload GitHub create-review и скрипт проверки черновика по правилам регистра (длина комментария,
     запрещённое — имена частного workflow, строки авторства AI).
  8. Показать человеку; отправлять только по его слову.

  Каждое правило сгенерированного skill-а ссылается на доказательство — раздел сгенерированного файла исследования в
  той же частной папке.
- **Порядок.** Epic идёт после `worfy-skills`. Только Claude Code; Codex позже.
