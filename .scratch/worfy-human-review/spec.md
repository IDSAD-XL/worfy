## Цель и что видит пользователь

Человек добавляет в worfy проект, где команда давно ревьюит PR на GitHub. Сегодня агент worfy пишет ревью своим
голосом: длинные разборы там, где команда пишет «nit: …», и вопросы о том, что команда пропускает молча.

После Epic-а:

1. При добавлении такого проекта worfy показывает одну строку «Собрать ревьюера в стиле вашей команды?» с кнопками
   «Собрать» и «Позже». Без истории ревью строки нет.
2. «Собрать» открывает Session с `/worfy:human-review-setup`. Скрипт читает историю PR за 12 месяцев и говорит, сколько
   PR и комментариев прочтёт модель и сколько это примерно токенов. Модель читает только после «да».
3. Генератор пишет частный skill `human-review` в папку Profile-а проекта на этой машине. Каждое правило skill-а
   ссылается на раздел файла доказательств `research.md` рядом.
4. Генератор прогоняет новый skill на 5 старых PR, где уже было ревью людей, и показывает черновик рядом с настоящими
   комментариями. Человек оставляет skill или собирает заново.
5. В любой Session worfy, которую ведёт человек, «отревьюй PR #N» даёт черновик ревью голосом команды. На GitHub
   ничего не уходит без явного «да» человека.
6. Раз в месяц worfy предлагает обновить ревьюера; кнопка обновления есть и в Project settings. Обновление показывает,
   что поменялось в правилах.

Если истории мало (меньше 30 содержательных комментариев людей), генератор честно говорит, что голос собрать не из
чего, и предлагает обычный `/worfy:code-review` по стандартам репозитория. Репозиторий worfy — такой случай
(исследование, раздел 3: 0 ревью и 0 нитей в последних 100 PR).

## Решения владельца 2026-11-07

Записаны в [02](issues/02-решения-владельца-grilling-2026-11-07.md); здесь — коротко.

1. **Генератор.** Skill-генератор `/worfy:human-review-setup` читает историю PR проекта и пишет частный проектный
   skill ревью.
2. **Чей голос — вся команда.** Голос — совокупность всех людей-ревьюеров команды: «как пишет человек из этой
   команды». Одного человека не копировать никогда. Наклоны по области кода или репозиторию — можно, где их
   показывает история. (Заменяет пункт «Чей голос» решения 01.)
3. **Сколько истории.** Последние 12 месяцев, не больше 500 PR с ревью. Боты и комментарии автора к своему PR
   отбрасываются. До запуска — сколько PR и комментариев будет прочитано и оценка токенов.
4. **Мало истории.** Меньше 30 содержательных комментариев людей — честное «голос не собрать» и предложение обычного
   `/worfy:code-review`, настроенного только на стандарты репозитория.
5. **Предложение при добавлении проекта.** Есть GitHub с историей ревью — одна строка «Собрать ревьюера в стиле вашей
   команды?» с «Собрать» / «Позже». «Позже» больше не спрашивает; кнопка остаётся в настройках проекта. Без истории
   строки нет.
6. **Проверка качества.** После генерации — прогон на 5 старых PR с ревью людей, черновик рядом с настоящими
   комментариями; человек оставляет skill или собирает заново. Число совпавших замечаний — грубая мера.
7. **Обновление.** Без самообновления. Раз в месяц или по кнопке — перечитать новые PR и показать, что поменялось в
   правилах. (Заменяет пункт «Обновление» решения 01.)
8. **Где лежит.** В skill-е слова коллег: только на машине пользователя, в папке Profile-а проекта; никогда в
   репозитории проекта и в репозитории worfy.
9. **Только черновик.** На GitHub ничего не уходит без явного «да» человека.
10. **Структура сгенерированного skill-а** — восемь шагов, раздел «Сгенерированный skill» ниже. Каждое правило
    ссылается на раздел `research.md` в той же частной папке.
11. **Порядок.** После `worfy-skills`. Только Claude Code; Codex позже.

## Как работает

### Частная папка (Ticket-ы 03, 05, 07)

Всё, что генератор узнал о команде, лежит в одной папке Profile-а проекта
(`$HARNESS_HOME/projects/<name>/`, `harness/profiles/README.md:24-38`):

```text
<папка Profile-а>/state/human-review/        «подтвердить» Q2: state/ или своя папка
  meta.json                окно истории, счётчики, даты запусков, курсор последнего PR, verdict, итог проверки
  ignore.json              логины ботов и служебных учётных записей, префиксы текстов агентов — человек правит
  research.md              доказательства: разделы `## R<n> — <заголовок>`
  lint.json                правила проверки черновика (Ticket 04)
  check/                   прогон на 5 старых PR: `<PR>.md` — черновик рядом с настоящими комментариями
  previous/                прошлые `research.md` и `SKILL.md` — для diff правил при обновлении
  raw/                     ответы GitHub текущего запуска; удаляются в конце запуска и при «нет»
  .claude/skills/human-review/
    SKILL.md               сгенерированный skill
    voice-examples.md      настоящие комментарии по уровням, со ссылками
```

- `state/` уже вне истории git папки Harness home: `.gitignore`, который пишет `project-connect`, исключает
  `/projects/*/state/` (`harness/bin/project-connect:108-118`). Слова коллег не попадают в историю git, «Удалить»
  стирает их по-настоящему, правка `.gitignore` и миграция старых Harness home не нужны.
- Новых полей Profile-а нет: наличие `SKILL.md` в этой папке и есть «ревьюер собран».
- Логинов коллег в `SKILL.md`, `voice-examples.md` и `research.md` нет — только ссылки на комментарии и метки
  «ревьюер A», «ревьюер B» в долях. Логины лежат только в `ignore.json` (боты) и в `raw/` на время запуска.

### Сбор истории — `bin/review-history` (Ticket 03)

Скрипт Harness на Node (ADR-0055), без модели. Ходит в GitHub через `gh api graphql` с `GH_TOKEN` аккаунта
`github.account` Profile-а: в Session его кладёт hook `gh-token-env.mjs` (`harness/profiles/README.md:192`), в
приложении — `accountAuth` (`src/main/github/prs.ts:12-16`, `:146`). Глобальный аккаунт `gh` не переключается.

- **GraphQL, страница по 100 PR.** Замер: 100 merged PR — 32 очка из 5 000 в час; 500 PR — около 160 очков, 3%
  часового лимита (исследование, разделы 3–4). REST — только `since` для новых комментариев при обновлении.
  Запросы по одному; при ошибке лимита — ждать `retry-after` / `x-ratelimit-reset`.
- **Окно (решение 3).** PR, обновлённые за последние 12 месяцев, у которых есть ревью; не больше 500 PR. PR,
  одобренные без единого комментария, тоже считаются: из них видно, что команда пропускает молча.
- **Фильтр (решение 3).** Отбрасываются: `author.__typename = Bot` и логины с `[bot]`; логины и префиксы
  `ignore.json` (служебные учётные записи типа `User`, отчёты агентов вроде `VERIFIED (…)` / `REJECTED (…)` —
  исследование, раздел 5); комментарий автора к своему PR. `CONTRIBUTOR` и `NONE` (внешние) идут только как контекст
  нити, не как голос команды. Ответы людей на комментарии ботов остаются.
- **Содержательный комментарий** — после фильтра, не короче 20 знаков собственного текста (без цитат) или с блоком
  `suggestion`, и не только «LGTM», «+1», «thanks», эмодзи. Порог голоса — 30 таких комментариев (решение 4).
- **Режимы.**
  - `review-history fetch` — всё окно в `raw/` (JSONL: PR, ревью с `state` и `commit_id`, комментарии к строкам с
    `path`, `line`, `diff_hunk`, нити с `isResolved`, `isOutdated`, общие комментарии) и оценка ниже. Модель ничего не
    читает.
  - `review-history estimate` — по `raw/`: число PR, ревью по состояниям, комментариев по видам, содержательных
    комментариев, людей-ревьюеров; число знаков текста; **оценка токенов**: знаки ÷ 4 для латиницы, ÷ 2 для
    кириллицы, × число проходов модели, которое называет генератор. Слово «оценка» стоит в выводе. Verdict
    `voice: yes` или `voice: no (N of 30)`.
  - `review-history probe` — тот же фильтр и порог без записи текстов: страницы до 30 содержательных комментариев или
    до конца окна; печатает `voice: yes|no` и счётчики. Его зовёт приложение при добавлении проекта (Ticket 09).
  - `review-history fetch --since <дата>` — только новое, для обновления (Ticket 10).
  - `review-history stats` — механические числа для `research.md`: длины по перцентилям, доли состояний ревью,
    approve без комментариев по размеру PR и по путям, повтор замечания в разных PR, правка кода после комментария
    (commit после `commit_id` комментария меняет его `path`).
  - `review-history clean` — удалить `raw/`.

### Генератор — `/worfy:human-review-setup` (Ticket-ы 06, 07, 08, 10)

Skill plugin-а `worfy` (`harness/skills/human-review-setup/`), тексты английские (ADR-0074). Шаги:

1. **Profile и папка.** `bin/profile --json` → `_resolved.dir`; нет Profile-а — предложить `/worfy:connect-project`.
2. **Сбор и оценка.** `review-history fetch`, затем `estimate`. Показать счётчики и оценку токенов; сказать, что тексты
   коллег уйдут Vendor-у модели, как любой код Session-а (исследование, раздел 8). Показать `ignore.json` — человек
   может дописать логины. Без «да» — `review-history clean` и стоп.
3. **Мало истории.** `voice: no` — сообщение «Голос команды не собрать: N содержательных комментариев людей за M PR,
   нужно 30» и предложение `/worfy:code-review` по стандартам репозитория. В частную папку пишется только `meta.json`
   со счётчиками (без текстов), `raw/` удаляется.
4. **Анализ (Ticket 06).** Subagent-ы читают `raw/` пачками по областям кода и раскладывают каждый комментарий по
   уровню (let go, nit, question, heads-up, followup, argued, blocker) и теме; вместе с `stats` это даёт
   `research.md` — разделы `R<n>` с числами и ссылками на комментарии.
5. **Запись skill-а (Ticket 07)** по шаблону `harness/skills/human-review-setup/template/`, `lint.json`, проверка
   `review-draft-lint --skill` (каждое правило ссылается на существующий раздел).
6. **Проверка на 5 PR (Ticket 08).**
7. **Решение человека.** «Оставить» — `raw/` удаляется, `meta.json` записывает дату. «Собрать заново» — шаги 5–6
   снова, с замечаниями человека. «Отказаться» — папка удаляется.

`--refresh` (Ticket 10) — шаги 2, 4, 5, 6 над новыми PR и показ diff правил.

### Сгенерированный skill (Ticket 07; решение 10)

Шаблон — восемь разделов; генератор заполняет каждый из `research.md`, каждое правило кончается ссылкой `[R<n>]`.

1. **Загрузить PR.** `gh pr view`, diff, файлы, head commit, связанная задача.
2. **Triage.** Что эта команда одобряет молча: bump-ы, backport-ы, сгенерированные файлы, мелкие правки текстов — по
   доле approve без комментариев. «Маленький — не значит безопасный»: исключения, которые показывает история
   (маленькие PR с `CHANGES_REQUESTED` или blocker-комментарием — по путям и видам). Большой или смешанный PR —
   попросить разделить; порог — из истории, где команда просила разделить, иначе — по умолчанию шаблона.
3. **Checklist по областям или репозиториям** — что команда действительно ловит, по темам анализа, с долей.
   Кандидаты ищет `/worfy:code-review`: этот checklist идёт ему ещё одним источником стандартов в бриф оси Standards
   (`harness/skills/code-review/SKILL.md:34-36`, `:62-66`), ось Spec — когда найдена задача PR.
4. **Проверить и оценить.** Каждый кандидат проверяется на head commit (`git show <sha>:<path>`); не проверенный
   становится вопросом. Уровень: let go / nit / question / heads-up / followup / argued / blocker. Список
   «не трогать» — на что команда возражает или что игнорирует.
5. **Голос по уровню.** Длина (медиана и 90-й перцентиль), типичные обороты, регистр (смягчения, оговорки), наклоны
   по областям. `voice-examples.md` — настоящие комментарии по уровням, со ссылками; совпадать по длине и
   температуре, не по словам. Ни один ревьюер не даёт больше трети примеров уровня, когда примеры есть от трёх и
   больше людей.
6. **Состояние ревью.** По умолчанию approve с nit-ами; когда только comment; когда request changes — по долям
   истории.
7. **Черновик** — payload GitHub create-review (`event`, `body`, `comments[]` с `path`, `line`, `side`), уровень
   каждого комментария рядом, в отдельном поле файла черновика. `review-draft-lint` проверяет черновик.
8. **Показать человеку.** Отправка — только после его «да» в разговоре; в Session без человека skill останавливается на
   черновике.

### Проверка черновика — `bin/review-draft-lint` (Ticket 04)

Скрипт Harness на Node. Вход — файл черновика `{ payload, tiers }` и `lint.json`. Exit 0 — чисто, 1 — находки (по
строке на каждую: комментарий, правило, что не так), 2 — ошибка входа.

- длина комментария больше предела его уровня из `lint.json`;
- следы workflow — те же правила, что у `bin/silent-check` (имя Epic-а, `<epic>/<NN>`, `Ticket <N>`, путь Workflow
  folder, `.scratch`, `HANDOFF`; `harness/bin/silent-check:14-20`), всегда, в любом режиме проекта; правила берутся
  из одного модуля, второй копии нет;
- строки авторства AI (`Co-Authored-By: Claude`, `Generated with [Claude Code]`, «as an AI»);
- личные данные — `harness/lib/privacy.cjs` (`findings`: путь домашней папки, имя машины, email, токен);
- слова `lint.json.forbidden`, которые человек дописал сам.

`review-draft-lint --skill <папка>` — каждое правило `SKILL.md` кончается `[R<n>]`, и такой раздел есть в
`research.md`.

Формат `lint.json` (`schema: 1`): `tiers.<уровень>.max_chars`, `forbidden: string[]`. Формат черновика:
`payload` — тело запроса `POST /repos/{o}/{r}/pulls/{n}/reviews` как есть; `tiers` — массив уровней в порядке
`payload.comments`, `body_tier` — уровень общего текста. Оба формата фиксирует этот spec, чтобы Ticket-ы 04 и 07 шли
независимо.

### Загрузка в Session (Ticket 05)

`sessionOptions` кладёт папку карточек Canvas в `additionalDirectories` (`src/main/vendors/claude/options.ts:571`).
Claude Code грузит `.claude/skills/` из каталога, добавленного так (исследование, раздел 9; живым запуском не
проверено). Ticket 05 сначала проверяет это на dev-сборке, потом добавляет частную папку вторым элементом.

- Папку получают Session-ы, которые ведёт человек: Orchestrator, «New session», «Ship ticket». Session без человека
  (`unattended`, Autopilot: `permissionMode` там `bypassPermissions`, `options.ts:533`) её не получает: там некому
  сказать «да».
- `skills.allowed` Profile-а (ADR-0084) выключает только plugin-ы пользователя и skills `~/.claude/skills` по имени
  (`options.ts:402-409`); skill из `additionalDirectories` он не трогает, test это закрепляет.
- Если проверка покажет, что skills из `additionalDirectories` не грузятся, — запасной путь «подтвердить» Q1 (б).

### Предложение при добавлении и кнопка (Ticket 09)

- После Connect (`src/main/projects/connect.ts`) приложение в фоне зовёт `review-history probe` через
  `runHarnessScript` (`src/main/workflow/profile.ts:397`). `voice: yes` — `action`-toast Project-а (держится до
  закрытия, показывается, пока Project активен; `docs/features/notifications.md`, «Toasts») с текстом и кнопками
  «подтвердить» Q7. `voice: no`, нет `origin` на GitHub, нет `gh`, ошибка — строки нет, без сообщения об ошибке.
- «Позже» или закрытие toast-а — `humanReview.offer: "later"` в настройках Project-а
  (`<папка данных Project-а>/settings.json`, `src/main/projects/settings.ts:1-2`); больше не спрашивать.
- «Собрать» — новая Session Node в корне Project-а с первым сообщением `/worfy:human-review-setup`, как «Ship ticket»
  (`src/main/actions/launch.ts:10-16`), всегда Claude Code.
- Project settings (`src/renderer/shell/ProjectSettings.tsx`) — раздел «Team reviewer»: состояние (не собран / собран
  <дата>, N PR / мало истории: N из 30) и кнопки «Build» или «Update» и «Delete». «Delete» удаляет частную папку.

### Обновление (Ticket 10; решение 7)

- Напоминание: при активации Project-а, если `meta.json` старше 30 дней и `offer` не `"never"`, — `action`-toast
  «Обновить ревьюера команды?». Сам ничего не читает и токенов не тратит (Q8).
- «Update» в toast-е и в Project settings — Session с `/worfy:human-review-setup --refresh`: `fetch --since`
  последней даты, анализ новых PR вместе с прежним `research.md`, новый `SKILL.md` в черновик, diff правил
  (добавлено / изменено / убрано, у каждого — раздел `R<n>`), проверка на 5 PR. Человек принимает — старые файлы
  уходят в `previous/`; отказывается — всё остаётся как было.

## Сгенерированное и решения без владельца

1. **Сначала данные, потом оценка.** `fetch` идёт до оценки: он стоит только очки GitHub API (около 160 из 5 000 в
   час), модель ничего не читает. Оценка токенов поэтому считается по настоящим текстам, а не по догадке. При «нет»
   `raw/` удаляется сразу.
2. **Логинов коллег в сгенерированных файлах нет.** Голос — вся команда (решение 2), имя не нужно; ссылки на
   комментарии остаются (решение 10: `voice-examples.md` со ссылками).
3. **Доля одного человека в примерах — не больше трети** уровня, когда примеры есть от трёх и больше людей. Это
   проверяемая форма решения «одного не копировать».
4. **Сгенерированный skill вызывается моделью** на «отревьюй PR» (без `disable-model-invocation`): отправка всё равно
   ждёт «да», а Session без человека skill не получает.
5. **Кандидатов ищет `/worfy:code-review`.** Сгенерированный skill — слой над ним: checklist команды в бриф Standards,
   потом проверка, уровень и голос (исследование, раздел 9).
6. **Язык.** Инструкции сгенерированного skill-а — английские (как skills plugin-а); примеры голоса — как в истории;
   черновик — на языке, на котором команда пишет ревью.
7. **Кнопка «Delete»** в Project settings удаляет частную папку одним действием (исследование, раздел 8).
8. **Codex.** Генератор говорит, что работает в Session-ах Claude Code; в Session Codex частная папка не подключается.

## Риски

1. **Skill из `additionalDirectories` не грузится.** Исследование видело это в документации, не в запуске. Ticket 05

2. **Голос совпал с одним человеком.** Если почти все ревью пишет один человек, «вся команда» и есть он. Генератор
   говорит об этом прямо («80% комментариев — от одного ревьюера») и держит правило трети в примерах; голос всё равно
   строится по статистике всех.
3. **Утечка слов коллег.** Тексты уходят Vendor-у модели (сказано до «да»); на диске — только в `state/` вне истории

   `evidence-check` и правило Ticket-ов ниже.
4. **Сгенерированный черновик выдаёт workflow.** Ссылки на Ticket-ы, `.scratch`, строки авторства в ревью для
   коллег. `review-draft-lint` ловит их всегда, не только в Silent mode.
5. **Совпадение имён.** Stage Pipeline-а `human-review` (`harness/profiles/README.md:188`) — это ревью человека в
   Pipeline, а не этот skill. Страница Feature разводит их явно; если владелец захочет другое имя skill-а — это правка
   шаблона Ticket-а 07.
6. **Проверка на 5 PR видит ответы.** Если 5 PR были в истории анализа, совпадения завышены. Q5.
7. **Порог 30 на маленьком проекте.** `probe` может показать строку по 30 комментариям, а анализ — дать бедный skill.
   Проверка на 5 PR и её грубая мера показывают это человеку до «оставить».

   PR без строки сравнивает только судья.
