Kind: pr · Epic: worfy-assistant · Ticket: 08 · PR: - · Language: ru

## 1. Что было не так

2026-11-13 5-часовой лимит остановил трёх implementer-ов, и продолжили их через 41 час. Auto-continue в ту ночь
ничего не отправил, а после сброса лимита простаивающий Orchestrator, у которого не было ни одной живой background task,
не будил никто: Auto-continue отвечает только на ход Orchestrator-а, закончившийся отказом. Session-ы на Canvas после
сброса Limits не продолжал никто. Действий, которые main делает сам по режиму обязанности (Ticket 07), не было, как и
журнала таких действий.

- Требование: [Что строить](../issues/08-закрытый-список-действий.md#что-строить), причина — [Итог](../issues/08-закрытый-список-действий.md#итог)

## 3. Одна дверь: список, обязанность, режим, Session — и только потом текст

Code: `src/main/assistant/actions/closed-list.ts:124-153` · key lines: 127, 131, 133, 139, 146, 147, 151

```ts
  private verdict(request: ActionRequest): Verdict {
    const verdict: Verdict = { refusal: null, shown: null, mode: null, sessionId: null, wait: null }
    const refuse = (refusal: ActionRefusal): Verdict => ({ ...verdict, refusal })
    if (!isClosedAction(request.action)) return refuse('not-in-list')
    verdict.shown = this.deps.shown().find((each) => each.item.id === request.itemId) ?? null
    if (verdict.shown === null) return refuse('no-item')
    const proposal = verdict.shown.proposals.find((each) => each.action === request.action)
    if (proposal === undefined) return refuse('not-proposed')
    verdict.mode = proposal.mode
    if (!modeAllows(proposal.mode, request.by)) return refuse('mode')
    const item = verdict.shown.item
    if (item.subject.kind !== 'session' || item.projectId === null) return refuse('no-target')
    verdict.sessionId = item.subject.id
    const orchestrator = this.deps.orchestratorOf(item.projectId)
    // An Orchestrator is woken, never continued: Auto-continue answers its refused turns (orchestrator-continue.ts).
    if ((request.action === 'wake-orchestrator') !== (orchestrator === item.subject.id)) return refuse('no-target')
    const session = this.deps.session(item.subject.id)
    if (session === null) return refuse('no-target')
    if (session.unattended) return refuse('run-owns')
    if (session.state !== 'idle') return refuse('busy')
    const now = this.deps.now()
    if (request.action === 'wake-orchestrator') {
      if (session.backgroundTasks().length > 0 || this.deps.continuing?.(item.projectId) === true) return refuse('busy')
      if (!limitsCheck(this.deps.limits(), 'on-demand', now).ok) return refuse('limits')
      return verdict
    }
    verdict.wait = this.deps.waits.wait(item.subject.id)
    if (verdict.wait === null || verdict.wait.until > now) return refuse('limits')
    return verdict
  }
```

- Что делает: решает, можно ли выполнить действие, и возвращает первую причину отказа. Действие должно быть в
  закрытом списке. Обязанность должна сейчас показывать пункт и предлагать это действие. Режим должен разрешать
  действие тому, кто просит: `ask` разрешает только пользователю. Будят только Orchestrator, продолжают только
  Session, которая не Orchestrator. Session должна быть жива, без Run-а и idle. Для побудки нужны ещё три условия: нет
  живых background task, Auto-continue не ждёт, Limits не отказывают (`limitsCheck` в режиме `on-demand`). Для
  продолжения ожидание сброса Limits должно истечь.
- Почему здесь: ADR-0114, пункт 4 и граница 3 — сам Assistant делает только действия закрытого списка; «Решения» тикета:
  действия идут по режиму обязанности. Почему отказ вычисляется раньше, чем текст, — чтобы Ticket 09 (`worfy-app`) не
  мог отправить ничего, кроме текстов main. В запросе нет поля для текста.
- Без него: Assistant через `worfy-app` мог бы разбудить Session, которой владеет Run, или отправить сообщение
  Orchestrator-у посреди хода. Побудка ушла бы, пока Limits ещё отказывают.
- Требование: [Решения](../issues/08-закрытый-список-действий.md#решения), [Готово, когда, пункты 2–4](../issues/08-закрытый-список-действий.md#готово-когда)
- Риски и пробелы test-ов: каждая проверка зовёт `shown()`, то есть `Duties.look`. Пунктов у ядра немного (медиана 8,5
  в день, spec), поэтому квадратичный проход не измерялся.

## 4. Действие пишет строку журнала, сделано оно или нет

Code: `src/main/assistant/actions/closed-list.ts:89-105` · key lines: 92, 96, 98, 103

```ts
  /** Does the action if every check holds; answers the journal line, written whatever the outcome. */
  act(request: ActionRequest): ActionResult {
    const verdict = this.verdict(request)
    if (verdict.refusal !== null) return this.refused(request, verdict, verdict.refusal)
    const action = request.action as ClosedAction
    const sessionId = verdict.sessionId as string
    const now = this.deps.now()
    const text = action === 'wake-orchestrator' ? WAKE_ORCHESTRATOR_TEXT : continueSessionText((verdict.wait as SessionLimitsWait).since, now)
    try {
      this.deps.session(sessionId)?.send(text)
    } catch {
      return this.refused(request, verdict, 'failed')
    }
    if (action === 'continue-session') this.deps.waits.resume(sessionId)
    const line = this.write(this.line(request, verdict, { outcome: 'done', text }))
    return { ok: true, line }
  }
```

- Что делает: если вердикт положительный, отправляет текст main и снимает ожидание Session, а потом пишет строку
  `done` с пунктом, обязанностью, режимом, Session и самим текстом. Если отказ — строка `refused` с причиной. Если
  Session не приняла сообщение — `failed`, и ожидание остаётся.
- Почему здесь: граница 6 — каждое действие пишется в журнал вместе с пунктом, который его вызвал. Файл журнала —
  `<WORFY_DATA_DIR>/assistant/journal.json` (ADR-0005, запись Ticket 08).
- Без него: не осталось бы следа, что Assistant сделал сам и почему; нечего было бы показать окну (Ticket 14) и
  `worfy-app` (Ticket 09).
- Требование: [Готово, когда, пункт 5](../issues/08-закрытый-список-действий.md#готово-когда)
- Риски и пробелы test-ов: если журнал не записался, это пишется в log, а действие остаётся сделанным. Test-а на
  журнал, который бросает ошибку, нет.

## 5. Что main делает сам: продолжить сразу, разбудить один раз, потом передать модели

Code: `src/main/assistant/actions/auto.ts:73-91` · key lines: 76, 78, 84, 85, 89

```ts
  const pass = (): void => {
    for (const shown of deps.shown()) {
      for (const proposal of shown.proposals) {
        if (!isClosedAction(proposal.action) || (proposal.mode !== 'self' && proposal.mode !== 'pre-approved')) continue
        const request: ActionRequest = { action: proposal.action, itemId: shown.item.id, by: 'main' }
        if (deps.list.check(request) !== null) continue
        if (proposal.action === 'continue-session') {
          deps.list.act(request)
          continue
        }
        const target = shown.item.subject.id
        if (woken.has(target) || wakesToday(target, deps.now()) >= WAKES_PER_DAY) {
          if (!escalatedBefore(shown.item.id)) deps.list.escalate(shown.item.id)
          continue
        }
        if (deps.list.act(request).ok) woken.add(target)
      }
    }
  }
```

- Что делает: просматривает то, что показывают обязанности. Если режим `self` или `pre-approved` и проверка прошла,
  выполняет действие с `by: 'main'`. Orchestrator будится один раз. Если побудка не помогла — Orchestrator не запустил
  Subagent и человек ему не писал — или побудок за 24 часа уже `WAKES_PER_DAY`, пункт один раз уходит модели
  (`escalate`).
- Почему здесь: решение 13 — действия закрытого списка main делает без модели. Срочное будит модель, когда «работа стоит
  и закрытый список не помог» (spec, «Решение о пробуждении»; `escalate` Ticket-а 06). Порог в шесть побудок — решено без
  владельца («Итог», пункт 3).
- Без него: каждый простой ждал бы щелчка пользователя. Если бы побудка ничего не дала, Orchestrator будили бы снова и
  снова каждые 15 минут.
- Требование: [Готово, когда, пункты 2 и 3](../issues/08-закрытый-список-действий.md#готово-когда)
- Риски и пробелы test-ов: после перезапуска worfy набор `woken` пуст, поэтому возможна ещё одна побудка (её
  ограничивает `WAKES_PER_DAY` из журнала). Перезапуск test не проверяет.

## 6. Session на Canvas ждёт сброса Limits на виду

Code: `src/main/assistant/actions/limits-waits.ts:147-165` · key lines: 150, 152, 154, 161, 164

```ts
  private turnEnded(sessionId: string, entry: Entry, event: Extract<AgentEvent, { type: 'result' }>): void {
    const session = this.deps.session(sessionId)
    // An Orchestrator has Auto-continue, a run answers the Session it owns: neither waits here.
    if (session === null || session.unattended || this.deps.isOrchestrator(sessionId)) return this.end(sessionId, entry)
    const message = event.error ?? (event.isError ? event.text : null)
    const hit = entry.wait.hitOf({ isError: event.isError, interrupted: event.interrupted, message })
    if (hit === null) return this.end(sessionId, entry)
    const plan = entry.wait.plan(hit, true)
    if (plan.kind === 'quota' || plan.kind === 'give-up') {
      this.end(sessionId, entry)
      this.notice(sessionId, plan.kind === 'quota' ? 'worfy: the Limits refused this turn by a quota, and nothing resets' : `worfy: not waiting for the Limits: ${plan.reason}`)
      return
    }
    entry.since ??= this.now()
    entry.wait.wait(plan.at, () => this.tell(sessionId))
    this.tell(sessionId)
    const at = clockText(plan.at, this.now())
    this.notice(sessionId, plan.kind === 'at' ? `worfy: waiting for the Limits, they reset at ${at}` : `worfy: waiting for the Limits, no reset time reported, next try at ${at}`)
  }
```

- Что делает: в конце хода любой Session, кроме Orchestrator-а и Session с Run-ом, отказ Limits распознаётся так же,
  как у Run-а (`LimitsWait.hitOf`), и Session ждёт сброса окна плюс запас. Ожидание видно через `wait()` и строкой worfy в
  чате Session. Когда ожидание истекает, его слушатели об этом узнают, и проход main продолжает Session (шаг 5).
- Почему здесь: тикет забирает идею 6 worfy-limits-out — «любая Session ждёт сброса Limits на виду» — и меняет решение 3
  worfy-retry для Session-ов на Canvas (ADR-0114).
- Без него: Session на Canvas, остановленную лимитом ночью, утром продолжал бы только пользователь.
- Требование: [Готово, когда, пункт 3](../issues/08-закрытый-список-действий.md#готово-когда)
- Риски и пробелы test-ов: Codex перед продолжением заново не читается (`shortcut:` в шапке файла). Ожидание живёт только
  в памяти и не переживает перезапуск worfy («Итог», пункт 5).

1. Почему побудка Orchestrator-а ждёт, пока Limits перестанут отказывать, а не уходит сразу после отказа?
