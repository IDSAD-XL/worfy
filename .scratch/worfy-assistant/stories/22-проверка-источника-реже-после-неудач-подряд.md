# Code story — worfy-assistant 22: Проверка источника реже после неудач подряд; ответ, где все записи отказаны по форме, — неудача

Kind: pr · Epic: worfy-assistant · Ticket: 22 · PR: - · Language: ru

## 1. Что было не так

Проверка Slack или Jira, у которой сломан connector или падает вызов, повторялась через обычный интервал без конца:
Slack — каждые 10 минут, и каждый вызов, дошедший до модели, оплачивался. Неудачи подряд нигде не считались. Второй
пробел: ответ, в котором все записи отказаны по форме, но их меньше предела, считался успехом, и `since` уезжал
вперёд — сообщения этого окна пропадали без пункта.

- Требование: [Что происходит](../issues/22-проверка-источника-реже-после-неудач-подряд.md#что-происходит)

## 2. Ответ без единой годной записи — неудача run-а


- Что делает: если в ответе есть записи и ни одна не прошла форму, run бросает через тот же `fail`, что и остальные

  без записей проходит дальше и остаётся успехом.
- Почему здесь: Ticket называет `sourceCheckRun` и строки 88–119 этого файла; проверка стоит до ingest и до ветки
  «ответ на пределе», поэтому ловит ответ любого размера.
- Без него: планировщик записал бы успех, `since` переехал бы на начало run-а, и сообщения окна не пришли бы никогда.
- Требование: [Что строить, пункт 1](../issues/22-проверка-источника-реже-после-неудач-подряд.md#что-строить)
- Риски и пробелы test-ов: ответ, где часть записей годна, а часть нет, остаётся успехом — годные становятся
  пунктами, отказанные только пишутся в журнал (так было и раньше).

## 3. Интервал после неудач подряд

Code: `src/main/assistant/schedule/scheduler.ts:54-76` · key lines: 55, 58, 61, 68, 72, 74, 75

```ts
/** How many failures in a row a check of BACKOFF_KINDS takes at its usual interval: the next one makes it wait longer. Decided without the owner (ticket 22). */
export const BACKOFF_AFTER_FAILURES = 3

/** How many times longer a backed-off check waits with each further failure in a row. Decided without the owner (ticket 22). */
export const BACKOFF_FACTOR = 2

/** The longest a backed-off check waits: the upper bound of a check's interval in the settings, a day. */
export const BACKOFF_CEILING_MS = CHECK_INTERVAL_BOUNDS.max * MINUTE_MS

/**
 * The kinds that back off: the checks of outside sources, whose every call is paid and whose window `since…now` grows
 * with each failure. The CI of the main branch (`main-ci`, ticket 21) keeps its interval: its read costs nothing, and
 * a red main branch must be seen soon after the network comes back. Decided without the owner (ticket 22).
 */
export const BACKOFF_KINDS: readonly CheckKind[] = SOURCE_CHECK_KINDS

/** The interval of a check of `kind` after `failures` failures in a row, in ms: the usual one until the backoff. */
export function backedOffInterval(kind: CheckKind, interval: number, failures: number): number {
  if (!BACKOFF_KINDS.includes(kind) || failures < BACKOFF_AFTER_FAILURES) return interval
  // The exponent is bounded so a long count cannot overflow to Infinity: the ceiling is reached long before.
  const steps = Math.min(failures - BACKOFF_AFTER_FAILURES + 1, 32)
  return Math.max(interval, Math.min(BACKOFF_CEILING_MS, interval * BACKOFF_FACTOR ** steps))
}
```

- Что делает: первые две неудачи подряд не меняют интервал; после третьей интервал удваивается, после каждой
  следующей — ещё раз, до суток. `main-ci` в набор не входит. Интервал, выбранный больше потолка, не укорачивается.
- Почему здесь: Ticket велит считать backoff в main, в планировщике проверок, и рекомендует N = 3, удвоение и
  потолок — верхнюю границу интервала в настройках (`CHECK_INTERVAL_BOUNDS.max`). Решение по `main-ci` — в «Решено без
  владельца» Ticket-а: его run не бросает на ошибках gh, неудачей для него бывает только превышение времени.
- Без него: сломанный Slack-connector оплачивал бы вызов каждые 10 минут без конца.
- Требование: [Что строить, пункты 2 и 5](../issues/22-проверка-источника-реже-после-неудач-подряд.md#что-строить)
- Риски и пробелы test-ов: верхняя граница степени (32) test-ом не проверяется — при интервале от 5 минут потолок
  достигается на восьмом шаге.

## 5. Счёт неудач в метках и две строки log

Code: `src/main/assistant/schedule/scheduler.ts:294-300` · key lines: 294, 296, 297, 300

```ts
      const failures = this.readMarks()[kind]?.failures ?? 0
      // A run that covered only part of its time moves `since` that far, never past its own start.
      if (succeeded) this.mark(kind, { succeededAt: coveredUntil === undefined ? now : Math.min(now, coveredUntil), failures: undefined })
      else if (BACKOFF_KINDS.includes(kind)) this.mark(kind, { failures: failures + 1 })
      entry.running = false
      entry.spread = this.draw()
      this.noteBackoff(kind, entry, succeeded ? 0 : failures + 1, failures)
```

- Что делает: неудача — исключение или превышение `CHECK_RUN_TIMEOUT_MS`, обе приходят сюда с `succeeded = false` —
  прибавляет единицу в метке вида; успех убирает поле. Метки пишутся в `assistant-check-marks.json`, поэтому счёт
  переживает перезапуск. `noteBackoff` пишет одну строку, когда счёт дошёл до трёх, и одну, когда успех снял backoff.
- Почему здесь: Ticket велит хранить счёт в метках (`checkMarkSchema`) и называет `launch`, конец run-а. Поле
  необязательное и в схеме с `.catch(undefined)`: число, которое схема отказывает, читается как «неудач нет», и файл
  не откладывается в сторону. Сборка до Ticket-а читает файл с новым полем, потому что её `z.object` не строгий.
- Без него: после перезапуска worfy сломанный источник снова шёл бы по обычному интервалу.
- Требование: [Что строить, пункты 3 и 4](../issues/22-проверка-источника-реже-после-неудач-подряд.md#что-строить)
- Риски и пробелы test-ов: пользователь узнаёт о backoff только из log main — предложение строки в настройках записано
  в «Вне скоупа» Ticket-а.

## 6. Человек снимает backoff: включил проверку снова или сменил интервал

Code: `src/main/assistant/schedule/scheduler.ts:198-212` · key lines: 202, 203, 206, 207

```ts
  reschedule(): void {
    const settings = this.options.settings()
    for (const [kind, entry] of this.entries) {
      const { enabled, intervalMinutes } = checkSettingsOf(settings, kind)
      const turnedOn = enabled && !entry.seen.enabled
      const newInterval = intervalMinutes !== entry.seen.intervalMinutes
      entry.seen = { enabled, intervalMinutes }
      const failures = this.readMarks()[kind]?.failures
      if ((turnedOn || newInterval) && failures !== undefined) {
        this.mark(kind, { failures: undefined })
        if (failures >= BACKOFF_AFTER_FAILURES) console.info(`[assistant] the ${kind} check was ${turnedOn ? 'turned on again' : 'given another interval'}: back to its usual interval`)
      }
    }
    this.plan()
  }
```

- Что делает: при изменении настроек (`reschedule`, его зовёт `startCheckScheduler` на каждое изменение app settings)
  сравнивает для каждого вида «включён» и интервал с прошлым разом. Если вид включили снова или сменили ему интервал,
  счёт неудач обнуляется, и следующий run идёт через обычный интервал. Другие поля и другие виды счёт не трогают.
- Почему здесь: review round 1 нашёл, что, кроме успеха, backoff ничем не снимался: кнопки Check now в UI нет
  (`runNow` вызывают только test-ы, кнопка — Ticket 15), а выключение и включение счёт сохраняли. Сломанный ночью Slack
  после входа утром ждал бы до 10 часов. Решение 5 в «Решено без владельца» Ticket-а.
- Без него: человек, который починил connector, не может вернуть обычный интервал до первого успешного run-а.
- Требование: [Что строить, пункт 2](../issues/22-проверка-источника-реже-после-неудач-подряд.md#что-строить)
- Риски и пробелы test-ов: изменение настроек, пока worfy закрыт, счёт не снимает — после перезапуска нет «прошлого
  раза» для сравнения, и счёт переживает перезапуск, как велит Ticket.

## Проверить себя

1. Почему ответ из пяти записей, все отказанные по форме, нельзя считать успехом, если пустой ответ — успех?
   - Ответ: успех двигает `since` на начало run-а. Пустой ответ значит, что сообщений не было, а отказанные записи —
     что сообщения были, но ни одно не стало пунктом; после успеха следующий run их больше не спросит.
   - Lines: `src/main/assistant/sources/connector-check.ts:114-115`
2. Почему `main-ci` не уходит в backoff?
   - Ответ: его чтение бесплатное, а красную основную ветку нужно увидеть вскоре после того, как сеть вернулась; к
     тому же его run не бросает на ошибках gh, так что неудачей для него бывает только превышение времени.
   - Lines: `src/main/assistant/schedule/scheduler.ts:63-68`
3. Что будет с числом неудач, если файл меток откроет сборка worfy до этого Ticket-а и потом запишет его?
   - Ответ: она прочитает файл, отбросив поле (её объект не строгий), и при записи поле пропадёт — счёт начнётся с нуля,
     но файл не отложится в сторону и метки времени сохранятся.
   - Lines: `src/main/assistant/schedule/scheduler.ts:97-103`
