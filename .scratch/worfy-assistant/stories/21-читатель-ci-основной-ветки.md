## 2. Один GraphQL-запрос — состояние ветки, начало красной серии и её PR

Code: `src/main/github/main-ci.ts:153-170` · key lines: 160, 162, 166, 167, 169

```ts
export async function readMainBranchCi(gh: (args: readonly string[]) => Promise<string>, repo: string, now: () => number = Date.now): Promise<MainBranchCi | null> {
  const [owner = '', name = ''] = repo.split('/')
  const stdout = await gh(['api', 'graphql', '-f', `query=${MAIN_CI_QUERY}`, '-f', `owner=${owner}`, '-f', `name=${name}`])
  const ref = answerSchema.parse(JSON.parse(stdout)).data.repository.defaultBranchRef
  if (ref == null) return null
  const branch = ref.name
  const commits = ref.target.history.nodes
  const newest = commits.findIndex((commit) => stateOf(commit) !== null)
  if (newest === -1) return null
  if (stateOf(commits[newest]!) === 'passing') return { repo, branch, state: 'green' }
  let first = commits[newest]!
  for (const commit of commits.slice(newest + 1)) {
    const state = stateOf(commit)
    if (state === 'passing') break
    if (state === 'failing') first = commit
  }
  return { repo, branch, state: 'red', commit: first.oid, redSince: failedAt(first) ?? now(), pr: prOf(first, branch) }
}
```

- Что делает: читает 20 последних commit-ов ветки по умолчанию с их check-ами и PR. Состояние ветки — состояние
  последнего commit-а с итогом: commit, у которого check-и ещё идут или которого CI пропустил, ничего не говорит.
  Красная серия начинается с самого старого красного commit-а после последнего зелёного; от него — время «покраснела» и
  PR.
- Почему здесь: Ticket называет образцами `src/main/github/deployments.ts` и `statusCheckRollup` из
  `src/main/github/prs.ts`; запрос — `defaultBranchRef.target.history` со `statusCheckRollup` и
  `associatedPullRequests`, как в пункте 1 «Что строить». Отметки агентов отсекает тот же `ciOf`, что и для PR.
- Без него: `mainCiAttention` некому вызвать, пункта нет.
- Требование: [Что строить](../issues/21-читатель-ci-основной-ветки.md#что-строить)
- Риски и пробелы test-ов: ответы gh в fixture-ах записаны в форме GraphQL-ответа GitHub, но не сняты с настоящего gh
  (test-ам запрещена сеть). Серия длиннее 20 commit-ов начинается с самого старого увиденного, у такой серии меняется
  `revision`, и пункт поднимется второй раз.

## 3. Отменённый run не делает ветку красной

Code: `src/main/github/main-ci.ts:122-127` · key lines: 125

```ts
function stateOf(commit: Commit): 'failing' | 'passing' | null {
  const checks = checksOf(commit)
  const state = ciOf(checks)
  if (state === 'failing' && checks.every((check) => (failureOf(check) ?? 'CANCELLED') === 'CANCELLED')) return null
  return state === 'failing' || state === 'passing' ? state : null
}
```

- Что делает: commit, у которого все упавшие check-и — отменённые run-ы, ничего не говорит, и состояние ветки решает
  commit до него. Отменённый run не считается и временем «покраснела». Отметки агентов отсекаются и из состояния, и из
  времени (`checksOf` с `isMark`).
- Почему здесь: review round 1 — при `concurrency: cancel-in-progress` на основной ветке каждый вытесненный run читался
  красным, и через порог появлялся ложный пункт с невиновным PR. Правило проекта — ADR-0068: отменённый run, который
  вытеснил более новый, — не красный.
- Без него: ложный «CI основной ветки красный» после каждого вытесненного run-а.
- Требование: [Что строить](../issues/21-читатель-ci-основной-ветки.md#что-строить)
- Риски и пробелы test-ов: commit, у которого отменён один необязательный job, а остальные зелёные, тоже ничего не
  говорит, и ветку решает commit до него.

## 4. Проверка обходит Project-ы; красное условие живёт, пока его подтверждает чтение

Code: `src/main/assistant/duties/main-ci-check.ts:76-111` · key lines: 86, 92, 94, 96, 97, 99, 105, 109

```ts
  const run: CheckRun = async () => {
    const started = generation
    const red = new Map<string, Armed>()
    for (const project of options.projects()) {
      if (generation !== started) break
      let repos: readonly string[]
      try {
        repos = await options.repos(project.root)
        logged.delete(project.root)
      } catch (error) {
        failed(project.root, `the repositories of ${project.root}`, error)
        continue
      }
      for (const repo of repos) {
        const key = `${project.root}\n${repo}`
        try {
          const read = await readMainBranchCi((args) => options.gh(project.root, args), repo, options.now)
          logged.delete(key)
          if (generation !== started) break
          if (read === null) continue
          mainCiAttention(options.core, { projectId: project.id, ...read }, options.thresholdMs())
          if (read.state === 'red') red.set(key, { projectId: project.id, id: mainCiId(repo, read.branch) })
        } catch (error) {
          failed(key, `the main branch of ${repo}`, error)
        }
      }
    }
    if (generation !== started) {
      // disarm() came while this run read: what it armed before that goes too.
      drop(red.values())
      return
    }
    // Armed before and not found red again by this run: the read failed, or the repository is gone.
    drop([...armed].flatMap(([key, condition]) => (red.get(key)?.id === condition.id ? [] : [condition])))
    armed = red
  }
```

- Что делает: для каждого Project-а берёт его репозитории на github.com и отдаёт прочитанное в `mainCiAttention` с
  порогом обязанности. Project без репозитория не даёт ни одного вызова gh. Ошибка gh, отказ входа для аккаунта
  Project-а или нечитаемый ответ пишутся в log один раз, пока причина та же, и пунктом не становятся. Красное условие,
  которое этот run не подтвердил (чтение упало, репозиторий ушёл), снимается через `AttentionCore.disarm`: уже
  поднятый пункт остаётся. `disarm()` посреди run-а не даёт ему взвести ничего нового.
- Почему здесь: пункты 3 и 4 «Что строить» — прочитанное идёт в `mainCiAttention`, ошибка — в log. Снятие условий —
  review round 1: условие, взведённое `core.expect`, срабатывало и после того, как чтение прекратилось. В приложении gh
  идёт через `sharedPrTracker().gh` (`src/main/assistant/duties/app.ts`), то есть аккаунтом, которым worfy читает PR
  этого Project-а.
- Без него: один упавший Project остановил бы чтение остальных, ошибка раз в 10 минут засоряла бы log, а красное
  условие поднимало бы пункт без подтверждения.
- Требование: [Готово, когда](../issues/21-читатель-ci-основной-ветки.md#готово-когда)
- Риски и пробелы test-ов: связка в `app.ts` (`remoteRepos`, `projectLayouts`, `sharedPrTracker`, настройки проверок)
  unit test-ом не покрыта; её проверяет typecheck. Проверка `generation` в начале цикла по Project-ам только экономит
  вызовы gh после `disarm()`; test на два Project-а её не ловит.

## 5. Проверка в планировщике — только пока обязанность включена

Code: `src/main/assistant/duties/main-ci-check.ts:139-161` · key lines: 142, 143, 147, 151, 159

```ts
export function followMainCiDuty(scheduler: Pick<CheckScheduler, 'register'>, duty: MainCiDuty, check: MainCiCheck, setting?: MainCiSwitch): () => void {
  let unregister: (() => void) | null = null
  const follow = (): void => {
    const enabled = duty.enabled(MAIN_CI_DUTY)
    if (enabled && unregister === null) unregister = scheduler.register(MAIN_CI_KIND, check.run)
    else if (!enabled && unregister !== null) {
      unregister()
      unregister = null
      check.disarm()
    }
  }
  const switchedOff = (): void => {
    if (setting?.enabled() === false) check.disarm()
  }
  const stops = [duty.onChange(follow), ...(setting === undefined ? [] : [setting.onChange(switchedOff)])]
  follow()
  return () => {
    for (const stop of stops) stop()
    unregister?.()
    unregister = null
    check.disarm()
  }
}
```

- Что делает: регистрирует проверку вида `main-ci` в планировщике Ticket-а 04, пока обязанность включена, и снимает её,
  когда пользователь обязанность выключил. `Duties` для этого получил `enabled(id)` и `onChange(listener)`. Выключение
  обязанности, выключение проверки в настройках и остановка снимают всё, что проверка взвела.
- Почему здесь: пункт 2 «Что строить» — расписание только через планировщик Ticket-а 04 и только при включённой
  обязанности; интервал, сон вне work hours и догон после сна Mac приходят оттуда.
- Без него: проверка ходила бы в GitHub и при выключенной обязанности.
- Требование: [Что строить](../issues/21-читатель-ci-основной-ветки.md#что-строить)
- Риски и пробелы test-ов: пауза обязанности проверку не снимает — только выключение.

## 7. Что сознательно не меняли

Marker `main-red` у land не читается: это процесс worfy, обязанности его не называют (раздел «Решения» тикета). Вид
`main-ci` не получил обязанности источника: встроенные обязанности источников строятся из `SOURCE_CHECK_KINDS`
(Slack и Jira), а пункты `ci` берёт «CI основной ветки красный».

## Проверить себя

1. Последний commit основной ветки ещё гоняет check-и, а предыдущий красный. Что скажет чтение и почему?
   - Ответ: «красная»: commit без итога ничего не говорит, и состояние ветки решает последний commit с итогом.
   - Lines: `src/main/github/main-ci.ts:160-162`
2. Пользователь выключил обязанность, а проверка в этот момент уже зарегистрирована. Что произойдёт с вызовами gh?
   - Ответ: `onChange` вызовет `follow`: тот снимет проверку из планировщика, новых запусков не будет, а `disarm()` снимет
     красные условия, которые ещё не подняли пункт.
   - Lines: `src/main/assistant/duties/main-ci-check.ts:141-149`
3. Последний commit — отменённый run, а до него зелёный commit. Почему ветка зелёная, и что было бы без этого правила?
   - Ответ: commit, у которого все падения — отменённые run-ы, ничего не говорит, и решает зелёный commit до него; иначе
     каждый вытесненный run давал бы через порог ложный пункт с невиновным PR.
   - Lines: `src/main/github/main-ci.ts:122-127`
