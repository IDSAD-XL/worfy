## 2. Один GraphQL-запрос — состояние ветки, начало красной серии и её PR

Code: `src/main/github/main-ci.ts:136-153` · key lines: 143, 145, 149, 150, 152

```ts
export async function readMainBranchCi(gh: (args: readonly string[]) => Promise<string>, repo: string, now: () => number = Date.now): Promise<MainBranchCi | null> {
  const [owner = '', name = ''] = repo.split('/')
  const stdout = await gh(['api', 'graphql', '-f', `query=${MAIN_CI_QUERY}`, '-f', `owner=${owner}`, '-f', `name=${name}`])
  const ref = answerSchema.parse(JSON.parse(stdout)).data.repository.defaultBranchRef
  if (ref == null) return null
  const branch = ref.name
  const commits = ref.target.history.nodes
  const newest = commits.findIndex((commit) => stateOf(commit) !== null)
  if (newest === -1) return null
  if (stateOf(commits[newest]!) === 'passing') return { repo, branch, state: 'green' }
  let first = commits[newest]!
  for (const commit of commits.slice(newest + 1)) {
    const state = stateOf(commit)
    if (state === 'passing') break
    if (state === 'failing') first = commit
  }
  return { repo, branch, state: 'red', commit: first.oid, redSince: failedAt(first) ?? now(), pr: prOf(first, branch) }
}
```

- Что делает: читает 20 последних commit-ов ветки по умолчанию с их check-ами и PR. Состояние ветки — состояние
  последнего commit-а с итогом: commit, у которого check-и ещё идут или которого CI пропустил, ничего не говорит.
  Красная серия начинается с самого старого красного commit-а после последнего зелёного; от него — время «покраснела» и
  PR.
- Почему здесь: Ticket называет образцами `src/main/github/deployments.ts` и `statusCheckRollup` из
  `src/main/github/prs.ts`; запрос — `defaultBranchRef.target.history` со `statusCheckRollup` и
  `associatedPullRequests`, как в пункте 1 «Что строить». Отметки агентов отсекает тот же `ciOf`, что и для PR.
- Без него: `mainCiAttention` некому вызвать, пункта нет.
- Требование: [Что строить](../issues/21-читатель-ci-основной-ветки.md#что-строить)
- Риски и пробелы test-ов: ответы gh в fixture-ах записаны в форме GraphQL-ответа GitHub, но не сняты с настоящего gh
  (test-ам запрещена сеть). Серия длиннее 20 commit-ов начинается с самого старого увиденного, у такой серии меняется
  `revision`, и пункт поднимется второй раз.

## 3. Проверка обходит Project-ы, ошибка — строка log-а, а не пункт

Code: `src/main/assistant/duties/main-ci-check.ts:51-73` · key lines: 55, 58, 64, 66, 68

```ts
  return async () => {
```

- Что делает: для каждого Project-а берёт его репозитории на github.com и отдаёт прочитанное в `mainCiAttention` с

- Требование: [Готово, когда](../issues/21-читатель-ci-основной-ветки.md#готово-когда)
- Риски и пробелы test-ов: связка в `app.ts` (`remoteRepos`, `projectLayouts`, `sharedPrTracker`) unit test-ом не

## 4. Проверка в планировщике — только пока обязанность включена

Code: `src/main/assistant/duties/main-ci-check.ts:85-102` · key lines: 88, 89, 91, 95

```ts
export function followMainCiDuty(scheduler: Pick<CheckScheduler, 'register'>, duty: MainCiDuty, run: CheckRun): () => void {
  let unregister: (() => void) | null = null
  const follow = (): void => {
    const enabled = duty.enabled(MAIN_CI_DUTY)
    if (enabled && unregister === null) unregister = scheduler.register(MAIN_CI_KIND, run)
    else if (!enabled && unregister !== null) {
      unregister()
      unregister = null
    }
  }
  const stop = duty.onChange(follow)
  follow()
  return () => {
    stop()
    unregister?.()
    unregister = null
  }
}
```

- Что делает: регистрирует проверку вида `main-ci` в планировщике Ticket-а 04, пока обязанность включена, и снимает её,
  когда пользователь обязанность выключил. `Duties` для этого получил `enabled(id)` и `onChange(listener)`.
- Почему здесь: пункт 2 «Что строить» — расписание только через планировщик Ticket-а 04 и только при включённой
  обязанности; интервал, сон вне work hours и догон после сна Mac приходят оттуда.
- Без него: проверка ходила бы в GitHub и при выключенной обязанности.
- Требование: [Что строить](../issues/21-читатель-ci-основной-ветки.md#что-строить)
- Риски и пробелы test-ов: пауза обязанности проверку не снимает — только выключение.

## 6. Что сознательно не меняли

Marker `main-red` у land не читается: это процесс worfy, обязанности его не называют (раздел «Решения» тикета). Вид
`main-ci` не получил обязанности источника: встроенные обязанности источников строятся из `SOURCE_CHECK_KINDS`
(Slack и Jira), а пункты `ci` берёт «CI основной ветки красный».
