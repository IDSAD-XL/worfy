# Code story — worfy-assistant 01: ADR Assistant-а: Session приложения, `worfy-app`, шесть границ, закрытый список, хранение пунктов, проверка источников

Kind: pr · Epic: worfy-assistant · Ticket: 01 · PR: - · Language: ru

## 1. Что было не так

Владелец 2026-11-20 принял spec Epic-а `worfy-assistant`: Assistant — агент worfy, по одному на машину, над всеми
Project-ами этой машины. Решения об его устройстве и правах лежали только в spec-е и в вопросах карты
proactive-runtime. ADR, на который могли бы сослаться Ticket-ы 03–18 и ревью их кода, не было. Кода в этом PR нет:
только новый ADR 0114.

- Требование: [Что строить](../issues/01-adr-assistant-а.md#что-строить)

## 2. Закрытый список действий и шесть границ

Code: `docs/adr/0114-assistant-app-session.md:63-81` · key lines: 65, 68, 70, 75, 77, 79

```markdown
4. **Закрытый список действий — в main, без модели** (решения 1 и 13, вариант C вопроса 01; spec, «Закрытый список
   действий»).
   - Сам Assistant делает только внутренние обратимые действия из этого списка, всё остальное предлагает.
   - Действия: разбудить простаивающий Orchestrator фиксированным сообщением, которое просит проверить и продолжить
     остановленные Subagent-ы; продолжить Session на Canvas после сброса Limits.
   - Текст действия задаёт main, а не Assistant.
   - Каждое действие — строка журнала Assistant-а с пунктом, который его вызвал.
   - Список расширяется только кодом.
   - Ticket 08, который его строит, начинает с причины простоя 2026-11-13 (возражение 3 критика): 5-часовой лимит
     остановил трёх implementer-ов, и Auto-continue Orchestrator-а, который был в main с 2026-11-07, их не продолжил.

5. **Шесть границ в коде** (решение 9, «Принимаю все 6»; spec, «Границы»).
   1. У Assistant-а только tools `worfy-app`: нет Bash, записи файлов и сети.
   2. Чужой текст приходит к нему только как данные, с источником и автором.
   3. Сам Assistant делает только действия из закрытого списка, и их текст задаёт main. Session с текстом, который
      написал Assistant, стартует только по щелчку пользователя, и пользователь видит этот текст до старта.
   4. Наружу — только существующий щелчок Send.
   5. Project-ы второй машины Assistant только читает.
   6. Каждое действие пишется в журнал вместе с пунктом, который его вызвал, и с like и dislike пользователя.
```

- Что делает: записывает, что Assistant сам делает только два действия из списка в main, текст которых задаёт main, а
  всё остальное только предлагает; и шесть границ, которые держит код, а не модель.
- Почему здесь: Ticket, «Решения», перечисляет эти части ADR; текст границ взят из spec-а, раздел «Границы», без
  изменений.
- Без него: Ticket-ы 08, 09 и 10 строили бы права Assistant-а каждый по своему чтению spec-а, и ревью не на что было бы
  сослаться.
- Требование: [Решения](../issues/01-adr-assistant-а.md#решения)
- Риски и пробелы test-ов: текст ADR test-ом не проверяется; соответствие spec-у сверено чтением.

## 3. Проверка внешних источников через connectors claude.ai

Code: `docs/adr/0114-assistant-app-session.md:83-95` · key lines: 85, 87, 88, 91, 93

```markdown
6. **Проверка внешних источников — через connectors claude.ai** (решение 19, вариант В вопроса 12; spec, «Проверка
   источников через connectors claude.ai»).
   - Пользователь подключает Slack и Jira в claude.ai. Своих token-ов для этих источников у worfy нет. Какие connectors
     подключены, main узнаёт без вызова модели — из списка MCP-серверов, который Claude Code уже отдаёт worfy.
   - Одна проверка — один одноразовый вызов Haiku 5.5 (thinking включено всегда). В вызове только read tools одного
     connector-а: ни tools Claude Code, ни `worfy-app`, ни настроек Project-а. Образец изоляции — narrator Live summary.
   - Рецепт источника говорит вызову, что искать («что касается пользователя» с прошлой проверки) и какие tools
     разрешены. В этом Epic-е два рецепта: Slack и Jira.
   - Выход — структурированные пункты: источник, id, автор, время, ссылка, короткий текст, касается ли пользователя,
     срочно ли, к какому Project-у или Ticket-у относится. main проверяет форму; ответ, который проверку не прошёл,
     пунктом не становится и пишется в журнал.
   - Session Assistant-а и тут видит только tools `worfy-app`: пункты источников приходят к ней как данные, с
     источником и автором.
```

- Что делает: записывает путь к Slack и Jira, который выбрал владелец (вариант В вопроса 12): одноразовый вызов Haiku
  5.5 с read tools одного connector-а, выход — пункты, форму которых проверяет main.
- Почему здесь: Ticket, «Решения», называет проверку источников одним из пунктов ADR; формулировка — из spec-а, раздел
  «Проверка источников через connectors claude.ai».
- Без него: Ticket 11 не знал бы, что Session Assistant-а не получает tools connector-ов, и мог бы дать их ей прямо.
- Требование: [Решения](../issues/01-adr-assistant-а.md#решения)
- Риски и пробелы test-ов: можно ли так ограничить вызов, не проверено; это первый шаг Ticket-а 11, и ADR называет это
  открытым.

## 4. Что ADR меняет и чего не меняет в прежних решениях

Code: `docs/adr/0114-assistant-app-session.md:111-120` · key lines: 113, 118, 119

```markdown
**Что это решение меняет и чего не меняет в прежних.**

- **ADR-0105 не меняется.** Ответ в PR публикует только main по щелчку Send пользователя; у Assistant-а нет пути к
  отправке ответа в PR (граница 4).
- **ADR-0058 этот ADR не меняет.** Переход одноразовых вызовов на Haiku 5.5 и правило «thinking не отменяет
  Suggestion» записал Ticket `worfy-polish` 135 (Amendment ADR-0058 от 2026-11-20). Проверка источников опирается на
  него.
- **Решение 3 Epic-а `worfy-retry`** («Повтор только у Orchestrator-а», `.scratch/worfy-retry/spec.md`) меняется для
  Session-ов на Canvas: их после сброса Limits продолжает Assistant по режиму обязанности. Поведение меняет Ticket 08;
  в остальном решение 3 остаётся как было.
```

- Что делает: называет, что ADR-0105 не меняется, а решение 3 Epic-а `worfy-retry` меняется только для Session-ов на
  Canvas, и кто это изменение делает.
- Почему здесь: Ticket, «Решения» и «Готово, когда», пункт 2, требует этих двух фраз; ADR-0058 Ticket прямо отдаёт
  Ticket-у `worfy-polish` 135, а его Amendment уже в ADR-0058.
- Без него: ревью Ticket-а 08 не видело бы, что продолжение Session-ов на Canvas — согласованное изменение решения
  `worfy-retry`, а не нарушение.
- Требование: [Готово, когда](../issues/01-adr-assistant-а.md#готово-когда)
- Риски и пробелы test-ов: что ADR-0105 в diff-е PR не правится, проверяет `git diff --name-only` (раздел 6).

## 5. Что сознательно не меняли

- ADR-0105, ADR-0058, ADR-0005 и spec `worfy-retry` не правились: ADR только называет, что меняется и кто это меняет.
- Значения, которые spec не задал (значение `WORFY_SESSION_KIND`, дневной предел пробуждений, N для паузы обязанности,
  имя файла пунктов и другие), ADR не выбирает: раздел «Что остаётся открытым» называет для каждого Ticket.

## 6. Как проверено

- `git diff --name-only origin/main...HEAD` — только `docs/adr/0114-assistant-app-session.md`, этот файл и файл
  Ticket-а с Evidence; ADR-0105 в списке нет.
- Все относительные ссылки ADR ведут на существующие файлы (проверка `[ -e ]` по каждой ссылке).
- `pnpm lint && pnpm typecheck && pnpm test` и gate fast — коды выхода в отчёте implementer-а и в Evidence Ticket-а.

   - Строки: `docs/adr/0114-assistant-app-session.md:91-95`

   - Ответ: только для Session-ов на Canvas: их после сброса Limits продолжает Assistant по режиму обязанности.
   - Строки: `docs/adr/0114-assistant-app-session.md:118-120`
