## Что строить

1. **Обязанность:** trigger, область (Project-ы, источники), режим каждого действия, счётчики и пауза.
   - Режимы действия: сам, по заранее данному «да», спросить, отдать пользователю.
   - Счётчики: показано, принято, отклонено, проигнорировано, like, dislike.
   - Пауза: после N проигнорированных предложений или dislike подряд обязанность встаёт на паузу, и это видно.
2. **Встроенные обязанности — только общие:** «работа стоит»; «CI основной ветки красный»; «ждёт пользователя»;
   утренняя сводка; по одной на каждый внешний источник. Их встроенные правила опираются только на то, что есть у любого
   Project-а:
   - Session молчит или ждёт ответа — дольше порога, который задал пользователь;
   - Run остановился;
   - CI основной ветки красный дольше N минут; N и само правило задаёт пользователь; у пункта — PR, после которого
     покраснело, и предложение Session починки;
   - PR ждёт пользователя.
3. **Правила конкретного Project-а** — процесс Project-а (land, `pc-main-red`, gate) — лежат в настройках этого
   Project-а; например «land закончился, а Orchestrator спит».
4. **Оценки:** dislike сразу снимает такие пункты этой обязанности и пишет правило в файл памяти Assistant-а. Правила
   видны и удаляются (экран — Ticket-ы 14 и 15).

## Где в коде

- Ядро внимания — Ticket 03 (пункт журнала несёт поле обязанности).
- Настройки Project-а — `src/main/projects/settings.ts`.

## Решения

- Шум снимают like и dislike (решение 3); dislike сразу меняет поведение: снимает пункты и пишет правило в память
  (spec, «Решено советником»).
- `worfy-triggers` становится регулярными проверками и обязанностями (решение 8).
- Правила не завязаны на процесс репозитория worfy: встроенные правила опираются только на то, что есть у любого
  Project-а; процесс конкретного Project-а — правила в его настройках (решение 14; spec, «Решено советником»).
- Состав встроенных обязанностей, оценки и пауза (spec, «Обязанности»).

## Test-ы

Стык А (spec, «Решения по test-ам»): на входе — пункты, часы и настройки; на выходе — что обязанность показывает,
предлагает или ставит на паузу. Fixture-события формы из замера, часы ненастоящие.

## Готово, когда

- [ ] У обязанности есть trigger, область, режим каждого действия (сам, по заранее данному «да», спросить, отдать
      пользователю), счётчики (показано, принято, отклонено, проигнорировано, like, dislike) и пауза.
- [ ] Встроенные обязанности: «работа стоит», «CI основной ветки красный», «ждёт пользователя», утренняя сводка, по
      одной на каждый внешний источник; ни одна не ссылается на land, `pc-main-red` или gate.
- [ ] Unit test: «CI основной ветки красный» поднимает пункт только после N минут, N из настроек; у пункта — PR, после
      которого покраснело, и предложение Session починки.
- [ ] Unit test: Session, которая молчит или ждёт ответа дольше порога из настроек, даёт пункт; короче порога — нет.
- [ ] Unit test: остановка Run-а и PR, который ждёт пользователя, дают пункты встроенных обязанностей.
- [ ] Правило Project-а задаётся в его настройках; unit test: правило «land закончился, а Orchestrator спит» из
      настроек Project-а поднимает пункт.
- [ ] Unit test: после dislike такие пункты этой обязанности больше не показываются, а в файле памяти появляется правило;
      удалённое правило больше не действует.
- [ ] Unit test: после N проигнорированных предложений или dislike подряд обязанность встаёт на паузу.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` — exit 0; `ci-ok` зелёный на head PR.
