## Что строить

1. **Сначала причина.** 2026-11-13 5-часовой лимит остановил трёх implementer-ов — Subagent-ов внутри Session
   Orchestrator-а, — и продолжили их только через 41 час. Auto-continue Orchestrator-а был в main с 2026-11-07. Ticket
   начинается с того, что выясняет, почему он той ночью не продолжил работу, и записывает причину в «Итог».
2. **Действия закрытого списка** — main выполняет их без модели, по режиму обязанности (Ticket 07):
   - разбудить простаивающий Orchestrator фиксированным сообщением, которое просит проверить и продолжить остановленные
     Subagent-ы;
   - продолжить Session на Canvas после сброса Limits. Сейчас Auto-continue делает это только для Orchestrator-а.
     Действие забирает отложенную идею 6 Epic-а worfy-limits-out: любая Session ждёт сброса Limits на виду.
3. **Текст действия задаёт main**, а не Assistant.
4. **Журнал Assistant-а:** каждое действие — строка журнала с пунктом, который его вызвал.
5. **Список расширяется только кодом.**

## Итог

### Причина простоя 2026-11-13

Источники: транскрипт Session Orchestrator-а `6e11ae60-…` (`~/.claude/projects/<проект worfy>/6e11ae60-….jsonl`,
строки 40890–40904 и ход 2026-11-13 21:56Z – 2026-11-14 20:51Z), память Orchestrator-а
`resume-2026-11-12-stable-update.md` (строки «00:30Z 11-13» и «11-14 ~21:00Z»), код `origin/main`. Живые Session-ы не
трогались. 41 час — это три отрезка с двумя разными причинами.

1. **00:29Z – 04:00Z, 3,5 часа — сам лимит.** Ход Orchestrator-а, который начала task-notification (Subagent ui-kit 07
   упал на лимите), закончился синтетическим ответом `You've hit your 5-hour limit · resets 6am (Europe/Kiev)`
   (`rateLimitType: five_hour`, `resetsAt: 1794542400` = 04:00Z). Ещё две task-notification (00:30:08, 00:32:35)
   легли в разговор без запроса к API и без hook-ов. Этот текст ловит `isLimitsMessage`
   (`src/shared/autopilot/resume-at.ts:157`), а такой ход — отказ без prompt — Auto-continue разбирает
   (`src/main/agent/orchestrator-continue.ts:290`, contract test-ы `test/contract/orchestrator-continue.test.ts:394` и
   `:437`).
2. **04:02Z – 21:56Z, около 18 часов — Auto-continue ничего не отправил.** Между 00:32:35Z и 21:56:38Z в Session не
   пришло ни одного сообщения (строки 40901 → 40904): продолжения `continueText` не было, хотя Mac в тот день работал
   (соседняя Session владельца гоняла workflow-ы с 11:07Z). Код, который отказ узнаёт и ждёт сброса, есть и покрыт
   test-ами. Значит, ожидания не было вовсе. Поток событий ведёт к одной точке: переключатель Auto-continue
   Project-а. По умолчанию он выключен (`autoContinueOn`, `src/main/settings/store.ts:561`; ADR-0005, запись
   2026-11-05: «нет записи — Off»). С выключенным переключателем конец такого хода сразу сбрасывает ожидание
   (`orchestrator-continue.ts:296`). Приёмку worfy-retry (11) делали на демо-проекте. Записи о том, что Auto-continue
   у Project-а worfy был включён до 2026-11-13, нет ни в памяти, ни в тикетах. Сейчас он включён:
   `app-settings.json` изменён 2026-11-19. **Доказано:** worfy не отправил продолжение. **Не доказано, только
   выведено:** что причиной был выключенный переключатель. worfy не хранит ни журнала переключателя, ни своих строк
   `notice` после перезапуска (`orchestrator-continue.ts`, шапка: строки живут только в событиях живой Session).
3. **21:56Z 11-13 – 20:47Z 11-14, около 23 часов — Orchestrator простаивал, хотя лимит уже сбросился.** В 21:56Z
   его разбудило сообщение соседней Session. В 21:57Z он ответил: «лимит … сбрасывается в 6:00 по Киеву… После сброса
   продолжу каждого». Время сброса он взял из старого отказа, хотя 04:00Z уже прошло. В 23:50Z он поставил фоновое
   ожидание на 2 часа. В 01:50Z 11-14 это ожидание сняли по пределу фоновой команды, и он решил ждать «любого события».
   До сообщения владельца в 20:47Z событий не было. Auto-continue по устройству такой случай не покрывает: он отвечает
   только на ход Orchestrator-а, который закончился отказом, а ходы 21:57Z, 23:50Z и 01:50Z закончились нормально.
   Простаивающий Orchestrator, у которого нет ни одной живой background task, в main не будит никто. Остановленные
   Subagent-ы Auto-continue не видит вовсе.

**Что из этого делает Ticket.** Разбудить простаивающий Orchestrator (idle, ни одной живой background task, Limits
не отказывают): фиксированное сообщение main `WAKE_ORCHESTRATOR_TEXT` (`src/shared/assistant/actions.ts`) просит
проверить остановленные Subagent-ы и продолжить каждого через SendMessage тому же агенту. Оно прямо говорит, что
Limits сейчас позволяют работать: это ответ на отрезок 3. Решения владельца для этого не нужно. Включить ли
Auto-continue у Project-а worfy — выбор в меню Modes; сейчас он включён.

### Что сделано

- `src/shared/assistant/actions.ts` — закрытый список (`CLOSED_ACTIONS`: `wake-orchestrator`, `continue-session`),
  тексты main (`WAKE_ORCHESTRATOR_TEXT`, `continueSessionText`), причины отказа, строка журнала
  `actionJournalLineSchema`, запрос `ActionRequest { action, itemId, by }`. Поля для текста в запросе нет.
- `src/main/assistant/actions/closed-list.ts` — `ClosedList.act()`: единственная дверь для main, Assistant-а
  (`worfy-app`, Ticket 09) и щелчка пользователя (Ticket 14). Проверяет по порядку: действие в списке → обязанность
  показывает пункт и предлагает действие → режим (`self` и `pre-approved` — кто угодно, `ask` — только пользователь,
  `hand-over` — никто) → Session (жива, ей не владеет Run, idle; у Orchestrator-а нет живых background task и не ждёт
  Auto-continue; Limits не отказывают, а для `continue-session` ожидание сброса закончилось). Отправляет только свой
  текст. Каждый вызов — сделанный или отказанный — даёт строку журнала с пунктом. `check()` — тот же вердикт без
  действия и без строки. `escalate()` — строка `escalated` и `WakeLoop.escalate` (Ticket 06).
- `src/main/assistant/actions/limits-waits.ts` — ожидание сброса Limits у любой Session, кроме Orchestrator-а и
  Session, которой владеет Run (идея 6 worfy-limits-out). Отказ распознаётся так же, как у Run-а (`LimitsWait`).
  Ожидание видно: `wait()`/`waits()`/`observeWaits()` и строка worfy в чате Session «worfy: waiting for the Limits,
  they reset at 06:02». Сообщение человека ожидание снимает. Само ожидание ничего не отправляет.
- `src/main/assistant/actions/auto.ts` — что main делает сам по режиму обязанности: смотрит после каждого изменения и
  раз в минуту. `continue-session` — как только ожидание истекло. `wake-orchestrator` — один раз. Если после побудки
  Orchestrator снова стоит, а Subagent-а он не запустил и человек ему не писал, закрытый список не помог: пункт один
  раз уходит модели (`escalate`). Побудок не больше `WAKES_PER_DAY` за 24 часа.
- `src/main/assistant/actions/journal.ts` — журнал `<WORFY_DATA_DIR>/assistant/journal.json`, строки 14 дней
  (ADR-0005, запись 2026-11-25 Ticket 08).
- `src/main/assistant/actions/app.ts` — сборка в приложении: `startClosedList({ escalate, power })`,
  `appClosedList()` для Ticket-ов 09 и 14, `appLimitsWaits()` для окна. Как и решение о пробуждении (Ticket 06),
  **пока ничем не запускается**: Assistant выключен, пока пользователь его не включит (ADR-0114, решение 10). Запускает

- `OrchestratorContinue.sessionOf(projectId)` (`src/main/agent/orchestrator-continue.ts`) — Session Orchestrator-а

- Предложения обязанностей (`src/main/assistant/duties/duties.ts`) показывают тексты main из `actions.ts`.
- Решение 3 worfy-retry меняется так, как записано в ADR-0114: Session-ы на Canvas после сброса Limits продолжает
  закрытый список по режиму обязанности «работа стоит», Orchestrator по-прежнему продолжает Auto-continue.

### Решено без владельца (подтвердить)

1. **`pre-approved` = `self`** для действий закрытого списка: «да, данное заранее», — это сам выбранный режим. Своего
   хранилища предварительных согласий пока нет; его может ввести Ticket 15.
2. **Когда будить Orchestrator.** Будить, только если он idle, у него нет ни одной живой background task, Run им не
   владеет, Auto-continue не ждёт его продолжения и Limits не отказывают (проверка `on-demand` Terminal AI,
   `limitsCheck`). Живая background task сама разбудит его task-notification-ом.
3. **Не больше 6 побудок одного Orchestrator-а за 24 часа** (`WAKES_PER_DAY`): по одной на 5-часовое окно и одна в
   запас. Побудка «помогла», если после неё Orchestrator запустил Subagent или ему написал человек. Иначе следующая
   остановка — `escalate`, один раз на пункт.
4. **Журнал** — `<WORFY_DATA_DIR>/assistant/journal.json`, строки 14 дней (как пункты ядра). В нём строка на каждый
   вызов `act()`, в том числе на отказ, если просил Assistant или пользователь. Автоматический проход main пишет
   только сделанное и `escalated`.
5. **Ожидание сброса Limits у Session-ов на Canvas** живёт только в памяти main. После перезапуска worfy его заново не
   строит: Session после перезапуска продолжает ADR-0108. Ждём любой сброс, даже дальше 24 часов, — так делает
   Auto-continue при включённом переключателе. Codex перед продолжением заново не читается: это `shortcut:` в
   `limits-waits.ts`.
6. **Взгляд раз в минуту** (`AUTO_LOOK_MS`) плюс взгляд после каждого изменения: ядра, Limits, ожиданий, пробуждения
   Mac.
7. **Что будит, а что продолжает.** `wake-orchestrator` действует только на пункт, предмет которого — Session
   Orchestrator-а этого Project-а. `continue-session` — только на Session, которая не Orchestrator. Иначе отказ
   `no-target`.
8. **Ничего не запускается до Ticket-а 10** (см. выше). Ожидание сброса Limits станет видно в живом приложении, когда
   Ticket 10 вызовет `startClosedList`.
