## На чём споткнулись

### 1. Epic-и не видны при запуске из Finder (блокер)

- Симптом: после шага 15 в окне «No epics in .scratch/» и «No epics yet», хотя Epic лежит в Workflow folder и закоммичен. Перезапуск из Finder не помог.
- Причина: у процесса worfy, запущенного из Finder, `PATH=/usr/bin:/bin:/usr/sbin:/sbin` (снято с живого процесса). Список эпиков приложение берёт из `epic-status --json`, вызывая его со своим окружением. `epic-status` зовёт `ticket root`, а `ticket` — скрипт с `#!/usr/bin/env node`. node из nvm в этом `PATH` нет.
- Воспроизведение из `~/silent-app`:
  - `env -i HOME=$HOME PATH=/usr/bin:/bin:/usr/sbin:/sbin ~/.claude/worfy-harness/plugin/bin/ticket root` → `env: node: No such file or directory`, код 127;
  - тот же `env -i ...` с `epic-status --json` → `{"ref":"main","epics":[],"tickets":[]}`, код 0;
  - с добавленным в `PATH` каталогом `~/.nvm/versions/node/v24.21.0/bin` → Epic `e3-acceptance` и Ticket 01.
- Обход в этом прогоне: Cmd+Q и запуск `~/Applications/worfy-stable.app/Contents/MacOS/worfy` из Terminal.app. После этого Epic появился и Wave прошла.
- Следствия:
  - строка инструкции «worfy берёт окружение из `$SHELL -ilc`, поэтому nvm ... он видит» верна для экрана First run, но не для вызовов скриптов Harness-а из главного процесса;
  - все 13 строк First run зелёные, а приложение при этом нерабочее;
  - `epic-status` при сбое `ticket root` отвечает пустым списком и кодом 0 вместо ошибки — отдельный дефект;
  - на node завязаны `ticket`, `profile`, `project-connect`, `qmd-collections`, `epic-board`, `silent-check`, `worktree-lock`, `decision-log`.
- Доисследовано по коду сборки (`app.asar`):
  - окружение login-shell приложение снимает (`captureLoginShellEnv`, `$SHELL -ilc`) и передаёт в проверки First run, в `project-connect` и в сессии агентов. Свой `process.env.PATH` оно при этом не меняет;
  - `runEpicStatus` вызывает `epic-status` с `scriptEnv(harness, process.env)` — параметра окружения у него нет вообще;
  - наблюдатель Workflow зовёт `readProjectLayout` без `env`, поэтому `profile --json` и `ticket root` тоже идут с `process.env`;
  - `profile --json` под `PATH` Finder-а падает с кодом 127 (воспроизведено). Тогда `readProjectLayout` молча переходит на раскладку Full: режим `full`, Tickets в `~/silent-app/.scratch`. То есть Silent Project приложение читает как Full и следит за папкой, которой нет. Сообщение об этом (`[workflow] …: Full mode, the workflow files in the Project root, because …`) уходит в консоль, которую при запуске из Finder не видно;
  - node из Homebrew тоже не помог бы: `/opt/homebrew/bin` в `PATH` Finder-а не входит. Сработает только node в `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin` или запуск из терминала. Значит, совет инструкции «на другом Mac: `brew install ... node`» эту проблему не снимает (вывод из кода, на другом Mac не проверялось).

### 2. «qmd collections were not set up» при подключении проекта

- Текст в сайдбаре: `qmd-collections failed: qmd-collections: /Users/worfy-test/.config/qmd/index.yml: "collections:" holds an inline value, ...` (дальше обрезано).
- В `~/.config/qmd/index.yml` стоит `collections: {}` рядом с блоком `models:`. Файл создан в 01:56:18, во время загрузки моделей.
- В `~/.cache/qmd/refresh.log` четыре раза «No collections found».
- Причина найдена, от находки 1 она не зависит:
  - `collections: {}` пишет сам qmd 2.8.3. При отсутствии файла `loadConfig` возвращает `{ collections: {} }`, а `ensureModelsConfiguredForCli` сохраняет это вместе с блоком `models:` через `YAML.stringify` (`dist/cli/qmd.js`, `dist/collections.js`). Пустой словарь сериализуется в одну строку;
  - `qmd-collections` Harness-а такую строку править отказывается: `bin/qmd-collections:135`, проверка `/^collections:\s*$/`;
  - в этом прогоне файл создал `qmd pull` (шаг «Download…», 01:56:18), проект подключался позже (01:58);
  - итог: на свежей машине любая команда qmd, записавшая конфиг до подключения первого проекта, ломает настройку коллекций. `ensureModelsConfiguredForCli` вызывается не только из `pull`, так что вариант «Skip…» от этого, вероятно, не спасает — не проверено.
- Последствие для прогона: поиск qmd по проекту не настроен, Wave прошла без него.

## Проверка: `PATH` — единственная причина находки 1 (02:39–02:43)

Четыре запуска одной и той же копии приложения; после каждого окружение снято с живого процесса (`ps eww`). В обоих проектах на диске лежит закрытый Epic `e3-acceptance`.

| Запуск | Окружение процесса | Epic-и в окне |
|---|---|---|
| `open ~/Applications/worfy-stable.app` из терминала | полное терминальное: `PATH` с nvm, `NVM_DIR`, `TERM` | не записано |
| `open --env "PATH=<nvm>:/usr/bin:/bin:/usr/sbin:/sbin" …` | `PATH` заданный, остальные переменные терминала унаследованы | не записано |
