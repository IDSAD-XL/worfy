## Что происходит

`harness/bin/profile-set`, функция `takeOver()` (около `:206-221`): чтобы снять устаревший замок, она делает
`renameSync(LOCK, aside)` и сверяет token в отодвинутой папке. Если замок оказался чужим и живым, она
возвращает его через `renameSync(aside, LOCK)`. Между двумя rename папки замка нет, и третий writer в
этот момент может выполнить `mkdir` замка. Ревьюер проверил оба исхода на macOS:

- третий writer ещё не записал `owner`: rename держателя поверх пустой папки проходит, третий writer
  пишет свой `owner` в замок держателя, и оба считают, что держат замок. Сравнение-и-запись больше
  не защищает;
- третий writer уже записал `owner`: rename падает с `ENOTEMPTY`, пустой `catch {}` это глотает,
  держатель остаётся без папки замка, а рядом лежит `.stale-*`.

Вероятность низкая: нужны брошенный замок убитого writer-а, два writer-а, одновременно признавших его
брошенным, и третий writer, попавший в окно в микросекунды. Дефект старый, PR #599 его не вносил.

## Что делаем

1. Красный детерминированный test в `profile-set.test.sh` на тех же файлах-сигналах, что ввёл ticket 57
   (`PROFILE_SET_STALE_SYNC`): точка остановки между двумя rename, третий writer делает `mkdir` в окне.
2. Правка `takeOver()` без окна. Например: не отодвигать замок, пока token не сверен через чтение
   `owner`; или при неудачном возврате не глотать ошибку, а сообщить и выйти с кодом «замок потерян».
   Выбор и причина — в «Итог».

## Итог

- **Выбор: живой замок не двигается никогда** (вариант «сообщить "замок потерян"» отклонён: он ловит только исход
  `ENOTEMPTY`, а при пустой папке третьего writer-а возврат проходит и замок держат двое — ошибки нет). Ждущий
  writer сверяет, что замок тот же устаревший (inode и token), кладёт в него файл-заявку с `O_EXCL` (`wx`,
  `takeover-0`), сверяет ещё раз и только тогда отодвигает и удаляет папку; возврата больше нет. Устаревшая папка,
  ушедшая с имени замка, не возвращается, поэтому заявку в ней получает только один writer.
- **Края.** Неудачный rename (Windows: открыт файл в замке) убирает заявку, иначе все ждали бы 60 s. Заявка с
  собственным token — своя. Заявка старше 60 s — от убитого ждущего, берётся следующее имя (`takeover-1`, …). Для
  замка без `owner` (судится по mtime папки) takeover возвращает времена папки после снятия заявки. Ждущий без
  takeover ждёт как при живом замке (100 ms, предел 10 s).
- **Пределы (в комментарии кода):** ждущий, уснувший дольше 60 s между проверкой и rename, считается мёртвым; замок
  без `owner` узнаётся только по inode.
- **Test-ы** (`profile-set.test.sh`): два случая с третьим writer-ом в окне на сигналах ticket 57 — красные на main
  (6 FAIL), зелёные с правкой; свежая и старая заявка; неудачный rename (с `owner` и без); своя заявка; подмена замка
  в точке `checked` (с `owner` и только по inode). 10 прогонов подряд — exit 0, 158 passed, 16–18 s; plugin-neutral — 0.
  Восемь мутантов (старый `takeOver()`, заявка без возраста, `w` вместо `wx`, без второй сверки, token без inode,
  заявка остаётся после неудачного rename, без строки своей заявки, без возврата mtime) — красные.
- **Ревью:** три круга. Круг 1: tests BLOCK (2 med — выживали мутанты без второй сверки и без inode), correctness —
  med (заявка после неудачного rename блокирует всех на 60 s); круги 2 и 3 — только low, исправлены.
