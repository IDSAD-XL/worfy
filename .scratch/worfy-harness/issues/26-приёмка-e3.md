## Что происходит

- «Готово, когда» E3 — пять пунктов решения Q35:

     человека;

     чтение — писать в `/Users/alexey/Work/*` нельзя);

- Ticket-ы 13–25 проверяют свои части по отдельности: на фикстурах, с fake-агентом, каждый в своей
  песочнице. Целиком — собранный `.app`, настоящий агент, пустой `~/.claude` — E3 никто не проверял.
- Test-ы собранного `.app` — `test/e2e/packaged.spec.ts` с тегом `@packaged` (`pnpm test:package`,
  входит в `gate full`). Они уже запускают Stable copy с временным `HOME`
  (`test/e2e/packaged.spec.ts:258-259`), но с fake-агентом (`launchApp` ставит `WORFY_AGENT: 'fake'`,
  `test/e2e/helpers.ts:130`) и без `CLAUDE_CONFIG_DIR`. В `src/` и в test-ах `CLAUDE_CONFIG_DIR` не
  задаётся; задаёт его только spike `scripts/spikes/sdk-probe.ts:571`.
- `CLAUDE_CONFIG_DIR` отделяет settings, plugins и запись входа в keychain: в песочнице нужен свой
  `/login` (факт spike, решения владельца). Вход в аккаунт агенты не выполняют (Q8).
- Журнал прогона Autopilot — `<WORFY_DATA_DIR>/autopilot/<run>.jsonl`
  (`src/main/autopilot/journal.ts:1`). Строки `refused-dialog` (Session просила человека) и
  `human-input` (человек вмешался) — дефект прогона (`src/shared/autopilot/journal.ts:35`, `:37`).
- Версия приложения — `0.2.0` после Ticket-а 04; по Q12 в конце E3 она становится `0.3.0`.
- Механизма, который помечает Ticket «агенты не берут» (шаг владельца), нет: `~/.claude/bin/epic-status`
  и `~/.claude/skills/epic-wave/SKILL.md` о таком не знают; поле `Type` читает только `bin/ticket`
  (`~/.claude/bin/ticket:183`), и только как строку шапки. worfy при расчёте Wave тип Ticket-а тоже не
  смотрит (`src/shared/workflow/`).

## Что делаем

**Кто ведёт.** Autopilot этот Ticket не берёт: в нём шаги владельца — вход в песочнице, пустой
репозиторий на GitHub, второй пользователь macOS. Механизма для такой пометки нет (раздел выше),
поэтому правило записано здесь словами. Orchestrator ведёт Ticket сам. Скрипты, spec и проверки
(пункты 1–6 и 8 ниже) пишет и запускает implementer по его брифу. Шаги владельца внутри них — вход в
песочнице и пустой репозиторий на GitHub — и весь пункт 7 делает владелец. Implementer на шаге
владельца останавливается и пишет в отчёте, какой шаг ждёт. Закрывает Ticket Orchestrator, после
шагов владельца.

1. **Песочница** (Q8). Новый `scripts/e3-sandbox.sh`:
   - заводит папку песочницы `$TMPDIR/worfy-e3-sandbox/` (повторный запуск берёт ту же, `reset`
     удаляет только её);
   - задаёт `HOME=<песочница>/home`, `CLAUDE_CONFIG_DIR=<песочница>/home/.claude` (так
     `~/.claude/worfy-harness/` тоже оказывается внутри песочницы), `npm_config_prefix=<песочница>/npm`
     (npm-установка qmd не уходит в глобальный prefix машины);
   - `GH_CONFIG_DIR` — настоящая папка `gh` машины: аккаунты и вход в `gh` — системные, их делает
     владелец (Q22); worfy и Harness в неё не пишут (test Ticket-а 25). Первая проверка песочницы —
     `gh auth token -u <аккаунт>` в её env, код 0 (токен не печатается). Не так (keychain macOS может
     не найтись при чужом `HOME`) — причина в «Итог», и пункт 2 не проверен до решения Orchestrator-а;
   - пишет `<песочница>/home/.gitconfig`: имя и почта коммитов приёмки, `credential.helper` через
     `gh auth git-credential`;
   - `shell` печатает команды для владельца: войти в Claude Code в песочнице (`claude`, затем
     `/login`) — один раз (Q8).
2. **Приёмочный прогон** — новый `test/acceptance/e3.spec.ts` (Playwright `_electron`, свой
   конфиг `playwright.acceptance.config.ts`, команда `pnpm test:acceptance`). Он не входит в
   `pnpm test:e2e`, `pnpm test:package`, `gate full` и CI. Идёт против `dist/mac*/worfy.app` из
   `pnpm package` (или `WORFY_PACKAGED_APP`), с настоящим агентом (без `WORFY_AGENT=fake`), в env
   песочницы, под замком `/tmp/worfy-e2e.lock`. Первым шагом смотрит строку «вход в Claude» экрана
   первого запуска: входа нет — стоп с «не проверено: нет входа в песочнице — шаг владельца».
3. **Пункт 1 — установка в песочнице.**
   - До старта: в `CLAUDE_CONFIG_DIR` песочницы нет `worfy-harness/` и plugin `worfy`.
   - Экран первого запуска показывает все проверки Q22: вход в Claude, `claude --version`, `git`,
     `gh` и аккаунты, node ≥22, `jq`, Harness и его версия, qmd и модели.
   - После подтверждения установки: версия в
     `<песочница>/home/.claude/worfy-harness/plugin/.claude-plugin/plugin.json` равна версии
     собранного `.app` (`<semver>+<SHA>`, Q12); `claude plugin list` в env песочницы — код 0, в выводе
     plugin `worfy` включён и с той же версией.
   - qmd с согласия (Q15): согласие → `<песочница>/npm/bin/qmd --version`, код 0. Модели (около 2 ГБ) —
     путь «пропустить»: поиск идёт по `qmd.fallback_grep`. Скачивание моделей — только при
     `E3_QMD_MODELS=1`, тогда проверяется и один поиск `qmd`.
4. **Пункт 2 — Silent Project и Wave.**
   - Шаг владельца: создать пустой private-репозиторий на GitHub для приёмки, от аккаунта, вход в
     который есть в `gh`, и назвать его в чате (`E3_SILENT_REPO=<owner>/<name>`). Агенты репозитории
     на GitHub не создают.
   - Прогон собирает локальный репозиторий из фикстуры `test/acceptance/fixtures/silent-repo/` (пакет
     node с `node --test`) и пушит `main` в этот репозиторий.
   - Подключение через UI (Ticket-ы 24 и 25): Silent mode, Workflow folder по умолчанию, аккаунт с
     правами → `workflow.finish: pr-green-ci`.
   - В Workflow folder прогон кладёт Epic из фикстуры `test/acceptance/fixtures/silent-epic/`
     (`spec.md` и один маленький Ticket: функция и test к ней) и коммитит его в git Workflow folder.
   - «Run wave» на Canvas песочницы; прогон ждёт `done` Ticket-а по `epic-status --json` из plugin
     песочницы, предел ожидания — 90 минут.
   - Проверка следов, по репозиторию и по GitHub. Тексты — ветки (локальные и в `origin`),
     сообщения коммитов от базы, заголовки, описания и ветки PR (`gh pr list --state all --json
     title,body,headRefName` с `GH_TOKEN` аккаунта):
     - `silent-check` из plugin песочницы (проверка следов Ticket-а 22) на каждом тексте — код 0;
     - отдельно от него — поиск значений именно этого прогона: имя Epic-а фикстуры, slug Ticket-а,
       `<epic>/01`, путь Workflow folder, `.scratch`, `worfy-harness` — ни одного совпадения. Так
       след, который пропустил бы и guard, и `silent-check` (они — один код), всё равно найдётся;
     - файлы (`git ls-files` и неотслеживаемые) — нет `.scratch/`, HANDOFF, ADR, `CONTEXT.md`, уроков;
     - строки атрибуции Claude — по полю `attribution` Profile-а (по умолчанию `on`, Q25): при `on`
       они разрешены, при `off` их нет.
   - Контрольный шаг до Wave: обе проверки на подложенном тексте с именем Epic-а фикстуры и
     `<epic>/01` находят след. Проверка, которая не может упасть, не считается.
5. **Пункт 3 — машина владельца, только чтение.** Новый `scripts/e3-owner-check.sh`:
   - `~/.claude` — только личное. Список «уберу / оставлю» — манифест переноса Ticket-а 14; второго
     списка этот Ticket не заводит. Если у Ticket-а 14 есть режим проверки, скрипт вызывает его.
     Отдельно: записи hooks в `~/.claude/settings.json` не ведут в убранные файлы; в `~/.claude.json`
     нет записи MCP-сервера qmd (Q15); `claude plugin list` — `worfy` включён.
   - Wave Autopilot без человека: скрипт получает путь журнала одного прогона после перехода машины
     (Ticket 16). Проверяет: прогон начался позже строки `Status: done` Ticket-а 16; в журнале нет строк
     `refused-dialog` и `human-input`; последняя строка `run-stopped` — Wave закончилась. Файлов
     Harness в `~/.claude` при этом нет — значит, прогон шёл на plugin.
   - Код выхода 0 — всё так; 1 — список нарушений, по строке на каждое. Скрипт ничего не пишет.
6. **Пункт 4 — Auction в Full mode, только чтение.**
   - `~/.claude/worfy-harness/plugin/bin/profile -C /Users/alexey/Work/Auction --field mode` печатает
     `full`, код 0; `--field schema` — `2`.
   - `epic-status --json` из plugin в `/Users/alexey/Work/Auction` — код 0, список Epic-ов не пуст.
   - До и после проверки `git -C /Users/alexey/Work/Auction status --porcelain=v2 --ignored` и
     `git -C /Users/alexey/Work/Auction rev-parse HEAD` совпадают. `git fetch` не делается.
   - Stable copy: на Canvas и в боковой панели Project-а Auction видны его Epic-и — ручная проверка
     окна.
7. **Пункт 5 — шаг владельца.** Владелец создаёт второго пользователя macOS (системные настройки —
   его) и под ним: копирует Stable copy последнего коммита в `~/Applications`, запускает, проходит
   экран первого запуска, входит в Claude, ставит Harness и qmd, подключает Silent Project (новый
   локальный репозиторий без `origin` — финиш локальный), запускает одну Wave. Результат — словами в
   чате; Orchestrator переносит его в «Итог».
8. **Версия в конце Epic-а** (Q12). Когда пункты 1–5 закрыты: `package.json` → `0.3.0` отдельным PR,
   после влития — `pnpm install:stable`; worfy переставляет plugin, потому что строка версии
   изменилась.

ADR не нужен: Ticket проверяет решения ADR-0040–0047, новых не принимает.
