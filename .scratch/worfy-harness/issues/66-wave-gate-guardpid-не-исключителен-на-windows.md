# 66 — `wave-gate`: `guardPid` на Windows не исключает вторую проверку

Type: bug
Status: done 2026-10-29T03:49Z
PR: #949
Blocked by: —
Source: находка ПК 2026-10-21 при работе над `worfy-windows` 72 (PR #705, замок e2e в `wave-gate`).

## Что происходит

На Windows `fs.renameSync` одного и того же пути удаётся в ОБОИХ процессах, которые делают его одновременно: libuv
переименовывает через открытый handle. Замер ПК: папка — 30 из 30 раз, файл — 22 из 30. Значит «отложить в сторону
переименованием» (rename-aside) не даёт взаимного исключения.

`guardPid` в `harness/bin/wave-gate:352` (pid-файл `<git common dir>/worfy-wave-gate.pid`) снимает устаревший pid-файл
именно так: `renameSync(file, aside)` (`:372`), потом сравнивает прочитанный текст. Две `wave-gate check`, начатые
вместе над устаревшим pid-файлом, могут обе его взять и пойти дальше параллельно.

## Что делаем

1. Красный test (на Windows): две `wave-gate check` над устаревшим pid-файлом стартуют вместе — проходит ровно одна.
2. Правка, как в `worfy-windows` 72: исключительный `mkdir <pidfile>.takeover`, под ним перечитать pid-файл и снять
   его, затем удалить `.takeover`. Устаревший `.takeover` (процесс убит) — по возрасту, как замок e2e.

## Готово, когда

- [ ] Test красный на main под Windows, зелёный с правкой; `wave-gate.test.sh` на Mac и ПК — exit 0.

## Где в коде

- `harness/bin/tests/wave-gate.test.sh`
- Как сделано для замка e2e — PR #705 (`worfy-windows` 72); брать после его merge, чтобы не было конфликта.

## Итог

Что было на деле (ПК, Windows 11). Две проверки над устаревшим pid-файлом запускались вместе. Обе делали rename успешно,
и вторая уносила файл, который первая уже отложила. Первая читала свой `.stale-<pid>` и получала ENOENT. Итог —
падение со stack trace вместо понятного отказа: 10 из 10 раундов. Обе проверки дальше не шли: обе возвращались к
`openSync(file, "wx")`, а там побеждает только одна.

Правка (`harness/bin/wave-gate`, `guardPid`), как у замка e2e (`takeOver()`, PR #705):

- Сначала исключительный `mkdir <pid file>.takeover`. Проверка, которой маркер не достался, выходит с кодом 1:
  «another wave-gate check is taking over … at the same moment».
- Под маркером pid-файл перечитывается и снимается, только если это всё ещё тот устаревший файл, который проверка
  видела. Дальше идут прежние rename, чтение и `link()`. Маркер удаляется в `finally`.
- Маркер старше `TAKEOVER_STALE_S` (60 s) оставила убитая проверка. Он удаляется, захват идёт дальше. Если удалить
  его не удаётся — ошибка с его именем.
- ENOENT при чтении отложенного файла: так бывает в гонке со старым wave-gate, который маркер не делает. Теперь это
  тот же понятный отказ.

Точка остановки для test-ов (`WAVE_GATE_PID_SYNC`):

- новая точка `stale`;
- метка теперь `<точка>-<pid>`;
- ожидание — цикл без паузы вместо сна по 20 ms. Две проверки идут дальше с разницей в микросекунды. Со сном гонка
  ловилась примерно в половине прогонов (1 из 2).

Test-ы в `harness/bin/tests/wave-gate-merge.test.sh`:

- Гонка двух проверок над устаревшим pid-файлом. Ровно одна запускает gate и выходит с кодом 0. Другая выходит с
  кодом 1 и сообщением «another wave-gate check», без `Error:`. Не остаётся ни `.pid`, ни `.started`, ни `.stale-*`,
  ни `.takeover`.
- Молодой маркер: выход 1, pid-файл и маркер не тронуты. Старый маркер: удалён, pid-файл снят.

Прогоны на ПК, каждый с временным HOME:

- Гонка отдельно (`race66.sh`, только этот case):
  - без правки — 10 из 10 красных, ENOENT на `…pid.stale-<pid>`;
  - с правкой — 10 из 10 зелёных.
- Файлы test-ов на итоговом коде, все с exit 0:
  - `wave-gate-merge.test.sh`: 58 passed (было 55 и три новых), 174 s;
  - `wave-gate.test.sh`: 71 passed, 174 s;
  - `wave-gate-lock.test.sh`: 27 passed;
  - `wave-gate-lock-killed.test.sh`: 4 passed;
  - `wave-gate-heartbeat.test.sh`: 14 passed;
  - `wave-gate-screen.test.sh`: 5 passed.

Review (correctness): блокирующих находок нет. Две низкие исправлены — ENOENT при чтении и старый маркер, который
не удаляется. Ещё две оставлены, они названы в PR:

- маркер проверяется на возраст и удаляется не атомарно — то же есть в `takeOver()`;
- pid-файл сравнивается только по тексту, а pid может достаться новой проверке; так было и до правки.

Осталось: `wave-gate.test.sh` на Mac.

Review моста (корректность, Mac): блокирующих находок нет. На Mac `wave-gate-merge`, `wave-gate`, `wave-gate-lock` — exit 0
(20 s, 25 s, 38 s); с `wave-gate` из `main` `wave-gate-merge` — exit 1. Случай гонки — регрессионный test только для
Windows: на macOS переименование и так исключает вторую проверку (mutant без `mkdir` маркера краснеет только в двух
случаях про маркер). Низкая находка — в следующий PR, который тронет `harness/bin/wave-gate`: маркер, оставленный
убитой проверкой (SIGKILL, TerminateProcess), 60 s даёт отказ «another wave-gate check is taking over … at the same
moment», хотя никто не захватывает; сообщение должно назвать путь маркера и срок 60 s (`harness/bin/wave-gate:545`).
Вопрос на замер ПК: на Windows `mkdir` маркера может получить EPERM вместо EEXIST, пока другой процесс держит handle
удалённой папки (`:539`).
