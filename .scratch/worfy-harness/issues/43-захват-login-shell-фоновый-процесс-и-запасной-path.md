Blocked by: 37
Source: ревью PR #305 (Ticket [37](37-скрипты-harness-из-главного-процесса-без-окружения-login-shell.md), срез 1), круг 1, 2026-10-14 — замечания low «rc-файл оставляет фоновый процесс», «старт из терминала при неудачном захвате» и замер старта; «Риски» Ticket-а 37. Срез 2 Ticket-а 37 (PR #311, head `57e9422`) меняет в `src/main/agent/env.ts` только пустой `SHELL` и шапку; эти два пункта он не трогает. Код перечитан по main `1c1beadd`.

## Что происходит

- **Окружение login shell.** worfy запускает `$SHELL -ilc` из минимального окружения и берёт его
  переменные (ADR-0007): `captureLoginShellEnv` (`src/main/agent/env.ts:97-121`). Результат кэшируется
  один раз на запуск приложения (`agentEnv()`, `:513-522`). С PR #305 этим окружением запускаются и
  скрипты Harness — `epic-status`, `profile`, `ticket` (`src/main/harness/script-env.ts:28`).
- **Фоновый процесс rc-файла держит захват до предела.** Shell запускается через `execFile` с
  пределом 10 s (`SHELL_TIMEOUT_MS`, `env.ts:35`) и `killSignal: 'SIGKILL'` (`:109`). Ответ
  читается в callback, а он приходит, когда закрылся вывод shell (`:105-119`). Процесс, который
  rc-файл оставил в фоне и который держит этот вывод, не даёт ему закрыться, и захват ждёт все
  10 s, хотя окружение уже напечатано. Это было и до PR #305, но теперь эти 10 s ждут и Epic-и.
- **Замер старта (ревью PR #305, shell-подмена):** первый `workflow.open` за запуск ждёт захвата —
  2038 ms при shell, который отвечает за 2 s, и 10031 ms при shell, который не отвечает; до PR #305 —
  27 ms; следующие вызовы — 25 ms. Окно, список Project-ов и первая отрисовка не ждут.
- **Запасной PATH теряет node.** Если захват не удался (shell упал, не уложился в 10 s, не
  напечатал маркеры), результат — минимальное окружение с PATH `/usr/bin:/bin:/usr/sbin:/sbin`
  (`SYSTEM_PATH`, `env.ts:29`; `shellBaseEnv`, `:38-45`; запасной результат — `:103`). Так задумано
  для старта из Finder (ADR-0007). Но при старте из терминала у самого процесса worfy PATH с node
  был, и до PR #305 скрипты Harness его получали. Теперь Silent Project (Project без файлов Harness
  в репозитории) у такого пользователя показывает «No epics in .scratch/» вместо своих Epic-ов.
  Кому это грозит: tcsh и csh (не принимают `-ilc`), rc-файлы дольше 10 s. Подключить Project через
  окно такой пользователь не мог и до PR #305 (ревью PR #305).
- **На Windows запасной путь уже другой:** если реестр не прочитался, остаётся `Path` процесса
  worfy (`env.ts:483-487`).

## Что делаем

1. **Захват заканчивается, как только напечатан маркер конца.** Читать вывод shell по мере
   прихода; встретился `ENV_END_MARKER` (`env.ts:34`) — разобрать окружение, ответить и завершить
   shell. Фоновый процесс rc-файла больше не держит ответ. Предел 10 s остаётся для shell, который
   не печатает ничего.
2. **Запасной PATH — решение с записью в «Итог».** Варианты:
   - (а) при неудачном захвате к системному PATH добавить PATH процесса worfy после него, как на
     Windows; для всех, кто берёт `agentEnv()` (Session-ы Claude Code, Terminal, скрипты Harness);
   - (б) то же только для скриптов Harness (`harnessScriptEnv`);
   - (в) не менять: причину уже показывает окно (срез 2 Ticket-а 37).
   Вариант (а) меняет окружение Claude Code, которое описывает ADR-0007: тогда к ADR-0007 —
   строка статуса с датой и ссылкой на этот Ticket.
3. **Номера строк** перечитать после merge PR #311: он добавляет в `env.ts` строки выше захвата.

## Риски

- **Shell, завершённый раньше,** не дойдёт до logout-файлов (`.zlogout`, `.bash_logout`). Окружение
  от этого не меняется. Проверить на zsh и bash, что в журнале worfy нет новой ошибки.
- **Вариант (а) меняет поведение Session-ов** при неудачном захвате: инструменты из PATH терминала
  станут видны Claude Code. Это ближе к ожиданиям пользователя, но расходится с текстом ADR-0007.

## Итог

PR [#639](https://github.com/IDSAD-XL/worfy/pull/639), merge 9848f563. Gate full Mac зелёный. Не платформенный PR. Ревью:
три круга. Круг 1 (high) — BLOCK обеих линз; круг 2 (medium) — PASS с тремя low; круг 3 их исправил.

- **Захват отвечает по маркеру конца.** `captureLoginShellEnv` читает вывод shell потоком (`spawn`) и отвечает, как только
  пришёл `ENV_END_MARKER`; на test-е — около 11 ms вместо 10 s на main. Предел 10 s — для shell, который ничего не печатает.
- **Фоновый процесс rc-файла не убит.** Первая версия закрывала вывод (`stdout.destroy()`), и фоновая задача, писавшая
  позже, умирала от SIGPIPE (находка круга 1). Теперь после ответа worfy дочитывает и выбрасывает stdout/stderr, пока
  задача их не закроет; закрывается только вывод сверх 16 MB. Отдельный дескриптор (fd 3) не годится: на macOS
  `bash -ilc` и `sh -ilc` закрывают унаследованные fd ≥ 3. После ответа процесс shell и его потоки — `unref`, они не
  держат выход приложения. Пункт «вывод закрыт со стороны worfy» поэтому не выполняется — он противоречил находке.
- **Цена дочитывания:** захват повторяется за сеанс (повтор чтения Epic-ов после неудачи, «Check again», Settings →
  Health); каждый держит два pipe-а, пока жива задача rc-файла. Рост ограничен числом захватов — принято.
- **EMFILE** (нет pipe-ов): сразу запасной результат, без исключений и без сигнала процессу, который не запустился.
- **Причина запасного результата** снова содержит хвост stderr shell (до 4 KB); тексты «exit code N», «killed by SIG…»,
  «printed no environment» покрыты test-ами.
- **Запасной PATH — вариант (б):** при неудачном захвате скрипты Harness получают PATH процесса worfy после системного,
  без повторов. Session-ы Claude Code и Terminal — по-прежнему системный PATH; ADR-0007 не меняется. Windows не тронут.
- **Test-ы** (`test/contract/login-shell-capture.test.ts`): ожидания по файлу-сигналу, без фиксированных пауз; 16 test-ов;
  мутанты красные: ответ по закрытию вывода, `destroy` вместо дочитывания, без обработчика `error`, без проверки 16 MB,
  stderr `inherit`, `output += chunk` до проверки `settled`, без `unref`, сигнал без pid.
- **Не проверено:** выход настоящего приложения при живой фоновой задаче rc-файла; fish.
