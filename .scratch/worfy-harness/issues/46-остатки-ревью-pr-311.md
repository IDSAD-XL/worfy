## Что происходит

1. **CA-1 (medium, пробел в test-ах).** «Check again» восстанавливает и неудачу, которая не про окружение:
   старый node на захваченном PATH падает с exit code 1, пользователь ставит новый node, жмёт
   «Check again» — Epic возвращается (замер ревью: 0,6–2,8 s, один запуск shell). Делает это
   `retryFailedLayout` (`src/main/workflow/watch.ts:318-327`): он спрашивает любую неудачную раскладку.
   Но все новые test-ы дают только неудачу окружения: `failedLayout(at, NO_NODE, true)` в
   `test/contract/workflow-watch-retry.test.ts:159-278` и exit code 127 в
   `test/contract/harness-script-env.test.ts:264-301`. Мутант K13 — спрашивать только неудачи
   окружения — переживает 8 файлов test-ов; с ним такой Project остаётся красным до перезапуска.
2. **CA-2.** `WorkflowHub.retryFailedLayouts` ждёт, пока закончат запуск все Project-ы хаба, и только
   потом спрашивает неудачные (`watch.ts:547-550`, `Promise.all`). Один медленный запуск (`profile` до
   15 s, `ticket root` до 15 s, первый `epic-status` до 60 s) задерживает восстановление всех. Замер:
   неудачный Project спрошен через 2000 ms, когда соседний Project отвечал 2 s.
3. **CA-3.** Каждый вызов `firstRun.checks` — «Check again», открытие First run без отчёта и каждый
   показ Settings → Health — спрашивает каждый неудачный Project и сбрасывает его back-off на 10 s.
   Project, который не восстановится, получает 4 чтения за 100 s после каждого показа Health вместо
   одного за 5 минут; при exit code 127 три из них снимают login shell. Это не шторм: окно ведёт одну
   проверку за раз (`src/renderer/shell/first-run-store.ts:24`). В «Behaviour changes» PR сброс
   back-off не назван.
4. **CA-4.** Doc comment `HarnessScriptEnvRequest` (`src/main/harness/script-env.ts:29-31`) говорит,
   что `always` следует и за скриптом, который «could not be started». После PR #311 ошибка запуска —
   обычная неудача, повтор просит `if-fallback`.
5. **R3-REST-1.** Настоящая авария node доходит до окна мусором. `scriptFailureDetail`
   (`src/main/workflow/profile.ts:78-86`) убирает строки `at …`, `Node.js vNN` и `^`, но не нативный
   стек (`----- Native stack trace -----`, ` 1: 0x… node::Abort(…)`) и не блок `<--- Last few GCs --->`,
   а строку `FATAL ERROR: … JavaScript heap out of memory` не берёт за строку ошибки. Подсказка строки
   First run на любой сигнал — «install the Harness plugin again», хотя при SIGABRT от нехватки памяти
   или SIGKILL плагин ни при чём.
6. **R3-REST-2.** В `harness/bin/profile:152-153` две ветки выбора строки без test-а: мутанты H6 (без
   фильтра `^`) и H7 (регулярка строки ошибки сужена до `^Error`) не роняют `profile.test.sh`. Случай
   аварии resolver-а опирается на то, что `gate-resolve.mjs` падает на записи `null`; когда resolver
   начнёт проверять записи (exit 4), случай сломается не из-за `profile`.
7. **R3-REST-3, тексты.** Ticket 37 говорит «85 test-ов» — их 82. «То же правило, что у
   `scriptFailureDetail`» (`harness/bin/profile:146-148`, Ticket 37, тело PR #311) верно для фильтров,
   но не для запасного варианта: `profile` берёт последнюю строку, `scriptFailureDetail` — первые три.
   `profile.ts:162-164` называет вывод больше предела скриптом, который «could not be started». В
   «What changes» PR #311 сигнал не назван среди неудач.

## Что делаем

1. CA-1: test-ы «Check again» для неудачи без окружения — в `workflow-watch-retry.test.ts`
   (`failedLayout(at, '…exit code 1…', false)`, простой запрос и восстановление) и вариант RC5 в
   `harness-script-env.test.ts` (старый node, exit 1, затем новый). Мутант K13 красный.
2. CA-2: спрашивать каждый watcher, как только закончился его собственный запуск
   (`project.watcher.then((w) => w.retryFailedLayout(), () => false)`), считать `true`. Test: медленный
   запуск соседа не задерживает ответ неудачного Project-а.
3. CA-3: решение исполнителя — либо `retryFailedLayout` снимает только ждущий таймер и не сбрасывает
   ступень back-off, либо сброс остаётся и называется в «Итоге» и комментариях. Test на выбранное.
4. CA-4 и R3-REST-3 — правка текстов и комментариев.
5. R3-REST-1: `FATAL ERROR:` считается строкой ошибки; строки нативного стека и блок GC
   отбрасываются. Подсказка на сигнал не отправляет переустанавливать плагин, если сигнал не про него
   (текст выбирает исполнитель). Test с настоящим `process.abort()` и с заготовленным stderr нехватки
   памяти.
6. R3-REST-2: подмена resolver-а, которая бросает TypeError со свойствами (`{ code: … }` после
   строки), и stderr со строкой `^`. Мутанты H6 и H7 красные.
