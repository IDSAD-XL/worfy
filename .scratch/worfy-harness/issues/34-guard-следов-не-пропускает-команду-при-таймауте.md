## Что происходит

В Silent mode репозиторий и его PR не должны нести следов workflow (имён Epic-ов, номеров Ticket-ов и
ADR, путей Workflow folder, `.scratch`, `HANDOFF`), а при `attribution: off` — строк атрибуции Claude.
Перед командами, которые публикуют текст (`git commit`, имя ветки, `gh pr create` и другие), hook
`harness/hooks/guard.mjs` зовёт `bin/silent-check` и отказывает, если тот нашёл след.

- Вызов — `spawnSync(…, { timeout: 8000 })` (`guard.mjs:192`). Отказ даётся только при коде 1
  (`:193`). Любой другой исход пропускает команду: код 2 (Profile не читается —
  `harness/bin/silent-check:90`, `:114`), таймаут 8 секунд (кода нет, `r.error`/`r.signal`), сбой
  запуска, неизвестный код.
- Комментарий над функцией (`guard.mjs:163-164`) говорит: «A failure of the check itself lets the
  command through: the guard must not break a session because a profile is unreadable». Довод верен
  для нечитаемого Profile-а, но тем же правилом пропускается и таймаут.
- Следствие: на загруженной машине (а проверка читает индекс git и файлы) коммит или PR со следом
  уходит без проверки, и никто об этом не узнаёт. 2026-10-12–13 на Mac владельца служба уведомлений
  о файлах и test-ы со сроками не укладывались в пределы часами — таймаут здесь не редкость.
- У самого hook-а в `harness/hooks/hooks.json` предел 10 секунд (`:140`): повтор внутри hook-а
  должен в него уложиться, иначе Claude Code снимет hook целиком — что он делает с командой при
  снятом PreToolUse hook-е, проверить при работе и записать в «Итог».

## Что делаем

1. Исходы вызова `silent-check` разделяются явно:
   - код 0 — команда идёт;
   - код 1 — отказ, как сейчас;
   - код 2 с причиной «Profile не читается» — команда идёт (единственный оставшийся пропуск);
   - таймаут — проверка повторяется один раз; если и повтор не успел — отказ с причиной: что
     проверка следов не закончилась за N секунд, что команда не выполнена и что её можно повторить;
   - всё остальное (сбой запуска, сигнал, неизвестный код, код 2 с другой причиной) — отказ с
     причиной и текстом ошибки. Развилку «код 2 с другой причиной» (например, не читается корень
     Ticket-ов, `silent-check:114`) решить при работе и записать в «Итог»: владелец назвал пропуском
     только нечитаемый Profile.
2. Сроки первого вызова и повтора выбрать так, чтобы оба уложились в предел hook-а; если предел
   hook-а нужно поднять — правка `hooks.json` входит в Ticket.
3. Комментарий над функцией и текст отказа — по новому правилу. Текст отказа называет команду
   (`git commit`, `gh pr create` …) и не советует обходить guard.

## Готово, когда

- [ ] `silent-check` не отвечает дольше срока в обоих вызовах: команда получает отказ с причиной
      (подставной `silent-check` через `CLAUDE_SILENT_CHECK_BIN`, который спит).
- [ ] Первый вызов не успел, повтор ответил 0 — команда идёт; повтор ответил 1 — отказ со следами.
- [ ] Profile не читается (код 2 с этой причиной) — команда идёт, как раньше.
- [ ] Сбой запуска `silent-check` (файла нет) и неизвестный код — отказ с причиной.
- [ ] Full Project с включённой атрибуцией — как раньше: проверка отвечает 0 сразу, задержки нет.
- [ ] Весь hook укладывается в свой предел из `hooks.json` и при двух таймаутах подряд (замер — в «Итог»).
- [ ] `bash harness/hooks/tests/guard-silent.test.sh` — код 0; новые случаи красные на мутантах
      «таймаут пропускает», «нет повтора», «любой код, кроме 1, пропускает».
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` — код 0; gate full на Mac зелёный.

## Риски

- Отказ вместо пропуска может остановить Session на машине, где проверка стабильно не успевает.
  Текст отказа должен дать выход: повторить команду; если не помогает — назвать, что проверить
  (нагрузка, `silent-check` вручную с тем же текстом).
- Правка `harness/` действует после `pnpm install:stable` — шаг владельца.
- `harness/hooks/` правят и открытые Ticket-ы других Epic-ов (`worfy-windows` — hooks Harness на
  Node): перед claim сверить открытые PR и разделы «Где в коде».
