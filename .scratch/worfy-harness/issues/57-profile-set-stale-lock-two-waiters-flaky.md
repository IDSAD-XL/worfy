## Что происходит

В `harness/bin/tests/profile-set.test.sh` (около строк 280–313, запускается из
`test/contract/harness-scripts.test.ts`) два писателя видят один и тот же устаревший замок:

- B стартует с `PROFILE_SET_STALE_PAUSE_MS=1500`: признаёт замок устаревшим и спит 1,5 s, прежде чем
  забрать его;
- через `sleep 0.5` стартует A с медленным `git` (stub спит 3 s на `commit`), забирает замок и держит
  его весь commit;
- через `sleep 2.5` test читает владельца замка, потом ждёт обоих.

Порядок «A забрал замок раньше, чем B проснулся» держится только на паузах. Под нагрузкой A стартует
позже 1,5 s паузы B: B забирает замок первым и пишет своё значение, A получает exit 5. Красные строки
2026-10-20: «B, from the same read, gets exit 5 after A» и «the file holds A's value» (95 passed,
4 failed в этом скрипте).

## Что делаем

1. **Сначала красный и детерминированный test.** Порядок задаётся не временем, а событиями:
   B после решения «замок устарел» ждёт файл-сигнал, который ставит A, когда уже держит замок
   (например, stub `git` создаёт файл при входе в `commit`). Варианты механизма — переменная для test-а
   в `harness/bin/profile-set` (ждать файл вместо паузы, как `PROFILE_SET_STALE_PAUSE_MS`) или обёртка
   в test-е; выбор — в «Итог». Test с принудительным «неправильным» порядком воспроизводит красный
   на main без нагрузки.
2. **Правка.** Если воспроизведение показывает дефект `profile-set` (B при захвате устаревшего замка
   может снести замок A) — правка в `profile-set`. Если дефекта нет и красный был только от порядка
   запуска — правка в test-е: порядок задаётся сигналом, паузы `sleep 0.5` / `sleep 2.5` уходят.
3. Остальные test-ы файла с паузами-«порядками» (`sleep` между фоновыми писателями) — проверить тем же
   взглядом и перечислить в «Итог».

## Итог

PR [#599](https://github.com/IDSAD-XL/worfy/pull/599), merge 56216a77. Gate full на merge с main 11418a09 зелёный
(plugin-neutral 26/0, harness-scripts 44/44); Windows verdict: `profile-set.test.sh` 87/0, три случая двух
ожидающих пропущены с причиной.

- **Причина — test, не `profile-set`.** Воспроизведено на main без нагрузки: старый test, где старт A задержан
  на 3 s, даёт те же 4 FAIL, что gate (подтвердили implementer и ревьюер). Дефекта в захвате замка нет.
- **Спецификация при принудительном порядке «B забирает замок раньше A».** B пишет своё значение, exit 0;
  A находит живой чужой замок, возвращает его нетронутым, ждёт и выходит с exit 5 (то же чтение, fingerprint
  сменился); файл держит значение B. Симметрично для «A первым»; третий случай — B стартует на 3 s позже.
- **Механизм.** Переменная только для test-а в `harness/bin/profile-set`: `PROFILE_SET_STALE_PAUSE_MS`
  заменена на `PROFILE_SET_STALE_SYNC` — папка сигналов. Писатель пишет token в `judged`, ждёт `go`
  (до 30 s по `Date.now()`) и ставит `tried` после попытки захвата. Без переменной рабочий путь прежний.
  Stub `git` ставит `in-commit` и держит commit до `release`. Порядок задают только файлы-сигналы.
- **Проверки ожидания.** Test проверяет `kill -0`, что проигравший жив, пока держатель в commit
  («the other waits while the lock is held»). Каждый `wait_for` (до 15 s) при отсутствии сигнала даёт
  именованный FAIL и отпускает обоих писателей, а не timeout файла.
- **Мутанты красные:** снос отодвинутого замка без сверки token; чужой замок не возвращается; писатель
  игнорирует `go` (FAIL за 61 s, в пределах 120 s); проигравший идёт дальше без замка; держатель выходит с 3.
- **Прогоны:** `profile-set.test.sh` 5 раз подряд — exit 0, 117 passed, 11–12 s; ранее 20 из 20;
  `plugin-neutral.test.sh` — exit 0.
- **Остальные паузы файла (п. 3).** `:264` (`sleep 0.5; rmdir` замка, пока писатель ждёт) и `:382`
  (`sleep 1` перед писателем B в «two writers from the same read») порядок не решают: при любом порядке
  исход тот же (exit 0 и запись; B exit 0, A exit 5, потому что A получает stdin только после `b-done`).
  `sleep 0.05` / `0.1` — опрос файлов.
- **Вне скоупа:** окно в `takeOver()` между `rename` замка в сторону и возвратом — ticket 59.
