# 02 — Линза ревью «упрощение»: что можно удалить, переиспользовать или упростить в diff-е

Type: task
Status: open
Blocked by: 01
Source: решение владельца 2026-10-09 («Хорошие идеи, сохрани их и добавь в планы к имплементации»), пункт «линза упрощение» из таблицы; [исследование](../../../docs/research/2026-10-09-ponytail-pstack-thermos.md), разделы о Thermos (skill ревью качества кода из plugin-а Cursor) и о ponytail (skill минимального изменения, его команда `/ponytail-review`); [spec.md](../spec.md)

## Что происходит

- **Линзы worfy — только названия.** В Profile (`~/.claude/worfy-harness/projects/worfy/profile.json`,
  вне git) поле `review.lenses` = `корректность`, `границы модулей`, `тесты`. Контракт поля —
  `harness/profiles/README.md:175-176`. Текста, что именно смотрит линза, нет ни в
  `harness/agents/reviewer.md`, ни в README Profile-а. Reviewer угадывает смысл линзы по названию.
- **Никто не ищет, что в diff-е лишнее.** Линза «границы модулей» спрашивает, на месте ли граница. Она
  не спрашивает, можно ли перестроить код так, чтобы ветка, слой или обёртка исчезли.
- **В источниках есть готовые списки.**
  - Thermos ищет «code judo» — перестройку без смены поведения, после которой исчезают ветки, режимы
    и слои. Ещё он ищет тонкие обёртки, приведения типов, `any`, лишние необязательные поля, логику не
    в своём слое и повторы существующих helper-ов.
  - ponytail-review ищет, что можно удалить, что уже есть в коде (с путём), что даёт стандартная
    библиотека, что не нужно сейчас (YAGNI). Ещё — что объединить, а что разделить по задачам.

## Что делаем

1. **Описание линзы — в `reviewer.md`**, новый раздел «Lens: simplification» по-английски. Содержание —
   два списка источников, сведённые в один:
   - перестройка, после которой исчезают ветки, слои или обёртки;
   - тонкие обёртки и функции-тождества;
   - приведения типов, `any` и `unknown` без нужды, лишние необязательные поля;
   - логика не в своём слое; повтор helper-а, который уже есть (с путём к нему);
   - удалить; взять из стандартной библиотеки или уже установленной зависимости; не нужно сейчас;
     объединить; разделить по задачам.
2. **Три фильтра в том же разделе:**
   - нет конкретного случая (строки, входа, повтора) — нет находки;
   - комментарий `shortcut: <предел>, <когда переделать>` — решение автора, не находка. Формат
     комментария первым записывает этот Ticket; Ticket 04 переносит его в `implementer.md` без
     изменений (spec, раздел «Волны», Wave 3);
   - перестройка за пределами файлов «Где в коде» Ticket-а — предложение нового Ticket-а, не
     блокирующая находка.
3. **Название линзы.** В Profile линза называется `упрощение`. Раздел в `reviewer.md` говорит, что
   линза `упрощение` и `simplification` — одна и та же. Кириллическое слово добавляется в `ALLOWED`
   test-а `agents-text.test.sh`.
4. **`harness/profiles/README.md`**: в строке `review.lenses` — ссылка на раздел описаний в
   `reviewer.md` и правило: линза без описания читается по названию, как сейчас.
5. **Шаг владельца, не в PR.** Skills этот Ticket не меняет: линзы из Profile уже берут два места
   (spec, «Как устроено», пункт «Где работают линзы»):
   - ship-ticket, шаг 7 — линзы по умолчанию из `review.ticket_lenses`;
   - правило Orchestrator-а Phase 2 — ревью перед каждым отчётом
     (`harness/hooks/rules/orchestrator.md:105-111`): одна линза из `review.lenses` или несколько,
     их выбирает Orchestrator, в любой Session, в том числе в Session Wave.

   Владелец добавляет `упрощение` в `review.lenses` Profile-а worfy. После этого Orchestrator может
   дать её reviewer-у в Phase 2. Чтобы ship-ticket запускал линзу по умолчанию на каждом Ticket-е,
   она нужна и в `review.ticket_lenses`. Там по контракту «две или три» линзы
   (`harness/profiles/README.md`, строка `review.ticket_lenses`), а у worfy их уже три:
   `корректность`, `границы модулей`, `тесты`. Цели «по умолчанию» отвечает только один вариант —
   заменить одну из трёх на `упрощение`. Убрать поле не помогает: без него ship-ticket сам берёт две
   или три из `review.lenses` по теме изменения (`harness/skills/ship-ticket/SKILL.md`, шаг 7), и
   `упрощение` идёт, только когда её выбрали. Затем `pnpm install:stable` (ADR-0047: правка Harness
   вступает в силу только в установленной копии). Исполнитель пишет в «Итог» точную правку Profile:
   какую из трёх линз заменить и почему.

## Вне скоупа

- Описания трёх существующих линз. Их можно дописать по тому же образцу, но это отдельный Ticket.
- Правило 1000 строк — в Gate, Ticket 03, не в prompt.
- Правка Profile на машине — шаг владельца.
- Skills ship-ticket и epic-wave. Запуск линз Profile в Gate каждой Wave (epic-wave, раздел 3) — не
  в этом Epic-е. В Wave линза «упрощение» работает в Phase 2 Orchestrator-а, когда он её выберет, и
  перед рискованным merge — через режим расширенного ревью Ticket-а 07.

## Риски

- **Ложные находки и разрастание Ticket-а.** Ambitious prompt Thermos предлагает перестраивать всё
  подряд. Третий фильтр уводит это в новые Ticket-ы.
- **Стоимость.** Ещё один reviewer на каждый diff, примерно один контекст diff-а.
- **Открытый вопрос:** где жить описаниям линз — в `reviewer.md` (предложено выше: один файл, одна
  версия с Harness) или объектами в Profile (каждый Project со своими текстами, но вне git). Решает
  исполнитель, итог — в «Итог».
