- **Замер цены круга, 2026-10-12, токены Subagent-ов.** `high` — 5,3–6,4 млн: четыре круга на

## Что делаем

Решения владельца 2026-10-12. Шкала, названия как у effort:

| Ступень | Что входит | Цена круга, токены |
|---|---|---|
| `low` | один агент читает diff и запускает test-ы PR | меньше 0,5 млн (оценка) |
| `medium` | два агента: пункты прошлого отчёта и уже готовые таблицы; mutation testing только по изменённым строкам; refute только для находок `med` и `high` | 1–2 млн (оценка) |
| `high` | три-четыре агента: своя таблица на настоящем коде, сравнение macOS с main, mutation testing всех строк кода PR, линза безопасности; refute для каждой находки | 5,3–6,4 млн (замер) |
| `max` | `high` и ревью всей ветки из Ticket-а 07 (две линзы, две модели) | около 10 млн (оценка) |

- **Где действует шкала** (решение владельца 2026-10-12). Умолчания ниже — для ревью PR, который
  написала другая Session или другой человек. В Wave под Autopilot глубина остаётся нынешней: один
  verifier, это примерно `low`; скептики идут только в узком круге доработки.
- **Умолчания для ревью чужого PR.** Первый круг PR с кодом — `high`; следующие круги — `medium`;
  PR только с документами — без ревью агентами; `max` — только по просьбе владельца.
- **Владелец меняет ступень словом** в сообщении («ревью #237 — low»). Каждый отчёт о ревью называет
  ступень и число токенов. `gate full` в шкалу не входит: он обязателен перед любым merge кода.
- **Что блокирует merge.** Только находка `high` или `med` в коде или пробел в test-ах на
  разрушающее действие (удаление, завершение процесса, замена копии). Остальные пробелы — списком в
  follow-up Ticket. Не больше трёх кругов на PR, если не осталась находка `high`. Этот предел — тоже
  только для ревью чужого PR: Wave оставляет свой счёт, один круг доработки и один узкий
  (решение владельца 2026-10-12).

Что делает Ticket:

1. **Поля Profile** (предложено, в стиле контракта): `review.depth.wave` — глубина в Wave;
   `review.depth.first_round` и `review.depth.later_rounds` — глубина ревью чужого PR. Значение —
   `low`, `medium`, `high` или `max`. Нет поля — skill берёт `low`, `high` и `medium` и говорит об
   этом. Строки — в `harness/profiles/README.md` и `draft.schema.json`.
2. **Skills `ship-ticket` и `epic-wave`** читают поле и принимают аргумент ступени, который его
   перекрывает; слово владельца в сообщении — тот же аргумент. Форму аргумента выбирает исполнитель.
   Для каждой ступени skill называет число агентов, линзы, mutation testing и находки для refute.
3. **`max` и Ticket 07.** `max` — это `high` и затем `/worfy:max-review`. Ticket 07 остаётся
   отдельным, его `Blocked by` не меняется. Предложено: пока 07 не влит, ступень `max` отвечает одной
   строкой, что она недоступна; связь двух skills дописывает тот Ticket, который вливается вторым.
4. **Отчёт: две новые строки** — ступень и токены Subagent-ов за круг: в шаге 7 ship-ticket, в
   отчёте Wave (`epic-wave/SKILL.md:576`) и в записанном вердикте. В вердикте они не первая строка и
   не начинаются с `REJECTED` или `gate:`: первую строку читает worfy (`src/main/github/prs.ts:164`),
   круги считаются по началу строки (`epic-wave/SKILL.md:262`, `:270`, `:341`).
5. **Правило блокировки** — в текст обоих skills. **Предел в три круга** — только в описание
   ревью чужого PR. Такого описания в `harness/` сейчас нет (grep по `needs-mac-gate` пуст): где
   оно живёт — отдельный skill или раздел `ship-ticket` — решает исполнитель, выбор — в «Итог».
6. **Eval-кейс — желательный:** платный прогон eval-кейсов заблокирован (spec, `:53-55`). Новый кейс
   дописывает имя в `CASES` (`test/contract/harness-evals.test.ts:18-29`) и число в названии test-а
   (`:84`). Skills уже проверяют четыре кейса (`:19-22`).

## Риски

- **Ревью чужого PR в `harness/` не описано.** Замеры `high` сделаны на нём: Mac проверяет PR с
  Windows-ПК. Ticket впервые даёт этому ревью текст; до него шкалу держит правило проекта вне
  репозитория.
- **`review.depth.wave` выше `low` дорог.** С `high` каждый Ticket Wave стоит 5,3–6,4 млн токенов.
  Skill говорит цену, когда поле задано выше `low`.
- **Откуда число токенов.** Как Orchestrator узнаёт токены своих Subagent-ов — не проверялось. Нет
  числа — строка отчёта говорит «not measured», а не оценку.
- **Общий файл** `epic-wave/SKILL.md` — с Ticket-ами 06 (журнал решений) и 07. Кто вливается вторым
  — rebase и все проверки заново. Уровни находок там — `high` / `med` / `low` (`:290-291`): ступень
  в тексте skill-а всегда стоит со словом `depth`.
