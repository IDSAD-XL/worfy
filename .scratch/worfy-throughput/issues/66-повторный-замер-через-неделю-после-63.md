# 66 — Повторный замер через неделю после Ticket-а 63: Gate → merge на Wave, минуты CI, красные `main` от несовместимых PR

## Что происходит

- ADR-0103 убрал rebase ради свежей базы. Ticket 62 ждал от этого: Wave из 5 PR — Gate → merge ≈ 15 min вместо
  ≈ 105 min (p90 ≈ 290), около 1 800 min CI меньше за двое суток.
- Цена — skew (несовместимость PR, каждый из которых зелёный сам по себе) виден только в push-run-е на `main`.
- Порог владельца (Q2): 2 или больше красных `main` от несовместимых PR за одну неделю — вопрос о передаче
  репозитория в организацию ради GitHub merge queue.

## Что делаем

Замер, не код. Начать не раньше чем через 7 дней после merge Ticket-а 63; окно — эти 7 дней.

1. Те же команды, что в «Итог» Ticket-а 62, часть 2 (`gh pr list … --state merged`, `gh api …/actions/runs`,
   `…/jobs`, `…/commits/<sha>/statuses`), на окне после 63; рядом — числа Ticket-а 62 для сравнения.
2. Σ Gate → merge на Wave (`scripts/critical-path.mjs` по Wave-ам окна) против Wave-ов до 63.
3. Минуты CI на PR и доля минут на заменённых head-ах; число rebase-ов зелёного head-а (ожидается: только на
   конфликт).
4. Красные push-run-ы `main` с кодом: сколько, какие job-ы, сколько стали зелёными после одного повтора упавших
   job-ов (flaky), сколько — от несовместимых PR (у виноватого PR `ci-ok` на своём head зелёный, повтор красный,
   исправление касается сочетания PR). Для каждого — run, виноватый PR, исправление или revert, сколько стояла пауза
   merge.
5. Сравнить число красных `main` от несовместимых PR с порогом Q2. Порог пройден — вопрос владельцу о варианте A
   (merge queue в организации) с этими числами; нет — строка «порог не пройден» в «Итог».
