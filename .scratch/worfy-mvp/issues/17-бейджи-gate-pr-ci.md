## Что делаем

**Gate** (`~/.claude/hooks/gate.sh`) держит состояние по каждому worktree в
`<WORFY_CLAUDE_HOME>/gate/state/`: `red-<ключ>-<tag>` (красно) и `unverified-<ключ>-<tag>` (не
удалось проверить), где `tag` — первые 8 символов `shasum` (SHA-1) от пути worktree, а ключ —
запись репозитория в `gate/config.json`.

- `src/main/gate/state.ts`: для каждого worktree Проекта считает `tag`, находит ключ по
  `config.json` (самый длинный совпавший `match`), читает маркеры. Нет маркеров — исход берётся
  из последней строки `[gate] зелено | красно | ничего не прогналось | ПРОВЕРИТЬ НЕ УДАЛОСЬ` в
  транскриптах Сессий этого worktree (hook-и и вывод Bash). Итог: «зелено», «красно», «не удалось
  проверить», «нет данных». «Ничего не прогналось» — это «нет данных», не «зелено».
- Бейдж Gate — на Узле Сессии (по её `cwd`) и на Тикете (worktree или ветка → Тикет через
  `ticket-ref.ts`).
- **PR и CI** (`src/main/github/prs.ts`): раз в 60 с, только пока окно активно, один вызов
  `gh pr list --state all --limit 100 --json number,headRefName,state,url,statusCheckRollup,comments`
  в корне Проекта (без `--limit` `gh` отдаёт 30 последних PR, на Auction этого мало). Тикет в
  работе или с веткой worktree, чьей ветки в этом списке нет, добирается отдельным
  `gh pr list --state all --search "head:<ветка>" --limit 1` — не чаще раза в 5 минут на ветку. Ветка → Тикет через `ticket-ref.ts`. CI сводится к `passing | failing | running`.
  Вердикт ревьюера — последний комментарий, чья первая строка `VERIFIED` или `REJECTED`. Ошибка
  `gh` (нет, не залогинен, нет сети) — один бейдж «gh unavailable» и удвоение интервала, без
  потока ошибок.
- Только чтение: никаких команд `gh`, которые что-то меняют.
- Бейджи — `badges/ChecksBadges.tsx` в слоте Тикета и Сессии; цвета — токены ready / working /
  blocked с подписью.

## Итог

**Сначала падающий test.** `test/unit/gate-state.test.ts` со сверкой `gateTag(путь)` с
`printf '%s' <путь> | shasum | cut -c1-8` написан до `src/main/gate/state.ts`: прогон упал на
импорте несуществующего модуля, код 1.

**Как устроено.**
- `src/main/gate/state.ts` — `gateTag` (SHA-1 пути, 8 hex), `gateKey` (как
  `gate-resolve.mjs --which`: запись `config.json`, чей `match` — корень Проекта или папка выше,
  побеждает самый длинный; регистр `match` выравнивается по диску так же), маркеры
  `red-<ключ>-<tag>` / `unverified-<ключ>-<tag>` (красный сильнее), иначе последняя строка
  `[gate] зелено | красно | ничего не прогналось | ПРОВЕРИТЬ НЕ УДАЛОСЬ` в транскриптах Сессий
  worktree (`<home>/projects/<папка cwd>/*.jsonl`). `tag` считается от `realpath` worktree, как
  `git rev-parse --show-toplevel` в `gate.sh`.
- Строки гейта берутся только из вывода программ: `tool_result` (Bash и др.) и записей hook-ов
  (`attachment` типа `hook_*`, `system` с `hook` в `subtype`). Промпты, брифы, task-notification
  и текст модели не считаются: в них строка гейта цитируется (брифы содержат «`[gate] зелено (…)`»).
  Строка должна начинаться с `[gate] ` — так `grep` по `gate.sh` (`echo "[gate] зелено …"`) не
  считается вердиктом. Между транскриптами побеждает запись с самым поздним `timestamp`.
  Транскрипты читаются с места прошлого чтения (`readNewLines`), заменённый файл — заново.
- «Ничего не прогналось» — «нет данных» (`none`), даже если раньше было «зелено».
- `src/main/github/prs.ts` — `PrTracker`: `gh pr list --state all --limit 100 --json …` не чаще
  раза в интервал (60 с), ветки Тикетов в работе и ветки worktree, которых нет в списке, —
  `--search head:<ветка> --limit 1`, не чаще раза в 5 минут на ветку и не больше 10 за чтение.
  Ошибка `gh` → `gh: {available:false, error:<первая строка stderr>}`, PR пустые, интервал
  удваивается до 32 минут; первый успех возвращает 60 с. CI: `failing`, если что-то упало, иначе
  `running`, если что-то не закончилось, иначе `passing`; без проверок — `null`. Вердикт —
  последний комментарий, чья первая строка начинается со слова `VERIFIED` или `REJECTED`.
- `gh` — из PATH login shell (ADR-0007, `agentEnv()`); `WORFY_GH` подменяет исполняемый файл
  (tests и e2e). `test/e2e/helpers.ts` по умолчанию ставит `WORFY_GH` на stub
  `test/fixtures/gh/gh`, отвечающий «PR нет», — ни один e2e не ходит в настоящий GitHub.
- IPC (ADR-0006): один канал `checks.get({root, branches})` → снимок `{worktrees[{path, branch,
  gate}], pulls[], gh}`. Ветки Тикетов в работе присылает renderer (`fromBranch`, иначе
  `<эпик>/<NN>`), схема пропускает только ветки вида Тикета без пробелов и ведущего `-`; ветки
  worktree main добавляет сам. Событий нет: renderer спрашивает сам.
- Когда спрашивает renderer (`src/renderer/canvas/badges/use-checks.ts`): при появлении первого
  бейджа Проекта, при смене набора веток в работе, при событии `focus` окна и раз в 10 с, пока
  `document.hasFocus()`. `gh` main запускает не чаще своего интервала, как бы часто ни спрашивали;
  маркеры и транскрипты читаются при каждом вопросе. Так «раз в 60 с, только пока окно активно»
  выполняется: без фокуса renderer не спрашивает, и `gh` не запускается.
- Сопоставление (`src/shared/ipc/checks.ts`): Тикет ← worktree по ветке, иначе по папке
  `.claude/worktrees/<NN>`, если ветка не названа как Тикет; Тикет ← PR по ветке (открытый, потом
  слитый, новее — раньше); Сессия ← самый глубокий worktree, содержащий её `cwd`.
- Бейджи (`ChecksBadges.tsx`): на Тикете — Gate (если у Тикета есть worktree), `PR #N`
  (+ merged/closed), `CI <состояние>`, вердикт; «gh unavailable» — только на Тикетах в работе
  или с worktree (там, где ждут PR), а не на всех. На Сессии — только Gate. Цвета: зелено/passing/
  VERIFIED — ready, красно/failing/REJECTED — blocked, «не удалось проверить»/running — working;
  «нет данных» — нейтральный чип «gate: no data».

**Неочевидное.**
- У Узла Тикета (высота 104, `TicketNode.tsx`) ровно одна строка под бейджи, ~182 px. Поэтому
  чипы компактные (11 px), а PR — текстом-ссылкой, как в макете F. PR + CI + вердикт помещаются
  (e2e проверяет, что все три внутри Узла). Gate + PR + CI + вердикт вместе не помещаются: строка
  обрезается справа, полный список — во всплывающей подсказке строки (`title`). Две строки
  бейджей потребуют более высокого Узла Тикета — это вне следа тикета.
- Транскрипты subagent-ов (`<сессия>/subagents/*.jsonl`) не читаются: они лежат в папке
  родительской Сессии, а не того worktree, где работал subagent. Для Тикетов, которые ведут
  subagent-ы, «зелено» без маркера видно только из транскрипта Сессии, запущенной в самом
  worktree; «красно» и «не удалось проверить» видны всегда по маркерам.
