## Что делаем

- Под полем ввода три выбора (`Pickers.tsx`), у каждой Сессии свои:
  - модель — список из SDK (`supportedModels()`), запасной — модель из `init`;
  - effort — уровни, которые принимает SDK (по ответу 06);
  - режим разрешений — `bypassPermissions` (по умолчанию), `acceptEdits`, `default`, `plan`,
    с понятными подписями.
  Смена применяется к живой Сессии без перезапуска (`setModel`, `setPermissionMode`, effort — как
  выяснил 06) и сохраняется в `data` Узла, чтобы Resume продолжил с теми же настройками.
- Очередь (`src/main/agent/queue.ts`): сообщение, отправленное во время хода, не уходит в SDK, а
  встаёт в очередь Сессии; в поле ввода chip «N queued», каждое можно удалить до отправки. После
  `result` очередь отправляет следующее. «Interrupt» останавливает ход и очередь: очередь
  остаётся видимой и уходит кнопкой «Send queued». Отложенной отправки нет.
- Очередь живёт в main, а не в renderer: переключение Session view и Холста её не теряет.
- Fake-агент (`fake-query.ts` из 07) учится записывать вызовы `setModel`, `setPermissionMode` и
  смены effort, чтобы test-ы видели их.

Падающий первым test. `agent-queue.test.ts`, test «sends three messages written during a turn one

Из копии test убраны проверки, которых старый API не имеет (значение `send()` и событие `queue`).
Команда: `ELECTRON_RUN_AS_NODE=1 electron ./node_modules/vitest/vitest.mjs run <копия test>`,
exit code 1. Упало утверждение о порядке:
`expected [ 'sent first', 'sent one', …(6) ] to deeply equal [ 'sent first', 'result', …(6) ]` —
без очереди все три сообщения уходили в Claude Code сразу, до первого `result`.

Решения, которые не очевидны из кода:

- **Пересечение с тикетом 14 по `src/shared/agent/events.ts`.** Файл есть в следе тикета 14 (та же
  волна 7). Тикет 14 меняет doc-comment у события `unknown` в конце union, поэтому новые события
  `prompt`, `queue`, `settings` стоят в начале union: тогда `git merge-tree origin/worfy-mvp/14
  origin/worfy-mvp/19` проходит без конфликта. Ветки всё равно мержить по одной: вторую
  перебазировать на `main` с первой и прогнать `pnpm lint && pnpm typecheck && pnpm test` заново.
- **Смена модели сбрасывает effort, которого новая модель не знает.** Если выбранного уровня нет в
  `supportedEffortLevels` новой модели, пикер шлёт `{ model, effort: null }` одним
  `agent.configure`: Claude Code получает `setModel` и `applyFlagSettings({ effortLevel: null })`,
  а не уровень, который модель не принимает. Уровень, который новая модель знает, остаётся.

- **След шире, чем в тикете.** Каналы IPC (`src/shared/ipc/agent.ts`, `src/main/ipc/agent.ts`),
  события (`src/shared/agent/events.ts`), опции SDK (`options.ts`, `app-registry.ts`), хранение
  настроек Оркестратора (`orchestrator.ts`, `src/shared/ipc/orchestrator.ts`), store и заголовок
  Session view — без них пункты «Готово, когда» не выполнить. `Pickers.tsx` лежит в `composer/`, а
  не в `src/renderer/session/`: так его подхватывает точка расширения тикета 33 без правки
  `MessageInput.tsx`.
- **Сообщение пользователя в транскрипт кладёт main**, событием `prompt` в момент, когда отдаёт его
  Claude Code. Renderer больше не пишет prompt сам (`recordPrompt`/`retractPrompt` удалены): иначе
  сообщение из очереди появлялось бы до отправки. Это же убирает гонку из тикета 33 (`retractPrompt`
  искал prompt под временным id после `renamed`).
- **Interrupt держит только то, что уже в очереди.** Пустая очередь не держится; опустевшая —
  перестаёт держаться. Сообщение, отправленное в простаивающую Сессию, пока очередь держится,
  уходит сразу, а очередь ждёт «Send queued». Падение Claude Code держит очередь так же, как
  Interrupt: новый процесс не запускается сам ради очереди.
- **Effort.** Claude Code не сообщает применённый уровень (тикет 06, вопрос 6): в заголовке
  показан уровень, который попросил worfy (`settings.effort`), «—» — уровень модели по умолчанию.
  Подсказка у поля и у пикера говорит об этом. Что `applyFlagSettings({ effortLevel })` реально
  применился на живом Claude Code — не проверено (только fake-агент).
- **Модель `default`** из `supportedModels()` — это `model: null` (`setModel(undefined)`).
  Модель без уровней effort (haiku) выключает пикер effort; выбранный до неё уровень при переходе на
  неё сбрасывается в `null` (пункт выше).
- **Fixture `orchestrator.jsonl`**: ход 1 теперь держится до `interrupt`, а не до следующего
  сообщения — следующее сообщение во время хода уходит в очередь и до fake-агента не доходит.
- **Режим `default` («Ask before tools»)** без `canUseTool` на SDK значит отказ на каждый запрос
  разрешения; запрос разрешений в окне — тикет 21.

не проверено: смена модели, effort и режима на настоящем Claude Code (e2e и тесты идут на
fake-агенте, `WORFY_AGENT=fake`); вид окна проверен только снимками Playwright.

### Черновик ADR: Выбор модели, effort и режима разрешений Сессии хранится в data её Узла

Дата: 2026-10-05. Статус: черновик (номер выдаст оркестратор). Заменяет ADR-0010
(`docs/adr/0010-orchestrator-state-session-id-and-cost-only.md`) в части состава `data` Узла
Оркестратора; остальное в ADR-0010 (модель и блок состояния — из транскрипта) остаётся в силе.

Этот ADR нужно закоммитить до мержа PR #21 или вместе с ним: код ветки пишет в `data` ключ,
которого ADR-0010 не разрешает.

ADR-0010 разрешает в `data` Узла Оркестратора только `sessionId` и `costUsd`. Тикет 19 требует,
чтобы выбранные пользователем модель, effort и режим разрешений пережили перезапуск и применялись
при `resume`.

**Решение.** В `data` Узла добавляется ключ `settings: { model, effort, permissionMode }` — выбор
пользователя в worfy, а не факт, записанный workflow: effort Claude Code не пишет ни в `init`, ни
в транскрипт (тикет 06), режим и модель в транскрипте — то, с чем шёл последний ход, а не то, что
выбрано сейчас. main пишет ключ только при изменении (по событию `settings`), читает его
поле за полем (`readSettings`: повреждённое поле — значение по умолчанию) и передаёт в `query()`
(`model`, `effort`, `permissionMode`) при каждом старте и `resume`. Узлы Сессий-исполнителей
(тикет 18) могут хранить тот же объект.

**Цена.** Третий ключ в `data`, который может перезаписать любой писатель `patchData` (MCP,
тикет 24): защита `data` Узла Оркестратора, о которой говорит ADR-0010, должна закрывать
`sessionId`, `costUsd` и `settings`. Если пользователь сменил модель в терминале (`/model`), worfy при следующем `resume`
вернёт свою.

#### Considered Options

- Хранить в `data` Узла (выбрано).
- Не хранить, брать модель из транскрипта: effort и режим потерялись бы, `resume` шёл бы с
  `bypassPermissions` и моделью по умолчанию.
- Писать в настройки Claude Code (`updateSettings`): меняет файлы пользователя, запрещено ADR-0005.
