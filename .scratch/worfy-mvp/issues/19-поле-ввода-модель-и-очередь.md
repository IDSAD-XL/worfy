## Что делаем

- Под полем ввода три выбора (`Pickers.tsx`), у каждой Сессии свои:
  - модель — список из SDK (`supportedModels()`), запасной — модель из `init`;
  - effort — уровни, которые принимает SDK (по ответу 06);
  - режим разрешений — `bypassPermissions` (по умолчанию), `acceptEdits`, `default`, `plan`,
    с понятными подписями.
  Смена применяется к живой Сессии без перезапуска (`setModel`, `setPermissionMode`, effort — как
  выяснил 06) и сохраняется в `data` Узла, чтобы Resume продолжил с теми же настройками.
- Очередь (`src/main/agent/queue.ts`): сообщение, отправленное во время хода, не уходит в SDK, а
  встаёт в очередь Сессии; в поле ввода chip «N queued», каждое можно удалить до отправки. После
  `result` очередь отправляет следующее. «Interrupt» останавливает ход и очередь: очередь
  остаётся видимой и уходит кнопкой «Send queued». Отложенной отправки нет.
- Очередь живёт в main, а не в renderer: переключение Session view и Холста её не теряет.
- Fake-агент (`fake-query.ts` из 07) учится записывать вызовы `setModel`, `setPermissionMode` и
  смены effort, чтобы test-ы видели их.

### Решение владельца: настройки Сессии — отдельный файл, Раскладка по ADR-0010

Второе ревью нашло, что Узел Оркестратора писал в `data` третий ключ `settings` вопреки ADR-0010.
Черновик ADR, который заменял ADR-0010 в этой части, снят. Решение владельца 2026-10-05,
вариант (б): `data` Узла Оркестратора остаётся по ADR-0010 — только `sessionId` и `costUsd`;
модель, effort и режим разрешений хранятся отдельно, в данных worfy (`WORFY_DATA_DIR`). Новый
ADR не нужен: ADR-0010 не меняется, ADR-0005 (своё состояние worfy — только в `WORFY_DATA_DIR`)
соблюдён.

Как сделано (круг исправления после второго ревью):

- Файл `<папка данных Проекта>/session-settings.json`, вид `{ "nodes": { "<id Узла>": { model,
  effort, permissionMode } } }`, модуль `src/main/agent/session-settings.ts` поверх
  `src/main/storage/json-file.ts`: запись атомарная (временный файл и rename), неразборчивый файл
  откладывается в `session-settings.json.unreadable-<время>`, запуск идёт с настройками по
  умолчанию. Повреждённое поле настроек одного Узла — значение по умолчанию, остальные поля
  сохраняются (`readSettings`, как было в `data`).
- **Ключ — id Узла, а не SDK session id.** Выбор делает пользователь на Узле, который он видит.
  SDK session id меняется, когда сохранённую сессию продолжить нельзя (транскрипт удалён) и
  Оркестратор начинает новую под тем же Узлом: с ключом по session id выбор терялся бы. До первого
  `system/init` session id ещё нет, а выбор уже можно сделать. id Узла известен с самого начала и
  годится для Узлов Сессий-исполнителей (тикет 18) в том же файле.
- Файл лежит в папке данных Проекта (рядом с `layout.json` и `settings.json`), а не общим на всё
  приложение: удаление Проекта из списка не оставляет чужих записей в общем файле. Путь берётся
  через `projectStore().get()`, как у Раскладки: для Проекта, которого нет в списке, запись
  отказывается и не создаёт его папку заново.
- Ни чтение, ни запись файла настроек не останавливают Оркестратор: ошибка чтения (например,
  EISDIR) — старт с настройками по умолчанию и warning; ошибка записи — живая Сессия продолжает с
  выбранными настройками, после перезапуска приложения они будут по умолчанию.
- Ключ `settings` убран из `orchestratorDataSchema` (`src/shared/ipc/orchestrator.ts`):
  `readOrchestratorData` его не читает. `settings`, оставшийся в `layout.json` от ранней сборки
  этой ветки, игнорируется и не удаляется (только файлы разработчика; в `main` ветка не попадала).

Tests (`test/contract/orchestrator.test.ts`): схема `data` Узла объявляет только `sessionId` и
`costUsd`; после `configure` `data` Узла пустая, а файл настроек содержит выбор под id Узла;
выбор переживает перезапуск (новые stores над той же папкой) и применяется к `resume`; выбор
сохраняется, когда сохранённая сессия не продолжается; повреждённые поля; `settings` в `data` от
старой сборки игнорируется; неразборчивый файл и файл-не-по-схеме откладываются и не роняют
старт; файл, который нельзя ни прочесть, ни записать, не роняет Сессию; `SessionSettingsStore`
хранит Узлы раздельно и отказывает Проекту вне списка; проводка main (`app-orchestrators.ts`)
пишет файл в папку данных Проекта, а в репозиторий Проекта и Claude home — ничего. Сначала tests
упали на коде до правки (9 из 39, exit code 1), затем 10 мутантов (запись `settings` в `data`,
без записи, без чтения, без try/catch при чтении и записи, `settings` в схеме, запись без чужих
Узлов, ключ не по Узлу, строгая схема чтения, путь в репозиторий Проекта) — каждый краснит хотя
бы один test.
