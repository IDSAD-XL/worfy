## Что делаем

worfy не разбирает формат Тикетов сам. Единственный читатель формата — скрипт
`~/.claude/bin/epic-status`. Его `--json` отдаёт `{ref, epics[], tickets[]}`: у Эпика — `epic`,
`hasSpec`, `hasMap`; у Тикета — `epic`, `num`, `slug`, `title`, `statusRaw`, `state`
(`open | work | blocked | done | none`), `blockedRaw`, `blockedNums`, `blockedParsed`.
Фильтра по Эпику у `--json` нет: аргумент Эпика он игнорирует и всегда отдаёт все Эпики
`.scratch`. Зато есть `--ref <ветка>` — тот же снимок, прочитанный из указанной ветки.
Чего в нём нет — списка файлов из раздела «Где в коде», а без него не посчитать Волну. Этот
раздел worfy читает сам, только его.

- `src/main/workflow/reader.ts`: запускает `<WORFY_CLAUDE_HOME>/bin/epic-status --json` в корне
  Проекта, проверяет ответ zod-схемой, добавляет к Тикету пути из «Где в коде» (содержимое
  обратных кавычек в пунктах списка) и заголовок Эпика (H1 из `spec.md`, если он есть). Нет
  скрипта или он упал — модель пустая и с причиной, которую видно в UI.
- `src/main/workflow/watch.ts`: следит за `.scratch/**` (chokidar), debounce 300 мс, после
  изменения один раз запускает полный `epic-status --json`, сравнивает его с прошлым снимком в
  main и рассылает по каналу `workflow.changed` только изменившиеся Эпики и Тикеты. Прогоны не
  идут параллельно: правка во время прогона даёт ровно один следующий прогон. Замер 2026-10-05:
  полный `--json` на Auction (42 Эпика, 682 Тикета) занимает 0.6–0.75 с, поэтому цель —
  «изменение на экране ≤ 1.5 с после сохранения файла», а не «перечитать один Тикет».
- **Ветки worktree.** Тикет, взятый в worktree, меняет `Status:` в своей ветке, и в `main` это
  видно только после merge. Reader берёт `git worktree list --porcelain`, оставляет ветки,
  которые `ticket-ref.ts` разбирает в Тикет, и для каждой запускает
  `epic-status --json --ref <ветка>` (не больше 4 одновременно; замер — 0.85 с на прогон). Из
  снимка ветки берётся только её собственный Тикет: его `state` и `statusRaw` перекрывают снимок
  `main`, Тикет получает пометку «из ветки <ветка>». Слежение — за ссылками этих веток
  (`.git/refs/heads/…`, `packed-refs`) и за списком worktree; перезапускается только ветка, чья
  ссылка сдвинулась. `--ref` видит закоммиченное состояние: незакоммиченная правка в worktree не
  видна до коммита.
- `src/shared/workflow/waves.ts` — чистые функции:
  - уровень Тикета: 0 без блокеров, иначе 1 + наибольший уровень блокеров. Тикет с
    `blockedParsed=false` или в цикле — отдельный признак, а не произвольный уровень;
  - готовая Волна: открытые Тикеты, у которых все блокеры `done`, без общих файлов, в порядке
    номеров. Файлы Тикетов в работе (`claimed`, в том числе по снимку ветки worktree) заняты с
    самого начала; тикет, у которого файл совпал с занятым или с уже взятым в Волну, ждёт
    следующей. Тикет без «Где в коде»
    попадает в Волну с пометкой «файлы не указаны»;
  - номер Волны для всех Тикетов — тот же расчёт, повторённый до конца, как таблица «Волны» в
    `spec.md`.
- `src/shared/workflow/ticket-ref.ts`: разбор ветки `<эпик>/<NN>-<slug>` или `<эпик>/<NN>` (так
  названы ветки Auction, например `ui-triage-4/01`) и папки worktree
  `.claude/worktrees/<NN>-<slug>` в ссылку на Тикет. Им пользуются тикеты 16 и 17.
- worfy ничего не пишет в `.scratch`.

## Готово, когда

- [ ] Номера Волн совпадают с таблицей «Волны» в `spec.md` на копии эпика `test/fixtures/worfy-mvp-epic/`: `spec.md` и `issues/` (33 Тикета, у всех `Status: open`) плюс снятый с этой копии вывод `epic-status --json`. Живой `.scratch/worfy-mvp/` для сверки не годится: статусы там меняются по ходу работы, а таблица посчитана для всех открытых.
- [ ] Открытый Тикет, у которого файл совпадает с файлом Тикета в работе, в готовую Волну не попадает (test).
- [ ] Тикет, взятый в ветке worktree (`ticket claim` закоммичен в ветке, в `main` ещё `open`), показан в работе с пометкой ветки; после merge пометка уходит.
- [ ] Блокер из другого состояния, цикл и неразобранный `Blocked by` дают явные признаки, а не падение.
- [ ] Сгенерированный Проект размера Auction (42 Эпика, 682 Тикета) со stub-скриптом, который сразу отдаёт готовый JSON: разбор ответа, чтение «Где в коде» и diff с прошлым снимком ≤ 300 мс — это доля самого worfy.
- [ ] Настоящий `/Users/alexey/Work/Auction`: первое полное чтение (`main` плюс ветки worktree Тикетов) ≤ 3 с; `workflow.changed` после правки одного Тикета приходит ≤ 1.5 с после сохранения файла. Числа в «Итог»; вывод `git status --porcelain` там после работы тот же, что до неё.
- [ ] Нет `epic-status` → модель пустая с причиной «epic-status не найден», приложение работает.
