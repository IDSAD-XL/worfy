Type: task

Blocked by: 05, 07
Source: [CONTEXT.md](../../../CONTEXT.md), термин «Оркестратор»; [BRIEF.md](../../../docs/design/BRIEF.md), Screen 1 пункт 2; макеты `docs/design/F-session-*.dc.html`

## Что делаем

У каждого Проекта ровно один Оркестратор — главная Сессия, из которой расходится работа. Его
Узел создаётся при первом открытии Проекта и помечен `locked` (поле Раскладки из тикета 05: Узел
можно сдвинуть и изменить размер, удалить нельзя). Его `sessionId` хранится в поле `data` Узла в
Раскладке, и после перезапуска Сессия продолжается через `resume`. Session view с полным
транскриптом и полем ввода — тикет 33.

- `src/main/agent/orchestrator.ts`: при открытии Проекта находит Узел Оркестратора в Раскладке или
  создаёт его, поднимает Сессию (движок из 07) с сохранённым `sessionId` или новую.
- Узел в свёрнутом виде: заголовок «Orchestrator», статус (`idle`, `busy`, `error`) chip-ом,
  модель, стоимость Сессии, и последний блок состояния — четыре строки «— Этап / — Сейчас /
  — Дальше / — Жду» из последнего ответа ассистента, дословно, моноширинным шрифтом. Если блока
  ещё не было — строка «No status block yet».
- `src/shared/agent/status-block.ts` — чистая функция: находит последний блок из четырёх строк в
  тексте ассистента; терпит лишние пробелы, длинное тире или дефис, блок в конце или в середине
  текста; русский текст внутри строк.

## Готово, когда

- [x] При первом открытии Проекта появляется Узел Оркестратора с `locked`; удалить его нельзя, сдвинуть можно.
- [x] На fake-агенте: `agent.send` (test зовёт канал напрямую, поле ввода — тикет 33) → статус `busy` → `idle`; стоимость из `result` видна на Узле.
- [x] Блок состояния из последнего ответа показан на Узле дословно; новый ответ с блоком заменяет старый, ответ без блока — не трогает.
- [x] После перезапуска Оркестратор продолжает ту же Сессию (`resume` с сохранённым `sessionId`).

## Итог

Сделано в ветке `worfy-mvp/08`. Проверено тестами: `test/unit/status-block.test.ts`,
`test/unit/orchestrator-transcript.test.ts`, `test/unit/orchestrator-node.test.tsx`,
`test/contract/orchestrator.test.ts`, `test/e2e/orchestrator.spec.ts` (fake-сценарий
`test/fixtures/agent-scripts/orchestrator.jsonl`).

Первый test. Тикет велел начать с `status-block.test.ts` на блок с русским текстом. В истории ветки
это не видно: работа ушла одним коммитом. Поэтому падение воспроизведено при доработке по ревью,
на той же версии test-а:

- без `src/shared/agent/status-block.ts`: `pnpm test test/unit/status-block.test.ts` → exit code 1,
  «Error: Cannot find module '../../src/shared/agent/status-block'», «Tests no tests»;
- с заглушкой `findStatusBlock = () => null`: та же команда → exit code 1, 7 из 7 test-ов красные;
  первый — «finds a block of Russian text at the end of an answer and returns it verbatim»,
  «AssertionError: expected null to strictly equal { …(5) }».

Как устроено:

- `src/main/agent/orchestrator.ts` — класс `Orchestrators`. `open(projectId)` находит Узел вида
  `orchestrator` в Раскладке или создаёт его (`locked: true`, 360×200, в левом верхнем углу или под
  всеми Узлами, если угол занят). Затем поднимает Сессию в общем реестре Сессий: с `resume` из
  `data.sessionId` или новую. Повторный и одновременный `open` при живой (или стартующей) Сессии
  ничего не меняет.
- В `data` Узла в `layout.json` лежат только `sessionId` (что продолжать через `resume`) и `costUsd`
  (стоимость, сложенная по процессам Claude Code). Других записей этих фактов нет: стоимости в
  долларах в транскрипте нет. Схема — `orchestratorDataSchema` в `src/shared/ipc/orchestrator.ts`.
- Остальное, что показывает Узел, worfy не хранит (ADR 0002, ADR 0005). Это вид Оркестратора
  (`OrchestratorView`) в памяти main. Модель и последний блок состояния при открытии читаются из
  транскрипта сохранённой Сессии (`src/main/agent/orchestrator-transcript.ts`: файл читается с
  конца, кусками, только до нужного места). Дальше их обновляют события живой Сессии. Состояние
  (`idle`, `busy`, `error`) — живой Сессии.
- Renderer получает вид так: `orchestrator.view` по `nodeId` — снимок при монтировании Узла,
  `orchestrator.changed` — каждое изменение, во все окна. Подписка идёт до запроса, а из двух
  видов берётся тот, у кого больше `version`, поэтому ответ, пришедший после события, не
  откатывает Узел (`src/renderer/canvas/nodes/orchestrator-view.ts`).
- Блок состояния берётся только из текста самого Оркестратора. В живых событиях это `text` с
  `parentToolUseId: null` и не `synthetic`. В транскрипте — записи `assistant` без `isSidechain` и
  с моделью не `<synthetic>`. Блок subagent-а и текст, который вписал сам Claude Code, Узел не
  меняют.

Сохранённую Сессию нельзя продолжить. Claude Code удаляет транскрипты старше `cleanupPeriodDays`
(30 дней по умолчанию), пользователь может удалить их сам. На `resume` такой Сессии Claude Code
отвечает «No conversation found with session ID», и Сессия уходила в `error` на каждом сообщении.
Теперь:

- нет транскрипта при открытии — Оркестратор сразу начинает новую Сессию, в `data` пишет
  `sessionId: null` и `costUsd: 0`;
- транскрипт есть, но Claude Code всё равно отказал этим текстом до `system/init` — та же замена:
  отказавшая Сессия закрывается, новая стартует без `resume`;
- транскрипт не читается (ошибка чтения) или старт упал по другой причине — `sessionId` остаётся,
  Узел показывает `error`: потерять Сессию из-за временной ошибки хуже, чем показать ошибку.

Решения вне следа «Где в коде» (без них пункты «Готово, когда» не выполнялись):

- IPC-домен `orchestrator` — `src/shared/ipc/orchestrator.ts` и `src/main/ipc/orchestrator.ts`
  (подхватываются сами через `import.meta.glob`, ADR-0006). `orchestrator.open` отвечает видом
  Оркестратора, в нём `nodeId` и id живой Сессии — через него test (и потом тикеты 23 и 33)
  находит Сессию для `agent.send`. `orchestrator.view` и `orchestrator.changed` — для Узла.
- `src/main/agent/app-orchestrators.ts` — Оркестраторы приложения и когда main открывает их сам:
  активного Проекта — на событии `browser-window-created`, Проекта, ставшего активным, — по
  `projectStore().onChange`; Проект, удалённый из списка, останавливает свой Оркестратор.
  Подписку делает `startOrchestrators()` из `src/main/index.ts`, а не загрузка модуля
  обработчиков.
- `src/main/agent/app-registry.ts` — общий реестр Сессий приложения и фабрика запуска Claude Code
  (или fake-агента) перенесены сюда из `src/main/ipc/agent.ts`. Оркестратор живёт в том же
  реестре, иначе `agent.send` его не находит. Фабрика переехала вместе с подключением
  MCP-сервера Холста из тикета 24; `test/unit/agent-query-factory.test.ts` и
  `test/contract/canvas-tools.test.ts` импортируют её оттуда.
- `src/renderer/canvas/nodes/orchestrator-view.ts` — хранилище видов в renderer. Вид и размер
  Узла в `OrchestratorNode.tsx` записаны литералами (правило fast refresh иначе не пропускает
  экспорт), но через `satisfies typeof ORCHESTRATOR_*`: если константы в shared поменяются,
  typecheck упадёт.
- `test/e2e/canvas-layout.spec.ts`: на каждом Холсте теперь есть Узел Оркестратора, поэтому тест
  считает только заметки (`notesOf`), а двойной щелчок, создающий заметку, перенесён с (300, 200)
  на (300, 320) — прежняя точка попадает в Узел Оркестратора.

Неочевидное:

- **Стоимость.** Claude Code отдаёт `total_cost_usd` нарастающим итогом за процесс (в
  `test/fixtures/sdk-messages/controls.jsonl` значения растут от хода к ходу внутри одной сессии).
  Новый процесс — после падения или перезапуска приложения — считает с нуля. `CostCounter`
  складывает процессы: база — сохранённое `costUsd`, к ней последний `total_cost_usd` текущего
  процесса; состояние `error` или уменьшившееся значение означают новый процесс.
- **Оркестратор принадлежит приложению, а не окну.** Его события идут на `agent.event` во все окна;
  закрытие окна его не останавливает (обычные Сессии из `agent.start` закрываются вместе с окном).
  Останавливается при выходе из приложения вместе с остальными Сессиями. Оркестраторы ранее
  открытых Проектов продолжают работать после переключения на другой Проект.
- **Ход 1 fake-сценария держит `busy`** до следующего `agent.send` (строка `wait_message` между
  ответом и `result`): иначе ход на fake-агенте мгновенный, и `busy` на Узле не увидеть надёжно.
- **Где worfy ищет транскрипт.** Каталог Claude home — `claudeHome()` (`~/.claude` или
  `WORFY_CLAUDE_HOME`), как у тикета 13. Если Claude Code пользователя пишет в другой каталог
  (`CLAUDE_CONFIG_DIR` в login shell), транскрипт не найдётся, и Оркестратор при каждом запуске
  будет начинать новую Сессию. Это общее допущение чтения `~/.claude` в worfy, не только этого
  тикета.
- e2e между двумя запусками сам пишет транскрипт Сессии в `WORFY_CLAUDE_HOME`: fake-агент
  транскриптов не пишет, а без транскрипта Оркестратор не продолжает Сессию. Тот же test
  проверяет, что каталог Проекта пуст, а Claude home не изменился после обоих запусков (ADR 0005).
