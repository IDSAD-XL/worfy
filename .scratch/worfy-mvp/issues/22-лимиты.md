## Что делаем

**Первый шаг — проверка.** Есть ли в JSON, который Claude Code передаёт команде status line,
поле `rate_limits`, и что в нём. Проверить на текущей версии Claude Code временной командой
status line, которая сохраняет свой stdin в файл; итог (есть / нет, образец JSON без
персональных данных, версия) — в «Итог» до остальной работы. От ответа зависит второй источник
ниже.

**Основной источник** — сообщение SDK `rate_limit_event` (`SDKRateLimitInfo`: `status`,
`rateLimitType` — `five_hour`, `seven_day` и другие, `utilization?`, `resetsAt?`; два последних
могут отсутствовать).

- `src/shared/agent/limits.ts` — чистая функция: из последних событий всех Сессий собирает
  состояние по каждому окну: доля, время сброса, статус, время получения. Новое событие
  перекрывает старое того же окна.
- `src/main/agent/limits.ts` слушает события Сессий, хранит последнее состояние в
  `<WORFY_DATA_DIR>/limits.json` (Лимиты общие для всех Проектов) и рассылает изменения.
- Toolbar (`LimitsMeter.tsx`): две полосы «5-hour 62% · resets 14:20» и «7-day 38% · resets Thu
  09:00». Нет `utilization` — только статус словами. Данные старше часа помечены «as of 13:05».
  Нет данных вовсе — «Limits: no data yet». Цвет полосы — токены: обычный, working ≥ 60%,
  blocked ≥ 85%, всегда с числом.
- Правая панель Session view: `rail/LimitsRail.tsx` — те же две полосы мельче.

**Второй источник — только если проверка показала `rate_limits`.** `scripts/statusline-bridge.sh`
— скрипт, который пользователь сам вставляет в свою команду status line: он пишет `rate_limits`
в `<WORFY_DATA_DIR>/statusline-limits.json`, worfy следит за файлом. worfy не правит
`~/.claude/settings.json`; как подключить — в «Итог». Приватные OAuth endpoint-ы не
используются.

### Как устроено

- `src/shared/agent/limits.ts` — чистые функции. `limitUpdatesFromSdk` читает `rate_limit_event`
  (окна из `unifiedWindows`, запасной путь — `utilization`/`resetsAt` верхнего уровня);
  `status` относится только к окну `rateLimitType`. `limitUpdatesFromStatusline` читает объект
  `rate_limits` (проценты → доля). `mergeLimits`: обновление окна заменяет его целиком, если не
  старше известного (`receivedAt`). `limitBars` — две полосы: доля или статус словами
  (`allowed`, `near limit`, `limit reached`), `resets 14:20` / `resets Thu 09:00`, `as of 13:05`
  старше часа, уровень `working` ≥ 60 %, `blocked` ≥ 85 % (или по статусу
  `allowed_warning`/`rejected`).
- `src/main/agent/limits.ts` — `LimitsTracker`: состояние в `<WORFY_DATA_DIR>/limits.json`
  (через `storage/json-file.ts`: схема, атомарная запись, нечитаемый файл откладывается),
  подписчики, `observe(factory)` — обёртка фабрики запросов (через `observeMessages` из
  `mcp/canvas-server.ts`; ошибка записи ловится в самом `LimitsTracker` и пишется в лог с меткой
  `[limits]`, а не `[canvas]`), слежение за `statusline-limits.json` через `fs.watch` каталога данных
  (debounce 50 мс). Время данных из файла моста — его mtime: файл, записанный до последнего
  события SDK, ничего не меняет.
- IPC по ADR-0006: `src/shared/ipc/limits.ts` (`limits.open` → текущее состояние и подписка окна,
  событие `limits.changed`), `src/main/ipc/limits.ts`.
- Renderer: `src/renderer/shell/toolbar/LimitsMeter.tsx` (order 100, перед версией),
  `src/renderer/session/rail/LimitsRail.tsx` (order 90), общий hook
  `src/renderer/limits/useLimits.ts` (ESLint `react-refresh/only-export-components` не даёт
  экспортировать hook из файла компонента) и общий компонент полосы
  `src/renderer/limits/LimitBar.tsx` (`LimitBarView`): оба файла расширений импортируют его оттуда,
  а не друг из друга, — после ревью, круг 1. Цвета — токены `--text-secondary`, `--working-dot`,
  `--blocked-ring`; число показывается всегда.

### Неочевидные решения

- **Источник — сырые сообщения SDK, а не событие `rate_limit` из `src/shared/agent/events.ts`.**
  В этом событии нет времени сброса 7-дневного окна (`unifiedWindows.seven_day.resetsAt`), а
  `events.ts` — след тикета 14 той же волны 7. Поэтому `LimitsTracker.observe` оборачивает фабрику
  запросов, и разбор `rate_limit_event` для Лимитов живёт в `src/shared/agent/limits.ts`.
- **Точка подключения — одна строка в `src/main/agent/app-registry.ts`** (вне «Где в коде»):
  `new SessionRegistry(appLimits().observe(queryFactoryFromEnv()))`. Так видны Сессии и окон, и
  Оркестраторов, и fake agent. `session.ts` (след тикета 19) не тронут.
- Новые файлы вне «Где в коде»: `src/shared/ipc/limits.ts`, `src/main/ipc/limits.ts` (по ADR-0006,
  бриф это разрешает), `src/renderer/limits/useLimits.ts`, `src/renderer/limits/LimitBar.tsx`, fixture
  `test/fixtures/agent-scripts/limits.jsonl`, tests `test/contract/limits.test.ts`,
  `test/contract/statusline-bridge.test.ts`, `test/unit/limits-meter.test.tsx`.
- Мост пишет только при существующем каталоге данных (worfy уже запускался) и при наличии `jq`
  (`/usr/bin/jq` есть в macOS начиная с 15); иначе молча пропускает запись. Status line
  пользователя не ломается никогда: stdin уходит обёрнутой команде, её вывод и код выхода — как
  есть.
- Сломанный `statusline-limits.json` не откладывается в сторону (это файл пользователя, его
  перепишет следующий вызов status line), а просто пропускается.

### Как подключить мост (делает владелец, не worfy и не агент)

В `~/.claude/settings.json` поставить мост перед своей командой status line; своя команда
передаётся одним аргументом в кавычках и запускается через `sh -c` с тем же stdin:

```json
"statusLine": {
  "type": "command",
  "command": "/Users/alexey/Stuff/CanvasForAI/scripts/statusline-bridge.sh 'bash ~/.claude/statusline.sh'"
}
```

Без своей status line — без аргумента (мост ничего не печатает). Каталог данных — `WORFY_DATA_DIR`,
по умолчанию `~/Library/Application Support/worfy`. Файл появится после первого ответа модели в
любой сессии Claude Code; worfy подхватит его без перезапуска.
