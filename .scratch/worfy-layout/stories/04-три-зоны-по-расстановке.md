# Code story — worfy-layout 04: Три зоны по расстановке

Kind: pr · Epic: worfy-layout · Ticket: 04 · PR: - · Language: ru

## 1. Что было не так

Шесть View button-ов стояли одной группой View switch в header, в порядке реестра (`views.tsx`). Поле `viewButtons` в
app settings (Ticket 02) и footer (Ticket 03) уже были, но расстановку никто не читал: footer слева был пуст, на rail
кнопок видов не было. По решению владельца Q1 кнопки по умолчанию стоят в трёх зонах: header — Canvas и Session, rail —
Pull requests и Acceptance под чертой, footer — Pipeline и Runs. Бейджи были только у Acceptance.

- Требование: [Что строить](../issues/04-три-зоны-по-расстановке.md#что-строить)

## 2. Одна зона — одна группа kit ToggleGroup

Code: `src/renderer/shell/ViewZone.tsx:44-84` · key lines: 48, 50, 51, 60, 71, 81

```tsx
export function ViewZone({ zone, views, withRail = false, sectionNames }: ViewZoneProps) {
  const focusMode = useFocusState((state) => state.active)
  const { layout, view, project, onViewChange } = views
  const own = entriesOf(layout[zone])
  const guests = zone === 'header' && withRail ? entriesOf(layout.rail) : []
  const placed = [...own, ...guests]
  if (placed.length === 0) return null
  const pressed = placed.some((entry) => entry.id === view) ? view : null

  const button = (entryZone: Zone) => (entry: ViewButtonEntry) => (
    <ViewButton
      key={entry.id}
      entry={entry}
      look={zone}
      zone={entryZone}
      inactive={entry.button.needsProject !== undefined && project === undefined}
      badged={zone !== 'rail' || sectionNames?.has(entry.button.label) !== true}
    />
  )
  return (
    <ToggleGroup
      aria-label={GROUP_NAMES[zone]}
      className={zone === 'header' ? 'w-segmented w-view-zone w-view-zone--header' : `w-view-zone w-view-zone--${zone}`}
      orientation={zone === 'rail' ? 'vertical' : 'horizontal'}
      data-zone={zone}
      // The header's labels give way at 1400 px from four buttons on (shell.css).
      data-count={placed.length}
      inert={zone !== 'header' && focusMode}
      value={pressed}
      // A press opens the view as its entry says (views.tsx): Runs at the newest Run, the others switch the main area. A
      // press on the pressed button opens its view again, as the View switch did.
      onValueChange={(next) => {
        const entry = viewButtonOf(next ?? view)
        if (entry !== undefined) void openView(entry, project, onViewChange)
      }}
    >
      {own.map(button(zone))}
      {own.length > 0 && guests.length > 0 ? <span className="w-view-zone__line" aria-hidden="true" /> : null}
      {guests.map(button('rail'))}
    </ToggleGroup>
  )
```

- Что делает: рисует кнопки, которые расстановка кладёт в зону, в её порядке. Нажата кнопка вида на экране, в какой бы
  зоне она ни стояла; у `story` и `changes` кнопки нет, и группа ничего не нажимает. Пустая зона ничего не рисует. В
  header при спрятанном sidebar после черты идут кнопки rail. Блок rail и footer получают `inert`, пока идёт focus mode.
- Почему здесь: Ticket называет новый `ViewZone.tsx` в «Где в коде»; решения A (кнопки rail в header) и про `inert` в
  focus mode записаны в «Решениях» Ticket-а.
- Без него: три зоны пришлось бы рисовать трижды, и активная кнопка, порядок и пустая зона расходились бы между ними.
- Требование: [Решения](../issues/04-три-зоны-по-расстановке.md#решения)
- Риски и пробелы test-ов: `orientation` пришлось добавить в kit `ToggleGroup.tsx` (файла нет в «Где в коде»): без него
  ↑ и ↓ на rail не ходили бы по блоку. Стрелки проверяет только Base UI; отдельного test-а на ↑ ↓ в блоке нет.

## 3. Бейдж из источника, который читает сам вид

Code: `src/renderer/shell/views.tsx:81-93` · key lines: 83, 84, 90, 91

```tsx
/** Pull requests: the pull requests of the open Project that need you — the groups the section counts (PR_NEED_YOU). */
function useNeedYouBadge(): RailBadge | undefined {
  const { snapshot } = usePrInbox(activeProject(useProjects())?.id)
  const needYou = groupCounts(snapshot).reduce((sum, { group, count }) => sum + (PR_NEED_YOU.has(group) ? count : 0), 0)
  return needYou > 0 ? { tone: 'blocked', count: needYou, label: needYou === 1 ? '1 pull request needs you' : `${needYou} pull requests need you` } : undefined
}

/** Pipeline: a dot while a Ticket of the open Project is blocked or waits for a person — the section's rule. */
function useWaitingBadge(): RailBadge | undefined {
  const { snapshot } = usePipeline(activeProject(useProjects())?.path)
  const waits = snapshot?.tickets.filter((ticket) => inWork(ticket) && waitsForPerson(ticket)).length ?? 0
  return waits > 0 ? { tone: 'blocked', label: waits === 1 ? '1 Ticket waits' : `${waits} Tickets wait` } : undefined
}
```

- Что делает: Pull requests считает pull request-ы открытого Project-а в группах `PR_NEED_YOU`, Pipeline ставит точку,
  пока Ticket открытого Project-а blocked или ждёт человека — те же правила, что у секций sidebar. Данные — из
  `usePrInbox` и `usePipeline`, которые уже читают смонтированные виды.
- Почему здесь: Ticket в «Решениях»: «бейдж считает то, что показывает сам вид»; `useRailBadge` секций не годится,
  потому что секции размонтированы, пока sidebar спрятан.
- Без него: при спрятанном sidebar кнопки Pull requests и Pipeline не показывали бы ничего.
- Требование: [Решения](../issues/04-три-зоны-по-расстановке.md#решения)
- Риски и пробелы test-ов: оба hook-а берут счётчик ссылок у тех же store, что виды; новых вызовов gh и git нет, если вид
  смонтирован (он смонтирован всегда, `AppShell.tsx`). Unit-test `view-zones` проверяет счёт Pull requests (только группы
  `PR_NEED_YOU`) и точку Pipeline (не у Ticket-а агента) в header и footer с подменёнными источниками; мутант с
  `noBadge` у Pipeline валит его (exit 1). Настоящий GitHub и `epic-status` test не трогает.

## 4. Rail: без бейджа рядом с одноимённой секцией, с меткой «окно»

- Что делает: каждая кнопка читает свой бейдж всегда (hook зовётся на каждом render), а показывает его, только если

  (`Sidebar.tsx:283`, `sectionNames`). Неактивная кнопка берёт причину из реестра как tooltip.
- Почему здесь: решение владельца B (2026-11-25) — на rail у View button-а метка «окно» и нет второго бейджа рядом с
  одноимённой секцией; в header и footer бейдж есть всегда.
- Без него: на rail рядом стояли бы два одинаковых счёта Acceptance — секции и кнопки.
- Требование: [Решения владельца 2026-11-25](../spec.md#решения-владельца-2026-11-25)
- Риски и пробелы test-ов: правило сравнивает подписи: секции Pull requests, Acceptance и Pipeline совпадают с
  подписями кнопок, поэтому на rail эти три кнопки бейджа не показывают никогда, пока секции есть. Метку «окно» на
  экране проверяет e2e `view-buttons.spec.ts`; локально его не запускали.
