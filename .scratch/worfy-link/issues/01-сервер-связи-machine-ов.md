## Что происходит

- Сети в worfy нет. В `src/` не найдено ни `node:tls`, ни `node:https`, ни `node:net`, ни
  `safeStorage`, ни одного `listen(`. В зависимостях (`package.json:22-36`) нет ни сервера
  WebSocket, ни генерации сертификатов.
- Мост IPC знает только окна Electron.
  - `registerIpc` (`src/main/ipc/index.ts:163-184`) вешает каждый handler на `IpcMainLike` —
    интерфейс с одним методом `handle`, который `registerIpc` принимает вместо самого `ipcMain`
    (`:51-53`). Сетевой адаптер встаёт в эту точку без правки доменных handler-ов.
  - Обёртка `wrap` (`:127-156`) пускает вызов, только если `event.senderFrame.url` — страница
    самого worfy (`:130-133`; правило `isAppUrl`, `src/main/index.ts:79-80`). У сетевого вызова
    кадра нет: сейчас он получит отказ «untrusted frame».
  - `isTrustedSender(url)` передают в `registerIpc` 23 contract test-а (`grep -l isTrustedSender
    test/contract`). Смена сигнатуры правит их все.
  - Handler-ы берут из `event.sender` подписчика: `send`, `id`, `isDestroyed`, событие `destroyed`
    (Ticket 03 переводит это на реестр клиентов). Событие main отправляет функцией `emit` в любой
    объект с методом `send` (`index.ts:187-203`).
- У каждой сборки своя папка данных: `Application Support/worfy` у собранного приложения,
  `worfy-dev` у dev-сборки; переменная `WORFY_DATA_DIR` подменяет обе
  (`src/main/storage/paths.ts:30-34`). Один процесс на папку — single-instance lock по `userData`
  (`src/main/index.ts:24-34`). Поэтому dev-сборка и Stable copy (собранная копия worfy вне
  репозитория, из которой идёт Autopilot над самим worfy) работают на одном Mac одновременно, а у
  каждого e2e-запуска своя временная папка (`test/e2e/helpers.ts:116`, `:127-134`). Имя компьютера у них
  одно.
- Хранилища кладут свои файлы в `dataRoot()` сами (`src/main/projects/store.ts:256`,
  `src/main/agent/limits.ts:224`). Чтение и запись JSON — `src/main/storage/json-file.ts`: запись
  через временный файл, нечитаемый файл откладывается в сторону (`:1-17`). Для нового хранилища
  `paths.ts` менять не нужно.
- Шаги старта, сбой которых останавливает worfy, перечислены в `StartupStep`
  (`src/main/startup-failure.ts:11-21`).
- Версия сборки — `<semver>+<SHA>[.dirty]`, канал `app.version` (`src/shared/ipc/app.ts:5-10`,
  `src/main/ipc/app.ts:6-7`). dev-сборка и Stable copy часто разных версий.
- `pnpm test` гоняет vitest внутри Electron как Node (`ELECTRON_RUN_AS_NODE=1`, `package.json:16`).
  Там есть `node:tls`: Node 24.21, TLS — BoringSSL (`process.versions.openssl` = `0.0.0`), как и в
  самом приложении. API Electron (`safeStorage` и др.) там нет. CI — только Linux, test-ы связи
  должны проходить и на нём.
- ADR-0052 оставил решить Ticket-ам: где Machine хранит id, сертификат и токены; как код
  подтверждает именно эти два сертификата; срок жизни кода и число попыток; как отличить адрес
  локальной сети; когда открыт порт.

## Что делаем

1. **Machine** (Q9). При первом старте над папкой данных Machine получает id (UUID), имя и ключ с
   self-signed сертификатом. Всё переживает перезапуск.
   - Machine привязана к папке данных. dev-сборка, Stable copy и каждый e2e-запуск — разные
     Machine.
   - Имя — имя компьютера. У dev-сборки — с пометкой «dev» (`setBuildKind`, `paths.ts:17`): иначе
     на одном Mac две Machine с одним именем. Окончательная форма — в «Итог».
   - Сертификат — библиотекой на чистом JS (кандидаты: `selfsigned`, `@peculiar/x509`), без
     внешних программ вроде `openssl`: тот же код пойдёт на Windows (Epic worfy-windows, ADR-0054).
     Тип ключа — такой, что TLS в Electron (BoringSSL) его принимает; проверяется test-ом. Выбор
     и причина — в «Итог».
2. **Секреты.** Закрытый ключ Machine и исходящие токены — те, что эта Machine предъявляет
   Linked machine-ам, — нужны в исходном виде. Входящие токены — выданные этой Machine — хранятся
   только хэшем SHA-256 (ADR-0052, пункт 4).
   - Где хранить секреты — файл в папке данных с правами 0600 или `safeStorage` Electron (Keychain
     на macOS, DPAPI на Windows) — выбирает Ticket.
   - До выбора проверить: ad-hoc подпись (`electron-builder.yml:41`) меняется при каждой сборке.
     Спросит ли Keychain доступ после каждого обновления Stable copy — не проверено.
   - В test-ах хранилище секретов подменяется: в vitest `safeStorage` нет.
3. **Список Linked machine-ов** — файл в папке данных через `json-file.ts`: id, имя, последний
   адрес и порт, отпечаток SHA-256 сертификата, хэш входящего токена, ссылка на исходящий токен в
   хранилище секретов. Новые файлы папки данных описывает ADR-0052; ADR-0005 принят и не правится.
4. **Сервер** — HTTPS и WebSocket поверх него (`wss`) в main, TLS 1.3, сертификат Machine.
   - WebSocket — пакет `ws` в режиме `noServer`: рукопожатие разбирается в событии `'upgrade'`
     сервера HTTPS, все проверки — до `handleUpgrade`. Так советует документация `ws`;
     `verifyClient` она не рекомендует.
   - Встроенный `WebSocket` Node (в Electron он есть) — только клиент; принимает ли он свои
     опции TLS — не проверено. Клиент — тоже `ws`, если не доказано иное.
   - Порт (Q4: два worfy на одном Mac не делят порт). Предлагается: при первом запуске порт
     выбирает ОС (`0`), он сохраняется в папке данных и берётся снова; занят — берётся новый.
     Новый порт Linked machine узнаёт через Bonjour (Ticket 02) или вводом адреса. Решение — в
     «Итог».
   - Слушать на всех интерфейсах (`0.0.0.0` и `::`). Привязка к одному IP ломается при смене
     адреса по DHCP; от чужих защищают проверки п. 5.
5. **Проверки до upgrade** (Q4; ADR-0052, пункты 7 и 8). Отказ — ответ HTTP и закрытие сокета до
   рукопожатия WebSocket. Текст отказа не помогает подбирать токен.
   - Адрес собеседника — loopback или локальная сеть: IPv4 `127/8`, `10/8`, `172.16/12`,
     `192.168/16`, `169.254/16`; IPv6 `::1`, `fc00::/7`, `fe80::/10`. IPv4 внутри IPv6
     (`::ffff:a.b.c.d`) сводится к IPv4. Остальное — 403.
   - `Host` — из allowlist с портом сервера: адреса интерфейсов машины (`os.networkInterfaces()`,
     читается на каждый запрос — адрес по DHCP меняется), `localhost`, `127.0.0.1`, `[::1]`, имя
     машины в `.local`. Откуда брать имя `.local` на macOS и на Windows, проверяет Ticket.
     Остальное — 403.
   - `Origin`: запрос с любым `Origin` — 403. Клиент worfy (Node) его не шлёт, браузер шлёт
     всегда. Так закрыты страница с чужого сайта и DNS rebinding (подмена адреса, на который
     указывает имя сайта, адресом в локальной сети).
   - Версия протокола связи — целое число в заголовке рукопожатия (имя выбирает Ticket). Чужая
     версия — отказ с текстом, где названы обе версии протокола и версия сборки сервера. Клиент
     отдаёт этот текст наверх как есть (UI — Ticket 02).
   - Токен — в заголовке `Authorization`, не в адресе запроса: адрес попадает в логи. Хэш
     сверяется с хэшами входящих токенов. Нет совпадения — 401.
6. **Pairing** (Q11; ADR-0052, пункт 4). На Machine B открыт «Link a machine» (UI — Ticket 02); B
   слушает и ждёт. A соединяется с B по адресу, B показывает 6-значный код, пользователь вводит
   его на A. Итог: каждая сторона запомнила отпечаток сертификата другой (каким видела его в этом
   соединении) и токен для входа к ней, у себя — хэш выданного токена. Связь двусторонняя: в том
   же обмене каждая сторона выдаёт другой токен (32 случайных байта) и сообщает свой порт.
   - Код подтверждает отпечатки сертификатов обеих сторон. Иначе посредник в LAN (MITM) в момент
     связывания подставит свой сертификат и запомнится вместо настоящей Machine.
   - Код короткий — 10^6 вариантов. Простое «HMAC(код, отпечатки)» посредник подберёт перебором
     за миллисекунды по одному перехваченному сообщению. Нужен протокол, где перехват не даёт
     проверять догадки офлайн и у посредника одна попытка на код. Например, PAKE (обмен ключами по
     паролю: SPAKE2, CPace) с кодом в роли пароля, обоими отпечатками в transcript и подтверждением
     ключа в обе стороны.
   - Реализация — проверенная библиотека. Своя схема поверх примитивов — только по опубликованному
     протоколу, со ссылкой в «Итог». Выбор и причина — в «Итог».
   - Код одноразовый. Неверный код сжигает его, B показывает новый. Код живёт ограниченное время
     (предлагается 2 минуты, решение — в «Итог»). Одновременно идёт одна попытка.
   - Пока на B не открыт «Link a machine», pairing отвечает отказом.
7. **Соединение после pairing.** Клиент проверяет сертификат сервера по запомненному отпечатку до
   того, как отправит токен.
   - Чужой сертификат — отказ и состояние «certificate changed» для UI: Machine связывают заново.
   - Как сверять — свой `checkServerIdentity` с запомненным сертификатом в `ca` или
     `rejectUnauthorized: false` и сверка `getPeerCertificate().fingerprint256` до первого байта
     HTTP — выбирает Ticket. Test доказывает, что чужому серверу токен не уходит.
   - Соединение держится: ping/pong с таймаутом, обрыв виден событием. Когда соединяться и
     переподключаться — Ticket 02.
8. **Служебные сообщения связи** — кадры main ↔ main, не каналы `src/shared/ipc`. Этот Ticket
   вводит `hello` (id, имя, версия протокола и сборки) и `revoked`.
   - Точка расширения: модуль регистрирует своё сообщение по имени со схемой zod и обработчиком,
     шлёт его Machine по id. Ею пользуются Ticket-ы 13 (уведомления), 14 («засыпаю») и 15
     (проверка Autopilot). В список каналов Ticket-а 08 эти сообщения не входят.
   - Путь файла с этой точкой — в «Итог»: Ticket 15 дописывает его в свой «Где в коде» при claim.
9. **IPC по соединению — адаптер `IpcMainLike`.** `registerIpc(adapter, …)` регистрирует те же
   handler-ы. Адаптер принимает кадры `{id, channel, input}` и отвечает `IpcResult` — тем же
   `{ok, value}` или `{ok:false, error}`, что и окну.
   - Поддельный event: `sender` с `send`, `id`, `isDestroyed`, `once('destroyed')`. Его id не
     совпадает с `webContents.id` окон и с отрицательными id подписчиков Autopilot
     (`src/main/ipc/autopilot.ts:43-44`). Общее правило id вводит Ticket 03, соединение в реестр
     клиентов ставит Ticket 08.
   - Проверка доверия. Сигнатуру `isTrustedSender(url)` не ломать: её передают 23 test-а.
     Вариант (а): поддельный event несёт `senderFrame.url` вида `worfy-link://<machineId>`, а
     регистрация адаптера получает свою `isTrustedSender`, которая пропускает только Machine из
     списка Linked machine-ов, — `index.ts` не меняется. Вариант (б): необязательное поле
     `RegisterOptions` с проверкой по event. Выбор — в «Итог».
   - Открыт ровно один канал — `link.ping` (новый, `src/shared/ipc/link.ts`, handler —
     `src/main/ipc/link.ts`): id и имя Machine, версия протокола и сборки. Любой другой канал —
     `{ok:false}` «not open to Linked machines», handler не вызывается. Список открытых каналов —
     одно место; его расширит Ticket 08.
10. **Когда сервер слушает** (Q4; ADR-0052, пункт 6: без действия пользователя worfy сеть не
    слушает). Сервис связи держит набор причин слушать.
    - Причина «есть хотя бы одна Linked machine» — этот Ticket. Причина «открыт Link a machine» —
      API этого Ticket-а, включает её Ticket 02.
    - Нет причин — сервер закрыт. Над свежей папкой данных он не слушает.
    - Переключатель «Linked machines can work with my Projects» — другое. Он решает, что можно
      Linked machine-е в Project-ах этой Machine (Ticket 08), а не слушает ли сервер. Связь,
      `link.ping` и служебные сообщения работают и при выключенном переключателе.
11. **Отзыв** (ADR-0052, пункт 9) — на уровне сервиса: забыть Machine (запись, хэш, исходящий
    токен), закрыть её соединения в обе стороны, послать `revoked`, если соединение открыто.
    Получив `revoked` или 401 при входе к Machine с верным сертификатом, вторая сторона тоже
    забывает первую. UI отзыва — Ticket 02.
12. **Логи** (ADR-0052, пункт 10). Ни код, ни токены не попадают в `console.*`, тексты ошибок,
    ответы IPC и журналы worfy. Сообщения о связи называют Machine по id и имени.
13. **Старт.** `src/main/index.ts` поднимает сервис связи после `registerIpc`. Сбой связи (порт
    занят, файл ключа не читается) не останавливает worfy: это не шаг `StartupStep`, а
    предупреждение в журнал и состояние для UI Ticket-а 02.
14. **Стенд для test-ов** — `test/contract/link-bench.ts`: несколько сервисов связи над временными
    папками данных в одном процессе vitest, на `127.0.0.1`, с подменённым хранилищем секретов и
    часами; связывает их по коду через API сервиса. Им пользуются Ticket-ы 02, 13, 14 и 15.

Не входит: UI связывания, Bonjour, переподключение и состояние «в сети / недоступна» в UI (Ticket
02); каналы Project-ов по сети (Ticket 08); «спит» (Ticket 14). Запрос Local Network на macOS 15+
(Apple TN3179) этот Ticket не разбирает: его test-ы ходят только на `127.0.0.1`.

Сделано в ветке `worfy-link/01`.

- **Первый test падал так.** `test/contract/link-pairing.test.ts` без `src/main/link/` (так на main): vitest — `Test Files 1

- **Файлы связи (итог):** `src/main/link/{identity,secrets,store,checks,pairing,server,client,connection,messages,ipc-adapter,service}.ts`.
  `connection.ts` — сверх предложенного списка: одно установленное соединение (кадры, вызовы IPC с ответом, ping/pong).

- **Новые файлы папки данных:** `link/machine.json` (id, имя, сертификат, порт), `link/linked.json` (Linked machine-ы: id,
  имя, адрес, порт, отпечаток SHA-256, хэш входящего токена, ключ исходящего токена в хранилище секретов),
  `link/secrets.json` (закрытый ключ Machine и исходящие токены; 0600, папка `link/` — 0700).
- **Точка расширения служебных сообщений** (для Ticket-ов 13, 14, 15): `src/main/link/messages.ts` — `defineLinkMessage(name,
  schema)`; регистрация и отправка — `LinkService.registerMessage` / `LinkService.sendMessage` в `src/main/link/service.ts`.
  Приёмник разбирает payload своей схемой; не по схеме — предупреждение без payload, обработчик не вызывается.
  Сервис приложения — `appLinkService()` там же.
- **Список каналов, открытых Linked machine-ам**, — одно место: `LINK_OPEN_CHANNELS` в `src/main/link/ipc-adapter.ts`
  (сейчас только `link.ping`). Его расширит Ticket 08.
- **Новые зависимости.** `ws` 8.22.0 (+ `@types/ws` в dev) — сервер и клиент WebSocket, режим `noServer`; встроенный
  `WebSocket` Node — только клиент, и сервер всё равно нужен. `selfsigned` 5.5.0 — сертификат на чистом JS (над
  `@peculiar/x509` 1.x и WebCrypto), без `openssl`. `@noble/curves` 2.4.0 — арифметика P-256 для SPAKE2 (в Node её нет:
  `crypto` умеет ECDH, но не сложение точек). `@peculiar/x509` 2.x напрямую не взят: требует глобальный Reflect polyfill.

Решения (все — **решено без владельца, подтвердить**):

- **Секреты — файл 0600, не `safeStorage`.** На macOS `safeStorage` хранит ключ в Keychain под подписью приложения, а ad-hoc
  подпись (`electron-builder.yml`) меняется с каждой сборкой: Keychain, по тому, как он привязывает доступ к подписи,
  спрашивал бы доступ после каждого обновления Stable copy. **Не проверено:** сам запрос Keychain на Mac владельца —
  бриф запрещает вызывать системные диалоги. Хранилище спрятано за интерфейсом `SecretStore` (`secrets.ts`): store над
  `safeStorage`/DPAPI встаёт без правки остального. Файл читается своим кодом, не `json-file.ts`: тот цитирует ошибку
  JSON-парсера, а V8 цитирует в ней текст файла.
- **Сертификат:** ECDSA P-256, SHA-256, срок 20 лет, начало — сутки назад (часы Linked machine могут отставать). BoringSSL
  Electron принимает его в TLS 1.3 — это показывают contract test-ы связи под `ELECTRON_RUN_AS_NODE` (`process.versions.openssl`
  = `0.0.0`). Ключ не подходит к сертификату или пропал — новый ключ и сертификат с прежним id; Linked machine-ы увидят
  «certificate changed».
- **Pairing — SPAKE2 по RFC 9382** (https://www.rfc-editor.org/rfc/rfc9382, набор P256-SHA256-HKDF-HMAC) поверх
  `@noble/curves`, своя реализация по опубликованному протоколу: проверенной JS-библиотеки SPAKE2/CPace нет (npm `spake2`
  1.0.2 — 2022 год, `elliptic`/`bn.js`). Реализация сверена с test vectors приложения B RFC (test в
  `link-pairing.test.ts`). Идентичности в transcript — отпечатки сертификатов, как их видела каждая сторона в этом
  соединении (A — клиентский сертификат TLS, B — серверный); AAD — `worfy-link/1`. w = scrypt(код, N=2^14, r=8, p=1, 40
  байт) mod p. Ключ подтверждается в обе стороны; токены (32 случайных байта) идут только после проверки подтверждения.
- **Код:** 6 цифр, живёт 2 минуты; одновременно одна попытка (вторая — 409); первое сообщение попытки сжигает код, B
  показывает новый. **Сверх Ticket-а:** после 10 неудачных попыток подряд «Link a machine» закрывается сам — иначе
  атакующий в LAN перебирает по попытке на код, пока окно открыто.
- **Проверка сертификата сервера клиентом** — своя `createConnection`: `fingerprint256` сверяется до того, как сокет
  отдан HTTP-запросу, поэтому ни байта запроса (и `Authorization`) не уходит чужому серверу. `checkServerIdentity` не
  подходит: Node вызывает её только после проверки цепочки, которую self-signed сертификат без CA не проходит.
- **Взаимная аутентификация TLS:** сервер просит сертификат клиента; токен принимается, только если отпечаток сертификата
  клиента — тот, что запомнен для владельца токена.
- **Проверка доверия IPC — вариант (а):** поддельный event несёт `senderFrame.url` = `worfy-link://<machineId>`, адаптер
  регистрирует handler-ы со своей `isTrustedSender` (только Machine из списка). id отправителей связи считаются от
  1 000 000 000 вверх: id окон идут от 1, подписчиков Autopilot — от −1 вниз.
- **Порт:** при первом прослушивании выбирает ОС, он хранится в `link/machine.json` и берётся снова; занят — новый от ОС.
  Слушает на `::` (dual-stack), без IPv6 — на `0.0.0.0`.
- **Заголовок версии протокола:** `X-Worfy-Link-Protocol: 1`. Чужая версия — 400 с текстом «worfy link protocol mismatch:
  this Machine (worfy <сборка>) speaks link protocol 1, the connecting worfy speaks <N>…»; клиент отдаёт его как есть.
- **Имя Machine:** `os.hostname()` без домена; dev-сборка — «<имя> (dev)». На Mac владельца получилось
  «Alexeys-MacBook-Pro (dev)».
- **Имя `.local` для Host:** первая метка `os.hostname()` + `.local`. На macOS `os.hostname()` = `Alexeys-MacBook-Pro.local`,
  `scutil --get LocalHostName` = `Alexeys-MacBook-Pro` — совпадает. **Не проверено на Windows** (там `os.hostname()` —
  имя NetBIOS без домена; правило даёт `<имя>.local`).
- **Когда слушает:** причины `linked`, `linking` (`openLinking`/`closeLinking` — для Ticket-а 02) и `pairing` — пока эта
  Machine сама связывается с другой (B запоминает порт A, ему нужен работающий порт).
- **Ping** каждые 15 s; нет pong до следующего ping — соединение рвётся, событие `disconnected`.
- **Отзыв, пока вторая Machine не в сети:** она узнаёт его 401-м, только если отозвавшая Machine слушает (есть другая
  Linked machine или открыт «Link a machine»). Иначе порт закрыт — вторая Machine видит «недоступна».
