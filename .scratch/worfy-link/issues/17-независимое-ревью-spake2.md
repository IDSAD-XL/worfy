## Что происходит

- Две Machine (компьютеры с worfy) связываются по 6-значному коду. Вторая Machine показывает код на
  экране, его вводят на первой. Этот шаг называется pairing.
- Код проверяет протокол SPAKE2 (RFC 9382, https://www.rfc-editor.org/rfc/rfc9382). Это обмен ключами
  с аутентификацией по паролю. Стороны доказывают друг другу, что знают один код. Сам код по сети не
  передаётся. Перехваченный обмен не даёт проверять догадки о коде без участия сторон.
- Реализация протокола своя. Арифметику кривой P-256 даёт библиотека `@noble/curves` 2.4.0
  (`package.json:26`). Шаги SPAKE2 написаны в worfy: проверенной JS-библиотеки SPAKE2 нет. Так записано
  в «Итог» Ticket-а 01 этого Epic-а (сервер связи Machine-ов), строки 281–288.
- Код — `src/main/link/pairing.ts`. Test-ы — `test/contract/link-pairing.test.ts`. Других файлов со
  словом `spake` в `src/` и `test/` нет: `git grep -n -i spake -- src test` называет только эти два.
- Реализация сверена с одним test vector из приложения B RFC 9382 (`link-pairing.test.ts:59-81`;
  комментарий на `:60` — «The first test vector»).
- PR #154 внёс этот код и прошёл ревью двух агентов-ревьюеров («Итог» Ticket-а 01, строки 366–369).
  Их долги о pairing записаны там же, строки 370–373. Первый из них в коде на месте: `pairing.ts:412`.
- Владелец 2026-10-12 принял реализацию для локальной сети. Его условие: до первого внешнего
  пользователя реализацию проверяет независимый ревьюер.
- Сегодня связь работает только в локальной сети. Это пункт 7 ADR-0052 (решение о Machine и
  связывании по коду).

## Что делаем

Ревью делает человек или отдельная Session агента (Session — сеанс Claude Code). Условие одно:
исполнитель не писал `src/main/link/pairing.ts`. Исполнитель сам читает RFC 9382 и сверяет код с
текстом RFC, а не с комментариями в коде. Код он не правит.

Ниже M, N, pA, pB, w, K, TT, Ke, Ka, KcA, KcB и AAD — обозначения RFC 9382. w — число, которое
получается из кода связывания. TT (transcript) — все данные обмена, из которых считаются ключи.

Что проверяется:

1. **Шаги протокола против RFC 9382.**
   - Константы M и N для P-256 (`pairing.ts:33-34`).
   - Доли сторон pA и pB (`spake2Share`, `:68-71`) и случайные скаляры (`randomScalar`, `:57-59`).
   - Общая точка K, transcript TT, ключи Ke и Ka, ключи подтверждения KcA и KcB (`spake2Finish`,
     `:95-119`).
   - Порядок и состав четырёх сообщений `pake1`–`pake4` (`:237-243`; сторона A — `initiatePairing`,
     `:349-383`; сторона B — `respondToPairing`, `:389-427`).
   - Что стоит на месте идентичностей A и B и на месте AAD (`:43`, `:365-367`, `:405-407`): отпечатки
     сертификатов TLS и строка версии протокола связи.
2. **Недопустимые точки и нейтральный элемент группы.** Что делает код, если доля другой стороны —
   не точка кривой, точка в неверной кодировке, нейтральный элемент или точка, после которой общая
   точка K становится нейтральным элементом (`:96-103`). Что происходит при w = 0 (`:62-65`, `:70`).
3. **Подтверждение ключа.** Каждая сторона проверяет подтверждение другой до того, как отдаёт токен
   устройства (секрет, с которым связанная Machine входит потом) или записывает связь (`:372-380`,
   `:412-425`). Что успевает узнать сторона, которая не знает кода.
4. **Сравнение за постоянное время.** `sameBytes` (`:308-310`) и все остальные места, где
   сравниваются секретные значения.
5. **Как код становится входом протокола.**
   - `codeScalar` (`:62-65`): scrypt с постоянной солью, параметры N, r, p, длина 40 байт, приведение
     по модулю порядка группы.
   - Генерация кода (`newPairingCode`, `:122-124`).
   - Сколько догадок получает атакующий: срок жизни кода, одна попытка за раз, код недействителен
     после первой попытки, окно связывания закрывается после 10 неудач (`PairingWindow`, `:150-231`;
     `PAIRING_MAX_FAILURES`, `:143`).
   - Хватает ли 6 цифр и этих ограничений вне локальной сети. (Ответ владельца 2026-10-18, Q19: хватает
     вместе с пределом 10 неудач за час — Ticket [28](28-предел-неудачных-pairing-за-час.md).)
6. **Что пишется в лог.** Код, w, скаляры, ключи и токены не попадают в `console.*`, тексты ошибок и
   ответы IPC. Правило — пункт 10 ADR-0052. Места: `PairingError` (`pairing.ts:128-134`), лог неудачной
   попытки (`src/main/link/service.ts:666`), вызовы pairing в сервисе связи (`service.ts:293`, `:645`).

### Выводы по шести пунктам

**1. Шаги протокола — совпадают с RFC 9382.**
- M и N (`pairing.ts:33-34`) байт в байт равны значениям P-256 из раздела 6.
- Доли (`spake2Share`, `:68-71`): pA = w·M + x·P, pB = w·N + y·P, несжатый SEC1 — раздел 3.3 и
  раздел 6 («all others use the uncompressed SEC1 encoding»). A — клиент TLS, использует M; B —
  сервер, использует N. Это пример из раздела 3.1.
- Скаляры (`randomScalar`, `:57-59`): 48 случайных байт по модулю (p−1), плюс 1. Значение в [1, p),
  смещение около 2^-128. Раздел 3.3 просит [0, p), раздел 7 — равномерность и rejection sampling
  (RECOMMENDED, не MUST). Ноль исключён: `multiply` библиотеки ноль не принимает (скрипт:
  «invalid scalar: out of range»). x и y новые в каждом запуске (`:352`, `:395`) — запрет повтора из
  раздела 7 соблюдён.
- K = x·(pB − w·N) и K = y·(pA − w·M) (`:99-102`). Кофактор P-256 h = 1, умножать на h не нужно.
- TT (`:105`): len(A)‖A‖len(B)‖B‖len(pA)‖pA‖len(pB)‖pB‖len(K)‖K‖len(w)‖w. Длина — 8 байт little-endian
  (`le64`, `:49-53`). w дополнен до 32 байт big-endian (`bytes32`, `:48`) — раздел 3.3.
- Ke‖Ka = SHA-256(TT) (`:106-108`); KcA‖KcB = HKDF(Ka, salt = nil, info = "ConfirmationKeys"‖AAD, 32)
  (`:109-111`); cA = HMAC(KcA, TT), cB = HMAC(KcB, TT) (`:116-117`) — раздел 4. Все четыре вектора
  приложения B это подтверждают.
- Сообщения: `pake1` = pA; `pake2` = pB, cB, сведения о B; `pake3` = cA, сведения о A, токен A;
  `pake4` = токен B (`:237-243`). В примере раздела 3.1 cA идёт раньше cB, здесь B шлёт cB вместе с
  pB. Требования MUST раздела 3.1 соблюдены: A не завершает протокол без проверки cB (`:372`), B — без
  проверки cA (`:415`). Активный атакующий от этого порядка не выигрывает: cB даёт ему одну проверку
  одной догадки, ровно как ответ B на cA в порядке RFC.
- Идентичности — отпечатки SHA-256 сертификатов TLS, какими их видела каждая сторона в этом
  соединении (`:253`, `:365-366`, `:405-406`; в сервисе — `service.ts:315-316`, `:650-652`). Пустой
  идентичности не бывает: без клиентского сертификата B отказывает до pairing (`service.ts:625`).
  Это закрывает unknown key-share из раздела 3.3. Посредник со своими сертификатами разводит
  transcript-ы; это показывает test `link-pairing.test.ts:255`.
- AAD = `worfy-link/1` (`:43`, `:367`, `:407`) — раздел 3.2 допускает AAD как защиту от понижения
  версии. Согласования версий нет, так что AAD здесь — разделение доменов, а не защита от понижения.
  Это не расхождение.
- Ke не используется (`:74`): канал уже шифрует TLS, а связь transcript-а с этим TLS-соединением даёт
  отпечатки в идентичностях. K наружу не выходит — требование раздела 3.3 выполнено.

**2. Недопустимые точки и нейтральный элемент — совпадает с разделом 7; test-а нет (Н1, Н2).**
- `Point.fromBytes` (`:97`) отвергает точку вне кривой, длину 0, 1 байт `0x00` (SEC1-кодировку
  нейтрального элемента), 64 и 66 байт, x ≥ p, гибридную кодировку `0x06`/`0x07` — всё проверено
  скриптом. Кофактор 1, значит «на кривой» = «в группе G» — требование раздела 7 выполнено.
- Доля pA = w·M (для B) и pB = w·N (для A) после снятия маски даёт нейтральный элемент; `:101`
  отвергает её («the other share is invalid»), проверено скриптом. Проверка `:103` при x, y ≠ 0 в
  группе простого порядка не срабатывает никогда — она лишняя, но безвредная.
- Любая из этих ошибок ловится (`:369-371`, `:409-411`) и кончается закрытием 4001 с общим текстом
  `PAIRING_FAILED`. Код у B к этому моменту уже сожжён (`:392`).
- w = 0: `spake2Share` бросает ошибку (`multiply` не берёт 0, проверено скриптом). `codeScalar` даёт 0
  с вероятностью около 10^6 / 2^256 на весь набор кодов — на практике никогда.
- **Сжатая точка (33 байта) принимается** — скрипт: «compressed 33-byte encoding … no throw». Раздел 6
  требует несжатую, раздел 3.2 — «Applications MUST specify this encoding». Вреда нет: TT строится из
  полученных байт, и перекодированная доля разводит transcript-ы. → **Н2**.
- **Test-а на недопустимую точку и на нейтральный элемент нет**: `grep -n -i "invalid\|infinity\|toThrow"
  test/contract/link-pairing.test.ts` — пусто (exit code 1). → **Н1**.

**3. Подтверждение ключа — совпадает с разделами 3.1 и 4.**
- A проверяет cB (`:372`) до того, как проверяет id B (`:373`), выдаёт токен (`:376-377`) и пишет
  связь (`:380`). B проверяет cA (`:415`) до проверки id A (`:416`), записи (`:420`) и своего токена
  (`:425`).
- Что узнаёт сторона без кода в роли A (шлёт `pake1` на B): pB, cB и сведения о B — id, имя, сборку,
  порт (`:412`). cB даёт одну проверку одной догадки (это свойство SPAKE2). Код при этом сожжён и
  засчитан как неудача (`PairingWindow.end`, `:208-221`). Сведения о B до подтверждения — долг 1
  PR #154. → **Н3**.
- В роли B (отвечает A): только pA. По pA догадку не проверить, без cB A ничего больше не шлёт и
  закрывает соединение кодом 4001.
- B записывает связь до того, как A получила `pake4` (`:420` раньше `:425`). Если `pake4` потерян, у B
  запись есть, у A нет. Это неустранимо для двух сторон, а не дыра: запись B без записи A не открывает
  ничего. Не находка.

**4. Сравнение за постоянное время — совпадает.**
- `sameBytes` (`:308-310`) — `timingSafeEqual` после проверки длины. Длина MAC (32 байта)
  публична. Используется на `:372` и `:415`.
- Токен при входе: `byToken` (`store.ts:53-57`) сравнивает SHA-256 токена через `timingSafeEqual`.
- Других сравнений секретов в `src/main/link` нет: `git grep -n "timingSafeEqual\|sameBytes" -- src`
  называет только эти места. Отпечатки сертификатов (`service.ts:490`, `:634`) не секретны.
- Арифметика точек — `multiply` (`:70`, `:100`, `:102`), а не `multiplyUnsafe`. Раздел 7 запрещает
  умножение, которое выдаёт длину скаляра. Оговорка: на BigInt в JS постоянного времени гарантировать
  нельзя. Здесь это не открывает перебора: w меняется с каждым кодом, а код сгорает после одной
  попытки. Одно измерение на код не даёт сузить 10^6 вариантов. Не находка.

**5. Как код становится w — совпадает с разделом 3.2; 6 цифр хватает для локальной сети (Н4).**
- `codeScalar` (`:62-65`): scrypt (N = 2^14, r = 8, p = 1), 40 байт = 256 + 64 бит, по модулю p.
  Раздел 3.2: MHF (scrypt — его пример) и запас в 64 бита по NIST SP 800-56A — выполнено. Около 18 мс
  на вызов (скрипт). Соль постоянная. Это допустимо: SPAKE2 не даёт проверять догадки по
  перехваченному обмену, а w нигде не хранится. Ни соль, ни scrypt тут не главная защита: главная —
  одна догадка на попытку. Нормализации нет и не нужно: `PAIRING_CODE_PATTERN` (`:126`) пускает только
  ASCII-цифры (`service.ts:294`, схема IPC — `src/shared/ipc/link.ts:150`).
- Код: `randomInt(0, 1_000_000)` (`:123`) — CSPRNG Node, равномерно.
- Догадки: одна попытка за раз (`begin`, `:186-196`); код сгорает при первом сообщении попытки
  (`take`, `:199-202`; `respondToPairing`, `:392`) и сменяется (`end`, `:219`). Срок кода — 2 минуты
  (`:37`). После 10 неудач подряд окно закрывается (`:143`, `:215-217`). Итого на одно открытие окна
  — 10 догадок против 10 свежих кодов: 1 − (1 − 10^-6)^10 ≈ 1 к 100 000. Так и написано в
  комментарии `:141`.
- Для локальной сети этого хватает. Вне её подбор кода остаётся на том же уровне, но окно уязвимо к
  отказу в обслуживании. Попытка, которая заняла слот и не прислала `pake1`, не считается неудачей.
  Слот можно держать бесконечно, а настоящая A получает 409. Предела на число открытий окна нет. →
  **Н4**, условие для выхода за локальную сеть.

**6. Что пишется в лог — совпадает с пунктом 10 ADR-0052.**
- Тексты `PairingError` в `pairing.ts` — постоянные строки (`:137`, `:260`, `:271`, `:279`, `:283`,
  `:287`, `:291`); в сервисе добавляются только имя Machine и причина, по которой сервер не слушает
  (`service.ts:301`, `:488-493`). Ошибки разбора точки (`:369`, `:409`) глотаются и заменяются на
  `PAIRING_FAILED`.
- Лог неудачи у B (`service.ts:666`) пишет адрес и этот текст. Текст ошибки не из `PairingError`
  идёт через `messageOf`: это ошибка scrypt, хранилища секретов или файла. Кода, w, скаляров и
  токенов в них нет.
- `link.pair` ловит все ошибки и отдаёт текст на экран своей Machine (`src/main/ipc/link.ts:248-258`).
  Канал `local` (`src/shared/ipc/link.ts:155`): Linked machine его не вызывает. Код в ответе IPC — только
  `link.state`, тоже `local` (`:135`): B должна показать его на своём экране.
- Test: каждый test `link-pairing.test.ts` после себя проверяет, что ни код, ни токен не попали в
  console.* и тексты ошибок (`:24-28`, `link-bench.ts:159-170`). w, скаляры и ключи эта проверка не
  ищет; по чтению кода их не выводит ни одна строка.

### Долги ревьюеров PR #154 («Итог» Ticket-а 01, `:370-376`)

Ticket называет строки 370–373. Четыре пункта на деле занимают `:370-376`: два из них в две строки.

- `:372` — `checkPeerId` не повторяется в `commitLink`. **Подтверждён**: `service.ts:501-519` без
  проверки. Ожидание сети между проверкой и записью есть только у A (`pairing.ts:373` → `:378-380`).
  У B обе синхронны (`:416` → `:420`). → low, Ticket [23](23-запись-связи-перепроверяет-id-и-сертификат.md).
- `:374` — ответ IPC больше 16 MiB рвёт соединение кодом 1009. **Подтверждён**: размер проверяет
  только получатель (`server.ts:116`, `client.ts:71`), отправитель нет (`connection.ts:87`,
  `service.ts:593`). Это не pairing, но долг из списка. → low, Ticket [24](24-слишком-большой-ответ-ipc-по-связи.md).
- `:375` — закрытие «Link a machine» даёт `pairing-failed` и warn, UI не должен показывать это как
  ошибку. **Снят для UI**: текст неудачи виден только пока окно открыто (`src/main/ipc/link.ts:189`).
  Он сбрасывается, когда закрывается последнее окно (`:206`) и когда окно открывается снова (`:232`).

  connection», хотя закрыла эта Machine. Секретов в ней нет. Ticket-а не завожу: это решено без
  владельца, подтвердить.
