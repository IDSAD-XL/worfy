# 40 — «Change address…» не закрывает старое соединение: запросы идут по старому адресу

Type: bug
Status: claimed 2026-10-31T03:41Z
Branch: worfy-link/40
Blocked by: —
Source: приёмка link 31 с владельцем 2026-10-31, шаг 4c: ПК связан с Mac по LAN `192.168.0.137:57769`, владелец
сохранил в «Change address…» адрес Tailscale `100.71.20.55:57769`. Сохранение прошло, `linked.json` — новый адрес, но
через 2 мин 11 с оба сокета ESTABLISHED (LAN и Tailscale) на обеих машинах; «disconnected» нет ни в одном журнале,
Mac записал «connected» дважды. Разбор кода — scout Orchestrator-а. Ticket заведён Orchestrator-ом. Blocked by 39 —
общая тема `src/main/link`, идут друг за другом.

## Что происходит

- `LinkService.setAddress` (`src/main/link/service.ts:540`) вызывает `connectAt(record, target, 'claimed')`
  (`service.ts:495`), а тот только добавляет новый сокет: `attach(...)` (`service.ts:522`). Старое соединение не
  закрывается. Docstring `service.ts:536-538` обещает «this dial is then the connection» — код этого не делает.
- Соединения Machine — `Map<machineId, Set<LinkConnection>>` (`service.ts:761-766`); второе соединение того же id
  просто добавляется (на B — через `admit`, `service.ts:885-897`). Два соединения допустимы по дизайну: стороны
  звонят друг другу (`src/main/link/remote-calls.ts:15`, `docs/features/link.md:344`).
- Вызовы и события идут по первому открытому соединению Set-а по порядку вставки (`remote-calls.ts:191-203`,
  `service.ts:668-670`) — то есть по старому LAN-сокету. Адрес, заданный вручную, не начинает работать, пока старый
  сокет жив; при его обрыве `current` переключается и окна перезагружаются (смена `epoch`, `remote-calls.ts:197-199`).
- Ping, `hello` и broadcast идут по обоим сокетам.

## Что делаем

1. `setAddress`: когда новый сокет прошёл проверку сертификата и прикреплён, остальные соединения этой Machine
   закрываются с отдельным кодом и причиной (`replaced by an address set by hand`). `disconnected` при этом не
   эмитится: Machine всё время на связи. Решено без владельца (Orchestrator, 2026-10-31): «Change address…» значит
   «связь идёт по этому адресу», а не «добавь ещё один путь».
2. Сторона B видит закрытие старого сокета с этим кодом и тоже не эмитит `disconnected` (в Set остаётся новый).
3. Строка журнала на обеих сторонах: `[link] Machine … : the connection at <old> is closed, replaced by <new>`.
4. Автоматические пути (`seen`, `reconnect`, `dial` — `src/main/link/connections.ts:111-131`, `:196`) не меняются:
   они не открывают второй сокет поверх живого.

## Итог

- `setAddress` теперь закрывает остальные соединения Machine: `connectAt` возвращает прикреплённое соединение,
  `replaceConnections` (`src/main/link/service.ts`) закрывает все прочие с кодом `CLOSE_REPLACED = 4005`
  (`src/main/link/connection.ts`) и причиной `replaced by an address set by hand`. Если новое соединение успело
  закрыться до этого шага, старые не трогаются: других у связи нет.
- `disconnected` не эмитится ни на одной стороне без особого правила по коду: обработчик закрытия в `attach` эмитит его,
  только когда у Machine не осталось открытого соединения, а новое к этому моменту открыто на обеих сторонах (B
  прикрепляет входящее соединение до ответа 101, то есть раньше, чем A может закрыть старое). Отдельное «не эмитить по
  коду 4005» не сделано сознательно: если бы на B не осталось ни одного соединения, подавленный `disconnected` оставил бы
  Machine «на связи» без связи, и `connections.ts` не стал бы звонить снова.
- Журнал: A пишет строку в момент закрытия, B — по коду 4005 в обработчике закрытия;
  `[link] Machine <id> (<name>): the connection at <old> is closed, replaced by <new>`. Для исходящего соединения адрес —
  набранный `host:port`, для входящего — адрес, откуда оно пришло (порт там случайный и не пишется). Эхо кода 4005 на
  стороне A вторую строку не даёт (`replaced`).
- Закрываются все соединения пары, кроме нового, включая исходящее соединение B к A. Причина: вызовы и события идут по
  первому открытому соединению Set-а (`remote-calls.ts`), и на B это могло остаться его старое исходящее — по старому
  адресу, ровно та ошибка, которую чинит тикет; к тому же ping, `hello` и broadcast шли бы по двум сокетам. После ручной
  смены у пары ровно одно соединение. Цена: окна на B, показывающие A, перезагружаются (смена `epoch`), как при любой
  смене текущего соединения. Позже обе стороны снова могут дозвониться друг до друга — это прежнее поведение по дизайну.
- Автоматические пути (`seen`, `reconnect`, `dial` в `connections.ts`) не менялись.
- Test-ы — `test/contract/link-reconnect.test.ts`, `describe('link.setAddress')`: второй адрес B — имя `localhost` на том же
  порту (проверка Host сервера требует его порт, поэтому TCP-forwarder на другом порту не годится). Проверяют: у A и B
  ровно одно соединение, это новое, старые закрыты, `disconnected` нет, `link.ping` идёт через новое; строки журнала на
  обеих сторонах; отказ (чужой сертификат, нет ответа) оставляет оба старых соединения и не пишет строк замены.
  Первые два были красными до правки (5 s ожидания одного соединения).
- `docs/features/link.md`: Change address… и раздел об одном соединении на Machine.
- Ручной пункт (`Get-NetTCPConnection` на ПК, `lsof` на Mac после «Change address…») — за Orchestrator-ом с владельцем,
  вместе с link 31.
