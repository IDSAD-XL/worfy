# Changes

> Перевод [английской версии](../changes.md), commit `same-pr`.

Changes показывает, что Ticket изменил в своих репозиториях: файлы, их строки и commit-ы, прочитанные из git на Machine
Project-а. Пока worfy читает, он ничего не пишет в репозиторий, поэтому чтение безопасно рядом с агентом, который в ту
же секунду делает commit в том же worktree. Термины объяснены в [Concepts](concepts.md).

## Reading the changes

### Behaviour

#### What is read

Предмет чтения — Ticket. В каждом репозитории Project-а Changes читает worktree Ticket-а: тот worktree, ветка которого
называет Ticket (`<epic>/<NN>` или ветка из его строки `Branch:`). Это может быть и сам checkout, когда ветка Ticket-а
выбрана там (`parallel: single`). Без worktree Changes читает ветку Ticket-а: локальную ветку, которая называет Ticket и
нигде не выбрана. Project над несколькими репозиториями даёт по ответу на каждый репозиторий, и репозиторий — верхний
уровень каждого ответа. Репозиторий, где у Ticket-а нет ни worktree, ни ветки, в ответ не попадает.

#### The base

Изменения считаются от merge-base Ticket-а с базовой веткой, а не от вершины базы: commit, который попал в main branch
после того, как сделали ветку Ticket-а, в изменения Ticket-а не входит. Базу задаёт Profile Project-а, в том же
порядке, что у preflight Harness-а:

1. `worktree.base` (`origin/main`), когда такая ветка есть;
2. иначе `origin/<default branch>` — ветка, на которую указывает `origin/HEAD`, затем `origin/main`;
3. в репозитории без `origin`, в Project-е, чьи Ticket-ы заканчиваются `local-green`, — локальная ветка: значение
   `worktree.base` без `origin/`, затем ветка по умолчанию, `main`, `master`.

Когда ни одной из этих веток нет, в любом Project-е пробуется локальная `main` или `master`. Когда нет и их, ответ
репозитория говорит, что базы нет, и файлов не перечисляет.

#### Scopes

| Scope | Что показывает | У кого есть |
|---|---|---|
| All changes (по умолчанию) | Ticket против merge-base: его commit-ы, то, что ещё не закоммичено, и новые файлы, которые git не отслеживает. Игнорируемые файлы не показываются | у любого Ticket-а |
| Uncommitted | Рабочее дерево против `HEAD`, с новыми файлами | у Ticket-а с worktree |
| Commit | Один commit Ticket-а из списка commit-ов после merge-base (от новых к старым, не больше 500); merge commit — против его первого родителя | у любого Ticket-а |
| Compare against | All changes, где вместо базы любая локальная или удалённая ветка | у любого Ticket-а |

У ветки, которая нигде не выбрана, нет рабочего дерева, поэтому нет scope-а Uncommitted, а её All changes — это её
commit-ы. Какие scope-ы есть у репозитория, входит в его ответ.

#### Files and limits

Список файлов всегда полный: для каждого файла его статус (A, M, D, R, T — добавлен, изменён, удалён, переименован,
сменил тип), число добавленных и удалённых строк, режимы и blob id обеих сторон. Файл, у которого изменилось время
изменения, а текст нет, — не изменение.

Patch файла читается, только когда его просят. Он приходит свёрнутым, как «Large diff · N lines», когда у файла больше
2 000 добавленных и удалённых строк, когда его patch больше 1 MB, для lock-файла менеджера пакетов (`pnpm-lock.yaml`,
`package-lock.json`, `yarn.lock`, `Cargo.lock` и подобных) и для файла с git-атрибутом `linguist-generated`. Свёрнутый
patch всё равно можно попросить целиком, до 64 MB. У бинарного файла строк нет: его ответ — размеры двух сторон. Patch
можно прочитать и со всеми строками файла как контекстом (параметр `whole` канала `changes.file`); кнопки для этого на
экране пока нет. Смена типа (файл, ставший ссылкой, или ссылка, ставшая файлом)
показывает обе стороны: сначала удалены строки старой стороны, потом добавлены строки новой.

Каждая строка patch-а несёт свой номер на старой и на новой стороне. Строка, которая кончалась на CRLF, приходит без
`\r` и с пометкой CRLF; последняя строка стороны без конца строки помечена так («\ No newline at end of file»). Hide
whitespace опускает изменения пробелов и концов строк.

В Full mode файлы под корнем Ticket-ов (`.scratch/`) помечены как группа Workflow files. В Silent mode файлов workflow в
репозитории нет, поэтому и такой группы нет.

#### What can be asked for

Файл просят по его пути от верхней папки репозитория: абсолютный путь или путь с частью `..` отклоняется. На Windows
части пути разделяет и `\`, а `C:x` — абсолютный путь; на macOS и Linux и `:`, и `\` — обычные буквы имени файла, так
что `c:notes.md` открывается как любой другой файл. Новый файл читается, только когда git сам перечисляет его как новый
файл репозитория: игнорируемый файл или любой другой файл на Machine через это никогда не читается.

#### Nothing is written

Ни одно чтение ничего не пишет в репозиторий: ни index, ни ref, ни объект, ни lock-файл. Changes никогда не делает
fetch, stage, stash и не обновляет index; что есть у `origin` — то, что оставил последний fetch.

#### On a Linked machine

Linked machine читает изменения Project-а на этой Machine, в том числе с доступом только для чтения: git работает на
той Machine, где лежит Project.

### How it works

git запускается только через один runner, который знает фиксированный список читающих команд и отклоняет любую другую
до запуска git; команды, у которых есть пишущие формы (`worktree`, `ls-files`, `hash-object`, `cat-file`), запускаются
только в той одной форме, которой пользуется Changes. У каждого запуска выключены необязательные lock-и, выключено
обновление index-а командой `git diff` (одни необязательные lock-и эту запись не останавливают), выключен file system
monitor, нет запроса в терминале, а пути берутся буквально, никогда как шаблоны. Переменные, которые направили бы git в
другой репозиторий или index (`GIT_DIR`, `GIT_INDEX_FILE` и подобные), убираются. Имена приходят с `-z` и
`core.quotePath=false`, поэтому путь с пробелами или буквами вне ASCII читается так же и на Windows. Ни внешний diff, ни
преобразование текста не запускаются. Одна программа из git-настроек пользователя всё же может запуститься: файл
рабочего дерева, у которого изменилось время изменения, проходит через clean filter, который называет его
`.gitattributes` (например, git-lfs), как в любом `git diff`. Blob id нового файла — это id его байтов как они есть, без
фильтра. Почему так: [ADR-0110](../../adr/0110-changes-reads-git-writes-nothing.md).

База берётся из фактов Profile-а, которые main уже держит для workflow (`worktree.base` и `workflow.finish`), поэтому
Changes не запускает собственный `bin/profile`.

- Каналы `changes.scopes`, `changes.list`, `changes.file` и `changes.commits` (`src/shared/ipc/changes.ts`, обработка в
  `src/main/ipc/changes.ts`), все читающие.

Test-ы: `test/unit/changes-parse.test.ts` (чтение вывода git), `test/unit/changes-base.test.ts` (порядок базы),

потому что для создания ссылки на Windows нужна привилегия, которой у runner-а нет.

## The Changes view

### Behaviour

#### Opening it

У карточки Ticket-а есть кнопка **Changes**, когда у Ticket-а есть что читать: ветка worktree, из которой пришёл его
статус, строка `Branch:` или работа над ним (Ticket взят в работу). Один worktree без этих признаков кнопки не даёт:
карточка раскладывается по Ticket-у до того, как прочитаны worktree. У такой карточки есть место для второй строки
действий, и её кнопки действий переносятся туда, выровненные вправо, когда не помещаются в одну строку. Счёта строк на
кнопке нет. Щелчок открывает вид Changes Ticket-а во всю основную область окна, как вид Pull requests показывает pull
request: toolbar и sidebar остаются, Canvas скрыт под видом. На Canvas ничего не ставится.

**Open changes** в Command palette делает то же для Ticket-а с веткой или в работе, а щелчок по пути комментария к коду
в чате открывает вид на этой строке ([Send](#send)).

Вкладки в toolbar у вида нет: без Ticket-а ему нечего показать. **← Canvas** слева от заголовка возвращает на Canvas, и
Esc тоже, если не открыто меню или popover (Esc сначала закрывает его) и фокус не в текстовом поле. Открытая из
сообщения в Session view, кнопка читается **← Session** и возвращает туда. Выбор другого Project-а в sidebar возвращает
на Canvas.

Ticket, у которого не оказалось ни worktree, ни ветки, показывает это в виде.

#### The screen

| Часть | Что в ней |
|---|---|
| Заголовок | **← Canvas** (или **← Session**), `Changes · Ticket 03 · <epic>`; «Read only» на экране Linked machine только для чтения |
| Первая строка | Меню scope-а, затем для каждого репозитория база и head (`origin/main ← <epic>/03`), merge-base, число файлов (и файлов workflow), добавленные и удалённые строки и Refresh |
| Вторая строка | Inline или Side by side, Wrap, Hide whitespace и Compare с ветками для сравнения |
| Слева | Дерево файлов с фильтром |
| Справа | Diff файлов дерева, один под другим |

Меню scope-а перечисляет то, что предлагает ответ репозитория: All changes, Uncommitted (только у Ticket-а с worktree)
и commit-ы Ticket-а под Commit. Compare перечисляет ветки; выбор ветки показывает All changes против неё. Выбранный
scope хранится для каждого Ticket-а, пока открыто окно, а после перезапуска снова All changes; Inline, Wrap, Hide
whitespace и фильтр принадлежат только этому экрану. Refresh заново читает scope-ы, файлы и patch-и: сам экран не обновляется.

Числа — одни цифры, без разделителя тысяч (`+1243`). Добавленные строки берут фон ready, удалённые — фон blocked; код
на них подсвечен ([Syntax colours](#syntax-colours)).

#### The tree

Файлы стоят по папкам, каждый со своей буквой статуса (A, M, D, R, T) и числом добавленных и удалённых строк или
«binary». У Ticket-а в нескольких репозиториях верхний уровень — репозитории. Файлы под корнем Ticket-ов (`.scratch/`)
стоят последними группой **Workflow files (N)**, свёрнутой; diff показывает их, только пока группа открыта. Больше чем
при 300 файлах каждая папка приходит свёрнутой.

Фильтр оставляет файлы, путь или старый путь которых содержит его текст, без учёта регистра. Он открывает папки и группу
workflow, в которых есть совпадение, говорит «N of M files», и diff показывает те же файлы. Фильтр, который не оставил
ни одного файла, так и говорит.

#### The diff

У каждого файла есть заголовок: статус, путь (`old → new` для переименования), числа и кнопка, которая сворачивает файл.
Inline рисует по строке на каждую строку, с номерами обеих сторон. Side by side рисует старую сторону слева, а новую
справа: серия удалённых строк стоит рядом с серией добавленных, которая идёт за ней, а более длинная серия продолжается
с пустой другой стороной. Wrap переносит длинные строки; без него строка шире diff-а обрезается по краю. Hide whitespace
заново читает файлы и patch-и без изменений пробелов и концов строк.

Большой файл, lock-файл и сгенерированный файл приходят свёрнутыми: «Large diff · N lines · Show» (или «Lock file»,
«Generated file»), и Show читает весь patch. Бинарный файл показывает размеры двух сторон: «Binary file · 12 KB → 14 KB».
Файл, текст которого не изменился, показывает смену режима.

#### Syntax colours

Код в diff-е подсвечен, как на GitHub: цветами тем GitHub `github-light-default` и `github-dark-default` — той, что
соответствует теме окна (она следует системе). Фон добавленных и удалённых строк остаётся. Цвета приходят через миг
после того, как hunk нарисован; до тех пор hunk — простой текст той же ширины.

- Язык — по расширению или имени файла (`Dockerfile`, `Makefile`, `.zshrc`): TypeScript и TSX, JavaScript и JSX, JSON,
  Markdown, CSS, HTML, YAML, TOML, shell, Python, Go, Rust, Swift, Kotlin, Java, C, C++, C#, Ruby, PHP, SQL, Vue,
  Svelte и ещё несколько. Файл любого другого языка остаётся простым текстом.
- Каждая сторона hunk-а красится как один текст: старая (контекст и удалённые строки) и новая (контекст и добавленные
  строки). Многострочный комментарий или строка внутри hunk-а окрашены на каждой своей строке; hunk, который начинается
  внутри такого комментария, красится так, будто это не так.
- Простой текст и у строки длиннее 400 символов, и у стороны hunk-а больше 100 000 символов, и у hunk-а больше 2 000
  строк. Свёрнутый файл (большой, lock-, сгенерированный) красится только после Show, binary-файл — никогда.
- Цвета не меняют текст: выделение, Copy line, строки комментария и сообщение агенту несут текст строки, как его даёт
  `git diff`. Переключателя «без подсветки» нет.

#### Keys

Пока вид на экране: `j` и `k` (или `↓` и `↑`) выбирают следующий и предыдущий файл и прокручивают к нему, `n` и `p`
прокручивают к следующему и предыдущему hunk-у, `c` комментирует выбранные строки ([Comments on
lines](#comments-on-lines)), Esc возвращает назад. Пока идёт ввод в поле или открыто меню или popover, клавиши ничего не
делают.

#### Size

Patch файла читается, только когда файл подходит к экрану. Diff рисует только блоки — заголовок файла, hunk, пометку, —
которые на экране и на два экрана выше и ниже него; остальные стоят пустым местом своей высоты, поэтому Ticket из 300
файлов или файл из 2 000 строк рисует несколько экранов.

#### On a Linked machine

Вид читает diff на Machine Project-а, в том числе с доступом только для чтения: он ничего не меняет, поэтому кнопка и
строка palette на экране только для чтения активны. Экран только для чтения не принимает комментариев к строкам: на нём
нет «+», `c` и tray.

### How it works

Вид — вид окна, рядом с Canvas, Session и Pull requests. То, что он показывает, — Ticket, вид, куда вернуться, и scope,
выбранный для каждого Ticket-а, — живёт в памяти окна, а не в Layout: открытие не меняет Layout и не требует операции
main. Всё, что он показывает, приходит из четырёх читающих каналов выше, которые спрашивают со строками `Branch:` и
`Repo:` Ticket-а. Дерево и diff — тот же экран, что Review mode pull request-а ([Pull requests](pr-inbox.md)): каждый
добавляет вокруг них свою шапку и свою панель.

Прежние версии ставили на Canvas Changes Node. main убирает такие Node-ы при чтении Layout-а, с одной строкой log-а на
Project; неотправленные комментарии — черновики своей Session и остаются.

Diff рисуется окнами, без библиотеки: у каждого блока высота, которую дают его строки, пока он не нарисован, и
измеренная высота после.

Подсветка — Shiki (ADR-0113) с движком регулярных выражений на JavaScript: без WebAssembly, так что
Content-Security-Policy renderer-а не меняется. Shiki, обе темы и каждая грамматика — отдельные chunk-и, которые
грузятся через `import()` на первом hunk-е, которому они нужны: окно стартует без них. Hunk красится, только пока он
нарисован, по одному hunk-у: каждая сторона читается шагами примерно по 2 000 символов, каждый шаг — своя задача event
loop-а, состояние грамматики переходит от шага к шагу. Hunk, ушедший из окна, останавливается на следующем шаге. Tokens
hunk-а хранятся по языку и тексту до следующего раза, всего не больше 1 000 000 символов hunk-ов, старые уходят первыми. Каждый token несёт цвета обеих тем как CSS variables, и
`prefers-color-scheme` выбирает одну.

## Comments on lines

### Behaviour

#### Making one

Комментарий делается к одной строке или к диапазону строк одного файла и одной стороны diff-а:

- **«+»** в gutter строки под указателем;
- клавишей **`c`** на выбранных строках: щелчок по строке выбирает её, щелчок с Shift или выделение через строки
  выбирает диапазон;
- **Comment** в меню правого щелчка по строке, рядом с **Copy line**.

Над строкой открывается popover. Он называет место (`src/cart.ts:13 · new side`), показывает код строк и принимает
текст и до трёх изображений, вставленных или добавленных, как комментарий к цитате (Comments on quotes,
[Sessions](sessions.md)). `⌘↵` (Ctrl+Enter на Windows и Linux) сохраняет его; Esc или щелчок вне закрывает неизменённый
popover и оставляет изменённый. Изменённый popover остаётся и тогда, когда «+», `c`, Comment или Edit нажаты в другом
месте: worfy сначала просит сохранить его или отменить. Затем комментарий стоит под своей последней строкой с пометкой
«not sent», с Edit и Delete. Delete предлагает Undo на шесть секунд.

#### The tray and «To»

Низ вида — tray: «N comments on M files» (и «K on messages», когда у Session из «To» есть ещё комментарии к её
сообщениям), chip на каждый комментарий, который прокручивает к его строке, Clear, список **To**, поле для общего
сообщения и **Send**.

«To» перечисляет Session-ы worfy, связанные с Ticket-ом (ручной Binding сильнее того, что сделал запуск), от новой
записи к старой, затем Orchestrator. Там может быть Session любого Vendor-а. По умолчанию — связанная Session с самой
новой записью, какой бы старой она ни была; без связанной Session — Orchestrator. Как только у показанной Session есть
комментарии или она приняла Send, «To» держит её, пока вы не выберете другую: более позднее значение по умолчанию
(после Refresh или когда список прочитан заново после Send) не уводит «To» от комментариев. Когда в «To» Orchestrator,
а Autopilot работает, tray говорит «Autopilot is running».

Комментарий принадлежит Session из «To»: это черновик этой Session, тот же, что её поле ввода показывает в своём tray.
Выбор другой Session переносит к ней комментарии этого Ticket-а к коду; комментарии к сообщениям остаются, где были.
Ещё не отправленные комментарии переживают перезагрузку окна и перезапуск worfy.

#### Send

Send отправляет одно сообщение Session из «To»: раздел «Comments on lines of the diff (N)» с worktree и веткой (по
разделу на каждую пару worktree и ветки), затем для каждого
комментария его путь и строки, сторона и commit, цитата его кода и его текст, затем «General:» и текст поля. Это то же
сообщение, которое собрал бы из тех же черновиков собственный Send этой Session, включая комментарии к её сообщениям.
Session, которая больше не работает, сначала запускается; Session посреди turn-а держит сообщение в своей очереди.
Ушедшие комментарии остаются тусклыми на своих строках, «sent to <Session>». Пока Send идёт, «To», поле, × и Clear в
tray, Edit и Delete под строкой ждут его: сообщение уходит той Session, которой его отправили, с комментариями такими,
какими они были.

В чате Session сообщение показывает каждый комментарий блоком с его путём и строками. Щелчок по пути открывает вид Changes
Ticket-а и прокручивает к строке, которая мигает; из Session view его кнопка возврата читается **← Session**.

#### After a Refresh

Каждый ещё не отправленный комментарий заново ищется в строках своего файла и переезжает вместе с ними. Это происходит в
чтениях того scope-а и Hide whitespace, в которых нажат Refresh, и только для комментария на том commit-е, который эти
чтения показывают на его стороне (рабочее дерево для незакоммиченных строк): комментарий, сделанный в другом scope-е,
сохраняет свои строки, верные на его commit-е. Комментарий, строки которого чтение показывает и которых больше нет,
остаётся на месте, помечается «Line changed» на строке и в tray и уходит таким, каким был написан; строки, которых
чтение не показывает, — не новость.

### How it works

`changes.targets` читает список «To» в main: Session Node-ы Layout-а, сохранённые Binding-и, время последней записи
каждого transcript-а и то, работает ли Autopilot. Работающая Session названа своим живым id. Session, которая ещё не
сообщила свой id, держит комментарии под временным ключом; они переезжают на её id, как только она его сообщит.

Комментарии хранятся в store комментариев к цитатам, в localStorage этого окна, который лежит в папке данных worfy: в
репозиторий ничего не пишется. Ушедшие комментарии хранятся по Ticket-у, 200 новейших, поэтому они остаются тусклыми и
после перезапуска. Commit комментария — head того scope-а, в котором он сделан: worktree для его незакоммиченных строк,
commit scope-а Commit, merge-base для старой стороны.
