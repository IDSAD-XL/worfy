# Storage и диагностика

> Перевод [английской версии](../storage-and-diagnostics.md), commit `same-pr`.

Два Feature. **Папка данных** — место, где worfy хранит своё состояние на Machine. **Диагностика** — то, что worfy
записывает и показывает о себе, когда что-то идёт не так: окно ошибки неудачного старта, запись о завершившемся процессе,
stack необработанного исключения, stack-и зависшего приложения и цифра памяти в toolbar. Термины объяснены в
[Concepts](concepts.md).

## Папка данных

### Behaviour

worfy хранит своё состояние в одной папке на Machine: список Project-ов, Settings, Layout, Card-ы и корзину каждого
Project-а, входы Browser profile, journal-ы Autopilot и идентичность Machine. Ничего из этого не попадает в репозиторий
Project-а. Ticket-ов, HANDOFF, ADR и транскриптов здесь нет: worfy читает их там, где они лежат.

**Какая папка.** Packaged-сборка берёт папку `worfy`, development-сборка (`pnpm dev`, `electron .`) — папку `worfy-dev`.
На macOS обе лежат в Application Support из Library пользователя. Переменная `WORFY_DATA_DIR` задаёт папку для любой
сборки. Пустое значение не учитывается, а относительное разрешается от рабочей папки.

Поэтому development-сборка и Stable copy могут работать одновременно и не делят папку. Без этой переменной все
packaged-сборки одного пользователя делят одну папку, и Stable copy, и свежая сборка. Все development-сборки делят другую,
из какого бы worktree они ни запускались.

**Один процесс на папку.** Второй старт над занятой папкой завершается с exit code 0 и печатает в stderr «another worfy
already runs over» и папку. Работающий worfy восстанавливает своё первое окно, если оно свёрнуто, и переводит на него
фокус. Если все окна закрыты, он открывает новое. Второй старт до того, как первый процесс создал первое окно, ничего на
экране не меняет.

**Папка, которой нельзя пользоваться, останавливает старт.** Если путь — это файл, лежит под файлом или ведёт к папке, в
которую worfy нельзя писать, worfy показывает окно ошибки неудачного старта (см. [Диагностика](#диагностика)) и завершается
с кодом 1. Папка, которой ещё нет, — это нормально.

**У каждого Project-а своя подпапка.** Её имя — id Project-а: имя папки Project-а, дефис и первые 8 шестнадцатеричных
символов SHA-256 от его пути. Значит, id следует за путём. Тот же путь, добавленный снова, находит те же данные и сохраняет
настройки. Репозиторий, перенесённый на другой путь и добавленный снова, — новый Project с настройками по умолчанию, а
старая подпапка остаётся на месте.

Удаление Project-а из списка сохраняет его подпапку и убирает сохранённую камеру. Только удаление Demo project стирает
подпапку Project-а. При старте приложения записи старше 3 дней удаляются из корзины каждого Project-а в списке.

**Файл состояния, который не читается.** JSON-файл состояния, который не разбирается или не подходит под свою схему, не
перезаписывается. Он переименовывается рядом с собой в `<name>.unreadable-<time>`, в консоль идёт предупреждение, и эта
часть worfy начинает с пустого состояния. Данные остаются у пользователя, чтобы посмотреть или восстановить их вручную, а
приложение всё равно запускается. Когда Getting started решает, новый ли пользователь, отложенный так список Project-ов
считается признаком существующего пользователя.

Три файла так не откладываются. Положение окна или отметка First run, которые не читаются, считаются отсутствующими, и
следующая запись их заменяет. Файл с Limits из status line worfy не вправе перемещать: он его только читает.

Чтение, которое не удалось по другой причине, например из-за нехватки прав, бросает ошибку и не считается пустым
состоянием.

#### Windows

Две папки — `%APPDATA%\worfy` и `%APPDATA%\worfy-dev`. Если `APPDATA` нет или это не абсолютный путь, они лежат в
`AppData\Roaming` домашней папки пользователя.

#### On a Linked machine

Machine привязана к своей папке данных, и её идентичность хранится там. Две папки данных на одном компьютере, например
development-сборки и Stable copy, — это две Machine. Layout Project-а остаётся на Machine этого Project-а. Экран на Linked
machine хранит камеру этого Canvas в своей папке, и камера остаётся там, пока Project-а нет в списке этой Machine.

### How it works

- **Состояние отдельно от workflow.** То, что workflow уже записывает, worfy читает и не копирует
  ([ADR-0005](../../adr/0005-worfy-own-state-inventory.md)).
- **Две папки и lock.** Раздельные папки позволяют development-сборке работать рядом со Stable copy, а lock не даёт двум
  packaged-сборкам перезаписывать файлы друг друга ([ADR-0023](../../adr/0023-separate-data-roots-packaged-and-dev.md)).
  Lock — это single-instance lock Electron, он привязан к папке `userData`. Поэтому worfy сначала проверяет папку, потом
  ставит на неё `userData` и только затем берёт lock. Иначе путь, указывающий на файл, закончился бы сообщением «another
  worfy already runs» с exit code 0.
- **Файлы Electron лежат там же.** Настройка `userData` кладёт в папку данных кэши и local storage Electron, а с ними и
  `persist:`-partition каждого Browser profile. Запуск test-а с временным `WORFY_DATA_DIR` не оставляет их в настоящей папке.
- **Запись либо целиком, либо никак.** Запись идёт во временный файл в той же папке, который затем переименовывается поверх
  целевого. Сбой оставляет старый файл или новый. Значение вне схемы бросает ошибку до того, как что-либо записано.
- **Чтение отдаёт разобранное значение.** Ключи, которых нет в схеме, отбрасываются, если схема не свободная. У
  `getting-started.json` она свободная, поэтому старая сборка не теряет то, что записала новая.
- **Вызовы синхронные.** Файлы маленькие, положение окна надо успеть сохранить внутри обработчика `close`, а два синхронных
  цикла чтения и записи не могут перемежаться в одном процессе.
- **Layout и камера ждут тишины.** Они пишутся через 250 мс после последнего изменения, Layout — не позже чем через 1 секунду
  после первого несохранённого, и оба сразу при выходе из приложения.
- **Удаление не идёт по ссылке.** Ссылка по указанному пути или где угодно ниже удаляется как ссылка, а то, куда она ведёт,
  не затрагивается. Это верно, пока дерево не меняет кто-то ещё. Единственное исключение на macOS: путь с разделителем на
  конце читается как папка за ссылкой, и никакой вызов так его не пишет.

#### macOS

`fs.rmSync` с `recursive` удалил бы файлы тома, смонтированного в дереве. Поэтому перед его запуском worfy просматривает всё
дерево, не следуя по ссылкам. Папка на другом томе, чем папка, в которой она лежит, завершает удаление с кодом `EXDEV`, и
ничего не удаляется. Часть дерева, которую нельзя просмотреть, завершает его так же, со своей ошибкой. Точка монтирования с
тем же `dev`, что у папки, в которой она лежит, не видна.

#### Windows

По замерам, под Node из Electron `fs.rmSync` с `recursive` проходит через junction и опустошает папку за ним. Поэтому на
Windows дерево удаляется собственным обходом worfy. Он читает список папки, только когда один `rmdir` ответил, что папка не
пуста, и не читает список папки, про которую знает, что она на другом томе, чем папка, в которой лежит. Запись, которую
нельзя удалить, не останавливает обход: остальные удаляются, а первая ошибка бросается в конце.

Другой процесс, например антивирус или индексатор, может на мгновение занять файл. Поэтому удаление ждёт до 5 раз по 100 мс,
не больше половины секунды на всё удаление. Перемещение файла или папки ждёт теми же шагами, когда встречает `EBUSY`, `EPERM`
или `EACCES`. На macOS перемещение — один вызов.

## Диагностика

### Behaviour

| Что случилось | Где это видно |
|---|---|
| worfy не смог запуститься | Окно ошибки и stderr, затем exit code 1 |
| Завершился renderer-процесс или вспомогательный процесс | Одна строка в log-файле в папке данных |
| Необработанное исключение в main | Stack в stderr, затем окно ошибки Electron |
| worfy перестал отвечать (macOS) | Stack-и потоков в файлах, из скрипта, запущенного вручную |
| Сколько памяти использует worfy | Цифра в toolbar |

Общего log-файла у worfy нет. Вывод консоли идёт в stdout и stderr процесса. Свои файлы ведут два Feature: journal
[Autopilot](autopilot.md) и строки `[link]` из [Link](link.md), которые ротируются на 1 MiB и занимают не больше 4 MiB.

#### Неудачный старт

Заголовок окна — «worfy could not start». В нём четыре части: шаг, который упал, и что этот шаг делал, ошибка, что
попробовать и путь к папке данных. Совет зависит от шага:

| Шаг | Что попробовать |
|---|---|
| Проверка папки данных | Сделать путь папкой, в которую можно писать, или указать на такую папку в `WORFY_DATA_DIR` |
| Загрузка окна с dev-сервера | Проверить, что dev-сервер запущен |
| Загрузка окна из bundle приложения | Bundle может быть неполным: установить заново или пересобрать |
| Любой другой шаг | Похоже на баг сборки: установить заново или пересобрать, и сообщить об ошибке, если она останется |

Тот же текст идёт в stderr, за ним stack ошибки. Затем worfy завершается с кодом 1. Окно открывает только первая ошибка,
следующая идёт только в stderr. `WORFY_STARTUP_DIALOG=off` пропускает окно, потому что e2e test не может закрыть нативное
окно.

Шаги — это проверка папки данных, запись о завершившихся процессах, меню, обработчики IPC, web policy, runtime Card-ов,
протокол изображений, Orchestrator-ы, уведомления, первое окно и загрузка его страницы. Ошибка вне именованного шага,
дошедшая до старта, всё равно открывает окно, и оно тогда пишет «An unexpected step of the start failed.»

Некоторые части старта сами ловят свои ошибки, и worfy работает без них: связь с другими Machine, автоматический архив,
Getting started, обновление Limits и иконка в Dock у development-сборки. Их ошибка — это строка в консоли.

Страница, которая не загрузилась в окне, открытом позже, из иконки в Dock или вторым стартом, только попадает в log. Первое
окно, закрытое во время загрузки, или загрузка, заменённая более новой навигацией, — это не ошибка.

#### Завершившийся процесс

Когда завершается renderer-процесс или вспомогательный процесс (GPU, utility), worfy дописывает одну строку JSON в
`process-gone.jsonl` в папке `logs` внутри папки данных:

```json
{"time":"2026-10-10T12:00:00.000Z","process":"renderer","reason":"crashed","exitCode":11}
{"time":"2026-10-10T12:00:05.000Z","process":"Utility","reason":"oom","exitCode":-1,"service":"network.mojom.NetworkService"}
```

В строке время, вид процесса, причина, exit code и service, если Electron его называет. В ней нет URL, пути и ничего от
Session. В текстовом значении каждый символ, кроме буквы, цифры, пробела, `.`, `_` или `-`, становится `?`, а значение
обрезается до 80 символов. Значение, которое не текст, — это `unknown`, а exit code, который не целое число, — `null`.

Это только запись: worfy ничего не показывает и не открывает окно заново. Файл появляется с первым событием и не обрезается.
Строка, которую нельзя записать, идёт в `console.error`.

#### Необработанное исключение

Необработанное исключение в main пишет в stderr `[worfy] uncaught exception in main (<origin>): <stack>`. Затем окно ошибки
Electron появляется как обычно и блокирует главный поток, пока по нему не щёлкнут.

#### Stack-и зависшего приложения (macOS)

Скрипт сохраняет stack-и потоков packaged-сборки worfy, которая перестала отвечать, не останавливая её. Его аргументы — pid
главного процесса и, по желанию, сколько секунд снимать: от 1 до 60, по умолчанию 3. Stack-и нативные, без кадров JavaScript.
По ним видно, ожидание ли это I/O или системного окна, или занятый цикл.

Он снимает одновременно главный процесс и тех его прямых потомков, чей настоящий путь лежит внутри того же `.app`. Он печатает
по строке на процесс:

```text
sampled: <pid> <kind> <file>
skipped: <pid> <path>
failed: <pid> <kind>: <why>
```

`kind` — это `main`, `--type=` вспомогательного процесса, например `renderer`, или имя исполняемого файла. Потомок вне `.app`,
например shell Terminal-а, пропускается, а уже завершившийся потомок — это `skipped: <pid> (ended)`. `failed` идёт в stderr.
Аргументы процесса могут содержать токен, поэтому они читаются только ради `--type=` и никогда не печатаются.

Exit code равен 0, когда каждый `sample` вернул 0, иначе первому ненулевому коду `sample`, и 1, когда `sample` не удалось
запустить или не удалось создать папку. Код 2 без записанных файлов означает неверные аргументы, систему не macOS или pid, который
не является главным процессом packaged-сборки worfy, например вспомогательный процесс, shell или development-сборка.

Файлы — `hang-<time>-<pid>.txt` в папке `logs` внутри папки данных packaged-сборки. Скрипт читает `WORFY_DATA_DIR` из своего
окружения, а не из процесса, который снимает.

#### Цифра памяти

Toolbar показывает, сколько памяти используют процессы самого worfy, на второй строке колонки Harness, после версии приложения.
Цифра выглядит как «412 MB» ниже 1024 MB, как «1.3 GB» от этого значения и как «…» до первого замера. Её tooltip даёт разбивку:

```text
Memory used by worfy's own processes (not counting terminal sessions)
Main 180 MB · Windows 200 MB · GPU 20 MB · Other 12 MB
```

Цифра — сумма working set процессов Electron, новый замер приходит каждые 5 секунд. Неудачное чтение оставляет последнее значение,
с одним предупреждением, пока чтение снова не удастся.

«Memory in the toolbar» в Settings → General выключает её сразу во всех открытых окнах и без перезагрузки. По умолчанию она включена,
в том числе с файлом настроек, записанным до появления этой настройки. Пока она выключена, замеров нет.

#### Windows

Скрипт для зависшего приложения отказывает с кодом 2, потому что запускает программу `sample` из macOS. В коде остальной диагностики
на этой странице нет ветвления по системе, а её файлы идут в папку данных Windows.

#### On a Linked machine

Цифра памяти всегда относится к Machine самого экрана: её каналы — `local`, и Linked machine до них не дотягивается. Каждая Machine
пишет свои `process-gone.jsonl` и `link.log`, и никакой канал IPC их не читает.

### How it works

- **В запись идёт только то, что не может утечь.** Строка о завершившемся процессе собирается по полям, поэтому ничего, что Electron
  добавит позже, не попадёт в файл. URL окна не попадает туда, потому что в packaged-приложении это путь внутри домашней папки
  пользователя.
- **Monitor, а не обработчик.** Electron показывает своё окно, только пока его собственный слушатель `uncaughtException` единственный.
  Поэтому worfy слушает `uncaughtExceptionMonitor`, который не меняет того, что приложение делает дальше. Он пишет в файловый дескриптор
  2 синхронно, потому что вывод, ещё стоящий в очереди в pipe, никогда не покинет процесс, заблокированный этим окном.
- **Неудачный старт вызывает `app.exit(1)`.** У `app.quit()` нет exit code, а его обработчики `before-quit` и `will-quit` написаны для
  приложения, которое запустилось. До `ready` выход сразу. После `ready` он идёт на следующем обороте цикла событий, потому что на Windows
  выход из callback-а `ready` оставлял работающим сетевой utility-процесс.
- **Каждый шаг идёт в `inStep`.** Throw или rejection выходит как `StartupError` с именем шага, а вложенный шаг сохраняет своё имя.
- **Sampler работает, только когда кто-то смотрит.** Timer есть, только пока настройка включена и хотя бы одно окно открыло цифру. Окно,
  открывшее цифру при остановленном sampler, сразу получает замер. Открытия каждого окна считаются. Они сбрасываются, когда окно уничтожено
  или в его главном фрейме закоммичен новый документ, потому что перезагружающаяся страница не шлёт закрытие.

### Implementation

| Модуль | Что делает |
|---|---|
| `src/main/startup-failure.ts` | Шаги с советами, `inStep`, `reportStartupFailure` и текст окна. |
| `src/main/index.ts` | Порядок старта и какие части считаются шагами. |
| `src/main/window.ts` | Сообщает о неудачной загрузке страницы первого окна как о шаге `loadURL` или `loadFile`. |
| `src/main/diagnostics/process-gone.ts` | `installProcessGone` подписывается на `render-process-gone` и `child-process-gone`, как первый шаг после `ready`. |
| `src/main/diagnostics/uncaught-stderr.ts` | `reportUncaughtToStderr`, первая инструкция `src/main/index.ts` после импортов. |
| `src/main/diagnostics/memory.ts` | `MemorySampler` поверх `app.getAppMetrics()`, следует за настройкой `memoryIndicator`. |
| `src/shared/memory.ts` | Сумма по видам процессов, формат и tooltip. Чистый модуль. |
| `src/shared/ipc/memory.ts`, `src/main/ipc/memory.ts` | Каналы `memory.open`, `memory.close` и `memory.changed` и счёт открытий на окно. |
| `src/renderer/memory/AppMemory.tsx`, `src/renderer/memory/useAppMemory.ts` | Цифра и её подписка. |
| `scripts/hang-sample.mjs` | Stack-и: `node scripts/hang-sample.mjs <pid> [seconds]`. |

Виды в разбивке памяти идут от типов процессов Electron: `Browser` — это Main, `Tab` — Windows, `GPU` — GPU, а любой другой тип — Other.

#### e2e test-ы

Этой части в приложении нет. Когда первое окно старта в e2e test-е не показано, `test/e2e/start-diagnostics-run.ts` спрашивает у приложения
состояние его окна, `readyState` страницы и снимок страницы. Он сохраняет последние 256 KB вывода приложения, копирует файлы папки `logs` и
прикрепляет всё это к test-у. Каждому шагу, который спрашивает приложение, даётся не больше 3 секунд. Чистые части — в
`test/e2e/start-diagnosis.ts`.
