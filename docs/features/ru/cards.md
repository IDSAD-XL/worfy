# Cards

> Перевод [английской версии](../cards.md), commit `same-pr`.

Card — это небольшое HTML-приложение, которое собирает агент и которое работает внутри Node на Canvas. На странице три
раздела: Card как файл описывает саму Card, Card API — вызовы `window.worfy` на странице Card, а Canvas MCP — tools, которыми
агент создаёт Card и заметки и меняет Canvas. Термины объяснены в [Concepts](concepts.md).

## Card как файл

### Behaviour

**Откуда берётся Card.** Агент создаёт Card через tool `create_card`, а затем пишет её файлы своими обычными tools для
файлов. В меню Canvas нет пункта для новой Card. Card принадлежит Project: менять её может любая Session этого Project.
Card — это папка с `index.html` и любыми другими нужными ей файлами. Сборки нет: файлы запускаются как есть.

**Что показывает Node.** В шапке — текст `<title>` из `index.html` или `Card`, если его нет. Длинный заголовок обрезается
многоточием «…», а целиком виден в tooltip. Содержимое Node зависит от состояния Card:

| Состояние | Что в содержимом Node |
|---|---|
| Папки Card нет | Текст `Card files missing` |
| Папка есть, zoom 0.4 или больше | Работающая страница |
| Папка есть, zoom меньше 0.4 | Заголовок в пунктирной рамке; страница не работает |

Закреплённая Card (pinned) и Card в плитке focus mode работают при любом zoom. На Canvas Card, чей Node вне экрана, не
работает, потому что Node-ы вне экрана не рисуются. Папка без `index.html` считается существующей: в её frame виден простой
ответ `Not found`.

**Перезагрузка.** Когда файл Card записан или удалён, Node перезагружает страницу в течение секунды. Серия записей
перезагружает её один раз, после 100 мс тишины. При перезагрузке загружается новый документ, поэтому всё, что страница
держит только в памяти, теряется. Данные, сохранённые через Card API, остаются.

**Мышь.** На Canvas страница Card принимает мышь, только пока её Node активен. До этого колёсико над Card двигает Canvas, а
первый клик активирует Card и до страницы не доходит. Пока Node перетаскивают или меняют его размер, а также пока двигают
Canvas, ни одна Card мышь не принимает. Card перетаскивают за заголовок, а вручную уменьшить можно до 160 × 100. Пунктирную
рамку, которая видна при zoom меньше 0.4, можно тащить и за содержимое: страницы в ней нет. Плитка focus mode рисуется вне
Canvas, поэтому её страница принимает мышь сразу.

**Что странице можно:**

- Запускать скрипты и стили из своих файлов и inline.
- Загружать изображения и шрифты из своих файлов, из `data:` и по https.
- Отправлять сетевые запросы только на адреса https. Это правило запрещает и `fetch` собственных файлов Card.
- Переходить на другие файлы своей Card.
- Пользоваться `localStorage` на своём origin, который не делит ни с одной другой Card.
- Пользоваться Card API, у него свой раздел.

**Чего странице нельзя:**

- Обращаться к окну worfy, другой Card или `file://`.
- Открывать окно, переводить окно worfy на другой адрес или уводить свой frame за пределы своей Card.
- Использовать frame-ы, формы, плагины и `<base>`.
- Получать web-разрешения: камеру, микрофон, уведомления и другие.
- Отдавать файл с другим расширением или файл вне своей папки. На такой запрос приходит 404. Отдаются HTML, CSS, JavaScript,
  JSON, простой текст, SVG и распространённые форматы изображений, шрифтов, аудио и видео.

**Find.** Поиск по Canvas читает и видимый текст Card, до 100 000 символов. Ответить может только Card с работающей страницей,
и на это у неё есть 2 секунды.

**Удаление.** Пользователь может удалить Node с Card. Её папка и данные переходят в корзину Project, хранятся там 3 дня, и их
можно восстановить. Они остаются на месте, если ту же Card ещё показывает другой Node. Агенты удалить Node не могут.

#### На Linked machine

Окно может показывать Card из Project на Linked machine. Её файлы находятся на Machine этого Project. Изменение файла на
Machine этого Project перезагружает Card в окне.

- На файл больше 20 МБ приходит ответ 413.
- Если Linked machine недоступна, приходит ответ 502.

### How it works

**Файлы, а не API.** Агент пишет Card теми tools для файлов, которые у него уже есть, а worfy их только читает
([ADR-0003](../../adr/0003-cards-as-files-canvas-via-tools.md)). Файлы и сохранённые данные лежат в папке данных Project, поэтому в
репозиторий Project они не попадают ([ADR-0005](../../adr/0005-worfy-own-state-inventory.md)). Это папка
`<Project data folder>/cards/<id>/` и файл `<Project data folder>/card-data/<id>.json`. См.
[Storage и диагностика](storage-and-diagnostics.md).

**Отдельный origin для каждой Card.** Card — это код, который написал агент, поэтому она изолирована от приложения
([ADR-0012](../../adr/0012-card-origin-worfy-card-scheme.md)). Её адрес — `worfy-card://<card id>.<project label>/<path>`, где метка —
8 hex-символов в конце id Project. Приложение регистрирует эту схему как standard и secure, поэтому каждый host — отдельный
origin. У iframe стоит `sandbox="allow-scripts allow-same-origin"`. «Same origin» здесь означает собственный origin Card и
никогда — origin окна. На адрес, метка которого не совпадает ни с одним Project или совпадает с несколькими, приходит 404.

**Три отдельные проверки.** Протокол отдаёт только файлы Card и на каждый ответ ставит одни и те же заголовки:
Content-Security-Policy, `nosniff` и `no-store`. Main process решает, куда может перейти frame, и отказывает в новых окнах и
web-разрешениях. Окно worfy принимает сообщение Card только от frame этой Card и только с origin этого frame. Любое другое
сообщение оно отбрасывает без ответа. Эти сообщения описаны в разделе Card API.

**Перезагрузка идёт от номера ревизии.** Main process следит за Card-ами Project с первого запроса к одной из них и до момента,
когда Project уходит из списка. Каждое изменение увеличивает ревизию Card, которая хранится только в памяти. На каждую новую
ревизию Node создаёт новый iframe, и более поздняя ревизия всегда побеждает более ранний ответ.

**У Card на Linked machine свой origin.** В её host появляется третья часть — id Machine без дефисов:
`worfy-card://<card id>.<project label>.<machine label>/<path>`. Поэтому её origin отличается от origin любой Card этой Machine,
даже с теми же id и меткой. Machine этого Project находит и проверяет файл так же, как для своих frame-ов, и отправляет его
частями не больше 4 МБ.

#### Windows

На Windows системный вызов, идущий по ссылке на `\\host\share\…`, заставляет систему обратиться к этому host с учётными данными
пользователя. Поэтому ссылки на пути к Card сначала читаются без перехода по ним:

- Card, папка которой ведёт на share, считается отсутствующей. У Card, `index.html` которой ведёт туда, нет заголовка.
- Файл за такой ссылкой не отдаётся.
- За папкой Cards, которая ведёт на share, слежения нет. Ссылка внутри Card, которая ведёт туда, остаётся без внимания, а
  за остальными Card-ами слежение идёт как обычно. По ссылке на папку или файл этой машины переход по-прежнему есть.

Само слежение тоже другое. Оно использует один рекурсивный handle вместо chokidar и не создаёт папку Cards, а ждёт, пока она
появится. Ссылки ищутся вплоть до папок прямо внутри Card. Когда Windows сообщает о потерянных событиях, заново читается каждая
Card этого Project, которую уже запрашивали. Файлы подкачки и резервные копии редактора изменением не считаются.

## Card API

### Behaviour

На каждой HTML-странице Card есть `window.worfy`, и страница не может его подменить. Каждый вызов, кроме
`worfy.workflow.subscribe`, возвращает Promise, а отказ отклоняет его с указанием причины. `worfy.workflow.subscribe` сразу
возвращает функцию, которая останавливает подписку, а неудача подписки только пишется в console страницы.

| Вызов | Что делает |
|---|---|
| `worfy.data.get()` | Отдаёт сохранённое значение JSON этой Card или `null` до первого сохранения |
| `worfy.data.set(value)` | Заменяет это значение. Предел — 1 МБ компактного JSON. Значение переживает перезапуск |
| `worfy.ask(text)` | Просит пользователя отправить до 10 000 символов в Session |
| `worfy.workflow.get()` | Отдаёт снимок workflow Project только для чтения |
| `worfy.workflow.subscribe(listener)` | Вызывает `listener` со снимком сейчас и при каждом изменении, возвращает функцию, которая это останавливает |

Изменить workflow Card не может: такого вызова в API нет. Снимок перечисляет Epic-и и Ticket-ы. Для каждого Ticket-а в нём
есть состояние, blockers, Wave, результат Gate, PR и CI. Поле `error` говорит, почему workflow не удалось прочитать. На первое
чтение workflow отводится 15 секунд. После этого `worfy.workflow.get` отклоняет свой Promise, а `worfy.workflow.subscribe` пишет
ошибку в console.

**Сообщения в Session.** `worfy.ask` открывает диалог с заголовком `Message from a Card` и кнопками `Send` и `Cancel`. Диалог
называет Card и получателя и показывает точный текст. Без `Send` ничего не отправляется. Результат — `{sent: true}` или
`{sent: false, canceled: true}` при любом другом ответе.

- **Получатель** — Session, которая последней правила Card, если она работает в worfy. Иначе это Orchestrator Project: worfy
  открывает его, если он не запущен. Выбрать получателя Card не может.
- **Сообщение** приходит как `Message from Card "<title>" (<id>):`, затем пустая строка и текст. Без заголовка вместо него
  стоит id.
- **Один вопрос на Card.** Пока первый вопрос ждёт, второй `worfy.ask` получает отказ. Вопрос перестаёт ждать, когда на него
  ответили, когда исчезло окно, которое его задало, или через 10 минут.
- **Получатель без человека.** За Session, которую ведёт Autopilot, на диалог отвечать некому. Вызов получает отказ без
  диалога, и ничего не отправляется. Та же проверка повторяется после `Send` на случай, если Session за это время стала такой.

#### На Linked machine

Сохранённые данные Card на Linked machine и Session, получающая её сообщения, находятся на Machine этого Project. Диалог
`worfy.ask` появляется на Machine окна. На экране только для чтения `worfy.data.set` и `worfy.ask` сразу завершаются ошибкой
с подсказкой о режиме чтения. Чтение продолжает работать.

### How it works

**Card API — это сообщения.** У Card нет Node.js и IPC. С родительским окном она общается через `postMessage`
([ADR-0015](../../adr/0015-card-api-window-worfy-postmessage.md)). Протокол вставляет небольшой скрипт с `window.worfy` в начало `<head>`
каждого отдаваемого HTML-файла, поэтому он выполняется раньше скриптов самой Card. Файл на диске не меняется. Card на Linked
machine приходит с Machine этого Project без этого скрипта, и Machine окна добавляет свой. Окно проверяет
каждый запрос по схеме и передаёт дальше только разобранный запрос. Сохранённые данные и сообщения идут в main process через
IPC. Снимок workflow окно строит из того, что уже читает, и начинает читать только после первого запроса Card. Подписанная Card
узнаёт только о настоящем изменении. worfy не владеет workflow, поэтому Card его только читает
([ADR-0002](../../adr/0002-worfy-is-a-view-over-the-workflow.md)).

**Последний редактор определяется по вызовам tools.** У Session, подключённой к Project, main process следит за вызовами
`Write`, `Edit`, `MultiEdit` и `NotebookEdit`, которые обращаются к папке Card-ов этого Project. Вызов, который называет файл
внутри папки Card, делает эту Session последним редактором Card, что бы агент ни говорил о себе. За Session вне Project и за
Session, у которой не запустился canvas, main process не следит. Изменение через Bash не считается. Значение хранится в данных
Node этой Card, поэтому переживает перезапуск. Пути сравниваются как текст, по symlink-ам проверка не идёт.

**Сообщение идёт в три шага.** Machine этого Project выбирает получателя и держит вопрос в ожидании. Machine окна показывает
диалог. Затем Machine этого Project отправляет сообщение или не отправляет. Диалог принадлежит экрану, который задал вопрос
([ADR-0053](../../adr/0053-several-screens-on-one-project.md)). Завершить вопрос может только окно, которое его задало. Отказ для Session
без человека также приходит подписчикам этой Session как событие `refused_dialog`, и его записывает журнал Autopilot. Сообщение,
которое пользователь отправляет в Session запуска Autopilot, записывается там как действие человека.

#### Windows

`/c/Users/…` читается как диск C:.

## Canvas MCP

### Behaviour

**Кто получает tools.** Session, которую worfy запускает в Project, получает MCP server `worfy-canvas`. Ещё она получает папку Cards
этого Project как дополнительную папку для записи и короткую инструкцию в system prompt. Server — это способ агента менять
Canvas, и он шире Card: он ещё создаёт заметки, а также перемещает, меняет размер и скрывает другие Node-ы.

- Session получает server, только если он есть в списке Profile этого Project. В списке по умолчанию он есть.
- Session, рабочая папка которой не входит ни в один Project, работает без этих tools. Так же работает Session, у которой не
  запустился canvas.
- Черновая Session, которую worfy запускает при подключении Project, не получает ни одного MCP server.

**Tools:**

| Tool | Что делает |
|---|---|
| `list_nodes` | Перечисляет Node-ы, включая скрытые: id, kind, title, положение, размер, hidden и locked |
| `create_card` | Создаёт папку Card и её Node, в ответе — Node, папка и путь к `index.html` |
| `create_note` | Создаёт Node с заметкой, до 20 000 символов текста |
| `update_node` | Меняет заголовок Card или текст заметки |
| `move_node` | Перемещает Node |
| `resize_node` | Меняет размер Node |
| `hide_node` | Скрывает Node или, с `hidden=false`, показывает его снова |
| `link_card` | Связывает Card с Epic (`<epic>`) или Ticket (`<epic>/<NN>`), либо снимает связь при `remove=true` |

**Пределы.**

- Размеры — от 40 до 4000, координаты — в пределах ±100 000, в единицах Canvas.
- Новая Card — 360 × 280, новая заметка — 220 × 120, если вызов не задаёт размер.
- Id Card создаёт сам tool: `card-` и 8 hex-символов.
- Tool для удаления Node нет.

**Размещение.** Без координат новый Node встаёт справа от Node вызвавшей Session и опускается вниз, пока не перестанет задевать
другие Node-ы. Если такого Node нет, он встаёт справа от всего видимого. Node-ы не перекрываются: занятое место или место ближе
16 px к другому Node заменяется ближайшим свободным. Край при изменении размера останавливается за 16 px до другого Node. Другие
Node-ы не двигаются, а в ответе стоят настоящие положение и размер ([ADR-0038](../../adr/0038-nodes-never-overlap.md)).

**Чего tools не трогают.** Рамки Epic, Ticket-ы и Subagent-ы расставляет worfy, поэтому tools их не перечисляют и не меняют.
Архивированных Node-ов на Canvas нет: tools их не перечисляют, а вызов с таким Node получает отказ, пока пользователь его не
вернёт. Остальные Node-ы можно перемещать, менять их размер и скрывать, только Node с `locked`, например Orchestrator, скрыть нельзя.
`update_node` работает только с Card и заметками. Перед скрытием Node с Session страницы её Browser-ов получают вопрос о несохранённых
изменениях.

**Отказы.** Отказ — это ошибка tool с сообщением, которое агент может прочитать. Вызов с Node другого Project получает отказ как
вызов с неизвестным Node. Если изменение Layout в `create_card` не удалось, новая папка удаляется.

**У заголовка Card два источника.** Заголовок из `create_card` или `update_node` хранится в Layout. Его показывают `list_nodes`,
Command palette, Find и заголовок плитки focus mode. Шапка Node показывает `<title>` из `index.html`, поэтому агент, которому нужно изменить шапку, правит этот файл.

**Связи.** `link_card` проверяет, что Epic или Ticket существует, если только связь не снимается. Повторная связь не создаёт вторую.
Связи хранятся в данных Node этой Card, и сейчас их читает только сам `link_card`: Canvas для них ничего не рисует.

### How it works

**Файлы для содержимого, tools для Canvas.** У Layout один источник записи — main process, поэтому изменение от агента идёт тем же
путём и через те же проверки, что и изменение от пользователя ([ADR-0003](../../adr/0003-cards-as-files-canvas-via-tools.md)). Набор
tools — это контракт между агентом и приложением, и он меняется вместе с инструкцией агенту.

**Один server на Session.** Server работает в процессе worfy и привязан к одному Project. Project определяется по рабочей папке
Session: самый глубокий Project, содержащий её, причём пути сравниваются в написании на диске. Связанный git worktree вне корня
Project находится через git. Собственный id Session берётся из её сообщений и решает, рядом с каким Node встанет новый. Возобновлённая
Session начинает со своего resume id, а первое сообщение каждого хода может его заменить.

**Только server-ы из списка.** Каждый tool расходует контекст в каждом ходе, поэтому Session в Project получает только MCP server-ы из
списка своего Profile ([ADR-0021](../../adr/0021-mcp-servers-allowlist-in-profile.md)). Папка Cards остаётся доступной для записи, даже
если `worfy-canvas` в списке нет.

**Аргументы проверяются дважды.** MCP server проверяет их по схеме tool, а обработчик снова разбирает по той же схеме. Ключи, которых
tool не объявляет, до Layout не доходят.

#### Windows

Когда папка Cards ведёт на share или ссылки на пути к ней нельзя проверить, `create_card` получает отказ с сообщением, и папка не
создаётся. Рабочая папка в коротком написании 8.3 от корня Project всё равно находит этот Project.

### Implementation

| Модуль | Что в нём |
|---|---|
| `src/shared/canvas/tools.ts` | Имена tools, схемы, описания, пределы и размещение по умолчанию |
| `src/main/mcp/canvas-server.ts` | Обработчики, server, Project для Session и запись последнего редактора |
| `src/main/mcp/agent-instructions.md` | Текст, добавляемый в system prompt; в нём названа папка Cards |
| `src/main/agent/options.ts` | Передаёт server, папку Cards и инструкцию в Claude Code |
| `src/main/agent/app-registry.ts` | Определяет canvas при старте Session |
| `src/main/workflow/profile.ts` | Список MCP server-ов в Profile и список по умолчанию |
| `src/main/layout/store.ts` | `LayoutStore`, через который проходит каждое изменение Layout |
| `src/shared/layout/free-place.ts` | Ближайшее свободное место и зазор 16 px |

В той же папке лежит server `worfy-browser`, он описан на странице [Browser](browser.md).

**Поток данных `create_card`.** Агент вызывает tool. `canvasToolCaller` в `src/main/mcp/canvas-server.ts` разбирает аргументы. Обработчик
выбирает свободный id, создаёт папку и применяет к Layout операцию `create`. Renderer рисует новый Node и запрашивает его Card через
`cards.get`, отчего начинается слежение. Затем агент пишет `index.html`. Изменение файла перезагружает Node, а вызов tool этой Session
делает её последним редактором Card.

**Главные test-ы:**

- `test/contract/canvas-tools.test.ts`: каждый tool, отказы, Node-ы вне действия tools, параллельные изменения, Project для Session и
  то, что в репозиторий Project ничего не пишется.
- `test/unit/agent-options.test.ts`: какие server-ы Session получает по списку Profile.
- `test/contract/card-last-editor.test.ts`: запись последнего редактора на fake agent.
