# Pull requests

> Перевод [английской версии](../pr-inbox.md), commit `5d1efe69`.

**PR inbox** Project-а: открытые pull request-ы (PR) пользователя и запросы ревью у него в репозиториях Project-а,
сгруппированные по тому, чей ход, с нитями ревью и их последними комментариями. В UI — **Pull requests**. Он читает
GitHub. Единственное, что он вообще публикует, — ответ, который Session написала skill-ом `pr-reply`: пользователь может
его поправить, и уходит он только по щелчку пользователя на **Send**. Больше ничего он там не закрывает, не запрашивает,
не ревьюит и не помечает
([ADR-0105](../../adr/0105-pr-reply-only-on-the-users-click.md)). Термины — в [Concepts](concepts.md); badge-и PR и CI
у Ticket-а — на странице [Gate и GitHub](gate-and-github.md).

## Вид Pull requests

### Поведение

**Где открывается.**

- **Pull requests** в View switch toolbar-а — пятая вкладка после Canvas, Session, Pipeline и Runs. Без Project-а
  вкладка неактивна, tooltip говорит открыть Project.
- Строка **Pull requests** в Command palette, группа View, при открытом Project-е.
- Группа в разделе **Pull requests** sidebar-а: вид Project-а этой строки, прокрученный к этой группе, её заголовок
  выделен, её первый PR выбран (увиденным не помечается). Строка другого Project-а сначала выбирает этот Project.
- Щелчок по системному уведомлению о новом запросе ревью или новом ответе открывает вид на этом PR; **Open** в morning
  digest тоже открывает его: см. [Notifications](notifications.md).

Вид принадлежит активному Project-у. У другого Project-а — свой inbox и свой выбор.

**Две панели.** Слева — компактный список PR по группам, справа — выбранный PR целиком. В окне, где под вид остаётся
уже примерно 720 px, список стоит над PR, и каждая часть прокручивается сама.

**Группы.** Пять, всегда в этом порядке, у заголовка каждой — счётчик. Список показывает только группы, где есть PR.

| Группа | Что в ней |
|---|---|
| Needs my review | Ревью просят у пользователя — лично или через команду — или просят снова после его ревью |
| Needs my answer | Нерешённая нить, последний комментарий которой не пользователя, — на его PR или в нити, где он писал; упоминание пользователя новее его последнего комментария там |
| Needs a fix | PR пользователя с красным CI, запрошенными правками или конфликтом merge |
| Ready | PR пользователя одобрен, зелёный, без конфликта. Вливают люди: группа — напоминание тому, кто вливает |
| Waiting on others | PR пользователя, хода пользователя нет |

Группу и порядок внутри неё решает main: Needs my review — сначала старые PR, остальные — сначала старая активность.
PR без Ticket-а — такая же строка, как остальные.

**Строка списка.** Аватар автора (две буквы login-а на своём цвете; у самого пользователя — с кольцом), заголовок, под
ним имя репозитория и номер (`web#41`; весь `owner/repo#N` — tooltip; длинное имя обрезается многоточием, номер остаётся
целым, и список никогда не прокручивается вбок), chip Ticket-а (`<epic> <NN>`), если PR — Ticket-а,
и точка CI — с текстом рядом, когда CI не зелёный. Когда строке не хватает места, первым уступает имя репозитория, потом
имя Epic-а в chip-е Ticket-а (обрезается многоточием; его номер остаётся целым, а `<epic> <NN> — <title>` — tooltip
chip-а). `#N` и текст CI остаются целыми, и ничто не рисуется поверх другого. Справа: возраст, число открытых нитей со
значком реплики (оранжевое на PR самого пользователя, где ждут его; tooltip — «2 open threads») и синяя точка, когда есть
новые комментарии (tooltip — «N new since you looked»).

- **Заголовок**: обрезается многоточием, когда не помещается; весь заголовок — его tooltip.
- **Точка CI**: зелёная — проходит, оранжевая — упал, пустое синее кольцо — идёт, пустое серое кольцо — CI нет. Её текст —
  tooltip.
- **Возраст**: у Needs my review — возраст PR; в остальных — его последнего комментария или ревью. В tooltip — время.
  Цвет говорит, сколько PR ждёт: серый — меньше 12 часов, светлее — меньше 3 дней, оранжевый — меньше 14 дней, красный —
  дольше.
- **Chip Ticket-а**: Ticket, чья строка `PR:` называет этот PR, иначе Ticket, чья ветка — ветка PR (его строка `Branch:`
  или `<epic>/<NN>`). Номер считается только в своём репозитории: `PR: lib#41` называет #41 репозитория с именем `lib`
  (или `owner/lib`), а голый `PR: #41` — #41 репозиториев из строк `Repo:` Ticket-а; любого репозитория — только когда
  строки `Repo:` у Ticket-а нет.
- **N new since you looked**: комментарии других новее последнего взгляда пользователя на PR.

**Выбор.** Щелчок по строке выбирает её PR; **↑** и **↓** двигают выбор по списку — откуда угодно в показанном виде,
кроме текстового поля, меню и диалога, — и останавливаются на его концах. Пока пользователь не выбрал, вид сам выбирает
первый PR, который ждёт ответа пользователя, иначе первый в списке. Этот выбор делается один раз и держится: новый поиск,
который переставил группы, не уводит панель с PR и с черновика, который там набирают. Вид выбирает снова, только когда
выбранный PR ушёл из inbox. Если PR один, выбран он, и подсказки «↑ ↓ next PR» в панели нет.

**Выбранный PR.** Правая панель показывает:

- заголовок, `owner/repo#N`, chip Ticket-а, `Draft` у черновика PR, «via team», если ревью просят только у команды
  пользователя, автора, ветку и «N new since you looked»;
- **что делать дальше** — одна плашка в цвете группы PR, по группе, CI, ревью и черновикам, с главной кнопкой: «Your
  review is asked» с **Start review** (вкладка Files на GitHub); «Answer N open threads» — с **Send all (N)**, когда ниже
  готовы два черновика ответов или больше (открывает диалог Send all, см. ниже), с **Draft replies**, когда черновиков
  ещё нет, и без кнопки при одном черновике — его **Send** стоит под его нитью; «CI failing», «Changes requested»,
  «Merge conflict» или несколько из них («Merge conflict and CI failing») с кнопками причин PR и **Open checks**; «Ready
  to merge» с **Open to merge**; «Waiting for reviewers» или «Draft PR: no review asked yet». В светлой теме Needs my
  review — синяя, Needs my answer — фиолетовая (в тёмной — лаймовая);
- **кнопки PR, который надо исправить**: **Resolve conflicts** при конфликте merge (`DIRTY`), **Fix checks** при красном
  CI, **Address comments** при запрошенных правках или нитях, которые ждут ответа пользователя, — в этом порядке: PR с
  конфликтом CI не запускает. Первая причина — главная кнопка плашки, и строка плашки говорит, что эта кнопка делает
  (`Fix checks hands the failing checks to a Session; it asks before it pushes.`); остальные причины — кнопки рядом с
  ней; **Open checks** остаётся ссылкой на вкладку Checks на GitHub, после них. У собственного PR пользователя в Needs my
  answer эти кнопки стоят рядом с **Draft replies**, обычно только **Address comments**; у PR коллеги их нет. Щелчок
  передаёт PR в Session skill-а pr-fix с шаблоном Project-а: в Session Ticket-а этого PR, если она жива, иначе в новый
  Session Node (шаблоны, маршрут и каждый отказ описаны в [Projects](projects.md), «Project settings…»). Короткий toast
  говорит, куда ушёл текст: `Fix checks for owner/web#118: Sent to the Session of worfy-x 07`, `… Queued for the Session
  of …`, пока идёт ход этой Session, или `… Started a Session`; отказ main — toast ошибки с причиной. Кнопка, которая не
  может запуститься, неактивна, и её tooltip говорит почему: пустой шаблон (`Set the Fix checks template in Project
  settings`), экран только для чтения, PR из fork-а, PR не пользователя или PR, у которого причины больше нет. Кнопки
  ничего не пишут на GitHub: Session спрашивает, прежде чем push-ить;
- четыре ячейки: **CI**; **Review** (Approved, Changes requested, Review required или None yet); **Merge** (Mergeable,
  Behind the base, Blocked, Checks failing, Conflicts, Draft или Unknown — по состоянию merge на GitHub); **Size** —
  добавленные и удалённые строки (`+184 −22`) с полосой их долей, или `—`, если GitHub их не дал;
- **Open on GitHub**; **Code story** — открывает Code story Ticket-а этого PR в Story view, когда она есть в Tickets
  root, а иначе собирает story PR по кнопке, с полосой прогресса на её месте, или открывает сохранённую раньше;
  **Rebuild story**, когда story сохранена ([Workflow](workflow.md)); **Draft replies** (см. ниже; в плашке вместо этого
  места, когда она — кнопка плашки) и **Mark seen** — активна, пока у PR есть новые комментарии;
- «Threads N open · M resolved», затем нити ревью — сначала открытые, потом решённые, приглушённые. У каждой — файл и
  строка, ссылка на комментарий на GitHub (там видна эта строка кода), `Outdated`, если код ушёл вперёд, и её последние
  три комментария с автором и возрастом. Удалённый аккаунт — `ghost`, как на GitHub;
- **Conversation**: последние комментарии вкладки разговора PR, если они есть.

Комментарий читается так же, как на GitHub: его текст — GitHub-flavoured markdown — жирный, курсив, зачёркнутый, inline
code, списки (вложенные и нумерованные), цитаты, блоки кода (без подсветки синтаксиса), таблицы, списки задач (только для
чтения), заголовки по размеру комментария и горизонтальные линии; одиночный перевод строки — разрыв строки, как в
комментарии GitHub. Блок ```` ```suggestion ```` показывается под меткой «Suggested change», его строки — как добавленные
строки; пустой говорит «Delete the lines». `@login` и `@org/team` — ссылки на человека или команду на GitHub, `#123` —
ссылка на этот issue или PR репозитория PR, `owner/name#123` — того репозитория; в коде они остаются текстом.
HTML-комментарий `<!-- … -->` скрыт, как на GitHub. Любой другой HTML показывается текстом и никогда не исполняется:
`<details>` или `<sub>` GitHub-а читаются как свои теги. Изображение не загружается: оно показывается ссылкой со своим alt
text, которая открывает изображение в браузере. Так же читаются комментарии, на которые отвечает черновик ответа, и текст
отправленного ответа; поле черновика держит его текст как написан.

Выбор PR — щелчок, **↑** или **↓**, вход, который называет PR, — и **Mark seen** записывают, что пользователь посмотрел:
«N new since you looked» гаснет. PR, который вид выбрал сам, и первый PR группы, о которой попросила строка sidebar-а, не
записывают ничего. Ссылки открываются в браузере системы, никогда не в окне.

### Draft replies и Send

**Draft replies** на выбранном PR запускает новый Session Node Project-а на Claude Code, с человеком; его первое
сообщение — шаблон Project-а «Draft replies», заполненный этим PR (по умолчанию `/worfy:pr-reply owner/repo#N`). Skill
читает PR, его diff и открытые нити и пишет черновик ответа на каждую нить, которая ждёт ответа, в файл на этой машине, в
папке Profile (`state/pr-inbox/drafts/`). Он ничего не публикует. Строка пишет «A Session drafts the replies: they appear
under their threads» или почему Session не запустилась.

**Черновик под своей нитью.** Черновики выбранного PR читаются, когда его выбирают, каждые 5 секунд, пока он выбран, и
когда окно получает фокус; черновики других PR не читаются. Каждый черновик ответа стоит под своей нитью, а ответ в
разговоре PR — под **Conversation**: его метка (Needs code change, Needs answer, FYI, Resolved by push), `Edited`, когда
пользователь его изменил, и текст в поле, которое пользователь правит. Ответ, чьей нити PR не перечисляет, стоит под
«Replies to threads not shown here». План изменения кода, если skill его написал, стоит под полем; он никогда не
публикуется. Кнопки:

- **Send** публикует текст из поля, один раз. Неактивна, пока поле пустое.
- **Discard**: ответ не будет отправлен и уходит из вида.
- **Ask the Session to rewrite** шлёт сообщение той Session, которую **Draft replies** запустил для этого PR в этом окне,
  с просьбой переписать этот один ответ. Сообщение называет ответ нити по id нити, а не только по её `path:line`, поэтому
  две нити на одной строке различаются. Неактивна, когда такая Session неизвестна; когда она закрылась, об этом говорит
  строка под ответами. Неактивна и для ответа, который пользователь изменил (`Edited` или текст, набранный в поле), с
  tooltip «You changed this reply: the Session keeps your text when it drafts again, so it cannot rewrite it»: skill
  оставляет изменённый ответ как есть, пока его нить ждёт, так что переписывание ничего бы не изменило.

Правка сохраняется в файл черновиков, когда поле теряет фокус, поэтому skill при следующем запуске оставляет текст
пользователя. Набранный и ещё не сохранённый текст остаётся при своей нити, когда Session пишет новые черновики и ответы
сдвигаются в файле; ответ в разговоре держит его по тексту, поверх которого его набрали. Отправленный ответ показывает
`Sent`, свой текст и **View on GitHub**. Под неотправленным ответом написано почему, и так же — под отказом всего Send
(например, нет аккаунта); следующее чтение файла этого не стирает. Ответ, который GitHub принял, хотя файл черновиков не
смог это записать, показывает «Posted, but the draft file does not say so: …», и его Send неактивна.

**Send all** появляется, когда у PR два черновика или больше. Она открывает диалог «Send N replies to owner/repo#N?» с
каждым текстом ровно таким, каким он уйдёт, и его местом, и кнопками **Send all** и **Cancel**. Диалог держит тексты, с
которыми открылся: чтение файла, пока он открыт, не меняет ни того, что он показывает, ни того, что уходит. Cancel, Escape
или щелчок снаружи ничего не отправляют. Неактивна, пока какой-то ответ пустой.

**Что делает Send.** Вид называет ответ по его нити (в разговоре — по тексту, который он прочитал последним), никогда
только по месту в файле; когда в файле нет ни этого текста, ни показанного, Send отказывает с «The drafts changed
meanwhile … look at them again». Main сохраняет показанный текст в файл черновиков, читает файл снова и берёт этот текст
как есть. Он ещё раз проверяет его через `review-draft-lint --reply`: следы workflow (номера Ticket-ов и ADR, имена
Epic-ов, пути workflow), строки об авторстве AI, личные данные и длину. Есть находка или проверка не смогла запуститься —
ничего не публикуется: ответ остаётся черновиком и показывает «Not sent: review-draft-lint found …». Аккаунт — тот,
который Profile называет в `github.account`; Profile без него получает «Not sent: the Project's Profile names no GitHub
account (github.account) …», и ничего не публикуется — никогда от gh login машины. Ответ в нити ревью уходит только под
первый комментарий нити, как его видит GitHub; черновик, который называет другой комментарий, получает отказ. Затем ответ
помечается в файле как отправляемый, и main публикует его один раз, текст как тело без единого добавленного байта: ответ
в нити ревью — под её первым комментарием, или комментарий в разговоре PR. После этого файл черновиков пишет `sent` и URL
комментария.

- **Сбой.** Когда падает GitHub или сеть, ответ остаётся черновиком с «GitHub did not confirm the reply: <причина>».
  worfy никогда не публикует его снова сам. Повторный Send такого ответа — или ответа, который всё ещё помечен как
  отправляемый, после того как worfy остановился посередине, — сначала спрашивает GitHub, публиковал ли аккаунт там
  ровно этот текст; если да, ответ только помечается отправленным, так что ответ, чьё подтверждение от GitHub
  потерялось, не публикуется дважды. Первый Send никогда не спрашивает: «Thanks!», который аккаунт раньше написал под
  той же нитью, публикуется снова.
- **Send all** публикует ответы один за другим, не больше 80 в минуту — это лимит GitHub. Первый сбой GitHub
  останавливает остальные; ответ, которому отказала проверка, — нет.
- Уже отправленный ответ никогда не отправляется снова, его нельзя ни править, ни отбросить.
- Token без «Pull requests: write» (fine-grained token) получает отказ GitHub, он виден под ответом.

**Чего worfy никогда не делает на GitHub**: не закрывает нить, не запрашивает ревью, не отправляет ревью и не оставляет
pending-ревью, не помечает notification прочитанным, не push-ит и ничего не публикует без щелчка на **Send** или на
**Send all** в его диалоге.

**Строка состояния** под заголовком:

- «Next search in 4 min» или «Next search now», когда время пришло; в tooltip — время;
- «The last read failed: <причина>», если последнее чтение GitHub упало или читатель ждёт rate limit;
- «GitHub refused the sign-in: <причина>» и **Open Health check**, если чтение упало, потому что GitHub отказал gh во входе
  (в gh нет входа для `github.account`, HTTP 401, у gh нет никакого token-а, организация требует SAML). Причина — та же, что у
  строки `GitHub access` Project-а в Health check ([Gate и GitHub](gate-and-github.md#github-access)), которая сразу краснеет и
  проверяется снова; строка следует за ней. **Open Health check** открывает Settings → Health. Следующее чтение, получившее
  ответ, возвращает строку в `ok`. Project, Profile которого не называет `github.account`, читает от собственного аккаунта gh, и
  main один раз на Project пишет в log почему;
- notice читателя, если он есть, например «GitHub notifications unavailable for this token — checking every 5 minutes»;
- «Mark seen failed: <причина>», если main не смог записать взгляд.

До первого ответа вид пишет «Reading pull requests…». Project, который не читает pull request-ы — переключатель выключен
в Project settings или ни один его репозиторий не на GitHub, — показывает об этом одну строку и ни одной панели. Чтение
без единого PR показывает вместо панелей спокойную заметку «No open pull requests and no review requests.»

**Чтение при открытии.** Каждый раз, когда вид показан — вкладкой toolbar, командой палитры, группой раздела sidebar,
уведомлением или другим входом, или другим Project-ом, пока вид показан, — main сразу читает этот Project из GitHub, не
дожидаясь следующего поиска: review comment, оставленный минуту назад, уже виден. Пока это чтение идёт, строка состояния
пишет «Reading pull requests…» и «Last read 3m ago» (время чтения перед ним) вместо следующего поиска, а строки того
чтения остаются. Чтобы переключения вкладок не тратили rate limit, main пропускает это чтение, если Project читали меньше
30 секунд назад, пока его аккаунт ждёт rate limit, пока он ждёт после упавшего чтения (интервал, который удваивается до 30
минут), и для Project-а с выключенным переключателем. Идущее чтение не запускается второй раз: вид ждёт его. Следующий
поиск идёт через 5 минут после этого чтения.

**Открытие на одном PR.** Вход может попросить один PR Project-а: открывается вид этого Project-а, PR выбран, его строка
прокручена в поле зрения, PR помечен увиденным. Если в inbox такого PR нет, вид открывается и пишет «This pull request is
not in the inbox: owner/repo#N».

**Раздел sidebar.** **Pull requests** — раздел rail-а sidebar-а. Для каждого Project-а Machine окна, у которого есть PR, —
только активного Project-а, пока Project switcher sidebar-а стоит на одном Project-е: его имя, потом строка на каждую
непустую группу со счётчиком. Project, который не читает pull request-ы или не имеет их, не показывает ничего. Если нигде
ничего нет, раздел пишет «No pull requests». Project, чей inbox не читается, пишет почему. Его иконка в rail считает pull
request-ы, которые ждут пользователя: Needs my review, Needs my answer и Needs a fix.

**Переключатель.** В Project settings — **Read pull requests from GitHub**, по умолчанию включён. Выключенный, worfy не
запускает gh для PR inbox этого Project-а, вид сразу говорит об этом, а sidebar его не показывает. Включённый снова,
Project читается сразу, не дожидаясь следующего поиска. Переключатель применяется по Save, как остальные поля окна.

#### На Linked machine

Окно на Linked machine показывает inbox Project-а той Machine, как та его прочитала; само оно GitHub не спрашивает. С
доступом Read only PR можно выбирать, но ничего не помечается увиденным, **Mark seen** неактивна с подсказкой read-only,
**Resolve conflicts**, **Fix checks** и **Address comments** тоже неактивны с ней, а переключатель Project settings
неактивен. Ссылки открываются на той Machine, где по ним щёлкнули.

Черновики и Send остаются на машине Project-а: окно на Linked machine не показывает ни черновиков, ни **Draft replies**, а
каналы черновиков и Send отказывают Linked machine при любом уровне доступа.

### Как работает

- GitHub читает main — по Project-у, с GitHub-аккаунтом Project-а, только репозитории Project-а: поиск раз в 5 минут,
  потом детали сдвинувшихся PR, среди них размер (`additions`, `deletions`). Конфликт после merge другого PR или
  повторный запуск CI не сдвигают PR на стороне GitHub: такой PR читается снова, когда его деталям 30 минут, не больше
  одной страницы из 10 PR за поиск. Main считает группы и счётчики и шлёт виду снимок
  ([ADR-0105](../../adr/0105-pr-reply-only-on-the-users-click.md), пункт 1). Вид его только рисует.
- Слова коллег остаются в памяти main. Что пользователь видел, идёт в папку данных Project-а — id, commit и время, без
  текстов ([ADR-0005](../../adr/0005-worfy-own-state-inventory.md) с поправкой ADR-0105).
- Renderer держит одну копию inbox каждого Project-а для вида и раздела. Он спрашивает main снова, когда main сообщает
  об изменении inbox и когда меняются настройки Project-а, — так переключатель виден сразу.
- Main читает Project-ы по одному: чтения по таймеру и чтение по запросу (Project показан впервые или включён снова, или вид только что открыт: `prInbox.get` с `opened`) ждут
  друг друга в одной очереди.
- Черновики и Send: четыре канала `prInbox.drafts`, `prInbox.saveDraft`, `prInbox.discard` и `prInbox.send` —
  `local`, поэтому адаптер link отказывает в них Linked machine раньше, чем запустится любой handler. Main пишет в файл
  черновиков только текст пользователя (`edited`), отказ от ответа, отметку идущего Send и причину, по которой Send
  упал (обе в `error`), и отметку отправки — через временный файл и rename, и только пока файл всё ещё тот, что он
  прочитал: его текст, а прямо перед rename — его inode, размер и время изменения. Так Session, которая тем временем
  написала новые черновики, не перезаписывается. Одно изменение файла за раз, поэтому два щелчка на Send публикуют один
  раз ([ADR-0105](../../adr/0105-pr-reply-only-on-the-users-click.md), пункты 2–6).
- Все входы, открывающие вид, идут через одну функцию. С PR она оставляет просьбу; вид берёт её, когда снимок пришёл, и
  стирает, поэтому возврат к виду не выбирает этот PR снова.
- Правая панель привязана к PR: другой PR начинает со своих черновиков, набранных текстов и прокрутки. Shell держит все
  виды смонтированными и прячет лишние, поэтому **↑** и **↓** работают, только пока этот вид показан.
