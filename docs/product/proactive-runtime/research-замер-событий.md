# Замер событий Project-а worfy: сколько сигналов в день и сколько остаётся после фильтра

Дата: 2026-11-20. Замер заменяет догадку брифа «1 000 событий в день» измеренными числами. От них зависит выбор:
нужна ли агенту worfy дешёвая сортировка каждого события моделью Haiku, или хватит нескольких пакетных пробуждений
более сильной модели в день.

Период — 14 суток UTC, с 2026-11-06T00:00Z до 2026-11-20T00:00Z. День — сутки UTC. Медиана и максимум взяты по 14
суткам, день без событий считается нулём. Счёт шёл только по полям JSON и по строкам `git log`; текст комментариев,
сообщений и transcript-ов не выводился.

## Метод

### GitHub, `IDSAD-XL/worfy`

Перед каждой командой `export GH_TOKEN=$(gh auth token -u IDSAD-XL)`; только чтение, `gh api` без `--method`.

- PR: `gh api graphql --paginate`, запрос `search(query: "repo:IDSAD-XL/worfy is:pr updated:>=2026-11-06", type: ISSUE)`
  с полями `number createdAt mergedAt closedAt headRefName author{login} reviews(first:100){author submittedAt state}`.
  Сверка через REST `pulls?state=all&sort=created`: те же 578 PR, номера #1467–#2046.
- Комментарии: REST `issues/comments?since=2026-11-06T00:00:00Z` (комментарий относится к PR, если его `html_url`
  содержит `/pull/`) и `pulls/comments?since=…` (комментарии к строкам diff-а). Автор: `user.type=="Bot"` — бот,
  `user.login=="IDSAD-XL"` — аккаунт владельца, остальные — другие люди.
- Issue: REST `issues?state=all&since=…` с `pull_request == null`.
- Workflow run-ы: REST `actions/runs?created=<день>T00:00:00Z..<день>T23:59:59Z`, один запрос на день (запрос с
  фильтром отдаёт не больше 1 000 run-ов). Ранние попытки перезапущенных run-ов — `actions/runs/{id}/attempts/{n}`.
  Check run-ы — `actions/runs/{id}/jobs?filter=all`, все попытки.
- Падение на голове PR: event `pull_request`, conclusion `failure` или `startup_failure`, последняя или ранняя попытка;
  момент падения — `updated_at` попытки. Падение на main: event `push`, ветка `main`, conclusion `failure`.

### Session-ы Claude Code

`<папка>/<id>.jsonl` — Session; `<папка>/<id>/subagents/agent-*.jsonl` — Subagent-ы этого Session-а. Строки
отбирались `grep -E '"type":"(assistant|user|system)"'`, затем `jq` читал только поля `.type`, `.timestamp`,
`.sessionId`, `.agentId`, `.message.stop_reason`, `.isApiErrorMessage`, `.error`, `.origin.kind`,
`.permissionDecision.source`, `.message.content[].name`, `.tool_use_id`.

- ход завершён: `select(.type=="assistant" and .message.stop_reason=="end_turn")`; повторов по `.uuid` нет;
- ход закончился ошибкой: `select(.isApiErrorMessage==true)`, код — `.error`;
- prompt человека: строка `user` без `tool_result` и с `.origin.kind=="human"`; другие значения — `task-notification`
  (закончилась фоновая задача) и `peer` (сообщение другого агента);
- вопрос человеку: `tool_use` с `.name=="AskUserQuestion"`; разрешение, выданное человеком: строка `user` с
  `.permissionDecision.source=="user_temporary"`;
- ожидание дольше 15 мин: после `end_turn` у Session-а больше 15 мин нет новых строк, а потом приходит prompt
  человека — или не приходит ничего до 2026-11-20T00:00Z.

## После фильтра

Правила, как их применил замер:

- (a) комментарий или review в PR не от IDSAD-XL и не от бота;
- (b) упавшая попытка workflow run-а на `main`;
- (c) упавшая попытка workflow run-а на голове PR, которую не сняли за 30 мин: нет нового push в ветку PR (run с
  другим `head_sha`), не начат перезапуск, PR не закрыт и не влит;
- (d) строка `run-stopped` или `ticket-set-aside` в журнале Autopilot; строк сбоев в периоде нет;
- (e) ход Session-а закончился ошибкой API, или Session ждёт дольше 15 мин после `end_turn`: prompt человека пришёл

## Что не измерено и почему

- Правило (a) на этих данных не проверено: за 14 дней нет ни одного комментария или review не от IDSAD-XL и не от
  бота. Комментарии в PR пишут владелец и его агенты с одного аккаунта. В репозитории с командой это правило,
  вероятно, даст больше всего пунктов.
- Ожидание Session-а — оценка сверху. По полям не видно, закончил ли Session ход вопросом или просто доделал работу;
  для этого нужно читать текст. Явных вопросов (`AskUserQuestion`) 6, разрешений от человека 2, и ни одно не ждало
  дольше 15 мин.
- Запросы разрешения, которые человек отклонил или не увидел, отдельным полем в transcript-е не отмечены: видны
  только выданные человеком (`user_temporary`) и отклонённые hook-ом или проверкой безопасности. Почти все решения о
  разрешениях приняты режимом Session-а (`reasonType: mode`), а не человеком.
- Session-ы на других машинах (PC с Windows, Linked machine) и Session-ы Codex не считались: их transcript-ов на этом
  Mac нет.
- Ticket, поставленный в `blocked` на ветке и разблокированный до merge, в истории `origin/main` не виден.
- Задержка в (c) считалась от конца всей попытки workflow run-а. Первый упавший check run виден раньше, поэтому при
  счёте от него пунктов (c) может стать немного больше.
- Autopilot работал 3 дня из 14, поэтому частоту его остановок по этому периоду не оценить.
- Сколько пунктов на самом деле требовали реакции владельца, не измерялось: для этого нужна разметка человеком.

## Вывод

1. Сырой поток — медиана около 930 событий в день без check run-ов (максимум 1 658) и 3 337 с ними (максимум 5 012); догадка «1 000 в день» верна только без check run-ов, а check run-ы — 71 % всего объёма.
2. Фильтр (a)–(f) по полям оставляет медиану 15 пунктов в день (максимум 26, всего 218 — 1,7 % потока без check run-ов); склейка по PR, Ticket-у и Session-у за день — медиану 8,5 (максимум 16, всего 118).
3. Пики гасит склейка, а не модель: 1 188 отказов `rate_limit` у Subagent-ов 11-13 (1 064 из них за один час) дают 2 пункта по Session-у; 9 Ticket-ов, заблокированных одним commit-ом, — 9 пунктов по Ticket-у или 1 по commit-у.
4. Поэтому сортировка каждого события моделью ради объёма не нужна: всё, что осталось, распознано по полям без чтения текста, и 3–4 пакетных пробуждения сильной модели в день увидят по 2–5 пунктов; редкие срочные случаи (main красный дольше 30 мин — 7 за 14 дней, остановка Autopilot — 5) можно будить сразу тем же правилом.
5. Оговорки: в репозитории один автор, чужих комментариев и review 0, поэтому правило (a) не проверено; ожидание Session-а — оценка сверху; Autopilot работал только 3 дня из 14.
