# Агент worfy: предложение советника

Дата: 2026-11-20. Это предложение для разговора с владельцем. Это не spec, не черновик Epic-а и не разрешение на
реализацию. Факты сверены с main `ad2169058`. Заметки, на которые ссылается текст, лежат в этой папке.

Решения владельца 2026-11-20, уже учтённые ниже:

- права агента — вариант C ([вопрос 01](issues/01-что-агент-делает-сам.md));
- Haiku 5.5 вместо Haiku 4.5;
- like и dislike на сообщениях агента против шума;
- фоновая работа на подписке считается разрешённой;
- регулярные проверки источников со своими интервалами (Slack — около 10 минут, Jira — раз в час), настраиваемые work
  hours и настройка каждого типа проверки;
- по агенту на каждую машину;
- всё опционально, включая самого агента.

## 1. Одной фразой

Агент worfy — агент приложения, а не Project-а. У него несколько обязанностей по всем Project-ам обеих машин:

- заметить, что работа стоит или ждёт владельца;
- объяснить почему;
- подготовить следующий шаг;
- в пределах, которые задал владелец, самому сделать внутреннее действие worfy.

Код он не пишет. Вовне ничего не публикует.

## 2. Чего не хватает сейчас

- **Видеть, что ждёт владельца, во всех Project-ах.**
  - Есть счётчики `projectPulse`: live, busy, PR need you, waits (`src/main/claude-home/pulse.ts:1-19`).
  - Есть утренний digest PR без модели (`docs/features/notifications.md:80-100`).
  - Нет списка самих пунктов. Вопрос Orchestrator-а виден только внутри его Session. Waits известны, только пока окно
    показывает Pipeline этого Project-а (`docs/features/app-shell.md`, раздел Projects).
- **Заметить, что работа встала.**
  - Auto-continue продолжает Orchestrator после ошибки API и после сброса Limits
    (`docs/features/orchestrator-modes.md:52-64`).
  - Внутри Run-а Autopilot сам проверяет, не зависла ли работа.
  - Обычные Session-ы и Subagent-ы никто не продолжает.
  - С 11-05 по 11-14 на Mac не было ни одного Run-а, а в main влито 422 PR: большая часть работы шла мимо проверок
    Autopilot-а (`docs/product/critic/worfy-limits-ledger-2026-11-14.md:10`).
  - Об остановке Run-а сообщает только toast в окне (`src/renderer/flight-recorder/stop-toast.ts:1-5`).
- **Узнать о событии, которое пришло, пока worfy был закрыт.**
  - Отметки «просмотрено» у PR Inbox хранятся на диске (`src/main/projects/pr-inbox-state.ts`).
  - Какие события уже уведомлены, main помнит только в памяти. После перезапуска такое событие уведомления не даёт
    (`src/main/notify.ts:661-668`).
- **Связать событие с работой.**
  - PR привязывается к Ticket-у по строке `PR:` или по ветке, но только чтобы отправить текст pr-fix
    (`src/main/actions/launch.ts:376-378`).
  - Объяснения «почему это важно» и предложения нет.

История владельца за три месяца: 28 случаев, когда работа стояла ([research-история-простоев.md](research-история-простоев.md)).
Там, где остановился агент или пришло событие PR либо CI, читаемый сигнал лежал непрочитанным от 4 часов до 14 дней.
2026-10-20 владелец сам поручил эту роль Orchestrator-у — словами.

## 3. Чем агент не будет

- **Вторым Orchestrator-ом.** Он не пишет код, не ведёт Wave-ы, не делает merge. Работу выполняют прежние исполнители.
- **Копией Auto-fix от Anthropic.** Ответить на review comment и починить CI в своей Session Anthropic уже умеет: Desktop
  и Projects ([research-anthropic-модели-цена-и-правила.md](research-anthropic-модели-цена-и-правила.md), разделы 4.2 и
  4.6). Такую работу агент worfy отправляет в уже существующий pr-follow.
- **Общей лентой находок.** Такие ленты закрыли OpenAI, Google и LangChain
  ([research-проактивные-агенты-у-конкурентов.md](research-проактивные-агенты-у-конкурентов.md), раздел «Главное»).

## 4. Устройство: три слоя

```text
источники в main (есть)         слой 1: журнал внимания        слой 2: агент worfy           слой 3: исполнители (есть)
SessionRegistry.observe ─┐      записи, а не счётчики;         Session приложения,           Orchestrator Project-а
PrInbox.onChange        ─┤      дедупликация; хранение   ──►   cwd вне Project-ов,    ──►    Session Ticket-а
workflow hub (waits)    ─┼──►   между перезапусками;           MCP worfy-app,                Autopilot (диалог владельца)
Autopilot: state, журнал─┤      таймеры «ничего не             файл памяти;                  pr-follow; pr-reply (Send —
healthReports, Limits   ─┘      произошло»; без модели         будит его main                щелчок владельца)
```

### 4.1 Слой 1 — журнал внимания (main, без модели)

- **Источники.** Журнал подписывается на то, что уже есть в main:
  - `SessionRegistry.observe` (`src/main/agent/session/registry.ts:95`): вопрос, разрешение, ошибка, конец хода;
  - `PrInbox.onChange` (`src/main/ipc/pr-inbox.ts:115-118`);
  - подписчик workflow hub (`src/main/workflow/waits-notify.ts`);
  - состояние и журнал Autopilot-а;
  - `healthReports().subscribe`;
  - `LimitsTracker` (`src/main/agent/limits.ts:83`).
- **«Ничего не произошло» считает сам, без модели.** Примеры условий:
  - Session Ticket-а молчит N минут;
  - land закончился, а Orchestrator не проснулся;
  - Limits сбросились, а остановленная Session не продолжена;
  - main красный дольше M минут.

  Одно условие даёт один пункт, пока условие не изменится.
- **Хранение.** Пункты лежат в папке данных Project-а на его машине, как `pr-inbox.json`
  (`src/main/projects/pr-inbox-state.ts`). Пункт переживает перезапуск. Linked machine их читает (ADR-0053, ADR-0066).
- **Полезен и без агента.** Этот слой — отложенный Epic `worfy-needs-you`
  (`docs/research/2026-11-13-competitors/README.md:849-851`) плюс таймеры.
- **Что придётся доделать.** Waits считаются, только пока окно показывает Pipeline Project-а. Значит, main должен
  считать Stages для всех Project-ов.

### 4.2 Слой 2 — агент worfy (Session приложения)

- **Где живёт.** Это Session Claude Code с cwd в папке данных worfy, вне всех Project-ов, как у narrator и Terminal AI.
  Поэтому в неё не попадают `CLAUDE.md` и hooks чужого Project-а.
- **Свои правила.** Это третий вид Session в hook Harness-а. Сейчас hook различает только Product Session и Orchestrator,
  по переменной `WORFY_SESSION_KIND` (`harness/hooks/inject-rules.mjs:19-49`).
- **Новый MCP-сервер `worfy-app`, привязанный к приложению.** Нынешние серверы привязаны к Project-у через cwd и вне
  Project-а не работают (`src/main/mcp/canvas-server.ts:563-567`). Его tools:
  - **чтение:** Project-ы и машины, пункты журнала, workflow Project-а, нити PR, хвост Session, Run Autopilot-а, Limits.
    Текст чужих людей помечен как недоверенный;
  - **предложения:** создать, обновить, снять;
  - **действия:** только те, что разрешает режим обязанности, и только через функции main, у которых уже есть свои
    проверки:
    - `Actions.prFollow` отказывает, пока идёт Autopilot (`src/main/actions/launch.ts:358-359`);
    - `autopilot_start` всегда открывает диалог владельца;
    - продолжить Session после сброса Limits.
- **Без Bash, записи файлов и сети.** Агенту доступны только tools `worfy-app`. Образец уже есть — Session черновика
  профиля. Ей разрешены Read, Glob, Grep, а Bash и всё, что пишет или ходит наружу, запрещено
  (`src/main/vendors/claude/options.ts:71-80`). ADR-0105 оставил силу Session публиковать через `gh api` «описанной, а не
  закрытой» (`docs/adr/0105-pr-reply-only-on-the-users-click.md:55-58`). У этого агента её снимает само устройство:
  опубликовать ему нечем.
- **Память — файл состояния.** В нём обязанности, открытые предложения, обязательства и ответы владельца. Каждое
  пробуждение — новая Session, которая читает этот файл, а не одна вечная Session. Причина:
  - продолжение длинной Session после остывшего cache заново шлёт весь контекст: замер — 287 865 token-ов, около $2,30
    по цене API (`docs/product/code-stories/research-из-чего-строить-code-story.md:35-38`);
  - новая Session с контекстом около 30 тыс. token-ов стоит около $0,15–0,24
    (`docs/product/code-stories/issues/01-из-чего-строить-code-story.md`, раздел Answer).
- **Будит его main, а не его собственные ходы.** Два простоя в истории — простой самого наблюдателя. Решение владельца:
  - **Регулярные проверки.** У каждого типа источника своя проверка и свой интервал: Slack — около 10 минут, Jira — раз
    в час, другой сервис — свой.
  - **Work hours.** Настраиваются work hours пользователя: ночью часть проверок спит.
  - **Настройка проверки.** Каждый тип проверки настраивается: включён ли он, интервал, спит ли ночью.

  Предложение советника к этому решению:
  - **Проверка — без модели.** Это вызов API: новые пункты идут в журнал.
  - **Сортировка — на Haiku 5.5.** Она разбирает текст Slack, Jira или почты.
  - **Сильный агент — только по делу.** Его будит сортировка, когда нашла дело. Иначе Slack раз в 10 минут даёт 144
    пробуждения модели в сутки.
  - **События worfy.** Внутренние события — остановилась Session, покраснел main — идут в журнал сразу. Их сортирует
    код, без модели.
  - **Проверка Limits перед пробуждением.** Образец есть в Terminal AI: `limitsGate` останавливает автоматические
    функции, когда 5-часовое окно занято больше чем на 80 % (`src/main/terminal-ai/limits-gate.ts:20`, `:48`). Сейчас он
    принимает только функции Terminal AI, его нужно обобщить.
  - **Как читать источники** — вопрос 12 карты.
- **По агенту на каждую машину.** Агент отвечает за Project-ы своей машины; Project-ы второй машины через Link только
  читает (решение владельца).
- **Всё опционально.** Агента можно выключить целиком, а каждую проверку и обязанность — по отдельности (решение
  владельца).
- **Запуск без Canvas.** Session можно запустить из main без Node (`src/main/agent/session/registry.ts:110`).

### 4.2a Границы в коде (решение владельца 2026-11-20, «Принимаю все 6»)

1. У агента только tools `worfy-app`: нет Bash, записи файлов и сети.
2. Чужой текст приходит к агенту только как данные — через tools `worfy-app`, с источником и автором.
3. Сам агент делает только действия из закрытого списка, и их текст задаёт main. Session с текстом, который написал
   агент, стартует только по щелчку владельца, и владелец видит этот текст до старта.
4. Наружу — только существующий щелчок Send. Пути к `prInbox.send` у агента нет.
5. Project-ы второй машины агент только читает.
6. Каждое действие агента пишется в журнал вместе с пунктом, который его вызвал, и с like и dislike владельца.

Решено советником, подтвердить: каждое пробуждение — новая Session с файлом памяти (вариант c
[вопроса 07](issues/07-где-живёт-агент.md)). Детали варианта владелец поправил, но сам вариант словом не подтвердил.

### 4.2b Знакомство и помощь (решение владельца 2026-11-20)

- **Когда знакомство.** При одноразовом предложении включить агента или когда пользователь впервые сам его включает.
  Агент говорит, кто он, что делает и что умеет. Потом спрашивает work hours и какие источники подключить, и по ответам
  настраивает.
- **Донастройка и помощь.** К агенту всегда можно обратиться за донастройкой и за помощью разобраться в worfy.
- **Настройки.** Меняет только щелчок Apply под карточкой «было → станет». Token-ы и вход в сервисы вводятся в окне
  worfy, агент их не видит.
- **Знания о worfy.** `docs/features` (английские и русские) кладутся в приложение. Сейчас сборка берёт только `out/**` и
  `package.json` (`electron-builder.yml:13-16`). `worfy-app` ищет и читает по ним, агент отвечает со ссылкой на страницу,
  а если страницы нет — говорит, что не знает.
- **Язык.** Агент говорит на языке Guide (`guideLanguage`).

### 4.3 Слой 3 — исполнители

Остаются как есть. Щелчок владельца по предложению вызывает уже существующее действие. Пути к `prInbox.send` у агента
нет: ответ в PR публикует только щелчок Send.

## 5. Обязанности для начала

Как устроена каждая обязанность:

- у неё есть trigger, область и режим каждого действия: сам, по заранее данному «да», спросить, отдать владельцу;
- владелец видит каждую и выключает её отдельно;
- у неё есть счётчики «показано, принято, отклонено, проигнорировано»;
- у каждого сообщения агента есть like и dislike (решение владельца). Dislike сразу меняет поведение: снимает такие
  пункты этой обязанности и пишется правилом в файл памяти, который агент читает при каждом пробуждении. Если оценки
  только копить, они не помогают: у ChatGPT Pulse были оценки вверх и вниз, и его всё равно закрыли
  ([research-проактивные-агенты-у-конкурентов.md](research-проактивные-агенты-у-конкурентов.md), таблица «Сравнение»);
- после N проигнорированных предложений или dislike подряд обязанность встаёт на паузу.

| Обязанность | Trigger | Что делает | Режим по умолчанию |
|---|---|---|---|
| Работа стоит | Session молчит или ждёт ответа; Run остановился; Limits сбросились, а Session не продолжена | Объясняет, что стоит и почему; продолжает Session после сброса Limits; будит Orchestrator фиксированным сообщением | продолжить после Limits — main сам, без модели; остальное — спросить |
| CI основной ветки красный | CI основной ветки красный дольше N минут (N и само правило настраиваются) | Находит PR, после которого покраснело, и его Project; предлагает Session починки | спросить |
| Ждёт владельца | вопрос, разрешение или park в любой Session; PR ждёт взгляда; решение ждёт дольше N часов | Держит один список; напоминает утром; если вопрос повторяется — предлагает постоянное правило | показать |
| Утренняя сводка | первое открытие worfy за день | Рассказывает, что случилось ночью на всех Project-ах и машинах, что ждёт и что делать дальше с учётом Limits | сам |

Принцип владельца (2026-11-20): правила агента не привязаны к тому, как работают в репозитории worfy. Поэтому:

- встроенные правила опираются только на то, что есть у любого Project-а;
- процесс конкретного Project-а задаётся правилами в настройках этого Project-а, а не в коде worfy. Например: land
  закончился, а Orchestrator спит; открыт issue `pc-main-red`.

Почему эти обязанности:

- они бьют в простои с самым долгим непрочитанным сигналом ([research-история-простоев.md](research-история-простоев.md),
  раздел «Итоги»);
- у Anthropic таких функций нет.

## 6. Цена

- Цена растёт с числом пробуждений, а не с числом событий: одно пробуждение разбирает пачку пунктов журнала.
- Сколько подписки стоит одно пробуждение, неизвестно. Anthropic не публикует, какую долю лимитов тратит каждая модель
  (`docs/adr/0058-terminal-ai-assist-process.md:154-155`).
- Сколько событий в день дают источники, замеряет Ticket 05 карты.
- Первая ступень разбора, если она нужна, идёт на Haiku 5.5 (решение владельца). Haiku 5.5 в Claude Code думает
  всегда, поэтому лимит ответа должен вмещать и thinking
  ([research-anthropic-модели-цена-и-правила.md](research-anthropic-модели-цена-и-правила.md), раздел 1.3). Нужна ли
  такая ступень на каждое событие, решает замер: если пачки выдерживают поток, она не нужна.

## 7. Правила Anthropic

- Прямого разрешения стороннему приложению запускать работу без запроса человека нет. Consumer Terms разрешают
  автоматический доступ только с API key или с явного согласия
  ([research-anthropic-модели-цена-и-правила.md](research-anthropic-модели-цена-и-правила.md), раздел 2.2).
- Решение владельца 2026-11-20: «Отсутствие разрешения пропускаем, действуем в парадигме того что подобное разрешено».
  Дальше тема считает фоновую работу на подписке разрешённой.
- Остаются два технических риска, которые от разрешения не зависят (там же, раздел 2.1, пункт 6):
  - `--bare` станет поведением `-p` по умолчанию, а bare mode не берёт вход по подписке;
  - вход по плану кончается в известный срок. Агент должен заметить это и сказать владельцу, а не остановиться молча.

## 8. Что меняется в прежних решениях

- Roadmap исключает «советника по расписанию; Epic-и, которые worfy выбирает или ставит в очередь сам»
  (`docs/roadmap.md:438-439`). Утренняя сводка — это советник по расписанию, на неё нужен Amendment.
- Очередь Epic-ов остаётся за владельцем (ADR-0100): агент предлагает, владелец ставит.
- Отложенные `worfy-needs-you` и `worfy-triggers` (README:849-854) становятся слоем 1 и обязанностями агента.

## 9. Самая дешёвая альтернатива

Без агента, только код:

- уведомление ОС об остановке Run-а;
- уведомление о «Needs a fix»;
- хранить на диске, какие события уже уведомлены;
- Auto-continue для всех Session-ов, а не только для Orchestrator-а;
- таймеры «ничего не произошло», которые шлют уведомление.

Это слой 1 без слоя 2. Он закрывает часть простоев и не тратит ни одного token-а. Но он не объясняет, не связывает
событие с работой и не готовит шаг. Если пилот агента не покажет выигрыша над этим набором, агент не нужен.

## 10. Что опровергнет идею

Пороги владелец задаёт до пилота.

- За две недели теневого режима агент не нашёл ни одного простоя, который слой 1 не показал бы сам.
- Доля принятых предложений ниже заданного порога.
- Пробуждения тратят больше заданной доли недельного лимита.
- Владелец не открывает утреннюю сводку.
