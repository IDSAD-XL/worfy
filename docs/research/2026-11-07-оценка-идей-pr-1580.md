## 3. Идеи по одной

### Идея 1. Intent-to-Behavior Contracts — контракты поведения у функции

**Предлагается.** У каждой функции — версионированный список наблюдаемых сценариев, связанных с требованием
владельца; состояния Passed / Failed / Unverified / Stale.

**Что уже есть.**

- Страницы функций: у каждого раздела блоки Behaviour, How it works и Implementation с главными test-ами
  (`docs/features/README.md:52-60`). Правило: «код и test-ы — источник страницы, claim без подтверждения на страницу
  не попадает» (`docs/features/README.md:66-67`). Каждый claim проверял отдельный агент; первый раунд нашёл 41
  неверный claim из ~2310 (память, `feature-docs-pilot-2026-10-31.md`, строка 17).
- У Ticket-а — пункты «Готово, когда» со строками Evidence и состояниями Failed / Verified / Not verified
  (`docs/features/evidence.md:50-54`); подробно — оценка PR #1314, идея 2.
- Ship-ticket начинает с падающего test-а (`harness/skills/ship-ticket/SKILL.md:166`). e2e-файлов `*.spec.ts` — 146
  (`test/e2e/`).

**Чего нет.** Behaviour-блок — проза без id и без ссылки на конкретный test; Evidence привязана к Ticket-у, а не к
функции; состояния Stale нет. `scripts/check-feature-docs.mjs:2` проверяет только, что пути на странице существуют.

**Ценность.** Неясна. Случая «все test-ы зелёные, а поведение не то, что хотел владелец» в найденных материалах не
видно как класса; такие расхождения ловит приёмка владельца. Сам PR называет главный риск: тот же агент закодирует
своё непонимание и в функцию, и в контракт.

**Стоимость.** Высокая: новый формат, связь «claim → test» на 31 странице, поддержка при каждом Ticket-е.

**Вердикт: отложить.** Если вернёмся — не новый формат, а таблица Tests на страницах функций (уже есть на 9 из 31,
например `docs/features/autopilot-faults.md:196-217`).

### Идея 2. Ambiguity Gate — реестр неоднозначностей до приёмки spec

**Предлагается.** До приёмки spec найти требования с несколькими существенно разными толкованиями, записать
варианты и задержать только затронутые Ticket-ы до решения владельца.

**Что уже есть — почти всё.**

- До приёмки: раунды вопросов владельцу Q1…Qn (grilling); `Q1` есть в 21 из 32 spec-ов. Ticket-ы с вопросами —
  `Type: grilling` (`harness/skills/continuous-audit/SKILL.md:149`).
- Во время Wave: вопрос владельцу Wave не останавливает — агент берёт рекомендованный вариант и пишет «решено без
  владельца, подтвердить» (`harness/skills/epic-wave/SKILL.md:342-347`). Таких отметок больше 550 в 311 файлах `.scratch`.
  Владелец подтверждает их пачкой: docs PR #1455 подтвердил 86, из них 9 позже изменены
  (память, `owner-decisions-2026-11-05-faults.md`, строка 45).
- Задержка только затронутых Ticket-ов: поле `Waits: owner` (`harness/bin/TICKETS.md:39`); Autopilot считает
  Epic `waits-owner`, когда всё несделанное ждёт владельца (`src/shared/autopilot/epic-queue.ts:8-10`), и Run
  останавливается с этой причиной (`src/main/autopilot/run.ts:176-181`, PR #1577).

**Чего нет.** Структурной записи вопроса (цитата требования, толкования, затронутые Ticket-ы). Отметка — свободный
текст.

**Ценность.** Низкая. 9 из 86 решений без владельца позже изменены, но цена этих изменений не посчитана, и ни одно
не вернулось к владельцу с жалобой (там же, строка 45).

**Вердикт: не берём.** Grilling до приёмки, отметки «решено без владельца» и `Waits: owner` уже делают то же самое.
Отдельный LLM-проход рискует, как пишет сам PR, плодить вопросы — а внимание владельца ограничено.

### Идея 3. Scenario Forge — генерация согласованных тестовых данных

**Предлагается.** Из схемы и правил домена строить детерминированный «мир» данных заданного размера.

**Что уже есть.** Fake agent: Session проигрывает сценарий из `test/fixtures/agent-scripts/` (64 файла) вместо
Claude Code (`src/main/agent/fake-query.ts:1-2`). Fake Codex app-server (`test/fixtures/codex-app-server/fake-app-server.mjs:1-3`).
Большой транскрипт генерируется в test-е (`test/big-transcript.ts:1-3`). Ручной Epic-образец —
`test/fixtures/worfy-mvp-epic/`.

**Чего нет.** Генератора «проект + Epic-и + Ticket-ы + транскрипты» из схемы; fixture с большим Canvas.

**Ценность.** Для worfy низкая: базы нет, домены данных — Markdown Ticket-ов, транскрипты, journal-ы, и под каждый
есть свой fixture. Для auction (база данных) — возможно, но запроса нет.

**Вердикт: не берём.** Fixture большого Canvas — только вместе с идеей 7, если она понадобится.

### Идея 4. State-Space Explorer — исследование переходов состояний

**Предлагается.** Модель «состояния, действия, инварианты», обход непосещённых переходов, минимизация падающей
последовательности.

**Что уже есть.**

- Цикл Autopilot — чистая функция «состояние + событие → состояние и эффекты» (`src/shared/autopilot/cycle.ts:1-3`).
- Инварианты восстановления I1–I8 и `checkRecovery` (`test/autopilot-invariants.ts:1-4`); сценарии сбоев выбраны
  руками (Epic worfy-faults; оценка PR #1314, идея 7).
- Свой seeded random в test-ах: 20 000 случайных потоков с фиксированным seed
  (`test/unit/console-request.test.ts:160-162`). Библиотек property-based testing (fast-check) нет в
  `package.json`.

**Ценность.** Небольшая сейчас. В `cycle.ts` 14 commit-ов, из них похож на исправление ошибки один —
`199d2f2fa` (worfy-polish 61, 2026-11-07). Состояние UI с «отключить сеть, сменить роль» в форме PR — дорого и
недетерминированно, что сам PR признаёт.

**Вердикт: отложить.** Если вернёмся — узкий вариант: генерация последовательностей событий для `step()` цикла
Autopilot с проверкой инвариантов, один test-файл, без обхода UI.

### Идея 5. Causal Regression Bisector — поиск виновного commit-а

**Предлагается.** По воспроизводимо красному test-у и известному зелёному ref-у — `git bisect` в одноразовых
worktree, с отдельным исходом «не определено» при flaky test.

**Что уже есть.**

- Деление пополам по префиксам набора merge-ей Wave (`docs/adr/0065-one-gate-full-per-wave-merge-set.md:25-28`;
  `harness/bin/wave-gate`). Для worfy выключено: `merge_gate` — `null` (profile worfy, строка 67), вернуть может
  только ADR Ticket-а worfy-throughput 07 (`docs/adr/0083-ci-ok-on-every-pr-is-the-merge-condition.md:49-51`).
- Красный `main` в CI: каждый push на `main` гоняет весь набор, поэтому красный push run сам называет виноватый
  merge; час на исправление вперёд, затем revert; «There is no bisection»
  (`harness/skills/epic-wave/SKILL.md:1378-1386`). Это решение владельца (память,
  `owner-decisions-2026-10-29.md`, строка 19).
- Записи о падениях и повтор поодиночке отделяют flaky test от регрессии
  (`docs/adr/0096-failure-records-and-solo-rerun.md:43-48`); подробно — оценка PR #1314, идея 5.

**Где поиск виновного правда идёт руками.** gate full на ПК гоняется на `main` раз за Wave и покрывает несколько
merge-ей (`docs/adr/0086-pc-gate-full-once-per-wave.md:30-32`). Пять issue-ов `pc-main-red` за 2026-10-31…11-06:

- #1481 и #1423 — виновник назван без деления: красный test впервые запущен на Windows и пришёл с конкретным PR.
- #1513 и #1153 — виновник не commit, а окружение ПК: тот же test красный на commit-е до merge (#1513), красный и
  на commit-е, где раньше был зелёным, после перезагрузки машины (#1153). Деление по commit-ам здесь ответило бы
  «не определено».
- #1120 — причина не установлена, test прошёл на следующем gate full.

**Ценность.** Низкая: ни в одном из пяти случаев `git bisect` не дал бы ответа быстрее рассуждения.

**Вердикт: не берём.** Попутная находка: пункт 4 ADR-0081 («красный `main` — bisect и revert, автоматически»,
`docs/adr/0081-per-pr-linux-ci-shards-and-affected-tests.md:39-42`) противоречит действующему правилу «no
bisection» в skill epic-wave; ADR стоит дополнить строкой Amendment в ближайшем docs PR.

### Идея 6. Architecture Fitness Functions — архитектурные правила как проверки

**Предлагается.** Правила импортов и границ модулей как машинные проверки со ссылкой на ADR и учётом исключений.

**Что уже есть — ядро идеи.**

- Своё правило ESLint `worfy/process-boundary`: renderer и card-runtime не импортируют main и preload, shared — ещё и
  renderer; Electron и Node в этих слоях запрещены, включая type-only импорты (`eslint.config.js:15-24`, включено
  `:118-120`). Его проверяет test на настоящем конфиге (`test/unit/process-boundary.test.ts:6-7`).
- Electron: `contextIsolation`, `sandbox`, без `nodeIntegration` (`src/main/window.ts:137-139`); fuses проверяет
  `scripts/check-fuses.mjs` в `test:package`.
- Тема review «границы модулей» в `review.lenses` и `ticket_lenses` (profile worfy, строки 145-155) — суждение агента,
  не машинная проверка.

**Чего нет.** Границ внутри `src/main`, ссылок на ADR в тексте ошибки, базовой линии «известный долг».

**Ценность.** Низкая: нарушения границы процесса, дошедшего до `main`, в Ticket-ах не найдено.

**Вердикт: сделано в нужном объёме; остальное не берём.** Новое правило — когда review найдёт нарушение, которое
повторяется.

### Идея 7. Performance Envelope — бюджеты производительности

**Предлагается.** 3–5 сценариев пользователя с бюджетами времени и памяти, сравнение с базовой линией на той же
машине.

**Что уже есть.** Замеры скорости test-ов и CI, а не продукта: `test/timings-reporter.ts:1-3`,
`scripts/critical-path.mjs`, Epic worfy-throughput. Один замер продукта — поток вывода Terminal
(`scripts/terminal-flood-bench.mjs:1-4`, «Not a test: numbers for a ticket»). Несколько жёстких пределов в e2e,
например `test/e2e/card-runtime.spec.ts:125` (≤ 1000 ms).

**Чего нет.** Базовой линии, бюджетов по сценариям, истории.

**Ценность.** Не подтверждена: жалоб владельца на скорость worfy в памяти нет (поиск «тормоз», «медленн», «лагает»);
в Ticket-ах — частные случаи Windows (worfy-windows 21, 67), закрытые.

**Стоимость и риски.** Замеры на бесплатных runner-ах шумные; честный бюджет требует одной машины и повторов —
это время владельца или ПК.

**Вердикт: отложить** до первой жалобы на скорость. Тогда — один сценарий с `performance.now()` в renderer, как в
`test/e2e/helpers.ts:656-661`.

### Идея 8. Platform Differential Testing — сравнение поведения Mac и Windows

**Предлагается.** Один сценарий на двух машинах, сравнение структурированного результата, а не только pass/fail.

**Что уже есть.** Тот же набор test-ов идёт на обеих платформах на каждом PR: unit и contract на Windows в трёх
шардах и e2e на Windows на тех же spec-файлах, что macOS (`.github/workflows/ci.yml:45-56`). Плюс gate full на ПК
после Wave (ADR-0086). Epic worfy-windows закрыт 120/120; около 50 его Ticket-ов — дефекты, найденные именно так.
Расхождения, которые решено не чинить, оформлены как исключения Windows с владельцем «worfy-windows 117»
(`test/quarantine.ts:19-20`) — по решению владельца (память, `owner-decisions-2026-10-31-evening.md`, строка 13).

**Чего нет.** Записи структурированного результата и сравнения двух записей.

**Ценность.** Низкая: общий набор test-ов уже и есть сравнение — test утверждает одно и то же поведение на обеих
платформах. Machine Link — функция продукта, не песочница для test-ов (сам PR это признаёт).

**Вердикт: не берём.**

### Идея 9. Migration Guardian — старые данные пользователя в новой версии

**Предлагается.** Набор исторических fixture-ов данных; проверка «прочитать → обновить → записать → открыть снова»
между версиями.

**Что уже есть.**

- Общий модуль state-файлов: чтение через zod-схему, неизвестные ключи отбрасываются; файл, не прошедший схему,
  переименовывается в `<name>.unreadable-<время>`, и часть приложения стартует пустой
  (`src/main/storage/json-file.ts:1-13`; `docs/features/storage-and-diagnostics.md:78-80`).
- Явная версия есть у немногих файлов, например настройки Link: версия 1 читается и сразу переписывается как 2
  (`src/main/link/settings.ts:15-42`). Старые форматы проверяются объектами внутри test-ов, а не набором fixture-ов
  (например, `test/contract/layout-store.test.ts:416`).
- Update держит одну прежнюю копию `worfy-stable.previous`, откат из Settings возвращает её
  (`docs/adr/0089-update-builds-main-in-own-clone.md:28-30`).

**Что случилось на деле.** В папке state Mac владельца лежат четыре отложенных файла: `link/settings.json` и
`limits.json`, по два раза, 2026-10-21 11:08Z и 2026-10-30 05:22Z. Отложенный `link/settings.json` — версии 2
(ключи `version`, `projectsAccess`, `machines`, `keepAwake`). 2026-10-30 в 05:23Z на Mac запустилась старая
копия worfy от 2026-10-14 (память, `stale-worfy-copy-shared.md`), а версия 2 настроек Link появилась 2026-10-16
(PR #399): старая сборка не узнала новый формат и отложила файл — доступы Linked machines сбросились.
2026-10-21 владелец поставил Stable из checkout-а, отставшего на 161 commit (память,
`owner-decisions-2026-10-21.md`, строка 19); время совпадает с первой парой файлов, причину по содержимому не
проверял.

**Чего нет.** Проверки, что старая сборка не сбрасывает файлы новой (направление отката), и набора fixture-ов
форматов по версиям. В spec worfy-update и на странице `docs/features/updates.md` совместимость state при откате
не упомянута.

**Ценность.** Высокая для одного владельца: откат — функция Settings, а Stable обновляется с `main` часто. Каждый
следующий откат через изменение схемы повторит сброс.

**Стоимость.** Небольшая, если узко: исправить уже выпущенные старые сборки нельзя, поэтому работа — для будущих
откатов.

**Вердикт: берём, один Ticket** (например, в worfy-polish). Содержание на выбор Ticket-а: (а) правило для схем
state — новое поле необязательное, новая версия файла не делает его нечитаемым для предыдущей сборки, а где это
невозможно — Update предупреждает перед откатом; (б) contract test на наборе синтетических state-файлов каждой
версии схемы (без личных данных): текущая сборка читает их без откладывания. Полный «Guardian» для чужих баз данных
— не берём.

### Идея 10. Dependency Migration Pilot — обновление зависимостей

**Предлагается.** План обновления SDK/Electron/toolchain с анализом breaking changes, реализация в отдельной ветке
только после одобрения.

**Что уже есть.**

- Точные версии: Agent SDK `0.3.289`, Codex `0.166.0`, Electron `44.5.1` (`package.json:29`, `:31`, `:65`).
- Для SDK и Codex — test-ы совместимости с записанными сообщениями: поднятая версия без новых записей — красный
  test; процедура обновления Codex в четыре шага, шаг 3 (запись с логином) — владелец
  (`test/contract/codex-compat.test.ts:17-24`; `test/contract/sdk-compat.test.ts:1-9`). Реальный Codex агенты не
  запускают (память, `multi-vendor-wave7-2026-11-03.md`, строка 16).
- Dependabot и Renovate нет: в `.github/` только `workflows/ci.yml` и `workflows/windows-tests.yml`.

**Что важно сейчас.** Electron `44.5.1` (релиз 2026-09-30) не менялся с первого PR (`5da0b9859`, 2026-10-05). В
линии 44 после неё вышло 12 релизов, 44.6.0…44.10.2 (последний — 2026-11-03), последняя мажорная — 45.2.3 (`npm view electron`). Browser
Node открывает произвольные сайты в Chromium этой сборки (`docs/adr/0078-browser-node.md:35-36`). Есть ли в этих
patch-релизах исправления безопасности, не проверял (нет сети к release notes в этой оценке).

**Ценность.** Patch-обновление Electron — дёшево и проверяется существующим CI (e2e на macOS и Windows). SDK
(`0.3.319`) и Codex (`0.167.0`) требуют записи владельца — это его время, без явной пользы сейчас.

**Вердикт: берём узко, один Ticket** — поднять Electron в линии 44 до последнего patch-а, с прогоном
`test:package` (fuses). «Pilot» как функцию — не берём: для одной зависимости раз в месяц процедуры в test-ах
хватает.

### Идея 11. Security Boundary Auditor — аудит границ доверия продукта

**Предлагается.** Найти границы доверия продукта и проверить выбранные статическими правилами и локальными
негативными test-ами.

**Что уже есть.**

- IPC: все каналы через один модуль; вызов из недоверенного frame отклоняется, вход и выход проверяются zod
  (`src/main/ipc/index.ts:136-145`); у канала класс доступа, Linked machine видит только `link` и `project`
  (`src/shared/ipc/channels.ts:24-38`).
- Link: TLS 1.3 с закреплённым сертификатом, SPAKE2, токены только как хэши (`docs/features/link.md:330-348`),
  test-ы `test/contract/link-access.test.ts`.
- Webview Browser Node — без preload и `nodeIntegration` (`docs/adr/0078-browser-node.md:35-36`).
- Privacy check — личные данные в ветке, не секреты (`harness/lib/privacy.cjs`; оценка PR #1314, идея 2).
- Тема review `security` упоминается только на глубине `high` (`harness/skills/ship-ticket/step-7-review.md:36`);
  в `harness/agents/reviewer.md` слов о безопасности нет. В profile worfy тем безопасности нет ни в review, ни в
  `audit_lenses` (там одна тема — documentation; profile worfy, строки 145-171).

**Чего нет.** Единого списка границ доверия и проверки их всех разом; поиска секретов в diff.

**Ценность.** Средняя: репозиторий публичный, worfy слушает сеть (Link) и открывает чужие сайты (Browser). Случаев
утечки или обхода в Ticket-ах не найдено.

**Вердикт: исследовать — один прогон continuous-audit с темой безопасности** (IPC, webview, Link, открытие файлов),
без нового кода: skill берёт темы из profile (`harness/skills/continuous-audit/SKILL.md:79-84`). Находки — по
обычным правилам (низкие не становятся Ticket-ами). Постоянную функцию «Auditor» для чужих продуктов — не берём.

### Идея 12. Autonomous Roadmap Critic — критика следующего Epic-а

**Предлагается.** Советник сравнивает следующий Epic с целями владельца, известными сбоями и упущенной выгодой и
предлагает Keep / Reorder / Split / Defer.

**Что уже есть.** Очередь Run-а берёт только принятые владельцем Epic-и и сама их не выбирает
(`docs/adr/0100-run-epic-queue.md:44-46`); порядок по умолчанию — дата приёмки
(`src/shared/workflow/accepted-epics.ts:15-17`); во время Run-а очередь не переставляется (память,
`owner-decisions-2026-11-05-faults.md`, строка 37). continuous-audit проверяет код, а не планы. `docs/roadmap.md` —
направление и «вне E2–E4» (`docs/roadmap.md:11`, `:394`), без порядка приоритетов; последний commit 2026-11-01.

**Ценность.** Низкая: Epic-ов в работе мало (`epic-status`: открыто 8, из них 7 ждут владельца или заблокированы),
а порядок задаёт сам владелец словами. Сам PR называет риск — советник забирает решение у владельца, а численных
целей, против которых сравнивать, нет.

**Вердикт: не берём.**

## 5. Порядок для «берём»

1. **Ticket: старая сборка не сбрасывает state новой** (идея 9). Первый, потому что ущерб уже случился дважды, а
   откат — штатная функция Update.
2. **Ticket: Electron до последнего patch-а линии 44** (идея 10). Дёшево, проверяется существующим CI.
3. **Один прогон continuous-audit с темой безопасности** (идея 11) — после 1 и 2, если владелец согласен потратить
   на это прогон агентов.
4. Попутно, без Ticket-а: строка Amendment в ADR-0081, пункт 4 — «bisect и revert» заменены правилом «час на
   исправление, затем revert, без деления» (идея 5).

## 6. Что делать с самим PR #1580

**Рекомендация: не сливать; закрыть с комментарием после решения владельца.** Причины:
