# Организация Canvas: компактные Epic frame-ы, автоуборка Session-ов, цвет по типу, группы по связям

- **Дата:** 2026-10-19
- **Статус:** исследование, не решение. Решения принимает владелец (раздел 6). Код не менялся.
- **Запрос владельца (2026-10-19, дословно):** «Эпики при автолейауте уходят тупо вниз, немного
  нелогично и некомпактно выглядит. Ну и само расположение карточек на канвасе тоже немного дикое,
  ибо очень много карточек сессий которые закончились уже очень давно. Конечно предполагается что
  юзер будет их как-то сам чистить, но предлагаю какой-то интеллектуальный механизм автоуборки
  ненужных. Так же было бы славно как-то различить карточки по типам, сессии, оркестраторы, эпики и
  тикеты в них. Например цветами. И что бы они группировались по смыслу и связям. Проведи большое
  детальное исследований этой идеи и возможные пути решения задачи.»
- **Что прочитано.** Код `origin/main` `ae7603f0`; ADR 0011, 0016, 0031, 0032, 0037, 0038, 0039,
  0053; `docs/design/F-SPEC.md` (таблица Tokens), `docs/design/BRIEF.md`; `CONTEXT.md`; скриншот
  владельца (Windows PC, Canvas Project-а CanvasForAI с Mac через Linked machine); внешние
  источники — раздел 7. Каждая ссылка `файл:строка` ниже перечитана по `origin/main`.

## 1. Коротко

**Проблема.**

1. Все Epic frame-ы (рамки Epic-ов с Ticket-ами внутри) стоят одной колонкой. 11 Epic-ов дают
   колонку высотой примерно в три экрана, справа и слева пусто.
2. Session Node (карточка одного разговора с Claude Code) появляется при старте Session и остаётся
   навсегда. Убрать её может только пользователь, по одной.
3. Все Node-ы, кроме Terminal, — одна и та же поверхность. Цвет есть только у статуса Ticket-а и
   Epic frame-а. Minimap рисует всё серым.
4. На дальнем zoom карточки — мелкие нечитаемые пятна. Тип не узнать ни по цвету, ни по форме.
5. Связи (какая Session над каким Ticket-ом работает) известны коду, но на место Node-а не влияют.

**Рекомендуемое направление.**

1. Epic frame-ы — в K колонок вместо одной, K из общей площади. Готовые Epic-и — на отдельную полку
   маленьких chip-ов. Правило детерминированное: одинаковое на всех экранах.
2. Автоуборка в main: Session кончилась и простаивает дольше порога (по умолчанию 24 ч) или её
   Ticket done — Node уходит в историю своего Ticket-а/Epic-а или в «Архив». Ничего не удаляется,
   есть toast с Undo и настройка в Settings.
3. Цвет по типу — новые токены `kind-*` в F-SPEC: полоса в шапке, иконка, Minimap. Статус остаётся
   на своих ролях (ready, working, blocked, done) и всегда со словом.
4. Semantic zoom (вид карточки зависит от zoom): на дальнем zoom карточка — блок цвета типа с
   крупным заголовком.
5. Группы по связям: сначала подсветка «семьи» при наведении (без движения Node-ов), потом команда
   «Arrange by Epic» — Session-ы встают рядом со своим Epic frame-ом, один шаг ⌘Z.

## 2. Что сейчас

### 2.1 Почему Epic-и уходят вниз колонкой

- Рамки ставит `stackFrames` (`src/renderer/canvas/epic-layout.ts:412`). Это одна колонка с общим
  `x`, `y` от 0, между рамками `FRAME_GAP = 48` (`epic-layout.ts:39`). Строк и сетки нет.
- `x` колонки ищет `frameColumnX` (`epic-layout.ts:375`): первое место слева, где полоса шириной
  самой широкой рамки и высотой всей стопки не задевает ни одного Node-а. Так решил ADR-0032 (рамки
  Epic-ов обходят Node-ы на плоскости; main не знает размеров рамок). Высота полосы берётся с
  запасом под открытую стопку done каждой рамки (ADR-0032, пункт 2).
- Вызов — `src/renderer/canvas/sources/epics.ts:440`. На вход идут Node-ы Layout-а на плоскости и
  прямоугольники деревьев Subagent-ов (`publishPlaneRects`, `epics.ts:190`).
- Рамка — Derived Node (Node, место которого считает worfy из workflow; ADR-0011). В Layout на Epic
  лежит один невидимый Node 1×1 со смещением, которое задал пользователь, и флагом `collapsed`
  (`epics.ts:7-14`). Сдвинутая рамка уступает соседям через `freePlace` (ADR-0038: Node-ы не
  перекрываются, зазор 16 px).
- Внутри рамки Ticket-ы раскладывает ELK (Eclipse Layout Kernel, библиотека раскладки графов) в Web
  Worker: `layered`, слева направо, ортогональные Edge-и, колонки через `partitioning`
  (`src/renderer/canvas/elk/layout.ts:56-72`, ADR-0037). Колонка Done для ELK — один блок
  (ADR-0039). Между рамками ELK не работает.
- Порядок рамок в колонке не зависит от активности: активный Epic может оказаться внизу, под тремя
  готовыми.
- **Корень проблемы:** рамки складываются только по вертикали. Ничего не переносит их в ряды или
  сетку.

### 2.2 Почему копятся Session-ы

- `src/renderer/canvas/overlays/SessionNodes.tsx:1-5`: Node появляется при старте Session и
  остаётся, finished, после того как процесс ушёл. Новый внешний Session Node встаёт под последним
  Session Node (`nextPlace`, `src/renderer/claude-home/session-nodes.ts:200`). Так растёт левая
  колонка на скриншоте.
- Session, запущенная из worfy, встаёт по `placeNewNode` (`src/main/layout/place.ts:15`): в (40, 40)
  или под всеми Node-ами. «Ship ticket» ставит Session справа от колонки рамок на высоте Ticket-а
  (`placeDownFrom`, `place.ts:31`).
- Убрать Node можно кнопками Hide и Remove (`src/renderer/canvas/nodes/SessionNode.tsx:381-391`,
  `:502-506`). Remove живой Session запрещён, транскрипт остаётся. ⌘Z отменяет (история в renderer,
  `HISTORY_DEPTH = 40`, `src/renderer/canvas/history.ts:36`).
- Удалённый Node не создаётся заново только в пределах одного запуска приложения: множество
  `seenByProject` живёт в памяти (`SessionNodes.tsx:22`).
- Trash (корзина Node-ов) хранит записи 3 дня (`src/shared/ipc/trash.ts:12`, ADR-0016) и служит
  для удалений пользователя.
- **Автоуборки нет, настройки нет.** Код не связывает «Session кончилась» и «её Ticket done».

Какие данные уже есть для правила уборки (`src/shared/ipc/claude-home.ts:25-52`):

| Данное | Откуда | Зачем правилу |
| --- | --- | --- |
| `status`: `idle` / `busy` / `unknown`, `startedAt`, `updatedAt` | реестр живых Session-ов | живую не трогать |
| `firstAt`, `lastAt`, `modifiedAt` | транскрипт в `~/.claude/projects` | сколько простаивает |
| `gitBranch`, `cwd` | транскрипт | Binding по ветке и worktree |
| Binding (связь Session с Ticket-ом или Epic-ом) | `src/shared/binding/resolve.ts:1-20` | «Ticket done» → можно убрать |
| `pinned`, `hidden`, теги | Layout | исключения |

### 2.3 Почему типы выглядят одинаково

- Типы Node-ов собирает glob по `nodes/*Node.tsx` (`src/renderer/canvas/nodes/index.ts:86`).
  Размеры: Session 300×120 (`session-nodes.ts:22-23`), живая Session из worfy 340×220
  (`src/shared/ipc/sessions.ts:29-30`), Orchestrator 360×200 (`src/shared/ipc/orchestrator.ts:21-22`),
  Subagent 260×84 (`src/renderer/canvas/sources/subagents.ts:34-35`), Ticket 204×160
  (`epic-layout.ts:17`, `:29`), Card 360×280 и Note 220×120 (`src/shared/canvas/tools.ts:22-23`),
  HANDOFF 360×320 (`src/shared/ipc/docs.ts:17-18`).
- Все, кроме Terminal, рисуются одной поверхностью `.w-node-surface`
  (`src/renderer/theme/tokens.css:167`). Цвет есть только у статуса Ticket-а и Epic frame-а.
- Minimap берёт цвет из `minimapColor` типа (`src/renderer/canvas/overlays/MiniMapOverlay.tsx:20-23`).
  Объявляют его три типа, и все три серые: Session — `--text-secondary`
  (`nodes/SessionNode.tsx:56`), Subagent и Note — `--border-strong` (`nodes/SubagentNode.tsx:22`,
  `nodes/NoteNode.tsx:12`).
- **Правила цвета.** F-SPEC, раздел Tokens (`docs/design/F-SPEC.md:18-37`): роли — поверхности,
  текст, primary, ready, working, blocked, done, terminal. Описания экранов F-SPEC повторяют «only
  roles from the Tokens table; no colors of its own» (например `F-SPEC.md:82`, `:125`). BRIEF
  (`docs/design/BRIEF.md:86`): цвета статусов различаются светлотой, не только оттенком; синий и
  оранжевый лучше красного и зелёного; цвет всегда в паре со словом или иконкой.
- **Вывод:** цвет по типу требует новых ролей в таблице Tokens. Без правки F-SPEC его делать нельзя.
- Оттенки статусов уже заняты: ready — зелёный (светлая тема) / лайм (тёмная), working — синий,
  blocked — оранжевый. Цвет типа не должен с ними спорить.

### 2.4 Какие связи уже известны

- **Binding** — Session или Subagent → Ticket или Epic. Сигналы по силе: ручной, запуск из worfy,
  `ticket claim`, `/epic-wave`, ветка или worktree, `/ship-ticket`, путь Ticket-а в задаче Subagent-а
  (`resolve.ts:1-20`).
- **Edge-и сейчас:** Blocked by между Ticket-ами (`src/renderer/canvas/edges/blocking.ts`), Session →
  дерево Subagent-ов (`edges/subagents.ts`), пунктир Binding (`edges/bindings.ts:1-8`: у работающего
  агента всегда, у остальных — при наведении или выделении).
- **Готовые группы:** Epic frame — родитель Ticket-ов, сворачивается (по умолчанию свёрнут, когда все
  Ticket-ы done, `epics.ts:9-10`). Session — родитель дерева Subagent-ов, done Subagent-ы свёрнуты в
  строку «N done» (`sources/subagents.ts:3`). Теги — свободные строки без цвета
  (`src/renderer/canvas/tags.ts:1-4`), фильтр по тегу в палитре команд.
- **Чего нет:** групп для Session-ов, места Session-а рядом с её Epic-ом (кроме «Ship ticket»),
  подсветки «семьи» связанных Node-ов.

### 2.5 Ограничения

- **ADR-0011** (рамки и Ticket-ы — производные, Layout хранит только ручные изменения): место рамки
  считается, хранится только смещение пользователя. Новая раскладка рамок это сохраняет.
- **ADR-0016** (корзина и undo): всё автоматическое шлёт операции Layout мимо истории ⌘Z. Иначе ⌘Z
  начнёт отменять работу автомата вместо шагов пользователя.
- **ADR-0032** (колонка рамок обходит Node-ы): переход к нескольким колонкам или к упаковке меняет
  его пункт 1. Нужен новый ADR.
- **ADR-0038** (Node-ы не перекрываются): любое новое место проходит через `freePlace`, зазор 16 px.
- **ADR-0053** (несколько экранов на одном Project): Layout общий, камера и ⌘Z у каждого экрана свои.
  Значит, раскладка рамок не может зависеть от размера окна: два экрана увидели бы разные места, а
  смещения пользователя считались бы от разных точек.
- **Read-only экран Linked machine** (ADR-0066): перетаскивание выключено
  (`src/renderer/canvas/Canvas.tsx:524`, `src/renderer/canvas/read-only-nodes.ts:1-3`). Команды,
  которые двигают или убирают Node-ы, там недоступны.
- **Производительность:** `onlyRenderVisibleElements` (`Canvas.tsx:542`) не помогает на дальнем
  zoom — тогда видно всё. Card уже перестаёт рисовать живое содержимое ниже zoom 0.4
  (`LIVE_ZOOM_MIN`, `nodes/CardNode.tsx:27`). Предела числа Node-ов нет.

## 3. Четыре задачи и варианты решения

Цена: **S** — до дня работы одного агента, **M** — 2–4 дня, **L** — неделя и больше или новая
подсистема.

### P1. Компактное размещение Epic frame-ов

**Вариант 1a. K колонок вместо одной (masonry с постоянным распределением).**

- Как: `stackFrames` раскладывает рамки не в одну, а в K колонок. Рамка номер `i` всегда идёт в
  колонку `i mod K`. K считается из суммарной площади рамок и целевого соотношения сторон области
  (например 16:10): `K = round(sqrt(площадь × 1.6) / ширина колонки)`, не меньше 1.
- Почему постоянное распределение, а не «в самую короткую колонку»: выросла рамка — сдвигаются только
  рамки ниже в той же колонке. Остальные стоят.
- Что меняется: `epic-layout.ts` (`stackFrames`; `frameColumnX` ищет место для полосы шириной K
  колонок). Вход `sources/epics.ts` не меняется. Данные — только уже известные размеры рамок.
- Плюсы: малое изменение ADR-0032 (колонка → полоса из K колонок); детерминировано, одинаково на всех
  экранах; смещения пользователя работают как прежде. Минусы: с новым Epic-ом K может вырасти на 1 —
  рамки перераспределятся один раз; широкая полоса чаще упирается в Node-ы и уезжает вправо.
- Риски: мысленная карта (представление пользователя о том, где что лежит) ломается при смене K.
  Смягчение: гистерезис (K меняется, только если соотношение сторон ушло дальше чем на 30 %) или K в
  Settings. ⌘Z не затронут: раскладка автоматическая. Read-only экран видит то же самое.
- Цена: **S**.

**Вариант 1b. ELK `rectpacking` на верхнем уровне с `desiredPosition`.** Рамки как прямоугольники
без Edge-ей уходят в ELK `rectpacking` [1] в том же Web Worker (`elk/client.ts`), с `elk.aspectRatio`
[3] и порядком прошлого прогона в `rectpacking.desiredPosition` [2]. ELK уже упаковывает Node-ы для
«Tidy up» (`elk/pack.ts:31-32`); из библиотек раскладки для React Flow вложенные группы умеет только он
[9]. Плюс — плотнее колонок при рамках очень разной ширины. Минусы — асинхронно (до ответа ELK рамки
стоят на старых местах), и упаковка рядами: рамка выросла — сдвигается весь ряд и всё ниже.
Интерактивные режимы ELK держат порядок не идеально [4]. Риск — дрожание мест при каждой смене
статуса Ticket-а и двойной путь «синхронно до ответа, асинхронно после», как внутри рамок (ADR-0037).
Цена **M**.

**Вариант 1c. Свой упаковщик рядами (shelf / potpack).** Синхронная функция вроде `potpack`
(Mapbox, около 1 KB) [5] или `shelf-pack` [6] прямо в `epic-layout.ts`: ряды заданной ширины, рамки
по порядку. Плюс — без worker-а; минус — те же сдвиги рядами, что у 1b, а `potpack` не держит
порядок. Цена **S–M**.

**Вариант 1d. Полка готовых Epic-ов и порядок по активности.**

- Как: Epic, у которого все Ticket-ы done, не занимает рамку в общей раскладке. Он становится chip-ом
  на полке «Готовые Epic-и» (имя и `8/8`) под рамками. Клик по chip-у разворачивает рамку. Остальные
  Epic-и идут в порядке: сначала с работой (claimed Ticket, живой агент, Autopilot), потом остальные.
- Что меняется: `sources/epics.ts` (какие рамки идут в `stackFrames`), новый источник Node-ов «полка»
  (`canvas/sources/`). Флаг `collapsed` уже есть (`epics.ts:9-10`).
- Плюсы: на скриншоте это сразу минус три рамки. Активное — наверху, его видно без прокрутки.
- Минусы: порядок по активности меняется сам — рамка прыгает, когда агент взял Ticket. Смягчение:
  пересчитывать его только при открытии Project-а и по команде «Re-pack».
- Цена: полка — **S**, порядок по активности — **S**.

**Вариант 1e. Epic как вложенный Canvas** (как доски в Muse [11]). Рамка — компактная карточка,
двойной клик открывает Epic отдельным Canvas. Ломает идею «весь Project на одном Canvas»,
Binding-линии между уровнями не видны. Цена **L**. Не рекомендую.

**Прецеденты P1.** ELK `rectpacking`, `desiredPosition`, `aspectRatio` [1][2][3]; ограничения
интерактивной раскладки ELK [4]; перенос по ширине в Figma auto layout [33]; сохранение мысленной
карты [7] и данные, что её польза больше в удобстве, чем в скорости задач [8] — отсюда кнопка
«Re-pack» вместо постоянной перестановки; секции Heptabase с читаемыми на любом zoom заголовками [10].

```
 После P1 (1a + 1d): K = 3 колонки, готовые Epic-и — chip-ы на полке

 ┌─ harness ──┐  ┌─ link ───────┐  ┌─ neutral ──┐
 │ ▢ ▢ ▢      │  │ ▢ ▢ ▢ ▢ ▢    │  │ ▢ ▢ ▢      │
 └────────────┘  │ ▢ ▢          │  └────────────┘
 ┌─ pipeline ─┐  └──────────────┘  ┌─ polish ───┐
 │ ▢ ▢        │  ┌─ terminal-ai ┐  │ ▢          │
 └────────────┘  │ ▢ ▢ ▢        │  └────────────┘
 ┌─ windows ──┐  └──────────────┘  ┌─ ui ───────┐
 │ ▢ ▢ ▢ ▢    │  ┌─ throughput ─┐  │ ▢ ▢        │
```

### P2. Автоуборка законченных Session-ов

**Правило (общее для всех вариантов «куда»).**

- Кандидат — Session Node, у которого Session не живая (её нет в реестре живых) **и** выполнено одно
  из двух:
  - простой дольше порога N по `lastAt` транскрипта (по умолчанию 24 ч);
  - её Ticket done и с конца Session прошло больше 1 ч.
- Никогда не убираются: живая Session, Orchestrator, закреплённый (`pinned`) Node, Node с флагом
  «Keep» (новое поле, ставит пользователь), Session, которую пользователь открывал или двигал за
  последние N часов (как у Arc: просмотр сбрасывает таймер).
- Не знаем — не убираем: статус `unknown` считается живым. То же правило, что в ADR-0031 (закрытая
  Session кончает своих Subagent-ов; «не знаем — не закрываем»).
- Subagent-ы уходят вместе со своей Session — как в Linear sub-issue ждёт родителя. Отдельно их не
  убираем: дерево уже сворачивает done Subagent-ов.
- Session, которую продолжили (`claude --resume`), возвращается на Canvas на старое место.

**Кто убирает.** Main, по таймеру (например раз в 10 минут и при старте). Main — единственный
писатель Layout (ADR-0003). Так уборка идёт один раз, даже если Project открыт на двух экранах
(ADR-0053), и работает, когда смотрит только read-only Linked machine. Операции идут мимо ⌘Z
(ADR-0016). Данные: реестр живых Session-ов и история транскриптов уже читаются в main
(`src/main/claude-home/`), статусы Ticket-ов — в модели workflow main.

Где хранить: поле `archived: { at, rule }` у Node-а Layout-а. Не `hidden`: скрытое пользователем и
убранное автоматом должны различаться, иначе «показать скрытые» вернёт сотню старых Session-ов.

**Вариант 2a. Сворачивать в chip на месте** (как Chrome Memory Saver оставляет от вкладки заголовок
и иконку [20]). Node становится полоской 300×28 с заголовком и временем конца. Ничего не исчезает,
но колонка лишь короче примерно в 4 раза — через месяц снова длинная. Цена **S**.

**Вариант 2b. История у своего Ticket-а или Epic-а.** Session с Binding уходит с Canvas, у Ticket-а
появляется badge «3 sessions», в шапке Epic frame-а — «12 sessions». Клик открывает список; «Show»
возвращает Node рядом с Ticket-ом. Для этого уже есть Binding (`resolve.ts`) и якоря Binding-линий
(`sources/workflow-bindings.ts`). Session находится там, где её будут искать. Минус — Session без
Binding сюда не попадает. Цена **M**.

**Вариант 2c. Popover «Архив».** Кнопка «Archive N» рядом с кнопкой Trash внизу Canvas (устроена как
`overlays/TrashPopover.tsx`): список по дате, поиск, «Restore», «Restore all from today», без срока
хранения. Одно место для всего убранного, в том числе без Binding; без 2b связь с работой теряется.
Цена **S–M**.

**Вариант 2d. Trash** — не подходит. Trash удаляет записи через 3 дня (`shared/ipc/trash.ts:12`)
и по ADR-0016 принимает только удаления пользователя. Автомат с удалением через 3 дня теряет данные.

**Прецеденты P2.** Arc архивирует незакреплённые вкладки после 12 ч простоя, просмотр сбрасывает
таймер, архив ищется [19]. Linear архивирует законченные issue, sub-issue ждёт родителя [21]. VS Code
закрывает старые редакторы сверх лимита, но не несохранённые [22]. Destalinator сначала
предупреждает, потом архивирует [23]. Things переносит сделанное в Logbook, а не удаляет [24].
Undo после действия лучше подтверждения до него [25]. Пользователи Claude Code desktop уже просят
массовый архив Session-ов [26].

**Undo.** После уборки — toast: «Archived 7 finished sessions · Undo». Undo — отдельная операция
«вернуть эту партию», не шаг ⌘Z (автомат идёт мимо истории). Компонента toast-а в renderer нет; его
заводит Ticket worfy-ui 16 (внутренние toast-ы: одно хранилище и один компонент; статус open). P2
ждёт его или делает временную надпись, как «⌘Z пропущен» (`overlays/UndoSkipped.tsx`).

**Настройка.** Settings → Canvas: «Archive finished sessions after: Never / 6 h / 24 h / 3 days /
7 days», по умолчанию 24 h; галочка «…and when their Ticket is done». Плюс команда палитры «Archive
finished sessions now» — это жест пользователя, один шаг ⌘Z.

**Риски.** Пользователь не найдёт Session, которую искал вчера: смягчают поиск в архиве и уже
существующая History в боковой панели. Таймер считает время Machine Project-а, не Linked machine.
Производительность — только выигрыш.

### P3. Различать Node-ы по типу

**Вариант 3a. Токены типа (`kind-*`) + полоса в шапке + иконка.**

- Как: в таблицу Tokens F-SPEC добавляются роли типа: `kind-orchestrator`, `kind-session`,
  `kind-subagent`, `kind-epic`, `kind-ticket`. По два значения на тему: насыщенное «band» (полоса 4 px
  в шапке, иконка, Minimap) и бледное «tint» (фон шапки). Текст статуса этими цветами не красится.
- Палитра — от Okabe–Ito [13] (8 цветов, различимых при частых нарушениях цветового зрения). Оттенки
  статусов уже заняты: зелёный/лайм (ready), синий (working), оранжевый (blocked). Черновик, который
  надо проверить скриптом контраста и симуляцией нарушений зрения до ADR:

| Тип | Оттенок | Okabe–Ito | Чем ещё отличается (не только цвет) |
| --- | --- | --- | --- |
| Orchestrator | пурпурный | #CC79A7 | крупнее (360×200), своя иконка, двойная рамка |
| Session | небесно-голубой | #56B4E9 | иконка prompt `>_`; светлее синего working |
| Subagent | как у Session, только контур | #56B4E9 | меньше (260×84), пунктирная полоса, висит на своей Session |
| Epic frame | жёлтый, в светлой теме охра | #F0E442 | контейнер с толстой шапкой и прогресс-баром |
| Ticket | нейтральный (поверхность) | — | номер моноширинным шрифтом; тип ясен по месту в рамке |
| Card, Note, Terminal, HANDOFF | нейтральные, как сейчас | — | свои иконки |

- Четыре оттенка типа вместе с тремя статусными — в пределе, который Munzner называет рабочим для
  категорий (6–12 вместе с фоном), но близко к нему. Больше типов цветом не кодировать.
- Состояние «finished» — через непрозрачность (например 60 %) и слово в chip-е, не через оттенок.
- Что меняется: `docs/design/F-SPEC.md` (таблица Tokens), `src/renderer/theme/tokens.css`, шапки
  Node-ов (`src/renderer/canvas/NodeChrome.tsx`, `nodes/*Node.tsx`), `minimapColor` в каждом типе.
- Плюсы: тип виден сразу; Minimap перестаёт быть серым. Минусы: правка дизайн-системы, новые
  e2e-снимки обеих тем.
- Риски: спор оттенков типа и статуса (голубой Session рядом с синим working). Поэтому тип — только в
  полосе и иконке, статус — только в chip-е со словом (BRIEF.md:86, WCAG 1.4.1).
- Цена: токены и шапки — **M**.

**Вариант 3b. Только форма и иконка, без нового цвета.** Разные радиусы, рамки, иконки, размеры;
F-SPEC почти не трогается. Но на дальнем zoom форма и иконка не читаются — а проблема видна именно
там. Цена **S**.

**Вариант 3c. Semantic zoom.**

- Как: три уровня. Zoom ≥ 0.6 — полная карточка. 0.3–0.6 — заголовок и статус-chip, без тела. Ниже
  0.3 — блок цвета типа с крупным заголовком; размер шрифта держится постоянным на экране. Заголовок и
  прогресс Epic frame-а читаются на любом zoom (так делает Heptabase с секциями).
- Реализация — шаблон React Flow «contextual zoom»: Node читает zoom из store и выбирает уровень.
  Подписка только на номер уровня, чтобы Node не перерисовывался на каждом шаге zoom. Прецедент в
  коде — Card ниже 0.4 (`CardNode.tsx:27`).
- Плюсы: лечит «мелкие нечитаемые карточки» со скриншота; на дальнем zoom меньше DOM. Минусы: пороги —
  компромисс, e2e на каждый уровень. Цена: **M**.

**Вариант 3d. Цвет в Minimap.** Minimap красит Node-ы по `kind-*`, рамки Epic-ов — прямоугольник
цвета Epic. Можно делать сразу после ADR о токенах. Цена **S**.

**Прецеденты P3.** Палитра Okabe–Ito [13] и правило «цвет всегда в паре с формой или словом» [14];
предел числа категорий цвета у Munzner [15]; цвет вместе с формой — CatPAW [35]; WCAG 1.4.1 [16];
Node-RED: цвет Node-а задан типом, цвет группы — пользователем [12]; JSON Canvas: небольшой набор
готовых цветов [36]; semantic zoom [17], три уровня zoom в Wonderbits [34], contextual zoom в React
Flow [18].

### P4. Группировка по смыслу и связям

**Вариант 4a. Подсветка «семьи» при наведении и выделении.**

- Как: наводишь на Ticket — его Session-ы, их Subagent-ы, его Epic frame и Binding-линии остаются
  яркими, остальное тускнеет до 30 %. Наводишь на Session — её Ticket и Epic. Это паттерн
  focus+context (так делает sigma.js через reducers [31]).
- Что меняется: `src/renderer/canvas/edge-focus.ts` (подсветка уже своя у каждого окна, ADR-0053)
  расширяется до Node-ов. Семья строится из Binding (`resolve.ts`) и дерева Subagent-ов.
- Плюсы: Node-ы не двигаются — мысленная карта цела, ⌘Z не нужен, работает на read-only экране и на
  нескольких экранах. Минус: родственники за краем экрана не видны; помогает команда «Show family»,
  камера охватывает всю семью (`focusEpic` уже есть, `sources/epics.ts:161`). Цена: **S–M**.

**Вариант 4b. Session рядом со своим Epic-ом: место при создании и команда «Arrange by Epic».**

- Шаг 1: новая Session с Binding (любой сигнал из `resolve.ts`, не только «Ship ticket») встаёт
  справа от рамки своего Epic-а, на высоте Ticket-а — обобщение `placeDownFrom` (`place.ts:31`).
  Binding по ветке появляется не сразу; Node, поставленный до Binding, не двигается.
- Шаг 2: команда «Arrange by Epic» (как «Tidy up» в `src/renderer/canvas/tidy.ts`: один `moveMany`,
  один шаг ⌘Z). Кластер = Epic frame + его Session-ы с деревьями Subagent-ов в колонке справа.
  Session-ы без Binding — отдельный кластер «Unbound». Кластеры раскладываются, как рамки в P1.
- Плюсы: «группировались по смыслу и связям» ровно в смысле запроса. Пользователь сам решает, когда.
- Минусы: Session-ы — Node-ы пользователя. Двигать их без жеста — против ADR-0011 («Layout хранит
  ручные изменения»). Поэтому только по команде или при создании.
- Риски: K колонок рамок (P1) плюс колонка Session-ов увеличивают ширину кластера; нужен общий расчёт.
- Цена: шаг 1 — **S**, шаг 2 — **M**.

**Вариант 4c. Док Session-ов как Derived-часть рамки.** Session-ы с Binding к Epic-у рисуются сбоку
рамки, место считает источник `epics.ts` (как дерево Subagent-ов). Всегда упорядочено, но две модели
места для одного типа Node-а, смена Binding двигает Node сама, меняются ADR-0011 и ADR-0038. Цена **L**.

**Вариант 4d. Swimlanes** (ряд на Epic, колонки «рамка | живые Session-ы | законченные», как
partition grid в yFiles [27]). Предсказуемо, но жёсткая сетка против свободного Canvas; Card, Note,
Terminal в неё не входят. Цена **L**. Не рекомендую.

**Вариант 4e. Edge-и и группы по графу.** Edge bundling (сгибать линии вдоль иерархии [30]) и Bubble
Sets (контур вокруг членов группы без их движения [29]) — для связей через несколько рамок. Связные
компоненты или Louvain (поиск сообществ в графе [28]) нужны, только если появится много Node-ов без
Binding. Сейчас Binding даёт группы явно. Не делать, пока нет данных, что 4a и 4b не хватает. Цена
**M–L**.

**Прецеденты P4.** Подсветка соседей и приглушение остальных в sigma.js [31]; соседи за краем экрана
— отдельный вид в yWorks [32]; Session + Subagent-ы как дерево — так же устроены трассы агентов
(вложенные spans) [37].

## 5. Рекомендуемый план

Предлагаю завести Epic (рабочее имя `worfy-canvas`). Ниже — кандидаты в Ticket-ы, не готовые
Ticket-ы.

### Фаза 0 — решения до кода

Три ADR, номера — через preflight:

- **ADR «Рамки Epic-ов — K колонок и полка готовых»** — меняет пункт 1 ADR-0032 (колонка → полоса из K
  колонок; готовые Epic-и — chip-ы на полке). Фиксирует: раскладка не зависит от размера окна.
- **ADR «Автоархив законченных Session-ов»** — правило, исключения, исполнитель (main), поле
  `archived`, связь с ⌘Z (мимо истории) и с toast-ом.
- **ADR «Токены типа Node-а»** + правка таблицы Tokens в F-SPEC: роли `kind-*`; где их можно применять
  (полоса, иконка, Minimap, блок дальнего zoom) и где нельзя (текст статуса).

### Фаза 1 — быстрые выигрыши, все параллельно

1. **Рамки Epic-ов в K колонок.**
   `stackFrames` и `frameColumnX` раскладывают рамки по колонкам `i mod K`; K из площади и целевого
   соотношения 16:10, с гистерезисом.
   _Готово, когда:_ 11 рамок Project-а CanvasForAI занимают не больше 1,5 высоты экрана при «fit»;
   смена статуса Ticket-а двигает только рамки ниже в той же колонке (unit-test); результат не
   зависит от размера окна (unit-test на чистой функции).
2. **Полка готовых Epic-ов.**
   Epic со всеми Ticket-ами done — chip «✓ имя N/N» на полке; клик разворачивает рамку.
   _Готово, когда:_ три готовых Epic-а со скриншота стоят chip-ами; разворот и сворачивание — шаг ⌘Z;
   e2e-снимок в обеих темах.
3. **Подсветка семьи при наведении.**
   Hover или выделение Ticket-а, Session, Subagent-а или Epic frame-а приглушает всё вне семьи;
   команда «Show family» подгоняет камеру.
   _Готово, когда:_ семья строится из Binding и дерева Subagent-ов (unit-test); работает на read-only
   экране; другой экран того же Project-а не меняется.
4. **Minimap по типу** (после ADR о токенах).
   Каждый тип объявляет `minimapColor` из `kind-*`; рамки Epic-ов видны цветом.
   _Готово, когда:_ в Minimap различимы Session, Orchestrator, Subagent и рамки в обеих темах.

### Фаза 2 — тип и zoom

5. **Токены и шапки типа.**
   Роли `kind-*` в `tokens.css` для двух тем; полоса и иконка в шапке каждого типа; finished —
   приглушённая непрозрачность.
   _Готово, когда:_ контраст полосы и иконки к поверхности ≥ 3:1, текста ≥ 4.5:1 (скрипт); симуляция
   протанопии и дейтеранопии различает типы; e2e-снимки обеих тем обновлены.
6. **Semantic zoom.**
   Три уровня вида Node-а по zoom; заголовок рамки Epic-а постоянного экранного размера.
   _Готово, когда:_ на zoom 0.15 читаются имена Epic-ов и типы карточек; смена zoom внутри уровня не
   перерисовывает Node-ы (счётчик рендеров в test-е); e2e-снимки на трёх уровнях.

### Фаза 3 — уборка

7. **Правило автоархива в main.**
   Таймер в main; правило и исключения из ADR; поле `archived` в Layout; продолженная Session
   возвращается.
   _Готово, когда:_ unit-test на каждое исключение (живая, `unknown`, pinned, Keep, Orchestrator,
   недавно тронутая); два окна — одна уборка; read-only экран видит результат без ошибок.
8. **Настройка и команда.**
   Settings → Canvas: порог и галочка «Ticket done»; команда палитры «Archive finished sessions now» —
   один шаг ⌘Z.
   _Готово, когда:_ «Never» выключает таймер; команда и её ⌘Z проверены e2e.
9. **История у Ticket-а и Epic-а + popover «Архив».**
   Badge «N sessions» у Ticket-а и в шапке рамки; popover архива рядом с Trash; «Show» и «Restore».
   _Готово, когда:_ Session с Binding видна в истории своего Ticket-а, без Binding — в архиве; Restore
   ставит Node на свободное место (ADR-0038).
10. **Toast с Undo** (после worfy-ui 16 — внутренних toast-ов).
    «Archived N finished sessions · Undo» после каждой партии.
    _Готово, когда:_ Undo возвращает ровно эту партию; на read-only экране toast без кнопки Undo.

### Фаза 4 — группировка

11. **Место новой Session у её Epic-а.**
    Session с Binding при создании встаёт справа от рамки Epic-а, на высоте Ticket-а.
    _Готово, когда:_ unit-test на функцию места; Node без Binding ставится по-старому.
12. **«Arrange by Epic».**
    Команда палитры и меню Canvas: кластеры «рамка + Session-ы» и «Unbound»; один `moveMany`, один ⌘Z.
    _Готово, когда:_ повторная команда ничего не двигает; ⌘Z возвращает всё; на read-only экране
    команды нет.
13. **(Если понадобится) ELK `rectpacking` для верхнего уровня.**
    Только если K колонок оставят заметную пустоту при рамках очень разной ширины.

**Параллельность.** Фаза 1 — четыре независимых кандидата (Minimap ждёт только ADR о токенах).
Фазы 2 и 3 идут параллельно: они меняют разные файлы (шапки Node-ов и тема — против main и Layout).
Кандидат 10 (toast с Undo) ждёт worfy-ui 16. Фаза 4 — после кандидата 1 (рамки в K колонок): ей
нужна новая раскладка рамок.

## 6. Вопросы владельцу

1. **Можно ли раскладке рамок самой менять K и переставлять рамки без жеста пользователя?**
   Рекомендую: да. Рамки и так производные и двигаются сами; K — с гистерезисом.
2. **Порядок Epic-ов: постоянный (как сейчас) или «активные сначала»?**
   Рекомендую: постоянный внутри дня; «активные сначала» — при открытии Project-а и по команде
   «Re-pack».
3. **Готовые Epic-и — на полку chip-ов?**
   Рекомендую: да, полка под рамками.
4. **Порог автоархива по умолчанию.**
   Рекомендую: 24 часа простоя, плюс «Ticket done и прошёл 1 час». Выбор: Never, 6 h, 24 h, 3 d, 7 d.
5. **Куда уходят убранные Session-ы.**
   Рекомендую: с Binding — в историю своего Ticket-а или Epic-а; без Binding — в popover «Архив».
   Не в Trash.
6. **Автоархив включён по умолчанию во всех Project-ах?**
   Рекомендую: да, с toast-ом и Undo. Выключается в Settings.
7. **Какие типы получают цвет.**
   Рекомендую: Orchestrator — пурпурный, Session — голубой, Subagent — голубой контур, Epic frame —
   жёлтый (охра в светлой теме), Ticket — нейтральный; Card, Note, Terminal, HANDOFF — нейтральные.
   Утвердить после проверки контраста.
8. **Можно ли менять F-SPEC и вводить роли `kind-*`?**
   Рекомендую: да, отдельным ADR. Цвет типа — только полоса, иконка, Minimap и блок дальнего zoom.
9. **Двигать ли Session-ы к их Epic-у автоматически?**
   Рекомендую: нет. Только место новой Session и команда «Arrange by Epic».
10. **Перебивает ли «Arrange by Epic» ручное размещение?**
    Рекомендую: да, но только по команде и одним шагом ⌘Z. Node-ы с `pinned` и «Keep» не двигаются.
11. **Semantic zoom сразу или после цвета?**
    Рекомендую: параллельно с токенами. Без него цвет на дальнем zoom помогает мало.
