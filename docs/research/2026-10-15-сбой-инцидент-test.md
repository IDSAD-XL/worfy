# Сбой → инцидент → регрессионный test или «урока нет»: предложение процесса

Дата: 2026-10-15. Статус: предложение, ждёт решения владельца.
Ticket: `worfy-reliability` 03 (идея E исследования [PR #325](https://github.com/IDSAD-XL/worfy/pull/325)).
Документ ничего не меняет: `harness/`, Profile и `src/` остаются как есть. Правки — отдельными
Ticket-ами после решения владельца.

## Коротко

1. Каждый сбой сначала записывается как инцидент: симптом, ссылки, воспроизведение, корневая причина.
2. Инцидент сверяется с уже известными причинами (дедупликация) и получает один из шести классов.
3. Класс определяет вывод: детерминированная проверка (красная до правки, зелёная после) или явное
   «урока нет» с причиной. Новое правило prompt-а без проверки — не вывод.

## Что есть сейчас

- **Урок не связан с проверкой.** Формат урока — заголовок-утверждение, суть, путь к коду, источник
  (`docs/lessons/README.md:20-21`). Поля «чем это проверяется» нет. Из 33 уроков в четырёх файлах
  `docs/lessons/` строку `Код:` имеют 8, и только 2 из них указывают на файл test-а:
  `test/unit/free-place.test.ts:201` (`docs/lessons/testing.md:73`) и helper `test/e2e/snapshots.ts`
  (`docs/lessons/testing.md:53`). Остальные уроки ничем не проверяются: следующий исполнитель узнает о
  повторе, только если повтор заметит человек.
- **Skill `retro` не классифицирует причину.** Он отсеивает «одноразовые промахи и сбои окружения»
  (`harness/skills/retro/SKILL.md:57-61`) и ищет дубликаты среди уже записанных уроков (`:63-66`).
  Куда идёт сбой окружения, если не в урок, skill не говорит. Требования доказать урок test-ом нет.
- **Часть правил Harness уже стала детерминированной.** PreToolUse hook `harness/hooks/guard.mjs`
  отказывает командам, которые стирают незакоммиченную работу, и pipe-ам, которые теряют exit code
  (`guard.mjs:1-3`). Это образец вывода «правило → проверка кодом», а не текстом prompt-а.
- **Eval-кейсы есть, платного прогона нет.** Кейсы лежат в `harness/evals/` (11 папок), но
  `worfy-harness` 27 (платная часть eval) ждёт 28, а 29 (карта «кейс → файлы правил») — оба
  (`HANDOFF.md:5`, `:52`). Проверить правило prompt-а прогоном eval сейчас нельзя.
- **Прецедент процесса уже был.** Каждая остановка прогонов Autopilot 1–3 стала Ticket-ом или правилом,
  и прогон 4 провёл три Wave подряд без человека (`docs/lessons/process.md:64-72`). Не хватает
  записи: какая проверка теперь сторожит каждую из этих причин.

## Классы инцидента

Класс ставится по корневой причине, а не по симптому. Один симптом бывает у разных причин:
таймаут первого окна в e2e дают заблокированный экран, параллельные e2e и окно macOS «восстановить
окна?» (`docs/lessons/agents.md:38-67`, `HANDOFF.md:46`).

Если ни один класс не подтвердился — причина не найдена, — инцидент остаётся открытым с пометкой
«причина не найдена» и признаками для следующего раза. Это не «урока нет»: «урока нет» ставится только
при известной причине.

## Шаги процесса

1. **Сбой.** Красный gate или CI, `blocked` Ticket, остановка прогона Autopilot, ручное вмешательство
   владельца.
2. **Запись инцидента.** В «Итог» Ticket-а, где сбой проявился, — подраздел «Инцидент» (вариант места
   записи — решение владельца 2). Поля:
   - **Симптом** — команда, exit code, первая строка ошибки;
   - **Ссылки** — PR, раздел «Итог», строка журнала Autopilot
     (`~/Library/Application Support/worfy/autopilot/*.jsonl`, номер строки, без текста транскрипта),
     commit;
   - **Воспроизведение** — на чистом main или только на ветке; сколько красных из скольких прогонов;
   - **Корневая причина** — одно предложение и файл, или «причина не найдена»;
   - **Дубликат** — ссылка на урок, строку «Риски и долги» `HANDOFF.md` или прошлый инцидент, или «нет».
3. **Дедупликация по корневой причине.** Поиск по `docs/lessons/`, `HANDOFF.md` и разделам «Итог»
   (qmd, коллекции `worfy-docs` и `worfy-tickets`). Совпал симптом, но не причина — это новый инцидент
   со ссылкой на соседний. Совпала причина — новый инцидент не заводится: к старой записи
   добавляется дата повтора. Повтор после вывода — сигнал, что вывод не работает (см. разбор 4 ниже).
4. **Класс** — по таблице выше, с тем подтверждением, которое она требует. Без подтверждения класс не
   ставится.
5. **Вывод.**
   - Детерминированная проверка: имя test-а, `file:line`, commit, на котором он красный, и commit, на
     котором зелёный. Для нестабильного test-а — число красных из N повторов до правки и после.
   - Или «урока нет: <причина>» — например, «временный сбой, признак и лечение — `HANDOFF.md`, «Риски и
     долги»».
6. **Урок**, если вывод обобщается за пределы Ticket-а (`docs/lessons/README.md:15-18`), получает строку
   `Проверка:` — `file:line` test-а, hook, eval-кейс или «урока нет: …».

## Что процесс не поощряет никогда

- **Выключить или пропустить нестабильный test вместо разбора.** Нет `it.skip`, `test.fixme`, retry в
  Playwright или «повторить gate, пока не зелёный». Playwright в Project-е намеренно без retry
  (`playwright.config.ts:6-7`). Допустимый `skip` — только по условию возможности машины (платформа,
  право создать symlink, поведение файловой системы) с комментарием «почему», как сейчас в `test/`
  (`test/contract/workflow-reader.test.ts:864-867`: inotify на Linux шлёт больше событий, test идёт в
  gate на Mac и Windows), и никогда — по «падает иногда».
- **Перевести Ticket из `blocked` в `done` без доказательства.** Закрытие — только PR, вливание и
  проверки, которые требует «Готово, когда».
- **Обойти Gate.** «Временный сбой» не даёт права вливать при красном gate full: класс подтверждается
  зелёным повтором того же commit-а после лечения, и мерж идёт после этого повтора.
- **Добавить правило prompt-а без проверки, что оно что-то меняет.** Правило, которое нарушается
  после записи, — не вывод, а новый инцидент класса «правило Harness».
- **Записать в урок то, что выдумано.** Каждое поле записи — ссылка на артефакт; «наверное» в поле
  «Корневая причина» не пишется, пишется «причина не найдена».

## Проверка на прошлом: пять сбоев

### 1. `fseventsd` краснил gate full (2026-10-12 23:04 – 10-13 01:02)

- **Что было.** Test-ы наблюдателей `docs.test.ts` и `claude-home-registry.test.ts` красные и на main;
  `fseventsd` держал 102–116 % CPU и 4,2 ГБ; лечение — `sudo killall fseventsd` (`HANDOFF.md:35`).
- **Класс по процессу.** Временный сбой машины — но только после проверки дубликата. `worfy-windows` 26
  связывает рост `fseventsd` с папками, которые test-ы оставляли во временном каталоге (57 487 записей
  `worfy-*`), и прямо пишет «причина не доказана»
  (`.scratch/worfy-windows/issues/26-test-ы-на-windows-оставляют-папки-в-temp.md:36-41`).
- **Вывод.** Запись в «Риски и долги» уже есть. Утечка папок — отдельная корневая причина класса
  «слабая fixture или test», и у неё уже есть test против возврата `test/unit/no-rmsync.test.ts`
  (там же, «Итог», `:129`). Урока «как распознать» в `docs/lessons/` нет: признак живёт только в
  `HANDOFF.md`, который — снимок и будет сжат.
- **Расхождение с историей.** Процесс добавил бы урок в `docs/lessons/agents.md` рядом с другими
  ложно-красными причинами e2e и связал бы его с `no-rmsync.test.ts`.

### 2. Claude Code 2.1.296 мог выполнить одобренный вызов tool дважды

- **Что было.** CHANGELOG Claude Code: регрессия в 2.1.296, исправлена в 2.1.299
  (`.scratch/worfy-reliability/issues/01-рестарт-session-без-повтора-действий-и-правило-обновления-sdk.md:51-54`).
  У worfy SDK `0.3.289` (`package.json:28`), внутри — Claude Code 2.1.289
  (`.scratch/worfy-harness/issues/27-eval-кейсы-harness-через-plugin-eval.md:35-37`): worfy этот сбой
  не задел.
- **Класс.** Регрессия SDK поставщика, предупреждённая до проявления.
- **Вывод.** Правило версий «поднимать SDK только до Claude Code ≥ 2.1.299» и заново снятая fixture
  `test/fixtures/sdk-messages/` (Ticket 01, «Что делаем», пункт 3, `:71-74`). Fake SDK такой повтор не
  ловит (`:53-54`), поэтому eval-кейс или правило prompt-а здесь ничего не добавят.
- **Расхождение с историей.** Нет: Ticket 01 уже идёт этим путём.

### 3. `processState` сводил «не знаю» к «нет»

- **Что было.** Сбой `ps` (ненулевой код, таймаут, пустой вывод) считался ответом «процесса нет»;
  Session объявлялась закрытой, её Subagent-ы — `error` (`docs/lessons/testing.md:13-19`;
  `worfy-daily` 08, круг доработки PR #45).
- **Класс.** Дефект кода: `src/main/claude-home/registry.ts:225`.
- **Вывод.** Регрессионный test на все три ответа — `alive`, `gone`, `unknown` — уже есть:
  `test/contract/claude-home-registry.test.ts:355-360`.
- **Расхождение с историей.** Только в записи: урок называет код (`testing.md:20`), но не test. По
  процессу в уроке была бы строка `Проверка: test/contract/claude-home-registry.test.ts:355`.

### 4. `rm -rf` с переменной в пути ломал шаг агента

- **Что было.** На `rm -rf` с маской или переменной Claude Code спрашивает подтверждение даже в
  `bypassPermissions`; в Autopilot это отказ и сломанный шаг (прогоны 2 и 3). Правило записано
  текстом в `harness/agents/implementer.md:63-67` и `harness/agents/reviewer.md:122-125`. После
  записи его нарушили ещё четыре раза в Wave-ах 2 и 3 `worfy-harness`, а 2026-10-08 круг
  `worfy-harness` 22 стоял 50 минут на карточке разрешения (`docs/lessons/agents.md:87-106`).
- **Класс.** Правило Harness: правило есть, повтор не прекратился — вывод «правило в prompt-е» не
  сработал.
- **Вывод.** Нарушение видно механически по тексту команды, поэтому eval-кейс не нужен. Детерминированный
  вариант — отказ PreToolUse hook-а на `rm -rf` с маской или `$` в пути и test этого hook-а в
  `harness/hooks/tests/`. Сейчас `guard.mjs` разбирает только команды `git` (`guard.mjs:94`).
- **Расхождение с историей.** Большое: история дала второе и третье текстовое правило; процесс дал бы
  кандидат в Ticket Harness (решение владельца 5) и пометку «повтор после вывода» к старой записи.

### 5. e2e «long names» краснел без дефекта

- **Что было.** `test/e2e/epic-frame.spec.ts` «long names» мерил Node и его строки двумя отдельными
  чтениями; между ними ответ ELK сдвигал Node. На main c539cfd — 2 красных из 8, остановил мерж PR
  #109 (`.scratch/worfy-week/issues/06-snapping-при-перетаскивании.md:194-199`, подраздел «Долги из HANDOFF»).
- **Класс.** Слабый test: гонка в самом test-е, код приложения ни при чём.
- **Вывод.** Чтение Node и строк за один кадр анимации — commit `118f6588` (PR #201), helper
  `ticketRows` (`test/e2e/epic-frame.spec.ts:736`), проверки и допуск 0,5 px те же, retry нет.
  Запрещённые пути (skip, retry) не выбраны.
- **Расхождение с историей.** В описании commit-а `118f6588` нет числа прогонов после правки. По
  процессу оно обязательно: «до — 2 из 8, после — 0 из N под нагрузкой». Так же уже устроен
  `worfy-polish` 04 для трёх других нестабильных e2e (`--repeat-each=10` под нагрузкой CPU, «Что
  делаем», пункт 1).

## Решения владельца

1. Принять ли процесс и шесть классов (да / нет / с правками).
2. Где жить записи инцидента: подраздел «Инцидент» в «Итог» Ticket-а (предложение) или отдельный файл
   в `docs/` (журнал, который придётся сжимать, как `HANDOFF.md`).
3. Какие варианты встраивания брать: В1, В2, В3, В4 — и в каком порядке.
4. Строка `Проверка:` — только для новых уроков или дописать всем 33 существующим.
5. Брать ли Ticket Harness на отказ hook-а для `rm -rf` с маской или переменной (разбор 4).
6. Порог для нестабильного test-а: сколько повторов N и под какой нагрузкой считать «после — 0 красных»
   (`worfy-polish` 04 берёт 10).
7. Требовать ли для класса «временный сбой» зелёный повтор того же commit-а после лечения, прежде чем
   ставить класс (предложение — да).

## Ограничения

- Разбор сделан по пяти сбоям из `docs/lessons/`, разделов «Итог» и `HANDOFF.md`. Журналы Autopilot не
  читались: их разбирают `worfy-reliability` 02 и 04.
- Ошибка классификации возможна: `fseventsd` — пример, где «временный сбой» мог скрыть утечку test-ов.
  Поэтому класс ставится только с подтверждением из таблицы.
- Процесс добавляет запись к каждому сбою. Для мелкого промаха, который не обобщается, достаточно
  одной строки «урока нет: <причина>».
