# ponytail, pstack, Thermos: что взять в worfy Harness

- **Дата:** 2026-10-09
- **Статус:** исследование, не решение. Решения примут тикеты эпика `worfy-review`
  (эпик — группа связанных тикетов в `.scratch/worfy-review/issues/`).
- **Предмет:** три внешних проекта для AI-агентов, которые пишут и ревьюят код. Мы изучили их,
  чтобы решить, что заимствовать в worfy Harness. worfy Harness — это плагин Claude Code `worfy`,
  его исходники лежат в `harness/`. В нём есть skill-ы `ship-ticket`, `epic-wave`,
  `continuous-audit` и subagent-ы `worfy:implementer`, `worfy:reviewer`, `worfy:scout`.
- **Как собраны данные:** заметки трёх исследовательских subagent-ов и копии исходных файлов
  проектов, прочитанные через GitHub API 2026-10-09. Ничего из этих проектов не устанавливалось и
  не запускалось. Цифры, которые известны только со слов авторов (benchmark-и, звёзды), помечены.

## 1. ponytail

**Что это.** Skill и плагин Claude Code, который заставляет агента писать минимальное полное
изменение. Принцип YAGNI: не писать то, что не нужно сейчас. Есть адаптеры для Codex, Cursor,
Copilot, Gemini CLI и других агентов.

- **Автор:** Dietrich Gebert (GitHub `DietrichGebert`).
- **Лицензия:** MIT.
- **Репозиторий:** https://github.com/DietrichGebert/ponytail. Прочитана версия v5.1.0
  (`package.json`). SHA коммита в заметках не зафиксирован; его нужно записать при заимствовании.
- **Подлинность:** в сети есть копии и попытки выдать себя за проект. В обсуждении issue #502
  (жалоба на смещение review) кто-то приложил посторонний `install.sh`. Брать только из
  репозитория `DietrichGebert/ponytail` или npm-пакета `@dietrichgebert/ponytail`.

**Как устроен.** Суть — один prompt, `skills/ponytail/SKILL.md`, около 3,5 KB. Остальное —
адаптеры под разные агенты.

- Перед изменением агент перечисляет все места, куда оно должно дойти: вызывающий код, test-ы,
  fixture-ы, конфигурация, экспорты.
- Дальше — лестница вариантов, берётся первый, который полностью работает: (1) нужно ли это
  вообще; (2) есть ли это уже в кодовой базе; (3) стандартная библиотека или платформа;
  (4) уже установленная зависимость; (5) одна понятная строка; (6) минимальный рабочий код.
- Сокращение с известным пределом помечается комментарием `shortcut: <предел>, <когда менять>`.
- Никогда не урезаются: проверка входных данных на границе доверия, обработка ошибок, ведущих к
  потере данных, безопасность, доступность, всё, что попросил пользователь.
- Ответ агента заканчивается строкой о том, что не проверено, и о рисках.

Дополнительные skill-ы:

- `/ponytail-review` — review diff-а. Категории: Bug, Risk, Scale, Missing test, Speed, Lean.
  Lean — это «удалить, переиспользовать, взять из стандартной библиотеки, не нужно сейчас,
  слить, разделить». Правило «нет конкретного случая — нет находки». Комментарий `shortcut:`
  считается решением, а не находкой. Каждая находка в четырёх частях: что это, проблема,
  исправление, что будет, если не чинить. Код не меняет.
- `/ponytail-audit` — те же проверки по всему репозиторию, до 20 находок по рангу.
- `/ponytail-debt` — ищет комментарии `shortcut:` и строит реестр долга: файл, строка, предел,
  условие замены.

Hook-и Claude Code (все на `node`, timeout 5 секунд):

- `SessionStart` вставляет правила в контекст и добавляет карту кода (функции и классы по папкам,
  до 2000 символов). Ещё он читает `~/.claude/settings.json` и, если строка состояния ponytail не
  настроена, просит Claude её настроить.
- `SubagentStart` вставляет правила в каждый subagent. Ограничить круг можно переменной
  `PONYTAIL_SUBAGENT_MATCHER`; без неё правила попадают во все subagent-ы.
- `UserPromptSubmit` повторно вставляет правила на каждом ходе.

**Зрелость.** Создан 2026-06-12, последний push 2026-10-08. Пять релизов за четыре дня
(v4.11.0 → v5.1.0). Есть набор test-ов на `node --test`. По данным GitHub API на 2026-10-09:
около 158 тысяч звёзд и 8,5 тысяч форков (цифры не перепроверялись).

**Результаты со слов автора.** Agentic benchmark от 2026-10-07: 39 задач, одна модель, n=5.
Против агента без skill-а: на 53% меньше строк, на 26% дешевле, скрытые проверки пройдены в 97%
против 96%. Сам автор называет ограничения: одна модель и одна среда; агенты не запускали
написанные test-ы; судья — тоже модель; в 21 из 39 задач нет скрытой проверки корректности,
меряется только размер.

**Критика и ограничения.**

- Июньский benchmark оказался завышен. Colin Eberhardt (Scott Logic) показал, что prompt из семи
  слов про YAGNI обходит ponytail на том же benchmark-е. Автор признал это и переделал benchmark
  (InfoQ, 2026-08-05).
- На слабых моделях падает корректность (issue #65): у gpt-4.1-mini 10 из 15 вместо 15 из 15.
- В длинных сессиях стоимость может вырасти (issue #121): правила вставляются на каждом ходе, а
  вызовов инструментов становится больше.
- Review-агенты находят меньше (issue #502): `SubagentStart` вставлял режим «не больше трёх
  коротких строк» в subagent-ы review, audit и security.
- Выигрыш сосредоточен в задачах, где легко переусложнить. На простом backend CRUD он близок к нулю.

## 2. pstack

**Что это.** Набор skill-ов для AI-агентов от Lauren Tan (ник «poteto», Cursor). Состоит из
skill-маршрутизатора `poteto-mode`, 23 playbook-ов (пошаговых сценариев: bug fix, feature,
Autopilot-full и другие), около 27 рабочих skill-ов, 24 skill-ов с принципами и двух subagent-ов.

- **Лицензия:** MIT, по заметкам — с copyright Lauren Tan (файл лицензии в копиях не читался).
- **Официальный источник:** https://github.com/cursor/plugins/tree/main/pstack. SHA коммита в
  заметках не зафиксирован.
- **Порт на Claude Code:** https://github.com/michael-denyer/pstack-claude (MIT, сообщество,
  версия около 0.9.7x). Отдельное зеркало: https://github.com/backnotprop/pstack.
- **Зрелость:** проекту около 4,5 месяцев, активные коммиты на неделе исследования. Звёзды по
  данным GitHub: cursor/plugins около 10,4 тысячи, порт около 1,7 тысячи, зеркало около 1,3 тысячи.

**Как работает.** Маршрутизатор подбирает задаче один playbook, копирует его шаги в список дел
(пропущенный шаг остаётся с пометкой `skip: <причина>`), отдаёт код subagent-ам, смотрит diff и
проверяет результат там же, где проявилась проблема. Skill-ы, полезные для worfy:

- `interrogate` — review несколькими моделями. Один read-only reviewer на каждую модель, у всех
  одинаковые prompt и критерии. Разнообразие даёт разница моделей, а не разные роли. Ведущий
  агент сводит находки: совпадение у двух моделей — самый сильный сигнал. Итог раскладывается по
  группам **Act on / Consider / Noted / Dismissed** (чинить / обдумать / принято к сведению /
  отклонено с причиной) плюс карта согласия моделей. Отклонённое показывается намеренно, чтобы
  было видно, что отброшено.
- `show-me-your-work` — журнал решений `decisions.tsv`, в который только дописывают строки:
  время, фаза, решение, причина, ссылка на доказательство, результат. В конце прогона журнал
  сверяется с transcript-ом сессии, затем subagent на другой модели ищет решения со слабыми
  доказательствами.
- `swarm` — параллельные исполнители с ответом `PASS` / `ISSUES` / `BLOCKED`. Результат без
  точного SHA не засчитывается; отсутствие ответа — пробел, а не успех.
- `create-verification-skill` — генерирует skill проекта «запусти, проверь, что экземпляр
  живой, проведи сценарий, сохрани доказательства, убери за собой».

**Критика и ограничения.** Flavio Copes: избыточно для правок в одну строку; токены быстро
растут, если каждая роль идёт на дорогой модели; рассчитан на командный поток с worktree и PR.
Измерений стоимости не нашли. Есть зависимости от Cursor: облачные исполнители, модели Grok,
файл правил `~/.cursor/rules/`. Порт для Claude Code в hook-е `SessionStart` вставляет
обязательную инструкцию вызывать свой маршрутизатор. Форк ystack прямо предупреждает: два
маршрутизатора верхнего уровня в одной сессии конфликтуют.

**Unix pstack.** Это одноимённая утилита Linux и Solaris: `pstack <pid>` подключает GDB,
печатает стек каждого потока процесса и отключается. На macOS её нет. Аналоги для зависшего
Electron-приложения на macOS (общие знания, **в этой сессии не проверялись**):

- `sample <pid> 5 -file out.txt` — выборка нативных стеков всех потоков, без JS-фреймов;
- `spindump <pid>` — системный отчёт о зависании, нужен sudo;
- `lldb -p <pid>`, затем `thread backtrace all`;
- для main process Node/Electron: `process.report.writeReport()` или `node --report-on-signal`
  дают отчёт с JS-стеком.

## 3. Thermos («thermo nuclear code review»)

**Что это.** Плагин Cursor для review ветки: два reviewer-а и ведущий агент. Раньше это были
внутренние skill-ы Cursor; коммит 2026-05-28 убрал из них внутренние ссылки и опубликовал.

- **Автор:** Eric Zakariasson (Cursor); в `plugin.json` автор — «Cursor».
- **Лицензия:** MIT, Copyright (c) 2026 Cursor.
- **Репозиторий:** https://github.com/cursor/plugins/tree/main/thermos, версия 1.0.0. SHA
  коммита в заметках не зафиксирован.
- **Зрелость:** три коммита в `thermos/` с мая, после выпуска не менялся. Каталоги skill-ов
  сообщают о сотнях установок (данные сторонних каталогов). То, что это самый используемый skill
  внутри Cursor, известно только из перепостов, оригинал недоступен. Форма — обычные Markdown
  SKILL.md без скриптов и сетевых вызовов.

**Как работает.** Оркестратор берёт `git diff main...HEAD` и полные тексты изменённых файлов,
одним сообщением запускает два фоновых subagent-а с одинаковым контекстом и сводит их ответы:
убирает дубли, сильнее взвешивает находки, которые нашли оба. Отдельной проверки находок нет.

Reviewer корректности и безопасности (`thermo-nuclear-review`):

- только добавленный и изменённый код, старые проблемы не трогать;
- проследить побочные эффекты изменения в других модулях;
- **поломка локальной сборки и запуска**: переименованные или новые переменные окружения, другое
  место чтения секретов, смена портов, новый обязательный скрипт. Новый альтернативный способ
  запуска и обычная новая зависимость не считаются;
- **утечка за feature flag**: функция за флагом или внутренней проверкой не должна стать видна;
- **намеренная поломка**: если ветка сознательно убирает защиту и изменение ограничено, это не
  находка, если только автор явно не недооценил последствия;
- **не сдавать недоисследованное**: нельзя писать «на клиенте ошибка, но может, backend её
  ловит», когда код backend-а доступен — надо проверить.

Reviewer качества кода (`thermo-nuclear-code-quality-review`): искать реструктуризацию без
изменения поведения, после которой исчезают ветки, режимы, helper-ы или слои; удалять сложность,
а не переносить. PR не должен переводить файл через порог в 1000 строк без веской причины. Не
допускать разрастания ad-hoc условий в чужих сценариях, тонких обёрток без смысла, лишней
опциональности, `any` и приведений типов. Есть список условий, которые блокируют approve, пока
автор их не обоснует.

**Критика и ограничения.** Matt Pocock (видео, 2026-05-28) прогнал skill качества на своём
репозитории: примерно 5 из 7 советов полезны. Претензии: амбициозный prompt даёт ложные
срабатывания; test-ы и seam-ы (места, где код можно подменить в test-е) не рассматриваются;
prompt повторяется. Порог в 1000 строк произволен. Стоимость авторы не указывают.

**Наш вывод, не внешняя критика.** Prompt корректности держится на словах целиком заглавными
буквами («EXTREMELY», «NOTHING»). Рекомендации Anthropic по prompt-ам для свежих моделей Claude
советуют смягчать такой нажим: модели и так следуют инструкциям, а нажим ведёт к лишним
срабатываниям. Отсюда вывод исследователя: в переносе правил Thermos такие слова не нужны.

## Сравнение с worfy сегодня

**Что уже есть.**

- Три линзы review в профиле проекта worfy: корректность, границы модулей, тесты (поле
  `review.lenses` в `~/.claude/worfy-harness/projects/worfy/profile.json`).
- Один агент `worfy:reviewer` на одну линзу; они запускаются параллельно и сами прогоняют проверки
  с exit code.
- Состязательная проверка находок. В `continuous-audit` каждую находку высокого приоритета
  отдельный reviewer пытается опровергнуть. В `epic-wave` есть «узкий круг» — дополнительный
  раунд проверки одного Ticket-а с вердиктом `NARROW: VERIFIED` или `NARROW: REJECTED`.
- `harness/hooks/gate.sh` — скрипт итоговой проверки. Exit code `0` — зелено, `2` — красно,
  `3` — проверить не удалось. Итог пишется в файл `verdict-<tag>.json`.
- Verifier (reviewer, который проверяет отчёт implementer-а) работает в worktree того же
  implementer-а, когда тот уже закончил.

**Чего нет.**

- Линзы упрощения: ни одна из трёх линз не просит удалить сложность.
- Проверок корректности из Thermos: поломка локальной сборки, утечка за feature flag,
  «не сдавать недоисследованное», не репортить намеренную поломку.
- Журнала решений для прогонов без человека. Autopilot (режим приложения worfy, который сам
  запускает волны тикетов) хранит состояние в `HANDOFF.md`, но не причины и доказательства
  каждого решения.
- Проверок размера, которые не тратят токены: `gate.sh` не смотрит на рост файлов.
- Диагностики зависаний и падений в Electron-приложении. В `src/` нет `crashReporter` и
  обработчиков `render-process-gone` и `child-process-gone`; поиск по `src/` вернул exit code 1.
  Снятия стеков зависшего процесса тоже нет.

## Что не берём и почему

- **ponytail целиком.** Его hook `SubagentStart` вставляет правила в каждый subagent, включая
  `worfy:reviewer`. В issue #502 пользователи сообщили, что review-агенты после этого находили
  меньше. Его hook `SessionStart` читает `~/.claude/settings.json` и подталкивает Claude поменять
  `statusLine`, а строкой состояния и настройками уже управляет worfy. Ещё он повторно вставляет
  правила на каждом ходе, что растит входные токены (issue #121).
- **pstack-claude как плагин.** Это второй маршрутизатор задач поверх worfy: его `SessionStart`
  требует вызывать `poteto-mode`, а задачи в worfy уже распределяют `ship-ticket` и `epic-wave`.
  Два маршрутизатора в одной сессии конфликтуют.
- **Капслок-стиль Thermos** и разрешение «перестроить кодовую базу» внутри Ticket-а.
- **Как заимствуем.** Берём идеи и формулировки, а не устанавливаем плагины. Скопированный текст
  получает пометку MIT с copyright автора и SHA коммита, с которого он взят. Проекты меняются
  быстро, поэтому ссылаемся на конкретный коммит, а не на `main`.
