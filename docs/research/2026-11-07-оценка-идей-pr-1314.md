## 3. Идеи по одной

### Идея 1. Change Impact Graph — граф влияния изменения

**Предлагается.** До старта Ticket-а строить граф: файлы, символы, публичные контракты, test-ы, активные Ticket-ы, с
оценкой риска. После реализации сравнить предсказание с фактическим diff.

**Что уже есть.**

- Граф импортов для выбора test-ов: `scripts/affected-tests.mjs:1-12` берёт `git diff --name-only` и по графу модулей
  находит test-ы, которые изменение затрагивает; на этом стоят шарды Linux CI на каждый PR
  ([ADR-0081](../adr/0081-per-pr-linux-ci-shards-and-affected-tests.md)).
- Карта кода: `harness/bin/code-map` — описание папок текстом с проверкой устаревания; ею пользуется агент-scout.
- Список файлов Ticket-а: раздел trail каждого Ticket-а (`docs/features/workflow.md:80-83`); review считает правку
  вне этого списка находкой (`harness/agents/reviewer.md:314`).

**Чего нет.** Графа «файл ↔ символ ↔ контракт ↔ test ↔ активный Ticket» до старта. Сравнения trail-списка с
фактическим `git diff --name-only`.

**Ценность.** Низкая. Замер Ticket-а worfy-throughput 39 показал: разведка кода (то, что граф должен сократить)
занимает 10,4 % стоимости и 11,9 % token-ов Ticket-а
(`.scratch/worfy-throughput/issues/39-карта-кода-сначала-замер-доли-разведки.md:71`). Выиграть на ней можно немного.

**Стоимость и риски.** Большая: индекс символов для TypeScript, Node-скриптов Harness и Markdown-спецификаций, его
устаревание, ложные связи. Владелец уже решил, что карта кода — своя, без сторонних графов кода вроде graphify
(`.scratch/worfy-throughput/spec.md:659-660`).

**Вердикт: не берём** как функцию. Единственная полезная часть — сверка «предсказанные файлы против фактических» —
входит в доработку идеи 3.

### Идея 3. Conflict Radar — коллизии параллельных Ticket-ов

**Предлагается.** До Wave (набора Ticket-ов, которые идут параллельно) предсказать коллизии по файлам, символам,
контрактам и миграциям и предложить последовательный порядок.

**Что уже есть — уровень файлов.**

- `readyWave()` в `src/shared/workflow/waves.ts:175` собирает Wave: файлы Ticket-ов в работе и Ticket-ов, сделанных
  только в ветке, заняты с самого начала. Ticket, чей файл пересекается с занятым, ждёт следующей Wave
  (`filesOverlap`, `src/shared/workflow/waves.ts:157-162`; описание — `docs/features/workflow.md:75-83`).
- Определение Wave в глоссарии: «общих файлов нет» (`CONTEXT.md:84`).
- Skill epic-wave планирует Wave таблицей и ставит Ticket-ы с общим файлом последовательно; перед стартом смотрит файлы
  открытых PR других Epic-ов (`harness/skills/epic-wave/SKILL.md`, разделы плана Wave и проверки открытых PR).
- Один gate full на весь набор merge-ей Wave: PR в состоянии `DIRTY` идёт на rebase, красный gate full — на поиск
  виновного PR ([ADR-0065](../adr/0065-one-gate-full-per-wave-merge-set.md)).

**Чего нет.** Уровня символов и контрактов. Ticket без раздела trail не занимает ничего
(`docs/features/workflow.md:83`). Никто не проверяет, что фактический diff PR остался внутри trail-списка: правка вне
списка — только находка review (`harness/agents/reviewer.md:314`).

**Насколько больно сейчас.** В истории `main` около 1600 commit-ов; слово «conflict» есть в восьми. Настоящих коллизий
кода среди найденных три, и одна — нарушение уже существующего правила Orchestrator-ом
(`.scratch/worfy-review/issues/05-*.md:308`). Чаще конфликт — строка `Status:` в файле Ticket-а после docs-commit-а на
`main` (например, `.scratch/worfy-review/issues/03-*.md:158`). Это не коллизия Ticket-ов, а побочный эффект того, как
docs-commit-ы отмечают статусы.

**Вердикт: доработка, один Ticket.** Сверять фактические файлы PR (`git diff --name-only`) с trail-списком Ticket-а и
с файлами, которые держат другие Ticket-ы в работе; при выходе за список — предупреждение в отчёте Wave, а не запрет.
Это закрывает и проверку «предсказание против факта» из идеи 1. Символы и контракты — **не берём**: коллизий такого
рода в истории не найдено, а ложные срабатывания стоят последовательных Wave.

### Идея 4. Run Time Machine — исторический снимок Run-а

**Предлагается.** Из Flight Recorder (экран Run history — шкала времени одного Run-а Autopilot) открыть историческое
состояние: снимок worktree, транскрипт, инструкции, результаты инструментов, окружение; сделать безопасный fork для
расследования.

**Что уже есть.**

- Run history читает journal Run-а и источники, ничего своего не хранит (`docs/features/flight-recorder.md:3-5`). Head
  и worktree каждого gate run видны из логов gate (`docs/features/flight-recorder.md:229`).
- Сроки жизни источников: journal — навсегда, транскрипты — 30 дней по настройке Claude Code, логи gate — 31 день
  (`docs/features/flight-recorder.md:196-204`).
- Fork Session-а Claude Code SDK умеет (`forkSession`), но worfy его не запрашивает
  (`src/main/vendors/claude/options.ts:249`).

**Чего нет.** Снимков worktree, промптов, результатов инструментов и окружения; кнопки «fork от этого span-а».

**Против чего идёт.** [ADR-0092](../adr/0092-run-history.md): шкала вычисляется при открытии, своего индекса spans,
кэша и копий источников нет (`docs/adr/0092-run-history.md:33-34`); копия источников ради долгой памяти отклонена
(`docs/adr/0092-run-history.md:49-50`). Это продолжение
[ADR-0002](../adr/0002-worfy-is-a-view-over-the-workflow.md) (worfy не владеет состоянием workflow).

**Ценность для одного владельца.** Небольшая. Причину сбоя сегодня находят по транскрипту в панели деталей и по
`git checkout <sha>`; случая, где этого не хватило, в Ticket-ах не нашлось. Снимок окружения ещё и хранит пути и имена
машины, которые потом легко попадают в публичный PR.

**Вердикт: отложить.** Если понадобится, дешёвый вариант без нового хранилища — «новый worktree от head span-а плюс
`forkSession` транскрипта», и только пока транскрипт жив (30 дней). Снимки окружения и копии источников — **не
берём**: это прямо отклонено в ADR-0092.

### Идея 5. Failure Intelligence — группировка причин падений

**Предлагается.** Группировать повторяющиеся сбои по причине между Run-ами и предлагать правки Harness с
доказательствами.

**Что уже есть — суженная версия.** Epic worfy-failures закрыт 10/10. Красный gate пишет машинную запись о каждом
упавшем test-е с очисткой личных данных (`harness/hooks/gate.mjs:865-895`); команда отчёта отделяет flaky test от
детерминированного красного между run-ами и машинами и предлагает записи карантина, не записывая их сама
([ADR-0096](../adr/0096-failure-records-and-solo-rerun.md); `docs/features/gate-and-github.md:271`).

**Что осталось нового** (`.scratch/worfy-failures/spec.md:263-273`): LLM-классификация причин (нужен платный eval и
решение владельца с ценой), экран в worfy (формат записей сделан машинным «на потом», строки 267-268), связь с
Flight Recorder. Авто-правку Harness Epic исключил — как и сам PR #1314 советует.

**Вердикт: сделано.** Экран над записями — **отложить**, пока записей не накопится столько, что группировка
что-то покажет. LLM-классификацию — **не берём** без замера, что детерминированные группы чего-то не находят.

### Идея 6. Visual Regression Agent — сравнение снимков с эталоном

**Предлагается.** Browser Node (браузер на Canvas worfy) снимает воспроизводимые сценарии, сравнивает с одобренными
эталонами, агент разбирает значимые отличия; обновление эталона — только с одобрением.

**Что уже есть.**

- Сравнения с хранимым эталоном нет. Единственный `toMatchSnapshot` сравнивает два снимка одного run-а: эталон пишется
  и удаляется в том же test-е (`test/e2e/browser-layer.spec.ts:431-440`).
- Съёмка для Evidence из test-сборки: `test/e2e/evidence-capture.ts` (снимки и клипы worfy-evidence).
- Browser Node: только viewport; эмуляцию устройства (worfy-browser 19) владелец отложил
  (`.scratch/worfy-browser/issues/19-*.md:4-7`).

**Против чего идёт.** Вариант «агент в Browser Node» прямо отклонён: Browser не становится регрессионным набором в CI,
потому что прогон Claude медленный, недетерминированный и дорогой (`docs/adr/0078-browser-node.md:27-30`;
`docs/roadmap.md:379-380`; `.scratch/worfy-browser/spec.md:81-83`).

**Технические риски узкого варианта** (Playwright `toHaveScreenshot` в e2e test-сборке, без агента):

- Снимки различаются по платформам: vibrancy macOS не попадает в PNG (`docs/lessons/testing.md:53-60`), у Windows
  другие шрифты и масштаб. Значит, эталоны отдельно на каждую платформу и риск новых flaky test-ов в e2e на
  бесплатных runner-ах.
- Эталоны лежат в публичном репозитории. privacy check читает метаданные, не пиксели; пиксели проверяет человек
  (строка `scrub:` у снимка, `docs/features/evidence.md`, раздел про снимки). Значит, обновление эталона агент одобрить
  не может.
- Каждый UI-Ticket будет обновлять эталоны — постоянная стоимость.

**Ценность.** Неизвестна: замера, сколько визуальных регрессий владелец нашёл на приёмке, нет.

**Вердикт: агентный вариант в Browser Node — не берём (ADR-0078, п. 1). Узкий вариант — исследовать сначала.**
Исследование без кода: посчитать по «Итогам» приёмок и Ticket-ам polish за последний месяц, сколько дефектов были
чисто визуальными и прошли все test-ы. Если их мало — закрыть идею; если много — spike на трёх экранах на одной
платформе с замером стабильности.
