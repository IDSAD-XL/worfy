## Модель работы

**Тип развёртывания — hybrid.** Сервер (облако вендора или свой) хранит задачи и координирует. Выполняет работу
daemon на машинах пользователя, рядом с кодом [59][9].

- **Три способа запуска** [59]:
  - Cloud: регистрация на multica.ai, терминал не нужен.
  - Desktop-приложение: компьютер, на котором оно запущено, сам регистрируется как runtime.
  - Self-host: весь стек у себя.
- **Сервер нужен всегда.** Это Cloud или своя установка; своя может стоять на той же машине [46]. Одному человеку
  Multica тоже подходит: desktop-приложение само подключает свою машину [11].
- **Архитектура** [59][10]:
  - Сервер на Go с WebSocket и PostgreSQL 17.
  - Web на Next.js 16, desktop на Electron (он использует те же пакеты React, что и web), клиент для iPhone и iPad на
    Expo.
  - Локальный daemon подключается к серверу, забирает запуски и стартует CLI агентов рядом с кодом.
- **Граница данных** [9][30]:
  - Сервер хранит issues, комментарии, статусы, конфигурацию агентов, skills, записи запусков и transcripts.
  - Машины пользователей хранят CLI агентов, их учётные данные, код и выполняют команды. Сервер сам команд не
    выполняет.
  - Исключение: переменные окружения агента (`custom_env`) и его конфигурация MCP хранятся на сервере и передаются на
    runtime в момент запуска [9][30].
  - FAQ добавляет: содержимое workspace хранит Multica, код уходит тем провайдерам моделей, которых выбрал
    пользователь [1].
- **Удалённые и облачные runtimes:**
  - **Qoder Cloud Agents** — единственный документированный удалённый runtime. Свой daemon не нужен. Администратор
    подключает его token-ом Qoder. Параллельных запусков по умолчанию 3 (максимум 10). Timeout запуска по умолчанию
    60 минут (от 5 до 240) [30]. Появился 2026-10-23 [6].
  - **Облачные sandboxes Multica** главная страница рекламирует: агентов можно запускать и в managed cloud sandboxes
    вендора [1]. В интерфейсе группа «Cloud services» помечена «Coming soon». Диалог «Cloud Runtime / Fleet nodes» спрашивает
    поля в стиле AWS: тип instance, регион, AMI ID, subnet, key pair [81]. Код проксирует создание, запуск, остановку,
    перезагрузку и exec узлов в отдельный закрытый сервис «multica-cloud»/Fleet. Комментарий в коде: облако выпускает
    token `mcn_` для узла и передаёт его в EC2 instance через SSM bootstrap [102][45]. Доступны ли такие узлы
    пользователям сегодня и сколько стоят — (не подтверждено) [1][102].
- **Агенты и модели.** Своей модели у Multica нет. Он управляет CLI агентов, которые уже установлены и залогинены на
  машинах пользователя [59].
  - В текущем коде 31 CLI [59][31]: Claude Code, Codex, Cursor Agent, GitHub Copilot CLI, OpenCode, OpenClaw, Hermes,
    Pi, Oh-My-Pi, Antigravity, CodeBuddy, DevEco Code, Grok, Kimi, Kiro CLI, Qoder CLI и Qoder CN, Qwen Code, QwenPaw,
    Reasonix, Trae CLI, DeepSeek Harness, MiniMax Code, Dim, Huawei CodeArts, ZeroClaw, Muse Code, Devin CLI, Amp,
    Factory Droid, ZCode.
  - Маркетинг называет разное число: на главной ссылка «All 27 agents», в FAQ — 29, в README — 31 [1][59].
  - Gemini CLI: заметки расходятся. Заметка о функциях: Gemini CLI есть в changelog версии v0.1.33, в текущем коде
    адаптера нет, удаление не подтверждено [6]. Заметка о направлении развития: runtime Gemini CLI удалён 24–30 июня
    [6]. При написании досье проверено: changelog версий 0.3.29 (2026-06-24) и 0.3.33 (2026-06-30) называет runtime
    Gemini удалённым [6].
  - Возможности разных CLI различаются [31][35]:
    - продолжение session (resume) — у всех, кроме MiniMax Code;
    - MCP под управлением Multica — у всех, кроме Amp, Factory Droid, Antigravity, Copilot CLI, DevEco, Muse и
      ZeroClaw;
    - выбор модели в Multica — у всех, кроме QwenPaw, MiniMax Code и ZeroClaw (у них своя конфигурация); Amp вместо
      модели принимает «mode»;
    - у каждого CLI своя папка для skills; Copilot CLI не сообщает число tokens.
  - Список моделей приходит от каждого runtime. К нему добавляются уровень размышления (thinking level) и для части
    CLI уровень сервиса, например Fast mode у Codex [19][6]. С версии v0.4.38 Claude Code показывает только модели,
    доступные на этой машине [6].
  - Custom runtime profiles: владелец или администратор регистрирует обёртку или команду с закреплённой версией поверх
    поддерживаемого протокола. Важные для протокола флаги, например `--permission-mode`, из аргументов пользователя
    выбрасываются [30].
  - В запусках Codex под daemon встроенная память Codex и его встроенные subagents по умолчанию выключены [30].
- **Один пользователь или команда — команда** [13][18][30][27][6][24][14]:
  - роли owner, admin, member;
  - приглашения по email (действуют 7 дней) и ссылки-приглашения;
  - права на запуск каждого агента (Access);
  - runtimes по умолчанию приватные, их можно сделать общими или открыть выбранным участникам;
  - приватные чаты и приватные проекты;
  - quick actions и сохранённые views бывают личными и общими.
- **Вход:** код по email и Google. SSO не документирован. Запросы на OIDC и Keycloak открыты (#1014, #711) [11][74].
- **Платформы:**
  - Desktop: macOS (Apple Silicon и Intel; `.dmg`/`.zip`), Windows (x64 и ARM64; `.exe`), Linux (x64 и ARM64;
    AppImage, `.deb`, `.rpm`). Обновляется сам; на Linux — только AppImage [40][4][58].
  - Сборки для Windows не подписаны Authenticode. Defender считает встроенный CLI вредоносным (ложное срабатывание),
    документация даёт шаги для исключения [40][140].
  - CLI и daemon: macOS, Linux и Windows, установка одной командой. `multica setup` входит в аккаунт и оставляет
    daemon работать [11]. Автозапуск при входе: LaunchAgent на macOS, systemd или XDG на Linux, ключ Run в registry
    на Windows [30].
  - Мобильный клиент — только iOS и iPadOS, и только сборка из исходников в Xcode. В App Store его нет; бесплатная
    подпись истекает через 7 дней. Android-клиента нет [41]. Web-приложение на домашний экран — с v0.4.27, родная
    раскладка для iPad — с v0.4.37 [6].
  - Self-host: Docker Compose (нужны порты 3000 и 8080) или Helm chart для Kubernetes. Образы берутся из GHCR. Скрипт
    установки принимает `--with-server`. Helm умеет внешний PostgreSQL; хранилище — S3-совместимое или GCS [46][59][6].
  - Self-hosted сервер раз в день отправляет вендору анонимный снимок использования: версию и округлённые счётчики.
    `DO_NOT_TRACK=1` это выключает [59][47].
  - Ограничение Windows: Environments (dev-серверы на issue) работают только на macOS и Linux [32].

## Функции

Источники этого раздела — документация вендора и код. Номера версий взяты из changelog [6].

### Workspace, issues, проекты

- **Workspace** [12]:
  - Верхняя граница: участники, issues, проекты, агенты, skills, runtimes, история запусков.
  - Текст **Context** на уровне workspace получает каждый агент.
  - Ключи issues вида `MUL-1`; префикс можно поменять.
- **Issues** [14]:
  - Исполнитель — участник, агент или squad.
  - Семь встроенных статусов в четырёх категориях. Можно добавить свои статусы, но встроенного поведения они не
    наследуют.
  - Приоритет, даты, labels.
  - До 20 своих полей 11 типов. У полей-списков до 200 вариантов (с v0.7.2) [6].
  - Массовое редактирование и «Mark as duplicate».
- **«Create with agent»** [14]: пользователь пишет просьбу. Агент в фоне пишет заголовок и описание issue, результат
  приходит в inbox.
- **Quick create** превращает одну фразу в один вызов `multica issue create` [85].
- **Views** [14][6]:
  - список, доска (board), таблица, Gantt, swimlane;
  - сохранённые views — личные или общие для workspace;
  - боковой просмотр issue с переходом клавишами J/K;
  - view «Unread» (v0.8.1);
  - статус связанного PR прямо на досках и в списках (v0.9.0).
- **Deliverables** [14]: файлы из комментариев собираются в боковой панели issue. Повторная загрузка файла с тем же
  именем добавляет версию (v2, v3…).
- **Sub-issues со stages** [14][34]:
  - Sub-issues делятся на группы 1, 2, 3… Когда группа закрыта, встроенное правило «System» будит агента родительского
    issue.
  - Его инструкция по умолчанию: проверить зависимости и вывести sub-issues следующей группы из backlog.
  - Когда закрыты все группы, агент собирает результаты в родительском issue.
- **Projects** [15]:
  - статус, приоритет, ответственный (участник или агент), даты;
  - прогресс считается сам — по доле закрытых issues;
  - описание проекта попадает в контекст каждого запуска внутри проекта;
  - приватные проекты в любом workspace — с v0.8.2 [6].
- **Ресурсы проекта** [17]:
  - репозитории GitHub (любой Git URL) с необязательным ref;
  - локальные папки — добавляются только из desktop-приложения;
  - список записывается в рабочую папку запуска как `.multica/project/resources.json`.

### Workflows

- **Что это** [16]:
  - Упорядоченные колонки статусов проекта. Каждый шаг передаёт issue дальше: агенту с инструкциями, участнику или
    ответственному за проект.
  - У шага есть поля «When done, move to» (куда двигать после работы) и «If rejected, send back to» (куда вернуть при
    отказе).
  - Шаблоны: Delivery, Content, Community.
- Передача шага squad — с v0.8.2 [6].
- **Поведение** [16][34]:
  - Конец запуска сам issue не двигает. Статус меняет тот, кто ведёт шаг.
  - Если issue ушёл с шага, к которому привязан запуск, этот запуск статус уже не поменяет. API отвечает
    `409 workflow_step_moved`.
  - Сервер отклоняет статусы, которых нет в workflow [16].
- Workflows открыты всем участникам с 2026-10-23 и включены во всех установках, включая self-hosted, с 2026-10-27 [6].

### Агенты

- **Настройки** [18][19]:
  - имя, аватар, описание (только для показа), инструкции, до 3 подсказок для начала разговора (conversation
    starters);
  - skills, runtime, модель, уровень размышления;
  - Access, предел параллельных запусков (по умолчанию 6), переменные окружения, дополнительные аргументы командной
    строки, MCP servers, боты в чатах.
- **Agent Builder** [19][6]: кнопка «Let AI write it» составляет конфигурацию в разговоре. Создание агента разговором
  есть с v0.4.0; conversational builder объявлен 2026-07-13.
- **Access** [18]:
  - кто может запускать агента: Only me (по умолчанию), Entire workspace или Specific people;
  - администратор workspace не может обойти Access и запустить чужого приватного агента.
- **MCP** [19]:
  - servers на уровне агента плюс библиотека MCP workspace; после сохранения её конфигурацию нельзя прочитать, только
    перезаписать;
  - к ним добавляются servers, уже настроенные на машине runtime. Для Claude Code это и MCP servers из включённых
    plugins [30].
- **Секреты** [19]: значения `custom_env` лежат в базе сервера открытым текстом. Читать их может только администратор,
  каждое чтение пишется в audit.
- **Прочее:** агентов можно архивировать, восстанавливать и копировать [18][19]. Inbox у агентов нет; @-упоминание
  агента — это команда на запуск, а не уведомление [18].

### Skills

- **Формат** [20]: `SKILL.md` плюс вспомогательные файлы.
- **Откуда берутся** [20]:
  - создать вручную;
  - импортировать локальную папку, `.skill` или `.zip`;
  - импортировать по URL (GitHub, ClawHub, Skills.sh);
  - скопировать снимок с подключённой машины.
- **Обновления** [20][6][32]:
  - «Update from source» для импортированных по URL;
  - история версий с откатом (v0.8.1);
  - до 512 файлов в skill (v0.8.0);
  - встроенный «platform skill» получает каждый агент.
- Перед запуском skills раскладываются в родную папку skills каждого CLI [31].
- **Проверки нет** [20]: импортированные skills никто не просматривает, не подписывает и не изолирует.

### Squads

- **Состав** [21]: один **агент-лидер** плюс участники — агенты или люди, с описанием ролей и инструкциями squad.
- **Как ведёт себя лидер** [21]:
  - при назначении squad запускается только лидер;
  - он пишет один комментарий с поручением и @-упоминает выбранных участников;
  - записывает свою оценку командой `multica squad activity` и останавливается, сам ничего не делая;
  - новые сообщения участников будят его снова. Он переводит родительский issue в `in_review`. Статус `done` ставит
    человек или слитый PR.
- Правила лидера («Squad Operating Protocol») задаёт система, пользователь их менять не может [21].
- Squads появились 2026-05-14 [6].

### Как запустить агента

- **Точки входа** [22]: назначить issue; @-упомянуть в комментарии; quick action; шаг workflow; приватный чат;
  Autopilot; wakeup на issue.
- **Комментарии** [26]:
  - перед отправкой видно, каких агентов комментарий запустит (trigger preview);
  - простой ответ в ветке сам уходит агенту этой ветки;
  - несколько комментариев подряд сливаются в один ожидающий запуск;
  - `/note` и `@all` публикуют комментарий, не будя агентов;
  - агенты могут @-упоминать друг друга. Цикл из агентов, вызывающих друг друга, Multica не останавливает;
    документация советует прописать правила остановки в инструкциях.
- **Backlog** [23]: назначение issue в статусе backlog запуск не начинает. Диалог подтверждения назначения предлагает
  «Don't start yet». В CLI для этого есть `--no-start`.
- **Quick actions** [24]: сохранённая пара «агент + prompt». Показывается кнопкой в боковой панели или вставляется
  через `/`. Область — «Just me» или «Team». Переменных нет.
- **Управление идущим запуском (steering)** [26]:
  - четыре варианта: «Add to current run» (агент прочитает после текущего шага), «Start after this run», «Stop and
    start over», «Won't start this time»;
  - у комментария видны отметки о прочтении («Read by …»);
  - работает для Claude Code, Codex, Grok и Kiro [59], Cursor (v0.6.4), Pi (v0.8.0) [6]. Для Claude Code и Codex —
    с 2026-09-23 [6].
- **Агент — агенту** [6]: агент может из CLI отправить поправку в текущий запуск другого агента, в пределах лимита на
  запуск (v0.7.2, 2026-10-30).

### Runs и execution log

- **Состояния run** [29]: deferred → queued → dispatched → `waiting_local_directory` (ждёт освобождения локальной
  папки) → running → completed, failed или cancelled.
- **Execution log** в боковой панели issue [29]:
  - живая метка «Engineer is working»;
  - transcript в реальном времени: сообщения, вызовы инструментов, ошибки;
  - кнопки Stop и Retry;
  - Spent, Tokens и Agent time по issue; полоса стоимости у каждого run; диалог Runs — по запуску или суммарно, по
    агентам, по моделям.
- Открыв run, можно увидеть, какие инструкции, skills и MCP servers он получил (v0.9.0). Флажок «Include sub-issues»
  добавляет запуски дочерних issues (v0.8.2) [6].
- **Автоматический retry** только для временных сбоев [29]: runtime offline, перезапуск daemon, timeout, зависание
  Codex, сбой загрузки skill. Обычно 2 попытки, при обрывах сети — до 3.
- **Без автоматического retry** [29]: ошибки авторизации, исчерпанная квота или баланс, rate limit, ошибки 5xx
  провайдера (подсказка — «Retry later»). Ручной retry продолжает session, когда это безопасно.
- **Лимиты Claude** [6]: с v0.7.2 лимиты session и недельный лимит Claude Code показываются как ошибки квоты.
- **Проверка живости** [30][47]:
  - heartbeat раз в 15 с; runtime помечается offline примерно за 3 минуты;
  - идущие запуски падают только после 3 часов ожидания переподключения;
  - общего ограничения по времени по умолчанию нет. Watchdog останавливает запуск после 2 часов без вывода и без
    вызовов инструментов.
- **Коды отказов** [29]: полная классификация причин — на стороне платформы и на стороне CLI, с советом по исправлению
  для каждой.

### Autopilots (cron и webhook)

- **Настройка** [33]: runbook, исполнитель (агент или squad), необязательный проект, подписчики, триггеры.
- **Два режима** [33]:
  - «Create issue»: каждый раз новый issue, через обычную очередь запусков;
  - «Run only»: запуск без issue. Пропускается, если runtime offline, и никогда не повторяется автоматически.
- **Триггеры** [33]:
  - cron из 5 полей с часовым поясом IANA и предпросмотром ближайших запусков;
  - webhook URL: необязательная подпись, ключ идемпотентности, фильтры событий (заголовки GitHub и GitLab
    распознаются), повтор доставки, смена URL, тело до 256 KiB.
- **Автопауза** [33]: если за последние 7 дней было не меньше 50 запусков и 90% из них упали, Autopilot ставится на
  паузу, а автор получает уведомление.
- В списке Autopilots видны подписчики и следующий запланированный запуск (v0.4.35) [6].
- Autopilot и desktop-приложение появились 2026-04-15 [6].

### Issue wakeups (отложенный запуск агента по условию)

- **Что это** [34]: правила, сохранённые на issue, которые позже будят агента.
- **Условия** [34]:
  - время или регулярная проверка с датой окончания;
  - ответ от кого-то;
  - поле получило значение;
  - закончился запуск определённого агента;
  - закрылись sub-issues;
  - у связанного PR закончился CI, PR слит или в нём конфликт слияния (CI и конфликты — только GitHub);
  - статус другого issue;
  - любое из 25 «сырых» событий.
- **Поведение** [34]:
  - агенты сами ставят себе wakeups командой `multica issue wakeup`;
  - «silent check» может закончить запуск без комментария;
  - настройки: ждать до 1, 3, 7 или 30 дней; предел повторов — от 5 до 50 срабатываний; пауза после 12 срабатываний в
    час;
  - не больше 32 активных wakeups на issue и 1 000 на workspace.
- Wakeups по времени — с 2026-09-21, по событиям — с 2026-09-28 [6].

### Environments (dev-серверы на issue)

- **Обнаружение** [32]: daemon замечает TCP-серверы, запущенные внутри папки запуска. Desktop-приложения показываются
  один раз, с кнопкой «Switch to window».
- **Объявление** [32]:
  - репозиторий описывает environments в `.multica/environments.toml`;
  - агент запускает их командой `multica env start`. Каждому environment выдаётся 10 своих портов;
  - срок жизни — от 1 минуты до 168 часов, по умолчанию 24 часа.
- **Кнопки в боковой панели** [32][6]: открыть, скопировать URL, запустить, остановить, перезапустить, читать logs
  (последние 500 строк, живой хвост). Добавлены в v0.8.2 и v0.9.0.
- Только macOS и Linux [32].

### Git, PR, worktrees

- **GitHub App** [38]:
  - только чтение: не пушит коммиты, не пишет комментарии, не ставит status checks;
  - связывает PR с issue, если ключ issue есть в имени ветки или заголовке PR, или после ключевого слова закрытия.
    Связать можно и вручную;
  - карточка PR показывает состояние, число изменённых строк, результат CI (всё прошло / какие проверки упали / идёт)
    и возможность слияния. «Нет проверок» никогда не считается «прошло»;
  - когда все связанные PR слиты, issue переходит в выбранный workspace статус (по умолчанию `Done`);
  - необязательная строка `Co-authored-by: multica-agent` в коммитах агентов.
- **Self-hosted Git** [39]: Forgejo, Gitea и GitLab с той же связкой PR и показом CI. Только для self-host; в Cloud
  нет. Появились вместе с живым статусом PR 2026-07-24…25 [6].
- **Кто открывает PR** [39][6]: агенты сами пушат ветки и открывают PR, используя Git-учётные данные машины runtime.
  По умолчанию один PR на issue (v0.8.0).
- **Где работают запуски** [30]:
  - у каждого запуска своя папка в `~/multica_workspaces`;
  - репозитории берутся как git worktrees из одного общего bare-репозитория (кеша) на каждый репозиторий workspace.
- **Режим локальной папки** [17]:
  - `in_place` (по умолчанию): запуски идут по одному прямо в рабочей копии пользователя;
  - `worktree`: запуски идут параллельно. Незакоммиченное состояние пользователя переносится в worktree (до 2000 файлов
    или 200 MiB);
  - одна ветка на issue, `agent/<agent>/<issue>`. Следующие запуски продолжают ту же ветку;
  - незакоммиченные остатки сохраняются в `refs/multica/leftovers/…`;
  - сливать ветку Multica не будет никогда — это делает человек.
- Привязка проекта к локальной папке появилась 2026-05-27 [119][122].

### Чат, каналы, inbox, комментарии

- **Чат** [27]:
  - один на один с агентом, полностью приватный (администраторы его не читают);
  - необязательный контекст проекта;
  - плавающее окно (⌘J), очередь сообщений, «Steer», подсказки следующего вопроса, продолжение session.
- **Mika** [103][81]: встроенный агент «Chief of Staff» отвечает в чате. Он направляет просьбу себе, коллеге, новому
  агенту, squad или Autopilot. Ему запрещено писать код в чате — вместо этого он создаёт issue.
- **Чат-платформы** [36][37]:
  - Slack, Feishu/Lark, DingTalk, WeCom, Telegram. Каждый бот привязан к одному агенту;
  - команды `/issue`, `/new`, `/clear`. Участник сначала связывает свой аккаунт чата;
  - новые подключения Feishu — только для материкового Китая;
  - DingTalk, WeCom и Telegram поддерживает сообщество, без гарантии сроков ответа.
  - Lark — с 2026-06-04, Slack — с 2026-06-25 [6].
- **Inbox** [28][81]:
  - уведомления о назначениях, упоминаниях, активности в подписанных issues, упавших запусках и паузах Autopilot;
  - шесть групп уведомлений, каждую можно выключить;
  - уведомления в браузере и системные. Уведомлений по email не найдено.
  - фильтр по тому, кто запустил, и «только непрочитанные» (v0.4.35) [6].
- **Комментарии** [25]:
  - ветки, закрытие ветки с выбранным ответом, реакции;
  - пометки к тексту — до 20 на ответ;
  - «Create sub-issue from here» копирует снимок контекста в новый sub-issue;
  - блоки кода `html` и `mermaid` рисуются прямо в комментарии;
  - если двое правят одновременно, показывается сравнение бок о бок.

## Принципы и подходы

### Философия: манифест VISION.md

VISION.md впервые опубликован 2026-08-06 и с тех пор почти не менялся [62].

- **Имя.** Multica расшифровывается как Multiplexed Information and Computing Agent — отсылка к Multics и разделению
  времени (time-sharing). Мысль такая: команды разработки работали в один поток (один инженер — одна задача), а агенты
  снова делают мультиплексирование актуальным; «пользователи» системы — и люди, и агенты. Ставка: два инженера с парком
  агентов работают как команда из двадцати человек [62][2].
- **Агенты — полноправные члены команды.** Выбор исполнителя, лента активности, жизненный цикл задачи и слой runtimes
  с первого дня спроектированы под это [62].
- **Какую проблему решают.** Каждый новый агент добавляет ещё один inbox. Контекст застревает в чатах, терминалах или в
  голове одного человека и теряется при передаче работы [62].
- **Желаемый цикл работы** [62]:
  - работа начинается там, где люди уже общаются: разговор с клиентом, ветка в Slack, пара черновых фраз;
  - агент превращает это в структурированную задачу и называет, что неясно;
  - людей зовут, когда работа меняет поведение продукта, добавляет риск или требует выбора;
  - reviewer смотрит на сами результаты — план, diff, preview, результат тестов, открытые вопросы, — а не на отчёты о
    статусе;
  - история намерений, решений и результатов остаётся при задаче, и следующий агент или коллега не начинает с нуля.
- **Не только код.** Исследования, брифы для клиентов, контент, поддержка, результаты для клиентов [62].
- **Граница, которую команда поставила себе:** Multica — не автономная компания, работающая вне контроля людей. Вместо
  этого — общая операционная система для людей и агентов, «система учёта и действия» для их совместной работы [62].

### Позиция основателя: человек в контуре

В #815 (2026-04-13, 16 👍) пользователь написал, что Multica управляет AI так же, как людьми, и у него нет ядра
оркестрации: человек всё равно сам делит работу, передаёт её дальше и закрывает [113]. Ответ co-founder Bohan Jiang,
в пересказе [113]:

- Конечная цель — AI выполняет большую часть работы, а люди решают в важных точках.
- Переход от работы под руководством людей к работе под руководством AI постепенный. Три причины: команды ещё не
  готовы доверить AI структуру работы; модели ещё ненадёжны в решениях «уровнем выше»; право и compliance требуют, чтобы
  за результат отвечал человек.
- Контур управления в стиле Paperclip (другой продукт для оркестрации агентов), где человека нет, он пока отклонил.
- Уже существующие поля — родительские issues, критерии приёмки, зависимости между issues — названы основой для
  будущей оркестрации.
- Примитивы workflow и согласований — в планах; роль агента-менеджера — обсуждается.
- В продолжении (2026-04-28) он повторил: человек в контуре плюс качественное выполнение агентами, а не автономные
  цепочки агентов. Но агенты должны уметь передавать работу друг другу без человека посередине — например, один пишет
  код и упоминает агента-reviewer.

Что вышло после этого ответа [6]: squads с агентом-лидером (14 мая), sub-issues со stages (23 июня), wakeups
(21 и 28 сентября), workflows проектов с передачей шагов (23 октября), поправки агента в чужой идущий запуск
(30 октября).

В #750 команда сформулировала разницу с Paperclip так: Paperclip нацелен на компанию, которую целиком ведут агенты;
Multica — на нескольких людей, работающих с несколькими агентами [111].

### Принципы, видимые в правилах продукта

1. **Только явные триггеры.** Каждый запуск идёт от назначения, @-упоминания, чата, Autopilot или wakeup [9][22].
   Issues в Backlog «припаркованы» и никого не запускают [21].
2. **Учёт отделён от выполнения.** Сервер хранит issues, конфигурацию и записи запусков. Подключённая машина хранит
   CLI, учётные данные и код и выполняет работу. Разделение одинаково в Cloud и в self-hosted. Исключение —
   `custom_env` агента на сервере [9]. FAQ: содержимое workspace хранит Multica, код уходит выбранным провайдерам моделей
   [1].
3. **Нейтральность к агентам.** Смена провайдера задумана как выбор в выпадающем списке, а не как миграция [59].
4. **Сдачу работы закрывает человек.**
   - README обещает: работа попадает на review, а не в main, и ничего не уходит без человека [59].
   - Инструкция, которую получает каждый агент, требует переводить сданную работу в `in_review`; `done` оставлен
     людям [86].
   - Лидер squad переводит родительский issue в `in_review`, только когда общая цель достигнута. `done` ставит человек
     или слитый PR, который закрывает issue [21].
5. **Один запуск — один ход на переднем плане.**
   - Агенту запрещено оставлять работу в фоне после конца хода.
   - Агенту сказано не ждать CI. Локальные тесты плюс ссылка на PR — законченная передача работы, если issue прямо не
     просит результат CI.
   - Последующие события — упавший CI, конфликты, слияние — возвращаются через wakeups [86][34][6].
6. **Узкие автоматические retry.**
   - Повторяются только временные сбои инфраструктуры: runtime offline, перезапуск daemon, timeout, обрыв сети. Обычно
     не больше 2 попыток, при сетевых ошибках CLI — 3.
   - Квота, авторизация и ошибки конфигурации сами не повторяются. Совет документации при исчерпанной квоте — пополнить
     баланс или сменить аккаунт [29].
   - Лимиты session и недельный лимит Claude Code показываются как ошибки квоты (0.7.2, 30 октября) [6].
   - На запрос сообщества (2026-10-09) продолжать работу после сброса окна лимита подписки команда не ответила [150].
7. **Sandbox нет — сознательно.**
   - Запуск получает все права пользователя daemon. На запросы разрешений агент отвечает автоматически: Claude Code
     работает с `--permission-mode bypassPermissions`, Codex — с `danger-full-access`.
   - Объяснение: частичный sandbox ломает реальную работу и всё равно не мешает запуску прочитать учётные данные. По
     этой причине sandbox Codex на Linux убрали.
   - Рекомендованная граница — отдельный пользователь ОС, контейнер или VM [42].
8. **CLI — интерфейс агента.** Агенты управляют Multica той же командой `multica`, что и люди [59][86]. Внешние агенты
   получают переносимый CLI skill, его можно поставить из marketplace plugins Claude Code [187].
   Встроенный skill `multica-platform` прямо говорит агенту: записи настоящие, не запускай команду записи просто
   посмотреть, что будет [87].
9. **Опыт накапливается в общих skills** [20][59].
10. **Прозрачность стоимости — по ценам API.**
    - Стоимость каждого запуска и кривые накопленной стоимости [6].
    - Все суммы — оценки: опубликованная цена за token умножается на число tokens [35].
    - Открытый issue сообщества говорит, что для подписок с фиксированной платой эти оценки вводят в заблуждение;
      команда не ответила [145].
11. **Маленький контекст агента.**
    - Более короткие инструкции runtime (24 июня) и короче инструкции (4–7 августа).
    - Закрытые ветки обсуждения сворачиваются до вывода.
    - Продолжение длинной задачи Claude Code больше не повторяет около 95% записей в кеш (28 июля) [6].
12. **Доказательства и ответственность — в собственном процессе разработки.**
    - PR интерфейса без скриншотов или записи экрана по умолчанию отклоняется [66].
    - AGENTS.md говорит coding-агентам, что кодовая база — их, и её надо развивать [65].
13. **Разбивка задач — работа агента, а не движка.** Инструкция агенту: по умолчанию один issue — один PR; резать
    по видимому пользователю поведению, а не по слоям кода [86][87]. Двигать stages вперёд решает агент, сервер только
    замечает, что stage закрыт [87][34].

## Как это устроено внутри

Код прочитан на коммите `f7365ff` (2026-11-13). Файлы `apps/docs/content/docs/*.mdx` в репозитории — исходники
multica.ai/docs; опубликованная страница о безопасности сверена с ними и совпадает [42].

**Размер кода** (подсчёт исследователя) [51]: около 423 тыс. строк Go без тестов и около 529 тыс. строк тестов на Go;
680 up-migrations базы; около 19 тыс. строк SQL, написанного вручную.

### Топология

- **Три уровня** [59][10]:
  - клиенты: web на Next.js; desktop на Electron с общими пакетами React; iOS на Expo;
  - API на Go (Chi, sqlc, gorilla/websocket) и PostgreSQL 17;
  - **локальный daemon** на каждой машине-исполнителе; он запускает CLI агентов.
- **Два отдельных канала WebSocket** [10]:
  - `internal/realtime/` отправляет изменения в интерфейс;
  - `internal/daemonws/` будит daemons и несёт удалённые вызовы daemon.
  - Окончательное состояние — в базе. После переподключения клиенты запрашивают данные заново. У daemon остаётся путь
    через опрос сервера (polling), чтобы один обрыв связи не оставил задачу в очереди навсегда.
- **Redis необязателен.** Он нужен для realtime между несколькими экземплярами сервера, кеша и координации. Один
  экземпляр обходится версиями внутри процесса [10].
- **Runtime = машина × CLI агента (или custom profile) × workspace** [30]. В текущем коде 31 CLI [59].
- **Один интерфейс адаптера для всех провайдеров.** `pkg/agent` определяет
  `Backend.Execute(ctx, prompt, opts) → Session{Messages, Result}`; по комментарию в коде, это повторяет приём
  `AgentBackend` из happy-cli [82]. Адаптеры приводят к одному виду запуск, поток вывода, отмену и данные об
  использовании [10].
- **Граница данных** [9][30]: сервер никогда не выполняет команды; код, учётные данные и изменения файлов остаются на
  машине. Сервер хранит issues, комментарии, записи запусков и transcripts. Исключение — `custom_env` агента: он хранится
  на сервере и уходит на runtime при запуске.
- **Удалённые runtimes.**
  - Qoder Cloud Agents: сервер держит мост (bridge), который говорит на протоколе задач daemon и восстанавливается по
    сохранённому журналу запусков [30].
  - Облачные sandboxes Multica: сайт их перечисляет [1]; код проксирует вызовы узлов в закрытый сервис Fleet [102][45].
    Что именно создаётся и сколько стоит — (не подтверждено).

### Цикл агента

- **Своего цикла агента у Multica нет.** Run (в коде — task) — это один вызов чужого CLI на машине daemon. Инструменты
  вызывает собственный цикл CLI [10][82].
- **Путь одного запуска в коде** [10][67]:
  1. Приходит триггер, и `TaskService` вставляет строку в таблицу `agent_task_queue`.
  2. Сервер отправляет сигнал «проснись» по WebSocket.
  3. Daemon забирает работу пачкой.
  4. Сервер выпускает token на этот запуск.
  5. Daemon готовит папку, пишет инструкцию (brief) и запускает CLI.
  6. Сообщения и данные об использовании идут потоком на сервер.
  7. Запуск завершается или падает; сервер обновляет issue и рассылает события realtime.
- **Как запускается Claude Code** [83]:
  - постоянные флаги: `-p --output-format stream-json --input-format stream-json --verbose
    --permission-mode bypassPermissions --disallowedTools AskUserQuestion`;
  - по ситуации: `--strict-mcp-config` (если у агента сохранена конфигурация MCP), `--model`, `--effort`,
    `--resume <session>` и файл `--settings`, которым владеет daemon;
  - свои аргументы агента не могут переопределить флаги протокола;
  - `AskUserQuestion` выключен: в режиме без интерфейса он возвращает пустой ответ. Вопросы агент задаёт комментариями в
    issue.
- **Слои prompt** [85][86]:
  - Постоянная **инструкция runtime** пишется в рабочую папку как `CLAUDE.md`, `AGENTS.md`, `CODEBUDDY.md` или
    `QWEN.md`, между маркерами `<!-- BEGIN MULTICA-RUNTIME … -->`. Собственное содержимое файла пользователя
    сохраняется.
  - Сообщение на ход минимальное: какой issue назначен и что начать надо с `multica issue get …`.
  - Блоки конкретного запуска дописываются **после** постоянной части, чтобы начало prompt оставалось в кеше
    (MUL-5377): от чьего имени работа, connected apps, родительский issue, шаг workflow, уведомление о потере session.
- **Агент сам берёт контекст и сам сдаёт результат** [86]:
  - issue он читает через CLI `multica`. Историю комментариев — в два ограниченных чтения: сначала
    `--roots-only --summary --compact`, потом `--thread <id> --tail 30`;
  - сдаёт результат только командой `multica issue comment add --content-file`. Инструкция прямо говорит, что текст в
    терминале никуда не доставляется;
  - если агент закончил без комментария, сервер может опубликовать запасной комментарий из финального вывода: со
    скрытыми секретами, не длиннее 8 000 символов, иначе — уведомление вместо текста [89].
- **Правила статусов в инструкции агента** [86]:
  - `in_progress` — сначала, если ход делает сам результат issue;
  - `in_review` — при сдаче;
  - `blocked` и комментарий — если агент застрял;
  - `done` остаётся за людьми;
  - ходы «вопрос — ответ» статус не пишут, чтобы параллельные запуски не дёргали доску туда-сюда.
  - Собственные инструкции агента важнее этих правил и могут запретить менять статус или делегировать. Это держится
    только на prompt [86].
- **Встроенный skill `multica-platform`** ведёт агента к 10 справочным файлам: issues, sub-issues, упоминания, squads,
  autopilots, проекты, runtimes, environments и другие [87].

### Триггеры и модель событий

- **У каждого запуска явный триггер** [9][22]: назначение issue агенту или squad; @-упоминание или ответ, направленный
  агенту; сообщение в чате; Autopilot (cron, webhook или вручную); wakeup.
- **Назначение** открывает диалог подтверждения с вариантом «Don't start yet». Статус `backlog` паркует работу. В CLI —
  `--no-start` [23].
- **Слияние комментариев.** Новые комментарии добавляются в ещё не начатый запуск того же агента. База разрешает один
  ожидающий запуск на пару (issue, агент) [26][88].
- **Steering идущего запуска** [26]: «Add to current run» / «Start after this run» / «Stop and start over» /
  «Won't start». Отметки о прочтении показывают, когда агент прочёл сообщение. Только текст, и только если CLI это
  поддерживает.
  - **Механизм для Claude Code** [84]: daemon регистрирует callbacks hooks SDK (`UserPromptSubmit`, `PreToolUse`,
    `PostToolUse`, `PostToolUseFailure`, `Stop`) через управляющий протокол stream-json. На границах ходов он добавляет
    `additionalContext`. Если есть ожидающий ввод, hook `Stop` продолжает тот же цикл.
  - **Лимиты, когда агент управляет агентом:** 10 сообщений на ход всего и 3 от одного агента-автора. Для людей
    ограничения нет [96].

### Планирование и разбиение задач

- **Движка планирования и артефакта «план на утверждение» нет.** Разбить работу — задача агента, через sub-issues
  [86][87]:
  - инструкция: по умолчанию один issue — один PR; резать по видимому пользователю поведению, а не по слоям;
  - `--status todo` запускает дочерний issue сразу; `--status backlog` паркует его;
  - `--stage N` собирает дочерние issues в упорядоченные группы с барьером между ними;
  - сервер только **замечает**, что stage закрыт, и отправляет встроенный wakeup «System» исполнителю родительского
    issue. Двигать следующий stage решает агент [87][34];
  - каждый дочерний запуск получает блок `[Parent issue]`: сначала прочитать обсуждение родителя [85].
- **Squads** [21][95]:
  - первым будят лидера. К его инструкциям жёстко добавлен «Squad Operating Protocol»: поручать точной ссылкой-
    упоминанием, писать коротко, записывать `multica squad activity`, останавливаться после раздачи, никогда не делать
    работу самому;
  - он получает список участников со skills каждого и инструкции squad;
  - большинство следующих комментариев будят лидера снова. Его собственные комментарии и комментарии с явными
    @-упоминаниями — нет. Если у лидера уже есть запуск в очереди или в работе, второй не создаётся [21].
- **Workflows** (настраивают владельцы и администраторы) [16][34]: колонки статусов передают issue агенту, участнику
  или squad; у шага агента есть «When done, move to» и «If rejected, send back to». Сервер отклоняет статусы вне
  workflow и смену шага устаревшим запуском — ответом `409 workflow_step_moved`.
- **Mika** ведёт чат и направляет просьбы: себе, коллеге, новому агенту, squad или Autopilot. Код в чате писать
  запрещено — только создать issue [103].
- **Quick create** превращает одну фразу в один вызов `multica issue create` [85].
- **Triage** есть в коде сервера как этап приёма задач, который не запускает производные запуски (MUL-7189). Код сам
  говорит, что части «ещё не построены». В документации его нет; выпущен ли — (не подтверждено) [101].
- **Критика пользователей** (мнения, не заявления вендора): в #815 — Multica управляет AI как людьми и не имеет ядра
  оркестрации [113]; в #1943 (23 👍) — просьба о встроенном движке workflow с жёсткими проверками, потому что
  координации на skills и prompt не хватает [121].

### Параллельность и координация

- **Очередь — таблица в Postgres** [88]:
  - захват: `UPDATE … WHERE id = (SELECT … ORDER BY priority DESC, created_at ASC … FOR UPDATE SKIP LOCKED)`;
  - строку можно взять, только если её runtime online со свежим heartbeat;
  - и только если у того же агента на том же issue или чате нет активного запуска (`dispatched`, `running` или
    `waiting_local_directory`).
- **Пределы параллельности:** 20 запусков на daemon по умолчанию (`MULTICA_DAEMON_MAX_CONCURRENT_TASKS`) [104][30];
  6 запусков на агента по умолчанию (migration 023) [104]; необязательный предел на runtime от 1 до 50 (migration 605)
  [104]. Номер слота запуска передаётся в `MULTICA_TASK_SLOT` [30].
- **Когда работа уходит на daemon** [67]: сигнал по WebSocket вызывает один захват пачкой по всем runtimes daemon;
  опрос раз в 30 с — запасной путь; при здоровом WebSocket опрос захвата идёт примерно раз в 3 минуты.
- **Защита захвата от гонок** [88][89]: compare-and-swap по `dispatched_at`; аренда на подготовку 45 с; потерянные
  ответы на захват забираются обратно через 90 с; heartbeat runtime должен быть моложе 150 с.
- **Как агенты согласуют работу:**
  - через комментарии и @-упоминания;
  - через `multica issue runs --active` и `--siblings` — справочное чтение, которое ничего не резервирует; его советуют
    делать перед PR в общем коде [87];
  - через wakeups по событиям, условиям, проверкам PR, слиянию и конфликтам или по состоянию другого issue [34][68].
  - Если два агента упоминают друг друга, повторные запуски сливаются, но система не решает, когда их совместную работу
    пора закончить [26].
- **Защита от бесконечных wakeups** [34]: правило встаёт на паузу, если цепочка триггеров проходит через него третий
  раз без человека посередине; и после более чем 12 срабатываний в час. Не больше 32 включённых wakeups на issue и
  1 000 на workspace.
- **Агент привязан к одному runtime, и запуск никогда не переезжает на другую машину** [23]. Запрос на несколько
  runtimes у одного агента (#1900) открыт [120].

### Изоляция (папки, а не безопасность)

- **Папка на запуск** — `~/multica_workspaces/<workspace>/<task>/`, внутри `workdir/`, `output/`, `logs/` и
  `.gc_meta.json`. Следующие запуски на том же issue используют её снова [30][67].
- **Репозитории.**
  - Агент сам берёт код командой `multica repo checkout <url> [--ref]`. Вызов идёт в локальный HTTP endpoint daemon
    `/repo/checkout` [86][106].
  - Daemon создаёт **git worktree** из bare-кеша на workspace (`.repos/<workspace-id>/`) на ветке
    `agent/<agent-name>/<task-key>` [93][30].
  - Исключение: запуски Codex на Linux и Windows получают отдельный clone, потому что sandbox Codex делает git-данные
    вне рабочей папки доступными только для чтения [30].
- **Режим `local_directory`** (существующая папка на одной машине, подключённая из desktop) [17]:
  - **`in_place`**: агент правит рабочую копию пользователя. Запуски идут по одному под блокировкой папки и показывают
    состояние `waiting_local_directory`. Автоматической ветки, коммита и PR нет.
  - **`worktree`**: запуски параллельны, каждый в своём worktree, одна ветка на issue `agent/<agent>/<issue>`.
    - Незакоммиченные и неотслеживаемые файлы пользователя переносятся в worktree, до 2 000 файлов или 200 MiB.
    - Базовый коммит отмечает, откуда началась ветка.
    - Чья это ветка, записано в `refs/multica/local-state/`.
    - Незакоммиченные остатки сохраняются в `refs/multica/leftovers/<branch>/<task>`.
    - Ветку Multica не сливает никогда.
- **Прочее состояние запуска** [30]: свой `TMPDIR`; свой `CODEX_HOME` на запуск, где встроенные память и subagents
  Codex по умолчанию **выключены**; свой `HERMES_HOME` на разговор для Hermes.
- **Environments** [32]: `.multica/environments.toml` объявляет dev-серверы. У каждого environment 10 портов, надзор
  за группой процессов, срок жизни и logs. Серверы, слушающие порт внутри папок запусков, находятся сами — только на
  macOS и Linux.
- **Очистка** [30]: раз в 2 часа; папка issue удаляется через 24 часа после того, как issue готов; `node_modules`,
  `.next` и `.turbo` удаляются через 12 часов после запуска; управляемые папки запусков issue — через 14 дней после
  завершения.

### Состояние

- **Источник истины — Postgres**: issues, комментарии, задачи, сообщения, использование, wakeups; доступ через sqlc
  [10].
- **Transcripts** загружаются вызовом `ReportTaskMessages` в таблицу сообщений задач (migration 026). Перед записью в
  базу и отправкой по WebSocket секреты вырезаются регулярными выражениями: ключи AWS, ключи PEM, token-ы GitHub, ключи
  `sk-`, token-ы Slack и другие [98].
- **На стороне daemon** финальные отчёты о запусках пишутся в очередь на диске и отправляются, когда сервер снова
  доступен. Token авторизации в этой очереди не хранится [105].
- **Фоновые задачи сервера** идут через планировщик с арендой в базе (`sys_cron_executions`) и тиком 30 с; он
  безопасен при нескольких репликах сервера [100]. Раньше для этого был pg_cron (расширение Postgres); его заменили в
  июне после жалоб на self-hosting [125].

### Память и контекст

- **Долгая память — это сам issue**, плюс ресурсы проекта, инструкции агента и skills. Агент перечитывает их
  ограниченными чтениями CLI в каждом запуске [86][87].
- **Продолжение session провайдера** на пару (агент, issue) и на чат [88][89]:
  - `GetLastTaskSession` берёт самую новую законченную запись каждой session и снова использует её рабочую папку на
    том же runtime;
  - исключаются выведенные из работы session и «испорченные»: переполнение контекста, предел итераций, неверный запрос,
    слишком большой resume Codex и подобные;
  - если продолжить не удалось, добавляется «Session Continuity Notice». Его текст разный для issue, Slack, transcript
    чата и для случая, когда восстановить нельзя [85].
- **Снимок issue.** Сервер записывает состояние issue при каждом захвате. Следующему запуску можно сказать, что issue
  не менялся, и он пропустит чтение. Для комментариев то же делают выборки `--since` [88][86].
- **Квитанции о контексте** (context receipts, схема v1), одна на запуск [92]:
  - какие источники контекста переданы: инструкция runtime, инструкции агента, описание проекта, prompt, skills;
  - их размеры и короткие hash;
  - как передан каждый: файлом, внутри текста или в prompt;
  - насколько daemon уверен, что CLI его загрузил.
  - Содержимое с машины не уходит — только эти сведения.
- **Векторной памяти и поиска по embeddings нет** (нет pgvector и embeddings в migrations). Собственный клиент LLM на
  сервере нужен только для заголовков чатов и подсказок quick actions [107].

### Проверка качества

- **Платформа сама ничего не проверяет.** Код, где сервер или daemon запускает тесты или lint перед сдачей работы, не
  найден.
  - Проверка — это статус и человек: агент переводит issue в `in_review`, `done` ставит человек или автоматика слияния
    PR [86][38].
  - README подаёт это как «Review gates»: работа попадает на review, а не в main [59].
- **По умолчанию код сдаётся PR-ом до финального комментария.** Агенту сказано сообщать об упавших тестах или проблемах
  с авторизацией как о блокерах, а не делать вид, что запуск закончен. Это только инструкция [87].
- **GitHub App** (только чтение: pull requests, checks, statuses) [38]: карточки PR показывают CI и возможность
  слияния; «нет проверок» никогда не считается «прошло»; когда все связанные PR слиты, issue переходит в Done
  (настраивается).
- **Агент может дождаться CI** через wakeups `--until-pr checks|merged|conflicts`. Условие checks не учитывает
  результаты, которые закончились до создания правила [34][68].
- **Агентов-reviewer пользователи собирают сами** — например, агент на шаге Review в workflow или squad с
  участником-reviewer [16][21]. Встроенных reviewer и review lenses (заданных углов проверки) нет.
- Запрос на встроенную реакцию на упавший CI и комментарии review (#3719) открыт [131].

### Восстановление после сбоев

- **Классификация отказов** [90][29]:
  - причины платформы: `queued_expired`, `runtime_offline`, `runtime_recovery`, `timeout`, `iteration_limit`,
    `agent_blocked`, `environment_prepare_failed` и другие;
  - 14 причин `agent_error.*`, которые определяются по тексту ошибки CLI;
  - значения хранятся в базе и выводятся как labels Prometheus.
- **Автоматический retry — только для шести причин** [89][29]:
  - `runtime_offline`, `runtime_recovery`, `timeout`, `codex_semantic_inactivity`, `provider_network`,
    `skill_bundle_unavailable`;
  - по умолчанию 2 попытки; `provider_network` — 3, с паузой около 5 с перед последней;
  - retry после `runtime_offline` ждёт, пока вернётся heartbeat runtime;
  - запуски Autopilot в режиме «Run only» и запуски triage не повторяются никогда;
  - retry наследует session и рабочую папку, если продолжать безопасно. Ручной retry использует того же агента;
    `--fresh` начинает новую session [29][89].
- **Таймеры живости** [29][99]:
  - heartbeat раз в 15 с; runtime помечается offline примерно за 3 минуты;
  - идущие задачи падают только после 3 часов ожидания переподключения (по умолчанию);
  - задача, застрявшая в `dispatched` дольше 5 минут, падает;
  - задача в очереди падает, только если runtime молчит дольше этого срока **и** задача стоит в очереди столько же.
- **Перезапуск daemon** заново регистрирует runtimes и забирает запуски, которые не закончились чисто [30].
- **Watchdogs** [67][91]:
  - общего ограничения по времени по умолчанию нет (`agent_timeout` 0);
  - watchdog простоя 2 часа, watchdog инструмента 2 часа, плюс таймер бездействия Codex;
  - они считают время только пока машина не спит (sleep ноутбука не считается);
  - они не срабатывают, пока в буфере есть сообщения или финальный результат уже пришёл.
- **Retry с новой session внутри хода** — только когда новая session может помочь. Rate limit, квота, авторизация и
  сеть исключены [91].
- **Автопауза Autopilot**: не меньше 50 запусков за 7 дней при 90% отказов; проверка раз в день [33][99].
- **Статус issue после отказа:** issue в `in_progress` возвращается в `todo`, если других запусков и retry не
  ожидается [29].

### Лимиты и стоимость

- **Окна лимитов подписки система не понимает** [90][89][29]:
  - сообщения Claude Code о лимите session (с временем сброса) и о недельном лимите классифицируются как
    `agent_error.provider_quota_limit`;
  - 429, 529, «rate limit» и «overloaded» превращаются в `provider_capacity_or_rate_limit`;
  - **ни то ни другое не повторяется**. Документация советует пополнить баланс, сменить аккаунт или повторить позже;
  - поиск `rate_limit_event`, `resetsAt`, `five_hour` и `seven_day` по серверу и клиентам ничего не нашёл.
    Планировщика «подождать до сброса» нет.
- **Защита от лишних запросов при auto-review Codex.** После двух подряд ответов 429 в проверках одобрений Codex
  (Guardian) запуск падает с советом подождать, пока лимит провайдера не освободится [94].
- **Расчёт стоимости** [35][82][91][97]:
  - tokens считаются на (задача, провайдер, модель) — в конце запуска и по ходу (`OnUsage`);
  - таблица цен в коде хранит цены за миллион tokens для входа, выхода, чтения и записи кеша, с датированными
    комментариями вроде «2026-10-31»;
  - если CLI сообщает свою стоимость (так делает xAI), берётся она;
  - неизвестные модели стоят $0. Свои цены хранятся только на устройстве;
  - аналитика пересчитывается каждые 5 минут: таблица лидеров, вкладка Errors, heatmap по runtime, диалог Runs на issue.
- **У Multica Cloud своя коммерческая квота** на запуски Autopilot, со временем сброса [108].
- **Расход tokens — жалоба пользователей** (#3292) [130]. Что в коде против этого: раскладка prompt под кеш,
  ограниченные чтения комментариев и пропуск повторного чтения по снимку issue [85][86][88].

### Права и безопасность

- **Sandbox явно нет** [42]: запуск получает все права пользователя ОС, под которым работает daemon. Документация
  советует отдельного пользователя Unix, контейнер или VM.
- **CLI агентов работают с выключенными подтверждениями** [42][83][94]:
  - Claude Code: `bypassPermissions`;
  - Codex: по умолчанию `sandbox_mode = "danger-full-access"`; исключение — Windows, если пользователь включил родной
    sandbox Codex;
  - на запросы одобрения Codex всегда уходит ответ `{"decision":"accept"}`;
  - sandbox Codex `workspace-write` на Linux убран: он ломал CLI на машине и всё равно не мешал запуску прочитать и
    вынести учётные данные [42];
  - запуск от root падает, если не задан `IS_SANDBOX=1` [83].
- **Token запуска `mat_`** [45][30]: привязан к пользователю, workspace, агенту и запуску; живёт не больше 24 часов;
  записи с ним подписаны агентом; передаётся через переменные окружения, поэтому его наследуют дочерние процессы.
- **Роли и доступ** [23][30]: роли workspace — owner, admin, member. Access агента — Only me (по умолчанию), Specific
  people или Entire workspace; администратор не может обойти Access. Runtimes — приватные, общие или открытые выбранным
  участникам. Отзыв доступа отменяет затронутые запуски с причиной `runtime_access_revoked` и ставит Autopilots на
  паузу.
- **Действия от чужого имени** [34][6]: wakeup-запуски действуют от имени автора правила, права перепроверяются перед
  стартом. Триггеры Autopilot используют права автора.
- **MCP** [30]: сохранённая конфигурация MCP агента главная (strict mode). На машине runtime она объединяется с
  локальными конфигурациями пользователя; подробности локальных servers на сервер не отправляются.
- **Skills** импортируются как есть: Multica их не проверяет, не подписывает и не изолирует [20].
- **Защита prompt** [86]: имена, которые задаёт пользователь, очищаются перед вставкой в инструкцию. `source_context`
  подаётся как фон только для чтения.
- **Plugins** есть в коде за feature flag `plugins_v1`: проверка пакета, hooks, инструменты агента. Не документированы;
  выпущены ли — (не подтверждено) [76].

### Где вмешивается человек

- **До запуска:** подтверждение назначения; парковка в `backlog`; предпросмотр, каких агентов запустит комментарий
  [23][26].
- **Во время запуска** [26][83][86]: steering, остановка, живой transcript; агент ставит `blocked` и пишет
  комментарий, если застрял; вопросы приходят комментариями, потому что `AskUserQuestion` выключен; запросов разрешения
  на каждый инструмент **нет**.
- **После запуска** [16][38][18]: `in_review`, затем `done` ставит человек; шаги workflow для людей, например QA; review
  PR на GitHub; retry; уведомления в inbox (у агентов inbox нет).
- **Отложенные проверки, которые агент ставит себе сам:** `multica issue wakeup create`, с «тихими проверками», когда
  отвечать не нужно [34].

### Наблюдаемость

- **Execution log на issue** [29]: активные запуски закреплены сверху, с источником триггера, агентом и состоянием;
  живой transcript сообщений и вызовов инструментов; Spent / Tokens / Agent time с полосой стоимости на запуск; диалог
  Runs по агентам и моделям.
- **Analytics** [35]: стоимость, tokens, время работы и число запусков; вкладка Errors с 7 классами отказов.
- **Другие записи:** квитанции о контексте [92]; `multica daemon logs`, где видно, какой режим sandbox действует [42];
  logs environments — последние 500 строк, со скрытыми секретами [32]; история запусков Autopilot и повтор доставок
  webhook [33]; история срабатываний wakeups [34]; оценки лидеров squads в ленте issue [21].
- **Эксплуатация:** метрики Prometheus `multica_*` и продуктовая аналитика PostHog [109][35].
- **Запись изменений файлов на каждый запуск** влили и затем откатили в v0.9.0 [58].

### Что ругают

#### Главная критика: AI управляют так же, как людьми

- **#815 (2026-04-13, 16 👍).** Multica — хорошая оболочка для управляемых агентов, но ядра оркестрации нет [113]:
  - человек всё равно сам делит работу, назначает, двигает к следующему этапу и передаёт;
  - агенты сами ставят статус issue через CLI Multica;
  - модель статусов — плоский список, а не этапы с обязательными согласованиями.
- **Ответ maintainers:** переход от работы под руководством людей к работе под руководством AI будет постепенным; они
  противопоставили это полной автономии в стиле Paperclip [113].
- **Конкретная просьба в той же ветке:** пользователь из финтеха попросил минимальную оргструктуру — менеджер,
  reviewers, кто кому может поручать. Маршрутизация через свободный текст инструкций работает лишь иногда, и её нельзя
  проверить [113].
- **#6875 / #6876 (2026-08-13, 7 👍): вердикт после двух дней работы** [144]:
  - агент «PMO» разбил одну цель на много issues, у каждого — проверки;
  - потом всё встало: лидер утверждал, что раздал работу, но ни один запуск не начался; агент сказал «готово», а
    карточка не сдвинулась; агент-reviewer так и не проснулся;
  - сообщения о блокерах — тысячи слов logs, хотя суть — одна строка;
  - каждая законченная задача попадала в `in_review`, и пользователь превратился в клерка очереди review;
  - issues поздних этапов создавались до конца исследования и после смены плана стали мусором;
  - Inbox смешивал уведомления с настоящими решениями.
  - Итог автора: "It advertises orchestration, while delivering dispatch plus a board." (liuzhao1225, #6876) [144].
  - Предложение автора: каждый блокер должен говорить четыре вещи — что заблокировано, что пробовали, какое действие
    рекомендуется и какой один ввод нужен от человека [144].

- **Стоимость для подписчиков.** Analytics переводит tokens в доллары по публичным ценам API [35]. Self-hoster только с
  подписками фиксированной цены увидел, что ни у одного из его 296 запусков нет стоимости от провайдера. Для него
  реальная предельная стоимость — ноль, пока не кончилось окно лимита, так что все суммы в долларах бессмысленны [145].

#### Лимиты подписки и квоты (самое близкое к worfy)

- **Как сейчас.** Документация: исчерпанная квота автоматически не повторяется. Совет — пополнить баланс или сменить
  аккаунт, затем повторить вручную [29].
- **#9159 (2026-10-09, 6 👍, открыт).** Пользователи хотят, чтобы Multica ставил задачу на паузу при исчерпании квоты и
  продолжал ту же session после сброса 5-часового или недельного окна, как это делает сам Claude Code [150]. Команда не
  ответила [150].
- **Позиция maintainers.** Закрывая PR о переключении на другого провайдера (2026-08-05), они согласились, что задачи без
  присмотра должны переживать лимиты квоты. Обещали паузу и продолжение на уровне платформы, где сброс квоты отличается
  от rate limit, а любая смена аккаунта или оплаты видна и включается только явно [174].
- **На 2026-11-13** PR сообщества о продолжении после квоты (#8964) и о запасных runtimes (#5282) открыты. Общий
  ограничитель квоты (shared quota gate) отозван [178][143].
- **Связанные запросы:**
  - #1398 (12 ❤): цепочка запасных вариантов — например, перейти на runtime GPT, когда план Claude упёрся в лимит [116];
  - #6650, предложение дизайна: агент привязан ровно к одному runtime. При нескольких daemons каждая машина тратит
    запуск, чтобы узнать, что аккаунт исчерпан. Парк агентов на Claude, Codex, Gemini и DeepSeek приходится
    перенаправлять вручную [143];
  - #6618: когда кончился месячный план, настройки модели меняют у агентов по одному [172];
  - #4513: общий агент тратит квоту того, чей это runtime [138].
- **Условия использования (#1497).** Пользователь сообщил, что поддержка Anthropic ответила ему: сторонний инструмент,
  который запускает Claude Code на учётных данных Pro/Max, в том числе по cron, запрещён [117].
  - Maintainers ответили: Multica — слой оркестрации того же рода, что Conductor, Paperclip и OpenCode; до сих пор меры
    применялись к продуктам, которые конкурируют с Claude Code; пользователь может передать API key через переменные
    окружения агента [117].
  - Ответ Anthropic известен только со слов пользователя — (не подтверждено).

#### Надёжность работы без присмотра

- **Застрявшие очереди:**
  - чат висит в «Queued», пока пользователь не нажмёт паузу (#2341, открыт). Позже комментатор назвал чат непригодным
    (2026-08-02) [123];
  - захват задач падал по timeout у агента с 13 skills: ответ на захват нёс несколько MB содержимого skills. Исправлено в
    июне [133];
  - запуски Codex висели в «running» без вывода. Одна из причин — запуск MCP server упирался в жёсткий watchdog на 30 с
    [129].
- **Сон и выключение:**
  - если Mac спал больше 2 часов, watchdog при пробуждении убивал все идущие запуски и помечал их окончательно
    упавшими. Исправлено 2026-10-12 [149];
  - штатная остановка daemon помечала идущие запуски упавшими, и они не повторялись. Исправлено в v0.8.0 [154][57].
- **Шторм повторов.** Одну упавшую session повторили 16 раз за 16 минут, каждый раз заново оплачивая tokens (v0.6.1,
  Windows, OpenCode). У другого пользователя каждый комментарий-триггер запускал новую цепочку retry, потому что запуски
  OpenCode 2.x ошибочно определялись как сетевые ошибки [151].
- **Тихие остановки.** В squad из 7 агентов исполнитель опубликовал финальный отчёт, никого не упомянув, и ни один агент
  не проснулся. Вместе с удалённым правилом пробуждения pipeline простоял около 6 часов. Исправления сообщества открыты с
  2026-09-28 и 2026-11-06 [153].
- **Диск.** Очистка старых папок задач оставила 2 290 папок и 33 GB; пользователь удалил их вручную. Исправление влито
  2026-11-13 [158].
- Пользователи просят обнаружение зависших запусков и telemetry задержек по фазам [159].
- **Готовность задачи — со слов самого агента.** Отчёт агента — единственный вердикт. Что наблюдали [134]:
  - пустые запуски, отмеченные как успешные;
  - исправление, которое ломает соседний тест;
  - выдуманные функции;
  - ежедневный Autopilot дал 30 «успешных» запусков, прежде чем кто-то заметил, что результат ушёл от спецификации.
  - Пользователи предлагают агентов-проверяющих и проверки на доказательствах, прежде чем issue можно закрыть
    [134][139]. Maintainer предложил вместо этого свои статусы (2026-07-02) [139].
- **Работа с PR после открытия.** Пользователи просили будить агента, когда CI его PR упал или пришёл review [131].
  - Пробуждение по проверкам CI вышло (maintainer, 2026-09-27) [131].
  - Пробуждение по review добавили и откатили в том же v0.8.0 [57].

- **Цена отдельного worktree на каждый запуск:**
  - репозиторий одного пользователя весит 70 GB [119];
  - тщательно настроенный агент Hermes теряет конфигурацию MCP, память и учётные данные в каждой новой папке [167];
  - в мае пользователь писал, что результаты хуже, чем в его Vibe Kanban с MCP servers Serena и Context7, потому что
    MCP в Multica тогда не было [167].
- **Режим локальной папки выполняет задачи по одной:**
  - второй агент того же проекта ждёт первого (#3761). Пул worktrees добавили, потом он пропал из main и вернулся в

  - вопросы только на чтение часами ждали за запусками, которые пишут код и держат блокировку папки [146].
- **Проверка результата агента.** Путь к worktree пользователям приходилось искать вручную; maintainers советуют
  проверять ветку PR или полагаться на CI [114].

#### Интерактивное управление против автоодобрения всего

- **Как запускается Claude Code.** Текущий код стартует Claude Code с `--permission-mode bypassPermissions`, и
  пользователь не может это поменять. Каждый вызов инструмента одобряется сам, `AskUserQuestion` выключен [83][166].
  Поэтому нет потока «план → одобрение» и нет одобрения отдельных инструментов.
- **Что просили:**
  - оценивающие продукт просили steering по ходу работы [166];
  - командам, привыкшим к Claude Code и Codex, не хватало добавления указаний посреди запуска и быстрых skills через
    slash-команды [165];
  - команда, которая опирается на plan mode, увидела, что её процесс сломан: обратная связь приходит только в конце
    задачи [114].
- Steering посреди запуска теперь есть для Claude Code, Codex, Grok и Kiro [59].
- Агент-PM не реагировал, когда менялся статус issues, на которые он подписан; пользователи вернулись к Autopilots по
  cron [168].

## Направление развития

## Слабые места и чего нет

**Оркестрация и качество**
- Своего цикла агента и движка планирования нет. Разбивку, передачу работы и движение по stages решают prompts и
  агенты; пользователи пишут, что это раздача задач плюс доска, а не оркестрация [113][121][144].
- Платформа не проверяет результат: ни тестов, ни lint перед сдачей. Готовность — со слов агента; встроенных reviewer
  и review lenses нет [86][134][139].
- Сигналы теряются: лидер «раздал», а запуск не начался; агент «закончил», а карточка не сдвинулась; финальный отчёт
  без упоминания никого не будит, и pipeline стоит часами [144][153].
- Цикл агентов, вызывающих друг друга, система не останавливает; правила остановки — на совести инструкций [26].
- Inbox смешивает уведомления и решения; каждая законченная задача добавляет работу в очередь review [144].

**Лимиты, retry и стоимость**
- Ожидания сброса лимита подписки нет. Ошибка квоты (в том числе лимиты session и недельный лимит Claude Code) роняет
  запуск, дальше нужен человек [29][90][150].
- Rate limit и ошибки 5xx провайдера автоматически не повторяются [29][90].
- Агент привязан к одному runtime; переключения на запасной аккаунт или провайдера нет [23][120][143].
- Стоимость показывается только в долларах по ценам API; для подписок с фиксированной платой эти суммы
  бессмысленны [35][145]. Счётчиков окон лимитов, планирования запусков под лимиты и экономного режима нет (поиск
  исследователя по документации, интерфейсу и коду на `f7365ff`).
- Большой расход tokens и медленная работа: инструкция runtime около 7 000 tokens на ход, статистика в 5–8 раз выше,
  чем у провайдера, squads в 6 раз дороже subagents Codex [135][130][121][126].

**Безопасность**
- Sandbox нет; каждый запуск работает со всеми правами пользователя ОС. Подтверждения у CLI выключены целиком, политики
  одобрения нет, plan mode и одобрения отдельных инструментов нет [42][83][94][166][114].
- Секреты агентов и конфигурация MCP — открытым текстом в базе сервера [19][162].
- Skills из внешних источников никто не проверяет и не изолирует [20].

**Надёжность работы без присмотра**
- Зависший в «Queued» чат, падения после сна Mac, шторм повторов, тысячи брошенных папок задач — часть исправлена,
  часть открыта [123][149][151][158].
- Режим локальной папки по умолчанию выполняет задачи по одной; чтение ждёт за записью [132][146].
- Отдельный worktree на запуск дорог для больших репозиториев и теряет локальную настройку агента [119][167].

**Платформы, интеграции, продукт**
- Сервер нужен всегда; локального режима без сервера нет [46].
- GitHub — только через GitHub App; в чужие open-source репозитории его не поставить [148].
- Перенести данные из Cloud в self-hosting нельзя [124]. SSO и OIDC нет [11][115][164]. Синхронизации с Jira нет
  [118]. Уведомлений по email не найдено [28].
- Сборки Windows не подписаны, Defender блокирует CLI; Environments на Windows нет [40][140][32]. iOS — только сборка
  из исходников, Android нет [41].
- Качество desktop: зависания отрисовки, неудачные обновления, спорный редизайн [157][128][155].
- Лицензия ограничивает fork и hosting для других; описание репозитория всё ещё говорит «open-source» [63][161][51].
- PR сообщества ждут review месяцами: медианный возраст открытого PR — 79 дней [72].
- Публичного roadmap и цен нет [147][5].

**Чего нет совсем** (поиск исследователя по документации, интерфейсу и коду; поиск xterm, node-pty, reactflow/xyflow и
tldraw в клиентах ничего не нашёл):
- терминала внутри приложения;
- встроенного браузера;
- просмотра diff внутри приложения (transcripts показывают diff правок файлов);
- canvas;
- режима продуктового советника или критика спецификаций;
- отдельного inbox для PR;
- скриншотов-доказательств со скрытием личных данных;
- счётчиков лимитов подписки и планирования под них;
- экономного режима (eco mode);
- векторной памяти [107].

## Механизмы, которые стоит изучить

1. **Квитанция о контексте на каждый запуск (context receipt).**
   - Что: запись о том, какой контекст на самом деле получил агент.
   - Как работает: daemon пишет на каждый запуск квитанцию (схема v1): какие источники переданы — инструкция runtime,
     инструкции агента, описание проекта, prompt, skills; их размер и короткий hash; способ доставки (файл, текст,
     prompt); насколько daemon уверен, что CLI это загрузил. Содержимое с машины не уходит. С v0.9.0 в интерфейсе
     видно, какие инструкции, skills и MCP servers получил запуск.
   - Источник: [92][6].
2. **Раскладка инструкций под кеш prompt.**
   - Что: постоянная часть инструкции отделена от данных конкретного запуска, чтобы начало prompt не менялось.
   - Как работает: постоянная инструкция runtime пишется в `CLAUDE.md` или `AGENTS.md` между маркерами
     `<!-- BEGIN MULTICA-RUNTIME … -->`, не трогая текст пользователя. Блоки запуска (родительский issue, шаг workflow,
     уведомление о потере session) дописываются после постоянной части. Сообщение на ход — одна строка:
     какой issue назначен и что начать надо с `multica issue get`. Цену ошибки показал #6008: переписывание `CLAUDE.md` в каждом запуске дало 76%
     записей в кеш за неделю; исправление уменьшило запись в кеш на 61% по замеру пользователя.
   - Источник: [85][86][142][6].
3. **Steering идущего запуска Claude Code через hooks SDK.**
   - Что: новое сообщение человека или агента попадает в уже идущий запуск, без перезапуска.
   - Как работает: daemon регистрирует callbacks `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`
     и `Stop` через управляющий протокол stream-json и на границах ходов добавляет `additionalContext`. Если ввод ещё
     ждёт, hook `Stop` продолжает тот же цикл. Пользователь выбирает одно из четырёх: добавить в текущий запуск, начать
     после него, остановить и начать заново, не запускать. Комментарий показывает отметку о прочтении. Агент может
     поправлять чужой запуск не больше 3 раз за ход, всего — не больше 10 сообщений на ход.
   - Источник: [84][26][96].
4. **Wakeups с защитой от бесконечных циклов.**
   - Что: агент сам ставит себе отложенную проверку — по времени, по событию, по CI или слиянию PR.
   - Как работает: правило хранится на issue (`multica issue wakeup create`, `--until-pr checks|merged|conflicts`).
     Условие checks не учитывает результаты, закончившиеся до создания правила. «Тихая проверка» может закончить запуск
     без комментария. Защиты: пауза, если цепочка триггеров третий раз проходит через правило без человека; пауза после
     более 12 срабатываний в час; не больше 32 правил на issue и 1 000 на workspace; срок ожидания до 30 дней и предел
     повторов 5–50. Wakeup-запуск действует от имени автора правила, права перепроверяются перед стартом.
   - Источник: [34][68].
5. **Классификация отказов с узким списком повторов.**
   - Что: каждая причина отказа — значение из словаря, и только малая часть причин повторяется сама.
   - Как работает: причины платформы (`runtime_offline`, `timeout`, `iteration_limit`, `agent_blocked` и другие) и 14
     причин `agent_error.*`, распознанных по тексту ошибки CLI. Значения лежат в базе и выводятся в Prometheus.
     Автоматически повторяются шесть причин, обычно 2 попытки (сеть — 3). Квота, rate limit и авторизация не
     повторяются. Продолжение session пропускает «испорченные» session (переполнение контекста, предел итераций, неверный
     запрос). Retry с новой session внутри хода — только когда новая session может помочь. Вкладка Errors показывает 7
     классов отказов.
   - Источник: [90][89][88][91][35].
6. **Watchdogs, которые не считают сон машины.**
   - Что: ноутбук, ушедший в сон, не убивает идущие запуски.
   - Как работает: watchdog простоя и watchdog инструмента (по 2 часа) считают время только пока машина не спит и не
     срабатывают, пока в буфере есть сообщения или уже пришёл финальный результат. Сервер ждёт переподключения runtime
     3 часа, прежде чем ронять идущие задачи. Финальные отчёты daemon пишет в очередь на диске и отправляет после
     восстановления связи; token в очереди не хранится. До исправления 2026-10-12 сон дольше 2 часов убивал все запуски.
   - Источник: [91][99][105][149].
7. **Очередь в Postgres с защитой захвата.**
   - Что: распределение запусков между машинами без отдельного брокера сообщений.
   - Как работает: захват — `FOR UPDATE SKIP LOCKED` по приоритету и времени создания; строка достаётся только runtime
     со свежим heartbeat и без другого активного запуска того же агента на том же issue. Защита от гонок:
     compare-and-swap по `dispatched_at`, аренда на подготовку 45 с, возврат потерянных захватов через 90 с. Один
     ожидающий запуск на пару (issue, агент): новые комментарии вливаются в него. Сигнал по WebSocket будит daemon,
     опрос раз в 30 с — запасной путь.
   - Источник: [88][89][67][26].
8. **Worktree для локальной папки с переносом незакоммиченной работы.**
   - Что: параллельные запуски в папке пользователя, не ломая его рабочую копию.
   - Как работает: режим `worktree` переносит незакоммиченные и неотслеживаемые файлы в worktree (до 2 000 файлов или
     200 MiB), ставит базовый коммит, пишет владельца ветки в `refs/multica/local-state/`, а остатки после запуска —
     в `refs/multica/leftovers/<branch>/<task>`. Одна ветка на issue, следующие запуски её продолжают. Ветку Multica не
     сливает. Режим `in_place` вместо этого выполняет запуски по одному под блокировкой папки.
   - Источник: [17][30][93].
9. **Отсечение устаревших запусков от смены статуса.**
   - Что: запуск, привязанный к шагу workflow, не может сдвинуть issue, если тот уже ушёл с этого шага.
   - Как работает: API отвечает `409 workflow_step_moved`; статусы вне workflow сервер отклоняет. Рядом — правила
     статусов в инструкции агента: ходы «вопрос — ответ» статус не пишут, чтобы параллельные запуски не дёргали доску;
     `done` оставлен людям. Карточка PR никогда не считает «нет проверок» успехом.
   - Источник: [16][86][38].
10. **Сдача результата только комментарием, с запасным путём и вырезанием секретов.**
    - Что: результат агента всегда попадает в историю задачи, даже если агент забыл его опубликовать.
    - Как работает: инструкция говорит, что вывод в терминал никуда не доставляется; сдавать — только
      `multica issue comment add --content-file`. Если агент закончил без комментария, сервер публикует запасной
      комментарий из финального вывода: со скрытыми секретами, до 8 000 символов. Перед записью в базу и отправкой по
      WebSocket transcripts чистятся регулярными выражениями от ключей AWS, PEM, token-ов GitHub и Slack, ключей `sk-`.
      Записи агента подписаны token-ом запуска `mat_`, который живёт до 24 часов.
    - Источник: [86][89][98][45].
11. **Автопауза автоматизации по доле отказов.**
    - Что: автоматизация, которая почти всегда падает, сама встаёт на паузу.
    - Как работает: раз в день проверяется Autopilot. Если за 7 дней было не меньше 50 запусков и 90% упали, он
      ставится на паузу, автор получает уведомление. Webhook-триггеры принимают подпись, ключ идемпотентности, фильтры
      событий GitHub и GitLab, повтор доставки и смену URL.
    - Источник: [33][99].
12. **Environments — dev-серверы, привязанные к issue.**
    - Что: человек открывает запущенное агентом приложение прямо из issue.
    - Как работает: репозиторий объявляет серверы в `.multica/environments.toml`; агент стартует их командой
      `multica env start`. Каждому environment выдаётся 10 портов, срок жизни (по умолчанию 24 часа), надзор за группой
      процессов и logs (последние 500 строк, со скрытыми секретами). Серверы, которые слушают порт внутри папки запуска,
      находятся сами. В боковой панели — открыть, скопировать URL, перезапустить, читать logs. Только macOS и Linux.
    - Источник: [32][6].
