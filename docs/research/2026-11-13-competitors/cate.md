## Модель работы

### Где работает: local, с удалёнными машинами пользователя

- Cate — desktop-приложение, local-first [2][30].
  - В beta 2.1 у каждого открытого workspace есть свой фоновый процесс — runtime (daemon). Он работает на машине, где лежат файлы проекта, и делает всю работу: файлы, git, поиск, терминалы, агенты [30][26].
  - Терминалы, агенты и наблюдение за файлами продолжают работать, когда приложение закрыто. При новом открытии приложение подключается к тому же живому состоянию [26].
  - Privacy policy: файлы и сессии хранятся на компьютере, где работает runtime этого workspace [2].
  - В stable 2.0.5 такого runtime ещё нет. Он пришёл с PR #744 (слит 2026-10-17) в линию beta 2.1 [83].
- **Удалённые машины.**
  - Страница Machines открывает папки на SSH-хостах (в том числе из `~/.ssh/config`) и в дистрибутивах WSL [26].
  - Runtime передаётся на машину при первом использовании, без install-скрипта. Соединение идёт через системный OpenSSH [26].
- **Headless-режим и свой сервер.**
  - Установка: `curl -fsSL …/releases/latest/download/install.sh | sh`. Скрипт кладёт runtime в `~/.cate/runtime`, а launcher `cate` — в PATH [42].
  - Команда `cate serve [path] [--connect]` отдаёт workspace сопряжённым устройствам и печатает QR-код для сопряжения [37][42].
  - Сборки runtime есть для darwin-arm64/x64, linux-arm64/x64 и win32-x64 [22].
- **Cate Connect — сервис вендора.**
  - Он помогает устройствам найти друг друга и пересылает трафик. Канал — WebRTC data channel. Signalling и STUN/TURN держит вендор [30].
  - Адрес по умолчанию — `wss://connect.cate.cero-ai.com`. Переменная окружения `CATE_CONNECT_URL` его меняет [69].
  - В публичном репозитории есть только тестовая замена сервера [69]. По описанию PR #744, код сервиса живёт в отдельном репозитории 0-AI-UG/cate-connect. Этот репозиторий отвечает 404: он закрыт или не существует (не подтверждено) [83][145].
  - Можно ли развернуть Cate Connect у себя — не подтверждено [69].
  - Трафик workspace шифруется end-to-end. Privacy policy: сервис «cannot read its plaintext» [2].
- **Аккаунтов нет.** Нет аккаунта Cate и нет входа через соцсети. Устройства сопрягаются по ключу устройства [35].
- **Облачные workspaces — план, а не продукт.** Файл `plan.md` описывает «Cate Cloud: EC2 Remote Workspaces» [36]:
  - платно: одна машина AWS EC2 с диском EBS на workspace, учёт оплаты через Stripe;
  - размеры Standard, Large и Compute — от 2 CPU / 4 GB RAM / 30 GB диска до 4 CPU / 8 GB / 50 GB;
  - на каждой машине работает процесс-runner; перед машинами стоит региональный gateway с mutual TLS; есть GitHub App;
  - совместное редактирование командой и Windows-workspaces явно вне первой версии;
  - цель: запустить несколько CLI-агентов, закрыть Cate и позже подключиться к тем же терминалам.
  - План добавлен 2026-07-26 и последний раз изменён 2026-09-05. Ни один release его не упоминает. Выйдет ли он — не подтверждено [36][26].

### Агенты и модели

- Своего агента в Cate нет. С 2.1 нет встроенного агента, с beta.10 у Cate нет своего доступа к моделям [26][30].
- Реестр — 7 CLI-агентов: Claude Code (`claude`), Codex (`codex`), Cursor (`cursor-agent`), Grok (`grok`), OpenCode (`opencode`), Pi (`pi`), Kiro (`kiro-cli`) [45].
  - У каждого записана команда resume, например `claude --resume <id>` и `codex resume <id>` [45].
  - CI ставит последнюю публичную версию каждого CLI, чтобы ловить изменения upstream [43]. В заметках к beta.8: «All seven agent CLI integration jobs passed» [21].
- **Аккаунты и модели.**
  - С 2.1.0-beta.10 агенты работают со своим аккаунтом и настройками CLI [26].
  - Beta.10 убрала управляемые workspace endpoints провайдеров, API-ключи и выбор модели. Beta.8 их только что добавила [26][21].
  - Выбор модели теперь живёт внутри каждого CLI [26].
- **Агенты, которых больше нет** [26][18]:
  - распознавание Gemini CLI (0.1.5). В коде упоминаний не осталось [30];
  - встроенная панель агента на основе Pi. В 1.2.0 её переименовали в «Cate agent»;
  - свои OpenAI-совместимые endpoints (1.1.1, 1.6.0);
  - панели чата T3 Code с 1.7.0 по 2.0.5, включая Antigravity. T3 Code — сторонний чат-интерфейс для coding-агентов [24];
  - Hermes: добавлен в 2.0.3, убран в 2.1.0-beta.1. Hermes 0.22 работает одним общим фоновым процессом, и hooks, настроенные на каждый терминал, больше не понимают, к какому терминалу относится сессия [26][82].

### Canvas и раскладка

- **Панели:** терминалы, редакторы Monaco, браузеры, просмотрщики PDF, изображений и DOCX, вложенные Canvas [23].
  - Панели лежат на Canvas свободно, собираются во вкладки и splits или выносятся в отдельные окна ОС [23].
  - Раскладка сохраняется для каждого проекта [23].
  - Вложенный Canvas нельзя положить внутрь узла Canvas [30].
  - Тип панели «surface» — заготовка, которая превращается в выбранный тип панели [30].
- **Инструменты Canvas** [26][18]:
  - minimap: клик переводит фокус, цвета — по worktree, видна иконка агента;
  - привязка к сетке (snap to grid);
  - выбор места для новой панели: пронумерованные варианты и вариант «Best»;
  - выделение рамкой, перетаскивание группы, закрытие группы;
  - переход между панелями с клавиатуры (Cmd+стрелка);
  - undo возвращает удалённые панели;
  - инструмент «рука» (hand tool).
- **Внешний вид** [26][18][30]:
  - обои: Hillside, 4K «Lighthouse» и «Snowy Pass» (beta.10) или своё изображение с затемнением;
  - настройки Canvas: скорость zoom, стиль сетки, фон и его прозрачность, `showWorktreeTerritory`, snap to grid, выбор места, auto-focus.
- **Убранные функции Canvas** [26][18]: стикеры, свободные области (regions), рисование от руки, сохранённые раскладки (убраны в 2.0.0), система расширений с панелями на своём сервере (1.4–1.6, убрана в 1.7.0). Полный список удалений — в подразделе «Функции, которые убрали».

### Терминалы, которые знают об агентах

- **Статус и уведомления** [23][12]:
  - на каждой панели терминала виден статус агента: работает, ждёт, закончил;
  - когда агенту нужен ввод, приходит уведомление. Клик по нему выводит вперёд именно этот терминал;
  - уведомления приходят при смене состояния, а не на каждое событие hook [12];
  - настройки уведомлений: вкл/выкл и «только когда окно не в фокусе» [30];
  - с 2.1 уведомления принадлежат workspace. Уведомление снимается, когда его агент снова начинает работать [26].
- **Сессии переживают перезапуск** [23][12]:
  - scrollback восстанавливается;
  - каждый агент подключается снова своей командой resume;
  - восстановление — намеренно одна попытка [12].
- **Общая очередь prompt** (beta 2.1) [23][38]:
  - у каждой панели есть очередь prompt, которую держит runtime. Prompt могут прийти из приложения, из CLI или с телефона;
  - prompt вводится, только когда агент стоит на своём приглашении к вводу. По одному и ровно один раз;
  - состояния: queued, sending, failed. Prompt, который за 10 секунд не начал ход агента, получает пометку `agent-prompt-not-taken`;
  - prompt в очереди или с ошибкой можно отозвать.
- **Вложения** (beta.2): фото и файлы. Claude Code, Codex, OpenCode и Kiro получают их через свой submit hook. Cursor и Grok получают их текстом после prompt [26].
- **Agent changes** [58]:
  - Cate записывает правки файлов каждого агента по событиям hooks. Они видны в представлении «Agent changes» с фильтром по агенту;
  - интерфейс предупреждает: правки, сделанные через shell или не сообщённые агентом, могут отсутствовать;
  - в beta.15 сводка правок поверх панели показывается только на панелях агентов [26].
- **Чип «Hooks off»** — на агентах с выключенными hooks [26].
- **Страница настройки агентов** (Agent setup): установить CLI, войти или сменить аккаунт, выбрать установку hooks для каждого агента — `auto`, `on` или `off` [30][26].

### Orchestration: сейчас и в прошлом

- **Сейчас встроенного orchestrator нет.**
  - Любой агент в терминале Cate может управлять другими через команды `cate agent`: `start`, `types`, `list`, `send`, `wait`, `read`, `withdraw`, `interrupt` [38][26].
  - `start` принимает `--agent <id>`, `--new-worktree <name>`, `--worktree` или `--canvas` [38].
  - Пример из встроенного skill: `id=$(cate agent start --agent codex --new-worktree fix-login "Fix the flaky login test"); cate agent wait "$id"; cate agent read "$id"` [38].
  - Встроенный skill `cate-cli` учит агентов так запускать других coding-агентов в своих панелях или worktrees и ждать их ответов [37].
- **В прошлом — «Cate Agent», с 2026-07-07 по 2026-10-17.**
  - 1.4.0-beta.1: «Always-on Cate Agent» — постоянно работающий агент. Он мог наблюдать за работой, запускать параллельные попытки, управлять терминалами и worktrees, продолжать задания [26].
  - 1.4.0-beta.3: «structured verifier verdicts» — структурированные вердикты по каждой проверке. Verifier — отдельный агент, который проверял попытку [26].
  - 1.6.0: «Agent mission orchestration». Missions — задания, которые Cate Agent планировал, раздавал coding-агентам в изолированных worktrees, вёл в фоне, проверял и убирал после завершения [26].
  - Пост основателя описывал то же устройство. Orchestrator только читает и задаёт цель и проверку. Попытки идут в свежих worktrees и в настоящих терминалах на Canvas. Отдельный verifier оценивает каждую попытку. Законченная работа ждёт review, пока человек не сольёт её, не откроет PR или не отбросит [11].
  - 2.1.0-beta.1 это убрала: «Missions and `cate codingAgent.*`, replaced by `cate agent start`» [26]. В коде на HEAD ни один файл не упоминает «mission» или «verifier» [44].
- **Модели задач нет.** Эпиков, тикетов, волн, очередей задач и досок задач не найдено [44].

### Worktrees и territories

- **Создание worktree** [23][55]:
  - пользователь пишет, над чем работает, и Cate создаёт worktree и ветку — от локальной ветки, удалённой ветки или открытого PR;
  - интерфейс спрашивает «What are you working on?» и делает из ответа имя ветки, например «fix the login bug» → `fix-the-login-bug`;
  - checkouts лежат в `<root>/.cate/worktrees/<slug>`.
- **Territory** — цветная область на Canvas вокруг панелей одного worktree [23][55]:
  - один клик создаёт git worktree со своей цветной territory;
  - область рисуется через WebGL, с запасным вариантом на CPU [66][44];
  - область следует за пометкой worktree у панели, а не за положением панели [55];
  - цвета — из палитры темы на 12 ключей, зелёный — для основного checkout [55].
  - Territories появились в PR #287 (2026-06-06). Старую функцию свободных «canvas regions» убрали в тот же день, в PR #306 [77].
- **Связанные функции** [26][18][55]:
  - чип worktree на панелях;
  - новые панели получают worktree выбранной панели;
  - Command palette предлагает «New `<panel>` in `<worktree>`»;
  - действия «Remove missing worktrees» и discard;
  - skills копируются в связанные worktrees.

### Usage и метры лимитов подписки (beta 2.1)

- **Usage** [26][62][30]:
  - открывается кнопкой Usage в sidebar (⌘⌥U);
  - показывает tokens и «API-equivalent cost» — сколько стоило бы то же самое через API. Разбивка по дням или часам, агентам и моделям. Данные читаются из файлов сессий самих CLI;
  - покрывает Claude Code, Codex, Grok и OpenCode. Kiro записывает только кредиты, Cursor — без счёта tokens. Интерфейс об этом говорит;
  - периоды: последние 24 часа, 7, 30 и 90 дней. Метрики: input, output, cache read/write и экономия на кэше;
  - свои цены моделей (USD за миллион tokens) — настройка workspace.
- **Вкладка Limits** [60][62]:
  - Claude Code: окно Session (лимит на 5 часов), окно Weekly и недельные окна по моделям;
  - Codex: окна session, weekly и monthly, плюс «reset credits banked» — накопленные кредиты сброса со сроком действия;
  - у каждого окна: остаток в процентах, «resets in 2h 13m» и pace — темп расхода: ahead, on или under, с допуском 5 пунктов от равномерного расхода;
  - использованная часть окна заштрихована, чтобы было видно, что вернёт сброс [62];
  - кнопка «Refresh limits» перечитывает лимиты;
  - Cate узнаёт лимиты так: запускает CLI и спрашивает его по JSON-lines протоколу, с timeout 20 с. Для Codex это вызов `account/rateLimits/read` [60][61].
- **Только показ.**
  - В коде ни один путь не использует лимиты, чтобы ставить агентов на паузу, планировать или замедлять [44][60].
  - Заметки о функциях и о направлении помечают это отсутствие как не подтверждённое: они проверяли только release notes и прочитанный код (не подтверждено) [18][60].
- Метры появились в PR #773 (2026-10-18). Они есть только в beta 2.1, не в stable 2.0.5 [84][18].

### Review panel и агенты-рецензенты

- **Review panel для diff многих файлов** (1.6.1-beta.5 / 1.7.0) [26]:
  - сравнивает working tree, staged, unstaged, commit или ветку с её merge base;
  - unified или split view, фильтр файлов, превью изображений;
  - локальные заметки review с severity, которые можно экспортировать;
  - stage, unstage, discard, commit, push и «open pull request» — для локальных, SSH- и WSL-workspaces.
- **Review агентом в терминале** [58]:
  - «Review in terminal» или «Review with Codex» запускают CLI агента с prompt для review только на чтение. Prompt велит в первую очередь искать ошибки корректности, регрессии, проблемы безопасности и недостающие тесты;
  - рецензент записывает замечания через `cate review note add` и заканчивает командой `cate review complete`;
  - «Send open findings to an agent» превращает открытые заметки в prompt на исправление. Этот prompt говорит не делать commit и push, пока пользователь не попросит;
  - роль рецензента одна. Типов рецензентов или lenses (разных углов проверки) не найдено.
- Как это устроено — в разделе «Как это устроено внутри → Проверка качества».

### Relations между панелями и connected editors

- **Relations** — типизированные связи между панелями. Пользователь рисует их на Canvas (с 2.0) [26][54]:
  - виды: use, context, verify, trigger;
  - пункты меню: «Hand off to», «Share context with», «Ask to verify», «Ask to review», «Send findings to», «Hand off fixes to»;
  - связь рисуется через одну из четырёх точек подключения на панели [30];
  - когда prompt отправляется, Cate дописывает к нему инструкции: выполнить `cate agent send --panel <target> …` [54];
  - режим контекста у каждой связи: Next (только следующий prompt), Always или Off [33].
- **Connected editors** [33]:
  - редактор, связанный с панелью агента, становится общим рабочим файлом. Autosave — через 300 мс;
  - несохранённые правки сохраняются перед отправкой prompt.
- **Предел.** Документ прямо говорит: это «does not execute relations, send tasks automatically, or coordinate agent workflows». Связи не исполняются сами, задачи сами не отправляются, работа агентов не координируется [33].

### Браузер и автоматизация браузера

- **Панели браузера** [18][26][30]:

  - Cate может стать браузером по умолчанию в macOS;

  - скрытые страницы выгружаются через 10 минут (beta.11).
- **Автоматизация агентами через `cate browser`** [39]:

  - вход и регистрация с сохранёнными логинами, логи консоли и сети, загрузки, пресеты viewport, управление вкладками.
- **Совместная работа с агентом** (beta.4). Агент, который работает на странице, не забирает фокус клавиатуры. Клик или ввод на этой странице возвращает управление человеку [26].

## Принципы и подходы

### Кто делает продукт и как работает команда

- Два основателя-брата. `CONTRIBUTING.md` описывает маленькую команду и продукт с твёрдым направлением [29]:
  - сначала issue, потом PR;
  - мейнтейнеры могут отклонить предложенное направление;
  - PR сливаются squash;
  - разработка идёт на Bun.
- `AGENTS.md` велит coding-агентам следовать skill «karpathy-guidelines» и требует запись в CHANGELOG перед каждым release [28].
- Основатели сами активно пишут код агентами:
  - Product Hunt отмечает, что Cate сделан с помощью Claude Code [141];
  - план рефакторинга от 2026-10-17 написан для агента, который будет его выполнять, не видя обсуждения на review. Каждый перечисленный баг сначала доказывается падающим тестом [34];
  - в одном iOS PR TestFlight проверяли через встроенный браузер самого Cate [85].
- Принципы головной студии (по-немецки, пересказ) [5]:
  - open source по умолчанию, под MIT, без lock-in;
  - сначала выпустить в production, потом рассказывать;
  - код можно выбрасывать, рефакторинг — обычная работа;
  - всё живёт на GitHub.

### Манифест сайта

- Проблема — «terminal overload», перегрузка терминалами. Решение — один бесконечный Canvas [1].
- «It is not another window manager». Tiling window managers только переставляют уже открытые окна. Cate даёт каждому проекту одно пространственное рабочее место. Инструменты и агенты делят там одну поверхность и сохраняют контекст [1].
- Финальный призыв — переосмыслить рабочее место теперь, когда агенты участвуют в работе [1].
- Отзывы на сайте — отобранные комментарии с Hacker News [1][119]. Как их отбирали — в разделе «Что говорят пользователи → Как вендор использует отзывы».

### Эссе основателей

Все эссе — Paul Horn, кроме отмеченного.

- **«The UI problem of AI coding agents» (2026-05-31)** [8]:
  - сессия агента — не вкладка терминала. Это задача с намерением, контекстом, состоянием, правами и побочными эффектами. Поэтому проблема — в рабочем месте, а не в терминале;
  - вкладки теряют намерение, ради которого задача начата;
  - запустить агентов легко, следить за несколькими сразу трудно. По его словам, «the bottleneck moves from keystrokes to attention» — узкое место смещается с нажатий клавиш на внимание человека;
  - рецепт: каждая задача — полноценный объект; терминал — честная запись того, что произошло; Cate — поверхность координации, а не «AI IDE»;
  - на этой поверхности терминалы, ветки, diff и логи остаются настоящими. Агенты видны как исполнители с видимым состоянием. Что важно, решает человек;
  - пять предпочтений: объекты задач вместо сообщений чата; worktrees вместо простых папок; видимое состояние агента вместо сырого вывода; явные одобрения вместо prompt; долгая история вместо scrollback терминала.
- **«Trusting AI blindly» (2026-06-06)** [9]:
  - когда агент говорит «готово», это набор отдельных утверждений, а не одно состояние;
  - слияние непроверенной работы агентов копит долг review. Отвечает за результат всё равно человек;
  - пример автора: брат-сооснователь слишком быстро сливал вывод агентов, и это дало баги и дублирование архитектуры;
  - объявлено, что review кода внутри Cate станет одним из главных направлений: работа агентов должна быть видна и проверяема на Canvas.
- **«The vibecoding addiction» (2026-06-12)** [10]:
  - циклы «prompt — повтор» похожи на игровой автомат: непредсказуемые выигрыши и «почти выигрыши» держат человека у автомата;
  - ссылка на исследование METR, где разработчики с AI работали на 19% медленнее;
  - ссылка на исследования о том, что профессиональные разработчики контролируют агентов, а не просто «вайбят».
- **«Designing an agent loop for coding» (2026-07-12)** [11]:
  - сейчас цикл работы агента — это сам человек;
  - спецификация цикла: триггер, цель, исполнение, проверка, правило остановки, память. Цель отделена от проверки, которая её проверяет;
  - проверка — лестница от слабой к сильной: (1) отчёт самого агента; (2) статическая проверка или сборка; (3) целевые тесты; (4) запуск продукта; (5) отдельный review;
  - повтор должен приносить новую информацию;
  - каждая попытка идёт в своём свежем worktree;
  - каждый запуск кончается явным состоянием: success, blocked, exhausted, cancelled или error;
  - правило «нет прогресса» останавливает циклы, которые никуда не ведут;
  - описан тогдашний Cate Agent: orchestrator только на чтение; каждая попытка — в свежем worktree, в своём терминале на Canvas; отдельный verifier; review, где человек выбирает merge, PR или отказ;
  - этот продукт потом убрали. Эссе остаётся самым ясным заявлением основателей о работе без присмотра.
- **«How we made six coding-agent CLIs observable without wrapping their processes» (2026-07-22, без автора)** [12]:
  - статус агента берётся из механизма hooks самого CLI. Hooks шлют события на локальный endpoint, у каждого терминала свой token;
  - если hooks CLI ничего не сообщают, Cate не показывает статус вовсе, а не угадывает;
  - session id подтверждается до восстановления сессии, и восстановление делается один раз;
  - уведомления приходят при смене состояния;
  - публичная модель — три состояния: working, waiting, finished.
- **«Why LLMs can't design dashboards» (2026-07-22)** [13]: в интерфейсах, которые делает LLM, узкое место — дизайнерское суждение, а не отрисовка.

### Инженерные принципы

Источник — `docs/architecture.md`, последний раз изменён 2026-11-12 [30]. Документ открывается тремя идеями:
1. Runtime daemon workspace — это и есть приложение. Всё, что трогает файлы, процессы, сеть или функции ОС, работает там. Окна — только клиенты.
2. У каждой задачи кода ровно одно очевидное место в коде и в модели.
3. Workspaces общие: несколько людей и телефонов работают в одном workspace одновременно.

Пронумерованные решения D1–D10, среди них [30]:
- **D1:** один daemon на workspace на каждой машине. Никогда — один общий локальный daemon.
- **D3:** все клиенты равны, ролей нет.
- **D4:** каждое сетевое соединение идёт внутри handshake Noise с закреплёнными ключами. Локальный socket защищён правами файла ОС (0600). CLI видит только capability `api`.
- **D5:** всё состояние лежит в папке данных workspace на машине runtime. Папка `.cate/` в репозитории держит только skills, временные файлы и checkouts worktrees.
- **D6:** между workspaces ничего не общее.
- **D8:** «clean cuts» — без кода миграций, без чтения старых форматов, без слоёв совместимости (shims).
- **D10:** `localhost` в панели браузера всегда значит машину runtime, какое бы устройство ни показывало панель.

Рабочие правила: нет shims и мостов между старым и новым кодом, мёртвый код удаляется. Если документ и код расходятся, прав документ [30].

Вопросы, которые документ держит открытыми [30]:
- зеркалирование браузера между клиентами;
- перенос настроек из одного workspace в другой;
- права на каждого человека;
- потребление ресурсов runtime.

### Чем подход отличается

- **Агенты остаются родными.**
  - С 2.1 нет встроенного агента, с beta.10 у Cate нет своего доступа к моделям. Агенты — настоящие CLI в терминалах, со своими аккаунтами и настройками [30][26].
  - Все прежние попытки иначе убраны: встроенный агент Pi, Missions Cate Agent, панель T3, Cate credits, свои API-провайдеры [26].
  - Агента, которого hooks не видят, убирают. Hermes убран в 2.1.0-beta.1 именно поэтому [26].
- **Права остаются у CLI.**
  - Документ об активности агентов: Cate не даёт переопределить одобрения и не меняет политику прав CLI [31].
  - Для Codex на странице настроек — только метка «Approvals: Automatic / Manual / Unknown» [31][63].
  - Много работы уходит на то, чтобы для каждого CLI отличить настоящий запрос человеку от автоматической проверки [31]. Уведомление Claude Code о запросе прав приходит примерно на 6 секунд позже. Для Codex Cate читает итоговый config через вызов `config/read`. Hooks Cursor и Kiro этого не различают, и Cate для них не поднимает сигнал внимания.
- **Canvas — граф, а не только раскладка.** Линии между панелями становятся контекстом prompt. В issue #745 Anton Horn приводит пример: Claude Code передаёт задачи computer use агенту Codex через CLI [117].
  - Пользователь в том же issue счёл функцию трудной для обнаружения. Anton Horn предложил выпустить второй skill с документацией по Cate [117].
- **Координация — у агентов, а не у центрального планировщика.** Своего orchestrator больше нет. Агенты сами вызывают `cate agent start/wait/read/send` [38][26].
- **Метры лимитов с темпом расхода.** Cate спрашивает лимиты у самих CLI, не отправляя prompt [30][61]:
  - Claude Code — control request `get_usage`;
  - Codex — `account/rateLimits/read` у `codex app-server`.
  - У окна лимита есть вид (session — например, окно Claude на 5 часов; weekly; monthly; other), остаток в процентах, время сброса, pace и накопленные кредиты сброса со сроками [62].
  - Стоимость считается по скану всех локальных транскриптов за 90 дней, по ставкам LiteLLM, с кэшем на файл [30][60].
- **Инженерная позиция:** clean cuts без shims; документ главнее кода [30].
- **Мало типов узлов на Canvas — намеренно.** Стикеры убрали именно по этой причине [108].

## Как это устроено внутри

Всё ниже описано по коду и документам на commit `c12247d`. Ничего не запускалось [44]. Описано состояние линии beta 2.1. Где stable 2.0.5 отличается, это сказано.

### Процессы и транспорт

- **Один runtime daemon на workspace** [30][27]:
  - он работает на машине с файлами и делает всё: файлы, git, поиск, терминалы (PTY — псевдотерминалы), агенты, API `cate`. Он держит всё состояние;
  - desktop- и iOS-приложения — тонкие клиенты. Они рисуют общий документ и пересылают ввод.
- **Установка и время жизни** [30]:
  - daemon — отдельный процесс Node, `runtime.cjs`. Он ставится для каждой сборки в `~/.cate/runtime/<build>/`;
  - daemon переживает приложение. Его PTY и процессы агентов — его дочерние процессы и живут, пока жив он;
  - releases содержат tarball runtime под каждую платформу и `install.sh` [18].
- **Транспорт** [30][27]:
  - локально клиенты подключаются через unix socket с правами `0600`: `~/.cate/workspaces/<runtimeId>/runtime.sock`. Захват этого socket — заодно и блокировка «один daemon на workspace»;
  - по сети — WebSocket в той же сети (поиск через mDNS) или Cate Connect: signalling-сервис вендора с relay TURN, поверх которого идёт канал WebRTC. Каждое сетевое соединение идёт внутри handshake Noise;
  - на SSH-хостах и в WSL работает свой daemon, который приложение туда передаёт. Граница доверия там — SSH.
- **Одновременный доступ** [30]:
  - пишет только runtime. Очередь записи — на каждую вещь: документ, сессию панели, путь файла, репозиторий;
  - общий документ — упорядоченный журнал операций с порядковыми номерами и epoch (номером запуска daemon). Клиенты применяют свои операции сразу и переигрывают их после переподключения;
  - в редакторах — по одному буферу Yjs на файл. Yjs — библиотека, которая сливает одновременные правки; поэтому одновременный набор не конфликтует;
  - все зрители терминала печатают в один PTY, «as in a shared tmux session».
- Клиент говорит с runtime только через протокол runtime (`kernel/rpc`): типизированные capabilities, объявленные один раз через `defineCapability`, и каналы сессий для панелей. Отдельного IPC на каждую функцию нет [27].
- **Правила кода:** импорты между слоями и «сторонами» проверяет dependency-cruiser в CI [27]. Политика «clean cuts» запрещает код миграций и shims [30].

### Модули и файлы

Слои `src/`, снизу вверх, по `CLAUDE.md` репозитория [27]:
- `kernel/` — rpc, api, settings, lifecycle, state, log, interaction (общие механизмы);
- `runtime/` — daemon, data, transports, security, pairing, connect, tunnel, power, push;
- `workspace/` — document, lifecycle (trust), canvas, files, repository, skills, relations, notifications;
- `services/` — terminal, browser, agents;
- `client/` — ядро клиента, соединения, workspaces, зеркало документа;

Внутри модуля код делится по «сторонам»: `contract` (чистые типы и логика, без Electron, Node, React и ввода-вывода), `runtime/` (сторона daemon), `node/` (общий код daemon и desktop), `client/` (логика клиента без React, DOM, Node и Electron), `desktop/` [27].

### Цикл агента: Cate наблюдает, но не владеет

- **Агент — запись в статическом реестре CLI:** claude-code, codex, cursor, grok, kiro, opencode, pi [45].
  - Запись хранит: команду, аргументы resume, где лежит хранилище сессий, аргументы prompt, клавиши прерывания, шаблон имени процесса, путь контекста prompt в ход, папку skills [45].
  - Каждая таблица по агентам — полное отображение по id агента. Новый агент не скомпилируется, пока в каждой таблице нет записи для него [45].
- **CLI работает без обёртки** — своим процессом в PTY панели терминала [30]. Bridge hooks срабатывает, только когда CLI сам вызывает свой hook [12].
- **Как внедряются hooks** [46][30]:
  - в файлы внутри репозитория: `.claude/settings.local.json`, `.codex/hooks.json`, `.cursor/hooks.json`, `.grok/hooks/cate-hook.json`, `.opencode/plugin/cate-hook.js`, файлы hooks Kiro, `.pi/extensions/cate-hook.ts`;
  - файлы, где есть и настройки пользователя, сливаются. Cate находит свои записи по маркеру `cate-hook` и сохраняет записи пользователя [46];
  - файлы скрываются через `.git/info/exclude`, никогда через `.gitignore`. Глобальный config пользователя Cate не пишет [47][27];
  - режим на агента: `auto`, `on`, `off`. `auto` внедряет hooks, только если в репозитории есть папка config этого агента или терминал запущен как этот агент [46];
  - файлы, а не флаги командной строки — намеренно. Shell aliases и добавления в PATH молча обходили старые флаги `--settings` и `-c` [46].
- **Как события доходят до runtime** [47]:
  - сгенерированный bridge на Node (его запускает Node самого daemon) отправляет JSON hook на loopback HTTP endpoint: 127.0.0.1, случайный порт;
  - у каждого терминала свой bearer token: HMAC-SHA256 от id PTY по секрету, который создаётся при каждом старте. Поэтому один терминал не может подделать события другого;
  - bridge всегда завершается с exit code 0. Timeout запроса — 3 с, жёсткий предел — 10 с. Сбой hook «must never surface into the user's agent turn» — не должен попасть в ход агента;
  - путь к bridge не меняется между перезапусками. Codex привязывает свой одноразовый запрос доверия к hook к этому пути [46][47];
  - для Codex Cate ставит в каждом PTY `CODEX_EXEC_SERVER_URL=''`, чтобы hooks сохраняли окружение этого PTY [46].
- **Единый поток событий** [46]:
  - виды: session-start, session-end, session-title, turn-start, turn-end, permission-check, permission-wait, turn-resume, input-submit;
  - для Claude Code: `UserPromptSubmit` → turn-start; `Stop`/`StopFailure` → turn-end; `PermissionRequest` → permission-check; `Notification(permission_prompt)` → permission-wait; hooks инструментов → turn-resume;
  - события от subagents (в них есть `agent_id`) отбрасываются. Поэтому `Stop` дочернего агента никогда не отмечает родителя готовым [46][31].
  - Здесь источники расходятся. Пост в блоге и документ об активности говорят о шести событиях: session-start, turn-start, permission-wait, turn-resume, turn-end, session-end [12][31]. В коде на HEAD видов девять [46]. Пост написан в июле, когда поддерживаемых CLI было шесть.
- **Машина состояний статуса:** running, waitingForInput, finished, notRunning [48].
  - Входы — события hooks, наличие процесса и Enter, который runtime видит в PTY. «There is no screen scraping» — экран не читается [48].
  - Изменение публикуется только при настоящем переходе состояния. Поэтому повторное ожидание уведомляет один раз [48].
  - Id сессии и хода отбрасывают поздние события ходов, которые уже прерваны [48].
- **Присутствие процесса** [49][48]:
  - реестр process id привязан к проверенным POST от hooks;
  - runtime идёт вверх по таблице процессов от родителя bridge, пока не найдёт процесс агента. При каждом обходе он проверяет этот процесс заново, сверяя имя, чтобы переиспользованный pid не считался;
  - когда процесс пропал, статус становится «finished». Это нужно, потому что Codex никогда не шлёт SessionEnd;
  - агент, чьи hooks не срабатывают, просто не обнаруживается [49][12].
- **Одобрения (approvals)** [31][63]:
  - Cate различает permission-check (может решиться автоматически) и permission-wait (подтверждённый запрос человеку);
  - для Codex Cate читает итоговый config одобрений через `codex app-server` `config/read`. Результат кэшируется на 30 с. За пределы runtime уходят только метаданные одобрений;
  - Cursor и Kiro не различают эти два случая, поэтому их ходы остаются в Running;
  - «There are no approval overrides and Cate never modifies the CLI's permission policy» [31]. Кода auto-approval в `src/` нет [44].
- **Прерывания** [46][45][51] — каждый CLI заканчивает прерванный ход по-своему:
  - Codex шлёт hook `Interrupt`;
  - Claude Code не шлёт ничего. Runtime читает хвост его транскрипта и ищет маркер «[Request interrupted by user»;
  - у Kiro нет ни того, ни другого. Ход завершает Ctrl-C самого терминала;
  - `cate agent interrupt` нажимает клавиши самого CLI: Esc, Ctrl-C или, у OpenCode, двойной Esc с паузой 500 мс.

### Доставка prompt — единственная раздача работы в Cate

- **Один путь для всех prompt.** Prompt из CLI, любого клиента, iOS-приложения и review panel идут через `sendToAgent` в одну очередь на панель [30][50].
- **Состояния:** queued (по порядку поступления), sending (по одному), failed [30][50].
- **Когда prompt уходит.** Только когда агент может его принять: процесс есть, hook это подтвердил, хода нет, запроса прав нет [48][50]. Очередь работает и тогда, когда ни один клиент не подключён [30].
- **Как prompt вводится** [50][51]:
  - как bracketed paste — вставка, которую программа отличает от набора с клавиатуры. Enter нажимается, когда программа отобразила вставку, или максимум через 2 с;
  - доставленным prompt считается, только если за 10 с пришло событие turn-start. Иначе prompt получает состояние `failed` с причиной `agent-prompt-not-taken`;
  - после сбоя ничего больше не вводится, пока не начнётся ход или кто-то не отзовёт prompt. Текст мог остаться в поле ввода CLI [50][38];
  - slash-команды считаются доставленными сразу [51].
- **Очередь только в памяти.** Она теряется, когда daemon завершается [50].
- **Старт агента** — `cate.agent.start`, требует доверия к workspace [52]:
  - выбирает агента, у которого hooks готовы для этого checkout;
  - может сначала создать новый worktree. Если старт не удался, удаляет этот worktree;
  - запускает CLI вместо shell в новой или свободной панели терминала;
  - панель считается «starting» до 60 с — до первого hook.
- **Resume после перезапуска** [53][51]:
  - session id для resume записывается только из событий hooks, никогда не через сканирование хранилищ сессий. Сессии Claude и Kiro записываются при первом событии хода;
  - id хранится в `agents/stamps.json` вместе с checkout панели;
  - при восстановлении Cate один раз вводит команду resume, например `claude --resume <id>` [12][51];
  - перед вводом session id проверяется строгим шаблоном: подделанный id мог бы внедрить флаги командной строки [45];
  - ход, который шёл в момент остановки daemon, не продолжается. Возобновляется только разговор, потому что процессы агентов — дети daemon [30][53].
- **Чтение разговоров** — из хранилища самого CLI, например JSONL Claude в `~/.claude/projects` [45][30].
  - На панель — одно наблюдение за файлами. Перечитывание идёт, только если файлы хранилища изменились [30].
  - Счётчик «generation» сбрасывает кэш сообщений, когда разговор очищен или переключён [30].

### Параллельность и координация

- **Встроенного планировщика и модели тикетов нет.** Координируют сами агенты, через команды CLI [37][38]:
  - `cate agent start --new-worktree <name> "<task>"`, затем `wait` (от 5 до 60 с за вызов), `read`, `send`, `withdraw`, `interrupt`, `list`;
  - этому учит встроенный skill `cate-cli`. Весь его «цикл»: start → wait (повторять) → read → send.
- **Relations** [54][30]:
  - пользователь рисует типизированные связи между панелями: use, context, verify, trigger («Hand off»);
  - runtime отказывает в связи, которая замкнула бы цикл;
  - при отправке prompt runtime собирает достижимые связи в блок `<cate-connected-panels>` с инструкциями вида `When ready, run cate agent send --panel <id> "<task>"`;
  - блок внедряется через submit hook самого CLI: как `additionalContext` у Claude и Codex, простым текстом у Kiro, через endpoint у OpenCode и Pi. Cursor и Grok его не получают [45][47];
  - режим по умолчанию — «once», только следующий prompt. Есть ещё «always» и «off» [54].
- **Connected editors** — общий файл с агентом: autosave через 300 мс, сохранение перед каждой отправкой prompt. Документ прямо говорит, что связи не исполняются и работа не координируется. Когда действовать, решают сами агенты [33].
- **Блокировок между агентами нет.** Агенты в одном checkout не защищены друг от друга. Изоляция — отдельный worktree на агента [44][55]. Файлы, которые агенты пишут мимо runtime, замечает только наблюдатель за файлами [30].
- **Раньше, в Cate Agent (июль — октябрь 2026), было иначе:**
  - задача превращалась в job card — карточку задания [79];
  - orchestrator только на чтение ставил цель и проверку [79];
  - попытки шли в свежих worktrees. Каждую вёл «driver», который запускал CLI в терминалах на Canvas [79];
  - отдельный verifier оценивал попытку; вердикты лежали в `.cate/verdict.json` [79];
  - человек выбирал merge, PR или отказ [79];
  - Missions умели повторить сбой, специфичный для одного CLI, другим агентом [26][80].

### Изоляция

- **Только git worktrees** [55][56][57]:
  - checkouts лежат в `<root>/.cate/worktrees/<slug>`. Имя ветки делается из свободного текста;
  - worktree можно начать от любой базы или от PR — через `gh pr checkout`.
- **Создание и удаление** [56][57]:
  - статус (creating → ready → removing) пишется в общий документ, поэтому прогресс видят все клиенты;
  - после падения недоделанные создания и удаления завершаются или отбрасываются. Worktrees, созданные вне Cate, принимаются;
  - удаление worktree по умолчанию удаляет и его ветку. Панели worktree закрываются или переносятся;
  - после создания Cate синхронизирует skills в новый checkout [56]. Setup-скриптов и копирования env-файлов не найдено [44].
- **Ничего сильнее worktrees.** Контейнеров и VM нет [44].
  - Единственная граница на запуск — доверие к workspace (trust). Пока workspace не отмечен доверенным, runtime не запускает ни одного процесса: терминалы, агенты, hooks, поиск и git отвечают «untrusted» [30].
  - Sandbox Codex не может достучаться до локального endpoint `cate`. Поэтому внедрённые инструкции велят Codex запускать команды `cate` вне sandbox, с повышенными правами [45].
- **Запланировано, но не выпущено:** в «Cate Cloud» — одна машина EC2 с диском EBS на платный workspace. Обещание безопасности там — изоляция клиентов друг от друга, «not isolation between a user's agent and that user's credentials» [36].

### Состояние и память

- **Пять классов состояния:** document, session, workspace data, device, client [27][30].
- **Данные workspace** лежат в `~/.cate/workspaces/<runtimeId>/` с правами `0700` [30]:
  - документ, сессии, настройки;
  - `secrets.json` с правами `0600`, без keychain ОС;
  - устройства, trust;
  - `agents/`: bridges, история правок, `stamps.json`, кэши usage;
  - логи терминалов и daemon.
- **Запись JSON-состояния** идёт через `kernel/state`: главное состояние — в памяти; запись с задержкой 150 мс; атомарный rename; наблюдение за внешними правками; битые файлы уходят в карантин с предупреждением [27][68].
- **Логи терминалов:** сырой вывод ротируется на 1 MB, экран сериализуется при остановке терминала. Восстановление берёт сохранённый экран, а если его нет — сырой лог [65].
- **Когда runtime продолжает работать** — настройка `keepRunningWhile` [30]:
  - условия: `agents` (идёт ход), `commands`, `clients`, `always`;
  - пока выбранное условие выполняется, runtime не даёт машине уснуть: `caffeinate` на macOS, `systemd-inhibit` на Linux, `SetThreadExecutionState` на Windows;
  - если клиентов нет и ничего не держит, runtime останавливается через 5 минут;
  - с 2.1.0-beta.2 агент, который стоит на приглашении к вводу, больше не считается работающим [26].
- **Приостановка простаивающих терминалов.** Невидимый терминал, который 2 минуты ничего не печатал, получает SIGSTOP на свою группу процессов. Он продолжает работу при показе или вводе. Включено по умолчанию, кроме Windows [65].
  - Исключения для агентов в этой проверке нет [65]. Может ли идущий ход агента на практике молчать так долго — не подтверждено.
- **Обновления runtime.** Клиент сам обновляет старый runtime, только если тот простаивает. Иначе спрашивает, потому что обновление останавливает терминалы и агентов [30].
- **Совместимость версий — источники расходятся.** README и заметки о направлении: клиент и runtime должны быть одной версии Cate [23][26]. Архитектурный документ: они должны совпадать по «compatibility version» [30]; beta.8 ввела общую «compatibility version 1» для разных releases [21].
- **Своей памяти и сжатия контекста нет.** Контекст доходит до агентов тремя путями: блок маршрутизации relations, файлы connected editors, skills [30][33][54][40]. История разговоров живёт в хранилищах самих CLI [30].

### Проверка качества

- **Review panel** сравнивает диапазон git (working tree, staged, commits, ветки) или правки, которые записали агенты [58].
  - «Review with agent» запускает одного рецензента-CLI в том же checkout. Prompt говорит, что review — только чтение, и перечисляет шаги: `cate review inspect`, `cate review note add --severity …`, `cate review complete` [58].
  - Только чтение держится лишь на тексте prompt. Sandbox и правил прав для рецензента Cate не ставит [44][58].
  - Закрыть review может только назначенный рецензент. Рецензент, который вышел, не закончив, отмечается как failed [58].
  - «Request changes» отправляет открытые замечания агенту, который написал изменение. Если его уже нет, запускается новый — с указанием добавить тесты и выполнить проверку [58].
- **Записанные правки агентов** берутся из успешных вызовов инструментов, о которых сообщают hooks `PostToolUse` [46][59].
  - Правки хранятся как неизменяемые patch-файлы на checkout. Prompt и вывод инструментов не хранятся [59].
  - Правка считается «активной», пока git показывает файл изменённым [59].
- **Gate проверки нет.** Cate не запускает тесты и не ждёт CI [44].
  - PR открывает `gh pr create --fill`. `prStatus` возвращает только номер, состояние, url и draft — без checks [57].
  - Отдельный обзор PR показывает сводку CI status checks для ваших PR и PR, ждущих вашего review, с кэшем 60 с [57].
- **Заявленное намерение:** основатели пишут, что review кода станет одним из главных направлений [9]. Июльский пост о цикле «цель → проверка → попытка → verifier» описывает orchestrator, который потом убрали [11][83].

### Восстановление после сбоев

- **Есть** [50][53][56][30][68][44]:
  - состояние failed у prompt и отзыв prompt;
  - одноразовый resume сессии после перезапуска;
  - починка worktrees, которые падение оставило наполовину созданными или удалёнными;
  - переигрывание документа после перезапуска — по epoch и порядковому номеру;
  - карантин битых файлов состояния;
  - кнопка Retry у терминала, который не смог стартовать.
- **Нет** [44][80]:
  - повтора хода после ошибки API;
  - ожидания сброса лимита;
  - «auto-continue» для остановившегося агента;
  - переключения на другого агента при сбое. Это было только в убранных Missions [80].
  - Поиск retry, backoff и обработки перегрузки в `src/` находит только кнопки повтора в UI и повторы соединения [44].
  - Заметки о направлении помечают отсутствие auto-approval, ожидания сброса и повтора ошибок API как не подтверждённое: проверены только прочитанные документы и код (не подтверждено) [31][62].

### Лимиты и стоимость

- **Движок usage** [30][26][60]:
  - разбирает append-only транскрипты Claude Code, Codex и Grok и базу OpenCode. Kiro пишет только кредиты, Cursor — без tokens; интерфейс так и говорит;
  - берёт только сессии, у которых рабочая папка — корень проекта или worktree под ним. Дубликаты убирает [30];
  - читает инкрементально: кэш на файл продолжает с последней прочитанной позиции [60];
  - стоимость: своя цена пользователя, иначе цена, которую записал CLI, иначе таблица ставок LiteLLM, которая обновляется раз в день. Результат — по дням или часам, по агенту и модели [30][60];
  - сканирует все локальные транскрипты за 90 дней, с кэшем на файл [30][60].
- **Запрос лимитов без prompt — запрос к модели не начинается** [61]:
  - Claude Code: runtime запускает `claude --output-format stream-json --input-format stream-json --strict-mcp-config --setting-sources ''` и шлёт control requests `initialize` и `get_usage`. Читает окно на 5 часов, окно на 7 дней, недельные окна по моделям и название плана;
  - Codex: runtime запускает `codex app-server` и вызывает `account/read` и `account/rateLimits/read`. Читает основное и дополнительное окна и накопленные кредиты сброса;
  - timeout каждого запроса — 20 с. Отчёты кэшируются на 60 с [60].
- **Pace.** Процент израсходованного сравнивается с долей окна, которая уже прошла. Больше чем на 5 пунктов выше — «ahead», больше чем на 5 ниже — «under» [60].
- **Только показ.** Ни один путь кода не использует лимиты, чтобы ставить агентов на паузу, планировать или замедлять [44][60].
- Запланированный биллинг облака требует: «Never silently stop a running agent at a budget threshold» [36].

### Права и безопасность

- **Права CLI.** У каждой области — чтение и управление, плюс общий выключатель [64].
  - По умолчанию: агенты — чтение и управление включены; панели и редактор — включены; браузер — чтение и управление включены. Ввод в терминалы и сохранённые пароли браузера выключены [64].
  - Документ честно говорит: эти права «are not a security boundary against programs running as the same OS user» — от программ того же пользователя ОС они не защищают [30].
  - У каждого PTY свой `CATE_TOKEN`. Он называет вызывающую панель и отзывается, когда её процесс завершается [30].
- **Сеть** [30][26]:
  - каждое соединение — `Noise_XX_25519_ChaChaPoly_BLAKE2b` с закреплёнными ключами. Cate Connect видит только шифротекст;
  - несопряжённые соединения ограничены по размеру, времени и числу. Код сопряжения сгорает после пяти неверных попыток;
  - у каждого сопряжённого устройства полный доступ, ролей нет (решение D3).
- **Учётные данные.** При входе на сайт runtime передаёт сохранённый пароль драйверу страницы, а не агенту [30].
- **Trust.** Недоверенный workspace не запускает процессов (см. «Изоляция») [30].
- **Telemetry.** С 1.3.1 crash reports в Sentry и usage analytics нельзя выключить (privacy policy от 2026-11-03) [2].

### Человек в цикле и наблюдаемость

- **На запросы одобрения отвечает человек — в терминале.** Это работает с любого клиента, включая iPhone, потому что все клиенты печатают в один PTY [30][31].
- **Уведомления** [67][30]:
  - только при переходах состояния: ход закончился или ждёт запрос прав;
  - задержка 300 мс против повторов, учёт настроек фокуса, отмена, когда агент снова работает;
  - push на iPhone шифруется для каждого устройства (ChaCha20-Poly1305) и идёт через Cate Connect. Очереди нет: если маршрута нет, push теряется [30].
- **Что можно наблюдать** [30][65]:
  - статус каждой панели;
  - живой разговор и шаги инструментов;
  - очередь prompt;
  - записи правок по checkout;
  - обзор usage;
  - ротируемые логи daemon и терминалов;
  - аватары присутствия.
- **Чего нет.** Timeline всего запуска и вида работы по дням нет. Единственная «timeline» в коде — история одного чата на iOS [44].

  - сначала статус угадывался по выводу терминала. Участник назвал это достаточным для ежедневной работы, но не окончательным;
  - внутри tmux это не работало. В 1.5.2 (2026-07-21) распознавание перешло на hooks агентов. Hooks пишутся в проект автоматически, если там есть папка `.claude`.
- **Побочные эффекты в проектах пользователей** [113][116]:
  - пользователь обнаружил, что несколько skills Claude ставятся автоматически при каждом входе в папку — даже при выключенной установке skill Cate CLI [113];

Появлялись пустые файлы с именами из кусков исходного кода, и могли выполниться команды. Исправили на следующий день; уборка этих записей при удалении приложения ещё не сделана [116].
- **Ограничения встроенного браузера:** вход через Google не работал. На Windows вход в ChatGPT зацикливался на проверке Cloudflare [93].
- **Удалённая работа по SSH:** цикл переподключения на Windows; не поддерживались SSH-сертификаты, пока Cate не перешёл на системный OpenSSH в v1.6.0; терминалы замирали после переподключения [102].

## Слабые места и чего нет

**Работа без присмотра и лимиты.**
- Нет режима «прогнать пачку задач без человека». Своего orchestrator больше нет: Missions убраны в beta.1 [26].
- Лимиты только показываются. Нет ожидания сброса, паузы или планирования работы по лимитам [44][60].
- Нет повтора хода после ошибки API, нет auto-continue, нет переключения на другого агента при сбое [44].
- Нет auto-approval — намеренно [31].
- Очередь prompt живёт только в памяти и теряется при остановке daemon [50]. Ход, который шёл при остановке, не продолжается [30].
- Невидимые терминалы получают SIGSTOP после 2 минут тишины, без исключения для агентов [65].

**Планирование и проверка.**
- Нет модели задач: эпиков, тикетов, волн, досок [44].
- Нет gate проверки: Cate не запускает тесты и не ждёт CI [44][57].
- Рецензент один, и «только чтение» держится лишь на тексте prompt [58].
- Relations не исполняются сами. Блок маршрутизации получают не все CLI: Cursor и Grok — нет [33][45].
- Записи правок неполны: правки через shell или не сообщённые агентом могут отсутствовать [58].

**Безопасность и права.**
- Изоляция — только worktrees. Контейнеров и VM нет [44].
- Права CLI не защищают от программ того же пользователя ОС [30].
- Ролей нет: каждое сопряжённое устройство имеет полный доступ [30].
- Секреты лежат в файле `secrets.json` с правами 0600, без keychain ОС [30].
- Codex приходится запускать команды `cate` вне своего sandbox, с повышенными правами [45].
- Hooks и skills пишутся в проект автоматически. На Windows это уже приводило к исполнению JSON через `cmd.exe` [113][116].
- Telemetry нельзя выключить [2].

**Стабильность и ресурсы.**
- Electron. Жалобы на CPU, нагрев и отрисовку в свёрнутом окне; этот issue открыт [127][118].
- Истории потери данных и состояния Canvas [110][98][106].
- Большие репозитории вешали приложение [104].
- Push на iPhone без очереди: если маршрута нет, push теряется [30].

**Продукт и процесс.**
- Частые удаления функций: 15+ за полгода. Пользователь жалуется, что функции исчезают без объяснений [26][117].
- Нет онбординга и документации для новичков [117][91].
- Ключевые функции 2.1 (общие workspaces, телефон, метры лимитов) — только в beta, у маленькой группы [18][22].
- Список releases на сайте не совпадает с GitHub [4][18].
- Отзывы на сайте отобраны и обрезаны [1].
- Нельзя положить на Canvas свои приложения. Встроенный браузер — без расширений и devtools [94].
- Нет timeline запуска и вида работы по дням [44].
- Нет MCP-сервера и управления MCP. Интеграции — только GitHub через `gh` [44][57].
- Нет профилей браузера: хранилище cookies одно на workspace [30].
- Скриншоты без скраба приватных данных [70].
- Компания в процессе регистрации. Почти весь код пишут два человека [3][15].
- Cate Connect — сервис вендора. Self-hosting и цена не подтверждены [69][145].

## Пересечение с worfy

worfy здесь — однопользовательское Electron-приложение для macOS (порт на Windows в работе). Оно запускает сессии Claude Code и Codex CLI и показывает их работу на бесконечном Canvas. Термины worfy в таблице:
- Epic — крупная цель из нескольких Tickets; Ticket — одна задача;
- Orchestrator session — сессия, которая планирует и раздаёт Tickets;
- Autopilot — режим, который прогоняет Waves (группы Tickets) без присмотра: ждёт сброса лимитов подписки, повторяет запросы при ошибках API, одобряет запросы прав по политике;
- Gate — локальный запуск проверок перед PR;

## Механизмы, которые стоит изучить

1. **Token на каждый терминал для hooks и bridge, который никогда не мешает ходу.**
   - Что это: способ получать события hooks от многих терминалов так, чтобы один не мог подделать события другого, а сбой hook не ломал работу агента.
   - Как работает: bridge на Node шлёт JSON hook на 127.0.0.1 со случайным портом. Bearer token терминала — HMAC-SHA256 от id PTY по секрету, который создаётся при каждом старте. Bridge всегда завершается с exit code 0; timeout запроса 3 с, жёсткий предел 10 с. Путь bridge постоянен, поэтому Codex не спрашивает доверие к hook заново.
   - Источники: [47][46][12].
2. **Отличать настоящий запрос прав человеку от автоматической проверки.**
   - Что это: сигнал внимания поднимается, только когда агент действительно ждёт человека.
   - Как работает: событие permission-check (может решиться само) отделено от permission-wait (подтверждённый запрос). У Claude Code permission-wait приходит из `Notification(permission_prompt)`, примерно на 6 с позже. У Codex Cate читает итоговый режим одобрений через `codex app-server` `config/read` с кэшем 30 с. События subagents (с `agent_id`) отбрасываются, чтобы `Stop` дочернего агента не отмечал родителя готовым. Для CLI, которые не различают эти случаи (Cursor, Kiro), сигнала нет.
   - Источники: [31][46][63].
3. **Доставка prompt с подтверждением начала хода.**
   - Что это: защита от prompt, который напечатан в TUI агента, но не принят.
   - Как работает: одна очередь на панель для всех источников. Prompt уходит, только когда процесс есть, хода нет и запроса прав нет. Ввод — bracketed paste, Enter — после отображения вставки или через 2 с. Если за 10 с нет turn-start, prompt получает `failed` / `agent-prompt-not-taken`, и дальше ничего не вводится, пока ход не начнётся или prompt не отзовут: текст мог остаться в поле ввода. Slash-команды считаются доставленными сразу.
   - Источники: [50][51][48].
4. **Присутствие агента по дереву процессов от hook.**
   - Что это: определение «агент ещё жив» без обёртки над процессом.
   - Как работает: от родителя bridge, который прислал проверенный POST, runtime идёт вверх по таблице процессов до процесса агента. При каждом обходе он сверяет имя процесса, чтобы переиспользованный pid не считался. Когда процесс исчез, статус — finished. Это закрывает случай Codex, который не шлёт SessionEnd. Прерванный ход Claude Code распознаётся по маркеру «[Request interrupted by user» в хвосте транскрипта.
   - Источники: [49][48][46].
5. **Запрос лимитов подписки без запроса к модели.**
   - Что это: окна лимитов Claude Code и Codex без расхода самого лимита.
   - Как работает: для Claude Code runtime запускает `claude` в режиме stream-json с `--strict-mcp-config --setting-sources ''` и шлёт control requests `initialize` и `get_usage`. Для Codex — `codex app-server` с вызовами `account/read` и `account/rateLimits/read`. Timeout 20 с, кэш 60 с. Pace: «ahead», если израсходовано больше чем на 5 пунктов выше доли прошедшего окна, «under» — если ниже. Использованная часть окна заштрихована; накопленные кредиты сброса Codex показаны со сроками.
   - Источники: [61][60][62].
6. **Resume только по session id из hooks.**
   - Что это: безопасное восстановление разговоров после перезапуска.
   - Как работает: id для resume берётся только из событий hooks, никогда из сканирования хранилищ сессий. Он хранится в `agents/stamps.json` с checkout панели. Перед вводом id проверяется строгим шаблоном, чтобы подделанный id не внедрил флаги. Команда resume вводится один раз; прерванный остановкой ход не продолжается.
   - Источники: [53][45][51].
7. **Hooks в файлах проекта со слиянием и без следа в git.**
   - Что это: способ внедрить hooks в 7 CLI, не трогая глобальный config пользователя.
   - Как работает: записи Cate помечены маркером `cate-hook` и сливаются с записями пользователя. Файлы скрываются через `.git/info/exclude`, а не `.gitignore`. Режим `auto` внедряет hooks, только если в репозитории есть папка config агента или терминал запущен как этот агент. Флаги командной строки отвергнуты, потому что aliases и PATH их молча обходили. Пользователи жаловались на этот подход: на Windows запись hook привела к исполнению JSON через `cmd.exe`.
   - Источники: [46][47][113][116].
8. **Relations как контекст в submit hook.**
   - Что это: связи, нарисованные на Canvas, превращаются в инструкции для агента.
   - Как работает: при отправке prompt runtime собирает достижимые связи в блок `<cate-connected-panels>` с командами `cate agent send --panel <id>`. Блок идёт через submit hook CLI: `additionalContext` у Claude и Codex, текст у Kiro, endpoint у OpenCode и Pi. Связь, которая замкнула бы цикл, отвергается. Режимы: once (по умолчанию), always, off.
   - Источники: [54][45][47].
9. **Условия, при которых runtime работает, и запрет сна машины.**
   - Что это: явная политика, когда фоновый процесс живёт после закрытия приложения.
   - Как работает: `keepRunningWhile` с условиями `agents`, `commands`, `clients`, `always`. Пока условие выполняется, runtime держит машину без сна: `caffeinate`, `systemd-inhibit` или `SetThreadExecutionState`. Без клиентов и условий runtime останавливается через 5 минут. Агент на приглашении к вводу не считается работающим.
   - Источники: [30][26].
10. **Один писатель и журнал операций с epoch.**
    - Что это: модель состояния, которая выдерживает несколько клиентов и перезапуски.
    - Как работает: пишет только runtime, у каждой вещи своя очередь записи. Документ — упорядоченный журнал операций с порядковыми номерами и epoch на каждый запуск; клиенты применяют свои операции сразу и переигрывают их после переподключения. JSON-состояние пишется с задержкой 150 мс и атомарным rename; битые файлы уходят в карантин.
    - Источники: [30][68].
11. **Ежедневный CI против свежих версий всех CLI.**
    - Что это: раннее обнаружение изменений в hooks и протоколах сторонних CLI.
    - Как работает: CI ставит последнюю публичную версию каждого из 7 CLI и запускает их против локальных fixtures моделей — на каждый PR и ежедневно в 06:23 UTC. Проверяются жизненный цикл hooks, одобрения, прерывания, resume и запись правок.
    - Источники: [32][43][21].
12. **Жизненный цикл worktree в общем документе.**
    - Что это: создание и удаление worktree, которое переживает падение и видно всем клиентам.
    - Как работает: статус creating → ready → removing пишется в общий документ. После падения недоделанные операции завершаются или отбрасываются; worktrees, созданные вне Cate, принимаются. `cate agent start --new-worktree` удаляет worktree, если старт агента не удался. После создания в checkout синхронизируются skills.
    - Источники: [56][55][52].
