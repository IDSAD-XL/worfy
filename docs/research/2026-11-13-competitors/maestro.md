- **Одной фразой:** Maestro — бесплатное open-source desktop-приложение на Electron для macOS, Windows и Linux. Оно
  запускает рядом много CLI coding-агентов (Claude Code, Codex, OpenCode и другие) и без присмотра проходит
  markdown-чеклисты задач. При этом оно ждёт сброса лимитов подписки и повторяет запросы при сбоях провайдера
  [1][12][14][15].

## Модель работы

- **Local.**
  - Desktop-приложение на Electron. Агенты — дочерние процессы на машине пользователя [10][75].
  - Облачного сервиса, где работали бы агенты, нет. Страница сравнения вендора отмечает «Cloud sandboxes» и
    «Container isolation per agent» как то, чего в продукте нет [2].
  - Установщики лежат в GitHub Releases [10][55]:
    - macOS: .dmg и .zip, Intel и Apple Silicon;
    - Windows x64: установщик NSIS и portable .exe;
    - Linux x86_64 и arm64: AppImage, .deb и .rpm.
  - Обновление — замена бинарника, данные остаются в папке конфигурации [10]. Сборка из исходников требует Node 22+.
    Работа под WSL2 описана [10].
  - Описание пакета Chocolatey `maestro-ai` лежит в репозитории. Публикация на chocolatey.org описана как шаг
    maintainer-а, который ещё впереди. Есть ли пакет в каталоге (не подтверждено) [81].
  - Auto-update есть с v0.8.7 (2025-12-16) [54]. Канал beta/RC включается по желанию [11][37].
- **Удалённые и серверные режимы** (подробности — в разделе «Функции»):
  - Web-интерфейс Live: desktop-приложение отдаёт весь интерфейс в браузер, есть раскладка для телефона [30][61].
    Доступ — по LAN или через Cloudflare tunnel; аккаунт Cloudflare не нужен [30].
  - Агенты на других машинах по SSH [32].
  - [RC] `maestro-cli host start` запускает Maestro без desktop-приложения: на сервере, в контейнере или на ноутбуке
    [65].
  - [RC] Cue server — движок автоматизации по событиям в виде образа контейнера или systemd service для
    Debian/Ubuntu. Помечен «early» [25][65].
  - [RC] Maestro Lite — тонкий клиент к удалённому полному Maestro [30][65].
  - [RC] Federation — агент живёт на удалённой машине и продолжает работу, пока ноутбук спит [31].
- **Telemetry.**
  - По умолчанию включены анонимная ежедневная отметка (случайный id установки, версия, ОС, архитектура CPU, тема) и
    отчёты о падениях в Sentry. Обе можно выключить [4][11][37].
  - Счётчики Cue уходят вендору с хешированными именами [4].
  - Prompts и код вендору не отправляются [4].
  - Документация расходится сама с собой. Страница Configuration упоминает только ежедневную отметку [37], а в коде
    настройка Sentry по умолчанию включена [121].
- **Агенты и модели.**
  - Maestro — промежуточный слой (pass-through) над CLI агентов, которые пользователь уже поставил. Каждый ход идёт в
    batch-режиме: prompt на вход, ответ на выход. MCP tools, skills, разрешения и логины пользователя продолжают
    работать как есть [9][10].
  - Провайдеры [10][12]:
    - Claude Code, Codex и OpenCode — «fully integrated»;
    - Factory Droid — «fully integrated» на странице установки [10], но «beta» на странице функций [12];
    - beta: Copilot-CLI, Grok CLI, Hermes, Pi, Qwen3 Coder, Oh My Pi;
    - Antigravity CLI добавлен в 1.0.0 [61];
    - Gemini CLI — «planned» [10].
  - Код помечает как beta всех провайдеров, кроме Claude Code и Codex, в том числе OpenCode. Значок в интерфейсе и
    документация расходятся [10][84].
  - Вендор пишет, что поддерживает десять провайдеров из фиксированного списка, без адаптера для «любого CLI» [2].
  - Локальные модели: Ollama или LM Studio через переменную окружения с base URL провайдера [16].
  - У Claude Code есть «token source» — способ вызова. Он выбирается для каждого агента [17]:
    - `claude -p` (print mode);
    - TUI Wrapper — интерактивный TUI Claude, которым управляет встроенный helper `maestro-p`;
    - Dynamic — начинает в TUI и переходит на `claude -p`, когда окно лимита плана почти исчерпано.
    - Документация говорит, что режим не меняет оплату: при входе по подписке оба пути тратят 5-часовой и недельный
      лимиты [17]. Как менялась эта позиция — в разделе «Лимиты и стоимость».
  - Codex по умолчанию вызывается через `codex exec`. Экспериментальный транспорт `app-server` позволяет steering —
    вставить сообщение в идущий ход агента [17].
  - Выбор модели:
    - модель по умолчанию на агента и pill модели и effort на каждой вкладке (pill — маленькая кнопка-метка в
      интерфейсе); pill принимает любой id модели [13][61];
    - override модели и effort на один запуск [14];
    - маркеры уровня `low`/`medium`/`high` внутри документов Auto Run. Для Claude Code они означают
      haiku/sonnet/opus; effort ложится на шкалу конкретного провайдера [14];
    - synopsis (краткий итог задачи) всегда идёт на самой дешёвой модели [14];
    - настройка Utility Agent отдаёт названия вкладок и сжатие контекста более дешёвому агенту [61].
  - Несколько аккаунтов [16]:
    - один аккаунт на агента; аккаунт выбирается переменной окружения `CLAUDE_CONFIG_DIR`, `CODEX_HOME` или
      `XDG_DATA_HOME`;
    - квота каждого аккаунта считается отдельно;
    - автоматически работа между аккаунтами не распределяется.
    - Смена аккаунта без повторного входа — открытый issue #1482 от 2026-09-01 [165].
  - [RC] Перевод агента между Claude Code и Codex: разговоры и память проекта конвертируются. Это preview, привязанный
    к версиям Claude Code 2.1.296/2.1.302 и Codex 0.162.1/0.163.0 [16][17][65].
- **Права по умолчанию.**
  - Вкладка без явного режима работает в Full Access и передаёт Claude флаг `--dangerously-skip-permissions` [84].
  - Режимы идут по кругу: Full Access → Standard → Read-Only. Standard показывает запросы инструментов и встречные
    вопросы агента прямо в приложении, но через SSH не работает [13][17].
  - Cue «always runs agents in YOLO mode», то есть всегда без подтверждений [25]. Запуски OpenCode одобряют всё
    автоматически [17].
- **Один пользователь или команда.**
  - Приложение построено вокруг одного человека — «conductor», который управляет набором агентов [2][71].
  - Web Login даёт каждому человеку свой аккаунт в web-интерфейсе и подписывает его сообщения. Но «There are no
    roles. Every account is an equal operator» [30].
  - Вендор оценивает командную работу как «Partial». SSO, SOC 2 и командные функции он считает вне рамок приложения
    для одного оператора [2].
  - Что есть для нескольких людей:
    - общая история проекта через SSH [38];
    - один hosted-агент обслуживает нескольких клиентов [31];
    - Relay даёт отдельные треды в Discord или Slack на пользователя [132];
    - bundles pipeline и агентов можно передавать другим [26].
  - Противоречие: сайт SMASH Labs называет Maestro платформой для команд инженеров [186], а страница сравнения —
    приложением для одного оператора [2].
- **Платформы.** macOS, Windows, Linux, WSL2; web-интерфейс в браузере и на телефоне [10][30]. Нативного мобильного
  приложения нет [2]. Около 81% загрузок установщиков приходится на macOS [56].

## Функции

Описание собрано по документации, коду и release notes [8][14][55][84]. «Агент» в Maestro — рабочее место,
привязанное к папке проекта и одному CLI провайдера. У агента есть AI-вкладки (одна вкладка — одна session
провайдера) и терминал [9]. Пометка **[RC]** — функция есть только в линии 1.1.x [8][65][84].

Видны ли Pianola и Concerto в стабильных сборках, источники говорят по-разному. Обе функции вышли в 0.18.5-RC [59],
и release notes v1.0.0 их включают [61]. Код Pianola в `main` есть, но за флагом plugin [116][117]. Показывает ли его
стабильная сборка, по коду проверить не удалось (не подтверждено).

### Раскладка и агенты

- **Три панели** [13]:
  - Left Bar — агенты, группы, закладки, фильтр;
  - главная панель — AI-вкладки, вкладки терминала, файлов и браузера;
  - правая панель — Files, History, Auto Run.
- **Статусы.** Цветная точка у агента: зелёная — готов, жёлтая — думает, красная — отключён. Красный значок —
  непрочитанное [13].
- **Группы.** Группы агентов с emoji в названии. Groups+ вкладывает группы в два уровня, с иконками и цветами
  [36][61]. [RC] Группы можно скрывать [13][65].
- **Сколько угодно агентов.** У каждого своё рабочее пространство и своя история [12]. Агента можно дублировать,
  экспортировать и импортировать как bundle — пакет с его настройками [13].
- **Вкладки.**
  - Вкладки раскладываются в split panes [12][61].
  - Вкладку можно отложить (snooze) до времени, заданного обычными словами. К ней можно приложить заметку и prompt,
    который запустится, когда время придёт [12][61].
  - Агента можно перенести в другое окно ОС [49][61].
- **Поиск существующих sessions.** Maestro находит sessions Claude Code, Codex, Copilot и OpenCode, в том числе
  созданные до установки Maestro. Их можно искать, отмечать звёздочкой, переименовывать и продолжать [1][12].
- **Очередь сообщений** на каждой вкладке [13]:
  - сообщения в очереди можно править, задерживать, переставлять, сливать и удалять;
  - Force Send отправляет сообщение параллельно, не дожидаясь очереди;
  - общий экран Execution Queue показывает очереди всех агентов.
  - [RC] Steer вставляет сообщение в идущий ход. Нужен Claude в режиме TUI или Codex через `app-server` [13][65].
- **Настройки агента** [13]:
  - скрытое New Session Message добавляется в начало каждой новой session, в том числе каждой задачи Auto Run;
  - скрытое Nudge Message добавляется в конец только к сообщениям, набранным вручную;
  - свой путь к бинарнику CLI, свои аргументы и переменные окружения;
  - дополнительные папки с отдельными переключателями чтения и записи.
  - Ещё есть глобальные переменные окружения и Conductor Profile — текст «о себе», который получают агенты
    [12][37].
- **Shell из чата.**
  - Command Terminal — настоящий PTY shell у каждого агента, со стартовой командой на вкладку [13].
  - Режим `!` выполняет shell-команды из поля ввода, даже во время хода агента [13].
  - AI Command Mode (`!!`): модель вкладки предлагает одну команду, пользователь её запускает или отклоняет [13].
  - У блоков shell-кода в ответах агента есть кнопка Run [63].
- **Контекст.**
  - Предупреждения при заполнении окна контекста на 60% и на 80% [46].
  - Действия: compact & continue (сжать и продолжить), слить sessions, отправить разговор другому агенту [46].
  - [RC] Автоматическое сжатие при переполнении [65].
  - Context Timeline — как заполнялся контекст по ходу разговора [61].
- **Memories.** Просмотр и правка памяти проекта Claude Code, в том числе в виде графа. С 1.0.3 то же работает для
  агентов Codex [47][54].
- **Файлы.**
  - Дерево файлов и preview. Встроенный редактор: автодополнение, несколько курсоров, клавиши Vim по желанию [12].
  - Отдельные viewers: jq по JSON/JSONL, таблицы CSV с фильтрами, Parquet с типизированным языком запросов,
    Mermaid, медиаплеер [12].
  - Document Graph — граф wiki-ссылок между документами [12].
  - [RC] Запросы Obsidian Dataview [36][53].
  - Аннотатор картинок [12].
- **Вкладки браузера.**
  - Встроенный браузер. Ссылка `maestro+https://` открывается в приложении, `system+https://` — в системном
    браузере [13].
  - Хранилище браузера — одно постоянное на агента плюс временные вкладки без сохранения (incognito) [84].
  - Именованные профили браузера (не подтверждено).
- **Прочее в интерфейсе.**
  - Закреплённые сообщения [13]. [RC] Собственный чеклист агента над полем ввода [13][65].
  - Фильтр вывода по regex; поиск по сообщениям во всех вкладках [12].
  - Slash commands с template variables. В комплекте наборы команд Spec-Kit, OpenSpec и BMAD — это сторонние
    методики разработки по спецификации [42].
  - 23 системных prompt ядра, которые пользователь может править [52].
  - 18 тем и конструктор тем [12]. README называет 12 тем, документация и страница сравнения — 18 [2][67].
  - Почти 100 переназначаемых shortcuts. Приложение отслеживает, какие из них пользователь освоил [1][43][51].
  - Системная горячая клавиша, которая вызывает окно Maestro [51].
  - [RC] Quick Chat — плавающее окно чата, которое открывается из любого приложения [53][65].
- **Первый запуск.**
  - Мастер первого запуска спрашивает шрифт, тему, настройки обновлений и отчётов о падениях и предлагает поставить

  GitHub через `gh` [12][48].

### Auto Run — запуск без присмотра

Auto Run — движок, который без человека проходит задачи из markdown-документов. До v0.6.0 он назывался Scratchpad
[57].

- **Spec-Driven mode** — режим по спецификации.
  - Проходит папку markdown-документов с чеклистами `- [ ]`. По умолчанию каждая задача получает новую session
    провайдера. Режим «per document» держит одну session на весь документ [14].
  - Maestro выбирает режим сам, по размеру окна контекста: пороги 5, 10 или 20 задач на документ при окне 256K,
    512K или 1M [14].
  - Документы можно ставить в очередь, переставлять и дублировать [14].
  - Loop Mode повторяет документы по кругу [14].
  - Reset on Completion: работа идёт на копиях в папке `runs/`, оригинал не меняется, копии остаются журналом аудита
    [14].
  - Сохранённая конфигурация запуска называется **Playbook** [14].
- **Goal-Driven mode** — режим по цели.
  - Пользователь задаёт цель текстом, критерии выхода и лимит итераций (или без лимита) [14].
  - Каждая итерация сообщает прогресс числом от 0 до 100 [14].
  - Запуск останавливается, когда цель достигнута, когда агент объявил тупик (deadlock), когда исчерпан лимит
    итераций или когда прогресс не растёт 3 итерации подряд [14].
  - Из CLI — команда `maestro-cli goal-run` [61].
- **Настройки запуска.**
  - Override модели и effort на запуск. Опция игнорировать подсказки модели, записанные в документах [14].
  - Запуск в новом или существующем git worktree. Опция «Automatically create PR» создаёт PR по завершении [14].
  - [RC] Отложенный старт «At a set time». Документация предлагает так стартовать сразу после сброса лимита токенов
    [14][65]. Функция сделана по запросу пользователя [157].
- **Маркеры в документе** — HTML-комментарии, которые читает движок [14].
  - Human-in-the-loop gate — точка проверки человеком. Запуск встаёт на паузу до кнопки «Done, Resume». Запуск без
    интерфейса пропускает такой документ и сообщает об этом [14].
  - Halt marker — агент пишет его, чтобы остановить весь playbook [14].
  - В preview маркеры показаны как pills, которые отражают своё состояние [14].
- **Stall guard.** Документ бросается после 3 запусков подряд, которые не отметили ни одного checkbox. Playbook
  переходит к следующему документу [14].
- **Thought Stream.**
  - Плавающая лента с поиском: рассуждения агента и вызовы инструментов по одной строке, в одном формате для всех
    провайдеров [14].
  - Лента копится с начала запуска, только в памяти, и теряется при перезапуске приложения [14].
  - Заметки «Steer Auto Run», набранные в ленте, уходят в следующую задачу. У каждой заметки видно, какой ответ
    агента её принял [14][62].
- **[RC] Delegation.**
  - Задача может вызвать `maestro-cli dispatch` и отдать работу другим агентам [14].
  - Запуск ждёт всех («Waiting on N delegated agents») и передаёт их результаты в следующий ход [14].
  - Ожидание одного делегата — 1 час по умолчанию, не больше 24 часов. Нужно desktop-приложение [14].
- **Прогресс.** «Document X of Y / Task X of Y», процент, прошедшее время и оценка окончания [14][62]. Каждая задача
  пишется в History с пометкой AUTO [14].
- **Восстановление.**
  - Auto-Resume on Limit — продолжение после лимита. Включено по умолчанию. Проверяет каждые 2 часа и сдаётся через
    7 дней. Для Claude перед продолжением читает фактическое использование плана; у других провайдеров просто
    повторяет запрос [14].
  - Auto-Resume on Limit переживает перезапуск приложения для разговора агента, но не для цикла Auto Run [14].
  - Auto-resume after error — продолжение после ошибки, настраивается на запуск. По умолчанию ждёт 5 минут, не
    больше 5 попыток [14].
  - Значок ERR на агенте: янтарный, пока повтор запланирован; мигающий красный, когда нужен человек [14].
- **Длительность.**
  - README: «my current record is nearly 24 hours of continuous runtime» [8][67]. Это рекорд создателя от декабря
    2025 [67][180].
  - Публичный leaderboard сейчас показывает отдельные запуски до примерно 125 часов. Самый длинный запуск создателя —
    50.7 часа (2026-09-25) [187].
  - Сторонний обзор приписывает создателю «80% успеха на 12-часовых запусках» (не подтверждено) [201].
- **Контент сообщества.**
  - Playbook Exchange — каталог playbook-ов сообщества из репозитория Maestro-Playbooks (manifest кешируется на 6
    часов), плюс локальные manifests [41]. В каталоге 17 playbook-ов, manifest обновлён 2026-11-10 [82].
  - Achievements — 11 рангов по суммарному времени Auto Run [43]. Публичный leaderboard — по желанию, с регистрацией
    по email [4][43].

### Сбои провайдера и лимиты — Agent Resilience

Agent Resilience — повтор запросов при сбое провайдера и при исчерпанной квоте. Включено по умолчанию [15].

- **Ошибки доступности** (529, 503, 502, 500, 429, ошибки сети). Повтор через 30 с, 1 мин, 2 мин, 4 мин, 8 мин,
  16 мин, затем каждые 30 мин [15][96].
- **Исчерпанная квота.** Документация и код расходятся.
  - Документация: проверки через 15 с, через 30 с, затем раз в минуту, и ещё одна ровно в момент сброса [15].
  - Код: 15 с, 60 с, затем каждые 15 минут, и ещё одна в разобранный момент сброса плюс 5 с [96]. Комментарий в коде
    объясняет: проверка раз в минуту тратила «the first half hour of a four-hour outage» [96].
- **Откуда берётся время сброса**, по порядку [15]:
  - поле `quotaLimits.resetsAt` у Claude Code;
  - поля или фразы `retryAfter`, `resetAt`, «try again in N»;
  - устаревший маркер epoch у Claude;
  - текст баннера с часовым поясом.
  - Время без часового пояса игнорируется [15].
- **Никогда не повторяются:** неверные или истёкшие учётные данные, отказ в доступе, session не найдена, полное окно
  контекста, падение процесса, human-in-the-loop gate, не установленный CLI [15][96].
- **Интерфейс.**
  - Одна живая карточка статуса на каждый сбой, с кнопками Try now и Stop [15].
  - Сообщения в очереди ждут. Упавший prompt остаётся сверху с пометкой «Awaiting retry» [15].
  - Статистика — на Usage Dashboard: сколько времени простоя перекрыто, какая доля сбоев закончилась восстановлением
    [15].
- **Пробелы.**
  - Запланированные повторы не переживают выход из приложения. Это сделано нарочно: закрытое приложение не должно
    тратить квоту [15].
  - Пакетные запуски из `maestro-cli` не повторяются автоматически [15].
- **Кредиты сброса лимита Codex.** Их можно погасить вручную или автоматически, один раз на сбой. Автоматический
  режим выключен по умолчанию [15][18].
- **Failover.** «Fail over to a backup endpoint» упомянут только в README [67]. Страница сравнения пишет, что это
  заявление удалено [2]. Failover (не подтверждено).
- **Запрет сна.** Пока агенты работают, система не засыпает. По желанию не гаснет и экран [37].

### Агенты работают с агентами

- **Cross-Agent Mentions.**
  - `@agent` в сообщении — одноразовая консультация с другим агентом в фоновом процессе. Режим — только чтение или с
    правом записи [34][61][62].
  - Ответ подписан именем агента и приходит прямо в разговор [34].
  - Несколько упоминаний идут параллельно. От формулировки зависит, будет это консультация или передача работы [34].
- **Group Chat.** Агент-модератор ведёт разговор нескольких агентов в несколько раундов и пишет итог. Можно смешивать
  локальных агентов и агентов по SSH. В 1.0 вышел из beta [33][61].
- **Координация через CLI.** Команды `maestro-cli dispatch`, `ask`, `send`. Флаг `--notify-on-complete` будит
  вызвавшего агента карточкой с результатом. Так агент-orchestrator проходит цикл build → review → fix → verify, и
  человеку не нужно передавать результаты руками [35][61].
- **Pianola** — plugin «агент-менеджер», выключен по умолчанию [20]:
  - закреплён в Left Bar; следит за выбранными агентами, которые ждут ответа на вопрос или на запрос разрешения;
  - отвечает по правилам пользователя (scope / match / action, срабатывает первое подходящее) или передаёт вопрос
    человеку (escalate);
  - запросы высокого риска всегда уходят человеку; если подходящего правила нет — тоже человеку;
  - решение записывается в журнал Decisions до отправки ответа;
  - правила можно получить из прошлых transcripts пользователя;
  - `--dry-run` классифицирует запросы, но не отвечает.
  - [RC] Планы задач с зависимостями (`pianola orchestrate`). Необязательные `requiredChecks` держат задачу в
    статусе `needs_review`, пока названные проверки не пройдут [20][125].
  - Рабочее имя Pianola в планах разработки — «Autopilot» [20][83].
- **Записи запусков и кампаний** через `maestro-cli agent-run` и `campaign`. Описаны только в справочнике CLI [35].

### Maestro Cue — автоматизация по событиям

Cue — plugin, который запускает агентов по событиям. Документация говорит, что он включён по умолчанию [23], а главная
страница — что выключен [1]. По release notes он включён по умолчанию с 0.18.5-RC [59].

- **Подписки.** Подписка — триггер плюс prompt. Подписки лежат в `.maestro/cue.yaml` и перечитываются на лету [23].
- **События** [23][24]:
  - `app.startup`;
  - `time.heartbeat`, `time.scheduled`, `time.once`;
  - `file.changed`;
  - `agent.completed`;
  - `task.pending` — неотмеченные задачи в markdown;
  - `github.pull_request`, `github.issue`, `github.label`;
  - `cli.trigger`;
  - `webhook.received` с проверкой подписи HMAC.
  - Документация говорит об 11 типах событий [23][24]. Webhook-триггер добавлен в 1.0.0 [61].
- **GitHub-триггеры** опрашивают GitHub через `gh` раз в 5 минут по умолчанию. Они могут принимать webhooks и
  срабатывать заново на новые комментарии [24].
- **Pipelines:** fan-out, fan-in, фильтры по payload, цепочки агентов, узлы с shell-командой, лимиты параллельности,
  своя модель и effort на подписку [23][62].
- **Окно Cue** [23]:
  - Dashboard с кнопкой Run Now;
  - Scheduled Tasks;
  - визуальный Pipeline Graph с кнопками Tidy и Arrange; у узлов агентов есть выбор модели;
  - Pipeline List;
  - Activity Log — payload, exit code, stdout;
  - редактор YAML с шаблонами и «AI Assist».
- **Агент назначает себе продолжение:** `cue schedule --in 20m`. С флагом `--here` продолжение вернётся в ту же
  вкладку [23][54].
- [RC] **Bundles** — экспорт pipeline или агента вместе с Claude skills, конфигурацией MCP, CLAUDE.md и памятью.
  Секреты вычищаются [26][65].
- [RC] **Cue server** — Cue без desktop-приложения на сервере (образ контейнера или systemd service, «early»)
  [25][65].
- **Пример вендора.** X-аккаунт @RunMaestroAI работает на Cue. Pipeline из восьми цепочек ищет в X посты под
  кампании, пишет ответы и публикует их после одобрения человеком [27][183].
- **Рецепт «Karpathy loop»** в документации — это пример настройки Cue, а не встроенная функция [28]:
  - агент-оценщик оценивает каждый запуск по рубрике и пишет результат в `evaluations.jsonl`;
  - аналитик раз в неделю предлагает правки файла `program.md`;
  - человек одобряет правку checkbox-ом («Do not automate the checkbox»), правка коммитится.

  - Доступ — по LAN или через Cloudflare tunnel [30].

- **SSH remote execution** — агенты на других машинах по SSH с тем же набором функций: Git, дерево файлов, Auto Run,
  Group Chat [32][54].
- **Общая история между машинами** через SSH [38].
- [RC] **Federation** [31]:
  - SSH-агент переезжает на headless host на удалённой машине;
  - ходы, очередь, Auto Run и Cue продолжаются, пока ноутбук спит;
  - Maestro сам ставит себя на удалённую машину и общается через SSH tunnel; sudo не нужен.
- [RC] **Maestro Lite** — тонкий клиент. Находит Maestro по LAN или Tailscale, сопрягается одноразовым PIN или
  подключается через SSH/HTTPS. Помечен «early» [30][65].
- **Web Login** (по желанию) — отдельные аккаунты для людей в web-интерфейсе [30].
- **Синхронизация между устройствами (beta).** Настройки хранятся в папке iCloud, Dropbox или OneDrive. Рассчитано на
  одно устройство за раз; побеждает последняя запись [37].
- [RC] **`maestro-cli host start`** — Maestro без desktop-приложения. Картинки, смена провайдера и запуски Auto Run
  в worktree по-прежнему требуют desktop [65].

## Принципы и подходы

### Constitution

CONSTITUTION.md — файл с принципами продукта в корне репозитория. Создатель добавил его 2026-01-04, седьмой принцип —
2026-04-11 [71].

- **Главная идея.** Дать одному человеку управлять многими агентами сразу и не распылять внимание. Пользователь — это
  «conductor», он направляет «fleet», то есть набор своих агентов [71]. Описание пакета и слоган сайта говорят то же
  самое [9][67].
- **Два режима** [71]:
  - Solo Mode — агенты работают без присмотра, пока человека нет;
  - Interactive Mode — человек управляет агентами вживую.
- **Семь принципов** (пересказ) [71]:
  1. **Unattended Excellence.** Успех измеряется тем, как долго агенты работают без вмешательства человека.
     - Auto Run — главная функция.
     - Восстановление после сбоев должно быть автоматическим.
     - Каждое прерывание считается сбоем.
     - Leaderboard награждает автономность, а не активность.
     - Autonomy Principle: «Every feature we build should extend the runway of unattended operation». Функция,
       которая требует больше присмотра, — шаг назад.
  2. **The Conductor's Perspective.** Обзор важнее деталей. Статус должен читаться с одного взгляда. Пакетные операции
     лучше одиночных. Агентам доверяют и направляют их.
  3. **Keyboard Sovereignty.** Ни одна функция не должна требовать мыши. Escape всегда возвращает в известное
     состояние. Фокус ввода никогда не перехватывается.
  4. **Instant Response.** Задержка считается bug. Тяжёлая работа идёт в фоне.
  5. **Delightful Focus.** Делать хорошо управление агентами и отказываться от лишних функций. Сначала доводить
     существующее, потом добавлять новое.
  6. **Transparent Complexity.** Сложные функции показываются, только когда нужны, и включаются по желанию. «Iceberg
     Principle»: около 90% возможностей не видны, пока не понадобятся.
  7. **Agent Omniscience** (добавлен в апреле 2026). Всё, что пользователь видит и делает, агенты тоже могут видеть и
     делать — через CLI и файловую систему. Разговор агентов друг с другом — полноценная операция.
- **Чем Maestro себя не считает** [71]:
  - не IDE;
  - не обёртка над одним агентом;
  - не чат;
  - не project manager: он исполняет, а планирование — работа агентов;
  - не законченный продукт.
- **«Maestro Test»** — семь вопросов перед выпуском любой функции [71]:
  - Продлевает ли она работу без присмотра?
  - Улучшает ли она управление агентами?
  - Можно ли пользоваться ею без мыши?
  - Быстрая ли она?
  - Оправдана ли её сложность?
  - Порадует ли она пользователей?
  - Может ли агент сделать это без рук человека?
  - Одно «нет» — повод пересмотреть функцию.

### Как принципы закреплены в разработке

- **CLI parity — у каждого действия интерфейса есть команда CLI.** CLAUDE.md — инструкции репозитория для
  coding-агентов — делает это обязательным правилом [72][73]:
  - каждое действие интерфейса выходит вместе с командой `maestro-cli`; формулировка — каждое действие «MUST have a
    maestro-cli path» [72];
  - у интерфейса и CLI одна реализация;
  - путь через CLI не открывает диалогов;
  - у каждой записи есть парное чтение;
  - соответствие ведётся в таблице CLI-UI-PARITY.md [73].
- **«Focus belongs to the human».** Агент может создать вкладку или панель, но не должен переключать то, что видит
  пользователь. У команд CLI есть флаг `--background`, и агентам велено передавать его по умолчанию. Аудит этого
  правила датирован 2026-08-19 [73].
- **Цели разработки.** CONTRIBUTING.md называет быстрый отклик интерфейса и малый расход батареи [74].
- **Encore Features — правило против разрастания продукта.**
  - Необязательные функции выходят выключенными и полностью невидимыми, пока их не включат: ни shortcuts, ни пунктов
    меню, ни строк в palette [1][36].
  - Функции, которые себя оправдали, «graduate» — выходят включёнными по умолчанию [1][36].
  - В 0.18.5-RC и 1.0.0 Encore Features переименованы в Plugins [59][61].
- **Privacy как «open ledger».** Страница privacy перечисляет все сетевые вызовы приложения [4]:
  - счётчик установок;
  - счётчики Cue с хешированными именами pipelines;
  - leaderboard — по желанию;
  - отчёты о падениях в Sentry.
  - У каждого вызова есть выключатель. Prompts и код к вендору не уходят.
- **Осторожный Pianola по умолчанию** [20]:
  - без правил он только сообщает;
  - автоматически отвечает только по правилу, которое написал пользователь;
  - запросы высокого риска всегда идут человеку, потому что transcripts агентов считаются недоверенным вводом;
  - правила, полученные из прошлых transcripts, ждут одобрения человека.

### Как создатель описывал продукт

- **Демо в декабре 2025.** Описание подчёркивает быстрый интерфейс и параллельные экземпляры агентов. Сначала
  поддерживался только Claude Code [193].
- **Release notes v0.12 (декабрь 2025).** Переключатель «Show Thinking» появился, потому что его просили чаще всего.
  Сам создатель предпочитает видеть результат работы, а не процесс, — как с коллегами-людьми [54].
- **Разрешения (issue #76, январь 2026).** По словам создателя, batch-режим провайдеров сам по себе означает обход
  запросов разрешений. Кому нужен контроль, пусть запускает провайдера во вкладке терминала [135].

### Чем подход отличается — позиция вендора

Источник всего подраздела — страница сравнения вендора («battle cards»), ревизия 11 от 2026-11-11 [2]. Это оценка
вендора о самом себе.

- **Собственный счёт.**
  - Maestro делает 27 из 39 возможностей, которые страница отслеживает, — больше всех в таблице. Следующий — Cursor с
    26 [2].
  - Если считать частичную возможность за половину, два конкурента немного впереди: 29.5 и 29 против 28.5. Страница
    признаёт, что отрыв маленький [2].
- **Где вендор ставит себя на первое место** (7 направлений) [2]:
  - запуски без присмотра длиной в дни; по словам вендора, никто из конкурентов не строит продукт вокруг этого;
  - цепочки работы: Cue реагирует на события, а конкуренты только запускают по расписанию;
  - восстановление после сбоя провайдера: повтор запроса и ожидание реального момента сброса лимита;
  - наблюдаемость работы агентов;
  - инструменты для данных и файлов: jq, фильтры CSV, язык запросов Parquet;
  - расширяемость: большой CLI, SDK `maestro-lib`, MCP server на агента, deep links, plugins;
  - работа с клавиатуры и темы.
- **Где вендор признаёт отставание** (5 направлений) [2]:
  - охват провайдеров: десять провайдеров из фиксированного списка, адаптера для «любого CLI» нет;
  - рабочее место IDE: правка кода — простое редактирование в preview, diff только для чтения;
  - выход за пределы репозитория: нет автоматизации desktop-приложений; удалённое управление — web-приложение или
    PWA, а не нативное мобильное приложение;
  - голос: только диктовка в мобильном web-интерфейсе;
  - изоляция: worktrees изолируют checkout, но не домашнюю папку.
- **Вне рамок продукта намеренно** (3 направления) [2]:
  - облачные sandboxes — только локальная работа и SSH;
  - SSO и SOC 2 — приложение для одного оператора;
  - командная работа — Web Login даёт нескольким людям общий экземпляр, все равны, ролей нет.
- **Собственная карточка Maestro** [2]:
  - первыми перечислены восемь известных пробелов;
  - главная сила — один markdown-чеклист одновременно служит планом, точками проверки человеком, подсказками модели
    на задачу и трекером прогресса;
  - «Pick us if»: работа должна идти, пока вы спите, с измерениями и по событиям, а не по часам;
  - итог: Maestro сделан, чтобы запустить пятнадцать задач и вернуться завтра; для чтения diff и правки файла он
    заметно отстаёт.
- **Метод сравнения** [2]:
  - ранжирование по возможностям, а не по популярности;
  - частичная возможность считается за ноль у всех, включая Maestro;
  - утверждения о конкурентах должны ссылаться на документацию самого конкурента;
  - сборка страницы падает, если таблица изменилась без записи в журнале ревизий;
  - ревизия 2 (2026-09-01) убрала из счёта звёзды и «mindshare»;
  - ревизия 11 убрала заявление Maestro о failover.
- **Взгляд вендора на рынок** (заявления вендора о других компаниях, не проверены; не подтверждено) [2]:
  - рынок сокращается, и выживание при ежедневных релизах подаётся как достоинство;
  - Conductor купила Meta, и 2026-11-04 он закрыт для новых пользователей;
  - Vibe Kanban сворачивается;
  - Terragon больше нет;
  - Crystal переименован в Nimbalyst и не развивается.

## Как это устроено внутри

Раздел написан по коду веток `main` (коммит `86b2258`) и `rc` (коммит `d5d97d2`) и по документации [66][84]. Код

### Процессы и стек

- **Стек.** Main process и renderer process Electron. Renderer — React со stores на zustand. Зависимости: electron
  ^41.5.0, node-pty 1.2.0-beta.12, better-sqlite3, fastify ^5.12.6, reactflow, chokidar, electron-store,
  @sentry/electron [85].
- **Процессы агента.** У каждого агента один процесс AI (дочерний процесс) и один процесс терминала (PTY) [75].
- **Вызов Claude.** Claude запускается с `--print --verbose --output-format stream-json`. Вкладка продолжает свой
  разговор у провайдера через `--resume` [105].
- **Где живёт цикл Auto Run.**
  - Контроллер цикла и все координаторы продолжения — React hooks в renderer: `useBatchRunner`,
    `useAutoResumeCoordinator` [86][97].
  - Main process только следит, чтобы у агента был один старт Auto Run за раз, через `claimAutoRunStart` [86].
  - Код объясняет почему: «Renderer stores cannot serialize starts across desktop and browser clients» [86].
  - Координатор продолжения пишет, что приложение «must be open to resume regardless» [97].
- **Перезапуск приложения.**
  - Состояние пакетного запуска «is intentionally NOT reconstructed on cold start». «The orchestration LOOP does not
    resume; the agent session and its queued work do» [97]. Документация говорит то же [14]. Запланированные повторы
    тоже теряются [15].
  - Release notes 1.0 при этом пишут, что запуск, остановленный на лимите, продолжается даже после перезапуска [61].
    Официальные источники расходятся; что верно (не подтверждено).
- **Второй движок Auto Run — внутри `maestro-cli`.** Это async generator, который выдаёт события JSONL. В нём нет
  повторов, нет watchdog и нет обработки квоты [14][15][93].
- **Два движка разошлись.** Документ проекта в `rc` от 2026-10-04 сравнивает их по 24 пунктам поведения и перечисляет
  12 расхождений [122]. Примеры:
  - в CLI нет паузы на ошибке, нет продолжения после лимита, нет watchdog и нет запуска в worktree;
  - CLI считает задачи, не учитывая code fences;
  - CLI игнорирует выключатель `autoRunDisabled`;
  - desktop забирает одно сообщение из очереди каждый раз, когда процесс задачи завершается посреди запуска.
- **План сведения в `rc`.** Оба движка переходят на общую библиотеку `maestro-lib` с явной политикой для каждого
  интерфейса [123]:
  - CLI: пропускать документы с gate, продолжать после ошибки, без продолжения после лимита, без
    checkpoint-коммитов;
  - desktop: пауза на gate и на ошибке, продолжение после лимита, checkpoint-коммиты.
  - Общий runtime пока не умеет запуски в worktree, steering, рабочие копии на каждый круг Loop Mode, повторы
    Agent Resilience и Auto Run по SSH [123].
- **Агенты управляют Maestro через его CLI.**
  - Правило в CLAUDE.md: каждое действие интерфейса «MUST have a maestro-cli path» [72].
  - CLI связывается с работающим desktop по WebSocket. Адрес он берёт из файла `cli-server.json`, для доступа нужен
    секрет [76][114].
  - System prompt размером 31.6 KB передаётся при каждом запуске агента через `--append-system-prompt` и учит агента
    этим командам [115].
  - Порядок старшинства инструкций: Nudge Message, затем New Session Message, затем Conductor Profile, затем system
    prompt [115].

### Цикл агента: Auto Run по спецификации

- **Вход.** Папка markdown-документов. Задача — строка `- [ ]` [14].
- **Порядок.** Документы идут последовательно, сверху вниз. Опции: очередь из нескольких документов, Loop Mode и
  Reset on Completion. Reset on Completion работает на копиях в `runs/` и не меняет оригинал [14].
- **Свежий контекст.** Настройка «Fresh context per» — Task (новая session на каждую неотмеченную задачу) или Document
  (одна session на документ). Maestro советует вариант по размеру окна контекста (256K, 512K, 1M) и среднему числу
  задач в документе (пороги 5, 10, 20) [14].
- **Одна задача (`processTask`)** [14][88]:
  1. Подставить template variables и записать раскрытый документ обратно.
  2. Прочитать подсказки `<!-- MAESTRO:MODEL tier= effort= -->`.
  3. Вставить блок выбора задачи.
  4. Добавить в начало заметки steering и New Session Message.
  5. Запустить агента.
  6. Перечитать документ. Число завершённых задач = max(0, отмечено после − отмечено до).
- **Учёт ведёт сам агент.** Prompt по умолчанию велит агенту [89]:
  - взять первую неотмеченную задачу (в режиме per document — все);
  - заменить `- [ ]` на `- [x]`;
  - «Ensure that test cases are created, and that they pass»;
  - «Commit after EVERY task. One task, one commit» с префиксом `MAESTRO:`, затем «Push to GitHub»;
  - выйти, потому что остальное сделает другой экземпляр агента.
- **Заметки steering** от пользователя старше и prompt, и документа. Synopsis задачи, в которую вмешались,
  начинается с `[steered]` [89].
- **Synopsis.** Источники описывают его по-разному.
  - Документация: synopsis всегда идёт на самой дешёвой модели [14].
  - Код desktop в `main`: synopsis — первое предложение ответа агента, без отдельного хода [88].
  - Политика CLI в `rc` тратит на synopsis отдельный ход продолжения [123].
  - В апреле 2026 пользователь измерил, что второй проход с итогом после каждой задачи — часть накладных расходов.
    Maintainer добавил флаг, который этот проход отключает [158].
- **Состояния запуска.** IDLE → INITIALIZING → RUNNING → PAUSED_ERROR или STOPPING → COMPLETING → IDLE [87].
  Прогресс опрашивается раз в 20 с [86].
- **Правило остановки (stall).** Три запуска подряд без изменения checkbox — документ брошен, playbook идёт дальше
  [14][90].
  - Прогресс — это состояние checkbox, а не объём текста: «a document that grew by a thousand words of apology - is
    no progress» [90].
  - Срабатывание watchdog сразу засчитывается как остановка [14][86].
- **Watchdog.** Проверяет раз в 15 с. По умолчанию убивает задачу после 240 минут без активности или после 480 минут
  всего [94][95].
  - До 1.0.3 для Claude Code он считал активностью только финальное сообщение с результатом. Так он убил занятую
    задачу с subagent после 240 минут. Исправлено в `main` 2026-11-11, вошло в 1.0.3 [64][173].
- **Halt marker** `<!-- maestro:halt: reason -->` останавливает всю дальнейшую раздачу задач. Внутри code blocks он
  игнорируется. Старый маркер блокирует повторный запуск, пока его не уберут [14][86].

### Цикл агента: Auto Run по цели

- Одна цель текстом. Каждая итерация — новый агент: он делает один шаг и выходит [14].
- Агент пишет `<!-- maestro:progress N | rationale -->`. Нет маркера — прогресс 0. Ещё есть маркеры «цель
  достигнута» и «тупик» [14][89].
- **Выход:** 100% или маркер завершения; тупик; лимит итераций; нет роста 3 итерации. Жёсткий максимум — 500
  итераций [14][92].
- **Связь между итерациями.** Отдельный ход продолжения просит закончившего агента написать записку для следующего:
  около 150 слов, не длиннее 1500 символов. Записка вставляется через `{{PREDECESSOR_HANDOFF}}` вместе с указанием
  сверить её с репозиторием [92].
- **Checkpoints.** Desktop делает коммит после каждой итерации [91].

### Расписание

- Разовый старт «at a set time» переживает перезапуск приложения. Для него нужен Cue [14].

### Планирование и разбиение на задачи

- **В стабильной версии нет модели эпиков и тикетов.** Разбить работу — значит написать документы с checkbox [14][71].
- **Wizard.** Разговаривает, пока уверенность не дойдёт до 80 (`READY_CONFIDENCE_THRESHOLD`). Потом пишет документы
  фаз в `.maestro/playbooks/Initiation/` [14][77].
  - Фаза 1 должна дать самостоятельный работающий прототип [77].
  - «The Auto Run engine ONLY executes `- [ ]` checkbox items» [77].
- **Повторное использование.** Playbooks, общий каталог Playbook Exchange, наборы команд Spec-Kit, OpenSpec и BMAD
  [8][14].
- **Стоимость внутри плана.** Подсказки модели помечают дешёвые и дорогие задачи. Запуск «per document» делится там,
  где меняются итоговые настройки модели [14].
- **[RC] Планы задач Pianola** [20][125]:
  - граф зависимостей `dependsOn`;
  - статусы задачи: pending, running, needs_review, fixing, done, failed, blocked, skipped;
  - на программу: `maxConcurrent`, `maxAttempts`, `validationRequired`;
  - `pianola orchestrate <plan-id>` отдаёт задачу в фоновую вкладку, как только готовы её зависимости.

### Параллельность и координация

- **Агенты работают параллельно.** У каждого агента своя очередь выполнения: операции записи идут по одной, операции
  только на чтение — параллельно. Очередь сохраняется в записи агента [75].
- **Без worktree** Auto Run работает в checkout агента, и «Manual write messages queue behind Auto Run». **С
  worktree** — «True parallelization» [75].
- **Group Chat внутри** [75]:
  - модератор раздаёт работу через @mentions;
  - упомянутые агенты работают как параллельные batch-процессы;
  - модератор пишет итог; ответ модератора без @mentions заканчивает ход;
  - чат хранится в `chat.json`, `log.jsonl` и `history.json`.
- **Консультация через @mention.** Maestro запускает новый временный процесс `cross-agent-<requestId>`, а не печатает в
  живую вкладку адресата. Ответ попадает во вкладку консультации. Повторные консультации продолжают session адресата
  у провайдера [112].
- **Делегирование** [14][113]:
  - `maestro-cli dispatch` открывает скрытую вкладку у другого агента;
  - Auto Run ждёт всех делегатов до следующей задачи и вставляет их результаты в следующий prompt;
  - ожидание — 1 час по умолчанию, не больше 24 часов;
  - callbacks живут в памяти, одновременно не больше 200;
  - переменные окружения `MAESTRO_CALLER_AGENT_ID` и `MAESTRO_CALLER_TAB_ID` записывают, кто делегировал.
- **Cue** (настройка в `.maestro/cue.yaml`) [78]:
  - триггеры: старт приложения, таймеры heartbeat, расписание и разовый запуск, изменения файлов (через chokidar),
    завершение агента, опрос PR, issues и labels в GitHub, неотмеченные задачи, webhooks, CLI;
  - `max_concurrent` на агента — 1 по умолчанию;
  - очередь хранится в SQLite и проигрывается при старте;
  - цепочки обрываются на глубине 10; у fan-out и fan-in есть timeouts;
  - вывод предыдущего шага обрезается до 5000 символов;
  - после сна машины дольше 120 с расписание делает один догоняющий запуск.
- **[RC] Orchestrator Pianola.** Координатор работает по одному шагу за вызов, на задачу — не больше 3 попыток
  исправления [117][125]. Перед раздачей он сохраняет claim — запись о том, что задача отдана. Если ответ потерян,
  claim ждёт сверки и не отправляется повторно [20].

### Изоляция

- **Единица изоляции — git worktree для агента, по желанию** [29][107]:
  - создаётся через `git worktree add -b <branch> <path> <base>` или подключается к существующей ветке;
  - лежит в «Worktree Directory», которая задаётся у родительского агента;
  - путь занимается до `add`, чтобы не было гонки с наблюдателем файлов;
  - есть вариант для удалённой машины по SSH.
- **Setup script** у родительского агента. Получает переменные `MAESTRO_WORKTREE_PATH/BRANCH/MAIN_REPO_PATH/BASE_BRANCH`
  (так их записывает документация): путь worktree, ветку, путь основного репозитория и базовую ветку. Ограничен 10
  минутами, его сбой не блокирует работу. Файлы из .gitignore и зависимости не копируются [29].
- **Auto Run в worktree.** Запуск может создать новый worktree и по желанию открыть PR по завершении (`auto-run
  --worktree ... --create-pr`). Как сливать и решать конфликты, документация не описывает [29].
  - Агентам велено пользоваться `maestro-cli create-worktree`, а не голым `git worktree` [114].
  - Правило проекта держит worktrees внутри Worktree Directory. Оно появилось после случая 2026-09-11: готовая
    функция день пролежала незакоммиченной [72].
- **Контейнера или VM для агентов desktop нет.** Агенты работают с правами пользователя [76]. Вендор признаёт:
  worktrees изолируют checkout, но не домашнюю папку [2].
- **Серверный режим.** Headless-движок Cue ограничивает переменные окружения, которые наследуют агенты. Агенты там
  работают без подтверждений, поэтому документация советует отдельную машину или контейнер [25].
- **Фильтр окружения Cue.** Переменные из `cue.yaml` не могут задать PATH, HOME, USER, SHELL, LD_PRELOAD,
  LD_LIBRARY_PATH, DYLD_INSERT_LIBRARIES и NODE_OPTIONS, без учёта регистра [78].
- **[RC] Проверки в sandbox.** Проверочные команды Pianola идут в bubblewrap с `--unshare-net` и `--clearenv`, под
  лимитами systemd-run: 600 с, 2 GiB, 256 процессов. На Windows — через `wsl.exe` [125][126].
  - «Missing kernel, bubblewrap, or user-manager controls are errors, never an unsandboxed fallback» [126].
  - Сами агенты в sandbox не работают.
  - Работает ли sandbox на macOS (не подтверждено): встроенный runner требует Linux-инструментов bubblewrap и
    systemd-run [126].

### Состояние и хранение

- **JSON-хранилища (electron-store):** bootstrap, settings, sessions (агенты), groups, настройки агентов,
  capabilities, состояние окон, происхождение sessions [118].
- **Синхронизация** через облачную папку, по желанию. Одно устройство за раз, побеждает последняя запись [37].
- **History** — файлы JSONL на агента [118]. Записи Auto Run содержат id session, synopsis и полный ответ [14].
- **SQLite в режиме WAL:**
  - `stats.db`: query_events, auto_run_sessions, auto_run_tasks, session_lifecycle, resilience_events,
    wizard_runs и другие таблицы [119];
  - `cue.db`: события (хранятся 14 дней), постоянная очередь событий, heartbeat, уже виденные объекты GitHub, outbox
    telemetry [78].
- **Журнал запусков агентов (agent-run ledger)** [109][111]:
  - файлы `maestro-agent-runs.json` (и архив), `maestro-agent-run-events.jsonl`, `maestro-campaigns.json`;
  - запись хранит статус (от queued до merged или discarded), проверки, findings review с уровнем серьёзности, PR,
    итог merge, затронутые файлы и использование;
  - лимит хранения добавили после того, как «a heavy user reached 7,500 runs / 20MB», а каждая запись занимала
    около 150 мс в main thread [111].

### Память и контекст

- **Своей системы памяти нет.** Maestro показывает и правит память провайдера: `projects/<path>/memory/MEMORY.md` у
  Claude и `memories/` у Codex [8][120].
- **Длинные запуски** держатся на свежих sessions на задачу или итерацию, на документе как общем состоянии и на
  записке преемнику в режиме по цели [14][92].
- **Сжатие контекста** [46]:
  - ручное сжатие при объёме больше примерно 50 тыс. токенов: части сжимаются параллельно, потом до 3 проходов
    объединения;
  - Claude сжимает сам, когда получает «Prompt is too long»;
  - но «Auto Run tasks are not compacted automatically» [46], а полное окно контекста никогда не повторяется [15].
- **Перенос контекста.** Работу можно передать или слить между агентами, даже разных провайдеров [46]. Preview-функция
  конвертирует память и sessions между конкретными версиями Claude Code и Codex [17].

### Проверка качества

- **В стабильной версии нет gate.** В пути Auto Run нет встроенного запуска тестов, quality gate или агента review.
  - Проверка — это инструкция в prompt: писать тесты, добиться их прохождения, коммитить, делать push [89].
  - Сам движок проверяет только изменения checkbox, остановку, watchdog и маркеры halt и HITL (human-in-the-loop —
    точка проверки человеком) [86][88][90].
  - Создатель подтвердил 2026-07-25: команды проверки до или после задачи нет; о завершении агент сообщает сам,
    отмечая checkbox [152].
- **PR** создаётся через `gh pr create --base --title --body-file -` [108]. Symphony открывает draft PR [1][108].
- **Статус CI в `main` не читается.** Поиск `gh pr checks`, `statusCheckRollup` и check runs нашёл только проверку
  формата поля `checks` в журнале запусков [109]. Ветку `rc` так не искали (не подтверждено).
- **В журнале запусков есть поля, но не gate.** Поля проверок и review заполняются через `maestro-cli agent-run`,
  например агентом, который сам записывает свою проверку. Код приложения, который их пишет, в `main` вызывается только
  из тестов [109][110].
- **Агенты review** в `main` не найдены; `rc` не проверяли (не подтверждено).
- **Рецепт из документации** — «Karpathy loop» на Cue: оценщик, еженедельный аналитик, одобрение человеком [28].
- **[RC] Приёмка в Pianola** [20][117][125][126]:
  - «Successful execution and acceptance are separate»;
  - каждая проверка из `requiredChecks` должна иметь статус `passed` на `runId` задачи; иначе задача остаётся в
    `needs_review`, и зависимые задачи ждут;
  - открытые findings уровня high или critical тоже блокируют;
  - проверки идут в sandbox bubblewrap, до 3 попыток исправления.
  - Без объявленных проверок «готово» по-прежнему означает только, что выполнение закончилось [20].

### Восстановление после сбоев

Сбои обрабатываются на трёх уровнях.

- **Уровень 1: Agent Resilience (на агента).**
  - Ошибки доступности (529, 503, 502, 500, 429, сеть): первый повтор через 30 с, дальше пауза удваивается до 30
    минут, потом повторы каждые 30 минут без конца [96].
  - Ошибки квоты: 15 с, 60 с, затем каждые 15 минут, плюс проверка в разобранный момент сброса + 5 с [96].
    Документация пишет «15s, then 30s, then once a minute» [15]. Код и документация расходятся.
  - Не повторяются никогда: истёкшая авторизация, отказ в доступе, session не найдена, HITL gate, полное окно
    контекста, падение процесса, не установленный CLI [15][96].
  - Время сброса разбирается в порядке надёжности: `quotaLimits.resetsAt`; `retryAfter`, `resetAt` или «try again
    in N»; устаревший маркер `|epoch`; текст баннера с часовым поясом. Время без часового пояса отбрасывается [15].
  - Баннер лимита Claude приходит как обычное сообщение ассистента. Он распознаётся, только если занимает всё
    сообщение целиком [15][104].
  - Повтор — это повторная отправка исходного prompt с картинками, slash commands и настройками модели. Пока квота
    исчерпана, провайдер отказывает до траты токенов, поэтому проверка ничего не стоит [15].
  - Очередь ждёт; упавший prompt остаётся сверху как «Awaiting retry». Auto Run встаёт на паузу и при продолжении
    перечитывает документ [15].
- **Уровень 2: Auto-Resume on Limit (глобально).**
  - Включено по умолчанию. Проверяет каждые 2 часа, сдаётся через 7 дней [14][99].
  - Claude продолжает работу, только когда `maestro-p --status` показывает оба окна использования ниже 99%. Другие
    провайдеры и агенты по SSH проверяются повторной отправкой запроса [97][101].
- **Уровень 3: Auto-Resume After Error (на запуск).**
  - Для ошибок не из-за квоты: пауза 5 минут, 5 попыток на запуск; настраивается от 1 до 240 минут и от 1 до 50
    попыток [14][98].
  - Таймеры живут в памяти модуля и не переживают выход из приложения [98].
- **После перезапуска приложения:**
  - цикл Auto Run потерян [97], запланированные повторы тоже [15];

### Лимиты и стоимость

- **Использование Claude.** Встроенный `maestro-p --status` разбирает панель `/usage` в TUI Claude: session, неделя по
  всем моделям, неделя по Sonnet, у каждой процент и время сброса [100][102].
  - Только локально, таймаут 30 с, одна выборка на `CLAUDE_CONFIG_DIR` [100].
  - Комментарий в коде: 11.8% неудачных проверок на 204 запусках одного аккаунта, причина — параллельные запуски
    [100].
- **Использование Codex.** OAuth-токен из `CODEX_HOME/auth.json` используется для запроса
  `chatgpt.com/backend-api/wham/usage` [103].
- **Оценка сброса.** Надёжную оценку даёт только Claude: окна 5 часов и 7 дней [102]. В 1.0.x добавлена обработка
  того, что Claude Code убрал 5-часовое окно со своего экрана usage [62][63][64].
- **Режимы token source для Claude** [17][101]:
  - `api`: каждый ход через `claude --print`;
  - `interactive`: maestro-p управляет TUI под node-pty;
  - `dynamic`: TUI до 99%, потом `--print`, и так до тех пор, пока оба окна не сбросятся.
- **Что режим меняет — позиция менялась.**
  - v0.17.0 (июнь 2026): Maestro утверждал, что Anthropic переводит headless `--print` на оплату по API, и начал
    управлять интерактивным TUI, чтобы оставаться в квоте плана [58].
  - Новый код: «The mode picks the INTERFACE, not the bill», проверено 2026-10-10 [101]. Документация согласна: оплата
    зависит от учётных данных, поэтому Dynamic помогает только с API-ключом [17].
  - Справочная статья Anthropic подтверждает: `claude -p` со входом по плану тратит лимиты плана [205].
  - Заголовок файла maestro-p до сих пор говорит, что он нужен, чтобы «consume the interactive Claude Max quota
    instead of API billing» [100].
- **Тихий переход на оплату API.** maestro-p ищет в TUI заголовок «· API Usage Billing». Он появляется, когда Claude
  не может прочитать вход по подписке и переходит на оплату по API [100].
- **Риск, который называет документация.** Если `claude -p` в будущем станет по умолчанию работать с `--bare`, агенты
  со входом по плану и без API-ключа перестанут работать [17].
- **Автоматический сброс лимита Codex.** Выключен по умолчанию. Если включён, Maestro тратит кредит сброса при первом
  сбое из-за лимита, и только если аккаунт подтверждает, что сброс сработает [15].
  - Вызов `/rate-limit-reset-credits/consume` с ключом идемпотентности `redeem_request_id`; успех доказывает
    `windows_reset > 0` [103].
- **Несколько аккаунтов.** Один аккаунт на агента через переменную окружения; полосы квоты по аккаунтам. Работа между
  аккаунтами автоматически не распределяется [16]. Распределение на аккаунт со свободной квотой (provider pooling)
  описано как «в активной разработке» 2026-09-05 в посте, который написал агент создателя [184].
- **Показ стоимости.** Полная разбивка для Claude Code, для Codex — только число токенов [17]. В 1.0.x исправлен
  завышенный подсчёт стоимости Claude [62][63][64]. Synopsis идёт на самой дешёвой модели [14].
- **Цена «свежего контекста на задачу».** Замер апреля 2026 на маленьких задачах Codex: около 260 секунд и 1.82 млн
  входных токенов на одну задачу-checkbox [158].
- **Чего нет.** Планирования запусков заранее под остаток квоты не найдено. Лимита бюджета, порога предупреждения и
  авто-паузы нет — так подтвердил создатель 2026-07-25 [152].

### Права и безопасность

- **Auto Run всегда работает с полным доступом.** Код ставит `permissionMode: 'full'`, потому что «Auto Run runs
  unattended in --print mode». Иначе агенты «can't get tool approvals non-interactively, and deadlock the run» [94].
  - Claude: `--dangerously-skip-permissions` [105].
  - Codex: `exec --json --dangerously-bypass-approvals-and-sandbox --skip-git-repo-check` [105].
  - Другие CLI — свои флаги пропуска или «разрешить всё» [17].
- **Режим Standard (только интерактивные вкладки Claude).** Запросы разрешений передаются через
  `--permission-prompt-tool`: это мост MCP через локальный socket с токеном из 64 шестнадцатеричных символов. По SSH
  не используется. В Full Access встречный вопрос агента останавливает ход [17][106].
- **Фоновые задачи Claude выключены:** `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, потому что batch-sessions
  завершаются раньше, чем фоновые задачи [17][105].
- **Pianola для отслеживаемых вкладок** [20][117]:
  - правило — scope, условие и действие; срабатывает первое подходящее;
  - regex-классификатор риска («when in doubt we rate higher») отмечает rm -rf, force push, reset --hard, deploy,
    production и секреты;
  - высокий риск всегда уходит человеку; отсутствие правила или неуверенное распознавание — тоже;
  - transcript агента считается недоверенным вводом;
  - `pianola learn` разбирает прошлые transcripts CLI и предлагает правила; человек их одобряет.
- **Поверхность атаки** [76]:
  - локальный web-сервер для CLI работает всегда; токен в URL «grants full control, including terminals»;
  - сервер слушает 127.0.0.1, пока Live выключен. Live слушает все интерфейсы по обычному HTTP;
  - Cloudflare tunnel может открыть тот же сервер по HTTPS; cross-origin запросы браузера отклоняются.
- **Уязвимость, исправленная в v0.17.8** (2026-10-04): встроенный сервер слушал LAN даже при выключенном Live и
  отвечал любой web-странице. Advisory GHSA-q8p2-cpg2-fhpc [60].
- **Federation.** Любой, кто может писать hosted-агенту, может выполнить что угодно от имени SSH-пользователя [31].
- **Plugins.** Выключены по умолчанию. Разбиты на уровни. Подписанный код работает в отдельном utility process на
  plugin. Broker разрешений по умолчанию отказывает [79].
- **Оценка prompt injection.** Текст из GitHub для триггеров Cue можно оценивать сервисом 0DIN SusFactor. При ошибке
  проверки текст пропускается (fails open) [78].
- **Отчёты о падениях.** В коде настройка Sentry по умолчанию включена [121]. Страница Configuration упоминает только
  анонимную ежедневную отметку [37].
- **Утечка в Read-Only.** В феврале 2026 режим только для чтения в release candidate с OpenCode пропускал запись:
  переменная окружения по умолчанию разрешала всё. Исправлено [153].

### Где участвует человек

- **HITL marker** ставит запуск desktop на паузу до «Done, Resume»; кнопка записывает отмеченный checkbox в документ.
  CLI такой документ пропускает [14][86].
- **Заметки steering** доставляются один раз, в начале следующей задачи [14].
- **Halt и Stop.** Агент может написать halt marker. Stop даёт текущей задаче закончиться [14].
- **Значок ERR**: янтарный — повтор запланирован; красный — нужно действие человека [14].
- **Телефон.** Web-интерфейс по QR-коду или через Cloudflare tunnel [1].
- **[RC]** Toasts Pianola о передаче вопроса человеку [20]. Карточки Cadenza в Concerto поверх всех окон, с кнопками
  решения [21].

### Что ругают

#### Тихие остановки и нет обзора того, что идёт внутри запуска

- **Январь 2026.** 24-часовой запуск двух агентов имел перерыв около 4 часов, вероятно из-за исчерпанного лимита.
  Приложение ничего не сообщило и чисто не продолжило. Пользователь нашёл перерыв только в git log [145].
- **Февраль 2026.** Несколько отчётов слили в один issue [150]:
  - playbooks шли часами, а цифра прогресса стояла на месте;
  - один агент писал заметки вместо работы, потому что в его PATH не было `node`;
  - собственный процесс Claude у maintainer-а простоял без дела около 6 часов;
  - другой запуск показывал 100%, но оставался в статусе «running».
- **Июль 2026, уход пользователя.** Первый же prompt нового пользователя завис, и ничего не было видно. Он доделал
  работу в обычном Claude Code и ушёл со словами, что ему «not comfortable using a tool that isn't reliable» [162].
- **Что сделали потом:** живую ленту рассуждений (Thought Stream), watchdog остановок с toasts и панель файла статуса
  (слита в августе 2026) [61][144][145].
- **Потом watchdog сработал зря.** Для Claude Code он считал активностью только финальное сообщение с результатом.
  Поэтому он убил занятую 4-часовую задачу с subagent на 240-й минуте и перешёл к следующему документу. Исправлено в
  `main` 2026-11-11 и выпущено в 1.0.3 [64][173].
- **Скрытое окно останавливает очереди.** Очереди задач Cue без присмотра вставали, пока окно было скрыто: проверка
  очереди зависела от флага видимости страницы в renderer [160].
- **Закрытая вкладка оставляет процесс.** Если закрыть вкладку, где агент ещё работает, остаётся orphan process
  (процесс без владельца), и очередь за ним не двигается. Issue от 2026-11-02 открыт [177].

#### Лимиты и продолжение — главное обещание продукта, каким его встретили пользователи

- **Начало 2026: лимиты не отслеживались.** Maintainer писал, что сам держит открытыми две вкладки, чтобы видеть своё
  использование. Он советовал стороннюю программу в строке меню: не хотел просить у пользователей логины или
  API-ключи [145].
- **Пользователи просили планирование, а не только продолжение.** Тот же пользователь хотел планирования под бюджет,
  например «окно обновится завтра, поэтому запусти пять агентов сегодня вечером» или «пауза на 80%» [145].
- **На середину 2026 ограничений нет.** Анализ пробелов от сообщества оценил контроль затрат как «High». При проверке
  2026-07-25 maintainer подтвердил: стоимость считается, но лимита бюджета, порога предупреждения и авто-паузы нет
  [152]. Ничего новее в документации и issues не найдено [14][69].
- **Сентябрь 2026: сообщение о лимите слишком скупое.** Администратор плана Team упёрся в 5-часовой лимит и увидел одну
  фразу. Ручная проверка в терминале показала, что ни одно из пяти решений, которые предлагает Claude Code, не
  подходит. Maestro сохранял из данных квоты Claude только время сброса и отбрасывал остальное — какое окно и есть ли
  перерасход. После исправления приложение показывает окно и доступный выход [163].
- **Октябрь 2026: регрессия.** Auto Run, остановленный на лимите, так и не продолжился, а его кнопки выглядели
  заблокированными. Пауза хранилась в состоянии Auto Run, а проверка продолжения смотрела только на агента [170].
- **Как это устроено сейчас, по документации:**
  - Agent Resilience повторяет prompt каждую минуту и ещё ровно в секунду сброса, если ошибка её называет [15]. Код
    использует другой шаг — 15 минут (подробно — в разделе «Как это устроено внутри») [96];
  - отдельный Auto-Resume on Limit проверяет остановленных агентов раз в 2 часа по умолчанию и сдаётся через 7 дней
    [14];
  - пакетные запуски из `maestro-cli` автоматически не повторяются [14];
  - цикл Auto Run не переживает перезапуск приложения [14]. Release notes 1.0 пишут, что запуск, остановленный на
    лимите, продолжается даже после перезапуска [61]. Официальные источники расходятся; что верно (не подтверждено).
- **Несколько аккаунтов.** Нагрузку можно разнести, дав каждому агенту свой `CLAUDE_CONFIG_DIR` или `CODEX_HOME` [16].
  Смена аккаунта без повторного входа всё ещё не сделана [165].

#### Разрешения по умолчанию обходятся

- **Декабрь 2025.** Пользователь попросил режим без одобрения всего подряд: Maestro коммитил после каждой задачи
  раньше, чем он успевал проверить. Пользователи из компаний написали, что не могут так работать. Issue закрыли как
  «wontfix»: Maestro управляет агентами в batch-режиме, а это подразумевает обход разрешений [135].
- **Февраль 2026.** Режим Read-Only в release candidate с OpenCode пропускал запись: переменная окружения по умолчанию
  разрешала всё. Исправлено [153].
- **С версии 1.0:**
  - режим Standard для Claude Code показывает запросы разрешений и вопросы агента в приложении, но не работает по SSH
    [17][61];
  - Full Access передаёт `--dangerously-skip-permissions` [17];
  - helper для TUI Claude Code (maestro-p) тоже обходит разрешения [17];
  - Pianola — «агент-менеджер» по желанию — отвечает на ждущие запросы по правилам пользователя или отдаёт их человеку
    [61]. Первый bug от пользователя: процессы его watchers копились до сотни с лишним и не убирались [171].
- **Steering посреди хода.** Пользователи хотят поправить или остановить ход, не убивая процесс. Предложение
  использовать для этого Claude Agent SDK открыто с февраля 2026 [151]. Один пользователь скучает по такому steering в
  Cursor и в desktop-приложении Codex [169].

#### Токены и время на «свежий контекст для каждой задачи»

- Замер апреля 2026 на маленьких задачах Codex: около 260 секунд и 1.82 млн входных токенов на одну задачу-checkbox
  [158].
- Накладные расходы идут из двух мест: весь документ попадает в каждый prompt, и после каждой задачи идёт второй
  проход с итогом [158].
- Maintainer ответил, что так задумано: токены обмениваются на долгие запуски без присмотра. Он добавил флаг, который
  отключает проход с итогом, и показ размера prompt [158].
- Wizard для существующего проекта написал бесполезный план и потратил на это токены [161].

#### Запуски не знают, когда остановиться; проверок между задачами нет

- **Январь 2026.** Два агента сделали все 16 функций примерно за 6 часов. Auto Run продолжал повторять playbook по
  кругу ещё 6 часов, потому что playbook не мог сообщить «готово» [142]. Halt marker тогда был только в CLI; в desktop он
  появился позже [142].
- **Точки проверки пропускались.** Спецификации сразу превращались в код, человек их не видел. Пользователь возражал,
  что делить playbooks руками — значит подстраивать человека под инструмент [143]. Теперь есть маркер human-in-the-loop
  gate [14][143].
- **Нет автоматического quality gate.** Анализ пробелов февраля 2026: агенты сами сообщают о завершении, между
  задачами Auto Run нет ни тестов, ни lint, ни review. Maintainer подтвердил это 2026-07-25 [152]. Документация Auto Run
  до сих пор знает только три вида директив в документе: human gate, halt marker и маркеры модели и effort [14].

- Удаление агента перенесло в корзину всю папку репозитория пользователя. Теперь удаление требует ввести имя агента

- Папку хранения, которую пользователь поместил внутрь папки установки, стёр auto-update — пропали все агенты и
  настройки. Версия 1.0.3 отказывается принимать такое место [64][172].

#### Порог входа и число понятий

- Новые пользователи не понимали, что такое документы Auto Run и почему они появляются в репозитории [139].

  achievements и другое [8]. Жалоб на «раздутость» именно такими словами в issues не найдено [69].
- Один опытный пользователь в апреле 2026 завёл серию bugs про связи на dashboard Cue [159]:
  - «Run Now» запускал только первый триггер;
  - триггеры срабатывали N раз, если агенты делили одну папку проекта;
  - кнопка удаления выглядела как checkbox и не спрашивала подтверждения.

#### Производительность на тяжёлых sessions

- Пользователи пишут о зависании интерфейса примерно на 5 секунд при переходе к агенту с длинной session, о
  задержках боковой панели и медленном вводе текста [140].
- До 1.0.3 очень большие transcripts (сотни МБ) могли уронить приложение [64].

### Работа в процессе (на 2026-11-13 ни в одном релизе)

- **Federation** (документация только в `rc`). Maestro на другой машине владеет агентом, поэтому ходы, Auto Run и Cue
  продолжаются, пока ноутбук спит. SSH-машины переводятся в host «opportunistically» — когда получается [31].
- **`maestro-lib` и TUI** (план от 2026-09-25). Библиотека запускает ходы агентов без Electron. TUI нужен прежде всего
  как доказательство, что библиотека может одна нести весь Maestro [128].
- **Native harness control plane** (помечен как сделанный; последняя правка 2026-10-27) [128]:
  - не привязан к транспорту. ACP v1 (Agent Client Protocol — открытый протокол, по которому приложение управляет
    coding-агентом) — один из адаптеров, рядом с Codex app-server, OpenCode HTTP, Copilot SDK и Claude Agent SDK;
  - цели: честный результат steering и передача запросов разрешений в тот интерфейс, которому принадлежит ход.
- **Планы задач Pianola** (в `rc`) [20]:
  - задачи идут по графу зависимостей;
  - необязательные `requiredChecks` держат задачу в `needs_review`, а зависимые задачи — в ожидании, пока названные
    проверки не пройдут; открытые findings уровня high или critical тоже блокируют;
  - это шаг к приёмке по доказательствам. Без объявленных проверок «готово» означает только, что выполнение
    закончилось.
- **Provider pooling** — отправка работы на аккаунт, у которого осталась квота. Описано как «в активной разработке»
  2026-09-05 в посте, который написал агент создателя, а опубликовал создатель [184].
- **A Cappella (голос) и Local Models** (ветка `acappella`, документы от 2026-08-14 и 2026-10-10) [130]:
  - на устройстве: wake word (слово для вызова), речь в текст, текст в речь, embeddings и классификаторы;
  - среди планируемых потребителей — gate в Cue и проверка на prompt injection;
  - это ответ на пробел в голосе, который вендор признаёт [2][130].
- **Sketch Book** (одобрена к разработке 2026-10-15) [129]:
  - поделиться доской может только человек;
  - после правок гостя ходы агента владельца идут с урезанными разрешениями.
- **Не только код.**
  - Создатель через Maestro ведёт в своём хранилище Obsidian агента, который управляет его личными делами [182].
  - Он собрал на Cue «message bus» для iMessage и Discord [185].
  - Computer History из 1.1.0-RC идёт в ту же сторону [65].
- Сроки выхода Federation, `maestro-lib`, A Cappella, Sketch Book и provider pooling (не подтверждено).

### Куда это ведёт — вывод исследования

Это интерпретация исследователя по источникам выше, а не заявление вендора [20][31][61][65][128]:

- продукт движется от «интерфейса над CLI агентов» к «агентам, которые работают постоянно»;
- уходит с Electron на серверы (headless host, Cue server, Federation);
- заменяет batch-режим нативными протоколами, чтобы ходом можно было управлять (steering);
- ставит в цикл агента-менеджера вместо человека (Pianola);
- главной метрикой делает долю работы без человека (Delegation Score, leaderboard).

## Слабые места и чего нет

- **Нет проверки результата в стабильном Auto Run.** Ни тестов, ни lint, ни review между задачами. О завершении агент
  сообщает сам, отмечая checkbox; prompt лишь просит писать тесты [89][152]. Первая проверка, которую обеспечивает
  движок, — `requiredChecks` Pianola, и она только в `rc` [20][125].
- **Нет работы с CI и PR после создания.** Статус CI не читается, PR inbox нет, комментарии к строкам diff агенту не
  возвращаются [2][109].
- **Лимиты — только реакция.** Нет лимита бюджета, порога предупреждения и авто-паузы [152]. Планирования запусков под
  остаток квоты не найдено [145][152].
- **Перезапуск ломает работу без присмотра.** Цикл Auto Run и запланированные повторы теряются при выходе из
  приложения; пакетные запуски из CLI не повторяются вовсе [14][15][97]. Thought Stream живёт только в памяти [14].
  [RC] Очередь headless host тоже живёт в памяти и теряется при перезагрузке [31].
- **Два движка Auto Run с разным поведением.** Desktop и CLI разошлись в 12 пунктах; сведение на `maestro-lib` ещё
  идёт [122][123].
- **Работа без присмотра — с обходом всех разрешений.** Auto Run и Cue всегда работают без подтверждений [25][94].
  Режим Standard есть только для Claude и не работает по SSH [17]. Pianola — отдельный plugin, выключен по умолчанию
  [20].
- **Слабая изоляция.** Worktree — по желанию; без него агенты пишут в общий checkout [75]. Контейнеров нет; агенты
  работают с правами пользователя; домашняя папка не изолирована [2][76]. [RC] Sandbox для проверок требует Linux;
  работа на macOS (не подтверждено) [126].
- **Нет модели планирования.** Нет эпиков и тикетов; продукт прямо говорит, что он «not a project manager» [71].
  Wizard не учитывает планирование, которое в проекте уже есть, и для существующего проекта написал бесполезный план
  [161].
- **Нет модели жизненного цикла агента.** Состояние агента — только «занят» или «свободен». Правил «событие →
  действие» вне Cue нет [152].
- **Фиксированный список провайдеров**, без адаптера для любого CLI [2].
- **Поверхность атаки.** Токен в URL локального сервера даёт полный контроль, включая терминалы. Live слушает все
  интерфейсы по обычному HTTP [76]. В 0.17.8 исправлена уязвимость: сервер слушал LAN при выключенном Live [60].
  Через Federation любой, кто пишет hosted-агенту, выполняет команды от имени SSH-пользователя [31].
- **Telemetry по умолчанию включена.** Sentry включён в коде, а страница Configuration упоминает только ежедневную
  отметку [37][121].
- **Проект одного человека.** 78% коммитов и 55% комментариев в issues — у создателя [68][69]. Сопровождение
  волонтёрское, сроков ответа нет [76]. Бизнес-модели нет; сторонние обзоры называют это риском долгой поддержки
  [201].
- **Частые RC и устаревшие описания.** Документация описывает RC [84]; метки на сайте устарели [1][61]; пользователи
  откатываются после неудачных RC [153][155].
- **Windows.** Предел командной строки cmd.exe всё ещё открыт для запусков без интерфейса [175]. Issue о вкладках
  терминала, которые перезапускаются по кругу, открыт, хотя release notes 1.0.3 пишут об исправлении [64][176].
- **Расход токенов.** Около 1.82 млн входных токенов на маленькую задачу при свежем контексте [158].
- **Случаи потери данных.** Удаление агента отправляло репозиторий в корзину; частичный список агентов перезаписывал
  сохранённый; auto-update стирал папку хранения [141][167][172].
- **Производительность на длинных sessions.** Зависания около 5 секунд, задержки ввода [140].
- **Чего нет по признанию вендора:** нативного мобильного приложения, голоса сверх диктовки, Linear и Jira, SSO и SOC
  2, design mode, computer use, изоляции в контейнерах. Правка кода — простая, diff только для чтения [2].
- **Steering посреди хода** — только в RC [65]. Предложение сделать его через Claude Agent SDK открыто с февраля 2026
  [151].
- **Много понятий.** Около 70 страниц документации [8]. Новые пользователи не понимают, зачем документы Auto Run лежат
  в репозитории [139].
- **Несколько аккаунтов — вручную.** Работа между аккаунтами не распределяется; смена аккаунта без повторного входа не
  сделана [16][165].

## Пересечение с worfy

Сведения о worfy взяты из его краткого описания, код worfy для этого раздела не читался. Термины worfy:

- Canvas — бесконечное полотно, на котором worfy показывает работу агентов.
- Epic — группа связанных Ticket-ов. Ticket — одна задача.
- Orchestrator — session, которая планирует и раздаёт Ticket-ы.
- Wave — набор Ticket-ов, которые запускаются вместе. Autopilot — запуск Wave-ов без человека.
- Gate — локальный запуск проверок перед PR.
- Harness — plugin, который приносит в Claude Code rules, skills, subagents и hooks.
- Flight Recorder — timeline запуска без присмотра. Work track — вся работа проекта по дням и неделям.
- Cards — карточки, которые агенты строят на Canvas через MCP server.
- Product Session — продуктовый советник с живой Mind map и критиком спецификаций.
- Linked machines — связанные машины в локальной сети.
- Evidence — screenshots с вычисткой личных данных.
- Eco mode — режим экономии лимитов.

### Где пересекаются

- **Desktop-приложение на Electron для coding-агентов.** Maestro — Electron для macOS, Windows и Linux [10][85].
  worfy — Electron для macOS, порт на Windows в работе.
- **Claude Code и Codex.** В Maestro оба «fully integrated», плюс ещё около восьми CLI [10][12]. worfy запускает
  sessions Claude Code и Codex CLI.
- **Работа без присмотра.** Maestro — Auto Run по чеклистам или по цели, Playbooks, Loop Mode [14]. worfy — Autopilot
  запускает Waves из Ticket-ов.
- **Ожидание сброса лимитов и повторы при ошибках API.** Maestro — Agent Resilience, Auto-Resume on Limit,
  Auto-Resume After Error [14][15]. worfy — Autopilot ждёт сброса лимитов подписки и повторяет запросы при ошибках
  API.
- **Ответы на запросы разрешений по политике.** Maestro — Pianola с правилами, классификатором риска и журналом
  решений, plugin выключен по умолчанию [20][117]. worfy — Autopilot одобряет запросы разрешений по политике.
  Рабочее имя Pianola в планах разработки — «Autopilot» [20][83].
- **Orchestrator.** Maestro — модератор Group Chat, `maestro-cli dispatch --notify-on-complete`, [RC] ожидание

  планирует и раздаёт Ticket-ы.
- **Worktree и PR на задачу.** Maestro — worktree для агента по желанию; Auto Run в новом worktree с автоматическим PR

- **Timeline работы.** Maestro — History, Director's Notes (общая timeline и AI-сводка за 1–90 дней), Thought Stream,

- **Другие машины.** Maestro — агенты по SSH, web-интерфейс Live по LAN или tunnel, [RC] Maestro Lite, [RC]

### Где расходятся

- **Единица работы.** Maestro — checkbox в markdown-документе или цель текстом [14]. worfy — Ticket в Epic: worktree,
  тесты, Gate, PR, CI и review.
- **Планирование.** Maestro прямо называет себя «not a project manager»: он исполняет, планирует агент [71]. Эпиков и
  тикетов нет; план — чеклисты из Wizard или сторонних методик Spec-Kit, OpenSpec и BMAD [42][77]. worfy — Epics,
  Tickets и Orchestrator, который их раздаёт.
- **Проверка результата.** В стабильном Maestro нет ни Gate, ни агентов review, ни чтения статуса CI. Агент сам
  отмечает checkbox, prompt лишь просит писать тесты и коммитить [89][109][152]. [RC] Появляются `requiredChecks` в
  Pianola [20]. worfy — тесты, локальный Gate, PR с CI badges, reviewer subagents с review lenses.
- **Как показана работа.** Maestro — список агентов, которым управляют с клавиатуры, панели, split panes, несколько
  окон. Холст есть только у графа pipelines Cue [13][23][71]. worfy — бесконечный Canvas.
- **Лимиты.** Maestro реагирует: ждёт сброса, проверяет, продолжает [15][97]. Планирования запусков под остаток квоты
  не найдено, лимитов бюджета и авто-паузы нет [145][152]. worfy — планирует запуски под лимиты подписки, есть Eco
  mode.
- **Разрешения в работе без присмотра.** Maestro — Auto Run всегда в Full Access, потому что иначе batch-режим встаёт
  на запросе [94]; Pianola — отдельный plugin, выключенный по умолчанию [20]. worfy — Autopilot одобряет запросы по
  политике.
- **Как агенты управляют приложением.** Maestro — через `maestro-cli` по WebSocket; у каждого действия интерфейса есть
  команда CLI [72][114]. worfy — MCP server для Cards.
- **Провайдеры и платформы.** Maestro — около десяти CLI; macOS, Windows и Linux уже выпущены [2][10]. worfy — Claude
  Code и Codex; macOS, Windows в работе.
- **Автоматизация по событиям.** Maestro — Cue: события файлов, расписаний, завершения агентов, GitHub и webhooks

- **Сообщество и игровые элементы.** Maestro — публичный leaderboard, Achievements, Delegation Score, Playbook

- **Несколько людей.** Maestro — Web Login, все аккаунты равны, ролей нет [30]. worfy — один пользователь.

## Механизмы, которые стоит изучить

1. **Прогресс по checkbox и правило остановки.**
   - Что это: Auto Run считает прогресс только по отмеченным `- [x]` в документе задач [14][90].
   - Как работает: после каждой задачи движок перечитывает документ. Завершённые задачи = max(0, отмечено после −
     отмечено до) [88]. Три запуска подряд без изменения checkbox — документ брошен, playbook идёт дальше [14][90].
     Рост документа не засчитывается: «a document that grew by a thousand words of apology - is no progress» [90].
     Срабатывание watchdog (проверка раз в 15 с; 240 минут без активности или 480 минут всего) сразу засчитывается
     как остановка [86][94][95].
   - Чем интересно: прогресс измеряется по файлу в репозитории, а не по словам агента. Чтобы остановить зависший
     запуск, не нужно разбирать текст ответа.
   - Источник: [14][86][88][90][94][95].
2. **Порядок разбора времени сброса и повтор как бесплатная проверка.**
   - Что это: часть Agent Resilience, которая решает, когда повторить запрос после исчерпанной квоты [15][96].
   - Как работает: время сброса берётся из источников по убыванию надёжности — `quotaLimits.resetsAt`, затем
     `retryAfter`, `resetAt` или «try again in N», затем устаревший маркер epoch, затем текст баннера с часовым
     поясом. Время без часового пояса отбрасывается [15]. Баннер лимита Claude распознаётся, только если он — всё
     сообщение целиком [15][104]. Повтор отправляет исходный prompt заново; пока квота исчерпана, провайдер
     отказывает до траты токенов [15]. Часть ошибок не повторяется никогда: авторизация, отказ в доступе, полное окно
     контекста, падение процесса [15][96]. В коде шаг проверки — 15 минут, потому что проверка раз в минуту тратила
     первые полчаса четырёхчасового сбоя [96].
   - Чем интересно: момент повтора привязан к данным провайдера, а не к фиксированному таймеру; класс ошибки решает,
     повторять ли вообще.
   - Источник: [15][96][104].
3. **Чтение лимитов подписки Claude через TUI `/usage` и сигнал о тихой оплате по API.**
   - Что это: встроенный helper `maestro-p` [100][102].
   - Как работает: `maestro-p --status` запускает TUI Claude под node-pty и разбирает панель `/usage` — session,
     неделя по всем моделям, неделя по Sonnet, у каждой процент и время сброса. Таймаут 30 с, одна выборка на
     `CLAUDE_CONFIG_DIR` [100][102]. Auto-Resume on Limit продолжает работу Claude, только когда оба окна ниже 99%
     [97][101]. Тот же helper ищет в TUI заголовок «· API Usage Billing», который означает, что Claude перешёл на оплату
     по API [100]. Код сам сообщает о 11.8% неудачных проверок на 204 запусках одного аккаунта [100].
   - Чем интересно: данные о лимитах берутся из того же экрана, который видит человек, без API-ключа. Плюс отдельный
     сигнал о неожиданной оплате.
   - Источник: [97][100][101][102].
4. **Погашение кредитов сброса лимита Codex с ключом идемпотентности.**
   - Что это: опция автоматического сброса лимита Codex, выключена по умолчанию [15].
   - Как работает: при первом сбое из-за лимита Maestro проверяет, что аккаунт подтверждает: сброс сработает. Затем
     вызывает `/rate-limit-reset-credits/consume` с ключом идемпотентности `redeem_request_id`. Успех доказывает
     `windows_reset > 0` [15][103]. Не больше одного раза на сбой [15][18]. Использование Codex читается OAuth-токеном
     из `CODEX_HOME/auth.json` через `chatgpt.com/backend-api/wham/usage` [103].
   - Чем интересно: ключ идемпотентности не даёт потратить кредит дважды при повторе запроса; решение опирается на
     ответ аккаунта.
   - Источник: [15][18][103].
5. **Режим по цели: маркер прогресса и записка следующему агенту.**
   - Что это: Auto Run, где вместо чеклиста — цель текстом [14].
   - Как работает: каждая итерация — новый агент, который делает один шаг и выходит. Агент пишет
     `<!-- maestro:progress N | rationale -->`; нет маркера — прогресс 0 [14][89]. Выход: 100% или маркер завершения,
     тупик, лимит итераций (жёсткий максимум 500), нет роста 3 итерации [14][92]. Отдельный ход просит закончившего
     агента написать записку около 150 слов, не длиннее 1500 символов. Она уходит следующему агенту через
     `{{PREDECESSOR_HANDOFF}}` с указанием сверить её с репозиторием [92]. Desktop коммитит после каждой итерации [91].
   - Чем интересно: длинная работа идёт свежими sessions без переполнения контекста. Связь между ними — короткая
     записка и состояние репозитория. Условия остановки заданы явно.
   - Источник: [14][89][91][92].
6. **Markdown-документ как канал управления запуском.**
   - Что это: HTML-комментарии в документе задач, которые читает движок [14].
   - Как работает: HITL gate ставит запуск на паузу до «Done, Resume», и кнопка записывает отмеченный checkbox в
     документ; запуск без интерфейса документ пропускает [14][86]. Halt marker `<!-- maestro:halt: reason -->`
     останавливает раздачу задач; внутри code blocks игнорируется; старый маркер блокирует повторный запуск, пока его
     не уберут [14][86]. Маркер `<!-- MAESTRO:MODEL tier= effort= -->` задаёт модель на задачу; запуск «per
     document» делится там, где меняются настройки модели [14][88]. Reset on Completion работает на копиях в `runs/`,
     копии остаются журналом аудита [14].
   - Чем интересно: вендор называет это главным отличием — один чеклист сразу план, точки проверки человеком,
     подсказки модели и трекер прогресса [2]. Всё видно и правится в обычном файле.
   - Источник: [2][14][86][88].
7. **Pianola: ответы на запросы агентов по правилам, с журналом и правилами из прошлых transcripts.**
   - Что это: plugin «агент-менеджер», выключен по умолчанию [20].
   - Как работает: правило — scope, условие и действие; срабатывает первое подходящее [20]. Regex-классификатор риска
     («when in doubt we rate higher») отмечает rm -rf, force push, reset --hard, deploy, production и секреты [117].
     Высокий риск, отсутствие правила или неуверенное распознавание — вопрос уходит человеку [20][117]. Решение
     пишется в журнал до отправки ответа; transcript считается недоверенным вводом [20]. `pianola learn` предлагает
     правила по прошлым transcripts, человек их одобряет; `--dry-run` классифицирует без ответа [20]. Watchers
     перезапускаются до 5 раз с паузой от 1 до 30 с [116].
   - Чем интересно: автоматическое одобрение с явным порядком правил, журналом до действия и способом получить
     правила из истории работы.
   - Источник: [20][116][117].
8. **[RC] Приёмка отдельно от выполнения: `requiredChecks` и проверки в sandbox.**
   - Что это: планы задач Pianola в ветке `rc` [20][125].
   - Как работает: «Successful execution and acceptance are separate». Задача остаётся в `needs_review`, пока каждая
     проверка из `requiredChecks` не получит `passed` на её `runId`; зависимые задачи ждут. Открытые findings уровня
     high или critical тоже блокируют [20][125]. Проверки идут в bubblewrap с `--unshare-net` и `--clearenv` под
     лимитами systemd-run (600 с, 2 GiB, 256 процессов); на Windows — через `wsl.exe` [125][126]. Нет sandbox —
     ошибка, запуска без sandbox не бывает [126]. До 3 попыток исправления [20][117]. Перед раздачей сохраняется
     claim; если ответ потерян, claim ждёт сверки и не отправляется снова [20].
   - Чем интересно: результат проверяется отдельно от сообщения агента «готово». Отсутствие sandbox — явная ошибка, а
     не тихий запуск без него. Работа на macOS (не подтверждено) [126].
   - Источник: [20][117][125][126].
9. **Правило «у каждого действия интерфейса есть команда CLI».**
   - Что это: правило из CONSTITUTION.md и CLAUDE.md [71][72].
   - Как работает: каждое действие интерфейса выходит вместе с командой `maestro-cli`, у обоих одна реализация, путь
     CLI не открывает диалогов, у каждой записи есть чтение; соответствие ведётся в таблице CLI-UI-PARITY.md [72][73].
     CLI находит работающий desktop через файл `cli-server.json` и подключается по WebSocket с секретом [76][114].
     Агенты узнают команды из system prompt на 31.6 KB, который передаётся при каждом запуске через
     `--append-system-prompt` [115]. Флаг `--background` не даёт агенту переключить то, что видит человек; агентам
     велено ставить его по умолчанию [73].
   - Чем интересно: агенты управляют тем же приложением, что и человек, через один и тот же код, а правило о фокусе
     не даёт им мешать человеку.
   - Источник: [71][72][73][76][114][115].
10. **Делегирование с пробуждением вызывающего агента.**
    - Что это: `maestro-cli dispatch`, `ask`, `send` и флаг `--notify-on-complete` [35][61].
    - Как работает: `dispatch` открывает скрытую вкладку у другого агента [14][113]. С `--notify-on-complete`
      вызывающий агент получает карточку с результатом [35][61]. [RC] Auto Run ждёт всех делегатов и вставляет их
      результаты в следующий prompt; ожидание — 1 час по умолчанию, максимум 24 часа [14]. Callbacks хранятся в
      памяти, одновременно не больше 200; переменные `MAESTRO_CALLER_AGENT_ID` и `MAESTRO_CALLER_TAB_ID` записывают,
      кто делегировал [113]. Консультация через `@agent` идёт во временном процессе `cross-agent-<requestId>`, а не в
      живой вкладке адресата [112].
    - Чем интересно: агент-orchestrator проходит цикл build → review → fix → verify без человека, который передаёт
      результаты [35].
    - Источник: [14][35][61][112][113].
11. **Cue: очередь событий в SQLite и один догоняющий запуск после сна.**
    - Что это: автоматизация Maestro по событиям [23].
    - Как работает: подписки в `.maestro/cue.yaml` перечитываются на лету [23]. Очередь событий хранится в SQLite
      (`cue.db`) и проигрывается при старте [78]. После сна машины дольше 120 с расписание делает один догоняющий
      запуск, а не все пропущенные [78]. Цепочки обрываются на глубине 10; вывод предыдущего шага обрезается до 5000
      символов; `max_concurrent` на агента — 1 по умолчанию [78]. Переменные из `cue.yaml` не могут менять PATH,
      HOME, LD_PRELOAD, NODE_OPTIONS и ещё несколько опасных переменных [78]. Текст из GitHub можно проверять на
      prompt injection сервисом 0DIN SusFactor; при ошибке проверки текст пропускается [78].
    - Чем интересно: автоматизация переживает перезапуск и сон машины и не запускает пачку пропущенных задач разом.
      Пределы на длину цепочки и объём передаваемого текста заданы явно.
    - Источник: [23][78].
12. **Журнал запусков со сверкой после перезапуска.**
    - Что это: agent-run ledger — файлы `maestro-agent-runs.json` (и архив), `maestro-agent-run-events.jsonl`,
      `maestro-campaigns.json` [109][111].
    - Как работает: запись хранит статус (от queued до merged или discarded), проверки, findings review с уровнем,
      PR, итог merge, затронутые файлы и использование [109]. После перезапуска запуски «в процессе» без живого
      процесса помечаются `failed` [110]. Лимит хранения добавили, когда у активного пользователя набралось 7500
      запусков и 20 МБ, а каждая запись занимала около 150 мс в main thread [111]. [RC] `cot-export` пишет журнал
      аудита каждого хода, связанный цепочкой хешей, и умеет его проверять (`hash-chain.ts`, `verify.ts`) [65][127].
    - Чем интересно: после падения приложения запуск не остаётся навсегда «в работе» — его состояние определяется
      явно. Журнал аудита можно проверить на подделку.
    - Источник: [65][109][110][111][127].
