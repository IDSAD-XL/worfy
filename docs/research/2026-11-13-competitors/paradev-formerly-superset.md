- **Что это за имя.**
  - Paradev — новое имя продукта Superset (superset.sh). С Apache Superset, BI-инструментом, он не связан [86][22]. Путаница с Apache Superset возникала в каждом треде запуска на HN [184][183].
  - Смену имени объявили 2026-10-12 и завершили 2026-10-25/26 [23][22][4]. Причина, по словам вендора: имя Superset уже носили многие другие продукты [22].
  - «Paradev» значит «параллельный разработчик», по аналогии с paralegal и paramedic [22].
  - Старое имя осталось в коде и инфраструктуре [76][80][55][103][120][97]:
    - команда CLI — `superset`, а `paradev` — её alias;
    - папки настроек `.superset/` и переменные окружения `SUPERSET_*`;
    - endpoints под доменом `superset.sh`;
    - `productName` в Electron на версии 2.0.8 — всё ещё «Superset».
  - Аккаунты, workspaces и старые URL продолжают работать. В подвале сайта по-прежнему «Superset Inc.» [22][4].

## Модель работы

**Где работает: local по умолчанию, плюс удалённые и облачные хосты.**
- Ядро — desktop-приложение на машине пользователя. Агенты — процессы CLI в терминалах. Терминалами владеет фоновый daemon, а не окно приложения [46].
  - Агенты продолжают работать, когда окно закрыто, приложение закрыто через ⌘Q или ставится обновление [46].
  - Агенты останавливаются по команде «Quit Paradev Completely» и при перезагрузке [46].
  - После ⌘Q машина недоступна с других устройств и для automations, пока приложение не откроют снова. Эту проблему решает отдельный CLI-хост [46].
- Workspace в Paradev — рабочее место одной задачи: git worktree со своей веткой и своими терминалами [33][34]. Где он может жить:
  - на этой машине;
  - на удалённом хосте через облачный «Paradev Relay» [51];
  - в cloud workspace — sandbox, который Paradev запускает сам [35];
  - в Bring Your Own Cloud (BYOC) — CLI-хост на своём Linux-сервере. Он всё равно подключается к relay и API Paradev [36].
- Self-hosting серверной части (API и relay) — не подтверждено. Код под MIT, но пути self-hosting в документации нет, а BYOC всё равно идёт через relay [86][36][24].

**Вход в аккаунт: источники расходятся.**
- Код на commit `340f4ae`: route guard desktop-приложения отправляет пользователя без входа на экран входа (GitHub или Google), затем на создание организации. Только после этого видны workspaces [113].
- Issue #4894 «убрать обязательный вход» (2026-05-23) открыт [160]. Более ранняя просьба #2685 (23 голоса) закрыта в чистке устаревших issues в июле [148][181].
- На Launch HN основатели сказали, что вход нужен для интеграций, совместной работы и удалённых функций. Сотрудник добавил: hosted-сборка всегда требует входа, без него — только свой fork и своя сборка [184].
- Документация при этом пишет, что Paradev работает offline и синхронизируется при подключении [32]. Roadmap утверждает, что основной цикл уже работает без входа и offline [3].
- Исследование направления связывает это с решением 2026-07-16 хранить проекты только в локальной базе и с issue #2685 [95][148].
- Итог: документация и roadmap говорят «можно без входа», код и issues — «вход обязателен».

**Приватность.**
- Вызовы моделей Paradev никогда не проксирует: агенты используют подписки и ключи пользователя [86][33].
- Relay передаёт трафик терминалов и портов удалённых и BYOC-хостов [36][51].
- Privacy policy называет PostHog для продуктовой аналитики [13]. В PostHog же живут feature flags [110][137].
- Обещание «не проксируем» выполняется не везде [73][35][124]:
  - MCP-записи plugins указывают на proxy Paradev;
  - в cloud workspaces Paradev подставляет учётные данные в исходящие запросы;
  - невыпущенная функция Devs использует в production ключ API router-а Paradev.

**Агенты и модели.**
- Своей модели и своего цикла агента для локальной работы у Paradev нет: он запускает чужие CLI [33][105][111].
- Число встроенных агентов в источниках разное: 22 в документации [40], 23 определения в коде (`builtin-terminal-agents.ts`) [105], «20+» на странице поддерживаемых агентов [42]. В середине 2026 года сайт писал о «100+» агентах [221].
- Любой другой CLI можно добавить как свой агент [42].
- Режим Chat работает поверх Agent Client Protocol (ACP — открытый протокол, по которому редактор управляет coding-агентом). Поддержаны Claude Code, Codex, OpenCode и Pi [41]. В коде каталогизирован ещё Gemini [111].
- Свои агенты Paradev стоят на краях продукта: Slack-агент [135], экспериментальный агент `pdev` [92] и «Devs» за feature flag [124].

**Один пользователь или команда.**
- Free — для одного пользователя [2].
- У организаций есть роли owner, admin и member. Удалить проект может владелец организации или владелец устройства [34][74].
- Общими бывают:
  - доступ к хосту, который выдаёт его владелец [51];
  - командные automations — для всех, кроме владельца, только чтение [50];
  - Pages, комментарии и хранилище на уровне организации [39];
  - командные ключи задач (с 2026-10-11) [4];
  - plugins организации [74];
  - настройки, которые синхронизируются между устройствами [71].
- «Paradev Teams» и «Team activity feed» в roadmap стоят в «Up Next» [3].
- Ответ Paradev на совместную работу — делиться самим запущенным cloud workspace [20].
- В мае 2026 года основатели сказали, что зарабатывают на командах и, в будущем, на облаке [184].

**Платформы.**
- macOS на Apple Silicon и Intel — поддерживаемая платформа [68][69].
- Linux x64: AppImage, по документации экспериментальный и не протестированный [68][69]. Пакет `.deb` и исправления вышли в сентябре 2026 года [141]. Issue #405 про Linux — открытый issue с самым большим числом реакций [141].
- Windows — в планах, без даты [68][69].
  - В README `pty-daemon` поддержка Windows ConPTY вне scope [101].
  - Native-сборку просят в #5209. Сообщество делает свои forks, например SuperWin [161].
  - На HN основатели сказали, что в команде никто не работает на Windows каждый день [184].
- CLI — один статический бинарник `superset` (alias `paradev`) для macOS и Linux x64/arm64. Ставится вместе с приложением, через curl или Homebrew [76].
- Телефон: iPhone и iPad, нужна iOS/iPadOS 26+ и план Pro. Для Android — только лист ожидания. Поддерживаемого web-dashboard нет [52][68].
- Интерфейс на 17 языках с 2026-08-30. Украинский добавлен 2026-11-01 [4].

## Функции

Состояние на 2026-11-13. Документация описывает продукт без дат; даты появления функций взяты из changelog [4].

### Агенты, модели и права

- **Встроенные агенты.** В документации их 22 [40]: Claude Code, Amp, Codex, Gemini CLI, Mastracode, OpenCode, Pi, Oh My Pi, Copilot, Mistral Vibe, Kimi Code, Grok, Cursor Agent, Droid, Polygraph, Hermes, Muse Code, Devin, fx, Antigravity, Kiro, UFO.
  - В коде 23 определения. У каждого есть команды запуска, resume, fork и неинтерактивного запуска [105].
- **Свой агент.** Любой другой CLI добавляется в Settings → Agents → Custom agent. Он получает worktree и терминал, но без интеграций из списка ниже [42].
- **Глубина интеграции разная** [42]:
  - статус, resume после перезапуска, история usage и метр квоты — у Claude, Codex, OpenCode и Grok;
  - несколько аккаунтов — только у Claude и Codex;
  - fork сессии — у Claude, Codex, OpenCode, Pi, Grok и Droid;
  - частично: у Mistral Vibe и Antigravity нет состояния «ждёт ввода»; UFO только запускается;
  - без статуса совсем: Kiro, Polygraph, Hermes, fx.
- **Настройки агента** [40]: название, иконка, команда запуска, аргументы только для prompt, способ передачи prompt (аргумент или stdin), аргументы resume и fork, переключатель hooks, шаблон prompt для задачи.
- **Запросы прав по умолчанию выключены.**
  - Claude Code стартует как `claude --dangerously-skip-permissions` [43].
  - Codex стартует как `codex --dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust` [44].
  - Другие агенты тоже получают флаги без подтверждений: Gemini — `--approval-mode=auto_edit`, Grok — `--always-approve`, Hermes — `--yolo` [105][44].
  - Флаги можно убрать для каждого агента в Settings → Agents [43][44]. Миграция переносит старые разрешающие настройки существующим пользователям [105].
  - Подробно — в разделе «Как это устроено внутри → Права и безопасность».
- **Как Paradev узнаёт статус агента.** Он записывает lifecycle hooks и обёртки команд (`~/.paradev/bin`) в настройки каждого агента. Вне терминалов Paradev эти hooks ничего не делают [47].
- **Модели.**
  - В выборе моделей есть GPT-6 Astra, Sol и Luna, а также Opus 5.5 и Sonnet 5.5. У Codex ещё GPT-6.1 Sol и Terra [40].
  - Выбор reasoning effort есть у девяти агентов [42].
- **Другие провайдеры для Claude Code:** Vercel AI Gateway, OpenRouter, Bedrock, Vertex, Microsoft Foundry и любой endpoint, совместимый с Anthropic. Настраиваются переменными окружения [62].
- **Свой агент Paradev — `pdev`, экспериментальный.**
  - Приложение поставляет его в комплекте, версия 0.2.5. Репозиторий сборок создан 2026-10-12 и называет агента экспериментальным. В списке агентов для пользователя его нет [92][40].
  - `pdev` построен на open-source агенте `pi` Mario Zechner (MIT). Релизы 0.1.2–0.2.5 вышли с 16 по 29 октября 2026 года [92].
  - Скрыт за feature flag `pdev-agent`. Может работать как harness (движок) для Chat [106].
  - Входит в router моделей Paradev [111].

### Проекты, workspaces и sessions

- **Модель продукта.** Пять частей: projects (зарегистрированные репозитории), workspaces, терминалы, агенты и устройства. Правило документации: работу делегируют в workspaces, а объединяют через ветки и PR [33].
- **Workspace = git worktree.** Один worktree и одна ветка на workspace, в папке `~/.paradev/worktrees/<project>/<branch>` [34][68].
  - В worktree попадают только файлы под git. Остальное (зависимости, env-файлы) делают setup-скрипты [33].
  - Worktree — не sandbox: процессы, сеть и файлы вне worktree общие [68]. Изоляцию в Docker просят в issue #3957 [154].
  - Одна ветка может быть только в одном workspace [68].
- **Без worktree.** 2026-09-25 Kiet Ho написал в X, что требование работать в worktree убрали: многие предпочитают работать в корне проекта [205]. Документация описывает workspace как worktree [34]. Как устроен режим без worktree, в собранных материалах не описано.
- **Создание workspace (⌘N)** [34]:
  - из новой ветки, существующей ветки или PR;
  - сначала prompt, с поиском по истории prompts;
  - маленькая модель называет workspace и ветку по prompt. Без учётных данных модели имена — случайные слова [34][68]. В коде имя придумывает CLI самого агента этого workspace: он запускается без интерфейса на маленькой модели с учётными данными пользователя [104];
  - для проекта можно задать инструкции по именованию;
  - workspace запускается примерно за секунду [4].
  - Поля для ручного имени workspace и ветки на новом экране создания нет. Четыре issue (вместе 43 голоса) просят его вернуть [168][170]. Подробнее — в разделе «Что говорят пользователи».
- **Импорт.** Paradev подхватывает уже существующие worktrees, в том числе оставленные Conductor, T3 Code и Orca [34][4].
- **Sessions.** «Session» — workspace без проекта: временная папка с `git init` [34].
- **Страница Workspaces.**
  - Колонки доски: Idle, Working, Needs attention, Needs review, Merged, Deleted [34].
  - Вид списка, фильтры и сохранённые виды, например «Needs me» и «Working» (2026-11-01) [4]. В ноябре список стал работать как issue tracker [4].
  - Roadmap называет эти состояния очередью внимания (attention queue) [3][4].
- **Sidebar** [34]:
  - закрепление, выбор нескольких workspaces, перенос в группу, массовое удаление с предупреждением о несохранённых изменениях;
  - для ветки — счётчики ahead/behind, состояние PR, проверки CI и кнопка deploy preview.
  - Полоса в sidebar показывает работающих агентов и порты [47].
- **Дерево файлов с просмотром Markdown** — его отмечает рецензент-продакт-менеджер [208].
- **Восстановление.**
  - Архивный workspace восстанавливается только с закоммиченной работой [34].
  - Удалённый проект можно вернуть в течение 30 дней [34].
- **Lifecycle-скрипты** в `.paradev/config.json`: setup, teardown и команда кнопки Run [66].
  - Переопределения: для пользователя, для worktree и в `config.local.json`, который игнорирует git [66].
  - По умолчанию агент стартует параллельно с setup. Можно включить ожидание конца setup [66].
  - Если teardown упал, Paradev предлагает «Delete Anyway» [66].
- **Monorepos.** Настройка sparse checkout (режим git cone; если он не сработал — полный checkout) и поддержка submodules [72][104].
- **Terminal scripts** (раньше «presets»): именованные команды с режимами запуска — новая вкладка, split или по очереди. Есть панель Scripts и сочетания ⌃1–9. Добавлять их можно и из CLI [67].
- **Порты.** Paradev показывает, какие порты открыл каждый workspace. Диапазонов портов на workspace он не выделяет [33][60].
  - Сканер портов дорогой: пользователь с примерно 60 сессиями агентов насчитал около 13 запусков `ps` в секунду [164].
  - Кнопка, которая закрывает все порты, убивала и сессии агентов (issue #9683 открыт) [180].

### Терминалы и сессии агентов

- **Терминал** [59]:
  - вкладки, splits без ограничения, переименование, объединение вкладок;
  - предупреждение при закрытии, если идут процессы;
  - ⌘-click открывает путь к файлу на нужной строке и колонке;
  - правила копирования повторяют обработку пробелов Ghostty;
  - «Mark as Unread» для терминала.
- **Редактор prompt.** ⌘I открывает многострочный ввод с упоминанием файлов через @ [86].
- **Сессии переживают окно.** Агенты продолжают работать при закрытии и обновлении приложения [46].
- **Auto-resume.** Если терминал агента неожиданно умер, Paradev перезапускает агента его командой resume и показывает «Resuming…». При неудаче — кнопка Retry [45].
  - Документация и код включают сюда перезагрузку машины [45][108]. В changelog за июль–август: прерванные сессии продолжаются сами [4].
  - Здесь источники расходятся: issue #3496 «продолжать сессии агентов после перезагрузки» открыт с апреля, к нему есть черновой PR [153].
- **Fork сессии** — через команду fork самого агента [45].
- **Продолжить другим агентом.** Новый агент получает последние 36 000 символов контекста. Paradev сначала показывает объём и предупреждает, что ничего не вычищается [45].
- **Транскрипты.** `superset agents read` отдаёт сохранённые транскрипты, только для Claude и Codex [45].
- **Subagents.** Subagents Claude и Codex показаны под родительской сессией [42]. Панель в верхней строке перечисляет работающие subagents и фоновые shells (2026-11-01) [4].

### Chat поверх ACP

- Chat запускает установленный CLI по ACP, поэтому использует тот же вход и те же MCP-серверы, что и терминал [41].
- Минимальные версии: Claude Code 2.1.226, Codex 0.160.0, OpenCode 1.15.5; поддержан Pi [41].
- Переключатель CLI/Chat меняет вид той же сессии без потери контекста [41].
- 2026-11-08 Chat вышел из статуса Experimental. Теперь он продолжает работу после падения и помнит модель, effort и режим каждого агента [4]. При первом запуске приложение спрашивает, что открывать: Terminal или Chat [4].
- Chat показывает, насколько заполнено окно контекста [4].
- Каждый prompt делает git snapshot, поэтому есть Undo на каждый ход [111].
- В чате появляются вопросы агента, запросы на инструменты и review плана [47].
- В 2.0.x новые сессии Claude Code по умолчанию открываются в Chat. Пользователи терминала просят вернуть CLI по умолчанию [178].
- Документация обещает одобрение и отказ одним кликом [41]. Код стартует чаты в режиме без ограничений [111]. Исследования здесь расходятся — подробно в разделе «Права и безопасность».
- Уведомление о лимите подписки — в разделе «Usage, лимиты и leaderboard».

### Review, git и pull requests

- **Панель Changes** [57]:
  - stage, commit, push и создание PR;
  - diff рядом или в одну колонку; режим «один файл за раз»;
  - «Edit Here» открывает редактор на этой строке;
  - вкладка Review для комментариев PR.
- **Diff и редактор.**
  - Diff для картинок, видео и PDF (2026-09-06) [4].
  - Встроенный редактор CodeMirror. Он показывает баннер, если файл изменился на диске, и вид сравнения при конфликте [58].
  - Поиск по всем workspaces [58].
- **Экран Pull requests** [49]:
  - PR из всех репозиториев проектов. Фильтры, в том числе «Awaiting review from you» и «Changes requested»;
  - вкладка Summary: проверки CI (отменённая проверка считается упавшей), reviewers, лента событий с полем ответа;
  - вкладка Code: полный просмотр diff.
- **Действия с PR** [49]:
  - merge через squash, merge commit или rebase;
  - stacked PRs (цепочка PR, где каждый строится на предыдущем): merge всей цепочки, создание стека на GitHub, restack;
  - добавление в merge queue, закрытие и повторное открытие, «Start Workspace» из PR.
  - Stacked PRs, merge queue и restack слиты 2026-11-11 (PR #9554) [93].
- **Комментарий прямо агенту.** Можно выделить строки diff и отправить их работающему агенту или в новый workspace с checkout этого PR. Публикация на GitHub — по желанию [49].
- **Чьё имя.** Действия с PR идут от GitHub-аккаунта пользователя, а не от аккаунта машины-хоста (2026-11-01) [4].
- **Другие git-хостинги.** GitHub поддержан полностью через `gh`. С другими remote работают только локальные функции. Поддержку GitLab просят в issue #6445, он открыт [68][169].
- **Что за плату.** Интеграция с GitHub стала бесплатной 2026-04-20, экран Pull Requests — 2026-08-23. С 1–4 октября синхронизация Linear и GitHub требует Pro [4][94].

### Браузер и управление компьютером

- **Панель браузера (⌘⇧B):** автодополнение по истории, DevTools, ссылки «открыть найденный порт» [37].
- **Design mode.** Пользователь выбирает элемент на странице. Агент получает его DOM, вычисленные стили, метаданные React-компонента и обрезанный скриншот вместе с заметкой пользователя [37].
  - Перед отправкой данные чистятся: остаются только безопасные схемы URL, query и hash убираются, строки, похожие на секреты, вырезаются [129].
  - В октябре Enter в Design mode стал не вставлять комментарий, а сразу отправлять его агенту — без предупреждения (issue #8566) [173].
- **Расширения Chrome** (2026-11-08) [37][4]:
  - ставятся из Chrome Web Store после запроса разрешения;
  - работают 1Password и LastPass, passkeys и блокировщики рекламы;
  - файлы расширений сверяются с подписанными hash магазина.
- **Две сессии браузера** [37][129]:
  - панели, которые открыл пользователь, работают в его сессии со входами на сайты;
  - панели, которые открыл агент, работают в отдельной сессии (partition) без расширений и входов, пока пользователь их не импортирует.
  - «Import from Chrome» копирует историю и входы по профилям из Chrome, Edge, Brave, Arc, Dia и Comet (2026-08-23) [4].
- **Управление агентом.**
  - Команды `superset browser open/eval/screenshot/console` и `cdp`. Последняя отдаёт endpoint Chrome DevTools Protocol (CDP), ограниченный одной панелью [37].
  - CDP-методы для cookies запрещены [129].
  - Для браузеров вне панели — запасной путь через Browser Use 3.0 [37].
  - Явное согласие пользователя нужно для установки расширений, подключения к его настоящему Chrome и запуска облачных браузеров [37].
- **Управление компьютером.** Skill `computer` управляет нативными приложениями через Cua Driver или Peekaboo — сторонние инструменты, которые ставятся отдельно [38]. Перед важными действиями driver должен спросить пользователя [38].
- **Панель мобильного симулятора.** iOS Simulator и Android emulator рядом с агентом [4].
  - Добавлена 2026-10-18, приостановлена 2026-10-25. Команда хочет, чтобы агенты сначала сами собирали приложение под симулятор и проверяли его [4].
  - В roadmap она в «In Progress» [3].

### Pages: HTML-страницы, которые публикует агент

- **Что это.** Агент публикует HTML или папку с `index.html` как страницу, которой можно поделиться [39].
  - Способы публикации: CLI (`superset pages publish`), MCP или «Create with AI» [39].
  - Каждая публикация — новая версия, ссылка остаётся той же [39].
  - Размер страницы — до 16 МБ (2026-09-06) [4].
- **Кто видит** [39]:
  - только автор, вся организация (по умолчанию) или любой со ссылкой;
  - внешние читатели не могут комментировать;
  - ссылка показывает либо последнюю версию, либо закреплённую.
- **Комментарии и «listening agents»** [39]:
  - коллеги прикрепляют комментарии к элементам страницы;
  - listening agent (агент, который следит за страницей) получает новые комментарии, правит страницу, публикует её снова, отвечает в thread или закрывает его;
  - для этого хост агента и его сессия должны работать.
  - Комментарии людей печатаются в терминал этого агента [134].
- **Хранилище страницы** [39]:
  - `window.superset.storage` с тремя областями: одно значение на человека (`slot`), личное и общее;
  - до 20 MiB на страницу. Примеры использования — опросы и списки участников.
- **Живые данные** [39]:
  - страница может вызывать инструменты plugins, например Neon SQL или поиск Exa, от имени читателя — после диалога согласия;
  - на телефоне это не работает. Отозвать у страницы доступ к инструментам пока нельзя.
- **Где ещё видны Pages.** Ссылки разворачиваются в Slack [65]. На iOS страницы можно читать и комментировать [52].
- **Hook, который защищает Pages.** Paradev ставит в Claude Code PreToolUse hook. Раз за сессию он блокирует публикацию Artifact самого Claude и отправляет агента к Paradev Pages [107].

### Tasks: встроенный трекер задач

- **Источники задач:** собственные задачи Paradev, issues из Linear или из GitHub [48].
- **Возможности** [48][77]:
  - список и Kanban; фильтры;
  - иерархические метки (`acme/website`); семантический поиск; выбор нескольких задач;
  - у задачи есть статус, приоритет и исполнитель. Из CLI — ещё оценка и срок.
- **Делегирование.** «Run in workspace» на одной или нескольких задачах создаёт по workspace на каждую, и агент в нём уже работает. Шаблон агента превращает задачу в prompt [48].
- **Чего нет.** Зависимостей между задачами, связей родитель–потомок и эпиков нет ни в документации, ни во флагах CLI [48][77].
- **Linear.**
  - Каждый участник подключает свой аккаунт Linear (2026-10-04) [4].
  - Привязка issue берёт имя ветки из Linear и переводит issue в In Progress [64].
  - С октября задачи Linear обновляются вживую, а отдельная вкладка Linear убрана [4].

### Automations (план Pro)

- **Что это.** «Cron jobs для сессий агентов» (2026-05-18) [4]. Run, который дошёл до устройства, создаёт живой workspace. Его можно открыть и продолжить работу [50].
- **Триггеры** [50]:
  - расписание в формате RRULE (RFC 5545);
  - webhooks: bearer token (`sset_wh_…`), тело до 1 MiB, 300 запросов в минуту, без дедупликации;
  - события GitHub (PR открыт, push, merge, запрошен review, проверки закончились, workflow run, release и другие), Slack, Linear, Sentry, Notion и Microsoft Teams (только Enterprise);
  - до 25 триггеров на одну automation.
  - События GitHub из forks пропускаются [50].
  - Триггеры Google Calendar убрали: ими никто не пользовался [4].
- **Куда идёт run** [50]:
  - целевое устройство: эта машина, хост или Cloud с выбранным размером машины;
  - каждый раз новый workspace, всегда один и тот же или выбранный;
  - в общем workspace — «Start fresh» или «Continue» прошлого разговора.
- **Что получает агент.** Payload события, обрезанный до 24 000 символов, стоит перед prompt. Для событий PR делается checkout ветки PR [50].
- **Состояния run:** created, creating, missed, failed [50].
  - Missed-runs никогда не повторяются автоматически.
  - «Retry all» заново отправляет упавшие, «Run now» запускает вручную.
- **Управление** [50][4][55]:
  - статистика здоровья за 7 дней, вкладки Mine и Team, группы, архив с Undo;
  - история версий prompt (2026-05-18);
  - Run History и инструмент MCP `automations_logs`.
- **Ограничения, которые признаёт документация** [50]:
  - доставка at-least-once: prompt должен выдерживать повторный запуск;
  - результат агента не отслеживается: успех значит только «workspace создан»;
  - выключенный хост пропускает run;
  - действия самого агента могут снова запустить automation — риск цикла;
  - один prompt на automation.
  - У организации, которая понизила план, расписания продолжают сдвигаться, но не срабатывают [50][118].
- **Готовые рецепты:** гонка агентов, управление группой агентов, review запрошенных PR, ночной аудит [81][82][83][84].
- **Пример от самой команды.** Ежедневная automation каждое утро открывает 5 PR с уборкой кода и пишет журнал в issue. Сливает их человек [174].

### Remote access, cloud workspaces и BYOC

- **Remote access (Pro)** [51][4]:
  - включается переключателем в приложении (нужно напечатать подтверждение; работающие терминалы перезапускаются) или командой `superset start --daemon`;
  - хосты без интерфейса входят по API-ключам `sk_live_…`;
  - встроена настройка хоста по SSH (октябрь 2026);
  - владелец хоста выдаёт доступ коллегам.
- **Порты удалённого хоста** [51]:
  - найденный порт пробрасывается на тот же локальный порт, пока workspace выбран;
  - только TCP и только порты, которые открыл сам workspace;
  - занятый локальный порт можно переназначить;
  - трафик идёт через relay.
- **Прямой связи по LAN нет.** Подключение к хосту напрямую по LAN или Tailscale просят в issue #5360, он открыт [162].
- **Cloud workspaces** (Team и Ultra; вышли из beta 2026-11-08) [35][4]:
  - environment (описание облачного окружения) содержит от 1 до 20 репозиториев GitHub, переменные и регион;
  - «Set up with an agent» готовит environment с помощью агента; «Save as environment» сохраняет снимок настроенного workspace;
  - размеры машин: Small 2 vCPU / 4 GB, Medium 4 / 8 (по умолчанию), Large 8 / 16; XL и 2XL — по запросу [35]. Исследование внутреннего устройства по той же документации пишет: от 2 до 32 vCPU по 2 GB на vCPU, диск 64 GB, checkout в `/workspace` [35];
  - остановка после примерно часа простоя; файлы хранятся 30 дней; архивный workspace восстанавливается 7 дней;
  - учётные данные в sandbox не копируются: Paradev подставляет их в исходящие запросы;
  - порты облачного workspace пробрасываются только по запросу [60];
  - когда лимит использования исчерпан, работающая машина останавливается примерно через 10 минут [35].
- **Bring Your Own Cloud** [36]:
  - репозитории и входы агентов остаются на своём Linux-сервере (x64 или arm64), входящие порты не нужны;
  - связь всё равно идёт через relay Paradev;
  - кто получил доступ к хосту, получает всё, что видит хост, включая входы агентов.
- **Перенос workspace между машинами** («teleport») пока за feature flag. Детали — в разделе «Как это устроено внутри» [106][132].

### Мобильное приложение (iOS и iPadOS 26+, план Pro)

- **Главный экран** [52]:
  - workspaces, сгруппированные по машинам;
  - цветные точки статуса: жёлтая — ждёт разрешения, красная — сбой, зелёная — готово к review;
  - запуск агента: проект, ветка, агент и модель; можно приложить фото.
- **Внутри workspace** сессии видны вживую. Ответить можно текстом или диктовкой [52].
- **Review с телефона** [52]:
  - комментарии к строкам diff, затем «Send review» агенту;
  - merge PR, «Fix Checks with Agent», «Address Comments with Agent»;
  - чтение и комментарии Pages.
- **Чего пока нет.** Push-уведомления обещаны [68]. Голосовой прототип — только внутри команды (2026-10-04) [4]. В коде есть feature flags голосового режима и карточки Live Activity на iOS со статусом агентов [106].
- Приложение вышло в App Store 2026-09-09 и стало №1 дня на Product Hunt 2026-09-21 [199][198][30].

### Usage, лимиты и leaderboard

- **Метры квоты.**
  - Для входов Claude Code и Codex, обновляются каждые 5 минут. У Claude видны окна «Session (5h)» и «Weekly» — процент заполнения и время до сброса [53].
  - Метры есть и для входов Grok, Antigravity и OpenCode [53].
  - Планы, которыми управляет организация, и образовательные планы могут не отдавать лимиты [53].
  - Данные берутся из endpoints провайдеров по сохранённым учётным данным агента: у Claude — `api.anthropic.com/api/oauth/usage`, у Codex — `chatgpt.com/backend-api/wham/usage` [127].
- **Несколько аккаунтов.**
  - Несколько аккаунтов Claude или Codex живут как отдельные профили (`CLAUDE_CONFIG_DIR` / `CODEX_HOME`) [53].
  - Один аккаунт — по умолчанию для новых запусков. Skills, MCP-серверы и история общие для всех аккаунтов [53].
  - Профили Claude делят состояние сессий через symlinks, поэтому `--resume` работает между аккаунтами. Учётные данные у каждого профиля свои [53][127].
  - Работающий агент остаётся на своём аккаунте, пока его не перезапустят [53].
  - Changelog за июль–август объясняет цель: переключиться на другой аккаунт, когда один упёрся в лимит [4].
- **Стоимость tokens** [53]:
  - оценивается по локальным журналам сессий по прайс-листу API;
  - периоды 7, 30 и 90 дней; разбивка по агенту, модели и workspace;
  - использование по подписке показано как $0, рядом — оценка по ценам API и экономия от кэша.
- **Ресурсы машины.** CPU и RAM по каждому workspace и панели, обновление каждые 2 секунды [53].
- **Упёрся в лимит — только в Chat** (с 2026-11-01) [112][4]:
  - уведомление называет, какой лимит, какая модель и какой аккаунт, и показывает обратный отсчёт до сброса;
  - кнопки: «Resume» сейчас; «Resume at reset» — продолжить по расписанию; «Continue this chat on another login»; настройки usage.
  - Пока лимит действует, новые prompts встают в очередь. «Resume at reset» ставит таймер на время сброса плюс 30 секунд и затем отправляет следующий prompt из очереди или просто «Continue» [110].
- **Чего не нашлось.**
  - Автоматического ожидания сброса лимита и автоматического повтора при ошибках API в терминальных сессиях нет. Ошибка API Claude Code просто показывает красный статус «failed» на панели (2026-08-02) [4].
  - Аналога «Resume at reset» для агентов в терминальном режиме не найдено (не подтверждено) [110].
  - Учёта квоты при запуске automations и агентов не найдено (не подтверждено) [119][127].
- **Публичный leaderboard** (по желанию, работает с 2026-08-30) [25][26][4]:
  - публикует дневные суммы: tokens, сессии, сессии одновременно, слитые PR агентов, стоимость по ценам API. Prompts, имена репозиториев и пути файлов не публикуются;
  - профили и «Super Fights» — режим, где два профиля превращаются в дерущихся персонажей;
  - четыре уровня навыка — от «Button pusher» до «Henry Ford».
  - Сейчас на странице счётчики по уровням 1 933 / 782 / 31 / 19 и даты «при таком темпе» от апреля 2027 до июня 2028 года. Что именно значат эти числа — не подтверждено [15].

### Расширяемость: skills, plugins, MCP server, CLI, SDK

- **Встроенные skills.** При каждом запуске приложение записывает их в `~/.claude/skills/superset/` и `~/.agents/skills/` [54]:
  - `superset:setup`, `superset:orchestrate`, `superset:automate`, `superset:page`;
  - `superset:browser`, `superset:computer`, `superset:panes`;
  - `superset:standup` — сводка «что ждёт тебя, что в работе, что заблокировано»;
  - `superset:doctor`, `superset:feedback`, `superset:10x`, `superset:contribute`.
- **Plugins** — MCP-сервер инструментов плюс skills [73]:
  - инструменты получают Claude Code и Codex; skills — ещё Kimi, Vibe и Grok;
  - вызовы инструментов идут через proxy Paradev, поэтому учётные данные не попадают к агенту [73];
  - учётные данные хранятся запечатанными в API Paradev. OAuth — с PKCE и динамической регистрацией клиента [128];
  - MCP-серверы синхронизируются в настройки Claude, Codex и `pdev`. Ledger владения запоминает, какие записи поставил сам Paradev [128].
- **Каталог plugins (19)** [75]: GitHub, Sentry, Resend, Sazabi, Inngest, Stripe, Peec, Supabase, Firecrawl, Ahrefs, Linear, Notion, Granola, Circleback, Wispr Flow, YNAB, Slack, Gmail, Superhuman.
- **Plugins организации** [74][128]:
  - администратор синхронизирует их из репозитория-маркетплейса на GitHub;
  - доступ по ролям: Unavailable, Available или Installed;
  - hooks из plugins не запускаются: папка `hooks/` вырезается.
- В октябре plugins и подключения к приложениям стали доступны прямо в prompts [4].
- **MCP server** по адресу `api.superset.sh/mcp`, вход по OAuth 2.1 или API-ключу [55].
  - Инструменты: задачи, workspaces, агенты, терминалы (создать, отправить, прочитать), Pages, automations, проекты, хосты и участники [55].
  - API-ключ MCP даёт полный доступ к организации [55].
- **CLI** [77][116]:
  - команды `workspaces`, `agents create/wait/explain/read`, `terminals send/read/wait`, `snapshot` (весь хост за одно чтение), `panes` (скрипт раскладки окна), `browser`, `pages`, `automations`, `plugins`, `settings` и `schema`;
  - `agents wait --until settled` возвращается, когда агент в покое или заблокирован; timeout по умолчанию — 600 секунд;
  - `agents explain` объясняет, почему агент показан как starting, working, blocked, idle или exited.
- **TypeScript SDK** (`@superset_sh/sdk`) — ранняя alpha, не для production [79]. Roadmap при этом держит «SDK and public API» в «Exploring», хотя SDK вышел в мае [3][4].
- **Orchestration.** Skill `superset:orchestrate` превращает сессию Claude Code или Codex в coordinator — агента, который раздаёт работу другим агентам [56]:
  - coordinator создаёт workspaces и агентов-workers через CLI и следит за ними командами `terminals read/send`;
  - worker в конце пишет структурированное сообщение «done» или «blocked»; coordinator проверяет его до объединения работы.
  - Как это устроено — в разделе «Как это устроено внутри → Параллельность и координация».

- Менялось и существительное: терминал, потом редактор или IDE, потом workspace. Ещё команда называет продукт ADE — agent development environment, среда разработки для работы с агентами [18].

### Заявленная философия

1. **Узкое место — внимание человека, а не мощность агентов.**
   - План на 2026 год (2026-02-02): команда надёжно держала 5–7 агентов одновременно и целилась в 100 агентов на человека к концу 2026 года [27].
   - Каждому агенту всё равно нужен человек: проверить работу, дать обратную связь, выбрать следующую задачу [27].
   - Проверка для любой функции: сокращает ли она время человека на одно взаимодействие с агентом [27].
   - Три рычага плана [27]:
     1. Агент делает больше, прежде чем просить помощи. Идеи: агент-фильтр (в плане — gatekeeper), который не пропускает к человеку недоделанную работу; цепочки review-агентов, чьи находки измеряются; долгие итеративные циклы вроде «Ralph loop» (агент повторяет одну задачу, пока она не будет сделана).
     2. Review становится быстрее. Агент готовит сводку — краткое описание, preview, страницы для проверки, результаты нужных тестов — вместо голого diff. Решения сводятся к «да/нет» или выбору из вариантов; обычный review должен помещаться на телефоне.
     3. Агенты начинают работу сами — из переиспользуемых skills и по событиям.
   - На Launch HN команда сказала: трудно не запустить больше агентов, а управлять состоянием вокруг них и помнить, что делает каждый [184].
2. **Независимость от агента: свой агент и своя подписка.**
   - Paradev запускает CLI-агентов, которые у пользователя уже есть, на его планах или API-ключах [1].
   - Вызовы моделей не проксируются [1][33].
   - Команды запуска оборачиваются, а lifecycle hooks ставятся только ради сигналов статуса [33].
   - В мае 2026 года сотрудник сказал: на SDK вендоров не строим и не планируем, потому что терминальный подход сразу даёт каждую новую функцию любого CLI [184]. Ответ написан с аккаунта hoakiet98. Исследование отзывов считает его аккаунтом Kiet Ho [184]; исследование направления — вероятно, Kiet Ho (не подтверждено) [184].
   - Chat, который вышел из experimental 2026-11-08, тоже управляет собственным CLI пользователя по ACP [4][41].
   - FAQ на сайте отвергает мысль, что Paradev — обёртка над Claude Code [1].
3. **Изоляция — один worktree на задачу, с признанными пределами.**
   - Одна модель: делегировать в workspaces, объединять через ветки и PR [33].
   - Workspaces задуманы дешёвыми и одноразовыми [33].
   - Документация прямо пишет: worktrees разделяют только файлы. Порты, базы данных, учётные данные и merge-конфликты остаются общими [28][33].
4. **Сессии живут дольше интерфейса.**
   - Сессиями владеет отдельный terminal daemon. Команда попробовала tmux, отказалась и написала свой [29].
   - Агенты продолжают работать, когда приложение закрыто, завершено или обновляется [46].
   - После перезагрузки прерванные сессии продолжаются через команду resume самого агента [28][4].
5. **Local-first и приватность по умолчанию.**
   - Код, worktrees, вывод терминалов и сессии агентов остаются на машине [1][2].
   - С решения 2026-07-16 проекты хранятся только в локальной базе хоста, облачная синхронизация workspaces выключена. Облако вернётся позже как отдельная сущность [95].
   - Roadmap пишет, что основной цикл работает без входа и offline [3]. Это ответ на популярную просьбу сделать вход необязательным (issue #2685) [148]. Код и открытый issue #4894 говорят обратное — см. раздел «Модель работы» [113][160].
6. **Работу на задачи разбивает разработчик.**
   - Гид по orchestration делит категорию по одному вопросу: кто разбивает работу на задачи [20].
   - В инструментах, где ведёт coordinator, план и раздачу задач делает AI; пример — Augment Intent [20].
   - Paradev относит себя к группе, где ведёт разработчик, вместе с Conductor и Zed [20].
   - Avi Peltz в мае 2026 года: Paradev — не столько инструмент для роя агентов (swarm), сколько способ запускать независимых агентов в изолированных окружениях [184].
7. **Прогнозы должны быть проверяемыми.**
   - Страница Factory 2026 называет себя рубрикой из проверок «да/нет» и обещает не сдвигать цели [14].
   - «The Production Run» ставит датированный публичный прогноз, который можно опровергнуть. Пороги уровней не меняются, даже если результаты плохие [26].
8. **Строить публично и делать продукт в самом продукте.**
   - Еженедельный changelog, открытый репозиторий и открытые PR [6].
   - Paradev разрабатывают в Paradev [6][183].
   - Найм заканчивается оплачиваемым 5-дневным испытанием в офисе [6].
   - Правила репозитория требуют писать комментарии на упрощённом техническом английском (ASD-STE100) [98].
   - Контрибьютор отвечает за код, который написал агент, и не должен писать, что проверки прошли, если он их не запускал [98].
9. **Полный доступ по умолчанию внутри worktree.**
   - Claude Code стартует с `--dangerously-skip-permissions`, Codex — с `--dangerously-bypass-approvals-and-sandbox` [43][105].
   - Документация объясняет, как убрать флаг и вернуть запросы прав [43].
   - Безопасность держится на изоляции и review, а не на политике прав.
   - Исключения:
     - по планам Chat выводит сессии из режима bypass [140]. Код при этом стартует чаты в режиме без ограничений [111] — источники расходятся;
     - skills браузера и управления компьютером велят агенту спрашивать перед важными действиями [21][38].

### Ключевые понятия

**Пять частей «The Paradev Model»** [33]:
- **Projects** — зарегистрированный репозиторий со скриптами `.paradev/config.json` (setup, teardown, run).
- **Workspaces** — worktree на своей ветке со своими терминалами.
- **Terminals** — сессии, которые переживают приложение.
- **Agents** — любой CLI-агент.
- **Devices** — машина, на которой живёт workspace.

Любой рецепт — те же пять частей в другой расстановке: гонка агентов, разнесённый рефакторинг, ночной аудит [33].

**Понятия работы и review.**
- **Hosts и devices, Remote Access, BYOC, Cloud workspaces, Environments.** Cloud workspace — sandbox, собранный из environment. Агенты видят в нём подставные учётные данные, а настоящие Paradev подставляет в исходящие запросы [35].
- **Automations** — prompt плюс до 25 триггеров: расписание, GitHub, Slack, Linear, Sentry, Notion, Microsoft Teams, webhook. Каждый run даёт живой workspace [50]. Команда прямо пишет: созданный workspace не доказывает, что агент справился [20].
- **Pages** — HTML, который публикует агент. Версии живут по одной ссылке; коллеги прикрепляют комментарии, а следящий агент по ним работает [21][4].
- **Tasks** — свой трекер Paradev или зеркало Linear: работа «от тикетов» [3][4].
- **Plugins** — skills плюс MCP-серверы, которые ставятся один раз для многих агентов. MCP-записи указывают на proxy Paradev; plugins организации синхронизируются из репозиториев GitHub [73][4].
- **Состояния workspace для разбора:** Needs attention, Working, Needs review, Idle, Merged. Roadmap называет это очередью внимания [4][3].
- **Session handoff и fork** — продолжить сессию другим агентом или сделать её копию [4].

**Понятия категории и имени.**
- **ADE.** Стек из трёх слоёв: модель, агент (harness) и ADE вокруг них. В ADE главный объект — задача, а не файл [18].
- **«Paradev»** — параллельный разработчик, по аналогии с paralegal или paramedic [22].

**Понятия измерения.**
- **Уровни Factory F0–F5:** Manual, Assisted, Supervised, Delegated, Orchestrated, Autonomous [14].
- **Личные уровни:** Button pusher, Operator, Plant Manager, Henry Ford [26].
- **Production Run** — месяц, в который все стремятся к одной общей цели [26].

### Главная идея: «software factory»

**Страница Factory 2026** (без даты; оценки — на август 2026 года) [14]:
- Оценивает команды разработки так же, как оценивают уровни автономии беспилотных машин.
- Ставит отрасль и себя на F3, Delegated: открыто 2.5 из 3 проверок F3 и 1 из 5 проверок F4.
- Называет F4, Orchestrated, ставкой на 2026 год. На F4 люди задают направление, а единицей внимания становится решение.
- F5 на 2026 и 2027 годы прямо не прогнозируется.
- Прогноз:
  - начало 2026: review становится узким местом (отмечено как случившееся);
  - середина 2026: инженеры становятся диспетчерами со вкусом (идёт);
  - конец 2026: ночная смена — работу, выданную в 18:00, к 9:00 можно сливать (прогноз);
  - 2027: первые команды на F4 (прогноз).
- Paradev называет себя рабочим местом для перехода от F3 к F4.

**«The Production Run»** (2026-08-27) [26]:
- Для каждого разработчика записываются шесть величин, оцениваются пять:
  - Width — параллельные сессии, считаются по 15-минутным интервалам;
  - Depth — tokens на сессию;
  - Output — слитые PR агентов;
  - Sustain — активные дни;
  - Cost — доллары на слитый PR. Чем меньше, тем лучше: это оценка эффективности, а не трат.
- Уровень человека — минимум по всем осям, а не среднее.
- Пороги:
  - Operator: 2 параллельные сессии, 1 слитый PR агента в неделю, не больше $9 на слитый PR;
  - Henry Ford: 10 параллельных сессий, 10 слитых PR агентов в неделю, не больше $3.50 на слитый PR.
- Прогноз: к августу 2028 года больше каждого пятого разработчика на доске будет на верхнем уровне.
- Замер 2026-08-27: 99.7% из 320 разработчиков с рейтингом были на нижнем уровне. Команда признаёт, что учёт PR занижен: только GitHub и только PR из workspaces Paradev.
- Пост с результатами обещали на начало октября 2026 года. На 2026-11-13 его в индексе блога нет [31].

**Leaderboard** (работает с 2026-08-30) [4][25]:
- Участие добровольное. Публикуются суммы tokens, модели и уровень; prompts, имена репозиториев и пути файлов — никогда.
- Игровой режим «Super Fights» превращает два профиля в дерущихся персонажей [25].

**Как это видит инвестор.** USV называет orchestration управляющим слоем работы агентов. Фонд ожидает, что победят открытые слои, не привязанные к модели и harness, а агенты будут учиться на результатах [215].

### Чем подход отличается

- **Терминал, а не обёртка.** Пользователь работает в настоящем TUI Claude Code, Codex или OpenCode, а Paradev добавляет вокруг worktrees, статус и review [184][189][207]. Conductor, ближайший конкурент, построен вокруг чата [184][200].
- **Разбивает работу человек.** Coordinator-агент — лишь skill по желанию, а не ядро продукта [20][56].
- **Безопасность — изоляцией и review, а не политикой прав.** Агенты по умолчанию работают без запросов подтверждения [43][44].
- **Мерило — время человека и стоимость результата.** Человеческое время на взаимодействие с агентом и доллары на слитый PR [27][26].
- **Сессии отделены от окна.** Собственный terminal daemon вместо tmux [29].
- **Широта агентов при отказе от SDK.** Больше 20 CLI-агентов [42]. При этом черновые планы описывают свой протокол чата с adapter Claude прямо на Agent SDK — это расходится с позицией «без SDK» мая 2026 года [140][184].

### Процессы на локальном хосте

**1. Electron desktop** [130]
- Запускает или подхватывает по одному `host-service` на организацию. Двойной запуск исключён блокировкой.
- Хвост вывода, который прикладывается к отчёту о падении, очищается от секретов.
- Упавший `host-service` перезапускается с backoff: 1 секунда в начале, не больше 30 секунд, 8 попыток, со случайным разбросом. 60 секунд стабильной работы обнуляют счётчик.

**2. `host-service`**
- Headless HTTP-сервер на 127.0.0.1. Desktop, CLI и телефон вызывают его tRPC router [78][99].
- Клиенты находят его по файлу `~/.paradev/host/<orgId>/manifest.json`: там endpoint и token [78].
- Token — заранее выданный bearer-ключ, сравнение идёт за постоянное время [131].
- Изменения router-а должны только добавлять, потому что его вызывают клиенты разных версий. Одно ломающее изменение уже дало ошибки HTTP 405 в desktop 1.24.0 [99].
- Режим без интерфейса — `superset start --daemon`. Под systemd нужен `KillMode=process`, иначе перезапуск убьёт и terminal daemon [78].
- Обработчик ошибок на уровне процесса пишет в log неперехваченные исключения и не даёт сервису упасть. Подключён Sentry [131].

**3. `pty-daemon`**
- Отдельный процесс, который владеет всеми PTY. Поэтому терминалы переживают перезапуск `host-service` [100].
- Единственная граница доступа — Unix socket с правами файла 0600. Token внутри протокола нет [101].
- Кадры начинаются с 4-байтной длины (big-endian). Версия протокола была с первого дня [101].
- Работает на Node, встроенном в Electron, а не на Bun [101].
- `node-pty` закреплён на beta-версии, потому что 1.1.0 терял дескриптор `/dev/ptmx` [101].

**Git worker pool** [125]
- Git-операции идут в пуле `worker_threads` размером `max(1, min(4, cpus−1)) + 2`. Если пул недоступен — выполняются в основном потоке.
- Пул появился после stress-тестов: фоновый git status занимал 3.7–14.6 секунды, а один терминал с потоком вывода обрывал общий socket организации.
- После исправления p99 задержки event loop — 6.3 мс.

### Облачная часть

- **API** — Next.js и tRPC в Turborepo [98].
- **Relay** — Cloudflare Worker с одним Durable Object на хост [120]:
  - в августе 2026 года заменил 7 VM на Fly.io и каталог в Redis;
  - у каждого хоста один JSON-канал управления. Каждый поток — отдельный WebSocket, который хост открывает обратно; байты потока relay не разбирает;
  - хост считается отключённым после трёх пропущенных keepalive по 30 секунд;
  - продолжение терминала — через ring buffer и номер последовательности в URL;
  - в тесте relay передеплоили посреди сессии: хост переподключился примерно за 15 секунд, сессии не потерялись.
- **Realtime hubs** — Durable Objects на организацию, страницу, workspace, пользователя, сессию агента и перенос workspace; хранилище R2 [132].
- **QStash** — тики и dispatch automations [118].
- **Vercel Sandbox** — облачные workspaces. Учёт использования — через Autumn, слой биллинга поверх Stripe [121][139].
- **Temporal на контейнерах Cloudflare** — Devs [123].
- **PostHog** — feature flags [110][137].

### Хранилища состояния

- **`host.db`** — SQLite, одна база на организацию: сессии терминалов, привязки терминал–агент, проекты, workspaces, PR, метки и настройки хоста [78][136].
- **`chat.db`** — SQLite в режиме WAL: журнал событий чата (event sourcing — состояние восстанавливается из списка событий) [110].
- **Вывод терминалов** — только в памяти. Daemon хранит 64 KB на сессию [101]. `host-service` держит кольцевой буфер 2 MiB для клиентов, которые пропустили вывод [102].
- **Облачная база** — в коде видны таблицы run-ов automations, загрузок облачных машин и памяти Devs [119][121][124].

### Цикл агента: чей он

**Терминальный режим (по умолчанию).**
- 23 встроенных определения агентов. У каждого команды запуска, resume, fork и неинтерактивного запуска. Примеры: Claude Code, Codex, Gemini, OpenCode, Cursor Agent, Copilot, Droid, Amp, Devin [105].
- **Как доставляется prompt.** Prompt печатается в shell как heredoc. В fish он кладётся во временный файл, который удаляется сразу после чтения [105].
- **Статус — через hooks.** Paradev вписывает lifecycle hooks в глобальные настройки каждого агента, рядом с hooks пользователя [47][107]:
  - Claude Code: SessionStart, SessionEnd, UserPromptSubmit, Stop, StopFailure, SubagentStart/Stop, PostToolUse(Failure) и PermissionRequest — в `~/.claude/settings.json`;
  - Codex: hooks — в `~/.codex/hooks.json`. Его события «ход закончен» и «запрос одобрения» превращаются в Stop и PermissionRequest.
- **Как ведёт себя скрипт hook** [47][107]:
  - вне терминала Paradev ничего не делает;
  - отбрасывает события чужого harness — например, когда Cursor проигрывает настройки Claude или запущен вложенный `codex exec`;
  - если событие не разобралось, отбрасывает его, а не сообщает ложное «закончил»;
  - отправляет POST в `host-service` на `/trpc/notifications.hook`: 2 секунды на подключение, 5 секунд всего.
- **Трафик моделей.** В этом режиме Paradev его не касается: CLI сам ходит к провайдеру [33][36].

**Режим Chat (ACP).**
- Установленный CLI управляется по ACP, поэтому чат делит с ним вход, настройки и MCP-серверы [41].
- Минимальные версии: Claude Code 2.1.226, Codex 0.160.0, OpenCode 1.15.5. Gemini и Pi тоже в каталоге [41][111].
- Одну сессию можно переключать между видом чата и терминала без перезапуска [41].
- **Конвейер выполнения** [110]:
  - adapter harness питает живую сессию, она дописывает события в журнал, а hub подписок рассылает их клиентам;
  - переподключившийся клиент сначала проигрывает журнал, потом получает живые события;
  - команды дедуплицируются по `commandId`;
  - Codex управляется через свой app-server по JSON-RPC поверх stdio.
- Каждый prompt делает git snapshot в worker pool — отсюда Undo для каждого хода [111].
- История стека чата: первый чат на Mastra (open-source фреймворк агентов на TypeScript) вышел в марте; потом его заменил ACP поверх CLI пользователя. Черновые планы описывают уже свой протокол чата с adapter Claude прямо на Agent SDK [4][140].

**Свои агенты Paradev.**
- **Slack-агент.** Его цикл работает внутри API Paradev на моделях Claude, по умолчанию `claude-sonnet-5`. QStash дедуплицирует события Slack [135]. Инструменты агента не могут удалять, сливать и массово записывать [65].
- **`pdev`.** Публичные сборки есть с 2026-10-12 [92]. Desktop поставляет для него ACP harness; агент входит в router моделей Paradev [111].
- **Devs** — ниже, в «Параллельность и координация».
- **Скрытое использование моделей.** Имя нового workspace придумывает CLI агента этого workspace: Paradev запускает его без интерфейса на маленькой модели и с учётными данными пользователя [104].

### Планирование и разбиение задач

- **Планировщика в продукте нет.** Документация описывает модель «делегировать в workspaces, объединять через ветки и PR» [33]. Блог февраля 2026 года оставляет объём, порядок и зависимости задач человеку [28].
- **Машинное планирование — это skill.** Его выполняет сессия-coordinator Claude Code или Codex по `superset:orchestrate` [56][114]. Skill прямо говорит: Paradev даёт только транспорт сессий, а зависимости задач и учёт завершения держит coordinator [114].
- **Таблица задач coordinator-а** [114]:
  - живёт в контексте самого coordinator-а. Колонки: задача, зависимости, workspace, хост, терминал, статус (pending, ready, running, completed, blocked, failed), результат;
  - Tasks Paradev — записи трекера, а не узлы графа.
- **Prompt для worker-а** [114]:
  - обязан содержать: id задачи, объём, разрешённые файлы, критерии приёмки, команды проверки, зависимости и формат отчёта о завершении;
  - worker заканчивает текстовым блоком `SUPERSET_WORKER_DONE` или `SUPERSET_WORKER_BLOCKED`. Это договорённость в prompt, которую coordinator читает из вывода терминала, а не надёжное событие.
- **Чего нет в документации.** Как coordinator делит работу, не описано. Лимитов, timeouts и правил повтора нет [56].
- **Roadmap от 2026-02-02 обещал три вещи** [27]:
  - долгие циклы агентов;
  - работу по событиям — она вышла как automations [50];
  - агента-фильтра между агентами и человеком (в плане — bouncer). Что он вышел — не подтверждено: поиск по коду такого компонента не нашёл.

### Параллельность и координация

**Раздача работы и наблюдение**
- Раздача — `workspaces create` плюс `agents create`. Несколько запусков в одном workspace стартуют параллельно (`Promise.all`) [104][114].
- Наблюдение — опросом [114][116]:
  - `terminals read --max-lines 240` читает последний вывод;
  - `agents wait --until settled` возвращается, когда агент в покое или заблокирован; timeout по умолчанию — 600 секунд;
  - `agents explain` объясняет текущее состояние агента.
- На запрос прав coordinator отвечает нажатием Enter в терминал worker-а, а прерывает — клавишей Esc [114].

**Правила skill** [114]
- Повторно раздавать задачу можно, только изменив prompt, входные данные или worker-а.
- После повторяющихся неудач — остановиться.
- Рискованные или пересекающиеся изменения проверять отдельно.
- Ветки workers Paradev никогда не сливает.

**Лимиты и гонки**
- Ни документация orchestration, ни документация automations не называют предела параллельности [56][50].
- Рецепт «race agents» отправляет один prompt нескольким агентам. Победителя выбирает человек и сам запускает тесты перед push [81].

**Devs** (feature flag `channels`; по плану 2026-10-28 production-пользователей нет) [124]
- У каждого Dev одна главная сессия без машины. Работу с кодом она отдаёт сессиям-задачам, каждая на своей облачной машине, в роли writer или reviewer.
- Одновременно идут не больше 3 задач, остальные ждут в очереди. Результат задачи будит главную сессию сообщением в её текущем ходе.
- Классификатор «Jev» направляет сообщения из каналов нужному Dev. На отложенных примерах — 93.8% precision и 100% recall.
- Инструменты Dev собраны в MCP-сервер: reply, start/message/stop task, remember/recall и другие.
- Инцидент: главная сессия не видела сбой запуска и шесть раз подряд запустила задачу. Исправление: инструмент возвращает ошибку, плюс правило в prompt.
- Инструмент subagents у `pdev` запрещён: вся делегация идёт через задачи.
- Devs опираются на Temporal и сервис `ParadevAI/router`. Router не публичный, его роль — не подтверждено [124][106].
- **Надёжность через Temporal** (движок workflows) [123]:
  - один workflow на сессию агента; он завершается после 10 минут простоя;
  - последние 500 ID prompts хранятся для дедупликации;
  - сообщения, пришедшие во время хода, вливаются в него как уточнения;
  - сверка запускается раз в минуту и пропускается, если прошлая ещё идёт;
  - worker закрепляет `pdev` 0.2.3 по sha256 и использует модель Sonnet 5.5 через router Paradev.

### Работа без присмотра: automations изнутри

**Конвейер расписания** [118][117]
- Раз в минуту QStash вызывает route `evaluate`. Он выбирает триггеры расписания, которым пора сработать, пачками по 2 000 [118].
- Следующее время запуска вычисляется до постановки в очередь. Поэтому триггер, который не может сдвинуться вперёд, не срабатывает на каждом тике [118].
- Каждый dispatch ставится в очередь с ID дедупликации `<automationId>_<scheduledFor>`, двумя повторами QStash и callback на случай сбоя [118].
- Отдельный проход переотправляет события, которые не дошли до QStash [118].
- План апреля 2026 года рисовал здесь Vercel Cron, код использует QStash [117][118].

**Dispatch** [117][119]
- Пустой prompt отклоняется [119].
- Выбирается хост в сети. Кто в сети, решают Durable Objects relay. Если в сети никого — run записывается как missed [119].
- Выпускается JWT пользователя на 300 секунд. Довод плана: общий секрет при утечке раскрыл бы всех пользователей и все хосты навсегда, а выпущенный token раскрывает одного пользователя максимум на 5 минут [117][119].
- Workspace создаётся на хосте через relay [119]:
  - для событий PR — checkout ветки PR;
  - можно переиспользовать закреплённый workspace, а если его уже нет — создать новый;
  - можно продолжить сессию агента из прошлого run.
- Агент запускается в режиме Chat или в терминале [119].
- Строка run вставляется с игнорированием конфликта и потом всегда закрывается: dispatched или `dispatch_failed` с кодом ошибки [119].

**Статусы и повторы** [50][118]
- `created` значит только, что workspace существует. Это не значит, что агент справился.
- `missed` (нет устройства в сети) не повторяется. Расписание сдвигается при любом исходе.
- «Retry all» и «Run now» запускают заново вручную.
- Доставка at-least-once, поэтому prompts должны выдерживать повторный запуск.
- У организации, которая понизила план, расписания сдвигаются, но не срабатывают.

**Что видели пользователи** [167][166]
- Запланированные runs тихо терялись, хотя хост был в сети. Гонку исправили 2026-08-26 (issue #6128) [167].
- Runs пропускаются как «host offline», хотя хост здоров. Issue #6014 открыт, повторяется на 1.24.2 [166].
- Режим «продолжить сессию» открывал новую сессию на каждом run (issue #7941) [166].

### Изоляция

**Локальные workspaces**
- Один git worktree на workspace, на своей ветке [33][104].
  - Новая ветка создаётся `git worktree add --no-track -b`. Существующая удалённая ветка отслеживается [104].
  - Если post-checkout hook упал, добавление всё равно считается удачным, когда worktree зарегистрирован и HEAD разрешается [104].
  - Sparse checkout (git cone mode) — по желанию; если не сработал, делается полный checkout [104][72].
  - Worktrees живут вне основного checkout: `<папка приложения>/worktrees/<project>/<branch>` [104].
- В worktree приходят только файлы под git. Зависимости и env-файлы — из setup-скриптов [33][66].
  - Скрипты лежат в `.paradev/config.json` под ключами `setup`, `teardown` и `run`. Три слоя настроек: переопределение пользователя, worktree, значение репозитория по умолчанию [66].
  - По умолчанию агент стартует параллельно с setup [66].
- **Не изолированы:** процессы, порты, сеть, базы данных, учётные данные, ресурсы машины [33][43][28].
  - Диапазонов портов на workspace Paradev не выделяет. Он только показывает, какие порты открыл каждый workspace [33][60].

**Cloud workspaces**
- Одна машина Vercel Sandbox на workspace [121]. Публичная документация не называет технологию изоляции [35].
- Размеры — от 2 до 32 vCPU, по 2 GB на vCPU, диск 64 GB. Checkout лежит в `/workspace`. Машина останавливается примерно после часа простоя, файлы хранятся 30 дней [35].
- **Порядок загрузки** [122]:
  - `superset-boot` запускается от root при каждом создании и пробуждении;
  - он запускает `host-service` от пользователя `ubuntu`;
  - затем запускает `memguard` и start hook репозитория.
- Трафик доходит до машины только через домен sandbox, без relay [121].

**BYOC**
- Linux-сервер клиента. Изоляции на уровне workspace документация не описывает [36].
- Кто получил доступ к хосту, получает всё, что видит хост, включая входы агентов [36].

**Браузер**
- Панели, которые открывает агент, живут в отдельной partition сессии, без входов пользователя [37][129].

### Состояние и непрерывность

**Что что переживает** [46]
- ⌘Q оставляет агентов работать, но машина недоступна извне, пока приложение не откроют снова.
- «Quit Paradev Completely» завершает все сессии. Перезагрузка и выход из системы — тоже.
- Защиты от сна нет. Документация советует не давать машине засыпать: во сне агенты встают на паузу. Поиск по коду не нашёл ни `powerSaveBlocker`, ни `caffeinate`.
- Пользователь, который ушёл с Conductor, просит держать Mac бодрствующим, пока работают агенты (issue #9608) [179].

**Обновление daemon** [100]
- Старый daemon передаёт открытые дескрипторы PTY новому.
- Если передача не удалась, старый daemon продолжает работать.
- Фоновые автообновления никогда не перезапускают его принудительно.
- Когда PTY завершился, строка терминала удаляется.

**Scrollback: два поколения**
- Пост о daemon (январь 2026) описывает историю на диске и «cold restore» после падения [29]. Код v1 ещё ссылается на это [138].
- Daemon v2 держит вывод только в памяти, а менеджер истории v1 называет вне scope [101]. Источники расходятся: блог описывает старую схему.

**Перенос workspace между машинами («teleport»)** [132][133]
- Worktree вместе с незакоммиченной работой уходит в одну новую ветку [132].
- Истории чатов и файлы сессий агентов уходят в облако [132].
- Hub проваливает перенос, если машина перестала отвечать [132].
- Журналы чатов синхронизируются с облаком с backoff от 5 секунд до 5 минут [133].

**Облачные машины.** Снимок делается при остановке. Восстановление — примерно 2 секунды. Снимки живут 30 дней [121].

**Local-first.**
- С декабря 2025 года проекты и workspaces синхронизировались через облако на Electric SQL. Решение 2026-07-16 заменило это локальным хранением [4][95].
- До этого, в мае 2026 года, у пользователей пропали из приложения workspaces и агенты. Maintainer объяснил это сбоем Electric SQL вместе с обновлением, которое очистило локальный кэш. Он извинился и перевёл приложение на локальные данные в первую очередь [159][157].

### Память и контекст

- **Памяти, которой управляет Paradev, для локальных агентов не найдено.** Память — то, что хранит каждый CLI сам. Отсутствие — не подтверждено.
- **Передача сессии другому агенту** [45][105][109]:
  - до 36 000 символов с пометкой «история только для чтения»;
  - источники текста по порядку [109]: 1) хранилище сессий самого harness (реплики пользователя и ассистента, без вывода инструментов); 2) повтор кольцевого буфера вывода на 2 MB; 3) видимый экран;
  - предел взят у Orca. В Linux один аргумент командной строки ограничен 128 KB [109];
  - новому агенту велят доверять workspace больше, чем транскрипту, и начать с `git status` [45];
  - ничего не вычищается. Секрет, который напечатала команда, уйдёт новому провайдеру [45].
- **Fork** — через родной fork агента, весь разговор копируется. Обе сессии работают с одними файлами workspace [45][105].
- **Аккаунты.** Профили Claude Code делят состояние сессий через symlinks, поэтому `--resume` работает между аккаунтами. Учётные данные у каждого профиля свои [53][127].
- **Automations.** Payload события (до 24 000 символов) идёт перед prompt. Run может продолжить разговор прошлого run [50][119].
- **Devs.** Инструменты `remember` и `recall`, таблица `agent_memories` [124].
- **Chat** показывает заполненность окна контекста [4].
- **Skills и plugins.** Skills ставятся в `~/.agents/skills` и зеркалятся в `~/.claude/skills`. MCP-серверы синхронизируются в настройки Claude, Codex и `pdev` с ledger владения [128].
- В roadmap «Per-repo agent memory» — в «Up Next» [3].

### Проверка качества

- **Встроенной проверки нет.** Ни локального запуска проверок перед PR, ни review-агентов [49][114].
- **Экран PR** [49][126]:
  - показывает проверки GitHub; отменённая считается упавшей;
  - поддерживает stacked PRs и merge queue;
  - кэширует состояние review, checks и merge queue на каждый head PR.
- **Skill orchestrate** [114]:
  - prompt worker-а называет команды проверки;
  - coordinator должен убедиться, что вывод вокруг блока завершения подтверждает заявленное;
  - рискованные или пересекающиеся изменения проверяются отдельно.
- **Рецепты** [83][85][81]:
  - review запрошенных PR только оставляет комментарии: без approve, push и merge. Review идёт от имени пользователя;
  - ответы на замечания PR: один commit на комментарий, без force-push;
  - гонка агентов: тесты перед push запускает человек.
- **Devs.** Задача-writer следит за `gh pr checks` и сама чинит упавшие проверки. Reviewer — отдельная роль. Числа раундов review ничто не ограничивает [124].
- **Свой конвейер Paradev.** Перед выпуском нового базового образа облачной машины система сначала загружает копию нового снимка, вместе с остановкой и пробуждением. Каждую ночь идёт тест «загрузить дважды» [122].
- В репозитории есть skill для контрибьюторов с правилами доказательств при проверке через CDP. Это правило разработки, а не функция продукта [98].
- В roadmap «Agent self-verification» и конвейер «ticket-to-PR» с доказательствами — пока в «Exploring» [3].

### Восстановление после сбоев

**Терминалы** [100]
- Подхваченный daemon проверяется каждые 2 секунды, его версия опрашивается.
- Circuit breaker (предохранитель от повторных падений) срабатывает после 3 падений за 60 секунд. Сбрасывает его перезапуск пользователем.
- Сигнал закрытия — SIGHUP, потому что login-оболочка zsh перехватывает SIGTERM.

**Автоматическое продолжение агента** [45][108]
- Когда терминал умер неожиданно (убит daemon, перезагрузка, упал PTY), desktop заново запускает агента его командой resume, например `claude --resume <id>`.
- Намеренное закрытие и чистый выход не продолжаются.
- Хост забирает каждого кандидата на продолжение атомарно и объединяет одновременные запросы.
- Интерфейс появляется только при неудачном перезапуске: баннер с кнопкой Retry.
- После потери связи с daemon проход проверяет его 5 раз с интервалом 2 секунды. Только потом привязки без живой сессии помечаются завершёнными. Так работающие сессии не попадают в список на продолжение [108].

**Hooks.** После каждого вызова инструмента hook снова ставит состояние «working». Если событие Start потерялось, статус всё равно станет верным [107].

**Chat.** Чаты, остановленные перезапуском при обновлении, продолжаются или предлагаются к продолжению [111]. Продолжение после падения вышло 2026-11-08 [4].

**Devs на Temporal** [123]
- У activity агента timeout 2 часа и heartbeat раз в минуту.
- Повторы — с backoff от 5 секунд до 5 минут, без предела числа попыток.
- Повтор продолжает сохранённую сессию `pdev` и никогда не отправляет prompt заново. Поэтому сбой провайдера не может потерять ход.

**GitHub.** Пока GitHub недоступен, вызовы придерживаются. Когда он вернулся, обновляются все workspaces [126].

**Облачные машины** [121]
- `memguard` выставляет приоритеты для OOM killer (механизм ядра, который убивает процессы при нехватке памяти): `host-service` и `pty-daemon` — −900, агенты — −300.
- Когда свободной памяти меньше 8%, он убивает самый большой процесс и при необходимости добавляет swap.
- Открытая проблема: агента, чей процесс убит, а терминал жив, продолжить нельзя.

**Автообновление хоста** [78]
- Включается по желанию. Релиз, который не прошёл проверку здоровья, дальше пропускается. Откат на старую версию хост не делает.

**`host-service` и relay.** Перезапуск `host-service` с backoff описан в «Процессах на локальном хосте» [130]. Передеплой relay посреди сессии в тесте не потерял сессий [120].

### Лимиты и стоимость

**Кто платит за модели.** CLI-агенты тратят подписки или ключи пользователя. Paradev эти вызовы не проксирует [1][33][36].

**Метры квоты** [53][127]
- Опрашиваются раз в 5 минут с endpoints провайдеров по сохранённым учётным данным агента: у Claude — `api.anthropic.com/api/oauth/usage`, у Codex — `chatgpt.com/backend-api/wham/usage`.
- Один метр на окно (например, «Session (5h)» и «Weekly») и время до сброса.
- Метры только показывают. В dispatch automations и запуске агентов учёта квоты не нашлось [119][127]. Отсутствие — не подтверждено.

**Лимиты в Chat** (с 2026-11-01) [4][110]
- Определение читает `rate_limit_info` Claude: `status: "rejected"`, `resetsAt`, `rateLimitType`. По ACP оно приходит в `_meta["_claude/rateLimit"]`. Запасной путь — regex по тексту [110].
- Пока лимит действует, новые prompts стоят в очереди [110].
- Пользователь выбирает: продолжить, закрыть уведомление или «Resume at reset». Последнее ставит таймер на время сброса плюс 30 секунд, затем отправляет следующий prompt из очереди или «Continue» [110].
- Работает только внутри одной сессии чата. Для агентов в терминале аналога не нашлось (не подтверждено).

**Показ стоимости** [53]
- Стоимость оценивается по локальным журналам сессий по прайс-листу API.
- Использование по подписке показано как $0, рядом — оценка по ценам API и экономия от кэша, за 7, 30 или 90 дней.

**Аккаунты** [53]
- Несколько аккаунтов на агента, один — по умолчанию для новых запусков.
- Работающий агент остаётся на своём аккаунте до перезапуска.

**Учёт облака самим Paradev** [121][137][35][139]
- GB-hours облака резервируются в Autumn на каждую загрузку машины и сверяются раз в 30 минут [121].
- Запуск машины отклоняется без платного плана или когда лимит использования организации исчерпан [137].
- Работающая машина останавливается примерно через 10 минут после достижения лимита [35].
- Autumn поддерживает лимиты трат [139].
- Открытая проблема: облачные automations оставляют по одной машине на run, и предела трат на это нет [121].

**Бюджет запросов к GitHub API** [126]
- Условные запросы: ответ 304 не тратит rate limit.
- Кэш на 60 секунд для каждого репозитория.
- Закэшированный отказ при повторных неудачах живёт вдвое дольше каждый раз.

### Права и безопасность

**Одобрение действий агента**
- Флаги запуска по умолчанию обходят собственные запросы подтверждения агентов [43][105][44]:
  - Claude: `--dangerously-skip-permissions`;
  - Codex: `--dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust`;
  - Gemini: `--approval-mode=auto_edit`; Grok: `--always-approve`; Hermes: `--yolo`.
- Документация показывает, как убрать флаги в Settings → Agents [43].
- Issue #2419 (2026-03-12) жаловался, что флаг навязывался даже в собственных presets пользователя (13 голосов). 2026-07-11 его закрыли в чистке устаревших issues как дубликат общего issue [147].
- Миграция переносит старые разрешающие настройки существующим пользователям [105].
- Режим plan нельзя совместить с пропуском прав при создании workspace [184].
- **Права в Chat — три источника расходятся:**
  - код стартует чаты в режиме без ограничений: у Claude — `bypassPermissions`, у Codex — `agent-full-access` [111];
  - документация описывает одобрение и отказ одним кликом [41], а агент спрашивает в чате, прежде чем трогать файлы вне workspace [40][44];
  - планы чата пишут, что Chat выводит сессии из режима bypass [140].
  - Какой режим пользователь видит на деле — не подтверждено.
- **Движка политик для автоматического одобрения не найдено.** Автоматическое одобрение — это coordinator, который нажимает Enter в терминале worker-а [114].
- **Trust папок.** Paradev заранее помечает папку доверенной в Claude, Codex и Antigravity, только если хост создал её сам. Папку, где уже лежали файлы пользователя, он не помечает никогда [104].

**Локальные endpoints**
- `host-service` слушает только loopback и требует заранее выданный ключ [78][131].
- Socket PTY — с правами 0600 [101].
- Endpoint для hooks агентов намеренно без аутентификации: он только проигрывает звуки и отмечает событие в связанной задаче [103].

**Remote access**
- Включение требует напечатать фразу подтверждения [51].
- Владелец хоста выдаёт доступ участникам. Они получают всё, до чего дотягивается `host-service` [51].
- Пробрасываются только порты, которые открыл workspace, и только TCP [51].
- При переходе на WebSocket через relay секрет хоста идёт в query string параметром `token` [131].
- Сквозного шифрования на уровне приложения в коде relay не найдено (не подтверждено) [120].

**Учётные данные в облаке** [35][121][103]
- Учётные данные моделей и GitHub не попадают на машину. Там лежат подставные значения, а правило firewall на выходе подставляет настоящие.
- Терминалы sandbox получают CA-сертификат этого firewall.
- Принятый риск: посетитель workspace действует на GitHub от имени создателя workspace [121].
- Открытый риск: машина может дотянуться до приватных workspaces своего создателя [121].
- Не сделано на проверке доступа к sandbox: убрать ticket из query string, сузить CORS с `*`, поддержать ротацию секретов [121].

**Прочие части продукта**
- API-ключи MCP дают полный доступ к организации [55].
- Plugins [128]: учётные данные запечатаны в API; вызовы инструментов уходят из API, а не от агента; OAuth с PKCE и динамической регистрацией клиента; у plugins организации из GitHub вырезается папка `hooks/`.
- Браузер [37][129]: CDP агента ограничен одной панелью, методы cookies запрещены; установка расширений требует одобрения, файлы сверяются с подписанными hash; данные Design mode чистятся.
- Token для dispatch automations — JWT одного пользователя на 300 секунд [117][119].
- Инструменты Slack-агента не могут удалять, сливать и массово записывать [65].
- Хвост вывода в отчётах о падении чистится от секретов [130].
- Hook, который защищает продукт самого Paradev: PreToolUse hook раз за сессию блокирует публикацию Artifact в Claude и направляет агента к Paradev Pages [107].

### Где решает человек

- Уведомления, когда агент закончил или ждёт ввода; badge в Dock; флаг «needs attention» [47].
- В чате — вопросы агента, запросы на инструменты и review плана [47].
- Coordinator спрашивает, прежде чем добавить SSH-хост. Перед повторной раздачей заблокированной задачи он устраняет причину или спрашивает пользователя [114].
- Review: diff и PR; комментарии к строкам отправляются агенту [49]. В Pages комментарии людей печатаются в терминал следящего агента [134]. Всё это доступно и с телефона [1][51].
- Явное согласие — на установку расширений, подключение к настоящему Chrome и запуск облачных браузеров [37]. Drivers управления компьютером спрашивают перед важными действиями [38].
- Automations заканчиваются workspace, который открывает человек. `created` не значит успех [50].

### Что хвалят

**Это терминал, а не обёртка.**
- Самая частая причина, особенно в сравнении с Conductor. В панели работает настоящий терминальный интерфейс Claude Code, Codex или OpenCode, а приложение добавляет вокруг worktrees, статус и review [184][189][207].

  - не-инженеру, который тоже перешёл, не нравились лишний интерфейс Conductor и то, как он показывает текст;
  - давний пользователь описал разницу как «вокруг терминала» против «вокруг чата».
- Ещё один пользователь HN назвал продукт эмулятором терминала с помощниками для агентов и похвалил, что Claude и Codex не завёрнуты в чужой интерфейс [189]. Wes McKinney в апреле 2026 года противопоставил его Conductor так же [207].

Один комментатор связал это с тем, что Anthropic с середины июня 2026 года будет считать использование через SDK-приложения вроде Conductor «программным». Другой спросил, подтверждено ли это; ответа нет (не подтверждено) [184][188].

**Worktrees плюс настройка окружения.**
- Конвейер на тикет через setup-скрипты [190][184]:
  - пользователь берёт тикет из Linear, создаёт worktree, резервирует порты, запускает серверы и браузер, потом запускает Claude с тикетом как инструкцией;
  - держит около десяти копий одного стека серверов на разных портах;
  - каждую копию тестирует end-to-end параллельно — Claude плюс MCP-сервер Chrome.
- Пользователь, который пробовал Emdash и Superset для инфраструктуры на worktree, смог заставить работать setup-скрипт только в Superset [191].
- Wes McKinney ценит номер PR и статус CI у каждого worktree. Его цикл: worktree из PR → автоматический review (RoboRev) → исправления → push → merge, когда CI зелёный [207].

  - Issue закрыли в июльской чистке [145]. Настройка хоста по SSH появилась в октябре 2026 года [4].

- **Linux:** AppImage сначала падал. Patch контрибьютора ждал месяцами, и пользователь жаловался, что maintainers не отвечают. `.deb` и исправления вышли в сентябре 2026 года [141].
- **Удалённые и облачные workspaces.** Удалённые workspaces вышли в beta в мае 2026 года, облачные появились в плане Team к ноябрю [184][186][2]. Что пишут пользователи:
  - на старте набор текста на удалённом хосте шёл с задержкой [184];
  - в ноябре пользователь насчитал 24 обрыва relay на хост за четыре часа [176];
  - при просмотре через Remote Access workspaces пропадают с доски [176].

**Цены и paywalls.**
- Тарифы сейчас: Free — только локальные workspaces; Pro $20 — remote access, automations, Linear, Slack и телефон; Team $60 — облачные workspaces; Ultra $200 [2].
- На HN один пользователь назвал Linear за $20 в месяц дорогим. Другой хотел разовую покупку примерно за $50 [184].
- **Февраль 2026: платная интеграция, которая не работала.** Платная интеграция с Linear была просто списком задач и показывала неверный статус подключения. Пользователи переходили на Free; команда предлагала возврат денег, пока не исправила [144].

**Безопасность и права.**
- Сессии Claude, запущенные из prompt, всегда шли с `--dangerously-skip-permissions` (issue #2419, 13 голосов) [147].
- Пользователи просят workspaces в Docker-sandbox, чтобы такой режим был безопасным. Просьба открыта с мая; в октябре один пользователь назвал её жизненно важной [154].
- Пользователи делают обходные пути сами: Docker Sandboxes вокруг worktrees Superset [193] или скрипт на 50 строк с sandbox [183].
- Один обзор описал продукт как много агентов в worktrees без sandbox [211].
- Режим plan нельзя совместить с пропуском прав при создании workspace [184].

**Automations и hooks.**
- **Надёжность запусков по расписанию.**
  - Запуски тихо терялись, хотя хост был в сети. Гонку исправили 2026-08-26 [167].
  - Запуски пропускаются как «host offline», хотя хост здоров. Issue открыт, повторяется на 1.24.2 [166].
  - Режим «продолжить сессию» открывал новую сессию на каждом run [166].
- **Просьбы:**
  - возвращать упавшую проверку CI в workspace, который открыл PR [171];
  - не давать Mac засыпать, пока работают агенты — просьба от пользователя, который уходит с Conductor [179];
  - продолжать сессии агентов после перезагрузки — открыта с апреля, есть черновой PR [153].
- **Цена hooks.** Hook уведомлений, который приложение ставит в Claude Code, занимал 10–14 секунд на событие и упирался в timeout 30 секунд, когда агентов много. В 1.39.0 проблема ещё была [172].

**Смена имени и лицензии.**
- **Имя.** Комментаторы HN постоянно путали продукт с Apache Superset. Kiet признал, что имя было неудачным [184]; пост о новом имени ссылается на совпадение имён [22]. Один отзыв на Product Hunt, похоже, описывает self-hosted dashboards Apache Superset — это вывод исследования, а не факт [198].
- **Лицензия.** Пользователей путала формулировка ELv2 про self-hosting [184]. Обзоры отмечали, что ELv2 — не open source в смысле OSI [212][213]. С 2026-11-04 проект под MIT [89].
- **Соглашение контрибьютора.** В цикле 2.0.0 (2026-10-26) для PR стал обязателен CLA [87].

**Как обрабатывают issues.**
- AI-бот отвечает на каждый issue разбором кода [178].
- Чистка устаревших issues 10–12 июля 2026 года закрыла 552 issue и свела их в трекеры по категориям [181]. Пользователи продолжают писать в эти трекеры свежие воспроизведения [164].
- Обзор насчитал больше 1 300 открытых issues в июне 2026 года [212]. Сейчас открыто 576 [88].

### Реальные результаты и неудачи

- **Сколько агентов на деле.**
  - Команда: 5–7 параллельно на исправлениях ошибок, 2–3 на настоящих функциях (декабрь 2025) [183]. Kiet: 5–6 продуктивных агентов на прототипах и мелких задачах (май 2026) [184].
  - Пользователи: 40–50 открытых сессий [184], около 60 сессий в примерно 32 панелях [164], около 10 копий стека разработки [190].
- **Заявленные результаты.**
  - Рецензент на Product Hunt: параллельные агенты Claude Code позволяют выпускать его продукты за часы вместо дней [198].
  - Ежедневная automation самой команды каждое утро открывает 5 PR с уборкой кода и пишет журнал в issue. Сливает их человек. В журнале записан урок: PR в стеке поверх другой ветки закрывается, когда эту ветку удаляют [174].
- **Неудачи.**
  - Сбой провайдера синхронизации — workspaces пропали из приложения [159].
  - Вход через OAuth был сломан около двух месяцев [143].
  - Запуски automations по расписанию тихо терялись [167].
  - Удалённые хосты постоянно теряют связь [176].
  - Вспомогательный процесс вырастает до 30 GB [164].
  - Перезапуск каждые 30 минут при 17 workspaces [149].

### Скептики: доводы против всей категории

- **Узкое место — review человеком.** Руководитель разработки не понимал, зачем кому-то 10 агентов. Другие писали, что встречи и уточнение задач важнее, чем больше тикетов в работе [183].
- **Надзор.** Комментатор считает, что LLM может пройти spec и тесты и всё равно построить не то [184].
- **Стоимость.** Одна компания израсходовала дневную квоту одним агентом [184].
- **Нужность.** Кто-то считает, что Linux и хороший терминал — уже IDE [184]. Пользователь HN считает, что один общий checkout и координация агентов лучше worktrees [183].
- **Перенасыщение.** Комментатор сравнил такие инструменты с бесконечным потоком новых JavaScript-фреймворков [183].
- Даже доброжелательный обзор советует начинать с 2–3 агентов и устойчивого процесса review [209].
- Kiet признал: нынешняя раскладка (sidebar плюс терминал) не выдержит будущего, где запуск агентов и review их работы важнее, чем написание кода [184].

### Невыпущенная работа в репозитории

Всё это — экспериментальное.
- **`pdev`, свой агент.** Построен на open-source агенте `pi` Mario Zechner (MIT); релизы 0.1.2–0.2.5 — 16–29 октября 2026 года [92]. Скрыт за флагом `pdev-agent`, может работать как harness для чата [106].
- **Devs — агенты-коллеги в каналах приложения** (флаг `channels`, production-пользователей нет) [124][106]:
  - у каждого Dev одна главная сессия с памятью; своей машины у неё нет, работу с кодом она всегда делегирует;
  - работа уходит задачам writer и reviewer, каждая на своей облачной машине. Writer ждёт проверок своего PR и сам чинит упавшие;
  - классификатор направляет сообщения из каналов нужному Dev: 93.8% precision и 100% recall на отложенных примерах;
  - построены на Temporal и сервисе `ParadevAI/router`. Router не публичный, его роль — не подтверждено.
- **Другие флаги в `main`** [106]: новая оболочка приложения; перенос workspace и его чатов в облако или на другой компьютер; голосовой режим на телефоне (раньше описан как внутренний прототип [4]); карточка Live Activity на iOS.
- Вывод исследования направления: курс — свой агент, командные каналы, облачные машины и review агентами. Это шире прежнего «слоя orchestration для ваших агентов» [92][124][3].

### Бизнес-модель

- Paradev не берёт деньги за использование моделей [23]. Он продаёт места, командные функции и облачные вычисления [2].
- Ставка, названная в мае 2026 года: зарабатывать на командах, а в будущем — на облаке. Команда ожидает, что компании захотят держать общие настройки Linear, GitHub и skills в одном месте [184]. Satya Patel добавил, что правильный тариф для каждой функции ещё не найден [184].
- Инфраструктура cloud workspaces [139][35]:
  - машины — Vercel Sandbox («boxes»);
  - использование считается в GB-minutes через Autumn (слой биллинга поверх Stripe), с лимитами трат;
  - размеры — от 2 до 8 vCPU в стандартных вариантах; остановка после примерно часа простоя.
- Около 60 страниц сравнения с «альтернативами», все обновлены 2026-11-05. Это похоже на крупный маркетинг через контент и SEO [19].
- Работа на доверие enterprise: penetration-тест (март 2026) и SOC 2 Type II (август 2026) [4].

  - Conductor объявил переход в Meta [219].
  - У Paradev есть guides миграции с Conductor и Conductor Cloud. Conductor Cloud перешёл в режим только чтения 2026-11-13 и начнёт удалять данные 2026-11-20 [80].
  - Paradev добавил импорт и мелодию-дань: гудок поезда, который Conductor играл в конце работы workspace [4].
  - Источники расходятся о локальном приложении Conductor: guide Paradev пишет, что Conductor сворачивается; страница самого Conductor — что разработка продолжается, а что-то новое выйдет в начале следующего года [80][219].
- **Круг сравнения.** Paradev относит к ADE себя, Orca, Emdash и Conductor. Cursor, Zed и JetBrains для него — редакторы, которые добавляют интерфейсы для агентов [18].
- **Совместная работа.** Гид orchestration самого Paradev отмечает, что Cursor 2026-11-10 перестроил Projects для совместной работы. Ответ Paradev — делиться самим запущенным cloud workspace [20].
- **Почему важны родные CLI.** Комментатор HN утверждал, что Anthropic с 15 июня будет считать использование Conductor «программным». Это не подтверждено, но объяснило бы ставку на родные CLI [184][188].

### Расхождения между словами и делами

- **«Open source».** Так говорили всё время, но девять месяцев лицензия была ELv2 [89][184].
- **«Без proxy».** Верно для вызовов моделей [1]. Но MCP-записи plugins указывают на proxy Paradev [73], cloud workspaces подставляют учётные данные в исходящие запросы [35], а невыпущенные Devs используют в production ключ router-а [124].
- **«Независимость от агента».** Это по-прежнему главный тезис [1], а параллельно Paradev строит свой агент `pdev` [92].
- **«Работу разбивает разработчик».** Это заявленная позиция [20], а roadmap изучает планирование силами AI и автономный конвейер от тикета до PR [3].
- **Платформы.** Продукт для macOS. Linux — экспериментальный AppImage, Windows нет [1]. Issues про Windows открыты [161][142]. В мае основатели сказали, что Windows каждый день в команде никто не использует [184].
- **Качество.** На HN в мае 2026 года писали о зависаниях и большой нагрузке на машину [184]. В июле устаревшие issues закрыли и свели в трекеры [165][181].

## Слабые места и чего нет

### Слабые места

1. **Вход обязателен.** Код требует входа и организации до любого workspace; просьбы убрать вход либо открыты, либо закрыты чисткой. Документация и roadmap утверждают обратное [113][160][148][32][3].
2. **Реально — только macOS.** Windows нет, Linux экспериментальный [68][69][141][161].
3. **Удалённая работа — только через облачный relay.** Прямой связи по LAN нет [51][162]. Пользователи видят обрывы relay [176]. Секрет хоста идёт в query string при переходе на WebSocket [131]; сквозного шифрования в relay не найдено (не подтверждено) [120].
4. **Worktree — не sandbox.** Процессы, порты, сеть, базы данных и учётные данные общие; диапазонов портов на workspace нет [68][33][60]. Docker-sandbox просят с мая [154].
5. **Агенты по умолчанию работают без запросов прав.** Политики автоматического одобрения нет; автоматическое «одобрение» coordinator-ом — нажатие Enter [43][44][114]. Режим прав в Chat описан противоречиво [111][41][140].
6. **Automations не знают результата.** Успех — это «workspace создан»; missed-runs не повторяются; выключенный хост пропускает запуск; есть риск цикла; доставка at-least-once [50]. Пользователи сообщают о потерянных и ложно пропущенных запусках [167][166]. У облачных automations нет предела трат: по машине на каждый run [121].
7. **Встроенной проверки нет.** Ни локального запуска проверок, ни review-агентов; «Agent self-verification» и конвейер «ticket-to-PR» — в «Exploring» [49][114][3].
8. **Только GitHub.** GitLab и другие хостинги — только локальные функции [68][169].
9. **Лимиты только показываются.** Метры не влияют на запуск; «Resume at reset» есть только в Chat; в терминале ошибка API лишь красит статус в «failed» [53][127][110][4].
10. **Нет защиты от сна.** Во сне агенты встают на паузу [46][179].
11. **План живёт в контексте coordinator-а.** Состояние задач — таблица в контексте агента, а сигналы завершения — текстовые блоки в выводе терминала. В Tasks нет зависимостей и эпиков [114][48].
12. **Производительность и ресурсы.** Задержки ввода, гигабайты памяти, нагрузка от опроса git и сканера портов; зависания на 2.0.2 [149][152][155][164][175].
13. **Стабильность обновлений.** Случаи потери workspaces и разделов sidebar при обновлениях на фоне 18–31 релиза в месяц [157][159][163][87].
14. **Передача сессии не чистит секреты** [45].
15. **Широкие права ключей и хостов.** API-ключ MCP даёт полный доступ к организации [55]; доступ к BYOC-хосту даёт всё, что видит хост [36]; в облаке есть принятые и открытые риски доступа [121].
16. **Hooks статуса бывают медленными:** 10–14 секунд на событие при многих агентах [172].
17. **Популярные просьбы закрывались при чистке устаревших issues, а не после решения:** вход (#2685), SSH (#1513), принудительный флаг прав (#2419 сведён в общий issue как дубликат) [181][148][145][147]. Настройка хоста по SSH появилась позже, в октябре [4].
18. **Продукт меняется под пользователями:** убрали ручное имя workspace, сделали Chat видом по умолчанию, переделали правую панель; пользователей включали в эксперимент без согласия [168][170][178][177].
19. **Смена имени и лицензии** за один год, плюс обязательный CLA [89][87][22].

### Чего нет (или не найдено)

- Infinite canvas или другого пространственного вида — только sidebar, вкладки, splits, доска и список [34][59].
- Эпиков, зависимостей и иерархии задач [48][77].
- Автоматического ожидания сброса лимита и повтора ошибок API для терминальных агентов (для терминала — не подтверждено) [4][110].
- Планирования работы по лимитам подписки и режима экономии [53][127].
- Локального запуска проверок и review-агентов в выпущенном продукте [49][3].
- Записи действий агентов, которую можно проиграть как timeline (не подтверждено) [50][116].
- Памяти агентов, которой управляет Paradev, для локальной работы (не подтверждено); «Per-repo agent memory» — в «Up Next» [3].
- Очистки приватных данных на скриншотах и при передаче сессии [45][129].
- Прямой связи машин по LAN [162].
- Self-hosting серверной части (API и relay) [86][36].
- Windows-сборки, поддерживаемого web-dashboard, приложения для Android и push-уведомлений на телефоне [68][52].
- Стабильного SDK — только ранняя alpha [79].

## Пересечение с worfy

## Механизмы, которые стоит изучить

1. **Терминалы, которые живут дольше приложения.**
   - Что это: отдельный процесс `pty-daemon` владеет всеми PTY, поэтому агенты переживают закрытие, падение и обновление приложения.
   - Как работает: граница доступа — Unix socket с правами 0600, без token внутри протокола; кадры с 4-байтной длиной и версией протокола с первого дня. Клиенты находят `host-service` по manifest-файлу с endpoint и token. При обновлении старый daemon передаёт открытые дескрипторы PTY новому; если передача не удалась, старый продолжает работать; автообновление никогда не перезапускает его принудительно. Подхваченный daemon проверяется каждые 2 секунды; после 3 падений за 60 секунд срабатывает circuit breaker. Закрытие — сигналом SIGHUP, потому что login-zsh перехватывает SIGTERM. Команда сначала пробовала tmux и отказалась от него.
   - Источники: [100][101][78][29].
2. **Правила автоматического продолжения агента.**
   - Что это: перезапуск агента его командой resume после неожиданной смерти терминала.
   - Как работает: продолжаются только неожиданные смерти (убит daemon, перезагрузка, упал PTY); намеренное закрытие и чистый выход — нет. Хост забирает каждого кандидата атомарно и объединяет одновременные запросы. После потери связи с daemon сессия проверяется 5 раз через 2 секунды, и только потом считается мёртвой — так живые сессии не перезапускаются. Интерфейс появляется только при неудаче: баннер с Retry.
   - Источники: [45][108].
3. **Определение лимита по структурированным данным и продолжение после сброса.**
   - Что это: реакция чата на исчерпанный лимит подписки.
   - Как работает: читается `rate_limit_info` Claude (`status: "rejected"`, `resetsAt`, `rateLimitType`), по ACP — из `_meta["_claude/rateLimit"]`; regex по тексту — запасной путь. Пока лимит действует, новые prompts стоят в очереди. Уведомление называет лимит, модель и аккаунт и предлагает: продолжить сейчас, «Resume at reset» (таймер на сброс плюс 30 секунд, затем следующий prompt из очереди или «Continue») или продолжить на другом аккаунте. Работает только в Chat.
   - Источники: [110][112][4].
4. **Гигиена hooks статуса.**
   - Что это: правила, по которым hooks агента сообщают приложению о состоянии и не врут.
   - Как работает: вне терминалов приложения hook ничего не делает; события чужого harness (Cursor, который проигрывает настройки Claude, вложенный `codex exec`) отбрасываются; неразобранное событие отбрасывается вместо ложного «закончил»; после каждого вызова инструмента hook снова ставит «working», поэтому потерянный Start не портит статус; события Codex переводятся в имена событий Claude. POST в `host-service` — 2 секунды на подключение и 5 секунд всего. Пользователи всё же видели 10–14 секунд на событие при многих агентах.
   - Источники: [107][47][172].
5. **Передача сессии другому агенту.**
   - Что это: продолжение работы другим CLI-агентом в том же workspace.
   - Как работает: до 36 000 символов с пометкой «история только для чтения». Источники текста по порядку: хранилище сессий самого harness (реплики без вывода инструментов), повтор кольцевого буфера вывода на 2 MB, видимый экран. Новому агенту велят доверять workspace больше транскрипта и начать с `git status`. Перед отправкой показывается объём и предупреждение, что секреты не вычищаются. Предел взят у Orca; в Linux один аргумент командной строки ограничен 128 KB.
   - Источники: [45][109].
6. **Учёт запусков по расписанию ровно один раз и короткие token для dispatch.**
   - Что это: защита от двойных и «вечных» запусков automations.
   - Как работает: следующее время запуска вычисляется до постановки в очередь, поэтому триггер, который не может сдвинуться, не срабатывает на каждом тике. ID дедупликации — `<automationId>_<scheduledFor>`. Строка run вставляется с игнорированием конфликта и всегда закрывается как dispatched или `dispatch_failed` с кодом ошибки. Отдельный проход переотправляет потерянные события. Для запуска на удалённом хосте выпускается JWT одного пользователя на 300 секунд вместо общего секрета.
   - Источники: [118][119][117].
7. **Повтор хода без повторной отправки prompt (Devs на Temporal).**
   - Что это: устойчивость к сбоям провайдера модели.
   - Как работает: activity агента — timeout 2 часа и heartbeat раз в минуту; повторы с backoff от 5 секунд до 5 минут без предела попыток. Повтор продолжает сохранённую сессию `pdev` и никогда не отправляет prompt заново, поэтому сбой провайдера не теряет ход. Последние 500 ID prompts хранятся для дедупликации; сообщения во время хода вливаются в него как уточнения; workflow завершается после 10 минут простоя. Пока это только за feature flag.
   - Источники: [123][124].
8. **Учётные данные подставляются на выходе, а не хранятся у агента.**
   - Что это: агент в облачной машине не видит настоящих ключей.
   - Как работает: на машине лежат подставные значения; правило firewall на выходе подставляет настоящие учётные данные моделей и GitHub; терминалы получают CA-сертификат этого firewall. Тот же принцип в plugins: учётные данные запечатаны в API Paradev, а вызовы инструментов уходят из API. Признанные риски: посетитель действует на GitHub от имени создателя workspace; машина может дотянуться до приватных workspaces своего создателя.
   - Источники: [35][121][103][128].
9. **Узкие права по умолчанию в окружении агента.**
   - Что это: набор ограничений вокруг агента, кроме запросов прав.
   - Как работает: папка заранее помечается доверенной в Claude, Codex и Antigravity, только если её создал сам хост, и никогда — если там уже были файлы пользователя. Панели браузера агента живут в отдельной сессии без входов пользователя; CDP ограничен одной панелью, методы cookies запрещены; данные Design mode чистятся (только безопасные схемы URL, без query и hash, без строк, похожих на секреты). Хвост вывода в отчётах о падении чистится от секретов.
   - Источники: [104][129][130].
10. **Бюджет запросов к GitHub API.**
    - Что это: способ показывать состояние PR и CI для многих workspaces без исчерпания rate limit.
    - Как работает: условные запросы (ответ 304 не тратит лимит); кэш на 60 секунд для репозитория; состояние review, checks и merge queue кэшируется на каждый head PR; закэшированный отказ при повторных неудачах живёт вдвое дольше; пока GitHub недоступен, вызовы придерживаются, а после его возвращения обновляются все workspaces.
    - Источники: [126].
11. **Pages со следящим агентом.**
    - Что это: HTML-страница, которую публикует агент, а команда комментирует.
    - Как работает: каждая публикация — новая версия по той же ссылке; ссылка показывает последнюю или закреплённую версию. Комментарии прикрепляются к элементам страницы и печатаются в терминал следящего агента; он правит страницу, публикует заново и отвечает в thread. У страницы есть хранилище `window.superset.storage` с областями «одно значение на человека», личной и общей (до 20 MiB) и вызовы инструментов plugins от имени читателя после согласия.
    - Источники: [39][134].
12. **Метрики «The Production Run».**
    - Что это: способ измерять отдачу от параллельных агентов одним уровнем на человека.
    - Как работает: шесть величин, пять оцениваются: Width (параллельные сессии по 15-минутным интервалам), Depth (tokens на сессию), Output (слитые PR агентов), Sustain (активные дни), Cost (доллары на слитый PR, чем меньше, тем лучше). Уровень — минимум по осям, а не среднее. Пороги фиксированы заранее, прогноз датирован и публичен. Признанное ограничение: учитываются только PR на GitHub из workspaces Paradev.
    - Источники: [26][25][15].
