## Модель работы

- **Local, cloud или hybrid.**
  - Сегодня — local. `npx vibe-kanban` скачивает готовый бинарник, поднимает сервер на 127.0.0.1 и открывает
    интерфейс в браузере [21][68]. Порты задаются переменными PORT, BACKEND_PORT, FRONTEND_PORT, MCP_HOST и MCP_PORT
    [21].
  - Desktop-приложение сделано на Tauri v2 (фреймворк desktop-приложений на Rust с web-интерфейсом), id
    `ai.bloop.vibe-kanban`. Оно оборачивает тот же сервер и добавляет уведомления ОС и auto-update [66][55]. Запуск —
    установщиком или командой `npx vibe-kanban --desktop` [68].
  - Сервер можно поставить на другую машину. Docker-образ слушает 0.0.0.0, порт 3000 [77]. README советует доступ
    через tunnel (Cloudflare Tunnel, ngrok) и переменную `VK_ALLOWED_ORIGINS` для reverse proxy [21].
  - С февраля по апрель 2026 VK был hybrid. Issues, доска, организации и связи с PR хранились в облаке вендора
    (cloud.vibekanban.com, api.vibekanban.com). Workspaces оставались на машине каждого пользователя [2][3][14].
    Облачную часть можно было поднять у себя [35].
  - Remote Access (с 2026-02-28) даёт доступ к своей машине с другого устройства, в том числе с телефона. Связь идёт
    через relay вендора (сервер-посредник) или прямым соединением WebRTC. Сопряжение — через cloud.vibekanban.com
    [4][31][84 #3139]. Работает ли это после закрытия — не подтверждено.
- **Агенты и модели.**
  - Встроены 9 агентов: Claude Code, Codex, Gemini CLI, Amp, Cursor Agent, OpenCode, Qwen Code, GitHub Copilot,
    Factory Droid. Ещё есть общий executor (модуль запуска агента) для любого ACP-сервера [42]. ACP (Agent Client
    Protocol) — открытый стандарт, по которому приложение управляет coding-агентом. У каждого агента в документации
    своя страница [33].
  - С 2026-11-10 агентов можно ставить из публичного ACP registry — списка ACP-совместимых агентов [49][84 #3489].
  - CCR (Claude Code Router — сторонняя обёртка над Claude Code, которая направляет запросы к другим моделям) —
    опция executor-а Claude [45]. Провайдеры, совместимые с API Anthropic (Z.ai GLM, OpenRouter), подключаются
    переменными окружения в профиле агента [33].
  - Своего агентного цикла у VK нет. Он запускает CLI вендоров без их интерфейса и переводит их вывод в общий формат
    [42][51].
  - Модель выбирается в селекторе (с 2026-02-17) и в профиле агента. У Claude есть уровень effort: low, medium, high,
    xhigh, max [84 #2571][45].
- **Один пользователь или команда.**
  - Сегодня — один пользователь на своей машине. С нескольких устройств — через Remote Access [2][31][82].
  - С февраля по апрель 2026 были команды: организации с ролями, общие проекты, назначение issues, синхронизация в
    реальном времени, уведомления [3][34].
  - Сайт до сих пор описывает командные сценарии: агент работает по issue в фоне, worktree можно поднять из любого PR
    команды [1].
- **Платформы.**
  - Установщики v0.1.44: macOS .dmg (arm64, x64); Windows .msi и setup.exe (x64, arm64); Linux .deb и .AppImage
    (x64, arm64) [17].
  - Бинарники для `npx` — Linux, Windows и macOS на x64 и arm64 [68].
  - Мобильный браузер: есть полная мобильная раскладка [84 #2947].
  - Расширение для VS Code, Cursor и Windsurf [37].
  - Языки интерфейса: английский, французский, японский, испанский, корейский, китайский упрощённый и традиционный
    [78].

## Функции

Описание дано по коду и документации на коммите `5f06193` [16]. Сначала то, что работает сегодня. В конце — функции,
которые выведены из работы. «Ход» ниже — один ответ агента на одно сообщение (turn).

### Первый запуск

- **Выбор агента и редактора.** Стартовый экран спрашивает coding-агента и редактор [81].
- **Предупреждение о безопасности.** Тот же экран сообщает, что агенты по умолчанию работают без проверки разрешений,
  и сохраняет согласие пользователя [81]. Сбросить согласие можно в Settings → Safety & Disclaimers [78].
- **Вход — по желанию.** Страница входа объясняет: аккаунт нужен для Kanban, приглашений в команду, проектов и
  организаций. Workspaces работают и без него [81].
- **Тур по интерфейсу.** Показывает command bar, context bar, sidebar, multi-repo, sessions, preview и diff с
  комментариями [78].

### Workspace — единица работы

- **Что это.** Workspace — одна задача. В нём на каждый репозиторий своя ветка и свой worktree, терминал, dev servers
  и одна или несколько sessions с агентами [21][25]. Workspace можно связать с issue. У одного issue может быть
  несколько workspaces [24].
- **Создание.** Пользователь выбирает репозитории (недавние, через обзор диска или новый), целевую ветку для каждого,
  описывает задачу и выбирает агента и вариант его настроек [25]. Ветка называется `<префикс>/<id>-<slug>`, префикс по
  умолчанию — `vk` [78]. В коде это `vk/<короткий uuid>-<slug до 16 символов>` [59].
- **Несколько репозиториев.** В workspace по папке на репозиторий [25]. В корне workspace генерируются CLAUDE.md и
  AGENTS.md. Они через `@` импортируют файлы каждого репозитория, например `@repo/CLAUDE.md` [84 #1614][56].
- **Скрипты и файлы репозитория** [78][32]:
  - setup — подготовка; по желанию идёт параллельно с агентом;
  - cleanup — после запуска агента, только если файлы изменились; для lint, format и tests;
  - archive — при архивировании workspace;
  - dev server;
  - copy files — glob-шаблоны вроде `.env`. Эти неотслеживаемые файлы копируются из основного checkout в каждый новый
    worktree, timeout — 30 секунд [56];
  - рабочая папка и целевая ветка по умолчанию.
  - Документация и код расходятся. Документация говорит, что cleanup запускается при закрытии workspace. Код
    запускает его после каждого хода агента, который изменил файлы [32][54][56].
- **Auto-commit.** После каждого успешного запуска агента VK делает коммит. Сообщение коммита — итог агента, то есть
  его последнее сообщение, до 4096 символов. Затем запускается cleanup, и его изменения коммитятся отдельно [56].
  Отключить auto-commit нельзя. Запрос на это открыт [85 #2739].
- **Commit reminder.** Отдельная настройка: VK напоминает агенту закоммитить изменения. По умолчанию включена
  [63][78][46].
- **Действия с workspace** [79][25]:
  - duplicate, rename, pin, archive;
  - delete, по желанию вместе с веткой;
  - notes — заметки к workspace;
  - spin-off — дочерний workspace, целевая ветка которого — ветка родителя [84 #2269];
  - workspace из открытого PR [84 #2201];
  - привязка существующего PR.
- **Жизненный цикл worktree.**
  - Worktree удаляется через 72 часа после последнего использования или через 1 час после архивирования. Ветка
    остаётся. Пока идёт процесс, worktree не удаляется [57].
  - Очистка запускается каждые 30 минут. При старте ищутся брошенные worktree [56].
  - Удалённый worktree пересоздаётся из ветки, когда он снова нужен [59].
  - Переменная `DISABLE_WORKTREE_CLEANUP` отключает очистку [21].
  - Пользователи пишут о другом. У одного за два дня накопилось 26 GB worktrees [85 #765]. По другим отзывам, очистка
    иногда удаляла активные worktree, а пересоздание заново запускало setup и ломало `node_modules` [91 #2335]. Это
    расходится с правилом в коде «не удалять, пока идёт процесс» [57]. Относятся ли отзывы к старым версиям — не
    подтверждено.
- **Где лежат worktree.** На macOS — `$TMPDIR/vibe-kanban/worktrees`, на Linux — `/var/tmp/vibe-kanban/worktrees`.
  Если папка задана в настройках — `<папка>/.vibe-kanban-workspaces` [25][32][59].
- **PR monitor.** Раз в 60 секунд проверяет открытые PR. Когда все PR workspace слиты или закрыты, workspace
  архивируется, если он не закреплён. При этом останавливаются dev servers и запускается archive-скрипт [60][54].

### Раскладка экрана

- **Четыре панели** [26][80]:
  - список workspaces (sidebar);
  - чат;
  - панель контекста: changes, logs, preview;
  - панель деталей: git, терминал, notes.
  - Раскладка сохраняется для каждого workspace [26]. Есть полная мобильная раскладка [84 #2947].
- **Строка workspace в sidebar** показывает [62][80]:
  - статус: Needs Attention, Running, Idle;
  - непросмотренные ходы агента;
  - запущенный dev server;
  - номер и состояние PR;
  - число изменённых файлов и строк (+/−);
  - ожидающий approval.
- **Поиск и фильтры.** Поиск по имени или ветке. Фильтр по проекту или по наличию PR. Сортировка по дате создания
  или изменения [80].

### Чат и sessions

- **Поле ввода.**
  - Форматированный текст. Картинки и любые вложения, в том числе во время работы агента [84 #3129, #3094]. Вложения
    лежат в папке `.vibe-attachments` [59].
  - Упоминания файлов через `@`. Tags — сохранённые фрагменты prompt, вставляются через `@имя` [26][32]. MCP server
    VK тоже раскрывает `@tag` в тексте [64].
  - Отправка по Enter или по Cmd+Enter, как настроено [78].
- **Во время работы агента.**
  - Кнопка Stop.
  - Очередь из одного follow-up сообщения. Оно уходит, только если текущий запуск успешен. При ошибке или остановке
    сообщение выбрасывается [56][69]. Очередь хранится в памяти, одна на session [69].
- **Правка истории.**
  - Edit & Retry — правка сообщения с fork session [26].
  - Reset to This Point — откат к выбранному месту разговора [84 #2483].
  - Popover для перехода между ходами [84 #3233].
- **Что видно в ленте.** Прогресс todo, статистика изменений файлов, shell-команды с exit code, вывод MCP-инструментов
  [26].
- **Context gauge** — индикатор заполнения контекстного окна. Серый ниже 30%, оранжевый от 60%, красный от 80% [26].
  Для Claude окно считается равным 200k токенов, пока запуск не сообщит точное значение [45].
- **Slash commands.** Список команд берётся у каждого агента и кэшируется на workspace. Команды, которые работают
  только в терминальном интерфейсе агента, не поддерживаются [26].
- **Несколько sessions в workspace**, в том числе с разными агентами. Они делят файлы, но не контекст. Документация
  предупреждает: при одновременной правке остаётся последняя запись [26]. Переименование sessions появилось
  2026-03-16 [84 #3144], хотя документация говорит, что переименовать session нельзя [26].
- **Вопросы агента.** Инструмент вопросов пользователю у Claude Code и OpenCode показывается как форма в интерфейсе
  [84 #2834]. Ответы записываются обратно во входные данные инструмента, в поле `answers` [46].

### Approvals (запросы разрешений)

- **Политика на каждый запуск:** Auto — по умолчанию, проверок нет; Supervised — действия идут через человека; Plan —
  сначала план [44].
- **Карточка approval.** Кнопки Approve и Deny с причиной. В поле причины работают @-упоминания [80]. Виден обратный
  отсчёт до timeout — 10 часов [53][80].
- **Одобрение плана** с возможностью попросить изменения [26].
- **Уведомления ОС** «Approval Needed» и «Question Asked» [55][53].

### Review

- **Панель Changes** [27]:
  - дерево файлов с поиском;
  - unified или side-by-side;
  - перенос строк, игнор пробелов, сворачивание.
  - Очень большие diff (300+ файлов) рендерятся виртуализированно [84 #3248]. Markdown-файлы можно смотреть как
    preview прямо в diff [84 #3125]. Diff обновляется вживую по file watcher [75].
- **Комментарии к строкам diff.** Комментарий несёт текст строки [84 #2449]. Комментарии копятся и уходят со
  следующим сообщением в чат [27]. Агент получает их одним Markdown-блоком `## Review Comments (N)`: файл, строка,
  цитата кода и текст комментария [83][27].
- **Комментарии с GitHub.** Review-комментарии, которые уже есть на GitHub, видны в diff. Их можно добавить в ту же
  пачку [84 #2195][83].
- **Start Review.** Запускает агента-reviewer-а в новой или текущей session, с дополнительными инструкциями
  [84 #1849]. Prompt — просьба проверить изменения плюс `git diff <точка ответвления>..HEAD` по каждому репозиторию
  [50]. Codex использует свой режим review [42][47].
- **Облачный review через GitHub App (декабрь 2025 — февраль 2026).** Запускался при открытии PR или комментарием
  `!reviewfast`. Письма приходили, когда review готов или упал [84 #1521][67]. Отключён 2026-02-11 [84 #2693].
  Насколько полно отключён — не подтверждено: у PR нет описания.
- **CLI `vibe-kanban review <URL PR>`** (сервис review.fast) [65]:
  - загружает код PR на сервер вендора (api.vibekanban.com) и возвращает сводку изменений в виде связного рассказа
    для reviewer-а;
  - может приложить session Claude Code, выбранную из `~/.claude/projects`;
  - данные удаляются через 14 дней.
  - Сайт review.fast открыт и называет авторами команду VK. Бесплатен ли он — не подтверждено [15]. Работает ли CLI
    сейчас — не подтверждено.

### Git и PR

- **Панель git:** ahead/behind, конфликты, число незакоммиченных изменений [28].
- **Create PR:** заголовок, базовая ветка, флаг draft [28].
- **AI-описание PR.** После создания PR агент переписывает заголовок и описание по prompt из настроек, с подстановками
  `{pr_number}` и `{pr_url}` [63]. Prompt по умолчанию добавляет к заголовку суффикс «(Vibe Kanban)», а в описание —
  строку о том, что PR написан с VK [63]. В репозитории самого VK такой суффикс несут 493 из 1873 коммитов, не считая
  коммитов смены версии [19].
- **Провайдеры.** GitHub — через CLI `gh`. На macOS `gh` ставится через Homebrew. Поддерживаются GitHub Enterprise и
  SSH-алиасы [28][84 #1783]. Azure Repos — через CLI `az` [28][60].
- **Операции с веткой:** rebase, смена целевой ветки, push [79].
- **Конфликты.** Диалог передаёт конфликт в текущую или новую session агента [80]. Сгенерированный prompt перечисляет
  до 12 файлов с конфликтами и просит агента выставить `GIT_EDITOR=true` [83][40].
- **Merge** — локальный squash merge (все коммиты ветки одним коммитом) в целевую ветку [61]. Merge блокируется, если
  [61]:
  - открыт PR;
  - целевая ветка — удалённая;
  - целевая ветка ушла вперёд;
  - в checkout целевой ветки есть staged-изменения.
  - После merge ветка задачи переставляется на squash-коммит [61]. Документация описывает обратное направление: что
    merge подтягивает целевую ветку в рабочую [28].
- **Состояние PR** — только open, merged, closed или unknown. Статуса CI и checks нет нигде [60].

### Агенты, профили, модели

- **Variants (профили).** У каждого агента есть именованные наборы настроек. Их можно править как JSON [32][78].
  Встроенные значения сливаются с пользовательским `profiles.json` [43].
- **Что есть в профиле:** модель, effort (low, medium, high, xhigh, max), subagent, текст, дописываемый к prompt,
  переменные окружения, дополнительные аргументы [45]. Профиль может заменить базовую команду запуска [43].
- **Вариант DEFAULT у каждого агента отключает проверку разрешений** [43]: Claude — skip-permissions; Codex — sandbox
  `danger-full-access`; Gemini и Qwen — yolo; Amp — allow-all; Copilot — allow-all-tools; Droid —
  skip-permissions-unsafe; Cursor — force; OpenCode — auto-approve.
- **Настройки отдельных агентов.**
  - Codex: режим sandbox, approval policy (untrusted, on-failure, on-request, never), reasoning effort, стиль summary
    [33][47].
  - Droid: уровень autonomy и уровень reasoning [33].
  - CCR: строки `provider,model` и классы маршрутов background, think, longContext, webSearch, image [33].
- **Флаги возможностей агентов** [42]:
  - fork session — Claude, OpenCode, Codex, Gemini, Qwen;
  - отчёт о заполнении контекста — Claude, OpenCode, Codex;
  - помощник входа внутри приложения — Codex, Cursor, Copilot.
- **Вход в Copilot** по device code (код вводится на другом устройстве) — с 2026-11-11 [84 #3498].
- **ACP registry** (с 2026-11-10) [49][84 #3489]:
  - агентов из registry ставят и запускают в Settings;
  - берутся только сборки, которые распространяются через npx;
  - список кэшируется, timeout загрузки — 5 секунд, копия лежит на диске для работы offline;
  - встроенные агенты в списке скрыты.
  - На запрос разрешения от ACP-агента VK отвечает «allow once». «Allow always» он выбирает, только если варианта
    «allow once» нет [49]. Так работает новый ACP-harness — у агентов из registry и у Copilot. Старый harness Gemini
    и Qwen при автоодобрении без approvals сначала выбирает «allow always» [49].
  - Список моделей, режимы и разрешения задаются через ACP вживую. Первым это получил Copilot [84 #3496]. До
    исправления 2026-10-28 Copilot игнорировал политику Supervised [84 #3487].
- **Как VK узнаёт, что агент залогинен:** по времени изменения конфиг-файлов — `~/.claude.json` для Claude,
  `~/.codex/auth.json` для Codex [45][47].
- **Показ расхода.** Только в двух местах [47][26]:
  - команда Codex `/status`: токены, контекстное окно и rate limits — план, процент использования основного и
    дополнительного лимитов, credits;
  - context gauge в каждом чате.

### MCP

- **VK как MCP server.** Транспорт stdio, команда `npx vibe-kanban --mcp` [36][68]. 34 инструмента [64]:
  - организации, участники, проекты, issues, tags и связи между issues;
  - репозитории и правка их скриптов;
  - workspaces: `start_workspace` с executor, репозиториями и веткой, по желанию с prompt и issue;
  - sessions: `create_session`, `run_session_prompt`, `get_execution`.
  - Клиенты, которые называет документация: Claude Desktop, Raycast и агенты внутри VK [36]. Агент внутри VK может так
    запускать новые workspaces [36][64].
  - Агенты получают в окружении `VK_SESSION_ID` [84 #2385], а также `VK_WORKSPACE_ID` и `VK_WORKSPACE_BRANCH` [54].
- **Планирование через MCP.** Документация советует обсудить план в чате любого MCP-клиента и попросить агента
  превратить план в issues через MCP [36].
- **Orchestrator mode** — режим MCP server для агента, который раздаёт работу (`vibe-kanban-mcp --mode orchestrator`,
  2026-03-07/08) [64][84 #3065][19]:
  - инструментов меньше: `get_context`, `update_workspace`, `create_session`, `list_sessions`, `update_session`,
    `run_session_prompt` (возвращает ответ сразу) и `get_execution` (результат опрашивается);
  - каждый вызов проверяется на принадлежность к workspace самого агента;
  - «orchestrator session» — просто первая созданная session, по «временной политике». Запускать coding-агента внутри
    себя она не может;
  - в PR режим описан как заготовка под будущего orchestrator-агента [84 #3065]. Интерфейса и документации к нему
    исследование не нашло.
- **VK как менеджер MCP-конфигов.** VK пишет MCP-конфиг прямо в собственный конфиг-файл каждого агента. Файлы JSONC и
  TOML правятся с сохранением комментариев [32][52]. Пресеты в один клик: сам VK, Context7, Playwright, Exa, Chrome
  DevTools, Dev Manager [52].

### Remote Access

- **Сопряжение** [31][78][4]. Host показывает pairing code, для этого нужен вход. На другом устройстве пользователь
  входит на cloud.vibekanban.com, привязывает host и вводит код. После этого он управляет workspaces этого host, в том
  числе с телефона.
- **Транспорт** [84 #3023, #3139][73]:
  - relay поверх WebSocket и yamux (несколько потоков в одном соединении), отдельный поддомен на каждый host;
  - прямое соединение WebRTC с откатом на relay;
  - встроенный SSH/SFTP-сервер, чтобы open in IDE работал через relay;
  - preview proxy.
- **Модель безопасности** [4][72][73]. Host привязан к одной сессии браузера. Каждый запрос подписывается в браузере
  ключом Ed25519 и проверяется на host. Вендор называет это zero trust и признаёт, что это закрывает не все атаки. Bug
  bounty — до $5000 [4][38].
- **Страница Security** [11]: TLS 1.2+, шифрование данных на диске, OAuth 2.0 с PKCE, сессии с подписью Ed25519,
  audit logs за 90 дней, сертификатов нет. Адрес для сообщений об уязвимостях расходится: security@bloop.com в
  документации и security@vibekanban.com на странице Security [38][11].

### Self-hosting

- **Сервер в Docker** — HOST 0.0.0.0, порт 3000 [77]. Доступ через tunnel, `VK_ALLOWED_ORIGINS` — для reverse proxy
  [21].
- **Облако у себя** через Docker Compose [35]:
  - Caddy;
  - Postgres 16 с logical WAL;
  - ElectricSQL 1.4.13 — синхронизация Postgres с клиентами;
  - remote server на порту 8081;
  - по желанию relay на порту 8082, ему нужны wildcard DNS и TLS.
  - Вход — GitHub или Google OAuth, или один локальный администратор. Email (Loops) и вложения в Azure Blob — по
    желанию.
  - Требования: от 2 GB RAM (рекомендуется 4 GB) и 10 GB диска. Первая сборка — 10–15 минут. Backup — `pg_dump`.
  - v0.1.44 включил режим «только экспорт» и на self-hosted серверах [85 #3396].

## Принципы и подходы

### Философия

- **AI-лаборатории забирают прикладной слой.** 2025-06-01, за две недели до создания репозитория, Louis Knight-Webb
  написал: модели и собственные CLI лабораторий уже делают то, что раньше делали инструменты, — структурированный
  вывод, приёмы prompt, многошаговые циклы кодинга и самопроверку. Его совет авторам инструментов: не собирать цепочки
  вызовов модели, а давать высокоуровневые цели CLI лабораторий [8].
- **VK сделан по этой идее.** Документация прямо говорит, что VK сам не coding-агент. Он управляет Claude Code, Codex,
  Gemini CLI, OpenCode и другими [23][21].
- **Узкое место — планирование и review человеком.** В посте Launch YC основатели пишут, что агенты пишут больше
  половины их собственного кода. Значит, скорость выпуска ограничена тем, как быстро человек планирует и проверяет.
  Время на наблюдение за агентами теряется [107][106].
  - То же сказано в README, на главной странице документации, в приветствии Discussions от 2025-10-03, в заголовке
    сайта и в описании на YC [21][23][91 #921][1][106].
  - 2026-02-19 Louis повторил цель: сделать планирование и review работы агентов как можно быстрее [85 #2288].
- **Без привязки к одному агенту.** Сайт обещает пробовать других агентов, не меняя процесс работы, потому что лучший
  агент постоянно меняется [1].
  - Агентов добавляли быстро: Amp — 2025-06-18, Gemini — 06-25, OpenCode — 06-27, CCR — 07-16, Codex — 07-24, Qwen —
    08-12, Cursor CLI — 08-13, Droid — 11-20 [19].
  - ACP внедряли по шагам. Gemini перешёл на ACP в сентябре 2025, OpenCode — в декабре 2025. В ноябре 2026 появился
    весь ACP registry [19][84 #3489]. Registry ответил на запрос поддержать любой ACP-клиент (8 голосов) [90].
- **Границы держит человек.** Каждый workspace — worktree на новой ветке. По документации, ничего не уходит в push,
  пока пользователь не создаст PR, и агент не может сделать push или merge без явного действия пользователя [24]. При
  этом по умолчанию агенты работают без проверки разрешений и без sandbox [43][56]. Как в такой конфигурации
  соблюдается запрет на push, в материалах не описано (не подтверждено).
- **Цикл review.** Пользователь оставляет комментарии к строкам diff. Они копятся и уходят со следующим сообщением.
  Цикл повторяется, пока результат не устроит [27]. Заголовок и описание issue становятся prompt агента [34][36].

### Метод Louis Knight-Webb (Vibe Guide, без даты) [12]

- Сначала план, даже для маленьких задач. Проверить план дешевле, чем diff. Ранний план важен: агенты склонны
  дорабатывать первую рабочую версию, а не переосмысливать её.
- Если план требует большой переделки, начать новую session с итогом того, что выяснили. Не накапливать замечания в
  старой session.
- Запускать агентов в фоне надолго и с минимумом approvals: пропускать проверку разрешений или разрешать широкий
  список команд.
- Брать самую сильную модель на максимальном effort. Главная метрика, по словам автора: «The metric that matters is
  how often you have to intervene» — как часто приходится вмешиваться [12].
- Делать код проверяемым самими агентами. Frontend всё равно должен посмотреть человек.
- Использовать реалистичные seed-данные, чтобы параллельные агенты не делили одну базу.
- Отдать dev servers в Dev Manager MCP: он раздаёт порты и останавливает зависшие серверы.
- Просить агентов не сохранять обратную совместимость и не отключать правила lint комментариями.
- Листовые UI-компоненты — только отображение. Данные и логика — в родительских компонентах.

### Инженерные принципы из блога вендора

- **Один мощный host на всех агентов** вместо маленькой VM на каждого [4]. Агенты собирают и тестируют, им нужно
  сильное железо. Один только Rust-backend VK собирается на хорошем MacBook больше 5 минут. Простаивающие Mac можно
  сделать host-ами. Планировались headless host-ы на арендованных серверах.
- **Zero trust для удалённого доступа** [4]. Host привязан к одной сессии браузера, а не к backend bloop. Каждое
  действие подписывается в браузере и проверяется на host. Поэтому backend вендора не может слать команды машинам
  клиентов.
- **Хранить данные в форме, которая им подходит** [5]. Logs агентов занимали около 98% базы SQLite и вызывали ошибки
  «database is locked». WAL (write-ahead logging, режим журнала SQLite) не подходил: он ломал их синхронизацию на
  pre-update hooks. Logs переехали в JSONL-файлы. База сжалась с гигабайтов до ~20 MiB, ошибки блокировок прекратились.
- **QA агентами в браузере пока ненадёжен** (Britannio Jarrett, 2025-11-27) [6]. Один thread агента обошёлся в $103:
  91 вызов Playwright MCP за 14 ходов. Агенты не открывают браузер без прямой просьбы и рано объявляют успех. Помогли
  явные правила для агентов, управляемые dev servers, subagents для экономии контекста, worktrees и headless-браузеры.
- **Пусть модель решает так, как её учили** (Alex Netsch, 2025-07-10) [7]. 71.14% на SWE-bench Verified с Claude 4
  Sonnet только с bash и инструментом правки файлов. В среднем меньше 19 шагов на задачу против 40+ у других агентов.
  Свои инструменты отладчика и «критики» на o3 ничего не добавили.
- **Противоречие в позиции вендора.** 2026-02-16 Louis объяснял переход в облако ставкой: скоро большинство компаний
  потребует облачные sandbox ради безопасности [85 #2687]. Через 12 дней пост о Remote Access доказывал, что всех
  агентов надо запускать на одном большом host [4].

### Чем подход отличается

- **Главное — цикл человека: план, prompt, review.** Агенты взаимозаменяемы [1][21].
- **Планирования между задачами нет.** В коде цепочка действий есть только внутри одного workspace: setup, затем
  агент, затем cleanup [54]. Запросы на циклы агента, периодические prompt и зависимости issues остались без ответа
  maintainer-ов [85 #1946, #3039, #1700, #1848].
- **Push и merge — за человеком** [24].
- **Слой планирования** — доска Kanban (выведена) и внешний MCP-клиент, который превращает план в issues [36].
  Orchestrator mode для MCP server сделали, а orchestrator-агента, который бы им пользовался, не выпустили
  [64][91 #3424].
- **Удалённый доступ** — через hosted relay с прямым WebRTC и подписанными запросами, с расчётом на телефон [4][19].
- **Тактика роста.** По умолчанию — суффикс «(Vibe Kanban)» в заголовке PR и строка о VK в описании [63][19]. На сайте
  — отзывы людей из ElevenLabs, T3, Google и других [1]. Bug bounty до $5000 [4].
- **Open core** — открыт весь код, кроме платной части. Облачный сервер — open source, а биллинг — закрытый crate,
  вырезанный из публичных сборок [67].

### Цикл агента

- **Своего цикла нет.** VK запускает CLI вендора без его интерфейса и переводит протокол этого CLI в общий формат
  [42].
- **Один trait на всех агентов.** `StandardCodingAgentExecutor` описывает [42]:
  - `spawn` и `spawn_follow_up(session_id, reset_to_message_id)`;
  - `spawn_review`;
  - `normalize_logs`;
  - путь к MCP-конфигу агента;
  - проверку доступности;
  - `discover_options`.
- **Claude Code** [45][46]:
  - команда: `npx -y @anthropic-ai/claude-code@2.1.119 -p --verbose --output-format=stream-json
    --input-format=stream-json --include-partial-messages --replay-user-messages` плюс флаги модели, effort и agent.
    stream-json — режим, где ввод и вывод идут потоком JSON-сообщений;
  - CCR заменяет базовую команду на `@musistudio/claude-code-router`;
  - VK работает как вторая сторона control protocol Claude Code: шлёт `initialize` с hook callbacks, которые
    регистрирует; шлёт `set_permission_mode`; шлёт prompt; перестаёт читать на сообщении `result`;
  - отмена — interrupt;
  - follow-up — `--resume <id>`. «Retry from here» добавляет `--resume-session-at <uuid сообщения>`.
- **Codex** [47][56]:
  - команда: `npx -y @openai/codex@0.124.0 app-server`, общение по JSON-RPC: `thread/start`, затем `turn/start`;
  - follow-up делает fork предыдущего thread (`thread/fork`), а не продолжает его;
  - app-server сам не завершается. Executor сигналит «готово», и VK убивает группу процессов.
- **Остальные агенты** [48]:
  - Gemini (`--experimental-acp`), Qwen (`--acp`) и Copilot (`--acp`, пакет из ACP registry) говорят по ACP;
  - OpenCode запускается как `serve` на 127.0.0.1 со сгенерированным паролем. VK читает его поток SSE (server-sent
    events) и переподключается с backoff: база 3 секунды, 20 попыток;
  - Amp, Cursor (`cursor-agent` из PATH) и Droid (`droid exec`) работают в режимах stream-JSON командной строки.
- **Закреплённые версии:** Claude Code 2.1.119, Codex 0.124.0, Gemini 0.29.3, Qwen 0.9.1, OpenCode 1.4.7. Amp — всегда
  `@latest` [45][47][48].
  - Copilot: VK больше не закрепляет версию сам. Точную версию пакета даёт запись в ACP registry, поэтому npx
    запускает пакет из своего кэша без запроса к npm и работает offline. Если записи в registry нет, запускается
    `npx -y @github/copilot --acp` без версии. npm-пакет Copilot — только launcher: CLI сам скачивает свою последнюю
    версию [84 #3497].
- **Общая схема событий** [51]. Нормализатор каждого агента превращает вывод в записи `NormalizedEntry` и шлёт их как
  JSON Patch (формат описания изменений JSON-документа). Типы записей:
  - сообщения пользователя и ассистента;
  - вызовы инструментов с типом: чтение или правка файла, запуск команды, поиск, загрузка из web, subtask, план,
    todo-список, вопрос пользователю;
  - thinking;
  - ошибки;
  - расход токенов;
  - «следующее действие».
- **Цепочка действий** [50]. Каждый `ExecutorAction` — это первый запрос агенту, follow-up, скрипт (setup, cleanup,
  archive, dev server, установка инструмента) или запрос review. У каждого есть необязательный `next_action`.
  Получается связный список.
- **Старт workspace** [54]:
  1. создать worktrees;
  2. создать session;
  3. собрать действие агента с cleanup в `next_action`;
  4. если у всех репозиториев setup помечен параллельным, запустить все setup и агента сразу; иначе — цепочкой setup,
     setup, …, агент.
- **Каждый запуск** [54][56]:
  - записывает HEAD каждого репозитория;
  - создаёт строку процесса и строку хода с prompt;
  - должен стартовать за 30 секунд;
  - получает в окружении `VK_WORKSPACE_ID` и `VK_WORKSPACE_BRANCH`;
  - пишет logs в JSONL-файл.
- **Монитор завершения** [56][19]. Ждёт выхода процесса ОС (опрос каждые 250 мс) или сигнала «готово» от executor.
  Затем:
  1. ставит статус и exit code;
  2. сохраняет последнее сообщение ассистента (до 4096 символов) как итог хода;
  3. при успехе делает коммит во всех репозиториях с изменениями, с итогом в сообщении коммита;
  4. запускает следующее действие, только если агент что-то изменил; иначе cleanup пропускается;
  5. записывает HEAD после запуска;
  6. убивает всё, что осталось в группе процессов, например MCP servers. С 2026-04-03 группы процессов убираются и при
     обычном выходе [19].
- **Когда запуск считается законченным** [54]:
  - dev server — никогда;
  - параллельные setup — нет;
  - failed и killed — всегда;
  - остальное — когда нет следующего действия.
  - По завершении приходит уведомление «Workspace Complete» с отметкой успеха или ошибки. Если запуск остановил сам
    пользователь, уведомления нет.
- **Очередь follow-up** [56][69]. Одно сообщение на session, в памяти. Уходит после успешного запуска, выбрасывается
  после ошибки или остановки. Законченный ход помечается непросмотренным.

### Параллельность и координация

- **Общего лимита параллельных запусков нет** — по крайней мере, исследование его не нашло. Каждый запуск — своя
  группа процессов [54][56].
- **Sessions одного workspace** делят файлы, но не историю, и могут работать одновременно [26]. Review и setup не
  стартуют, пока в workspace идёт другой процесс, кроме dev server [69].
- **Координации между workspaces нет.** Нет планировщика, зависимостей и очереди задач между workspaces [54]. Запрос
  запускать задачу в момент сброса лимита закрыт как «not planned» 2025-12-28 [85 #1638]. Запрос на зависимости и
  триггеры открыт [85 #1700].
- **Агент может запустить другой workspace** через MCP (`start_workspace`) [36][64]. Orchestrator mode ограничивает
  такого агента его собственным workspace [64].
- **Orchestrator-агента** команда сделала внутри, но не выпустила (Louis, 2026-06-07) [91 #3424].

### Изоляция

- **Только git.** Папка workspace — `<короткий uuid>-<slug>`, по worktree на репозиторий [59]. Container или VM
  sandbox нет: агенты работают под пользователем прямо на host [56][43].
- **Создание worktree** [59]:
  - глобальная блокировка на путь;
  - git CLI, поэтому sparse checkout учитывается;
  - при ошибке чистятся метаданные worktree в git и делается одна повторная попытка;
  - multi-repo workspace откатывается целиком, если упал хоть один репозиторий.
- **Конфликты портов.** Документация объясняет, как чинить их вручную [30]. В опытах с QA в браузере вендор отдал dev
  servers в dev-manager-mcp, который раздаёт порты и останавливает простаивающие серверы [6].
- **Столкновения параллельных агентов** (вторичный источник — пост автора набора hooks bulkhead) [91 #3502]. Один
  агент убивает dev servers других (`pkill node`). Двое спорят за порт 3000. Параллельные сборки съедают всю RAM.
  bulkhead — PreToolUse hooks, которые это блокируют.
- **Агент вне worktree.** Агент правил основной репозиторий через настройку проекта Serena MCP. Команда ответила, что
  это не баг VK [85 #2401]. Merge однажды стёр незакоммиченные изменения отслеживаемых файлов в основном checkout.
  Исправлено в v0.0.66 [85 #543].
- **Основатель за один host.** Louis предлагал запускать всех агентов на одной большой машине, а не по VM на агента [4].

### Состояние и память

- **Модель данных** [57][58]:
  - Workspace: ветка, папка, archived, pinned, `worktree_deleted`;
  - WorkspaceRepo: репозиторий и его целевая ветка;
  - Session: executor, имя, рабочая папка агента;
  - ExecutionProcess: причина запуска (setup, cleanup или archive script, агент, dev server), статус (running,
    completed, failed, killed), действие как JSON, флаг `dropped`;
  - CodingAgentTurn: id session агента, prompt, итог;
  - для каждого процесса и репозитория — HEAD до запуска, после запуска и при merge.
- **Рефакторинг декабря 2025** [58]: `task_attempts` → `workspaces`; новая таблица `sessions`; `execution_processes`
  принадлежат sessions; `executor_sessions` → `coding_agent_turns`. Таблица `pull_requests` — с марта 2026.
- **Настройки репозитория** [57]: setup, cleanup, archive и dev-server скрипты; флаг параллельного setup; glob-шаблоны
  `copy_files`; целевая ветка и рабочая папка по умолчанию.
- **Logs** [70][5]. Сырой вывод и нормализованные patches идут в кольцевой буфер в памяти `MsgStore` — около 100 MB на
  процесс. Одновременно они дописываются в файл `<app-data>/sessions/<2 символа>/<session>/processes/<process>.jsonl`.
  При показе истории сохранённый сырой log нормализуется заново, дубликаты patches отбрасываются [54][70].
- **Доставка изменений в интерфейс** [71][70]. SQLite pre-update и update hooks превращают изменения строк в сообщения
  JSON Patch в одном потоке событий. Logs, diff и approvals идут каждый по своему WebSocket.
- **Живой diff** [75]:
  - file watcher с учётом `.gitignore`: рекурсивный на macOS и Windows, по watch на каждую папку в Linux;
  - следит и за `.git/HEAD`, чтобы заметить новые коммиты;
  - поток останавливается после 200 MB diff.
- **Памяти между sessions нет.** Новая session начинается с чистым контекстом. Документация советует начинать новую,
  когда context gauge стал оранжевым или красным [26].
- **Источники контекста:** текст issue [64]; tags [32]; вложения [56]; сгенерированные CLAUDE.md и AGENTS.md [56];
  комментарии review [83]; рабочая папка session [57]. Инструмент MCP `get_context` возвращает workspace, репозитории,
  целевые ветки и связанное issue [64].
- **MCP-каталог** [52]. Встроенные записи: vibe_kanban, context7, playwright, exa, chrome-devtools, dev-manager. VK
  пишет их в глобальный конфиг каждого агента.
- **Облако (выведено)** [67]. Postgres реплицировался клиентам через «shapes» ElectricSQL — подмножества таблиц,
  которые клиент держит у себя. Запись шла через REST API с возвратом номера транзакции.

### Проверка качества

- **Нет встроенного test gate и нет статуса CI.** Код, который читает результаты CI checks, не найден. Обёртка над `gh`
  только создаёт, показывает и перечисляет PR, читает комментарии и делает checkout PR [60].
- **Что есть:**
  1. **Commit reminder** (включён по умолчанию) [46][47][63]. Для Claude — Stop hook: он один раз блокирует
     остановку, пока в репозиториях есть незакоммиченные изменения, и цитирует `git status`. Флаг `stop_hook_active`
     не даёт зациклиться. Для Codex — одно дополнительное сообщение пользователя на событии `turn/completed`.
  2. **Cleanup-скрипт после каждого хода, который изменил файлы** [32][54][56]. Документация советует formatters и
     linters, например `cargo fmt && cargo clippy --fix`.
  3. **Запуск review** [50][47][69]. Prompt с просьбой проверить изменения и `git diff <точка ответвления>..HEAD` по
     каждому репозиторию. По желанию — продолжение session агента. У Codex — свой режим review: fork thread и
     `ReviewTarget::Custom`.
  4. **Review человеком** в панели diff [27].
- **Безопасность merge** [61]. В `git_ops_safety.rs` 29 tests. Например, merge не должен перезаписывать
  неотслеживаемые файлы, а конфликт не должен двигать refs. Merge идёт через git CLI там, где целевая ветка в
  checkout. В остальных случаях — через libgit2, только по refs.

### Восстановление после сбоев

- **После перезапуска** строки «running» становятся Failed, записывается коммит «после». Прерванные запуски не
  продолжаются [54][74].
- **Ошибка старта.** После timeout 30 секунд запуск помечается failed со строкой ошибки. Если программы нет,
  появляется запись «SetupRequired». По ней интерфейс показывает кнопку входа [54][56][51].
- **Остановка запуска** [56]:
  1. отмена через cancellation token (для Claude — interrupt);
  2. 5 секунд ожидания;
  3. kill группы процессов;
  4. до 5 секунд на сброс logs.
- **Пропавший worktree** пересоздаётся перед follow-up или review [56][59].
- **Автоматического retry нет** — ни для упавших запусков, ни для ошибок API. Retry — вручную [54][69]. Единственный
  backoff — переподключение к потоку OpenCode [48]. Сообщение в очереди выбрасывается, если запуск упал [56].
- **Retry с выбранного сообщения** [54][69][45]:
  1. hard reset каждого репозитория к коммиту «до» этого запуска; грязный worktree пропускается, если не указано force;
  2. остановка работающих процессов;
  3. более поздние процессы помечаются dropped;
  4. Claude продолжается с uuid этого сообщения.
  - Открытый баг: retry не сбрасывает планы Claude [85 #1398].

### Лимиты и стоимость

- **Под лимиты ничего не планируется.** События Claude `rate_limit_event` разбираются и выбрасываются. В интерфейс
  ничего не попадает [45]. Лимиты Codex видны только в его `/status` [47]. Context gauge питается записями о расходе
  токенов [45][26].
- **Запуск по сбросу лимита.** Запрос планировать старт задачи на момент сброса credits закрыт «not planned»
  2025-12-28 [85 #1638].
- **Деньги** видны только в блоге: один thread QA в браузере стоил $103 [6].
- **`claude -p` и биллинг.** VK запускает Claude Code в режиме `-p` [45].
  - 2026-05-13 Anthropic объявила в посте @ClaudeDevs: с 2026-06-15 `claude -p`, Agent SDK, GitHub Actions Claude
    Code и сторонние приложения на Agent SDK тратят отдельный месячный credit — $20 на Pro, $100 на Max 5x, $200 на
    Max 20x [120][85 #3417].
  - 2026-06-15 Anthropic приостановила это изменение, в силу оно не вступило. По справке Anthropic (обновление от
    2026-10-07), `claude -p` и Agent SDK со входом по плану Claude по-прежнему тратят лимиты подписки. Новые месячные
    API credits планов Max, Ultra и Team покрывают `claude -p` только при запуске с API-ключом из привязанной
    организации Console [119].
  - Юридическая страница Anthropic: заявленные лимиты планов Pro, Max и Ultra рассчитаны на обычное личное
    использование Claude Code и Agent SDK. Сторонним разработчикам запрещено предлагать вход через claude.ai и
    направлять запросы через учётные данные планов от имени своих пользователей [112].
- **Защита от оплаты по API-ключу** — предупреждение и настройка, которая убирает `ANTHROPIC_API_KEY` из окружения
  агента [84 #713, #1229].

### Права и безопасность

- **Полные права по умолчанию** у каждого агента [43]:

| Агент | Значение по умолчанию |
|---|---|
| Claude | `dangerously_skip_permissions` |
| Codex | sandbox `danger-full-access` |
| Gemini, Qwen | `yolo` |
| Amp | allow-all |
| Cursor | `force` |
| Copilot | `allow_all_tools` |
| Droid | `skip-permissions-unsafe` |
| OpenCode | `auto_approve` |

- **Claude, Supervised** [45][46]. Запуск с `--permission-prompt-tool=stdio --permission-mode=bypassPermissions` и
  регистрацией PreToolUse hook callbacks. Для всех инструментов, кроме Glob, Grep, NotebookRead, Read, Task и
  TodoWrite, callback отвечает `ask`. Тогда Claude шлёт VK запрос `can_use_tool`, и в интерфейсе появляется approval.
- **Claude, Plan** [46]. К человеку доходят только `ExitPlanMode` и `AskUserQuestion`, остальное разрешается
  автоматически. Одобрение плана возвращает обновление разрешений, которое переводит session в `bypassPermissions`.
- **Claude, Auto** [45]. VK добавляет `--disallowedTools=AskUserQuestion`. Поэтому запуск без человека никогда не ждёт
  ответа на вопрос.
- **Отказ и timeout** [46]. Отказ передаёт причину пользователя после стандартного префикса отказа Claude. Timeout —
  это отказ и interrupt.
- **Codex** [47]. Auto → approval policy `never`. Supervised → `unless-trusted`. Sandbox «Auto» → `workspace-write` с
  approvals `on-request`. Автоматическое одобрение — только при sandbox `danger-full-access` без approval policy.
- **ACP-агенты** получают «allow once» или «allow always» [49].
- **Брокер approvals** [53]:
  - ожидающие запросы хранятся в памяти и потоком уходят в интерфейс;
  - уведомление ОС «Approval Needed: <workspace>» или «Question Asked»;
  - timeout — 36 000 секунд (10 часов).
- **Локальный API** [72][64]. Проверка Origin отклоняет чужие origins браузера. Запросы без заголовка Origin проходят.
  Токена авторизации нет. MCP-бинарник ходит в API по обычному HTTP.
- **Preview proxy** [76]:
  - отдельный порт и маршрутизация `{port}.localhost` держат preview на другом origin, чем приложение;
  - proxy внедряет скрипт, который собирает console, network и ошибки и шлёт их через `postMessage`;
  - он же загружает Eruda с jsDelivr и инспектор React fiber для click-to-component.
- **Удалённый доступ** [73][4]. Сессии подписи Ed25519; WebRTC data channels с откатом на relay (с 2026-03-27 [19]);
  встроенный SSH/SFTP для VS Code Remote. Сопряжение шло через cloud.vibekanban.com. Работает ли оно после закрытия —
  не подтверждено.
- **Скачивание бинарников** через npx проверяется по SHA-256 [68].
- **История telemetry.**
  - На старте, в июле 2025, analytics были включены по умолчанию. Они собирали email и имя на GitHub, события старта,
    завершения и merge задач и exit code агентов. После критики Louis слил PR с явным opt-in примерно через час [92].
    С 2025-07-11 согласие спрашивается при первом запуске [19].
  - В октябре 2026 пользователь показал, что вход в аккаунт снова включал telemetry и связывал прошлые анонимные
    события с email [85 #3482].
  - 2026-11-12 PR #3503 отключил analytics (PostHog) и crash reports (Sentry) в коде: функции настройки возвращают
    `None` при любых ключах сборки и запуска, интерфейс их больше не инициализирует. Пакеты PostHog и Sentry остались в
    зависимостях. PostHog облачного сервера (`crates/remote`) не тронут: он не входит в npx-сборку [84 #3503].
- **Доступ к GitHub.** OAuth-приложение на старте просило широкий доступ к приватным репозиториям. В обсуждении
  предлагали GitHub App с доступом по отдельным репозиториям [92].

### Что ругают

- **Переход в облако и обязательный вход (февраль 2026) — самое сильное недовольство** [85 #2687]:
  - обновление с 0.1.7 на 0.1.9 убрало старый интерфейс и спрятало старые задачи и проекты; обходной путь —
    закрепить 0.1.8;
  - одиночки спрашивали, зачем доске вход (32 голоса). Самый популярный ответ просил не заставлять входить ради
    базовых функций (21 голос);
  - новую раскладку называли неудобной, как VS Code с боковыми панелями и множеством кликов до merge (19 голосов).
    Кто-то уходил (16 голосов) или называл изменение резкой сменой условий;
  - такое изменение не должно выходить в patch-релизе;
  - облаку, которым обязан пользоваться, нужны ISO 27001 или SOC 2;
  - на работе нельзя входить в сторонний API.
  - **Ответы команды.** Доска ушла в облако, потому что синхронизировать состояние команды на локальном хранилище
    трудно. Workspaces работают offline, доски — нет. У каждого есть личная организация. Два параллельных стека
    команда не потянет. 2026-02-16 Louis закрыл тред: локальная архитектура несовместима с командными функциями, а
    компании скоро потребуют облачные sandbox [85 #2687].
  - **Другие жалобы** [85 #2300, #2812][91 #2727]:
    - принудительная миграция в облако в мастере настройки, без ясности, какие данные уходят;
    - нет связи проекта с репозиторием по умолчанию; выбор не того репозитория тратит токены;
    - сторонник VK в компании сделал fork только ради удаления миграции;

### Почему приходят и почему уходят

- **Приходят:**
  - бесплатно и open source, старт через npx, любой агент [110][92];
  - параллельные worktrees и review diff в одном GUI [91 #3424][85 #1335];
  - GUI поверх многих терминалов, когда агенты выдают всё больше вывода [98];
  - доступ с телефона [4][103].
- **Уходят или не начинают:**
  - принудительный вход и облако в феврале 2026 [85 #2687, #2812][91 #2727];
  - закрытие компании, выключение проектов в v0.1.44 и остановка исправлений [85 #3396][103];
  - режим без проверок по умолчанию мешает на работе [85 #2348];
  - нет выигрыша по сравнению с терминалами и worktrees: инженер хедж-фонда сделал fork и не увидел нового [92];
    другой не заметил роста продуктивности [101];
  - похоже на Jira: задачи и ветки приходится вводить руками [110];
  - orchestrators AI-лабораторий, например Codex Desktop, догнали VK — это мнение самого Louis [91 #3424];
  - объявленное в мае 2026 изменение биллинга `claude -p`; 2026-06-15 Anthropic его приостановила
    [85 #3417][102][119].
- **Куда уходят:** Multica (55.9 тыс. звёзд), kandev (локальный, без telemetry; 1.1 тыс. звёзд), Kanbots (запуск на HN
  — 263 очка), fork indie, доски в markdown-файлах, свои инструменты [85 #3408, #3354][103][105][114].

### Результаты и истории неудач

- **Основатель на запуске** [92]:
  - типичная задача занимала у агента 2–5 минут;
  - VK получил более лёгкую половину его backlog;
  - MacBook тормозил после четырёх параллельных запусков, в основном из-за сборок Rust;
  - около 80% кода VK, по его оценке, написал Amp.
- Один пользователь получил прирост в 10–50 раз на личных проектах, но считает такой стиль плохим для больших
  коммерческих систем [94].
- Другой запускал агентов наугад, без ясной цели, и получил запутанный MCP server [93].
- **Ранние скептики** [92]:
  - параллельные агенты конфликтуют, и человек перестаёт понимать, кто что делает;
  - worktrees утомительны, а разрешения конфликтов merge всё равно приходится ждать;
  - модели прячут обходные хаки, которые ловит только review.
- **Выбирающие инструмент.** Один за неделю попробовал GitButler, Spectator, VK и Conductor и вернулся к обычным
  worktrees [95]. Другой предпочитает container или VM на каждого агента ради изолированных сервисов [97].
- **Опыт вендора с QA** [6]. Playwright MCP с управляемыми dev servers работал только с явными правилами в AGENTS.md,
  полными правами и subagents. Один thread стоил $103 за 91 вызов браузера. Агенты рано заявляли об успехе.
- **Доля агентов** (вторичный источник, не подтверждено). Рассылка со ссылкой на пост в Reddit писала, что доля Claude
  Code в использовании VK упала с 83% до 70% по мере роста Codex. Комментатор HN усомнился в этой цифре [111].

### Сравнения с другими инструментами

- **Backlog.md.** VK сам ведёт агента. Backlog.md — задачи в markdown внутри git [92].
- **Обзор Mark Ferree** (вторичный) [110]. VK лучше Claude Squad (tmux, трудно освоить), Claude-Flow (много багов),
  TaskMaster (тянет в платный план) и Conductor (очередь ожидания для Windows и Linux). Но автору больше нравится Agor
  за интеграцию MCP. Быстрые subtasks в стиле Beads ему удобнее, чем VK, который напоминает Jira.
- **Conductor и Sculptor** — Electron-приложения, которые, по словам пользователя, работают тяжело; Conductor при этом
  вполне хорош [97]. Conductor и Superset позволяют выключить worktrees [85 #2472].
- **Emdash** импортирует задачи из Linear и Jira [85 #2159].
- **Superset** — терминальный инструмент на той же идее. Его автор хвалил функции планирования VK [96].
- **Codex App** — более простая альтернатива [96].
- **Kanbots.** Комментаторы спрашивали, не тот же ли это VK [105].
- **Основатель:** темп для ежедневного orchestrator задают Codex Desktop и AI-лаборатории [91 #3424].
- **Работа вдвоём и больше.** Пользователь считает идею VK верной, но VK не отличился от досок GitHub или Jira. Модель
  общих задач Zed Delta ему нравится меньше, чем VK [105].
- **Ранний поклонник.** VK был интересен, пока это был один человек и много агентов. Потом продукт ушёл в другую
  сторону [105].

### Выводы самого вендора

- **Пост о закрытии** [2]. Команда пишет, что первой выпустила поддержку многих агентов, комментарии к diff, живой
  preview, click-to-edit и удалённый доступ, и что теперь это стандарт. Большинство пользователей не платили. Главная
  работа инженера теперь — планирование и review.

  Платить должны были команды.
- **Июнь 2026** [91 #3424]:
  - VK был двумя продуктами: краткосрочное управление проектом и ежедневный orchestrator;
  - roadmap «догонять AI-лаборатории» не вдохновляет;

  - агент управления проектом — скорее всего, просто coding-агент;

## Слабые места и чего нет

- **Нет компании и почти нет сопровождения.** Один maintainer. Релизов с апреля нет. CI организации не работает.
  Инфраструктура выпуска версий — в закрытой организации [2][17][18][19][84 #3484][68].
- **Нет слоя планирования.** Kanban, issues, проекты и организации выведены. Экспорт теряет связи issue↔workspace
  [82][85 #3396]. Планирования между задачами, зависимостей и очереди нет [54].
- **Нет работы без присмотра.**
  - Нет retry при ошибках API. Нет ожидания сброса лимитов. События rate limit от Claude выбрасываются [45][54].
  - Запрос на старт по сбросу лимита закрыт «not planned» [85 #1638].
  - Открыты запросы на цикл агента, heartbeat с retry, зависимости и повторяющиеся задачи [85 #1946, #3039, #1700,
    #3230].
- **Небезопасный режим по умолчанию.** Все агенты пропускают проверку разрешений. Sandbox нет. Агенты работают под
  пользователем на host [43][81][56].
- **Нет изоляции процессов и портов между параллельными агентами** [91 #3502].
- **Нет статуса CI и test gate** [60].
- **Мало данных о расходе:** только context gauge и `/status` у Codex [26][47].
- **Выход из приложения убивает запущенных агентов.** Прерванные запуски не продолжаются [74][54].
- **Локальный API без токена.** Запросы без заголовка Origin проходят [72].
- **Нет общей ленты событий по workspaces и отчёта о запуске** — поиск по коду их не нашёл [16].
- **Нет памяти между sessions** [26].
- **Производительность в длинных sessions:** память, тяжёлый bundle, медленная загрузка [86]. Сообщения в очереди
  часто не уходят. Sessions медленнее прямого CLI [91 #3416].
- **Хрупкие интеграции:** обновления CLI вендоров ломают executors [87].
- **Windows и WSL:** установка, пути, approvals [88].
- **Документация расходится с кодом:**
  - направление merge [28][61];
  - архивирование: документация говорит, что worktree сохраняется, а код удаляет его через час [25][57];

  - время запуска cleanup [32][54];
  - два значения слова Project [34][24].

- **Auto-commit не отключается** [85 #2739].
- **Нет интеграций** с GitLab, Linear, Jira, Trello, Slack и нет импорта GitHub issues [85 #1697, #2159, #1677,
  #479][10].

## Пересечение с worfy

Термины worfy в этом разделе:

- Canvas — бесконечное полотно, на котором worfy показывает работу агентов.
- Epic — группа связанных Ticket-ов. Ticket — одна задача.
- Orchestrator — session, которая планирует и раздаёт Ticket-ы.
- Wave — набор Ticket-ов, которые запускаются вместе. Autopilot — запуск Wave-ов без человека.
- Gate — локальный запуск проверок перед PR.
- Harness — plugin, который приносит в Claude Code rules, skills, subagents и hooks.

### Где пересекаются

- **Параллельные sessions агентов, по worktree на задачу.** VK: workspace — отдельный git worktree и ветка на каждый
  репозиторий; среди агентов есть Claude Code и Codex [59][42]. worfy: у каждого Ticket свой git worktree; sessions
  Claude Code и Codex CLI.
- **PR из задачи.** VK создаёт PR через `gh` или `az` и может поручить описание PR агенту [28][63]. worfy: PR на каждый
  Ticket.
- **Агенты-reviewer-ы.** VK: Start Review — один агент на изменения session, с дополнительными инструкциями; у Codex —
  свой режим review [84 #1849][47]. worfy: reviewer subagents с review lenses (разными углами проверки).
- **Встроенный браузер.** VK: preview с devtools Eruda, режимами устройств и click-to-component [30][76]. worfy:
  встроенный Browser с профилями.
- **Терминал.** VK: xterm на каждый workspace [26]. worfy: Terminal с AI-помощником.
- **Уведомления.** VK: звуки и уведомления ОС о завершении, сбое, approval и вопросе агента [55]. worfy: уведомления.
- **Управление через MCP.** VK: MCP server для внешних клиентов и для агентов внутри — workspaces, sessions, prompts
  [64]. worfy: MCP server, через который агенты строят Cards на Canvas.
- **Работа с другого устройства.** VK: Remote Access через relay вендора и WebRTC, в том числе с телефона [4][31].
  worfy: Linked machines — связанные машины в локальной сети.
- **Approvals по политике.** VK: политики Auto, Supervised и Plan; карточки approval с timeout 10 часов [44][53].
  worfy: Autopilot одобряет permission prompts по политике.
- **Desktop-приложение для одного пользователя.** VK: Tauri на macOS, Windows и Linux; сегодня один пользователь
  [17][2]. worfy: Electron, macOS, порт на Windows в работе, один пользователь.
- **Счётчики расхода.** VK: context gauge и `/status` Codex с rate limits [26][47]. worfy: счётчики лимитов и
  расхода.
- **Планирование задач.** VK в облачный период: issues с sub-issues и связями blocking, статус меняется по workspace и
  PR [34][3]. Сейчас — только MCP, через который агент превращает план в issues [36]. worfy: Epics и Tickets,
  Orchestrator.
- **Работа с PR и комментариями.** VK: workspace из открытого PR, импорт комментариев GitHub в diff [84 #2201, #2195].
  worfy: PR inbox.

### Где расходятся

- **Работа без присмотра.** VK не ждёт сброса лимитов, не повторяет ошибки API и выбрасывает события rate limit от
  Claude [45]. Запрос на старт по сбросу лимита закрыт [85 #1638]. worfy: Autopilot запускает Wave-ы без человека,
  ждёт сброса лимитов подписки и повторяет ошибки API. Есть планирование запусков под лимиты подписки и Eco mode.
- **Проверка результата.** VK: нет test gate и статуса CI. Качество держится на cleanup-скрипте, commit reminder,
  review агентом и человеком [60][46][54]. worfy: tests, локальный Gate и PR с CI badges.
- **Иерархия работы.** VK сегодня — плоский список workspaces; issues и проекты выведены [82]. worfy: Epic → Ticket →
  Wave, Orchestrator раздаёт работу.
- **Права по умолчанию.** VK: все агенты без проверки разрешений и без sandbox [43]. worfy: Autopilot одобряет
  permission prompts по политике.
- **Экран.** VK: фиксированные четыре панели и список в sidebar [26]. worfy: бесконечный Canvas и Cards.
- **Наблюдение за запуском.** VK: logs по процессам и статусы в sidebar. Общей ленты событий и отчёта о запуске поиск
  по коду не нашёл [26][62][16]. worfy: Flight Recorder — лента событий автономного запуска; Work track — вся работа
  проекта по дням и неделям.
- **Сколько агентов.** VK: девять встроенных агентов и ACP registry [42][49]. worfy: Claude Code и Codex CLI.
- **Как запускается Claude Code.** VK — headless `claude -p` со stream-json и control protocol [45][46]. Как именно
  worfy запускает Claude Code, в описании worfy не сказано.
- **Настройка агента.** VK пишет MCP-конфиг в файлы агентов и регистрирует hook callbacks через control protocol
  [52][46]. worfy: Harness plugin с rules, skills, subagents и hooks внутри Claude Code.
- **Продуктовый слой.** У VK его нет. Orchestrator-агент не выпущен [91 #3424]. worfy: Product Session —
  продуктовый советник с живым Mind map и критиком spec.
- **Доказательства.** Скриншотов-доказательств у VK поиск по коду не нашёл [16]. worfy: Evidence screenshots с privacy
  scrub.
- **Удалённый доступ.** VK — через интернет и сервер вендора: relay и вход в облако [4][31]. worfy — по локальной сети.
- **Платформы.** VK работает и на Linux, есть мобильная раскладка в браузере [17][84 #2947]. worfy — macOS, Windows в
  работе.

## Механизмы, которые стоит изучить

1. **Checkpoint на каждый ход агента и откат к нему.**
   - Что это: VK записывает HEAD каждого репозитория до и после каждого хода агента. После успешного хода он делает
     коммит с итогом агента в сообщении [54][56].
   - Как работает: откат к ходу — hard reset репозиториев к коммиту «до», остановка процессов, пометка более поздних
     ходов `dropped` и продолжение Claude Code с `--resume-session-at <uuid>` [54][69][45].
   - Чем интересно: откат задачи к любому ходу агента сводится к git reset и одному флагу CLI. История ходов и история
     коммитов совпадают.
   - Источник: [45][54][56][69].
2. **Stop hook против незакоммиченной работы.**
   - Что это: commit reminder, включённый по умолчанию [63].
   - Как работает: для Claude Code VK регистрирует Stop hook через control protocol. Hook один раз блокирует
     остановку, если в репозиториях есть изменения, и цитирует `git status`. Флаг `stop_hook_active` не даёт
     зациклиться. Для Codex — одно дополнительное сообщение пользователя на событии `turn/completed` [46][47].
   - Чем интересно: агент сам доводит работу до коммита, отдельного шага после запуска не нужно.
3. **Approvals через control protocol Claude Code.**
   - Как работает: флаг `--permission-prompt-tool=stdio` и PreToolUse callbacks, которые для каждого инструмента
     отвечают `ask` или `allow`. Claude шлёт `can_use_tool`, VK показывает карточку. После одобрения плана VK
     возвращает обновление разрешений и переводит session в `bypassPermissions`. В режиме Auto флаг
     `--disallowedTools=AskUserQuestion` убирает вопросы человеку [45][46].
   - Чем интересно: решение по каждому инструменту принимает приложение, по структурированному запросу, а не по тексту
     в терминале. Запуск без человека не может зависнуть на вопросе.
4. **Codex через `app-server` по JSON-RPC.**
   - Как работает: `thread/start` и `turn/start`; follow-up — `thread/fork`; review — fork thread и
     `ReviewTarget::Custom`. Команда `/status` даёт план, процент основного и дополнительного лимитов и credits [47].
   - Чем интересно: у Codex программно доступны структурированные approvals, данные о лимитах подписки и встроенный
     режим review.
5. **Одна схема событий для всех агентов и ACP registry.**
   - Как работает: нормализатор каждого агента выдаёт `NormalizedEntry` — сообщения, вызовы инструментов с типом,
     thinking, ошибки, токены — и шлёт их как JSON Patch [51]. Gemini, Qwen и Copilot подключены по ACP. Registry
     кэшируется на диске, timeout загрузки — 5 секунд. Новый ACP-harness (агенты из registry и Copilot) на запрос
     разрешения отвечает «allow once»; старый harness Gemini и Qwen при автоодобрении сначала берёт «allow always»
     [48][49].
   - Чем интересно: одна лента событий для разных вендоров. Новый агент добавляется без отдельного executor.
6. **Logs вне SQLite и доставка изменений через SQLite hooks.**
   - Как работает: logs — JSONL-файл на процесс плюс кольцевой буфер в памяти. Изменения строк SQLite через
     pre-update и update hooks превращаются в JSON Patch и идут одним потоком. Logs, diff и approvals — по отдельным
     WebSocket [70][71].
   - Результат по замеру вендора: logs занимали ~98% базы и вызывали «database is locked». После переезда база —
     ~20 MiB, ошибок блокировок нет [5].
7. **Комментарии review одним блоком в следующий prompt.**
   - Как работает: комментарии к строкам diff копятся и уходят одним Markdown-блоком `## Review Comments (N)` — файл,
     строка, цитата кода. Комментарии PR с GitHub можно добавить в ту же пачку. Для конфликтов rebase генерируется
     prompt со списком до 12 файлов и `GIT_EDITOR=true` [83][27][84 #2195, #2449][40].
   - Чем интересно: пользователи называют это вторым по важности вкладом VK после worktrees [85 #1335].
8. **Preview proxy с внедрённым скриптом и click-to-component.**
   - Как работает: proxy на отдельном порту маршрутизирует `{port}.localhost` и держит preview на отдельном origin. Он
     внедряет скрипт, который собирает console, network и ошибки и передаёт их через `postMessage`, а также Eruda и
     инспектор React fiber. Выбранный на странице элемент уходит в чат как компонент и место в исходном коде [76][30].
   - Чем интересно: встроенный браузер становится источником точного контекста для агента.
9. **Orchestrator mode MCP с ограничением области.**
   - Как работает: `vibe-kanban-mcp --mode orchestrator` оставляет 7 инструментов. Каждый вызов проверяется на
     принадлежность к workspace самого агента. Orchestrator не может запустить coding-агента в себе.
     `run_session_prompt` возвращает ответ сразу, результат опрашивается через `get_execution` [64][84 #3065].
   - Чем интересно: агент, который раздаёт работу, может трогать только свою область.
10. **Гигиена worktree.**
    - Как работает [57][59][56][60][84 #1614]:
      - удаление через 72 часа простоя или через 1 час после архивирования; ветка остаётся, worktree пересоздаётся по
        требованию;
      - блокировка на путь при создании; одна повторная попытка после очистки метаданных git; multi-repo создание
        откатывается целиком;
      - `copy_files` переносит `.env`; setup может идти параллельно агенту; archive-скрипт; автоархивирование после
        merge всех PR;
      - CLAUDE.md и AGENTS.md в корне multi-repo workspace импортируют файлы каждого репозитория.
    - Ограничение: по отзывам, очистка удаляла активные worktree, а пересоздание ломало `node_modules` [91 #2335].
11. **Доверие между host и браузером.**
    - Как работает: pairing code; host привязан к одной сессии браузера; каждый запрос подписан в браузере ключом
      Ed25519 и проверяется на host; прямое WebRTC-соединение с откатом на relay; встроенный SSH/SFTP для VS Code
      Remote [4][72][73][84 #3139].
    - Чем интересно: backend вендора не может сам отдать команду машине пользователя [4].
12. **Раздача портов и защита параллельных агентов друг от друга.**
    - Как работает: dev-manager-mcp выдаёт порты dev servers и останавливает простаивающие серверы [117][6]. Набор
      hooks bulkhead (вторичный источник) — PreToolUse hooks, которые не дают агенту убить чужие процессы по имени
      (`pkill node`), занять чужой порт и запускать тяжёлые сборки при нехватке памяти [91 #3502].
    - Чем интересно: изоляция git не мешает параллельным агентам ломать друг другу dev servers и память на одной
      машине [91 #3502].
