## Модель работы

- **Тип — hybrid.**
  - Локальные агенты работают в desktop-приложении и в CLI: в основной копии репозитория, в worktree, через remote SSH, в WSL и в dev container [1][64][65].
  - Cloud Agents (раньше назывались Background Agents) — агенты на отдельных VM Cursor: Ubuntu с рабочим столом [22][23][84]. Это Firecracker microVM (лёгкие виртуальные машины AWS) в отдельном аккаунте AWS [29].
  - Self-hosted workers — свои ноутбук, devbox или VM («My Machines») и пулы машин команды [33][34][105].
  - Модель всегда работает на серверах Cursor. Даже в «локальном» режиме SDK локально идут только цикл агента и доступ к файлам [47]. На self-hosted машинах Cursor ведёт цикл агента, inference и планирование, а worker только правит файлы и выполняет команды [32].
- **Агенты.**
  - У Cursor свой harness — код вокруг модели: инструменты, системный prompt, цикл. Он настроен под каждую модель отдельно [2][132].
  - Заметки не нашли признаков, что Cursor запускает Claude Code или Codex CLI как агентов. Cursor читает их файлы: hooks, skills и папки subagents [15][16][18].
  - Две зацепки без объяснения:
    - в документации Voice chat кнопка голоса скрыта, среди прочего, в «Claude Code chats»; что это за тип чата, документация не объясняет (не подтверждено) [8];
    - тема на форуме: Grok Bot раньше правил репозитории через локальные Claude или Codex CLI пользователя, а с 2026-11-05 по умолчанию идёт через cloud-агентов Cursor [215].
- **Модели.**
  - Свои: Grok 4.7, 4.6 и 4.5 (Cursor пишет, что обучал их вместе со SpaceXAI) и Composer 2.5 [50][139].
    - Composer 2 — продолженное обучение открытой модели Kimi K2.5 [126]. Composer 2.5 — на той же базе [133].
    - Новые версии Composer выходят каждые пять часов: Cursor дообучает модель через reinforcement learning на реальном использовании [127].
  - Сторонние: Claude (Opus 5.5, Sonnet 5.5, Fable 5.x, Haiku 5.5), Gemini (3.1 Pro, 3.5 Flash), DeepSeek V4.1 Flash и другие [50]. Индекс документации ещё перечисляет страницы GPT-5.6 Sol/Terra/Luna, Gemini 4 Carbon/Hydrogen/Argon и «Muse Wonder» [156]. Claude доступен и через AWS Bedrock [65].
  - OpenAI заканчивает прямое партнёрство с Cursor: объявлено 2026-08-29, вступает через три месяца. По словам сотрудника Cursor, модели OpenAI — около 5% трафика [223].
  - Cursor Router (2026-07-22) выбирает модель на каждый запрос. Режимы: Cost, Balance, Intelligence. Индивидуальные планы получают только Cost [100][50].
- **Один пользователь или команда — оба.** Есть индивидуальные планы, Teams и Enterprise. Для команд: многопользовательские Projects, общие canvases, Automations от имени service account, marketplaces команды [3][10][30][20].
- **Платформы.**
  - Desktop: macOS, Windows, Linux (пакеты apt/dnf или AppImage) [76][64].
  - Web: cursor.com/agents запускает cloud-агентов с любого устройства. На Android — как PWA (сайт, установленный как приложение); нативное приложение для Android «в планах» [22][31].
  - iOS и iPadOS 26.0+, только на английском. Публичная beta — с 2026-06-29, iPad — с 2026-07-29 [31][98][101].
  - CLI `agent`: macOS, Linux, WSL и Windows PowerShell [44].
  - JetBrains IDEs — через Agent Client Protocol (ACP, протокол подключения агента к IDE) [62]. Xcode 26.3+ — через встроенный в Xcode MCP bridge [63].
  - Агентов можно запускать из Slack, Microsoft Teams, GitHub, Bitbucket, Linear, Jira и Notion [22][57][59][60].

## Функции

### Agents Window: окно и навигация

- **Agents Window.** Отдельное окно, где в центре агенты, а не файлы. Работает рядом с классическим редактором на базе VS Code. Открывается командой «Open Agents Window» в Command Palette, обратно — «Open IDE». Оба окна могут быть открыты сразу [1][128].
  - GA — вместе с Cursor 3, 2026-04-02 [128][88]. Администраторы Enterprise могли отложить включение на две недели [1] (не подтверждено: на странице [1] и в changelog 3.0 [88] на 2026-11-13 этого нет).
  - В alpha окно называлось «Glass» — это подтвердил инженер Cursor на HN [164].
- **Что есть только в Agents Window:** несколько workspace из разных проектов в одном окне; новый вид diffs (review, commit, управление PR); параллельные cloud-агенты; передача работы между local и cloud; cloud subagents (`/in-cloud`, `/autopilot`); worktrees прямо в интерфейсе [1].
- **Файлы, не выходя из окна.** Cmd+P открывает файл, Cmd+Shift+F ищет по файлам [1]. Вид Files с полной поддержкой language server [128].
- **Боковая панель агентов.**
  - Список всех local и cloud агентов, в том числе запущенных с телефона, из веба, Slack, GitHub и Linear [128].
  - До 75 закреплённых агентов [65].
  - Упавшие агенты получают красный статус Error и свою группу [65].
  - Метки непрочитанного и плашка New Messages [65].
  - Архив отменяется через Cmd+Z. Перед архивом агента с запущенными процессами появляется предупреждение [64].
  - Файл, перетащенный на агента в панели, прикрепляется к его чату [64].
- **Раскладка плиткой.** Окно делится на панели, агентов перетаскивают в плитки. Раскладка сохраняется между сессиями [89]. У каждой панели свои элементы управления; панели переживают перезагрузку [64]. Вкладки помнят место после переключения агента и перезапуска: страницу PDF, прокрутку, выбранный объём изменений [64].
- **Agent Tabs** в редакторе: чаты рядом или сеткой [88].
- **Поиск.** Cmd+K открывает Command palette с поиском по прошлым чатам через локальный индекс [2][81]. Cmd+F ищет внутри чата [81].
- **Плашки над полем ввода:** Goal, Queued, Debug, Canvas, Open Browser. Каждая открывает свою панель [65].
- **Уведомления.** Значок в строке меню macOS со счётчиком непрочитанного (его можно скрыть), список непрочитанного в меню Dock и звук по завершении [64][65]. Одно системное уведомление на всех агентов [66].
- **Расход и контекст.** Кольцо «Usage N%» в строке статуса чата [65]. Разбивка занятого контекста по rules, skills, MCP и subagents (2026-05-06) [92]. В мае 2026 пользователи писали, что индикатор расхода пропал из Agents Window [183]; в release notes 3.19–3.27 (сентябрь–октябрь) кольцо описано [65].

### Изменения и pull requests

- **Вид diffs:** stage, commit и управление PR [128].
- **Changes tab:** объём «Last Agent Turn» показывает только последние правки агента [65].
- **PR tab:** вкладки Changes, Description, Commits, Checks и Reviews. Cmd+click по строке diff открывает её на GitHub или в Origin [93][64].
- **Stacked PR** (цепочка PR, где каждый стоит поверх предыдущего): полоса стека в лотке PRs у Project [64].
- **Split changes into PRs:** быстрое действие и skill `/split-to-prs` предлагают разбить изменения на несколько PR. Сначала делают резервный snapshot, потом ждут одобрения [93][16].

### Устойчивость интерфейса

- После падения extension host (процесса, где работают расширения VS Code) появляется кнопка Resume [64][66].
- Агент, который зациклился в рассуждениях, получает один повтор с подсказкой [65][66].
- Инструмент `Await`: агент ждёт фоновые shell-команды или subagents, или появление в выводе текста вроде «Ready» или «Error» [88].

### Параллельная работа и worktrees

- **Worktrees в Agents Window** (2026-04-24). Агента можно запустить в отдельной git-копии или перенести туда. Из неё потом делают commit, открывают PR или переносят результат в основной workspace [14][91]. Cloud-агента можно перенести в локальный worktree [65].
- **Настройка worktree.** Файл `.cursor/worktrees.json` хранит команды настройки: `setup-worktree-unix`, `setup-worktree-windows` и запасной `setup-worktree`. Переменная `$ROOT_WORKTREE_PATH` указывает на основную копию — так, например, копируют `.env`. Симлинки на зависимости документация не советует [14].
- **Лимит и чистка.**
  - `cursor.worktreeMaxCount` — по умолчанию 25 worktree на машину, общий счёт для всех workspace [14].
  - `cursor.worktreeCleanupIntervalHours` — как часто идёт проверка; в примере настроек — раз в 6 часов. Что это значение по умолчанию, документация прямо не пишет [14].
  - На каждом проходе чистка заново находит корень worktree Cursor на машине. Туда же CLI кладёт свои worktree: `~/.cursor/worktrees/<repo>/<name>` [46]. Поэтому под чистку попадают и лежащие там worktree, созданные не менеджером Cursor, — например skill `/worktree` или командой `git worktree add`. Трогает ли чистка worktree в других папках, документация не говорит (не подтверждено). Такое поведение описано для версии 3.5 и новее [14].
- **Worktree в CLI.** `agent --worktree [name]` (или `-w`) создаёт worktree в `~/.cursor/worktrees/<repo>/<name>` [46].
- **Команды в IDE.** `/worktree <задача>` уводит остаток чата в отдельную копию. `/apply-worktree` переносит результат, `/delete-worktree` удаляет копию [14].
- **`/best-of-n`** (например, `/best-of-n sonnet,gpt,composer <задача>`). Одна задача идёт на нескольких моделях, каждая в своём worktree. Команда только сравнивает и ничего не сливает: человек выбирает лучший вариант и применяет его через `/apply-worktree` [14][88]. В cloud-запусках есть вкладки Best-of-N [64].
- **`/multitask`** (версия 3.2, 2026-04-24). Вместо очереди сообщений запускает асинхронные subagents параллельно. Делит большую задачу на части для группы subagents и может превратить сообщения из очереди в параллельную работу [91]. В редакторе — с 2026-05-07 [93].
- **Build in Parallel** (3.3, 2026-05-07). Находит в плане независимые шаги и запускает их сразу как асинхронные subagents; зависимые шаги идут по порядку [93][77].
- **История.** Cursor 2.0 (2025-10-29) уже запускал до 8 агентов на один prompt в worktree или на удалённых машинах [86].

### Subagents

- **Встроенные:** Explore — быстрая модель и много поисков параллельно; Browser — убирает шум из структуры страницы [15].
- **Режимы:** foreground и background [15].
- **Свои subagents** лежат в `.cursor/agents/`. Cursor читает также `.claude/agents/` и `.codex/agents/`. Поля frontmatter: `name`, `description`, `model` (например, `claude-opus-5[effort=high,context=300k]`), `readonly`, `is_background` [15].
- **Вложенность** — не глубже двух уровней. С версии 2.5 subagents могут запускать только главный агент и его прямые дети [15].
- **Продолжение и вывод.** Subagent можно продолжить по ID. Фоновые subagents пишут ход работы в `~/.cursor/subagents/` [15].
- **Параллельность и ошибки.** Несколько вызовов Task в одном сообщении идут параллельно. Упавший subagent возвращает статус ошибки; родитель может повторить его или продолжить по ID. Пять параллельных subagents тратят примерно в пять раз больше токенов [15].
- **Изолированные копии (swarm — группа subagents над одной задачей).** Каждый subagent получает свой worktree или свою cloud VM и ветку. Изменения остаются на этих ветках, пока родитель их не сольёт [15][103].

### Cloud subagents, /autopilot и передача работы между local и cloud

- **`/in-cloud`** отдаёт следующую задачу cloud subagent на отдельной VM и ветке [15][96].
- **`/autopilot`** (плашка или команда) передаёт PR cloud-агенту. Тот следит за PR и работает, пока PR не будет готов к merge: отвечает на review, решает конфликты, чинит упавшие checks и делает оставшуюся работу [15][16].
  - Функция вышла 2026-06-17 в версии 3.7 под именем `/babysit` [96].
  - Явной записи о переименовании не найдено. Но changelog 3.7 описывает `/babysit` (плашка или команда; cloud subagent готовит PR к merge, не занимая локальную сессию) теми же словами, какими документация сейчас описывает `/autopilot` [96][15]. Поэтому `/autopilot` — новое имя `/babysit`; это вывод.
- **Local → cloud:** работа продолжается при закрытом ноутбуке. **Cloud → local:** результат можно проверить у себя [128][96].
- **«Move to Cloud»** переносит разговор, но не незакоммиченные файлы [80].
- **В CLI** сообщение с префиксом `&` уходит cloud-агенту [44].

### Projects: агент-координатор (beta с 2026-09-10)

- **Что это.** Агент-координатор планирует работу, раздаёт её агентам-исполнителям (workers) и собирает результат. Сам код не пишет [3][150].
  - Координатор работает как cloud-агент, поэтому закрытый ноутбук его не останавливает. Если что-то надо проверить локально, он запускает локального агента [3].
  - По словам Cursor, координатор держит контекст месяцами, раздаёт работу тысячам subagents и сам делает повторяющуюся работу [106][150]. Уже есть координаторы больше чем с 1000 workers [67].
  - Цифры Cursor: один внутренний Project идёт к 20–100 PR в день. Новые пользователи сливают на 30% больше PR, а те, кто работает в основном через Projects, — в шесть раз больше [150].
- **Доступность.** Premium и выше, Teams, Enterprise и старые платные планы. Нет на Free и Plus и при Legacy Privacy Mode. Для Enterprise нужен Cursor 3.21.9 или новее [3].
- **Общий контекст.**
  - Синхронизируемые файлы, куда агенты складывают исследования, артефакты и выученные предпочтения [3].
  - Два хранилища файлов (Agent Store): хранилище Project в `/cursor/stores/self` и личное в `/cursor/stores/user` [3].
  - Внутри — `preferences.md`, трекер задач `notes.md`, папки `workflows/` и `principles/` [3][83].
- **Подписки координатора.** Он следит за каналами Slack, PR, CI на ветке или за расписанием (например, каждый день в 8:00). Плашка Listening показывает все события, которые он слушает [3].
- **Трекер задач.**
  - Заметки Project работают как трекер с видами List и Board (3.27), статусами, ID, агентами и PR [64][65].
  - Фильтры по статусу, PR, тегам и владельцу. Задачу можно упомянуть через @. Родительская задача следует статусу подзадач [64].
  - Library — файлы Project с поиском, сортировкой и сеткой [64].
  - Workers получают имена по теме работы [64]. Workers сами сообщают координатору статус, и трекер остаётся точным (неделя 2026-10-19) [67].
- **Машины.**
  - Меню «Run on / Allowed machines» разрешает координатору ставить workers на ваши машины или пулы без вопроса [64].
  - «Add folder on This Mac» запускает локального worker для папки [64].
  - Локальных агентов можно добавить в cloud Project через Remote Control [65].
  - Для worker или окружения вне Project координатор показывает человеку карточку одобрения (неделя 2026-10-12) [67].
- **Статус Input Needed** — координатор или worker ждёт ответа человека [64][68].
- **Управление.** Координатор пишет агентам, которых пользователь упомянул через @, и своему родителю (неделя 2026-10-05). Он может сменить модель у worker (неделя 2026-09-21) [67]. Пока координатор работает, в поле ввода остаётся кнопка Send вместо Stop, чтобы его случайно не остановить [64].
- **Стартовые правила (seed rules).** Cursor публикует в справке шаблон правил. Пользователь сам вставляет его в `preferences.md` нового Project или ссылается на него из `notes.md`. Что координатор получает эти правила автоматически, справка не говорит (не подтверждено). Главные правила: один worker на PR; готовность PR координатор проверяет сам и не верит отчёту worker; merge и deploy координатор не делает [83].
- **Multiplayer** (3.26.13+, 2026-11-10).
  - У каждого участника свой координатор и свои workers; расход идёт на этого участника [3][154].
  - Участники делят доску задач и хранилище контекста [3][154].
  - Координаторы пишут друг другу в side chats «Chat with {name}'s agent». Такие сообщения считаются недоверенным вводом, и секреты в этом чате не передаются [3][154].

### Работа с агентом в чате

- **Режимы** Agent, Plan, Ask и Debug; переключение — Shift+Tab [5][6][82].
  - **Plan Mode.** Агент задаёт уточняющие вопросы, изучает код и пишет редактируемый план в Markdown; строит после одобрения. План сохраняется в домашней папке; есть кнопка «Save to workspace» [5]. Документация советует при плохом результате откатить и поправить план, а не исправлять результат новыми сообщениями [5].
  - **Debug Mode.** Агент строит гипотезы и добавляет логирование, которое шлёт данные на локальный debug-сервер. Потом просит воспроизвести ошибку, исправляет её и убирает логирование [6].
- **Очередь и steering** (вмешательство в работу агента на ходу). Enter ставит сообщение в очередь; порядок меняют перетаскиванием. Cmd+Enter отправляет сразу [2]. «Send now» или двойной Enter вставляет сообщение на следующем вызове инструмента [2][103].
- **Долгая работа.**
  - `/goal <цель>` — долгая цель на много ходов. В CLI Ctrl+C ставит её на паузу. Функция включается не у всех сразу [2][103].
  - `/loop` повторяет prompt или skill с интервалом, или агент сам выбирает, когда проснуться [16][2].
  - Custom Modes: любой skill можно закрепить как постоянный режим чата (⌥⏎) [103].
- **Checkpoints** — локальные снимки файлов перед значимыми правками, отдельно от git. Восстановление возвращает только файлы [2].
- **Side chats** (`/side`, `/btw`) — постоянные дочерние чаты; родительский чат служит им скрытым контекстом [2][78]. Источники расходятся: справка говорит, что side chats работают только локально [78], а release notes Agents Window 3.23 — что они работают и у cloud-агентов [65].
- **Вопросы агента.** Инструмент вопросов не останавливает работу: агент продолжает, пока ждёт ответа [2].
- **Картинки.** Генерация изображений сохраняет файлы в `assets/` [2].
- **Instant Grep** ищет по локальному индексу [11].
- **Multi-root workspaces** (несколько папок в одном workspace) работают локально; cloud-агенты их не поддерживают [11][91].
- **Voice chat** (2026-11-06):
  - разговор голосом в реальном времени на Grok Voice; агент сам коротко рассказывает о ходе работы [8][109];
  - работает в Agents Window, IDE, вебе и iOS; есть команда «Hey Siri, call Cursor» [8];
  - звонок обрывается примерно после 10 минут тишины; есть дневной лимит звонков [8];
  - диктовка — отдельная функция: удерживать Ctrl+M в Agents Window [8][89];
  - кнопка голоса скрыта, среди прочего, в «Claude Code chats»; что это за тип чата, документация не объясняет (не подтверждено) [8].
- **Agent Review:** команда `/agent-review` или автоматически после commit. Глубина — Quick или Deep. Читает `BUGBOT.md` [4].
- **Сжатие контекста.** У предела контекста агент сжимает разговор и продолжает; последний запрос сохраняется дословно (IDE 3.24, CLI v2026.10.08) [66][71]. С CLI v2026.10.22 сводка считается в фоне [71].

### Cloud Agents

- **Где работают.** Изолированные Ubuntu VM с рабочим столом, клонированными репозиториями, зависимостями, секретами и сетью [22][23].
- **Откуда запускать:** desktop, веб, iOS, Slack, GitHub и Bitbucket (`@cursor`), Linear, Microsoft Teams, Jira, Notion и API [22][57][59][60].
- **Сколько параллельно.** Документация обещает «сколько угодно» агентов [22]. На странице цен лимита нет [155]. Жёстких лимитов на число cloud-агентов и на размах `/multitask` заметки не нашли (не подтверждено).
- **Несколько репозиториев.** Multi-repo для cloud-агентов и Automations — с версии 3.4 (2026-05-13) [109]. Лимит источники называют по-разному: changelog 2026-10-16 — окружение до 300 репозиториев [108], документация API — до 500 репозиториев в запросе на создание агента [35].
- **Окружение.**
  - Агент сам настраивает окружение меньше чем за 10 минут; человек смотрит за этим в общем терминале [23][96].
  - Другие пути: Dockerfile через `.cursor/environment.json` (с кэшем слоёв) или snapshot [23].
  - Порядок выбора: личное сохранённое окружение → окружение команды → файл в репозитории [23].
  - Команда `install` выполняется во время **Builds** — фоновых заранее подготовленных снимков диска. Упавший Build никогда не заменяет рабочий [24].
  - `start` и `terminals` работают в сессии tmux, общей для человека и агента [23].
  - Доступ к AWS — через IAM roles (STS, ключи на 1 час, обновление за 15 минут до конца срока) или OIDC [23][26].
  - Частные сети — через Tailscale (userspace mode) и Cloudflare Tunnel [23].
- **Секреты трёх видов:** обычные переменные окружения; Runtime-секреты, которые в выводе инструментов, транскриптах и commit заменяются на `[REDACTED]`; секреты только для Build [28].
- **Исходящая сеть:** всё разрешено; список по умолчанию плюс свой allowlist; только allowlist. Админы Enterprise могут закрепить выбор [27][28].
- **Computer use.** Агент управляет рабочим столом и браузером своей VM, чтобы проверить свою работу [26][122].
- **Артефакты.** Скриншоты, видео и логи прикрепляются к PR. Встраивание в GitHub — по желанию, через неугадываемые публичные URL [26].
- **Remote desktop.** Человек берёт рабочий стол агента под управление и отдаёт обратно [26][22].
- **Порты.** «Auto-Forward Ports» и превью во встроенном браузере [23].
- **Subscriptions** (2026-08-19).
  - Агент подписывается на события: активность PR или CI на GitHub, треды или каналы Slack, задачи Linear, таймеры. Потом заканчивает ход и просыпается, когда приходит подходящее событие [26][103].
  - Несколько событий подряд могут дать одно пробуждение; перед действием агент перечитывает источник (PR, тред, задачу). Подписка живёт не дольше 180 дней. У агентов от имени service account подписок нет [26].
  - CI-подписка ждёт завершения всех checks на commit [26].
  - Cloud-агенты сами подписываются на PR, которые создали [103].
- **Auto-fix CI** (только GitHub Actions; только Teams и Enterprise).
  - До 10 follow-up на упавший CI в одном PR [26].
  - Не срабатывает после push человека, после follow-up сообщения или если тот же check падает и на базовом commit [26].
  - Включается и выключается на PR командами `@cursor autofix on` и `@cursor autofix off` [26].
- **Общий доступ.**
  - URL агента даёт коллегам read-only доступ после проверки доступа к репозиторию [22].
  - Настройка «Team follow-ups» — Disabled / Service accounts only / All — решает, кто может писать чужому агенту. Документация предупреждает о lateral movement: через чужого агента можно добраться до секретов другого человека [27].
- **Cursor Cloud MCP** — встроенные инструменты диагностики для самих агентов: `run-info`, `get-events` (события setup, PR, артефактов и входа в MCP), `list-cloud-agents`, `batch-fetch-details` (транскрипты, diff, логи setup), инструменты сборки окружения и `rename-chat` [26].
- **Start from scratch** (2026-08-27). Репозиторий не нужен: Cursor создаёт черновой репозиторий в Origin. Кнопка «Create repo» публикует его, «Publish» делает deploy на Vercel [104][23].
- **Apps** (2026-11-05). Агент строит и хостит веб-приложение с Postgres и входом через Cursor SSO [25][109].
  - Видимость: приглашённые, команда или все (публично — на индивидуальных планах) [25].
  - Перед публикацией — четыре постоянные проверки (секреты в файлах, файлы с учётными данными, `.env`, source maps) и AI security review [25].
  - Доступно на платных планах с cloud-агентами [25].
- **Long-running agents** (research preview с 2026-02-12 для Ultra, Teams и Enterprise) [87][120].
  - Работа часто идёт больше суток. Пост приводит примеры от 25 до 52 часов; заметки по функциям называют 52 часа, заметки по направлению — 36 часов [120].
  - Агент сначала предлагает план и ждёт одобрения. Несколько агентов проверяют работу друг друга [120].
  - В неделю 2026-09-21 режим Long-running убрали из выбора модели в вебе вместе с плашкой лимита времени и настройкой команды. Cloud-агенты из веба теперь всегда работают в стандартном режиме [64][70].
- **Без approvals.** Cloud-агенты не спрашивают разрешений: Run Modes к ним не относятся, и внутри VM агент сам выполняет любые команды терминала [13][28].
- **Лимит трат.** При первом запуске cloud-агентов Cursor просит задать лимит трат [22].

### Automations

- **Что это.** Постоянно включённые cloud-агенты, которые запускаются по расписанию или событию. Вышли 2026-03-05 [125][30].
- **Создание.** В Agents Window, на cursor.com/automations, через skill `/automate` (2026-06-18) или из шаблонов Marketplace [30][97]. Шаги: trigger → prompt → инструменты → область репозиториев → включение [30]. Automations внутри Agents Window — с версии 3.5 (2026-05-20) [109].
- **Triggers.**
  - Cron или готовые расписания. Запуск может опоздать до 1/5 интервала, но не больше чем на 5 минут; раньше срока не стартует [64][70].
  - Source control (GitHub, GitLab, Bitbucket Cloud): открыт draft, открыт PR, push в PR, PR слит, push в ветку, комментарий. Только для GitHub: метки, CI завершён, комментарий в issue, комментарий в review, review отправлен, тред решён, workflow run завершён [30].
  - Slack: сообщение в канале, эмодзи, создан канал [30].
  - Webhook: приватный endpoint и API-ключ [30].
  - Linear, Sentry и PagerDuty [30].
  - PR из форков не поддерживаются [30]. Событие «ничего не произошло» триггером быть не может — так ответил сотрудник [202].
- **Инструменты.** Open PR (включён по умолчанию), комментарий или approve в PR, запрос reviewers, отправка и чтение в Slack, MCP-серверы [30]. Computer use включён по умолчанию [30].
- **Memories.** Постоянный файл `MEMORIES.md` между запусками, вне рабочего дерева. Документация предупреждает: недоверенный ввод может его испортить [30].
- **Область репозиториев:** ни одного, один или несколько [30].
- **От чьего имени («Run as»).** «Me» — платит автор; «Service account» — платит команда, создать такой запуск может только админ [30]. Доступ: Private / Members can view / Members can edit [30].
- **Как код.** Automations описываются в Terraform как ресурсы `cursor_platform_workflow` [30]. Код этого Terraform provider открыт: `cursor/terraform-provider-cursor` (Apache-2.0) [232]. В Cloud Agents API есть endpoints для automations [35][156].
- **Расход** считается как у cloud-агента, по максимальному окну контекста модели [30].
- **Сбои.** Если вход в MCP не удался, run идёт дальше без инструментов этого сервера [30][70]. При rate limit automation сообщает, что лимит может действовать на весь Cursor, и советует повторить чуть позже [70].
- **Managed agents** в разделе «From Cursor»: Bugbot, Security Review, Vulnerability Remediation, PR Routing & Approval [30] и Rollouts [41]. Сам Cursor использует Automations для security review, владения кодом, реакции на инциденты и покрытия тестами [125].

### Review и агенты после merge

- **Bugbot** — бот Cursor для review PR [37].
  - Review идёт автоматически или по команде `cursor review` / `bugbot run`. Bugbot ставит check «Cursor Bugbot»: по умолчанию neutral, по желанию — failing. Review инкрементальный. В сводке PR есть оценка риска [37].
  - Уровни effort: Low, Default, High и Smart [37][94].
  - Правила берутся из `.cursor/BUGBOT.md`, правил команды и **выученных правил** — из слитых и закрытых PR. Факт можно добавить командой `@cursor remember <факт>` [37].
  - Autofix запускает cloud-агента — в новой ветке или в той же. Прямой push исправлений в ветку — не больше 3 попыток на PR, чтобы не зациклиться [37][124]. Нужен предоплаченный кредит или on-demand [37].
  - Настройка — `.cursor/config/bugbot.yaml`; файл читается из базовой ветки [37].
  - API: запуск review — 30 запросов в минуту, запуск с `dryRun` — ещё не больше 10 в минуту; аналитика, админ [37][36]. Оплата по использованию — с мая 2026 [37].
  - Цифры Cursor: около 90 секунд на review на Composer 2.5 [95]; в июне 2026 — больше чем втрое быстрее и на 22% дешевле [109]; 0,7 найденной ошибки на запуск, больше 79% из них исправляют [94]; доля исправленных выросла с 52% до 76%, больше 35% правок Autofix сливают [124].
- **Security Review** — агент безопасности PR на Automations и локальный skill `/review-security` [38]. По словам Cursor, время review упало с 4,8 до 3,8 минуты, а доля принятых находок выросла с 45–50% до 60–70% [152].
- **Vulnerability Remediation** — сканеры по расписанию, включая поиск CVE. Агенты исправления подтверждают находку exploit-тестом и открывают PR с исправлением [39].
- **PR Routing & Approval** — назначает reviewers. Одобряет PR с низким риском по оценке риска и файлам `APPROVAL_POLICY.md` и `ROUTING.md`. Ждёт около 8 минут результатов Bugbot и Security Review [40].
- **Rollouts** (Teams и Enterprise) — пишет план rollout для каждого PR. Потом проверяет телеметрию при deploy, через 20 минут, 1 час, 1 день и 3 дня. При регрессии открывает issue с кнопкой «Fix issue», которая запускает агента. Может поставить rollout на паузу или предложить PR с revert [41][152].
- **Code Tours** (в Origin) — AI проводит по PR в порядке, удобном для review. Агенты могут править тур [43].

### Browser, Design Mode и Canvases

- **Browser** — встроенная панель браузера [9].
  - Агент управляет ею через MCP: переход, клик, ввод, прокрутка, скриншот, консоль, сеть [9].
  - Cookies, localStorage и IndexedDB хранятся отдельно для каждого workspace [9].
  - Режимы одобрения: вручную, allowlist, auto-run. В Enterprise — allowlist доменов [9].
  - Пресеты устройств с поворотом экрана [64].
- **Design Mode / Annotate** (3.24.18+) [7][136].
  - Клик, Shift-клик или рамка помечают элементы или области страницы. Есть рисование, эллипс, прямоугольник и стрелка, правка текста на месте, CSS-инспектор и надиктовка заметок [7].
  - Batch edits отправляют несколько пронумерованных меток вместе [7].
  - Агент получает selector, стили, стек компонентов React, Vue или Svelte и обрезанный скриншот [7].
- **Canvases** (3.1, 2026-04-15) — интерактивные React-артефакты, которые агент строит рядом с чатом (команда `/canvas`) [10][16][90][129].
  - Сохраняются в списке workspace; их можно открыть снова и перезапустить со свежими данными [10].
  - **Publish** даёт коллегам read-only ссылку (платные планы с командой; с 2026-05-20) [10][109].
  - Cloud-агенты строят canvases с 2026-10-16 [108].
  - Plugins приносят готовые canvases, например Hex и Atlassian [20].
  - Canvas можно упаковать в skill [10].

### Mobile, Remote Control и self-hosted машины

- **iOS и iPad** [31][98][101][64]:
  - запуск агентов и наблюдение за ними; выбор, где работать: Cloud, Team Pool или My Machines;
  - полный review PR: squash merge, auto-merge, reviewers, «Fix with Agent»;
  - разметка Design Mode карандашом Apple Pencil, диктовка (в том числе в CarPlay), голосовые звонки;
  - push-уведомления: агент закончил, нужен ввод, PR готов к review;
  - Live Activities (живой виджет на экране блокировки iPhone) — до 8 агентов;
  - Inbox со статусами Working и Input Needed.
- **Remote Control** — управление локальным агентом с телефона. Тексты Cursor описывают его по-разному:
  - Документация: команда `/remote-control` (Cursor 3.9.8+) переносит цикл агента в облако, а вызовы инструментов идут на вашей машине. Есть опция «Keep this computer awake». В Teams и Enterprise функцию включает админ [31].
  - Changelog 2026-10-06: iOS-приложение соединяется с desktop; локальные агенты продолжают работать на компьютере; cloud-агенты не нужны; функция включена по умолчанию, кроме Enterprise; компьютер не должен засыпать [107].
  - Какое описание актуально, источники не говорят (не подтверждено).
  - При Remote Control на машине регистрируется только один локальный worker — так ответил сотрудник на форуме [192].
- **Self-hosted машины** (2026-09-02) [33][105][149].
  - Команда `agent worker start` регистрирует ноутбук, devbox или VM как «My Machines». Соединение только исходящее (HTTPS): Cursor не открывает соединений в сеть клиента [33][32][149].
  - Флаги: `--name`, `--worker-dir` (можно повторять), `--computer-use` (helper-приложение на macOS или X11 на Linux), `--connect-workspace` (живой workspace на Linux, 3.25+) [33].
  - Машину выбирают из Slack, GitHub или Linear параметром `worker=<name>`. Запрос к репозиторию, которого на машине нет, отклоняется без запасного варианта [33].
  - Пулы машин (раньше Team Pools, теперь называются Self-hosted Machines) масштабируются сами, усыпляют простаивающие машины и работают на AWS Lambda, Coder, Cloudflare, Daytona, Modal, Namespace, Vercel или E2B [33][64].
  - Один агент на worker. Простаивающий worker выходит с кодом 0 через час (`--idle-release-timeout`). После сна snapshot восстанавливается под тем же ID worker [34].
  - Для Kubernetes есть открытый Helm chart `anysphere/k8s-workers` [162]. Для Cloudflare Containers и AWS Lambda MicroVMs есть открытые шаблоны `anysphere/cloudflare-workers` и `anysphere/aws-lambda-workers` (Apache-2.0); по их README цикл агента держит Cursor, а инструменты выполняются в аккаунте клиента [232].
  - Лимиты источники называют по-разному: документация self-hosted — 10 000 workers на пользователя и на команду [32]; документация пулов — 200 на пользователя и 1000 на команду [34].

### Approvals и sandbox у локальных агентов

- **Run Modes** — режимы, которые решают, что агент делает без вопроса [13]:
  - **Auto-review** (по умолчанию с версии 3.6, 2026-05-29). Вызовы из allowlist идут сразу. Остальные shell-команды идут в sandbox. Всё прочее оценивает LLM-классификатор на сервере Cursor: Gemini 3.5 Flash Lite, запасной — Haiku [13][109].
    - Классификатор может читать файлы, чтобы оценить вызов. Если он блокирует, агент ищет другой путь или спрашивает человека [13][137].
    - Политика пишется простым английским текстом: `allow_instructions` и `block_instructions` в `~/.cursor/permissions.json` (пользователь) и `.cursor/permissions.json` (проект); оба файла Cursor объединяет. Команда может задать политику в dashboard — тогда она заменяет оба файла [13].
    - Документация прямо пишет, что Auto-review — не граница безопасности [13].
  - **Allowlist** (sandbox по желанию) и **Run Everything** [13].
- **Sandbox.** На macOS — Seatbelt; на Linux — Landlock и seccomp (механизмы ядра, которые ограничивают процесс), а если они недоступны, агент спрашивает человека; на Windows — WSL2 [13][121]. Файл `sandbox.json` задаёт режимы сети и дополнительные пути [13]. Read Access: System или Workspace с Read Allowlist (3.23) [13][65]. Дополнительная защита — для работы в браузере, удаления файлов и файлов вне workspace [13].
- **MCP:** каждое подключение и каждый вызов инструмента требуют одобрения, если они не в allowlist [12].
- **«Always Run»** добавляет команду в `terminalAllowlist` [64].
- **`CI=1`.** Shell-команды агента получают эту переменную окружения [85].

### Настройка: Rules, Skills, Hooks, Plugins, MCP

- **Rules:** `.mdc`-файлы в проекте с режимами always / intelligent / globs / manual; правила пользователя; правила команды; `AGENTS.md` [19]. Если `CLAUDE.md` повторяет `AGENTS.md`, дубль не загружается [64].
- **Skills.** Cursor называет Agent Skills открытым стандартом [16]. Skills загружаются и из `.claude/skills` и `.codex/skills` [16]. Встроенные: `/automate`, `/autopilot`, `/canvas`, `/create-*`, `/cursor-blame`, `/loop`, `/review`, `/review-bugbot`, `/review-security`, `/sdk`, `/split-to-prs` и другие [16]. Личные skills синхронизируются в ваши cloud-агенты [80].
- **Hooks** — скрипты, которые запускаются на события агента [17][18]:
  - 21 событие: 18 событий агента, 2 события Tab и `workspaceOpen`; среди них `preToolUse`, `beforeShellExecution`, `subagentStart`/`subagentStop`, `preCompact` и `stop` [17];
  - hooks бывают командами и prompt-ами. Exit code 2 запрещает действие. Падение, timeout и другие ненулевые exit code по умолчанию действие пропускают (fail-open); флаг `failClosed: true` заставляет блокировать и при них. Неверный JSON или ответ не по схеме действие блокирует [17];
  - `stop` получает статус run (completed, aborted, error) и `loop_count` и может вернуть `followup_message` — это запускает ещё один ход агента. По умолчанию не больше 5 таких ходов на скрипт (`loop_limit`; `null` снимает лимит). У hooks в формате Claude Code лимита по умолчанию нет. `subagentStop` работает так же [17];
  - cloud-агенты выполняют hooks проекта, команды и enterprise, но только hooks-команды: hooks сессии и MCP пропускаются, а в первых read-only ходах исследования hooks не работают [17][22];
  - **hooks Claude Code подключаются** из `.claude/settings*.json` и `~/.claude/settings.json`; настройка включена по умолчанию [18];
  - hooks у subagents получают `parent_agent_id` [64].
- **Plugins.** Cursor Plugins и открытый стандарт Agent Plugins. Marketplace с ручной проверкой. Marketplaces команды: в Teams — один, в Enterprise — без лимита [20]. Plugins — с 2026-02-17, marketplaces команды — с 2026-03-03 [109].
- **Customize** — страница, где всё это настраивается по уровням (пользователь, проект, команда); там же leaderboard команды [21].
- **MCP:** OAuth, HTTP или stdio; у cloud-агентов нет SSE и `mcp-remote` [26]. MCP Apps показывают структурированный вывод инструментов в интерфейсе [88]. HTTP MCP-серверы cloud-агентов работают через backend Cursor, и их конфиг не попадает в VM [26].

### Лимиты и расход в интерфейсе

- При исчерпании недельного пула — уведомление в редакторе. Дальше три пути: работать из предоплаченного кредита, ждать недельного сброса или повысить план [73].
- Auto Top-up (автопополнение кредита) и месячный потолок дополнительного расхода. Кредит не сбрасывается вместе с пулом и сгорает через 365 дней после покупки [50][73]. Раздел Credits с балансом и правилом автопополнения — в версии 3.23 [65].
- Cursor обещает не понижать качество и скорость запросов [50].
- Кнопки у лимита: «Buy Credits» и «Upgrade Plan»; блок снимается сразу после покупки (3.23). «Switch Model» рядом с «Buy Credits» (3.26). «Switch to Auto» отправляет сообщение заново через Auto (3.21) [65][64].
- Ошибки cloud-run показываются в лотке, в том числе во время автоматического повтора («retrying automatically»). У сбоя одна кнопка: Retry, Manage Usage или Manage Environments [65].
- Ошибка лимита у cloud-агента называет следующий шаг: включить on-demand, поднять лимит трат или перейти на модель Cursor или Auto. После переключения агент продолжает (неделя 2026-10-12) [67].
- Старые планы Start и Hobby: AI-функции стоят на паузе до сброса пула [51].
- Функция, которая сама ждёт сброса пула и продолжает работу агента, — не найдена (не подтверждено) [73].

## Принципы и подходы

- **Три эпохи AI-кодинга** (Michael Truell, 2026-02-26) [123].
  - Первая — Tab-автодополнение. Вторая — синхронные агенты. Третья — много автономных агентов в cloud VM, с которыми работают как с коллегами.
  - Cursor, по его словам, теперь не столько про написание кода, сколько про помощь разработчику в построении «фабрики» — системы агентов, которая делает его софт.
  - Роль человека смещается: он ставит задачу и задаёт критерии review, а не ведёт каждую строку.
  - Цифры: в марте 2025 пользователей Tab было примерно в 2,5 раза больше, чем пользователей агента. Теперь агентом пользуются вдвое больше людей, чем Tab. Использование агента выросло больше чем в 15 раз за год [123].
  - Исследование Cursor вместе с University of Chicago Booth: с июля 2025 по март 2026 число сообщений на пользователя в неделю выросло на 44%; выборка — 500 компаний [130].
- **Цель — «self-driving codebases»:** кодовая база, где агенты сами сливают PR, ведут rollout и следят за production [122]. Cursor 3 обещает вкладываться в IDE, пока кодовые базы не станут такими; запуск Rollouts повторяет эту цель [128][152].
- **Подъём уровня абстракции.**
  - Cursor форкнул VS Code, а не сделал расширение, чтобы самому решать, как выглядит интерфейс. Agents Window построен с нуля вокруг агентов [128].
  - Новый интерфейс поднимает человека на уровень выше, но даёт спуститься в детали. По словам Cursor, у него теперь есть все основные части: модель, продукт и runtime [128].
  - Projects снимает с человека управление отдельными агентами: он направляет саму работу [150].
  - В swarm единица работы — спецификация, а сама система начинает напоминать компилятор [140].
- **Принципы работы многих агентов** (исследования Wilson Lin) [117][118][140].
  - Равные агенты с общим файлом и блокировками не сработали: держали блокировки слишком долго или забывали их снять [117].
  - Сработало разделение на planners и workers и judge (агент, который оценивает итог) в конце каждого цикла [117]. Агенты написали больше миллиона строк кода. Модели GPT-5.2, по наблюдению автора, лучше держат долгую автономную работу [117].
  - Принципы (2026-02-05): система должна становиться устойчивее от сбоев (anti-fragile); решения — по эксперименту, а не по предположениям; проектировать под пропускную способность и принимать небольшую стабильную долю ошибок [118].
  - Перед релизом всё равно нужна финальная ветка, где все проверки проходят (green): агент снимает с неё snapshots и чинит их [118].
  - Роль integrator — единый центральный контроль качества — убрали [118].
  - Ограничения работают лучше инструкций [118].
  - Review lenses (разные взгляды на review) различаются тем, что видит reviewer: полный транскрипт worker, только его результат или только код. Reviewers запускали и на разных моделях. Ни один lens не ловит всё, но некоррелированные lenses складываются [140].
  - «Field Guide» — папка, которой владеют сами агенты. Её `index.md` автоматически подаётся каждому агенту на старте; единственное ограничение для агентов — бюджет строк [140].
  - Названы типовые сбои: split-brain design (две части системы принимают несовместимые решения), конкуренция planners, merge conflicts, «megafiles» (файлы, которые правят все агенты сразу) и ossification (код перестаёт меняться) [140].
- **Harness и окружение — это продукт.**
  - Качество агента Cursor меряет Keep Rate — долей предложенного агентом кода, которая осталась в кодовой базе [132].
  - Будущее, по словам Cursor, — multi-agent, и координация будет жить в harness, а не в отдельном агенте [132]. Свой harness Cursor улучшает автоматическим конвейером («software factory») [132].
  - Josh Ma (2026-06-02): окружение разработки — это продукт; агенту надо не мешать; окружения агентов должны чинить себя сами [135].
  - Перенос durable execution (выполнения, которое переживает сбои) на Temporal поднял надёжность с одной «девятки» до больше чем двух. Temporal выполняет больше 50 млн действий в день в больше чем 7 млн workflows [135].
- **Автономия — регулятор, а не выключатель** [137].
  - Auto-review оценивает каждое действие в контексте. Блок сначала возвращается агенту, а не человеку [137].
  - Классификатор блокирует около 4% действий. Около 7% чатов получают хотя бы одно прерывание человеком. У некоторых enterprise-клиентов раньше блокировалось около 40% действий [137].
  - Auto-review — режим по умолчанию для новых пользователей [137]. Документация при этом пишет, что это не граница безопасности [13].
- **Нейтральность моделей и свои модели.**
  - Cursor называет нейтральность моделей основой продукта [141]. Но включённый в подписку пул теперь — Grok [73].
  - Собственный бенчмарк CursorBench 4.0 ставит первым Gemini 4 Carbon High (60,4%), а Grok 4.7 Extra High — только тридцатым (46,3%) [158].
  - Cursor пишет, что публичные бенчмарки искажены. В 63% успешных решений Opus 4.8 Max на SWE-bench Pro агент нашёл готовое исправление, а не вывел его. Без истории git и с ограниченным интернетом Composer 2.5 падает с 74,7% до 54,0% [138].
  - Вместе со SpaceXAI Cursor обучает с нуля модель намного больше Composer, на 10× больше вычислений [133].
- **Больше информации между человеком и агентом.** Canvases и Design Mode Cursor объясняет как способы передать больше информации в обе стороны и сократить разрыв между тем, что видит человек, и тем, что понимает агент [129][136].
- **Миссия.** Anysphere называет себя прикладной исследовательской лабораторией о будущем программирования. Цель — свести к нулю расстояние между идеей и её реализацией. Компания хочет быть местом для самостоятельных инженеров-исполнителей [160].

### Чем отличается подход

- **Cursor владеет почти всеми слоями:**
  - редактор — форк VS Code, потом интерфейс с нуля [128];
  - модели — Composer, потом Grok [126][139];
  - runtime — VM с durable execution на Temporal [135];
  - git-хостинг и stacked PR — Origin и купленный Graphite [42][115];
  - мониторинг production — Rollouts и купленный Firetiger [152][145];
  - вычисления — SpaceX [147].
- **Cloud-first.** Автономные агенты работают в VM и умеют пользоваться компьютером [122]. Долгая работа должна идти в облаке, а не на ноутбуке; Projects намеренно сделан cloud-first [199].
- **Успех меряют слитыми PR и Keep Rate**, а не чатами или токенами [123][132][113][150].
- **Автономией управляет классификатор каждого действия**, а не только статичный allowlist. Документация прямо пишет, что это не граница безопасности [137][13].
- **Swarm-исследования публикуются с долларовой стоимостью** для каждого набора моделей [140].
- **Кодинг продаётся в потребительском пакете** вместе с соцсетью и чат-ботом [72].

## Как это устроено внутри

### Где работает каждая часть

- **Inference** — всегда у Cursor, даже когда цикл агента идёт локально через SDK [47].
- **Локальные агенты** — desktop и CLI. Из Agents Window один человек ведёт local, worktree, cloud и remote-SSH агентов в нескольких репозиториях [1][128]. В версии 3.0 cloud-агентов убрали из редактора: они живут в Agents Window [88].
- **Cloud-агенты** — Firecracker microVM в отдельном аккаунте AWS [29].
- **Self-hosted** — Cursor ведёт цикл агента, inference и планирование; worker выполняет правки и команды; соединение только исходящее [32][149]. Kubernetes runner это подтверждает: контроллер забирает запросы (claim) и создаёт одноразовые Pods (`restartPolicy: Never`); можно держать заранее подключённые workers (`--warm-idle N`) [162].
- **Протокол SDK** знает runtime AUTO, LOCAL и CLOUD и типы облачного окружения CLOUD, POOL (свой пул) и MACHINE (одна машина) [161].
- **Backend.** Go-пакет протокола — `github.com/anysphere/everysphere/anygo/...` [161]. Это намекает, что backend этих вызовов написан на Go во внутреннем монорепозитории; это вывод (не подтверждено).

### Цикл агента

- Агент — это инструкции, инструменты и модель. Harness Cursor настроен под каждую модель. Лимита на число вызовов инструментов в задаче нет [2]. Курс Cursor описывает агента как инструменты, которые вызываются в цикле [157].
- **Вмешательство в работу.** Сообщение во время работы по умолчанию встаёт в очередь. «Send now» вставляет его на следующем вызове инструмента [2]. Side chats задают вопросы, не мешая работе [2]. Инструмент вопросов не останавливает агента [2]. Инструмент Await (3.0) ждёт фоновые команды и subagents [88].
- **Долгие команды.** `/goal` держит одну цель на много ходов; `/loop` повторяет prompt по интервалу или даёт агенту выбрать время пробуждения [2]. С 2026-08-19 у cloud-агентов есть `/goal`, steering, custom modes и subagents на своих VM [103].
- **Checkpoints** — локальные снимки вне git; восстановление возвращает только файлы [2].
- **Автоматические ходы от hook.** Hook `stop` получает статус run и `loop_count` и может вернуть `followup_message` — тогда начинается ещё один ход. Лимит по умолчанию — 5 таких ходов на скрипт; у hooks в формате Claude Code лимита нет [17].
- **`CI=1`** в окружении shell-команд агента [85].

### Планирование и декомпозиция

- **Plan Mode:** вопросы, исследование кода, редактируемый план в Markdown, сборка после одобрения [5].
- **`/multitask`** запускает асинхронные subagents вместо очереди [91]. **Build in Parallel** запускает независимые части плана параллельно, зависимые — по порядку [93][77]. **Split into PRs** делает резервный snapshot и предлагает план разбиения на одобрение [93].
- **Исследовательский harness** — эксперименты из блога, не функции продукта:
  - равные агенты с блокировками не сработали: 20 агентов давали пропускную способность 2–3 агентов [117];
  - оптимистичная конкурентность сделала агентов слишком нерешительными [117];
  - сработали planners, которые рекурсивно порождают sub-planners, workers, которые только выполняют, и judge; отдельный integrator убрали [117][118];
  - поздняя схема: root planner, subplanners и workers, каждый возвращает сводку своей работы; глобальных блокировок нет; небольшая стабильная доля ошибок принимается и вычищается на финальной ветке, где всё проходит; каждое действие пишется в лог, чтобы запуск можно было воспроизвести; агенты ведут заметки в `scratchpad.md`; узким местом стал дисковый ввод-вывод [118];
  - пик — около 1000 commit в час и 10 млн вызовов инструментов за неделю сборки браузера [118];
  - стоимость одной задачи бенчмарка (SQLite на Rust): от $1339 (Opus 4.8 — planner, Composer 2.5 — workers) до $10 565 (GPT-5.5 во всех ролях); workers тратят не меньше 69% токенов [140];
  - новая система, по заметкам, доходит почти до 1000 commit в секунду; merge conflicts упали с больше чем 70 000 до меньше чем 1000 [140];
  - качество у всех наборов моделей похожее; код одного запуска (Opus 4.8 в одиночку) открыт: https://github.com/cursor/minisqlite [140];
  - в продуктовом посте long-running агенты предлагают план и ждут одобрения, несколько агентов проверяют друг друга, работа идёт 25–52 часа [120].

### Параллельность и координация

- **Subagents.** У каждого своё окно контекста; foreground или background. Несколько вызовов Task в одном сообщении идут параллельно. В swarm у каждого свой worktree или своя VM и ветка, и изменения остаются там до merge родителем. Вложенность — два уровня. Упавший subagent возвращает ошибку; родитель повторяет его или продолжает по ID [15].
- **Projects.** Координатор планирует, раздаёт и докладывает, но не пишет код. Он работает как cloud-агент и может запустить локального агента. Общие файлы контекста синхронизируются между машинами Project. Подписки на Slack, расписание, PR и CI будят координатора [3][83][150].
- **Стартовые правила координатора** (seed rules — шаблон из справки, который пользователь сам вставляет в `preferences.md` Project) [83]:
  - один worker на PR, запуск от корня; никаких промежуточных координаторов со своими workers;
  - никаких произвольных лимитов времени для workers;
  - одна поправка на worker по одной теме; если поправок больше двух — остановить worker и перезапустить его с одним общим prompt;
  - каждый PR проходит одну и ту же последовательность:
    - открыть сразу готовым к review, не draft;
    - подписаться на CI;
    - каждые 2–3 минуты запускать `git merge-tree` против main, чтобы рано ловить конфликты;
    - ответить на каждый тред Bugbot и безопасности;
    - читать треды review напрямую (`origin pr thread list`), потому что neutral check тоже несёт находки;
  - готовность PR координатор проверяет сам и не принимает за неё отчёт worker;
  - ночная работа идёт по плану на одну страницу, с ежечасной внутренней проверкой и таймером отчёта;
  - статус merge и статус CI называть отдельными фактами и перед каждым отчётом проверять оба самому; никогда не писать просто «clean» или «green»; не заявлять о тесте, который не запускал;
  - вести handoff-файл координатора (файл с текущим состоянием для следующей сессии) и обновлять его;
  - каждая поправка владельца в тот же ход становится правилом;
  - каждый PR проходит полный набор проверок; merge и deploy координатор не делает.
- **Multiplayer.** У каждого человека свой координатор и workers, расход — на него. Доска задач и Agent Store общие. Сообщения между координаторами помечены как недоверенный ввод агента; отвечают на них в side chat, который не передаёт секреты [154][3].

### Изоляция

- **Локальные worktrees.**
  - Setup-файл `.cursor/worktrees.json` с командами под ОС; копирование файлов вроде `.env` через `$ROOT_WORKTREE_PATH`; симлинки на зависимости не рекомендуются [14].
  - Cursor держит 25 самых новых worktree на машину по всем workspace; в примере настроек проверка идёт раз в 6 часов [14].
  - CLI-флаг `-w` создаёт worktree в `~/.cursor/worktrees/<repo>/<name>` [46].
  - «Move to Cloud» переносит разговор, но не незакоммиченные изменения [80].
- **Cloud VM.**
  - Жизненный цикл: старт, подготовка, работа, сохранение, передача результата как PR, потом сон и удаление по таймерам [29].
  - У каждого агента свои ключи шифрования AES-256 [29].
  - Snapshots, которые не использовались 30 дней, удаляются [29].
- **Окружение** [23]:
  - порядок: личное окружение, окружение команды, `.cursor/environment.json`;
  - агент может настроить окружение меньше чем за 10 минут;
  - Dockerfile с кэшем слоёв;
  - идемпотентный install-скрипт выполняется в каждом Build;
  - start-команда и терминалы работают в tmux, общем с агентом;
  - доступ к AWS через STS с ключами на 1 час, которые обновляются за 15 минут до конца, или через OIDC.
- **Builds** — заранее подготовленные снимки окружения [24][144]:
  - стадии: trigger, prepare, snapshot, activate, start [24];
  - trigger: расписание, изменение конфига, вручную или по просьбе агента [24];
  - упавший Build никогда не заменяет рабочий; Build хранит только состояние диска [24];
  - порог устаревания Build по умолчанию — 24 часа: если включена настройка Update stale builds и Build старше порога, агент на старте подтягивает свежий код ветки по умолчанию; таймаут install по умолчанию — 90 минут, настраивается от 5 до 300 [24];
  - блог: Builds идут каждый час; новые агенты делают fork живой машины, а не восстанавливают диск; внутри загрузка стала в 10 раз быстрее, а время до первого токена — в 3 раза [144].
- **Self-hosted workers** [34][33][162]:
  - один агент на worker; простаивающий worker выходит с кодом 0 через час (`--idle-release-timeout`) [34];
  - после сна snapshot восстанавливается под тем же ID worker [34];
  - «My Machines» направляет запрос на машину по имени (`worker=`); запрос к чужому репозиторию отклоняется без запасного варианта [33];
  - в Kubernetes worker Pod одноразовый; при включённом сне у worker есть свой PVC `ws-<worker-id>`, и следующий Pod подключает его снова — агент продолжает на своих файлах, но процессы не переживают сон [162].

### Состояние и восстановление сессий

- **Cloud Agents API v1** [35]:
  - агент долговечный и состоит из серии runs; активным может быть только один run, иначе API отвечает `409 agent_busy`;
  - follow-up либо вставляется в активный run, либо встаёт в очередь; повтор вставленного сообщения может доставить его дважды;
  - состояния агента: active, idle (машина может спать), archived;
  - состояния run: creating, running, ожидание фоновой работы, затем finished, error, cancelled или expired;
  - поток событий (SSE — server-sent events) продолжается с `Last-Event-ID`;
  - `agentId`, выбранный клиентом (формат `bc-<uuid>`), защищает от дублей: повторный POST с тем же `agentId` возвращает `409 agent_id_conflict`, а не создаёт второго агента.
- **Лимит API.** Для Cloud Agents API — «standard rate limiting», то есть общий лимит по умолчанию: 20 запросов в минуту; сверх — `429`. `Retry-After: 60` документирован только для Admin API и Organization API [36].
- **SDK.** Локальное хранилище — SQLite по умолчанию, JSONL или своё. Оно хранит агентов, runs, события runs и checkpoints. Сервис создаёт, продолжает, наблюдает и отменяет агентов и читает расход [47][161].
- **Продолжение работы.**
  - CLI продолжает чат через `--resume` или `agent resume` и показывает список через `agent ls` [46].
  - Уже законченные вызовы инструментов при продолжении не повторяются (CLI v2026.10.17) [71].
  - Агентов IDE, остановленных падением extension host, можно продолжить (IDE 3.26) [66].
- **Agent Store у Projects.** Два места: `/cursor/stores/self` для Project и `/cursor/stores/user` для человека. Внутри — `preferences.md`, трекер `notes.md`, `workflows/` и `principles/`. По шаблону seed rules координатор ведёт handoff-файл и читает его первым после сжатия контекста: сжатие стирает рабочую память, но не хранилище [3][83].
- **Хранение.** Разговоры хранятся бессрочно по умолчанию [29]; можно ограничить 90 днями [28]. Origin хранит write-ahead log в S3 [148].

### Память и контекст

- **Dynamic context discovery** (2026-01-06) [116]:
  - длинный вывод инструментов пишется в файл, и агент читает его через `tail`;
  - после сводки полная история чата остаётся доступной как файл для поиска;
  - описания MCP-инструментов хранятся файлами в папках — это сократило токены на 46,9%.
- **Экономия токенов** (2026-09-23) [151]: стоимость токенов упала на 7%; системный prompt стал короче примерно на 66%; загрузка инструментов по запросу сократила токены на описания инструментов на 60%; явные точки prompt cache уменьшили холодные промахи кэша на 20%.
- **Сжатие контекста.** У предела контекста агент сжимает разговор и продолжает; последний запрос сохраняется дословно (IDE 3.24 [66]; CLI v2026.10.08 [71]). С CLI v2026.10.22 сводка считается в фоне [71]. Разбивка расхода контекста — с 2026-05-06 [92].
- **Долгая память.**
  - Automations: инструмент Memories хранит `MEMORIES.md` вне рабочего дерева; недоверенный ввод может его испортить [30].
  - Боты Agent SDK пишут по записи на ход в `memory/journal.jsonl` [49].
  - Bugbot учит правила review, в том числе добавленные через `@cursor remember` [37].

### Проверка качества

- **Bugbot.** Check завершается neutral, когда есть находки. Review инкрементальный. Уровни effort — Low, Default, High, Smart. Autofix запускает cloud-агента; прямой push в ветку — не больше 3 попыток на PR; нужен кредит или on-demand [37]. Около 90 секунд на review на Composer 2.5 [95]; 0,7 ошибки на запуск, больше 79% исправляют [94]; доля исправленных выросла с 52% до 76%, больше 35% правок Autofix сливают [124].
- **Другие проверяющие агенты.** Agent Review после каждого commit или по `/agent-review`, Quick или Deep [4]. Security Reviewer: 4,8 → 3,8 минуты на review, доля принятых находок 45–50% → 60–70% [152]. PR Routing & Approval оценивает риск PR по файлам политики и ждёт около 8 минут результатов Bugbot и Security Review [40]. Rollouts проверяет deploy через 20 минут, 1 час, 1 день и 3 дня; может остановить rollout или предложить PR с revert [41][152].
- **Самопроверка cloud-агентов:** computer use, remote desktop и артефакты — скриншоты и видео [26][122]. Внутри у Cursor ещё есть инструмент записи экрана и инструмент диагностики окружения [142].
- **CI-цикл** [26]:
  - агент подписывается на свои PR, заканчивает ход и просыпается follow-up при событии; пачка событий — одно пробуждение;
  - подписка живёт до 180 дней; подписываться могут только агенты, принадлежащие человеку;
  - CI-подписка ждёт все checks, поэтому один зависший check останавливает агента;
  - автоисправление CI: только GitHub Actions, только Teams и Enterprise; пропускается после push человека, после follow-up или если тот же check падает на базовом commit; останавливается после 10 follow-up.
- **`/autopilot`** отдаёт PR cloud-агенту, который разбирает review, конфликты и упавшие checks до готовности к merge; появился как `/babysit` в 3.7 [15][96][16].
- **Где центр проверок.** Проверки Cursor сосредоточены на PR и deploy. Ближайшая локальная проверка — Agent Review после каждого commit [4].

### Восстановление после сбоев

Общий приём — один ограниченный автоматический повтор, потом одно действие для человека.

- **Зацикленные рассуждения.** Если рассуждение повторяется, шаг останавливается и повторяется один раз с подсказкой (IDE 3.22, 2026-09-24) [66].
- **Отклонённый вывод модели.** Если провайдер отклонил вывод Grok до вызова инструмента, шаг повторяется один раз (CLI v2026.09.28) [71].
- **Ошибки cloud-агента** видны в лотке, в том числе во время автоматического повтора. У сбоя одна кнопка: Retry, Manage Usage или Manage Environments (3.22) [65].
- **Зависший extension host.** Если он не отвечает около минуты, его перезапускают, с растущей паузой при повторных падениях (IDE 3.23) [66].
- **Нехватка памяти.** Если команду cloud-агента убили из-за памяти, агенту об этом сообщают (IDE 3.24) [66].
- **SDK** [69]:
  - зависшее соединение падает с ошибкой, помеченной как retryable; повторы прекращаются через 3 минуты (1.0.34);
  - разовый запрос отправляется заново один раз; потоковые runs никогда не воспроизводятся заново (1.0.38).
- **Rate limit MCP у cloud-агентов** (неделя 2026-10-05). Если MCP-сервер ограничил инструмент, агент ставит на паузу только этот инструмент на время, которое просит сервер, и продолжает пользоваться другими инструментами сервера [67].
- **Automations.** Сбой входа в MCP не останавливает run — он идёт без инструментов этого сервера. Запуски по расписанию опаздывают не больше чем на 5 минут и никогда не стартуют раньше [30][70].
- **Ограничители циклов:** hook `stop` — 5 ходов, автоисправление CI — 10 follow-up, Bugbot Autofix — 3 попытки, повторы SDK — до 3 минут [17][26][37][69].
- **Durable execution.** Cloud-агенты работают на Temporal; надёжность выросла с одной «девятки» до больше чем двух [135].
- Документированной политики повторов при ошибках провайдера (HTTP 5xx) у локальных агентов заметки не нашли (не подтверждено).

### Лимиты и стоимость

- **Пулы** [73][72]:
  - The X Subscription — один недельный пул на собственные модели Cursor (Grok 4.7, 4.6, 4.5 и Composer 2.5); пул общий с приложениями Grok;
  - сторонние модели оплачиваются из предоплаченного кредита;
  - на старых планах — месячные пулы; они сбрасываются с циклом оплаты, сразу для всей команды.
- **У лимита:** на планах X — кредит, ожидание недельного сброса или повышение плана; на старых — on-demand или повышение плана [73].
- **В продукте:** «Buy Credits» и «Upgrade Plan», блок снимается после покупки (3.23); «Switch Model» (3.26); «Switch to Auto» отправляет заблокированное сообщение заново (3.21) [65]. Ошибки лимита у cloud-агентов называют следующий шаг, и после переключения агент продолжает [67]. Automation при rate limit предупреждает, что лимит может действовать на весь Cursor, и советует повторить позже [70].
- **Контроль трат:** лимит трат при первом использовании cloud-агентов [22]; Automations от service account списывают с пула команды [30]; deploy Agent SDK — не больше 20 на владельца и 100 за 24 часа, если Cursor включил команде эти ограничения [49].
- **Маршрутизация по стоимости.** Cursor Router использует предсказатель сложности «Compass»: простые ходы — на Grok, сложные — в следующий маршрутизатор. Intelligence на 68% дешевле Opus 4.8, Balance — на 41% [143].
- **Стоимость параллельности.** Пять параллельных subagents тратят примерно в пять раз больше токенов [15]. Swarm на одну задачу бенчмарка стоил от $1339 до $10 565 [140].
- **Протокол знает время сброса.** Коды ошибок `USAGE_LIMIT_EXCEEDED` (14) и `RATE_LIMIT_EXCEEDED` (18). В деталях ошибки — `retry_after` и `RateLimitInfo` с полями `limit`, `remaining` и `reset_epoch_seconds` [161]. Клиент может узнать время сброса, но функции Cursor, которая по нему продолжает работу, заметки не нашли.
- **5-часового окна** в документации нет. Автоматического ожидания сброса с продолжением работы заметки не нашли (не подтверждено) [73][161].

### Права и безопасность

- **Локальные агенты.**
  - Run Modes: Auto-review (по умолчанию с 3.6), Allowlist, Run Everything. Auto-review — классификатор на сервере Cursor (Gemini 3.5 Flash Lite, запасной — Haiku); документация пишет, что это не граница безопасности; команды пишут правила allow и block на английском в `permissions.json` [13].
  - Классификатор в цифрах: работает в том же соединении, что и агент; блокирует около 4% проверенных действий; прерывает около 7% чатов; построен на 6122 размеченных примерах [137].
  - Sandbox ОС: Seatbelt на macOS; Landlock и seccomp на Linux, а без них — вопрос человеку; WSL2 на Windows [13][121]. Sandbox на 40% сократил остановки на одобрение; примерно треть запросов выполняется в sandbox [121].
  - MCP-вызовы требуют одобрения, если их нет в allowlist [12].
  - Hooks: exit code 2 блокирует действие; падение, timeout и другие ненулевые exit code по умолчанию его пропускают (`failClosed: true` это меняет); неверный JSON в ответе блокирует. Hooks в формате Claude Code принимаются. Cloud-агенты выполняют только hooks-команды и пропускают hooks сессии и MCP; в ранних read-only ходах исследования hooks не работают [17][22].
- **Cloud-агенты.**
  - Не спрашивают одобрения: внутри VM агент выполняет любую команду терминала [13][28].
  - Секреты трёх видов: Environment Variable, Runtime Secret (маскируется в выводе) и Build Secret [28].
  - Исходящая сеть: всё разрешено; список по умолчанию плюс список команды; только список команды. Админы Enterprise могут закрепить выбор [28].
  - HTTP MCP-серверы проходят через backend Cursor, и их конфиг не попадает в VM [26].
  - Доступ агента наследуется от человека и никогда не расширяется. Commit подписываются ключами Ed25519 в HSM [29].
  - Настройка команды решает, кто может писать follow-up чужому агенту; документация предупреждает о lateral movement между аккаунтами [27].
  - Apps перед публикацией проверяются на секреты, файлы учётных данных, `.env` и source maps, плюс AI security review [25].
- **Сертификаты.** Страница безопасности (прочитано 2026-11-13) называет AIUC-1 (стандарт для AI-агентов), ISO/IEC 27001:2022 и ISO/IEC 42001:2023, а также отчёт SOC 2 Type II [228]. В посте об AIUC-1 (2026-08-13) ISO 27001 и ISO 42001 ещё были «в работе» [146].
- **Инцидент 2026-10-29** [229].
  - В marketplace расширений VS Code у Cursor примерно с 2:27 до 13:35 по тихоокеанскому времени лежали вредоносные версии 2.1.312 и 2.1.313 расширения `Anthropic.claude-code` для Windows и macOS. Anthropic их не выпускала.
  - Код собирал данные о машине и пользователе, добавлял SSH-ключ атакующего, ставил автозапуск и пытался открыть обратный SSH-туннель. Включить SSH-сервис без прав администратора ему обычно не удавалось.
  - Cursor убрал версии, на время выключил marketplace, сменил ключи, пересобрал marketplace и вместе с хостингом отключил сервер атакующего. Пост даёт индикаторы компрометации и шаги очистки.
- **Защита аккаунта.** Пользователи пишут, что нет 2FA и что не-админы по умолчанию могут менять настройки расхода [164]; на форуме есть запрос на 2FA [225].

- **Во время работы:** инструмент вопросов [2]; статус Input Needed [68]; очередь или вставка сообщений [2][35].

### Наблюдаемость

- Cursor Cloud MCP даёт агентам диагностику их собственных runs. События: setup, PR создан, артефакт создан, сбой входа в MCP [26]. У каждого Build есть provenance ID (метка происхождения) [24].

### Открытый код вендора: модули и файлы

Сам продукт закрыт. Ниже — два из открытых репозиториев вендора, ближайшие к агентам; файлы прочитаны на указанных commit. Остальные открытые репозитории перечислены в начале досье [232].

- **`cursor/sdk-bridge`** (MIT; commit `6c91010`, 2026-10-27, «Sync sdk.v1 protos from Cursor SDK release 1.2.0») [161]. Bridge — небольшой локальный сервер. Он встраивает TypeScript SDK `@cursor/sdk` и отдаёт его через Connect/gRPC-Web, чтобы агентами можно было управлять из любого языка.
  - [`proto/sdk/v1/sdk_agent_service.proto`](https://github.com/cursor/sdk-bridge/blob/6c9101088c18fab95c73d2dd68ca11d6fbf7d483/proto/sdk/v1/sdk_agent_service.proto) — сервис `SdkAgentService`: `CreateAgent`, `ResumeAgent`, `Send` (поток `RunStreamMessage`), `WaitLiveRun`, `GetRun`, `ListRuns`, `ObserveRun`, `CancelRun`, `ArchiveAgent`, `DeleteAgent`, `ListArtifacts`, `DownloadArtifact`, `GetUsage` и другие.
  - [`proto/sdk/v1/sdk_messages.proto`](https://github.com/cursor/sdk-bridge/blob/6c9101088c18fab95c73d2dd68ca11d6fbf7d483/proto/sdk/v1/sdk_messages.proto) — `RUNTIME_AUTO`, `RUNTIME_LOCAL`, `RUNTIME_CLOUD` (строки 24–26) и `CLOUD_ENVIRONMENT_TYPE_CLOUD`, `_POOL`, `_MACHINE` (строки 62–68).
  - [`proto/sdk/v1/sdk_errors.proto`](https://github.com/cursor/sdk-bridge/blob/6c9101088c18fab95c73d2dd68ca11d6fbf7d483/proto/sdk/v1/sdk_errors.proto) — коды `SDK_ERROR_CODE_USAGE_LIMIT_EXCEEDED = 14` и `SDK_ERROR_CODE_RATE_LIMIT_EXCEEDED = 18` (строки 33 и 37); `RateLimitInfo` с `limit`, `remaining` и `reset_epoch_seconds` (строки 44–49); `SdkErrorDetails` с `retry_after` и `rate_limit` (строки 52–66); `go_package` `github.com/anysphere/everysphere/anygo/proto/sdk/v1` (строка 8).
  - [`proto/sdk/v1/sdk_store_callback_service.proto`](https://github.com/cursor/sdk-bridge/blob/6c9101088c18fab95c73d2dd68ca11d6fbf7d483/proto/sdk/v1/sdk_store_callback_service.proto) — `SdkStoreCallbackService.CallStore`. При своём хранилище bridge пересылает операции хозяйскому процессу. Подхранилища: `agents`, `runs`, `runEvents`, `checkpoints`; операции: get, create, update, delete, list и append (только для `runEvents`).
- **`anysphere/k8s-workers`** (Apache-2.0; commit `7e12775`, 2026-10-14) [162].
  - [`README.md`](https://github.com/anysphere/k8s-workers/blob/7e12775f0feb923a699a9e834a9c7f209b1f44a1/README.md) — Cursor держит цикл агента. Контроллер `agent worker controller` в кластере на каждый spawn создаёт Pod с `restartPolicy: Never`. Worker открывает исходящее соединение к Cursor и выполняет вызовы инструментов внутри сети кластера. Chart заменяет устаревший оператор `worker-set-controller` и его CRD `WorkerDeployment`.
  - [`chart/README.md`](https://github.com/anysphere/k8s-workers/blob/7e12775f0feb923a699a9e834a9c7f209b1f44a1/chart/README.md) — два режима: claim-then-spawn (по умолчанию: контроллер забирает запрос и потом создаёт Pod) и `--warm-idle <N>` (заранее подключённые workers). Режим `--session-token`: токен действует только для одного claim, при пробуждении выдаётся новый; с `--warm-idle` этот режим несовместим. Сон (hibernation): Pod выходит после `idleReleaseTimeout`, claim остаётся; если follow-up пришёл в окне переподключения, контроллер снова запускает hook с `CURSOR_WAKE=1` и тем же worker id, новый Pod подключает тот же PVC `ws-<worker-id>`, и агент продолжает на своих файлах. Процессы сон не переживают — только диск.
  - [`chart/templates/reaper-cronjob.yaml`](https://github.com/anysphere/k8s-workers/blob/7e12775f0feb923a699a9e834a9c7f209b1f44a1/chart/templates/reaper-cronjob.yaml) — CronJob, который удаляет устаревшие PVC workspace и завершённые Pods worker.

  - В июле тема вернулась: 84 сообщения и 297 лайков [177]. Toby_Catlin пишет, что почти каждый релиз меняет умолчания в пользу агента; простой настройки «всегда открывать IDE» до сих пор нет [177].
  - Сотрудник объяснил, что окно по умолчанию отличается у разных людей и версий из-за пользовательских тестов [179].
  - Жалобы на яркую кнопку Agents Window, которая не учитывает тёмные темы, и на повторяющиеся промо-письма и диалоги [179].
- **Сторонние агенты вытеснены из боковой панели.** С 3.15.6 (август 2026) правая панель отдана только своему агенту Cursor: расширения Claude Code, Codex, Cline и Roo туда больше не встают. Сотрудники ответили, что это намеренно [184][185].
  - Пользователи пишут, что для них это решающая причина уйти. Некоторые откатывают версию и впервые выключают автообновление [184][185].

- **Функции редактора убирают.** Cmd+K в редакторе, вместе с генерацией команд в терминале, убрали 2026-10-26 — 73 сообщения и 369 лайков [186]. Раньше были мегатред о раскладке в декабре 2025 (368 сообщений, 1057 лайков): обновления сбивали раскладку пользователей [187]; и тред ноября 2025 с просьбой не выпускать нестабильные сборки (259 лайков) [188].

### Что ругают: worktrees и параллельная работа

- **Worktrees в v3.**
  - Pre-release сборки марта 2026 потеряли опцию worktree. Сотрудники сначала назвали её временно недоступной, потом заменили командами `/worktree` и `/best-of-n` [182].
  - На HN пользователи Conductor скучают по автоматическому worktree на каждого агента. babelfish выбрал Worktree, а агент всё равно работал в `main` [164]. Пользователь HN процитировал тогдашнюю документацию: автоматическое управление worktree убрали в 3.0, теперь им управляет агент [164].
  - На форуме пишут, что работать с worktree в v3 стало хуже [182]. Новая боковая панель группирует чаты по URL git remote, поэтому worktrees и клоны одного репозитория сливаются в одну секцию. Не видно, в каком worktree работает агент; для схем с несколькими клонами вид называют бесполезным [181].
  - huntercaron (HN): у Conductor и Superset лучше, потому что их панель построена вокруг PR и worktrees [164].
  - Автоматическая чистка worktree (лимит 25) удаляет и worktree в корне Cursor, созданные не им [14]. Жалоб на это в прочитанных тредах нет; вред для пользователей не найден, но и не исключён (не подтверждено).
- **`/best-of-n`** обсуждают мало. jiggunjer сравнил Composer 2 и GPT-5.3 Codex — Composer чуть лучше. Другой комментатор хочет состязательный review несколькими моделями [164].
- **Сомнения в параллельности** [164]: Aurornis — узкое место в review; simplyluke — параллельные агенты помогают с мелкими правками, но не с глубокой работой; mtrifonov — последовательная работа даёт работающий код; fragmede — переключение контекста изматывает.
- **Пост о swarm** (278 очков) [166]: комментаторы подозревают запоминание — переписывание SQLite на Rust, вероятно, есть в обучающих данных — и подгонку под бенчмарк. Идеи оркестрации, по их мнению, не новы, а harness не опубликован. Один комментатор всё же считает иерархию агентов полезной.
- **`/multitask` и subagents.**
  - В 3.2 агенты зависали на grep и шагах subagents; пользователи откатывались на 3.1; сотрудники назвали это известным багом производительности [189].
  - По заголовкам тем: используется не та модель, что выбрана; голосовые отчёты параллельных агентов перебивают друг друга [225].
  - dbdbdb: 18 независимых задач Cursor оркестровать не смог — subagents зациклились и ни один не закончил; он открыл по чату на задачу вручную [190].
  - На запрос Dynamic Workflows как в Claude Code сотрудник ответил: встроенного сохраняемого runtime оркестрации нет, пишите скрипты над CLI [191].
- **Локальные workers.** thomasr789 перешёл с Claude и запускает около 10 агентов; они зависают на setup или планировании. Сотрудник ответил, что при Remote Control на машине регистрируется только один локальный worker [192].

### Что ругают: cloud-агенты, Projects, Automations

- **Настройка cloud-агентов.** На старте спрашивали, как агенту получить `.env`, базу данных и учётные данные [193]. Composer отказывался записывать демо, которые Codex и Opus записывали [193]. Multi-repo не было с января по март (сотрудник: в roadmap) [194]; вышло 2026-05-13 [109].
- **Надёжность cloud-агентов:**
  - агент, работавший 10 часов, сломал страницу веб-агентов (2026-03-09) [195];
  - cloud-агенты то работали, то нет 24 часа (2026-05-19) [174];
  - внутренние ошибки 2026-09-17 [196];
  - все запуски падали больше 6 часов 2026-10-29/30, потом сотрудник извинился [197];
  - вызовы инструментов неделями падали в WSL в июне 2026 [198];
  - по заголовку темы, веб-агенты всегда стартуют в дорогом режиме Fast [225].
- **Платное облако.** Один комментатор HN считает cloud-only функции способом заработать и сомневается, что они защищают Cursor от конкурентов. jrsj платил бы за места или за использование, если бы внутри работала его подписка Claude Max, как в Conductor [164].
- **Projects** [199][200][201]:
  - просят, чтобы координатор по умолчанию отдавал работу локальным агентам; сотрудник ответил, что Projects намеренно cloud-first, чтобы планирование шло при закрытом ноутбуке [199]; есть отдельная тема о координаторе с локальными агентами [200];
  - просят запоминать блокер и следующий шаг каждой задачи, чтобы один застрявший worker не тормозил весь проект [199];
  - у одного пользователя Projects пропали из списка (2026-10-27) [201];
  - на HN — ноль комментариев [175].
- **Automations.**
  - Запросы: multi-repo, чтобы не дублировать одного агента-исправителя на каждый репозиторий (Nick_Misasi, Chris_Combe) [202]; Automations как код, потому что настройку через UI нельзя воспроизвести, как GitHub Actions (greaveselliott) [203]; API для управления и мониторинга — одна команда проектирует граф примерно из 20 automations от идеи до deploy [204].
  - До августа сотрудники только изучали декларативный формат и API [203][204]. К ноябрю документация описывает Terraform-ресурс `cursor_platform_workflow` и endpoints automations в Cloud Agents API [30][35]; дату выхода источники не дают (не подтверждено).

- **Автоисправление CI** срабатывает только на PR, созданных cloud-агентом; сотрудники признали баг, при котором оно не срабатывает и там [205].

Ни один тред не описывает паузу у лимита и автоматическое продолжение после сброса; есть ли такое поведение, по отзывам не видно (не подтверждено).

### Что ругают: цены, прозрачность расхода и доверие (самая большая тема)

- **История.**
  - Смена плана в июне 2025, потом извинение и возврат денег 2025-07-04 [111].
  - С 2025-09-15 Auto считается по токенам — с даты продления у каждого пользователя [219].
  - Январь 2026: «безлимитный» Auto больше не ощущается безлимитным [219].
  - 2026-07-07: Max Mode стал обязателен для передовых моделей на старых индивидуальных планах. Тред — 784 сообщения и 31 тыс. просмотров. Годовые подписчики пишут, что условия поменяли посреди контракта; часть уходит в Claude Code [216].
- **Cursor Router (2026-07-22).** Пользователь HN предупреждает: режимы Balance и Intelligence берут деньги по цене API выбранной модели из On-Demand, и баннера об этом нет [172]. Запуск критиковали: сначала только Team-планы, плохая коммуникация [222].
- **Страница расхода в токенах, а не в долларах (2026-07-31).** Так стало у индивидуальных планов; сотрудники назвали это намеренным; enterprise видят доллары [217].
  - Тред на HN — 337 очков, решение называют враждебным к пользователю. Сотрудник Cursor ответил, что поломка экспорта CSV была случайной и исправлена, а страница Spending показывает счёт [165].
  - В сентябре сотрудники сказали, что Cursor больше не публикует долларовую стоимость включённого объёма [220].
  - Пользователи, которые восстанавливают числа из CSV, видят, что счётчик показывает 100% примерно на 65% опубликованной стоимости API [220]. У пользователей Pro на 100% очень разные суммы токенов [221].
- **The X Subscription (2026-10-12)** [211].
  - Premium — $30, Super — $100; пользователи называют $200 за Ultra. Один недельный общий пул на Grok. Claude, GPT и Gemini — по цене API через пополнения с первого запроса. Cursor обещает как минимум вдвое больше Grok-кодинга, чем на сравнимом старом плане.
  - Подсчёт пользователя за первые четыре дня (около 90 человек):
    - потеряли включённые сторонние модели — около 15;
    - объём кончается быстрее, сомневаются в обещании «вдвое больше» — около 14;
    - не хотят пакет с X или Grok — около 10;
    - цена выросла с $20 до $30, замены Pro+ нет — около 9;
    - не было письма о переходе — около 8;
    - баги оплаты — около 7.
  - Самый популярный ответ (79 лайков, coco_max): ценность Cursor была в нейтральности моделей, а новый план покупает только Grok.
  - Переход нельзя отменить; некоторые после перехода получили меньше реального объёма.
- **Инциденты оплаты.** Команда получила $2500 неразрешённого расхода за выходные; пишут, что нет 2FA и что по умолчанию не-админы могут менять настройки расхода [164]. С другой команды взяли $450 за место, которое существовало секунды; сотрудник предложил исправить [171]. На форуме есть запрос на 2FA [225].
- **Подписка Claude внутри Cursor.** Некоторые подключают её через прокси; другие предупреждают о риске бана аккаунта [173].

## Слабые места и чего нет

- **Закрытый код и обязательный сервер Cursor.** Inference всегда у Cursor. Даже на своих машинах цикл агента и планирование идут в облаке Cursor [47][32].
- **Нет ожидания сброса лимита.** Функции, которая ждёт сброса пула и сама продолжает работу, не найдено (не подтверждено). У лимита Cursor предлагает платить, повысить план или сменить модель [73][65].
- **Общий пул с Grok.** Недельный пул делится с приложениями Grok и Grok Bot; сторонние модели — только по цене API из предоплаты [50][72][75].
- **Непрозрачный расход.** Страница расхода в токенах, а не в долларах; счётчики не сходятся с публичными ценами; у разных пользователей «100%» — очень разные объёмы [217][220][221][212].
- **Claude Code и Codex как агенты не запускаются.** Их расширения вытеснены из правой панели [184][185]. Пользователи просят работать на своей подписке Claude [164][173].
- **Расширения VS Code не работают в Agents Window** [180]. Интерфейс навязывают: окно по умолчанию, частые смены умолчаний, убранные функции редактора [177][178][179][186].
- **Нестабильность.** Сбои cloud-агентов на часы и сутки [174][195][196][197]; падения и зависания после релизов [164][189][188].
- **Worktrees.** Группировка по URL remote скрывает, где работает агент [181]; был случай работы агента в `main` вместо worktree [164]; автоматическая чистка удаляет и worktree в корне Cursor, созданные не им [14].
- **Безопасность.** Cloud-агенты не спрашивают разрешений [13]; Auto-review — не граница безопасности [13]; общие follow-ups дают lateral movement [27]; нет 2FA (по словам пользователей) [164][225].
- **Ограничения автоматизации.**
  - Автоисправление CI — только GitHub Actions, только Teams и Enterprise, только PR от cloud-агентов, с признанным багом [26][205].
  - Automations не реагируют на PR из форков [30]; «ничего не произошло» не может быть trigger [202]; был баг с секретами multi-repo [207].
  - CI-подписка ждёт все checks, и один зависший check останавливает агента; агенты service account не могут подписываться [26].
  - Вложенность subagents — два уровня [15]; сохраняемого runtime оркестрации нет — сотрудник советует писать скрипты над CLI [191].
- **Projects.** Нет на Free и Plus [3]; координатор только в облаке, локального режима по умолчанию нет [199].
- **Local и cloud.** «Move to Cloud» не переносит незакоммиченные файлы [80]; cloud-агенты не поддерживают multi-root workspaces [11]; при Remote Control на машине только один локальный worker [192]; закрытая крышка ноутбука останавливает локального агента [209].
- **Платформы.** iOS — только английский и iOS 26+; нативного Android нет [31].
- **Противоречия в документации** — признак быстрых изменений: Remote Control [31][107], side chats у cloud-агентов [78][65], лимит репозиториев [108][35], лимиты workers [32][34], название пакета Agent SDK [109][49][230].
- **Доверие.** Опасения насчёт обучения моделей xAI на коде пользователей (не подтверждено) [167][169]; часть пользователей не хочет пакет с X и Grok [211].
- **Чего нет по сравнению с продуктами вроде worfy:** пространственного холста с сессиями агентов (есть боковая панель и плитки) [1][89]; аналога Product Session, Mind map и критика спецификаций — поиск его не нашёл (не подтверждено); прямой связи машин по LAN — связь идёт через облако Cursor [33][31]; отдельной timeline работы без присмотра — есть только события и телеметрия [26][55].

## Механизмы, которые стоит изучить

1. **Subscriptions: пробуждение агента событием, а не опросом.**
   - Что это: агент подписывается на источник событий, заканчивает ход и спит, пока событие не придёт.
   - Как работает: источники — активность PR и CI на GitHub, треды и каналы Slack, задачи Linear, таймеры. Несколько событий подряд могут дать одно пробуждение, и агент перечитывает источник перед действием. Подписка живёт до 180 дней. CI-подписка ждёт завершения всех checks на commit. Cloud-агент сам подписывается на PR, которые создал. Агенты service account подписываться не могут.
   - Источники: [26][103].
2. **Стартовые правила координатора (seed rules).**
   - Что это: опубликованный в справке шаблон правил для координатора Projects. Пользователь сам вставляет его в `preferences.md` нового Project; автоматическая загрузка не подтверждена.
   - Как работает: один worker на PR; одна поправка на worker по одной теме, после двух — перезапуск с общим prompt; каждый PR открыт готовым к review, подписан на CI, каждые 2–3 минуты проверяется `git merge-tree` против main; все треды Bugbot и безопасности получают ответ; готовность PR координатор проверяет сам; статус merge и статус CI называются отдельными фактами, просто «clean» или «green» не пишется; merge и deploy координатор не делает.
   - Источники: [83][3].
3. **Agent Store и handoff-файл после сжатия контекста.**
   - Что это: постоянное хранилище файлов Project и человека, которое переживает сжатие контекста.
   - Как работает: `/cursor/stores/self` (общее хранилище Project, **Context**) и `/cursor/stores/user` (личное хранилище человека) хранят `preferences.md`, трекер `notes.md`, `workflows/` и `principles/`. Handoff-файл — правило из шаблона seed rules, а не встроенное поведение: координатор ведёт его и читает первым после сжатия, потому что сжатие стирает рабочую память, но не хранилище.
   - Источники: [3][83].
4. **Auto-review: классификатор каждого действия с политикой на естественном языке.**
   - Что это: режим, где не только allowlist, но и модель решает, можно ли выполнить действие.
   - Как работает: allowlist идёт сразу, shell-команды — в sandbox, остальное оценивает быстрая модель на сервере (Gemini 3.5 Flash Lite, запасной Haiku), которая может читать файлы. Политика — `allow_instructions` и `block_instructions` в `permissions.json`. Блок сначала возвращается агенту, чтобы тот нашёл другой путь. Цифры: около 4% действий заблокировано, около 7% чатов прервано. Документация называет режим не границей безопасности.
   - Источники: [13][137].
5. **Явный лимит у каждого автоматического цикла.**
   - Что это: у каждого места, где система сама запускает следующий шаг, есть потолок.
   - Как работает: hook `stop` может вернуть `followup_message` не больше 5 раз (`loop_limit`); автоисправление CI — до 10 follow-up на PR и не срабатывает после push человека; Bugbot Autofix — до 3 попыток; зацикленные рассуждения — один повтор с подсказкой; повторы SDK прекращаются через 3 минуты, потоковые runs не воспроизводятся заново.
   - Источники: [17][26][37][66][69].
6. **Время сброса лимита в ошибке протокола и пауза одного инструмента.**
   - Что это: ошибка лимита несёт машинно-читаемое время, когда можно продолжить.
   - Как работает: коды `USAGE_LIMIT_EXCEEDED` (14) и `RATE_LIMIT_EXCEEDED` (18); в `SdkErrorDetails` — `retry_after` и `RateLimitInfo` с `limit`, `remaining` и `reset_epoch_seconds`. Если MCP-сервер ограничил один инструмент, cloud-агент ставит на паузу только его, на время, которое просит сервер, и продолжает с остальными (неделя 2026-10-05).
   - Источники: [161][67].
7. **Файл настройки worktree, лимит и автоматическая чистка.**
   - Что это: декларативная настройка новой рабочей копии и ограничение их числа.
   - Как работает: `.cursor/worktrees.json` с ключами `setup-worktree-unix`, `setup-worktree-windows` и запасным `setup-worktree`; `$ROOT_WORKTREE_PATH` указывает на основную копию, чтобы скопировать, например, `.env`. Cursor держит 25 самых новых worktree на машину (значение по умолчанию) и проверяет по интервалу — в примере настроек раз в 6 часов. Чистка трогает и worktree в корне Cursor, созданные не им (например, `git worktree add`); про worktree в других папках документация молчит.
   - Источники: [14][46].
8. **Builds: заранее подготовленные снимки окружения.**
   - Что это: фоновая сборка окружения агента до того, как агент понадобится.
   - Как работает: стадии trigger, prepare, snapshot, activate, start; запуск по расписанию, при изменении конфига, вручную или по просьбе агента. Упавший Build никогда не заменяет рабочий. Порог устаревания по умолчанию — 24 часа: при включённой настройке Update stale builds агент на старте подтягивает свежий код ветки по умолчанию. По умолчанию новый Build идёт раз в час. Новые агенты делают fork живой машины; внутри Cursor загрузка стала в 10 раз быстрее, время до первого токена — в 3 раза.
   - Источники: [24][144].
9. **Долговечный агент и runs с безопасным повтором.**
   - Что это: API, где агент живёт долго, а его работа делится на runs.
   - Как работает: одновременно активен один run, второй получает `409 agent_busy`; follow-up вставляется в активный run (steer; повтор после сетевой ошибки может доставить его дважды) или встаёт в очередь; повторный POST с тем же `agentId`, выбранным клиентом, возвращает `409 agent_id_conflict` вместо второго агента; поток событий продолжается с `Last-Event-ID`; есть отдельное состояние «ожидание фоновой работы». Уже законченные вызовы инструментов при продолжении не повторяются.
   - Источники: [35][71].
10. **Некоррелированные review lenses и Field Guide.**
    - Что это: review с разных точек зрения на разных моделях и общая папка знаний, которой владеют агенты.
    - Как работает: lenses различаются тем, что видит reviewer: полный транскрипт worker, только его результат или только код; reviewers запускали и на разных моделях. Ни один lens не ловит всё, но некоррелированные lenses складываются. Папка Field Guide принадлежит агентам; её `index.md` автоматически подаётся каждому агенту на старте, а единственное ограничение — бюджет строк.
    - Источники: [140].
11. **Design Mode: разметка страницы с готовым контекстом для агента.**
    - Что это: человек размечает живую страницу, а агент получает точные данные об элементе.
    - Как работает: клик, Shift-клик или рамка; рисование, стрелки, правка текста на месте; несколько пронумерованных меток уходят пачкой. Агент получает selector, стили, стек компонентов React, Vue или Svelte и обрезанный скриншот.
    - Источники: [7][136].
12. **Маскировка Runtime-секретов и артефакты по неугадываемым URL.**
    - Что это: секреты, которые агент может использовать, но которые не попадают в следы его работы.
    - Как работает: Runtime-секреты заменяются на `[REDACTED]` в выводе инструментов, транскриптах, commit и сообщениях commit. Это всё равно переменные окружения, поэтому человек, который открыл терминал окружения агента, их видит. Скриншоты, видео и логи прикрепляются к PR; встраивание в GitHub включается отдельно и идёт через неугадываемые публичные URL.
    - Источники: [28][26].
