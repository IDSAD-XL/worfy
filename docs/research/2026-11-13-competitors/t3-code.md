## Модель работы

### Local, cloud или hybrid

- **Local: агенты всегда работают на машинах пользователя.** Облачного исполнения нет. Агенты из ACP Registry тоже работают на машине сервера, даже если пользователь зашёл через app.t3.codes [30]. Облачные агенты Cursor T3 пока не показывает [31]. Запрос на управление облачными sessions закрыт как «not planned» 2026-11-12 [154].
- **Один сервер на машину.** Сервер называется environment — это запущенный сервер вместе с машиной, учётными данными и состоянием, которыми он владеет [57]. Desktop-, web- и мобильные приложения — клиенты этого сервера. Все клиенты видят одни и те же thread-ы [11][57].
- **Desktop-приложение запускает свой локальный сервер.** Закрытие последнего окна этот сервер останавливает [25][57].
- **Способы запустить сервер:**
  - desktop-приложение;
  - CLI `t3` (`t3`, `t3 serve`);
  - фоновая служба `t3 service install`. На Linux это user-служба systemd с lingering — она работает и без входа пользователя в систему. На macOS и Windows (через Task Scheduler) служба работает, пока пользователь вошёл в систему [18][47];
  - SSH-хост под управлением desktop-приложения (Linux или Mac на Apple Silicon). Приложение ставит сервер в `~/.t3/runtime` и пробрасывает порт [25];
  - дистрибутив WSL [18];
  - разовый запуск `npx t3@latest` [18].
- **Как достучаться до сервера с других устройств:**
  - T3 Connect — hosted relay вендора поверх Cloudflare tunnel (`cloudflared`). Relay устанавливает связь, но не проксирует HTTP- и WebSocket-sessions. Исключение — пересылка webhook-ов [19][63][64].
  - Сопряжение (pairing) в локальной сети по QR-коду или ссылке, Tailscale HTTPS, публичный URL, SSH [25].
  - У машины может быть несколько маршрутов. Они упорядочены по скорости, при сбое приложение само переходит на следующий [25].
  - Маршруты запоминаются. После одного сопряжения через T3 Connect приложение дома само находит адрес машины в LAN и ходит по нему [25].
- **Hosted-части вендора:**
  - app.t3.codes — web-клиент. Он подключается прямо к серверу пользователя и требует HTTPS endpoint [25];
  - relay T3 Connect: вход через Clerk, инфраструктура на Cloudflare и PlanetScale [5][64];
  - relay push-уведомлений [64];
  - endpoint для telemetry [51].
- **Self-hosting.** Весь стек под MIT. Код relay и шаги его развёртывания лежат в репозитории, так что свою сборку можно направить на свой Clerk и свой relay [64]. Desktop-приложение может работать только как удалённый клиент, если выключить **Local environment** [25].
- **Куда идёт код.** Код и prompts идут с машины пользователя к provider-у модели, а не на серверы T3 [19][5].

### Агенты и модели

- **Своего агентного цикла нет.** FAQ прямо говорит: T3 Code — не harness и без harness-а не работает [19].
  - Harness — слой, который даёт модели инструменты, разбирает её вызовы инструментов, исполняет их и возвращает результат [8].
  - T3 Code запускает harness-ы вендоров: Anthropic Agent SDK для Claude, Codex App Server, Cursor SDK и агентов по ACP [8][19].
  - ACP (Agent Client Protocol) — открытый протокол, по которому приложение управляет coding-агентом [11][13].
- **Provider** — так T3 называет среду исполнения агента, например Codex [57]. Поддерживаются:

| Provider | Как T3 Code его запускает и какие есть ограничения |
|---|---|
| Claude Code | Через Anthropic Agent SDK, с логином пользователя в `claude` [19][28]. |
| Codex | Через Codex App Server [8]. Два способа входа. «Connect with ChatGPT»: T3 ставит свою управляемую копию Codex и использует план ChatGPT; на этом пути нет скоростей Fast и Ultrafast. Или существующий `codex login` [29]. |
| Cursor | Через официальный `@cursor/sdk`, только локальные агенты. Нужен платный план Cursor. Нет встроенных fork и rollback, нет интерактивных approval callbacks [31]. |
| Grok Build | Вход через `grok login` [18]. |
| Kiro | Beta, помечен «Early Access» [130]. |
| OpenCode | Нужна версия 1.14.19+; для OpenCode 2 — 2.0.18+. Для 1.x поддержка ограниченная («Limited support») [32][126]. |
| Antigravity | ACP-агент Google. Установку и вход ведёт T3 [32]. С v0.1.5 предлагает модели Claude и GPT и уровни thinking [128]. |
| Pi | Версия 0.80.5+ [32]. |
| Muse Code | Агент с dev.meta.ai. По умолчанию выключен [18][32]. |
| fx | Вход через `fx login` [18]. |
| ACP | Любой агент из официального ACP Registry (примеры в документации: Devin, Cline, Kimi, Droid) или локальная ACP-команда, например DeepSeek Harness [30][126]. |

- **GitHub Copilot.** Как он поддерживается, неясно (не подтверждено): документация упоминает его только в исправлении v0.1.5 [128]. Один пользователь HN запускает Copilot через ACP [176].
- **Несколько аккаунтов одного provider-а.** Можно завести несколько provider instances — настроенных экземпляров одного provider-а [18]:
  - Codex: «shadow home» (отдельная домашняя папка Codex) позволяет двум аккаунтам продолжать один и тот же thread [29];
  - Claude: у каждого аккаунта свой `CLAUDE_CONFIG_DIR` [28];
  - экземпляр может работать через API-ключ, OpenRouter или router вроде Claude Code Router — через свои переменные окружения [19][28];
  - можно добавлять свои модели и переименовывать встроенные [20].
- **Автоматического переключения аккаунтов нет — сознательно.** FAQ объясняет, что такой переключатель рискует бан аккаунтов за нарушение terms of service. Пользователей с несколькими аккаунтами отправляют к CLIProxyAPI — стороннему self-hosted proxy, который объединяет аккаунты в pool. T3 показывает общие лимиты этого pool-а [19][26][218].
- **Локальные модели.** Для агентов — нет: FAQ считает, что локальные модели не способны на серьёзную инженерную работу [19]. Локальный OpenAI-совместимый endpoint, например Ollama, разрешён только для генерации служебного текста: названий, сообщений коммитов и т. п. [44].
- **Минимальные версии в v0.1.0:** Codex 0.159+, Claude Code 2.1.280+, Grok 1.0.13+, OpenCode 2.0.18+, Pi 0.80.5+ [126]. Страница Providers в настройках предупреждает о несовместимых версиях и даёт кнопку **Update now** [18].
- **Заявления вендора об условиях использования:**
  - T3 утверждает, что работает в рамках terms of service Claude Code, Codex и Antigravity [19].
  - FAQ пишет, что команда работала с AI-подразделением SpaceX (аккаунт @SpaceXSI) над интеграциями Grok Build и Cursor. @SpaceXSI 2026-06-25 объявил, что подписки SuperGrok и X работают внутри T3 Code [19][223].
  - 5-часовой счётчик лимита Anthropic раньше списывал использование через Agent SDK примерно в 1,7 раза быстрее, чем через CLI. FAQ пишет, что с v0.1.7 это исправлено [19][162]. Пользователи сообщали о быстром расходе и после исправления — 2026-11-10 и 2026-11-13 [146].

### Один пользователь или команда

- **Один человек на своих машинах и устройствах.** Так продукт устроен и так его описывает FAQ [19][25].
- **Элементы для работы с другими людьми:**
  - **Guest links** (beta) — коллега следит за одним thread-ом в браузере без аккаунта [40]:
    - гость может предлагать сообщения; каждое ждёт, пока владелец его отправит или отклонит;
    - ссылка работает в одном браузере и истекает через 24 часа;
    - diff-ы гостю не показываются.
  - **Ссылки на prompt и на thread.** Ссылка на thread открывается только у того, кто подключён к машине, где идёт thread [39].
  - **Общие скрипты в `t3.json`** — файле проекта, который схема описывает как конфигурацию для всех, кто открывает репозиторий [6].
  - **Общий доступ к PR между машинами** [23].
  - **Scopes сопряжения** — клиенты с ограниченными правами [25].
  - **Managed policy** — настройки, которые фиксирует IT-отдел [42].
- **Чего нет.** Командных workspaces, общей оплаты, ролей и корпоративного SSO не найдено. Аккаунты есть только для T3 Connect, через Clerk [64][5].

## Функции

Описание собрано по документации пользователя и release notes на 2026-11-13 [18]–[56][122]–[133]. Термины, которые встречаются везде:

- **Thread** — долговечный разговор с агентом, привязанный к проекту. Thread переживает выход процесса provider-а [57].
- **Turn** — один цикл: сообщение пользователя и работа агента над ним. В Orchestrator V2 turn называется run [57][73].
- **Environment** — запущенный сервер T3 вместе с машиной и её состоянием [57].
- **Экран** — sidebar со списком thread-ов, вид thread-а и вкладки правой панели: Browser, Device, Diff, Files, Linked PRs, Pull request, Side chat, Terminal [114][117].

### Thread-ы, проекты и sidebar

- **Thread и worktree.** Кнопка **New worktree** даёт thread-у свою ветку и свою рабочую папку [21].
  - Пользователи описывают worktree на каждый thread как поведение по умолчанию [175][176][206].
  - Какое значение настройки `defaultThreadEnvMode` (local или worktree) встроено в код по умолчанию, не выяснено (не подтверждено) [107][108].
- **Thread-ы без проекта** живут в `~/.t3/scratch`. Команда **Turn into project** позже превращает такой thread в проект [21][128].
- **Новые проекты:**
  - **New project** просит только имя. Создаёт Git-репозиторий с README, иконкой и первым коммитом. По желанию публикует приватный репозиторий на GitHub [23][125].
  - **Add Project** клонирует репозиторий с хоста или по URL в фоне. Первый prompt можно писать, пока идёт клонирование [23].
  - **Publish Repository** отправляет локальный репозиторий на хост [23].
  - Раскладка клонов в стиле ghq (папки по хосту и владельцу) — по желанию [23][131].
- **Запуск работы:**
  - **Start in background** (Cmd/Ctrl+Enter) [21].
  - **Один prompt нескольким моделям.** Shift-клик по моделям в списке. Каждая модель получает свой thread и свой worktree [21].
- **Разделы sidebar:** Pinned, Active, **Working**, Snoozed и Settled [21].
  - Working — beta, включена по умолчанию. Занятые thread-ы сворачиваются в этот раздел и не мешают, пока не понадобится пользователь [21][125].
  - Thread-ы можно перетаскивать между разделами. 5 секунд после этого доступен Undo [21].
  - Порядок хранится на сервере и синхронизируется между устройствами [21].
  - Обычная группировка по проектам вынесена в Labs — страницу экспериментальных функций в настройках [21][115].
- **Автоматический уход в Settled** (раздел законченной работы):
  - thread уходит в Settled после 7 дней без активности или когда слит его PR [21];
  - для отдельного thread-а можно выбрать **Never** [21];
  - правила работают, даже когда все приложения закрыты [21].
- **Snooze** — отложить thread на настраиваемый срок или до своего времени. Отложенный thread возвращается раньше срока, если пришёл approval, вопрос агента или сбой [21].
- **Поиск.** Cmd/Ctrl+K ищет thread-ы на всех подключённых машинах по названию, ветке, PR или проекту. Есть и полнотекстовый поиск по сообщениям [21].
- **Статус thread-а и карточка деталей:**
  - статусы: working, waiting, **Limited** (provider остановился на лимите) или failed [126];
  - карточка деталей показывает локальные серверы с портами и кнопкой Stop (кроме Windows) [21];
  - ещё в карточке: окно контекста, строки лимитов, side chats, связанные PR, lineage (дерево thread-ов, порождённых этим) и скрипты. Строки карточки настраиваются [21][126][128].
- **Как следить за работой агентов:**
  - вид **Agents** и lineage view для subagents [21][126];
  - здесь заметки расходятся. Одна группа заметок описывает вид Agents и панель lineage с моделью, статусом и длительностью каждого subagent [21][126]. Другая пишет, что v0.1.0 убрал отдельную панель агентов [126]. Вероятно, отдельную панель заменил lineage view внутри thread-а (не подтверждено);
  - сгруппированные вызовы инструментов с живым выводом команд [36];
  - сводки оркестрации вида «отправлено 5 сообщений в 2 thread-а» [36];
  - настройка **Tool calls in chat** с тремя уровнями: Hide successful, Hide all и Zen [36];
  - minimap ленты thread-а с переходом к предыдущему и следующему turn-у [124][119];
  - история смены моделей [130].
- **Проекты** можно закреплять, архивировать, давать им иконки. Большинство настроек переопределяется на уровне проекта [24][129].

### Composer и контекст сообщения

Composer — поле ввода сообщения агенту.

- **Ограничения:**
  - Markdown-редактор, сообщение до 120 000 символов [20];
  - вставка от 32 KiB становится вложенным файлом [20];
  - до 100 файлов на сообщение: изображения до 10 MiB каждое и до 80 MiB всего, прочие файлы до 50 MiB каждый [20];
  - с v0.1.9 сообщение можно отправить, пока вложения ещё загружаются [132].
- **Chips** — короткие вставки в тексте сообщения, которые указывают на кусок контекста:
  - фрагмент терминала;
  - комментарий review из diff или файла;
  - пометка в preview браузера или выбранный элемент страницы;
  - файл;
  - PR — через `#`;
  - другой thread — через `@` и часть названия или перетаскиванием. Агент читает такой thread по необходимости. Thread может быть и со связанной машины [20];
  - `@model` — называет модель для делегирования, не меняя модель самого thread-а [20].
- **Cite in composer** — цитирует часть ответа агента и прикрепляет к ней комментарий [20].
- **Команды:**
  - `/` показывает команды provider-а, команды T3 и skills. `$` выбирает skill, в том числе skills из plugins Claude [20][28];
  - `/compact` сжимает контекст. `/clear` начинает новую session provider-а в том же thread-е [20];
  - `/usage-limits` показывает лимиты текущей модели [26];
  - `/side` или `/btw` открывает side chat. `/goal` задаёт цель, до которой агент работает сам [20][21];
  - `/feedback` отправляет отчёт в OpenAI, только для Codex [29].
- **Помощь при наборе:**
  - стрелка вверх вспоминает прежние prompts [20];
  - Cmd/Ctrl+S откладывает prompt (stash). Загруженные файлы в stash хранятся 24 часа [20];
  - **Suggest next prompt** (Labs, для Claude и Codex) предлагает следующий prompt. Это стоит одного дополнительного запроса с кэшем на каждый turn [20].
- **Ответы на вопросы агента** могут содержать вложенные файлы [55].

### Управление turn-ом

- **Queue или steer.** Сообщение, отправленное во время работы агента, либо ждёт следующего turn-а (queue), либо меняет направление текущего (steer). Что именно — задаёт настройка. Cmd/Ctrl+Enter делает обратное поведению по умолчанию [20].
  - Очередь хранится на сервере. Она сохраняет порядок после перезапусков и остановок на лимите. Сообщения в ней можно править, переставлять и отправлять сразу [20][126].
- **Edit from here** — откат разговора до выбранного сообщения.
  - **Revert files too** заодно восстанавливает checkpoint рабочей папки. Checkpoint хранится как скрытый Git ref — ссылка Git, которой нет среди веток пользователя [20][57].
  - Восстановление файлов работает только для thread-ов в своём worktree. Оно отклоняется, если эту папку использует другой thread или session агента [20].
- **Fork любого thread-а**, в том числе упавшего или прерванного. Где у provider-а есть свой fork (Codex, Claude, Pi, OpenCode 2), используется он. Контекст fork-а можно потом слить обратно [126].
- **Side chats** — вопросы о thread-е, которые не попадают в сам thread. **Bring back** переносит выводы из side chat в thread [21].
- **Goals.** `/goal <условие готовности>` заставляет агента работать через много turn-ов, пока он сам не сочтёт цель достигнутой. Работает с Codex, Claude и OpenCode 2.2.5+. У Codex и OpenCode есть pause и resume [20][132].
- **Plan mode.** Режим взаимодействия (plan или default) задаётся отдельно от прав [57].
  - Вывод плана становится долговечным артефактом «proposed plan». Реализация плана создаёт новый run или новый thread со ссылкой на план (`sourcePlanRef`) [74].
  - Карточка плана предлагает **Save plan to workspace** — сохранить план в рабочую папку [118].
  - Todo lists агента показывают ход работы вживую [74].
- **Restart agent session** перезапускает session агента, чтобы подхватить новые skills, plugins и MCP-серверы [20][125].
- **Compaction у Claude** (сжатие контекста):
  - порог auto-compact настраивается от 100k до 1M токенов [28];
  - для простаивающих thread-ов больше 200k токенов три режима: сжать, когда пользователь вернётся; сжать перед истечением prompt cache (beta, начинается за 2 минуты до истечения); никогда [28][89];
  - если пользователь вернулся после истечения prompt cache, появляется chip «Compact» [89].

### Работа нескольких агентов и передача между vendor-ами

- **Смена provider-а посреди thread-а.** Provider, аккаунт, модель или настройки можно менять между turn-ами. Смену можно поставить в очередь [126].
  - Передача теряет информацию. Новый provider получает отобранные по бюджету сообщения: 16 000 токенов по умолчанию, настраивается от 1024 до 64 000 [37][126].
  - Рассуждения, состояние вызовов инструментов и вложения не передаются. Пропущенную историю агент может дочитать инструментом [37][126].
  - Вендор сам называет такую смену потерей информации и советует вместо неё `delegate_task` [126].
- **`delegate_task`** — родительский агент запускает дочернего на любом provider-е и модели [75]:
  - роли: implementation, research, review, design, test или general;
  - режим async или wait;
  - у дочернего агента свой режим прав и свой режим взаимодействия — `plan` или default;
  - дочерний агент видит только prompt задачи. Родитель просыпается, когда дочерние агенты закончили; их результаты приходят вместе [75][126];
  - release notes называют это рекомендуемым способом совмещать harness-ы: например, Claude планирует, а Codex реализует [126].
- **MCP-инструменты T3 Code** позволяют агентам [75][126][27]:
  - создать от 1 до 20 thread-ов одним вызовом (`create_threads`);
  - запускать, перечислять, читать и обновлять thread-ы, отправлять в них сообщения (режимы auto, queue, steer или restart), ждать их и прерывать;
  - проверять и отменять делегированные задачи;
  - управлять scheduled tasks, связывать PR с thread-ами, переносить работу в worktree, закрывать preview.
- **Свои запросы разрешений агенты одобрять не могут** [126].
- **Встроенные subagents** Claude, Codex, OpenCode 2, Cursor и Pi показываются как дочерние thread-ы: модель, статус, ход работы, результат и длительность [126].
  - Thread-ы subagents только для чтения. Их approvals приходят в родительский thread [21][22].
  - Остановка родителя останавливает и делегированных им subagents [21].

### Работа без присмотра и автоматизация

- **Scheduled tasks** — задачи по расписанию, доступны в web и mobile [24][126][130]:
  - создать, изменить, поставить на паузу, возобновить, запустить сейчас, удалить;
  - расписание по времени идёт в часовом поясе environment-а. Расписание **Once** — один запуск в заданные дату и время;
  - результат запуска идёт либо в новый thread на каждый запуск, либо в один thread. Во втором случае thread либо продолжает тот же разговор, либо каждый раз начинает новую session.
- **Webhook-автоматизации** — тип расписания «On webhook» [24]:
  - публичный URL для webhook требует T3 Connect;
  - подстановки вида `{{body.path}}` вставляют значения из запроса в prompt. Эти значения оборачиваются и помечаются как недоверенные данные;
  - проверка подписи GitHub, фильтры, ключ против повторной доставки (повтор игнорируется 7 дней), окно объединения запросов от 10 до 3600 секунд (по умолчанию 120) и журнал доставок **Deliveries**;
  - по желанию T3 Connect держит входящие запросы до 24 часов, пока машина offline.
- **Лимиты подписки** [21][128]:
  - thread, который упёрся в лимит, показывает статус **Limited**;
  - **Resume at reset** ставит продолжение на момент сброса лимита. Отдельная настройка делает это поведением по умолчанию;
  - **Snooze until reset** прячет thread, пока лимит не вернётся;
  - новые thread-ы обходят provider-ов, которые только что упёрлись в лимит.
- **Continue threads after restarts** — включено по умолчанию [48]:
  - thread-ы продолжают работу после обновления, сбоя или перезагрузки;
  - после 3 автоматических продолжений подряд thread сам больше не продолжается;
  - thread, который ждёт approval, ответа или secret, сам не продолжается никогда.
- **PR watch.** Если попросить агента следить за PR («watch», «monitor» или «babysit»), сервер проверяет PR каждые 2 минуты [23]:
  - агент просыпается при упавшей проверке, при workflow, который ждёт одобрения maintainer-а, когда прошли обязательные проверки, при комментариях или review от других людей, при конфликте и при выпадении PR из merge queue;
  - наблюдение заканчивается при merge или закрытии PR, после 10 пробуждений подряд только из-за комментариев, после 8 неудачных чтений PR подряд или по Stop.
- **Фоновая работа.** Агент просыпается, когда закончил subagent, команда или monitor. Stop останавливает и фоновую работу [126].
- **Auto balance между машинами** (по умолчанию выключено). Каждой машине задаётся Prefer, Normal, Less often или Manual only. Выбор машины учитывает её свободные CPU и память [25].
- **Машина не засыпает, пока работают агенты.** Сервер держит машину проснувшейся: `caffeinate -i -w <pid>` на macOS или `systemd-inhibit` на Linux, плюс 60 секунд запаса между запусками. Включено по умолчанию (настройка `keepAwakeWhileAgentsWork`) [97][107].

### Режимы прав и approvals

Approval — запрос агента на разрешение выполнить действие.

- **Четыре режима прав**, выбираются для каждого thread-а [22]:
  - Supervised;
  - Auto-accept edits;
  - Auto — использует собственную автоматическую проверку provider-а у Codex, Claude, Cursor, Grok и fx;
  - Full access.
- **Режим по умолчанию для новых thread-ов — Full access** [22][106].
- **Ограничения provider-ов** [22]:
  - у Muse Code и Kiro — только Supervised и Full access;
  - у fx нет Auto-accept edits и Full access;
  - у Grok нет Auto-accept edits.
- **Approvals отвечаются прямо в thread-е.** Approval у Claude можно отклонить, написав вместо этого замечание текстом [22].
- **Своего движка правил approvals у T3 нет.** Есть только запоминание одобрений самими provider-ами: например, «Always allow» у Kiro и «Allow all edits this session» у Grok [22][32]. С v0.1.9 Claude умеет одобрять MCP на всю session [132].
- **Администратор может ограничить самый широкий режим** через managed policy [42].

### Git, worktrees и source control

- **Хосты кода** [23]:
  - GitHub — через сохранённый токен, `GH_TOKEN` или `gh` версии 2.81+. Поддерживается GitHub Enterprise;
  - GitLab, Forgejo/Gitea, Bitbucket, Azure DevOps, GitCafe и Cursor Origin.
- **Worktrees** [24][6]:
  - имя ветки: статический префикс (по умолчанию `t3/`), смысловой префикс, который выбирает модель, или свои инструкции для модели;
  - настраиваемое место хранения и обработка submodules;
  - setup-скрипты, которые запускаются при создании worktree;
  - **Fast worktree checkout** (beta, только macOS) копирует рабочую папку из кэшированных checkout-ов через copy-on-write в APFS. По словам вендора — примерно вдвое быстрее.
- **Очистка диска** выключена по умолчанию. Правила удаляют worktrees после заданного числа дней без активности, после ухода thread-а в Settled, после merge или когда в worktree нет коммитов. Один пользователь так освободил 500 GB [19][24].
- **Панель diff:** изменения текущего turn-а, сравнение ветки, последние 100 коммитов и восстановление файлов [23].
- **Commit, push и PR одной кнопкой** [23][1]:
  - сгенерированные сообщения коммитов, заголовки и тексты PR. Текст учитывает проверки, которые запускал thread;
  - draft, stacked и amended PR;
  - **Remove agent credits when merging** — убрать упоминание агента при merge. По умолчанию выключено.
- **Review локальных коммитов** — с v0.1.6 [129].
- **Automatically pull** держит ветку по умолчанию свежей, только fast-forward [24].
- **Файл проекта `t3.json`** [6]:
  - до 50 скриптов. У каждого имя, команда и иконка: play, test, lint, configure, build, debug;
  - флаги: `runOnWorktreeCreate` (с `async`), `runOnSettle`, `stopOnSettle`, `previewUrl` и `autoOpenPreview`;
  - схема описывает файл как конфигурацию, общую для всех, кто открывает репозиторий.

### Страница Pull requests

- **Один список PR по всем хостам и машинам** — с фильтрами, быстрыми действиями по Shift и выделением нескольких строк протягиванием, чтобы закрыть их разом [23][123].
- **Вкладки PR:** Summary, Code и Guide [120].
- **Действия** [23][132][120]:
  - Approve, Request changes, Comment;
  - Merge, Squash and merge, Rebase and merge;
  - auto-merge на GitHub, GitLab и Azure DevOps;
  - Update branch, Ready for review, Convert to draft, Reopen;
  - Revert на GitHub, на GitLab — с v0.1.9;
  - Approve workflows to run — для workflows из fork-ов, которые ждут одобрения.
- **Связанные PR** [23]:
  - у одного thread-а может быть несколько PR, в том числе в разных репозиториях одного хоста;
  - связь появляется сама, когда агент запускает `gh pr create` или `glab mr create`.
- **GitHub stacks** — цепочки PR, где каждый следующий построен на предыдущем [23][124]:
  - **Merge stack** сливает выбранный PR и все неслитые PR под ним;
  - **Rebase stack** обновляет удалённые ветки снизу вверх.
- **Review guides** (beta) [23]:
  - AI пишет тур по PR — упорядоченный список остановок. Пометки «Look closely» отмечают решения, которые может принять только maintainer. Механические изменения собраны в конце;
  - тур пишет Claude или Codex во временном checkout. Готовый тур хранится для всех пользователей этого сервера;
  - reviewer может спросить агента про любую остановку, а потом нажать **Finish review**.
- **Отметки Viewed.** Отметка файла как просмотренного синхронизируется с такими же отметками на GitHub [23].
- **Общий доступ к PR между машинами** — только чтение или чтение и действия [23].
- **Передача агенту и телефон** [23][123]:
  - запрос по конкретным строкам PR можно отправить агенту;
  - на телефоне можно делать review PR. Содержимое PR остаётся доступным offline.

### Расход и лимиты

- **Страница Usage** (сочетание mod+u) [26][130]:
  - собирает историю Codex, Claude Code, Grok Build, OpenCode, Antigravity, Pi, Muse Code и Cursor;
  - показывает токены, экономию на кэше и разбивку по моделям;
  - показывает оценку стоимости по ценам API. Вендор прямо пишет, что это не счёт за подписку;
  - периоды: 24 часа, 7, 30 или 90 дней. Фильтры по машине, provider-у и модели;
  - свои цены моделей и **Map to** — считать одну модель как другую.
- **Вкладка Limits** [26]:
  - объединяет все аккаунты подписки одного provider-а со всех машин и hub-ов в одну карточку на каждое окно лимита (например, 5-часовое и недельное). У каждого аккаунта свой сегмент;
  - показывает время сброса и сколько вернёт каждый сброс;
  - **Use reset** тратит накопленные credits сброса (banked resets) у Codex и Claude. Для Claude это недоступно, если сервер работает на macOS: функция читает сохранённый OAuth-токен Claude [26][94].
- **Где ещё видны лимиты:** команда `/usage-limits`, строки лимитов и счётчик контекста в карточке деталей thread-а, виджеты «Subscription usage» на iOS и Android, общие лимиты из hub-а CLIProxyAPI [26].

### Удалённый доступ и несколько машин

- **Способы подключения:** T3 Connect, LAN, Tailscale HTTPS, SSH и списки маршрутов с переходом на запасной [25].
- **Scopes у токенов сопряжения:** `orchestration:read/operate`, `terminal:operate`, `filesystem:read/write`, `source-control:write`, плюс отдельные scopes для настроек, provider-ов и управления доступом [25].
- **Linked environments** (beta) — связь между машинами для агентов [25]:
  - агенты на одной машине запускают, пишут, ждут и останавливают thread-ы на другой. `delegate_task` тоже работает между машинами;
  - у связи есть уровень доступа. Связь живёт 30 дней;
  - ниже Full access связь может менять только те thread-ы, которые сама запустила.
- **Управление доступом:** отзыв sessions на хосте или **Deregister** — убрать машину из T3 Connect [25].
- **Вход агентов в T3 Connect** — с v0.1.9 [132].

### Мобильные приложения

- **Телефон — пульт управления.** FAQ: работу делает компьютер, телефон им управляет [19]. После подключения приложение даёт почти все возможности desktop: запуски, файлы, Git, diff-ы и терминал [224][226].
- **Offline:** черновики вложений, сообщения в очереди и черновики работают offline и переживают перезапуск приложения [20].
- **Уведомления:** push, iOS Live Activities, Android Live Updates и iOS-виджет «Agent Activity». Всё это требует T3 Connect [45].
- **Голос:** диктовка на устройстве на iOS 26+ и Android 12+ [20].
- **Другое:** scheduled tasks, упорядочивание thread-ов, лист агентов, просмотр устройств, side chats [24][21][35]. Заметки к версии 2.3.0 добавляют упоминания `@model`, `/side`, approvals от subagents и отрисовку Mermaid и формул [224].

### Браузер, устройства и визуальный вывод

- **Панель браузера** [25]:
  - вкладки принадлежат машине и общие для всех устройств;
  - у вкладок агента отдельное хранилище. Пользователь берёт управление, чтобы что-то ввести, и потом возвращает его агенту;
  - удалённые вкладки транслируются с хоста. Панель показывает порты локальных серверов;
  - работает на headless Chrome примерно на 120 MB, который скачивается один раз.
- **Профили браузера и импорт cookies.** Для Safari нужен Full Disk Access. На Windows импортируются только профили Firefox, Zen и Helium [53].
- **Браузер по умолчанию.** На macOS T3 Code можно сделать браузером по умолчанию [54].
- **Visual replies** [33]:
  - агент строит самодостаточную HTML-страницу — график, таблицу, диаграмму или макет. Страница показывается над его ответом;
  - страница работает в sandbox и следует теме приложения. Агент проверяет её скриншотами перед публикацией.
- **MCP Apps** — интерактивные приложения, которые возвращают MCP-инструменты. Показываются прямо в ответе для Codex и Claude [33][131].
- **Mermaid и формулы.** Диаграммы Mermaid отрисовываются [127]. LaTeX — по желанию [50].
- **Панель Devices** [35]:
  - живой iOS Simulator или Android Emulator рядом с thread-ом. Агенты управляют им через инструменты `device_*` и CLI `agent-device`;
  - ящик Tools, 3D-вид и вид складного устройства, SSH-хосты устройств и пулы симуляторов Simlock (alpha).
- **SnapShots** [34]:
  - глобальное сочетание клавиш (по умолчанию обе клавиши Shift) снимает активное окно вместе с данными accessibility и кладёт снимок в черновик сообщения;
  - работает на macOS, Windows и Linux с Wayland. На X11 не работает.

### Терминал, файлы, редакторы и генерация текста

- **Терминалы** [43][57]:
  - процессами терминалов владеет сервер, поэтому любой клиент может к ним переподключиться;
  - сервер хранит 5000 строк или 8 MiB истории на каждый терминал;
  - терминалы работают и на телефоне.
- **AI-помощника внутри терминала не найдено.** Вывод терминала попадает к агенту только фрагментами, которые пользователь сам вставляет в composer [20].
- **Файлы** [20][25]:
  - просмотр рабочей папки и правка файлов при scope `filesystem:write`;
  - HTML, PDF, Markdown и CSV отрисовываются в просмотрщике;
  - ZIP до 50 MB открывается как список папок.
- **Open in — внешние редакторы** [109][123]:
  - VS Code, VS Code Insiders, VSCodium, Cursor, Zed;
  - IDE JetBrains, Kiro, Trae и Antigravity;
  - удалённую машину можно открыть в локальном редакторе через SSH.
- **Генерация служебного текста** пишет названия thread-ов, сообщения коммитов, тексты PR, имена веток и чистит расшифровки голоса. Отдельные «text generators» делают это дёшево через OpenAI, Anthropic, OpenRouter или любой OpenAI-совместимый endpoint [44].

## Принципы и подходы

### «Не harness»: интерфейс поверх чужих harness-ов

- **Три слоя.** Пост Theo «What is a 'harness'?» от 2026-10-22 разделяет [8]:
  - модель — она только порождает текст;
  - harness — даёт инструменты, разбирает вызовы инструментов, исполняет их и возвращает результат. Примеры: Anthropic Agent SDK под Claude Code, Codex App Server;
  - интерфейс — то, с чем работает человек.
- **Агент = harness + модель.** Claude Code и Codex продают интерфейс вместе со своим harness-ом. T3 Code подаётся как интерфейс, который ставится поверх любого harness-а [8][19].
- **Сравнение вендора.** Вендор объясняет это через кухню: модель — повар, harness — кухня, T3 Code — ресторан, куда можно принести любую кухню. MCP-сервер T3 Code в этом сравнении — книга рецептов, которую модель открывает только по указанию [8][19].
- **Практический смысл сравнения.** Дополнительные возможности поставляются один раз — через один лёгкий MCP-сервер, а не отдельным plugin-ом для каждого harness-а. Пример такой возможности: thread на Claude запускает subagents на Codex [8].
- **Почему не свой агент.** На запуске Theo говорил, что модели лучше всего работают в том harness-е, на котором их обучали. Поэтому T3 Code оборачивает официальные CLI и добавляет сверху лучший интерфейс, а не строит свой агентный framework (вторичный пересказ видео) [212].
- **Одинаковый опыт.** FAQ обещает, что любой harness внутри T3 Code ощущается почти одинаково, и о различиях harness-ов можно не думать [19].
- **Своя подписка пользователя.** T3 Code не перепродаёт токены. Он работает на планах, за которые пользователь уже платит. Сайт отдельно подчёркивает: ключи не перепродаются, квот нет [1][7][11].

### Четыре обязательных принципа

Их записал Theo в AGENTS.md 2026-07-28, в PR #4782 [14]. AGENTS.md — файл инструкций репозитория для coding-агентов.

1. **Открытость в основе.** Команда обещает делиться roadmap, ходом мыслей и всем кодом. Она отмечает, что большая доля пользователей работает на fork-ах [13].
2. **Производительность без компромиссов.** Команда утверждает, что не пропускает небрежно сгенерированный код и регулярно ищет регрессии [13].
   - Названные причины регрессий: слишком много данных по WebSocket; CSS-анимации, которые нагружают GPU; списки, которые медленно отрисовываются.
   - По их описанию, пользователи замечают пропущенный кадр, индикатор загрузки, который показывает неправду, и устаревшую подпись.
   - Анимации, которые перерисовываются непрерывно, запрещены [13]. README называет пропущенный кадр ошибкой [11].
3. **Готовность к удалённой работе.** WebSocket-сервер (команда `t3`) — ядро продукта. Каждая функция обязана работать через LAN, Tailscale (mesh VPN) и T3 Connect [13].
4. **Несколько поверхностей.** Web — и hosted app.t3.codes, и копия от локального сервера. Desktop — основной вход, он несёт сервер в себе. Mobile подключается к любому серверу [13].

**Заметка Theo в AGENTS.md** [13]:

- он любит амбициозные идеи, простые системы и программы, поведение которых очевидно;
- не держать сложность только потому, что она уже есть, и не добавлять механизмы ради впечатления;
- найти настоящее ограничение и добиваться самой маленькой модели, при которой правильное поведение никого не удивляет;
- сначала продумать, потом делать, и не делать того, что пока не нужно (принцип YAGNI); бороться с разрастанием задач.

**Приоритеты первого дня** — из первого руководства для агентов от 2026-02-09 [14]:

- сначала производительность;
- сначала надёжность;
- предсказуемое поведение под нагрузкой и при сбоях: перезапуски sessions, переподключения, оборванные потоки данных.

### Инженерные принципы, которые формируют продукт

- **Исполнением владеет environment** [57][58]:
  - процессы provider-ов, терминалы, Git и файлы проекта принадлежат серверу;
  - клиенты управляют им только через RPC с проверкой подлинности;
  - удалённый клиент никогда не подставляет свою файловую систему или свои учётные данные.
- **Сначала надёжно записать намерение, потом выполнять действия.** Сервер построен на event sourcing [58][13]:
  - orchestrator решает, какие события произошли, и при этом не делает ввода-вывода;
  - события, модели для чтения, квитанции команд и записи об ожидающих действиях фиксируются одной транзакцией;
  - затем отдельный worker выполняет действия: запускает turn у provider-а, снимает checkpoint и т. д.;
  - каждый turn заканчивается checkpoint-ом в скрытом Git ref. Поэтому приложение умеет показывать diff и восстанавливать файлы, не добавляя коммитов в ветку пользователя [13][58].
- **Поведение задают возможности provider-а, а не его имя** [72][77]:
  - дизайн V2 берёт Codex как самый богатый протокол. Более слабые provider-ы подгоняются под ту же модель через ID, которые назначает приложение, и явные флаги возможностей;
  - ID приложения главные, ID provider-а — только ссылки;
  - смена provider-а создаёт явную запись о передаче контекста, а не скрытую подстановку в prompt [72][76];
  - tests проигрывают записанный трафик provider-а, а не подменяют его mock-ами [72][78].
- **Сложность — на границе с адаптером.** Orchestration остаётся чистой логикой, UI — простым. Обработчик WebSocket, HTTP route или MCP-инструмент только разбирает вход, вызывает один метод сервиса и переводит ошибки [13].
- **Правила для каждого изменения** [13]:
  - всё, что может сделать пользователь, обычно должно быть доступно и агенту через MCP-инструменты. Scheduled tasks идут по тем же путям кода;
  - у каждого входа в состояние должен быть выход и способ это состояние увидеть. Snooze требует unsnooze. Состояние без пути назад считается ошибкой;
  - каждая функция, которая зависит от provider-а, требует решения для каждого адаптера — даже если решение «не поддерживается».
- **Бюджеты производительности записаны в документации** [13]:
  - холодное открытие или страница истории останавливается примерно на 1 MiB закодированных строк;
  - длинные разговоры грузятся страницами.
- **Маленький внедряемый контекст.** Текст, который T3 добавляет к каждому turn-у агента, ограничен проверкой в CI. Подробности — в разделе «Проверка качества» внутри «Как это устроено внутри» [95][111][170].

### Позиции: что отвергают и что выбирают

- **Нет локальных моделей для агентов.** FAQ считает, что локальные модели не справляются с серьёзной инженерной работой [19].
- **Нет автоматического переключения аккаунтов.** Theo говорит, что такой переключатель подставит пользователей под бан по terms of service. Для многих аккаунтов он отправляет к внешнему self-hosted proxy CLIProxyAPI, а T3 Code показывает общие лимиты этого proxy [19][26].
- **Соблюдение условий AI-лабораторий** [19][223]:
  - FAQ утверждает, что T3 Code работает со всеми лабораториями и остаётся в рамках условий Claude Code, Codex и Antigravity;
  - FAQ пишет о совместной работе с AI-подразделением SpaceX (@SpaceXSI) над Grok Build и Cursor. 2026-06-25 @SpaceXSI объявил, что подписки SuperGrok и X работают внутри T3 Code.
- **Claude — через официальный SDK.** Claude работает через Anthropic Agent SDK поверх локального CLI Claude Code. В марте Theo подчёркивал, что T3 Code не подделывает заголовки и не делает своего входа через OAuth (вторичный пересказ видео) [215]. С PR #28410 (слит 2026-11-02, вышел в v0.1.7) T3 Code помечает свои процессы Claude меткой entrypoint `t3-code` [172].
- **Режим прав по умолчанию — Full access.** Новые thread-ы работают без запросов разрешений, пока пользователь не поменяет режим [22]. Администратор может ограничить режимы [42]. Агенты не могут одобрять свои запросы разрешений [126].
- **Только режимы, которые provider соблюдает сам.** T3 отказывается изображать режим, отвечая на approvals за provider-а: по объяснению вендора, его проверка была бы слабее собственной проверки агента [60].
- **Смена provider-а посреди thread-а есть, но не рекомендуется.** Передача теряет рассуждения, состояние инструментов и вложения. Совмещать harness-ы советуют через `delegate_task`: например, Claude планирует, Codex реализует [126].
- **Нет системы plugins — по правилам проекта.** CONTRIBUTING.md автоматически закрывает PR с plugins и расширениями [15].

### Процесс разработки как часть принципов

- **Внешние PR с функциями не нужны** [15]:
  - команда пишет, что её ограничивает пропускная способность review, а не идеи, токены или код;
  - внешние участники должны только исправлять ошибки;
  - автоматически закрываются: новые функции, переделки UI, новые provider-ы, архитектурные изменения, новые способы входа, новые платформы, plugins и расширения;
  - Theo добавляет, что уже жалеет о поддержке Windows на ARM.
- **Лимиты на PR** [15]:
  - не больше трёх открытых PR на человека;
  - PR, который 7 дней конфликтует с базовой веткой, закрывается;
  - PR закрывается, если автор пишет, что любой код в нём написал Gemini (любая версия) или Muse Wonder;
  - доверенный список «vouched» участников освобождён от части этих правил.
- **Работа идёт через сам T3 Code, часто удалённо.** Текст PR обязан называть модель и harness, которые сделали работу [13]. Skill contribution-triage проверяет PR на соответствие правилам и закрывает неподходящие, не спрашивая одобрения на каждый [16].
- **Практики качества для кода, который пишут агенты:**
  - **Evals** — проверки текста, который читает модель: инструкций агенту, описаний и схем MCP-инструментов, сгенерированных названий [71];
  - **бесплатный replay-provider** — dev-provider проигрывает записанные turn-ы, так что для тестов не нужны настоящие вызовы моделей [13][170];
  - **scenario proofs** — e2e-тесты на настоящем приложении. Тест обязан падать на базовом коммите и проходить с исправлением [70];
  - **ограничение размера контекста в CI** — с 2026-10-27 CI падает, если контекст, который T3 Code добавляет к каждому turn-у, вырос по сравнению с `main` [170];

### Ключевые понятия продукта

- **Environment, client, project, T3 home** [13][57]:
  - environment — один сервер плюс машина и состояние, которыми он владеет;
  - client — интерфейс: web, desktop или mobile;
  - project — рабочая область на одном environment-е с корнем в папке;
  - T3 home — папка данных T3.
- **Thread, turn, run** [57][73]:
  - thread — долговечный разговор в проекте, переживает выход процесса provider-а;
  - turn — один цикл «сообщение пользователя → работа агента»;
  - в V2 turn называется run и состоит из дерева execution nodes — узлов исполнения: вызовов инструментов, approvals, subagents.
- **Термины provider-ов** [57]:
  - provider — среда исполнения агента, например Codex;
  - driver — интеграция для одного вида provider-ов;
  - provider instance — один настроенный экземпляр provider-а. Несколько аккаунтов могут использовать один driver;
  - adapter — переводит родной протокол provider-а в общий формат;
  - session — среда provider-а, подключённая к thread-у.
- **Режимы и checkpoints** [57]:
  - runtime mode — политика прав;
  - interaction mode — как агент работает, например в режиме плана;
  - checkpoints и diff-ы turn-ов берутся из скрытых Git refs.
- **Состояния внимания thread-а** [126][21]:
  - Pinned и Active;
  - Working (beta) — занятые thread-ы убраны с глаз, пока не нужен пользователь;
  - Snoozed — отложенные; возвращаются командой Wake;
  - Settled — законченная работа убрана из активного списка. По умолчанию — после 7 дней без активности или когда слит связанный PR;
  - Limited — provider остановился на лимите расхода или частоты запросов;
  - по умолчанию sidebar группирует thread-ы по этим состояниям, а не по проектам. Группировка по проектам — в Labs [21].
- **Queue или steer.** Следующее сообщение либо меняет направление текущего turn-а (steer), либо ждёт своей очереди (queue). Очередь живёт на сервере [126].
- **Термины родства thread-ов** [126][129]:
  - fork любого thread-а и последующее слияние его контекста обратно;
  - `delegate_task` — запуск дочерних агентов на любом provider-е или модели с ожиданием их результатов;
  - lineage view — вид, который показывает эти дочерние thread-ы;
  - side chats (с v0.1.6) — вопросы без отвлечения основного thread-а.
- **T3 Code MCP** — инструменты, через которые агент создаёт thread-ы, пишет в них, ждёт их, читает, ищет и прерывает, а также управляет очередями, проектами и scheduled tasks [126][75].
- **Удалённые функции** [11][25][40][27]:
  - T3 Connect — tunnel и relay вендора;
  - linked environments — агенты на одной машине запускают thread-ы на другой;
  - guest links — коллега следит за одним thread-ом в браузере без аккаунта;
  - outside agents — ChatGPT, Claude, Poke или терминальный агент управляют environment-ом через MCP со входом по OAuth.
- **Другие названные функции** [35][34][33][23][42]:
  - Devices — живой iOS Simulator или Android Emulator рядом с thread-ом, с инструментами `device_*` для агентов;
  - SnapShots — снимки окна вместе с данными accessibility;
  - visual replies — агент отвечает HTML-страницей в sandbox;
  - review guides — AI-тур по PR;
  - managed policy — значения по умолчанию и запреты от администратора.

### Топология: один сервер на машину, тонкие клиенты

- **Сервер владеет всем.** Процессы provider-ов, терминалы, Git и файлы проекта принадлежат серверу. Клиенты управляют им только через RPC с проверкой подлинности. Удалённый клиент никогда не подставляет свою файловую систему или свои учётные данные [58].
- **Desktop несёт сервер в себе** и может быть хостом для удалённых клиентов. Hosted web-клиент живёт на `app.t3.codes` [13].

### Ядро оркестрации: event sourcing и transactional outbox

Это самая продуманная часть устройства. Вендор описывает путь запроса так [13]:

1. Клиент отправляет типизированный запрос по WebSocket.
2. Сервер превращает запрос в command — команду.
3. Orchestrator (`Orchestrator.ts`) выполняет команды по одной и решает, какие events (события) из них следуют. Ввода-вывода он при этом не делает [13][79].
4. Event sink фиксирует одной транзакцией SQLite сразу четыре вещи: события; projections — сохранённые модели для чтения, которые читает UI; receipt — квитанцию команды; записи outbox — список действий, которые ещё предстоит выполнить.
5. Effect worker выполняет действия из outbox и возвращает результаты как новые команды.

Подробности:

- **Что значит подтверждение.** Подтверждение команды значит, что намерение записано. Оно не значит, что turn у provider-а или checkpoint уже закончены [58]. Внешний ввод-вывод вынесен и из решения по команде, и из транзакции базы [58].
- **Порядок.** Путь «зафиксировать и разослать» держит semaphore на один слот. Комментарий в коде объясняет: если рассылка поменяет порядок, клиенты отбросят более ранние номера событий [80].
- **Повторы без побочных эффектов.** Квитанции делают повтор команды идемпотентным: команда с уже виденным ID возвращает тот же результат из квитанции и не запускает действия у provider-а заново [58][72].
- **Виды действий в outbox** [81]:
  - работа provider-а: `provider-turn.start`, `.interrupt`, `.steer`, `.restart`, `runtime-request.respond`, `provider-thread.rollback`;
  - рабочая папка и обслуживание: `checkpoint.capture`, `thread-title.generate`, `delegated-tasks.stop` и действия очистки.
- **Одно действие за раз на thread.** Действие можно взять в работу, только если в том же thread-е ничего не выполняется и ничего не стоит раньше в очереди. У генерации названий своя отдельная очередь. Комментарий в коде требует, чтобы ожидание повтора (backoff) блокировало более поздние действия — иначе turn мог бы обогнать ожидающий rollback [81].
- **Цикл worker-а** [82]:
  - по умолчанию 4 слота для одновременных действий;
  - до 5 попыток на действие;
  - экспоненциальный backoff 100 мс·2^(n−1), не больше 30 секунд;
  - запрос к provider-у, который ждёт дольше 30 секунд, освобождает слот, но сохраняет свою запись «выполняется». Эта запись блокирует только свой thread.
- **После падения процесса.** При старте `reconcileAfterProcessLoss` разбирает действия, которые были в работе [81]:
  - действия, привязанные к умершему процессу (старт turn-а, steer, interrupt, ответы на approvals), отменяются;
  - действия, которые безопасно повторить (снятие checkpoint, очистка, генерация названия), снова ставятся в очередь.
- **Устаревшая заметка в дизайне.** Расхождение внутри документации вендора: README дизайна V2 всё ещё числит долговечный outbox в разделе «Tracked Follow-Up» (запланировано) [72]. Код и обзор архитектуры показывают, что outbox уже сделан [81][58]. Этот раздел README устарел.

### Модель данных

- **Сущности:** `AppThread` (thread, который видит пользователь), `Run` (учитываемый turn), `RunAttempt` (попытка run-а), дерево `ExecutionNode`, `ProviderSession`, `ProviderThread`, `ContextTransfer`, `ContextHandoff` и `CheckpointScope` [73].
- **ID приложения главные, ID provider-а — ссылки.** События одного provider-а никогда не переписываются под вид другого [72].
- **Виды execution nodes:** `root_turn`, `assistant_message`, `reasoning`, `plan`, `todo_list`, `tool_call`, `approval_request`, `user_input_request`, `subagent`, `hook` и `system`. Завершить run может только корневой узел. Завершение дочернего узла никогда не закрывает родителя [72][73].
- **Разные provider-ы в одном thread-е.** Run 1 может идти на Codex, run 2 — на Claude, а run 3 — вернуться в исходный thread Codex с передачей контекста за пропущенный отрезок [73].
- **Почему run и turn provider-а разделены.** Решение выросло из опытов с Codex app-server. Примеры: событие `turn/completed` считается окончательным, даже если статус стал idle раньше; дочерние turn-ы могут закончиться раньше родительского [72].
- **Steer без поддержки у provider-а.** У run-а может быть несколько попыток. Provider-у, который не умеет менять направление идущего turn-а, T3 делает interrupt и перезапуск под тем же `RunId` [73][74].

### Цикл агента: адаптеры к harness-ам вендоров

- **Своего цикла агента нет.** FAQ: T3 Code — не harness и без harness-а не работает [19]. Каждый адаптер переводит родной протокол provider-а в общие события [13][59].
- **Claude** — через функцию `query()` из Claude Agent SDK [91]:
  - параметры включают `canUseTool`, `includePartialMessages: true` и необязательный `pathToClaudeCodeExecutable`;
  - системный prompt — preset `claude_code`, к которому T3 дописывает свои инструкции по оркестрации.
- **Codex** — как `codex app-server`, который говорит по JSON-RPC [93]. T3 отключает у Codex событие `turn/diff/updated` и строит diff-ы из своих checkpoints [59].
- **Остальные:**
  - Cursor — через официальный `@cursor/sdk` [1][126];
  - Grok, Antigravity и агенты из registry — через общий ACP-адаптер [60];
  - Pi — в режиме RPC [59];
  - у OpenCode 1.x и 2.x отдельные runtime-ы [59].
- **Поведение задают флаги возможностей.** Orchestration и клиенты читают флаги возможностей provider-а, а не его вид. Если возможности нет, поведение заранее определено политикой [77][60]:
  - нет steer — interrupt и перезапуск;
  - нет своего fork — переносимая передача контекста;
  - нет rollback разговора — rollback отклоняется до любых изменений файлов.
- **Изоляция экземпляров.** Каждый настроенный аккаунт — отдельный provider instance. Два аккаунта никогда не делят состояние sessions и каталога моделей [59]. Примеры:
  - Antigravity принудительно использует учётные данные из файла и убирает учётные данные Google из окружения [59];
  - аккаунты Claude разделены через `CLAUDE_CONFIG_DIR` [28].
- **Ловушки протоколов, которые обрабатывает код** [59]:
  - `/goal` у Codex может сам начать следующий turn, поэтому один run может владеть несколькими родными turn-ами;
  - на асинхронные вопросы Codex отвечают новым сообщением пользователя, а не ответом RPC.
- **Workflows Claude Code** (собственная многоагентная функция Claude Code) показываются как ход работы. Агент может остановить workflow инструментом `t3_workflow_stop` [99].
- **Сырые кадры provider-ов** — только диагностический log, а не долговечное состояние [72]. Данные больше 64 KiB сокращаются до сводки [59].
- **Жизнь session-а.** Session provider-а освобождается после 30 минут простоя; закреплённая — максимум через 4 часа. Потом она возобновляется по долговечным ссылкам на родную session provider-а [73][86].

### Параллельность и координация

- **Координацию ведут сами агенты** через MCP-сервер T3, центрального планировщика нет.
- **Отдельный ключ на каждую session.** Перед каждой session provider-а `McpSessionRegistry` выпускает учётные данные. Они ограничены environment-ом, родительским thread-ом, provider instance и session provider-а [75].
  - Ключ истекает при простое или по максимальному сроку и отзывается, когда session заканчивается [75].
  - Claude получает сервер как `mcpServers["t3-code"]` по HTTP на `127.0.0.1:<port>/mcp`, инструменты `mcp__t3-code__*` разрешены [75].
  - Codex получает сервер, зарегистрированный дважды, чтобы `t3_thread_wait` был прямым вызовом [75].
- **Набор инструментов** (`OrchestratorToolkit` и другие) [75][99][100]:
  - делегирование: `orchestrator_capabilities`, `delegate_task`, `task_status`, `task_cancel`;
  - управление thread-ами: `create_threads` (1–20 thread-ов), `t3_thread_launch`, `t3_thread_send` (auto, queue, steer, restart), `t3_thread_wait`, `t3_thread_interrupt`;
  - очередь и контекст: `t3_queue` (правка, перестановка, перевод сообщения в steer), `t3_thread_transfer` (fork или слияние обратно);
  - расписание: `schedule_task`, плюс инструменты для PR, браузера preview, устройств и secrets.
- **`delegate_task`** [75][105]:
  - создаёт дочерний thread приложения на любом provider instance и модели;
  - принимает `role`: implementation, research, review, design, test, general;
  - `isolation: "shared"|"worktree"`. Вариант worktree даёт новый checkout от коммита родителя; незакоммиченные правки родителя туда не попадают;
  - `mode`: async (по умолчанию) или wait (по умолчанию ждёт 4 минуты). Истечение ожидания не отменяет дочерний агент;
  - дочерний агент получает только prompt задачи, без истории родителя.
- **Завершение будит родителя.** Инструкции прямо запрещают агенту ждать и опрашивать дочерние thread-ы: родитель проснётся сам [105]. Открытый вопрос дочернего агента приходит родителю как уведомление [75].
- **Свои subagents provider-а** (`Agent` у Claude, `spawn_agent` у Codex) предпочтительны для работы на том же provider-е. T3 показывает их как вложенные дочерние thread-ы [104][126]. Запрос на это (issue #538 — subagents как вложенные thread-ы) закрыт как сделанный 2026-08-15 [137].
- **Идемпотентность.** Из `clientRequestId` выводятся стабильные ID команды, thread-а и сообщения. Завершение делегированной задачи идемпотентно через передачу контекста `subagent_result`, поэтому переживает и перезапуск сервера [75].
- **Пределы параллельности.** Общего предела на число одновременных thread-ов не найдено (не подтверждено). Действия выполняются по одному на thread. 4 слота worker-а ограничивают только выполнение действий из outbox [82].

### Декомпозиция задач и планирование

- **Встроенной декомпозиции нет.** Модели backlog, epic, ticket или Kanban в документации нет [11][13].
- **Планирование — через режим плана самого provider-а.** Режим взаимодействия (plan или default) задаётся отдельно от прав [57].
  - Вывод плана становится долговечным «proposed plan». Реализация плана создаёт новый run или новый thread со ссылкой `sourcePlanRef` [74].
  - Todo lists агента показывают ход работы вживую [74].
- **Рекомендованная схема.** Вендор советует, чтобы оркестровал сам агент: например, Claude планирует, Codex реализует через `delegate_task` [126].
- **Встроенные указания для агентов** добавляются в каждую session [104]:
  - обычные задачи по коду не требуют инструментов T3;
  - каждый новый раунд review — новый `delegate_task`, в который передают задание, найденные проблемы и возражения;
  - Codex обрезает записи больше 4000 байт, поэтому каждый раздел указаний держится меньше этого размера.

### Изоляция

- **Worktrees:**
  - каждый thread работает либо в основном checkout (`local`), либо в `worktree` [108];
  - агент может перенести свой thread в новый worktree (`t3_worktree_handoff`) или запустить thread с `workspaceStrategy` [101];
  - место по умолчанию — `<T3 home>/worktrees`. Префикс веток по умолчанию — `t3/`, или имя выбирает модель [24];
  - скрипты из `t3.json` запускаются при создании worktree (`runOnWorktreeCreate`), при уходе thread-а в Settled (`runOnSettle`) или останавливаются при этом (`stopOnSettle`) [24][6];
  - на macOS есть быстрый checkout: копия кэшированных checkout-ов через copy-on-write в APFS (beta) [24];
  - правила очистки: простой, Settled, merge, worktree без изменений, удалённый thread [24].
- **Checkpoints.** Каждый turn заканчивается скрытым Git ref [13] с именем `refs/t3/orchestration-v2/checkpoints/<scope>/ordinal/<n>` [87].
  - Снимок делается через временный `GIT_INDEX_FILE`, коммит идёт от имени «T3 Code». В ветку пользователя ничего не попадает [96].
  - На базовый снимок отведено 5 секунд [87].
  - Откат файлов должен совпадать с откатом разговора у provider-а: «Revert and keep changes» или «Revert files too» [58][20].
- **Контейнеров и виртуальных машин нет.** Документация говорит, что проекты — организационные границы, а не sandbox файловой системы. Граница файловой системы — environment [61].
  - Sandbox на уровне ОС даёт только сам provider. Соответствие режимов у Codex [92]:
    - Supervised → `untrusted` + `readOnly`;
    - Auto-accept edits → `on-request` + `workspaceWrite`;
    - Auto → `on-request` + `auto_review`;
    - Full access → `never` + `dangerFullAccess`.
  - Dev container в репозитории нужен только участникам разработки.

### Состояние и память

- **Хранилище.** SQLite в `<T3 home>/userdata/statev2.sqlite` [98][38]. При первом запуске V2 старый `state.sqlite` копируется и мигрирует. Runtime-состояние V1 (runs, checkpoints, активность инструментов) не переносится [38].
- **Сколько живут события.** Log событий хранит примерно сутки (`RETAINED_EVENT_HISTORY = 1 day`) — только для повтора событий при переподключении и для повторов команд [83]. Более старые события удаляются, поэтому восстановить projections из log-а нельзя [58].
- **Расхождение в источниках.** Сторонняя статья Flavio Copes (обновлена 2026-11-13) всё ещё называет файл состояния `state.sqlite` [203]. Это файл V1; V2 использует `statev2.sqlite` [98][38].
- **Очередь на сервере.** Сообщения в очереди переживают перезапуск и после него стоят в состоянии «held», пока пользователь не возобновит работу [20][126].
- **Отдельного хранилища памяти нет.** Память — это сам долговечный thread. Рабочий контекст держат родные sessions provider-ов [57][73].
- **Переносимая передача контекста (portable handoff)** — для смены provider-а, fork-ов, которые нельзя возобновить, и мигрированных thread-ов [37]:
  - отбираются целые сообщения в пределах бюджета. Это не сводка, написанная агентом;
  - предел — переменная `T3CODE_CONTEXT_HANDOFF_TOKEN_CAP`: по умолчанию 16 000 токенов, допустимо от 1024 до 64 000;
  - если данных о размере окна нет, предполагается окно в 128k токенов;
  - рассуждения, состояние инструментов и вложения не копируются никогда.
- **Слияние fork-а обратно.** Сводка обрезает каждый элемент до 240 символов [65][90].
- **Вендор сам называет смену provider-а потерей информации** и советует `delegate_task` [126].
- **Чтение пропущенной истории.** Агент дочитывает историю инструментом `t3_thread_read`. Чтение останавливается примерно на 30 000 символов, потому что Claude Code сохраняет более длинные результаты MCP в файл [75].
- **Управление compaction** [28][89][126]:
  - порог auto-compact у Claude (`CLAUDE_CODE_AUTO_COMPACT_WINDOW`);
  - chip «Compact», если пользователь вернулся после истечения prompt cache;
  - «Compact idle threads before the cache expires» (beta) — для thread-ов больше 200k токенов, начинается за 2 минуты до истечения кэша;
  - счётчик окна контекста.

### Проверка качества

**В самом продукте.** Встроенного запуска tests или локального gate (запуска проверок перед PR) в документации не найдено. Вместо этого есть:

- diff-ы turn-ов из checkpoints [23];
- кнопка commit/push/PR. Сгенерированный текст PR учитывает thread и проверки, которые он запускал [23];
- `watch_pull_request` [88][102]:
  - будит агента при упавших проверках, прошедших обязательных проверках, новых комментариях или review, конфликтах;
  - опрашивает PR каждые 2 минуты;
  - скрыт от subagents;
  - описание инструмента прямо говорит, что пробуждение — не решение о merge;
- reactor синхронизации PR, который замечает merge, сделанный агентом через `gh pr merge` [58];
- AI review guides (beta) — тур по PR для человека [23];
- review, порученный другому provider-у через `delegate_task` с ролью `review` [104][105].

**В собственном процессе разработки T3 Code** [13][78][60][69][70][71][111][112][113][95]:

- интеграционные tests на записанном трафике (replay fixtures). Подменяется только транспорт provider-а. Mock-и orchestrator-а или адаптеров запрещены;
- бесплатный provider «Replay (dev)» для проверок без платных вызовов моделей;
- правила lint против sleep, опроса и ожидания по часам в tests;
- `scenarios:prove` — e2e-доказательство на настоящем приложении. Оно должно падать на базовом коммите и проходить с исправлением;
- платные evals описаний инструментов и prompts;
- живой verifier фоновой работы с настоящими учётными данными;
- проверка CI «agent context budget» — бюджет размера контекста, который T3 добавляет агентам. Текущие значения в `agentContextBudget.json` [95]:
  - добавка к системному prompt Claude — 5594 байта;
  - добавленный контекст Codex — 7324 байта;
  - список MCP-инструментов — 48 094 байта;
- проверка review-агентом Macroscope «Test Signal» (модель `gpt-6-1-terra`, бюджет 1 за запуск и 5 на PR, единицы не указаны);
- автоматическое одобрение запрещено для PR, которые меняют значения по умолчанию в продукте или подавляют lint.

**Расхождение в цифрах бюджета контекста.** Заметки о направлении развития пишут, что на момент введения проверки (2026-10-27) было 4857 байт у Claude, 5409 байт у Codex и 54 964 байта у списка MCP-инструментов [170]. Файл бюджета на 2026-11-13 показывает 5594, 7324 и 48 094 байта [95]. Части Claude и Codex выросли, список инструментов уменьшился. Как проверка, которая падает на рост, пропустила рост, неизвестно — например, бюджет могли явно поднять в PR (не подтверждено).

### Восстановление после сбоев

- **Продолжение после перезапуска** включено по умолчанию. Оно возобновляет прерванные thread-ы после обновления, сбоя или перезагрузки [48].
  - Prompt продолжения предупреждает агента, что команда могла уже закончиться или ещё идти [85].
  - После 3 автоматических продолжений подряд цепочка останавливается (`MAX_CONTINUATION_CHAIN = 3`) [85].
  - Thread-ы, которые ждут approval, ответа или secret, не возобновляются [48].
- **Фоновая работа после перезапуска.** Агентам сообщают, какая фоновая работа умерла [126].
- **Повторы запросов к API делают сами provider-ы.** Сообщения `api_retry` из Claude SDK показываются как элементы повтора. Если provider объявил повтор и не продолжил, через 15 минут срабатывает timeout зависания [86][91].
- **Повторной отправки обычных упавших turn-ов на уровне T3 не найдено** (не подтверждено). Автоматические продолжения есть только после перезапуска и после лимита расхода.
- **Webhook-и, пока машина offline.** Relay держит запросы до 24 часов. Заголовок `x-t3-relay-delivery-id` отсекает повторную доставку [63].
- **Падение процесса сервера.** При старте `reconcileAfterProcessLoss` отменяет действия outbox, привязанные к умершему процессу, и снова ставит в очередь те, что безопасно повторить [81].

### Лимиты и стоимость

- **Распознавание лимитов.** Адаптеры относят ошибки квоты и частоты запросов к виду `usage_limit` и вычисляют время сброса [60]:
  - Claude — из `rate_limit_event.resetsAt`, из HTTP 429 или из текста «reset after …», который присылают gateways [91];
  - Codex — из его статуса лимита и HTTP 429 [92].
- **Worker восстановления после лимита** (`UsageLimitRecoveryWorker`) [84][21][107]:
  - ставит восстановление, когда thread упал или упёрся в лимит, время сброса известно, thread не в Settled и не ждёт ответа на запрос;
  - после сброса отправляет от имени агента короткое сообщение с просьбой продолжить с места остановки;
  - время сброса, просроченное больше чем на 24 часа, игнорируется;
  - в UI — «Resume at reset» и «Snooze until reset». Оба значения по умолчанию (`autoResumeLimitedThreads`, `snoozeLimitedThreads`) выключены;
  - в момент сброса environment должен работать. Просроченные продолжения запускаются после перезапуска сервера [21].
- **Страница Usage** [26][94]:
  - читает локальную историю каждого provider-а и показывает оценку стоимости по ценам API, а не счёт;
  - Limits объединяет 5-часовые и недельные окна по всем аккаунтам и машинам;
  - «Use reset» тратит накопленные credits сброса. Для Claude функция читает сохранённый OAuth-токен, поэтому недоступна, когда сервер работает на macOS;
  - необязательный hub CLIProxyAPI (сторонний proxy с pool-ом аккаунтов) питает вид Limits.
- **Автоматического переключения аккаунтов нет — по правилам продукта:** оно рисковало бы баном по terms of service [19].
- **Исправление учёта Agent SDK.** FAQ пишет, что Agent SDK раньше расходовал 5-часовой лимит Claude примерно в 1,7 раза быстрее, чем Claude Code, и что с v0.1.7 это исправлено [19].
- **Машина не засыпает.** Пока работают агенты, работает `caffeinate -i -w <pid>` на macOS или `systemd-inhibit` на Linux, плюс 60 секунд запаса между запусками. Включено по умолчанию (`keepAwakeWhileAgentsWork`) [97][107].
- **Собственные расходы функций T3.** «Suggest next prompt» стоит одного дополнительного запроса с кэшем на turn [20]. Review guides пишет Claude или Codex на подписке пользователя [23]. Служебный текст можно отдать дешёвому «text generator» [44].

### Права и безопасность

- **Режимы прав:** Supervised, Auto-accept edits, Auto (собственная автоматическая проверка provider-а) и Full access [22].
  - По умолчанию — `full-access` (`DEFAULT_RUNTIME_MODE`) [106][22].
  - T3 предлагает только режимы, которые provider соблюдает сам. Изображать режим, отвечая на approvals за provider-а, T3 отказывается: такая проверка была бы слабее проверки самого агента [60].
- **Managed policy.** Политика администратора в JSON задаёт значения по умолчанию и запреты, ограничивает `maxRuntimeMode` и виды клиентов. Соблюдение политики проверяет сервер [42].
- **Дочерние агенты** могут только сужать режим прав и режим взаимодействия родителя. Инструменты, которые меняют thread-ы, требуют живого run-а у вызывающего агента [75].
- **Агенты не одобряют запросы разрешений.** `t3_pending_request` не умеет одобрять запрос разрешения [100][126].
- **Проверка подлинности клиентов** [61]:
  - sessions с scopes. Сопряжение по умолчанию выдаёт все scopes: доступ к терминалу или к оркестрации всё равно позволил бы выпустить любую session;
  - токены, привязанные к ключу клиента (DPoP), и короткоживущие билеты для WebSocket;
  - каждый вызов RPC объявляет нужный ему scope.
- **Внешние MCP-агенты** входят через OAuth с PKCE [61]:
  - доступ — либо только чтение, либо потолок режима прав;
  - такие sessions принимаются только на `/mcp`.
- **Guest links** — HMAC-токены без хранимого secret [61].
- **Secrets** проходят через карточки `request_secret` и ссылки на 1Password [41][99].
- **Webhooks.** Данные запроса попадают к агенту обёрнутыми и помеченными как недоверенные. Символы `$`, `@` и `/` обезвреживаются, чтобы упоминания и команды в них не срабатывали [24].

### Где решает человек

- Approvals. Approvals subagents показываются в родительском thread-е [22].
- Структурированные вопросы агента и запросы secrets [75][41].
- Принятие плана [74].
- Создание и merge PR. PR watch только будит агента [102].
- Resume после остановки или лимита и очередь, которая стоит в «held» после перезапуска [20].
- Карточки одобрения для связи машин и для входа внешних агентов [25][27].
- Подтверждение перезапуска при обновлении [48].
- Triage: агент сам расследует ошибку T3 Code, но спрашивает перед исправлением или публикацией [52].

### Наблюдаемость

- **Состояние thread-ов в UI.** Статусы в sidebar: Working, Waiting, Limited, Failed. Waiting учитывает ожидание другого thread-а (`blockedOnThreadWait`) и незаконченные фоновые задачи [75][126].
- **Activity log.** Сгруппированные вызовы инструментов с exit codes и живым выводом, плюс сводки orchestrator-а вида «отправлено 5 сообщений в 2 thread-а» [36].
- **Lineage view** — дерево subagents с моделью, статусом и длительностью [21][126].
- **Minimap ленты thread-а** [119].
- **Push-уведомления** (закончил, упал, ждёт approval, ждёт ввода) и Live Activities на iOS и Android. Доставляются через relay [45][64].
- **Telemetry для maintainers.** Файл трассы в NDJSON и необязательная отправка в OTLP [68]. Монитор процессов на Rust [66].
- **Не найдено:** ленты событий автономного запуска.

### Удалённая работа и несколько машин

- **Маршруты:** LAN, Tailscale, запуск по SSH или T3 Connect [62][25].
  - T3 Connect использует вход через Clerk и Cloudflare tunnel (`cloudflared`) [63].
  - Через relay не идёт основной трафик: он только устанавливает связь [63][19][64].
  - Бесплатно для 3 машин; привязка плана T3 Chat поднимает лимит [19].
- **Linked environments (beta)** — агент на одной машине запускает thread-ы на другой, пишет в них, ждёт и останавливает их [25]:
  - `delegate_task` может запустить дочерний агент на другой машине;
  - связь живёт 30 дней;
  - ниже Full access связь может менять только thread-ы, которые сама запустила.

### Что ругают

#### 5-часовой лимит Claude тратится быстрее — главная жалоба

- **2026-08-17.** Issue #7338 («Extremely high usage») сообщило о расходе в 3–5 раз выше, чем в родном Claude, на v0.0.33 [146]. За три месяца — около 80 комментариев. Несколько человек удалили T3 или вернулись к Claude Desktop или CLI [146].
- **2026-08-26.** Пользователь поставил перед API proxy с логированием. Запросы T3 совпадали с запросами родного Claude Code байт в байт, кэш работал [146].
- **2026-08-28.** Theo закрыл issue [146]:
  - разницу он объяснил в основном поведением пользователей в T3: больше параллельных thread-ов, больше возвратов к старым thread-ам, реже compaction;
  - он выпустил подсказки, которые подталкивают чаще сжимать контекст;
  - без сравнения двух инструментов бок о бок issue останется закрытым.
- **Октябрь: пользователи провели контролируемые A/B-тесты** [146]:
  - Mauznemo (10-02): на одинаковых запросах T3 тратил в 2–3 раза больше 5-часового окна. Отличалось только то, каким клиентом представлялось приложение;
  - gustavohariel (10-19) переделал T3, чтобы тот управлял CLI `claude`, а не Agent SDK. Через SDK вышло около 0,33 млн токенов на 1% окна, через CLI — 0,76–0,97 млн;
  - AchuAshwath (10-22): метка entrypoint причиной *не* была. Интерактивное терминальное приложение тратило примерно на 45% меньше окна за запуск.
- **2026-10-25.** Ответ, написанный AI от имени Theo, подтвердил настоящую ошибку на стороне Anthropic: 5-часовой счётчик списывал трафик Agent SDK примерно в 1,6–1,7 раза дороже интерактивного терминала. Недельные лимиты это не затрагивало [146][162]. В тот же день Theo написал об этом в X и сообщил Anthropic [162][222].
  - Цифры за запуск в issue, где отслеживали проблему: терминал +7%, T3 +13% и +16%, `claude -p` +9% [162].

  - Комментатор на GitHub описал это как перемаркировку трафика, чтобы уйти от наценки на SDK [146].
  - Проверка на плане Pro после merge показала расход как у терминала [162].

#### Сбои делегирования и работы без присмотра

Сбои случаются там, где работа переходит от одного агента или запуска к другому:

- вопрос или approval делегированного дочернего агента не доходил до родителя; для связанных машин issue всё ещё открыто [152][165];
- `delegate_task` не может запустить дочерний агент в другом локальном проекте [168];
- следующее сообщение потеряло итоговый результат [160];
- упавший запуск по расписанию записан как успешный [159];
- scheduled tasks всегда создают ветку от `main` — в репозиториях без такой ветки каждый запуск падает [155] — и не умеют задавать модель и effort [157];
- PR watch молча заканчивается при merge [163];
- режим Auto у Claude выполнял команды, которые правила пользователя «ask» должны были остановить [153]; режим Auto у OpenCode игнорирует шаблоны разрешений [149];
- в тесте Techstackups dispatcher (агент, который раздаёт задачи) подгонял исполнителей, которые просто ждали CI [202];
- skills у некоторых provider-ов не показываются [141][134].

### Почему приходят и почему уходят

- **Почему приходят:**
  - продажа Conductor компании Meta [177][204];
  - неприязнь к объединённому desktop-приложению ChatGPT/Codex [192];
  - желание держать агента на отдельной машине ради безопасности [197];

- **Почему уходят или откладывают:**
  - быстрый расход 5-часового лимита [146];
  - медленная работа [138];
  - ошибки и функции, которых нет по сравнению с Claude Desktop [176];

  - у пользователей Pi в июле не было поддержки [198]; сейчас Pi в списке [11];

  - нужны hosted облачные workspaces. T3 не размещает агентов у себя — машина пользователя должна быть включена [200][177, основатель boxes.dev][204].

  - тратит остаток недельного лимита: Opus предлагает улучшения, одобренные строятся в отдельных worktrees;
  - встаёт на паузу, пока пользователь сам работает; есть панель лимитов.
- **Qitt — агент «chief of staff»** [207][196]:
  - работает как закреплённый thread T3 с thread-ами-исполнителями;
  - запускается через scheduled tasks T3 и webhook-и из Slack и Jira;
  - требует постоянно включённого сервера.
- **Сервер T3 в каждом dev container (unbeholden.dev)** [201]. Проблемы:
  - каждый container нужно сопрягать отдельно;
  - worktrees, созданные обычным `git worktree`, не привязываются к thread-ам;
  - встроенному браузеру в root-containers нужно выключать sandbox Chrome;
  - пакет nix весит 3,7 GiB;
  - серверы не поднимаются сами после перезагрузки;
  - собственные инструкции T3 для агентов конфликтуют с инструкциями пользователя.
- **Обзор Cloudroom** (его написал конкурент; версия v0.0.45) [200]:
  - установленные provider-ы были скрыты из списка;
  - предупреждения появлялись без объяснений;
  - агенты не могли запускать thread-ы;
  - subagents нельзя было открыть;
  - проекты по умолчанию создавались в `~/.t3/projects`;
  - часть этого относится к той версии: позже появились CLI `t3` и `delegate_task` [202][203].
- **Фрилансер (bmateas.com)** заменил Cursor и Claude Code на T3. Он остался на T3 и после перехода с Claude на ChatGPT [199].

### Сравнения с другими инструментами

- **Claude Desktop и приложение Codex.** По функциям T3 идёт с ними на равных [177], UX для разработчика сильнее [175]. Но часть пользователей вернулась к Claude Desktop из-за расхода лимита [146] или нехватки функций [176].
- **Conductor.** Многие перешли на T3 после продажи Conductor компании Meta. В T3 всё ещё нет очистки worktree, вкладок и навигации по коду, как в Conductor [178]. Основатель конкурирующего продукта пишет, что T3 не заменяет Conductor Cloud один в один [177].
- **Paseo.** Лицензия Apache-2.0, сильная система plugins, мобильное приложение без app store. Вкладки ближе к Conductor [195][178][177]. Единственный отзыв на одну звезду в App Store называет T3 ничем не примечательным рядом с Paseo [225].
- **Herdr, cmux и менеджеры терминалов.** Часть пользователей прошла путь Conductor → Herdr → T3 [177][179]. Один перешёл с cmux [175]. Другие остаются на своих менеджерах терминалов [179]. В тесте Techstackups Herdr сам взял новые issues без prompt-а [202].
- **OpenChamber и Orca.** У OpenChamber, по отзывам, меньше ошибок [181]. Orca выигрывает браузером: выделяешь элемент страницы и отправляешь агенту комментарий к нему [181].
- **Переполненный рынок.** Комментаторы видят десятки почти одинаковых приложений этого вида [180][191].
- **Сравнение MindStudio.** T3 — лучший бесплатный интерфейс для задач поверх существующего плана Claude. Но параллельные thread-ы всё равно делят один лимит [205].

### Что принёс v0.1.0 (Orchestrator V2)

Orchestrator V2 — переписанное ядро, которое ведёт thread-ы, turn-ы и действия. Его вводили поэтапно: PR #4768 (2026-07-28) и PR #15041 (2026-10-03) [171]. Пользователи переходили на V2 через одноразовую миграцию базы [151]. Вместе с V2 пришли [126][151]:

- `delegate_task`, MCP-сервер T3 Code и ACP Registry;
- Pi и OpenCode 2;
- fork и смена provider-а посреди thread-а;
- очередь на сервере, которая переживает перезапуск;
- Resume at reset и Snooze until reset;
- продолжение прерванных thread-ов после перезапуска;
- scheduled tasks.

Объём следующих релизов: v0.1.6 — 521 изменение от 137 участников, v0.1.7 — 659 изменений от 160 участников [129][130].

### Темы последних трёх месяцев

- **Агенты управляют агентами.** `delegate_task` и MCP-инструменты управления [126], внешние агенты через MCP [27], linked environments [25]. В linked environments пользователь может, например, попросить агента делегировать задачу своему VPS [25].
- **Работа без присмотра — из маленьких частей, а не через планировщик:**
  - долговечная очередь [126];
  - Resume at reset и Snooze until reset. В момент сброса environment должен работать; просроченные продолжения запускаются после перезапуска [21];
  - продолжение после перезапуска [126];
  - scheduled tasks: повторяющиеся, одноразовые или по webhook — например, на новый PR на GitHub или упавший CI job. Публичный URL для webhook требует T3 Connect [24];
  - `watch_pull_request` — проверяет PR каждые 2 минуты и будит агента при упавших проверках, review или конфликтах [23];
  - auto-settle на стороне сервера [21][57].
- **Функции для администраторов и команд.** Managed policy задаёт режимы по умолчанию, список provider-ов, telemetry и разрешённые клиенты [42][130]. Есть secrets из 1Password [129], guest links [40] и ссылки на thread-ы [130].
- **Инструменты против узкого места в review:** страница Pull requests по всем environment-ам, stacked PR, review guides, отметки viewed [23][124].
- **Визуальная работа и устройства:** Devices, SnapShots, visual replies и встроенный браузер [35][34][33][25][122].

- **Цена.** Бесплатно и под MIT; заплатить команде нельзя [19]. Пользователь платит своим provider-ам [11][19]. Terms of Service (с 2026-07-15): подписки T3 Tools сейчас нет; цена будущих платных функций будет показана заранее [4].
- **Единственный платный рычаг сегодня** [19][25]:
  - T3 Connect бесплатен до 3 машин; телефоны и браузеры не считаются;
  - привязка платного плана T3 Chat поднимает лимит до 10 машин (Pro) или 100 (Premier). T3 Chat — AI-чат той же компании;
  - FAQ оговаривает, что курс может измениться, если расходы на relay станут слишком большими.
- **Слова основателя о деньгах** (всё — вторичные пересказы):
  - март: T3 Code отделён от T3 Chat и сделан потому, что команде он был нужен. Платный сервис, который объединит модели и harness-ы, возможен позже, но не в приоритете [212][215];
  - март: продукт не приносит денег, разработчикам платит компания [215];
  - август: у продукта есть некоторый потенциал заработка в будущем [211].
- **Данные.** Код и prompts идут с машины пользователя к provider-у, а не к T3 [19]. T3 Connect работает через Cloudflare tunnel; relay устанавливает связь, но не проксирует sessions [19]. События использования идут в PostHog без prompts и содержимого файлов [19][5]. Вход — Clerk, инфраструктура T3 Connect — Cloudflare [5].
- **Главный бизнес-риск — правила подписок AI-лабораторий:**
  - в мае 2026 Anthropic объявила, что с 15 июня программное использование (Agent SDK) будет расходовать отдельный месячный credit (вторичный пересказ видео) [216];

Заметки о направлении развития опирались на вторичную статью августа, по которой Anthropic временно отложила изменение; вступило ли изменение в силу, в них осталось неизвестным (не подтверждено) [211]. Заметки об отзывах приводят первичный источник — страницу поддержки Anthropic: изменение приостановлено 2026-06-15, а использование SDK со входом в аккаунт расходует лимиты подписки [230];

## Слабые места и чего нет

- **Нет слоя планирования.** Нет backlog, epic, ticket, Kanban или очереди задач. Единицы работы — проекты, thread-ы, goals и scheduled tasks. Разбиение задачи на части отдано агенту и режиму плана provider-а [11][13][74].
- **Нет проверки перед PR.** Встроенного запуска tests или локального gate не найдено. Tests — только скрипты в `t3.json`, а PR watch лишь реагирует на CI [6][23][88].
- **Работа без присмотра собрана из частей и ломается на стыках.**
  - Повторы ошибок API делают только сами provider-ы. Повторной отправки обычных упавших turn-ов на уровне T3 не найдено (не подтверждено) [86][91].
  - Продолжение после перезапуска останавливается после 3 попыток подряд [85].
  - Сообщения об ошибках: вопрос или approval дочернего агента не доходил до родителя; упавший запуск по расписанию записан как успешный; scheduled tasks всегда ветвятся от `main` и не задают модель; PR watch молча заканчивается при merge [152][165][159][155][157][163].
  - В тесте Techstackups dispatcher подгонял агентов, которые ждали CI, а на следующем круге сам ничего не начал [202].
- **Нет ленты автономного запуска.** Есть activity log, minimap, lineage view, история смены моделей и журнал Deliveries у webhook-ов, но отдельной ленты событий запуска без присмотра не найдено [36][119][126][130][24].
- **Нет журнала работы по дням.** Usage показывает расход за 24 часа — 90 дней, но не журнал сделанного [26].
- **Лимиты видны, но запуски под них не планируются.** Страница Limits сильная, но планирования запусков под лимиты и экономного режима не найдено [26].
- **Своего движка правил approvals нет, режим по умолчанию — Full access.** Только запомненные одобрения самих provider-ов и ограничение от администратора [22][42]. Пользователи сообщали, что Auto у Claude и OpenCode пропускал команды, которые должны были требовать подтверждения [153][149].
- **Нет sandbox от T3.** Контейнеров и виртуальных машин нет; изоляция ОС — только от provider-а [61][92].
- **Зависимость от правил подписок AI-лабораторий.** История с 5-часовым лимитом Claude шла с августа по ноябрь, и сообщения о быстром расходе приходили ещё 2026-11-13 [146][162]. Объявленное в мае изменение Anthropic для Agent SDK угрожало всей модели работы [216][230].
- **Качество и стабильность.** Регрессии в nightly (пустые thread-ы 2026-10-30), потеря истории при миграции на V2, утечка памяти после сна, compaction по Enter по умолчанию [167][151][142][158]. Скрытые refs checkpoints раздувают репозиторий и замедляют `git fetch` [161][164][200].
- **Обслуживание силами AI.** Трекер в основном пишут и отвечают агенты; часть пользователей просит ответа от человека и жалуется на закрытие issues не по делу [10][158][143].
- **Закрытая модель участия и нет системы plugins.** Внешние PR с функциями закрываются автоматически; plugins и расширения запрещены правилами [15]. Пользователи называют настройку под себя самым слабым местом; skills у некоторых provider-ов не показываются [176][141].
- **Нет проектов из нескольких репозиториев.** Это самая популярная просьба; работа только началась (слой 1 из 4) [145][173].
- **Telemetry включена по умолчанию.** Хэшированные ID включают аккаунты OpenAI и Claude; согласия внутри приложения нет [143][51].
- **Удалённый доступ хрупок.** Связь машин в LAN не работает из-за ссылок `http://`; сопряжение истекает через 30 дней; relay отдаёт 504; на Windows 11 бывают сбои настройки и нечитаемый список подключений [166][169][156][150][147]. Токен сопряжения по умолчанию даёт полный доступ, включая терминал [61][201].
- **Нужна постоянно включённая машина.** Облачных агентов нет, запрос на управление облачными sessions закрыт как «not planned» [154][200][177]. Официального Docker-образа нет [188]. В containers серверы сами не поднимаются после перезагрузки, пакет nix весит 3,7 GiB [201].
- **Нет локальных моделей для агентов** — по решению вендора [19].
- **Нет командных функций:** workspaces, ролей, общей оплаты, SSO [64][5].
- **Нет интеграций с Linear, Jira и Slack** [39].
- **Нет canvas-а.** Интерфейс — sidebar, thread и вкладки правой панели [114][117][121].
- **Нет AI-помощника в терминале** [20][43].
- **Нет privacy scrub для снимков.** SnapShots снимает окно целиком; гость по guest link видит всё, что напечатал агент [34][40].
- **Ограничения отдельных provider-ов.** У Cursor нет fork, rollback и интерактивных approvals [31]. «Use reset» для Claude не работает на сервере под macOS [26]. Сборки CLI для Intel Mac нет [18].

## Пересечение с worfy

Термины worfy в этом разделе:

- Canvas — бесконечное полотно, на котором worfy показывает работу агентов.
- Epic — группа связанных Ticket-ов. Ticket — одна задача.
- Orchestrator — session, которая планирует и раздаёт Ticket-ы.
- Wave — набор Ticket-ов, которые запускаются вместе. Autopilot — запуск Wave-ов без человека.
- Gate — локальный запуск проверок перед PR.
- Harness — plugin worfy, который приносит в Claude Code rules, skills, subagents и hooks.
- Flight Recorder — лента событий запуска без присмотра. Work track — вся работа проекта по дням и неделям.
- Cards — карточки, которые агенты строят на Canvas через MCP-сервер.
- Product Session — продуктовый советник с живым Mind map и критиком spec.
- Evidence — скриншоты-доказательства с privacy scrub (удалением личных данных).
- Eco mode — экономный режим расхода.

### Где пересекаются

- **Claude Code и Codex на подписках пользователя.** T3: Claude через Agent SDK, Codex через App Server, на планах пользователя; T3 не перепродаёт токены [19][28][29]. worfy: sessions Claude Code и Codex CLI.
- **Один пользователь, desktop-приложение на Electron.** T3: Electron 44 на macOS, Windows и Linux; продукт для одного человека на его машинах [110][2][19]. worfy: Electron, macOS, порт на Windows в работе, один пользователь.
- **Worktree на единицу работы.** T3: worktree на thread или на делегированную задачу, setup-скрипты и правила очистки [24][75]. worfy: git worktree на каждый Ticket.
- **PR из работы агента.** T3: commit, push и PR одной кнопкой, текст PR учитывает запущенные проверки [23]. worfy: PR на каждый Ticket с CI badges.
- **Список PR и реакция на CI.** T3: страница Pull requests по всем хостам и машинам, PR watch с пробуждением на упавших проверках, stacks, review guides [23][88]. worfy: PR inbox и CI badges.
- **Агенты-reviewer-ы.** T3: `delegate_task` с ролью `review`, каждый раунд review — отдельная задача; review guides для человека [104][105][23]. worfy: reviewer subagents с review lenses (разными углами проверки).
- **Оркестрация через агента.** T3: любой thread может планировать и раздавать работу через MCP — `create_threads` (до 20 за вызов), `delegate_task` с ролями [75]. worfy: Orchestrator session планирует и раздаёт Ticket-ы.
- **Ожидание сброса лимитов подписки.** T3: Limited, Resume at reset, Snooze until reset, обход provider-ов, которые только что упёрлись в лимит [21][84]. worfy: Autopilot ждёт сброса лимитов подписки.
- **Счётчики расхода и лимитов.** T3: Usage и Limits с объединением аккаунтов и временем сброса [26]. worfy: счётчики лимитов и расхода.
- **Политика прав.** T3: четыре режима прав и потолок от администратора [22][42]. worfy: Autopilot одобряет permission prompts по политике.
- **MCP-сервер, через который агенты управляют приложением.** T3: MCP-инструменты для thread-ов, задач, расписаний, PR, браузера, устройств и secrets [75][99]. worfy: MCP-сервер, через который агенты строят Cards на Canvas.
- **Визуальный вывод агента.** T3: visual replies (HTML-страница в sandbox над ответом) и MCP Apps [33]. worfy: Cards на Canvas.
- **Встроенный браузер с профилями.** T3: вкладки, общие для устройств, отдельное хранилище агента, передача управления, импорт cookies из профилей [25][53]. worfy: встроенный Browser с профилями.
- **Терминал.** T3: терминалы на сервере, переподключение с любого клиента [43]. worfy: Terminal с AI-помощником.
- **Связанные машины.** T3: linked environments (beta), сопряжение в LAN, T3 Connect, Auto balance [25]. worfy: Linked machines по LAN.
- **Скриншоты.** T3: SnapShots — снимок окна с данными accessibility в черновик [34]. worfy: Evidence screenshots.
- **Уведомления.** T3: уведомления desktop и web, push на телефон [116][45]. worfy: уведомления.

### Где расходятся

- **Иерархия работы.** T3 ставит в центр thread: нет Epic, Ticket или Wave, нет backlog [11][13]. worfy: Epic → Ticket → Wave, Orchestrator.
- **Работа без присмотра.** T3 собирает её из частей: очередь, расписания, webhook-и, PR watch, продолжение после перезапуска, `delegate_task` [126][24][23]. Ведущего запуска над набором задач нет. worfy: Autopilot запускает Wave-ы Ticket-ов без человека.
- **Повтор ошибок API.** T3 полагается на повторы самих provider-ов и timeout зависания 15 минут [86][91]. worfy: Autopilot сам повторяет ошибки API.
- **Approvals.** T3 сознательно не отвечает на approvals за provider-а и отдаёт решение режимам provider-а; по умолчанию — Full access [60][22]. worfy: Autopilot одобряет permission prompts по своей политике.
- **Проверка результата.** T3: нет локального gate; проверки — скрипты и CI через PR watch [6][88]. worfy: tests и локальный Gate перед PR.
- **Что T3 приносит в агента.** T3 добавляет инструкции и MCP-сервер и держит этот контекст маленьким проверкой в CI; plugins с skills и hooks не поставляет [104][95][111]. worfy: Harness plugin с rules, skills, subagents и hooks внутри Claude Code.
- **Сколько агентов.** T3: десять provider-ов плюс ACP Registry; смена provider-а посреди thread-а [126][30]. worfy: Claude Code и Codex CLI.
- **Где клиенты.** T3: desktop, web, iOS и Android — клиенты одного сервера; телефон — главный пульт [11][13][19]. worfy: desktop-приложение.
- **Удалённый доступ.** T3: и LAN, и интернет через relay вендора, Tailscale, SSH [25][63]. worfy: Linked machines по LAN.
- **Экран.** T3: sidebar, thread и вкладки правой панели; canvas-а нет [114][117][121]. worfy: бесконечный Canvas и Cards.
- **Наблюдение за запуском.** T3: activity log, minimap, lineage view, журнал Deliveries; ленты автономного запуска нет [36][119][24]. worfy: Flight Recorder и Work track.
- **Планирование под лимиты.** T3: показывает лимиты и продолжает thread после сброса, но запуски под лимиты не планирует, экономного режима нет [26][84]. worfy: планирование запусков под лимиты подписки и Eco mode.
- **Продуктовый слой.** У T3 его нет [11]. worfy: Product Session с Mind map и критиком spec.
- **Privacy scrub.** У T3 не найден [34][40]. worfy: Evidence screenshots с privacy scrub.
- **Терминал.** У T3 нет AI-помощника внутри терминала [20][43]. worfy: Terminal с AI-помощником.
- **Платформы.** T3 работает и на Linux, есть мобильные приложения [2][224][226]. worfy: macOS, Windows в работе.
- **Собственный процесс вендора.** Внутри своего репозитория T3 использует конвейер issue → PR с review агентами двух vendor-ов и снятием доказательства [174][70]. Это ближе всего к Autopilot, reviewer lenses и Evidence в worfy, но в продукт T3 этот конвейер не входит [174].

## Механизмы, которые стоит изучить

1. **Transactional outbox с порядком по thread-у и разбором после падения.**
   - Что это: ядро Orchestrator V2. Решение по команде, события, модели для чтения, квитанция команды и список предстоящих действий фиксируются одной транзакцией SQLite. Действия выполняет отдельный worker [13][58].
   - Как работает: действие берётся в работу, только если в его thread-е ничего не выполняется и ничего не стоит раньше; backoff повтора блокирует более поздние действия того же thread-а. 4 слота, до 5 попыток, backoff 100 мс·2^(n−1) до 30 секунд. После падения `reconcileAfterProcessLoss` отменяет действия, привязанные к умершему процессу (turn-ы, ответы на approvals), и снова ставит в очередь безопасные (checkpoint, очистка, названия). Квитанции делают повтор команды идемпотентным [81][82][58].
   - Чем интересно: запуск без присмотра переживает падение процесса без двойного старта turn-а и без гонки turn-а с rollback.
   - Источник: [13][58][80][81][82].
2. **Checkpoint каждого turn-а в скрытом Git ref.**
   - Что это: снимок рабочей папки после каждого turn-а [13][87].
   - Как работает: снимок пишется через временный `GIT_INDEX_FILE` в ref `refs/t3/orchestration-v2/checkpoints/<scope>/ordinal/<n>`, коммит от имени «T3 Code», на базовый снимок отведено 5 секунд. Diff-ы turn-ов строятся из этих refs, а не из событий агента (у Codex T3 даже отключает его `turn/diff/updated`). Откат файлов («Revert files too») согласован с откатом разговора и отклоняется, если папкой пользуется другой thread [87][96][59][20].
   - Чем интересно: diff и откат на любом turn-е без коммитов в ветку пользователя. Обратная сторона — refs раздувают репозиторий и замедляют `git fetch` [161][164].
   - Источник: [87][96][59][20][161].
3. **Распознавание лимита и продолжение после сброса.**
   - Что это: `UsageLimitRecoveryWorker` и статус Limited [84][21].
   - Как работает: адаптеры переводят ошибки квоты в вид `usage_limit` с временем сброса — у Claude из `rate_limit_event.resetsAt`, HTTP 429 или текста gateway, у Codex из статуса лимита и HTTP 429. Worker ставит продолжение, только если thread упал или упёрся в лимит, не в Settled и не ждёт ответа на запрос; после сброса отправляет агенту сообщение продолжить; сбросы, просроченные больше чем на 24 часа, игнорирует. Новые thread-ы обходят provider-а, который только что упёрся в лимит [60][91][92][84][21].
   - Чем интересно: ожидание сброса привязано к отдельному thread-у и к времени сброса, которое сообщил сам provider, с явными условиями «не продолжать».
   - Источник: [21][60][84][91][92].
4. **Продолжение после перезапуска с пределом цепочки и запретом сна.**
   - Что это: «Continue threads after restarts» плюс `KeepAwake` [48][85][97].
   - Как работает: после обновления, сбоя или перезагрузки прерванные thread-ы возобновляются; prompt предупреждает агента, что команда могла уже закончиться или ещё идти. После 3 продолжений подряд цепочка останавливается (`MAX_CONTINUATION_CHAIN = 3`); thread-ы, которые ждут approval, ответа или secret, не трогаются. Пока работают агенты, машину держит проснувшейся `caffeinate -i -w <pid>` или `systemd-inhibit` с 60 секундами запаса [48][85][97].
   - Чем интересно: длинный запуск без присмотра защищён и от сна машины, и от бесконечного цикла «упал — продолжил — упал».
   - Источник: [48][85][97][107].
5. **Флаги возможностей provider-а с заранее заданной деградацией.**
   - Что это: orchestration и клиенты читают флаги возможностей, а не имя provider-а [77][60].
   - Как работает: нет steer — interrupt и перезапуск под тем же `RunId`; нет своего fork — переносимая передача контекста; нет rollback — rollback отклоняется до изменений файлов. Каждая функция, которая зависит от provider-а, требует явного решения для каждого адаптера, даже если это «не поддерживается». Режимы прав, которые provider не соблюдает сам, T3 не изображает [77][60][73][13].
   - Чем интересно: способ держать несколько агентов (Claude Code, Codex и другие) в одной модели данных без веток кода по имени агента.
   - Источник: [13][60][73][77].
6. **`delegate_task` через MCP с ключом на session и пробуждением родителя.**
   - Что это: делегирование задачи дочернему агенту любого provider-а [75][105].
   - Как работает: перед каждой session `McpSessionRegistry` выпускает ключ, ограниченный environment-ом, родительским thread-ом, provider instance и session; ключ истекает при простое и отзывается в конце session. Дочерний агент получает только prompt задачи, режим `isolation: "worktree"` даёт ему checkout от коммита родителя, права можно только сузить. Родителя будит завершение — опрашивать запрещено инструкцией. Вопрос дочернего агента приходит родителю уведомлением. `clientRequestId` делает создание идемпотентным, итог фиксируется передачей `subagent_result` и переживает перезапуск сервера. Агент не может одобрить запрос разрешения [75][105][100].
   - Чем интересно: reviewer или исполнитель на другом vendor-е запускается из самого агента, без центрального планировщика, и без прав выше родительских.
   - Источник: [75][100][104][105].
7. **Переносимая передача контекста по бюджету и чтение истории по запросу.**
   - Что это: portable handoff при смене provider-а, fork-ах без возобновления и миграции [37][65].
   - Как работает: новому provider-у отбираются целые сообщения в пределах бюджета — 16 000 токенов по умолчанию, от 1024 до 64 000 (`T3CODE_CONTEXT_HANDOFF_TOKEN_CAP`); при неизвестном окне считается 128k. Рассуждения, состояние инструментов и вложения не передаются. Остальное агент дочитывает инструментом `t3_thread_read`, ответ которого обрезан на 30 000 символов, чтобы Claude Code не уводил его в файл. Сводка слияния fork-а обрезает каждый элемент до 240 символов [37][65][90][75].
   - Чем интересно: предсказуемый размер контекста при передаче работы между агентами, без сводки, которую пишет модель.
   - Источник: [37][65][75][90].
8. **PR watch с явными условиями пробуждения и остановки.**
   - Что это: `watch_pull_request` и `PullRequestWatchReactor` [88][102].
   - Как работает: сервер опрашивает PR каждые 2 минуты. Агент просыпается на упавшей проверке, workflow, который ждёт одобрения, прохождении обязательных проверок, чужих комментариях или review, конфликте, выпадении из merge queue. Наблюдение заканчивается при merge или закрытии, после 10 пробуждений подряд только из-за комментариев, после 8 неудачных чтений подряд или по Stop. Инструмент скрыт от subagents, а его описание говорит агенту, что пробуждение — не решение о merge [23][88][102].
   - Чем интересно: агент дежурит у PR без постоянной session и без зацикливания на комментариях. Пользователи жалуются, что о merge наблюдение сообщает молча [163].
   - Источник: [23][88][102][163].
9. **Бюджет контекста агента как проверка CI.**
   - Что это: CI падает, если текст, который T3 добавляет к каждому turn-у агента, растёт по сравнению с `main` [170][111][95].
   - Как работает: `agentContextBudget.json` хранит размеры: добавка к системному prompt Claude, контекст Codex, список MCP-инструментов (на 2026-11-13 — 5594, 7324 и 48 094 байта). Workflow `agent-context-budget.yml` сравнивает их при каждом PR. Рядом — платные evals текста, который читает модель: инструкций, описаний и схем инструментов [95][111][71].
   - Чем интересно: размер «обвязки», которую приложение приносит агенту, становится измеряемой величиной с проверкой, а не случайно растущим prompt-ом.
   - Источник: [71][95][111][170].
10. **Replay-provider и доказательство «падает до исправления, проходит после».**
    - Что это: способ тестировать приложение, которое управляет агентами, без платных вызовов моделей [13][78][70].
    - Как работает: интеграционные tests проигрывают записанный трафик provider-а; подменяется только транспорт, mock-и orchestrator-а и адаптеров запрещены. Dev-provider «Replay (dev)» отдаёт записанные turn-ы бесплатно. `scenarios:prove` запускает настоящее приложение и требует, чтобы сценарий падал на базовом коммите и проходил с исправлением. Lint запрещает в tests sleep, опрос и ожидание по часам [13][78][70].
    - Чем интересно: детерминированные tests оркестрации агентов и доказательство исправления, которое можно приложить к PR.
    - Источник: [13][70][78][170].
11. **Состояния внимания thread-а с серверными правилами и ранним пробуждением.**
    - Что это: разделы Working, Snoozed, Settled и Limited в sidebar [21].
    - Как работает: занятые thread-ы сворачиваются в Working, пока не нужен пользователь. Snooze прячет thread до срока, но возвращает его раньше при approval, вопросе или сбое. Settled наступает после 7 дней без активности или после merge связанного PR; правила работают на сервере, даже когда все клиенты закрыты. Принцип продукта: у каждого состояния есть выход и способ его увидеть [21][13].
    - Чем интересно: много параллельных агентов без перегрузки человека. Пользователи отдельно хвалят именно такой разбор thread-ов [176][175].
    - Источник: [13][21][175][176].
12. **Webhook-триггеры с недоверенными данными, дедупликацией и объединением.**
    - Что это: scheduled task типа «On webhook» [24].
    - Как работает: значения из запроса подставляются в prompt через `{{body.path}}`, обёрнутые и помеченные как недоверенные; символы `$`, `@` и `/` обезвреживаются. Проверяется подпись GitHub, повтор с тем же ключом игнорируется 7 дней, запросы объединяются в окне 10–3600 секунд (по умолчанию 120), всё пишется в журнал Deliveries. Relay держит запросы до 24 часов, пока машина offline, и отсекает повторы по `x-t3-relay-delivery-id` [24][63].
    - Чем интересно: запуск агента по событию из CI или трекера с защитой от prompt injection через данные события и от лавины повторных запусков.
    - Источник: [24][63].
