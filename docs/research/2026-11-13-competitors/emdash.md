## Модель работы

- **Local, cloud или hybrid.**
  - Classic — local. Состояние приложения хранится в локальной базе SQLite. Код и чаты на серверы Emdash не уходят;
    CLI агентов отправляют данные своим провайдерам [33][7].
  - Агенты — CLI вендоров, установленные на машине. Пользователь входит своей подпиской или ключом API [30][2][7].
  - По желанию — удалённые hosts по SSH. На host Emdash ставит Workspace Server — свой daemon (фоновый процесс). Он
    отвечает за файлы, Git, терминалы, агентов, поиск и automations. Интерфейс и preview в браузере остаются на
    локальной машине, публичный порт не открывается [27].
  - Облачного backend для работы пользователя у Classic нет. Есть необязательный Emdash account — через него идёт
    вход в GitHub и GitLab [20][10].
  - 2.0 — hybrid, пока только анонс. Run location (где выполнять задачу): Your computer, Emdash Cloud (под управлением
    Emdash) или Hosts (компьютер или сервер пользователя) [5].
  - Доступ к 2.0 обещан из desktop, web, с телефона и из Slack [101][131]. Публичного web-приложения, приложения для
    Slack или мобильного приложения исследование не нашло (не подтверждено) [1][101].
  - Раньше вендор продавал облачные варианты. Страница Cloud (снимки с февраля по октябрь 2026) обещала временные
    изолированные ресурсы на задачу, которые удаляются после работы, хранение кода на одобренной инфраструктуре,
    compliance и форму связи с продажами. Страница Enterprise (август 2026) обещала любых агентов на локальных
    репозиториях, SSH hosts и управляемых средах разработки и спрашивала размер компании [138]. На 2026-11-13 обе
    ссылки ведут на waitlist [138].
- **Агенты и модели.**
  - Classic. Сколько агентов, источники вендора называют по-разному:
    - в коде 37 plugin-ов агентов [80];
    - документация Providers — 35, все находятся автоматически в PATH [16];
    - обзор документации — 34 [13];
    - FAQ на странице Classic — «25+» [2];
    - на Show HN в феврале 2026 был 21 агент [122], в посте Launch YC — около 20 [132].
  - Сверх таблицы документации в коде есть Muse Code (с v1.2.4) и Prime Agent (с v1.2.3) [80][10].
  - Агенты из документации: Amp, Antigravity, Auggie, Autohand Code, Charm (Crush), Claude Code, Cline, CodeBuddy,
    Codebuff, Codex, Command Code, Continue, Cursor, Devin, Droid, Freebuff, GitHub Copilot, Goose, Grok, Hermes Agent,
    Jules, Junie, Kilocode, Kimi, Kiro, Letta, MiMo Code, Mistral Vibe, Oh My Pi, OpenCode, Pi, Qoder, Qwen Code,
    Rovo Dev, Zero [16][80].
  - 23 plugin-а поддерживают ACP (Agent Client Protocol — открытый стандарт обмена сообщениями между редактором и
    агентом), среди них Claude Code, Codex, Cursor, Copilot, OpenCode, Droid, Devin, Goose и Qwen [80][50].

  - Кто на чём работает:

## Функции

Функции Classic описаны по документации, changelog и коду на коммите `ccc6cce` [10][13][32]. В конце раздела —
удалённые функции, открытые запросы пользователей и то, что объявлено для 2.0. Для 2.0 есть только анонс, в работе его
никто не проверял.

### Экран

- **Левый sidebar.**
  - Дерево проектов с задачами, пункты Automations и Library и вызов поиска [24][25][10].
  - В строках задач — точки статуса агента и значки PR [10].
  - С v1.2.11 в sidebar есть карточка waitlist 2.0; её можно закрыть [35].
- **Вкладки проекта:** Tasks, Pull Requests (для GitLab — Merge Requests), Workspaces и Settings [104].
  - Задачи сортируются по Last used, Created at, PR status или Unread first [104].
- **Экран задачи.**
  - В title bar — панели Changes, Files и Conversations (⌘⇧1/2/3), значок dev server и связанный issue
    [23][18][21][10].
  - Панели с вкладками держат conversations агентов, терминалы, вкладки браузера, файлы и diff. Панель делится, если
    перетащить вкладку к её краю или нажать ⌘\ [23][10].
  - Выдвижной терминал (⌘J) показывает logs скриптов setup и run [17].
- **Home view** — карточки быстрых действий с проектами [10].

### Проекты и задачи

- **Добавить проект:** открыть локальную папку, клонировать репозиторий или создать репозиторий на GitHub. Папки без
  Git тоже подходят. Папку можно перетащить в sidebar [30][10].
- **Создать задачу** (Add Task, ⌘N) [14]:
  - начать от ветки, issue или PR;
  - задать имя или дать Emdash его сгенерировать;
  - выбрать агента, модель (или «Default model») и интерфейс — Chat UI или терминал.
- **Изоляция.**
  - По умолчанию у каждой задачи своя ветка Git и свой worktree в `~/emdash/worktrees`. Место можно сменить в
    настройках проекта или машины [14].
  - Другие варианты: существующий workspace или корень репозитория. Если отключить worktree, Emdash предупреждает
    [14][27].
  - Обзор документации говорит, что Add Task создаёт «один или несколько» worktree [13]. Остальная документация и код
    описывают один worktree на задачу; режим нескольких агентов на одну задачу (Best-of-N) из кода убран [14][32].
- **Несколько conversations в задаче.**
  - New conversation (⌘T), новая conversation в правой половине (⌘D), новый терминал (⌘⇧T) [23].
  - У каждой conversation свой агент, свой интерфейс (Chat UI или терминал) и свой auto-approve. Поэтому разные агенты
    могут работать в одном worktree задачи [104].
  - Conversations показываются вкладками с v1.1.15 [10].
- **Жизненный цикл.**
  - Задачу можно архивировать и восстановить. Архивирование запускает teardown-скрипты [10].
  - По умолчанию при удалении задачи удаляется и ветка; это настройка [10].
  - Несколько задач удаляются сразу (⌘Backspace) [23].
  - Имя задачи можно взять из имени ветки в Linear [15].

### Агенты (providers)

- **Сколько:** 37 plugin-ов в коде, 35 в документации Providers, 34 в обзоре документации, «25+» в FAQ Classic
  [80][16][13][2].
- **Что поддерживает каждый агент** (документация Providers) [16]:

  | Функция | Агентов | Что делает |
  |---|---|---|
  | Auto-approve | 26 | пропускает запросы разрешений |
  | Resume | 26 | продолжает прошлую session |
  | Lifecycle hooks | 20 | сообщают статус: работает, ждёт ввода, закончил |
  | Initial prompt | почти все | первый prompt идёт аргументом CLI; нескольким агентам — через stdin или вводом в терминал |

- **Управление агентами.**
  - Установка агента прямо из приложения, в том числе через WinGet для Claude Code на Windows [10].
  - Для агента можно указать свой исполняемый файл или скрипт-обёртку (v1.2.5) [10].
  - Settings → Refresh заново ищет агентов [16].
  - Модель, effort, режим доступа и fast mode запоминаются для каждого агента и каждой машины [10][16].
  - У Codex в чате есть Plan mode (v1.2.2) [10].
- **Вход.** Для Claude Code — вход через сам CLI или переменная `ANTHROPIC_API_KEY` [76].
- **Auto-approve.**
  - В режиме терминала Emdash включает флаг самого CLI. Для Claude это `--dangerously-skip-permissions` [76].
  - Есть глобальное значение по умолчанию (v1.1.35) [10].
  - Одобрения по правилам (policy) нет: approval для conversation либо включён, либо выключен [104][16].

### Терминал и Chat UI

- **Терминал** — TUI (текстовый интерфейс) самого агента в эмуляторе терминала.
  - Поиск по терминалу (⌘F), свой shell и шрифт для каждого терминала, Option как Meta на macOS [10].
  - Ссылки в выводе открываются по клику [10].
  - В локальные и удалённые терминалы можно перетащить файлы и вставить картинки (v1.2.6) [10].
- **Chat UI** — чат поверх ACP [7].
  - Общедоступен с v1.1.39 (2026-07-14). При первом использовании пользователь включает его сам [10].
  - Для Claude чат запускает ACP-адаптер на Claude Agent SDK. Адаптер вызывает установленный бинарник `claude` [76].
  - Переключатель между Chat UI и терминалом — с v1.2.7 [7][10].
- **Что умеет чат.**
  - Вставка картинок, очередь prompts, экспорт чата [10][7].
  - Показ subagents, диаграммы Mermaid, формулы LaTeX [10].
  - Блоки размышлений модели сгруппированы. Подряд идущие вызовы инструментов сворачиваются в строку «Ran N commands»
    [10].
  - Черновик хранится отдельно для каждой conversation [10].
  - Голосовой режим: Emdash просит разрешение микрофона macOS для команды `/voice` в Claude Code [10].
  - Экспорт transcript и сырого log ACP — только пока session жива [47].
- **Меню в поле ввода.**
  - «@» добавляет файлы, issues и «Diff comments» — черновые комментарии к diff [104][10].
  - В меню «/» — сохранённые prompts и собственные команды агента [10][104].

### Статус агента, hooks и уведомления

- **Hooks от Emdash.**
  - Для агентов с поддержкой hooks Emdash пишет в пользовательский конфиг агента записи с маркером. Hooks сообщают
    статус, запускают уведомления и помогают продолжать sessions. Вне Emdash они ничего не делают [33].
  - Claude Code получает `SessionStart`, `UserPromptSubmit`, `Notification` и `Stop` в `~/.claude/settings.json`.
    Текст Notification Emdash относит либо к запросу разрешения, либо к простою [76].
  - Codex получает `Stop`, `PermissionRequest` и `SessionStart` в `config.toml` [78].
  - По выводу терминала статус не угадывается [50].
- **Уведомления.**
  - Виды: агенту нужно внимание; агент закончил; обновление доступно, скачано или не удалось [95].
  - Каналы: уведомления ОС, лента в приложении, звук [95].
  - Настройки: вкл/выкл, уведомления ОС, звук (можно свой файл), звук всегда или только когда окно не в фокусе
    [95][10].
  - Клик по уведомлению открывает нужную вкладку conversation [10].
  - Лента хранит 500 последних записей [10] и удаляет записи старше 14 дней. События собираются пачками за 2 секунды
    [95].

### Задачи из issue-трекеров

- **Как это выглядит** [15]:
  - Add Task → From Issue, поиск, выбор базовой ветки, создание задачи.
  - Issue остаётся привязан к задаче. Его можно вставить в conversation как контекст: трекер, идентификатор,
    заголовок, URL, описание, статус, исполнители и проект.
  - Плашка контекста позволяет поправить сгенерированный текст до отправки.
  - Шаблон контекста настраивается для каждой задачи (v1.1.36) [10].
- **Трекеры.**
  - В коде 13 plugin-ов: Linear, Jira, GitHub Issues, GitLab, Asana, Monday.com, Trello, Plane, Forgejo, Featurebase,
    Plain, Notion и YouTrack [80].
  - Страница документации на 2026-11-13 перечисляет 12, без YouTrack. YouTrack пришёл в v1.2.8 и описан в changelog
    [15][10].
  - Заметки исследования здесь расходятся. Одна насчитала 13 трекеров по документации, changelog и коду [15][10][80].
    Другая — 13 в коде и 12 в документации [100][15].
- В каждой интеграции может быть несколько аккаунтов: один по умолчанию и выбор для проекта (v1.2.5) [10].
- **Ограничения** [15][10]:
  - Asana — только открытые задачи пользователя в основном workspace;
  - Trello — 20 последних активных досок;
  - Monday.com — первые 20 досок;
  - Notion — только страницы, открытые интеграции;
  - YouTrack — до 100 комментариев на ticket;
  - большинство трекеров подключается личным token; Jira принимает и bearer token; GitLab и Plane можно держать на
    своих серверах.
- **Только чтение.** Emdash получает список, ищет и читает issue. Webhooks и обратной записи статуса нет [100][15].
- **Открытые запросы:** создавать задачу по событию трекера, например по webhook Linear (#1029); синхронизировать
  статус issue из задачи или PR (#1930) [105].

### Review, PR и CI

- **Changes panel** [18]:
  - разделы Changed, Staged и Pull Requests; панель обновляется по событиям файлов и Git;
  - diff одной колонкой или двумя; unstaged-изменения можно править прямо в diff;
  - stage, unstage, discard (с подтверждением);
  - Commit, Commit & Push, Commit & Create PR, Push & Create PR.
- **Помощь в review.**
  - Комментарии к строкам diff в редакторе Monaco (с v1.0) [10][8].
  - Черновые комментарии уходят агенту через пункт «Diff comments» (v1.2.8). Черновики стираются только после
    подтверждённой доставки [10][91].
  - Review по коммитам в sidebar PR (v1.1.25) [10].
  - Коммиты ветки видны до создания PR [10].
  - Дерево изменённых файлов и число строк по каждому файлу [10].
- **PR.**
  - Раздел PR показывает файлы, коммиты, проверки, комментарии и состояние merge [18].
  - Draft PR, перевод в ready, копирование URL [10].
  - Merge, squash или rebase. Невыполненные правила ветки можно обойти после явного подтверждения [89][10].
  - Заголовок PR заранее заполнен именем ветки. Текст PR и коммитов пишет пользователь: своего AI-текста для PR и
    коммитов у Emdash нет [90].
  - Вкладка Pull Requests проекта: список PR с поиском и фильтром по автору. Задачу можно начать от PR [10][14].
  - Поддержка remotes GitHub Enterprise [10].
  - Несколько аккаунтов GitHub. Для проекта выбирается один аккаунт или «No GitHub account» [20].
- **Проверки CI** [19]:
  - вкладка Checks показывает check runs GitHub для head-коммита PR: статус, имя и источник, длительность, ссылку;
  - под проверками — комментарии PR; упавшие проверки идут первыми;
  - вкладка синхронизируется при открытии и при смене head-коммита; репозитории опрашиваются раз в минуту (v1.2.4)
    [10][88];
  - logs и ошибки CI агенту не передаются — такого пути в коде нет [88][32].
- **GitLab merge requests (v1.2.9)** [10]:
  - просмотр, создание и merge;
  - approvals, задания pipeline, обсуждения, коммиты и изменённые файлы;
  - снятие статуса draft; задачи и review от MR, в том числе от MR из fork.
- **Чего нет:** локального gate (проверочного запуска перед PR), агентов-reviewer-ов и diff «что изменилось за
  последний ход агента» (#1635) [105]. Встроенная помощь в review агентом — только готовый prompt «Review prompt» в
  библиотеке [25].

### Встроенный браузер

- **Основное** [21]:
  - вкладки браузера внутри задачи (⌘⇧B);

  ответит, потом — раз в 15 секунд [98].
- **Профили** [21]:
  - постоянные и отдельные от системного браузера; у каждого свои cookies, localStorage, IndexedDB и кэш;
  - можно держать несколько профилей — под разные аккаунты или sessions на staging;

- **Дополнительно (v1.1.33)** [10][92]: поиск Google на стартовой странице, zoom, история назад и вперёд, кнопка
  «Copy screenshot» — копирует скриншот в буфер обмена.
- **Ограничения** [21]:
  - только http, https и about:blank;
  - профиль Chrome взять нельзя, расширений нет;
  - DevTools — только в dev-сборках;
  - агент браузером не управляет. Моста к браузеру через CDP (Chrome DevTools Protocol) или MCP в коде нет [92][32].
    Выбор элемента на странице — открытый запрос #2519 [105].

### Library: prompts, skills, MCP

- **Prompts** [25]: сохранённые prompts вставляются из меню Prompts или дописываются к черновику. В комплекте —
  «Review prompt».
- **Skills** [25][10]:
  - стандарт Agent Skills — папка с файлом `SKILL.md`, которую агент подгружает как инструкцию; каталоги OpenAI,
    Anthropic и skills.sh;
  - skills ставятся в `~/.agentskills/` и подключаются symlink-ами в папки шести агентов: Claude Code
    (`~/.claude/commands/`), Codex, OpenCode, Cursor, Roo Code и Mistral Vibe;
  - можно создать свой skill — Emdash напишет `SKILL.md`.
- **MCP** [26]:
  - сервер берётся из каталога на 54 сервера (Playwright, Sentry, Linear, Slack и другие) или добавляется свой — stdio
    или http;
  - Emdash пишет конфиг в формате каждого выбранного агента; агентов 11, в том числе `~/.claude.json` и
    `~/.codex/config.toml`;
  - агенты без HTTP-транспорта для HTTP-серверов недоступны;
  - доступность серверов Emdash не проверяет [55].
- **Область действия.** Всё это — на машину. У удалённого host своя Library: Settings → Machines [25][27].
- **Rules нет.** Функции rules (CLAUDE.md, AGENTS.md) в Classic нет, она есть только в 2.0 [104][5]. Внедрения rules
  или system prompt поиск по коду Classic тоже не нашёл [32].

### Automations

- **Настройка** [24][69]:
  - Sidebar → Automations: имя, проект, cron-расписание с часовым поясом, prompt, агент, модель и опции, auto-approve
    по желанию;
  - где работать: новый worktree на каждый запуск, существующий workspace или корень репозитория;
  - «Run now» запускает сразу.
- **История запусков** [24][69]:
  - у запуска видны время, статус (scheduled, queued, provisioning workspace, starting session, done, failed, skipped,
    cancelled) и ошибки;
  - запуск можно открыть или превратить в обычную задачу;
  - automation можно поставить на паузу.
- **Шесть шаблонов** [69]: Find critical bugs, Summarize changes daily, Scan for vulnerabilities, Add test coverage,
  Fix reported bugs, Generate docs.
- **Триггеры** — только cron или вручную [69].
- **На удалённом host** automations выполняет Workspace Server; desktop для этого подключать не нужно. Выключенная
  машина запуски пропускает [24][27].
- **«done» значит «session запущена».** Запуск не следит за агентом до конца и не проверяет результат [66].
- **История:** в beta с марта 2026 [34]; вышли в v1.1.32 — 2026-06-09 по changelog, 2026-06-10 по времени релиза на
  GitHub в UTC [10][34]; из beta — в v1.1.33 (2026-06-12) [10].

### Emdash 2.0: что объявлено

Всё ниже — анонс и скриншоты блога. В работе это никто не проверял.

- **Позиционирование:** coding-агенты для всей команды; облачная среда разработки для команд с любой моделью, любым

  - waitlist в приложении описывает управление агентами из desktop, web, mobile или Slack и управление платформой
    самими агентами через MCP [101].
- **Автоматизация и доказательства:** повторяющаяся работа по расписанию [1]. Агенты тестируют приложения, чинят
  упавший CI и открывают PR с визуальными доказательствами [1]. Как это сделано — не опубликовано (не подтверждено).

  3. Подключить компьютеры — «Server or Mac mini» (по желанию). Пользователь запускает однострочную команду установки

  - Карточка host показывает ядра, RAM, диск, «Containers», число sessions и «Runtime Manager UI».

  - «Global Agent Rules» копируются в файл rules каждого агента при старте session и синхронизируются в уже запущенные

  - как расход измеряется и как лимиты применяются — не подтверждено.
- **Командные функции** [1][101]: общие sessions, живые preview, review PR; SSO, роли, учёт использования, лимиты
  расходов по всем провайдерам, соблюдение соглашений команды; общие среды и секреты, управление учётными данными.

## Принципы и подходы

Позиции даны с датами: часть из них за год поменялась.

### Что заявляет команда

1. **Оборачивать родные CLI, а не API** (Show HN, 2026-02-24). Emdash запускает CLI провайдера, поэтому пользователь
   получает все его возможности. Новая функция провайдера, например plan mode, работает без доработки в Emdash [122].
   На вопрос, получает ли пользователь в GUI весь harness Claude Code, основатель ответил: Emdash запускает CLI
   вендора как есть [123].
2. **Без привязки к провайдеру.**
   - Разным задачам подходят разные агенты, поэтому человек и команда должны свободно переключаться [122].
   - Вход — напрямую у провайдера. Существующие подписки Claude Code и Codex работают как есть [7].
   - На Product Hunt (май 2026) Raban сказал, что выбор агента и модели остаётся за пользователем и Emdash ничего не
     советует [135].
3. **Уровень задачи; делить работу — дело агентов.**
   - Основателей спросили про orchestrator-агента, который запускает sub-агентов. Они ответили, что CLI вроде Claude
     Code сами всё лучше это делают. Emdash — слой задач над ними, декомпозицию он оставляет каждому CLI.
   - Разработчику всё равно нужен интерфейс, чтобы видеть статусы, смотреть и проверять результат. Этот интерфейс они
     называют ADE — Agentic Development Environment, среда разработки с агентами [122].
   - Один пользователь HN возразил: такой подход подрывает обещание независимости от провайдера [122].
4. **Производительность одного человека, а не масштаб команды** (февраль 2026). Основатель описал свою работу: одна-две
   активные задачи и длинный список исследовательских. Цель — удобно переходить между задачами, а не выполнять задачу
   за один запуск без человека [122]. 2.0 разворачивает продукт к командам [1][4].
5. **Open source.** 2026-02-24 аккаунт основателей на HN написал: «this UI layer for running multiple coding agents is
   and will be open-source» [122]. В ноябре 2026 open source обещан только Classic. Лицензия 2.0 нигде не названа
   [1][4].
6. **Local-first.**
   - Состояние — в локальном SQLite. Код и чаты не уходят на серверы Emdash; CLI агентов отправляют данные своим
     провайдерам [7][33].
   - Telemetry в PostHog включена по умолчанию в production-сборках. Её можно выключить в Settings или переменной
     `TELEMETRY_ENABLED=false`. Уходят только события из allowlist, без кода, prompts и путей [29].
   - После входа событие identify несёт имя GitHub, id аккаунта и email [29]. Privacy policy с датой «January 2025»
     говорит, что персональные данные не собираются [11]. Эти две страницы противоречат друг другу.
7. **Цель переписывания v1** — скорость, спокойствие и надёжность [8].
8. **Статус — только из явных сигналов.**
   - Статус агента приходит от hooks или plugin-ов, которые ставит Emdash. По выводу терминала он не угадывается. Если у
     провайдера нет hook для события, Emdash не показывает догадку [50].
   - Hooks пишутся в пользовательский конфиг провайдера, а не в worktree задачи. У них маркер версии, вне Emdash они
     ничего не делают [33][50].
9. **Источник истины — host** (ADR 0001, 0005, 0006; ADR — architecture decision record, запись архитектурного
   решения) [58].
   - Desktop координирует, hosts исполняют. Что host считает существующим — то и правда.
   - Модели «желаемого состояния», которую система сама приводит в порядок, нет. ADR 0001 прямо отказывается от
     подхода Kubernetes: Emdash — гость на host, поэтому всё, что пользователь сделал на диске, — факт, а не отклонение
     [59].
   - Изменения — простые RPC, которые сразу возвращают ошибку при сбое [58].
   - Пережить недоступность host может только удаление. Оно хранится как tombstone (запись «удалить») и выполняется,
     когда host вернётся [58][60].
10. **Не отправлять prompt повторно, если исход неизвестен.** Заметки исследования здесь расходятся.
    - По одной, это действующее правило. Если после отправки нельзя доказать завершение, попытка переходит в состояние
      «outcome unknown» и блокирует новые отправки, пока человек её не разберёт или не бросит. Тишина и timeout никогда
      не считаются завершением [56].
    - По другой, эти термины (Prompt attempt, Provider dispatch, Outcome unknown, Command receipt) есть только в
      глоссарии; код на `ccc6cce` их не использует [56]. Код делает проще. Сбой, о котором известно, что он случился
      до отправки, помечается «not sent», и черновик возвращается пользователю. Неуверенные сбои автоматически не
      повторяются. Документация прямо говорит, что это не durable outbox — не надёжная очередь исходящих [47].

### Ключевые понятия

**Уровень продукта (документация Classic)**

- **ADE** — Agentic Development Environment, название категории. Emdash так называет себя как минимум с февраля 2026
  [122][132]. Это же слово использует конкурент Superset (вторичный источник) [150].
- **Task** — единица работы одного агента. Начинается от ветки, issue или PR; у неё провайдер, модель и интерфейс —
  Chat UI или TUI [14]. Task принадлежит desktop и связана с Workspace [56].
- **Project** — группа задач вокруг одного репозитория. Существует только в приложении [56].
- **Worktree на задачу** — по умолчанию, в `~/emdash/worktrees`. Задача может взять существующий workspace или
  работать без worktree — с предупреждением [14].
- **Provider** — CLI агента, который Emdash нашёл в PATH [16].
- **Plugins** — слово для трёх вещей: каркас возможностей, провайдеры агентов и сервисы host, которые их запускают
  [56].
- **ACP chat и TUI.** Агенты с ACP получают чат с очередью prompts, вставкой картинок и экспортом. Остальные работают в
  терминале. Переключатель между ними — с v1.2.7 [7][10].
- **`.emdash.json` и lifecycle-скрипты.** Файл задаёт preserve patterns (например, какие `.env` копировать) и скрипты
  prepare, setup, run и teardown. Emdash добавляет переменные вроде `$EMDASH_PORT`, чтобы dev servers разных задач не
  делили порт [122][57]. Порядок: личный конфиг, затем файл команды, затем значение host по умолчанию [57].
- **Automations** — prompts по cron с историей запусков. Удалённые расписания ведёт Workspace Server [24].
- **Library** — сохранённые prompts, skills и MCP-серверы, которые Emdash раздаёт агентам [13].
- **Remote projects и Machines** — SSH hosts. С v1.2.0 на host работает Workspace Server — daemon, который отдаёт Git,
  файлы, терминалы, агентов и automations [48][34]. tmux держит sessions при разрыве связи [7].
- **Usage page** (v1.2.8) — остаток лимитов подписок Codex и Claude Code и время до сброса [34].

**Глоссарий архитектуры** — файл CONTEXT.md, около 630 строк [56]:

- Host, Repository, Worktree, Workspace.
- Session — запущенный процесс. Conversation — долговременная запись, которая живёт дольше sessions.
- Prompt и Prompt attempt (попытка отправки); Provider dispatch (передача провайдеру); Outcome unknown (исход
  неизвестен).
- Host registry — единственный писатель списка ресурсов, живёт на host. Registry — его зеркало на desktop.
- Tombstone — запись об удалении. Reconcile sweep — периодический проход, который доделывает отложенные удаления.
- Desktop writer — идентичность одного профиля desktop. Она нужна, чтобы подписывать команды, а не чтобы давать права.
- Слово «Machine» разрешено только как подпись в интерфейсе.
- Для каждого термина глоссарий перечисляет слова, которых надо избегать [56].

**Словарь 2.0** (блог, 2026-11-12) [5][6]:

- Hosts — серверы или Mac mini, добавленные одной сгенерированной командой, на странице Hosts организации.
- Run location — где выполнять задачу: локально, на Hosts или в Emdash Cloud.
- Team usage page — расход по дням, агентам и моделям.
- Лимиты расходов на разработчика, общие для всех агентов.
- Правила на всю организацию: копируются в файл rules каждого агента при старте session и синхронизируются, пока она
  идёт.

### Чем подход отличается

**По словам вендора**

- Сравнение в августе 2026 с Conductor, Vibe Kanban, Superset, cmux и Solo выделяет три вещи: родные приложения для
  macOS, Windows и Linux; 34 агента, которых Emdash находит сам; Apache-2.0 бесплатно [7].
- Против Conductor — SSH, больше агентов, open source. Против приложения Codex — любой провайдер моделей, не только
  OpenAI [122].
- Вендор называет Emdash первой ADE с удалёнными проектами по SSH [8].

**Что видно со стороны**

- **Широкая, но неглубокая интеграция с агентами.** Hooks Classic сообщают статус, уведомления и resume. Правила
  процесса они агенту не передают [33][50]. 2.0 добавляет правила, skills и управление MCP на организацию [5][6].
- **Над Task ничего нет.** Запросы сообщества функциями не стали:
  - иерархические планы в духе Beads (#533, закрыт 2026-04-29) [108];
  - оркестрация агентов (#2981) [107];
  - RFC «Collaborative Task Mode» (#2643) [107];
  - ответ Arne Strickmann 2026-07-14 обещал только больше программных способов создавать задачи и automations —
    например, Emdash CLI или внешние триггеры [107].
- **Безопасность важнее доведения до конца.** Emdash не отправляет prompt повторно, если исход неизвестен [47][56].
  Automations не повторяют неудачный запуск [66].
- **Два продукта с разной философией.** Classic — local-first инструмент одного разработчика. 2.0 — облачный продукт для
  руководителя инженерной команды, который управляет расходами [1][6].

### Как команда строит сам Emdash

- Планирование в репозитории [62][56][58]:
  - файлы `.scratch/<topic>/map.md` с меткой `wayfinder:map`;
  - пронумерованные файлы issues с полями «Blocked by» и «Status»;
  - записи решений в `docs/adr/`;
  - глоссарий CONTEXT.md со словами, которых надо избегать;
  - skills `/grilling`, `/domain-modeling` и `/codebase-design`, которые sessions должны использовать.
- Папка `agents/`, CONTEXT.md и ADR — источник правды для coding-агентов, которые пишут код Emdash [46].
- В `.claude/settings.json` репозитория — `defaultMode: bypassPermissions` [62].
- Не меньше 185 коммитов с соавтором Claude и не меньше 486 — с агентом Cursor [40].

## Как это устроено внутри

Всё ниже описывает Classic на коммите `ccc6cce`, если пункт не помечен «2.0». «Не найдено» — результат поиска
исследования по этому коммиту, а не слова вендора [32]. Для 2.0 нет ни документации, ни кода, ни инженерных постов;
каждый механизм 2.0 — не подтверждено [4].

### Процессы и стек

- **Desktop.** Electron 40.10.2: renderer на React и main process [96]. Preload bridge (мост между страницей и main
  process) отдаёт только запрос порта Wire — внутреннего канала RPC — и поиск пути файла [46].
- **Workers.** Main process запускает дочерние процессы Node под присмотром supervisor-а через `createWireWorkerHost` и
  `childProcessSpawner`, с переменной `ELECTRON_RUN_AS_NODE` [63][47].
  - Список: acp, agent-config, automations, conversations, file-search, files, git, host-settings, lsp,
    provider-usage, resource-usage, scripts, terminals, tui-agents, workspace-registry, fs-watch и pull-requests [63].
  - При сбое worker перезапускается через 250 мс, 1 с, потом 2,5 с (последняя пауза повторяется), не больше 5 раз.
    На готовность — 10 секунд [64].
- **Транспорт** — свой пакет `@emdash/wire` [56]:
  - типизированные контракты и простые RPC;
  - «live models» — ячейки состояния, которые публикует сервер. Клиент следит за номерами поколения и
    последовательности, замечает пропуски и пересинхронизируется.
- **Базы.** На desktop — SQLite через better-sqlite3 и Drizzle [49][54].

### Удалённые hosts: Workspace Server

- `apps/workspace-server` — daemon без Electron с тем же набором runtimes. Каждый основной runtime обязателен: если один
  не стартовал, сервер не запускается [48].
- Ставится в `~/.emdash/workspace-server/`. Каждая версия лежит в своей неизменяемой папке, активную указывает symlink
  `current`, который переключается атомарно. Файлы проверяются по SHA-256 до установки [48].
- Поддерживаются Linux на glibc (x64, arm64) и macOS на Apple silicon. Управляемые удалённые hosts на Windows
  отклоняются [48].
- Desktop связывается с daemon через канал SSH streamlocal к Unix socket. Папка socket создаётся с правами 0700,
  публичного порта нет [87][27].
- Каждое подключение, включая переподключение, начинается с handshake `initialize`. Совпала major-версия — стороны
  совместимы. Не совпала — ошибка «upgrade client» или «upgrade server» [48].
- В коде `PROTOCOL_VERSION = '12.2.0'`, документация всё ещё показывает 9.1.0 [48].
- Workspace Server живёт дольше своих клиентов. Протокол рассчитан и на клиентов не на TypeScript — например, на
  будущее мобильное приложение [48].

### Состояние и модель «host — источник истины»

- **Два долговременных владельца** [49]:
  - SQLite на desktop — проекты, задачи, automations, conversations и связи с ресурсами host [49][54];
  - каждый host — свои репозитории, worktree, ветки и процессы.
- **ADR 0001** [59]:
  - Emdash — гость на host. Worktree, созданные вне Emdash, принимаются как есть.
  - Удаления вне Emdash записываются, но не «чинятся».
  - Скан, который упал или прошёл частично, ничего не пишет. Поэтому «скан с ошибкой» не может выглядеть как «worktree
    нет».
- **Изменения** — простые RPC без очереди, шесть команд workspace [56][60]. Команда сделала durable outbox и журнал
  операций, потом отказалась от них (ADR 0006 и 0007, август 2026) [60][58].
- **Удаление — исключение** [60][86]:
  - удаление пишет tombstone в строку-зеркало; tombstone фиксирует параметры удаления и id цели;
  - reconcile sweep вызывает идемпотентную команду удаления при старте, при переподключении и по таймеру раз в
    10 минут;
  - пауза для каждого элемента — от 60 секунд до 60 минут.
- **Порядок операций.** Mutex по ключу: на репозиторий — для создания и удаления worktree, на workspace — для
  activate, deactivate и delete [49][60].
- **Состояние на host** — в папке состояния daemon: базы automations и поиска файлов, session intents (записи о том,
  какую session надо запустить) и вложения ACP [48].
  - Session intents пишутся по allowlist, с версией и атомарно.
  - Окружение провайдера, учётные данные MCP и endpoints runtime не сохраняются [47].
- **Задел на нескольких клиентов.** Tombstone задуман как будущая единица синхронизации между клиентами; в планах CRDT
  (структура данных, которая сливает правки без конфликтов) [58]. Desktop writer тоже рассчитан на нескольких
  клиентов [56].

### Цикл агента: своего нет, Emdash оборачивает CLI

- В реестре 37 CLI, 23 из них работают через ACP [50]. Документация называет 35 [16].
- Plugin провайдера объявляет [50][76]:
  - как доставить prompt — `argv`, stdin или вводом в терминал (`pty-only`);
  - флаг auto-approve;
  - поддержку ACP, hooks, MCP, моделей, resume, доверия к workspace и опроса лимитов.

**TUI runtime** — агент в своём текстовом интерфейсе:

- Агент работает в PTY (псевдотерминале; node-pty 1.1.0), по желанию внутри tmux [52][96].
- Окружение собирает одна функция. Значения окружения не попадают в аргументы команды: launcher tmux получает их через
  приватный FIFO (именованный канал) [52].
- Команда Claude Code [76]:
  - `--session-id` — детерминированный на conversation; это отделяет conversations друг от друга [50];
  - `--resume` и `--model`;
  - `--dangerously-skip-permissions`, если включён auto-approve.
- Команда Codex [78]:
  - `resume <id>` или `resume --last`, `-m`;
  - auto-approve превращается в `-c approval_policy=never -c sandbox_mode=danger-full-access
    --dangerously-bypass-hook-trust`.
- Prompt длиннее 16 384 символов пишется в `task-context.md` во временной папке. Агент получает короткий prompt со
  ссылкой на этот файл. Старые папки удаляются через 24 часа [74].
- TUI-процессы по простою не завершаются (политика `always`) [48][73].

**ACP chat runtime** — чат через ACP:

- Общедоступен с v1.1.39 (2026-07-14) [10].
- Два встроенных адаптера [96][76][78]:
  - `@agentclientprotocol/claude-agent-acp` ^0.81.2 на Claude Agent SDK 0.3.280;
  - `@agentclientprotocol/codex-acp` ^1.13.1.
  - Оба работают как Node внутри бинарника Electron. Они вызывают установленный CLI через `CLAUDE_CODE_EXECUTABLE` и
    `CODEX_PATH`, то есть работают с логином пользователя.
- Модули [47]:
  - `AcpRuntime` — корень сборки;
  - `SessionManager` — каталог conversations;
  - `ConversationHandle` — по одному на conversation;
  - `LifecycleCell` — сливает одновременные старты, ведёт аренды и остановку;
  - `SessionMaterializer` — без состояния; запускает или загружает session провайдера;
  - `SessionRouter` — направляет события провайдера в нужную conversation;
  - `SessionCell` — машина состояний без побочных эффектов, плюс сборка transcript, брокер разрешений и очередь
    prompts.
- Процессы провайдера кэшируются по провайдеру, рабочей папке и отпечатку окружения. Один процесс может вести несколько
  sessions. Счётчики поколений отбрасывают поздние события от заменённых процессов [47][56].
- **Доставка prompt** [47]:
  - `sendPrompt` подтверждает приём, а не завершение;
  - сбой, который точно случился до отправки, помечается «not sent», черновик возвращается;
  - неуверенные сбои автоматически не повторяются; документация подчёркивает, что это не durable outbox;
  - долговременные маркеры `initialQueueConsumed` и `unstarted` решают, когда безопасно заменить пропавшую session
    провайдера.
- **Приостановка.** ACP session засыпает после 60 минут без вывода (`SESSION_IDLE_MS`) [83]. Следующий prompt поднимает
  её через `loadSession` провайдера [47]. Если провайдер ответил `session_not_found`, пользователь выбирает retry или
  новую session [47].
- Модель, effort и режим берутся из `configOptions` ACP и хранятся в conversation. Режим Codex Default/Plan — селектор
  в поле ввода [47][50].

**Планирование и декомпозиция** — нет. На Show HN основатели сказали: Emdash работает на уровне задач, каждый CLI сам
делит работу на subagents [122]. План виден только как события плана провайдера в transcript [47].

### Параллельность, координация, изоляция

- **Единица работы.** Task — запись desktop, связанная с Workspace: worktree, репозиторием или обычной папкой [56]. В
  задаче несколько Conversations, вкладками с v1.1.15 [10].
- **Координации нет.** Агенты разных задач никак не связаны: нет общей памяти, блокировок файлов и управления merge
  [32].
- **Создание worktree** [51][94]:
  - шаги inspect → resolve-base → add-worktree → verify; базовая ветка скачивается (fetch), только если её нет
    локально;
  - ветки создаются командой `git worktree add --no-track`;
  - устаревшие регистрации worktree в Git удаляются (prune);
  - второй запрос на тот же workspace присоединяется к уже идущему созданию.
- **Место и имена.** Корень по умолчанию — `<home>/emdash/worktrees`, переопределяется для проекта и host [53]. Ветки
  называются `prefix/name`, по желанию со случайным суффиксом [51].
- **Копирование файлов.** `preservePatterns` копирует перечисленные gitignored-файлы (например, `.env`) через
  copy-on-write. Значений по умолчанию больше нет [51].
- **Окружение задачи** [93]:
  - `EMDASH_TASK_ID`, `EMDASH_TASK_NAME`, `EMDASH_TASK_PATH`, `EMDASH_ROOT_PATH`;
  - `EMDASH_PORT` = 50000 + (хэш пути mod 1000) × 10. Функция не проверяет, свободен ли порт.
- **Контейнеров и VM в Classic нет** [32]. 2.0 обещает отдельную Linux-среду на workspace без доступа к папкам сервера
  (не подтверждено) [5].
- **История.** v0 держал небольшой пул заранее созданных worktree, и задача стартовала за 0,5–1 секунды [122]. v1
  (2026-04-24) убрал эти «reserve branches» [10]. Best-of-N в v1 beta не было, и вернуть его обещали лишь возможно [9].
  В коде его нет [32].
- **Лимиты параллельности.** Планировщик automations — не больше 4 запусков одновременно на host [65]. Для интерактивных
  задач лимита не найдено [32].

### Lifecycle hooks: статус, уведомления, resume

- **Куда пишутся.** В пользовательский глобальный конфиг агента, никогда в worktree [50].
  - У каждой записи маркер и `EMDASH_HOOK_CONFIG_VERSION=1`.
  - Установщик проверяет записи до и после того, как берёт блокировку записи на папку конфига.
  - Файлы, которые не удаётся разобрать, не трогаются; hooks пользователя сохраняются [50][75].
- **Команда hook** [75][50]:
  - выходит с кодом 0, если нет `EMDASH_HOOK_PORT`, `EMDASH_HOOK_NONCE` или `EMDASH_PTY_ID`, — то есть вне Emdash ничего
    не делает;
  - иначе `curl --noproxy "*"` отправляет POST с payload из stdin на `http://127.0.0.1:$PORT/hook` с заголовками
    `X-Emdash-Pty-Id` и `X-Emdash-Event-Type`;
  - token читается из конфига curl на файловом дескрипторе 3, поэтому его не видно в аргументах команды;
  - на Windows — один вызов `powershell -EncodedCommand`.
- **Сервер приёма** [71]: Node `http` на 127.0.0.1 на случайном порту. Нужен случайный UUID-token, тело — до 1 МБ, на
  неверный token — ответ 403.
- **Claude Code** [76]:
  - `SessionStart`, `UserPromptSubmit`, `Notification` и `Stop` в `settings.json`;
  - Notification считается запросом разрешения, если текст совпадает с `permission|approval`, иначе — простоем;
  - `session_id` из каждого payload отслеживается, поэтому `/resume` внутри TUI не теряется.
- **Codex** [78]: `Stop`, `PermissionRequest` и `SessionStart` в `config.toml`.
- **Машина состояний** [72]:
  - start → working; stop → completed; error → error;
  - уведомление о разрешении, простое или elicitation (запрос данных у пользователя) → awaiting-input;
  - любое другое уведомление → idle.
  - Вывод терминала для статуса не разбирается [50]. Если у провайдера нет hook на старт, нажатие Enter в PTY ставит
    статус working [72].
- **Статус ACP** берётся из сводок session; ожидающий запрос разрешения значит awaiting-input [50].
- **Уведомления** попадают в сохраняемую ленту (14 дней) с пачками за 2 секунды, звуками и уведомлениями ОС [95][46].

### Работа без человека: Automations

- Вышли в v1.1.32, из beta — в v1.1.33 [10].
- **Deployment** (сохранённая automation) состоит из трёх частей [68][70]:
  - расписание — cron из 5 полей и часовой пояс; его считает библиотека croner [67];
  - агент — ACP (провайдер, опции и очередь первых prompts, минимум один) или TUI (провайдер, модель, prompt,
    `autoApprove`);
  - workspace — новый worktree от выбранной ветки, по желанию с push remote; существующая ветка; существующая папка.
- **Планировщик** [65][67]:
  - проверка раз в 60 секунд; не больше 4 одновременных запусков; не больше 100 запусков за одну проверку;
  - у каждой automation ровно один будущий запуск со статусом `scheduled`;
  - срок запуска — следующее срабатывание cron; просроченный запуск пропускается, пропущенные не догоняются;
  - если прошлый запуск той же automation ещё идёт, новый пропускается (`previous_running`);
  - смена расписания пропускает ожидающие запуски (`redeployed`).
- **Исполнитель** [66]:
  1. подготовить workspace;
  2. создать запись conversation;
  3. зарегистрировать и активировать workspace — это запускает блокирующий скрипт prepare;
  4. начать новую ACP session или headless TUI размером 80×24;
  5. отметить запуск `done`.
- **Статусы**: scheduled, queued, provisioning_workspace, starting_session, done, failed, skipped, cancelled. У ошибки
  есть шаг и код [68].
- **Главное ограничение** [66][65][67]:
  - `done` значит «session стартовала»;
  - запуск не следит за агентом до конца и не проверяет результат;
  - автоматического retry нет;
  - при перезапуске запуски, застрявшие на подготовке или старте, получают ошибку «прервано перезапуском».
- **Где выполняется.** Worker automations живёт в runtime host: это дочерний процесс desktop для локальных проектов и
  Workspace Server для удалённых [63][48]. Документация говорит, что удалённым расписаниям desktop не нужен, но
  выключенная машина их не выполнит [24]. Вывод исследования, не слова вендора: локальные расписания срабатывают, только
  пока приложение открыто.
- Новые automations стартуют с выключенным auto-approve для TUI. Снимок опций замораживается при сохранении [53].
- **Шаблоны**: find critical bugs, daily change summary, vulnerability scan, add test coverage, fix reported bugs,
  generate docs [69].

### Проверка качества: CI, PR, review

- Нет test runner, quality gate, review-агента или проверки definition of done (не найдено). Проверка лежит на агенте и
  человеке [32].
- **Lifecycle-скрипты в `.emdash.json`** [51][94][56]:
  - `prepare` блокирует работу и выполняется до старта любой session;
  - `setup` — после активации, не блокирует;
  - `run` ждёт успешного `setup`;
  - `teardown` выполняется внутри деактивации и никогда её не блокирует;
  - все работают в PTY с timeout 5 минут по умолчанию; у `run` timeout нет;
  - сбои становятся notices (заметками) workspace, а не ошибками.
- **PR engine** (worker на desktop) [88][63][10]:
  - GitHub через GraphQL: check runs и status contexts через `statusCheckRollup`;
  - GitLab merge requests с v1.2.9;
  - опрос зарегистрированных репозиториев раз в 60 секунд.
- **CI** показывается для текущего head-коммита PR [19]. Пути, по которому logs или ошибки CI попадают к агенту, нет
  (не найдено) [32].
- **Merge** повторяет состояние merge у провайдера (blocked, unstable, pending, failed). Обход возможен, если он
  разрешён пользователю, и только явный [89][10].
- **Текст PR и коммитов вводит пользователь.** Заголовок PR заполнен именем ветки. AI-текста PR или коммита в flow
  Emdash нет [90].
- **Review человеком** — комментарии к строкам в diff на Monaco [8]. Они копятся черновиками и уходят агенту через
  упоминание `@context:diff-comments` [91]. Черновики очищаются только после подтверждения доставки (v1.2.8) [10].
- **«Visual evidence»** в Classic — встроенный браузер копирует скриншот в буфер обмена [92]. Агенты браузером не
  управляют: моста CDP или MCP не найдено, документация об этом молчит [21][32].

### Восстановление после сбоев

- **TUI** [73][28]:
  - неожиданный выход (ненулевой код или сигнал) session без tmux — один перезапуск через 500 мс с продолжением
    сохранённой session провайдера;
  - если продолженный процесс умирает в течение 3 секунд, Emdash начинает новую session (`fresh-fallback`);
  - tmux держит процессы при перезапуске приложения и обрыве SSH, но не после перезагрузки host.
- **ACP** [47][10]:
  - счётчики поколений отбрасывают устаревшие события;
  - новый старт ждёт, пока старый процесс закончит остановку;
  - чтение истории — 5 попыток с экспоненциальной паузой до 15 секунд;
  - первые prompts переживают сбои старта и перезапуски worker (v1.2.7).
- **Supervisor подключения к host** (ADR 0008) [61][85]:
  - один владелец подключения на host;
  - паузы retry 0,5, 1, 2, 5, 10, 20 и 30 секунд, последняя повторяется, со случайным разбросом (jitter);
  - health check раз в 15 секунд с deadline 5 секунд; 10 секунд на открытие канала и на initialize; 120 секунд —
    потолок на установку соединения;
  - ошибки аутентификации и ключа host останавливают автоматические retry; несовпадение протокола требует явного
    обновления.
- **Прерванное создание** повторяется с тем же UUID. Удаления идут через tombstone [49][60].
- **Неудачный push** даёт состояние «branch not pushed» и ручной retry [51].
- **Ошибки API агентов** Emdash не повторяет — это делают сами CLI. Обработка rate limit есть только в интеграциях
  issues и PR [100].

### Лимиты подписки и стоимость

- Usage page появилась в v1.2.8 (2026-10-10) [10].
- **Опрос Claude** [77]:
  - вызывает `query()` из Claude Agent SDK с генератором prompts, который никогда не отдаёт сообщение;
  - только пользовательские настройки, hooks выключены, без инструментов и MCP;
  - затем шлёт управляющий запрос SDK `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET`;
  - разбирает окна `five_hour`, `seven_day`, `seven_day_oauth_apps` и недельные окна по моделям;
  - вход по ключу API или через сторонний логин показывается как «не поддерживается».
- **Опрос Codex** [79]:
  - JSON-RPC вызовы `initialize`, `account/read` и `account/rateLimits/read`;
  - работает только со входом через ChatGPT;
  - разбирает основное и дополнительное окна и отдельные лимиты.
- **Runtime** [81]:
  - один кэш на host для всех подключённых desktop;
  - обновление раз в 5 минут, пока кто-то смотрит; ручное обновление игнорируется, если прошлая проверка была меньше
    10 секунд назад; timeout опроса — 35 секунд;
  - при ошибке остаются последние окна, если аккаунт не сменился.
- **Только показ.** Планирование, automations и старт sessions эти окна не читают [81][65]. Нет ожидания сброса, паузы
  и учёта стоимости.
- **2.0** обещает расход команды по дням, агентам, моделям, участникам и чатам; недельные или месячные лимиты на
  разработчика по всем агентам; свои подписки или tokens через Emdash [6]. Как это измеряется и применяется — не
  подтверждено.

### Права и безопасность

- **Sandbox нет.** Агенты работают с правами пользователя, изоляция — только worktree [51].
- **Auto-approve в TUI** — флаг CLI. Глобальное значение по умолчанию — с v1.1.35 [10]. Настройка запоминается по host,
  провайдеру и транспорту [47].
- **ACP сам ничего не одобряет.** Брокер разрешений держит каждый запрос, пока пользователь не выберет вариант, без
  timeout. При остановке ожидающие запросы отменяются [84][47][53].
- **Автоматическое доверие к папке.** До запуска Emdash пишет `hasTrustDialogAccepted` и `hasCompletedProjectOnboarding`
  для worktree в `~/.claude.json`, под последовательной блокировкой записи [76][71].
- **Окружение агента.** Один allowlist решает, какие переменные получит запущенный агент [50].
- **Git-учётные данные** [82]:
  - каждой session — порт на loopback и случайный nonce;
  - credential helper подключается через переменные `GIT_CONFIG_*`;
  - desktop выбирает нужный аккаунт на каждый запрос;
  - tokens не попадают в окружение, аргументы команд и logs;
  - режимы: `effective-account`, `system`, `none`.
- **Секреты** шифруются через Electron `safeStorage` [97]. README пишет, что учётные данные SSH хранятся в keychain ОС
  [33].
- **Telemetry** — PostHog, можно выключить. Код, prompts и пути файлов не отправляются [29].
- **Local-first.** Код и чаты не уходят на серверы Emdash [33].

### Память и контекст

- Своей памяти агента у Emdash нет. Непрерывность — это session провайдера: id для resume в TUI, повтор через
  `loadSession` в ACP [47][50].
- **Что Emdash добавляет к prompt** [91][70][10]:
  - первый prompt — контекст issue плюс prompt пользователя;
  - у ACP prompts есть поле `hiddenContext`, которое не попадает в повторённый transcript;
  - prompts из Library и diff comments можно добавить как контекст.
- **Issues** — только чтение: list, search и get по 13 plugin-ам трекеров. Webhooks и обратной записи статуса нет
  [100][15].
- **MCP.** Emdash переписывает записи MCP-серверов в глобальный конфиг каждого агента через адаптеры провайдеров,
  например в `.claude.json`. Доступность серверов он не опрашивает [55][76].
- **Skills** лежат в `~/.agentskills`, поиск — через skills.sh [55][10].
- **Rules и system prompt** в Classic не внедряются (не найдено) [32]. 2.0 обещает копировать rules в файл rules
  каждого агента при старте session и синхронизировать их во время работы (не подтверждено) [5].

  - CPU, память и диск host [99];
  - метрики производительности каждого worker — в telemetry [63];
  - экспорт transcript ACP и сырого log, только для живых sessions [47];
  - поиск URL preview в выводе терминала: проверка раз в секунду, пока сервер не ответит, потом раз в 15 секунд [98].
- **Чего нет:** ленты событий запуска без человека, кроме transcript и терминала; учёта времени и стоимости по задаче
  [32].

### Где действует человек

- Создание задачи: ветка, issue или PR, провайдер, prompt [14].
- Ответ на запросы разрешений ACP — или заранее включённый флаг TUI [84][76].
- Комментарии к diff и их отправка агенту [91].
- Commit, push, создание и merge PR, обход требований merge [90][89].
- Retry или новая session после `session_not_found` [47].
- Удаление, застрявшее как tombstone: Retry или «Untrack anyway» [49].
- Превращение запуска automation в задачу [24].

### Почему выбирают

1. **Одно окно для многих CLI-агентов, под ним настоящие CLI.**
   - Пользователям нравится выбирать агента под работу: Codex для тяжёлого backend, Claude Code для остального [122];
     Claude Code вместе с Pi [122][137]; Codex, Claude Code и Antigravity рядом [110]; Auggie для embedded-разработки
     [115].
   - Один пользователь HN прошёл путь Cursor → Claude Code CLI → Emdash [122]. Другой сказал, что Emdash избавляет от
     переключения между агентами [122].
   - На вопрос, получает ли пользователь в GUI весь harness Claude Code, основатель ответил, что Emdash запускает CLI
     вендора как есть [123]. Первые пользователи назвали это правильной стратегией [122].
2. **Рутину worktree делают за пользователя.**
   - Самая конкретная похвала — скриптам setup, run и teardown в `.emdash.json` и переменной `$EMDASH_PORT`, которая
     даёт каждой задаче свой диапазон портов [122][125].
   - Руководитель студии сказал, что это ровно то, что ему нужно. Если продукт себя покажет, он раздаст его команде
     [122].
   - Другой пользователь раньше вёл worktree на агента своими скриптами; GUI заметно ускорил его работу [115].
   - Отзыв на Product Hunt: worktree перестали мучить, с несколькими агентами автор стал выпускать быстрее [135].
3. **Кроссплатформенность и SSH.**
   - Поклонник Conductor на Mac искал то же самое для Windows и WSL2 и счёл Emdash почти готовым [122].
   - Удалённые пользователи хвалят проекты по SSH, а позже — автоматический проброс портов [118].
   - Подборки стабильно выбирают Emdash для Windows, Linux и удалённой работы [141][147].
4. **Скорость команды.**
   - Исправления выходили в тот же день, что и запуск на HN [122].
   - Пользователи много раз отмечают отзывчивость: вопросы решались быстро [122], исправления выходили за часы [135],
     скорость команды хвалят отдельно [117].
   - Один пользователь назвал Emdash лучшей agentic IDE, перепробовав все [114].
   - Проброс портов для SSH-проектов прошёл путь от запроса до рабочей canary-сборки примерно за 10 дней [118].
5. **Задачи из трекеров.**
   - Один пользователь месяцами работал через интеграцию с Jira, пока её не сломала регрессия [111].
   - Обзоры выделяют задачи из трекеров как главную функцию [141][148].
6. **Open source.**
   - На запуске комментаторы хотели open-source замену Cursor или Conductor [122].
   - Лицензия сменилась с MIT на Apache-2.0 2026-04-29 [39]. Один комментатор HN раньше сомневался в MIT [122].

### На что жалуются

**1. Полноэкранный интерфейс Claude Code плохо рисуется внутри Emdash.** Это самая долгая проблема.

- Июнь 2026: меню рисуются поверх прошлых строк, текст накладывается сам на себя [110].
- Сентябрь 2026, отчёт по v1.1.40: панелью нельзя пользоваться — кадры рисуются друг поверх друга, transcript
  пропадает [110].
- Сентябрь 2026: без установленного tmux панели становятся пустыми после часа простоя [110].
- Что помогало пользователям: изменить размер окна, нажать Ctrl+O, перезагрузить [110].
- Maintainer признал, что ошибки этого класса возвращаются снова и снова в немного другом виде, особенно с Claude Code
  [110].
- Синхронизацию размера терминала после смены вкладки окончательно исправили в v1.2.8 (2026-10-10) [110].
- Один пользователь HN перешёл на Herdr: тот правильно рисует интерфейс Claude Code, не падает внезапно и работает на
  удалённом сервере [128].

**2. Обновления, после которых приложение не запускается.**

- В день запуска на HN была сломана сборка .deb [122].
- 0.4.44 падала с segfault на macOS [111].
- v1 beta падала по кругу на Windows, Ubuntu, Fedora и CachyOS [111].
- 1.1.10 сломала пользовательские шрифты, откатиться пользователь не смог [111].
- 1.2.10 падала по кругу при старте: в пакете не хватало модуля [111].
- 1.1.40 сломала задачи из Jira [111].
- Diff comments без всякого сообщения перестали доходить до агента. Новый путь — скрытое сочетание Cmd+Shift+A; в
  документации пользователи его не нашли [111].

**3. Производительность на больших объёмах.**

- При запуске на HN пользователь загрузил 78 задач, и интерфейс еле двигался [122].
- Позже пришли отчёты с аккуратным профилированием [112]:
  - индекс файлов на 2,5 ГБ замораживал интерфейс;
  - 190 worktree дали около 250 одновременных процессов `git worktree list`;
  - в простое приложение занимало около 0,8 ядра CPU;
  - renderer не успевал при большом выводе агентов;
  - задержка ввода по SSH выросла вдвое.
- Всё ещё открыто: фоновый `git fetch` каждые 2 минуты, который нельзя настроить. Один пользователь насчитал 461 fetch
  за 21 час на репозитории 10,4 ГБ с 53 тыс. веток [112].
- Тоже открыто: квадратичная работа с базой при синхронизации workspaces [112].

**4. Hooks в файлах конфигурации пользователя.**

- В мае 2026 пользователь возразил: Emdash молча пишет hooks в `.claude/settings.local.json`, `.codex/config.toml` и
  похожие файлы, и отказаться нельзя. Другие назвали это навязчивым [113].
- Исправление в тот же день пообещали, потом отложили; позже maintainer сказал, что оно потерялось [113].
- Затем Emdash перешёл на глобальные hooks с маркером в пользовательском конфиге [113][33].
- В ноябре пользователь показал: на Windows с Git Bash глобальные hooks отправляли JSON hook-а в интерактивный
  `cmd.exe`. Это задевало и sessions Claude Code, запущенные вне Emdash, и влияло на безопасность. Исправлено в
  v1.2.11 [113][35].
- Отдельно: hooks на Windows оставляли в worktree лишние файлы `NUL` [113].

**5. Процессы агентов живут дольше вкладок.**

- Закрытие вкладки не останавливает агента. Пользователь через два дня нашёл список «Active» полным conversations
  [114].
- На SSH-host пользователь нашёл 12 брошенных процессов `claude`. Они делили один файл учётных данных, поэтому смена
  refresh token заставляла часто входить заново [114].
- Продолжение session Claude падало с ошибкой «session ID already in use» [114].

**6. Трудности на Windows, WSL и Linux.**

- Агенты, установленные внутри WSL, не находились [115].
- Хранение учётных данных ломалось на Linux-окружениях, кроме GNOME и KDE [115].
- Требование к версии glibc отрезало Ubuntu 22.04 [115].
- Skip-permissions не работал на Windows [115].
- Ctrl+V не вставлял текст, хотя пользователь ждал, что вставка просто работает [115].
- Раньше проекты без git remote были непригодны [115].
- Первый пользователь HN на Windows и WSL2 упёрся в три разных сбоя [122].

**7. Electron и только desktop.**

- На Product Hunt и HN спрашивали, не тяжёлое ли приложение. Один ответил, что самый лёгкий вариант — Claude Code в
  iTerm [135][122].
- Просили режим сервера на localhost [122], TUI для пользователя, у которого есть только телефон [107], и доступ с
  телефона [122].
- Один пользователь HN заметил: раз Emdash встраивает терминалы, а не структурированный вывод агента, мобильный вид
  сделать нельзя [122].

**8. Emdash владеет состоянием worktree.**

**9. Побочные эффекты и безопасность.**

  - Пользователь HN возразил, что это подрывает обещание независимости от провайдера [122].
- **Чтобы агенты и инструменты могли создавать задачи** [105]:
  - локальный HTTP API (3 голоса);
  - MCP-сервер — есть proof of concept от сообщества;
  - запуск задач из Linear — запрос открыт с февраля;
  - обратная синхронизация статуса в трекер — один потенциальный клиент хочет её до внедрения.
- **Удобство review** [105]:
  - diff за последний ход агента — самый популярный открытый issue;
  - доска сравнения разных агентов;
  - предложение архивировать worktree после merge.
- **Один обзор всего запущенного.** Активный пользователь хочет видеть запущенные и зависшие задачи и automations по
  всем проектам, с длительностью и tokens по моделям [106].
- **Задачи на несколько репозиториев** (frontend и backend). Второй пользователь удивился, что этого нет [107].
- **Уже сделано после запросов:**
  - удалённая разработка — самый популярный issue за всё время (8 голосов) — стала Workspace Server. Здесь
    заметки исследования расходятся: одна датирует это сентябрём [118], а по релизам v1.2.0 с Workspace Server вышел
    2026-08-28 [34][10];
  - несколько аккаунтов одного провайдера — у пользователей по 2–3 подписки Claude; решено переменными окружения на
    уровне проекта [118];
  - включение skip-permissions посреди session [118];
  - поддержка GitLab [121][34];
  - убранную функцию staging вернули за несколько дней [107].

### Реальные результаты и неудачи

- **Практическое сравнение от Augment** (вторичный источник, конкурент) [140]:
  - разбор багов одного сервиса по трём ticket-ам Linear: настройка заняла меньше 10 минут, процесс работал хорошо;
  - изменение OAuth2 в трёх сервисах прошло плохо: агенты выбрали несовместимые схемы refresh token, согласование
    заняло около 45 минут;
  - вывод автора: в Emdash сводить результаты агентов вместе приходится человеку.
- **Как работают активные пользователи** [112]:
  - 24 workspaces примерно по 40 тыс. файлов;
  - 190 worktree и 312 задач в одном monorepo;
  - 27 проектов и 143 активных workspaces;
  - удалённая машина с несколькими dev servers.
  - Каждый такой случай вскрыл ошибку с нагрузкой на CPU или зависанием. Зависание индекса исправил PR сообщества;
    официальный релиз с исправлением вышел примерно через 6 недель после отчёта.
- **Реалистичность.**
  - Один пользователь HN оценил, что для передачи параллельным агентам подходят только 20–30% задач спринта [122].
  - Основатель описал свою работу: 1–2 активные задачи и длинный список в sidebar [122].

### Что публично о 2.0

- **Где работают агенты:** на своих серверах, в облаке Emdash или локально. Сервер или Mac mini добавляется одной
  сгенерированной командой. Каждый workspace — изолированная среда Linux, похожая на контейнер; недостающие пакеты
  ставятся при первом использовании [1][5].
- **Откуда приходит работа:** из Emdash, Slack, Linear, GitHub или с телефона. Агенты продолжают после закрытия
  ноутбука; sessions доступны из web, desktop и с телефона [1][131].
- **Агенты:** Claude Code, Codex, Cursor, OpenCode или свои агенты через ACP, любая модель [1].
- **Командные функции** [1][6]: общие среды, skills, MCP-серверы и секреты; общие sessions, живые preview и review PR;
  SSO и роли; учёт использования и лимиты расходов по всем провайдерам; недельные или месячные лимиты на разработчика
  с исключениями; администратор одобряет, какие MCP-серверы можно инженерам.
- **Обещанный результат:** агенты тестируют приложения, чинят упавший CI и открывают PR с визуальными доказательствами
  [1]. Не проверено: публичной сборки нет.
- **Статус:** waitlist без даты, цен и лицензии [1][4][5].
- **Деньги:** отдельные пользователи — бесплатно со своими серверами и подписками. За использование можно платить
  через Emdash или купить у него tokens и вычисления [6][5].

## Слабые места и чего нет

- **Продукт, который можно скачать, больше не развивается.** С 2026-11-05 Classic получает только исправления. Новый
  продукт 2.0 — waitlist без документации, цен, даты и лицензии [4][1][13].
- **Нет ничего над задачей.** Ни планирования, ни разбиения работы, ни orchestrator-а, ни координации агентов. Основатели
  оставляют это CLI [122][107][108].
- **Работа без человека заканчивается на старте session.** Automation отмечает `done`, когда session запустилась. Она
  не следит за агентом, не проверяет результат, не делает retry и не ждёт сброса лимитов. Просроченные запуски
  пропускаются без догона [66][65][67].
- **Лимиты только показываются.** Usage page есть только для Claude Code и Codex. Планирование и automations её не
  читают, учёта стоимости по задаче нет [81][65][80][32].
- **Одобрение без правил.** В терминале — один флаг на всю conversation, который отключает все запросы. В чате каждое
  разрешение ждёт клика человека без timeout [76][84].
- **Нет проверки качества.** Нет локального gate, агентов-reviewer-ов и передачи ошибок CI агенту. CI — только экран
  статусов. Текст PR пишет человек [32][88][90].
- **Нет sandbox.** Агенты работают с правами пользователя, worktree — единственная изоляция. Вопросы о sandbox на HN
  остались без ответа [51][122].
- **Браузер без агента.** Агент не управляет встроенным браузером. «Visual evidence» в Classic — кнопка копирования
  скриншота [92][21].
- **Нет программного интерфейса.** Ни CLI, ни HTTP API, ни MCP-сервера для создания задач. Issues — только чтение, без
  webhooks и без обратной записи статуса [105][100].
- **Плохая отрисовка Claude Code в терминале.** Ошибки отрисовки полноэкранного интерфейса Claude Code возвращались
  месяцами; размер терминала после смены вкладки починили только в v1.2.8 [110].
- **Регрессии при обновлениях.** Падения при старте в v1 beta и 1.2.10, сломанные Jira и шрифты, молча пропавшая
  доставка diff comments [111].
- **Производительность на сотнях worktree.** Сотни процессов `git worktree list`, CPU в простое, зависания индекса.
  Фоновый `git fetch` каждые 2 минуты без настройки всё ещё открыт [112].
- **Hooks в чужих конфигах.** Запись hooks в конфиги агентов вызвала жалобы. Переход на глобальные hooks сломал
  sessions Claude Code вне Emdash на Windows с Git Bash; исправлено в v1.2.11 [113][35].
- **Процессы переживают вкладки.** Закрытая вкладка не останавливает агента. Брошенные процессы `claude` на SSH-host
  меняют общий refresh token и заставляют входить заново [114].
- **Трудности на Windows, WSL и Linux:** агенты в WSL не находятся, учётные данные не сохраняются вне GNOME и KDE,
  требование к glibc отрезает Ubuntu 22.04 [115].
- **Безопасность.** Ошибка проверки ключа SSH-host открыта с 2026-03-08, security policy нет [116]. Telemetry включена
  по умолчанию и после входа отправляет email, а privacy policy говорит, что персональные данные не собираются
  [29][11].
- **Порт без проверки.** `EMDASH_PORT` считается по хэшу пути и не проверяет, свободен ли порт [93].
- **Нет обзора и истории работы.** Нет общего вида запущенного по проектам (#3348), ленты событий запуска без человека,
  времени и стоимости по задаче [106][32].
- **Нет задач на несколько репозиториев** [107].
- **Нет мобильного и web-доступа в Classic.** Встроенные терминалы мешают мобильному виду; PR с мобильным видом закрыт
  [122][120].
- **Отношения с внешними авторами.** Во время переписывания v1 закрыто без слияния 122 PR [120].
- **Цифры и обещания вендора.** Заявление о более чем 1 млн загрузок по установщикам не воспроизводится [36]. Маркетинг
  месяцами обещал уже убранные функции — BYOI и Best-of-N [138][131].
- **Имя.** Совпадение с CMS от Cloudflare засоряет поиск и issues [153][109].

## Пересечение с worfy

Термины worfy в этом разделе:

- Canvas — бесконечное полотно, на котором worfy показывает работу агентов.
- Epic — группа связанных Ticket-ов. Ticket — одна задача.
- Orchestrator — session, которая планирует и раздаёт Ticket-ы.
- Wave — набор Ticket-ов, которые запускаются вместе. Autopilot — запуск Wave-ов без человека: ждёт сброса лимитов
  подписки, повторяет ошибки API, одобряет запросы разрешений по политике.
- Gate — локальный проверочный запуск перед PR.
- Harness — plugin, который приносит в Claude Code rules, skills, subagents и hooks.
- Flight Recorder — лента событий запуска без человека. Work track — вся работа проекта за день или неделю.
- Cards — карточки, которые агенты строят на Canvas через MCP-сервер worfy.
- Product Session — продуктовый советник с живым Mind map и критиком spec.
- Linked machines — связанные машины в локальной сети.
- Evidence screenshots — скриншоты-доказательства с privacy scrub (удалением личных данных).
- Eco mode — переключает роли агентов на более дешёвую модель.

- **Параллельные sessions агентов, по worktree на задачу.** Emdash: по умолчанию своя ветка и worktree на задачу;

  Codex CLI.

- **PR и статусы CI в приложении.** Emdash: Changes panel с разделом PR, вкладка Checks, режимы merge, GitLab MR
  [18][19][10]. worfy: PR с CI badges.
- **Список PR проекта.** Emdash: вкладка Pull Requests с поиском и фильтром по автору, задача от PR, review по коммитам
  [10][104]. worfy: PR inbox.
- **Встроенный браузер с профилями.** Emdash: постоянные профили, проброс портов, скриншот в буфер обмена [21][92].

- **Уведомления от hooks агента.** Emdash: уведомления ОС, звук и лента; источник — hooks в конфиге агента [95][33].

- **Hooks в Claude Code.** Emdash ставит `SessionStart`, `UserPromptSubmit`, `Notification` и `Stop` в

- **Skills и MCP для агентов.** Emdash Library: skills через symlink-и в шесть агентов, конфиг MCP в 11 агентов

- **Счётчики лимитов подписки.** Emdash: Usage page с окнами Claude Code и Codex и временем до сброса [10][77][79].

- **Запуски без человека и их история.** Emdash: Automations по cron или вручную, история запусков с упавшим шагом и

- **Проверка результата.** Emdash: нет gate, агентов-reviewer-ов и передачи CI агенту; текст PR пишет человек

## Механизмы, которые стоит изучить

1. **Hooks, которые вне приложения ничего не делают.**
   - Что это: Emdash пишет hooks в глобальный конфиг агента. Статус агента берётся только из hooks, вывод терминала не
     разбирается [50][75].
   - Как работает:
     - команда hook выходит с кодом 0, если нет `EMDASH_HOOK_PORT`, `EMDASH_HOOK_NONCE` или `EMDASH_PTY_ID`;
     - иначе `curl --noproxy "*"` шлёт POST на `http://127.0.0.1:$PORT/hook` с заголовками id PTY и типа события;
       token берётся из конфига curl на файловом дескрипторе 3; на Windows — `powershell -EncodedCommand`;
     - сервер приёма на случайном порту требует UUID-token, принимает до 1 МБ, на неверный token отвечает 403;
     - записи помечены маркером и `EMDASH_HOOK_CONFIG_VERSION=1`; установщик проверяет их до и после блокировки и не
       трогает файлы, которые не может разобрать;
     - машина состояний: start → working, stop → completed, запрос разрешения → awaiting-input; Notification с текстом
       `permission|approval` — запрос разрешения [71][72][76].
   - Чем интересно: статус и уведомления без разбора терминала, а одна запись hooks на машину не мешает sessions вне
     приложения. История с Git Bash на Windows показывает, где такой подход ломался до v1.2.11 [113].
   - Источник: [50][71][72][75][76][78][113].
2. **Чтение лимитов подписки без запроса к модели.**
   - Что это: Usage page читает окна лимитов Claude Code и Codex [77][79].
   - Как работает:
     - Claude: `query()` из Agent SDK с генератором prompts, который ничего не отдаёт; только пользовательские
       настройки, hooks выключены, без инструментов и MCP; затем управляющий запрос
       `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET`; окна `five_hour`, `seven_day`,
       `seven_day_oauth_apps` и по моделям;
     - Codex: JSON-RPC `initialize`, `account/read`, `account/rateLimits/read`; только при входе через ChatGPT;
     - один кэш на host, обновление раз в 5 минут, ручное — не чаще раза в 10 секунд, timeout 35 секунд; при ошибке
       остаются последние окна [81].
   - Чем интересно: это те же источники данных, что нужны для счётчиков лимитов и планирования запусков. Имя запроса
     Claude прямо говорит, что API экспериментальный и может измениться.
   - Источник: [77][79][81].
3. **Host — источник истины; удаление через tombstone и reconcile sweep.**
   - Что это: ADR 0001 и ADR 0006 — правила согласования desktop и машины, на которой лежат worktree [59][60].
   - Как работает:
     - изменения — простые RPC, которые сразу возвращают ошибку; скан с ошибкой ничего не пишет; worktree, созданные
       руками, принимаются;
     - удаление пишет tombstone с замороженными параметрами; sweep повторяет идемпотентное удаление при старте, при
       переподключении и раз в 10 минут, с паузой на элемент от 60 секунд до 60 минут;
     - человеку остаются Retry или «Untrack anyway»; mutex по репозиторию и по workspace;
     - durable outbox и журнал операций сделали и выбросили [60][58].
   - Чем интересно: простая модель для машины, где пользователь сам меняет файлы и ветки, и честный опыт отказа от
     более сложной схемы.
   - Источник: [49][58][59][60][86].
4. **Установка и версия daemon на удалённой машине.**
   - Что это: Workspace Server на SSH-host [48].
   - Как работает: неизменяемые папки версий и атомарный symlink `current`; проверка SHA-256 до установки; канал SSH
     streamlocal к Unix socket в папке с правами 0700, без открытого порта; handshake `initialize` на каждое
     подключение, совместимость по major-версии с ошибками «upgrade client» и «upgrade server»; все runtimes
     обязательны [48][87].
   - Чем интересно: обновление и откат daemon без полуустановленного состояния и без открытого порта.
   - Источник: [48][87].
5. **Supervisor подключения с фиксированными бюджетами времени.**
   - Что это: ADR 0008 — один владелец подключения на host [61].
   - Как работает: паузы retry 0,5, 1, 2, 5, 10, 20 и 30 секунд со случайным разбросом; health check раз в 15 секунд с
     deadline 5 секунд; 10 секунд на канал и initialize; 120 секунд на установку соединения; ошибки аутентификации и
     ключа host останавливают retry; несовпадение протокола требует явного обновления [61][85].
   - Чем интересно: связь с другой машиной восстанавливается сама, но не крутится вечно на ошибках, которые retry не
     исправит.
   - Источник: [61][85].
6. **Окружение задачи: диапазон портов и lifecycle-скрипты с общим файлом.**
   - Что это: переменные `EMDASH_*` и скрипты из `.emdash.json` [17][93].
   - Как работает:
     - `EMDASH_PORT` = 50000 + (хэш пути mod 1000) × 10 — 10 портов на задачу, без проверки, свободен ли порт;
     - `prepare` блокирует до старта session, `setup` не блокирует, `run` ждёт `setup`, `teardown` не блокирует
       деактивацию; timeout 5 минут, у `run` нет; сбой становится notice, а не ошибкой;
     - preserve patterns копируют gitignored-файлы через copy-on-write;
     - «Share with team» пишет общий `.emdash.json`, личные значения его перекрывают [93][51][94][17][57].
   - Чем интересно: пользователи называют это самой полезной частью продукта [122][125].
   - Источник: [17][51][57][93][94].
7. **Git-учётные данные через helper на loopback.**
   - Что это: агент делает push под нужным аккаунтом, а token в окружение не попадает [82].
   - Как работает: каждой session — порт на loopback и случайный nonce; credential helper подключается через
     переменные `GIT_CONFIG_*`; desktop выбирает аккаунт на каждый запрос; режимы `effective-account`, `system`,
     `none`; аккаунт GitHub выбирается для проекта [82][17][20].
   - Чем интересно: несколько аккаунтов GitHub на одной машине без tokens в окружении, аргументах и logs.
   - Источник: [17][20][82].
8. **Доставка prompt в чате: «принят» не значит «выполнен».**
   - Что это: правила ACP runtime для отправки prompts и восстановления sessions [47].
   - Как работает:
     - `sendPrompt` подтверждает только приём; сбой до отправки помечается «not sent», и черновик возвращается;
       неуверенные сбои не повторяются;
     - маркеры `initialQueueConsumed` и `unstarted` решают, когда безопасно заменить пропавшую session;
     - процессы провайдера кэшируются по провайдеру, папке и отпечатку окружения; счётчики поколений отбрасывают поздние
       события;
     - session засыпает после 60 минут без вывода и поднимается через `loadSession`; при `session_not_found` выбор за
       человеком [47][83].
   - Чем интересно: явное разделение «принят» и «выполнен» и запрет на повтор, когда исход неизвестен. В глоссарии уже
     описан более строгий вариант с состоянием «outcome unknown», но код его пока не использует [56].
   - Источник: [47][56][83].
9. **Запуск и перезапуск TUI-агента.**
   - Что это: как Emdash стартует CLI агента в терминале и поднимает его после сбоя [73][76].
   - Как работает:
     - до запуска Emdash пишет `hasTrustDialogAccepted` и `hasCompletedProjectOnboarding` для worktree в
       `~/.claude.json`, чтобы Claude Code не спрашивал о доверии к папке [76][71];
     - `--session-id` детерминирован на conversation; `session_id` из hooks отслеживается, поэтому `/resume` внутри TUI
       не теряется [76][50];
     - окружение передаётся launcher-у tmux через приватный FIFO, а не через аргументы [52];
     - prompt длиннее 16 384 символов уходит в файл `task-context.md`, агент получает ссылку [74];
     - неожиданный выход без tmux — один перезапуск через 500 мс с resume; если процесс умер за 3 секунды — новая
       session (`fresh-fallback`) [73].
   - Чем интересно: запуск в новом worktree без вопросов агента и короткий предсказуемый путь восстановления.
   - Источник: [50][52][71][73][74][76].
10. **Планировщик automations с одним будущим запуском.**
    - Что это: правила cron-запусков [65][67].
    - Как работает: проверка раз в 60 секунд; не больше 4 запусков одновременно и 100 за проверку; у automation ровно
      один запуск `scheduled`; срок — следующее срабатывание cron; просроченный пропускается без догона;
      `previous_running` и `redeployed` пропускают лишнее; у ошибки — шаг и код; после перезапуска приложения
      зависшие запуски получают ошибку «прервано перезапуском»; запуск можно превратить в обычную задачу
      [65][66][67][68][24].
    - Чем интересно: простые правила, при которых запуски не копятся. Граница тоже видна: `done` значит только то, что
      session стартовала.
    - Источник: [24][65][66][67][68].
11. **Комментарии к diff как контекст для агента.**
    - Что это: review человеком, который уходит агенту одним сообщением [91].
    - Как работает: комментарии к строкам в diff на Monaco копятся черновиками и уходят через упоминание
      `@context:diff-comments`; черновики стираются только после подтверждённой доставки; у ACP prompts есть поле
      `hiddenContext`, которое не попадает в повторённый transcript [91][10][70].
    - Чем интересно: замечания человека к коду превращаются в один prompt и не теряются, если доставка не прошла.
    - Источник: [10][70][91].
12. **2.0: правила, skills и MCP на организацию и лимиты расходов с запросом исключения** (не подтверждено в работе).
    - Что это: управление агентами команды из одного места [5][6].
    - Как работает (по блогу): Global Agent Rules копируются в файлы rules шести агентов при старте session и
      синхронизируются в запущенные sessions; администратор одобряет MCP-серверы; Team usage считает расход по ценам
      API по агенту, модели, участнику и чату; лимиты — потолок организации, недельные и месячные значения по
      умолчанию и исключение, когда администратор одобряет запрос участника [5][6].
    - Чем интересно: одна копия правил для разных агентов и бюджет, который считается по всем агентам сразу.
    - Источник: [5][6].
