## Модель работы

**Схема — hybrid.** Часть клиентов работает локально, часть — в облаке AWS. Один и тот же сеанс можно открыть из разных клиентов [27][82].

- **Один harness на все клиенты.** Harness — процесс, который ведёт цикл агента. Он собирает контекст, вызывает модель, запускает инструменты, проверяет права, хранит сессии и запускает sub-agents [9].
  - В Kiro harness — отдельный серверный процесс, а не библиотека внутри каждого клиента [82][83].
  - Клиенты подключаются к нему по ACP с расширениями Kiro [53][83]. ACP (Agent Client Protocol) — открытый протокол между агентом и редактором.
- **Клиентов пять** [1][4][9]. Если считать Kiro for Enterprise отдельно, частей шесть [1].

| Клиент | Где работает | Платформы |
|---|---|---|
| IDE | Локальное desktop-приложение на Code OSS (открытая основа VS Code). Extensions — из Open VSX, открытого реестра extensions [4] | macOS, Windows, Linux [4]. Native ARM64-сборки с версии 1.1; системный установщик для Windows с 1.4.62 [11] |
| CLI | Локальный бинарный файл. Установка: `curl -fsSL https://cli.kiro.dev/install \| bash` [5] | macOS, Linux, Windows [5]. Один самостоятельный бинарный файл `kiro-cli` с версии 3.0 [51] |
| Web | SaaS на app.kiro.dev. Каждая сессия работает в sandbox под управлением AWS [6][27] | Браузер. Облачные сессии — только в регионе us-east-1 [27] |
| Mobile | Тонкий клиент к облачным сессиям [7] | Android 10+ в Google Play, GA 2026-11-12 [37]. iOS 26+ — только ранний доступ через TestFlight [7][36] |
| Crew | Self-hosted: локально, на удалённом хосте, в Docker, на EC2 или Fargate [62][65] | macOS (.dmg), Windows (.exe), Linux (.deb, .rpm, AppImage для x86_64 и aarch64), Python wheel, Docker [65][70] |

- **Облачная сессия** (cloud session) — сессия в управляемом sandbox, которая продолжает работать после отключения клиента [125]. Любой клиент может подключиться к ней и отключиться. Одновременно работают до 10 облачных сессий [27].
- **Конфигурация одна на все клиенты.**
  - Всё под `.kiro/` действует везде: steering, specs, агенты, hooks, MCP [27].
  - Уровней конфигурации три: `.kiro/` в репозитории, `~/.kiro/` у пользователя и облачная конфигурация, синхронизированная с аккаунтом [82].
  - Configuration Sync загружает личные настройки из `~/.kiro` для облачных сессий. Он может применить их и к локальным IDE и CLI [27][52].
- **Агенты.**
  - Основной агент работает на собственном harness Kiro. Встроенные агенты: Default, Spec, Plan, sub-agent Introspect (назначение в источнике не раскрыто), в CLI ещё Guide и Help [45].
  - Пользователь может описать свои агенты (custom agents) [45].
  - Kiro Crew запускает и чужих агентов. По умолчанию — Kiro Agent (с Crew 0.11, по changelog [67]; страница Agent backends всё ещё называет backend по умолчанию Kiro CLI [57]); доступен и Kiro CLI. В экспериментальном режиме — Claude Code, Codex, OpenCode, Pi, goose, DeepSeek Harness, с 0.12 ещё Strands и GitHub Copilot CLI [57][58][67].

## Функции

Ниже — все функции из источников. Сначала то, что работает во всех клиентах через общий harness. Затем — функции отдельных клиентов, Kiro Crew, интеграции и enterprise.

### Specs: требования → дизайн → задачи

- **Что это.** Spec — набор Markdown-файлов в `.kiro/specs/<имя>/`: `requirements.md` (или `bugfix.md` для исправления), `design.md` и `tasks.md` [18]. Пользователь видит вид задач, который обновляется по ходу работы [18].
- **Требования пишутся в формате EARS.** EARS (Easy Approach to Requirements Syntax) — шаблон фраз-требований с фиксированной структурой [72][21]. Задачи в `tasks.md` упорядочены по зависимостям и связаны с требованиями [72].
- **Виды spec** [18][21][113]:
  - Feature Spec в двух вариантах: requirements-first (сначала требования) и design-first (сначала дизайн).
  - Bugfix Spec: текущее поведение, ожидаемое поведение и то, что должно остаться *без изменений*. Последний пункт нужен, чтобы исправление не сломало соседнее поведение.
  - Quick Spec: требования, дизайн и задачи за один проход, без остановок на утверждение между фазами [18][20].
  - Plan mode: план в диалоге, без формальных документов. Только IDE и CLI [18][21].
  - Quick Plan — появился в IDE 0.12 [19].
  - Пост о новых видах spec признаёт: всё ПО заранее описать нельзя. Поэтому spec можно начинать с того места, с которого начинает думать разработчик [113].
- **Run all tasks — запуск задач волнами по зависимостям** [18][19][20]:
  - Kiro строит граф зависимостей из `tasks.md`.
  - В волну 1 попадают задачи без зависимостей. В волну N — задачи, чьи зависимости закрыли предыдущие волны. Волны идут по очереди, задачи внутри волны — одновременно.
  - Задачи, которые трогают одни и те же файлы, параллельно не запускаются. Подготовка идёт первой, тесты — после кода, который они проверяют [18][19][20].
  - Источники расходятся. В другом разборе тех же страниц правило про общие файлы не найдено, там упомянут только отдельный контекст на задачу. Отдельные worktree или блокировки файлов для задач волны нигде не описаны (не подтверждено) [18][19].
  - Каждая задача работает в своём изолированном контексте. Упавшая задача не останавливает остальные [18][19].
  - Kiro обещает ускорение «до 4x», если независимых задач 4 и больше [19]. Пример вендора: большие spec, которые шли больше часа, стали занимать примерно четверть этого времени [20].
  - Работает в IDE, CLI, Web и Mobile [18].
  - История. Кнопка Run all tasks вышла в январе 2026 (пост от 2026-01-16) [85]. По этому посту Kiro держал функцию, пока не появились три опоры: property-based tests, dev servers с диагностикой language server и sub-agents [85]. В другом прочтении того же поста функцию держали, пока пользователи не попросили. Пост советует её только для небольших spec и признаёт, что агент иногда уходил не туда [85]. Параллельные волны появились позже, в IDE 0.12 (2026-05-06) [19]. Майский пост уже говорит об ускорении именно больших spec [20].
- **Analyze Requirements** — проверка требований до дизайна. Только IDE и CLI [18][21].
  - Ищет противоречия, неоднозначности, конфликтующие ограничения, неявные допущения и пропущенные граничные случаи [18][21].
  - Работает в три этапа [86][20]:
    1. LLM переписывает размытые критерии в проверяемые строки EARS, без готового решения внутри.
    2. Каждый критерий несколько раз переводится в SMT-LIB — входной формат логических solver. Переводы группируются по логической эквивалентности. Если группы расходятся, требование неоднозначно.
    3. SMT-solver ищет противоречия и пробелы.
  - Каждая находка показывается пользователю как вопрос с двумя вариантами ответа [86].
  - Вендор подчёркивает: это automated reasoning, то есть математическая логика, а не догадка LLM [20].
- **Correctness: property-based tests (PBT).** Только IDE [18][21].
  - PBT — тесты, которые проверяют заявленное свойство на множестве сгенерированных входов.
  - Kiro выводит свойства из требований в стиле EARS [21].
  - Тесты используют Hypothesis (библиотека PBT), по умолчанию 100 сгенерированных случаев. Упавший вход сокращается до минимального контрпримера [106][21].
  - Вендор прямо называет PBT свидетельством корректности, а не доказательством [106].
  - При контрпримере Kiro спрашивает человека, что неверно: код, spec или тест [106].
- **Markdown Review** — комментарии к точным местам отрендеренного spec или любого Markdown. Все комментарии уходят агенту одним пакетом [18][40].
- **Spec review в CLI** — с августа 2026 [11].
- **Spec hardening** — Power, который до начала кода добавляет в spec требования безопасности по каталогу CWE (перечню типовых слабостей ПО). Вендор называет это контролем на входе, а не границей безопасности во время работы [128].

### Workflows: граф шагов агента (ближе всего к worfy)

- **Что это.** Workflow — граф из шагов агента, ветвлений с объединением, циклов и ожиданий [12][84].
  - Сохранённый workflow называется recipe. Это файл JSON или YAML в `.kiro/workflows/`, в пользовательской конфигурации, в синхронизированной конфигурации или встроенный в Kiro [12].
- **Как запускается.**
  - Обычно Kiro сам пишет workflow по запросу и показывает план. Ничего не запускается, пока пользователь не ответит [12].
  - План приходит карточкой разрешения: Allow, Deny, Always allow, Always deny или текстовый отзыв [12][15].
  - В плане видны агент, модель, effort и первая задача каждого шага [17].
  - В Web с 2026-10-28 workflow, созданный из запроса, начинается с шага create-workflow. Этот шаг спрашивает недостающие детали, а не угадывает [17].
- **Где работает:** IDE, CLI и облачные сессии Web. В Mobile — нет [12][27]. Функция включается настройкой `kiroAgent.workflows.enabled` [12].
- **Как охотно Kiro предлагает workflow.**
  - Настройка «Use workflows» (IDE 1.4.26+): Only when asked (по умолчанию), Only for large tasks, As much as possible [12]. В CLI ключ называется `chat.workflowLaunch` [88].
  - До CLI 2.33.1 (2026-10-21) включение функции само запускало workflows. Теперь они запускаются только по просьбе [136][12].
- **Типы узлов** [13]:
  - `step` — один агент в своей новой сессии со свежим контекстом.
  - `sequence` — шаги по очереди.
  - `repeat` — цикл. Обязательны `maxIterations` и `onMaxIterations`, то есть что делать на пределе: abort, continue или pause. Страница называет все три значения [13]. Жёсткий потолок в 1 000 итераций в документации workflows не найден (не подтверждено) [12][13][15].
  - `parallel` — параллельные ветви с правилом объединения `joinPolicy`: all, allSettled или any.
  - `watch` — ожидание внешнего события без вызова модели (описано ниже).
  - Пределы: не больше 50 шагов и вложенность не глубже 8 [13][15].
- **Передача данных между шагами.**
  - Шаги не читают сессии друг друга [12][13].
  - Данные идут только через сохранённый вывод (`{{previous.output}}`, `{{<id>.output}}`), объявленные файлы-артефакты (`{{artifacts.<имя>}}`) и входные параметры запуска [13].
  - Сохранённый вывод оборачивается в защищённые от подделки разделители. Так текст одного шага не может выдать себя за инструкцию для следующего [13].
- **Сигналы шага** идут через `send_message` с уровнем важности [12][13]:
  - success завершает шаг;
  - warning ставит запуск на паузу и просит ввода;
  - error проваливает шаг;
  - info — просто заметка о ходе работы [13].
- **Выход из цикла только по доказательствам** [13][14]:
  - `stopCondition`: `containsText`, `completionSignal` или `fileCheck`. В `fileCheck` путь JSON в файле должен совпасть со значением, например `verdict == APPROVED` [13].
  - `stopWhen`: выражения вроде `wait.terminal` или «итоговый вывод содержит `VERDICT: APPROVED`» [13].
  - Заявление об успехе обычным текстом цикл не завершает [14]. Документация называет пределы итераций страховкой, а не доказательством успеха [14].
  - Каждый цикл должен иметь конечный `maxIterations` [12].
  - Для каждого шаблона документация называет, что считается доказательством: отчёт-артефакт; утверждённые дизайн, план и проверки; воспроизводимый тест или машиночитаемый результат; состояние review в PR, проверки и готовность к merge [12].
  - Пример схемы в документации: gate пропускает дальше при VERIFIED или возвращает к реализации, не больше 3 раз [12].
- **Модель и effort на шаг.**
  - Порядок выбора модели: настройка шага → значение по умолчанию у workflow → модель родительской сессии (фиксируется при создании запуска) → модель агента [13].
  - Неизвестная модель падает на первом вызове. Замены нет [13].
  - Reasoning effort задаётся на сессию или на шаг [13][47].
- **Ожидание без токенов — узел `watch`** [13]:
  - Обработчиков два. `github-pr` опрашивает GitHub раз в 60 с по умолчанию, минимум раз в 30 с. `command` на каждом опросе запускает вашу программу (по умолчанию раз в 60 с, минимум раз в 10 с). Программа возвращает `idle`, `new-activity` или `terminal-state` и непрозрачный cursor.
  - **Пока ничего не происходит, модель не вызывается.**
  - Наблюдение за PR будит агента на новые комментарии, review, inline-комментарии, упавшие CI checks и (CLI 2.33+) merge-конфликты.
  - Каждый сбой или конфликт будит агента один раз на head commit. За один опрос приходит не больше 10 элементов.
  - Наблюдение завершается, когда PR слит или закрыт. `idleTimeoutSec` завершает слишком долгое ожидание без событий.
  - Формат данных и коды выхода — в разделе «Как это устроено внутри → Ожидание без токенов».
- **Встроенные агенты для workflows** [13]: wf-planner, wf-coder, wf-design, wf-design-reviewer, wf-review-aggregator, wf-pr-submitter, wf-pr-responder, wf-auto-researcher, wf-workflow-creator и semantic_reviewer.
- **Встроенные recipes** [12][14]:
  - `investigate` — исследование только на чтение. Итог — отчёт со ссылками на источники.
  - `feature-pipeline`:
    - Этапы: требования → цикл дизайна → план → цикл кода [14].
    - Цикл дизайна — не больше 3 проходов. Он завершается, когда `design-review.json` говорит APPROVED; иначе запуск прерывается [14][84].
    - Цикл кода — не больше 3 проходов. В нём **два reviewer на моделях разных семейств** работают параллельно, затем aggregator сводит их находки [14][84].
    - Источники расходятся в названии моделей reviewer. Страница шаблонов называет `claude-fable-5` и `gpt-5.6-sol` [14]. Пост о запуске workflows — `claude-opus-5.5` и `gpt-5.6-sol` [84].
    - Последний шаг `validate` сверяет результат с исходными требованиями [14].
    - Effort по шагам: High при запуске из Opus 5, Extra high для дизайна и review, Low для подготовки [14][84].
  - `publish-pr` (на странице шаблонов — publish-and-respond) [14]:
    - Submitter открывает PR и пишет `pr.json`.
    - Затем идёт цикл до 200 итераций с паузой на пределе. Он ждёт событие PR через `watch` и отвечает по одному разу на событие, пока PR не завершится (`wait.terminal`).
    - По описанию итог — зелёный одобренный PR. Merge остаётся за человеком.
    - Responder (wf-pr-responder) при конфликте сливает base-ветку обычным merge commit. Он никогда не делает rebase и force-push.
    - Responder чинит checks, которые сломала его ветка. Чужой упавший check он перезапускает один раз на GitHub Actions run.
    - Responder закрывает threads review, на которые ответил. Сам PR не сливает. Перед изменениями дизайна, объёма работы или UX спрашивает человека [14].
  - На странице шаблонов есть заготовка с входами `worktree_path` и `run_id` и циклом `validate-gate` [14].
- **Состояния запуска** [15]: running; paused (нужен ввод, остановка на границе узла или на пределе итераций); completed; failed; aborted. У отдельных узлов есть ещё pending и skipped.
- **Управление запуском** [15]:
  - Pause — кооперативная: срабатывает на следующей границе узла. Resume продолжает с сохранённого состояния.
  - Stop помечает запуск как aborted. Изменения в файлах он не откатывает.
  - Retry сбрасывает упавшие узлы и сохраняет завершённые соседние. В CLI — `/workflow retry <id> [nodeId]`.
  - На пределе итераций можно дать ещё: «Add loops» в IDE, «Run N more» в Web, «Run 1 more iteration» в CLI 3.2+.
  - С 2026-10-28 цикл review по умолчанию встаёт на паузу после двух отклонённых проходов. Раньше такие циклы делали 3–5 проходов и падали. Собственный предел проходов, заданный в workflow, по-прежнему главнее. Это запись changelog Kiro Web [17]; на странице управления workflows [15] этого правила нет.
  - `update_workflow` меняет оставшуюся часть плана. Завершённые и активные узлы менять нельзя [15].
- **Устойчивость к сбоям** [12][15]: checkpoint на каждой границе узла; cursors наблюдения переживают перезапуск; при обрыве соединения шаг повторяется на месте до 24 часов, затем запуск встаёт на паузу. Расписание повторов — в разделе «Как это устроено внутри → Восстановление после сбоев».
- **Изоляции в git нет.** Документация прямо пишет, что workflows не изолируют ветки git и не создают worktree [15]. В IDE Kiro только говорит workflow работать от текущей ветки и потом сделать rebase обратно [12].
- **Управление по клиентам** [12]:
  - IDE: панель Workflows и вкладки по шагам; Pause, Resume, Stop. Уведомления о шагах — с IDE 1.3.11 [11].
  - CLI: `/workflow run`, история запусков и полноэкранный монитор с Retry. Кредиты по шагам — с CLI 3.1 [52].
  - Web: панели Workflows, Summary, Files и Artifacts; Retry для упавших узлов [16]. Активные запуски закреплены над чатом [17].
- **Sub-agents и workflows.** Если workflows включены, передача задачи custom agent превращается в фоновый запуск workflow [46].
- **Как Kiro использует workflows сам** [84]: среда выполнения workflows и интеграция Kiro Web в основном построены с помощью workflows, в отдельных worktree. Это тысячи запусков, обычно по 5–10 шагов. Команды запускают десятки workflows за сессию. Сессии живут неделями, workflows работают почти круглосуточно. Если шаг спрашивает то, на что разговор уже ответил, основная сессия отвечает за пользователя.

### Права: режимы, Approve for me, sandbox

- **Правила прав.** Каждое правило называет capability (вид действия) и эффект. Эффекты по старшинству: deny > ask > allow > evaluate [23].
  - Ни один уровень настроек не главнее другого. Побеждает самое строгое правило [23].
  - Устройство движка — в разделе «Как это устроено внутри → Права и безопасность».
- **Shell-команды** перед проверкой режутся по `;`, `&&` и `|`. Каждая часть проверяется отдельно [23]. Команду, которую нельзя разобрать, Kiro блокирует и просит агента её переписать [23].
- **Режимы прав в IDE** [24][23]:
  - Supervised — пользователь утверждает правки каждого хода по hunks. Проверка по hunks в Supervised появилась в феврале 2026 [113].
  - Accept file changes — бывший «Autopilot». Правки идут без вопросов, команды по-прежнему спрашивают [24][23].
  - Approve for me (описан ниже).
  - Режим хранится в настройке `kiroAgent.agentAutonomy` [23]. В IDE 1.4.154 там, где доступен Approve for me, старый переключатель Autopilot стал меню режимов [102].
- **Approve for me** [22][23][24][25][26]:
  - Действия, которые не покрыло ни одно правило, получают эффект `evaluate`. Их проверяет LLM — «trust classifier». Сейчас это модель Anthropic. Классификатор одобряет действие, блокирует его или спрашивает пользователя [22][23].
  - Правила решают первыми. Правила deny, встроенные правила ask и любой сбой классификатора по-прежнему блокируют или спрашивают [23].
  - После трёх шагов подряд с заблокированным действием Kiro возвращается к вопросам пользователю и объясняет причину [22].
  - Данные вендора: правила решили около 70% действий. Из 30%, ушедших на проверку, около 97% решены без пользователя, около 2% ушли к пользователю, меньше 1% заблокированы. Медианное время проверки — меньше 1 с [22].
  - Каждая проверка списывается с плана пользователя [22].
  - Только платные планы и только регионы us-east-1 и eu-central-1. По умолчанию выключено [22].
  - Как это видно пользователю. Одобренный вызов помечен «Approved for you». Заблокированный вызов падает и показывает причину. Запрос к пользователю объясняет, почему действие отмечено, или что оно слишком большое для проверки [23][25].
  - В Web по каждой сессии видно, что одобрено, что заблокировано и что отправлено пользователю [25].
  - В CLI выбор хранится на уровне workspace в `permissions.yaml` [26].
  - Организации могут управлять функцией или требовать её [22].
  - Режим не действует в автономных сессиях Web, в сессиях, начатых комментарием на GitHub, и в задачах по расписанию [25].
  - Если ни один клиент не подключён, запрос ждёт следующего клиента [25][27].
  - Отдельный экспортируемый журнал решений в ядре Kiro не найден (не подтверждено) [23][25].
  - Вендор советует сочетать режим с OS sandbox [22].
- **Другие средства управления правами:**
  - `--trust-all-tools` и `/tools trust-all` доверяют всем действиям [22][52].
  - Workspace trust — доверие к папке проекта. Оно хранится вне репозитория [23].
  - `.kiroignore` — файл исключений для агента [45].
  - Kiro Web без Approve for me одобряет все действия внутри sandbox [23].
- **Локальный sandbox для команд** (IDE 1.3+, CLI 2.31+; по умолчанию выключен) [43]:
  - macOS — Seatbelt; Linux — bubblewrap; Windows — после разовой настройки с правами администратора [43].
  - Режимы сети: DEFAULT_BLOCKED, COMMON_DEPENDENCIES, DEFAULT_ALLOWED [43].
  - `/autonomous on` в CLI включает sandbox и затем работает без вопросов по каждой команде [52].
  - Дата: по changelog — 2026-10-13 [11][52], пост в блоге — 2026-10-14 [94].

### Агенты и sub-agents

- **Встроенные агенты:** Default, Spec, Plan, sub-agent Introspect, в CLI — Guide и Help [45].
- **Custom agents** — свой агент с промптом, моделью, инструментами, правами, MCP-серверами и ресурсами [45]. В IDE появились в версии 0.9 (2026-02-12) [11].
- **Sub-agents** [46]:
  - Работают параллельно, у каждого свой контекст. Общие у них — steering, MCP-серверы, workspace и права.
  - Главный агент заранее планирует весь граф зависимостей. Во время работы граф не меняется.
  - Циклы review задаются так: целевой этап, строка-триггер не короче 4 символов, `max_iterations` от 1 до 10. Цикл на самого себя и взаимные циклы отклоняются.
  - Отчёт пользователя: параллельные sub-agents сначала шли по одному. Более поздний комментарий в том же issue говорит, что теперь параллельно идут до 5 [140: #4547 — жалоба на последовательный запуск sub-agents].

### Контекст, расширения, память

- **Steering** — постоянные Markdown-файлы с правилами проекта в `.kiro/steering/`, плюс глобальный steering [45][11].
  - Режимы включения в контекст: always, fileMatch, manual, auto [45].
  - Читаются и вложенные `AGENTS.md` (с августа 2026) [45][11].
- **Skills** — открытый формат Agent Skills для навыков агента [45]. В CLI — с января 2026, в IDE — с версии 0.9 [11].
- **Powers** — пакет из инструкции `POWER.md`, конфигурации MCP-сервера и, по желанию, steering и hooks [111][45]:
  - Power включается по ключевым словам в разговоре. Так Kiro борется с перегрузкой контекста: по словам вендора, пять MCP-серверов могут занять около 40% окна контекста ещё до первого запроса [111].
  - Появились в декабре 2025: пост от 2025-12-03, IDE 0.7 — 2025-12-06 [111][11].
  - Реестр показывает 158 Powers и MCP-серверов [81]. Пост к годовщине говорит о 100+ отобранных Powers и 15 000+ Powers от сообщества [121]. Источники считают разные вещи.
  - С августа 2026 Powers принимают открытый формат «Agent Plugins 1.0.0». AWS входит в его steering committee вместе с Cursor, Microsoft, OpenAI и Vercel [81].
- **MCP** (Model Context Protocol — протокол подключения внешних инструментов): реестр, поиск инструментов (tool search), OAuth, ссылки для установки в один клик [45].
- **Hooks** — команды или промпты, которые срабатывают на события агента и файлов [44]:
  - Триггеры: Prompt Submit, Agent Stop, Session Start/End, Pre/Post Tool Use, Pre/Post Compaction, File Create/Save/Delete, Pre/Post Task Execution (для задач spec), Manual и MCP [44].
  - Hook Pre Compaction может отменить compaction кодом выхода 2 [11]. Глобальные hooks — с июля 2026 [11].
  - Источники расходятся. Документация по типам hooks перечисляет триггер Manual [44]. Changelog IDE 1.0 пишет, что ручные hooks стали ручными steering-файлами [120].
  - Коды выхода и таймауты — в разделе «Как это устроено внутри → Цикл агента».
- **Memory** в IDE и CLI [42][91]:
  - Запись памяти — заголовок, описание и содержание [42].
  - Память хранится локально, отдельно для каждого аккаунта. Она общая для IDE и CLI на одной машине. Область — глобально или один репозиторий [42].
  - Уровни: Use and learn, Use but don't learn, Use only, Off. По умолчанию — Off [42][91].
  - Нужны IDE 1.4.0+ или CLI 2.29+ (V3). Sub-agents память читают, но не пишут. Поддержка в Web обещана позже [42].
- **Compaction** — сжатие истории, когда контекст подходит к пределу. Есть во всех клиентах [41][92]. Сохраняется структурированная сводка и последние сообщения целиком [92].
- **Checkpoints** (IDE) — снимки файлов, изменённых встроенными инструментами. Изменения через bash и MCP в снимки не попадают [41]. В CLI есть `/rewind`: он делает ответвление разговора [41].
- **Прочее:** web search и fetch; code intelligence на Tree-sitter и LSP [40]; code intelligence для 18 языков — с января 2026 [11].

### Модели

- **Список** [47]:
  - Claude: Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, 4.8, 4.7, 4.6, 4.5, Sonnet 5, 4.6, 4.5, Haiku 4.5.
  - Fable 5.1 — только для enterprise, множитель 6x.
  - GPT-5.6 Sol, Terra и Luna.
  - Grok 4.7 (experimental).
  - Kimi K3, GLM-5, MiniMax M2.5/M2.1, DeepSeek 3.2, Qwen3 Coder Next.
- **Множители кредитов** считаются относительно Auto (1.0x): от 0.05x (Qwen3 Coder Next) до 6x (Fable) [47].
  - Примеры: Opus 5.5 — 2.0x, Opus 5 — 2.2x, Sonnet 5.5 — 1.3x, Haiku 5.5 — 0.06x, GPT-5.6 Terra — 2.2x, GPT-5.6 Luna — 0.6x [47].
  - GPT-5.6, Haiku 5.5 и Grok 4.7 стоят дороже, если контекст больше порога [47].
- **Auto** — маршрутизатор моделей по умолчанию. Стоит 1x и рекомендуется вендором [47][105].
  - С ноября 2026 Auto работает каскадом. Сессия начинается на экономичной модели. Независимая модель в фоне следит за ходом работы. Если ход неэффективен, сессия переходит на более сильную модель [48].
  - Цифры — в разделе «Как это устроено внутри → Лимиты и стоимость».
- **Запасная модель (fallback).**
  - Если модель недоступна, запасная отвечает один ход. Если модель отказалась отвечать, сессия остаётся на запасной [47][28].
  - Запасная модель вендора срабатывает только на отказы. Заданная пользователем — ещё и на недоступность [47][87].
  - Выбор запасной модели в Web — с 2026-10-12 [87].
- **Конец поддержки старых моделей** задан датами. Например, Sonnet 4 снят 2026-10-14 [11].

### Web (app.kiro.dev) и облачные сессии

- **Режимы** [28]: Default (интерактивный), Spec и Autonomous.
  - В Autonomous агент сам планирует, задаёт критерии приёмки и раздаёт шаги sub-agents для анализа, кода и проверки [28][29].
  - Он открывает один или несколько PR (или merge requests) и сам выбирает модель [28].
  - Если агенту нужен ввод, задача переходит в «Needs attention» [29].
- **После PR** [6]: агент следит за результатами CI, чинит падения и подхватывает отзывы reviewer. Сам он никогда не делает merge [6][28] и не может обойти защиту ветки [126].
- **Поведение облачной сессии** [27]:
  - До **10 одновременных** сессий без доплаты за вычисления. Лишние задачи ждут в статусе «Queued» [27][28].
  - Любой клиент может подключиться и отключиться. Запросы разрешений ждут следующего подключённого клиента.
  - Режима Supervised пока нет. Переименовать сессию пока нельзя.
  - Сессия истекает через 90 дней после последней активности; открытие сессии или новое сообщение начинают отсчёт заново. PR, merge requests и изменения кода на GitHub или GitLab это не затрагивает. Остановленный sandbox запускается снова, когда сессию открывают [28].
- **GitHub** [30]:
  - GitHub-приложение Kiro Agent просит чтение и запись для Actions, Checks, Contents, Issues, Pull requests и Workflows.
  - Задача стартует по метке `kiro` или комментарию `/kiro`.
  - `/kiro all` отвечает на все комментарии review. `/kiro fix` — на один thread.
  - Падения GitHub Actions агент разбирает, когда пользователь даёт любой отзыв.
  - PR открывается от имени приложения или от имени пользователя.
  - Агент учится шаблонам команды только по комментариям review владельца задачи.
  - Несколько пользователей в одном репозитории получают отдельные задачи.
- **Просмотр PR в сессии.** Панель Reviews показывает файлы, diffs и commits. Комментарии и merge делаются на GitHub [34].
- **GitLab** подключается через personal access token. Self-managed GitLab работает, если он доступен из интернета. Одна сессия может смешивать репозитории GitHub и GitLab [31][6]. Specs и GitLab появились в Web в июне 2026 [11].
- **Schedule** — раньше Automations; переименовано 2026-10-28 [32][17][118]:
  - Каждая задача по расписанию идёт в режиме Autonomous и открывает PR.
  - До 5 расписаний на задачу: каждый час, каждый день или cron, по UTC, не чаще раза в час.
  - Промпт — до 10 000 символов.
  - Каждый запуск — отдельная сессия.
  - По changelog функция вышла 2026-06-19 [11], пост в блоге — 2026-06-18 [118].
- **Sandbox** [33][74]:
  - Репозитории клонируются на сервере. Окружение берётся из вашего Dockerfile или из найденных настроек. DevFile и Dockerfile распознавались ещё в preview [33][74].
  - Доступ в интернет: только интеграции, общие зависимости, открытый или свой allowlist [33].
  - Переменные окружения и секреты; IAM-роль; Powers и MCP-серверы [33].
  - **Headless Chrome с Playwright MCP, agent-browser CLI и Chrome DevTools MCP** для проверки UI [33]. Playwright в sandbox — с июля 2026 [11].
  - Технология виртуализации (microVM или контейнер) не раскрыта (не подтверждено) [33].
- **Прочее** [28][17]: группы сессий; автоматические названия; проводник файлов; краткие пересказы сессий (session recaps); запасная модель; web search со ссылками на источники.
- **История.** Kiro autonomous agent вышел в preview 2025-12-02 [74]:
  - асинхронные sandbox, до 10 задач одновременно, PR в нескольких репозиториях, обучение на отзывах review;
  - недельные лимиты использования — единственный случай таких лимитов в истории Kiro [74][80];
  - уровни сети на задачу [74].
  - Потом он стал режимом Autonomous в Kiro Web [74][117]. Вывод команды при запуске Web: автономность должна быть частью основного продукта, а не отдельным продуктом [117].

### Kiro Crew — открытая рабочая среда для агентов (больше всего пересекается с worfy)

- **Что это.**
  - Вырос из внутреннего проекта Amazon «MeshClaw». По словам Kiro — 39 000+ внутренних пользователей и около 500 contributors [68].
  - Открыт 2026-08-04 [68]. Версия 0.12.2 вышла 2026-11-12 [70].
  - Архитектура: Gateway — локальный сервер на Python — и web-dashboard на `localhost:5476` [65][66][97]. Есть desktop-обёртка на Electron. Источники расходятся в том, что в неё входит: страница Crew и инструкция по установке говорят о Kiro CLI в комплекте [8][65], а changelog Crew 0.11 (2026-10-30) — что desktop-приложение больше не включает Kiro CLI и поставляет проверенную сборку harness Kiro Agent [67].
  - Интерфейсы: CLI `kirocrew` и чат-каналы Slack, Teams, Discord, Telegram, Webex, WeChat, WeCom [66]. С версии 0.4 — ещё WhatsApp, iMessage и Feishu [67].
- **Агентные backends («harnesses»)** [57][58]:
  - По changelog Crew 0.11 (2026-10-30) новые сессии по умолчанию идут на harness Kiro Agent, если пользователь не выбрал другой; Kiro CLI тоже доступен [67]. Источники расходятся: страница Agent backends (обновлена 2026-11-11) всё ещё называет backend по умолчанию Kiro CLI, а встроенный движок Kiro Agent — опцией, выключенной по умолчанию [57].
  - Экспериментальные: **Claude Code, Codex**, OpenCode, Pi, goose, DeepSeek Harness [57]. С 0.12 — ещё Strands и GitHub Copilot CLI [58]; в таблице на странице Agent backends их пока нет [57].
  - История. В сентябре 2026 (Crew 0.6) можно было выбрать Claude Code, Codex или KAS (preview; источник не расшифровывает сокращение) [67]. Claude Code стал рабочим backend в сентябре 2026 [141: discussion 7723 — Claude Code как backend]. С октября 2026 по умолчанию работает harness Kiro Agent [67].
  - Оговорки [57]. Инструмент, заранее разрешённый в настройках самого Claude Code, проходит мимо одобрения и audit log Crew. Codex не запускается, пока sandbox Crew выключен.
- **Task Runner: выполнение spec без человека, рассчитан на 10+ часов** [54]:
  - Цикл: Markdown-spec → LLM разбивает его на задачи → каждый шаг в новой сессии → тесты → **отдельная сессия-reviewer читает настоящий `git diff HEAD~1`** → commit или откат и повтор.
  - Бюджеты: 3 повтора на шаг, 2 восстановления после падения процесса, 2 перепланирования, не больше 50 задач всего.
  - Обнаружение зацикливания: 3 одинаковые ошибки подряд — шаг получает статус FAILED с пометкой «Loop detected».
  - Параллельность: до 3 запусков одновременно; независимые задачи идут пачками по 3 [54]. В коде размер пачки считается от доступной памяти, а 3 — запасное значение [100: `taskrunner_parts/run_inputs.py`].
  - Git: у каждого запуска своя ветка в git worktree [54].
  - Одобрения: gates `force_approval` блокируют даже при полном автоодобрении. Автоодобрение на запуск включается максимум на 6 часов, жёсткий потолок — 24 часа [54].
  - Watchdog простоя: предупреждение через 60 минут без активности, сброс сессии через 2 часа.
  - Уведомления: по одному на событие — шаг прошёл или упал, перепланирование, простой, выученный урок, запуск завершён.
  - Восстановление: после падения процесса незавершённые шаги сверяются. Запуски без координации через git открываются в состоянии Paused с пометкой «unknown side-effect» [54].
- **Workflows и monitor loops Crew** — своя система, не workflows Kiro [55]:
  - Workflows Crew — скрипты на Python. Шаблоны: fan-out, pipeline, «judge-and-verify».
  - Встроенный **conductor** делит цель на элементы, запускает сессию на каждый, проверяет критерии приёмки и планирует следующий раунд. Он продолжает работу после закрытия вкладок.
  - **`monitor_watch`** опрашивает провайдера PR и не тратит ход агента, пока ничего не меняется. Провайдеры: GitHub (gh), GitLab (glab), Azure DevOps Services, Bitbucket Cloud. Будит агента на комментарии и вопросы review, а не только на упавшие checks. Завершается на merge или закрытии PR.
  - У циклов бывают правила пробуждения и тишины. «Quiet verdict» — проверка, где ничего не изменилось, — не тратит ход модели [55][67].
  - Предел работы цикла — 7 дней по умолчанию, до 30.
  - Один ход чата может длиться до 4 часов [55][67].
- **Bots и Ultra Mode** [63][58]:
  - **Bot** — долгоживущий именованный агент. У каждого: свой thread, личная память, workspace, цели с вехами, проверки раз в день, неделю или месяц, расписания и вкладка на dashboard [63].
  - Heartbeat бота — раз в 30 минут, 1, 2 или 4 часа [63].
  - Bot — это **conductor**, который раздаёт работу **workers**. С версии 0.12 у каждого бота свой git worktree и своя ветка. Журнал работы (work ledger) показывает одобрения и вопросы workers [63][58].
  - Изменение модели, прав или целей бота требует одобрения [63].
  - По словам вендора, bots переводят человека с координации задач на постановку направления [63].
  - **Ultra Mode** (preview) раздаёт задачи чата рабочим чатам и показывает их на доске Board. Remote dispatch запускает эти задачи на подключённых удалённых машинах [58].
  - **Crew Mode** — агент вне отдельной сессии. Он делит работу, раздаёт её, обходит работающие сессии, принимает результаты и выстраивает их порядок [97][69].
- **Вид Sessions** [56]:
  - Conductor view показывает workers под их conductor.
  - `session_ledger_record` хранит цель, фазу, следующий шаг и отброшенные подходы. Эта запись переживает compaction.
  - Steer или Queue во время хода. Broadcast — одно сообщение во много сессий. `session_send` передаёт сообщения между сессиями.
  - Режимы памяти: Persistent, Incognito, Temporary.
- **Запуск без человека** [60]:
  - **Cron jobs.** Таймаут на задачу — от 30 минут (по умолчанию) до 24 часов. Автопауза после N сбоев (`--auto-pause-after N`); throttling повторяется и в счёт сбоев не идёт. Есть jitter, постоянные или новые сессии и режим «minimal context». Пропущенные запуски *не* выполняются задним числом. Skill `cron-cost-optimize` предлагает более дешёвый способ выполнения.
  - **Heartbeats** проверяются раз в 60 с по файлу `HEARTBEAT.md` и сообщают только об изменениях. Это отдельный механизм от heartbeat ботов.
  - **Webhooks с аутентификацией:** до 6 одновременно, таймаут по умолчанию 10 минут.
  - **Autonudge** — таймер повторной проверки внутри сессии.
  - Для круглосуточной работы Crew ставится как служба systemd или launchd. Служба перезапускается при падении и стартует при загрузке [65].
- **Наблюдаемость и стоимость** [59][58][56]:
  - Crew log — журнал событий по чату с вычищенными секретами. Он разложен на Status, Usage, Timeline, Tools и Approvals [59].
  - Надёжная очередь задач переживает перезапуск [59].
  - Вид ресурсов ограничивает число одновременных агентов по памяти и CPU хоста [59].
  - Вкладка **Usage** — оценка токенов и кредиты по дням [59].
  - **Прогноз кредитов** говорит, хватит ли кредитов до сброса. Если не хватит — в какой день они кончатся при текущем темпе [59].
  - Уведомления: desktop; push в установленное web-приложение, даже когда Crew закрыт (0.12); оповещение, когда запрос одобрения истёк без ответа [58].
  - Краткие сводки сессий — по желанию [56].
- **Браузер и управление компьютером** [61][58]:
  - Встроенная панель Browser. Пользователь может перехватить управление для CAPTCHA, 2FA или решения, которое должен принять человек.
  - Режим Annotate отправляет агенту пронумерованные заметки к элементам страницы и скриншот.
  - Агент может управлять вашим Chrome, Edge или собственным Chromium Kiro.
  - Окно входа (sign-in sheet) вводит секреты в страницу так, что агент их не видит.
  - Computer Use управляет native-приложениями через accessibility-слой на macOS и Windows. Поля паролей не читаются.
- **Удалённые машины** [62][67][58]:
  - Удалённые crews подключаются по SSH, через AWS SSM (Systems Manager) или Fargate. У задачи Fargate время жизни 6 часов, задач — не больше 10.
  - Один dashboard показывает сессии по машинам со значками online/offline. Обе стороны должны работать на одной версии [62].
  - Цепочки подключений — до двух переходов.
  - Shared Crew (preview) открывает машину другим людям через Tailscale [58].
- **Безопасность: «8 layers»** [64][67]:
  1. Owner lock — привязка к владельцу.
  2. Запрещённые команды — 137 встроенных шаблонов.
  3. Governance ceiling — верхняя граница прав, заданная политикой.
  4. Защита чувствительных путей.
  5. Одобрение инструментов: Automatic (по умолчанию), Interactive, доверие на команду или на инструмент, Autopilot.
  6. Проверка входных данных.
  7. OS sandbox: Seatbelt на macOS, namespaces на Linux. При сбое sandbox работа блокируется (fail-closed).
  8. Удаление учётных данных из вывода.
  - Плюс подписанный audit log и зашифрованное хранилище секретов [64].
- **Память и знания** [66]:
  - Шесть слоёв памяти, включая уроки из исправлений пользователя («lessons»), с затуханием.
  - Knowledge Library с векторным и полнотекстовым поиском. Можно подключить Amazon Bedrock Knowledge Base [58].
  - Снимок и восстановление состояния.
  - Каждая задача Task Runner начинается с новой сессии, в которую подставлена память [54].

## Принципы и подходы

### Как Kiro описывает себя

- **Самоописание менялось.**
  - Описание репозитория на GitHub до сих пор называет Kiro «agentic IDE» [71].
  - README называет его «agentic AI development platform» для IDE, CLI, Web, Mobile и Crew [71].
  - FAQ называет его «agentic AI engineering system» [3]. Так же AWS продвигает продукт: пять клиентов поверх одного agent harness [1][4][9].
  - Заголовок главной страницы — «Ship quality software». Её разделы — об оркестровке множества агентов, которые работают часами, о передаче работы и о блоках для автоматической поставки ПО [1].
- **Главная страница описывает pipeline, а не только IDE** [1]:
  - Триггеры: heartbeat, расписания, разбор падений CI.
  - Разбор (triage): мелкая работа строится сразу. Для крупной пишется spec, и её получает человек.
  - Сборка идёт в новом изолированном sandbox. К результату прикладываются доказательства.
  - Review — property tests и состязательные review-агенты, затем ожидание человека.
  - Workflows нужны, чтобы агент не мог пропустить упавший тест.
  - Общий цикл из шести стадий: сигналы → триггеры → разбор → сборка → review → production [1].
- **«Frontier agents».** Amazon относит Kiro autonomous agent к классу автономных агентов, которые работают часами или днями без участия человека [110][74].
- **Доверие как суть продукта.** Пересказ панели на AAAI-26 в блоге Kiro описывает доверие как основу продукта. Работа человека в этой картине — проверять и поручать [115].

### Исходная идея (июль–ноябрь 2025)

- **Проблема.** У прототипов, собранных по промптам, нет записанных допущений, требований и дизайна. Kiro обещал сохранить скорость «vibe coding» — разработки по промптам без плана — и добавить структуру, которой хватит для production [72]. Пост к годовщине повторяет исходное убеждение: разработчики заслуживают большего, чем vibe coding [121].
- **Три понятия при запуске** [72]:
  - Specs: user stories с критериями приёмки в EARS, затем документ дизайна, затем задачи. Задачи упорядочены по зависимостям, связаны с требованиями и синхронизируются с кодом.
  - Hooks: фоновые автоматизации на сохранение, создание и удаление файлов.
  - Steering: постоянные правила проекта.
- **Долгосрочная цель** — решать задачи координации команды: согласование дизайна, противоречивые требования, технический долг, строгость review, потеря знаний при уходе инженеров [72].
- **Эссе Marc Brooker** [103]:
  - Языки программирования описывают, *как* делать. Агенты наконец позволяют описать, *что* нужно.
  - Spec — версионируемый и читаемый человеком «super prompt». По нему агенты проверяют свою работу.
  - Изменение сначала вносится в spec. Затем агент обновляет код.
  - Brooker ставит это в ряд привычек Amazon всё записывать: working-backwards документы, design docs и формальные методы (TLA+, P).
- **Цена отражала философию.** Первая платная схема считала «spec requests» и «vibe requests» отдельно. Планы подталкивали к работе через spec. Обоснование — исследования, по которым исправить дефект при разработке в 5–7 раз дороже, чем поймать его на планировании [104].
- **Позиция при GA (2025-11-17)** [73][106]:
  - Сначала план.
  - Затем проверка «spec correctness»: вывести свойства из требований и проверить их через PBT.
  - PBT подаётся как свидетельство корректности, а не доказательство.
  - При контрпримере Kiro спрашивает человека, где ошибка: в коде, в spec или в тесте.

### Заявленные принципы, которые отличают подход

1. **Намерение до кода, проверка после.**
   - Specs фиксируют намерение. PBT, анализ требований и проверка неизменного поведения в Bugfix проверяют результат [73][106][113][86].
   - Раздел главной страницы 2026 года о проверке говорит то же самое [1].
   - При этом Kiro признаёт, что всё заранее описать нельзя. Поэтому spec можно начинать с любой точки: с требований, с дизайна или с бага [113].
2. **Наследие automated reasoning применяется к самому продукту.**
   - Анализ требований через SMT-solver [86].
   - «Spec hardening» по каталогу CWE как Power. Вендор называет его контролем на входе, а не границей безопасности [128].
   - Доказательства на Lean 4 для 26 функций harness: 70 из 96 свойств доказаны, 18 опровергнуты и воспроизведены как настоящие баги, около 98 тысяч differential tests [99].
3. **Один harness — много клиентов.** Принципы из документации [82][83][123]:
   - Между агентом и клиентом проходит граница протокола.
   - Конфигурация хранится вместе с репозиторием.
   - Безопасность заложена в структуру.
   - Функция строится один раз в harness и попадает во все клиенты.
   - Каждый клиент сделан под своё устройство.
   - Два продуктовых принципа: обслуживать жизненный цикл поставки ПО, а не общую помощь; работать там, где уже работают разработчики.
4. **Решение принимает детерминированный код, модели только предлагают.**
   - Цикл самоулучшения `kiro-trace` формулирует это прямо: модели предлагают изменения, а принимает или отклоняет их детерминированный код [93].
   - Другие его правила: тот, кто предлагает, отделён от того, кто судит. Решение принимается по разнице с повторно запущенным контрольным вариантом. Каждое подтверждённое исправление становится постоянной регрессионной проверкой [93].
   - Главная страница обещает детерминированные workflows с изолированными шагами. Они не дают модели срезать путь, поэтому агент не может пропустить упавший тест [1].
5. **Доказательство — критерий завершения** [12]:
   - Каждый шаблон workflow называет своё доказательство: отчёт-артефакт; утверждённые дизайн, план и проверки; воспроизводимый тест или машиночитаемый результат; состояние review в PR, проверки и готовность к merge.
   - На схеме примера gate выпускает дальше при VERIFIED или возвращает к реализации, не больше 3 раз.
   - Документация требует конечный `maxIterations` у каждого цикла.
6. **Никто не оценивает сам себя.**
   - В Auto рабочая модель не оценивает свой прогресс. Это делает отдельная модель [48].
   - Reviewer в workflows работают в новых сессиях и не наследуют рассуждения автора кода [84].
   - В «software factory» Crew reviewer разделены по роли и по семейству моделей. Ни одна модель не проверяет код своего же семейства [98]. «Software factory» — так команда Crew называет свой поток автоматической разработки.
7. **Экономия внимания и токенов.**
   - Ожидание не тратит ходы модели [12]. «Quiet checks» в Crew тоже [67].
   - Powers и MCP tool search загружают инструменты только по необходимости [111][11].
   - Workflows держат вывод инструментов вне основного чата [84].
8. **Объём работы и дизайн остаются за человеком.**
   - Агенты workflows спрашивают перед изменениями дизайна, объёма или UX [84].
   - Главная страница: мелкое строится сразу, крупное уходит в spec для человека [1].
   - Kiro никогда не сливает свои PR и не обходит защиту веток [126].
   - Bots Crew переводят человека с координации задач на постановку направления [63].
9. **Многоуровневая защита вместо усталости от вопросов** [22]:
   - Данные вендора: Kiro спрашивал разрешение перед 15.8% вызовов инструментов в CLI. Пользователи одобряли 97.1% таких вопросов. 13.4% сессий шли с trust-all.
   - Вывод вендора: вопросы в основном приучали людей нажимать «да».
   - Approve for me добавляет эффект evaluate с самым низким приоритетом. Решает LLM-проверка, сейчас на модели Anthropic.
   - Около 70% действий решают правила, около 30% уходят на проверку. Из проверенных около 97% решены без человека, около 2% ушли к человеку, меньше 1% заблокированы. Медианное время проверки — меньше секунды.
   - После трёх шагов подряд с блокировкой Kiro снова спрашивает человека.
   - Вендор советует сочетать режим с OS sandbox.
10. **Сначала pipelines, потом оркестраторы; правила обеспечивает host, а не промпт.** Принципы из постов о «software factory» Crew [69][98]:
    - Координация между агентами должна быть явной и надёжно сохранённой, а не жить в контексте модели.
    - Агенты не должны иметь возможности править свой audit trail.
    - Governance нужен с первого дня.
    - Уверенность даёт автоматическое тестирование каждого изменения, а не человек, который читает каждую строку.
    - Блокирующая находка review должна указать место, доказательство, условие срабатывания и последствие. Иначе она считается советом.
    - Код PR из fork запускается без секретов, а правила review загружаются из `main`. Так PR не может сам написать себе проверяющего.
11. **Открытое управление Crew** [131][132]: восемь принципов, публичные решения, RFC для крупных изменений и обещание не закрывать проект. Подробности — в разделе «Функции → Kiro Crew».

### Ключевые понятия

- **Spec** — три Markdown-файла: требования, дизайн, задачи [18].
- **Wave** — группа задач spec без взаимных зависимостей, которая идёт параллельно [18][20].
- **Steering** — постоянные файлы с правилами проекта для контекста агента [45].
- **Hooks** — автоматизации на события агента и файлов [44].
- **Powers** — пакет инструкции, MCP-сервера, steering и hooks, который включается по ключевым словам [111].
- **Auto** — маршрутизатор моделей с каскадом от дешёвой модели к сильной [48].
- **Agent harness и ACP** — один процесс агента и протокол, через который к нему подключаются клиенты [82][83]. Права построены на capabilities и Cedar — языке политик доступа [83][82].
- **Cloud session и cloud configuration** — сессия в управляемом sandbox, которая живёт без клиента, и конфигурация `.kiro`, синхронизированная с облаком [125].
- **Workflow и recipe** — граф шагов агента и его сохранённая версия [12].
- **Approve for me** — режим прав, где не покрытые правилами действия решает модель-классификатор [22].
- **Local command sandbox** — граница уровня ОС для shell-команд агента [43][11].
- **Memory** — локальная память агента, по умолчанию выключена [91].
- **Checkpoints и rewind** — откат файлов и ответвление разговора [41][73].
- **Markdown Review** — комментарии к Markdown, которые уходят агенту одним пакетом [18][11].
- **Agent Focus** — экспериментальная раскладка IDE для управления параллельными агентами [119].
- **Kiro Crew** — открытая среда: Gateway (локальный сервер), Bots (долгоживущие агенты со своей памятью и правами), heartbeats и watches (проверки по расписанию), schedules (повторяющиеся задачи), lessons (исправления пользователя, превращённые в долговременную память), Crew Mode (агент, который делит и раздаёт работу), remote crews (Crew на других машинах) [97][63][69][67].

### Как Kiro используют внутри AWS (dogfooding)

- **Команда Kiro Crew (три инженера на полной ставке)** [69][98]:
  - Слили 1 000 PR за 7 дней, больше 120 в день. Каждый PR прошёл CI и review.
  - У Crew ещё около 500 contributors из сообщества.
  - Команда описывает пять стадий работы с агентами: одна сессия → много сессий вручную → память, dashboard, cron и workflows → agent pipeline → Crew Mode (агент берёт на себя обязанности человека, когда сессий становится около 50; до этого один человек ведёт около 20 сессий).
  - Стабильность: одна проверка «PR Readiness» сводит 80+ checks в один вердикт. Каждый PR несёт запись review. Тестовые среды прикладывают к PR скриншоты и видео. Покрытие тестами — больше 90%.
- **`AUTOSDE.yaml` в репозитории Crew** — блокирующие правила review, каждое основано на реальном инциденте. Их применяют reviewer PR на Claude и Codex. Набор взят из внутреннего набора правил Amazon, внутренние ссылки удалены [134].
- **Kiro построен с помощью workflows.** Большая часть среды выполнения workflows и интеграции Kiro Web сделана через workflows: тысячи запусков, обычно по 5–10 шагов [84].
- **Агент разбора инцидентов на Kiro CLI.** Около 250 расследований в месяц без человека, медиана — 13.6 минуты. 96.9% вызовов инструментов — только чтение. Закрывать тикеты могут только люди [124].
- **AWS Automated Reasoning Group на Kani и CBMC** (своих открытых verifiers). В ноябре–декабре 2025 Kiro открыл PR по 87 issues, против 94 issues, закрытых за предыдущие 22 месяца. Всего слито 183 PR от Kiro, о регрессиях не сообщалось [126].

## Как это устроено внутри

Ядро Kiro (harness, IDE, CLI, Web) — закрытый код. Описание ниже для него построено по документации и блогу. Kiro Crew — открытый код; он прочитан на commit 51349e1 от 2026-11-13 [100]. Ссылки на файлы Crew собраны в конце раздела.

### Архитектура

- **Один процесс harness.** Agent harness работает как отдельный серверный процесс, а не как библиотека внутри каждого клиента [82][83].
- **Он заменил три harness** (пост от 2026-08-03): на TypeScript в IDE, на Rust в CLI и на Python в Web [83].
- **Клиенты говорят с ним по ACP** (версия 1.0 — июнь 2026) с расширениями Kiro [83]:

### Цикл агента

- **Один ход — шесть шагов** [82]:
  1. Собрать контекст: промпт, история, steering-файлы и hooks Prompt Submit.
  2. Модель планирует. Auto выбирает модель для запроса.
  3. Проверить права (deny > ask > allow), `.kiroignore` и hooks PreToolUse.
  4. Запустить инструменты, MCP-серверы, Powers и sub-agents. Затем — hooks PostToolUse.
  5. Вернуть результаты модели и повторить. В конце срабатывают hooks Agent Stop.
  6. Сжать контекст (compaction), чтобы он оставался в пределе.
- **События hooks** [44]: Prompt Submit, Agent Stop, Session Start/End, Pre/Post Compaction, Pre/Post Tool Use, File Create/Save/Delete, Pre/Post Task Execution (для задач spec), Manual и MCP.
- **Коды выхода hooks** [44]:
  - Код 0 добавляет stdout в контекст.
  - Код 2 блокирует PreToolUse и Pre Task Execution.
  - На Agent Stop код 1 или `decision: "block"` заставляет агента сделать ещё один ход.
  - Таймаут hook по умолчанию — 60 с в IDE и 30 с в CLI V3.
- **`/goal`** в CLI — цикл «план → реализация → проверка». По умолчанию 5 итераций; `--max` поднимает предел [50].
- **Headless-запуски CLI** [23][96]:
  - Любой «ask» превращается в deny [23].
  - Код выхода 3 — MCP-сервер не стартовал при `--require-mcp-startup`. Код 4 — запрошенный агент не найден [96].

### Планирование и декомпозиция

- **Specs** лежат в `.kiro/specs/<имя>/`: `requirements.md` (или `bugfix.md`), `design.md`, `tasks.md` [18].
- **Run all tasks** [18][19][85]:
  - Строит граф зависимостей из `tasks.md` и делит задачи на волны [18].
  - В волну 1 попадают задачи без зависимостей. Волны идут одна за другой, задачи внутри волны — одновременно [18].
  - В IDE 0.12 (2026-05-06) каждая задача волны получила свой изолированный контекст. Это до 4x быстрее, если независимых задач четыре и больше [19].
  - Тот же релиз добавил Quick Plan и Analyze Requirements [19].
  - Отдельные рабочие деревья или блокировки файлов для задач волны не описаны (не подтверждено) [18][19].
  - Kiro держал функцию, пока не появились три опоры: property-based tests, dev servers с диагностикой language server и sub-agents (пост от 2026-01-16) [85].
- **Property-based tests** [21] проверяют сгенерированные входы на заявленное свойство:
  - только IDE;
  - свойства берутся из требований в стиле EARS;
  - упавшие входы сокращаются до минимальных контрпримеров.
- **Analyze Requirements** (2026-05-12) [86]:
  - LLM переводит уточнённые требования в SMT-LIB — входной формат логических solver.
  - Затем их проверяет движок automated reasoning.
  - Неоднозначность видна там, где независимые выборки LLM формализуют одно требование по-разному.
  - Каждая находка становится вопросом пользователю с двумя вариантами.
- **Sub-agents** [46]:
  - У каждого sub-agent свой контекст. Общие — steering, MCP-серверы, workspace и права.
  - Главный агент заранее планирует весь граф зависимостей. Во время выполнения граф не меняется.
  - Циклы review задаются целевым этапом, строкой-триггером не короче 4 символов и `max_iterations` от 1 до 10.
  - Цикл на себя и взаимные циклы отклоняются.
  - Если workflows включены, передача задачи custom agent становится фоновым запуском workflow.
- **Autonomous mode в Web** [29][74]:
  - Пишет требования и критерии приёмки, запускает специализированных sub-agents и открывает PR [29].
  - Задача, которой нужен ввод, переходит в «Needs attention» [29].
  - На запуске (2025-12-02) давал до 10 задач одновременно, sub-agents для исследования, кода и проверки, распознавание DevFile и Dockerfile и уровни сети на задачу [74].

### Ожидание без токенов

- **Наблюдение `github-pr`** опрашивает GitHub и не тратит ходы модели [13]:
  - `pollIntervalSec` — по умолчанию 60, минимум 30. Другие настройки: `idleTimeoutSec`, `ignoreAuthors`, `includeOwnActivity`.
  - Данные пробуждения содержат:
    - новые комментарии, review и inline-комментарии;
    - `headSha`, `mergeable` и `mergeStateStatus`;
    - `newFailedChecks` и число прошедших и ожидающих checks.
  - За один опрос приходит не больше 10 элементов. Упавшие checks в этот лимит не входят.
  - Будит агента при merge-конфликте (CLI 2.33+) и при упавшем check.
  - Упавший check GitHub Actions придерживается, пока не закончится весь run.
  - Доставка — «хотя бы один раз» (at least once).
- **Наблюдение `command`** запускает программу пользователя на каждом опросе [13]:
  - Программа получает JSON на stdin: `{cursor, config, workspacePath, additionalDirectories}`.
  - Она печатает JSON на stdout: `outcome` (idle, new-activity или terminal-state), обязательный `cursor`, по желанию `payload` и `targetId`.
  - Коды выхода 2, 126 и 127 проваливают узел. Любой другой ненулевой код считается опросом без событий.
  - Минимальный интервал опроса — 10 с.
  - Программа работает под политикой прав и sandbox сессии, которая запустила workflow.
  - Пока эта сессия не загружена, наблюдение стоит на паузе с `ParentSessionUnavailable`.
- **Crew** [55][100]:
  - `monitor_watch` следит за PR на GitHub, GitLab, Azure DevOps и Bitbucket Cloud без ходов агента [55].
  - Контроллер наблюдения сначала проверяет состояние и обрезает текст пробуждения до 4 096 символов [100: `monitoring/controller.py:39`].
  - `autonudge_service/gate.py` решает, стоит ли очередной такт цикла хода модели. Если результат неясен, ход тратится [100].

### Параллельность и координация

- **Внутри одной сессии:**
  - задачи волны идут одновременно [19];
  - узлы `parallel` в workflows объединяются по правилу `joinPolicy` [13];
  - sub-agents идут по графу зависимостей, зафиксированному заранее [46].
- **Между сессиями:**
  - Kiro Web держит до 10 облачных сессий одновременно; лишние задачи ждут в статусе «Queued» [27][28].
  - Экспериментальный Focus Mode в IDE показывает параллельные сессии со значками статуса, карточками внимания и панелью под колокольчиком [38].
- **Task Runner в Crew:**
  - Не больше 3 одновременных запусков [100: `taskrunner_parts/run_lifecycle.py:65`].
  - Шаги идут параллельными пачками через `asyncio.gather` [54].
  - Размер пачки считается от доступной памяти; 3 — запасное значение [100: `taskrunner_parts/run_inputs.py`].
- **Очереди с честным разделением в Crew.** Диспетчер использует smooth weighted round-robin — поочерёдный выбор с весами. Cron, hooks и heartbeat делят одну очередь «system». В Shared Crew у каждого человека своя очередь [100: `taskq/lanes.py`].
- **Хранилище задач Crew** — строки SQLite с атомарным захватом, арендой (lease) и fencing по номеру поколения. Так два диспетчера не могут взять одну задачу [100: `taskq/store.py`]. Это свойство доказано на Lean [99].
- **Conductors в Crew:**
  - Встроенный conductor делит цель на элементы и запускает сессию на каждый. Он проверяет критерии приёмки и планирует следующий раунд [55].
  - `session_send` передаёт сообщения между сессиями [56].
  - Bot — это conductor плюс workers; у каждого своя память и workspace [63].
  - С Crew 0.12 (2026-11-05) у каждого бота ещё и свой git worktree и ветка [58][63].
  - Heartbeat бота — раз в 30 минут, 1, 2 или 4 часа [63].
  - `WaveDigestCoordinator` придерживает сводку по волне, пока не закончат все участники пачки [100: `subagent_manager/waves.py:25`].
- **Несколько машин** [62]:
  - Удалённые crews подключаются по SSH, через AWS SSM или Fargate.
  - Задачи Fargate живут по умолчанию 6 часов; задач — не больше 10.
  - Один hub-dashboard показывает все машины. Обе стороны должны работать на одной версии.
- **Масштаб по отчёту команды Kiro** (2026-09-18) [69]:
  - 3 инженера на полный день и почти 500 contributors из сообщества. Один из авторов держит 6–10 машин, на них одновременно идут 30–50 сессий.
  - Работа шла через очередь: разбор → реализация → review → merge.
  - Команда называет четыре задачи управления: координацию, память, права и audit trail. Сама координация стоит денег.

### Изоляция

- **Workflows ядра работу не изолируют.** Документация пишет это прямо: workflows не изолируют ветки git и не создают worktree [15].
  - Файлы recipe тоже не разделяют пути вывода, ветки или worktree. Параллельным запускам нужны разные значения `run_dir` и свои worktree [15].
  - В IDE Kiro говорит workflow, который меняет файлы, работать в ветке, выбранной при старте. Если workflow использует worktree, Kiro просит создать его от этой ветки и в конце сделать rebase на неё [12].
  - Это инструкция агенту, а не механизм, который что-то обеспечивает [12].
  - Страница шаблонов предлагает заготовку с входами `worktree_path` и `run_id` и циклом `validate-gate` [14].
- **Локальный sandbox для команд** (IDE 1.3+, CLI 2.31+ V3; октябрь 2026) [43][94]:
  - По умолчанию выключен. Оборачивает только команды; сам harness остаётся снаружи.
  - macOS — Seatbelt (`sandbox-exec`). Linux — bubblewrap и socat. Windows — AppContainer после разовой настройки с правами администратора.
  - Режимы сети: DEFAULT_BLOCKED, COMMON_DEPENDENCIES, DEFAULT_ALLOWED.
  - `/autonomous on` включает sandbox с закрытой сетью. Если защиту нельзя подтвердить, режим не стартует или выключается.
  - Headless-флаг `--sandbox` при сбое блокирует работу (fail-closed).
- **Облачные sandbox** [27][33]:
  - Каждая сессия или задача получает изолированный sandbox, в котором работает тот же harness. Репозитории клонируются на сервере [27].
  - В каждом sandbox есть headless Chrome с Playwright MCP, agent-browser CLI и Chrome DevTools MCP [33].
  - Уровни сети: только подключения, общие зависимости или открытый интернет, плюс allowlist [33].
  - Технология виртуализации (microVM или контейнер) не раскрыта (не подтверждено).
- **Crew** [54][64][100]:
  - Каждый запуск Task Runner получает worktree на ветке `kirocrew/task/<id>` [54].
  - В `src/kiro_crew/git_coord.py` [100]:
    - `init_workspace` выполняет `git worktree add <wt> -b <branch>` (строка 84);
    - `commit_step` делает один commit на шаг (строка 123);
    - `revert_step` выполняет `reset --hard HEAD~1` (строка 200);
    - очистка выполняет `worktree remove --force` (строка 257).
  - OS sandbox Crew использует namespaces Linux или Seatbelt. Режимы — auto, strict или off; при сбое работа блокируется [64].

### Состояние и память

- **Состояние workflow** [15]:
  - Статусы запуска: running, paused, completed, failed и aborted. Запуск встаёт на паузу, когда нужен ввод, на границе узла или на пределе итераций.
  - Узлы могут быть ещё pending или skipped.
  - На каждой границе узла Kiro сохраняет статус узлов, выводы, артефакты, прогресс циклов, cursors наблюдений и сессии шагов.
  - Прерванный шаг продолжает работу в своей прежней сессии.
- **Сессии:**
  - CLI хранит сессии в одной базе SQLite в `~/.kiro/`, по папке проекта [95].
  - Сохраняет после каждого хода и допускает один процесс за раз. `/chat save` пишет zip [95].
  - Облачные сессии живут в хранилище на сервере; клиенты подключаются и отключаются [27].
  - Облачная сессия истекает через 90 дней после последней активности; открытие сессии или новое сообщение начинают отсчёт заново. Остановленный sandbox запускается снова, когда сессию открывают [28].
  - Checkpoints в IDE снимают файлы, изменённые встроенными инструментами, но не изменения через bash или MCP. `/rewind` в CLI делает ответвление разговора [41].
- **Steering** [45]: файлы в `.kiro/steering`; режимы always, fileMatch, manual и auto; поддерживается `AGENTS.md`, в том числе в подпапках.
- **Memory** [42][91] (2026-10-20):
  - Каждая запись — заголовок, описание и содержание.
  - Записи хранятся локально, отдельно для каждого аккаунта, и общие для IDE и CLI на одной машине. Область — глобально или один репозиторий.
  - По умолчанию выключена. Нужны IDE 1.4.0+ или CLI 2.29+ (V3).
  - Sub-agents память читают, но не пишут. Поддержку в Web обещают позже.
- **Compaction** [92][93]:
  - Запускается сама около предела контекста. Сохраняет структурированную сводку и последние сообщения целиком [92].
  - Настройки CLI: `compaction.autoCompactionThreshold` — по умолчанию 80, `excludeMessages` — по умолчанию 2 [92].
  - Hooks PreCompact и PostCompact — в CLI 3.1+ [92].
  - Работа Kiro по трассировке подняла измеренную оценку сохранения контекста с 0.82 до 0.92 [93]. Для этого сделали три изменения:
    - убрали сырой список старых сообщений пользователя;
    - перешли на короткий фиксированный шаблон;
    - добавили фиксированную подсказку для продолжения работы.
- **Crew:**
  - Каждая задача Task Runner начинается с новой сессии, в которую подставлена память [54].
  - У каждого бота своя память [63].
  - `session_ledger_record` хранит цель, фазу, следующий шаг и отброшенные подходы сквозь compaction [56].
  - Очередь задач и координатор зависимостей сохраняют своё состояние и переживают перезапуск [59][100].

### Проверка качества

- **В продукте:**
  - Property-based tests и Analyze Requirements [21][86].
  - Циклы останавливаются по файлам и выражениям, а не по тексту ответа [13][14].
  - Два reviewer на моделях разных семейств передают находки aggregator. Затем результат сверяется с требованиями [14][84].
  - Hook Pre Task Execution может заблокировать задачу spec. Hook Agent Stop может заставить агента сделать ещё один ход [44].
  - Task Runner в Crew делает commit, только если тесты прошли [54].
  - Отдельная сессия-reviewer в Crew читает `git diff HEAD~1`. Если review не прошёл, шаг откатывается и повторяется до 3 раз; затем задача перепланируется [54].
- **Трассировка для самоулучшения — «kiro-trace»** (2026-10-20) [93]:
  - Детерминированный gate для кода работает в три стадии: отбор, проверка на регрессии, подтверждение.
  - Набор эталонных агентов показывает поведение, которого у Kiro нет.
  - За первую неделю система открыла 8 PR, 7 из них слиты.
  - Урезанный профиль инструментов и промптов набрал 82.4% против 77.5% pass@1 на Terminal-Bench 2.1, примерно за треть токенов. В продукт он пока не вышел.
- **Как команда Kiro выпускает Crew** (2026-10-26) [98]:
  - Одна проверка «PR Readiness» сводит все линии checks в один результат: всё запустилось и прошло.
  - Skill `prepare-pr` доводит PR до зелёного состояния.
  - Находки разделены на уровни важности. Блокирующая находка должна указать место, процитировать доказательство и назвать условие срабатывания и последствие.
  - Reviewer разделены по роли и по семейству моделей.
  - Изменения простых уровней сливаются автоматически.
  - CI проверяет, что описание PR соответствует коду.
  - Первым идёт быстрый gate.
  - Review перенесли в AWS CodeCommit из-за лимитов запросов GitHub.
  - Проверки соответствия идут каждый час, проверки безопасности — каждый день.
- **Skill `prepare-pr` в репозитории** [100: `builtin_skills/kirocrew-dev/kirocrew-prepare-pr/SKILL.md`]:
  - Агент сливает PR только через `gh pr merge --auto`.
  - «PR Readiness» — единственная обязательная проверка.
  - PR готов к review, когда выполнено всё сразу:
    - `pr_status.py` возвращает 0;
    - PR можно слить;
    - `green_age.py` возвращает 0. Код 30 значит, что зелёный результат относится к старой base-ветке;
    - в PR один чистый commit;
    - на каждое замечание есть ответ.
- **CI-workflows репозитория KiroCrew** включают pr-readiness, fast-gate, claude-review, codex-review, design-review, first-principles-review, ux-review, security-scope-review, merge-queue-readiness, main-red-watch и gui-user-test [100].

### Восстановление после сбоев

- **Обрыв соединения в workflow** [15]:
  - Сессия шага повторяет запрос на месте до 24 часов, затем ставит запуск на паузу.
  - Первые 5 минут повтор идёт примерно раз в минуту, потом примерно раз в 2 минуты со случайным разбросом (jitter).
  - Успешный ход или явный Resume начинают новое 24-часовое окно.
  - Для ошибок 5xx, throttling и зависших потоков ответа — свои, более короткие повторы.
- **Другие временные ошибки** повторяются с backoff [88]. Значения таймаутов по умолчанию [88] (единицы измерения в источнике не указаны — не подтверждено):

  | Настройка | По умолчанию |
  |---|---|
  | `api.timeout` | 3600 |
  | `streamIdleSoftTimeout` | 60 |
  | `streamIdleHardTimeout` | 300 |
  | `subagentTimeout` | 3600 |

- **Отчёты пользователей** [140]:
  - В июле 2026 CLI сдавался после 3 повторов при throttling [140: #10516 — повторы обрываются после трёх; закрыт как дубликат #8905].
  - Отчёты о throttling за ноябрь 2026 всё ещё открыты [140: #12324, #12377, #12413 — ошибки rate limit при наличии кредитов].
- **Запасная модель** [47][87]:
  - Запасная модель вендора срабатывает только на отказы. Заданная пользователем — ещё и на недоступность модели.
  - При недоступности запасная модель отвечает только этот ход. После отказа разговор остаётся на запасной модели.
  - Выбор запасной модели в Kiro Web — с 2026-10-12 [87].
- **CLI** с версии 2.19 сам восстанавливает прерванный поток ответа [11].
- **Повторы в Crew** [100: `recovery/policy.py`]:
  - Одно расписание повторов для всех уровней, кроме фонового процесса Gateway (уровень L4): экспоненциальный рост с потолком и «equal jitter» — задержка выбирается из [raw/2, raw]. У L4 свой закреплённый backoff: база 1 с, потолок 60 с [100: `recovery/ladder.py:104-112`].
  - `retry_after` от сервера — нижняя граница задержки.
  - Счётчики попыток ведутся отдельно для каждой единицы работы и затухают через 600 с.
  - Базовая задержка — 2 с, потолок — 120 с (строки 50–51).
- **Лестница восстановления Crew** [100: `recovery/ladder.py`]:
  - Пять ступеней:
    1. вызов инструмента — 3 попытки;
    2. backend — 2 попытки;
    3. ACP runtime — 2 попытки;
    4. фоновый процесс Gateway — 1 попытка за 10 минут;
    5. сам Gateway — только вручную, с уведомлением.
  - Перегрузка на лестницу не попадает. При нагрузке система снижает пределы параллельности и перестаёт брать новую работу (строка 21).
  - Ошибка ёмкости `-32001` классифицируется вместе с `retry_after_secs`.
- **Координатор зависимостей Crew** [100: `taskq/dependency.py`]:
  - На каждую область зависимости — один координатор.
  - Если сервер прислал `retry_at`, координатор ждёт ровно до этого момента. Иначе — backoff.
  - После восстановления он будит ожидающие задачи по ёмкости: сначала одну пробную, затем по несколько за такт.
  - Он сохраняет события ожидания, пробуждения и сбоя и восстанавливает расписание после перезапуска.
  - Окончательные (неповторяемые) сигналы сразу завершают задачу.
- **Task Runner Crew** [54][100]:
  - Рассчитан на 10+ часов работы без человека [54].
  - После падения процесса запуски, которые координируются через git, продолжаются сами [54].
  - Запуски без git или другой гарантии идемпотентности открываются в состоянии Paused с пометкой о неизвестных побочных эффектах. Шаги из очереди, которые не начались, отменяются [54].
  - Пределы: `MAX_RETRIES` 3, `MAX_RECOVERIES` 2, `MAX_REPLAN` 2, `MAX_TOTAL_TASKS` 50 [100: `task_models.py:13-16`].
  - Три одинаковые ошибки помечают шаг как FAILED [54].
  - Watchdog предупреждает через 60 минут без активности и сбрасывает сессию через 2 часа [54].
- **Cron и круглосуточная работа Crew:**
  - Таймаут cron-задачи по умолчанию — 1 800 с, до 24 часов [60].
  - `--auto-pause-after N` ставит задачу на паузу после N сбоев. Throttling повторяется и в счёт не идёт [60].
  - Для круглосуточной работы Crew ставится как служба systemd или launchd. Служба перезапускается при падении и стартует при загрузке [65].

### Лимиты и стоимость

- **Планы Kiro считают месячные кредиты, а не скользящие окна** [2][89]:
  - Free 50, Pro 1 000, Pro+ 2 000, Pro Max 5 000, Power 10 000.
  - Кредиты обновляются каждый расчётный период.
  - Документация по оплате не описывает никакого 5-часового окна [89][90]. Окон на 5 часов или на неделю в текущих планах нет; единственные недельные лимиты были в preview autonomous agent в декабре 2025 [80][74].
- **Когда кредиты кончились, работа встаёт.** Это происходит, когда израсходованы и кредиты плана, и дополнительные. Работа продолжается, когда пользователь покупает пакет или план сбрасывается. На Free ждать приходится до следующего месяца [90][80].
- **Автоматическое продолжение после исчерпания** не описано (не подтверждено) [89][90].
- **Kiro предупреждает заранее:**
  - уведомление на 80% кредитов [80];
  - ограничение перерасхода через AWS Service Quotas или предоплаченные пакеты (с 2026-07-02) [79];
  - кредиты сессии в `/usage` и кредиты по шагам в мониторе workflow (CLI 3.1, 2026-11-05) [52].
- **Crew узнаёт сообщения Anthropic о лимитах.** Crew может работать с backend Claude Code. Его классификатор ошибок узнаёт названные окна (`monthly`, `daily`, `weekly`, `session`), написание `5-hour limit` и фразу `usage limit has been reached` [100: `acp/transport_errors.py:1003-1014`].
- **Но Crew считает такой лимит окончательным, а не поводом подождать** [100]:
  - Время сброса из сообщения показывается пользователю дословно и не разбирается (`acp/transport_errors.py:1003-1013`).
  - Адаптер очереди задач превращает `usage_limit` в сигнал `quota_exhausted` без `retry_at` (`taskq/adapters/acp_provider.py:81`).
  - `taskq/dependency.py:205` затем делает такой сигнал неповторяемым.
  - Переключение на другой backend при `usage_limit` объявлено, но пока не работает (`acp_failover.py:39`). Работают только два триггера переключения: «backend не установлен» и «backend нужно перезапустить» (`acp_failover.py:35`).
  - Диагностическая проверка говорит пользователю, что ходы отклоняются, пока лимит не сбросится или план не разрешит перерасход (`diagnose_probes.py`).
- **Итог:** ни ядро Kiro, ни Crew не ждут сброса лимита подписки, чтобы потом продолжить работу [89][90][100].
- **Множители кредитов** относительно Auto (1.0x) [47]:

  | Модель | Множитель |
  |---|---|
  | Claude Opus 5.5 | 2.0x |
  | Opus 5 | 2.2x |
  | Claude Haiku 5.5 | 0.06x |
  | GPT-5.6 Terra | 2.2x |
  | GPT-5.6 Luna | 0.6x |

  Для GPT-5.6 и Haiku 5.5 цена зависит от размера контекста [47].
- **Каскад Auto** (2026-11-06) [48]:
  - Каждая сессия начинается на экономичной модели.
  - Независимая модель в фоне проверяет траекторию работы.
  - Если прогресс выглядит неэффективным, сессия переходит на более сильную модель. Переход идёт только вверх.
  - Результаты на DeepSWE v1.1 (pass@1): начальная модель одна — 63.96%; каскад — 69.37%; сильная модель одна — 70.57%.
  - 80.48% задач завершились на начальной модели.
- **Пользователь не видит переход на другую модель.** Issue #8903 просит показывать модель для каждого ответа [140: #8903].
- **Дополнительные кредиты** — $0.04 за штуку, пакеты $5–100, не больше 5 пакетов [90].
- **Проверки Approve for me** списываются с плана [22]. Многоагентные workflows тоже тратят кредиты [84].
- **История схемы оплаты:** счёт запросов («vibe» и «spec») заменили единым пулом кредитов с дробным учётом в сентябре 2025 [104][105]. Перерасход для отдельных пользователей заменили предоплаченными пакетами в июле 2026 [79].
- **Crew:** вкладка Usage и прогноз кредитов [59]. Запрос лимита использования — в `dashboard/handlers/kiro_usage_api.py`. Для чтения данных об использовании задан backoff 6 часов: `_USAGE_SCRAPE_BACKOFF_SECS = 6 * 3600` в `dashboard/handlers/sessions.py:475` [100].
- **Enterprise:** экспорт в OpenTelemetry отправляет дневные агрегаты в 02:00 UTC: кредиты, перерасход, сообщения, разговоры и число запросов по моделям [78].

### Права и безопасность

- **Движок политик** [83][23]:
  - Модель прав построена на capabilities и Cedar — языке политик доступа [83].
  - Capabilities: fs_read, fs_write, shell, web_fetch, web_search, mcp, subagent, skill, power, context, diagnostics, sandbox_network [23].
  - Эффекты: deny > ask > allow > evaluate. Ни один уровень не главнее другого; побеждает самое строгое правило [23].
- **Уровни правил** [23]:
  - встроенные правила Kiro;
  - `managed-settings.json` администратора;
  - пользовательский `~/.kiro/settings/permissions.yaml`;
  - workspace — хранится вне репозитория;
  - агент;
  - сессия.
- Настройки, которыми управляет организация, могут только запрещать или спрашивать [23].
- **Shell-команды** [23]: составная команда делится на части, каждая проверяется. Команду, которую нельзя разобрать, Kiro блокирует и просит агента переписать.
- **Sub-agents** [23]: побеждает более строгая из двух политик. Если у родителя нет правила для вызова, спрашивают пользователя. Свойство «sub-agent не получает больше прав, чем родитель» доказано на Lean [99].
- **Пресеты** [23]: allow-all, edit-workspace, read-workspace, read-all, read-only-shell, dev-shell, approve-for-me. ACP-клиент выбирает пресет через `_meta.kiro.policyPreset`.
- **Неизменяемые правила** [23]:
  - Всегда запрещено: запись в собственные настройки Kiro, в workspace-roots и в `.kiroignore`.
  - Всегда спрашивается: запись в `.git/**` и в папки `.kiro` для агентов, hooks, workflows и Powers.
- **Workspace без доверия** [23]:
  - Не загружает агентов, steering, MCP-серверы, skills и workflows.
  - Каждая shell-команда спрашивает разрешения.
  - Память и хранилище сессий — только чтение.
  - Склонированный репозиторий не может сам выдать себе права [23].
- **Выбор при одобрении в CLI V3** [23]:
  - Доверять точной команде, подкоманде, базовой команде или всему инструменту.
  - Хранить доверие на сессию, на workspace или на пользователя.
  - Есть `/tools trust-all`.
- **Режимы прав в IDE** [23][102]: Supervised, Accept file changes и Approve for me; настройка `kiroAgent.agentAutonomy` [23]. Accept file changes раньше назывался «Autopilot» [23]. Там, где доступен Approve for me, IDE 1.4.154 превратил старый переключатель Autopilot в меню режимов [102].
- **Kiro Web** без Approve for me одобряет любое действие внутри sandbox [23].
- **Approve for me**: CLI 2.36 (2026-10-29) [26], Kiro Web — 2026-11-06 [25], IDE 1.4.154 — 2026-11-10 [102][22]:
  - Добавляет `evaluate` — самый слабый эффект — для действий, которые не решило ни одно правило [23].
  - Trust classifier — проверка LLM, сейчас на модели Anthropic — одобряет, блокирует или спрашивает. Правила решают первыми [22].
  - Правила deny, встроенные правила ask и любой сбой классификатора по-прежнему блокируют или спрашивают [23].
  - После трёх шагов подряд с блокировкой Kiro возвращается к вопросам и называет причину [22].
  - Только платные пользователи, регионы us-east-1 и eu-central-1, по умолчанию выключено [22].
- **Данные о вопросах и одобрениях** [22]:
  - За неделю наблюдения в CLI 15.8% вызовов инструментов спрашивали разрешение. Пользователи одобрили 97.1% таких вопросов. 13.4% сессий начинались с trust-all.
  - Внутри Amazon около 70% действий решили правила, около 30% ушли на проверку.
  - Из проверенных около 97% решены без пользователя, около 2% ушли к пользователю, меньше 1% заблокированы.
  - Медианная проверка заняла меньше секунды.
- **Журнал Approve for me** [23][25]:
  - Карточка одобренного инструмента говорит «Approved for you».
  - Заблокированное действие падает и показывает причину.
  - Вопрос пользователю объясняет, почему действие отмечено, или что оно слишком большое для проверки.
  - Kiro Web показывает по каждой сессии, что одобрено, что заблокировано и что отправлено пользователю.
  - Автономные сессии Web, сессии от комментария на GitHub и запуски по расписанию режим не затрагивает [25].
  - Если ни один клиент не подключён, запрос ждёт следующего клиента [25][27].
  - Отдельного экспортируемого журнала решений в ядре Kiro не найдено (не подтверждено).
- **Безопасность Crew** [54][57][64][100]:
  - Восемь слоёв: owner lock, запрещённые команды, governance ceiling, чувствительные пути и маски sandbox, одобрение инструментов, проверка входных данных, OS sandbox, удаление секретов из вывода [64].
  - Журнал событий безопасности с записями, подписанными HMAC (ключ `sel_hmac.key`). Его проверяют команды `kirocrew security audit` и `verify` [64].
  - Уровни одобрения: Automatic (по умолчанию), Interactive, Trust command, Trust tool, Autopilot [64].
  - Gates `force_approval` в Task Runner действуют, даже когда всё остальное одобряется автоматически [54].
  - Автоодобрение на запуск ограничено по времени: до 6 часов из dashboard и не больше 24 часов. Окно сдвигается вперёд с каждым одобренным вызовом. На запуски cron и MCP оно никогда не распространяется [54].
  - С backend Claude Code инструменты, заранее разрешённые в настройках самого Claude, проходят мимо одобрения и audit Crew. Backend Codex требует sandbox Crew [57].
- **Необязательный журнал решений Crew («decision seam»)** [100]:
  - По умолчанию выключен. Для включения нужен файл согласия [100: `decisions/log.py:3`].
  - Пишет JSONL в `~/.kiro/crew/decisions/decisions-YYYYMMDD.jsonl` с правами файла 0600.
  - Каждая строка: время, точка решения, укороченный SHA-256 идентификатора сессии, задержка и ответы. Текста разговора там нет.
  - Точка `tool_risk` добавляет значок риска от LLM в сессиях с автоодобрением [100: `decisions/points/tool_risk.py`].
  - Значок — только пометка, он никогда не блокирует действие. Чтобы отправить в LLM аргументы инструмента, нужно второе отдельное согласие.
- **Enterprise:**
  - Политика Enterprise Management задаёт allow, deny и ask для моделей, команд, файлов, web search и инструментов MCP [75].
  - CloudTrail записывает только MCP-инструменты сервисов Kiro, как `AwsMcpEvent` [78]:
    - ListTools и CallReadOnlyTool — data events;
    - CallPrivilegedTool — management event;
    - аргументы вызова заменены placeholder.
  - Промпты можно логировать в свой S3 bucket [78].
- **Известные уязвимости** (по внешним отчётам):
  - Prompt injection могла переписать настройки и разрешить любые команды. Исправлено в v0.1.42, август 2025 [148].
  - Injection через Kiro Powers привела к утечке секрета. Исправлено в 0.8.140, январь 2026. Вознаграждение за находку — $40 в виде фирменных товаров [149].
  - Команда, приписанная после доверенной, обходила проверку доверия [140: #6130 — обход доверия цепочкой команд].
  - Сообщество сделало kiro-guard, чтобы ограничить файлы, которые может читать CLI [160][142: 47123175].

## Что говорят пользователи

### Как собраны отзывы

- Основной материал — трекер kirodotdev/Kiro (12 107 issues) и репозиторий KiroCrew, прочитанные через GitHub API [71][140][141]. Ещё — треды Hacker News за 2025–2026 годы и обзоры и новости, на которые они ссылаются [142].
- Reddit (r/kiroIDE) виден только через пересказ в одном блоге и ссылки внутри issues [153][140: #4547]. X и YouTube не охвачены (не подтверждено).
- Прямая цитата ниже одна. Остальное пересказано.

### Коротко

- **Spec — главная причина пользоваться Kiro; остальное отстаёт.**
  - Пользователи в целом согласны: процесс spec (требования → дизайн → задачи) — то, ради чего берут Kiro. Редактор, agent harness и надёжность уступают Claude Code и Cursor.
  - Один комментатор подытожил так: «Kiro IDE is a middling Cursor, but an excellent spec generator» [142: 47773388].
  - Частый приём: написать spec в Kiro, а реализацию делать в Claude Code [142: 46841664].
- **Цена — самая давняя претензия.**
  - Началось с разделения на «vibe» и «spec» requests в августе 2025 [144].
  - Продолжается как непонятные множители кредитов [140: #11573 — изменение множителей GPT; #8903 — какую модель выбрал Auto].
  - Пользователи просят и более дешёвые, и более дорогие планы [140: #6556 — планы за $5 и $10; #11600 — планы больше 10 000 кредитов].
- **Сбои повторяются периодами:**
  - июль 2025 — throttling на запуске [140: #413][145];
  - июнь 2026 — регрессии IDE 1.0 [140: #9524, #9620];
  - с 6–7 ноября 2026 — ошибки rate limit на первом же запросе; на 13 ноября issue всё ещё открыт [140: #12324].
- **Два публичных инцидента в начале 2026 года.**
  - Financial Times (FT) связала Kiro со сбоем AWS. Amazon это оспаривает [150][151].
  - Платные аккаунты массово блокировались, пока AWS настраивал защиту от массовой регистрации аккаунтов для перепродажи [140: #6102, #6607][142: 47474508][153][154].
- **Вне Amazon Kiro мало обсуждают; внутри Amazon он был обязательным.**
  - Вне: комментаторы редко видят упоминания Kiro, опрос на HN его не включил, посты о запуске Crew почти не обсуждались [142: 48247154, 48691044, 49176063].
  - Внутри Amazon Kiro был фактическим стандартом, а его использование превратили в соревнование с рейтингами [142: 48464729, 48149230][152]. Весной 2026 внутри Amazon раздали Claude Code и Codex [161].
- **Самая заметная неудовлетворённая потребность — меньше ручных одобрений. Она пересекается с worfy.**
  - Данные Kiro: пользователи CLI одобряли около 97% запросов, и 13.4% сессий начинались с trust-all-tools [22].
  - Много багов о том, что «Always allow» и Autopilot не сохраняются [140: #10012, #9620, #10655].
  - Пользователи хотят одобрять с телефона [140: #6099, #9460][141: #2779]. В Crew при работе без человека запросы одобрения молча отклонялись через 10 минут [141: #7659].
- **О самых новых функциях отзывов мало**, и это в основном ранние баги. Речь о workflows (2026-09-30) и Approve for me (2026-11-10) [140: #11938, #11876, #12314].

- **Август 2025 — недовольство ценами.**
  - Новые планы разделили использование на «vibe» и «spec» requests. Pro стоил $20 за 225 vibe и 125 spec requests. Сверх лимита — $0.04 за vibe и $0.20 за spec [144].

  - На HN писали, что цены испортили продукт. Часть пользователей перенесла повседневную работу в Copilot и оставила Kiro только для spec requests [142: 44942600].

### Что ругают

**Цена и кредиты**
- Пользователи не понимают, что покупает кредит. Один комментатор высмеял само понятие «Kiro token» [142: 49571602].
- Просят прозрачности:
  - показывать, какую модель Auto выбрал для каждого ответа [140: #8903 (51 👍), #8575];
  - показывать расход кредитов внутри sub-agents [140: #6213].
- Просят планы за $5 и $10 [140: #6556 (87 👍)] и планы больше 10 000 кредитов [140: #11600 (94 👍), #5199].
- Когда множители меняются, maintainers отправляют пользователей в AWS Support. Пользователи отвечают, что это проблема удобства, а не оплаты [140: #11573].
- Активные пользователи сообщают о $600–800 в месяц на докупку кредитов [142: 49301622] или о ~€200 за один выходной [142: 48520954].
- Текущие планы: Free $0 / 50 кредитов; Pro $20 / 1 000; Pro+ $40 / 2 000; Pro Max $100 / 5 000; Power $200 / 10 000. Дополнительный кредит — $0.04, неиспользованные кредиты не переносятся [2].

**Надёжность**
- Повторяющиеся ошибки throttling и «unexpected error» [140: #413 (162 комментария), #816, #6352]. Есть запрос на публичную страницу статуса [140: #8662].
- Сбои из-за предела контекста [140: #4181] и двойные запуски, которые списали кредиты дважды [140: #4731].
- Ответы без сделанной работы, которые всё равно тратят кредиты [140: #7071, #10059].
- Один комментатор заметил, что версию 1.0 убрали со страницы загрузки [140: #9524].
- **Ноябрьские ошибки rate limit** [140: #12324]:
  - Ошибка возникает на первом запросе, при оставшихся кредитах и одной открытой сессии.
  - 9 ноября maintainer подтвердил, что причина на стороне сервиса.
  - С 25 октября по 13 ноября открыто 38 issues о rate limit, против 15 за восемь недель до этого [140].

**Harness и качество агента**
- Люди, которые называют себя инженерами Amazon, пишут, что главные претензии — к harness, и Claude Code ощущается лучше [142: 47392420, 48246824]. Ещё один за несколько секунд решил, что kiro-cli хуже [142: 46553871].
- Описанное плохое поведение:
  - меняет файлы без причины [142: 46554344];
  - удалил код, который не смог вернуть [142: 45610996];
  - много проходящих тестов, но нет полезного кода [142: 46540927];
  - винит библиотеку тестов [142: 47999976];
  - хотел завести тикет Jira на другую команду из-за локальной проблемы [142: 49508101].
- Мнения о моделях Claude через Amazon Bedrock разделились. Одни считают их глупее [142: 46835130]. Другие ценят, что изменения на стороне Anthropic до них не доходят [142: 47856824].

**Издержки spec**
- Для одного мелкого бага Kiro написал 4 user stories и 16 критериев приёмки [146]. Пользователи жалуются на слишком много стадий, которые тратят токены [142: 47897291].
- Böckeler называет Kiro подходом «spec-first», а не «spec-anchored»: spec не поддерживаются в актуальном виде, когда код меняется [146].

### Отзывы о функциях, которые пересекаются с worfy

- **Работа без человека.**
  - Kiro держал «Run all tasks», пока пользователи не попросили. Теперь советует функцию для небольших spec и признаёт, что агент иногда уходил не туда [85].
  - Опытные пользователи запускают kiro-cli в своих «Ralph loops» — скриптах, которые перезапускают агента, пока работа не будет сделана [155].
  - На запуске после ошибок нагрузки задачи приходилось перезапускать вручную [142: 44560662].
  - Признаков того, что Kiro ждёт сброса лимита и продолжает работу, не найдено (не подтверждено).
- **Workflows** включаются отдельно. В них циклы до 3 попыток, параллельные ветви и свежий контекст на каждый шаг [84]. Первые отзывы:
  - медленно, потому что координация занимает больше, чем сама работа [140: #11938];
  - включение workflows отключает встроенных агентов [140: #11876];
  - пользователи хотят, чтобы каждый запуск указывал свою цель [140: #12317].
- **Crew.**
  - Примерно за четыре месяца репозиторий собрал 4 927 звёзд, 22 336 PR (18 625 слиты) и 14 175 issues [141].
  - Больше всего комментариев — у issues, которые машина открыла про расхождения CI и flaky tests [141].
  - Maintainers признали, что не ожидали такого объёма, и что многие issues требуют решения человека [141: discussion 1654].
  - Главные запросы пользователей [141: #35139, #1693, #2779, #6812, #21250]:
    - превращать задачи в браузере в повторно используемые skills;
    - другие провайдеры моделей;
    - мобильное приложение для одобрений;
    - режим одобрения по умолчанию;
    - доверие для каждого агента, которого запускает сессия.
  - Claude Code стал рабочим backend в сентябре 2026 [141: discussion 7723].
- **Одобрения, пока человека нет.**
  - В Crew при работе без человека запрос одобрения молча висел и через 10 минут отклонялся. Пользователь просил push-уведомление и режим «ждать одобрения» [141: #7659]. Issue закрыт 2026-10-08; как его решили — не подтверждено.

- **Approve for me.**
  - LLM проверяет любое действие, которое не покрыто правилами allow, ask или deny. После трёх блокировок подряд режим спрашивает пользователя. По умолчанию выключен и оплачивается из плана [22].
  - Kiro сообщает: около 97% проверенных действий одобрено, меньше 1% заблокировано [22].
  - Пока есть один отзыв пользователя. Когда классификатор падает, пользователь получает обычный запрос и не может понять, что автоодобрение не сработало. Maintainer подтвердил это как баг [140: #12314].

- **Волны по зависимостям и ожидание PR без токенов.** Обсуждений пользователей не найдено (не подтверждено). Heartbeats в Crew следят за PR [68].

### Что убрали или переделали

- **Счёт запросов → кредиты.** Раздельные «vibe» и «spec» requests стали одним пулом кредитов с дробным учётом в сентябре 2025 [104][105].
- **Перерасход → предоплаченные пакеты.** Отдельные пользователи покупают дополнительные кредиты; командам дали ограничения через AWS Service Quotas (июль 2026) [79].
- **Отдельный autonomous agent → функция ядра.** Он стал режимом Autonomous в Kiro Web; автономность появилась и в IDE и CLI [117][74].
- **Три harness → один.** Harness на TypeScript (IDE), Rust (CLI) и Python (Web) объединены за ACP [83].
- **Только requirements-first → три точки входа.** Добавлены spec Design-First и Bugfix; Quick Spec пропускает остановки на утверждение [113][20][18].
- **Переключатель Autopilot → меню режимов прав.** «Autopilot» переименован в **Accept file changes** [102][23].
- **Чистка в IDE 1.0** [120]:
  - Trusted Commands и command denylist заменены правилами в `permissions.yaml`.
  - Inline Chat удалён.
  - Ручные hooks стали ручными steering-файлами.
- **Удалено в CLI 3.0:** интерфейс Classic, desktop-приложение CLI, автодополнение в shell и инструмент `use_aws` [51][127].

## Слабые места и чего нет

- **Нет ожидания сброса лимита.** Планы считают месячные кредиты. Когда кредиты кончились, работа встаёт до покупки пакета или сброса плана [89][90]. Автоматическое продолжение не описано (не подтверждено). Crew считает лимит Claude Code окончательным и не разбирает время сброса [100].
- **Workflows ядра не изолируют git.** Нет веток и worktree на запуск. Параллельным запускам нужны свои `run_dir` и worktree, и их должен устроить автор recipe [15]. В IDE это только инструкция агенту [12].
- **Нет своего ключа к модели и локальных моделей** [71][140: #34, #695, #206, #8939].
- **Привязка к своему fork VS Code.** Нет devcontainers, WSL и удалённой разработки; пользователи просят extension для VS Code и plugin для JetBrains; часть extensions ломается [140: #164, #17, #3497, #4665, #1318, #7886, #9939].
- **Непрозрачная стоимость.**
  - Не видно, какую модель выбрал Auto [140: #8903][48].
  - Не виден расход кредитов внутри sub-agents [140: #6213].
  - Множители меняются без понятного объяснения [140: #11573].
  - Расход вырос примерно в шесть раз после принудительного включения агентных функций [140: #10131].
  - Ответы без работы тоже тратят кредиты [140: #7071, #10059]; двойные запуски списывают дважды [140: #4731].
- **Надёжность.** Повторяющиеся throttling и rate limit [140: #413, #12324, #12377, #12413]. Публичной страницы статуса нет — есть запрос [140: #8662]. Регрессии IDE 1.0 [140: #9524, #9620]. В июле 2026 CLI сдавался после 3 повторов [140: #10516].
- **Права.**
  - «Always allow» не сохраняется [140: #10012, #9620, #10655].
  - Sub-agents нельзя одобрить заранее [140: #4544].
  - Был обход доверия цепочкой команд [140: #6130].
  - Сопоставление только по glob раздувает правила: 21 → 665 [140: #11698].
  - Сбой классификатора Approve for me выглядит как обычный запрос [140: #12314].
- **Approve for me ограничен.** Только платные планы и два региона; каждая проверка стоит кредитов; режим не работает в автономных сессиях и запусках по расписанию [22][25]. Экспортируемого журнала решений не найдено (не подтверждено).
- **Издержки spec.** Слишком много стадий и критериев для мелких задач [146][142: 47897291]. Spec не поддерживаются в актуальном виде после изменений кода («spec-first, not spec-anchored») [146]. Steering засоряет каждый запрос [147]. Run all tasks в январе 2026 советовали только для небольших spec [85].
- **Workflows.** Медленные из-за координации [140: #11938]. Включение отключает встроенных агентов [140: #11876]. Запуск не указывает свою цель [140: #12317]. Не больше 50 шагов и вложенность до 8 [13]. В Mobile workflows нет [12].
- **Аккаунты и оплата.** Массовые блокировки платных аккаунтов [140: #6102, #6607]. Оплата не работает во многих странах [140: #2308, #8642, #9128]. Бот помечает отчёты дубликатами [140: #6130, #9460].
- **Инциденты безопасности:** prompt injection, которая разрешала любые команды, и утечка секрета через Powers [148][149].
- **Облачные сессии.** Только регион us-east-1; нет режима Supervised и переименования [27]; сессия истекает через 90 дней без активности [28]. Технология изоляции sandbox не раскрыта (не подтверждено).
- **Mobile.** iOS — только ранний доступ [7][36]. Push-уведомления не описаны (не подтверждено). Нужен платный план [7].
- **Интеграции.** Нет Linear; готового приёма задач из Jira или Confluence в Web не найдено (не подтверждено).
- **Нет пространственного интерфейса.** Canvas-подобного холста не найдено (не подтверждено). Вида всей работы проекта по дням или неделям не найдено [56][59]. Воспроизводимой ленты запуска без человека не найдено (не подтверждено).
- **Наблюдаемость для enterprise.** CloudTrail пишет только MCP-инструменты сервисов Kiro, аргументы скрыты [78]. OpenTelemetry — только дневные агрегаты; трассировок нет, есть открытый запрос [78][140: #6319].
- **Crew.**
  - Инструменты, заранее разрешённые в Claude Code, проходят мимо одобрения и audit Crew [57].
  - Пропущенные запуски cron не выполняются задним числом [60].
  - Одобрения при работе без человека раньше молча отклонялись через 10 минут [141: #7659]; как это решили — не подтверждено.
  - Переключение backend при лимите объявлено, но не работает [100].
- **Модели.** Запасная модель при недоступности отвечает только один ход [47]. Неизвестная модель в шаге workflow падает без замены [13].
- **Узнаваемость вне Amazon низкая** [142: 48247154, 48691044, 49176063].
- **Пробелы по словам конкурента** (источник с конфликтом интересов): нет отдельного поиска багов и code review; слабое изучение существующих кодовых баз; привязка к своему IDE [156].

## Механизмы, которые стоит изучить

1. **Ожидание PR без токенов — узел `watch` с обработчиком `github-pr`.**
   - Что это: шаг workflow, который ждёт событий в PR и не вызывает модель, пока событий нет [13].
   - Как работает: опрос раз в 60 с (минимум 30 с). Пробуждение несёт сводку: новые комментарии и review, `headSha`, `mergeable`, `mergeStateStatus`, `newFailedChecks`, число прошедших и ожидающих checks. Не больше 10 элементов за опрос; упавшие checks в лимит не входят. Упавший check GitHub Actions придерживается до конца run. Каждый сбой будит агента один раз на head commit и check (перезапуск check будит снова); конфликт — один раз на пару «head commit и вершина base-ветки». Доставка — хотя бы один раз. Наблюдение завершается на merge или закрытии PR [13].
   - Источник: [13].
2. **Протокол `command` watch — ожидание любого внешнего события своей программой.**
   - Что это: та же точка ожидания без токенов, но проверку пишет пользователь [13].
   - Как работает: программа получает на stdin JSON `{cursor, config, workspacePath, additionalDirectories}`. Она печатает `outcome` (idle, new-activity, terminal-state), новый `cursor` и по желанию `payload`. Коды 2, 126, 127 проваливают узел; любой другой ненулевой код считается «событий нет». Минимальный интервал — 10 с. Программа работает под правами и sandbox запустившей сессии [13].
   - Источник: [13].
3. **Выход из цикла только по машиночитаемому доказательству.**
   - Что это: условие остановки цикла проверяет файл или выражение, а не слова агента об успехе [13][14].
   - Как работает: `fileCheck` сравнивает поле JSON в файле со значением (например, `verdict == APPROVED`). `stopWhen` проверяет выражения вроде `wait.terminal`. Каждый цикл обязан иметь конечный `maxIterations`. Предел итераций — страховка, а не признак успеха [13][14][12].
   - Источник: [12][13][14].
4. **Approve for me — правила, затем модель-классификатор, затем человек.**
   - Что это: режим, где действия, не покрытые правилами, решает LLM [22][23].
   - Как работает: эффект `evaluate` ниже deny, ask и allow. Сбой классификатора превращается в вопрос человеку. После трёх шагов подряд с блокировкой режим снова спрашивает человека и называет причину. Одобренный вызов помечен «Approved for you»; запрос к человеку объясняет, почему действие отмечено. Данные вендора (внутреннее использование, выборка за одну неделю): ~70% действий решают правила, из остальных ~97% решены без человека, медиана проверки меньше секунды [22][23][25].
   - Источник: [22][23][25].
5. **Предел итераций ставит на паузу, а не роняет запуск.**
   - Что это: на пределе цикла запуск ждёт решения человека, а человек может дать ещё итераций [15].
   - Как работает: политика `onMaxIterations` — abort, continue или pause [13]. Кнопки «Add loops» (IDE), «Run N more» (Web), «Run 1 more iteration» (CLI 3.2+). С 2026-10-28 цикл review по умолчанию встаёт на паузу после двух отклонённых проходов; раньше он делал 3–5 проходов и падал. Собственный предел workflow главнее [17].
   - Источник: [13][15][17].
6. **Повтор шага на месте до 24 часов и checkpoint на каждой границе узла.**
   - Что это: опубликованное расписание повторов при обрыве соединения и сохранение состояния запуска [15].
   - Как работает: первые 5 минут — повтор примерно раз в минуту, затем примерно раз в 2 минуты с jitter. Через 24 часа запуск встаёт на паузу. Успешный ход или Resume начинают новое окно. Для 5xx, throttling и зависших потоков — свои короткие повторы. На границе узла сохраняются статусы, выводы, артефакты, прогресс циклов, cursors наблюдений и сессии шагов; прерванный шаг продолжает в своей сессии [15].
   - Источник: [15].
7. **Восстановление в Crew: координатор зависимостей и лестница восстановления.**
   - Что это: код, который сохраняет ожидания внешних сервисов и решает, какой уровень перезапускать [100].
   - Как работает: один координатор на область зависимости. Он ждёт ровно до `retry_at` от сервера, иначе — backoff (база 2 с, потолок 120 с, equal jitter). После восстановления будит сначала одну пробную задачу, потом по несколько за такт. События ожидания, пробуждения и сбоя сохраняются, расписание восстанавливается после перезапуска. Лестница: инструмент 3 попытки, backend 2, ACP runtime 2, фоновый процесс Gateway 1 раз за 10 минут, сам Gateway — только вручную. Перегрузка не идёт по лестнице, а снижает пределы параллельности. Лимит подписки Claude этот механизм не ждёт: время сброса не разбирается, сигнал без `retry_at` становится неповторяемым [100].
   - Источник: [100: `taskq/dependency.py`, `recovery/policy.py`, `recovery/ladder.py`, `taskq/adapters/acp_provider.py:81`].
8. **Task Runner Crew: commit на каждый шаг и независимый reviewer по настоящему diff.**
   - Что это: выполнение spec без человека, рассчитанное на 10+ часов [54].
   - Как работает: каждый шаг — в новой сессии, затем тесты, затем отдельная сессия-reviewer читает `git diff HEAD~1`. Прошло — commit; не прошло — `reset --hard HEAD~1` и повтор. Бюджеты: 3 повтора на шаг, 2 восстановления после падения, 2 перепланирования, 50 задач всего. Три одинаковые ошибки — «Loop detected». Watchdog: предупреждение через 60 минут простоя, сброс сессии через 2 часа. После падения запуски на git продолжаются сами, остальные открываются в Paused с пометкой о неизвестных побочных эффектах [54][100].
   - Источник: [54][100: `git_coord.py`, `task_models.py:13-16`].
9. **Правила responder для PR в recipe publish-pr.**
   - Что это: агент, который ведёт PR до зелёного одобренного состояния и не сливает его сам [14].
   - Как работает: при конфликте — merge base-ветки обычным merge commit, без rebase и force-push. Чинит только checks, которые сломала его ветка. Чужой упавший check перезапускает один раз на GitHub Actions run. Закрывает threads, на которые ответил. Перед изменением дизайна, объёма или UX спрашивает человека. Цикл ожидания и ответа — до 200 итераций с паузой на пределе [14].
   - Источник: [14].
10. **Автоодобрение на запуск с ограничением по времени и обязательные gates.**
    - Что это: в Task Runner Crew автоодобрение включается на конкретный запуск и само выключается [54].
    - Как работает: до 6 часов из dashboard, не больше 24 часов. Окно сдвигается вперёд с каждым одобренным вызовом. На cron и MCP-запуски не распространяется. Gates `force_approval` блокируют действие даже при включённом автоодобрении [54].
    - Источник: [54].
11. **Один обязательный статус «PR Readiness» и проверка свежести зелёного результата.**
    - Что это: все линии CI сводятся в один вердикт, а отдельный скрипт проверяет, что зелёный результат относится к текущей base-ветке [98][100].
    - Как работает: PR готов, когда `pr_status.py` возвращает 0, PR можно слить, `green_age.py` возвращает 0, commit один и на все замечания есть ответ. Код 30 у `green_age.py` значит, что base-ветка с тех пор изменилась в файлах этого PR. Агент сливает только через `gh pr merge --auto` [100]. Блокирующая находка review обязана указать место, доказательство, условие и последствие [98].
    - Источник: [98][100: `builtin_skills/kirocrew-dev/kirocrew-prepare-pr/SKILL.md`].
12. **Каскад моделей в Auto.**
    - Что это: маршрутизация, при которой сессия начинает на дешёвой модели и переходит на сильную только при плохом ходе работы [48].
    - Как работает: независимая модель в фоне оценивает траекторию; пока переход идёт только вверх (возврат на экономичную модель вендор обещает изучить); рабочая модель не оценивает сама себя. На DeepSWE v1.1 каскад дал 69.37% против 63.96% у начальной модели и 70.57% у сильной; 80.48% задач завершились на начальной модели [48]. Это внутренняя оценка (pass@1, среднее по трём прогонам), вендор прямо пишет, что это не прогноз для production [48]. Пост описывает каскад как работу «за кадром»; issue #8903 (открыт с 2026-05-26) просит показывать модель каждого ответа [140: #8903].
    - Источник: [48][140: #8903].
