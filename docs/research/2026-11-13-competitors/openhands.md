## Модель работы

- **Где идёт работа: hybrid.**
  - Canvas — только клиент. Действия агента выполняет Agent Server — сервер из SDK, который держит разговоры и
    запускает агента. Sandbox тоже даёт не Canvas [53][97].
  - Локальный стек — четыре части за портом 8000: веб-клиент Canvas, Agent Server, Automation Server (сервис
    расписаний и событий) и ingress [53].
  - Один Canvas переключается между backend-ами — серверами, на которых реально работают агенты: ноутбук, Docker,
    удалённый Agent Server, VM, Kubernetes, Modal, DigitalOcean Managed Agents, OpenHands Cloud, OpenHands Enterprise
    [70][71]–[75].
  - Позиция вендора: масштаб — в облаке или в VPC клиента, а локальные агенты — промежуточный шаг, не цель [5]. При
    этом главный продукт с июня 2026 — локальный Canvas. Вендор связывает одно с другим путём роста «ноутбук → VM →
    Cloud → Enterprise» [36].
- **Агенты.**
  - Собственный агент OpenHands из Software Agent SDK. Работает на любой LLM через LLM-профили — сохранённые
    настройки модели [58][59].
  - ACP-агенты: Claude Code, Codex, Gemini CLI, Pi, OpenCode и свои ACP-серверы [57]. ACP (Agent Client Protocol) —
    протокол, по которому Agent Server запускает CLI агента как подпроцесс и общается с ним JSON-RPC через stdio
    [57][37]. В коде SDK есть ещё провайдер Kimi Code [101].
  - Вход по подписке важнее API-ключа [57]. На OpenHands Cloud доступны только Claude Code, Codex и Gemini CLI; Pi и
    OpenCode — только на локальных backend-ах [57].
- **Модели.** По умолчанию — OpenAI GPT-5.6 Sol. Бесплатная модель через OpenHands — DeepSeek V4 Flash [55]. Можно
  подключить любого провайдера, в том числе локальные серверы (подробно — «Функции», раздел 3) [60].
- **Один пользователь или команда.**
  - Бесплатный Canvas — один пользователь или общая учётная запись («single user / shared identity») [3].
  - Команды — в платных вариантах: организации и роли в Cloud [86], RBAC и SSO/SAML в Teams и Enterprise [3][91].
- **Платформы.**
  - В первую очередь — браузер: React-клиент, который отдаёт локальный стек [53][54].
  - npm launcher: нужны Node 24+ и `uv` [54].
  - Desktop-приложение на Electron — preview-сборка для macOS (без подписи), Windows и Linux [54][100].
  - Docker-образ и Kubernetes через Helm [54][75][99].
  - Телефон — через удалённый доступ к своему стеку [76] и отдельное мобильное приложение (MVP) [105].

### 1. Установка, обновление, доступ

- **npm launcher.** Ставится командой `npm i -g @openhands/agent-canvas`, запускается командой `agent-canvas`. Нужны
  Node 24+ и `uv` [54].
- **Desktop-приложение (preview).**
  - Сборки: macOS universal `.dmg`, Windows x64 `.exe`, Linux AppImage и `.deb` [54][100]. Ни одна не подписана:
    сертификатов подписи нет ни для одной платформы, macOS-сборка подписана только ad-hoc (комментарии в
    `.github/workflows/desktop-*.yml`) [97].
  - Размер файлов v1.40.0: dmg 349 MB, exe 168 MB, AppImage 200 MB, deb 157 MB [100].
  - На macOS перед первым запуском нужна команда `xattr`. Issue #16774 («Mac Installer Produces Damaged Binary»)
    закрыт 2026-10-20, хотя подписи и notarization по-прежнему нет; workflow ссылается на него как на задачу подписи
    [54][119][97].
  - Linux-сборки — с v1.16 (2026-08-27); universal-сборка для macOS — с v1.23 (2026-09-23) [77].
  - Внутри — оболочка Electron, которая запускает Python-сервисы через встроенный `uvx` [97].
- **Обновление — вручную.** Новую версию надо скачать самому. В Settings видны установленная версия и кнопка
  «Check for updates» [54][61]. В main-процессе Electron нет auto-updater и иконки в tray [97]. Auto-update — открытый
  запрос #15529 [120].
- **Docker-образ** `ghcr.io/openhands/agent-canvas` [54]. На Windows документирован запуск Docker из PowerShell.
  Отдельный Docker-контейнер на разговор там требует WSL 2 [96].
- **Kubernetes и VM.** Helm chart и гайды по VM с чек-листом безопасности [75]. Helm chart помечен как experimental:
  без аутентификации и для одного tenant-а; для большего вендор предлагает Enterprise [99]. В 2025 году команда
  отклоняла PR с Helm chart, чтобы не создавать неверных ожиданий [14].
- **Удалённый доступ и телефон.**
  - SSH-туннель, Tailscale, TLS reverse proxy или ngrok, по желанию за Google OAuth [75][76].
  - Режим `--public` требует сильный `LOCAL_BACKEND_API_KEY` [75][76].
  - Отдельное мобильное приложение на Expo (MVP); репозиторий создан 2026-09-16 [105].
- **Приватность.**
  - Телеметрию выключает переменная `AGENT_CANVAS_DISABLE_TELEMETRY` (v1.17). Настройка браузера Do Not Track
    учитывается (v1.26) [77].
  - Об аналитике источники расходятся. В 2025 году её добавили только после публичного обсуждения и сделали opt-in
    [14]. В Canvas телеметрию выключают переменной окружения (v1.17) [77] — это похоже на opt-out (вывод, не
    проверено). Запрос согласия на аналитику в Canvas есть; у CEO он появлялся снова раз в несколько дней [126].
    Какое поведение у Canvas по умолчанию сейчас, неизвестно (не подтверждено).
- **16 языков интерфейса:** ar, ca, de, en, es, fr, id, it, ja, ko-KR, no, pt, tr, uk, zh-CN, zh-TW [97]. Турецкий
  — v1.22, индонезийский — v1.28 [77].

### 2. Backend-ы

- **Переключатель backend-а** — в интерфейсе [70]. Вместе с backend-ом меняются настройки, профили, MCP-серверы (MCP —
  Model Context Protocol, стандарт подключения внешних tools к агенту), automations и список разговоров: конфигурация
  у каждого backend-а своя [61].
  - Где стоит переключатель, документация пишет по-разному: «top bar» [72], «bottom-left corner» [67], «header» [1].
- **Виды backend-ов:** local, Docker, удалённый Agent Server, VM, Kubernetes, Modal, DigitalOcean Managed Agents,
  OpenHands Cloud, OpenHands Enterprise [70][71]–[75].
- **Docker execution.** По умолчанию: 4 GB памяти, 2 CPU, 512 PIDs, 120 s на старт, остановка после 20 минут простоя,
  все Linux capabilities сброшены [71].
- **DigitalOcean Managed Agents.** Один microVM на сессию, пауза после 15 минут простоя. Нужно desktop-приложение
  1.27 или новее [73][46].
- **Modal.** Около $102 в месяц, если backend всегда включён, или около $0.14 в час с остановкой до нуля. Только для
  одного пользователя. Остановка по умолчанию — через 600 s без работы [74].

### 3. Агенты и модели

- **Два вида агентов** [58][59][57][37]:
  - собственный агент OpenHands из Software Agent SDK; работает на любой LLM через LLM-профили;
  - ACP-агенты: Agent Server запускает CLI агента как подпроцесс и говорит с ним JSON-RPC через stdio.
- **Preset-ы ACP:** Claude Code, Codex, Gemini CLI, Pi, OpenCode; можно добавить свой ACP-сервер [57]. Pi и OpenCode
  — только на локальных backend-ах; на OpenHands Cloud — только Claude Code, Codex и Gemini CLI [57].
- **Вход по подписке** важнее API-ключа [57]. С v1.40 есть подсказки, как войти через подписку Codex [100]. Собственный
  агент тоже умеет входить по подписке ChatGPT Plus или Pro для моделей Codex без API-кредитов (guide
  «LLM Subscriptions» в SDK) [95].
- **Settings → Agent:** поля Preset, Command, Credentials, Model и «Agent default». Onboarding агента — 4 шага [57].
- **Модели ACP-агента.** На локальных backend-ах список приходит через `POST /api/acp/models` [57]. С v1.27 агенты
  сами сообщают свои модели [77].
- **История ACP в релизах:** новые ACP-harness-ы выключены по умолчанию (v1.18; harness — обвязка вокруг модели:
  цикл агента, tools, prompts); блоки tool call ACP-агентов видны в чате (v1.24); Pi и OpenCode — v1.27 [77].
- **Critic** для ACP-агентов может не работать: они ведут свой цикл [64].
- **LLM-профили** — сохранённые настройки модели. Вкладки Basic / Advanced / All. Модели, которые идут через
  OpenHands, помечены «Free» [59][88].
- **Provider Connections** — подключить провайдера один раз и добавить его модели пачкой. Сначала только локально;
  подключения на Cloud — v1.17 [59][77].
- **Base URL модели** должен быть доступен с backend-а, а не только из браузера [59].
- **Провайдеры:** LiteLLM, OpenRouter, DigitalOcean Inference и локальные серверы LM Studio, Ollama, vLLM, SGLang
  [60].
- **Модели по умолчанию.** Сейчас — OpenAI GPT-5.6 Sol; бесплатная через OpenHands — DeepSeek V4 Flash [55]. Раньше
  по умолчанию были GLM 5.2 (v1.10), Kimi K3 (v1.14), затем GPT-5.6 Sol (v1.16); GPT-6 Astra добавлен в v1.19 [77].
- **`/model`** меняет модель посреди разговора и сохраняет историю [60][97]. Есть issue #16356 о том, что конфигурация
  LLM разговора замораживается при создании; дата issue не записана, и как он соотносится с `/model`, не проверено
  [124].
- **Model Router (v1.25)** — отдельная модель выбирает, какой моделью выполнять задачу [60][77].
  - Шаблоны «OpenHands Router Pro» и «OpenHands Router Flash».
  - Переключатель «Run on first message» отправляет первое сообщение каждого нового разговора через router. Он
    выключен, пока router-а нет, и включается сам, когда пользователь добавляет первый router [60][97].
  - В коде router-профиль — это prompt: отнести задачу к одной категории (исправление в зрелом репозитории, тесты,
    визуальный UI и другие) и выбрать одну модель из таблицы с точностью и ценой по benchmark-ам. Такие профили
    лежат на странице настроек meta-llm [97].
- **SwitchLLMTool (v1.16)** — переключатель, который разрешает агенту самому менять модель [77].
- **Страницы настроек:** llm, meta-llm, agent, agents, condenser, agent-context, verification, runtime, app, secrets
  [97].
- **OpenHands Index** — рейтинг моделей, а с июня 2026 и пар «harness + модель», на пяти типах задач; рейтинг
  сравнивает качество, цену и время [26][37]. Вендор утверждает, что с моделями
  Anthropic по ценам API их harness точнее и дешевле Claude Code, а с моделями OpenAI точнее Codex при немного
  большей цене [37] (утверждение вендора).

### 4. Начало работы: onboarding, Home, workspace

- **Мастер первого запуска** [55]:
  - пользователь настраивает LLM;
  - последний шаг «Start From a Proven Workflow» предлагает шаблоны вместо пустого чата: GitHub PR Review Copilot,
    GitHub Repository Monitor, Slack Standup Digest;
  - каждый шаблон включает prompt, набросок реализации и нужные MCP-подключения;
  - мастер называет продукт «automation-centric developer control center».
- **Чек-лист Getting Started в sidebar** [55][77]:
  - шесть пунктов со ссылками: настроить LLM, подключить MCP-серверы, начать разговор, посмотреть automations,
    настроить агента, проверить настройки;
  - отслеживает прогресс, сворачивается и сам прячется, когда всё сделано;
  - можно закрыть (v1.28); на Cloud и Enterprise не показывается.
- **Home** [97][77][100]:
  - сохранённые workspace и «Workspace parents» — видно по строкам интерфейса; точное поведение неизвестно
    (не подтверждено);
  - выбор репозитория из нескольких git-провайдеров (v1.32);
  - настоящая default branch репозитория вместо зашитой «main» (v1.40).
- **Runtime на каждый разговор: Local, Worktree или Docker** [56][77][97]:
  - значение по умолчанию задаётся в Settings → Runtime (v1.34);
  - Worktree доступен, только когда открыта папка репозитория [77][56];
  - worktree может начинаться от default branch, текущего HEAD или другой ветки, tag или commit;
  - имя ветки — настраиваемый префикс (например `openhands/`) плюс id разговора.
- **Старт без ожидания.** Новый разговор открывается сразу; прогресс запуска sandbox виден прямо в чате [56].
- **Launch links** — разговор стартует по URL с plugin и параметрами. На локальных backend-ах параметры агенту не
  передаются [62][87][77].
- **Расширение Chrome** добавляет «Launch with OpenHands» на страницах GitHub. Последний push — 2026-03-07, раньше
  появления Canvas [106].
- **На Cloud** меню строки в sidebar предлагает «New Conversation in Sandbox» — то же, что `/new` [56].

  другой машине [56].
- Ширина меняется от 240 до 560 px (v1.35) [56][77].
- Фильтры: запуски automations — All / Hide / Only [56]; владелец (v1.25) [77].
- Tags (v1.17; хранятся на сервере с v1.35) и закреплённые разговоры (на сервере с v1.32) [77].
- Archive [56].

**Лента чата**
- Внизу чата — живая группа «stage»: текущий шаг или «Thinking» между шагами [56].
- Законченные группы сворачиваются в одну фразу-сводку, например «Ran a command, ran a hook» [56].
- Успешные запуски hook-ов прячутся внутрь своей группы. Заблокированные hook-и остаются на виду [56].
- Время сообщения — при наведении [56].
- Предпросмотр Markdown и PDF в чате, картинки во вложениях, lightbox, кликабельные пути к файлам [56][77].
- Голосовой ввод: распознавание речи браузера или endpoint, совместимый с Whisper (v1.25) [56][77].
- Если сообщение не ушло, есть кнопки Retry и Dismiss [56]. Структурные ошибки и проверка LLM перед отправкой — v1.14
  [77].
- Текст выводится со скоростью чтения (v1.28) [77].
- **Карточка `request_secret`.** Агент просит секрет через форму со скрытым вводом, а не в обычном чате. Только
  локально (v1.28) [77][79].

**Поле ввода и меню**
- Slash-команды [97]:
  - `/new` — только на Cloud;
  - `/btw` — задать агенту побочный вопрос и не сбить основную задачу (v1.26);

- Меню Tools: сменить профиль агента; показать skills, hooks, plugins; показать tools и метаданные агента [97].
- Меню Git: создать ветку, создать PR, pull, push [97].
- Готовые макросы: Increase test coverage, Fix README, Auto-merge PRs, Clean dependencies [97].
- Меню Cmd/Ctrl+K: навигация, новый чат, показать или скрыть sidebar [97].
- Сообщение можно отправить работающему агенту; SDK учтёт его на следующих шагах [95]. Явного управления — прервать
  ход, направить его или поставить сообщение в очередь — нет; это открытый issue sdk#4829 [145].

**Правая панель (drawer)**
- Вкладки: files, commits, planner, tasklist, terminal, browser, usage. Вкладки можно закрепить; есть ссылка «открыть
  в VS Code» [97].
- **Overview:** открытые PR и issues репозитория — номер, заголовок, ссылка. Статуса CI в коде этой панели нет

- **Commits:** список commit-ов и git-действия [56].
- **Files:** просмотр и Download. На локальном backend-е скачиваются исходные байты, на Cloud — текст UTF-8 (v1.15,

- **Browser:** скриншоты браузера агента и строка URL. Не интерактивный [97].

**Контекст и стоимость**
- Индикатор заполнения окна контекста и ручная кнопка «Compact context» (v1.13). Индикатор есть только у моделей,
  которые сообщают размер окна [56][77].
- Панель Usage, в том числе баланс у провайдера [56]. Для ACP-агентов сумма в долларах — оценка по ценам API, а не
  счёт [97].
- **Budget meter** сравнивает расходы с необязательным потолком. Он только показывает: расходы могут превысить
  потолок, а индикатор — показать больше 100% (v1.38) [56][77].
- **Жёсткий потолок на разговор — источники расходятся.**
  - Документация по настройкам описывает поле «Maximum Budget Per Conversation» в Settings > Application: разговор
    останавливается, когда бюджет исчерпан [78].
  - Пользователи в issue #17691 пишут, что в текущей версии настройки бюджета нет: бюджет на задачу из прошлой версии
    убрали [133].
  - В переводах интерфейса Canvas строки для такого поля нет; поле `max_budget_per_task` есть только в типах и API
    [97]. В SDK жёсткая остановка по бюджету есть (`max_budget_per_run`) [101].
- «Total Cost» пользователи называют непрозрачным — issue #19422 [141].

**Управление ходом работы**
- **Stop** прерывает агента и сохраняет его sandbox. На Cloud «Stop Sandbox» — отдельное действие (v1.38) [56][77].
- **Reopen:** решённый разговор можно открыть снова на локальном backend-е (v1.38) [56][77].
- **Branch from here** [56]:
  - на сообщении пользователя — как «исправить и отправить заново»: открывается новый разговор с этим сообщением в
    поле ввода;
  - на сообщении агента — новый разговор продолжает с этой точки;
  - ветка сохраняет историю, конфигурацию агента и контекст workspace; она не зависит от исходного разговора, и её
    тоже можно ветвить.
- **`/goal [--max N] <objective>`** [56]:
  - Agent Server запускает агента раунд за раундом. После каждого раунда судья-LLM проверяет, достигнута ли цель, и
    возвращает список недостающего.
  - Баннер показывает цель, номер раунда, статус, оценку судьи и что ещё не сделано.
  - Статусы: `running`, `complete`, `capped`, `interrupted`. Любое обычное сообщение прерывает цель.
  - Вызовы судьи стоят денег.
- **Plan mode.** `/plan` запускает агента-планировщика («Planning agent initialized»), кнопка Build передаёт план на
  выполнение [97]. Локальный Plan Mode — v1.17 [77]. Режим «Deep Planning» — открытый запрос #18104 [135].
- **Дочерние разговоры.** Tool агента `launch_child_conversation` запускает связанный дочерний разговор: локально — в
  отдельном worktree или в общем workspace родителя, либо на Cloud (v1.11) [56][77].
  - **Возвращается ли результат родителю — источники расходятся.** Документация пишет, что результат ребёнка
    возвращается в родительский разговор [56]. Описание tool-а в коде Canvas говорит обратное: ребёнок не блокирует
    родителя, и родитель не видит его вывод; родителю приходят только id, URL, target и начальный статус в сообщении
    с префиксом `[child-conversation] ` [97]. Contributor в issue #18751 тоже называет дочерние разговоры
    fire-and-forget (запустил и не ждёшь ответа) [136]. Возможно, документация называет «результатом» итог запуска
    (предположение, не проверено).

**Результат и общий доступ**
- Экспорт переписки в Markdown или HTML; файл собирается локально [56].
- На Cloud: публичная ссылка или «Share with Org users» (v1.34) [56][77].
- Архивные разговоры, которые нельзя продолжить, помечены (v1.21) [77].

**Уведомления**
- Только звук и только по согласию: `enable_sound_notifications` по умолчанию false, громкость 0.5 [97].
- Звук — когда агент ждёт ввода, закончил или ждёт подтверждения. К заголовку вкладки добавляется emoji [97].
- Системных уведомлений ОС в коде не нашлось; что их нет совсем, неизвестно (не подтверждено).
- Состояние «прочитано / не прочитано» — открытый запрос #17140 [122].

**Темы:** Light+, Solarized (v1.23), Paper (v1.38) и другие [77][61].

### 6. Настройка агента: профили, безопасность, проверка, память, hooks

- **Agent Profiles** — профиль роли агента [58]. Он хранит:
  - какой агент работает (OpenHands или ACP-агент);
  - доступ к секретам: All, None или Selected;
  - какие MCP-серверы доступны (`mcp_server_refs`);
  - какие tools включены;
  - системный prompt: стандартный, стандартный плюс свои инструкции или своя «persona»;
  - свой Model Router, condenser (сжатие старой истории) и настройки проверки.
  - История: профиль владеет этими настройками с v1.29; automation может закрепить профиль с v1.20; persona —
    v1.25; профили для preset-ов — v1.38 [77]. Переключатель профиля — в меню Tools [97].
- **Безопасность.**
  - Confirmation Mode: агент ждёт одобрения перед действием [97]. По умолчанию выключен (раздел «Права и
    безопасность») [101].
  - Security Analyzer: None или LLM; метки риска Low / Medium / High / Unknown [97].
  - Отдельный Docker-контейнер на разговор [56][71].
  - Секреты маскируются (v1.33) и раздаются по профилям (v1.20) [77][79].
  - Исправление XSS — v1.19 [77].
  - Гайд по интеграции с Cisco DefenseClaw — proxy и сканером безопасности [97].
- **Critic** — модель-оценщик, которая ставит оценку работе агента. Экспериментальный, hosted, сейчас бесплатный
  [64].
  - С «iterative refinement» агент получает повторный prompt, если оценка ниже 0.6. Не больше 3 итераций [64].
  - Critic рассчитан на собственного агента OpenHands. ACP-агенты ведут свой цикл, и critic для них может не
    работать [64].
- **Hooks.** Hooks в формате Claude Code лежат в `.openhands/hooks.json`. Шесть событий; hook может заблокировать
  действие [80]. Hooks на уровне workspace — v1.17 [77].
- **Память и долгие разговоры.**
  - Постоянная память агента — Settings → Agent Context [61][95].
  - Condenser — компонент, который заменяет старую часть истории кратким изложением [58][95].
  - Детектор зацикливания (stuck detector) [95].
  - Sub-agents внутри разговора через TaskToolSet [95].
- **Skills.**
  - Фильтр по признакам (v1.10) [77].
  - По умолчанию разрешены 11 skills из примерно 59 (v1.16) [77].
  - Установка из чата: `/add-skill` [61].
- **Авторство в git.** Commit-ы идут от имени пользователя, OpenHands — co-author [78].
- **Лимиты.** При ограничении частоты интерфейс пишет «Agent is rate-limited. Stopped.» [97]. В SDK есть переход на
  запасную модель для собственного агента [95]. Кода, который ждёт сброса окна подписки и потом продолжает работу, не
  найдено (подробно — «Как это устроено внутри», «Лимиты и стоимость») [101][102].

### 7. Automations — главная функция продукта

Automation — работа агента, которая запускается сама: по расписанию, по опросу или по событию.

- **Виды:** prompt; prompt с plugins; script bundle — детерминированный код плюс агент (v1.15) [81][77].
- **Запуск:** cron-расписание; опрос (агент сам опрашивает сервис через MCP); события [81][68]. Планировщик
  проверяет расписания раз в 60 s (`POLL_INTERVAL_SECONDS = 60`) [102].
- **События** [68][77]:
  - Свои webhook-и с подписью HMAC-SHA256 в заголовке `X-Signature-256`.
  - JMESPath (язык запросов к JSON) выбирает ключ события и фильтрует события. Типы событий задаются шаблонами вроде
    `*` и `build.*`.
  - Путь: `/api/automation/v1/events/<org-id>/<source-id>`.
  - URL должен быть доступен из интернета, поэтому локальный backend сначала надо открыть наружу.
  - Сервисам со своим форматом подписи, например Slack, нужен промежуточный relay.
  - Страница Events (v1.35) показывает по 50 событий. Источники событий меняются только через API.
  - Встроенные источники событий (GitHub, Jira Data Center, Bitbucket Data Center, Azure DevOps) — только в
    Enterprise [91][44][48].
- **Создание** [65][77]:
  - Разговор-ассистент составляет черновик automation (v1.27). Черновики сохраняются; значок ✦ показывает поля,
    которые заполнил агент.
  - Шаблоны подстраиваются под то, что уже подключено (v1.36).
  - У каждой automation сверху описание или сгенерированная сводка «How it runs» (v1.37).
- **Запуск и правка** [65][81]:
  - Run now; включить или выключить; изменить.
  - На Cloud переключатель «Keep sandbox alive» ставит `keep_alive`.
  - Timeout запуска — 10 минут по умолчанию, до 30 минут по запросу.
- **Наблюдение** [65][97][77]:
  - Статусы: PENDING, RUNNING, COMPLETED, FAILED, CANCELLED, SKIPPED. SKIPPED — лимит параллельных запусков
    организации, дневной лимит sandbox или выключенная automation [102]. Неопознанный исход показывается как «Needs
    review».
  - Текущая фаза запуска видна на карточке, в Activity Log и на Home.
  - Стоимость каждого запуска в USD с четырьмя знаками после запятой (v1.11).
  - Activity Log выгружается в CSV или JSON (v1.10).
  - На карточке: число запусков, доля успешных за последнее время, средняя длительность.
  - У script-запусков свои логи.
- **Сбои.** Баннер об отключении показывает причину, подробности и время (v1.19) [65][77]. Enterprise отключает
  automation сам после повторных сбоев [48].
- **Порядок** [77][65]:
  - tags (v1.11, v1.34), фильтр по владельцу, фильтр по service accounts (v1.39);
  - запуск от имени service account (v1.36);
  - админы могут править чужие automations (v1.38);
  - разговоры запусков на Cloud доступны другим только для чтения (v1.24).
- **Перенос.**
  - Экспорт в `<slug>.automation.json`; импортированная automation приходит выключенной [65].
  - **Git Sync** хранит automations в репозитории как `automation.yaml` плюс папка `tarball/`, по желанию с
    шифрованием (v1.14; для админов на Cloud — с v1.22) [69][77].
- **Где работает.** Диалог выбора предлагает два варианта [97]:
  - «Poll locally on your laptop» — перестаёт работать, когда ноутбук выключен;
  - «Use OpenHands Cloud» — отвечает всегда.
- **Каталог шаблонов** — около 27 в репозитории `OpenHands/extensions` [103]. Примеры:
  - **Issue to PR:** каждые 15 минут ищет issues с меткой `openhands`, работает в ветке `openhands/issue-N`,
    открывает draft PR с заголовком `[#N] …` и строкой `Closes #N` [66].
  - **GitHub PR Review Copilot:** ищет новые PR через GitHub MCP-сервер и запускает разговоры-ревью локально
    [55][67].
  - **Repository Monitor** отвечает на упоминания `@OpenHands`. **Slack Standup Digest** собирает сводку вчерашних
    сообщений в Slack [55].
- **Один разговор на тему.** Все события про один issue или PR попадают в один и тот же разговор, а пачка новых
  сообщений склеивается в один ход [102][45]. Подробно — раздел «Механизмы, которые стоит изучить», пункт 6.

### 8. Конвейер «issue → merged PR» в registry расширений

Это не экран Canvas, а skills и plugins в `OpenHands/extensions`, которые работают как automations [103][90].

- **Software Factory** — четыре automations: triage, разработчик, ревьюер и детерминированный watchdog (скрипт без
  агента, который делает merge); они ведут GitHub issue до merged PR [90][45]. Skills добавлены 2026-10-19 …
  2026-10-29 [103]:
  - шаги: разбор issues (triage) → issue в PR → ревью PR;
  - дополнения: поддержка AGENTS.md, watchdog доставки с auto-merge, закрытие устаревших CI, шаг QA изменений.
  - Сентябрьский обзор: Issue to PR отправляет готовые issues в стабильные разговоры, так что связанная работа
    возвращается в тот же разговор; PR Review проверяет точный head commit PR и передаёт решение maintainer-у [45].
- **Issue-to-PR worker** (`skills/github-issue-to-pr/scripts/worker.py`) [103]:
  - берёт issues с меткой-триггером, без PR и с закрытыми зависимостями; `priority:high` — первыми; ветка
    `<prefix>-<номер issue>`;
  - если статус `software-factory/review` на head PR — `failure` или `error`, отправляет задачу на доработку. Задача
    называет точный head SHA. Агент должен исправить каждое замечание или доказать, что правка не нужна. Push — в ту
    же ветку, без нового PR. Метка ревью ставится снова, чтобы проверили новый head;
  - сбой на одном issue не останавливает обход остальных.
- **Delivery watchdog** (`skills/github-delivery-watchdog`) — детерминированный скрипт без агента [103]. Делает merge,
  только если на точном head SHA есть успешные статусы `software-factory/tests` и `software-factory/review`,
  остальные проверки прошли и base актуальна. Ожидаемый head SHA передаётся в вызов merge, поэтому push, сделанный
  после проверки, в merge не попадёт.
- **Plugin `pr-review`** [103]: inline-комментарии, требование доказательств, ревью по файлам через sub-agents. После
  merge скрипт `scripts/evaluate_review.py` оценивает, исправили ли то, на что указало ревью (трассировка через
  Laminar). GitHub Action можно запускать с `agent-kind: acp`, тогда ревью делает подписка Claude или Codex [37].
- **Skill `/iterate`** ведёт PR через CI, бота-ревьюера и QA, пока всё не станет зелёным [103][38].
- **QA-агент**, который запускает приложение и выкладывает доказательства как ревью PR, — второй слой проверки у
  вендора [38]. Сценарий «QA changes» описан в документации [95].
- Собственный бот-ревьюер вендора на репозитории SDK за полгода: 1 000+ ревью на 900+ PR; им пользуются 90% PR;
  среднее время до merge −58%; покрытие тестами +~25%; точность приближается к людям (утверждение вендора) [38].

### Философия: манифест и эссе
Манифест без даты; его основной текст совпадает с постом о Series A от 2025-11-18 [5][21].
- Будущее разработки должны открыто формировать профессиональные инженеры. Агент — под MIT [5].
- Новая роль — «Agentic Engineer»: человек, который управляет десятками или тысячами облачных агентов, чтобы убрать
  рутинную работу. Множество агентов подходит не для всех задач [5].
- Масштаб — в облаке или VPC клиента. Локальные агенты — промежуточный шаг, а не цель [5].
- Открытость обязательна ради безопасности [5].
- Выбор модели — право команды: модель меняют, когда меняются качество и цена [5].
- Безопасность — во время работы: изолированные среды с аудитом, узкие права доступа, малый blast radius (ошибка
  агента задевает мало систем) [5].
- Обещания продукта: каждый агент — в контейнерном sandbox под контролем пользователя; каждый результат можно
  измерить; self-host или их облако; начать локально и вырасти до тысяч параллельных агентов [5].
- Призыв к читателю: найти рутину, ясно делегировать, мерить успех, считать управление агентами базовым навыком
  инженера [5].

### Открытый код и где проходит граница
- Основатели в 2024 году: Brennan — разработчик должен владеть своими инструментами, а технология слишком сильна для
  одной компании; Neubig — сделать один раз вместе вместо 50 компаний и помочь науке; Wang — воспроизводимость и
  баги, которые находит сообщество [10].
- Позиция по коммерческому open source (2025-06-11) [14]:
  - честно говорить пользователям и инвесторам одно и то же;
  - open source — не приманка для платной версии, а общественное благо, которое может пережить компанию;
  - исходная граница: open source — для разработчика на своём ноутбуке, платный продукт — для команд в облаке; в
    open-source-версии не было аутентификации и управления пользователями;
  - PR с Helm chart отклонили, чтобы не создавать неверных ожиданий;
  - аналитику добавили только после публичного обсуждения и сделали opt-in.
- Пост о Series A повторяет границу: open source максимально сильный для одного человека, команды платят за управление
  пользователями, облачный deploy и координацию [21].
- Время инженеров (июнь и ноябрь 2025): примерно 50/50 между open source и коммерческим продуктом; около трети
  инженеров занимаются исследованиями, и всё это уходит в open source [14][21].
- Управление проектом: компания называет себя «benevolent dictator» ради скорости. Допускает передачу проекта фонду.
  Предлагает сообществу fork, если компания перестанет вести себя добросовестно [51]. Две ценности сообщества: высокая
  открытость (публиковать планы, успехи и провалы) и высокая самостоятельность (готовность менять курс и браться за
  большие рискованные решения) [51].
- PR от имени человека. OpenHands перешёл на PR, владелец которых — человек. PR от бота позволяли тому, кто запустил
  бота, самому одобрить и смержить изменение без ревью, и за изменение никто не отвечал [165]. Commit-ы идут от имени
  пользователя, OpenHands — co-author [78].

### Как вендор думает об агентах
- **2024: один агент.** Один сильный универсальный агент лучше конвейера из нескольких. На передачах между агентами
  теряется контекст, структура навязывается неверно, такую систему труднее поддерживать [9].
- **Уровни автономии (2024).** Шкала Graham Neubig от Level 0 до Level 5 по образцу уровней SAE для беспилотных
  машин. Универсальные агенты — Level 4: человек внимательно проверяет результат, плюс контроль доступа [192].
- **Модель зрелости (сентябрь 2026)** для работы без присмотра — пять шагов [43]:
  1. Assisted — агент помогает человеку.
  2. Supervised autonomy — самостоятельность под наблюдением.
  3. Gated autonomy — человек проверяет на этапе pull request.
  4. Narrow unattended («lights-out») — узкие процессы совсем без людей.
  5. Broad unattended — широкая разработка без присмотра.
  - Каждый процесс получает автономию отдельно. Нужны стандартные входы, детерминированная проверка и непрерывная
    запись исполнения [43].
  - Запись исполнения — девять пунктов: входы, модель, tool calls, аргументы, результаты среды, изменения, проверки,
    вмешательства, паузы и повторы [43].
- **Outer loop важнее inner loop** (2025-12-02) [22]. Inner loop — цикл разработчика «написал — проверил». Outer loop —
  работа вокруг кода: issues, ревью, CI. Локальные агенты в IDE и CLI ускоряют inner loop. Больший выигрыш — облачные
  агенты в outer loop: запуск из Slack, Jira или GitHub, малый blast radius, без пошагового присмотра. По словам
  вендора, большинство разработчиков упираются в 2–3 локальных агента. Совет вендора: inner loop каждый выбирает сам,
  outer loop стандартизировать.
- **Узкое место — проверка (2026).** Ray Myers: объём кода больше никого не выделяет. Практики continuous delivery —
  тесты, модульность, типы, статический анализ — дают агенту полезную обратную связь от среды [27]. Xingyao Wang и
  Calvin Smith описывают проверку слоями: слой 1 — модель critic по траектории агента; слой 2 — skill code review и
  QA-агент на каждый PR; `/iterate` повторяет, пока PR не станет зелёным [28][38].
- **Безопасность — свойство всей системы (2026)** [39][41]: модели, harness, среда, identity, права и журналы.
  Практика: изолированный runtime без выхода в интернет (своё зеркало пакетов, mock-и внешних API, firewall на
  исходящий трафик); одобрение человека только для опасных категорий (секреты, исходящая сеть, системные пакеты, push
  и deploy); каждое действие записывается как структурное событие. OpenHands вступил в Open Secure AI Alliance под
  руководством NVIDIA 2026-08-10. Принцип: среда, модели и контроль — у пользователя [41].
- **Безопасность (2025).** Analyzer рисков сделан вместе с Invariant Labs; confirmation mode назван временной мерой;
  для Kubernetes — network policies, инструменты на eBPF и минимальные права агентам [15].

### Чем подход отличается: позиционирование вендора
- **Обещание.** Открытая (MIT) платформа, не привязанная ни к модели, ни к агенту. Растёт от ноутбука до тысяч
  агентов в облаке клиента [21][36].
- **Таблица самосравнения** со страницы /product (утверждение вендора) [2]:

  | | OpenHands | Devin | Claude Code | Factory |
  |---|---|---|---|---|
  | Open source | ✓ | – | – | – |
  | Не привязан к модели | ✓ | – | – | ✓ |
  | Sandbox runtime | ✓ | ✓ | – | ✓ |
  | Self-hosted | ✓ | – | ✓ | – |
  | SDK для coding-агентов | ✓ | – | ✓ | – |

- **Запускать чужих агентов, а не заменять их.** Декабрь 2025: OpenHands стал ACP-агентом внутри редакторов [23].
  Июнь 2026: Agent Canvas стал ACP-клиентом и запускает Claude Code, Codex и Gemini CLI на подписке пользователя; в
  облаке такая работа идёт по расписанию без отдельной оплаты API [37]. Октябрь 2026: добавлены Pi и OpenCode [77].
- **«Стройте на нас, а не делайте fork».** Анализ вендора (июль 2026): 5 679 merged PR за 12 месяцев в четырёх
  репозиториях, 31% — исправления багов, около 1.05M строк кода. Fork быстро устаревает, поэтому вендор советует
  настройку, MCP, skills или SDK [40].
- **Исследования питают продукт.** Critic обучен на production-трассах; сигнал исхода — merge PR и выживание кода
  [28]. Ещё: CAID [32], OpenHands Index [26], post-training модели внутри своего harness со Snowflake [47].
- **Свой продукт в своей разработке.** Около 20% commit-ов в январе 2025 и около 30% кода к августу 2025 — с участием
  OpenHands [157][174]. Бот-ревьюер работает на 90% PR репозитория SDK [38]. Перенос истории релизов делал агент
  OpenHands [100].

### Противоречия в подходе
1. **Локально или в облаке.** Манифест называет локальных агентов промежуточным шагом [5], а главный продукт с июня
   2026 — локальный Canvas [36].
2. **Sandbox обещан, но выключен.** Манифест обещает sandbox каждому агенту [5]. В V1 sandbox — по желанию by design
   [94], а установка через npm по умолчанию даёт агенту полный доступ к файловой системе [96].
3. **Граница open source.** Обещан «максимально сильный» open source для одного человека [14][21]. При этом backend
   Enterprise ушёл под лицензию, которая не считается открытой [108], а командные функции платные [91].
4. **Один агент → много агентов.** В 2024 вендор доказывал, что лучше один агент [9]; потом сделал CAID и Software
   Factory [32][90].
5. **CLI.** В 2025 CLI был первым потребителем SDK [16]; к концу 2026 он не поддерживается [50][104].

### Бизнес-модель
- **Open core.** Бесплатно и открыто (MIT): SDK, Agent Canvas, сервер automations, расширения [50][3]. Платно: hosted
  Cloud и self-hosted backend Enterprise под Polyform [108][50].
- **Источники дохода в эссе:** учёт затрат по token-ам, policy hooks, аудит [31][33].
- **Партнёры:** AMD [21][36], NVIDIA [36][41], MiniMax (бесплатный доступ к модели) [35], Modal и ngrok [36],
  DigitalOcean [77], Snowflake [47].
- **Продажи растут.** На странице About — CRO, account executives, business-development rep, forward-deployed
  engineer, customer success manager, Director of Product Marketing, Head of Product and Operations [6]. Ray Myers в
  феврале 2026 представлен как Chief Architect [27], но на странице About его нет; его текущая роль неизвестна
  (не подтверждено).
- Число клиентов и выручка не опубликованы (не подтверждено).

### Архитектура
- **Три репозитория.** Canvas — клиент на React/TypeScript и launcher на Electron [97]. Software Agent SDK — пакеты
  `openhands-sdk`, `openhands-tools`, `openhands-workspace`, `openhands-agent-server` [101]. Отдельный сервис
  automations [102].
- **Electron — оболочка над Python-сервисами.** `electron/main.mjs` запускает Agent Server и сервис automations через
  встроенный `uvx` и отдаёт статический клиент через локальный ingress [97].
- Документ об архитектуре Canvas прямо говорит: Canvas не выполняет действия агента и не даёт sandbox [97].
- **Типы workspace в SDK:** Docker, удалённый API, cloud, Apptainer и sandbox в Kubernetes с warm pool (заранее
  запущенные pod-ы) и runtime gVisor или Kata [101].
- **Принципы V1** [94]:
  - sandbox — по желанию;
  - компоненты — неизменяемые модели Pydantic без состояния;
  - единственный изменяемый объект — `ConversationState`;
  - агент и приложения строго разделены;
  - компоненты собираются друг с другом.
  - Статья о SDK (MLSys 2026): event sourcing почти не добавляет накладных расходов [148].
- **Что убрали при переходе на V1:** обязательный Docker-sandbox версии V0 [94]; архитектуру EventStream с
  publish/subscribe заменили синхронными разговорами [16].
- **Enterprise добавляет** [93][91]: Keycloak для SSO и ролей; proxy LiteLLM с бюджетами на организацию и
  пользователя по месячным циклам; Runtime API с warm pool, по pod-у на разговор; хранение разговоров в S3 или GCS;
  Laminar; каталог plugins; service accounts.

### Цикл агента
- **Один шаг** — `Agent.step` (`sdk/agent/agent.py`, с L738) [101]:
  1. выполнить действия, которые пользователь подтвердил;
  2. проверить hooks, которые могут заблокировать сообщение;
  3. собрать сообщения для LLM из кэшированного `View`, который проходит через condenser; если condenser вернул
     событие `Condensation`, шаг на этом заканчивается;
  4. вызвать LLM с `add_security_risk_prediction=True`: каждый tool call получает метку риска, которую модель ставит
     себе сама;
  5. превратить ошибки в шаги восстановления: неверный вызов функции → сообщение модели; блок по content policy →
     просьба переформулировать; испорченная история или переполнение окна → `CondensationRequest`;
  6. разобрать ответ: tool calls, текст, пустой ход или ход только с рассуждением.
- **Цикл запуска** — `LocalConversation._run` (`sdk/conversation/impl/local_conversation.py`, с L2310) [101]:
  - перед каждым шагом проверяет паузу и зацикливание;
  - на FINISHED запускает Stop hooks; hook может отказать в остановке и добавить замечание, и цикл продолжится
    (~L2343–2356);
  - останавливается на WAITING_FOR_CONFIRMATION; при превышении `max_budget_per_run` — ошибка `MaxBudgetReached`
    (L2419); на лимите шагов `max_iterations`, по умолчанию 500 (`sdk/settings/model.py` L1228);
  - ошибка аутентификации LLM → ERROR.
- **Статусы** (`sdk/conversation/state.py`): IDLE, RUNNING, PAUSED, WAITING_FOR_CONFIRMATION, FINISHED, ERROR, STUCK,
  DELETING [101].
- **Детектор зацикливания** (`sdk/conversation/stuck_detector.py`; пороги — `sdk/conversation/types.py` L150–161)
  [101]:
  - смотрит до 20 событий после последнего сообщения пользователя (L24);
  - ищет четыре шаблона: одно и то же действие и результат 4 раза; одно и то же действие с ошибкой 3 раза;
    3 сообщения агента подряд без tools; чередование A-B-A-B, повторённое 6 раз;
  - отдельно считает повторные ошибки переполнения окна контекста;
  - на серию одинаковых действий с ошибкой сначала отправляет одну подсказку агенту и только потом ставит STUCK
    (~L848–865 в `local_conversation.py`);
  - после возобновления начинает с чистого окна (`mark_resumed`).

### Планирование и декомпозиция
- **Plan mode.** `/plan` и `/code` переключают между preset-ом планирования и агентом-кодером [45]. Preset
  планирования получает только glob, grep и редактор, который может менять лишь `.agents_tmp/PLAN.md`
  (`tools/planning_file_editor/definition.py`) [101]. У шаблона плана жёсткие разделы: OBJECTIVE, CONTEXT SUMMARY,
  APPROACH OVERVIEW и другие (`tools/preset/planning.py`) [101].
- **Список задач.** Tool `task_tracker` ведёт список todo / in_progress / done внутри одного разговора [101].
- **Модели Epic-ов, ticket-ов и графа зависимостей** в Canvas и SDK нет (не найдено). Работу делят тремя способами:
  - агент вызывает tools для sub-agents (следующий раздел);
  - automations берут GitHub issues с меткой; worker из Software Factory берёт только issues, у которых закрыты все
    зависимости [103];
  - большие миграции — Refactor SDK, он в private beta [19].
- **Метод больших рефакторингов** (пост 2025-10-09) [19]:
  - разрезать работу на куски, которые агент закончит за 1–3 попытки; лучше всего — один commit или PR, который
    человек может проверить;
  - Refactor SDK ищет независимые части по границам каталогов и зависимостям;
  - параллельно работают около 5 агентов;
  - общий контекст — в AGENTS.md или в файле microagent (старое название skill — файла с инструкциями для агента) на
    общей ветке `v1-refactor`, которая постоянно обновляется; каждый агент ответвляется от неё и открывает PR в неё;
  - человек проверяет каждый PR и CI; агенты подтягивают слитую работу и обычно сами решают конфликты;
  - «fixers» — prompts или скрипты; «verifiers» — программы; пример проверяет, что код собирается под JDK 25 без
    предупреждений об устаревших API;
  - по словам поста, такую работу часто удаётся автоматизировать только на 80–90%.
- **Исследование CAID (Geng & Neubig), не продукт** [150][32]:
  - агент-менеджер строит план с учётом зависимостей;
  - агенты-инженеры работают в отдельных git worktree;
  - работа возвращается через ветки и merge и проверяется тестами;
  - без worktree результаты заметно падают [32][150].
  - **Цифры в источниках расходятся:** аннотация статьи — +25.6 пункта на PaperBench и +14.7 на Commit0 [150]; пост
    от 2026-04-27 — около 26.7% и 14.3% [32].
  - Стал ли CAID функцией продукта, неизвестно (не подтверждено).

### Параллельность и координация
Параллельная работа устроена в шесть слоёв.
1. **Параллельные tool calls в одном шаге.** `ParallelToolExecutor` (`sdk/agent/parallel_executor.py`) соблюдает
   `tool_concurrency_limit`; по умолчанию 1, то есть без настройки вызовы идут по очереди [101]. `ResourceLockManager`
   даёт каждому объявленному ресурсу FIFO-lock с timeout-ом (`sdk/conversation/resource_lock_manager.py` L21–27):
   файл 30 s, terminal 300 s, browser 300 s, MCP 300 s, прочий tool 60 s [101]. Tools объявляют ресурсы через
   `DeclaredResources`; вызовы tool-а без объявления идут по одному через общий mutex этого tool-а
   (`sdk/tool/tool.py`) [101]. У каждого исполнителя свой lock manager, поэтому sub-agents и другие разговоры эти
   lock-и не делят (`sdk/agent/parallel_executor.py`) [101].
2. **TaskTool — sub-agent, который блокирует родителя.** Запускает `LocalConversation` в том же процессе и workspace,
   наследует секреты и политику подтверждений (`tools/task/manager.py`) [101]. Возвращает итоговый ответ или ошибку с
   частичным выводом и добавляет свою стоимость к метрикам родителя. Preset-ы: default, bash_runner, code_explorer,
   web_researcher. Исходы: success, partial_success, blocked, failed, unknown (`tools/preset/task_outcome.py`). Свои
   sub-agents — Markdown-файлы; при совпадении имён побеждает первая регистрация (`sdk/subagent/load.py`) [101].
   Открытый баг: TaskTool держит lock состояния родителя всё время работы sub-agent-а — sdk#4537 [144].
3. **WorkflowTool — программа fan-out (раздать работу многим агентам и собрать ответы), которую пишет сам агент.**
   Агент пишет на Python `async def main(wf)` с `run_agent`, `map_agents`, `reduce_agent`, `pipeline`, `flatten`.
   `max_concurrency` по умолчанию 8, максимум 64 (`tools/workflow/definition.py` L35–40). Первая версия работает в
   том же процессе [101].
4. **Дочерние разговоры.** В SDK — `StartChildConversationTool` с изоляцией `worktree` (по умолчанию) или `shared`
   (`tools/child_conversation/definition.py` L36) [101]. В Canvas — клиентский tool `launch_child_conversation` с
   target local или cloud [97]. Родитель получает только id, URL и статус в сообщении с префиксом
   `[child-conversation] ` (`src/constants/child-conversation.ts` L20) [97]. Журнал запусков хранится в localStorage
   браузера. Связь с родителем требует Agent Server 1.37.1 или новее (L37) [97]. Документация говорит, что результат
   возвращается родителю, — это расхождение описано в «Функциях», раздел 5 [56].
5. **Много разговоров на одном Agent Server.** `max_concurrent_runs` по умолчанию 10 (`server/config.py` L348); сверх
   этого сервер отвечает HTTP 429 [101]. Разрешение на запуск `RunSlot` держится через цепочку запусков
   (`server/event_service.py`) [101].
6. **Automations.** Обычно каждый запуск — отдельный разговор. События про один issue или PR попадают в один общий
   разговор (раздел «Механизмы, которые стоит изучить», пункт 6) [102].
- **Координация.** Общей доски задач, lock-а между разговорами и оркестратора merge в Canvas и SDK нет (не найдено)
  [97][101]. Координация остаётся за git-ветками, людьми и watchdog-ом со статусами в registry расширений [103].
- **Известные проблемы:**
  - больше трёх разговоров — Canvas очень медленный и отказывает в соединении; issue открыт с 2026-08-18 [128];
  - один разговор не может выбрать несколько репозиториев; запрос открыт с 2025-04-07 [112];
  - нельзя прервать, направить или поставить в очередь сообщение во время работы агента; issue открыт с 2026-09-02
    [145].

### Изоляция
Agent Server даёт три runtime на разговор [101]. Canvas показывает выбор с v1.34.0 [77].
- **Local — по умолчанию.** Агент работает прямо в папке на хосте с полным доступом к файловой системе [96].
  Умолчания в коде: `default_runtime = "local"` в SDK (`sdk/settings/model.py` L1270) [101] и
  `DEFAULT_WORKSPACE_MODE = "local_repo"` в Canvas (`src/utils/workspace-mode.ts` L5) [97]. README предупреждает:
  разговоры в одной папке хоста делят файлы; советует отдельные папки или worktree [96].
- **Worktree** — выключен по умолчанию (`ConversationConfig.worktree`) [101]:
  - путь `/tmp/conversation-worktrees/<conversation_id>/<project>` (`server/config.py` L287);
  - ветка `openhands/<conversation_id>` (`DEFAULT_WORKTREE_BRANCH_PREFIX`, `sdk/settings/model.py` L163);
  - база: `git fetch origin` и `origin/<default branch>`; если не вышло — локальные `main`, затем `master`, затем
    `HEAD`; базу можно задать как текущий head или именованный ref (`server/conversation_service.py` ~L120–310);
  - в контекст агента добавляется блок с пояснением про worktree;
  - корень в `/tmp` может не пережить перезагрузку (предположение, не проверено).
- **Docker** [96][101]:
  - включается переменной `OH_CONVERSATION_RUNTIME=docker`; нужен `OH_SECRET_KEY`;
  - у каждого разговора свой контейнер со своим Agent Server;
  - флаги: `--cap-drop ALL`, `no-new-privileges`, `--user uid:gid`, `--pids-limit`, `--memory`, `--cpus`,
    `--ulimit core=0` (`server/docker_runtime/registry.py` ~L728–753);
  - порт публикуется только на 127.0.0.1 (~L762–783);
  - флага ограничения сети не найдено; есть ли сетевая изоляция, неизвестно (не подтверждено);
  - гибридный registry держит локальные и Docker-разговоры рядом (`server/docker_runtime/hybrid.py`).
- **Docker — источники расходятся.** Страница продукта пишет, что раньше Canvas создавал контейнер на разговор, а
  теперь запускает один Agent Server, и Docker — по желанию [1]. Сентябрьский обзор: отдельный Docker runtime на
  разговор вернулся как опция и включается одной переменной окружения [45]. С v1.34.0 (2026-10-27) пользователь
  выбирает Local, Worktree или Docker для каждого разговора [77].
- **Worktree — обещание и код расходятся.** Страница продукта обещает, что каждый из параллельных агентов изолирован
  в своём git worktree [1]. В коде worktree по умолчанию только у дочерних разговоров (`isolation="worktree"`) [101].
  В августе CEO сам попросил настройку «worktree по умолчанию»: он не мог добиться, чтобы Canvas стабильно его
  использовал. Co-founder Xingyao Wang отметил, что интерфейс не показывает, где правит агент — в worktree или в
  исходной папке [123].
- **Enterprise и cloud.** Каждый разговор получает pod из warm pool через Runtime API [93]. Стратегии группировки
  sandbox (none, newest, LRU, fewest, any) позволяют разговорам делить один sandbox; документация предупреждает, что
  общий sandbox — не граница безопасности [93].
- **Позиция 2025 года.** Для self-hosted Kubernetes вендор советует network policies, инструменты на eBPF и
  минимальные права агентам [15].

### Состояние и память
- **Хранилище — event sourcing.** Разговор — это `base_state.json` плюс по JSON-файлу на событие
  (`events/event-00001-<uuid>.json`), под защитой `.eventlog.lock` (`sdk/conversation/persistence_const.py`,
  `sdk/conversation/event_store.py`) [101].
- **Дерево событий.** `fork(from_event_id)` (L913) и `navigate_to` (L1058) в `local_conversation.py` стоят за
  действием «Branch from here» [97][101][56].
- **Побочные вызовы.** `ask_agent` (L3293) отвечает на побочный вопрос и не меняет состояние; `rerun_actions` (L3455)
  повторяет записанные действия [101].
- **Owner lease.** Файл `owner_lease.json` с TTL 45 s не даёт второму процессу сервера вести тот же разговор
  (`server/conversation_lease.py` L21) [101].
- **Восстановление после рестарта** (`server/conversation_service.py` ~L2305–2325) [101]:
  - при старте разговоры со статусом RUNNING загружаются и получают ERROR и событие восстановления: в них может
    остаться недоделанный tool call;
  - сами они не продолжаются;
  - живой lease по-прежнему не даёт перехватить разговор.
- **Архив.** Локальные разговоры, которые нельзя продолжить, уходят в архивную историю (v1.21.0) [45][77].
- **Выгрузка.** Разговоры без работы выгружаются из памяти через 20 минут (`server/config.py` L38) [101].
- **Condenser** `LLMSummarizingCondenser` (`sdk/context/condenser/llm_summarizing_condenser.py` L64–72) [101]:
  - значения по умолчанию: `max_size` 240 событий, `keep_first` 2, `minimum_progress` 0.1;
  - заменяет старшую половину истории кратким изложением;
  - журнал остаётся только на добавление: событие `Condensation` помечает, что выбросить, а `View` это применяет;
  - мягкие триггеры — размер и token-ы; жёсткие — явный запрос или ошибка переполнения окна. Жёсткий сброс — до 5
    попыток, каждая в 0.8 раза меньше;
  - пост 2025-04-09: до 2 раз дешевле на ход при почти той же доле решённых задач — 54% против 53% на части SWE-bench
    Verified (набор задач по исправлению реальных issues) [13];
  - Canvas показывает индикатор контекста и ручную кнопку сжатия [97].
- **Файлы памяти.** Пользователь — `~/.openhands/memory/MEMORY.md`; проект — `<workspace>/.openhands/memory/MEMORY.md`.
  Бюджет — 6000 символов; лишнее отрезается сверху (`sdk/context/memory.py` L24). Дневные журналы `YYYY-MM-DD.md`
  читаются только по запросу [101].
- **Инструкции и skills.**
  - SDK читает AGENTS.md, CLAUDE.md, .cursorrules и вложенные AGENTS.md [101].
  - Skills лежат в `.agents/skills` (старое имя — `.openhands/microagents`) и в публичном marketplace расширений
    [101][103].
  - Триггеры: ключевое слово, задача, путь. Правило для пути добавляется в результат tool-а, когда агент впервые
    трогает подходящий файл (`_maybe_inject_path_rules`, `local_conversation.py` L663) [101].
  - Для ACP-агентов skills и контекст репозитория вписываются в prompt до отправки внешнему агенту [37].
- **Дополнительные tools для контекста** [101]:
  - `ask_oracle` — второе мнение от LLM-профиля «oracle», без состояния;
  - `tom_consult` — модель намерений пользователя;
  - `route_task_to_model` и RouterLLM — выбор модели под задачу.

### Проверка качества
- **Внутри разговора.**
  - **Critic** (`sdk/critic/`) [101]:
    - режимы (`base.py` L62): `finish_and_message` (по умолчанию) — оценка при завершении и на сообщениях агента;
      `all_actions` — оценка каждого действия;
    - доработка: при оценке ниже 0.6 замечания уходят агенту, до 3 раундов (`base.py` L42–52);
    - реализации: hosted `APIBasedCritic`, `AgentFinishedCritic`, `EmptyPatchCritic`, `PassCritic`;
    - hosted critic — классификатор, обученный на реальных исходах. Его таксономия: проблемы поведения агента,
      ожидаемые follow-up пользователя и проблемы инфраструктуры [101][149];
    - сигнал исхода при обучении — merge PR и выживание кода [28].
  - **Судья `/goal`** [101]:
    - вход — `run_goal(conversation, objective, judge_llm, max_iterations=10)` (`sdk/conversation/goal/runner.py`
      L35);
    - модель-судья читает переписку и возвращает JSON `{score, complete, missing}`; по умолчанию судья — та же LLM,
      что у агента;
    - доказательство, которого нет, которое неуверенно или только заявлено, считается невыполненным;
    - если цель не достигнута, follow-up перечисляет недостающее и велит проверить реальное состояние workspace, а не
      полагаться на память;
    - `GoalController` — чистая state machine без I/O;
    - routes сервера: `/goal`, `/goal/stop`, `/goal/resume` (`server/conversation_router.py` ~L445).
  - **Stop hooks** могут отказать агенту в «готово» [101]. Automations добавляют hook, который требует вызвать tool
    завершения (`auto/presets/finish_tool_hook.py`) [102].
- **Вокруг PR** — в registry расширений: plugin `pr-review`, skill `/iterate`, Software Factory, issue-to-PR worker с
  доработкой по точному head SHA и delivery watchdog (подробно — «Функции», раздел 8) [103].
- **В интерфейсе Canvas** кнопка PR только отправляет агенту prompt создать PR
  (`src/components/features/chat/git-control-bar-pr-button.tsx`) [97]. Отрисовки CI-проверок в `src/` не найдено;
  показывает ли Canvas статус CI где-то ещё, неизвестно (не подтверждено) [97].
- **Процесс в самом репозитории Canvas** [98][97]:
  - PR несут доказательства файлами в `.pr/<topic>/` — скриншоты, видео, JSON, HTML-дизайн; шаблон PR требует
    описать проверку end-to-end командами, logs или скриншотами. Файла `evidence.md` и папки `test-evidence/` в 60
    последних merged PR нет;
  - в описании PR есть раздел `HUMAN:`, который пишут только люди;
  - skills проверки `verify-*` только для чтения у агентов-исполнителей; их меняют отдельным PR в отдельном контексте
    агента;
  - версия зависимости должна быть не моложе 7 дней;
  - проверки CI: lint, test, build, build:lib и `npm pack --dry-run`.

### Восстановление после сбоев
- **Повторы LLM.** `num_retries` = 5, ожидание 8–64 s, множитель 8 (`sdk/llm/llm.py` L385–390) [101].
  - Временными считаются HTTP 408, 409, 429 и 5xx (`sdk/llm/exceptions/classifier.py`) [101].
  - Если Retry-After от сервера длиннее максимального ожидания, повторы останавливаются сразу, без сна
    (`_StopBeforeLongWait`, `sdk/llm/utils/retry_mixin.py` L40) [101].
- **Квота не повторяется никогда.** Шаблоны `usage_limit_reached` и `insufficient_quota` (`classifier.py` L74–82)
  [101]. Комментарий в коде объясняет: такие ошибки не пройдут, пока лимит не сбросится или не поднимется, а повторы
  только тратят время ожидания. Отказ по бюджету также запрещает переход на запасную модель [101].
- **Запасная модель.** `FallbackStrategy` переключает на другие LLM-профили при временных ошибках
  (`sdk/llm/fallback_strategy.py`) [101].
- **Таксономия сбоев.** `FailureKind` — восемь значений: auth, quota, rate_limit, config, transient, agent_action,
  internal, unknown (`sdk/event/error_classification.py` L9–17). Рядом — `FailureAction`: none, retry, settings
  [101].
- **Зацикливание** — подсказка, потом STUCK. **Рестарт** — RUNNING превращается в ERROR плюс событие восстановления
  (оба описаны выше) [101].
- **ACP-агенты** [101]:
  - ошибки хода делятся на три вида: отказ по usage или content policy, нужна повторная аутентификация, общая ошибка
    prompt (`_classify_acp_turn_error`, `sdk/agent/acp_agent.py` L1358);
  - исчерпанный лимит у провайдера приходит как `ACPPromptError` и заканчивает запуск в ERROR;
  - timeout-ы: 1800 s без активности prompt-а (счётчик сбрасывается на каждом обновлении от ACP-сервера; L1941);
    90 s на старт;
  - открытый баг: если ACP `session/load` не удался, молча начинается новая сессия без старого контекста — sdk#5094
    [146].
- **Запуски automations** [102]:
  - watchdog переводит в FAILED запуски RUNNING, у которых прошёл `timeout_at`;
  - запуск длится 10 минут по умолчанию и не больше 30 (`auto/config.py` L234–235); запас timeout-а 120 s, жёсткий
    запас 600 s;
  - подготовка sandbox — до 3 попыток.

### Лимиты и стоимость
- **Ожидания сброса лимита нет.** Кода, который ждёт сброса окна подписки и потом продолжает работу, в SDK, сервере и
  сервисе automations не найдено [101][102]. Квота останавливает запуск [101].
  - Automation отключается сама после трёх запусков подряд со сбоем вида auth, config, quota или blocked
    (`PERMANENT_FAILURE_KINDS`, `auto/utils/unhealthy.py` L47; порог `failure_disable_threshold = 3`,
    `auto/config.py` L669). Правило «N любых сбоев подряд» по умолчанию выключено (L674) [102].
  - Страница automation показывает причину отключения со временем (v1.19.0) [45][77].
  - Интерфейс Canvas при ограничении частоты пишет «Agent is rate-limited. Stopped.» [97]. Свои HTTP-запросы к
    backend-у при ответе 429 Canvas повторяет с удвоенной задержкой (`src/utils/rate-limit-retry.ts`); это про запросы
    интерфейса к серверу, а не про лимиты модели [97].
- **Подписки для ACP-агентов.** Вход по подписке важнее API-ключа: у Claude Code — запись в Keychain или
  `~/.claude/.credentials.json`; у Codex — `~/.codex/auth.json` [97]. В контейнерах вход передаётся как
  `CLAUDE_CODE_OAUTH_TOKEN` или `CODEX_AUTH_JSON` [97]. OpenHands Cloud подставляет вход по подписке при старте сессии
  [37].
  - Известный пробел: у ACP-агентов пока нет отдельного HOME на разговор (`acp_isolate_data_dir` не выведен в
    настройки). Параллельные ACP-разговоры одного провайдера в одном контейнере делят состояние CLI [97].
- **Учёт затрат.** Статистика ведётся по usage id: agent, condenser, `task:<id>`, oracle
  (`sdk/conversation/conversation_stats.py`) [101]. Стоимость ACP берётся из сообщений ACP `UsageUpdate` или
  оценивается по token-ам и ценам LiteLLM [101]. Панель Usage подписывает сумму ACP как оценку по ценам API, а не счёт
  (`usage-panel.tsx` L27) [97].
- **Бюджеты.** Budget meter на вкладке Usage только показывает и не останавливает запуск (v1.38.0, 2026-11-10) [77].
  Activity Log показывает стоимость запуска (v1.11.0, 2026-08-07) [77]. Единственная жёсткая остановка в коде —
  `max_budget_per_run` в SDK [101]. Enterprise применяет бюджеты в proxy LiteLLM [93].

### Права и безопасность
- **Политики подтверждения** (`sdk/security/confirmation_policy.py`) [101]:
  - `AlwaysConfirm`, `NeverConfirm`, `ConfirmRisky`; у ConfirmRisky порог HIGH, и риск UNKNOWN тоже подтверждается;
  - настройка `confirmation_mode` по умолчанию False, то есть NeverConfirm (`sdk/settings/model.py` L1241,
    L1404–1414);
  - с подтверждением и analyzer-ом «llm» политика — ConfirmRisky; с любым другим analyzer-ом — AlwaysConfirm;
  - из коробки ничто не ждёт человека.
  - Документация по confirmation mode: CLI по умолчанию спрашивает пользователя только о HIGH [89].
- **Analyzer-ы риска** (`sdk/security/`) [101]:
  - `LLMSecurityAnalyzer`: модель-исполнитель сама размечает свои вызовы;
  - `ToolShieldLLMSecurityAnalyzer`: отдельная модель-охранник;
  - `GraySwanAnalyzer`: внешний API;
  - `PatternSecurityAnalyzer` и `PolicyRailSecurityAnalyzer`: детерминированные, со стабильными ID детекторов вроде
    `exec.destruct.rm_rf`;
  - `EnsembleSecurityAnalyzer`: берёт наибольший риск, а при сбое ставит HIGH.
- **Hooks** (`sdk/hooks/`) [101]: те же имена событий, что у Claude Code, — PreToolUse, PostToolUse,
  UserPromptSubmit, SessionStart, SessionEnd, Stop. Виды hook-ов: command, prompt, agent. Exit code 2 блокирует;
  другие ненулевые коды — нет.
- **Секреты** маскируются в событиях (`sdk/conversation/secret_registry.py`) [101].
- **Agent Profiles** (схема v4, `sdk/profiles/agent_profile.py`) [101][45]: allow-list секретов, MCP-серверов,
  интеграций и tools; выключенные skills; LLM-профиль, condenser, настройки проверки и `tool_concurrency_limit`.
- **ACP-агенты обходят всё это** (`sdk/agent/acp_agent.py` L1784–1801, `sdk/settings/acp_providers.py`) [101]:
  - `request_permission` выбирает первый предложенный вариант, обычно «allow once», и пишет одобрение в log;
  - режимы сессии: `bypassPermissions` у Claude Code, `agent-full-access` у Codex, `default` у Gemini CLI (его режим
    `yolo` падает при старте, а мост и так одобряет все запросы), `yolo` у Kimi, `build` у OpenCode; Pi режим не
    получает;
  - запросы MCP elicitation (сервер просит пользователя что-то ввести) отклоняются;
  - безопасность ACP держится только на изоляции runtime, а она по умолчанию выключена.
- **Точки, где участвует человек.** Есть: подтверждение (выключено по умолчанию), пауза и прерывание
  (`local_conversation.py` L3151, L3178), `/goal/stop`, plan mode, передача решения maintainer-у в PR Review,
  повторное включение отключённой automation, раздел `HUMAN:` в PR репозитория Canvas [101][45][102][98]. Нет: явно
  направить ход или поставить сообщение в очередь [145].
- **Observability.** Трассировка Laminar / OpenTelemetry настраивается через `LMNR_PROJECT_API_KEY` и `OTEL_*`
  (`sdk/observability/laminar.py`) [101]; в Enterprise Laminar встроен [93]. Webhook-и разговора копят по 5 событий и
  отправляют не реже раза в 30 s (`WebhookSpec`, `server/config.py`) [101]. У automations — фазы и структурные
  подробности статуса запуска (`auto/utils/run_status_detail.py`) [102].
- **Отчёт о безопасности:** ключи API backend-ов хранятся открытым текстом в `localStorage` браузера [125].

### Как менялось отношение, 2024 → 2026
- **Март 2024, запуск.** Комментаторы писали, что кроме README почти ничего нет. Один не смог скачать Docker-образ
  sandbox [151].
- **Август 2024, тред о статье.** Результаты работали, но дорого (таблица ниже) [153][154]. Maintainer (Brennan):
  помогает на нескольких разовых задачах, но ещё не стал основной частью его работы, в отличие от Copilot [155].
  Стоимость он назвал одной из главных проблем проекта [154]. Пользователи просили интеграцию с IDE и беспокоились,
  что браузерный агент может выйти за пределы sandbox [152].
- **Декабрь 2024 — март 2025.** Команда, сравнивавшая Devin, OpenHands и свой инструмент, нашла OpenHands далеко
  позади Devin [156]. Отдельные люди: раздражает и дорого, не быстрее ручной работы [158]; хорошо, но около $8 в час
  [161]; падал рано и зависал на настройке проектов Kotlin и Go, быстро упирался в лимиты Claude [162]; не готов для
  production, но поучительно наблюдать [160].
- **Середина 2025.** OpenHands стал основным harness-ом для локальных моделей. Несколько человек назвали Devstral
  (модель Mistral, обученную под OpenHands) плюс OpenHands своей самой надёжной связкой; один поставил её выше Gemini
  CLI [167][171]. Появились активные пользователи [173]. Другие: многообещающе, но сложно [166]; просили объяснить,
  чем он отличается от других [174].
- **Конец 2025 — 2026.** Обсуждение — в основном сравнение с Claude Code [173][180][183]. Несколько человек ушли на
  Claude Code, Cursor, pi, OpenCode, Shelley, Paseo или свой harness [173][178][182][186][188][189]. Отзывы об Agent
  Canvas приходят почти только через GitHub issues: 260 issues с меткой `agent-canvas`, из них 204 — bug [143].

### Что хвалят
- **Открытый код, любая модель, self-hosting.** Один пользователь называет OpenHands и Codex CLI любимыми открытыми
  альтернативами Claude Code [170]. Основатели продвигают его как открытый вариант без привязки к модели [174][168].
- **Локальные модели.** Devstral + OpenHands работает на одной GPU с 24 GB и было основным рабочим инструментом
  минимум у одного активного пользователя [171]. Другой использует модели Qwen с OpenHands локально [167]. Не все
  согласны: Simon Willison не нашёл локальной модели, которая помещается в Mac на 64 GB или Spark на 128 GB и
  надёжно ведёт агентов вроде OpenHands [175].
- **Sandbox по умолчанию (2025).** В пилоте одного пользователя работа агента внутри VM была ключевым требованием
  [173].
- **Ежедневная работа (2025).** Один пользователь месяцами работал с ним каждый день локально, в CLI и в облаке.
  Вывод: менее отполирован, чем Devin, но так же способен. Хвалит отзывчивость команды [173].
- **Обучение агента со временем.** Когда агент выбирает архитектуру, которая не нравится, тот же пользователь
  добавляет «microagent» — постоянный файл контекста, похожий на CLAUDE.md. Так агент со временем принимает его
  соглашения [173].
- **Мелкие нудные задачи.** Maintainer: в январе 2025 около 20% commit-ов в репозиторий OpenHands написал или
  соавторствовал OpenHands; любимые задачи — конфликты merge и упавшие linter-ы; выгода — не переключать контекст
  [157]. К августу 2025 — около 30% кода [174].
- **Прозрачность.** Нравится видеть шаги агента в терминале [159]; хвалят OpenHands Index [181].

### На что жалуются
- **Установка и инфраструктура.**
  - Docker — частая проблема [151][115].
  - Поддержка Podman — второй по популярности запрос за всё время (25 голосов). Stale-бот — бот, который закрывает
    issues без активности, — закрыл его после того, как пользователи выложили свои обходные пути [142].
  - Старт sandbox медленный — около 15 s на поток на современном ноутбуке [142].
  - Январь–март 2026: на Linux sandbox не стартовал за 120 s. Maintainers ответили, что почти все они на macOS, и
    воспроизвести трудно. Новичок спросил, не умирает ли проект; другой назвал баг блокирующим. Issue закрыт примерно
    через шесть недель [115].
- **Стоимость.** Ранние задачи стоили $10–$50 и больше [153][154]; один потратил $60 за три выходных [163]. В 2026
  жалоба другая: нужен контроль расходов на запусках без присмотра, а не низкая цена [133].
- **Надёжность агента.**
  - Правка файла падала, если заменяемый текст не совпадал точно — баг с Devstral, 12 голосов [142].
  - Ошибки параметров tool call с Qwen3-Coder; поломка на новых тегах формата чата gpt-oss [171].
  - Плохо правит повторяющийся код [159].
  - Без контекста проекта агент делал один неудачный шаг за другим и не мог из этого выйти [169].
- **UX и дизайн.** Неуклюжий и ограниченный, со слабым дизайном; похожий веб-UI у OpenCode лучше [182]. Один ушёл
  из-за настройки Docker и emoji в выводе [188]. Схема «контейнер на агента» тяжёлая [185].
- **Скрытая привязка к модели.** Обучение Devstral под OpenHands сделало её хуже в других harness-ах, например в Roo
  и Cline [176].
- **Процесс проекта.**
  - 1 433 из 5 633 issues закрыты с меткой `Stale` [143]; так закрылся и популярный запрос Podman [142].
  - Maintainers открыто используют AI-агентов для triage и поддержки [132][133][116].
  - Внешние contributors пишут, что CI блокирует их PR, пока на issue нет метки `ready-for-dev`; поставить её может
    только автор issue или maintainer [131][139].
  - Человек со стороны не смог войти в Slack по ссылке с сайта; понадобилось новое приглашение [129].

  - На Cloud в длинных сессиях результаты tools приходили не к тем вызовам, и сессии обрывались посреди задачи [138].

  - Нет состояния «прочитано / не прочитано», поэтому «закончил и ждёт» выглядит как «работает» [122].
  - Maintainer попросил по умолчанию группировать разговоры по workspace [122].

  возобновлении разговора замечать изменения в git за время простоя: смену ветки, новый HEAD, локальные правки [140].

  - Редактор профиля подписки подставляет другую модель [116].
  - С настроенным OpenRouter расход всё равно списывался с кредитов OpenHands [116].
  - Ошибки проверки ключа показываются как сырой JSON; зелёная галочка может стоять рядом с ключом, который не

  - Ключи API backend-ов хранятся открытым текстом в `localStorage` браузера [125].

    вешает агента; ошибки путей в automations [119].

  - Contributor отмечает, что дочерние разговоры работают по принципу fire-and-forget. Он просит «team»: устав, роли,

### Почему приходят и почему уходят

  изоляция в Docker или VM [173]; self-hosting и свои продукты поверх [187][185].

  следить [152]. Один предпочёл автоматические commit-ы и `/undo` у Aider [166].

- **С Gemini CLI:** пользователь локальных моделей ставит OpenHands выше [171].

## Слабые места и чего нет

- **Изоляция по умолчанию слабее обещаний.** Новый разговор работает прямо в папке хоста с полным доступом к файловой
  системе; worktree и Docker надо включать [96][97][101]. Страница продукта обещает worktree каждому агенту [1].
  Интерфейс не показывает, где правит агент [123].
- **ACP-агентам разрешено всё.** Каждый запрос разрешения одобряется автоматически; сессии стартуют в режимах вроде
  `bypassPermissions` и `agent-full-access` [101]. Подтверждение по умолчанию выключено и для собственного агента
  [101].
- **Лимит подписки или квота — конец работы.** Квота не повторяется; ACP-запуск заканчивается в ERROR; automation
  отключается после трёх таких сбоев подряд; ожидания сброса окна и продолжения нет (не найдено) [101][102].
- **Масштаб.** Больше трёх разговоров — медленно и с отказами соединения; упавший Agent Server не перезапускается
  [128].
- **Хрупкое локальное состояние.** Один испорченный разговор ломает весь список [131]; файлы workspace терялись при
  рестарте Docker (исправлено) [139]; Cloud путал результаты tools в длинных сессиях [138].
- **Расходы.** Budget meter только показывает [77]. Есть ли жёсткий потолок на разговор в Canvas — источники
  расходятся [78][133]. Во время работы расход показывается как $0 [133]. «Total Cost» непрозрачен [141].
- **Взаимодействие.** Terminal только для чтения, browser не интерактивный [97]; явно направить агента или поставить
  сообщение в очередь во время хода нельзя [145].
- **Уведомления и статус.** Только звук и заголовок вкладки [97]; нет unread [122]; idle и running выглядят одинаково
  [122].
- **Координация.** Нет Epic-ов, ticket-ов, графа зависимостей и общей доски задач (не найдено) [97][101]. Дочерние
  разговоры по коду не возвращают вывод родителю [97] (документация говорит иначе [56]). TaskTool держит lock
  родителя [144].
- **Несколько репозиториев** в одном разговоре — нельзя; это самый популярный открытый запрос [112].
- **Проблемы ACP.** Пустой Terminal для Claude Code, plan mode не работает, нет «Thinking» [118]; `session/load` молча
  теряет контекст [146]; параллельные ACP-разговоры делят состояние CLI [97]; critic для ACP-агентов может не
  работать [64]; подписка ChatGPT Business не принимается [116].
- **CI и PR в интерфейсе.** Статуса CI в Canvas не найдено (не подтверждено) [97]; кнопка PR — только prompt агенту
  [97]; конвейер PR живёт в registry расширений, а не в интерфейсе [103].
- **Сборки и платформы.** Сборки не подписаны ни на одной платформе [97]; нет auto-update [120]; баги Windows с вводом, зависанием и
  путями [119]; Windows-задача CI зелёная при выключенных проверках [119]; maintainers почти все на macOS и с трудом
  воспроизводят баги Linux [115].
- **События локально.** Automations по событиям на локальном backend-е требуют публичный URL [68].
- **MCP OAuth.** Redirect зашит на localhost [137].
- **Модели.** Модель по умолчанию в августе 2026 сменилась как минимум дважды: GLM 5.2 → Kimi K3 → GPT-5.6 Sol
  [77]. Есть issue #16356 о том, что конфигурация LLM замораживается при создании разговора; его дата и статус не
  проверены [124].
- **Безопасность.** Ключи API backend-ов — открытым текстом в `localStorage` [125]; Apps работают в контексте
  браузера Canvas без sandbox [63][42]; worktree лежат в `/tmp` [101].
- **Процесс проекта.** Примерно каждый четвёртый issue закрыт stale-ботом [143]; обратная связь в основном в Slack,
  куда не попасть без приглашения [96][129]; собственный бот triage ответил 191 раз на одном issue [132].
- **Чего нет вообще** (по найденному): пространственного холста — «Canvas» только название, интерфейс — список, чат и
  панель [56][97][52]; системных уведомлений ОС (не подтверждено) [97]; учёта окна подписки и планирования запусков
  под лимиты [101][102]; передачи сессии между машинами [180].

- **Тезис вендора против подхода worfy.** По словам вендора, большинство разработчиков упираются в 2–3 локальных
  агента, а больший выигрыш дают облачные агенты в outer loop [22]. worfy по описанию — локальное приложение одного
  человека с работой без присмотра.
- **Общая база.** Оба продукта строятся вокруг агентов, которые уже есть у пользователя по подписке (Claude Code,
  Codex), и оба показывают их работу в своём интерфейсе [57][37].

## Механизмы, которые стоит изучить

### 1. Судья цели `/goal`
- **Что это.** Цикл: агент работает, отдельная модель-судья проверяет, достигнута ли цель, и возвращает агенту
  список недостающего. Число раундов ограничено.
- **Как работает.**
  - `run_goal(conversation, objective, judge_llm, max_iterations=10)`. Судья читает переписку и отвечает JSON
    `{score, complete, missing}`. По умолчанию судья — та же модель, что у агента.
  - Доказательство, которого нет, которое неуверенно или только заявлено словами, не засчитывается.
  - Если цель не достигнута, follow-up перечисляет недостающее и велит проверить реальное состояние workspace, а не
    память.
  - Статусы: running, complete, capped (раунды кончились), interrupted (пришло сообщение пользователя).
    `GoalController` — state machine без I/O; у сервера есть `/goal`, `/goal/stop`, `/goal/resume`.
  - В интерфейсе — баннер с целью, номером раунда, статусом, оценкой судьи и списком недостающего. Вызовы судьи
    платные.
- **Источник:** [56][101] — `sdk/conversation/goal/runner.py`, `server/conversation_router.py`.
- **Почему интересно:** отдельная проверка «готово ли», с явным состоянием «лимит раундов исчерпан», — та же задача,
  что стоит перед любой работой без присмотра.

### 2. Причины остановки по видам и правило «квоту не повторять»
- **Что это.** Каждая ошибка разговора получает один из восьми видов, признак «можно повторить» и подсказку человеку.
  Это видят интерфейс, telemetry и сервис automations. Повторять ли запрос к LLM и переходить ли на запасную модель,
  решают отдельные правила классификатора ошибок LLM.
- **Как работает.**
  - `FailureKind`: auth, quota, rate_limit, config, transient, agent_action, internal, unknown. `FailureAction`: none,
    retry, settings.
  - HTTP 408, 409, 429 и 5xx — временные: 5 повторов с ожиданием 8–64 s. Если Retry-After длиннее максимума, повторы
    прекращаются сразу, без сна.
  - `usage_limit_reached` и `insufficient_quota` не повторяются вообще: по комментарию в коде, они не пройдут до
    сброса лимита. Переход на запасную модель запрещает только отказ по бюджету (`budget_exceeded`), потому что бюджет
    действует на все модели. При исчерпанной квоте провайдера переход на запасную модель разрешён.
  - ACP-агент с исчерпанным лимитом заканчивает запуск в ERROR. Automation отключается сама после трёх запусков
    подряд со сбоем вида auth, config, quota или blocked и показывает причину со временем.
- **Источник:** [101] (`sdk/event/error_classification.py`, `sdk/llm/exceptions/classifier.py`,
  `sdk/llm/utils/retry_mixin.py`, `sdk/llm/fallback_strategy.py`), [102] (`auto/utils/unhealthy.py`,
  `auto/config.py`), [77].
- **Почему интересно:** это ответ OpenHands на исчерпанный лимит — остановиться и показать причину, а не ждать сброса
  окна.

### 3. Детектор зацикливания
- **Что это.** Проверка последних событий на повторяющиеся шаблоны до того, как сработает общий timeout.
- **Как работает.** До 20 событий после последнего сообщения пользователя. Четыре шаблона: одно и то же действие и
  результат 4 раза; действие с ошибкой 3 раза; 3 сообщения агента без tools; чередование A-B-A-B 6 раз. Плюс
  повторные ошибки переполнения окна контекста. Подсказка есть только для действия с ошибкой: на 3-м повторе агент
  получает одну подсказку, на 4-м — статус STUCK. Остальные шаблоны сразу дают STUCK. После возобновления — новое
  окно. Пороги настраиваются (`StuckDetectionThresholds`).
- **Источник:** [101] (`sdk/conversation/stuck_detector.py`, `sdk/conversation/types.py`, `local_conversation.py`),
  [95].
- **Почему интересно:** зацикливание видно по журналу событий раньше, чем истечёт общий timeout.

### 4. Вердикты на точном head SHA и merge без агента
- **Что это.** Результаты тестов и ревью записываются как статусы на конкретный commit, а merge делает
  детерминированный скрипт.
- **Как работает.** Watchdog делает merge только при успешных статусах `software-factory/tests` и
  `software-factory/review` на точном head SHA, при всех остальных пройденных проверках и актуальной base. Ожидаемый SHA
  передаётся в API merge, поэтому push после проверки отменяет merge. Если ревью упало, worker отправляет задачу на
  доработку с этим SHA: исправить каждое замечание или доказать, что правка не нужна; push в ту же ветку; снова
  поставить метку ревью.
- **Источник:** [103] (`skills/github-delivery-watchdog`, `skills/github-issue-to-pr/scripts/worker.py`), [45].
- **Почему интересно:** вердикт привязан к конкретному коду, а не к PR в целом.

### 5. Объявленные ресурсные lock-и
- **Что это.** Tools заранее говорят, какие общие ресурсы им нужны. Параллельные tool calls одного шага агента ждут
  друг друга только на одном и том же ресурсе.
- **Как работает.** `DeclaredResources`; FIFO-lock на ресурс; timeout: файл 30 s, terminal, browser и MCP — 300 s,
  прочий tool — 60 s; вызовы tool-а без объявления идут по одному через общий mutex этого tool-а;
  `tool_concurrency_limit` по умолчанию 1, то есть без настройки вызовы идут по очереди. У каждого исполнителя свой
  lock manager: sub-agents и другие разговоры эти lock-и не делят.
- **Источник:** [101] (`sdk/conversation/resource_lock_manager.py`, `sdk/agent/parallel_executor.py`,
  `sdk/tool/tool.py`, `sdk/agent/base.py`).
- **Почему интересно:** простое правило против столкновений параллельных tool calls одного агента на общих ресурсах.
  Разные агенты и разговоры оно не координирует.

### 6. Один разговор на субъект и склейка повторных событий
- **Что это.** Все события про один issue или PR попадают в один разговор, а пачка событий — в один ход.
- **Как работает.** Id разговора — uuid5 (детерминированный id из строки) от организации, automation, service account
  (если есть), источника и ключа субъекта. Пока запуск ждёт в очереди, новые сообщения склеиваются в один ход, не
  больше 20. Смена service account даёт новые id, потому что Enterprise отклоняет webhook для разговора, созданного
  другим пользователем.
- **Источник:** [102] (`auto/subjects.py`, `auto/conversations.py`), [45].
- **Почему интересно:** повторные триггеры не создают новых запусков, а контекст по задаче копится в одном месте. У
  самого вендора был обратный случай: бот triage ответил 191 раз на одном issue [132].

### 7. Рестарт без молчаливого продолжения и owner lease
- **Что это.** После рестарта сервер не продолжает недоделанные шаги сам; один разговор ведёт один процесс.
- **Как работает.** При старте разговоры RUNNING получают ERROR и событие восстановления: в них может остаться
  недоделанный tool call. Сами они не продолжаются. Файл `owner_lease.json` с TTL 45 s не даёт второму процессу вести
  тот же разговор; живой lease блокирует перехват. После возобновления детектор зацикливания начинает новое окно.
- **Источник:** [101] (`server/conversation_service.py`, `server/conversation_lease.py`).
- **Почему интересно:** явное правило, что делать с работой, прерванной рестартом или обновлением приложения.

### 8. Журнал событий с ветвлением и побочными вопросами
- **Что это.** Разговор — журнал событий только на добавление. Из любой точки можно ответвиться, а вопрос «на полях»
  не меняет состояние. В Canvas ветвление работает только на локальных backend-ах Agent Server с поддержкой fork
  [56].
- **Как работает.** `base_state.json` плюс файл на событие. `fork(from_event_id)` и `navigate_to` стоят за «Branch
  from here»: на сообщении пользователя — правка и повторная отправка, на сообщении агента — продолжение с этой точки.
  `ask_agent` стоит за `/btw`. `rerun_actions` повторяет записанные действия. Сжатие истории — тоже событие
  (`Condensation`); исходные события не удаляются.
- **Источник:** [101][56][97].
- **Почему интересно:** попробовать другой путь можно без потери исходной сессии и её истории.

### 9. Model Router на LLM
- **Что это.** Отдельная модель выбирает модель под задачу.
- **Как работает.** Router-профиль — prompt, который относит задачу к одной категории (исправление в зрелом
  репозитории, тесты, визуальный UI и другие) и выбирает модель из таблицы с точностью и ценой по benchmark-ам.
  Шаблоны «OpenHands Router Pro» и «OpenHands Router Flash»; переключатель «Run on first message» выключен, пока
  router-а нет, и включается сам при добавлении первого router-а; SwitchLLMTool даёт агенту менять модель самому; в
  SDK есть `route_task_to_model` и RouterLLM.
- **Источник:** [60][77][97][101].
- **Почему интересно:** выбор дешёвой или сильной модели по типу задачи — та же цель, что у Eco mode.

### 10. Операционная поверхность automations
- **Что это.** У каждой регулярной работы видны статус, фаза, цена и надёжность.
- **Как работает.** Статусы PENDING, RUNNING, COMPLETED, FAILED, CANCELLED, SKIPPED (лимит параллельных запусков
  организации, дневной лимит sandbox или выключенная automation), «Needs review» для неопознанного исхода. Агент сам сообщает фазу (`POST /v1/runs/{id}/phase`, строка 1–200
  символов). Стоимость запуска — до четырёх знаков после запятой. Доля успешных и средняя длительность — на карточке.
  Выгрузка Activity Log. Баннер отключения с причиной и временем. Timeout 10 и 30 минут с watchdog. Экспорт в JSON,
  импорт выключенным, Git Sync.
- **Источник:** [65][77][102][69].
- **Почему интересно:** готовый набор того, что человек хочет видеть о работе, которая идёт без него.

### 11. Проверки, защищённые от исполнителя
- **Что это.** Агент, который пишет код, не может менять то, чем его проверяют.
- **Как работает.** В репозитории Canvas skills проверки `verify-*` только для чтения у агентов-исполнителей; их
  меняют отдельным PR в отдельном контексте агента. Раздел `HUMAN:` в описании PR пишут только люди. Шаблон PR
  требует доказать работу end-to-end командами, logs или скриншотами; файлы доказательств лежат в `.pr/<topic>/`
  самого PR. Файла `evidence.md` и папки `test-evidence/` в 60 последних merged PR нет. Зависимости — не моложе 7
  дней. CI: lint, test, build, build:lib, `npm pack --dry-run`.
- **Источник:** [98][97].
- **Почему интересно:** правило закрывает путь, при котором агент делает проверку зелёной, ослабив саму проверку.

### 12. Правила по пути при первом касании
- **Что это.** Правила модуля попадают в контекст, только когда агент впервые трогает его файлы.
- **Как работает.** Skills с триггерами по ключевому слову, задаче или пути. `_maybe_inject_path_rules` добавляет
  правило в результат tool-а при первом касании подходящего файла. Память проекта — с бюджетом 6000 символов; лишнее
  отрезается сверху.
- **Источник:** [101] (`local_conversation.py` L663, `sdk/context/memory.py`).
- **Почему интересно:** базовый prompt остаётся коротким, а правила модуля всё равно доходят до агента вовремя.
