- **Одной фразой:** Agent view — экран внутри Claude Code CLI (`claude agents`), который показывает все фоновые

  (supervisor) и перед первой правкой сами уходят в свой git worktree [1][44].

## Модель работы

- **Развёртывание — local.**
  - Фоновые сессии работают на машине пользователя. Они переживают сон машины и останавливаются при её выключении [1].
  - Хостинга и self-hosted сервера для agent view документация не описывает [1].
  - Облачные аналоги — отдельные продукты Anthropic: Projects и облачные сессии [2][24].
- **Форма продукта.**
  - Это функция CLI, а не отдельное приложение. Всё делает тот же бинарник `claude` [1].
  - Settings, hooks, plugins, MCP servers и keybindings переходят в запущенные сессии без отдельной настройки [1].
  - Интерфейс — полноэкранный терминальный (TUI). Пост о запуске описывает его как функцию CLI [44].
  - В Desktop-приложении и в расширении VS Code agent view нет: их документация его не упоминает [27][28]. У Desktop
    своя боковая панель параллельных сессий. CLI-сессий она не видит [27].
- **Фоновая сессия (background session)** — полный разговор Claude Code, который продолжает работать без подключённого
  терминала. Agent view показывает все такие сессии [1].
- **Процессы.**
  - Фоновые сессии держит служба supervisor (её же называют background service или daemon). Управляется командой
    `claude daemon` [1].
  - Supervisor стартует сам, когда пользователь впервые уводит сессию в фон или открывает agent view [1].
  - Каждая сессия — отдельный процесс Claude Code. Терминал каждой сессии живёт в своём host-процессе [1].
  - Служба держит заранее запущенные запасные процессы (warm standby) для следующего запуска [14].
- **Агенты.**
  - Только сессии Claude. Во всех подходах Anthropic к параллельной работе workers — сессии Claude. Другие инструменты
    подключаются только как MCP servers [2].
  - Страница agent view не упоминает Codex, Gemini или OpenAI [1].
  - Главным агентом сессии может быть свой subagent (`--agent`, `@agent`). Есть shell jobs — запуск команды shell без
    модели [1].
- **Модели.**
  - На Anthropic API алиасы `opus`, `sonnet` и `haiku` означают Opus 5.5, Sonnet 5.5 и Haiku 5.5. Есть также `fable`
    и `opusplan` [30].
  - Модель и effort выбираются для каждой сессии: `/model`, `/effort` от low до max, режим `ultracode` [1].
  - Имена и сводки строк пишет модель класса Haiku [1].
- **Провайдеры.**
  - Подписка Claude, ключ Console API, Amazon Bedrock, Google Cloud Agent Platform, Microsoft Foundry, Claude
    Platform on AWS и LLM gateways [1][29].
  - Всё, что работает локально, работает у любого провайдера [1][29].
  - У сторонних провайдеров модель для сводок задаёт переменная `ANTHROPIC_DEFAULT_HAIKU_MODEL` [1].
- **Один пользователь или команда.**
  - Один пользователь на одной машине. Список охватывает его сессии во всех проектах на этой машине. Общей доски для
    команды документация не описывает [1].
  - Для команд есть только администрирование: выключить agent view через managed settings (настройки, которые задаёт
    администратор), требовать corporate launcher (обязательную программу-обёртку для запуска процессов) и
    контролировать режим bypass [1][7][14].
- **Платформы.**
  - CLI работает на macOS 13+, Windows 10 1809+, Ubuntu 20.04+, Debian 10+, Alpine 3.19+ и WSL 2 [31].
  - Особая обработка в agent view [1]:
    - Windows: защита от неоднозначного нажатия `←` сразу после подключения к сессии; `taskkill` для зависшего
      supervisor;
    - macOS: отдельные запросы доступа к папкам и к Local Network для host-процесса сессий;
    - Linux и WSL: обнаружение умершего host-процесса терминала.
  - На Windows связь между процессами идёт через named pipe [12][38]. Corporate launcher на Windows не работает [14].
    Sandbox на Windows нет [18].
- **Как Anthropic позиционирует agent view.**
  - Anthropic предлагает пять способов параллельной работы и делит их по двум осям: насколько человек вовлечён и где
    идёт работа, локально или в облаке [2].
  - Agent view — способ раздать независимые задачи и вернуться к ним позже. Сессии agent view сообщают результат
    только человеку [2].
  - Если работу должен координировать сам Claude, Anthropic отправляет к agent teams (экспериментальные, выключены по
    умолчанию), dynamic workflows и облачным Projects [2].
  - Agent view — для работы, которой нужна машина пользователя. Облако и Projects — для долгой работы, которая
    продолжается, пока пользователь offline [24][50].
- **Соседние продукты Anthropic.**
  - Desktop-приложение: параллельные сессии в боковой панели, split view, worktree на сессию по желанию (переключатель
    по умолчанию выключен), слежение за PR, автоархивация после merge [27].
  - Projects: облачный разговор-координатор с threads (параллельными облачными сессиями) и панелью Overview. Public beta
    на Pro, Max и Ultra; на Team и Enterprise пока нет. Документация на 2026-11-13 называет предел 500 новых threads
    в день по всем проектам; field guide от 2026-10-06 называл 200 [24][50]. Thread может работать и на компьютере
    пользователя через Remote Control [24].
  - Desktop Dispatch: задачу отправляют с телефона, и она запускает сессию в Desktop. Только Pro, Max и Ultra [29][26].
  - По вторичному источнику, Boris Cherny заменил шесть вкладок терминала и шесть checkout на agent view вместе с
    Desktop-приложением [128].

## Функции

Функции собраны по документации, changelog и release notes. Версия Claude Code указана там, где источник её
называет.

### Как открыть agent view

- **`claude agents`.** Открывает список на весь терминал. С флагом `--cwd <path>` показывает сессии только одного
  проекта (v2.1.141) [1][35].
- **Клавиша `←` на пустой строке ввода** в любой обычной сессии [1]:
  - уводит разговор в фон и открывает agent view, где выделена его строка;
  - `Esc` возвращает в разговор;
  - сразу после правки prompt первое нажатие только просит подтверждения;
  - до v2.1.196 нужно было нажать дважды;
  - настройка `leftArrowOpensAgents` выключает это поведение [7].
- **`/background` или `/bg [prompt]`** уводит текущий разговор в фон [1].
- **`/fork [prompt]`** копирует разговор в новую фоновую сессию, а оригинал продолжает работать (с v2.1.212). Прежнее
  поведение — fork в виде subagent — переехало в команду `/subtask` [1].
- **`claude --bg "<prompt>"`** запускает фоновую сессию из shell [1][11]. Опции:
  - `--name` (имя) и `--agent <subagent>` (свой subagent как главный агент);
  - `--resume <id>` продолжает ту же сессию на месте (с v2.1.257);
  - `--exec '<cmd>'` запускает shell job вместо сессии Claude;
  - `--bg` нельзя сочетать с `-p` (неинтерактивный режим).
- **`defaultToAgentsView`.** С этой настройкой команда `claude` без аргументов открывает agent view [1][7].
- **Footer обычной сессии** [1]:
  - первые 10 секунд показывает подсказку «← for agents»;
  - потом — живой счётчик сессий, которые ждут человека; он обновляется примерно раз в 10 секунд;
  - ненадолго показывает «← N done», когда сессии заканчивают работу.
- **Заголовок вкладки терминала** показывает, сколько сессий ждут ввода [1].
- **Диалог выхода.** Если при выходе работают subagents или workflows, он предлагает «Move to background and exit»
  (увести в фон и выйти) [1].

### Строки списка и состояния

- **Что в строке** [1]:
  - имя — его пишет модель класса Haiku; цвет берётся из `/color` сессии;
  - однострочная сводка;
  - возраст — считается от создания и замирает на времени работы, когда сессия закончила;
  - необязательная метка PR.
- **Как обновляется сводка** [1]:
  - пока сессия работает, текст строки обновляется не чаще раза в 15 секунд из её собственного вывода, без вызова
    модели;
  - модель пишет свежую сводку в конце каждого хода и раз в несколько минут во время длинного хода;
  - с v2.1.205–206 сводка строится из собственного однострочного отчёта сессии, а не из сырых вызовов инструментов
    [1][38].
- **Состояния** [1]: Working (анимация), Needs input (жёлтый), Idle (тусклый), Completed (зелёный), Failed (красный),
  Stopped (серый).
- **Иконки** [1]:
  - `✻` или `✽` — процесс работает;
  - `∙` — процесс завершён, но сессия продолжит работу после ответа;
  - `✢` — сессия `/loop` (повтор prompt по расписанию) спит между запусками; рядом число запусков и обратный отсчёт.
- **Что попадает в Needs input** [1]:
  - вопросы агента, запросы разрешений (permission prompts), запросы сети от sandbox и запросы ввода от MCP;
  - команды, которым нужен подключённый терминал, например `/install-github-app` и список `/mcp`;
  - сообщения от других сессий, которые ждут одобрения; строка показывает «approve message from» (v2.1.257);
  - неверный вывод hook `PermissionRequest` или `PreToolUse`; строка называет этот hook;
  - ошибка, которую может снять только человек, например истёкший вход.
- **Прогресс веера задач.** v2.1.161 добавил в строку счётчик `done/total` для параллельных задач. С v2.1.205 строка
  вместо него показывает однострочный отчёт самой сессии [1].
- **Зависшие агенты** получают метку «Needs attention» (v2.1.196) [38].

### Группы и порядок

- **Группы по умолчанию** [1]: Pinned, Ready for review, Needs input, Working, Completed.
  - Ready for review — сессии с открытым PR, которому нужен review или у которого падают checks.
  - Completed объединяет закончившие, упавшие и остановленные сессии.
  - `Ctrl+S` группирует строки по папке. Выбор сохраняется.
- **Действия со строкой** [1]:
  - закрепить — `Ctrl+T`; закреплённая сессия держит свой процесс живым, даже когда простаивает;
  - переставить — `Shift+↑/↓`; переименовать — `Ctrl+R`;
  - свернуть группу — `Enter` на её заголовке;
  - остановить — `Ctrl+X`; второй `Ctrl+X` в течение 2 секунд удаляет; на заголовке группы удаляет всю группу.
- **Длинный список.** Completed сворачивается в строку «… N more». В низком терминале заголовок становится компактнее
  [1].
- **`/resume` в строке ввода** возвращает в список прошлую сессию репозитория, в том числе удалённую [1]. Выбор
  прошлой сессии прямо внутри view появился в v2.1.212 [1][38].
- **Удаление переименовали.** В v2.1.323 «Delete» стало «removed from list», transcript (запись разговора) сохраняется
  [38].

### Peek: быстрый просмотр и ответ без подключения

- **`Space` открывает peek** — панель под строкой [1]. Она показывает:
  - точный вопрос, который ждёт ответа, результат или полную фразу статуса;
  - связанные PR;
  - таймер ожидания вида «waiting 3m»;
  - пометку safe mode, если она есть.
- Документация говорит, что обычно хватает peek и открывать transcript почти не нужно [1].
- **Ответ из peek** [1]:
  - текст печатают прямо в панели; префикс `!` отправляет команду Bash;
  - вопросы с вариантами показывают нумерованные варианты; `Tab` подставляет предложенный ответ;
  - `/stop` сразу останавливает сессию;
  - `/model`, `/effort`, `/rename` и `/usage` применяются к работающей сессии сразу; остальные ответы ждут конца хода
    (с v2.1.287).
- **На запрос разрешения из peek ответить нельзя.** Нужно подключиться к сессии [1]. Исправление в v2.1.285 закрыло
  баг, при котором ответ из peek мог одобрить ожидающую команду [35].
- **Недоставленный ответ** сохраняется и уходит следующим prompt после перезапуска сессии. Исключение — ответы,
  которые начинаются с `!` или `/` [1].

### Attach и detach: подключение к сессии

- **Подключиться (attach):** `Enter` или `→` на строке, либо `claude attach <id|name>` из shell [1].
  - Терминал становится полной сессией, всегда на весь экран.
  - Claude пишет короткий пересказ того, что произошло, пока человека не было.
- **Отключиться (detach):** `←`, `/exit` или двойной `Ctrl+C`. Отключение никогда не останавливает сессию и её
  `/loop` [1].
- **`Alt+1…9`** подключает к n-й сессии в выбранной папке [1].
- Если процесс сессии был остановлен, повторное подключение показывает конец transcript, пока процесс
  перезапускается [1].

### Фильтры и поиск

- Префиксы фильтра в строке ввода [1]:
  - `a:` — агент;
  - `s:` — состояние или группа; `s:blocked` показывает всё, что ждёт человека;
  - `n:` — имя или первый prompt (v2.1.287); то же по `Ctrl+F` (v2.1.288) [35];
  - `o:` — текст результата, номер или URL PR и MR, любой URL из первого prompt.
- Фильтры можно сочетать [1].

### Ввод и клавиши

- `Ctrl+G` открывает внешний редактор (`$VISUAL` или `$EDITOR`). `Shift+Enter` и `Ctrl+J` вставляют новую строку.
  `Ctrl+Enter` запускает сессию и сразу подключается к ней. `?` показывает все сочетания [1].
- **Переназначение клавиш.** В `keybindings.json` есть context `Agents` с действиями switchView, togglePin, find,
  rename, previousGroup и nextGroup. Он появился в v2.1.257, часть действий добавлена в v2.1.288 [10].
- **Режимы ввода.** Vim mode и голосовой ввод с удержанием клавиши работают и в строке запуска, и в строке ответа [1].
- **Черновики.** Исправления в v2.1.312 и v2.1.319 говорят о том, что неотправленный текст запуска сохраняется между
  перезапусками (вывод) [35].
- **Доступность.** Режим screen reader прячет подсказку про `←`. Настройка `prefersReducedMotion` убирает цветовую
  вспышку [1].

### Запуск работы (dispatch)

- **Один prompt — одна сессия.** Каждый prompt в строке ввода плюс `Enter` запускает новую фоновую сессию.
  Продолжение разговора с уже идущей сессией — через peek. Prompts короче 4 символов отклоняются [1].
- **Вставка.** Можно вставить картинку. Длинный текст сворачивается в метку `[Pasted text #N]` [1].
- **Префиксы prompt** [1]:
  - имя своего subagent первым словом или `@subagent` в любом месте — этот subagent становится главным агентом;
  - `@<repo>` — дочерний репозиторий, зарегистрированный worktree или любая папка, где уже есть сессия;
  - `/<skill>` — skill или своя команда как первый prompt;
  - `! <cmd>` — shell job;
  - `#1234` или URL PR — выбрать сессию, которая уже работает над этим PR, вместо запуска новой.
- **Команды, которые выполняет сам view** [1]:
  - `/model`, `/effort` (от low до max) и `/fast` задают, с чем стартуют следующие сессии из этого окна; `/effort` и
    `/fast` — с v2.1.299;
  - `/resume` (он же `/continue`), `/login`, `/logout`, `/exit`.
- **Dispatch defaults** — значения по умолчанию для всех сессий, запущенных из окна. Их задают флагами при открытии
  view [1]:
  - `--permission-mode`, `--model`, `--effort` (в том числе `ultracode`) и `--agent`;
  - `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions` и `--restricted` (v2.1.248);
  - передаются дальше в сессии: `--settings`, `--setting-sources`, `--add-dir`, `--plugin-dir`, `--mcp-config`,
    `--strict-mcp-config`;
  - действующие значения видны в footer.
- После auto-update agent view, от которого пользователь отошёл примерно на час, перезапускается сам и сохраняет
  dispatch defaults (v2.1.274) [1][38].
- **Имя сессии** придумывает модель класса Haiku [1].
- **В каком режиме разрешений стартует сессия** [1][13]:
  - сессия, уведённая в фон, сохраняет свой текущий режим;
  - запущенная из view стартует так же, как новая `claude` в этой папке, если dispatch defaults не заданы;
  - из view, открытого клавишей `←`, сначала действует `permissions.defaultMode` целевой папки, если он не
    разрешительнее сессии, из которой пришёл пользователь; иначе — режим этой сессии;
  - при этом режимы `auto` и `bypassPermissions` засчитываются, только если заданы в managed settings, в файле
    `--settings` или в `~/.claude/settings.json`;
  - режим bypass требует записанного согласия с предупреждением (disclaimer).
- **Вероятный режим по умолчанию — auto mode (вывод).** С v2.1.283 встроенный стартовый режим терминальных сессий —
  auto mode: отдельная модель-классификатор проверяет действия вместо человека [13]. Значит, запущенные сессии,
  скорее всего, стартуют в auto mode. Страница agent view этого не говорит [1]. В v2.1.143 запущенным сессиям
  перестали принудительно ставить auto mode [38].
- **Workspace trust** (доверие к папке) проверяется перед каждым запуском (v2.1.225 и v2.1.281). В скриптах запуск
  завершается с ошибкой `Workspace not trusted` [1].
- **Shell jobs** [1]:
  - команда работает в pseudo-terminal; последняя строка вывода служит статусом строки;
  - вывод хранится только в памяти;
  - строка убирается примерно через 5 минут после выхода команды;
  - shell job никогда не перезапускается.
- **Safe mode.** `claude --bg --safe-mode` запускает сессию с выключенными настройками пользователя [1].

### Уход в фон и fork

- **Что переносится, когда сессия уходит в фон** [1]:
  - фоновые команды shell, фоновые subagents и задачи `/loop`;
  - автоматические ответы на комментарии к artifacts, список задач, переносимые сообщения из очереди и `/color`
    сессии.
- **Что требует перезапуска:** dynamic workflows (скрипты, которые раздают работу многим subagents). Их работающие
  subagents начинают заново и снова тратят токены [1].
- **Что останавливается:** monitors (фоновые наблюдатели за выводом). Сначала предупреждает диалог «Background this
  session?» [1].
- **Флаги запуска, которые переносятся** [1]: `--mcp-config`, `--strict-mcp-config`, `--settings`,
  `--setting-sources`, `--add-dir`, `--plugin-dir`, `--fallback-model`, `--allow-dangerously-skip-permissions` и
  папки, добавленные через `/add-dir`.
- **Что наследует копия `/fork`** [1]:
  - модель, режим разрешений, effort, добавленные папки и одобрения «don't ask again»;
  - копия создаёт свой worktree перед правками;
  - если задача строится на работе оригинала, копия берёт его ветку за основу;
  - сессию с заменённым system prompt или с allowlist `--tools` скопировать нельзя.
- Инструкции про worktree копия получает сообщением, а не правкой system prompt. Так сохраняется prompt cache
  (v2.1.257) [38].
- **`←` во время работы инструмента.** Переход ждёт окончания инструмента: около 10 секунд, дольше — пока работают
  foreground subagents или открыт prompt. Ввод текста отменяет переход [1].
- **Пустые сессии**, оставшиеся после `←`, убираются через 5 минут (v2.1.141) [38].

### Git, worktrees и PR

- **Автоматическая изоляция** [1]:
  - перед первой правкой запущенная или `--bg` сессия переходит в свой git worktree в папке `.claude/worktrees/`;
  - не переходят: сессии, уведённые в фон самим пользователем; сессии, уже работающие в linked worktree; папки без git
    и без hook `WorktreeCreate`; запись вне рабочей папки;
  - настройка `worktree.bgIsolation: "none"` (v2.1.143) выключает изоляцию [1][7];
  - другие системы контроля версий подключаются через hooks `WorktreeCreate` и `WorktreeRemove` [1][3][9].
- **Основа ветки и файлы** [3]:
  - по умолчанию основа `fresh` — ветка по умолчанию на remote; если репозиторий не обновлялся 24 часа, перед этим
    идёт fetch не дольше 5 секунд;
  - альтернатива `head` — текущий локальный HEAD;
  - `.worktreeinclude` копирует в новый worktree файлы из gitignore, например `.env`.
- **`worktree.symlinkDirectories`** подключает тяжёлые папки вроде `node_modules` через symlink, а не копией [63][1].
- **Принуждение к изоляции** [3]:
  - пока сессия изолирована, Claude Code блокирует правки main checkout (основной рабочей копии);
  - блокирует команды, которые работают в main checkout, git, перенаправленный в него, и команды, чьё обращение к git
    нельзя проверить;
  - те же правила действуют для всех subagents сессии;
  - запись обычными командами shell, например `cp` или перенаправлением вывода, эти правила не ловят.
- **Git-политика «сохранить работу»** [1]:
  - сессия коммитит без вопроса и делает push своей ветки, если есть remote;
  - открывает draft PR, когда задача этого требует;
  - никогда не делает push в main или master, force-push и merge;
  - git-инструкции в задаче, CLAUDE.md или memory важнее этих правил;
  - сессия, которая правит checkout без изоляции, по-прежнему спрашивает перед коммитом;
  - в конце сессия отчитывается, где лежит работа: путь, ветка, PR или ответ.
- **История git-политики.** v2.1.198 (2026-07-01) сделал коммит, push и draft PR автоматическими всегда. v2.1.221
  стал открывать draft PR, только когда задача этого требует [1][38]. Дата v2.1.221 в материалах расходится:
  2026-08-03 по датам публикации в npm [40][38] и 2026-08-04 по хронологии в docs changelog [35].
- **Метка PR в строке** [1]:
  - `#N` для GitHub, `!N` для merge request в GitLab (v2.1.233);
  - метка кликабельна и через SSH или tmux;
  - цвета: жёлтый — checks или review ещё ждут либо checks упали; зелёный — checks прошли и review не блокирует;
    фиолетовый — merged; серый — draft или закрыт;
  - несколько связанных PR показываются как «N PRs».
- **Как PR привязывается к строке** [1]:
  - по выводу команд `gh`, которые правят PR, комментируют, закрывают или помечают ready; `gh pr merge` обычно
    связи не оставляет;
  - по запросу `gh pr view` для ветки после `gh pr checkout` или push;
  - если PR ещё нет в момент push, поиск повторяется на следующих до 5 командах `git`, `gh`, `glab` или `curl` в той
    же папке.
- Статус PR нужен GitHub token: `GH_TOKEN`, `GITHUB_TOKEN` или вход через `gh auth` [4]. Колонка PR появилась в
  v2.1.153 (2026-05-28 по docs changelog [35]; в npm — 2026-05-27 UTC [40]) [38]. Статус обновляется и кэшируется;
  это видно по исправлениям в v2.1.248 и v2.1.300 [35].
- **Удаление сессии и worktree** [1]:
  - удаление из agent view убирает созданный Claude worktree вместе с незакоммиченными изменениями;
  - `claude rm` сохраняет worktree, где есть незакоммиченные изменения;
  - worktree с коммитами без push остаётся, пока их не отправят или пока сессию не удалят повторно с
    `--discard-unpushed` (v2.1.260);
  - worktree, который использует другая сессия, остаётся;
  - `--force-remove-worktree` (v2.1.268) убирает worktree, который не смогли убрать git или hook;
  - transcripts переживают удаление.
- **Блокировка и уборка.** Работающая сессия держит git lock на своём worktree (v2.1.248). Периодическая уборка
  удаляет старые фоновые worktrees после срока `cleanupPeriodDays`, если в них не осталось работы [1][3].

### Команды shell и интерфейс для скриптов

- **Команды** [1][11]: `claude attach|logs <id|name>`, `stop` (или `kill`), `respawn <id>` или `respawn --all`, `rm`
  и `daemon status|logs|run|stop --any [--keep-workers]`.
- К v2.1.311 команда `claude daemon restart` отключена. Сообщения отправляют к `claude daemon stop --any` [38].
- **`claude agents --json [--all] [--cwd]`** — документированный способ читать состояние для status bar,
  планировщика или другой сессии Claude, которая следит за работой [1].
  - Появился в v2.1.145 для tmux-resurrect, status bars и выбора сессий [35]. Флаг `--all` добавили в июне [37].
  - Поля: `cwd`, `kind` (interactive или background), `startedAt`, `id`, `state`, `pid`, `status`, `waitingFor`,
    `sessionId`, `name` [1].
  - `state`: working, blocked, done, failed или stopped [1].
  - `status`: busy, waiting или idle [1].
  - `waitingFor`: permission prompt, input needed, sandbox request, worker request или dialog open [1].
- Файлы в `~/.claude/jobs/` документация прямо называет нестабильным интерфейсом и советует читать `--json` [1].
- **`/status`** показывает вид сессии: `background job · attached`, `background job · unattended` или `interactive`
  [1].
- **`/resume`** помечает фоновые сессии меткой `bg` (v2.1.144) [35][15].

### Уведомления

- **Только пока agent view открыт.** Тогда Claude Code уведомляет, когда локальная фоновая сессия начала ждать ввода,
  закончила или упала. Сессии `/loop` уведомляют только о нужном вводе [1].
- Уведомления появились в v2.1.198 (2026-07-01) [38].
- **Каналы** (настройка `preferredNotifChannel`) [7]:
  - `auto`: desktop-уведомления в iTerm2, Ghostty и Kitty; в Terminal.app — звонок терминала (bell), только если там
    выключен звуковой bell;
  - также: terminal bell, iTerm2, Kitty, Ghostty или none.
- **Hook `Notification`** срабатывает с типами `agent_needs_input` и `agent_completed`, тоже только пока view открыт
  [9]. Переслать их в Slack или на телефон можно только своим скриптом hook (вывод).
- **Push на телефон.** Claude может присылать push, пока подключён Remote Control (настройка `agentPushNotifEnabled`)
  [7]. Используют ли этот канал фоновые сессии — не подтверждено.
- С v2.1.299 уведомления о фоновых агентах сообщают, если агента остановил лимит использования [38].

### Лимиты использования и работа без присмотра

- **Расход.** Фоновые сессии тратят лимиты подписки так же, как интерактивные. Десять параллельных сессий тратят
  лимит примерно в десять раз быстрее одной [1]. Пост о запуске говорит, что действуют обычные rate limits [44].
- **Интерактивные сессии продолжают работу сами** (с v2.1.234, 2026-08-17) [35][4]:
  - интерактивная сессия со входом через подписку claude.ai ждёт сброса лимита и после него продолжает задачу;
  - включено по умолчанию; настройка `autoContinueAtUsageLimit`, в `/config` — «Continue automatically at usage
    limit» [4][7];
  - после сброса Claude Code просит Claude продолжить задачу, а не отправляет последнее сообщение заново [4];
  - если машина спала дольше примерно 30 минут, ждёт нажатия `Enter` [4];
  - после трёх автоматических продолжений останавливается и показывает `/rate-limit-options` [4];
  - не начинает ждать сам, если до сброса больше 24 часов — обычно это недельный лимит [4];
  - сам не начинает ожидание в сессиях Remote Control, у teammates в agent teams и для лимита на семейство моделей,
    которое сессия не использует; там ожидание можно начать вручную через `/rate-limit-options` [4];
  - запросы разрешений всё равно могут остановить продолженную задачу [4];
  - включить настройку командой `/config key=value` нельзя: она разрешает работу без присмотра [4].
- **Фоновые сессии сами не продолжают.**
  - Документация прямо перечисляет фоновые сессии и запуски `-p` среди случаев, где ожидание сброса не предлагается
    вообще. Уход сессии в фон прерывает уже начатое ожидание [4].
  - Отсюда (вывод из [4] и [1]): сессия agent view, которая упёрлась в 5-часовой лимит, сама не продолжит. Нужно
    ответить ей или подключиться после сброса.
  - Какое состояние показывает строка на лимите — не подтверждено. Страница agent view о поведении на лимите молчит
    [1].
- **Retry watchdog** — режим бесконечных повторов для работы без присмотра [6][5]:
  - включается переменной `CLAUDE_CODE_RETRY_WATCHDOG=1` (v2.1.186);
  - повторяет ошибки 429 (rate limit) и 529 (перегрузка) бесконечно, с паузой до 5 минут между попытками;
  - если в ответе есть время сброса лимита, ждёт до сброса;
  - сразу завершается на 429 из-за лимита трат и нехватки кредитов (с v2.1.239);
  - ограничители: общий предел ожидания `…_MAX_WAIT_MS` (v2.1.295), предел ожидания сброса лимита
    `…_MAX_USAGE_LIMIT_WAIT_MS` (v2.1.301) и ранняя проверка, не сняли ли лимит до сброса,
    `…_USAGE_LIMIT_RECHECK_MS` с интервалом от 1 минуты до 3 часов (v2.1.305) [6][38];
  - документирован для eval harness, CI jobs и удалённых workers [6].
- Работает ли retry watchdog в сессиях agent view — не подтверждено. Фоновые сессии читают блок `env` из настроек
  проекта, поэтому переменная, заданная там, должна до них доходить (вывод) [1].
- **Обычные повторы.** Без watchdog временные сбои повторяются до 10 раз с растущей паузой [5].
- **Desktop-приложение.** На карточке 5-часового лимита есть свой флажок «Auto-continue when limits reset». На
  карточке недельного лимита его нет [5].
- **`/goal`** (цель, которую сессия преследует несколько ходов) останавливается на лимите. Продолжает, только если
  сессия в режиме ожидания авто-продолжения [22]. Пауза `/goal` до сброса — с v2.1.269 [38].
- **Dynamic workflows** останавливаются на лимите и продолжают после сброса (v2.1.271). Но в фоновой сессии запуск
  workflow на лимите на паузу не встаёт: агент, который упёрся в лимит, падает [19][38]. В Desktop workflows вкладки
  Code делают так с v2.1.323 [38].
- **Hooks о лимитах.** Типы уведомлений `quota_auto_resume_fired`, `quota_auto_resume_stale` и
  `quota_auto_resume_disabled` есть с v2.1.234 [9].
- **Облачные threads в Projects** ждут сброса и продолжают по умолчанию [24].
- **Видимость лимитов.**
  - Предупреждения появляются примерно на 85% окна. Status line отдаёт поля `rate_limits` [5].
  - `/usage` можно отправить ответом из peek [1].
  - Колонки токенов или стоимости на сессию в списке нет [1].
  - С v2.1.304 Claude Code предупреждает, если продолжение давно неактивного разговора съест заметную долю 5-часового
    лимита (из-за потери prompt cache). С v2.1.312 сообщения говорят «5-hour limit» вместо «session limit» [38].
- **Планы.** Ultra обещает отсутствие 5-часового лимита для подтверждённых аккаунтов [46].
- **Спрос.** Открытый запрос #41502 (2026-03-31) просит флаг `--wait-on-usage-limit` для неинтерактивных сессий и
  Remote Control [56].

### Агенты, модели и провайдеры в сессиях

- Workers — только сессии Claude; другие инструменты — только через MCP [2].
- Главным агентом можно сделать свой subagent или запустить shell job без модели [1].
- Модель и effort задаются на сессию и на окно (dispatch defaults) [1]. Алиасы `opus`, `sonnet`, `haiku` на
  Anthropic API — модели 5.5; есть `fable` и `opusplan` [30].
- Провайдеры: подписка Claude, Console API, Bedrock, Google Cloud Agent Platform, Microsoft Foundry, Claude Platform
  on AWS, LLM gateways [1][29].

### Интеграции

- **GitHub и GitLab:** привязка PR и MR с цветом статуса через `gh` и `glab` [1][35][37].
- **MCP servers, plugins и settings** загружаются и передаются в сессии флагами запуска [1].
- **Редакторы и терминалы:** `$EDITOR`, кликабельные ссылки через tmux и SSH, JSON для status bars [1][35].
- **Сообщения между сессиями (cross-session messaging)** [12]:
  - Claude находит адресатов инструментом `ListAgents` и отправляет сообщение инструментом `SendMessage`;
  - на одной машине сообщение идёт через Unix socket каждой сессии (на Windows — named pipe) и никогда не проходит
    через серверы Anthropic;
  - на другие машины и в облачные сессии — через серверы Anthropic по Remote Control, а не по LAN;
  - сессия читает сообщения между вызовами инструментов; простаивающая сессия начинает новый ход;
  - входящая политика: `accept`, `hold` или `refuse`; значение по умолчанию зависит от режимов разрешений обеих
    сессий; задержанных сообщений — не больше 100;
  - сообщение от другой сессии не может одобрить запрос разрешения, а команды из его текста не выполняются; менять
    настройки и CLAUDE.md по просьбе другой сессии Claude Code запрещает принимающему Claude инструкцией, а не
    технической блокировкой;
  - `notify_when_idle` — разовая подписка на сигнал «сессия освободилась»; истекает через 12 часов.
- Появились 2026-08-07 (v2.1.224, macOS и Linux) [12][38]. В auto mode классификатор проверяет каждое исходящее
  `SendMessage` (с v2.1.222) [13]. В v2.1.323 предел сообщений между сессиями одной машины без prompt от человека
  поднят примерно с 20 до 100 000 [38].
- **Remote Control** [35]:
  - фоновые сессии сохраняют `--remote-control` при перезапуске процесса (v2.1.169);
  - fork сессии Remote Control из приложения Claude запускает копию как фоновую сессию на компьютере пользователя
    (v2.1.273).
- **Доступ с телефона.** Направления исследования расходятся. Направление «функции» не нашло подтверждения, что список
  agent view можно смотреть с телефона или в вебе (не подтверждено) [1]. Ранний пользовательский обзор на HN пишет, что
  фоновые сессии можно читать и отвечать им из мобильного приложения Claude через Remote Control. Его автор продвигает
  своё приложение для удалённого доступа [112].
- **Slack, Linear, Jira.** Страница agent view их не упоминает. Внешние инструменты доходят до workers только через MCP
  [2]. Claude Code в Slack — отдельная функция [29].

### Администрирование

- **Выключатель.** `disableAgentView: true` или `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` выключают `claude agents`, `--bg`,
  `/background` и supervisor. Администратор может закрепить это через managed settings [1][6][7].
- **Corporate launcher.** `CLAUDE_CODE_PROCESS_WRAPPER` (v2.1.208) или настройка `processWrapper` (v2.1.210) запускают
  через обязательную программу-обёртку supervisor, каждую сессию, запасные процессы и все перезапуски [14]. На Windows
  это не работает: обёртке нужен `exec` [14].
- **Контроль режима bypass.** Нужен ключ `skipDangerousModePermissionPrompt` в `~/.claude/settings.json`. Без него
  запрос bypass игнорируется, а на экране остаётся предупреждение [13].
- **Ограничения сессий:** флаги `--restricted` и `--safe-mode` для запускаемых сессий [1].
- **Отдельные экземпляры.** Другой `CLAUDE_CONFIG_DIR` даёт отдельный supervisor со своими сессиями [1].
- **Выход из аккаунта.** С v2.1.323 `/logout` в фоновой сессии выводит из аккаунта все сессии на компьютере [38].
- **Истекающий вход.** С v2.1.203 предупреждение заранее сообщает, что вход скоро истечёт и прервёт фоновые сессии
  [35].

## Принципы и подходы

### Заявленная философия

Ниже — пересказ первичных документов и постов Anthropic.

1. **Внимание человека — дефицит, и список его распределяет.**
   - Строки сгруппированы так, что требующие человека стоят сверху: Pinned, Ready for review, Needs input, Working,
     Completed [1].
   - Сводки строк пишет модель класса Haiku, чтобы transcripts открывать редко. Документация говорит, что обычно
     хватает peek [1].
   - Заголовок вкладки терминала показывает число ждущих сессий. Footer обычной сессии показывает счётчик ждущих
     агентов вида `← 2 agents` [1].
   - Цель в формулировке Anthropic: человек вмешивается, только когда он нужен конкретной сессии [1].
   - Та же мысль есть в процессе самой команды Claude Code. Пост от 2026-10-15 называет время и внимание человека
     главным дефицитом. Цель команды — чтобы большинство PR вливались максимум с одним человеком в цикле [49].
2. **Человек — диспетчер независимых задач.**
   - Agent view — вариант «раздать независимые задачи и вернуться позже» [2].
   - Сессии сообщают результат только человеку. Координация между workers — в agent teams, dynamic workflows или
     Projects [2].
   - Во всех подходах workers — сессии Claude. Другие инструменты входят только как MCP servers [2].
3. **Сначала локально, облако — явная альтернатива.**
   - Agent view запускает сессии на машине пользователя, и каждую запускает человек [1].
   - Если нужно, чтобы Claude сам запускал и вёл параллельные сессии в облаке из одного разговора, документация
     отправляет к Projects [1][24].
   - Заявленные ограничения — локальные: сессии переживают сон, но не выключение машины [1].
4. **Сессия не привязана к терминалу и к процессу.**
   - Supervisor перезапускает упавшие процессы, останавливает простаивающие примерно через час и поднимает их из
     сохранённого transcript при подключении или ответе [1].
   - Supervisor переживает auto-update и переносит простаивающие сессии на новую сборку [1].
   - Сон машины считается разрывом, а не временем простоя [1].
   - Пост Anthropic о Managed Agents (2026-04-08) формулирует тот же принцип для облачных агентов: надёжный журнал
     сессии и harness, который может упасть и продолжить работу. Agent view этот пост не упоминает [52].
5. **Изоляция включена по умолчанию и принудительна.**
   - Перед первой правкой сессия уходит в git worktree [1].
   - Внутри worktree Claude Code блокирует правки, рабочие папки команд и перенаправления git в main checkout — для
     сессии и её subagents [3].
   - Выключается настройкой `worktree.bgIsolation: "none"` [1][7].
   - Для сравнения: в Desktop-приложении переключатель worktree по умолчанию выключен [27].
6. **Осторожный git-контракт: merge остаётся за человеком.**
   - Сессии коммитят без вопроса, делают push ветки и открывают draft PR, когда задача этого требует [1].
   - Они никогда не делают push в main или master, force-push и merge [1].
   - Git-инструкции пользователя в задаче, CLAUDE.md или memory важнее этих правил [1].
   - Каждая работа заканчивается отчётом, где лежит результат [1].
   - Метка PR зеленеет, когда checks прошли и review не блокирует. Документация говорит: в этот момент проверьте и
     влейте сами [1].
   - Это совпадает с линией Anthropic в Code Review: инструмент публикует находки, а не одобрения. В собственных
     репозиториях Anthropic владельцы разрешают auto-merge изменений с низким риском, и эта граница сдвигается [49].
7. **Скрипты — через стабильный интерфейс, а не через файлы.** `claude agents --json` — поддерживаемый способ
   читать состояние. Файлы `~/.claude/jobs/` прямо названы нестабильными [1].
8. **Стоимость названа прямо.** Каждая сессия тратит лимит отдельно; десять агентов — примерно десятикратный расход.
   Сводки строк — платные запросы [1].

### Ключевые понятия

- **Background session (фоновая сессия)** — любая сессия в agent view, подключённая или нет. `/status` показывает её
  вид: `background job · attached`, `background job · unattended` или `interactive` [1].
- **Supervisor** (он же background service или daemon) — служба, которая держит процессы фоновых сессий. Стартует при
  первом использовании, управляется `claude daemon status|logs|stop --any` [1].
- **Job folder** — папка сессии `~/.claude/jobs/<id>/` с файлом состояния и папкой `tmp/`. Переменная
  `CLAUDE_JOB_DIR` указывает на неё [1].
- **Terminal host и warm standby.** Каждая строка — это host-процесс терминала и сессия Claude Code внутри него.
  Warm standby — заранее запущенный запасной процесс для следующего запуска. В `ps` они видны как
  `claude bg-pty-host` и `claude bg-spare` [14].
- **Состояния строки:** Working, Needs input, Idle, Completed, Failed, Stopped. В JSON: `working`, `blocked`, `done`,
  `failed`, `stopped`. Причины ожидания в `waitingFor`: permission prompt, input needed, sandbox request и другие [1].
- **Иконки:** `✻`/`✽` — процесс работает; `∙` — процесс завершён, сессия продолжит после ответа; `✢` — `/loop` спит
  между запусками [1].
- **Peek** — панель быстрого просмотра с ответом без подключения. Ответ из peek уходит в очередь сообщений сессии. На
  запрос разрешения из peek ответить нельзя [1].
- **Attach, detach** — подключение терминала к сессии и отключение от неё. **Pin** (`Ctrl+T`) — закрепление; держит
  процесс живым, пока сессия простаивает [1].
- **Dispatch** — запуск новой сессии из строки ввода; каждый prompt — новая сессия. **Dispatch defaults** — флаги
  `--permission-mode`, `--model`, `--effort`, `--agent`, `--restricted` для всех сессий окна [1].
- **Shell job** — команда shell в списке без модели (`!cmd` или `--exec`) [1].
- **`/bg`, `/background`** уводят разговор в фон. **`/fork`** копирует разговор в новую фоновую сессию. До 2026-07-17
  `/fork` запускал fork в виде subagent; это поведение переехало в `/subtask` [1][38][35].
- **Метка PR** — `#N` или `!N` для GitLab с цветом статуса [1].
- **Research preview** — статус ранней версии, интерфейс которой может измениться [1].
- **Соседние понятия Anthropic:**
  - auto mode — режим, где модель-классификатор проверяет действия вместо человека [13];
  - `/loop` — повтор prompt по расписанию [23];
  - `/goal` — цель, выполнение которой после каждого хода оценивает отдельная модель [22];
  - dynamic workflows — скрипт на JavaScript, который пишет Claude и который раздаёт работу subagents [19];
  - agent teams — ведущая сессия и teammates с общим списком задач [20];
  - Projects — облачный разговор-координатор с threads [24].

### Чем подход отличается

- **Первая сторона и внутри самого агента.** Отдельное приложение не нужно: всё делает тот же бинарник `claude`.
  Settings, hooks, plugins, MCP servers и keybindings переходят в запущенные сессии [1].
- **Плоский список сессий, а не иерархия работы.**
  - Нет epics, tickets, waves и порядка зависимостей. Группировка — по состоянию или по папке (`Ctrl+S`) [1].
  - Координация силами Claude — отдельный облачный продукт Projects [24][47].
- **Глубокий надзор за процессами.** Блокировки worktree, правило 48 часов для сессий, найденных мёртвыми после
  выключения, отказ удалять коммиты без push, подсказки о нехватке памяти, передача учётных данных gateway [1].
- **Безопасность контрактом, а не проверкой.**
  - Безопасность держится на изоляции, git-контракте, режимах разрешений и согласии на bypass в настройках
    пользователя [1][3].
  - Шага проверки перед PR документация agent view не описывает.
  - Проверка живёт в других местах: `/goal` с отдельной моделью-оценщиком [22], Code Review и `/code-review` [49][34].
- **Уведомления через терминал.** Плюс hooks `Notification` с типами `agent_needs_input` и `agent_completed` [1].
  Desktop-приложение отдельно шлёт уведомления ОС, Dispatch на телефоне — push [27].
- **Путь от ручной работы к продукту (вывод).** Пост Boris Cherny 2025 года о практиках описывал ручной запуск
  параллельных сессий в отдельных worktrees и переключение между ними. 2026-01-26 пост пометили как больше не
  поддерживаемый [53]. Agent view делает этот ручной приём частью CLI.

## Как это устроено внутри

Код закрыт, ссылок на модули и файлы исходников нет. Всё ниже — из документации, changelog и метаданных npm и GitHub.
Протокол связи между процессами, схема `state.json` и способ обнаружения зависаний не описаны (не подтверждено).

### Процессы и файлы на диске

- **Supervisor.**
  - Одна служба держит все фоновые сессии. Стартует по требованию при первом уходе сессии в фон или при открытии
    agent view [1].
  - Запуск по требованию — режим по умолчанию: `claude daemon stop --any` спрашивает подтверждение именно для
    остановки supervisor, запущенного по требованию [11].
  - Changelog упоминает Linux без установленной службы и команду `claude daemon uninstall`. Режим установленной службы
    не документирован (не подтверждено) [38].
- **Процесс на сессию.**
  - Каждая сессия — отдельный процесс Claude Code под supervisor [1].
  - Каждая строка — host-процесс терминала и сессия внутри него. В `ps` помощники видны как `claude bg-pty-host` и
    `claude bg-spare` [14].
- **Запасной процесс (warm standby)** [38]:
  - новый запуск забирает готовый процесс; если тот неисправен, запускает свежий (v2.1.141);
  - supervisor выдаёт запасным процессам свежий снимок учётных данных (v2.1.174) [1];
  - простаивающий запасной процесс скрыт от `ListAgents` и `SendMessage`, пока его не займёт задача (v2.1.238).
- **Связь между процессами.**
  - `claude daemon status` показывает папку сокетов и число workers [1].
  - Changelog называет части, протокол которых не описан (не подтверждено): управляющий socket с токенами
    аутентификации на каждый socket, токен сессии daemon, файл `daemon.lock` с PID и на Windows — файл ключа pipe
    daemon [38].
  - Какая из двух сборок supervisor берёт управление, решает встроенная в версию метка времени сборки (v2.1.200) [38].
  - Старый supervisor никогда не перезапускает сессию, начатую новой версией, на своём старом бинарнике (v2.1.208) [1].
- **macOS.** Host фоновых сессий — отдельный процесс с точки зрения приватности macOS. Он отдельно запрашивает доступ к
  Files & Folders. На macOS 15+ при первом подключении к LAN вызывает запрос Local Network [1].
- **Окружение и учётные данные** [1]:
  - сессии используют те же сохранённые учётные данные, что и интерактивные;
  - настройки, включая блок `env`, сессия читает из своей папки;
  - из shell, который её запустил, сессия наследует `PATH`, выбор облачного провайдера, алиасы
    `ANTHROPIC_DEFAULT_*_MODEL` и `CLAUDE_CODE_EXTRA_BODY`;
  - URL gateway, заданный только в shell, передаётся лишь в узких условиях и никогда не пишется на диск; документация
    советует держать переменные gateway в файле настроек.
- **Файлы на диске** [1][38]:

| Путь | Что там |
|---|---|
| `~/.claude/daemon.log` | Log supervisor. С v2.1.290 многострочные сообщения пишутся одной строкой в кавычках JSON |
| `~/.claude/daemon/roster.json` | Работающие сессии; по нему supervisor переподключается после перезапуска |
| `~/.claude/jobs/<id>/state.json` | Состояние сессии. Документация говорит, что это не стабильный интерфейс |
| `~/.claude/jobs/<id>/tmp/` | Рабочая папка сессии (`$CLAUDE_JOB_DIR/tmp`); запись туда без запроса разрешения |
| `~/.claude/projects/<project>/<session-id>.jsonl` | Transcript сессии; по умолчанию хранится 30 дней [15] |

- Другой `CLAUDE_CONFIG_DIR` даёт отдельный экземпляр supervisor [1].

### Цикл агента

- **Agent view своего цикла не добавляет.** Внутри каждой сессии работает обычный цикл Claude Code: собрать контекст,
  действовать, проверить результат, и так по кругу [17].
- **Разбиение работы — внутри сессии:**
  - subagents: по умолчанию до 20 одновременно (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`) [21];
  - dynamic workflows: Claude пишет скрипт на JavaScript, а runtime его выполняет; план переносится в код. По
    умолчанию 16 агентов одновременно, до 1000 агентов за запуск; запуск можно продолжить в той же сессии [19];
  - при effort `ultracode` Claude сам решает, когда запускать workflows, например один — понять, второй — изменить,
    третий — проверить [19];
  - `/batch` делит одно изменение на 5–30 subagents, каждый в своём worktree [2];
  - agent teams (экспериментальные, выключены по умолчанию): ведущая сессия и teammates; общий список задач в
    `~/.claude/tasks/{team}`; почтовые ящики JSON в `~/.claude/teams/{team}/inboxes/{agent}.json`; зависимые задачи
    разблокируются сами [20].
- **`/loop` в фоне.**
  - Prompt по расписанию, например проверять, прошёл ли CI, и разбирать комментарии review. Интервал подстраивается
    от 1 минуты до 1 часа [23]. Пост о запуске называет такие циклы «PR babysitters» — циклы, которые следят за PR
    [44].
  - С v2.1.290 сессия, которая ждёт следующего запуска `/loop`, остаётся живой при обновлениях и нехватке памяти
    [38].
  - Если время запуска самостоятельного цикла пришлось на момент, когда процесс был остановлен, цикл
    останавливается, а в transcript появляется заметка [23].

### Параллельность и координация

- **Планировщика и координатора нет.** Каждый prompt в agent view запускает новую независимую сессию [1].
- Документация: сессии agent view сообщают результат только человеку. Координатор — человек: он раздаёт независимые
  задачи и возвращается позже [2].
- Сессии могут писать друг другу через cross-session messaging (сообщения между сессиями): `ListAgents` находит
  адресата, `SendMessage` отправляет [12].
  - Сессия читает сообщения между вызовами инструментов или начинает новый ход, если простаивает [12].
  - Задержанное сообщение становится строкой Needs input с текстом «approve message from» (v2.1.257) [1].
- Координация силами самого Claude — в agent teams [20], dynamic workflows [19] и облачных Projects [24].

### Восстановление после сбоев

- **Политика по состоянию сессии** [1]:

| Состояние | Что делает supervisor |
|---|---|
| Работает, ждёт на prompt или в диалоге, подключена | Держит процесс. Работающие subagents, workflows, monitors и ожидающие запуски `/loop` считаются работой |
| Закончила или ждёт сообщения и не подключена около часа | Останавливает процесс. Разговор остаётся на диске и продолжается при подключении или ответе. Закреплённая сессия (`Ctrl+T`) остаётся живой |
| Процесс неожиданно завершился | Перезапускает. Сессию, которую пользователь сам увёл в фон и убил, помечает stopped |

- **Пустые сессии** после `←` убираются через 5 минут (v2.1.141) [38].
- **Нехватка памяти.** Сначала останавливаются простаивающие сессии, потом простаивающие закреплённые, если память не
  освободилась. Закреплённые идут последними с v2.1.147 [1][38]. Сессия, умершая при старте на машине с нехваткой
  памяти, показывает подсказку «possibly low memory» [1].
- **Зависания.**
  - Если открыть сессию, которая перестала отвечать, supervisor перезапускает её, и она продолжает прерванный ответ
    с того места (v2.1.200) [1].
  - Перезапущенной после сбоя сессии сообщают о сбое. Прерванный ответ старше примерно часа не продолжается
    (v2.1.211) [1].
  - Есть обнаружение зависших workers. v2.1.143 убрал ложные срабатывания после сна машины и macOS App Nap [38].
  - Зависшие агенты получают метку «Needs attention» (v2.1.196) [38].
  - Daemon замечает скачки системных часов и не считает их временем простоя (v2.1.142) [38].
- **Обновления.** После auto-update supervisor перезапускается на новой версии и переносит простаивающие сессии.
  Работающие, ждущие и подключённые сессии не прерываются. `claude respawn --all` переносит и работающие [1].
- **Смерть supervisor.** На macOS и Linux сессии останавливаются, если за минуту не подключился новый supervisor.
  `claude agents` запускает новый [1]. С v2.1.295 выход из `claude agents` не запускает новый supervisor; тогда
  работающие сессии останавливаются примерно через минуту, если снова не открыть `claude agents` [1][38].
- **Сон.** Процессы продолжают работу после пробуждения. Сессия, которая отвечала в момент сна и не ожила,
  перезапускается и продолжает прерванный ответ [1].
- **Выключение и перезагрузка** [1]:
  - если последний прогресс был в пределах 48 часов, сессия показывается как failed и поднимается из сохранённого
    transcript при подключении или ответе;
  - если позже — как stopped с пометкой `ended while the background service was off`;
  - сессии, которые ждали ввода, остаются в Needs input.
- **Что переходит в новый процесс, когда старый останавливается** [1][6][38]:
  - фоновые команды shell и фоновые subagents передаются;
  - monitors и команды shell, запущенные subagents, останавливаются;
  - dynamic workflows продолжаются, только если Claude запустит их заново; с v2.1.300 повторный запуск идёт через
    одобрение инструмента Workflow;
  - `CLAUDE_CODE_DISABLE_BG_EXIT_HANDOFF=1` выключает передачу: всё останавливается вместе с процессом.
- **Сохранность сообщений и данных.**
  - Недоставленный ответ сохраняется и уходит следующим prompt после перезапуска, кроме ответов на `!` и `/` [1].
  - Transcript, ошибочно прочитанный как пустой, переименовывается с суффиксом `.orphaned-`, а не удаляется
    (v2.1.196) [38].
  - Shell jobs никогда не перезапускаются автоматически [1].
- **Повторы запросов к API.** Временные сбои повторяются до 10 раз с растущей паузой [5]. Режим retry watchdog
  меняет это на бесконечные повторы с ожиданием сброса лимита [6].

### Изоляция

- **Worktree создаётся лениво.** Запущенная сессия стартует в рабочей папке пользователя. Перед первой правкой Claude
  переводит её в git worktree в `.claude/worktrees/`. До этого `Edit`, `Write` и `NotebookEdit` по общей рабочей
  копии заблокированы [1].
- **Когда изоляции нет** [1]:
  - сессию увели в фон из уже открытой сессии клавишей `←` или командой `/bg`;
  - сессия уже в linked worktree;
  - папка не git-репозиторий и hook `WorktreeCreate` не задан;
  - запись идёт вне рабочей папки;
  - задано `worktree.bgIsolation: "none"`.
- **Четыре проверки** действуют для сессии и всех её subagents [3]:
  1. правки файлов, которые целят в main checkout;
  2. рабочие папки команд, которые указывают в main checkout;
  3. перенаправления git в main checkout: `-C`, `--git-dir`, `GIT_DIR`, `cd`;
  4. форма команды: команды, чьё обращение к git нельзя проверить по тексту. Эту проверку выключить нельзя.
- Запись вроде `cp` или перенаправления вывода shell в main checkout проверки не отслеживают. Это остаётся на
  разрешениях и sandbox [3].
- **Блокировки и уборка** [3][38]:
  - работающая сессия держит `git worktree lock` (v2.1.248);
  - периодическая уборка удаляет созданные Claude worktrees старше `cleanupPeriodDays`; worktree с изменёнными или
    неотслеживаемыми файлами или с коммитами без push остаётся;
  - Claude помечает свои worktrees в метаданных git; worktrees без этой пометки уборка не трогает;
  - уборка снимает блокировки, чей процесс-владелец уже умер;
  - с v2.1.143 уборка больше не откатывается к `rm -rf`.
- **Что worktree делит с main checkout** [3]:
  - `.git`;
  - plugins уровня проекта;
  - одобрения «don't ask again» — они пишутся в `.claude/settings.local.json` main checkout;
  - чтение неотслеживаемых skills, agents и commands из main checkout.
- **Sandbox ОС** [18]:
  - Seatbelt на macOS, bubblewrap и socat на Linux и WSL2; на Windows без WSL команды идут без sandbox;
  - в фоновых сессиях строгий режим sandbox распространяется и на команды, набранные в режиме `!`;
  - в worktree список разрешённой записи sandbox включает только общий `.git`, а `hooks/` и `config` внутри него
    запрещены (v2.1.149) [38].
- Локальных контейнеров и виртуальных машин нет. Облачные threads в Projects получают свой облачный sandbox на thread
  [24].

### Состояние и память

- **Transcripts** хранятся в JSONL по пути `~/.claude/projects/<project>/<session-id>.jsonl`, по умолчанию 30 дней.
  Фоновые сессии помечены `bg` в `/resume` [15]. Удаление сессии transcript не удаляет [1].
- **Что сохраняется между перезапусками процесса:** режим разрешений, модель, effort, перенесённые флаги, имя и
  отложенный текст prompt (prompt stash) [1].
- **Рабочая папка** `$CLAUDE_JOB_DIR/tmp`: запись и правка там без одобрения; папка удаляется вместе с сессией [1][6].
- **Пересказ при подключении.** Claude пишет короткий пересказ того, что произошло, пока человека не было [1].
- **Контекст** [17]:
  - автоматическое сжатие разговора (auto-compaction) с защитой от сжатия по кругу;
  - CLAUDE.md держит правила, которые должны пережить сжатие;
  - определения инструментов MCP загружаются по требованию.
- **Auto memory** [16][38]:
  - лежит в `~/.claude/projects/<project>/memory/MEMORY.md`; в каждую сессию загружаются первые 200 строк или 25 KB;
  - общая для всех worktrees одного репозитория и локальная для машины;
  - из фоновой сессии её можно выключить, но нельзя включить (v2.1.285).

### Проверка качества

- **Своего шага проверки у agent view нет.** Он не запускает tests, CI или агентов review [1].
- **Что есть вокруг:**
  - фаза проверки в цикле самого агента [17];
  - `/goal` — hook Stop на основе prompt в рамках сессии. После каждого хода маленькая быстрая модель решает: «ещё не
    выполнено», «выполнено» или «невозможно». Завершение решает отдельная модель, а не сам worker. Цикл
    останавливается, если Claude несколько ходов подряд не вызывает инструменты [22];
  - hooks Stop, а в agent teams — hooks `TaskCompleted` и `TeammateIdle` как детерминированные проверки [22][20];
  - `/loop` с проверкой CI и разбором комментариев review, интервал от 1 минуты до 1 часа [23];
  - `/autofix-pr` передаёт PR облачной сессии; она подписывается на события GitHub и отправляет исправления. Нужно
    Claude GitHub App [25];
  - `/code-review` локально, Code Review и ultrareview в облаке [34].
- **Сигнал для человека** — цвет метки PR: зелёный, когда checks прошли и review не блокирует [1].

### Лимиты и стоимость

- **Расход.** Каждая фоновая сессия тратит подписку отдельно. Десять агентов — примерно десятикратный расход [1].
- **Окна лимитов** [5][32]:
  - использование Pro и Max считается одновременно в 5-часовом и в недельном окне;
  - большой веер workflow может исчерпать недельный лимит раньше, чем сбросится 5-часовое окно;
  - места Team и Enterprise работают со скользящим 5-часовым окном и недельным окном;
  - перегрузка 529 не тратит лимит.
- **Дополнительные вызовы модели.** Каждая сводка строки — короткий запрос через провайдера [1]. Оценка `/goal` идёт
  на маленькой быстрой модели [22].
- **Ожидание сброса лимита.** Интерактивные сессии ждут сброса и продолжают сами (максимум 3 продолжения, не дольше
  24 часов до сброса) [4]. Фоновым сессиям это не предлагается [4]. Для них остаётся только retry watchdog, и его
  работа в agent view не подтверждена [6].

### Права и безопасность

- **Стартовый режим разрешений** зависит от того, как сессия появилась: уведённая в фон сохраняет режим, запущенная
  стартует как новая `claude` в папке, из view после `←` берёт `defaultMode` папки с ограничениями [1][13].
- **Bypass.** Требует ключ `skipDangerousModePermissionPrompt` в `~/.claude/settings.json`. Без него запрос
  игнорируется с постоянным предупреждением на экране [13].
- **Auto mode** [13]:
  - отдельная модель-классификатор (по умолчанию Sonnet 5 или проверка на стороне сервера, где она есть) блокирует
    действия, которые выходят за запрос, целят в незнакомую инфраструктуру или похожи на действия по указке
    враждебного содержимого;
  - после 3 блокировок подряд или 20 всего сессия возвращается к запросам разрешений; в фоновой сессии такой запрос
    становится строкой Needs input (вывод) [1];
  - запрос разрешения на удаление по критичному пути показывает обратный отсчёт 2 минуты (в режимах auto и
    bypassPermissions) и по истечении отклоняется, чтобы сессия без присмотра продолжала работу; после трёх таких
    отказов следующие отклоняются сразу.
- **Workspace trust** проверяется перед любым запуском [1].
- **Где нужен человек** [1]:
  - вопросы, запросы разрешений, sandbox и MCP, команды, которым нужен терминал, ошибки вроде истёкшего входа —
    строка уходит в Needs input;
  - вопросы можно закрыть ответом из peek, в том числе номером варианта;
  - диалоги разрешений, sandbox и MCP требуют подключения к сессии;
  - строка показывает, сколько сессия ждёт (`waiting 3m`), и неверный вывод hook.
- **Сообщения других сессий** никогда не считаются согласием человека [12].
- **Администрирование:** выключатель agent view через managed settings [1][6], corporate launcher [14], флаги
  `--restricted` и `--safe-mode` [1], выход из всех сессий через `/logout` (v2.1.323) [38].

### Наблюдаемость

- **Список.** Группы Pinned, Ready for review, Needs input, Working, Completed. Сводки — от модели класса Haiku в
  конце хода и раз в несколько минут, между ними — из вывода сессии не чаще раза в 15 секунд [1].
- **Сигналы вне списка.** Число ждущих сессий в заголовке вкладки, подсказка `← 2 agents` в footer, уведомления
  только при открытом view [1][9].
- **Скрипты.** `claude agents --json` с полями `state`, `status` и `waitingFor` [1].
- **Logs и задачи.** `claude logs <id>`, `claude daemon logs`, `/tasks`, `/workflows` [1][2].
- **Пробелы.** Хронологии запуска, кроме transcript (`Ctrl+O`), документация не описывает [1]. Метрик OpenTelemetry
  именно для agent view исследование не нашло (не подтверждено).

#### Видимость расхода и использования

- **Нет колонки использования.** Запросы на токены, контекст и лимит сессии или недели в строке (#59412, #92708 и
  другие) закрыл бот за неактивность, а не продуктовое решение [61][101][43]. Строки показывают состояние, сводку и
  метку PR; документация только предупреждает, что десять агентов тратят лимит примерно в десять раз быстрее [1].
- **Самая громкая тема на HN — стоимость сводок subagents** (591 очко, 236 комментариев, 2026-10-29). Она про сводки
  прогресса фоновых *subagents*, а не про строки agent view [121].
  - Одна команда измерила: такие сводки — 16,4% оценки недельных трат и 19,7% запросов [121].
  - Инженер Anthropic ответил иначе: сводку получают только активно работающие фоновые агенты, примерно раз в 30
    секунд. По пользователям, которые шлют телеметрию, сводки — около 2% стоимости по прейскуранту и чуть меньше 4%
    запросов (около 6% стоимости в терминале). Исправление сводок, которые промахивались мимо prompt cache, вышло в
    2.1.311, более дешёвый режим в работе [121]. Числа команды и Anthropic расходятся.
  - Комментаторы называли Claude Code раздутым и просили выключатель [121].
  - `CLAUDE_CODE_DISABLE_AGENT_PROGRESS_SUMMARIES` доступен с 2.1.318 и объявлен в 2.1.323 [39][93].
  - Сводки строк agent view — другой механизм: модель класса Haiku пишет их в конце хода и переписывает раз в
    несколько минут [1]. Пользователи путали два механизма; один спрашивал, останавливает ли `disableAgentView` эти
    вызовы [121].

#### Пробелы работы без присмотра

- **Запросы разрешений без ответа.** Фоновая сессия `--bg` без присмотра может часами стоять на запросе разрешения в
  auto mode, который никто не видит; автор замерил 8,5 часа (#97911, открыт) [106].
- Стороннее GUI для agent view не умеет отвечать на запросы разрешений инструментов и одобрения планов и советует
  задать режим разрешений заранее [124].
- **Нет отдельного API состояния сессий для внешних инструментов.** Официальный источник один — `claude agents
  --json`, а `~/.claude/jobs/` — нестабильный интерфейс [1]. По документации `--json` выводит все живые сессии,
  включая интерактивные (`kind: interactive`); интерактивные сессии из других терминалов не показывает сам список
  agent view, пока их не увели в фон [1]. Один пользователь собрал виджет KDE на hooks (#94620, открыт) [103].

### Лимиты использования: что пишут пользователи и что выпущено

- **Что выпущено.** С v2.1.234 (2026-08-17) Claude Code сам продолжает сессию после сброса лимита claude.ai. Включено
  по умолчанию, настройка «Continue automatically at usage limit» или `autoContinueAtUsageLimit` [39][4][7].
- **Документированные границы** [4]: только интерактивные сессии со входом через подписку; не больше трёх
  автоматических продолжений подряд; при сбросе дальше 24 часов, в Remote Control и у teammates agent teams ожидание
  само не начинается, но его можно начать вручную через `/rate-limit-options`; в фоновых сессиях и запусках `-p` не
  предлагается вообще; уход в фон отменяет ожидание; запросы разрешений могут остановить продолженную задачу.
- **Путь без присмотра.** С `CLAUDE_CODE_RETRY_WATCHDOG=1` ошибки 429 и 529 повторяются бесконечно, а запросы ждут
  сброса лимита [6]. v2.1.301 добавил предел, насколько далёкий сброс ещё ждать; v2.1.305 — раннюю проверку, не снят
  ли лимит [39]. Наследуют ли эту переменную сессии supervisor от shell, который их запустил, — не подтверждено.
- **Workflows.** Dynamic workflows останавливаются на лимите и продолжают после сброса с v2.1.271; workflows вкладки
  Code в Desktop — с v2.1.323 [39].
- **Сообщения пользователей:**
  - #74162 (закрыт ботом): фоновые агенты падают, а не ждут, хотя ошибка содержит время сброса. Комментатор выяснил,
    что авто-продолжение охватывает только главный поток [79].
  - #89263 (закрыт ботом 2026-11-03): авто-продолжение не включается, если лимит задел только фоновые subagents, а
    главный поток простаивает. Работа молча теряется [98].
  - #94222 (закрыт как выполненный 2026-11-12): автор, который сам публикует plugin в этой области, проверил шесть
    сессий. 449 subagents были оборваны, 438 из них запущены заново с нуля, а не продолжены [102]. С v2.1.299
    уведомления сообщают, что агента остановил лимит [39].
  - #96231 (открыт): subagents, ждущие в цикле retry watchdog, не показывают статус лимита и выглядят зависшими [105].
  - #85676 (открыт): уход сессии в фон после недельного лимита потерял её строку и запустил дубликат [91].
- **Стороннее решение.** `agent-limit-retry` пишет файл передачи работы на 90% окна, запускает задания без интерфейса,
  которые спят до сброса, и умеет недельные лимиты. Источник заинтересован: у проекта есть платный уровень [126].
- **Документация agent view молчит** о том, что делает фоновая сессия на лимите [1]. Кроме сообщений выше — не
  подтверждено.

### Почему внедряют, обходят или бросают

- **Внедряют, потому что** функция встроена и ничего не стоит отдельно; есть уведомления и метки PR; сессии
  переживают закрытие терминала; до сессий можно добраться из мобильного приложения [44][1][112][113][115][118].
- **Обходят или бросают:**
  - примерно в 17 issues метки комментаторы применяют или советуют `disableAgentView` как обход [43]. Причины:
    больше проблем, чем пользы [75]; возврат к обычной работе во вкладках [85]; раздвоение разговоров [96];
    протекание окружения [70];
  - на HN один пользователь остаётся на обычных вкладках [120], другой написал, что `claude agents` не прижился, и
    собрал свою локальную доску агентов [114];
  - 21 issue метки упоминает откат на старую версию [43].
- **Сторонние инструменты живут дальше**, потому что поддерживают нескольких вендоров (Claude, Codex и другие), дают
  GUI или строятся вокруг задач.
  - В теме Ask HN herdr (стороннее терминальное приложение для агентов) назвали в 3 из 13 ответов верхнего уровня,
    `claude agents` — в 1 [115]. Сторонники herdr ценят его собственный список агентов и встроенные worktrees [116].
  - Над agent view появляются GUI-слои:
    - чат-интерфейс для Windows отвечает сессии так: останавливает её и запускает снова через
      `claude --bg --resume`; это стоит нескольких секунд на ответ [124];
    - панель статуса рядом с Dock на macOS [125];
    - виджет KDE на hooks [103].
- **Прогноз с HN:** вся эта категория уйдёт внутрь Claude Code и Codex, и они будут делать большую часть работы без
  доплаты [116].
- **Разработчик своего TUI на Rust** написал: agent view удобен для перехода между сессиями, но не решает перегрузку
  окнами. Он хотел видеть issues и PR рядом с сессиями [119].

### С чем сравнивают

- **tmux, cmux, herdr.** Для работы только с Claude agent view может заменить tmux на своей машине [118]. Для
  удалённых серверов tmux по-прежнему советуют (вторичный источник) [130]. Тем, кто работает с несколькими
  агентами, больше нравится herdr [115][116][118].
- **Conductor** agent view заменяет частично [112].
- **Приложение Codex.** Одному пользователю оно показалось чуть лучше, но тоже трудно управляемым [114].
- **Claude Desktop.** Пользователи просили панель Background Tasks из Desktop в VS Code (+21, закрыт как выполненный
  2026-10-22) [82]. Часть пользователей HN перешла с TUI на desktop-приложения, когда сессий стало больше [122].
- **Claude Code Projects (облако).** Один пользователь ставит Projects выше agent view как менеджер проекта поверх
  сессий [118].

## Слабые места и чего нет

- **Research preview.** Интерфейс и клавиши могут измениться [1].
- **Только локально.** Сессии живут на машине пользователя и останавливаются при выключении [1].
- **Только Claude.** Codex и другие агенты как workers не поддерживаются; внешние инструменты — только через MCP [2].
- **Нет иерархии работы.** Нет epics, tickets, waves, зависимостей и планировщика. Каждую задачу запускает человек
  [1][2].
- **Нет своей проверки качества.** Agent view не запускает tests, CI и review; проверку собирают из `/goal`, hooks,
  `/loop` и Code Review [1][22][23][34].
- **Merge запрещён жёстко.** Фоновые сессии не делают merge даже с разрешением проекта и пользователя; три issue об
  этом открыты [1][87][97][109].
- **Фоновые сессии не ждут сброса лимита.** Авто-продолжение есть только у интерактивных сессий, и не дальше 24 часов
  и трёх продолжений. Для фоновых — только retry watchdog, его работа в agent view не подтверждена [4][6].
- **Subagents на лимите.** Обрываются и запускаются заново с нуля; авто-продолжение их не видит [79][98][102].
- **Нет счётчиков расхода в списке.** Нет токенов, контекста и лимитов по сессии; запросы закрыты ботом [61][101].
- **Уведомления только при открытом view** и только через терминал или hooks [1][9].
- **Запрос разрешения из peek не ответить.** Нужно подключаться; сессия без присмотра может часами стоять на запросе
  [1][106].
- **Нет хронологии запуска** кроме transcript; метрик OpenTelemetry для agent view не найдено [1].
- **Нет стабильного API, кроме `--json`.** Он отдаёт только время старта, поэтому сортировать по активности нельзя
  [58][1]. Интерактивные сессии `--json` по документации показывает; сам список agent view их не показывает до ухода в
  фон [1].
- **Уход за списком.** Нет сортировки по активности, нельзя скрыть без удаления, Completed смешивает разные случаи
  [58][71][89][57].
- **Хрупкость daemon.** Crash loops, утечки процессов (64 процесса, 7,1 GB), ожившие агенты, которые сожгли лимит
  [78][95][72].
- **Потери данных.** Раздвоение разговоров при уходе в фон, пропадающий текст в transcript, тихая смерть subagents,
  удаление worktrees с работой [90][68][65][80][108].
- **Протекание настроек и окружения** между сессиями [73][70][107].
- **Windows.** Неотзывчивый TUI, порча отрисовки, старая ширина после изменения размера; нет sandbox и corporate
  launcher [62][86][88][18][14].
- **Удаление из view удаляет незакоммиченные изменения** в worktree, созданном Claude [1].
- **Нет общей доски для команды** [1].
- **Нет GUI.** Только TUI в терминале; Desktop своей панелью CLI-сессий не видит [27]. GUI делают сторонние
  разработчики [124][125][103].
- **Стоимость сводок.** Каждая сводка строки — платный запрос [1]. Сводки прогресса subagents — отдельный спорный
  расход [121].
- **Автозакрытие issues ботом.** Много запросов закрыты за неактивность без решения [43][94].

### Где пересекаются

- **Исходная проблема одна.** Оба продукта исходят из того, что внимание человека — главный дефицит при многих
  параллельных агентах [1][49].
- **Сессии отдельно от терминала.** Обе системы держат работу агентов живой без открытого окна терминала и показывают
  все сессии одним видом [1].
- **Worktree на задачу.** Agent view автоматически даёт каждой сессии свой git worktree [1][3]; worfy — каждому
  Ticket.
- **PR как итог работы.** Agent view показывает PR и его checks цветом и собирает их в группу Ready for review [1];
  worfy показывает PR с бейджами CI.
- **Сортировка по вниманию.** Needs input, счётчик ждущих сессий, уведомления — та же задача, что уведомления worfy
  [1].
- **Работа без присмотра и лимиты.** Anthropic двигается к ожиданию сброса лимитов: в интерактивных сессиях, в
  workflows, в `/goal`, в облачных threads [4][19][22][24]. У worfy это часть Autopilot.
- **Повторы и перезапуски.** Retry watchdog и перезапуск процессов supervisor закрывают ту же область, что повторы
  ошибок API у Autopilot [6][1].
- **Auto-approval.** Auto mode с моделью-классификатором и обратным отсчётом для `rm` — та же область, что
  автоодобрение по политике у Autopilot [13].
- **Те же сессии Claude Code.** worfy запускает Claude Code; agent view — функция того же CLI, его settings, hooks и
  plugins общие [1].

### Где расходятся

- **Форма:** TUI в терминале против desktop-приложения с Canvas [1].
- **Агенты:** только Claude против Claude Code и Codex CLI [2].
- **Структура работы:** плоский список сессий против Epics, Tickets, Orchestrator и Waves [1][2].
- **Проверка:** у agent view нет Gate, ревьюеров и доказательств; проверка собирается отдельно [1][22][34].
- **Merge:** фоновые сессии agent view не делают merge никогда [1].
- **Лимиты в фоне:** фоновые сессии agent view сами не ждут сброса лимита [4].
- **Связь машин:** через серверы Anthropic против LAN [12].
- **История:** transcript и logs против Flight Recorder и Work track [1].
- **Цена:** agent view входит в подписку и ставится вместе с CLI [44].

- Нужна видимость расхода и лимитов по сессии [61][101].
- Нужно ожидание сброса лимитов без присмотра, включая subagents и недельные окна [4][79][98][102].
- Нужно скрывать сессии без удаления и сортировать по активности [58][71][89].
- Нужны tickets и PR рядом с сессиями [119].
- Нужна политика merge, которую задаёт пользователь [87][97].
- Нужна поддержка нескольких агентов [115][116].
- Нужен GUI и статус, видный всегда [124][125][103].
- Нужна устойчивая работа в терминалах Windows [62][88].

## Механизмы, которые стоит изучить

1. **Политика процесса по состоянию сессии.**
   - Что это: supervisor решает, держать ли процесс сессии, по её состоянию.
   - Как работает: работающие, ждущие на prompt и подключённые сессии держатся. Закончившие и неподключённые около
     часа останавливаются, разговор остаётся на диске и поднимается при ответе. Закреплённые не останавливаются.
     Упавшие перезапускаются. После выключения действует правило 48 часов: failed с подъёмом из transcript или
     stopped. При нехватке памяти первыми идут простаивающие, закреплённые — последними.
   - Источник: [1][38].
2. **Перенос сессий при обновлении и запасные процессы.**
   - Что это: обновление CLI без прерывания работы и быстрый старт новых сессий.
   - Как работает: после auto-update supervisor переезжает на новую версию и переносит только простаивающие сессии;
     работающие не трогает, `claude respawn --all` переносит их вручную. Старый supervisor не перезапускает сессию
     новой версии на старом бинарнике. Какая сборка главнее, решает встроенная метка времени сборки. Запасной процесс
     получает свежий снимок учётных данных и скрыт от других сессий, пока его не займут.
   - Источник: [1][38].
3. **Ленивая изоляция в worktree с проверками на уровне инструментов.**
   - Что это: сессия уходит в worktree перед первой правкой, а не при запуске.
   - Как работает: до первой правки `Edit`, `Write` и `NotebookEdit` по общей копии заблокированы. Четыре проверки
     ловят правки main checkout, рабочие папки команд, перенаправления git (`-C`, `--git-dir`, `GIT_DIR`, `cd`) и
     команды, чей git нельзя проверить по тексту. Проверки действуют и на subagents. `cp` и перенаправления вывода
     не ловятся.
   - Источник: [1][3].
4. **Безопасное удаление и уборка worktrees.**
   - Что это: правила, которые не дают потерять работу при удалении сессии.
   - Как работает: `git worktree lock` на время работы; уборка удаляет только worktrees с пометкой Claude в
     метаданных git и только без изменений и коммитов без push; снимает блокировки умерших процессов; без отката к
     `rm -rf`. Удаление отказывается выбрасывать коммиты без push, пока не дан `--discard-unpushed`. Transcript
     переживает удаление.
   - Источник: [1][3][38].
5. **Двухуровневые сводки строк.**
   - Что это: дешёвое обновление статуса и редкая сводка от модели.
   - Как работает: пока сессия работает, строка обновляется не чаще раза в 15 секунд из её собственного вывода без
     вызова модели. Модель класса Haiku пишет сводку в конце хода и раз в несколько минут на длинном ходу. С
     v2.1.205–206 сводка берётся из однострочного отчёта самой сессии. Имя сессии тоже даёт Haiku.
   - Источник: [1][35].
6. **Причины ожидания как данные.**
   - Что это: строка Needs input знает, чего именно ждёт сессия.
   - Как работает: поле `waitingFor` (permission prompt, input needed, sandbox request, worker request, dialog open),
     таймер «waiting 3m», имя hook с неверным выводом, строка «approve message from» для задержанных сообщений.
     Счётчик ждущих сессий выводится в заголовок вкладки и footer обычных сессий.
   - Источник: [1].
7. **Стабильный JSON для внешних инструментов.**
   - Что это: `claude agents --json [--all] [--cwd]` как единственный поддерживаемый способ читать состояние.
   - Как работает: поля `kind`, `state`, `status`, `waitingFor`, `pid`, `startedAt` и другие; файлы
     `~/.claude/jobs/` прямо объявлены нестабильными. В выводе есть все живые сессии, включая интерактивные
     (`kind: interactive`); список agent view показывает интерактивную сессию только после ухода в фон. Пользователи
     жалуются, что нет времени последней активности.
   - Источник: [1][58][103].
8. **Привязка PR к сессии по командам агента.**
   - Что это: сессия сама узнаёт свой PR без настройки.
   - Как работает: разбор вывода команд `gh`, которые правят PR; `gh pr view` по ветке после checkout или push; если
     PR ещё нет — повтор на следующих до 5 командах `git`, `gh`, `glab` или `curl`. Цвет метки — по checks, review
     и merge; группа Ready for review собирает PR, которым нужен review или у которых упали checks.
   - Источник: [1].
9. **Ожидание сброса лимита: интерактивный режим и retry watchdog.**
   - Что это: два разных способа пережить лимит подписки.
   - Как работает: интерактивная сессия ждёт сброса и просит Claude продолжить задачу, а не повторяет последнее
     сообщение; максимум 3 продолжения подряд; сама не начинает ожидание, если сброс дальше 24 часов, и в сессиях
     Remote Control и teammates agent teams (там его можно начать вручную через `/rate-limit-options`); фоновым
     сессиям и запускам `-p` ожидание не предлагается вообще; после сна дольше 30 минут ждёт `Enter`; включить через
     `/config key=value` нельзя, потому что это разрешает работу без присмотра; события видны hooks
     `quota_auto_resume_*`. Retry watchdog повторяет 429 и 529 бесконечно, ждёт время сброса из ответа, имеет
     пределы ожидания и раннюю перепроверку снятия лимита, а на лимите трат сразу завершается.
   - Источник: [4][6][9][38].
10. **Согласие не передаётся между сессиями.**
    - Что это: правила для сообщений одной сессии другой.
    - Как работает: политика входящих `accept`, `hold` или `refuse` зависит от режимов разрешений обеих сессий; до
      100 задержанных сообщений; задержанное сообщение ждёт человека как строка Needs input. Сообщение не может
      одобрить запрос, а команды из его текста не выполняются; менять настройки по просьбе другой сессии Claude Code
      запрещает принимающему Claude инструкцией. На одной машине — Unix socket или named pipe, без серверов
      Anthropic. В auto mode классификатор проверяет каждое исходящее сообщение.
    - Источник: [12][13][1].
11. **Git-контракт с отчётом в конце.**
    - Что это: фиксированные правила git для фоновой сессии.
    - Как работает: коммит без вопроса, push ветки, draft PR только когда задача требует; никогда push в main, force-
      push и merge; инструкции в CLAUDE.md и memory важнее. Каждая работа заканчивается отчётом, где лежит результат:
      путь, ветка, PR или ответ. Пользователи жалуются на жёсткий запрет merge.
    - Источник: [1][87][97].
12. **Отдельная модель решает, выполнена ли цель, и отсчёт для опасных команд.**
    - Что это: проверки, которые не зависят от самооценки worker.
    - Как работает: `/goal` — hook Stop, где после каждого хода маленькая быстрая модель отвечает «не выполнено»,
      «выполнено» или «невозможно»; цикл останавливается, если несколько ходов нет вызовов инструментов. В режимах
      auto и bypassPermissions запрос на удаление по критичному пути ждёт ответа 2 минуты и по истечении
      отклоняется; в auto mode после 3 блокировок классификатора подряд или 20 всего сессия возвращается к запросам
      разрешений.
    - Источник: [22][13].
