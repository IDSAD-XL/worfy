## Модель работы

- **Развёртывание — self-hosted.** Symphony — долгоживущий фоновый сервис (daemon) без собственного интерфейса.
  Спецификация описывает его как планировщик, запускатель агентов и читатель трекера [11]. Его ставят на свою машину
  или сервер. В OpenAI он работает на devboxes (удалённых машинах разработчиков) и не останавливается [1].
- **Чем Symphony не является.** Это не SaaS и не desktop-приложение [11][13]. Богатый веб-интерфейс, многопользовательский
  control plane (общий управляющий сервис для многих команд) и общий движок workflow — явные non-goals
  спецификации [11].
- **Что работает в облаке.** Трекер задач — внешний сервис: Linear, GitHub, Jira Cloud, Asana или GitLab [13]. Модель
  отвечает через аккаунт Codex пользователя [13].
- **Удалённые машины.** Опционально — SSH workers: один центральный оркестратор запускает Codex на других хостах по
  SSH [11][13][27].
- **Агенты.** Только Codex в режиме app-server: JSON-RPC через stdio [11]. Подходит любой процесс, который говорит на
  совместимом протоколе app-server [11]. Claude Code и другие агенты есть только в переписанных версиях сообщества,
  например hatice на Claude Agent SDK и форк Automattic [129][144][147].
- **Модели.** Выбираются флагами в `codex.command` [13]. Эталонный `WORKFLOW.md` ставит `gpt-5.5` с
  `model_reasoning_effort=xhigh` [14]. К 2026-04-27 модель там сменили с `gpt-5.3-codex` на `gpt-5.5` [38].
- **Аккаунт.** Symphony использует аккаунт, в который вошёл Codex CLI. Live e2e test монтирует файл входа хоста
  `~/.codex/auth.json` в каждый SSH worker [13]. Одно сообщение о баге в Discussions описывает запуск с аккаунтом
  ChatGPT [93][94][95].
- **Один пользователь или команда:**
  - Командная часть — общий трекер. Любой, кто может завести задачу в опрашиваемой области трекера, запускает работу
    агента [1][11][13]. `WORKFLOW.md` лежит в репозитории под контролем версий [11]. Есть маршрутизация по
    исполнителю, opt-in по метке и лимиты по состояниям [11][13].
  - По устройству это инструмент одного оператора: один сервис и один терминальный интерфейс. Нет аккаунтов, ролей и
    SSO [11][13]. Dashboard без аутентификации. Discussion #120 просит хотя бы предупреждать, если dashboard открыт не
    только на localhost [88]. Ничто не мешает двум экземплярам обслуживать один проект: PR #8 с блокировкой закрыт
    без слияния [41].
  - Уведомлений нет ни в документации, ни в коде. Люди узнают о событиях из уведомлений самого трекера [13][14].
- **Платформы.** Бинарники для macOS и Linux, на arm64 и x86_64. Windows нет [13]. Hooks и запуск агента
  предполагают `sh` и `bash -lc` [11][29].
- **Кто пользуется.** Внутри OpenAI — команды, которые взяли Symphony сами после внутреннего демо [1]. Снаружи —
  одиночки и маленькие команды, у которых уже есть Linear, Codex и нормальный CI [115][116][120].

### Что получает пользователь

1. **SPEC.md — главный продукт.**
   - Статус «Draft v1», без привязки к языку программирования. Около 2300 строк и 12 тыс. слов [11][10].
   - README в первом варианте («Make your own») предлагает сказать своему coding-агенту: реализуй Symphony по этой
     спецификации [10].
   - В спецификации есть матрица conformance tests (§17: проверки, что реализация соответствует спецификации) и
     чек-лист definition of done (§18) [11]. Профили соответствия: Core, Extension и Real Integration, то есть проверки
     на живых сервисах [11].
   - Раздел настроек нарочно избыточен, чтобы coding-агент быстро написал слой конфигурации [11 §6.4].
   - По словам OpenAI, Codex написал версию на Elixir за один проход. Чтобы найти неоднозначности, Codex также
     реализовал спецификацию на TypeScript, Go, Rust, Java и Python [1]. PR #102 (общий интерфейс трекеров) сообщает,
     что реализации на TypeScript, Python и Go без предварительного контекста прошли проверки [56].
2. **Эталонная реализация на Elixir/OTP** в папке `elixir/` [13].
3. **Эталонный набор политик:** `elixir/WORKFLOW.md` и семь Codex skills в `.codex/skills` [14][16]. Skill — папка с
   инструкцией и скриптами, которую агент подгружает под нужную работу.
4. **Настройка через агента.** Пользователю советуют попросить агента настроить Symphony для своего репозитория по
   `elixir/README.md`. FAQ предлагает запустить `codex` в своём репозитории и дать ему URL репозитория Symphony
   [10][13]. Dan McAteer пишет, что вставить URL эталонной реализации в Codex было достаточно [117].
5. **Предусловие — harness engineering.** Репозиторий уже должен быть подготовлен под агентов [10][13]. Пост OpenAI об
   этом подходе (2026-02-11, Ryan Lopopolo) описывает [3]:
   - репозиторий, который агент может читать сам, с AGENTS.md в роли оглавления;
   - приложение поднимается в каждом git worktree;
   - skills для Chrome DevTools Protocol;
   - агент записывает видео сбоя и видео исправления;
   - циклы ревью, где один агент проверяет другого;
   - регулярные агенты для уборки кода.

   Proof of work в Symphony (пакет доказательств работы: статус CI, ревью, видео) зависит от этого набора. Сама Symphony
   его не даёт [3][10].

### Установка и запуск

- **Готовые бинарники.** Самодостаточные исполняемые файлы, собранные упаковщиком Burrito: `macos_arm64`,
  `macos_x86_64`, `linux_arm64`, `linux_x86_64`. К каждому — файл с sha256 [13][37]. Появились в v0.0.1 2026-07-18
  (PR #100) [37][55].
- **Что всё равно нужно на машине:** `codex`, `git` и ключи трекера [13].
- **Nightly.** Сборка пересобирается на каждый push в `main` после того, как smoke tests прошли на всех четырёх
  платформах [13][37].
- **Windows** в списке сборок нет [13].
- **Сборка из исходников.** Erlang 28 и Elixir 1.19.5 ставятся через менеджер инструментов `mise`. Затем `mix setup`,
  `mix build` и `./bin/symphony ./WORKFLOW.md` [13][24].
- **Команда CLI:** `symphony [--logs-root <path>] [--port <port>] [path-to-WORKFLOW.md]`. Без пути берётся
  `./WORKFLOW.md` [23][13].
- **Обязательный флаг согласия** `--i-understand-that-this-will-be-running-without-the-usual-guardrails`:
  - без него CLI печатает красный баннер «Codex will run without any guardrails.» и выходит с кодом 1 [23];
  - флаг появился ещё до открытия кода, 2026-02-27, в PR #5 [40];
  - команды запуска в README этого флага не содержат; PR #114, который добавлял его в README, закрыт без слияния
    [13][39];
  - полную команду показал ответ сообщества в Discussion #94 (вопрос о том, какой `WORKFLOW.md` читается) [86].
- **Live e2e test.** Проверяет локальный сценарий и сценарий с SSH workers. Для второго docker compose поднимает два
  одноразовых SSH worker [13].

### Агент и модель

- **Протокол.** Symphony говорит с Codex в режиме app-server: JSON-RPC через stdio [11]:
  - `codex.command` по умолчанию — `codex app-server`; команда запускается через `bash -lc` в рабочей папке задачи;
  - принимается любой процесс с совместимым протоколом app-server через stdio.
- **Модель** задаётся флагами в `codex.command`, например `--config 'model="gpt-5.5"'` [13]. Эталонный workflow ставит
  ещё `model_reasoning_effort=xhigh` и `shell_environment_policy.inherit=all` [14].
- **Аккаунт** — тот, в который вошёл Codex CLI на машине [13].
- **Экспериментальная зависимость.** Инструменты трекера передаются Codex как dynamic tools — инструменты, которые
  клиент объявляет при старте thread (ветки разговора с Codex). В документации Codex поле `dynamicTools` в
  `thread/start` экспериментальное и требует `capabilities.experimentalApi` [4][1].

### Настройка: файл WORKFLOW.md

- **Формат.** YAML front matter хранит настройки. Тело Markdown — шаблон prompt в стиле Liquid [11]:
  - рендеринг строгий: неизвестная переменная или неизвестный фильтр проваливает эту попытку запуска [11][32];
  - переменные шаблона: `issue` — все нормализованные поля задачи, включая метки и блокеры; `attempt` — номер
    попытки, на первом запуске `null` [11].
- **Live reload обязателен по спецификации:**
  - интервал опроса, параллельность, состояния, настройки Codex, hooks и prompt применяются к следующим запускам без
    перезапуска сервиса [11];
  - реализация проверяет файл раз в секунду по mtime, размеру и хешу содержимого, а также при каждом чтении настроек
    [30][11 §6.2];
  - ошибочная правка оставляет последнюю рабочую версию настроек и пишет ошибку в log [11][13];
  - если при старте файла нет или YAML неверный, сервис не запускается [13].
- **Ключи и значения по умолчанию** [11][13][24]:

| Ключ | Значение по умолчанию и примечания |
|---|---|
| `tracker.kind`, `tracker.provider` | Область и авторизацию задаёт адаптер трекера |
| `tracker.required_labels` | `[]`; у задачи должны быть все перечисленные метки |
| `tracker.active_states`, `tracker.terminal_states` | Имена состояний в написании самого трекера |
| `polling.interval_ms` | 30000; в эталонном workflow — 5000 |
| `workspace.root` | `<tmp>/symphony_workspaces` |
| hooks `after_create`, `before_run`, `after_run`, `before_remove` | `timeout_ms` 60000 |
| `agent.max_concurrent_agents` | 10 |
| `agent.max_turns` | 20 |
| `agent.max_retry_backoff_ms` | 300000 (5 минут) |
| `agent.max_concurrent_agents_by_state` | Лимиты параллельности по состояниям |
| `codex.approval_policy` | Объект `reject`: запросы одобрения отклоняются (fail-closed) |
| `codex.thread_sandbox` | `workspace-write`; sandbox хода с корнем в рабочей папке |
| `codex.turn_timeout_ms` | 1 час *тишины*, а не общего времени хода |
| `codex.read_timeout_ms` | 5 секунд |
| `codex.stall_timeout_ms` | 5 минут |
| `server.port` / `server.host` | host 127.0.0.1 |
| `worker.*` | Настройки SSH workers |
| `observability.dashboard_enabled`, `refresh_ms`, `render_interval_ms` | Есть только в коде, в README нет |

- **Секреты** [13][11]:
  - значения подставляются через `$VAR`;
  - адаптеры по умолчанию читают переменные окружения `LINEAR_API_KEY`, `GITHUB_TOKEN`, `JIRA_*`, `ASANA_PAT`,
    `GITLAB_PAT`;
  - документация предупреждает не писать токены прямо в `WORKFLOW.md`, который лежит в репозитории.
- **Неочевидные правила:**
  - читается только файл, переданный сервису при старте; копии `WORKFLOW.md` в клонах задач не читаются (ответ
    сообщества) [86];
  - один файл — одна область трекера, например один project slug в Linear; для нескольких проектов нужно несколько
    сервисов с отдельными папками и logs (ответ сообщества) [75];
  - область уровня команды Linear — открытая просьба в Discussion #69 [80].

### Отбор и запуск задач

- **Цикл опроса.** Первый опрос идёт сразу при старте. Стартовая уборка удаляет рабочие папки задач, которые уже в
  конечном состоянии [11].
- **Когда задача берётся в работу** — нужны все условия сразу [11][25]:
  - состояние активное и не конечное;
  - адаптер отметил задачу как `dispatchable` (её можно запускать);
  - у задачи есть все метки из `required_labels`;
  - задача ещё не занята;
  - свободны глобальный слот, слот её состояния и, для SSH workers, слот хоста.
- **Opt-in по метке** (PR #88, 2026-06-04). Symphony берёт только задачи с нужной меткой и не запускает агента на все
  задачи проекта. Снятие метки останавливает работающего агента [51][39].
- **Порядок:** сначала приоритет 1–4, потом самые старые, потом идентификатор [11]. Приоритет даёт только адаптер
  Linear; остальные его не задают (по коду) [33].
- **Учёт зависимостей.** Задача стартует, только когда это позволяют её блокеры:
  - Linear: задача `Todo` с незакрытым блокером ждёт [13];
  - Jira: задачи категории `new` ждут, пока закроются задачи из входящих связей «Blocks» [13];
  - GitHub, GitLab и Asana ставят `blocked_by: []`, то есть зависимости там не учитываются (по коду) [33];
  - блокеры проверяются только на старте; задача, которая уже в работе, продолжает работу [13];
  - пример из блога: обновление React, которое спланировал агент, началось только после миграции на Vite [1].
- **Маршрутизация по исполнителю — только Linear.** `assignee` — ID пользователя или `me` [13].
- **Ходы продолжения (continuation turns):**
  - после обычного хода worker перечитывает задачу; если она ещё активна, worker начинает новый ход в том же thread
    Codex [28][11];
  - текст нового хода — фиксированная инструкция продолжения с пометкой «continuation turn #N of M»; ходов не больше
    `max_turns` [28];
  - когда worker завершился, через 1 секунду идёт повторная проверка задачи [11].
- **Сбои и зависания:**
  - повтор после сбоя — с задержкой 10 с × 2^(n−1), не больше 5 минут [11][25];
  - сессию без событий дольше 5 минут Symphony убивает и повторяет [11].
- **Сверка на каждом опросе (reconciliation)** [11]:
  - задача в конечном состоянии — агент останавливается, папка удаляется;
  - задача в неактивном состоянии (например `Human Review`) или больше не подходит по маршрутизации — агент
    останавливается, папка остаётся;
  - трекер не ответил — агенты продолжают работу.
- **Заблокированные сессии (blocked sessions)** — PR #66 [13][49][25]:
  - если Codex просит ввод оператора, одобрение или MCP elicitation (запрос данных от MCP-сервера к пользователю),
    задача остаётся занятой;
  - она видна как **Blocked** в состоянии сервиса, в API и в dashboard; повторов нет;
  - список заблокированных хранится только в памяти, перезапуск сервиса его очищает;
  - снять блокировку можно только сменой состояния задачи или маршрутизации; ответить агенту через Symphony нельзя.
- **Перезапуск сервиса.** Базы данных нет. Таймеры повторов и сессии теряются; сервис восстанавливается повторным
  опросом трекера [11]. Сохранение очереди повторов записано в спецификации как TODO [11].
- **Лимиты использования.** Снимки rate limit (лимитов запросов и подписки) хранятся только для показа. Кода, который
  приостанавливает запуск задач до сброса лимита, исследования не нашли. Ход, отклонённый из-за лимита, попадает в
  общую задержку повтора (по коду) [25][26].

### Рабочие папки и hooks

- **Устройство** [11]:
  - одна папка на задачу: `<root>/<очищенный идентификатор>`; если очистка изменила имя, добавляется хеш;
  - папка переиспользуется между запусками;
  - после успеха папка не удаляется.
- **Это не git worktree.** Папку наполняют hooks, например `git clone --depth 1 … .` в `after_create` [13][14].
- **Hooks** — shell-скрипты из `WORKFLOW.md` на четыре события: `after_create`, `before_run`, `after_run`,
  `before_remove`. Правила для ошибок [11]:
  - сбой `after_create` отменяет создание папки;
  - сбой `before_run` отменяет эту попытку;
  - сбои `after_run` и `before_remove` пишутся в log и работе не мешают.
- **Таймаут hook** — 60 секунд. По таймауту процесс hook жёстко убивается, его вывод в log обрезается до 2 КБ
  [29][11 §9.4].
- **Эталонный `before_remove`** запускает `mix workspace.before_remove`. Эта задача закрывает через `gh` открытые PR
  ветки задачи [14][36].
- **Гарантии безопасности** [11]:
  - рабочая папка агента — папка его задачи;
  - путь папки остаётся внутри корня;
  - имена папок очищаются от опасных символов.

Адаптеры GitHub, Jira, Asana и GitLab появились в v0.0.2 (2026-07-24) [37]. Linear был с самого начала: в мартовской
спецификации слово «Linear» стоит в 41 строке (49 упоминаний без учёта регистра) [12].

| `linear` | `project_slug` (+ `assignee`) | Статусы workflow | Ключ Linear | Да | `linear_graphql` (сырой GraphQL) |

- **Ключи трекера не попадают к агенту** [13][11]:
  - токены трекера удаляются из окружения процесса Codex;
  - инструменты трекера выполняет сам Symphony на хосте со своим ключом;
  - доступ инструмента так же широк, как права ключа, и не ограничен опрашиваемым проектом;
  - у инструментов нет слоя идемпотентности, повторов и rate limit; этим должен заниматься prompt workflow.

### Эталонный процесс агента: `elixir/WORKFLOW.md`

Это не код Symphony, а prompt и настройки из комплекта. Состояния трекера в нём работают как этапы процесса [14].

- **Карта статусов** [14]:
  - `Backlog` — не трогается;
  - `Todo` — агент сразу переводит задачу в `In Progress`;
  - `Human Review` — агент ждёт и опрашивает задачу;
  - `Merging` (ставит человек) — агент запускает skill `land`;
  - `Rework` — полный сброс: закрыть PR, удалить workpad, начать новую ветку от `origin/main`;
  - `Done` — стоп.
- Статусы `Rework`, `Human Review` и `Merging` нужно вручную добавить в настройках команды Linear [13].
- В настройках эталона активные состояния — `Todo`, `In Progress`, `Merging`, `Rework`. Конечные — `Done`, `Closed`,
  `Cancelled`/`Canceled`, `Duplicate`. `Human Review` нет ни в одном списке, поэтому перевод задачи туда останавливает
  агента [14][25].
- **Workpad** — ровно один постоянный комментарий `## Codex Workpad` на задачу; агент правит его на месте [14]. В нём:
  - отметка окружения `<host>:<path>@<short-sha>`;
  - иерархический чек-лист плана;
  - критерии приёмки (Acceptance Criteria);
  - раздел проверки (Validation);
  - заметки с временем;
  - раздел «Confusions» — что агенту было непонятно.
- **Правила выполнения** [14]:
  - сначала воспроизвести проблему и записать, как она проявляется;
  - синхронизироваться с `origin/main` и записать результат;
  - разделы задачи Validation, Test Plan или Testing — обязательные входные данные для приёмки;
  - проверить свой план так строго, как его проверял бы principal engineer;
  - после старта сжать контекст и перейти к выполнению;
  - финальное сообщение — только сделанные действия и блокеры; никогда не задавать вопросов человеку.
- **Обход комментариев PR (PR feedback sweep).** Агент читает комментарии верхнего уровня, построчные комментарии и
  итоги ревью, от людей и от ботов. Каждый комментарий, по которому можно действовать, держит задачу, пока его не
  исправят или не ответят обоснованным возражением. Цикл идёт, пока проверки не станут зелёными [14].
- **Аварийный выход.** Перевести задачу в `Human Review` с описанием блокера можно только при нехватке инструмента или
  ключа не от GitHub. В описании — чего не хватает, почему это блокирует и что именно должен сделать человек.
  Проблемы с GitHub по умолчанию блокером не считаются [14].
- **Находки вне задачи** агент заводит как новые задачи в `Backlog` со связями `related` и, где нужно, `blockedBy`.
  `Backlog` — не активное состояние, поэтому такие задачи ждут человека [14].
- **Оформление PR.** PR получает метку `symphony` и привязывается к задаче [14].
- **Недостающие части.** Для задач, которые трогают приложение, workflow требует проверку через skill `launch-app` и
  загрузку медиа через `github-pr-media`. Ни одного из этих skills в репозитории нет; их содержание неизвестно
  (не подтверждено) [14][16].
- **Размер.** Prompt эталона — около 2900 слов [14].

### Встроенные Codex skills

Все семь лежат в `.codex/skills` [16].

- **`commit`** — коммит в стиле conventional commits с трейлером `Co-authored-by: Codex`.
- **`push`** — запускает проверки, создаёт или обновляет PR, сверяет описание PR с шаблоном командой
  `mix pr_body.check`.
- **`pull`** — делает merge `origin/main` (не rebase), с маркерами конфликтов zdiff3 и rerere (git запоминает, как
  решались конфликты, и повторяет решение).
- **`land`** [16][17]:
  - squash merge только при зелёных проверках и ответах на все ревью;
  - ждёт комментарии `## Codex Review — <persona>` от GitHub Actions; эта настройка ревью внешняя, в репозитории её
    нет;
  - каждый комментарий агента начинается с `[codex]`;
  - auto-merge сознательно не используется;
  - цикл по конфликтам, CI и ревью идёт до squash merge;
  - на каждый комментарий агент выбирает: принять, уточнить или возразить; сначала отвечает, потом меняет код;
  - каждый комментарий агент относит к классу: корректность, дизайн, стиль, уточнение или объём работы;
  - flaky tests агент может оценить сам и пропустить [17].
- **`land_watch.py`** (необязательный скрипт) параллельно следит за ревью, CI и новыми коммитами в PR. Коды выхода:
  2 — пришли комментарии ревью, 3 — CI упал, 4 — изменился последний коммит PR, 5 — конфликты слияния [16][17]. В
  SKILL.md перечислены только коды 2, 3 и 4; код 5 есть в самом скрипте [17].
- **`linear`** — рецепты GraphQL: разбор схемы, привязка PR из GitHub, загрузка видео в комментарий [16][18]. Видео
  загружается так: мутация `fileUpload`, затем `PUT` по подписанному URL, затем `commentCreate` со ссылкой на файл
  [18].
- **`debug`** — рецепты `rg` по `log/symphony.log` с ключами `issue_identifier` и `session_id`: от задачи к сессии и
  к классу сбоя [16].
- **`release`** — поднять версию, влить, поставить tag, следить за сборкой релиза [16].

### SSH workers

- Один центральный оркестратор раздаёт задачи на хосты из `worker.ssh_hosts`. Лимит на хост —
  `worker.max_concurrent_agents_per_host` [11][13][25].
- Codex запускается по SSH через stdio: `ssh -T host bash -lc '…'`. `workspace.root` — путь на удалённом хосте
  [11][27].
- Выбор хоста: при повторе — прежний хост, если там есть место; иначе — наименее загруженный [11][25].
- Если все хосты заняты, задача ждёт. Локального запуска вместо удалённого нет [11][13].
- Одна жизнь worker не переходит между машинами [28].
- Переменная `SYMPHONY_SSH_CONFIG` передаёт файл настроек ssh [13].

### Одобрения агента (approvals)

- По умолчанию `approval_policy` — объект `reject`: запросы sandbox, запросы по правилам и MCP elicitations
  автоматически отклоняются [24][13].
- При `approval_policy: never` Symphony отвечает на запросы сама [26]:
  - выполнение команд и изменение файлов — «принять на всю сессию»;
  - запросы одобрения MCP-инструментов — только если ID всех вопросов начинаются с `mcp_tool_call_approval_`;
    предпочтение — «Approve this Session», затем «Approve Once»;
  - свободные вопросы, включая выбор Allow/Deny, автоматически не отвечаются (PR #112, таймауты и одобрения). Раньше
    PR #10 подставлял в такие вопросы выдуманные ответы [59][42].
- При любой другой политике запрос одобрения заканчивает ход, и задача становится blocked [26][49].
- Эталонный workflow работает с `approval_policy: never` и включённой сетью [14][26].

### Терминальный dashboard

Включён по умолчанию [34][22]. Строки шапки:

- Agents, например `19/50`;
- Throughput — токенов в секунду за скользящие 5 секунд, с графиком за 10 минут;
- Runtime;
- Tokens: входящие, исходящие, всего;
- Rate Limits: id лимита | `primary x/y reset Ns` | `secondary …` | баланс кредитов или «unlimited»;
- ссылка на проект Linear (только для Linear);
- URL веб-dashboard;
- обратный отсчёт «Next refresh».

Таблица Running: ID, STAGE (состояние в трекере), PID, AGE / TURN, TOKENS, SESSION, EVENT. EVENT — последнее событие
простыми словами, например «turn diff updated (152 lines)», «item started: context compaction», «(auto-approved)»
[34]. Под таблицей — «Backoff queue»: номер попытки, обратный отсчёт и ошибка [34].

### Веб-dashboard

На Phoenix LiveView, по адресу `/`, если задан `--port` или `server.port`. По умолчанию слушает только loopback
[13][35]. Показывает [35]:

- карточки Running, Retrying, Blocked, Total tokens, Runtime;
- rate limits как сырой JSON;
- таблицы работающих сессий, заблокированных сессий и очереди повторов;
- ссылки на задачи в трекере (только http и https);
- ссылку «JSON details» для каждой задачи;
- кнопку «Copy ID» для ID сессии;
- значки Live и Offline.

### JSON API

- `GET /api/v1/state` — всё состояние сервиса [11][35].
- `GET /api/v1/<issue_identifier>` — путь и хост рабочей папки, попытки, последние события, последняя ошибка
  [11][13][35].
- `POST /api/v1/refresh` — внеочередной опрос. Отвечает 202. Запросы склеиваются, если опрос уже идёт или скоро будет
  [11][25].
- Неподдерживаемые методы получают ответ 405 [35].
- Ограничение: API задачи возвращает одно событие в `recent_events`, а список `codex_session_logs` в версии на Elixir
  всегда пуст [35].

### Logs и учёт токенов

- `log/symphony.log` в формате `key=value` с обязательными полями `issue_id`, `issue_identifier` и `session_id`.
  Ротация — 10 МБ × 5 файлов [20].
- Учёт токенов [19][11][25]:
  - берутся абсолютные накопленные итоги (`thread/tokenUsage/updated`, `total_token_usage`), дельты
    (`last_token_usage`) не используются;
  - прирост считается от последнего полученного итога, чтобы не посчитать токены дважды;
  - время работы добавляется при завершении сессии, для живых сессий — в момент снимка.

### Что оператор может и чего не может

- **Может** [11][13][35]:
  - править `WORKFLOW.md`;
  - двигать задачи и метки в трекере;
  - вызвать `/api/v1/refresh`;
  - перезапустить сервис.
- **Не может.** Нет кнопки stop, pause или kill. Нет чата и подсказок агенту по ходу работы. Нет просмотра transcript и
  diff [11][13][35].
- **Что предлагали и не влили** (закрытые PR) [39]:
  - панель деталей агента с чек-листом (PR #68);
  - учёт токенов по задаче (PR #60);
  - claim leases (PR #82);
  - блокировка: один экземпляр на проект (PR #8) [41].
- Ссылки на thread Codex и продолжение работы по комментариям в Linear (PR #84) влили и примерно через 5 минут
  откатили (PR #85), оба — 2026-06-01 [50].

## Принципы и подходы

### Как появился продукт

- **Команда до Symphony.** Примерно с августа 2025 команда OpenAI делала внутренний продукт без кода, написанного
  вручную [3]:
  - к февралю 2026 — около 1 млн строк кода и около 1500 влитых PR;
  - команда выросла с 3 до 7 инженеров, в среднем около 3.5 PR на инженера в день;
  - правило команды: люди задают направление, агенты исполняют.
- **Узкое место.** Большинство людей удерживали только 3–5 интерактивных сессий Codex; дальше мешало переключение
  контекста. Внимание человека стало ограничением [1].
- **Поток PR.** В подкасте Latent Space Ryan Lopopolo сказал, что после GPT-5.2 поток вырос примерно с 3.5 до 5–10 PR
  на инженера в день, и переключаться между сессиями в tmux стало невозможно [102]. Это интервью, расшифровка местами
  искажена, год эпизода (2026) выведен из контекста [102].
- **Версия 1** — одна сессия Codex в tmux. Она опрашивала Linear и запускала sub-agents. Работала, но ненадёжно [1].
- **Версия 2** жила внутри основного репозитория продукта команды и пользовалась его настройкой агентов [1].
- **Выделение в спецификацию.** Идею вынесли в отдельный SPEC.md. Убрали зависимости от внутренних репозиториев и от
  Linear MCP server. App Server и dynamic tools заменили Linear MCP, и токен трекера больше не попадает в контейнеры
  [1].
- **Сначала внутри.** После внутреннего демо команды OpenAI взяли Symphony сами. Пост говорит, что внутренний
  product-market fit — условие, чтобы выпустить что-то наружу в OpenAI [1].
- **Результат по данным OpenAI:** в некоторых командах число влитых PR выросло на 500% за первые три недели [1].
- **Люди:**

### Заявленная философия

1. **Управлять работой, а не сессиями.** Команда решила, что оптимизировала сессии и влитые PR, а это лишь средства.
   Важны результаты: задачи, тикеты, этапы. Поэтому агенты сами берут работу из трекера, и их не надо вести вручную
   [1]. На вопрос, как он направляет Codex, Kotliarskyi отвечает: не на уровне сессии. Ручное ведение не
   масштабируется, как и микроменеджмент. Если Codex раз за разом ошибается, в кодовой базе не хватает контекста [96].
2. **Трекер — control plane и state machine.** Главное правило из блога: у каждой открытой задачи должен работать
   агент в своей рабочей папке [1]. Symphony следит за доской, перезапускает упавших и зависших агентов и берёт новую
   работу. Состояния Linear служат state machine (машиной состояний процесса) [1]. Kotliarskyi сравнивает Symphony с
   Kubernetes для агентов, где доска задач — управляющий слой [96].
3. **Работа отделена от сессий и PR.** Одна задача может дать несколько PR в разных репозиториях или ни одного,
   например исследование [1]. Поэтому задача может быть крупной. Схема для больших работ [1][96]:
   - первая задача просит агента составить план;
   - после проверки человеком агент заводит дерево зависимых задач;
   - агенты берут только незаблокированные задачи, и работа идёт в порядке зависимостей.

   Пример: переход с самописного фреймворка на tRPC прошёл как более 20 задач в фазах A, B и C; каждая фаза
   открывала следующую [96].
4. **Цели вместо жёстких переходов.** Когда агент был фиксированным узлом state machine, это не работало. Ранние
   версии просили Codex только реализовать задачу. Затем команда стала давать цель и инструменты: gh CLI, skills для
   чтения logs CI. Тогда агенты сами отвечают на ревью, закрывают старые PR и пишут отчёты [1]. Brock формулирует новую
   цель агента так: убедить человека влить его код. Он называет это следующей фазой разработки ПО [100].
5. **Проверять доказательства, а не процесс:**
   - агент возвращает proof of work: статус CI, отзывы ревью PR, анализ сложности и видео-обзоры; когда человек
     принимает работу, агент сам вливает PR [10];
   - успех часто означает переход в состояние передачи человеку, например `Human Review`, а не в `Done` [11];
   - в подкасте ревью описано как быстрое решение «да или нет»: можно вливать или назад в доработку [102];
   - Kotliarskyi описывает это как переход от ведения агентов к проверке их пакетов доказательств [96].
6. **Неудача улучшает harness, доработка начинается с нуля:**
   - неудачный результат считается сведением о пробеле; ответ — новые guardrails и skills, а не ручная правка [1];
   - `Rework` полностью сбрасывает подход: закрыть PR, удалить workpad, новая ветка от `main` [14]; Kotliarskyi
     называет это состояние своим аварийным выходом [96].
7. **Harness engineering — предусловие:**
   - README говорит, что Symphony лучше всего работает в кодовых базах, где уже есть harness engineering [10];
     Kotliarskyi называет harness engineering шагом один, а Symphony — шагом два [96];
   - его стресс-тест: простое TODO-приложение без подготовки под агентов; параллельные агенты ломали работу друг друга,
     застревали на конфликтах слияния и не могли поднять рабочее окружение; сама Symphony при этом без проблем
     обрабатывала миллионы токенов в секунду [96].
8. **Политика workflow живёт в репозитории:**
   - `WORKFLOW.md` хранит настройки YAML и строгий шаблон prompt; он версионируется вместе с кодом и должен
     перезагружаться без перезапуска [11];
   - формулировка блога: негласный процесс команды (двигать задачу, открывать PR, прикладывать видео) теперь записан,
     и Symphony заставляет агентов ему следовать [1];
   - разделить жёсткие настройки и свободные инструкции модели удалось не с первого раза [96].
9. **Распространять программу как спецификацию:**
   - технически Symphony — это просто `SPEC.md` [1];
   - Brock называет это software-as-a-spec: текст, который каждый превращает в код на любом языке своим агентом; он
     ожидает, что open source будут так распространять и дальше [100];
   - Latent Space называет такой проект ghost library — библиотекой без кода, только с описанием, по которому агент
     пишет код [102];
   - Kotliarskyi видит в спецификации практичную середину: подробнее идеи и гибче кода, поэтому её можно пересобрать
     в своём стеке [96]; это продолжает его эссе 2023 года о том, чтобы пересобирать приложения с нуля при каждой
     смене требований [98];
   - раздел настроек нарочно избыточен, чтобы агент быстро написал слой конфигурации [11 §6.4];
   - спецификацию проверяют на агентах: PR #102 сообщает, что реализации без контекста на TypeScript, Python и Go
     прошли [56].
10. **Минимализм и малые границы:**
    - инструкция для агентов (`AGENTS.md`) делает простоту правилом проекта: один владелец и один инвариант на
      решение, возражать против гибкости «на будущее»; для нетривиальных изменений ожидается раннее состязательное
      ревью, где ревьюер ищет, как сломать решение [15][54];
    - non-goals: богатый веб-интерфейс, многопользовательский control plane, общий движок workflow, встроенная
      бизнес-логика задач и PR [11];
    - состояние планировщика нарочно только в памяти, без базы; после перезапуска оно восстанавливается из трекера и
      рабочих папок на диске [11];
    - граница с трекером нарочно мала: два вызова чтения плюс необязательные родные инструменты провайдера;
      спецификация прямо запрещает добавлять общие вызовы CRUD (создать, прочитать, изменить, удалить) только ради
      одинакового вида провайдеров [11].
11. **Работа без присмотра, с явно заявленным уровнем доверия:**
    - запрос одобрения или ввода никогда не должен оставлять запуск висеть; каждая реализация обязана описать свою
      позицию по одобрениям и sandbox; укрепление окружения агента спецификация считает частью базовой модели
      безопасности [11];
    - эталонный workflow запускает Codex с `approval_policy: never`, sandbox `workspace-write` и включённой сетью [14];
    - CLI не стартует без флага согласия; флаг добавлен до запуска, 2026-02-27 [23][40];
    - ключи трекера остаются на хосте: инструменты трекера выполняет оркестратор, а переменные с токенами удаляются из
      окружения Codex [11][13]; это одна из названных причин выбрать dynamic tools App Server, а не MCP [1].
12. **Дешёвые эксперименты и больше людей, которые начинают работу:**
    - когда агентов не надо вести, каждое изменение кажется дешевле; экспериментальные задачи становятся обычным делом, неудачные
      исследования почти ничего не стоят [1];
    - пример Kotliarskyi: завести задачу «как выглядела бы серверная часть, переписанная на Rust» [96];
    - продакт-менеджеры и дизайнеры заводят запросы и получают пакет для ревью с видео [1];
    - Brock и блог подчёркивают, что работу можно начать с телефона [1][100].
13. **Неочевидные решения, по словам автора** [96]:
    - рабочие папки отвязаны от Git: shell hooks заменили настройку «worktree или полный checkout»;
    - у каждого thread ограниченное число ходов до перезапуска, чтобы модель не ходила по кругу; по умолчанию
      `max_turns: 20` [11];
    - запускаются только незаблокированные задачи.
14. **Почему Elixir:**
    - когда код почти бесплатен, язык можно выбирать по сильным сторонам; сильная сторона Elixir — надзор за
      параллельными процессами [1];
    - README эталона называет supervision в BEAM (виртуальной машине Erlang) и замену кода на лету без остановки
      работающих агентов [13]; Kotliarskyi добавляет, что Codex хорошо работает внутри живого REPL [96];
    - по словам Lopopolo, Elixir выбрала сама модель [102].
15. **Признанные ограничения:**
    - нельзя подтолкнуть агента посреди работы [1];
    - неоднозначная работа, где нужно суждение человека, остаётся в интерактивных сессиях [1];
    - оркестрация не исправляет слабую инженерную базу [96].

### Чем подход отличается

- **Своего интерфейса продукта нет:** ни обязательного UI, ни базы, ни многопользовательского control plane.
  Интерфейс и источник правды — существующий трекер. Dashboard — необязательное расширение для наблюдения [11][13].
- **Сначала спецификация, потом реализация.** Первый вариант в README — собрать свою версию [10][1].
- **Один агент на задачу как гарантия.** Нет планирующей сессии, которая раздаёт работу другим. Планирование — тоже
  задача, и её результат — новые задачи [1][96].
- **Работа без присмотра от начала до конца.** Люди входят в состояниях передачи, а не посреди запуска. Запросы ввода
  проваливаются или показываются как blocked; бесконечного ожидания нет [11][49].
- **Только Codex, сознательно.** Symphony говорит на протоколе Codex App Server и отсылает к документации Codex за
  деталями протокола [11]. Форки сообщества добавляют Claude Code [1][147].
- **Восстановление без хранимого состояния.** После перезапуска сервис заново читает трекер и находит рабочие папки на
  диске [11].

  планирования. Workers сообщают о себе сообщениями [11 §7][25].
- **Почему Elixir, по README эталона:** хороший надзор за долгими процессами и замена кода на лету без остановки
  работающих агентов [13].

### Цикл агента

1. **Подготовка.** Создать или переиспользовать рабочую папку, затем выполнить hook `before_run` [28][11 §16.5].
2. **Запуск.** `bash -lc "unset <переменные с секретами трекера> && exec <codex.command>"` с рабочей папкой как
   текущей. Команда по умолчанию — `codex app-server` [26]. Дочерний процесс — Erlang Port, то есть связь с процессом
   ОС через stdio. Имена переменных с секретами ещё и выставляются в `false` в окружении Port [26].
3. **Рукопожатие** — JSON-RPC, по одному JSON на строку [26]:
   - `initialize` с `clientInfo` `symphony-orchestrator` и возможностью `experimentalApi: true`, затем `initialized`;
   - `thread/start` с `approvalPolicy`, `sandbox`, `cwd` и `dynamicTools` (описания инструментов трекера);
   - `turn/start` с отрендеренным prompt, `cwd`, заголовком `"<identifier>: <title>"`, `approvalPolicy` и
     `sandboxPolicy`;
   - ID сессии — `<thread_id>-<turn_id>` [11 §4.2].
4. **Поток событий до конца хода** [26]:
   - `turn/completed` — успех; `turn/failed` и `turn/cancelled` — сбой;
   - запросы одобрения, `item/tool/call` и `requestUserInput` обрабатываются на месте; MCP elicitation означает, что
     нужен ввод человека;
   - строки не в формате JSON пишутся в log с уровнем warning, если похожи на ошибки;
   - строки приходят кусками по 1 МБ и собираются обратно.
5. **После каждого завершённого хода задача читается заново.** Если она ещё активна, подходит по маршрутизации и
   ходов меньше `max_turns` (по умолчанию 20), worker начинает новый ход в том же thread [28][11 §7.1]. Ход
   продолжения не отправляет весь prompt заново. Он отправляет фиксированный текст: продолжить с состояния рабочей
   папки и workpad и не заканчивать ход, пока задача активна, если нет настоящего блокера (`agent_runner.ex`, функция
   `build_turn_prompt`, строки 144–153) [28].
6. **Завершение.** Остановить сессию (закрыть Port) и выполнить `after_run`. `after_run` стоит в блоке `try … after`,
   поэтому выполняется и при сбое [28].

Ещё о цикле:

- **Новый thread на каждый запуск worker.** В `lib/` нет вызовов `thread/resume`, `turn/steer` и `turn/interrupt`
  (проверено поиском) [26][28]. PR #84 добавлял ссылки на thread Codex и продолжение по комментариям в Linear; примерно
  через 5 минут после слияния его откатил PR #85, оба — 2026-06-01 [50].
- **Шаблон prompt.** Liquid-шаблон рендерит библиотека `Solid` со строгими переменными и строгими фильтрами. Шаблон
  получает `issue` (все нормализованные поля) и `attempt` [32][11 §5.4]. `attempt` равен `null` при первом запуске и
  числу потом. Обычное продолжение и повтор после ошибки он не различает [32][11 §12.3].
- **Привязка инструментов фиксируется на сессию.** При старте сессии запоминаются адаптер, настройки трекера,
  описания инструментов и имена секретных переменных. Перезагрузка workflow не может заставить идущую сессию
  объявить один провайдер, а выполнить другой [33][11 §10.5].

### Параллельность и координация

- **Тик — один проход цикла опроса.** Первый тик — сразу при старте, дальше раз в `polling.interval_ms`: по умолчанию 30 секунд, в эталонном
  workflow 5 секунд [11 §8.1][14].
- **Порядок тика** [11 §8.1][25]:
  1. Сверить работающие задачи.
  2. Сверить заблокированные задачи.
  3. Заново проверить настройки.
  4. Получить кандидатов в активных состояниях.
  5. Отсортировать.
  6. Запускать, пока есть слоты.
  7. Уведомить dashboard.
- **Устаревшие таймеры отбрасываются.** Сообщения таймеров несут уникальный токен (`make_ref`), поэтому старые тики и
  старые таймеры повторов игнорируются (PR #43) [25][45].
- **Ручной опрос.** `POST /api/v1/refresh` ставит немедленный тик. Запросы склеиваются, если опрос уже идёт или скоро
  будет [25][11 §13.7.2].
- **Условия запуска** проверяет функция `should_dispatch_issue?` (`orchestrator.ex`, строка 816) [11 §8.2][25]:
  - поля `id`, `identifier`, `title` и `state` не пустые;
  - состояние активное и не конечное; состояния сравниваются после обрезки пробелов и перевода в нижний регистр;
  - адаптер поставил `dispatchable=true`;
  - у задачи есть все `required_labels`;
  - задача ещё не занята, не работает и не заблокирована;
  - свободны глобальный слот, слот состояния и слот SSH-хоста.
- **Порядок:** приоритет 1–4, затем самый старый `created_at`, затем идентификатор [11 §8.2][25].
- **Лимиты параллельности** [11 §5.3.5][11 App. A][25]:
  - глобальный `max_concurrent_agents`, по умолчанию 10;
  - `max_concurrent_agents_by_state` — словарь «имя состояния → лимит»;
  - `worker.max_concurrent_agents_per_host` для SSH workers.
- **Проверка прямо перед запуском.** Перед стартом worker оркестратор ещё раз читает задачу по ID. Если задачи нет,
  она устарела или стала заблокированной, запуск пропускается [25]:
  - это добавил PR #15: блокеры появлялись между опросом и стартом worker [43];
  - PR #110 сделал так, что повтор при неудачном втором чтении освобождает или переносит бронь задачи, а не бросает
    её занятой [58].
- **Сверка работающих задач.** Каждая работающая задача читается заново по ID [11 §8.5][11 §16.3][25]:
  - конечное состояние — остановить worker и удалить папку;
  - больше не подходит по маршрутизации (например, переназначена) — остановить без уборки;
  - всё ещё активна — обновить снимок задачи в памяти;
  - любое другое состояние — остановить без уборки;
  - задачи нет в трекере — остановить без уборки;
  - если само чтение не удалось, workers продолжают работу.
- **Стартовая уборка.** При старте удаляются папки задач, которые уже в конечных состояниях [11 §8.6][25].
- **Ядро не планирует и не делит работу.** Делить работу — дело человека в трекере. Оркестратор не должен ветвиться
  по правилам блокеров, досок, переходов и комментариев конкретного провайдера [11 §11.2].
- **Порядок зависимостей — только через флаг `dispatchable` адаптера.** Linear и Jira учитывают блокеры; GitHub,
  GitLab и Asana всегда оставляют `blocked_by` пустым [13][33]. Блокеры влияют только на старт [13].
- **Планирует агент внутри prompt** [14]: иерархический план, критерии приёмки и чек-лист проверки в workpad;
  проверка своего плана; воспроизведение проблемы до исправления; находки вне задачи — новые задачи в `Backlog`.
- **Агенты не общаются друг с другом.** Координация идёт через состояния трекера и git. Skill `pull` делает merge
  `origin/main` с `rerere` и стилем конфликтов `zdiff3` [16]. Skill `land` решает конфликты перед слиянием [17].
- **State machine процесса живёт в prompt, а не в оркестраторе.** Symphony различает только «активное», «конечное» и
  «другое» состояние [11 §7.1][14].

### Изоляция

- **Рабочая папка — одна на задачу**: `<workspace.root>/<ключ>` [11 §9][29]. Ключ заменяет символы вне
  `[A-Za-z0-9._-]` на `_`. Если замена что-то изменила, добавляются 16 hex-символов SHA-256 (64 бита) от исходного
  идентификатора [29][11 §4.2].
- **Проверка путей.** Путь папки приводится к каноническому виду с раскрытием symlinks (`path_safety.ex`). Запуск
  отменяется, если путь совпадает с корнем, выходит из корня через symlink или лежит вне корня [26][29].
- **Уборка завершённых задач (PR #109)** сначала останавливает workers, а потом удаляет папку. Удаляется путь,
  записанный для запуска, а не путь, заново вычисленный из, возможно, перезагруженных настроек [57].
- **Не git worktrees.** Настройка системы контроля версий отдана реализации и обычно делается hooks [11 §9.2]. Эталон
  делает `git clone --depth 1 … .` в `after_create`, поэтому у каждой задачи свой полный неглубокий клон [14].
- **Жизнь папки:**
  - папки переиспользуются между запусками и остаются после успеха [11 §9.1];
  - неудачный `after_create` удаляет недоделанную новую папку, и следующая попытка начинает с нуля (PR #111) [57];
  - эталонный `before_remove` закрывает открытый PR ветки с комментарием, что задача трекера перешла в конечное
    состояние без слияния [36][14].
- **Sandbox Codex по умолчанию** (если workflow их не задаёт) [24][13]:
  - `approval_policy` — объект `reject`: `sandbox_approval`, `rules` и `mcp_elicitations` автоматически отклоняются;
  - `thread_sandbox: workspace-write`;
  - `turn_sandbox_policy`: `workspaceWrite` с `writableRoots=[workspace]`, `networkAccess: false` и
    `readOnlyAccess: fullAccess`. Агент может читать всю файловую систему, а писать — только в свою папку.
- **Эталонный workflow это ослабляет** [14]: `approval_policy: never`, сеть включена,
  `shell_environment_policy.inherit=all`, `model="gpt-5.5"` с `model_reasoning_effort=xhigh`.
- **SSH workers** [11 App. A][25][27]. Оркестратор остаётся центральным и запускает app-server через
  `ssh -T host bash -lc '…'`. Хост при повторе — прежний, если там есть место, иначе наименее загруженный. Когда все
  хосты заняты, запуск ждёт и не переходит на локальную машину. Одна жизнь worker не переходит между машинами [28].
- **Платформы.** Бинарники Burrito — только macOS и Linux на arm64 и x86_64, Windows нет [13]. Hooks и запуск
  предполагают `sh` и `bash -lc` [11 §9.4][29].

### Состояние и память

- **Состояние в памяти** [25]: `running`, `claimed`, `blocked`, `retry_attempts`, `completed` (только для учёта),
  `codex_totals` и `codex_rate_limits`.
- **Базы нет.** Восстановление после перезапуска идёт от трекера и файловой системы. Таймеры повторов и работающие
  сессии не восстанавливаются [11 §7.4][11 §14.3]. Сохранение очереди повторов — TODO [11 §18.2].
- **Нет защиты от второго экземпляра на том же проекте:**
  - PR #8 предлагал блокировку на проект. В нём сказано, что два экземпляра Symphony на один проект Linear сейчас
    запускаются без ошибки. PR закрыт без слияния 2026-02-27 [41];
  - PR #83 предлагал claim leases для Jira, хранимые в комментариях. Открыт 2026-05-29, закрыт без слияния 2026-10-21
    [46];
  - частичная защита — маршрутизация по `assignee` в Linear: запускаемыми считаются только задачи нужного
    пользователя или `me` [13][33].
- **Память агента между запусками** [14]:
  - сама рабочая папка — ветка и коммиты;
  - один комментарий `## Codex Workpad` с отметкой окружения `<host>:<abs-path>@<short-sha>`, планом, критериями
    приёмки, проверкой, заметками и необязательным разделом «Confusions»;
  - PR и комментарии к нему;
  - число `attempt` в prompt.
- **Контекст внутри одного запуска.** Prompt велит после старта сжать контекст и перейти к выполнению [14]. Дальше
  сжатием контекста управляет Codex.

### Проверка качества

- **Ядро ничего не проверяет.** Успех — задача дошла до состояния передачи, например `Human Review`. Бизнес-логика
  живёт в prompt workflow и инструментах агента [11 §2.2][11 §11.5].
- **Планка перед `Human Review` задана в prompt** [14]:
  - чек-лист workpad закрыт;
  - разделы задачи `Validation` и `Test Plan` обязательны без исключений;
  - тесты зелёные на последнем коммите;
  - проверка идёт перед каждым push;
  - обход комментариев PR закончен: каждый комментарий человека или бота исправлен или получил обоснованное
    возражение;
  - проверки PR зелёные, у PR есть метка `symphony`;
  - для изменений приложения нужны skills `launch-app` и `github-pr-media`; их в репозитории нет, содержание не
    подтверждено.
- **Proof of work.** Демо показывает статус CI, отзывы ревью PR, анализ сложности и видео-обзоры [10][6]. Skill
  `linear` загружает видео так: `fileUpload` → `PUT` по подписанному URL → `commentCreate` со ссылкой [18].
- **Skill `land` в состоянии `Merging`** [17]:
  - цикл по конфликтам, CI и ревью до squash merge;
  - `land_watch.py` параллельно следит за комментариями ревью, проверками CI и последним коммитом PR и выходит с
    кодами 2–5;
  - протокол на каждый комментарий: принять, уточнить или возразить; сначала ответ, потом правка; класс комментария;
    префикс `[codex]`;
  - flaky tests агент может признать таковыми и пропустить;
  - автоматическое ревью — комментарии GitHub Actions с заголовком `## Codex Review — <persona>`; сам этот workflow
    ревью в репозиторий не входит.
- **Проверки в репозитории самой Symphony** [15]:
  - `make all`: проверка форматирования, lint, покрытие с порогом 100% и dialyzer (статический анализ типов для
    Erlang);
  - порог 100% не распространяется на основные модули: Orchestrator, AgentRunner, AppServer, Workspace, клиенты
    трекеров, веб-слой;
  - `mix specs.check` требует `@spec` у каждой публичной функции;
  - `mix pr_body.check` и lint в CI требуют шаблон PR с разделами Context, TL;DR, Summary, Alternatives и Test Plan.
- **Похоже, Symphony разрабатывает сама себя (вывод).** Ветки вида `frantic/mt-713-…` и закрывающий комментарий
  PR #8, который совпадает с текстом hook `before_remove`, указывают на запуски агентов [41][36]. Документ smoke test
  пишет, что Symphony взяла задачу Jira SD-4 [21].

### Восстановление после сбоев

| Событие | Поведение |
|---|---|
| Worker завершился нормально | Продолжение через 1 с с `attempt=1`; новый запуск, если задача ещё активна [11 §8.4][25] |
| Worker завершился с ошибкой (любая ошибка, таймаут, выход Port) | Задержка `min(10 с·2^(attempt−1), max_retry_backoff_ms)`; потолок 5 минут; показатель степени не больше 10 [11 §8.4][25] |
| Нет событий `stall_timeout_ms` (5 минут) | Убить worker и повторить с задержкой, если он не ждал ввода [11 §8.5][25] |
| `turn_timeout_ms` (1 час) | Интервал тишины: сбрасывается каждой строкой от app-server; это не общий лимит времени (PR #112) [11 §10.6][59] |
| `read_timeout_ms` (5 с) | Таймаут запроса и ответа во время рукопожатия [26] |
| Таймаут hook (60 с) | Задача hook жёстко убивается; вывод в log обрезан до 2 КБ; `after_create` и `before_run` проваливают попытку; ошибки `after_run` и `before_remove` игнорируются [29][11 §9.4] |
| Трекер не ответил | Пропустить запуск на этом тике; при ошибке сверки workers продолжают работу [11 §11.4][25] |
| Ошибочная перезагрузка `WORKFLOW.md` | Оставить последнюю рабочую версию и записать ошибку; ошибка при старте — сервис не запускается [13][30] |
| Таймер повтора сработал, а слотов нет | Снова в очередь с ошибкой «no available orchestrator slots» [11 §8.4][25] |

- **Нет потолка на число повторов и на расходы.** Максимального числа попыток и настройки бюджета нет ни в `lib/`, ни
  в SPEC.md (проверено поиском). Каждый нормальный выход ставит продолжение через 1 секунду. Поэтому задача, которая
  остаётся активной, получает всё новых workers по 20 ходов без конца (вывод) [25][11 §7.1].
- **Типы ошибок не различаются.** Сбой из-за лимита, падение процесса и красный тест идут одной дорогой задержки
  [11 §12.3][25].

### Лимиты и стоимость

- **Учёт токенов** [19][11 §13.5][25]: абсолютные итоги вместо дельт, прирост от последнего итога, время работы
  добавляется при завершении сессии.
- **Лимиты хранятся и показываются, но не управляют запуском.** Хранится только последний полученный набор данных о
  лимитах, для показа [25][34]. Терминальный dashboard показывает, например,
  «primary 12,345/20,000 reset 30s | secondary 45/60 reset 12s | credits 9876.50» [34]:
  - планировщик это значение не читает: поиск находит только сохранение и показ [25];
  - значит, нет ожидания сброса лимита и нет планирования запусков под лимиты; ход, упавший на лимите, повторяется с
    обычной задержкой, не реже раза в 5 минут [25];
  - особой обработки лимитов использования в `elixir/lib` нет (поиск 2026-11-13); как сервис ведёт себя при реальном
    упоре в лимит, никто не проверял (не подтверждено) [25];
  - с Codex 0.160 поле лимитов в API и dashboard остаётся пустым: новые ключи в camelCase не разбираются (сообщение
    сообщества) [93].
- **Документация Codex App Server** [4]:
  - событие `account/rateLimits/updated` несёт `usedPercent`, `windowDurationMins` и `resetsAt`;
  - документация называет app-server интерфейсом для богатых клиентов Codex и советует для автоматизации и CI брать
    Codex SDK; Symphony при этом автоматизирует работу именно через app-server;
  - документация говорит, что авторизация app-server никогда не разрешалась для коммерческих и hosted-сервисов;
  - `dynamicTools` и `item/tool/call` помечены как экспериментальные.
- **Расходы у пользователей.** Dan McAteer: около 388 млн токенов за 14 часов, примерно $1000 по ценам API GPT-5.4;
  недельный лимит Codex исчерпан [116]. Alessio Fanelli заявляет около 1 млрд токенов в день на облачной машине с
  32 ГБ памяти и 4 ядрами, без разбивки [115].

### Права и безопасность

- **Флаг согласия при каждом старте.** Без `--i-understand-that-this-will-be-running-without-the-usual-guardrails`
  старт проваливается с баннером о работе Codex без ограничений [23].
- **Автоматические одобрения — только при `approval_policy == "never"`** (`app_server.ex`, строка 55) [26]:
  - команды и изменения файлов — «принять на всю сессию»;
  - одобрения MCP-инструментов — только если ID всех вопросов начинаются с `mcp_tool_call_approval_`;
  - свободные вопросы, включая Allow/Deny, — никогда (PR #112); до него PR #10 подставлял выдуманные ответы [59][42];
  - при другой политике запрос одобрения заканчивает ход, и задача становится blocked.
- **Ключи трекера остаются у оркестратора** [11 §10.5][11 §15.3][13][26][33]:
  - запись в трекер идёт через инструменты на хосте: `linear_graphql`, `github_api`, `jira_rest`, `asana_api`,
    `gitlab_api`;
  - каждый адаптер объявляет имена секретных переменных, например `GITHUB_TOKEN`, `GH_TOKEN` и варианты для
    Enterprise; они удаляются из окружения процесса Codex.
- **Утечка через псевдонимы токенов** GitHub и GitLab к агентам закрыта в PR #119 (2026-08-12). Исправление
  благодарит участника сообщества, который нашёл проблему [60].
- **Охват инструментов.** Доступ инструмента равен доступу токена. `project_slug` ограничивает чтение планировщика, а
  не вызовы инструментов. У инструментов нет ключа идемпотентности, повторов, ограничения области и правил rate limit
  [13].
- **Hooks** — полностью доверенная настройка [11 §15.4].
- **Dashboard** слушает `127.0.0.1` по умолчанию и не имеет аутентификации [24]. Ошибки stored XSS и внедрения
  ANSI-последовательностей в dashboards исправлены в PR #22 и #23 [44].
- **На SSH workers** путь рабочей папки не сверяется с корнем перед `rm -rf` (Discussion #107) [87].
- **Укрепление — забота того, кто разворачивает.** Спецификация предлагает: строже одобрения, контейнер или VM,
  ограничения сети, фильтр задач, которые можно запускать, и более узкие инструменты [11 §15.5].

### Люди в цикле

- **Интерфейс человека — состояния трекера** [14][11 §14.4]:
  - человек переводит задачу из `Backlog` в `Todo` и этим разрешает работу;
  - агенты останавливаются на `Human Review`;
  - человек ставит `Merging` (одобрение) или `Rework` (полный сброс: закрыть PR, удалить workpad, новая ветка).
- **Заблокированные сессии.** Когда запуску нужен ввод, одобрение или MCP elicitation, задача остаётся занятой и
  видна как blocked. Повтора нет: блокер, которому нужен человек, не считается временным сбоем (PR #66) [25][49].
  Блокировка снимается только сменой состояния или маршрутизации задачи или перезапуском оркестратора [13][25].
  Канала, чтобы ответить агенту, нет; попытку его добавить (PR #84) откатили [50].
- **Аварийный выход агента** — `Human Review` с описанием блокера, если не хватает инструмента или ключа. Проблемы
  GitHub по умолчанию блокером не считаются [14].
- **Прочее управление.** Правки `WORKFLOW.md` действуют сразу: файл проверяется раз в секунду [30][11 §6.2]. Кнопки
  stop, pause или kill нет ни в API, ни в dashboard [35].

### Наблюдаемость

- **Logs** в формате `key=value` в `log/symphony.log`, ротация 10 МБ × 5 файлов, обязательные поля `issue_id`,
  `issue_identifier` и `session_id` [20]. Skill `debug` учит агента проходить путь «задача → сессия → класс сбоя»
  через `rg` [16].
- **Терминальный dashboard:** агенты x/N, токены в секунду (окно 5 секунд, график за 10 минут), время работы, токены,
  лимиты, таблица Running и очередь повторов [34].
- **LiveView dashboard:** счётчики Running, Retrying, Blocked, Total tokens, Runtime; панель лимитов; таблицы
  работающих, заблокированных и ожидающих повтора задач [35].
- **JSON API:** `GET /api/v1/state`, `GET /api/v1/<identifier>`, `POST /api/v1/refresh` [35][11 §13.7].
- **Ограничения:**
  - в памяти хранится только *последнее* событие по задаче [35];
  - API задачи возвращает одно событие в `recent_events`, а `codex_session_logs` в версии на Elixir всегда пуст [35];
  - уведомления Codex пишутся в log только именем метода и только на уровне debug [26].

  много токенов. Неделя работы с ней ближе всего подвела его к недельному лимиту Codex [117].
- В блоге он пишет: около 388 млн токенов за 14 часов, примерно $1000 по ценам API GPT-5.4; недельная квота Codex
  израсходована [116].
- Разработчик на HN тратит $140 в месяц на подписки и ещё около $100 в неделю на кредиты API [131].
- Форк George сообщает: агенты исходной версии тратили токены на чтение схемы GraphQL Linear перед каждым вызовом
  [143].
- DevDigest (вторичный источник, местами расходится со SPEC.md) сообщает об одной задаче за $11 до введения потолков
  расходов [109].
- Сломался и показ лимитов: с Codex CLI 0.160 поле rate limit в API и dashboard Symphony остаётся пустым [93].
- В SPEC.md лимиты — телеметрия для показа. Правила, которое держит запуск до сброса окна лимита, исследование там не
  нашло [11].

**B. Трудная настройка:**

- Сборка версии на Elixir внутри Codex Cloud не удалась: hex.pm (реестр пакетов Elixir) и инструменты не скачивались
  через proxy (Discussion #70) [81].
- Пользователи писали свои обёртки: настройка Linear, переиспользуемые workflow-файлы, скрипты перезапуска
  [129][73].
- George выпустил skill настройки, который создаёт в Linear нужные Symphony состояния [143]. Fanelli написал свой
  skill первичной настройки [115].
- DevDigest (вторичный) описывает медленную и хрупкую установку Erlang на Apple Silicon. Рабочие папки по умолчанию
  лежали в /tmp, и перезагрузка машины их стёрла [109].
- Готовые бинарники появились только в июле [37].
- Путают понятия:
  - читается только `WORKFLOW.md`, переданный при старте, а не копия в каждом клоне (ответ сообщества) [86];
  - как задавать область — по проекту Linear или по команде [80][75];
  - что будет с размытой задачей или когда агенту нужно решение человека (Discussions #59 и #63) [76][77].

**C. Работа останавливается из-за sandbox и одобрений:**

- С документированным безопасным профилем агенты могли править файлы, но не могли писать в `.git` и проверять
  приложение на localhost. Задачи висели на ревью, повторы заново находили то же частичное состояние (Discussion #33)
  [66].
- Форк George сообщает: sandbox исходной версии по умолчанию молча ломает весь процесс git и PR [143].
- В v0.0.3 Codex 0.164 и 0.165-alpha отклоняют политику одобрений по умолчанию (fail-closed) уже при старте thread.
  Обходной путь — одобрения по запросу — ослабляет защиту (Discussion #134) [95].
- Сбой настройки папки плюс запрос MCP elicitation оставили задачу в `In Progress`. Symphony повторяла её примерно раз
  в 5 минут и не показала блокер (Discussion #64) [78]. Сообщение датировано 2026-05-04, раньше PR #66 о
  заблокированных сессиях [78][49].

**D. Тихие сбои — главный класс багов:**

- Codex сообщает о проваленном ходе как о завершённом со статусом failed. Symphony считает это успехом и повторяет ход
  примерно раз в секунду, пока не кончится rate limit API Linear. Dashboard после этого показывает только ошибку
  Linear (Discussion #133, Codex 0.157.1) [94].
- Если модель отклоняет каждый ход, запуски тратят весь лимит ходов. Настоящая ошибка видна только на уровне debug в
  log (Discussion #92) [84].
- Отмена запуска может оставить живой процесс app-server после выхода Symphony (Discussion #126) [89].
- Текст prompt не в ASCII (китайский) роняет каждый запуск в бесконечный цикл повторов (Discussions #129 и #80)
  [91][82].
- McAteer однажды нашёл Symphony направленной не на тот workspace Linear и написал свою защиту от этого [116].

**E. Новые версии Codex ломают Symphony.** Сообщения о сбоях вызваны выпусками Codex CLI 0.114, 0.128, 0.157, 0.160 и
0.164, которые меняли поведение app-server [84][78][94][93][95]. В исходном репозитории нет коммитов с 2026-09-15,
поэтому октябрьские исправления есть только в форках авторов сообщений [9][38].

**F. Закрытая модель участия:**

- Issues выключены, PR могут открывать только collaborators [9].
- Все 81 PR — от аккаунтов collaborators (не подтверждено). Сейчас GitHub помечает авторов 55 PR как COLLABORATOR,
  1 — как MEMBER, 18 — как CONTRIBUTOR и 7 — как NONE; были ли все авторы collaborators в момент PR, проверить не
  удалось [39]. 77 PR — от логинов, которые оканчиваются на `openai` или `oai`, 54 — от аккаунта ведущего автора [39].
- Вопрос, как внешним людям участвовать в проекте, остался без ответа (Discussion #40) [69]. Авторы сообщений о багах
  дают ссылки на ветки своих форков, потому что не могут открыть PR [91][93][94][89].
- Ответов в Discussions от аккаунтов, чей логин указывает на сотрудника OpenAI, исследование не нашло. Это проверка по
  имени логина [61].
- Maintainers при этом действуют, но молча:
  - мартовская идея для dashboard — ссылки на задачи в трекере (Discussion #46) — вышла в июне в PR #89 [71][52];
  - участник сообщества сообщил, что псевдонимы токенов GitHub и GitLab утекали к агентам; исправление в PR #119
    благодарит его [60];
  - неудачная настройка рабочей папки теперь повторяется с нуля (PR #111) [57].
- Настоящий канал участия — 2892 fork [9].

**G. Качество спецификации и сомнения в подходе «сначала спецификация»:**

- Читатель HN назвал спецификацию нечитаемым текстом, написанным агентом: она перечисляет поля, но не описывает state
  machine, о которой говорит [132].
- Mike Hearn спросил: если проект строится от спецификации, почему исправления после запуска меняли код, но не
  спецификацию (Discussion #49) [72].
- Пользователь противопоставил длинный prompt по умолчанию собственному совету OpenAI держать инструкции агента
  короткими (Discussion #93) [85]. Prompt по умолчанию — около 2900 слов [14].

**H. Пробелы, на которые натыкаются:**

- Состояние трекера не передаёт работу в нескольких репозиториях и командную память: кто активен, очереди ревью,
  история [133].
- Информация теряется, когда работа переходит между инструментами [134].
- Нет ничего до задачи: шага, который превращает идею в спецификацию и граф задач (Discussion #31, Chorus) [65].
- Агенты не читают файлы, приложенные к комментариям в трекере (Discussion #34) [67].
- Опрос идёт по проекту Linear, а не по очереди команды [80].
- Долгоживущий процесс не умеет обновлять токены GitHub App (Discussion #128) [90].
- У dashboard и API нет аутентификации. На SSH workers путь папки не сверяется с корнем перед `rm -rf` [88][87].
- Только Codex: большинство портов существует, чтобы добавить Claude Code [129].
- DevDigest (вторичный) добавляет: плохая работа с задачами на несколько репозиториев, нет жёсткой остановки, нет
  потолков расходов [109]. К DevDigest нужна осторожность. Он пишет, что логики повторов нет и по умолчанию около 20
  параллельных запусков. SPEC.md описывает повторы с растущей задержкой и 10 параллельных агентов по умолчанию [11].

**I. Сомнения в самом подходе:**

- Сарказм: разработчики теперь будут жить в Jira [135].
- Скепсис: software factories в основном производят инструменты для других software factories; вопросы о расходах
  [131].
- Агенты-ревьюеры как обязательное условие слияния зацикливаются почти без конца, потому что ревьюер всегда находит
  мелочь [136].
- Когда агент может трогать весь репозиторий, и код, и задачи, ограничить его трудно [137].
- Аналитики в InfoWorld (вторичный источник): проверка не масштабируется так, как генерация. Они советуют мерить
  пропущенные дефекты и переделки, а не число PR, и вести журнал аудита [106].
- Главную цифру OpenAI пересказывают неточно: рост влитых PR на 500% (то есть в 6 раз) превращается в «в 5 раз»
  [123][110][107].
- Ведущий автор рассказывает о стресс-тесте: параллельные агенты на простом TODO-приложении без подготовки под агентов
  закончили полным хаосом [96].
- В подкасте Latent Space (7 апреля; год не указан, по контексту 2026) ведущий спросил, почему Symphony нет внутри
  приложения Codex. Он также сомневался, что обычным командам нужна параллельность, ради которой создан Elixir [102].
- В теме HN на 263 очка о Kanban-приложении для агентов спрашивали, что даёт интерфейс доски, и называли локальную
  работу обязательным минимумом [139].

### Кто внедряет, кто форкает, кто уходит

- **Кто внедряет:** одиночки и маленькие команды, у которых уже есть Linear, Codex и приличный CI [115][116][120].
  README говорит, что лучше всего Symphony работает в кодовых базах, подготовленных для агентов, с тестами и
  guardrails [10].
- **Кто форкает и укрепляет:**
  - Публичный форк в организации Automattic на GitHub работал с мая по июль 2026: около 995 коммитов в main вместе с
    историей исходного проекта, все 135 влитых PR — от одного аккаунта. Использование в production не подтверждено
    [144]. Его добавления:
    - Claude как среда агента и маршрутизация по нескольким репозиториям;

    - пауза при нехватке места на диске.
  - Форк George чинит sandbox и процесс git, сокращает расход токенов на Linear, добавляет загрузку медиа [143].
  - Stavros переписал Symphony на Python поверх OpenCode, с sandbox bubblewrap. Запуск продолжается, когда человек

### Куда пошли продукты OpenAI (вывод)

Ни один источник не связывает это с Symphony. На DevDay 2026-09-29 OpenAI объявила [5]:

- Codex можно запускать на своём компьютере, удалённо с телефона или в облаке;
- вид `/agents` в Codex CLI, чтобы раздавать и отслеживать несколько задач;
- автоматическое облачное ревью кода;
- события MCP, по которым ChatGPT следит за доской проекта и готовит планы, пока пользователя нет.

Lopopolo сказал в апреле, что многие идеи его команды потом вошли в продукты OpenAI [102].

### Что думает автор сейчас

- 2026-11-09 Kotliarskyi написал, что работа с агентами стала изматывающей [97]. Причины, по его словам:
  - переключение контекста;
  - интерфейсы, сделанные как соцсети: счётчики непрочитанного, push-уведомления;
  - усталость от решений;
  - тревога, когда ни один агент не работает.
- Итог он называет cognitive surrender — человек перестаёт думать сам [97].
- Он предлагает строить системы вокруг защиты внимания человека, а не ради максимального выхода. Настоящими
  проблемами он называет доверие к агентам и нехватку контекста [97].
- Это личный блог, а не roadmap OpenAI [97].

### Куда идёт Linear

- CEO Linear связал всплеск новых workspaces с появлением репозитория и назвал Linear общим контекстом агентов и людей
  [103].
- Через две недели Linear опубликовал «Issue tracking is dead» (2026-03-24) [105]:
  - задача как главный организующий слой отжила;
  - агенты должны работать от общего контекста;
  - за три месяца до публикации агенты написали почти 25% новых задач в Linear.
- Это расходится с исходной идеей Symphony, где трекер — control plane (вывод) [105][1].

## Слабые места и чего нет

- **Только Codex.** Другие агенты — только в форках и портах [11][129][147].
- **Нет Windows.** Hooks и запуск предполагают `bash` [13][11].
- **Нет управления запуском.** Нет stop, pause и kill. Нет чата и подсказок агенту по ходу работы. Нет просмотра
  transcript и diff [11][13][35].
- **Нельзя ответить агенту.** Заблокированную сессию снимает только смена состояния задачи; канал ответа (PR #84)
  откатили [13][50].
- **Лимиты подписки не учитываются при планировании.** Лимиты только показываются. Нет ожидания сброса и нет
  планирования под лимиты. Ход, упавший на лимите, уходит в общую задержку до 5 минут [25][34]. Как сервис ведёт себя
  при реальном упоре в лимит — не подтверждено [25]. С Codex 0.160 лимиты даже не показываются [93].
- **Нет потолка на повторы и расходы (вывод)** [25][11]. Пользователи жалуются на расход токенов [116][117].
- **Ошибки не различаются по типу.** Лимит, падение и красный тест получают одну и ту же задержку [11][25].
- **Тихие сбои:** проваленные ходы считаются успешными (Discussion #133), ходы тратятся до лимита при отказах модели
  (#92), остаются осиротевшие процессы app-server (#126), prompt не в ASCII зацикливает запуски (#129)
  [94][84][89][91].
- **Нет сохранения состояния.** Перезапуск теряет таймеры повторов, сессии и список заблокированных задач [11][13].
- **Нет защиты от второго экземпляра** на том же проекте [41][46].
- **Сильная зависимость от протокола Codex.** Пять версий Codex ломали поведение; `dynamicTools` экспериментальные;
  документация советует для автоматизации SDK, а не app-server [84][78][94][93][95][4].
- **Разработка остановилась.** Коммитов нет с 2026-09-15, октябрьские сообщения о багах без ответа, исправления только в
  форках; OpenAI не планирует поддерживать продукт [38][93][94][95][1].
- **Закрытая модель участия:** Issues выключены, PR только для collaborators [9][69].
- **Нет уведомлений** [13][14].
- **Нет аутентификации у dashboard и API**, нет ролей и аккаунтов [24][88][11].
- **Широкий доступ инструментов.** Доступ равен правам токена; нет идемпотентности и ограничения области [13].
- **Sandbox по умолчанию читает всю файловую систему** [24].
- **Sandbox и одобрения ломают процесс:** безопасный профиль не даёт писать в `.git`; политика по умолчанию ломает
  старт с Codex 0.164 [66][143][95].
- **Записи агента в Linear идут от личного аккаунта человека**, судя по демо и совету README про личный API-ключ
  [6][13].
- **Недостающие skills** `launch-app` и `github-pr-media`, на которые ссылается эталонный workflow [14][16].
- **Зависимости и приоритеты — только частично.** Блокеры учитываются только в Linear и Jira, приоритет — только в
  Linear [33][13].
- **Одна область трекера на сервис.** Нет области уровня команды; задачи на несколько репозиториев обрабатываются
  плохо [75][80][109][133].
- **Рабочие папки по умолчанию во временной папке** `<tmp>/symphony_workspaces`; у пользователя её стёрла
  перезагрузка машины [11][109].
- **Нет встроенной проверки качества.** Всё задаёт prompt; ревью-персоны «Codex Review» — внешняя настройка [11][17].
- **Нужна подготовка репозитория (harness engineering).** Без неё параллельные агенты мешают друг другу [10][96].
- **Нет истории работы.** В памяти только последнее событие по задаче, `codex_session_logs` пуст [35].
- **Спецификация отстаёт от кода** и местами трудно читается [72][132].
- **Трудная установка:** Erlang, ручное создание состояний в Linear, флага согласия нет в командах README
  [109][143][13][39].
- **Нет шага до задачи** — от идеи к спецификации и графу задач [65].
- **Агенты не читают вложения** из комментариев трекера [67].
- **Долгоживущий процесс не обновляет токены GitHub App** [90].
- **SSH workers:** путь не сверяется с корнем перед `rm -rf` [87].

Сравнение идёт по описанию worfy: desktop-приложение на Electron для одного пользователя (macOS, порт на Windows в
работе), которое запускает и показывает работу Claude Code и Codex CLI на бесконечном Canvas. Здесь только сходства и
различия, без предложений.

| Форма продукта | Desktop-приложение на Electron с Canvas | Фоновый сервис без интерфейса; терминальный и веб-dashboard, JSON API [11][34][35] |
| Платформы | macOS; порт на Windows в работе | macOS и Linux; Windows нет [13] |
| Агенты | Claude Code и Codex CLI | Только Codex app-server [11] |

| Работа без присмотра | Autopilot запускает Waves — пакеты Tickets | Постоянный цикл опроса: у каждой активной задачи свой агент [1][11] |

### Где пересекаются

- **Одна и та же исходная проблема.** Оба продукта исходят из того, что внимание человека — главный дефицит. Symphony прямо
  говорит, что люди удерживали только 3–5 сессий [1]. Автор Symphony в ноябре пишет о защите внимания человека [97].
- **Работа без присмотра по тикетам.** Оба запускают агентов на тикеты без человека рядом и повторяют сбои [1][11].
- **Изоляция задачи.** Оба дают каждой задаче отдельную копию репозитория [11][14].
- **Правила работы агента рядом с кодом.** У Symphony это `WORKFLOW.md` и `.codex/skills` [11][16], у worfy —
  Harness plugin.
- **Путь до PR.** Оба доводят работу до PR с проверками CI и ревью [14][17].
- **Удалённые машины.** Оба умеют запускать агентов на других машинах [11][27].
- **Codex.** Оба работают с Codex; Symphony — только через app-server [11].
- **Материалы для проверки человеком.** У Symphony это видео, статус CI и ревью [6][10]. У worfy — Evidence
  screenshots, Gate и бейджи CI.

### Где расходятся

- **Источник правды.** У Symphony — внешний трекер, своей базы нет [11]. У worfy — свои Epics и Tickets.
- **Планирование.** У worfy есть Orchestrator session, которая планирует и раздаёт работу. У Symphony планирование —
  обычная задача, а её результат — новые задачи [1][96].
- **Лимиты подписки.** worfy ждёт сброса лимитов и планирует запуски под лимиты. Symphony лимиты только показывает
  [25][34]. Это прямо касается вопроса, может ли работа сама продолжиться после упора в 5-часовой лимит. В Symphony
  отдельного механизма для этого нет. Упавший ход повторяется с задержкой до 5 минут без потолка попыток (вывод), а
  поведение на реальном лимите никто не проверял (не подтверждено) [25].
- **Проверка.** У worfy Gate и ревьюеры — часть продукта. У Symphony ядро ничего не проверяет, всё задаёт prompt [11].
- **Вмешательство человека.** Symphony исключает подсказки посреди запуска: запрос ввода блокирует задачу, `Rework`
  начинает работу с нуля [11][14][49]. worfy одобряет запросы разрешений по политике.
- **История.** Symphony хранит в памяти только последнее событие по задаче [35]. У worfy есть Flight Recorder и Work
  track.
- **Агенты.** Symphony работает только с Codex [11]; worfy — с Claude Code и Codex CLI.
- **Интерфейс.** Symphony — сервис без интерфейса с dashboards [34][35]; worfy — desktop-приложение с Canvas.
- **Платформы.** У Symphony нет Windows [13]; worfy делает порт на Windows.
- **Кто ставит задачи.** В Symphony задачи может заводить любой участник команды через трекер, в том числе с телефона
  [1]. worfy рассчитан на одного пользователя.

### Что из отзывов касается той же области

- Главная жалоба пользователей Symphony — расход токенов и лимиты подписки [116][117][93].
- Пользователи сами строят desktop-, Kanban- и canvas-интерфейсы поверх спецификации [79][70][83][146][64]. На HN при
  этом сомневаются, что интерфейс доски что-то даёт [139].
- Пользователи сами добавляют ревьюеров и quality gates: форк Automattic, проект Sinai [144][142].
- Большинство портов существует, чтобы запускать Claude Code [129][144][146].
- Автор Symphony в ноябре критикует интерфейсы агентов в стиле соцсетей: счётчики непрочитанного и push-уведомления
  [97]. В worfy есть уведомления и счётчики лимитов.

## Механизмы, которые стоит изучить

1. **Сверка с состоянием задачи на каждом опросе и стартовая уборка.**
   - Что это: оркестратор на каждом опросе заново читает из трекера каждую работающую задачу.
   - Как работает: конечное состояние — остановить агента и удалить папку; неактивное состояние или переназначение —
     остановить, папку оставить; трекер не ответил — ничего не трогать. При старте удаляются папки уже закрытых задач.
   - Источник: [11 §8.5–8.6][25].
2. **Повторное чтение задачи прямо перед запуском.**
   - Что это: защита от изменений между опросом и стартом worker.
   - Как работает: перед стартом задача читается по ID. Если она исчезла, устарела или стала заблокированной, запуск
     пропускается. Если второе чтение не удалось, бронь задачи освобождается или переносится.
   - Источник: PR #15 и PR #110 [43][58][25].
3. **Обнаружение зависания по тишине.**
   - Что это: два независимых таймера на «агент молчит».
   - Как работает: `stall_timeout_ms` (5 минут без событий) убивает worker и ставит повтор. `turn_timeout_ms`
     (1 час) — интервал тишины, который сбрасывает каждая строка от app-server, а не общий лимит хода.
   - Источник: [11 §8.5][11 §10.6][59].
4. **Blocked как состояние, а не повтор.**
   - Что это: запрос ввода, одобрения или MCP elicitation не считается временным сбоем.
   - Как работает: задача остаётся занятой и видна отдельным счётчиком Blocked в dashboard и API. Повторов нет.
     Блокировку снимает смена состояния или маршрутизации задачи; перезапуск сервиса очищает список заблокированных.
   - Источник: PR #66 [49][25][35][13].
5. **Ходы продолжения по состоянию задачи.**
   - Что это: сообщению агента «я закончил» не верят; решает состояние задачи.
   - Как работает: после каждого хода задача перечитывается. Если она ещё активна, тот же thread получает короткую
     фиксированную инструкцию с пометкой «continuation turn #N of M», до `max_turns` (20).
   - Источник: `agent_runner.ex`, функция `build_turn_prompt`, строки 144–153; фраза «continuation turn #N of M» —
     строка 149 [28][11 §7.1].
6. **Лимиты параллельности по состоянию и хосту, opt-in по метке.**
   - Что это: настройка того, сколько задач на каком этапе идёт одновременно и какие задачи вообще можно брать.
   - Как работает: `max_concurrent_agents_by_state` задаёт лимит на имя состояния; например, можно разрешить не
     больше одной задачи в `Merging` (пример исследователя, в документации его нет). `max_concurrent_agents_per_host`
     ограничивает хост. `required_labels` пускает только помеченные задачи, а снятие метки останавливает агента:
     задача перестаёт подходить по маршрутизации, и сверка останавливает worker без уборки папки.
   - Источник: [11 §5.3.5][11 §8.5][24][51].
7. **Один workpad на задачу.**
   - Что это: один постоянный комментарий агента в задаче, который правится на месте.
   - Как работает: отметка окружения `host:path@sha`, иерархический план, критерии приёмки, проверка, заметки со
     временем и раздел «Confusions» с тем, что агенту было непонятно. `Rework` удаляет workpad вместе с PR.
   - Источник: [14].
8. **Файл политики в репозитории с перезагрузкой на ходу.**
   - Что это: настройки и prompt в одном версионируемом `WORKFLOW.md`.
   - Как работает: файл проверяется раз в секунду по mtime, размеру и хешу. Шаблон строгий: неизвестная переменная
     проваливает попытку. При ошибке остаётся последняя рабочая версия. Привязка инструментов фиксируется на сессию.
   - Источник: [30][32][33][11 §6.2].
9. **Инструменты с ключами на стороне хоста.**
   - Что это: агент пишет в трекер, не видя токена.
   - Как работает: каждый адаптер объявляет имена секретных переменных. Они удаляются из окружения агента (`unset` в
     команде запуска и `false` в окружении Port). Вызовы трекера выполняет оркестратор как dynamic tools.
   - Источник: [26][33][11 §10.5].
10. **Наблюдатель PR на кодах выхода и протокол ответа на комментарии.**
    - Что это: скрипт, который ждёт события в PR и сообщает его кодом выхода.
    - Как работает: `land_watch.py` параллельно следит за ревью, CI и последним коммитом PR. Код 2 — ревью, 3 — CI
      упал, 4 — новый коммит, 5 — конфликты. На каждый комментарий агент выбирает «принять, уточнить или возразить»,
      отвечает до правки и ставит префикс `[codex]`.
    - Источник: [17].
11. **Связка перезапуска планировщика и агентов.**
    - Что это: защита от двойного запуска одной задачи после падения планировщика.
    - Как работает: оркестратор и supervisor задач агентов стоят в режиме `:one_for_all`. Если оркестратор упал, все
      агенты останавливаются, и всё стартует заново с пустым состоянием.
    - Источник: PR #97 [53][31].
12. **Учёт токенов по абсолютным итогам.**
    - Что это: правило, которое не даёт посчитать токены дважды.
    - Как работает: брать накопленные итоги (`total_token_usage`), игнорировать дельты и считать прирост от последнего
      полученного итога. Время сессии добавлять при её завершении.
    - Источник: [19][25].
