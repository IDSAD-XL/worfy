## Модель работы

**Hybrid: локальное приложение плюс облако GitHub.**
- Приложение ставится локально. Сборки: Windows x64 и ARM64 (.exe), macOS Apple Silicon и Intel (.dmg), Linux x64 и ARM64 (AppImage) [61].
- Где идёт сессия — выбирается в меню *Run on* [3][62 v1.1.24]:
  - *This computer* — на этой машине. На Windows — ещё и внутри дистрибутивов WSL 2 (Windows Subsystem for Linux) [3].
  - *Cloud* — изолированный Linux sandbox на серверах GitHub [3][24].
  - удалённая машина: SSH, Codespaces (облачные среды разработки GitHub), Docker, managed sandboxes [62 v1.1.24, v1.1.26].
- На WSL, SSH и Linux-хостах приложение ставит фоновый процесс-помощник `copilotd` [62 v1.2.0].
- Changelog упоминает ещё типы workspace «Direct» и «Mission Control». Документация их не объясняет [62 v1.1.15].
- Cloud automations — задачи по расписанию и событиям — идут в облаке и работают при выключенном компьютере [9].
- Self-hosted варианта нет. GitHub Enterprise Server (GHES, GitHub на своих серверах компании) подключается только как дополнительный аккаунт для репозиториев, issues и PR. Запросы к моделям всё равно идут через облачный аккаунт с лицензией Copilot или через BYOK [36]. Сначала нужен вход в аккаунт GitHub.com или GHE.com; cloud-сессий для GHES нет [134].

**Агенты.** Только собственный agent runtime Copilot — тот же, что в Copilot CLI и Copilot SDK [1][119].
- Запустить Claude Code или Codex CLI агентом сессии нельзя. Запрос подключать чужие runtime через ACP (Agent Client Protocol — открытый протокол связи между редактором и агентом) stale-бот (бот, который закрывает неактивные issues) закрыл как «not planned» [127 #2366].
- Агентов «Anthropic Claude» (на Claude Agent SDK) и «OpenAI Codex» (на Codex SDK) GitHub предлагает в Agent HQ (раздел GitHub для агентов других вендоров) — на GitHub.com, в GitHub Mobile и VS Code, с оплатой через Copilot. Приложение в списке мест не указано [23][102].
- Приложение читает файлы `.claude/skills` и `.claude/agents` [62].

**Модели.** Много вендоров — через AI Credits или свой ключ [16][17]:
- Anthropic Claude, например Claude Opus 4.8 с контекстом 1M [62 v1.0.9]; OpenAI GPT-5.6 Terra, GPT-5.5, GPT-5.3-Codex [62 v1.1.24]; Google Gemini [69]; xAI Grok [62 v1.1.3]. Набор зависит от плана и настроек организации [16].
- Copilot Fusion — автоматический выбор и комбинация моделей под задачу [93].
- BYOK: OpenAI, Azure OpenAI, Microsoft Foundry, Anthropic, Ollama, Foundry Local, LM Studio и любой OpenAI-совместимый endpoint. Ключи хранятся в keychain ОС [17][72].
- Локальная модель MAI Code 1.1 Flash через Windows ML (preview): работает офлайн и не тратит credits [17].

**Один пользователь или команда.** В основе — приложение одного разработчика. Совместная работа идёт через объекты GitHub: PR, review, checks [107][77].
- Командные части: shared automations [10], canvases и конфиг на уровне репозитория [8][14], общий пул credits в Business и Enterprise [30], политики, managed settings и метрики для администраторов [75][76][77].
- Одновременная работа двух людей в одной сессии — не подтверждено.

**Платформы и вход.** macOS, Windows, Linux [61][70]. Нужны Git и аккаунт GitHub — на GitHub.com или на GHE.com (облако GitHub с хранением данных в выбранном регионе) [2]. Локальной сессией можно управлять с GitHub.com и из GitHub Mobile — это remote control [22].

## Функции

### Сессии

Сессия — изолированное рабочее место агента со своей веткой, файлами, разговором и состоянием задачи. Её можно поставить на паузу и продолжить [67].

- **Создание.**
  - Источник: открыть локальную папку, добавить репозиторий GitHub или клонировать по любому Git URL, например из Azure DevOps [2].
  - Workspace: *New worktree* или *Current checkout*, плюс base branch [3].
  - Настройки: sparse checkout для очень больших репозиториев [62 v1.0.17]; префикс веток и место хранения [62 v1.2.0]; шаблон пути worktree [62 v1.1.4].
  - `.worktreeinclude` — список неотслеживаемых файлов, которые копируются в каждый новый worktree. Файл есть как минимум с v1.1.35; v1.2.0 только перестал копировать файлы внутри submodules и уже отслеживаемые файлы [62 v1.1.35, v1.2.0]. *Keep one worktree ready* держит один worktree заранее готовым [62].
- **Вид.** Боковая панель группирует сессии по репозиториям [3]. Есть сетка из нескольких сессий [62 v1.0.20, v1.1.4]. У каждой сессии свой контекст, между ними можно свободно переключаться [116].
- **Статусы:** Working, Done, Idle, Needs input, Loading [62 v1.1.28].
- **Режимы:** Interactive, Plan, Autopilot. Переключаются в любой момент, Shift+Tab — по кругу [3][62].
- **Права на инструменты** — отдельный переключатель, три уровня [3][12][90]:
  - *Ask every time* — спрашивать каждый раз.
  - *Assisted* — модель оценивает каждый запрос, явно безопасные пропускает, про остальные спрашивает человека. GA с 2026-10-26.
  - *Approve all* — разрешать всё; то же делает команда `/yolo`.
- **Autopilot** — агент идёт по шагам, не дожидаясь человека. Прав он не выдаёт: это отдельная настройка [20].
  - После задачи режим возвращается в Interactive, чтобы следующий prompt случайно не ушёл без присмотра [62 v1.0.4].
  - Если включить Autopilot при *Ask every time*, приложение предложит режим прав, с которым можно работать без человека [62 v1.1.11].
- **Цели.** `/goal` задаёт долгую цель для Autopilot в локальных сессиях [62 v1.1.15]. `/autopilot` тоже задаёт цель [62 v1.1.18].
  - Goal pill — метка в поле ввода. Показывает Active, Paused или Done, причину паузы, число ходов и потраченные credits [62 v1.1.17].
- **Настройки сессии:** модель, reasoning effort, размер контекста. Есть модель по умолчанию [3][62 v1.4.0].
- **Поле ввода (composer).**
  - `#` — ссылка на issue, `@` — файл, `/` — команда [3].
  - Голосовой ввод на скачанной локальной модели распознавания речи [3].
  - Вложения: картинки и видео [62 v1.1.27].
- **Несколько агентов** [12][13]:
  - `/fork` делит сессию; `/merge-to-parent` возвращает работу fork в родителя.
  - `/spawn` запускает дочернюю сессию под узкую задачу.
  - `/fleet` — несколько агентов параллельно над одной задачей.
  - `/orchestrate` — координатор ведёт дочерние сессии в разных сессиях и репозиториях.
  - `/pr-stack` строит stacked PRs — цепочку PR, где каждый следующий основан на ветке предыдущего; по одной дочерней сессии на слой.
  - Stacked sessions — то же для сессий: каждая следующая строится на ветке предыдущей [111].
  - Dynamic workflows — оркестрация, записанная кодом: шаги идут последовательно или параллельно (public preview) [87].
- **Побочные вопросы** без прерывания текущего ответа: `/side`, `/ask`, `/btw` [62 v1.1.3, v1.1.12].
- **Chats** — разговоры без ветки и worktree, для обсуждений. Раньше назывались Quick chat и Start from scratch [3][62].
- **Уборка.**
  - Manage sessions: поиск, массовые archive и delete, место на диске по сессиям [3].
  - Авто-archive и авто-delete по расписанию [62 v1.1.11].
  - Archive останавливает dev servers. Восстановление возвращает checkout в ту же папку [62 v1.1.35].
- **Прочие команды** [12]:
  - контекст и расход: `/compact`, `/context`, `/usage`;
  - проверка и анализ: `/review`; `/research` — отчёт с цитатами; `/spar` — спорит с выбранным подходом; `/rubber-duck` — критика от модели другого семейства; `/security-review`;
  - сессия и репозиторий: `/init`; `/export-gist` — стенограмма в секретный gist; `/remote`; `/sandbox on|off`; `/terminal`;
  - поиск и история: `/af` — поиск MCP servers, skills и agents в каталоге Agent Finder; `/inbox`; `/chronicle` — отчёты по прошлым сессиям (standup, search, cost-tips, improve).
- **Расписание.** `/every` и `/schedule` — повторяющаяся или разовая работа в сессии или Project [62 v1.4.0].
- **Перенос.** Сессию можно продолжить в VS Code — с worktree и разговором [123]. QR-код в меню *Open in* передаёт cloud- и Codespace-сессию в GitHub Mobile на телефоне [62 v1.2.0].

### Встроенные панели

- **Diff и PR.** Вкладка Changes, вид PR и кнопка Create PR прямо в сессии [2]. В diff можно оставлять комментарии [118]. Очень большие PR рендерятся через виртуализированный список [120].
- **Терминалы:** несколько на сессию [118], плюс `/terminal` [12].
- **Run scripts** из файла `.github/github-app.yml` [14]:
  - запуск при создании или archive сессии;
  - regex `server_ready_pattern` ловит момент, когда dev server поднялся; приложение открывает его URL во встроенном браузере.
- **Браузер.** Встроенный браузер называется Browser Canvas. Ссылки GitHub открываются внутри приложения [62 v1.2.0, v1.4.0].
  - Режим Pick & Polish: клик выбирает элемент страницы, протяжка снимает screenshot области [62 v1.2.0].
  - Инструменты агента для браузера работают только во вкладках, которые пользователь сам отдал агенту [62 v1.1.27].
  - Профили браузера — не подтверждено.
- **Files.** Панель файлов и правка в приложении с обнаружением конфликтующих изменений [62 v1.1.15, v1.1.24]. Present mode показывает canvas, diff или файл на весь экран [62 v1.0.13].
- **Insights.** Timeline вызовов инструментов и работы sub-agents, время на каждый инструмент [62 v1.0.17]. График заполнения context window [62 v1.0.18].
- **Health check.** Окно с версией фонового процесса агента; чинит сломанные plugins [62 v1.1.13, v1.4.0]. По сообщению пользователя, проверяет вход в GitHub, запись в хранилище репозиториев и Git [127 #3856].
- **Computer use** (public preview) [18][91]:
  - локальные сессии на macOS и Windows;
  - агент читает окна приложений через accessibility tree или screenshots, кликает, печатает, переходит между приложениями;
  - выключено по умолчанию и подчиняется правам сессии; выбор «Always allow» для приложения хранится локально; enterprise может запретить.
  - Дата запуска в заметках расходится: changelog от 2026-10-01 [88] против релизов на конференции GitHub Universe 2026-10-28 [91].
- **Картинки.** Чат генерирует и редактирует изображения [91].
- **Клиент GitHub.** Вкладка Code репозитория и dashboards с widgets; приложение всё больше работает как десктоп-клиент GitHub [62].

### GitHub и путь PR до merge

- **My Work** — общий список issues, PR, сессий и automations по подключённым репозиториям. Раньше назывался Inbox [62 v0.2.28].
  - Вкладки All, Active, Review requests, Done. Только репозитории, с которыми работали в приложении [114].
  - Свои виды с фильтрами в стиле GitHub [114]. Фильтр можно описать словами — его сгенерирует модель [62 v1.1.23]. Квалификаторы `has:` и `no:`, массовый запуск сессий [62][38].
  - Больше десяти сохранённых видов и фильтр командных review requests [62 v1.1.35]. Ссылка `ghapp://mywork` [19].
- **Issues.**
  - Открытие issue может сразу запускать сессию с ним. По умолчанию включено (`automation.auto_issue_session`) [4][14].
  - Агент следует шаблонам issue и PR репозитория [4].
  - В локальных сессиях перед созданием issue агент спрашивает подтверждение: репозиторий, заголовок, текст [62 v1.3.0].
- **Pull requests.**
  - Обзор с CI checks и активностью review, вкладка Files changed, отправка review, открытие в браузере или IDE [4].
  - Кнопка Fix у каждого review comment и кнопка Fix failing checks [4].
  - Команды `/pr-open`, `/pr-fix-checks`, `/pr-resolve-comments`, `/pr-merge` [12].
  - Баннер статуса merge queue и работа с auto-merge [62 v1.1.29, v1.1.30].
- **Agent Merge в приложении** — фоновый цикл, который доводит PR до merge.
  - Включается отдельно на каждый PR. Сессия этого workspace чинит упавшие GitHub Actions workflows, конфликты merge и review comments, и делает merge, когда GitHub разрешает [4].
  - Отвечает в ветке комментария reviewer и закрывает её (resolve) [62 v1.1.8].
  - Работает в фоне, переживает перезапуск приложения, сам выключается после merge [4].
  - Обязательная проверка, которая ещё не отчиталась, считается pending; пока такие есть, Agent Merge остаётся включённым [62 v1.1.5, v1.1.34].
  - Опция keep-awake не даёт компьютеру уснуть, пока Agent Merge следит за PR [62 v1.1.31].
  - Когда кончается квота Copilot, ставит себя на паузу и продолжает после сообщения пользователя или возврата квоты [62 v1.1.34].
  - Свой учёт расходов [62 v1.0.13].
  - Как часто проверяет PR: по умолчанию раз в 10 минут, с v0.2.6; до того — раз в 30 минут [62 v0.2.6]. «Раз в минуту» из v1.2.0 — про другой случай: так проверяется workspace, у которого ещё нет PR; до исправления это происходило каждые 5 секунд [62 v1.2.0]. Кроме таймера, цикл реагирует на события GitHub — завершение CI, новый review comment [119].
- **Agent Merge в облаке** — кнопка «Watch and fix» на странице PR в GitHub; доступен с 2026-10-28 пользователям платных планов [100][5][6]. Заметка changelog помечена «Release», слова GA в ней нет. Там же сказано, что Agent Merge уже был в приложении и в VS Code [100]:
  - работает в окружении GitHub Actions;
  - чинит только упавшие workflows и конфликты merge, на review comments не отвечает;
  - нужны платный план и политика «Enable automations»;
  - не работает со stacked PRs и PR из fork;
  - платит тот, кто включил;
  - можно включать автоматически для своих PR и сочетать с auto-merge.
- **Security.** `/security-review` (public preview с 2026-07-14) [3][74]. Security extension (public preview) показывает alerts code scanning в canvas и просит Copilot их исправить [8][96].
- **Не-GitHub хосты.**
  - Клонировать можно из Azure DevOps и по любому Git URL [2]. Поддержка Azure DevOps вышла 2026-10-29 [127 #620].
  - Исправлены Git-операции с remotes на GitLab и Bitbucket [62 v0.2.31].
  - Агенты в сессиях Azure DevOps комментируют PR [62 v1.3.0].
  - Открывать PR на не-GitHub remotes пока нельзя — открытый запрос [127 #2009].

### Projects (public preview)

- Project — контейнер под цель поверх нуля или нескольких репозиториев. Copilot сам координирует сессии и повторяющиеся automations ради цели, запускает столько агентов, сколько нужно, и возвращает результаты, например PR [7][91].
- В контекст можно добавить треды Slack, макеты дизайна, заметки встреч [91].
- Правая панель, три вкладки [7]:
  - **Overview** — группы Needs input, Open (с PR и числом добавленных и удалённых строк), Working, Done. Любую сессию можно открыть и направить.
  - **Library** — отдельно файлы пользователя и файлы, созданные агентом.
  - **Automations** — пауза, смена расписания, удаление повторяющейся задачи. Changelog называет ещё вкладку Routines [62].
- Повторяющаяся задача создаётся просьбой на обычном языке, например «every Monday at 9 AM» [7].
- Есть настройка памяти на уровне Project [7][62]. Это не то же, что Copilot Memory — общая память фактов о репозитории [37].
- До v1.1.31 (2026-10-23) Projects назывались Persistent Agents. Тогда агент мог владеть чатами вроде «Slack watch» и «Teams watch» [62 v1.1.27, v1.1.31]. Следят ли Projects за каналами сейчас — не подтверждено.
- Локальные репозитории в Projects использовать нельзя — открытый запрос [127 #5175].

### Canvases (canvas extensions)

- Это не пространственный холст. Canvas — общая интерактивная поверхность в правой боковой панели: kanban-доска, доска разбора, сессия браузера, чек-лист, dashboard, документ [8].
- Человек работает с ней через UI. Агент — через функции, которые canvas открывает ему, например `get_board`, `add_card`, `move_card` [8].
- Создаётся командой `/create-canvas` [8]:
  - уровень репозитория — в `.github/extensions`, расходится через git;
  - уровень пользователя — в `~/.copilot/extensions`;
  - типичный canvas — `package.json`, `extension.mjs` и JSON-файлы с его состоянием.
- Встроены canvases Browser, Terminal и Markdown [62].
- Canvases поставляются в plugins. Среди рекомендованных: Azure DevOps, Jira, Sentry, security extension GitHub [8][62 v1.1.15, v1.1.23].

### Automations

- **Local и cloud.** Local automations идут на машине пользователя. Cloud automations идут через Copilot cloud agent и работают при выключенном компьютере [9]. Набор триггеров у них разный [9].
- **Триггеры:**
  - расписание (каждый час, день, неделю), создание issue, открытие PR, обновление PR — с фильтрами поиска и изменённых файлов [10];
  - комментарии в issues и PR [78];
  - вызов через API с дополнительным контекстом; цепочки automations в многошаговые процессы [10][98];
  - события от пользователей без права записи по умолчанию игнорируются — защита от prompt injection [10].
- **Инструменты:** инструменты GitHub только для этого репозитория (20 новых добавлены 2026-10-28) и инструменты MCP servers репозитория [10][98].
- **Владелец.** Automation бывает personal или shared; тип потом не меняется [10][99]:
  - *personal* — видит только автор, платит автор, действует от его имени;
  - *shared* — видят все с правом чтения, правят все с правом записи, платит владелец репозитория, действует от имени Copilot.
  - PR от shared automations требуют дополнительного подтверждения [10].
- **Видимость.** Prompts и логи cloud-запусков видят все с правом чтения репозитория — даже у personal automations [9].
- **Лимиты расходов** — только у cloud automations [9]:
  - на запуск (минимум 30 credits) — останавливает запуск;
  - на день, неделю, месяц (сброс по UTC) — блокируют новые запуски, но не прерывают идущий.
- **Самоулучшение.** Группы automations делят сохранённые артефакты и по итогам предлагают правки своих prompts; правки утверждает человек [10][97].
- **Уровни автоматизации** для разбора issues: Full control, Cautious (по умолчанию), Balanced, Full automation. Каждое изменение несёт обоснование и оценку уверенности; изменения с низкой уверенностью ждут review. Документация оговаривает: это удобство процесса, а не мера безопасности [11].
- **Условия cloud automations:** private или internal репозитории; план Pro, Pro+, Max, Business или Enterprise. Каждый запуск тратит AI credits и минуты GitHub Actions [10].
- Управлять automations можно также на вкладке Agents в GitHub, в VS Code и через REST API [10].

### Модели

Список моделей и BYOK — в разделе «Модель работы». Здесь — функции поверх моделей.

- **Copilot Fusion** (GA 2026-10-28) выбирает и сочетает модели под задачу. Уровни усилия: Standard, High, Max [16][93]. Учитывает текущее состояние систем и доступность моделей [39].
- **HydraFusion** (research preview; позже стал Copilot Fusion) выбирает один из трёх шаблонов [86][117]:
  - *Single* — задачу решает одна модель;
  - *Cascade* — дешёвая модель делает черновик, проверка решает, звать ли сильную;
  - *Critique* — модель другого семейства один раз критикует черновик, автор правит.
- **Rubber duck** — критика от модели другого семейства, только чтение, с уровнями серьёзности. В приложении включён по умолчанию с v0.2.14 [43][62].
- **Свои настройки review.** У агентов code review настраиваются модель и усилие [62 v1.1.15].
- **Заявления вендора о бенчмарках** (не проверены независимо): Fusion Max набрал 60 на Artificial Analysis Coding Agent Index — «в пределах двух пунктов» от Claude Code с Opus 5.5 Max. При этом средняя цена API на задачу примерно вдвое ниже, токенов примерно вдвое меньше, времени на задачу примерно на 40% меньше [93]. HydraFusion на TerminalBench 2.1: +4,9 пункта при расчётной цене на 67% ниже Opus 5; это offline-оценка [117].

### Sandbox, безопасность, управление

- **Cloud sandbox** — эфемерный изолированный Linux [24]:
  - снимок (snapshot) сохраняется, пока sandbox остановлен; сессия продолжается со снимка; общего лимита в один час нет;
  - сетевой доступ — по allowlist firewall cloud agent;
  - окружение нельзя сменить после старта сессии;
  - GA на платных планах с 2026-10-28 [94];
  - цена: $0.000024 за vCPU-секунду, $0.000003 за GiB-секунду, $0.005 за GiB-месяц хранения снимков; compute можно списывать из включённых минут Actions [24][94].
- **Local sandbox** — MXC (Microsoft eXecution Container) [25][66]:
  - выключен по умолчанию, бесплатен [25];
  - backends (механизмы изоляции процессов в самой ОС): macOS 15+ — Seatbelt; Linux — bubblewrap 0.5.0+ и slirp4netns; Windows 11 25H2 или 26H1 со свежим обновлением — processcontainer [25][27][66];
  - по умолчанию запись только в рабочую папку и временные папки; выход в интернет разрешён, локальная сеть закрыта; git и `gh` получают подставные credentials [27];
  - политика файловой системы — «всё запрещено, кроме разрешённого»; встроенные файловые инструменты проверяют её только программно [26];
  - в CLI sandboxed-инструменты получают подставные credentials, а настоящие добавляет локальный proxy [25];
  - в приложении: если ОС не может обеспечить политику, команда в sandbox падает с ошибкой (fail closed), а не запускается без защиты [25][85]. В CLI иначе: на неподдерживаемом хосте сохранённая настройка пользователя выключается на эту сессию, и команды идут без sandbox с предупреждением; fail closed там требуют enterprise managed settings (`sandbox.failIfUnavailable`) [25];
  - выход из sandbox требует подтверждения *Run outside the sandbox?*; Assisted такие запросы не оценивает [27][28];
  - в приложении с v1.1.23; public preview 2026-09-23; GA 2026-10-07 [62][85][89]. Переключатель `/sandbox` [12].
- **Управление в организации.**
  - У приложения своя политика доступа, включена по умолчанию [1][77].
  - Enterprise рассылает `managed-settings.json`: plugins, marketplaces, computer use, remote control, telemetry [14][18][76][84].
  - Content exclusion (исключение файлов из контекста) — GA [1][82].
  - Использование видно в usage metrics API [75]. Экспорт OpenTelemetry; содержимое prompts и ответов по умолчанию не выгружается [84].
  - В справочнике политик приложение — отдельная колонка [37]. Можно запретить работу без подтверждений [62].
- **Remote control.** Локальную сессию можно смотреть и вести с GitHub.com или из GitHub Mobile. Нужна политика организации «Store local sessions in the Cloud» = «View and control»; флаг репозитория по умолчанию выключен [12][14][22]. События уходят в GitHub, команды приложение забирает опросом [22].
- **Privacy.** Streamer Mode скрывает расход, названия моделей и квоты [62 v1.0.26]. Полный охват не описан. Функции, которая вымарывает личные данные на screenshots, не найдено.

## Принципы и подходы

**Какую проблему решают.** По словам Mario Rodriguez на запуске (2026-06-02), агенты ускорили написание кода, но раздробили процесс работы [107]:
- больше переключений контекста и больше времени на review результатов агентов;
- инструменты не рассчитаны на несколько агентов сразу;
- контекст разбросан по окнам, легко потерять, что сейчас работает;
- PR приходят без записи о том, что агент пробовал, что проверил и где нужен человек.

Приложение подают как центр управления разработкой с агентами [107].

**Результат важнее объёма.** Jay Parikh (Executive Vice President CoreAI в Microsoft) на Universe 2026: главный результат — завершённая работа, а не больше кода [124]. Из этого следует [124]:
- разработка больше не идёт по прямой линии; люди задают направление, принимают решения и отвечают за результат, агенты реализуют и проверяют;
- непрерывный цикл обучения улучшает каждый следующий проход;
- три цели: скорость, «интеллект» (контекст платформы плюс обучение) и качество (безопасно по умолчанию);
- GitHub обещает открыть базовые строительные блоки; контроль над работой, инструментами и расходами остаётся у пользователя.

**Решение выпускать — за человеком.** Agent Merge подают как автоматизацию, где пользователь сам выбирает, насколько далеко она заходит и что ей можно выпускать [107]. Довод: профессиональному софту нужны суждение, проверка и ответственность; агенты берут больше работы, а люди держат качество, политику и поставку. Хостить это должен GitHub, потому что код, review, issues и команды уже там [107].

**Агенты внутри жёстких правил.** Агенты берут неоднозначную работу с большим контекстом. Повторяемые правила — CI checks, branch protection, CODEOWNERS, обязательные review — дают командам доверие к системе. Разработчик становится оркестратором: задаёт триггеры, права агентов и передачу работы [112].

**Чат — не главный интерфейс.** Canvases на запуске назвали началом «agent experience (AX)» — интерфейсов, которыми люди и агенты пользуются вместе [107][68]:
- в чате дают указания и снимают неясности; на canvas работа становится видимой, редактируемой, утверждаемой и проверяемой;
- три участника canvas: пользователь (смотрит и направляет), агент (читает состояние, действует, использует canvas как доказательство выполнения), приложение (связывает canvas с настоящим объектом и решает, какие действия разрешены) [68];
- Burke Holland (developer advocate): когда задача ясна, чат обычно неудачный UI; canvas — маленькое full-stack приложение внутри приложения с двусторонней связью с агентом; дешевле один раз попросить агента построить инструмент, чем каждый ход использовать агента как инструмент [121];
- рецепт Ayan Gupta: явно описать состояния процесса, вынести на экран решения, которые важны, сохранять прогресс сразу, оставить явные точки утверждения человеком. Сборка двух его примеров стоила около 2 000 и 3 000 credits [113].

**«Ambient intelligence».** Martin Woodward (VP Developer Relations) описывает три слоя: способ ввода фиксирует намерение, harness (обвязка агента: цикл, инструменты, правила) планирует и действует, слой управления даёт человеку смотреть, перенаправлять и утверждать. ИИ должен быть внутри процесса работы, а не сбоку [122].

**Один runtime — много поверхностей.** Один и тот же agent runtime работает в CLI, приложении, SDK (GA на шести языках), VS Code, Visual Studio, cloud agent, code review и других продуктах Microsoft [107][119]. Holland: harness изучаешь один раз и пользуешься везде; ближе всего к нему CLI [110].

**Автономия требует безопасной среды, а не новых подтверждений.** Holland: подтверждать каждый шаг — убивать продуктивность; частые запросы приучают людей их не читать; поэтому агенту дают полную автономию, но внутри sandbox [110]. В продукте это сделано так:
- Autopilot («продолжай без новых prompts») и права на инструменты («что можно без вопроса») — разные настройки [20];
- три режима подтверждений, включая Assisted, где решает модель [3];
- cloud agent по умолчанию спрашивает перед каждой записью; когда доверие появилось, советуют переключиться на autopilot [107];
- для automations — уровни автоматизации с оценкой уверенности [11].

**От выбора модели — к процессу из моделей.** HydraFusion (позже Copilot Fusion) считает исполнение задачей оптимизации. Пять принципов [117]:
- учитывать стоимость каждого шага;
- ограничивать каждый шаг timeout и отменой;
- проводить review в изолированных контекстах без инструментов;
- не применять patch, если запуск упал или отменён;
- проверять маршрут до исполнения.

**Делегировать выборочно.** GitHub урезал склонность CLI раздавать задачи subagents: на 23% меньше сбоев инструментов на сессию и на 5% ниже P95 времени ожидания [108]. Subagent нужен для параллельной работы, а не как кнопка паузы [108]. Stephen Toub (Distinguished Engineer, Microsoft) различает [119]:
- дочернюю сессию — свой worktree, своя ветка, свой цикл агента;
- subagent — работает внутри workspace и контекста родителя.

Его уроки параллельной работы: явно формулировать намерение; любую открытую возможность агент применит и там, где её не ждали; равноправным сессиям нужен арбитр — координатор или человек [119].

**Чем подход отличается.**
1. Всё построено вокруг объектов GitHub: issues, PR, checks, review, stacks, merge queue [67][62].
2. Цикл не заканчивается на открытии PR: Agent Merge ведёт PR через CI, review и конфликты до merge [107][4]. Toub провёл через Agent Merge все 128 PR переноса runtime, но последний шаг merge обычно делал сам [119].
3. Одна сессия — много мест: приложение, VS Code, CLI, web, Mobile [124][106][123].
4. Общий runtime переписан на Rust: больше 800 000 строк в 128 PR, в основном написаны агентами под надзором одного инженера; около $120 000 на токены и около трёх недель его времени. В нагрузочном тесте с десятью клиентами прирост памяти упал с 1 383 МБ до 247 МБ (Rust вне процесса клиента) и 126 МБ (Rust внутри процесса) [119].
5. Canvases — маленькие приложения, которыми управляет агент, в боковой панели, а не пространственная доска [8][121].
6. Маршрутизация моделей как продукт: Fusion, модели многих вендоров, BYOK [93][72].
7. Расчёт на управление в enterprise: отдельная политика, managed settings, OpenTelemetry, content exclusions, sandbox с fail closed [77][84][85][82].
8. Runtime одного вендора: в приложении работают только сессии Copilot [102][23].

**Ключевые понятия** (подробно — в «Функциях»):

| Понятие | Что это |
|---|---|
| Session | Изолированная работа агента: ветка, файлы, разговор, состояние задачи |
| Chat | Разговор без ветки и worktree |
| My Work | Общий список issues, PR, сессий и automations |
| Project | Цель поверх нескольких репозиториев; Copilot сам ведёт сессии и automations |
| Coordinator / orchestrator | Сессия, которая раздаёт работу дочерним сессиям (`/orchestrate`) |
| Interactive / Plan / Autopilot | Режимы работы сессии |
| Goal | Долгая цель Autopilot; потолок credits описан для CLI |
| Assisted | Подтверждения инструментов, которые решает модель |
| Agent Merge | Фоновый цикл, доводящий PR до merge |
| Canvas | Панель-приложение, которой пользуются и человек, и агент |
| Automation | Задача по расписанию или событию, локально или в облаке |
| Fusion | Автоматический выбор и сочетание моделей |
| Rubber duck | Критика от модели другого семейства |

## Как это устроено внутри

Код закрыт. Ниже — то, что следует из документации, changelog приложения и Copilot CLI и из сообщений пользователей (помечены «сообщение пользователя»).

### Архитектура

- **Оболочка и UI.**
  - Окно приложения рисуется в системном webview ОС. Changelog упоминает перезапуск после сбоя WebView2 на Windows (v1.1.15), WebKitGTK в поле ввода на Linux (v1.0.6) и сбой в Customize на «older system WebViews» (v1.2.0) [62]. Запись v0.2.1 про «native WebView2 surface» и «React placeholder» касается встроенного browser preview, а не всего окна [62 v0.2.1]. UI написан на React [120].
  - Значит, это не Electron с встроенным Chromium (вывод из changelog). Tauri это или другой framework — не подтверждено.
- **Движок.**
  - Приложение несёт в себе сборки Copilot CLI (v1.1.35) [62]. Оно управляет CLI через copilot-sdk: SDK — транспорт JSON-RPC, цикл агента выполняет CLI [54].
  - Каждую сессию CLI приложение настраивает типизированным config SDK; так, например, включается память (v1.0.4) [62].
  - Сообщение пользователя: при создании cloud sandbox встроенный CLI вернул ошибку JSON-RPC -32601 — неизвестный метод `session.create` [127 #3878].
- **Rust.** Противоречия нет.
  - Agent runtime — цикл агента, инструменты, MCP, hooks, persistence — целиком переписан с TypeScript на Node.js на Rust. К концу переноса временных вызовов между TypeScript и Rust внутри runtime не осталось [119].
  - Runtime поставляется как нативная библиотека `runtime.node` с двумя входами. CLI — сам процесс Node — загружает её как native addon через napi. Другие языки SDK могут загрузить её в свой процесс через C ABI; этот путь пока opt-in, по умолчанию SDK по-прежнему говорит с отдельным процессом по JSON-RPC [119].
  - В приложении Rust-runtime включён по умолчанию с v1.1.31. v1.4.0 убрал настройку *Native Rust runtime wrapper* и прежнюю возможность оставить сессии на Node [62 v1.1.31, v1.4.0]. Разбор командной строки CLI перешёл с библиотеки Commander на грамматику на Rust в CLI 1.0.85 [65].
- **Процессы.**
  - Один общий процесс CLI обслуживает несколько сессий. Перед отправкой сообщения приложение пингует его и перезапускает, если тот не отвечает (v1.1.35) [62].
  - Раньше перезапуск медленного общего runtime прерывал все сессии на нём (v1.1.31) [62].
  - Сообщение пользователя (v1.1.30, Windows): приложение держит по процессу `copilot.exe --server --stdio` на каждую запущенную сессию и не освобождает их в простое; у каждого ещё 2–3 процесса `extension_bootstrap.mjs`. Было 17 серверов при 2 активных сессиях, всего около 18 ГБ [127 #4979].
  - Как это сочетается с «общим процессом CLI» из changelog — не подтверждено. Возможно, общий процесс обслуживает группу сессий, а не все.
- **Хранение.**
  - Локальная база приложения: восстановление из backup, если база пуста или повреждена (v1.0.3); ограниченный по времени ремонт при обновлении (v1.1.30); починка пропавших индексов (v1.1.24) [62].
  - Полная запись сессии — в `~/.copilot/session-state` плюс хранилище сессий на SQLite [49][50]. В папке сессии: `events.jsonl` (журнал событий), пронумерованные `checkpoints/NNN.json`, `plan.md` и `files/` [55].
  - Сообщение пользователя: сессию с `events.jsonl` больше 560 МБ не удалось открыть [127 #3119].
- **Окружения.**
  - На удалённых хостах работает управляемый daemon агента, он сообщает версию клиентского протокола (v1.1.13, v1.1.29) [62].
  - CLI 1.0.110 требует «AHP environment» для cloud-сессий и удалённых подключений; CLI 1.0.88 уже упоминает `--ahp-host` [65]. Расшифровка AHP — не подтверждена.
  - Cloud-сессии сейчас — заметки расходятся. v1.1.27 убрал создание новых Cloud-сессий и automations; v1.1.29 вернул cloud automations; документация на 2026-11-12 всё ещё показывает окружение Cloud [62][3]. По одной заметке, Cloud вернулся в выбор окружения в v1.1.28 [62 v1.1.28]; по другой, можно ли сейчас создать новую Cloud-сессию в приложении, — не подтверждено. Причину удаления GitHub не назвал (не подтверждено).
- **Связки.**
  - Scripts репозитория получают `COPILOT_PORT` — WebSocket-порт приложения для workspace [14].
  - Удалённые feature flags — общий список, который умеет только выключать функции [63].
  - Экспорт OpenTelemetry настраивается через свойство `telemetry` в enterprise managed settings [84].
- **Известные файлы и папки** (вместо модулей кода):
  - `~/.copilot/session-state/…/events.jsonl`, `checkpoints/NNN.json`, `plan.md`, `files/` — запись сессии [55];
  - `permissions-config.json` — сохранённые разрешения инструментов по корню git [50];
  - `.github/github-app.yml` — конфиг репозитория [14]; `.worktreeinclude` — файлы для копирования в worktree [62];
  - `.github/extensions/` и `~/.copilot/extensions/` — canvases; каждое extension — отдельный процесс Node, который подключается к сессии через `joinSession` из `@github/copilot-sdk/extension` [8][58];
  - `managed-settings.json` — настройки от enterprise [76];
  - `flags/feature-flags.md` в github/app — список удалённых флагов [63].

### Изоляция

- **Worktree.** Сессия получает новый worktree или работает в текущем checkout [3]. Дочерние сессии и fork по умолчанию тоже получают свои worktrees (сообщение пользователя) [127 #2157].
  - Путь worktree в приложении по умолчанию — не подтверждён. В CLI по умолчанию `<repo>.worktrees/`, задаётся `worktreePathTemplate` [50].
  - Демон git fsmonitor останавливается при удалении worktree (v1.0.9). Создание worktree ждёт окончания других git-операций в том же проекте (v1.1.35) [62].
- **Удаление.**
  - Worktrees удаляются принудительно. Незакоммиченная работа сначала сохраняется в recovery ref (служебную git-ссылку); вернуть её — ручная git-операция (v0.2.21) [62].
  - Снимки checkpoints, сохранённые внутри репозитория, при удалении стираются (v1.4.0) [62].
  - Исправлены две ошибки с потерей данных: принудительно удалялась незапушенная ветка (v0.2.26); уборка удаляла активный worktree (v1.1.16) [62].
- **Один основной checkout на проект.** В v1.1.5 вторая сессия *Current checkout* в том же репозитории падала с ошибкой «already has an active Local workspace»; сессии с worktree работали [127 #3535]. В Windows v1.1.15 перед новой сессией приходилось архивировать простаивающие [127 #3856]. Оба issue закрыты как исправленные в сентябре 2026.
- **Общие разрешения.** Сохранённые разрешения хранятся по корню git. Связанные worktrees сводятся к основному репозиторию — значит, делят одни разрешения [50].
- **Sandbox.** Local (MXC) и cloud — см. «Функции → Sandbox, безопасность, управление».

### Цикл агента

- Одна итерация цикла — один вызов LLM. Когда остановиться, решает модель [54].
- Событие `session.idle` не сохраняется; `session.task_complete` сохраняется и не обязательно [54].
- **Как заканчивается Autopilot.**
  - Через инструмент `task_complete`.
  - Если цикл кончился без него, CLI вставляет синтетическое сообщение пользователя: продолжай реализацию [54]. `--max-autopilot-continues` ограничивает число автоматических продолжений вне активной цели autopilot (`/goal`), по умолчанию 5 [51].
  - При продолжении сессии режим Autopilot восстанавливается (CLI 1.0.76) [65].
  - Возможное противоречие: CLI 1.0.106 и 1.0.107 упоминают «autopilot completion check», который решает «reviewer verdict» [65], а страница SDK о цикле говорит, что скрытых вызовов нет [54]. Судит ли о завершении отдельный вызов модели — не подтверждено.
- **Hook agentStop** может запретить остановку и заставить сделать ещё ход. После 8 запретов подряд ход всё равно заканчивается [52][53].
- **Goals.** В CLI `/goal` и `/autopilot` задают цель с потолком `--max-ai-credits`. На потолке цель встаёт на паузу; новое значение открывает новое окно credits на полную сумму, а не добавку [51]. В приложении `/goal` есть с v1.1.15, но потолок credits для него в документации приложения не описан (не подтверждено) [62 v1.1.15].
- **Без человека.**
  - Autopilot сам отвечает на вопросы агента (v1.1.35) [62]. Фоновые Autopilot-сессии сами отвечают на `ask_user` (CLI 1.0.107) [65].
  - При ручных подтверждениях Autopilot отклоняет всё, что требует подтверждения [21]. При Assisted отказ и его причина возвращаются агенту [28]. С CLI 1.0.106 Autopilot с Assisted не останавливается на запросах подтверждения [65].
  - «Сначала план, потом Autopilot»: `--plan --mode autopilot` или переменная `COPILOT_PLAN_THEN_AUTOPILOT` [51].
  - Координатор может утвердить план дочерней сессии вместо человека (v1.0.10) [62].

### Параллельность и координация

- **`/orchestrate`** (v0.2.33, 2026-06-16) раздаёт работу дочерним сессиям [13][62].
  - Координатор запускает локальных или облачных детей инструментом `create_session` [62].
  - Надзор: `notify_on_idle` (v0.2.26); родителю сообщают, когда план ребёнка ждёт утверждения (v1.1.8); отсоединение ребёнка прекращает автоматический надзор (v1.1.23); вопросы ребёнка остаются в ребёнке (v1.3.0) [62].
  - Прерванного координатора с детьми можно продолжить из боковой панели (v1.1.27). Overview показывает статус, todos, PR и dev servers каждого ребёнка (v1.1.30, v1.1.31) [62].
  - При Assisted дети наследуют разрешения родителя (v1.2.0) [62]. Сообщение пользователя от 2026-11-09: дети координатора с «approve all» работали с ручными подтверждениями и встали [127 #5589].
  - Открытое сообщение пользователя: режим оркестрации принимает служебные сообщения координации за указания пользователя и не сходится к результату [127 #5681] (прочитан только заголовок).
  - Toub запускал через координатора 15 дочерних сессий семью пачками, все в Autopilot [119].
- **`/fleet`** — параллельные subagents, у каждого своё context window; `/tasks` показывает их [44][45].
  - В SDK координация идёт через инструмент `task` и SQL-таблицы `todos` и `todo_deps`. Todo проходит pending → in_progress → done или blocked [56].
  - Оркестратор проверяет работу subagents (CLI 0.0.412) [65].
  - Работают ли исполнители `/fleet` в одном checkout — не подтверждено. Совет SDK избегать пересекающихся файлов говорит, что да [56].
- **Фоновые агенты:** инструменты `read_agent`, `write_agent`, `list_agents` [65].
- **Dynamic workflows** (2026-10-01) — процесс, записанный кодом внутри Copilot extension; subagents наследуют разрешения сессии [46][87]. Внутренние имена раньше: Agent Factories и Software Factories (v1.1.23–v1.1.24) [62].
  - Потолки: одновременные агенты, всего агентов, время работы, примерные credits [46][47].
  - Остановленный потолком запуск сохраняет результаты. Перезапуск ручной: *Resume* или *Resume with limit…*. Отменённый запуск продолжить нельзя [47].
- **Расписание.** В CLI `/every` и `/after` срабатывают, только пока сессия запущена; `/after`, чей срок прошёл при закрытой сессии, срабатывает при её открытии [48]. Automations идут локально или в облаке [9][10].

### Проверка качества

- **До PR.** Агент сам запускает tests [1]. Rubber duck включён по умолчанию [43][62]. Команды `/review`, `/security-review`, `/spar` [12]; у агентов review настраиваются модель и усилие (v1.1.15) [62]. Уровни Copilot code review: Lite, Balanced, Max [4][62].
- **Fusion** в шаблоне Cascade проверяет черновик и решает, звать ли модель сильнее; в шаблоне Critique — критика от другого семейства [39][117].
- **Локальная проверка перед PR** (свой run lint и tests как условие открытия PR) — не подтверждена. Проверка держится на tests, которые запускает агент, на критиках и на CI.
- **CI.** Панель checks и `/pr-fix-checks` [4][12]. Дальше — Agent Merge (см. «Функции»).
- **Automations.** Изменения несут обоснование и оценку уверенности; неуверенные ждут review [11].

### Состояние и память

- **Compaction** (сжатие истории) начинается примерно на 80% context window; на 95% работа встаёт на паузу. Используются пронумерованные checkpoints. Вывод инструмента больше 20 KiB уходит в файл [40]. В SDK есть опция `infiniteSessions` [55].
  - Сообщение пользователя: compaction ломала сессии, чьи запросы превышали лимит 5 МБ [127 #2437] (прочитан только заголовок).
- **Что сохраняется.** История, `plan.md` и файлы — да; ключи провайдеров — нет. Блокировки сессии (защиты от двух одновременных писателей) нет [55]. Сессии по умолчанию синхронизируются в аккаунт GitHub (`remoteExport`) [49].
- **Copilot Memory** хранит факты о репозитории со ссылками на источник и голосованием. Факты по умолчанию живут 90 дней; для репозитория срок настраивается от 7 до 180 дней [41].
- **Dreaming** — фоновая чистка памяти; правки instructions приходят как PR [42].
- **Отчёты по прошлой работе:** `/chronicle`, включая `/chronicle standup` [12]. Своя память у Project [7].

### Восстановление после сбоев

- Если CLI упал во время вызова инструмента, ход помечается прерванным, сессия предлагает продолжить (v1.1.35) [62].
- Автоматическое переподключение и кнопка *Retry now* (v1.2.0) [62].
- Повтор ответа другой моделью (v1.1.24); правка сообщения и откат (v1.0.20) [62].
- Автовосстановление daemon в WSL (v1.1.29) [62]. Keep awake в приложении [62]; `/keep-alive` в CLI [51].
- Повторы запросов к своему провайдеру модели и временных сбоев действий с PR [62 v1.4.0, v0.2.31].
- Восстановление локальной базы, recovery ref перед удалением worktree, пинг и перезапуск общего процесса CLI — см. «Архитектура» и «Изоляция».
- Отката на прошлую версию приложения нет. Ручной downgrade не работает: старая сборка не читает данные новой (сообщение пользователя) [127 #3595].

### Лимиты и стоимость

- **Какие лимиты есть.**
  - Помесячные AI Credits со сбросом 1-го числа [29].
  - Rate limits. CLI различает «session rate limit» и «global rate limit» (формулировка с CLI 1.0.34) [65].
  - `/usage` показывает полосы session limit и weekly limit (CLI 1.0.52, 2026-05-23). Предупреждения на 75% и 90% weekly limit (CLI 1.0.32), затем на 50% и 95% (CLI 1.0.33) [65].
  - Приложение показывает weekly limit в кольце расхода (v1.1.35) и баннер с обратным отсчётом (v1.1.0) [62].
- **Длина окон — не подтверждена.** Цифры «5 часов» нет ни в одном прочитанном источнике. Есть раздел справки `copilot help limits` (CLI 1.0.108); он не прочитан [65]. Заметки расходятся:
  - по одной, у Copilot нет 5-часового окна, только помесячные credits [104];
  - по другой, в апреле 2026 были session и weekly token limits, и после session limit надо было ждать сброса окна; остались ли они после перехода на credits 2026-06-01 — не подтверждено [103];
  - при этом в ноябре приложение показывает weekly limit [62 v1.1.35].
  - Сообщение пользователя от мая 2026: session и weekly limits блокировали работу, хотя 95% месячного объёма не было потрачено [127 #381].
- **Что подтверждено при упоре в лимит.**
  - Временный rate limit: сессия ставит сообщения в очередь и повторяет их сама (CLI 1.0.32, 2026-04-17); ответ, оборванный перегрузкой провайдера, повторяется с backoff (1.0.102); вложения переживают повторы (1.0.107) [65]. Учёт Retry-After в CLI 1.0.100 относится к обновлению списка сессий, а не к повтору запросов к модели [65].
  - Смена модели вместо ожидания: диалог предлагает перейти на Auto, теперь «Copilot Fusion mode» (CLI 1.0.108, 1.0.109) [65]. Настройка `continueOnAutoMode` делает переход автоматическим (CLI 1.0.35) [50][65]. Не работает для global rate limit и для своего провайдера модели [50]. Приложение перестало предлагать переход при global limit (v1.1.34) и перестало молча переводить BYOK-сессии на Auto (v1.0.16) [62].
  - Исчерпанная квота и потолок расходов: об ошибке сообщают, повтора нет (CLI 1.0.107) [65].
  - Agent Merge встаёт на паузу до сообщения пользователя или возврата квоты (v1.1.34) [62]. Это единственное подтверждённое автоматическое продолжение после лимита в приложении. Сообщение пользователя: проверка Agent Merge упала с HTTP 402 `quota_exceeded` — значит, проверки тратят квоту [127 #555].
  - В CLI goals встают на паузу на своём потолке credits [51]. Dynamic workflows останавливаются на потолках и ждут ручного *Resume* [47]. У cloud automations потолки на запуск (минимум 30 credits), день, неделю, месяц; у local automations потолков нет [9].
  - Ожидание сброса подтверждено ровно один раз: массовое удаление cloud-сессий ждёт сброса rate limit и потом доделывается (v1.1.35) [62]. Это служебная операция.
- **Не подтверждено:** чтобы Autopilot, goal, Project или workflow сами ждали сброса session или weekly окна и потом продолжали. Этого нет в документации и в changelog до v1.4.0 [62][65]. Пользователи описывают остановки [127 #772, #3113].
- **Потолок credits на сессию** (public preview, только CLI и SDK) — отдельная функция с похожим названием:
  - `/limits set max-ai-credits N` (минимум 30) — мягкий потолок, проверяется после каждого ответа модели [34];
  - интерактивная сессия просит поднять потолок и может продолжить; неинтерактивный запуск заканчивается [34];
  - в SDK событие `session_limits_exhausted.requested` ждёт решения пользователя; потолки считаются по «accounting window» [35][57]; сбрасываются по `/clear` (CLI 1.0.66) [65];
  - справочник команд CLI описывает `/limits set max-ai-credits` и `--max-ai-credits` иначе: мягкий лимит на один ответ, который сбрасывается с каждым сообщением пользователя [51]. Страница о лимите сессии [34] и справочник [51] расходятся.

### Права и безопасность

- **Режимы прав:** Ask every time, Assisted, Approve all [3][28].
  - Assisted — судья-LLM, модель выбирается автоматически [28]. Включён для всех в v1.1.31; с v1.1.35 ему можно дать личные instructions (объявлено 2026-11-06) [62][101].
  - Для cloud-сессий настройки прав недоступны [28].
  - Действуют enterprise managed settings [28]. С CLI 1.0.88 они покрывают и режим ACP, хосты AHP и сессию `--server` [65].
- **Automations:** инструменты по принципу наименьших прав; события от пользователей без права записи игнорируются; PR от shared automations требуют отдельного подтверждения [10].
- **Остальное.** Computer use спрашивает разрешение перед управлением приложением [91]. Инструменты браузера — только во вкладках, отданных агенту (v1.1.27) [62]. Конфиг репозитория — только после проверки пользователем [14]. Remote control требует политики *View and control* [22]. Sandbox — см. «Функции».
- **Регресс в extensions:** в 1.1.31 чаты потеряли инструменты `extensions_reload` и `extensions_manage` (сообщение пользователя) [127, список по голосам].

- Пробные $200 credits на приложение, которые пользователи не могли увидеть или потратить, — не подтверждено источником GitHub [127 #1242, #1249, #1250, #1256, #1258][128 #1234].

- **Один runtime.** Только агенты Copilot. Нельзя запустить Claude Code или Codex CLI и нельзя использовать имеющиеся подписки Claude или ChatGPT; запросы закрыты ботом [127 #2366, #120, #1137][23].

- **Стабильность.** Частые автообновления с регрессиями в создании сессий; отката нет [127 #3530, #4358, #5690, #3595].
- **Ресурсы.** Простаивающие сессии держат процессы (около 18 ГБ на Windows) [127 #4979]; большой журнал сессии не открывается [127 #3119]; compaction ломалась на больших запросах [127 #2437].

- **Agent Merge** тратит квоту на каждую проверку и может ошибаться в готовности PR [127 #185, #555, #4509, #935]. Облачная версия не отвечает на review comments и не работает со stacked PRs и fork [6].
- **Потолки расходов только у cloud automations,** у local — нет [9]. Prompts и логи cloud automations видны всем с правом чтения репозитория, даже у personal [9].
- **Обратная связь.** 2 358 из 4 140 закрытых issues — «not planned», многие закрыты ботом без ответа [64][128 #4684].
- **Локальной проверки перед PR** (своего run lint и tests как условия) не найдено; опора — tests агента, критики и CI.
- **Пространственного холста нет:** Canvas — панель сбоку [8].
- **Вымарывания личных данных на screenshots нет;** Streamer Mode только скрывает расход и модели [62].
- **Видимость работы без человека:** молчаливые паузы, поток уведомлений, плохо видно subagents [129 #199979][127 #4659, #2014, #371].
- **Не-GitHub remotes:** PR открывать нельзя [127 #2009]. Локальные репозитории в Projects — нельзя [127 #5175].
- **Не найдено:** профилей браузера, связи машин по локальной сети (только SSH, WSL, Codespaces, облако), файлов tickets и epics, советника по продукту с mind map и критиком specs, планирования запусков под окна лимитов.

## Механизмы, которые стоит изучить

1. **Agent Merge — фоновый цикл «PR до merge».** Включается вручную на один PR. Сессия по таймеру (по умолчанию раз в 10 минут) и по событиям GitHub — завершение CI, новый review comment — проверяет checks и состояние PR. Она чинит упавшие workflows и конфликты, отвечает в ветках комментариев reviewer и закрывает их, делает merge, когда GitHub разрешает, и выключается. Переживает перезапуск; обязательная проверка без отчёта считается pending; если GitHub отклонил merge из-за ещё не выполненных правил, Agent Merge остаётся включённым. При исчерпанной квоте встаёт на паузу до сообщения пользователя или возврата квоты; opt-in настройка keep-awake не даёт компьютеру уснуть. Цена: каждая проверка — вызов модели, что пользователи критикуют [4][119][62 v0.2.6, v0.2.33, v1.1.5, v1.1.8, v1.1.31, v1.1.34][127 #185, #555].
2. **Контракт завершения Autopilot.** Агент заканчивает работу только вызовом инструмента `task_complete`. Если цикл закончился без вызова, CLI вставляет синтетическое сообщение «продолжай». Вне активной цели (`/goal`) число таких продолжений ограничено (`--max-autopilot-continues`, по умолчанию 5). Hook agentStop может запретить остановку, но после 8 запретов подряд CLI всё равно заканчивает ход (с CLI 1.0.72) [54][51][52][53][65].
3. **Goal с потолком credits и Goal pill.** В CLI `/goal` задаёт долгую цель с `--max-ai-credits`. На потолке цель встаёт на паузу; новое значение открывает новое окно credits на полную сумму [51]. В приложении метка Goal pill в поле ввода показывает статус (Active, Paused, Done), причину паузы, число ходов и расход [62 v1.1.15, v1.1.17]. Потолок credits для goal в приложении не описан (не подтверждено).
4. **Assisted — подтверждения, которые решает модель.** Судья-LLM пропускает безопасные вызовы инструментов и спрашивает человека о рискованных. В Autopilot отказ с причиной возвращается агенту, и сессия не стоит. Можно дать судье личные instructions; дети наследуют разрешения родителя; запросы на выход из sandbox судья не оценивает [28][62 v1.1.31, v1.1.35, v1.2.0][27][101].
5. **Аккуратный жизненный цикл worktree.** Перед принудительным удалением незакоммиченная работа уходит в recovery ref. Один worktree держится заранее готовым. `.worktreeinclude` копирует нужные неотслеживаемые файлы. Создание worktree ждёт других git-операций проекта; fsmonitor останавливается при удалении; sparse checkout для больших репозиториев [62 v0.2.21, v1.0.9, v1.0.17, v1.1.35, v1.2.0].
6. **Конфиг репозитория с проверкой доверия.** `.github/github-app.yml` хранит instructions, scripts с триггерами и regex `server_ready_pattern`, который ловит запуск dev server и открывает его во встроенном браузере. Файл действует только после того, как пользователь его просмотрел и принял [14]. Повторное принятие после каждого изменения документация требует [14], но changelog v1.1.31 упростил доверие до одного решения на репозиторий [62 v1.1.31]; что действует сейчас — не подтверждено.
7. **Canvas extensions — общая поверхность человека и агента.** Canvas открывает агенту функции (`get_board`, `add_card`, `move_card`), состояние хранит в JSON-файлах, на уровне репозитория расходится через git; каждое extension — отдельный процесс Node, подключённый к сессии через SDK. Рецепт GitHub: явные состояния, видимые решения, сохранение сразу, явные точки утверждения [8][58][113][121].
8. **Потолки у dynamic workflows.** Ограничения на одновременных агентов, общее число агентов, время и примерный расход. Остановленный потолком запуск сохраняет результаты и продолжается вручную — *Resume* или *Resume with limit…*; отменённый — нет. Новый лимит при продолжении — общий на весь запуск, включая уже потраченное, а не новая сумма [46][47].
9. **Обработка rate limit по типам.** Временный limit: очередь сообщений и автоматический повтор; ответ, оборванный перегрузкой провайдера, повторяется с backoff. Исчерпанная квота и потолок расходов: сообщение без повтора. Опционально — автоматическая смена модели (`continueOnAutoMode`), но не при global limit и не для своего провайдера. Массовая операция умеет ждать сброса и доделаться [65][50][62 v1.1.34, v1.1.35].
10. **Local sandbox с fail closed и подменой credentials.** Backend своей ОС (Seatbelt, bubblewrap, processcontainer). В приложении: если ОС не может обеспечить политику, команда не запускается. В CLI на неподдерживаемом хосте sandbox выключается с предупреждением, если enterprise не требует `sandbox.failIfUnavailable`. Инструменты получают подставные credentials, настоящие добавляет локальный proxy [25][26][27][66].
11. **Владение automations и потолки расходов.** Personal — видит и платит автор, действует от его имени; shared — видят все с правом чтения, платит владелец репозитория, действует Copilot; тип не меняется. Потолки на запуск останавливают его, дневные и выше — только новые запуски. Группы automations предлагают правки своих prompts по итогам, человек утверждает [10][9][98][97].
12. **Общий процесс CLI с проверкой живости.** По changelog, несколько сессий работают в общем процессе CLI; перед отправкой приложение пингует процесс и перезапускает, если тот молчит [62 v1.1.31, v1.1.35]. Сообщение пользователя на Windows (v1.1.30) показывает другое: по процессу `copilot.exe --server` на каждую запущенную сессию, и в простое они не освобождаются — около 18 ГБ [127 #4979]. Как сессии распределяются по процессам — не подтверждено.
