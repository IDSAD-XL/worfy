## Модель работы

- **Local, cloud или hybrid.** Hybrid: локальная часть бесплатна, облачные workspaces платные [1].
  - **Local.**
    - Desktop-приложение запускает долгоживущий Go daemon и следит за ним [31].
    - Daemon слушает 127.0.0.1:3001 — только loopback, без аутентификации [31].
    - Данные лежат в SQLite в `~/.ao/data` [31].
    - Документация называет систему локальной, для одного пользователя, построенной вокруг долгоживущего Go daemon
      [31].
    - CLI `ao` — тонкий клиент daemon [34].
    - Локально продукт бесплатен и не требует аккаунта [1].
  - **Cloud (hosted workspaces).**
    - Каждая задача получает облачный workspace с уже склонированным репозиторием [29].
    - Cloud открыт для всех с v0.14.10 (stable 2026-11-06) и больше не требует Developer Mode [29]. Developer Mode —
      режим настроек, в котором видны экспериментальные функции.
    - Раньше облачные sandbox-ы работали на AWS/NodeOps за feature flag [19].
    - На Pro можно подключить свой Coder deployment [1].
    - В Cloud работают только Claude Code, Codex, Cursor и OpenCode [49].
    - Источники расходятся: руководство по Cloud до сих пор пишет, что доступ закрыт [49], а changelog — что Cloud
      открыт для всех с 8 ноября [29].
  - **Свой удалённый host.** VM на Ubuntu 24.04, ставится bootstrap-скриптом, помечен experimental [70][40].
  - **Мобильное приложение-компаньон** подключается к daemon на компьютере или к удалённому host [3].
  - **Установка и каналы.**
    - Файлы: dmg, zip, exe, AppImage, deb, rpm [55][4].
    - Homebrew cask: `brew install --cask agentwrapper/tap/agent-orchestrator` [35].
    - Каналы Stable и Nightly, самообновление [4].
- **Агенты и модели.**

    - FAQ — больше двадцати harness-ов [32];
    - документ архитектуры — 23+ adapters [31].
  - Ревьюерами могут быть 22 из 38 агентов [9][10].

## Функции

Описание собрано по коду на коммите `48709b6a`, документации, changelog и release notes v0.15.0. Если функция есть
только в коде, в preview-сборках или в Developer Mode, это сказано. Session ниже — одна задача: агент, его worktree,
чат или терминал, его PR и вычисленный статус [65]. Worker — агент, который делает одну задачу. Orchestrator — агент,
который раздаёт задачи workers [45].

### Orchestrator-агент и постановка задач

- **Orchestrator на проект.** У каждого проекта один агент-orchestrator. Лозунг сайта: пользователь описывает
  результат, orchestrator ведёт всех агентов [1]. Пользователь видит отдельный чат с orchestrator.
- **Что ему велит system prompt** [80]:
  - только координировать и никогда не править код;
  - для сложной задачи сначала написать короткий план;
  - запускать workers через `ao spawn`, писать им через `ao send`, запускать review через `ao review trigger`;
  - не сливать PR без прямой просьбы.
- **Отчёты workers в чате orchestrator.** С 2026-10-24 отчёты видны в чате orchestrator компактными строками: needs
  you, stuck, done [25].
- **`ao report`** — команда, которой worker сообщает orchestrator о ходе работы [34]:
  - `--checkpoint` — промежуточный отчёт, может ждать доставки до часа;
  - `--needs-input` — нужен человек, доставляется сразу;
  - `--stuck` — агент застрял;
  - `--done` — готово, доставка задерживается на 5 минут.
- **Вкладка Summary** (v0.15.0). Показывает активность orchestrator и выбор аккаунта: orchestrator, который упёрся в
  лимит, может продолжить на другом аккаунте. У облачного orchestrator там же список workers [29][55].
- **Задачи.**
  - Текст задачи — до 100 KiB, раньше было 16 KiB [55].
  - Откуда берутся задачи: New task, проект Scratch (без репозитория), standalone tasks (задачи без проекта), issues
    GitHub или GitLab через intake [38][44].
  - Постоянных объектов плана — epics, tickets, waves — не найдено. План orchestrator живёт в его чате [110].

### Board и статусы sessions

- **Lanes — колонки board.**
  - Колонки строятся из фактов: активность агента, PR, CI, review [1].
  - Статус session вычисляется из сохранённых фактов и никогда не хранится полем [31].
  - Карточки не перетаскиваются руками [1][53][9]. Пользователь жаловался, что карточка осталась «In Review» после
    слияния и сдвинуть её нельзя; причина была в нескольких аккаунтах GitHub [62 #6108].
- **Названия колонок в источниках расходятся:**
  - сайт, по заметке о функциях: Working, Needs you, In review, Ready to merge [1];
  - сайт, README и страница сравнения, по заметке о направлении развития: те же четыре плюс Archive [1][53][9];
  - строки интерфейса: Working, Needs you, In review, Ready to merge, Terminated [106];
  - код: building, validating, in review, ready, archive [110].
- **Статусы карточек:** среди них «Fixing CI failures», «Addressing comments», «Reviewing» [106].
- **Sidebar** (новый дизайн 2026-11-08) [29]:
  - spinner, пока агент работает;
  - сигнал, когда нужен ввод или внимание к CI или review;
  - значки PR и merged;
  - закреплённые проекты.

### Sessions: Chat и Terminal

- **Один controller на session.** Controller — компонент, который сейчас управляет агентом [64][31][36]:
  - Chat работает через ACP drivers, Codex app-server или `claude-agent-acp` для Claude Code. ACP (Agent Client
    Protocol) — открытый протокол, по которому приложение управляет coding-агентом;
  - Terminal UI работает через собственный PTY host на macOS и Linux (PTY — псевдотерминал), через tmux как старый
    запасной вариант и через ConPTY на Windows.
- **Возможности Chat** [11][37]:
  - approvals и структурированные вопросы агента с ответом клавишами 1–9;
  - панель плана и context meter;
  - compaction (сжатие истории) и rollback (откат);
  - правка отправленного сообщения начинает ветку разговора, файлы при этом не меняются;
  - очередь сообщений и steering — добавление указаний в идущий ход агента;
  - side chats (`/btw`) и suggested next messages (готовые варианты следующего сообщения) — они тратят квоту;
  - LaTeX (с 2026-10-27) и Mermaid [26];
  - добавление строк кода или diff в чат по Cmd+L, до 8 вложений в сообщении [11];
  - поиск по всей истории чата [55];
  - полоса «Not sent» с кнопками Retry и Discard [29];
  - «Continue» после прерванной задачи заново отправляет до 8 KiB её контекста в JSON [95].
- **HTML-страницы прямо в чате.**
  - К каждой Chat session подключён скрытый MCP server `ao mcp`, который работает через stdio [82].
  - Он даёт инструменты `html_preview` и `html_render`. При включённом computer use — ещё и его инструменты [82].
  - HTML ограничен 512 000 символов [82]. Интерактивные страницы в чате появились 2026-10-11 [11].
- **Сбои провайдера.** Повторы на стороне провайдера модели показаны как «Reconnecting…». Ход, который молчит
  15 минут, завершается ошибкой [11].
- **Только в Developer Mode:** голосовой ввод на macOS и split panes [29].
- **Terminal.**
  - Переключение Chat ↔ Terminal для Claude Code и Codex [37]. Разговор переносится между режимами, session, worktree
    и владение PR остаются прежними [31].
  - Обычные shell-терминалы с выбором shell [55].
  - Вкладки терминалов показывают логотип агента, spinner и точку сигнала или готовности [29].
  - AO читает заголовки терминалов и замечает агента, запущенного руками во вкладке shell, по процессу на переднем
    плане [31].
  - AI-помощника внутри терминала не найдено [110].
- **Жизненный цикл session.**
  - Архивную session можно восстановить вместе с worktree и разговором [29].
  - Архивные sessions удаляются через 7, 30 или 90 дней — по выбору [11].
  - `ao session top` показывает память по sessions, `ao session history` — прошлые sessions [84].

### Проекты, worktrees, скрипты

- **Типы проектов:** один репозиторий, multi-repo workspace, Scratch, standalone tasks [38].
- **Worktree.** Один git worktree на session, ветка `ao/<session-id>/root` [38].
- **Скрипты.** Setup (`postCreate`) и Cleanup (`preRemove`). Каждый шаг setup по умолчанию ограничен 30 минутами,
  предел настраивается от 1 до 120 минут [38].
- **Окружение.** Переменные окружения и symlinks. Страница Environment маскирует значения. Документация
  предупреждает, что это не хранилище секретов [38].
- **Cues** — сохранённые prompts агента или команды, которые пользователь запускает руками [38].

### PR, CI и review — главный цикл продукта

- **Наблюдение за PR.** GitHub и GitLab опрашиваются по таймеру (polling), webhooks не нужны [31][43].
- **Падения CI.** Падающая проверка уходит session-владельцу: имена проверок, ссылки и хвост log [88][10]. Сообщение
  велит сначала разобрать приложенный хвост log и ссылку, полные logs качать только при нужде, потом исправить и
  сделать push [88].
- **Review comments и конфликты слияния** тоже уходят агенту-владельцу. Повторы отсекаются по сигнатуре [46][47].
- **Без бюджета попыток.** Настраиваемого бюджета повторов нет, текст сообщений про CI не настраивается [47][39]. В
  коде для review comments зашит предел — 3 напоминания на комментарий [88].
- **Переключатели в inspector session** [106]:
  - «Automatically fix CI failures» — отправлять падения CI worker-у по PR этой session;
  - «Automatically fix review comments».
  - По умолчанию оба включены [102].
- **Tracked и linked PR.** Linked PR — только ссылка для справки. AO не следит за его проверками, review, слиянием и
  событиями [106].
- **Захват и обновление PR** [29]:
  - `ao session claim-pr` забирает существующий PR в session;
  - в preview-сборках статус PR обновляется через секунды после push агента;
  - проверки, отменённые новым push, показаны как pending.
- **Карточка PR** — CI со ссылками на упавшие проверки, число нерешённых review threads, причины, по которым слияние
  невозможно [31][64]. Комментарии review видны внутри приложения [11].
- **PR inspector** — детали PR, действия, комментарии и активность в inspector session. PR #7394 слит 2026-11-13 в
  02:42Z, в release notes v0.15.0 его нет [61 #7394][55].

### Агенты-reviewer-ы

- **Что делает reviewer** [85][46]:
  - один общий prompt: корректность, обработка ошибок, безопасность, покрытие тестами, соглашения проекта;
  - тесты не запускает;
  - публикует review типа COMMENT через `gh api`;
  - одобрение reviewer-а AO никогда не становится approval в GitHub.
- **Как запускается review** [46][34]:
  - автоматически — для одной session или для всего проекта;
  - флаг `workersRequestReview` — worker сам просит review;
  - `--rerun --agent` добавляет второго reviewer-а от другого вендора, например Codex проверяет работу Claude Code [9].
- **v0.15.0:** reviewer на Claude работает в Chat и только читает [55].
- **Состояния review в inspector:** Review needed, Not run, Approved, Changes requested, «Latest commit has not been
  reviewed». Действия: Stop review, Archive reviewer [106].
- **Lenses** (разные углы проверки) и ролевые reviewer-ы не найдены [110].

### Merge и stacked PR

- **Сливает только человек.** AO сам не сливает. Сливает пользователь — в приложении или через CLI [10]:
  - команда `ao pr merge <n> --url <url> --expected-head-sha <sha>` [34]. SHA — это head commit, который проверили и
    одобрили. Daemon перед слиянием заново проверяет готовность PR и отказывает, если head изменился [109];
  - методы: squash, merge, rebase [106];
  - другие пользователи могут попросить владельца о слиянии — «Request merge» [106];
  - уведомление «готово к слиянию» приходит на компьютер и на телефон [10].
- Главная страница пишет, что слить может пользователь или orchestrator [1]. Это агент по прямой просьбе человека, а не
  автоматическое правило [80][39].
- **Что мешает слиянию** — интерфейс показывает: Draft, Merge conflict, Checks failing, Changes requested, Review
  required, Unresolved threads [106].
- **Stacked PR** — PR, который построен поверх другого PR [84][106]:
  - `ao spawn --base <branch>` ставит новую работу поверх PR этой ветки;
  - действия интерфейса: «Add to stack»; «New task on this PR» — PR новой задачи нацелен на этот PR; «Merge through
    #N · k PRs» с правилом «If one can't merge, none will»; сообщение «The stack joined the merge queue».
  - В документации и changelog этого нет. Выпущены ли stacked PR — (не подтверждено).

### Работа без присмотра

- **Automations** [39][29]:
  - расписание cron или RRULE (правило повторения из стандарта календарей iCalendar) с часовым поясом;
  - шаблоны: PR review inbox, Daily issue triage, Weekly release notes. Они просят агента сделать отчёт по GitHub без
    изменений;
  - prompt — до 4096 байт;
  - работают в локальном daemon, поэтому компьютер должен не спать;
  - после простоя догоняют не больше 3 пропущенных запусков и никогда не идут внахлёст.
- **Stay Awake** (macOS; в menu bar с 2026-11-03) [28][40]:
  - «Keep this Mac awake» держит Mac и с закрытой крышкой — на MacBook с Apple silicon и macOS 13–27;
  - выключается при заряде ниже 10% или при критическом нагреве;
  - проверено на одном MacBook с macOS 26;
  - ADR 0006 о Stay Awake — в статусе implementation, физическая приёмка ещё не пройдена [75];
  - старую страницу настроек Stay Awake с таймером и Low Power Mode убрали в v0.14.4 [24].
- **Облачные агенты** работают, пока компьютер спит [29].
- **Выход из приложения** останавливает агентов, сворачивание в tray — нет [29]. На macOS закрытие окна оставляет
  daemon и агентов. «Quit Completely» останавливает агентов, но сохраняет историю и worktrees [64].
- **Права** [106][29]:
  - режимы: Use agent permissions, Accept edits, Auto, Bypass. Документация называет первый режим Ask [45];
  - переключатель «Remember for this project» — запомнить режим для проекта [29][110];
  - на Bypass значок щита становится жёлтым [29];
  - политики одобрения на уровне orchestrator не найдено [110].
- **Grok Bot «away mode»** [108]. Grok Bot — шаблон чат-бота, который управляет `ao`; у него skills `ao-rules`,
  `ao-answer` и `ao-status`. В away mode, пока человека нет, он:
  - отвечает на рутинные вопросы агентов;
  - разово принимает approvals низкого и обычного риска;
  - никогда не выдаёт `allow_always`;
  - никогда не принимает approvals высокого риска.
- **Не подтверждено или убрано:**
  - собственный retry ошибок API у Orchestrator — (не подтверждено); в коде автоматического повтора упавших ходов
    не найдено [95];
  - старые сборки (март–май 2026) ставили workers на паузу при лимитах модели, находили зависших агентов, имели
    verification gate и pipelines. В текущем CLI этого нет [11][76].

- **Intake issues** выключен по умолчанию, чтобы workers не запускались без ограничений [44][22]. Нужны два явных
  включения: `AO_TRACKER_INTAKE=on` и правило по assignee в проекте. В issues intake ничего не пишет [44][100].

### Принципы при запуске

1. **Скорость ограничивает человек, а не агенты.** Координация тратит внимание: следить за CI, читать review,
   пересылать ошибки. Цель продукта — убрать человека из этого цикла опроса [111][112]. Сегодня это выражает лозунг
   «Stop babysitting agents. Start merging real work.» [53]
2. **Orchestrator сам — агент**, а не dashboard или скрипт. Он читает код, делит работу, раздаёт её, следит за ходом
   и решает, что дальше [111].
3. **Решает человек, реализуют агенты.** За человеком — архитектура, приоритеты, review на уровне архитектуры,
   конфликты между агентами и спорные решения. За агентами — код, тесты, PR, исправления по review и CI [111][112].
4. **Каждое изменение идёт через PR.** Каждый коммит несёт trailer с именем модели [111][112].
5. **Статус берётся из наблюдаемых фактов, а не из отчётов агента.** Сначала факты брались из JSONL-файлов sessions
   Claude Code [111][113].
6. **Агента должно быть видно, и его можно прервать.** Основатель предпочитал tmux sessions, в которые человек может
   войти, а не subagents, которых запускают и забывают [113].
7. **Отвлекать человека только ради настоящих решений** [111][112].
8. **Всё сменное.** Восемь слотов plugins: runtime, agent, workspace, tracker, SCM, notifier, terminal, lifecycle
   [111][112]. В слотах были, например, trackers GitHub и Linear, notifiers desktop, Slack, Composio и webhook,
   dashboard на Next.js с kanban [111]. Позже от этого принципа отказались — см. «Направление развития».

### Принципы в сегодняшнем продукте

- **Design guide (DESIGN.md)** [65]:
  - читатель — инженер, который координирует несколько sessions агентов;
  - его задача — понять состояние за секунды и точно вмешаться;
  - главный объект — session;
  - обещание продукта — вести нескольких агентов и не терять нить работы;
  - тон — деловой и прямой, без обещания, что доставка изменений даётся без усилий;
  - фиксированный порядок приоритетов: 1) правдивое рабочее состояние и безопасные действия; 2) активная задача
    пользователя; 3) контекст активной session; 4) обзор всех sessions; 5) визуальная отделка;
  - стиль — сначала тёмная тема, минимум украшений;
  - прямо отвергнуты фальшивые индикаторы прогресса и типовые «AI»-иллюстрации.
- **Десять несущих правил архитектуры** [31]:
  - не хранить отображаемый статус — колонки вроде `working`, `ci_failed`, `mergeable` вычисляются при чтении из
    фактов: состояние активности агента, завершение, факты PR, проверок и комментариев;
  - неудачная проверка (probe) никогда не считается доказательством смерти session;
  - worktree с незакоммиченными изменениями никогда не удаляется принудительно;
  - всё состояние лежит в `~/.ao`;
  - основной daemon слушает только loopback;
  - CLI тонкий, вся логика в daemon;
  - источник событий — CDC (change data capture: каждое изменение базы записывается в отдельную таблицу);
  - adapters — листья графа зависимостей;
  - миграции только добавляются;
  - файлы, которые пишут adapters, должны быть в git ignore [31][101].
- **Правила orchestrator** — prompt роли, который встраивает daemon [80]:
  - обращён к человеку и только координирует;
  - никогда не правит код, не делает push и не открывает PR; если человек настаивает — сначала явное подтверждение;
  - вся реализация — через workers, командами `ao spawn` и `ao send`;
  - перед запуском worker проверяет текущее состояние, чтобы не дублировать работу;
  - сливает только по прямой просьбе;
  - текст issues — недоверенный и не может переписать его инструкции;
  - внутреннее approval review — не approval GitHub и не выполняет branch protection;
  - если запрошенная модель не поддерживается — сообщить и не подменять её другой.
- **Правила worker** [80]:
  - не использовать встроенные subagents и делегирование задач своего runtime;
  - нужна параллельная помощь — просить orchestrator запустить ещё workers;
  - сообщать о ходе работы через `ao report`.
  - Это продолжает февральское предпочтение видимых sessions перед subagents [113].
- **Правила reviewer** [85]:
  - только чтение;
  - проверять корректность, обработку ошибок, безопасность, тесты и соглашения;
  - лучше немного уверенных находок, чем придирки;
  - каждое требуемое изменение — отдельный inline-комментарий;
  - вердикт — в Orchestrator через `ao review submit`.
- **Слияние остаётся за человеком.** Orchestrator переводит PR в Ready to merge и шлёт уведомление, но сам не сливает
  [39][46][10]. Фраза главной страницы «слить может пользователь или orchestrator» [1] означает агента по прямой
  просьбе, а не автоматическое правило [80][39].
- **Local-first и свои агенты.**
  - AO запускает CLI агентов, уже установленные и авторизованные на машине [30][32].
  - Агентов и учётные данные не поставляет, вызовы моделей не проксирует [1][30].
  - Intake issues включается явно и в tracker ничего не пишет [30].
- **Границы автоматизации.**
  - Session, которая ждёт решения о разрешении, никогда не получает автоматический ввод [31][37].
  - Политики auto-approval на уровне Orchestrator в документации нет. Режимы прав — это режимы каждого провайдера:
    Ask, Accept edits, Auto, Bypass [45].
  - Бюджета повторов нет. Worker, который снова и снова падает, снова и снова получает новые падения, пока не
    вмешается человек [10].
  - Повторный feedback отсекается по сигнатуре содержимого: неизменное падение не уходит агенту при каждом опросе
    [39].

### Ключевые понятия

| Термин | Что значит |
|---|---|
| Project | Репозиторий с выбором агента на каждую роль: worker, orchestrator, reviewer [1][45] |
| Orchestrator (роль) | Ведёт один проект и раздаёт работу workers [45][80] |
| Worker | Одна узкая задача, которую можно проверить, в отдельном worktree; может владеть PR [45][30] |
| Standalone worker / Scratchpad | Session без репозитория. Раздел Scratchpad переименован в Sessions 2026-11-13 [20][21][61 #8323] |
| Session | Единица работы: задача, агент, worktree, чат или терминал, PR и вычисленный статус [65] |
| Chat и Terminal UI | Один controller на session; совместимые sessions переключаются между режимами [30][33] |
| Board lanes | Working, Needs you, In review, Ready to merge, Archive — вычисляются, не перетаскиваются [1][53][9] |
| Claim PR | Записывает, какой worker владеет PR, чтобы feedback пришёл к нему [39][10] |
| Feedback routing | Упавшие проверки с хвостом log, нерешённые комментарии и конфликты уходят владельцу [39][10] |
| Native reviewer | Reviewer-агент, можно от другого вендора; его approval только внутренний [46] |
| Report / Artifact / `ao render` | Отчёт worker-а orchestrator-у; готовые файлы; HTML-страницы в чате [83][26] |
| Automations / Cues | Повторяющиеся prompts по cron или RRULE; сохранённые prompts или shell-команды [39] |
| Connect Mobile / LAN Listener / Pairing QR | Listener для телефона: включается явно, защищён паролем [66] |
| Remote host / Machines | Другой компьютер или VM, привязанные к аккаунту [9][76] |
| Stay Awake | Не даёт Mac уснуть, пока работают агенты [24][28] |

### Как вендор объясняет отличие

- **Над отдельными инструментами.** AO стоит над агентами, которые у пользователя уже есть, и не меняет его workflow
  [1].
- **Против встроенных функций Claude Code** [9]:
  - встроенных worktrees, agent view и agent teams хватает на 2–3 sessions Claude;
  - AO — для момента, когда sessions больше, чем внимания;
  - AO добавляет автоматическую доставку CI и review агенту, reviewer-а от другого вендора, разных агентов на одной
    board, телефон, родной Windows и свои серверы.
- **Что значит «autonomous PRs»** [10]:
  - инструмент замечает сбои и направляет их агенту, агент чинит, человек решает о слиянии;
  - таблица вендора: у Orca и Conductor — исправление в один клик, у Superset, Emdash и Nimbalyst — вручную, у
    Orchestrator — полностью автоматическая доставка в session-владельца.
- **Comparison hub** — около 25 страниц сравнений и альтернатив: Orca, Paseo, T3 Code, Happy, Paradev, Conductor,
  Emdash, Nimbalyst, Claude Squad, Codex app, Cursor, Omnara, Vibe Kanban, AgentsMesh [8].

### Чем подход отличается

- **Статус вычисляется, а не хранится.** Для приложения одного пользователя здесь очень много инженерии надёжности:
  CDC, отдельные процессы-host-ы агентов, номера поколений controller, outbox [31][73].
- **Orchestrator — обычная session агента с prompt.** Отдельного движка планирования и графа задач нет [80].
- **Workers запрещено использовать subagents.** Параллельность — только через новые видимые sessions [80][113].
- **Нейтральность к агентам.** Много CLI разных вендоров на одной board [1][41].
- **Нет локальной проверки перед PR.** Цепочка такая: самопроверка агента по prompt → удалённый CI → reviewer-агент →
  слияние человеком [80][39].
- **Feedback без бюджета попыток.** Для CI повторы ограничены только сигнатурой: новое падение снова уходит агенту
  [88][10].

### Цикл агента

- **Своего цикла модели нет.** Каждая session запускает установленный CLI агента со входом пользователя [1][38].
  Режимов интерфейса два, и в каждой session ровно один живой controller [31].
- **TUI mode.**
  - Агент работает в отсоединённом PTY host на macOS и Linux, в ConPTY на Windows. tmux — старый запасной вариант
    [31].
  - PTY host использует один протокол кадров (framing) на всех ОС [93].
  - Claude Code запускается с `--session-id <uuid>` — чтобы потом продолжить разговор; с `--permission-mode` или
    `--settings defaultMode`; с `--append-system-prompt-file` — постоянным prompt AO [92].
- **Активность агента в TUI определяют hooks** [91]:
  - AO пишет свои hooks в `.claude/settings.local.json` внутри worktree session, в виде `ao hooks claude-code <event>`;
  - события: SessionStart, UserPromptSubmit, Pre/PostToolUse, PostToolUseFailure, PermissionRequest, Stop,
    StopFailure, Notification, SubagentStart/Stop, SessionEnd;
  - соответствие состояниям: PermissionRequest → `blocked`; Stop и StopFailure → `idle` (StopFailure — это лимит
    расхода, истёкший вход или ошибка сервера); `agent_needs_input` → `waiting_input`;
  - правило старшинства: события параллельных subagents не снимают живое состояние `blocked`;
  - для Codex есть такой же набор hooks.
  - Reconciler раз в 30 секунд: если данные hooks старше 2 минут, он читает последние 40 строк терминала и поправляет
    состояние [93].
- **Chat mode.** Терминала нет, AO говорит с агентом по протоколу [64][94]:
  - `codex app-server` для Codex;
  - ACP для Claude Code — через закреплённый пакет `@agentclientprotocol/claude-agent-acp` 0.70.0, который AO
    поставляет сам и направляет на `claude` пользователя;
  - ACP для Cursor, OpenCode, Droid, Kimi, Qwen, Copilot и других.
- **Отдельный процесс-host на каждую Chat session** (ADR 0003). Daemon — единственный клиент host-а, но не его
  родительский процесс [73]:
  - host слушает loopback и пускает только по 256-битному ключу, который лежит в файле с правами 0600;
  - хранит буфер кадров провайдера на 32 MiB и ACP journal на каждый prompt до 256 MiB;
  - неотвеченные запросы approval переживают перезапуск daemon;
  - ID запросов перенумеровываются выше отметки максимума, чтобы не пересечься со старыми.
  - Итог: ход агента в процессе переживает закрытие desktop и перезапуск при обновлении [73].
- **Переключение между TUI и Chat.**
  - Durable drain или interrupt handoff переносит один разговор Claude Code или Codex между режимами. Session,
    worktree и владение PR не меняются [31].
  - Защита от двух controller-ов сразу: номер поколения controller, compare-and-swap (атомарная замена при
    совпадении) строки session и outbox — очередь, которая держит сообщения lifecycle на время переключения [31].
  - Перенести между режимами вызов инструмента, который идёт прямо сейчас, нельзя [64].
- **План в Chat.** AO включает инструменты to-do у Claude и велит вести план через TaskCreate/TaskUpdate. Так
  заполняется панель плана в чате [94].

### Orchestrator: планирование и разбиение задач

- **Обычная session агента с постоянным system prompt**, а не отдельный движок планирования [80].
- **Инструменты — команды shell** [80]:
  - `ao status`, `ao session ls/get`;
  - `ao spawn --project … --name "<метка до 100 символов>" --prompt …|--issue …`, по желанию `--agent` и `--model`;
  - `ao send`, `ao session claim-pr`, `ao session kill`;
  - `ao review trigger/ls`.
- **Порядок координации записан текстом в prompt** [80]: посмотреть состояние → найти владельца задачи → запускать
  worker, только если подходящего нет → следить за PR, CI и review → возвращать сбои владельцу → подводить итог
  человеку.
- **Графа задач и модели зависимостей не найдено.** Разбиение идёт внутри рассуждений модели. Единственная
  структурная зависимость — stacking PR: `BaseBranch` начинает ветку от родительского PR и нацеливает на него; prompt
  worker учит именовать ветки для стеков [80][81].
- **Инструкции и факты проекта.**
  - Правила проекта добавляются в prompt: `agentRules[File]` — для workers, `orchestratorRules[File]` — для
    orchestrator. Пути файлов проверяются: они должны быть внутри репозитория [80][38].
  - Каждый prompt несёт ссылку на встроенный skill `using-ao`. Daemon устанавливает его в свою папку данных при
    каждом старте. Инструкции передаются файлами, а не через MCP server [82].
  - Chat sessions дополнительно получают `ao mcp` — stdio MCP server. Он даёт только preview и render HTML и, по
    желанию, инструменты computer use через Cua Driver [82].
  - Adapters вкомпилированы, marketplace нет [34][42].
- **Запуски без orchestrator.**
  - Intake issues: один worker на каждый подходящий issue GitHub или GitLab. Проверка раз в минуту, после сбоя пауза
    5 минут, prompt — до 16 KiB. Нужны и `AO_TRACKER_INTAKE=on`, и правило в проекте. В issues intake ничего не пишет
    [100][38]. Для сравнения: предел текста задачи в v0.15.0 поднят с 16 KiB до 100 KiB [55], а предел prompt
    intake в коде на коммите `48709b6a` — 16 KiB [100].
  - Automations — по cron или RRULE. После перезапуска догоняют не больше 3 пропущенных запусков. Запуск никогда не
    идёт внахлёст с предыдущим. Компьютер должен не спать [39].

### Параллельность и координация

- **Запуск worker** — сначала строка session, потом workspace, потом controller [31]:
  - название и slug ветки генерирует в фоне сам агент: срок 20 секунд, не больше четырёх вызовов;
  - ветка начинается как `ao/<session-id>/root` и переименовывается в `ao/<slug>/root`, только если её ещё не
    отправили push-ем;
  - локального предела числа sessions в коде не найдено. Сайт обещает неограниченное число локальных агентов на Free
    [1].
- **Отчёты worker → orchestrator через `ao report`** [96]:
  - `--needs-input` и `--stuck` доставляются сразу;
  - `--done` открывает фиксированное окно в 5 минут, чтобы собрать завершения пачкой;
  - `--checkpoint` доставляется через час или вместе со следующим ходом orchestrator;
  - отчёт `stuck` может прервать идущий ход Chat orchestrator не чаще раза в 3 минуты на каждого worker;
  - если в поле ввода orchestrator лежит неотправленный черновик человека, доставка повторяется через 30 секунд.
  - Открытый issue #6613 (2026-10-12) просит отдавать `done` раньше, если других активных workers нет [62 #6613].
- **Очередь сообщений в Chat** [31]:
  - пока ход идёт, сообщения хранятся в SQLite;
  - каждое набранное человеком сообщение получает свой ход;
  - соседние сообщения от агентов и orchestrator (сообщения агентов, комментарии review, уведомления о конфликте)
    склеиваются в один ввод для провайдера;
  - «Steer» добавляет указание в идущий ход;
  - пачки AO не обрезает.
- **Все автоматические записи в TUI проходят через `sessionguard`** [90]:
  - guard заново читает session прямо перед вставкой текста;
  - отказывает, если session ждёт ответа на диалог разрешения (завершающий Enter ответил бы на него), если агент
    завершился (в pane теперь может быть shell), если session ещё не стартовала или если в поле ввода черновик
    человека;
  - других путей записи в pane нет.
- **Cloud — та же модель через API** [105]: orchestrator в sandbox вызывает `createWorkerChild`,
  `sendWorkerChildMessage` и `listWorkerChildren`, workers отвечают через `reportToParent`.

### Изоляция

- **Локально контейнера или VM нет.** Агенты работают от имени пользователя прямо на машине [31][38].
- **Worktree.** Session проекта получает связанный git worktree в `~/.ao/data/worktrees/<project>/<session>`. Он
  создаётся командой `git worktree add -b … origin/<default>` [31][48][101]. Scratch и standalone sessions получают
  обычные папки. Проекты типа Workspace выкладывают корневой репозиторий вместе с дочерними [38].
- **Защита git — только в prompt**, принудительной нет. Prompt запрещает `git remote add` и `git config --local` и
  велит использовать `git config --worktree` [80].
- **Служебные файлы.** Файлы, которые пишут adapters, должны быть в git ignore. Adapter worktree дописывает шаблоны в
  локальный для worktree `info/exclude` [31][101].
- **Worktree с изменениями** никогда не удаляется принудительно [31].
- **Docker.** Сам AO контейнеры не запускает. Когда session заканчивается, он принудительно удаляет контейнеры с
  меткой `ao.session=$AO_SESSION_ID`, если у них нет метки `ao.spare=true` [80].
- **Browser.** У каждой session свой Electron `WebContentsView` [31].
- **Setup hooks:** `env`, `symlinks` (секреты по умолчанию не копируются), `postCreate`, `preRemove` [38].
- **Cloud** [105][67]:
  - облачные sandbox-ы; контракт называет провайдерами Coder (включая свой Coder) и Freestyle, Docker упоминается для
    очистки;
  - Daytona и NodeOps есть в перечне провайдеров, но их роль (не подтверждено);
  - workers сами подключаются к control plane; токены защищены номером эпохи, попытки хода закрепляются за
    исполнителем;
  - control plane — в закрытом репозитории.

### Состояние и память

- **Хранение.** Всё — в `~/.ao` [31][64].
- **CDC.** Triggers базы пишут каждое изменение в таблицу `change_log`. Poller читает её каждые 100 мс и рассылает
  события подписчикам и в SSE-поток `GET /api/v1/events` (SSE — server-sent events, поток событий от сервера по HTTP).
  После обрыва клиент получает пропущенное по `Last-Event-ID` [31][93].
- **Основные таблицы** [31]: projects, sessions, conversations (turns, messages, activities),
  `session_interface_transitions` и outbox сообщений, `pull_requests`, `pr_checks`, `pr_review_threads`,
  `pr_comments`, notifications.
- **Дедупликация напоминаний переживает перезапуск**: сигнатура хранится как JSON в `pr.last_nudge_signature` [88].
- **Флаги по умолчанию** [102]: `auto_inject_ci` и `auto_inject_review` — TRUE; `terminate_on_pr_merge` — FALSE,
  поэтому session живёт и после слияния.
- **Долгой памяти нет.** Отдельного хранилища памяти или базы знаний в документации и коде не найдено [39][38].
  Пользователи жалуются, что агенты в разных sessions заново узнают одни и те же факты о проекте [63 #1267].
- **Разговор orchestrator принадлежит проекту.** Он переживает отдельные sessions orchestrator. Новая session
  вставляет явную границу «context reset», а не делает вид, что продолжает тот же разговор [95]. Пользователь жалуется,
  что очистить контекст orchestrator в приложении непросто [63 #6913].
- **История worker** — своя у каждой session [95].
- **Compaction делает сам провайдер.** AO показывает её в Chat и может выставить окно auto-compact Claude Code в 200k
  или 1M токенов [64][81].
- **Прерванные задачи.** «Continue» заново отправляет до 8 KiB контекста прерванной задачи в JSON [95].
- **Side chats и prompt suggestions** работают в отдельных родных копиях разговора (fork; у Codex — только чтение) и
  никогда не пишут transcript в базу [31].
- **Спящий Chat.** Если ход завершён и вид Chat не открыт, host провайдера можно остановить; при нужде он продолжает
  разговор родным resume. Только в Developer Mode [31].

### Проверка качества

- **Цепочка:** самопроверка агента по prompt → удалённый CI → reviewer-агент по желанию → слияние человеком.
- **Локальной проверки AO не требует.** Workers получают указание запустить узкую проверку и сделать push [80].
  Шага tests, который бы проверял daemon, нет.
- **Наблюдение за SCM** (`observe/scm`) [89]:
  - опрос раз в 30 секунд, review threads — раз в 2 минуты, принудительное перечитывание — через 5 минут, запросы
    GraphQL пачками по 25;
  - защита по ETag и сравнение по смыслу (semantic diff);
  - объект опознаётся по ID провайдера: node ID в GitHub или global ID merge request в GitLab;
  - курсор никогда не уходит дальше наблюдения, которое ещё не записано;
  - лимиты запросов GitHub превращаются в структурные паузы [89][95];
  - вход в GitHub: сначала `AO_GITHUB_TOKEN`, потом `gh auth token`;
  - PR привязываются к sessions по автору и по пространству имён ветки.
- **Реакции** (`lifecycle/reactions.go`) [88]:
  - **падение CI**: сообщение со списком упавших проверок, их URL и последними 20 строками log каждого упавшего job,
    без управляющих символов. Повтор отсекается по сигнатуре: имя, коммит, статус, URL, хвост log. Предела попыток
    нет, поэтому падение на новом коммите снова уходит агенту;
  - **комментарии review**: одно напоминание на каждый нерешённый комментарий, не больше 3 попыток на комментарий.
    Так же для review с changes requested;
  - **конфликт слияния**: «срочное» напоминание, только нижнему PR стека. Может прийти в session, которая ждёт ввода
    у prompt, но никогда — в session с диалогом разрешения;
  - каждое условие стоит в своей очереди, одно не прячет другое;
  - напоминания про CI и review ждут, пока session ждёт ввода.
- **Конец session** [88]: только если включён `terminateOnPRMerge`, слит хотя бы один PR, открытых PR нет и агент не
  активен.
- **Встроенный «adversarial» reviewer** — отдельный агент, который проверяет head PR в workspace worker-а [80][85]:
  - публикует review через `gh api …/reviews` с `event: COMMENT` от аккаунта автора PR. GitHub не даёт поставить
    APPROVE или REQUEST_CHANGES на свой PR;
  - каждое требуемое изменение — inline-комментарий; эти комментарии автоматически уходят worker-у;
  - вердикт reviewer записывает через `ao review submit` с JSON на стандартном вводе, поэтому в worktree ничего не
    пишется;
  - approval AO никогда не становится approval GitHub и никогда не разрешает слияние.
- **Auto-review** (`autoreview`) [86]:
  - раз в минуту проверяет: worker простаивает не меньше минуты, PR не draft, head ещё не проверен, на нём меньше
    3 неудачных автоматических review;
  - CI **не** ждёт;
  - на одном head могут работать несколько reviewer-ов сразу (`--rerun --agent X`).
- **Ограничения reviewer** [87][72]:
  - Claude-reviewer запускается с разрешёнными инструментами Read, Grep, Glob, `printf`, `gh pr view/diff/checks`,
    `git status`;
  - и с запрещёнными `mcp__*`, Edit, Write, `git push/commit`, `gh pr merge`;
  - на всё остальное отвечает hook PermissionRequest — allow или deny, потому что в headless reviewer диалог некому
    подтвердить;
  - ADR 0002 (2026-08-01) добавляет gateway возможностей для интерактивных TUI reviewer-ов, но прямо пишет, что сам
    по себе он не sandbox процесса. Поэтому восемь reviewer-ов помечены как «experimental host-trusted»;
  - открытый issue #3745 — read-only соблюдается не для всех reviewer-ов [62 #3745]. Issue #6962 — reviewer может
    писать файлы через перенаправление вывода shell, несмотря на запрет записи [62 #6962].
- **Слияние** — всегда явное: из desktop или командой `ao pr merge <n> --url … --expected-head-sha <sha>`.
  Автоматического слияния нет [39][46]. Daemon заново проверяет готовность и отказывает, если head изменился [109].
- **Старый verification gate** (март 2026) был [12]. В текущем CLI его нет [76]. Перенесли ли gate и pipelines на Go —
  (не подтверждено).

### Восстановление после сбоев

- **Reaper** раз в 5 секунд. Правило: неудачная проверка — не доказательство смерти. Session завершается, только
  если и runtime, и процесс явно мертвы и недавняя активность этому не противоречит [31][93].
- **Перезапуск daemon.** Chat hosts и отсоединённые PTY hosts его переживают. При старте daemon уничтожает host,
  только когда сохранённое состояние доказывает, что session закончена [73].
- **Прерванное переключение режима** откатывается к последнему зафиксированному режиму. Сообщения outbox
  повторяются с ключами идемпотентности [31].
- **Resume и Restore.** «Resume agent» заново запускает остановленный controller. «Restore» поднимает завершённую
  session через родной resume агента [38][34].
- **Обновление CLI агентов** [71]: AO ставит новые версии рядом со старыми. Sessions, которые простаивают 10 минут,
  переводятся на новый бинарник через родной resume, не больше 4 одновременно.
- **Обычные ошибки API.** Автоматического повтора упавших ходов не найдено. Есть ручной Retry. Единственный
  автоматический повтор — при лимите расхода, см. ниже [95].
- **Известная хрупкость.** Открытый issue #6639 (2026-10-13, Windows, v0.13.7) [62 #6639]:
  - каждый перезапуск daemon переводил sessions в `exited`, и resume, restore и send не работали;
  - отчёты мёртвому orchestrator повторялись больше 13 000 раз без паузы.
- **Следы сбоев.** `lifecyclelog` пишет локальный, очищенный от лишних данных `daemon-lifecycle.jsonl` и crash log Go
  [103][69].

### Лимиты и стоимость

- **Чтение лимитов** [97]:
  - Claude: AO шлёт Claude Code его собственный control request `get_usage` по stream-json. Читает 5-часовое окно,
    7-дневное окно, окна Opus/Sonnet и по отдельным моделям, расход extra usage;
  - Codex: capacity buckets `app-server`, время сброса и reset credits;
  - `AutoResumeResetsAt` вычисляется, только если сброс доказуемо снимает лимит;
  - фоновый ticker записывает показания, история хранится 14 дней [98].
- **Несколько аккаунтов подписки** [97][64]:
  - каждый аккаунт — свой `CLAUDE_CONFIG_DIR` или `CODEX_HOME`;
  - папки истории, skills, plugins, hooks и подобные связаны между аккаунтами ссылками; переменные окружения с
    учётными данными очищаются;
  - AO «never reads a token» — не читает токены.
- **Автоматика лимитов — только в Chat** [98][106]:
  - упавший prompt человека можно взвести на «Auto-resume at reset». Цикл daemon — раз в секунду, 4 worker-а, пауза
    30 секунд — повторяет prompt, когда время сброса прошло. Новое чтение аккаунта может сдвинуть срок только позже,
    не раньше;
  - настройка «Move to another account at a usage limit» (Claude Code и Codex): session через drain transition
    переходит на другой подключённый аккаунт, где есть запас, и prompt повторяется **один** раз. Если запаса нет ни
    у кого или session закреплена за аккаунтом, включается auto-resume при сбросе.
- **TUI sessions.** Лимит виден только как `idle` через StopFailure. Auto-resume для TUI нет:
  `validateUsageLimitSession` требует Chat [91][98].
- **Стоимость** [99][61 #7148]: расход токенов разбирается из transcripts или баз каждого harness-а и оценивается по
  каталогу цен LiteLLM. Страница Usage показывает стоимость, токены и лимиты; на момент слияния PR — только в
  Developer Mode.
- **Потолка трат и планировщика работы под лимиты в коде не найдено** [110]. AO не проксирует модели, счёт выставляет
  провайдер [1].
- **У Cloud свои лимиты плана** [105]: активные и запущенные sandbox-ы, слоты orchestrator, скользящее окно и
  недельные sandbox-hours, ручной сброс.

### Права и безопасность

- **Режим прав по умолчанию.** Если ничего не сохранено, новая session получает **`auto`** [81]. Adapters переводят
  его в уровень авто-одобрения каждого агента; для Claude Code это `--permission-mode auto` [92]. Режим
  `bypass-permissions` включается явно [38].
- **Своей политики одобрения для workers у AO нет.** Исключение — headless reviewer [87].
- **Открытые проблемы с правами:**
  - режим Codex «Default» передаёт флаг Codex, который отключает approvals и sandbox. Интерфейс описывает Default как
    режим, который никогда не спрашивает и где единственная граница — worktree [62 #4840];
  - AO доверяет hooks Codex, закоммиченным в репозиторий. Скрипт hook из репозитория запускается на машине
    пользователя при старте session Codex [62 #3280].
- **Защита от prompt injection** [80][88]:
  - контекст issues подаётся как недоверенный;
  - заголовки PR, комментарии и logs CI очищаются от управляющих символов, прежде чем попасть в pane;
  - workers, которые только проверяют, получают указание не запускать код проекта;
  - публикация требует явного разрешения пользователя или правила: доступные учётные данные сами по себе не дают
    права на push или PR.
- **Сеть** [31][74][66][55]:
  - loopback listener без аутентификации, но с проверкой источника запроса;
  - LAN listener: пароль из 8 символов, который меняется, и блокировка источника после ошибок;
  - доступ телефона из интернета — через Cloudflare quick tunnel; TLS снимается на стороне Cloudflare (ADR 0004,
    2026-08-28);
  - токены на каждое устройство и одноразовые коды сопряжения — с v0.15.0.
- **Исправление 2026-10-24:** раньше чужая web-страница могла открыть shell через daemon [25].
- **Секреты.** Страница Environment — не хранилище секретов; symlinks по умолчанию не копируют секреты [38].
- **Telemetry** [69][103][32][53]: PostHog и Sentry включены по умолчанию в release-сборках. Передаются ID установки,
  имя пользователя GitHub, имена владельцев репозиториев, а после входа в Cloud — email. Код и prompts не передаются.
  Документация сама пишет, что данные не полностью анонимны. Отключается в настройках.
- **Подпись Windows.** Установщики шли без подписи. Issue закрыт 30 августа, но 20 октября пользователь нашёл
  неподписанный установщик v0.14.3, который блокировал Windows Smart App Control [62 #4502]. Chrome блокировал
  загрузку как вирус; maintainer посоветовал выключить Smart App Control [62 #7487].

### Где в цикле человек

- **Агент заблокирован или ждёт** [39][64][104]: session переходит в колонку «Needs you», создаётся постоянное
  уведомление, телефон получает push через Expo. Approvals и вопросы отвечают в Chat или на телефоне. В TUI — в
  терминале; автоматика никогда не печатает в заблокированную session [90].
- **Orchestrator правит код сам** — только после явного подтверждения человека [80].
- **Запуск review** требует согласия пользователя или orchestrator, если не включён `workersRequestReview` [80].
- **Слияние** — всегда действие человека [39].
- **Зоны board:** Working, Needs you, In review, Ready to merge, Terminated [106].

### Наблюдаемость

- **Живые виды** [31][64]: board из фактов, центр уведомлений, поток SSE для обновления клиентов, карточка PR.
- **Запись координации:** отчёты workers — строками в чате orchestrator [25].
- **Терминалы:** AO читает заголовки терминалов и находит агентов, запущенных руками во вкладках shell, по процессу
  на переднем плане [31].
- **Нагрузка:** Diagnostics и `ao session top` показывают память и CPU по sessions [106][84].
- **Отдельной ленты событий одного запуска без присмотра не найдено** — но и отсутствие (не подтверждено) [110].

### Что ругают

#### Первый запуск и настройка — главная причина ухода

- **Непонятно, с чего начать.** В апреле пользователь увидел пустой dashboard и не понял, как запустить агентов
  [63 #1535].
  - Второй поставил сборку для Windows, получил непонятные ошибки проверки и удалил приложение [63 #1535].
  - Около двух месяцев maintainer-ы не отвечали. Первые ответы (июль) пришли не от core team [63 #1535][60].
- В X менее технический подписчик счёл Discord слишком сложным. Член команды предложил созвон один на один для
  настройки [128].
- **Переименование сломало установку.** В июле `ao start` падал с 404: он качал AppImage со старого адреса
  `AgentWrapper` [62 #2427]. Augment отмечает, что npm CLI заморожен на 0.10.0, а старые руководства указывают на
  мёртвые пакеты [145].
- **Telemetry вендора, выложенная в issues:**
  - около 2026-08-11 примерно половина запусков агентов из приложения падала: 700 запрошено, 344 упали. Главные
    причины — нет runtime или бинарника агента и проблемы с ветками git [62 #3873];
  - за 14 дней до 2026-10-22 у 31% установок, которые запускали хоть одного агента, был хотя бы один сбой. Упали 13%
    из 76.6 тыс. попыток запуска [62 #7024].
- **Удержание** (тот же issue) [62 #7024]. Когорта — установки, где первый запуск агента был за 14–45 дней до
  2026-10-22. «Вернулся» — открыл приложение на 7–14 день:

  | Первые два дня | Установок | Вернулись на второй неделе |
  |---|---|---|
  | Без сбоев | 2514 | 17.3% |
  | Сбои и успехи | 1004 | 28.4% |
  | Только сбои | 406 | 9.6% |

  Примерно каждая десятая новая установка за первые два дня так и не запустила агента. Главные препятствия: настройка
  аккаунта Codex, нет бинарника агента, не стартовал компонент чата [62 #7024].

#### Нестабильность в начале; основатель — «не для production»

- **Неделя запуска (февраль), ответы в X** [119]:
  - один пользователь быстро сломал приложение. Он выяснил, что флаг Claude Code для пропуска разрешений фактически
    обязателен, а его агенты зависали вместо того, чтобы реагировать на падения CI;
  - другой встретил много ошибок при запуске sessions Claude. Основатель ответил, что продукт только вышел и тогда
    еле работал;
  - основатель также писал, что когда AO совсем сломан, он чинит его через Claude Code.
- **Апрель.** Пользователь спросил, почему у якобы хорошего framework так много открытых issues. Основатель ответил,
  что не советует запускать на нём production workflows [62 #901].

#### Простаивающие агенты и запросы разрешений

- Discussion в марте: агенты всё время уходят в простой и требуют ручных кликов, это убивает продуктивность
  [63 #533].
- Augment видел, как две из четырёх sessions больше 90 секунд ждали одобрения инструмента. Для тех, кто платит за
  токены, это деньги [145].

#### Неверный статус, ложные сигналы, потерянные sessions — главная тема активных пользователей

- **Sessions застывают в «waiting for input».** Один активный пользователь насчитал 233 таких session и 737 таких
  переходов. Он назвал это главным ограничением скорости для парка из 12 orchestrator и до 18 workers [62 #3738].
- **Ложные сигналы.** Живые sessions без сигнала днями горят красным цветом «Needs you» [62 #5751].
- **Потерянные и мёртвые sessions:**
  - пользователь с шестимесячным стажем теряет orchestrator проекта при каждом выходе или обновлении приложения
    [62 #7907];
  - на Windows каждый перезапуск daemon оставляет все sessions невосстановимыми, а отчёты workers повторяются больше
    13 000 раз без паузы [62 #6639];
  - orchestrator раз за разом останавливается после сна или смены сети [62 #5069];
  - все 14 sessions одного проекта завершились с интервалом около 0.7 секунды без действий пользователя [62 #4948].
- **Утечка file descriptors на macOS в v0.12.0.** Исправление требовало ещё и перезагрузки [63 #3646].
- **Жёсткая kanban-board.** Карточка осталась «In Review» после слияния, руками её не сдвинуть. Причина — несколько
  аккаунтов GitHub [62 #6108].

#### Ресурсы при большом числе агентов

- **Mac на 16 GB со многими проектами** [62 #2523]: grep одного worker-а вырос примерно до 31 GB; оставшиеся серверы
  `next dev` занимали по 5–12 GB.
- **Mac на 8 GB** [62 #3921]: ночной запуск 40–45 workers убил orchestrator, проект пришлось удалить. Второй отчёт —
  то же около 15 workers.
- **Другие проблемы с памятью и CPU:**
  - старый dashboard на Next.js падал по памяти примерно на 4 GB [62 #1935];
  - база в 975 MB давала высокий CPU [62 #3963];
  - ввод тормозил в sessions с длинной историей [62 #6886];
  - буферы терминалов на Windows вырастали примерно до 1 GB [62 #6259];
  - приложение не работало, когда папка данных лежала на NFS [62 #4657].

#### Права и безопасность — всё открыто

- Режим Codex «Default» передаёт флаг Codex, который отключает approvals и sandbox. Интерфейс описывает Default как
  режим без вопросов, где единственная граница — worktree [62 #4840].
- AO доверяет hooks Codex из репозитория: скрипт hook запускается на машине пользователя при старте session Codex
  [62 #3280].
- Reviewer может писать файлы, несмотря на запрет записи, через перенаправление вывода shell [62 #6962].
- **Telemetry** [69]: включена по умолчанию в release-сборках; передаёт имя пользователя GitHub, а после входа в Cloud
  — email. Документация сама пишет, что это не полностью анонимно. Жалоб пользователей на это исследование не нашло,
  но искало ограниченно.

- **Приходят:**

## Слабые места и чего нет

- **Нет структуры плана.** Ни epics, ни tickets, ни waves. Планирование — текст рассуждений модели плюс стеки PR
  [110][80].
- **Нет локальной проверки перед PR.** AO полагается на удалённый CI и reviewer-агента; reviewer тесты не запускает
  [80][85]. Старый verification gate убран [11][76].
- **Один общий prompt reviewer-а**, без lenses и ролей [85][110].
- **Нет бюджета повторов для CI.** Сбоящий worker получает новые падения, пока не вмешается человек [88][10]. Для
  review comments есть только фиксированный предел — 3 напоминания на комментарий [88].
- **Нет своей политики одобрения.** Режимы прав — это режимы провайдеров, по умолчанию `auto` [81][92]. Открытые
  проблемы с небезопасными умолчаниями: Codex «Default» отключает approvals и sandbox [62 #4840]; hooks Codex из
  репозитория запускаются без вопроса [62 #3280]; read-only reviewer-а соблюдается не везде [62 #3745][62 #6962].
- **Автоматика лимитов — только в Chat.** В TUI лимит виден лишь как `idle` [91][98]. Потолка трат и планировщика
  работы под лимиты нет [110]. Автоматический перевод на другой аккаунт — только в `main` [61 #7534].
- **Повтора обычных ошибок API нет** — в коде не найдено, своё повторение у Orchestrator (не подтверждено) [95].
- **Статус ненадёжен при большом числе агентов:** застывание в «waiting for input», ложные «Needs you», потерянные
  sessions, сломанное восстановление на Windows после перезапуска, 14 sessions, убитых разом
  [62 #3738, #5751, #7907, #6639, #4948].
- **Ресурсы при большом числе агентов:** память и CPU на машинах с 8–16 GB [62 #2523, #3921].
- **Первый запуск:** каждая десятая новая установка не запускает агента за первые два дня [62 #7024].
- **Windows:** неподписанный установщик блокирует Smart App Control [62 #4502][62 #7487]; CLI не попадает в PATH
  [62 #5464]. **Linux** — сырой интерфейс, на Arch приходится запускать руками [123].
- **Локальная работа требует, чтобы компьютер не спал.** Automations работают в локальном daemon [39]. Stay Awake
  проверен на одном MacBook, физическая приёмка ADR 0006 не пройдена [40][75].
- **Удалённый доступ ограничен:** удалённый preview — только Chat, terminal и stop [106]; LAN — без шифрования [40];
  Cloudflare снимает TLS у tunnel [40][74]; встроенного relay нет [40].
- **Интеграций мало:** нет Linear, Slack, Discord, webhooks [38][39]; Jira — не найдено (не подтверждено); нет
  marketplace plugins [42].
- **Документация отстаёт:** сверена с v0.13.3 [30]; руководство по Cloud пишет, что доступ закрыт [49].
- **Telemetry включена по умолчанию** и передаёт имя пользователя GitHub [69].
- **Нет долгой памяти.** Агенты заново узнают факты о проекте [39][63 #1267]; контекст orchestrator трудно очистить
  [63 #6913].
- **Риск одного maintainer-а**, по вторичным источникам; там же — агенты, которые больше 90 секунд ждут одобрения
  инструмента [145][146].
- **Сам основатель в апреле не советовал production** [62 #901].
- **Многое новое — в preview или Developer Mode:** Usage, голосовой ввод, split panes [29][107].
- **Независимых подтверждений мало.** Отзывы вендора — в основном от участников проекта [2][60].
- **Жёсткая board:** карточки нельзя двигать руками [62 #6108].
- **Работа без экрана** пропала после переписывания и вернулась только частично — через удалённые hosts
  [63 #2855][62 #3853].
- **Не найдено аналогов функций worfy** (поиск по коду и документации) [110]: ленты событий одного запуска без
  присмотра, как Flight Recorder (отсутствие — (не подтверждено)); Work track; AI-помощника в терминале; Product
  Session с Mind map и критиком spec; Evidence screenshots с privacy scrub; Eco mode.

## Пересечение с worfy

Термины worfy в этом разделе — по описанию worfy:

- Canvas — бесконечное полотно, на котором worfy показывает работу агентов.
- Epic — группа связанных Ticket-ов. Ticket — одна задача.
- Orchestrator — session, которая планирует и раздаёт Ticket-ы.
- Wave — набор Ticket-ов, которые запускаются вместе. Autopilot — запуск Wave-ов без человека.
- Gate — локальный запуск проверок перед PR.
- Harness — plugin, который приносит в Claude Code rules, skills, subagents и hooks.
- Flight Recorder — лента событий запуска без присмотра. Work track — вся работа проекта по дням и неделям.
- Cards — карточки, которые агенты строят на Canvas через MCP server.
- Product Session — продуктовый советник с живым Mind map и критиком spec.
- Linked machines — связанные машины в локальной сети.

### Где пересекаются

- **Worktree на задачу.** AO: свой git worktree на каждую session, ветка `ao/<session-id>/root`, скрипты setup и
  cleanup [38]. worfy: свой git worktree на каждый Ticket.
- **Orchestrator, который планирует и раздаёт работу.** AO: агент-orchestrator только координирует, запускает
  workers через `ao spawn` и никогда не правит код [80]. worfy: Orchestrator session планирует и раздаёт Ticket-ы.
- **PR и CI.** AO следит за PR, CI и review и сам отправляет падения, комментарии и конфликты агенту-владельцу; у
  каждой session есть переключатели [88][106][10]. worfy: PR с CI badges.
- **Reviewer-агенты — частично.** AO: один общий reviewer, по флагу — второй от другого вендора; review типа COMMENT;
  lenses нет [85][46][9]. worfy: reviewer subagents с review lenses.
- **Работа без присмотра.** AO: Automations по расписанию, Stay Awake, облачные агенты, пока компьютер спит
  [39][28][29]. worfy: Autopilot запускает Wave-ы без человека.
- **Ожидание сброса лимита.** AO: auto-resume при сбросе, включается на конкретный prompt, только Chat [24][98].
  worfy: Autopilot ждёт сброса лимитов подписки. Пользователи AO отдельно просили показывать квоты, ждать сброса и
  переключаться на запасного агента [62 #6455, #7160, #7793, #4995].
- **Счётчики лимитов и расхода.** AO: страница Usage (в Developer Mode), chip квоты в поле ввода, прогноз «pace»
  [61 #7148][106]. worfy: счётчики лимитов и расхода и планирование запусков под лимиты подписки. Из планирования у AO
  есть только прогноз «pace» [61 #7148].
- **Встроенный Browser с профилями — близкое совпадение.** AO: браузер на каждую session, временные или именованные
  профили, импорт из Chrome, Firefox и Safari [37][29]. worfy: встроенный Browser с профилями.
- **Hooks и инструкции внутри Claude Code — частично.** AO пишет свои hooks в `.claude/settings.local.json` worktree,
  чтобы видеть активность агента, и встраивает skill `using-ao` и prompts ролей [91][83][80]. worfy: Harness plugin с
  rules, skills, subagents и hooks.
- **Содержимое, которое агент строит через MCP.** AO: скрытый MCP server `ao mcp` с `html_preview` и `html_render` —
  HTML-страницы в чате и галерея Artifacts [82][26]. worfy: Cards на Canvas через MCP server.
- **Другие машины.** AO: удалённые hosts, VM, LAN listener для телефона, постоянные адреса через Cloudflare [40][70].
  worfy: Linked machines в локальной сети.
- **Уведомления.** AO: центр уведомлений, toast, звук, push на телефон [37][3]. worfy: уведомления.
- **Desktop-приложение на Electron для одного пользователя.** AO: локальная часть — для одного пользователя, на
  Electron [31]. worfy: то же.
- **Claude Code и Codex.** AO запускает оба — и в Chat, и в Terminal [41][64]. worfy: sessions Claude Code и Codex
  CLI.
- **Terminal — частично.** AO: shell-терминалы и TUI агентов [37][55]; AI-помощника в терминале нет [110]. worfy:
  Terminal с AI-помощником.
- **PR inbox — частично.** AO: только шаблон Automations «PR review inbox» [39][29]; отдельной страницы inbox среди
  маршрутов desktop нет [107]. worfy: PR inbox.

- **Структура работы.** AO: нет Epics, Tickets и Waves; задачи — свободный текст или issues; план живёт в чате

- **Экран.** AO: board с вычисляемыми колонками, галерея artifacts, HTML в чате [1][26][82]. worfy: бесконечный

## Механизмы, которые стоит изучить

1. **Статус вычисляется из фактов и не хранится; события идут через CDC.**
   - Что это: три стадии — OBSERVE (наблюдать) → UPDATE (записать факты) → DERIVE (вычислить статус и действовать).
     Отображаемый статус — `working`, `needs_input`, `ci_failed`, `mergeable` — не хранится, а вычисляется при
     чтении [31].
   - Как работает: статус собирается из `activity_state`, `is_terminated`, режима session и поколения controller,
     точек переключения TUI/Chat и таблиц PR, проверок и комментариев [31]. Triggers SQLite пишут каждое изменение в
     `change_log`. Poller читает его каждые 100 мс и рассылает подписчикам и в SSE `GET /api/v1/events`. Клиент после
     обрыва получает пропущенное по `Last-Event-ID` [31][93].
   - Чем интересно: колонка board не может отстать от фактов из-за пропущенного обновления поля, а desktop, телефон и
     CLI получают одни и те же события. Ложные сигналы активности это не убирает: пользователи жалуются на «Needs you»
     и застывший «waiting for input» [62 #5751][62 #3738].
   - Источник: [31][93][65].
2. **Агенты переживают перезапуск и обновление приложения.**
   - Что это: процессы Chat и PTY живут в отдельных host-процессах, а daemon только подключается к ним (ADR 0003)
     [73].
   - Как работает: host слушает loopback и пускает по 256-битному ключу из файла с правами 0600. Он держит буфер
     кадров провайдера на 32 MiB и ACP journal до 256 MiB на prompt, сохраняет неотвеченные approvals, перенумеровывает
     ID запросов выше отметки максимума [73]. При старте daemon уничтожает host, только когда сохранённое состояние
     доказывает, что session закончена [73]. Reaper раз в 5 секунд завершает session, только если и runtime, и процесс
     явно мертвы и недавняя активность этому не противоречит [31][93]. Плановое обновление передаёт работу новому
     daemon без остановки агентов [64].
   - Чем интересно: ход агента не теряется при закрытии окна или обновлении. Известное исключение — Windows: по
     issue #6639 перезапуск daemon переводил все sessions в `exited` [62 #6639].
   - Источник: [73][31][93][64].
3. **Один guard на все автоматические записи в терминал агента (`sessionguard`).**
   - Что это: единственная точка, через которую AO печатает текст в TUI агента [90].
   - Как работает: перед вставкой guard заново читает session и отказывает, если открыт диалог разрешения (завершающий
     Enter ответил бы на него), если агент завершился (в pane теперь может быть shell), если session ещё не стартовала
     или если в поле ввода черновик человека [90]. Напоминания про CI и review ждут, пока session ждёт ввода [88].
   - Чем интересно: автоматика не может случайно одобрить разрешение или выполнить свой текст в shell.
   - Источник: [90][88].
4. **Активность агента по hooks и сверка по экрану.**
   - Что это: состояния TUI-агента `blocked`, `idle`, `waiting_input` приходят из hooks Claude Code и Codex [91].
   - Как работает: AO пишет hooks `ao hooks claude-code <event>` в `.claude/settings.local.json` worktree.
     PermissionRequest → `blocked`; Stop и StopFailure (лимит, истёкший вход, ошибка сервера) → `idle`. Правило
     старшинства: события параллельных subagents не снимают живой `blocked` [91]. Reconciler раз в 30 секунд: если
     hooks молчат больше 2 минут, он читает последние 40 строк терминала [93].
   - Чем интересно: hooks дают точный сигнал без разбора экрана, а чтение экрана страхует от потерянных событий.
   - Источник: [91][93].
5. **Возврат feedback агенту-владельцу PR.**
   - Что это: модуль reactions — сообщения агенту о падении CI, о review comments и о конфликте [88].
   - Как работает:
     - CI: имена и ссылки проверок плюс последние 20 строк log каждого упавшего job, без управляющих символов.
       Сообщение велит сначала разобрать этот хвост и ссылку и только потом качать полные logs [88][10];
     - повтор отсекается по сигнатуре — имя, коммит, статус, URL, хвост log. Сигнатура хранится в
       `pr.last_nudge_signature` и переживает перезапуск. Предела попыток нет: падение на новом коммите снова уходит
       агенту [88];
     - review comments: по одному напоминанию на нерешённый комментарий, не больше 3 на комментарий; так же для
       changes requested [88];
     - конфликт: срочное сообщение только нижнему PR стека. Может прийти в session, которая ждёт ввода, но никогда — в
       session с диалогом разрешения [88];
     - каждое условие в своей очереди; CI и review ждут, пока session ждёт ввода [88].
   - Чем интересно: агент получает ровно тот кусок log, который обычно нужен; повторы не идут на каждом опросе;
     конфликт не рассылается по всему стеку.
   - Источник: [88][89][46][47].
6. **`ao report`: срочность сообщений от worker к orchestrator.**
   - Что это: команда и сервис доставки отчётов [96][34].
   - Как работает: `--needs-input` и `--stuck` — сразу; `--done` — окно 5 минут, чтобы собрать завершения пачкой;
     `--checkpoint` — через час или вместе со следующим ходом orchestrator. Отчёт `stuck` прерывает идущий ход Chat
     orchestrator не чаще раза в 3 минуты на worker. Если в поле ввода orchestrator черновик человека, доставка
     повторяется через 30 секунд [96]. Отчёты показываются в чате orchestrator компактными строками [25]. Открытый
     issue #6613 просит отдавать `done` раньше, если других активных workers нет [62 #6613].
   - Чем интересно: у сообщений между агентами есть явная политика срочности и пакетной доставки.
   - Источник: [96][25][62 #6613].
7. **Reviewer с ограничениями и отдельным каналом вердикта.**
   - Что это: reviewer-агент, который не может писать в код и не выдаёт настоящий approval [85][87].
   - Как работает:
     - Claude-reviewer запускается с разрешёнными Read, Grep, Glob, `printf`, `gh pr view/diff/checks`, `git status`
       и запрещёнными `mcp__*`, Edit, Write, `git push/commit`, `gh pr merge`. На остальное hook PermissionRequest
       отвечает allow или deny сам: в headless reviewer диалог некому подтвердить [87];
     - review публикуется как COMMENT через `gh api …/reviews` от аккаунта автора PR — GitHub не принимает APPROVE и
       REQUEST_CHANGES на свой PR. Каждое требуемое изменение — inline-комментарий, который сам уходит worker-у [80][85];
     - вердикт reviewer записывает через `ao review submit` с JSON на стандартном вводе, в worktree ничего не пишется
       [85];
     - auto-review раз в минуту: worker простаивает не меньше минуты, PR не draft, head не проверен, меньше 3
       неудачных автоматических review; CI не ждёт. Второй reviewer другого вендора — флагом `--rerun --agent` [86];
     - ADR 0002 признаёт, что gateway для интерактивных reviewer-ов — не sandbox процесса. Issues #3745 и #6962
       описывают дыры в read-only [72][62 #3745][62 #6962].
   - Чем интересно: approval агента отделён от approval GitHub, а запись вердикта не трогает рабочую копию.
   - Источник: [85][86][87][72][46].
8. **Лимиты подписки читаются у самого CLI; срок auto-resume только сдвигается позже.**
   - Что это: AO берёт лимиты не из своих оценок, а у Claude Code и Codex [97].
   - Как работает: для Claude — control request `get_usage` по stream-json: 5-часовое окно, 7-дневное окно, окна
     Opus/Sonnet и по моделям, расход extra usage. Для Codex — capacity buckets `app-server`, время сброса, reset
     credits [97]. `AutoResumeResetsAt` вычисляется, только если сброс доказуемо снимает лимит [97]. Цикл daemon —
     раз в секунду, 4 worker-а, пауза 30 секунд; prompt повторяется после сброса; новое чтение аккаунта может
     сдвинуть срок только позже, не раньше. История чтений — 14 дней [98]. Работает только в Chat; в TUI лимит виден
     лишь как `idle` [91][98].
   - Чем интересно: время повтора берётся из данных провайдера, а не из догадки.
   - Источник: [97][98][24].
9. **Несколько аккаунтов подписки и перевод session при лимите.**
   - Что это: каждый аккаунт Claude Code или Codex — отдельный `CLAUDE_CONFIG_DIR` или `CODEX_HOME` [97].
   - Как работает: папки истории, skills, plugins, hooks и подобные связаны ссылками между аккаунтами; переменные
     окружения с учётными данными очищаются; токены AO не читает [97][64]. При лимите (настройка выключена по
     умолчанию) session через drain transition переходит на аккаунт, где есть запас, и prompt повторяется один раз.
     Если запаса нет или session закреплена за аккаунтом, включается auto-resume при сбросе [98][61 #7534]. На
     2026-11-13 — только в `main` и nightly [61 #7534, #8310].
   - Чем интересно: skills, plugins и hooks общие для всех аккаунтов, а вход у каждого свой.
   - Источник: [97][98][61 #7534].
10. **Away mode для approvals (Grok Bot).**
    - Что это: шаблон чат-бота, который управляет `ao`, пока человека нет [108].
    - Как работает: отвечает на рутинные вопросы агентов; разово принимает approvals низкого и обычного риска;
      никогда не выдаёт `allow_always`; никогда не принимает approvals высокого риска [108].
    - Чем интересно: политика авто-одобрения с двумя жёсткими границами — только «один раз» и без высокого риска.
    - Источник: [108].
11. **Обновление CLI агентов без остановки работы.**
    - Что это: AO ставит новые версии CLI агентов рядом со старыми [71].
    - Как работает: sessions, которые простаивают 10 минут, переводятся на новый бинарник через родной resume, не
      больше 4 одновременно [71].
    - Чем интересно: обновление CLI не обрывает идущие ходы.
    - Источник: [71].
12. **Слияние только проверенного head и слияние стека «всё или ничего».**
    - Что это: команда merge, которая принимает SHA проверенного commit, и действие для стека PR [34][106][109].
    - Как работает: `ao pr merge <n> --url <url> --expected-head-sha <sha>`. Флаг обязателен: это head commit, который
      проверили и одобрили. Daemon заново проверяет готовность и отказывает, если head изменился; adapters GitHub и
      GitLab передают этот SHA в API слияния провайдера [109]. Для стека интерфейс предлагает «Merge through #N · k
      PRs» с правилом «If one can't merge, none will» и вводом стека в merge queue [106]. Stacked PR есть только в
      коде; выпуск (не подтверждено) [84][106].
    - Чем интересно: между review и слиянием в PR не может проскочить новый commit.
    - Источник: [34][109][106].
