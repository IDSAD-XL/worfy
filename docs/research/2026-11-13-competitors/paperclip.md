- **Одной фразой:** Paperclip — бесплатный (MIT) self-hosted сервер на Node.js с web-интерфейсом, который ведёт «компанию» AI-агентов (Claude Code, Codex, Gemini CLI, OpenCode и других): org chart, задачи, денежные budgets, heartbeats (пробуждения агента для очередного run-а) и approvals человека, который играет роль board (совета директоров) [76][19][1].

**Из чего собрано досье.** Досье собрано из трёх заметок одного исследования: о функциях, о внутреннем устройстве и об отзывах пользователей. Четвёртый угол — направление развития — отдельно не исследовался. Раздел «Направление развития» собран из release notes, roadmap и changelog, которые есть в трёх заметках. Где заметки расходятся между собой или источники вендора противоречат друг другу, в тексте так и написано, с источниками обеих версий.

**Ограничения исследования.**

- Во всех трёх заметках бюджет web-поиска закончился в начале работы.
- Заметки о функциях и о внутреннем устройстве опираются только на первичные источники: сайт, docs, репозиторий, release notes, блог, GitHub API и npm [1][18][75]. Обзоры и новости не собирались. Доклады и посты основателя и инженеров не искались.
- Заметка об отзывах не смогла искать по Reddit, X, YouTube и вебу в целом. Reddit отказывал в загрузке, X отвечал HTTP 402. Она опирается на issues, discussions и PR в GitHub, API Hacker News, сайт, блог и репозиторий вендора, API Discord и npm и на внешние страницы из ссылок в discussions: одно видео YouTube, два пользовательских блога и одну новостную статью [87][189][219][218][84].
- Голоса в GitHub — выборка тех, у кого баг или запрос. Многие сообщения явно написаны с помощью агента. Объём обсуждений говорит о вовлечённости, а не об удовлетворённости [189].

**Термины Paperclip в этом досье.**

- **Company** — единица работы: набор агентов с org chart, целями, задачами и budgets. Одна инсталляция держит много компаний с изолированными данными [76][19].
- **Board** — люди-пользователи. CEO-агент подчиняется board [19].
- **Heartbeat** — одно пробуждение агента: run, в котором агент берёт работу, делает её и отчитывается [19][101].
- **Adapter** или **harness** — мост между Paperclip и средой агента, например Claude Code или Codex [67].
- **Paperclip Runner** — native слой запуска агентов на Rust; заменяет legacy adapters для части агентов [65][90].
- **Issue** — задача. В UI это «task», в API — «issue» [24].
- **Checkout** — захват задачи агентом: в работе задачу держит только один агент [19].
- **Routine** — запуск по расписанию, webhook или API; каждый запуск создаёт отслеживаемую задачу [38].
- **Execution policy** — стадии review и approval, которые задача проходит перед «done» [41].
- **Watchdog** — агент, приставленный к дереву задач; проверяет каждую остановку [40].

## Модель работы

- **Развёртывание — hybrid: в основном self-hosted, hosted Cloud в beta.**
  - Установка — `npx paperclipai@latest onboard --yes`. Нужен Node.js 24.11 или новее [2][76].
  - Локально один процесс Node держит embedded Postgres и локальное хранилище файлов. Для production указывают свой Postgres [2][76]. UI и API отвечают на `localhost:3100` [76].
  - `test-drive` создаёт одноразовую инстанцию с уже настроенным CEO-агентом. Команда принимает `--harness codex|opencode` [76].
  - Docs описывают установку на VPS (systemd, Nginx, Let's Encrypt). Есть Docker-образ [21][76].
  - Пользователи называют и другие способы: one-click app на VPS Hostinger [179]; шаблоны Railway — около 190 deploy-ев за 90 дней, по словам автора шаблона на 2026-09-28 [210]; пакет сообщества для Cloudron от 2026-10-31 [210]; галерея приложений Umbrel [184].
- **Режимы запуска** [71]:
  - `local_trusted` — по умолчанию: только localhost, без входа, один пользователь;
  - `authenticated` + `private` — доступ по LAN, Tailscale или VPN, со входом;
  - `authenticated` + `public` — доступ из интернета, со входом.
  - Onboarding принимает presets `--bind lan` и `--bind tailnet` [76]. Все данные разделены по компаниям [145].
- **Paperclip Cloud (hosted).**
  - Страница waitlist говорит только, что Paperclip раскатывают постепенно [6]. Пост от 2026-11-10 называет Cloud beta с waitlist [11]. Пост вендора об альтернативах признаёт: общедоступной hosted-версии нет, Cloud — beta по приглашениям [12].
  - Инстанции в Cloud — отдельные «stacks» на каждого клиента. Вход — через Cloud вместо email и пароля. Инстанция стартует из warm pool, то есть из заранее поднятых машин [146].
  - Часть experimental-переключателей заблокирована с пометкой «Managed by Paperclip Cloud» [43].
  - OAuth broker за кнопкой «Connect with Paperclip» доступен только инстанциям, записанным в Cloud (Cloud-enrolled) [52].
  - Через Cloud вендор запускает и свой plugin пула соединений [44].
  - Включены ли в Cloud отдельные worktree на задачу — (не подтверждено).
- **Удалённое исполнение.** Environments позволяют запускать runs на SSH-хосте или в sandbox от provider plugin [49]. Поддержаны Cloudflare, Daytona, exe.dev, E2B, CreateOS, Modal, Novita и Kubernetes [68]. Черновик v2026.1113.0 добавляет boxd: каждая sandbox — отдельная KVM microVM [80].
- **Агенты.**
  - Встроенные adapters [67][77]:
    - coding CLI — Claude Code (`claude_local`), Codex (`codex_local`), Gemini CLI, Cursor (локальный и Cloud), OpenCode, Pi, Grok Build, Kimi Code;
    - другие агенты — Hermes (локальный и через gateway) и OpenClaw через свой gateway или invite flow;
    - общие — `process` и `http`. В UI они помечены «Coming soon», работают только через API или импорт [67].
  - GitHub Copilot стал native harness в v2026.1106.0 [79].
  - Paperclip Runner с v2026.1106.0 — по умолчанию для новых агентов Claude, Codex, OpenCode и Pi [79][65]. Он фиксирует точные версии сред: Codex 0.160.0, Claude Agent SDK 0.3.286 (запускает Claude Code 2.1.286), OpenCode 1.18.34 [79][65].
  - Legacy adapters запускают CLI, установленный на машине пользователя, с его входом [4]. С `homeMode: "preconfigured"` Runner тоже берёт вход, skills, MCP servers и hooks машины [65].
  - Встроенный в Runner Claude Code не мог запускать новые модели, пока его не направили на CLI пользователя (issue #13889) [162][178].
  - Внешние ассистенты как агенты (experimental): OpenAI Dot, Grok Bot и Meta Muse. Их расход токенов и стоимость Paperclip не видит [50][79].
- **Подписка или API key.**
  - Вход по подписке Claude запускает `claude setup-token` в отдельном `CLAUDE_CONFIG_DIR`. Попытка входа живёт 30 минут [53]. Codex входит через device login [81].
  - Соединения по подписке Claude перестают работать примерно через 8 часов после входа (issue #13725 открыт) [162][177]. Подробности — в разделе «Что говорят пользователи».

  - Adapter для Copilot запрошен 44 голосами, а release v2026.1106.0 сделал Copilot native harness [162][79]. Закрыт ли запрос — в заметках не сказано.
  - **Расхождение по OpenRouter.** Docs называют подписки и ключи OpenRouter среди способов платить за модели [53][29]. При этом запрос на поддержку OpenRouter набрал 35 голосов [162]. - **Один пользователь или команда — команда.**
  - Одна инсталляция держит много компаний с изолированными данными и много людей [76].
  - Роли людей: Owner, Admin, Operator и Viewer [61].
  - Режим `local_trusted` рассчитан на одного пользователя без входа [71].
- **Платформы.**
  - Сервер работает на macOS, Linux и Windows [18].
  - Runner работает только на macOS (Apple Silicon и Intel) и на Linux x64/ARM64 с glibc 2.39 или новее. Windows, Linux на musl и 32-битный ARM остаются на «Legacy runner» [65].
  - Агенты по ACP (Agent Client Protocol — открытый протокол управления coding-агентами) работают на Windows нативно. Если Windows не даёт создать symlink, файл копируется [69]. Подкоманды `service` на Windows не работают [69].
  - Баг с правами на symlink в Windows открыт с 2026-03-05 (11 голосов). Вопросы о том, как распространяется Runner для Windows, идут и в ноябре [164].
- **Desktop-приложения нет.**
  - «Desktop App» — пункт roadmap [76][77]. Сравнительная таблица вендора отвечает на вопрос о native desktop app: нет, web UI [5].
  - Есть неофициальная обёртка сообщества на Electron, только для macOS: aronprins/paperclip-desktop, 595 звёзд, v3.2.15 от 2026-10-03. У неё режим Local и режим Remote, который подключается к серверу [60][225].
  - PR сообщества с Electron-приложением (#1424) закрыт без слияния 2026-03-25 [217].
- **Телефон.**
  - UI — устанавливаемое web-приложение (PWA) с v0.3.0 [81]. Manifest задаёт `display: standalone` [159].
  - Service worker отдаёт только offline-страницу. Push handler-а нет, и код UI не вызывает Notification API и Push API браузера [159].
  - На телефоне свойства задачи уходят в нижнюю выдвижную панель (bottom sheet) [24]. README обещает управление бизнесом с телефона [76].
  - Доступ с телефона — через Tailscale или authenticated-развёртывание [76][39].
- **Telemetry.** Анонимная telemetry включена по умолчанию. Её отключают переменными `PAPERCLIP_TELEMETRY_DISABLED`, `DO_NOT_TRACK` или в конфиге [76].

## Функции

### Onboarding и создание компании

- **Путь за пять минут** [20][22]: создать company, нанять CEO-агента, включить его heartbeat и одобрить его первую стратегию.
  - Первый run CEO создаёт approval «CEO Strategy». Дальше ничего не идёт, пока человек не нажмёт Approve, Reject или Request revision [20].
  - Timer heartbeats у новых агентов выключены. Кнопка «Run now» запускает run вручную [20].
- **Team Catalog** [37] — готовые команды агентов для установки.
  - В комплекте: исполнительная команда (CEO, CTO, QA) и продуктовая команда разработки с еженедельным sync.
  - Дополнительные команды могут подтягивать skills из GitHub или skills.sh.
- **Шаблоны и перенос.**
  - Репозиторий `paperclipai/companies` — 16 готовых компаний и 440+ агентов [85]. В организации paperclipai есть и репозиторий clipmart; его назначение в заметках не описано [85].
  - Export и import компании дают пакеты Markdown. Значения secrets в пакет не попадают [42].
  - Export/import заменил выведенный из работы «Cloud Sync» [72].
- **Много компаний в одной инсталляции**, данные изолированы [76].

### Org chart, агенты и управление

- **Org chart** [35]. Список агентов переключается между списком и деревом org chart. У каждого агента ровно один менеджер. CEO подчиняется board, то есть людям [19].
- **Найм** [30].
  - Менеджеры просят нанять агента через approval «Hire Agent».
  - Board может поставить любого агента на паузу, продолжить его работу или уволить, переназначить любую задачу и создать агента напрямую.
  - Approvals сами не истекают [19].
  - **Расхождение.** Сайт пишет, что найм по умолчанию требует approval [1]. Колонка базы `requireBoardApprovalForNewAgents` по умолчанию равна false [152].
- **Страница агента** [35]. Разделы: Overview, Instructions, Skills, Harness/Runtime, Secrets/Tools/Channels, Permissions/Trust, Revisions, Runs, Budgets, API Keys.
  - Instructions — набор файлов. Предлагаемое деление: `AGENTS.md` — роль; `SOUL.md` — персона и тон; `HEARTBEAT.md` — чек-лист на каждое пробуждение; `TOOLS.md` — заметки о доступных инструментах.
  - Карточка Run Policy держит интервал таймера. В расширенных настройках: timeout, пауза перед жёстким прерыванием (interrupt grace period), пробуждение по запросу, cooldown, max concurrent runs и продолжение после остановки по лимиту ходов.
- **Roster агентов** [79]. Массовая смена AI-соединения или модели у многих агентов сразу. Кнопка «Upgrade runner» переводит существующего агента на native Runner.
- **YAML-редактор** всей конфигурации агента — в черновике v2026.1113.0 [80].

### Задачи (в API — issues)

- **Статусы** [19]: backlog, todo, in_progress, in_review, done, blocked, cancelled.
- **Atomic checkout** [19]: задачу в работе держит только один агент.
- **Composer новой задачи** [24][25].
  - Поля: проект, исполнитель, модель, effort и файлы. Клавиша `C` открывает composer, ⌘+Enter отправляет.
  - Work modes: Auto — сделать работу; Plan — сначала написать документ с планом; Ask — ответить, ничего не меняя. Переключение — ⌘+. или Shift+Tab [25].
  - Задачу можно сделать private [24].
- **Страница задачи** [24].
  - Разговор занимает центральную колонку. Комментарии, живой run и прошлые runs идут одной лентой. Законченные ходы сворачиваются в краткие сводки.
  - Боковая панель: Properties, Plan, Artifacts и Tasks.
  - Связи задачи: parent, подзадачи, «blocked by» (жёсткий запрет на старт), reviewers, approvers, watchdog, запланированная проверка (`set_task_monitor`), ветка и папка workspace.
- **Планы и документы** [24].
  - Вкладка Plan показывает ревизию плана и кнопки Confirm или Decline с причиной.
  - Документы задачи хранят версии; на них можно дать прямую ссылку (deep link).
  - Документ можно заблокировать (locked). Если агент пишет в заблокированный документ, вместо правки создаётся новый производный документ.
  - Люди и агенты оставляют треды комментариев, привязанные к отрывку текста. После правок треды снова находят свой отрывок.
- **Разговор с работающим агентом** [24].
  - `@mention` — только контекст. Агента он не будит и не назначает.
  - Ответы, написанные во время run-а, встают в очередь. Их можно оставить ждать (Wait), влить в текущий ход (Steer) или прервать ход (Interrupt).
  - Каждый комментарий агента привязан к run-у, который его написал.
  - **Расхождение.** Сайт пишет, что агенты просыпаются от @-упоминаний [1]. Docs, README и код говорят, что упоминание само агента не будит [24][76][100].
  - Live steering для Codex и Pi — в черновике v2026.1113.0 [80].
- **Ограничения на записи агента** [24].
  - Агент может писать в любую задачу, которую может читать, от имени ответственного человека.
  - За один run — не больше 20 записей в чужие задачи.
  - **Расхождение.** `doc/execution-semantics.md` пишет, что run может писать только в свою захваченную задачу и её потомков [101].
- **Stop, retry и recovery** [24].
  - Stop ставит на паузу задачу или всё её поддерево.
  - Каждое действие восстановления — отдельная запись: тип, владелец и доказательства. Число повторов ограничено. После него восстановлением занимается board.
  - Вместо дампов ошибок — короткие строки статуса: «Trying again in …» и «Retry available».
- **Списки** [24][79]. Доска (board view) с настройкой плотности карточек. Колонки done и cancelled можно свернуть. Задачи, созданные агентами, по умолчанию скрыты.

### Пробуждения, heartbeats и routines

- **Что будит агента** [38][19]: таймер (включается вручную), назначение задачи, комментарий в его задаче, пробуждение по запросу или routine. Решение по approval тоже будит агента, который его запросил.
- **Routines** [38].
  - Триггеры: cron, webhook или API. Webhook подписан и защищён окном от повторной отправки (replay window); есть отдельный путь для GitHub.
  - Если прошлый запуск ещё идёт: слить с ним (coalesce), пропустить (skip) или всегда ставить в очередь (always enqueue).
  - После простоя сервера: пропустить пропущенные запуски или запустить их пачками с ограничением.
  - Шаблоны переменных и история запусков. Каждый запуск routine создаёт отслеживаемую задачу.
- **Task watchdogs** [40].
  - Watchdog — агент, приставленный к одному дереву задач.
  - Он просыпается, только когда остановились все листья дерева. Каждую остановку он проверяет как утверждение и либо снова открывает работу, либо подтверждает blocker.
- **Сигнал тихого run-а.** Автоматическая проверка помечает run без вывода как «suspicious» через 5 минут и как «critical» через 15 минут. Run она не отменяет [40].

### Где человек видит, что требует внимания

- **Inbox** [24].
  - Вкладки: Mine, Recent, Unread, Blocked, All.
  - Кнопки Approve и Reject — прямо в строке.
  - Строка упавшего run-а говорит, что нужно задаче, например «Approval required» или «Budget limit reached».
- **Blocked inbox** [32].
  - Метки причин: Needs decision, Blocked chain stalled, Needs attention, Recovery required, External wait, Owner paused.
  - Есть сортировки «Most urgent» и «Longest stopped».
- **Decisions queue** [31] — решения, которые агенты предлагают человеку.
  - Метка «1 target changed since this was proposed» появляется, если затронутые задачи изменились после предложения.
  - Для разрушительного варианта надо ввести идентификатор задачи.
  - Решение без ответа истекает через 7 дней. Approvals, в отличие от decisions, сами не истекают [19].
  - Именованные очереди: PRs, Plans и Questions.
- **Command palette** [26]. ⌘K открывает поиск и действия, `?` показывает сочетания клавиш. Sidebar держит пять последних открытых задач; список хранится в браузере.
- **Уведомления.**
  - Toasts в приложении — только по задачам, в которых пользователь участвует [24].
  - Исходящих webhook-ов Paperclip сейчас не отправляет. Docs предлагают рецепт: routine будит агента-уведомителя, и тот пишет в Slack или Discord [59].
  - Черновик v2026.1113.0 добавляет tool `send_chat_message`: агент пишет результат в постоянный чат ответственного человека [80].
  - Push-уведомлений нет: service worker PWA их не обрабатывает [159].

### Наблюдение и аудит

- **Dashboard** [23]. Четыре карточки: Agents Enabled, Tasks In Progress, Month Spend, Pending Approvals. Графики за 14 дней: Run Activity, Tasks by Status, Success Rate. Данные обновляются в реальном времени.
- **Audit** [28]. Пять вкладок: Activity, Runs, Costs, Budgets, Timeline.
  - Activity — постоянный журнал событий.
  - Export в CSV требует право `audit:view_agent_actions`. Каждый export сам записывается в журнал.
  - Сайт обещает append-only журнал аудита и полную трассировку вызовов tools [1]. Действительно ли журнал только дописывается, в коде не проверено (не подтверждено).
- **Work Timeline** (появился в v2026.707.0) [27][81].
  - Диаграмма Gantt: по одной линии на агента или автоматизацию. Наведение на полосу рисует передачу работы следующему агенту.
  - Диапазоны: Today, 7 дней, 30 дней или свой, до 31 дня. Есть zoom и minimap.
  - Docs подают её как ответ на вопрос, что происходило ночью, пока агенты работали без присмотра.
- **Транскрипты и живой run.** На странице агента — карточка Live Run. У каждого run-а — полный транскрипт [22].
  - Черновик v2026.1113.0 показывает run подробнее [80]: план агента как список задач; diffs `+N −M` прямо в ленте и карточка «Changed in this turn»; строки вызовов tools с exit code и длительностью; карточки subagents Claude.
- **Tracing и ошибки.**
  - OpenTelemetry и Sentry для сервера — по желанию (opt-in) [76].
  - Logs и traces агентов можно отправлять в Braintrust или в любой OTLP endpoint [79].
- **Agent commentary** [63][79]. Агенты оставляют жалобы и предложения о своих инструментах. Человек читает их в Audit → Commentary.
- **Feedback votes** [34]. Оценки «Helpful» или «Needs work» на результат агента. По умолчанию хранятся локально.

### Расход, budgets и лимиты подписки

Это область, где Paperclip ближе всего к счётчикам лимитов и Autopilot в worfy.

- **Budgets** [29].
  - Budgets компании и агента — месячные, сбрасываются 1-го числа по UTC. Budget проекта — лимит на всё время жизни проекта.
  - На 80% появляется предупреждение, работа продолжается. На 100% область (company, agent или project) автоматически встаёт на паузу.
  - Если расход неизвестен (usage ещё не записан или у модели нет цены), новая работа задерживается.
  - Карточки incident предлагают «Raise budget & resume» или «Keep paused».
- **Страница Costs** [29].
  - Расход по агенту, пользователю, проекту, провайдеру, модели и плательщику (biller). Есть finance ledger — журнал финансовых записей.
  - Плитка Subscriptions считает общую платную подписку один раз, даже если её делят несколько агентов.
  - Subscription quota windows — для каждого подключённого аккаунта Anthropic или OpenAI: окна 5 часов и неделя, процент использования и время сброса. «Window spend» показывает, сколько потрачено внутри каждого окна.
- **Check usage** [53][54]. Чтение лимитов провайдера по запросу. Показывает «Limit reached» или «Blocked». Функция только читает: docs прямо говорят, что она не переносит работу на другой аккаунт и не останавливает runs на лимите.
- **Ожидание сброса лимита.**
  - v2026.720.0 добавил quota-aware retries — повторы, которые ждут сброса квоты провайдера [81].
  - PR #4383 разбирает сообщение Codex «try again at …», чтобы назначить повтор на это время [161].
  - Черновик v2026.1113.0 добавляет три вещи [80]: строку Usage limit на уровне задачи, например «5h 78% · resets 15:40»; состояние «Waiting for usage limit reset», которое заменяет пустые runs и повторы; показ заполнения context window с кнопкой «Compact now».
- **Connection pools** (experimental; нужны флаг и router plugin) [44].
  - Новые задачи распределяются по нескольким AI-аккаунтам.
  - Режим usage-aware по умолчанию пропускает аккаунты, у которых использовано 90% и больше.
  - Каждая задача закреплена за одним аккаунтом.
  - Если все аккаунты за лимитом, задача показывает «Pool exhausted» и ждёт, не тратя свой бюджет повторов.
- **Открытые запросы:** автоматическая смена модели при исчерпании квоты (#3317) и budgets в токенах (#1756) [162][169].

### Работа с кодом

- **Isolated workspaces** — за experimental-переключателем «Enable Isolated Workspaces» [39][4].
  - Три режима: новый git worktree и ветка на задачу; повторное использование workspace другой задачи; основной checkout проекта.
  - HTTPS previews публикуются в сети Tailscale пользователя (tailnet) через broker [39].
  - «Open workspace» входит в workspace через одноразовую передачу входа (single-use login handoff) [39].
  - Сам Paperclip никогда не делает push из workspace [39].
  - **Расхождение о runtime services** (dev servers и подобное). Страница docs о workspaces пишет, что их запускают вручную [39]. Guide в репозитории пишет, что они настраиваются на проект или workspace и стартуют сами в начале run-а [119].
- **Очистка workspaces** (v2026.1106.0) [79].
  - Через час после завершения дерева задач восстанавливаемые папки удаляются.
  - По желанию законченные worktrees удаляются через 24 часа. Если задачу откроют снова, worktree восстанавливается на точном коммите.
  - По желанию перед очисткой сохраняются зашифрованные точки восстановления (encrypted restore points) с незакоммиченной работой.
- **Просмотр изменений.**
  - Experimental file viewer — обзор файлов workspace и прямые ссылки на файл и строку [48].
  - Plugin `plugin-workspace-diff` (alpha) добавляет вкладку Changes со staged и unstaged diffs [70].
- **GitHub** [58][76][4].
  - Учётные данные: personal access token, GitHub App или managed connection, чей webhook синхронизирует статус PR.
  - PR открывается от имени человека, который направил работу.
  - Встроенный skill требует от агентов добавлять в каждый коммит `Co-Authored-By: Paperclip <noreply@paperclip.ing>` [100]. Открытый issue просит возможность это выключить (#4677, 10 голосов) [174][162].
  - **Расхождение.** Docs называют personal access token среди способов подключения [58]. Пользователи пишут, что на self-hosted-инстанции подключение GitHub требует записи в Paperclip Cloud, а запасной вариант с token спрятан [184].
- **Статус PR в задаче** [24].
  - Ссылки GitHub показываются как плашки статуса: Open, Draft, Merged и другие.
  - Каждая плашка показывает свежесть данных: Fresh, Stale, Requires auth или Unreachable.
  - Баннер «Pull request review requested» с кнопкой «Check status».
  - Карточка PR во вкладке Artifacts показывает состояние, checks и число изменённых строк.
- **Стадии review (execution policy)** [41].
  - Каждый run обязан оставить комментарий. Можно добавить стадии review и approval.
  - Когда исполнитель помечает задачу done, runtime переводит её в `in_review` и назначает reviewer-у.
  - `maxReviewRounds` по умолчанию 3, максимум 50. После трёх раундов «changes requested» между агентами review передаётся ответственному человеку.
- **GitHub review bot** [55][79].
  - Одно GitHub App на каждого агента-reviewer-а.
  - Оценка бота становится check run «Paperclip Review» и сравнивается с порогом. Блокирует ли этот check слияние, решают правила веток (branch rules) в GitHub.
  - Бот держит в PR один комментарий и обновляет его после каждого push.
- **Permission prompts** [66][65].
  - Claude Code по умолчанию запускается с `--dangerously-skip-permissions`: docs объясняют это тем, что нажимать approve некому.
  - Режимы разрешений ACP в Runner: `approve-all` (по умолчанию), `approve-paperclip`, `approve-reads`, `deny-all`.
  - Для Codex есть только режим `never`, в UI он называется «Automatic (isolated)».
- **Встроенного test gate нет.** Функции, которая запускает tests проекта или шаг проверки перед done, обе заметки не нашли (не подтверждено) [41][4]. Качество держится на стадиях review, QA-агентах, watchdogs и monitors.

### Skills и «обучение» агентов

- **Библиотека skills компании** [36][79].
  - Импорт из GitHub, gist, локальных файлов, skills.sh или проекта.
  - Источники в GitHub синхронизируются сами. Репозитории проекта перепроверяются каждые 5 минут.
  - Каждый run фиксирует версии skills, с которыми стартовал.
- **Skill Studio** [36]. Три панели: файлы skill, вход и тестовые runs. Сохранённые входы, тесты на скрытой служебной задаче, история версий с восстановлением. Агенты могут создавать и улучшать skills прямо во время задачи.
- **Встроенные агенты** [73][46]: Summarizer, Briefs Agent, Learning Agent и Reflection Coach. Reflection Coach предлагает изменения инструкций и skills и просит approval перед тем, как их применить. Summarizer работает в Status Cards (см. ниже). Что делают Briefs Agent и Learning Agent, заметки не описывают.

### Connectors и tool gateway

Tool gateway — слой Paperclip, через который агенты вызывают внешние сервисы; на нём проверяются права.

- **Каталог.**
  - **Расхождение в размере.** Docs перечисляют около 95 записей в 12 группах [52]. Маркетинговая страница говорит о 46 connectors (запись от 2026-10-01) [2].
  - Рабочие tools: GitHub, Linear, Jira, Asana, Notion, Google Workspace. Разработка и эксплуатация: Sentry, PagerDuty, Stripe, Supabase, Railway, Netlify, Cloudflare. Агрегаторы tools: Zapier, Composio, Arcade. Другие: Daytona, Braintrust, Browser Use Cloud [52].
  - Черновик v2026.1113.0 добавляет в каталог 1Password, Supabase, Vercel и boxd. Агенты смогут сами настраивать соединения [80].
- **Способы подключения** [52]: «Connect with Paperclip» (только для Cloud-enrolled инстанций), «Sign in with provider», свой OAuth app, API key, регистрация app у провайдера, без учётных данных.
- **Права на действия.** У каждого действия три состояния: Allowed, Ask first или Off. Все действия стартуют как Allowed, включая разрушительные [56]. Reviewer может одобрить вызов один раз или сохранить правило, которое потом можно отозвать [76].
- **Прочее** [52][77][79]:
  - свои MCP servers;
  - memory connectors: Mem0, Zep, Supermemory, Cognee и Honcho;
  - классификатор prompt injection на модели, который проверяет результаты tools; выключен, пока его не настроят.
- **Ticket systems.** Jira, Linear и Asana — только tools агента. Брать из них задачи — пункт roadmap «bring-your-own-ticket-system» [77][76].

### Чат, голос и доступ из ассистентов

- **Agent Chat** [45][80]. Один постоянный разговор с каждым агентом. Настоящую работу агент передаёт в задачи и сообщает, когда они готовы. В черновике v2026.1113.0 чат становится рабочим местом по умолчанию — «Coordinator workspace».
- **Chat channels** (за experimental-флагом) [52]: Slack, Discord, Microsoft Teams, Telegram, iMessage через Photon, голос и телефон через Speko.
- **Assistant connections** (через MCP) [51][160]. ChatGPT, Claude или другой ассистент подключается к одной организации от имени пользователя: OAuth к `/mcp/paperclip`. Пакеты plugins для Claude и OpenAI лежат в репозитории как пакеты для разработки, в магазины они не отправлены.

### Результаты и сводки

- **Artifacts page** [33].
  - Вложения, документы и результаты работы, сгруппированные по задачам.
  - Картинки и видео открываются в галерее, CSV — таблицей, HTML-отчёты — как изолированные (sandboxed) страницы.
  - Файл можно загрузить в задачу, не будя агента.
- **Status Cards** (experimental) [46].
  - Пользователь одним предложением пишет, за чем следить. Summarizer превращает его в запрос и держит живую плитку со сводкой.
  - Плитка показывает Fresh, Stale или Updating. У каждой карточки — дневной лимит токенов и часы активности.
- **Cases** (experimental) [47]. Одна долгая единица работы: её главная задача переходит от агента к агенту, каждая передача записывается в журнал (handoff ledger).
- **Browser Use Cloud connector** (v2026.1005.0) [81]. Задача показывает живые вкладки браузера; человек может следить за ними или перехватить управление. Optional skill agent-browser делает скриншоты [74].

### Команда, доступ и безопасность

- **Роли** [61]: Owner, Admin, Operator и Viewer.
  - Пригласить можно только ссылкой.
  - SSO и MFA пока нет; вход — email и пароль. Запрос на SSO/OIDC набрал 13 голосов [162].
- **Приватность и secrets.** Задачи и проекты могут быть private. Значения secrets могут быть персональными [24][8]. Общие агенты могут действовать под GitHub-идентичностью человека, который ими руководит [77].
- **Low-trust presets** [64]. Работа, которая началась с недоверенного входа (чужой PR, внешний ticket), остаётся изолированной, пока её не посмотрит человек или доверенный reviewer.
- **Расширения.**
  - Plugins (alpha) работают как отдельные процессы (out-of-process workers). Они добавляют места в UI, фоновые jobs и webhooks [62].
  - В CLI два слоя: setup и control plane. Команда `agent local-cli` позволяет локальному Claude или Codex работать как агент Paperclip [72].

## Принципы и подходы

### Философия

- **Главная единица — компания, а не репозиторий.** README предлагает управлять бизнес-целями, а не pull request-ами [76]. CEO-агент предлагает стратегию, нанимает подчинённых и делегирует им работу [18][22]. Coding — один из вариантов использования, не центр продукта [76].
- **Целевой пользователь** в README — человек, у которого одновременно открыто около 20 терминалов Claude Code и который теряет из виду, кто чем занят [76].
- **Управлять, а не исполнять.** Принцип из docs звучит так: «Control plane, not execution plane» [89]. Paperclip задумывался как слой управления, который сам агентов не исполняет [89]. На деле сервер запускает процессы агентов сам — через adapters или через Runner [89][90].
- **Позиционирование сдвинулось.**
  - В марте 2026 все публикации на Hacker News шли с лозунгом запуска о компаниях без людей («zero-human companies») [219].
  - Сейчас описание на GitHub — open-source приложение для управления агентами на работе. Tagline сайта — команда агентов для каждого человека [75][1].
  - Сдвиг — от компаний без людей к командам под надзором человека [75][1][219]. Недавние посты блога — об approvals, о назначении и проверке работы агентов без терминала и о запуске агентов на ночь [10][14][13].
- **Как вендор сам себя сравнивает.**
  - Для одного разработчика, который следит за несколькими sessions Claude, Paperclip — лишний слой; Agent View в Claude Code подходит лучше. amux подходит для большого числа терминальных sessions. Agent Teams — experimental и работает только с Claude [15].
  - Список альтернатив вендора: Multica, CrewAI, OpenHands, Orca, Paradev, Claude Code и Codex. Вендор признаёт, что UI есть только в web и общедоступного hosting нет [12].

### Ключевые понятия

- **Company, board, org chart.** У каждого агента ровно один менеджер, CEO подчиняется board — людям [19].
- **Goals → Projects → Tasks.** Цели, проекты и задачи с подзадачами и blockers; для долгой работы с передачами — Cases [19][24][47].
- **Heartbeat** — пробуждение агента для run-а. Пробуждения идут от событий: назначения, комментария, снятия зависимости, routine. Таймер по умолчанию выключен [96][101].
- **Approval gates** — точки, где решает человек: найм, стратегия CEO, превышение budget [151].
- **Budgets** — денежные лимиты с жёсткой остановкой [29].
- **Пять инвариантов** из `AGENTS.md` репозитория [78]: у задачи один исполнитель; atomic checkout; approval gates; автоматическая пауза при достижении budget; запись в журнал каждого изменяющего действия.
- **Governance — на уровне API и tool gateway.** Permission prompts самого CLI по умолчанию выключены, права проверяет Paperclip [108][57].

### Чем подход отличается

- **Модель организации.** Агенты устроены как сотрудники: должность, менеджер, найм через approval, budget [19][30].
- **Сервер и web UI для многих людей и многих компаний**, а не приложение на одном компьютере [76][61].
- **Много сред агентов сразу:** около десяти harnesses от разных вендоров в одной компании [67].
- **Не только код.** Пользователи ведут маркетинг, финансы и новостной сайт [1][199][202].
- **Человек решает в очередях**, а не в терминале: Inbox, Blocked inbox, Decisions, approvals [24][31][32].

## Как это устроено внутри

### Архитектура, модули и файлы

- **Stack** [89]: Express 5 на TypeScript; PostgreSQL 17 или embedded Postgres через Drizzle ORM; Better Auth; React 19 и Vite; pnpm workspaces.
- **Два пути исполнения сосуществуют.**
  1. **Legacy adapters** — по пакету на harness: `claude_local`, `codex_local`, cursor, gemini, opencode, pi, hermes, grok, kimi, `process`, `http`, `openclaw_gateway` [67].
     - Сервер вызывает `execute()` adapter-а. Adapter запускает CLI с переменными окружения `PAPERCLIP_*` и prompt.
     - Агент сам вызывает REST API Paperclip: захватывает задачи, комментирует, меняет статус.
     - Adapter разбирает stdout: usage, стоимость и ID session [89].
     - Исходная spec говорит, что эти CLI работают прямо на хост-машине, без sandbox [91].
  2. **Paperclip Runner** — отдельный процесс на Rust, `paperclip-runnerd` [90][92].
     - С сервером он говорит по протоколу Paperclip Runner Protocol (PRP v1): WebSocket на `/api/runner/v1/connect/:runId`. Протокол описан JSON Schema; parity tests сверяют реализации на TypeScript и Rust [90].
     - Runnerd владеет группой процессов провайдера, его session, передачей ходов и durable outbox — журналом исходящих событий, который переживает сбой [90].
     - Сервер остаётся главным по identity, политикам, budgets, approvals, workspace и статусу задачи [90].
     - Drivers: Codex, OpenCode, профили ACPX для Claude и Codex, Claude Managed, AWS AgentCore. Позже добавлены Copilot, Grok, Muse и Cursor [79][92].

Release v2026.1106.0 сделал его default для новых агентов Claude, Codex, OpenCode и Pi на macOS и Linux x64 с glibc 2.39+. ### Цикл агента (heartbeat)

- **Очередь пробуждений.** Каждое пробуждение — строка в `agent_wakeup_requests` [94]. В ней: источник, причина, payload, статус (по умолчанию `queued`), `coalescedCount`, кто запросил, `idempotencyKey` (с частичными уникальными индексами для каждого вида восстановления) и `runId` получившегося run-а.
- **Run** — строка в `heartbeat_runs` [95]. Она хранит:
  - источник вызова и статус;
  - `runtimeMode` (legacy или native) и профиль runner-а;
  - session до и после run-а;
  - ссылку на log и его размер;
  - PID, группу процессов и хэш хоста;
  - controller lease — какой процесс сервера владеет run-ом и до какого времени;
  - `retryOfRunId`, `processLossRetryCount`, `scheduledRetryAt` и счётчик плановых повторов;
  - `issueCommentStatus`, состояние liveness и `continuationAttempt`;
  - поля учёта стоимости.
- **Откуда пробуждения** [76][101]: назначение задачи; новые комментарии и follow-up сообщения; события зависимостей `issue_blockers_resolved` и `issue_children_completed`; routines (cron, webhook или API), monitors, approvals и восстановление.
  - Одно @-упоминание агента не будит [76][100]. Сайт пишет обратное [1].
- **Таймер по умолчанию выключен:** `enabled` = false, `intervalSec` = 0 [96]. Если пользователь включает таймер, UI подставляет 300 секунд [123]. Таймер можно настроить так, чтобы он пропускал пробуждение, когда у агента нет работы. Есть лимиты на агента: `maxDailyRuns` и `maxDailyCostCents` [96].
- **Слияние пробуждений.** Если run уже держит lock задачи, новое пробуждение разбирает чистая функция `decideWakeAdmission` [99]:
  - coalesce — влить в живой run, если это тот же агент и follow-ups разрешены;
  - defer — ждать, пока живой run закончится;
  - proceed — lock свободен, можно запускать.
  - Комментарии, которые ждут за run-ом, можно переупорядочить или отбросить. Потом они доставляются одной пачкой [99].
- **Что делает legacy-агент за один heartbeat.** Встроенный skill `paperclip` учит процедуре из девяти шагов [100]:
  1. Узнать свою identity.
  2. Разобрать решение по approval, если пробуждение пришло от него.
  3. Прочитать inbox.
  4. Выбрать работу: сначала `in_progress`, потом `in_review`, если разбудил комментарий, потом `todo`.
  5. Захватить задачу (checkout). Если ею владеет другой агент, ответ — `409`. Правило skill — никогда не повторять запрос после 409.
  6. Прочитать компактный контекст из `GET /api/issues/{id}/heartbeat-context`: состояние задачи, сводки предков, цель и проект, курсор комментариев.
  7. Сделать работу.
  8. Обновить статус с обязательным заголовком `X-Paperclip-Run-Id`.
  9. По желанию создать подзадачи.
- **Ещё правила того же skill** [100]:
  - остановиться после двух неудачных записей в control plane подряд;
  - проверять, что запись прошла, а не предполагать это: пустой ответ считается ошибкой;
  - пройти чек-лист финального статуса: для `in_review` нужен настоящий путь review, для `blocked` — настоящий blocker.
- **В native-режиме завершение — вызов tool, а не текст.** Run получает набор semantic actions [102]:
  - задача: `get_task_context`, `write_document`, `report_progress`, `finish_task`, `block_task`, `request_review`, `create_task`, `set_dependencies`;
  - ожидание: `set_task_monitor`, `schedule_wake`;
  - люди и управление: `request_human_input`, `request_approval`, `hire_agent`, `reassign_task`;
  - workspace: `select_workspace`, `prepare_repository`;
  - общий запасной вариант: `call_api`.
  - Агент видит только действия, разрешённые ему. Права проверяются заново при каждом вызове [102][90].
  - Ход должен закончиться ровно одним вызовом `paperclip_finish` или `paperclip_block`. Если ход закончился без такого вызова, runtime добавляет корректирующий ход [103].
  - Результат runner-а сервер считает недоверенным заявлением. Он проверяет его, классифицирует доказательства, выбирает статус чистой функцией и фиксирует решение в транзакции [90][104]. Подробнее — в «Проверке качества».
- **Другие страховки цикла.**
  - Каждый run по задаче обязан оставить комментарий. Если комментария нет, агента будят ещё раз с причиной `missing_issue_comment`. После этого статус становится `retry_exhausted` [105].
  - Если run упёрся в лимит ходов, его продолжают по умолчанию 2 раза (не больше 10), с паузой 1 секунда по умолчанию (не больше 5 минут) [106].
  - Claude CLI запускается с `--print --output-format stream-json --verbose`, `--resume <session>`, `--max-turns`, `--append-system-prompt-file` (только для новой session), `--mcp-config … --strict-mcp-config` и `--add-dir` для пакета skills [108].
  - **Расхождение о лимите ходов.** `maxTurnsPerRun` по docs — 300 [107], по умолчанию в UI — 1000 [123].
  - Если session нельзя продолжить из-за испорченного resume, делается один повтор в новой session, а сохранённая session стирается [107].

### Декомпозиция и планирование

- **Две разные связи** [101].
  - `parentId` — только структура: разбивка, свёртка итогов и пробуждение parent, когда все дети завершены.
  - `blockedByIssueIds` — зависимость, которая на деле запрещает старт. Отменённый blocker не считается снятым [101][100].
- **Лимит глубины.** Агенты строят только два уровня: корневую задачу и её детей (`MAX_AGENT_TASK_HIERARCHY_DEPTH = 2`) [97]. Более глубокую задачу система молча делает соседней, а в ответе ставит `parentAdjusted` [100]. У board такого лимита нет [97].
- **Work modes в коде:** `standard`, `ask`, `planning` и `skill_test` [97].
- **Планирование.**
  - В режиме planning агент пишет документ `plan` с ревизиями. Человек принимает конкретную ревизию, и это разрешает исполнять только её [101].
  - По умолчанию после acceptance работа идёт в той же задаче. Skill `paperclip-converting-plans-to-tasks` велит создавать дочерние задачи только на настоящей границе: другой владелец или права, параллельный результат, предварительное условие, независимый review или продолжение со своим жизненным циклом [101][110].
  - Старый API декомпозиции срабатывает ровно один раз на пару `(sourceIssueId, acceptedPlanRevisionId)`. Он хранит claim и частичные результаты, поэтому упавшая раздача задач продолжается и не создаёт дублей [101].
- **Делегирование по org chart** [111]. CEO предлагает стратегию как approval для board. Потом разбивает цели на задачи для подчинённых. Они просыпаются по назначению и могут делегировать ниже.
- **Отчёт вверх — три канала** [101]: пробуждение parent по завершению; один комментарий прямому parent (только для trust preset `standard`); системное сообщение, когда дочерняя задача заблокирована или отменена.
- **Координация в сторону** — courier pattern: создать новую задачу с полным контекстом в описании и назначить её нужному агенту [101].
- **Review — отдельная задача.** Reviewer помечает её done даже при отрицательном вердикте. Parent заблокирован этой задачей review [101][100].

### Параллельность и координация

- **Лимиты.**
  - На агента: `maxConcurrentRuns` по умолчанию 20, допустимо от 1 до 50. Для некоторых native providers — всегда 1 [96][97].
  - Лимит проверяется при захвате: SQL считает идущие runs (`assertAgentRunSlotFree`) [98].
  - Таблицы лимитов на проект есть (`project_task_execution_policies`), но ни один путь захвата их пока не проверяет [113].
  - Общего лимита на adapter нет; issue #332 открыт [166].
- **Atomic checkout** [112].
  - Захват — один условный `UPDATE issues SET assignee, checkoutRunId, executionRunId, status='in_progress' … WHERE status IN (expected) AND (assignee IS NULL OR same) AND <execution lock free> RETURNING`.
  - Если строка не вернулась, вызывающий получает `409`.
  - `checkoutRunId` — у кого право исполнять задачу. `executionRunId` — какой run работает прямо сейчас [101].
  - При завершении колонки lock очищаются, только если всё ещё указывают на этот run (compare-and-clear). Устаревший lock чинится сам, только если run-владелец завершён или пропал [101].
- **Routines** [114]. Политика при живом прошлом запуске: `coalesce_if_active` (по умолчанию), `skip_if_active`, `always_enqueue`. Политика догоняния после простоя: `skip_missed` (по умолчанию) или `enqueue_missed_with_cap`.

### Изоляция

- **Режимы и стратегии workspace** [115]. Режимы: `shared_workspace`, `isolated_workspace`, `operator_branch`, `reuse_existing`, `agent_default`. Стратегии: `project_primary`, `git_worktree`, `adapter_managed`, `cloud_sandbox`.
- **Отдельный worktree на задачу — experimental-настройка инстанции, по умолчанию выключена.** `enableIsolatedWorkspaces` и `enableIsolatedWorkspacesByDefault` по умолчанию false [116].
- **Без неё задачи идут в общем checkout проекта**, если checkout настроен. Его настройка конкурентности: `auto | serialize | allow` [117]. Стратегия по умолчанию в UI — `project_primary` [123].
- Задача без checkout проекта получает свою постоянную папку [79].
- На local и SSH режим `allow` кладёт нескольких агентов в одну физическую папку. Удалённые sandboxes так не делают: они откладывают run с причиной `workspace_busy` [117]. Повтор ждёт 60 секунд плюс до 60 секунд случайной добавки (jitter) [133].
- **Как создаётся worktree, когда изоляция включена.**
  - Команда — `git worktree add -b <branch> <path> <baseRef>` [118].
  - Шаблон ветки — `{{issue.identifier}}-{{slug}}`. Путь — `<repo>/.paperclip/worktrees/<branch>`, с проверкой, что путь не выходит за пределы репозитория [118].
  - Каждая новая дочерняя задача получает свой workspace от базы проекта. Она никогда не стартует от checkout parent и его неслитых изменений [101].
  - Runtime services (dev servers, preview URLs) по guide в репозитории настраиваются на проект или workspace и сами стартуют в начале run-а [119]. Страница docs пишет, что их запускают вручную [39].
- **Очистка** (последний релиз) [79]:
  - восстанавливаемые папки (`node_modules`, `dist`, `target`) удаляются через час после завершения дерева задач;
  - по желанию законченные worktrees и базовые клоны удаляются через 24 часа;
  - encrypted restore points возвращают workspace задаче, которую открыли снова.
- **Удалённое исполнение.**
  - Drivers окружений: `local`, `ssh`, `sandbox` и `plugin`. Политики аренды окружения (lease): `ephemeral`, `reuse_by_environment`, `reuse_by_execution_workspace`, `retain_on_failure` [97].
  - Plugins sandbox-провайдеров: Daytona, E2B, Modal, Kubernetes, Cloudflare, boxd, createos, exe-dev и novita [120].
  - Состояние кода переносится в удалённую среду git bundle-ами по SSH. Правило «no-remote-git contract»: adapters никогда не делают `git push` из кода runtime [119].
- **Права внутри агента.**
  - `claude_local` по умолчанию ставит `dangerouslySkipPermissions: true`, то есть запускает Claude с `--dangerously-skip-permissions` для всех встроенных и подключённых tools [108][121]. В UI по умолчанию то же [123].
  - Codex запускается как `exec --json` с `sandbox_mode="workspace-write"` и включённой сетью, если bypass не включён явно [122].
  - **Расхождение о Codex.** Код (`codex-args.ts`) включает bypass только по явному выбору [122]. Issue #21317 от 2026-11-13 пишет, что у adapter-а Codex sandbox bypass включён по умолчанию, и агенты, которых просят нанять другие агенты, приходят на карточку approval уже с bypass [187]. Docs Runner для Codex знают только режим `never` («Automatic (isolated)») [65].
  - Права проверяются на уровне API Paperclip и tool gateway, а не permission prompts самого CLI [108][57].

### Состояние и память

- **Postgres — источник истины для всего:** около 187 файлов схемы, миграции до номера 0479 [75].
- **Группы таблиц** [75][95]:
  - работа: `issues`, `issue_relations`, `issue_documents` (с ревизиями), `issue_thread_interactions`, `issue_execution_decisions`, `issue_recovery_actions`, `issue_watchdogs`;
  - исполнение: `agent_wakeup_requests`, `heartbeat_runs`, `heartbeat_run_events`, `agent_task_sessions`, `agent_runtime_state`, `execution_workspaces`, `environment_leases`;
  - деньги: `budget_policies`, `budget_incidents`, `cost_events`;
  - аудит: `activity_log`.
- **Полные logs runs** лежат вне Postgres, в хранилищах `local_file`, `s3_segments` или `s3_archive` [125].
- **Домашняя папка агента** — постоянная: `AGENTS.md`, заметки, память. По желанию хранится в S3 с manifest в Postgres [126].
- **Runner** сохраняет каждое событие до отправки. Сервер подтверждает накопленный курсор. ID команд идемпотентны, поэтому после переподключения события повторяются без повторных последствий [90].
- **Session.** Sessions хранятся на пару «агент — ключ задачи» в `agent_task_sessions` [157]. Claude продолжается через `--resume`, с учётом рабочей папки [107].
- **Смена session.** Для adapters без своего управления контекстом session меняется после 200 runs, 2 млн входных токенов или 72 часов. Claude и Codex полагаются на своё сжатие контекста (compaction) [109].
- **Сборка контекста.** Каждое пробуждение несёт «Wake Payload» или «Resume Delta»: компактную задачу, новые комментарии по порядку, цель и цепочку предков [100]. Если нужна новая беседа, строится детерминированная передача дел размером 24 000 байт: исходный запрос, недавние сообщения, решения, отрывки документов [92].
- **Долгая память.**
  - Skill памяти на файлах «PARA»: knowledge graph, дневные заметки и неявные знания в `$AGENT_HOME` [127].
  - Домашние файлы агента [126] и skills компании, зафиксированные на каждый run [79].
  - Подключаемый слой провайдеров памяти описан в обзоре-design от марта 2026 [128]. В коде выпущенный слой не найден (не подтверждено).
  - **Расхождение.** Roadmap отмечает память как частично готовую: experimental-соединения с Mem0, Zep, Supermemory, Cognee и Honcho [77]. Заметка о внутреннем устройстве такого слоя в коде не нашла [128].
  - Файл на Rust `task_memory.rs` — о лимитах RAM через cgroup, а не о памяти агента [92].

### Проверка качества

- **Execution policy** (на задачу) [105].
  - Упорядоченные стадии `review` и `approval`. Участники — агенты или люди. Исходный исполнитель в них не участвует.
  - Когда исполнитель переводит задачу в done, runtime её перехватывает: задача становится `in_review` и назначается reviewer-у.
  - «Changes requested» возвращает задачу исполнителю, а потом снова в ту же стадию.
  - Решает только текущий участник; остальные получают `422`. Каждое решение требует комментария в том же PATCH-запросе.
- **Completion contracts** (native runs) [104].
  - Сервер классифицирует каждую ссылку на доказательство: `accepted`, `missing`, `rejected` или `unverifiable`.
  - Режим «durable-evidence completion» требует принятого доказательства для каждого критерия и каждой проверки.
  - Но по умолчанию действует низкорисковая `agent_claim_policy`. Она принимает заявление самого агента, что критерии выполнены и проверки прошли [104].
- **Required quality review** — по желанию. Агенты могут добавить это требование, но менять или снимать принятое требование может только человек [129].
- **Task watchdog** — агент по желанию. Он сверяет остановленное дерево задач с доказательствами и перезапускает работу, если остановка была ошибкой [130].
- **Issue monitors** — разовые отложенные пробуждения (`issue_monitor_due`). Так агент ждёт checks в GitHub, CI или deploy. После срабатывания monitor надо ставить заново [101].
- **GitHub review bot** — Paperclip выступает reviewer-ом PR на GitHub и публикует check runs [131].
- **Test gate** — встроенного шага, который запускает tests перед завершением, поиск по коду не нашёл (не подтверждено).
- **Собственные tests Paperclip.** Поведение продукта проверяется платными live end-to-end планами «TestOps» [132].

### Восстановление после сбоев

- **Сроки повторов.**
  - Временный сбой: ограниченные повторы через 30 секунд, затем через 60 [133].
  - Сбои инфраструктуры: `30 s × 2^(n-1)` со случайной добавкой ±20% [134].
  - Продолжение взаимодействия: не больше двух попыток при сбое инфраструктуры [133].
- **Падение и перезапуск сервера** [101].
  - Брошенная назначенная задача в `todo` или `in_progress` получает **одно** автоматическое пробуждение для восстановления или продолжения.
  - Если и оно не помогло, задача становится `blocked` с действием восстановления, которым владеет board. Исполнителя не меняют.
  - Намеренное ожидание без цели получает 5 попыток починки: сразу, затем через 60, 120, 240 и 480 секунд. Попытки привязаны к отпечатку (fingerprint) постоянного состояния задачи.
- **Сигнал тихого run-а.** Нет вывода 5 минут — `suspicious`, 15 минут — `critical`. Сигнал только информирует: ничего не отменяет и никого не будит [101].
- **Кнопка Retry** [135].
  - Если это безопасно, Retry продолжает в worktree задачи с новой session.
  - Иначе запускает новую изолированную попытку и передаёт подсказки `priorWorkspace`. Старая папка остаётся без изменений.
  - Idempotency key защищает от двойного нажатия.
- **Восстановление Runner ограничено.** Когда исчерпаны лимиты хранилища, переподключений, команд или времени, run завершается с классифицированной ошибкой [90].
- **Runs переживают перезапуск сервера и redeploy** — в черновике v2026.1113.0 [80].

### Лимиты и стоимость

- **Ожидание сброса лимита — `deferRunForProviderLimit`** [136][137].
  - Проверка идёт до любой работы с workspace или провайдером. Если недавние runs (за 24 часа) упали с `rate_limit` или `quota_exhausted`, новый run отменяется, а повтор назначается на время сброса.
  - Время сброса берётся из типизированного поля `retryAt` или из текста провайдера, например «try again at 4:30 PM (America/Chicago)» или «resets Nov 12, 6pm (UTC)» [138].
  - Если время сброса не сообщено, ожидание — 1 час [134]. Ожидание не длиннее 24 часов. Успешный run стирает старые свидетельства лимита [137].
  - Ручные runs, разговоры, восстанавливающиеся runs и router pools это ожидание обходят [136].
  - Так закрыт issue #2101 о повторе после лимита (закрыт 2026-07-21) [168].
  - **Ожидание только реактивное.** Окна rate limit сохраняются для каждого агента, но на исполнение не влияют [140]. Планирования runs под оставшийся лимит нет.
- **Счётчики квот.** Квота Claude читается с `api.anthropic.com/api/oauth/usage`: окна `five_hour`, `seven_day`, `seven_day_sonnet`, `seven_day_opus` и `extra_usage` [139]. Для Codex есть похожее чтение [139].
- **Пулы и смена модели.**
  - AI connection routers (experimental, выключены по умолчанию) объединяют несколько аккаунтов. Выбор — по кругу (round-robin) или по использованию (usage-aware). На проверку аккаунтов — 15 секунд, данные считаются свежими 60 секунд [141].
  - Автоматическая смена модели или провайдера — открытый запрос #3317 [169].
  - Открытый баг #13725: соединения по подписке Claude умирают примерно через 8 часов, потому что refresh token отбрасывается при входе [177].
- **Денежные budgets** [142][29].
  - Company и agent — месячное окно по UTC. Project — на всё время жизни.
  - 80% — только предупреждение. 100% — область встаёт на паузу, новая работа не принимается [29].
  - Runs, которые уже идут, получают Stop с небольшой задержкой и успевают ещё немного потратить [29].
  - **Usage, включённый в подписку, в денежные budgets не входит** [142][29].
  - Usage без цены по умолчанию блокирует новую работу [29].
  - Резервирование суммы на run берётся до запуска (по желанию). Docs оговаривают: оценка ограничивает допуск run-а, но не может ограничить счёт провайдера [144][29].
  - Проверка budgets переходит на схему без lock с небольшой задержкой учёта [143].

### Права и безопасность

- **Режимы развёртывания** [145]: `local_trusted` — только loopback, без входа; `authenticated` — вход через Better Auth, доступ private (LAN или Tailscale) или public. Все данные разделены по компаниям.
- **Учётные данные агента.**
  - Агент получает JWT на run в `PAPERCLIP_API_KEY`. Алгоритм HS256, срок жизни по умолчанию — 48 часов, хотя docs называют token короткоживущим [147].
  - Долгоживущие API keys агентов хранятся как hash [147].
  - Runnerd не получает широкий API key. Он получает одноразовый bootstrap ticket, привязанный к компании, агенту, задаче, run-у и артефакту [90].
- **Trust presets** [148]. `standard` или `low_trust_review`; действует самая узкая политика. Агенты low-trust не могут читать и менять привилегированную конфигурацию. Их задачи хранят пометку, что источник на карантине.
- **Tool gateway — четыре проверки на каждый вызов** [57]: соединение; grant (личный, на организацию или выделенный агенту); доступ агента; политика действия — Allowed, Ask first или Off.
  - На Ask first агент ждёт. Человек отвечает «Allowed once», «Always allowed» (отзываемое правило доверия) или «Declined» [57].
  - Shell-команды `git` и `gh` под Ask first не попадают [57].
- **Защита от prompt injection** [149]. По умолчанию — проверка результатов tools регулярными выражениями. По желанию — классификатор через OpenRouter (по умолчанию `gpt-oss-safeguard-20b`) с timeout 10 секунд; при сбое — снова регулярные выражения.
- **GitHub identity** [150]. Общие агенты используют GitHub-соединение человека, чьи инструкции исполняют. `git` и `gh` запускаются через обёртки без token; учётные данные выдаёт broker.

### Что ругают

#### Расход токенов на heartbeats и веер делегирования (главная тема)

- **Первая большая ветка — #449 от 2026-03-10** (11 голосов, 17 комментариев) [191].
  - Автор считает продукт впечатляющим, но дорогим по токенам даже на простых задачах.
  - Разбор сообщества: планировщик срабатывает каждые 30 секунд. Каждый агент, которому подошёл срок, получает полный run модели, без проверки, есть ли у него работа.
  - Самый популярный ответ: будить агента надо простым правилом — только когда ему назначена работа. Запускать модель, чтобы проверить, есть ли работа, — расточительно [191].
  - Основатель поддержал более безопасные настройки по умолчанию и выложил план снижения расхода, написанный агентом [191]. Отчёт в репозитории от 2026-03-13 описывает исправление: уменьшенные endpoints inbox и контекста и повторное использование session между пробуждениями [158].
  - В текущем коде таймер по умолчанию выключен и может пропускать пробуждение без работы [96]. Фоновые workers работают на сигналах `pg_notify`, а не на опросе базы [124].
- **Пользователи упирались в это и позже.**
  - 2026-04-01: подписки Claude Max хватило примерно на 10 минут с пятью агентами; недельный лимит кончился за 3 дня [197].
  - 2026-05-24: первый же тестовый найм потратил примерно 760–780 тыс. токенов Sonnet на API key пользователя [203].
  - 2026-09-25: onboarding новичка разросся до 15, затем до 25 одновременных sessions и около 3 млн токенов [207]. Диагноз сообщества: цель компании читалась как рабочий заказ. Пробуждения цепляются друг за друга от назначений, комментариев, approvals и расписаний, поэтому org chart отлично умеет держать всех занятыми. Помогло: поставить на паузу всех агентов, кроме CEO, выключить пробуждения по таймеру и дать одну задачу с критериями приёмки и без права нанимать и создавать подзадачи [207].
  - 2026-10-21: пользователь, который говорит, что любит продукт, намерил около 54 тыс. токенов на один heartbeat и около 34 тыс. — только на проверку, есть ли у агента задачи [214].
- **Обходные пути, которыми делятся пользователи.**
  - Правило раннего выхода в skill heartbeat [200].
  - Контекст пробуждения прямо в prompt: примерно 11 тыс. → 1 тыс. токенов на пробуждение. Команда на 14 агентов добавила предварительную проверку «нет работы — не будить»: около 90% их heartbeats были пустыми [200].
  - Перевод большинства ролей на дешёвые модели: Codex, LM Studio или DeepSeek через OpenRouter [197][203].
  - Предупреждение: правка файла инструкций агента по умолчанию может сломать логику платформы [197].

#### Подписки (Claude Max, ChatGPT/Codex): budgets, лимиты и соединения

- **Budgets на подписках ничего не делают.**
  - Runs по подписке записываются как $0, поэтому денежные лимиты не срабатывают. Один агент Codex потратил 19.8 млн входных токенов за час, и ничто его не остановило (2026-03-08) [167].
  - Команды на Claude Max пишут то же: личная компания на 7 агентов, 5 агентов в RosterIQ, около 6 агентов у AirwayLab на Max 20x. Денежный budget на подписке с фиксированной ценой они называют бессмысленным [167][171].
  - На 2026.1106.0 это всё ещё так: комментарий от 2026-11-13 делится обходом через cron-скрипт [167].
  - Команда, которая ведёт на Paperclip свою компанию, увидела 80 runs меньше чем за 3.5 часа; 79 из них упали на одном и том же лимите usage, а страница Costs показывала $0 [212].
  - Так устроено намеренно: usage, включённый в подписку, в денежные budgets не входит [142][29].
- **Лимиты usage.**
  - Запрос от 2026-03-29 — повторять при сбросе лимита, а не каждый час — закрыт как исправленный 2026-07-21 [168].
  - В сентябре четыре агента остались в «error» после отказа по 5-часовому лимиту, даже когда окно сбросилось. В ноябре явный resume ошибку всё ещё не снимал [172].
  - Отказы по квоте в новой среде исполнения не распознаются, и агенты застревают без способа проснуться (2026-10-07). Месячный лимит расходов организации тоже не распознаётся как квота (2026-10-18) [182].
- **Что просят пользователи.**
  - Переключаться на другую модель, когда квота плана кончилась — 13 голосов [169].
  - Окна запуска: агенты работают ночью, а днём не трогают 5-часовой и недельный лимиты самого пользователя [183].
  - Виджеты dashboard для квот Claude (session и неделя) и балансов API [185].
- **Соединения Claude ломаются.**
  - Соединения по подписке переставали работать примерно через 8 часов после входа. Хранился только access token, refresh token — нет. Соединения Codex это не задевало. Сообщения от 2026-09-20 и 2026-09-26; второе закрыто 2026-11-04 [177][180].
  - Связанный отчёт: 33 из 33 heartbeats упали на мёртвом входе примерно за 11 часов [177][180].
  - На one-click установке Hostinger агенты Claude Code падают с общей ошибкой «terminal access failure» [179].
  - Встроенная среда Claude, которой Paperclip теперь управляет по ACP, не могла запускать новые модели, пока её не направили на установленный CLI пользователя [178].
  - На 2026.1106.0 вход на macOS не показывает ссылку авторизации. Несколько пользователей подтвердили это 2026-11-12 и 2026-11-13 [186].

#### Работа, которая молча останавливается

Многие самые обсуждаемые issues сентября–ноября описывают задачи, которые встают без видимого сигнала [181]:

- удержание восстановления блокирует задачу навсегда, а watchdog тем временем каждые 30 секунд добавляет дубликат;
- передача reviewer-у пропускается, и повтора нет;
- задачу невозможно восстановить после отмены, сделанной до запуска;
- длинные треды комментариев делают задачу непробуждаемой: payload пробуждения превышает лимит длины аргументов shell (один отчёт насчитал 139 молча мёртвых runs);
- агенты навсегда застревают в состоянии «pausing»;
- жёсткая остановка budget срабатывает при расходе $0.

Самые новые issues от 2026-11-12 и 2026-11-13 показывают ту же картину [87][181]. У компании, которая ведёт бизнес на Paperclip, parent-задача простояла заблокированной около 29 часов без связи с blocker-ом [212].

#### Рискованные настройки по умолчанию и нет жёстких правил

- **Права и sandbox.**
  - Adapter Claude по умолчанию запускает Claude без permission prompts [121].
  - Issue #21317 (2026-11-13): у adapter-а Codex sandbox bypass включён по умолчанию; агенты, нанятые по запросу других агентов, приходят на карточку approval человека уже с bypass [187]. Код `codex-args.ts` включает bypass только явно [122] — расхождение описано в разделе «Изоляция».
- **Secrets.** Скриншот показывает, как агент печатает раскрытое значение secret в log run-а (2026-06-05) [176].
- **Hooks и жёсткие правила** [211].
  - Пользователь, который переходит со своей схемы hooks в Claude Code, просит правила, которые нельзя обойти, а не просто инструкции.
  - Ответ объясняет: PreToolUse hooks Claude Code выполняются и при выключенных permission prompts; runs на соединениях под управлением Paperclip используют свою папку конфигурации; в sandbox попадает копия `settings.json` без hooks.
  - Другой пользователь считает, что жёсткий лимит должен быть в учётных данных, а не в prompt [211].
- **Принудительный commit trailer.** Встроенный skill добавляет `Co-Authored-By: Paperclip` в каждый коммит. Команды, которым важно авторство, просят выключатель (10 голосов) [174][100]. Исследование использования вендора считает как раз этот trailer [17].

#### Self-hosted, Cloud и Enterprise Edition

- **Enterprise Edition непонятна.** Панель Trust агента упоминает расширение прав из EE, которого пользователи self-hosted не находят. Страница EE в июле отвечала 404 [206].
- **Доступ к GitHub зависит от Paperclip Cloud.**
  - Чтобы подключить GitHub на self-hosted-инстанции, её надо записать в Paperclip Cloud; запасной вариант с personal access token спрятан [184].
  - Пользователь self-hosted пишет, что это калечит новые инстанции.
  - 2026-11-04 запись в Cloud не работала больше 8 часов, и агенты остались без доступа к Git [184].
- **Признания вендора.** Общедоступного hosted-продукта нет (Cloud — beta по приглашениям), native desktop-приложения нет [12].

### Сравнения с другими инструментами

  - Один пользователь получил от CEO-агента Paperclip ответ, что тот — всего лишь чат-бот без прав [163].

- **Своя схема hooks в Claude Code.** Ветка об ограничениях сравнивает с ней Paperclip и находит его слабее в принудительном соблюдении правил [211].

### Как вендор отвечает на отзывы

- **Чат.** В марте пользователь указал, что README называет Paperclip «не чат-ботом» [163]. Теперь README говорит «не просто чат-бот», а roadmap отмечает Agent Chat, включая чат с CEO-агентом, как доступный [76][77].
- **Несколько людей в одной инсталляции.** Основатель открыл ветку сбора спроса 2026-03-28. Часть пользователей возражала, что это ослабляет идею компании без людей [195]. Сейчас поддержка нескольких людей отмечена как сделанная [77]. Запросы поставить людей в org chart и заменить агента человеком набрали по 15 голосов [195].
- **Память.** Основатель сделал обзор инструментов памяти 2026-03-17. В июне пользователи всё ещё спрашивали о статусе [192]. Roadmap отмечает память как частично готовую: experimental-соединения с Mem0, Zep, Supermemory, Cognee и Honcho [77].
- **Исправления по запросам:** снижение расхода токенов — отчёт от 2026-03-13 [158]; повтор при сбросе лимита — закрыт 2026-07-21 [168]; изоляция worktree — закрыта 2026-08-18 [165].
- **Desktop-приложение.** PR сообщества с Electron не слит. Официальное приложение остаётся в планах [217][77].
- **Позиционирование** сдвинулось от компаний без людей к командам под надзором человека [75][1][219]. Недавние посты блога — об approvals, о работе без терминала и о запуске агентов на ночь [10].

## Слабые места и чего нет

- **Нет desktop-приложения.** Только web UI и PWA; есть неофициальная обёртка на Electron для macOS [5][76][225].
- **Нет push- и desktop-уведомлений и исходящих webhook-ов.** Toasts только внутри приложения, по своим задачам [24][59][159].
- **Общая рабочая папка по умолчанию.** Отдельные worktree — experimental и выключены [116][123]. Пользователи теряли remotes и полдня работы, когда агенты путали репозитории [173][170].
- **Нет встроенного test gate** (не подтверждено) [41][4]. По умолчанию сервер принимает заявление агента, что проверки прошли (`agent_claim_policy`) [104].
- **Лимиты — только реакция на сбой.** Paperclip узнаёт о лимите после упавшего run-а и не планирует работу под остаток лимита [136][140]. Распознавание квот даёт сбои [182][172].
- **Денежные budgets не видят подписки.** Usage подписки не входит в budgets, поэтому на Claude Max и подобных планах лимиты не срабатывают [142][167][171].
- **Большой расход токенов** на пробуждения и цепочки делегирования [191][207][214].
- **Работа встаёт молча:** удержания восстановления, пропущенные передачи reviewer-у, непробуждаемые задачи [181][212].
- **Трудно увидеть результат**, агенты заявляют «done» без работы [198][223].
- **Рискованные настройки по умолчанию.**
  - Claude Code — с `--dangerously-skip-permissions` [121][66].
  - Действия connectors стартуют как Allowed, включая разрушительные [56]. `git` и `gh` не попадают под Ask first [57].
  - Approval найма в базе по умолчанию выключен [152]. По issue #21317, Codex приходит на approval с bypass sandbox [187].
  - JWT run-а живёт 48 часов [147]. Агент напечатал secret в log [176]. В sandbox hooks пользователя удаляются из копии `settings.json` [211].
- **Нет SSO и MFA** [61].
- **Хрупкие соединения Claude:** подписка отваливалась через 8 часов [177]; на 2026.1106.0 вход на macOS не показывает ссылку авторизации [186].
- **Onboarding требует Codex или Claude Code** [209]. Локальные модели работают плохо [204][162].
- **Windows — второй сорт:** Runner не работает на Windows и Linux на musl [65]; `service` не работает на Windows [69]; баг с symlink открыт с марта [164].
- **Агенты строят только два уровня задач** [97].
- **Лимиты конкурентности на проект не применяются;** общего лимита на adapter нет [113][166].
- **Self-hosted зависит от Cloud** в подключении GitHub [184]. Цен Cloud нет (не подтверждено) [6]. Enterprise Edition не описана [206].
- **Принудительный trailer** `Co-Authored-By: Paperclip` в каждом коммите [100][174].
- **Здоровье проекта:** большая очередь issues и PR, мало слитых внешних вкладов, 25% красных CI runs на PR по стороннему подсчёту [87][216]. Почти каждый релиз ломает совместимость [3]. Логика собрана в очень больших файлах [75].
- **Нет визуального полотна, терминала и браузера для человека.** Терминал есть только в браузере для настройки своего образа sandbox [49][159]. Браузер — только connector Browser Use Cloud [81].
- **Нет автоматической смены модели** при исчерпании квоты [169].
- **Ticket systems пока только как tools,** не как источник задач [77].
- **Слой памяти не подтверждён** в коде [128].
- **Telemetry включена по умолчанию** [76].

## Пересечение с worfy

Термины worfy в этом разделе:

- Canvas — бесконечное полотно, на котором worfy показывает работу агентов.
- Epic — группа связанных Ticket-ов. Ticket — одна задача.
- Orchestrator — session, которая планирует и раздаёт Ticket-ы.
- Wave — набор Ticket-ов, которые запускаются вместе. Autopilot — запуск Wave-ов без человека.
- Gate — локальный запуск проверок перед PR.
- Harness — plugin, который приносит в Claude Code rules, skills, subagents и hooks.

### Где пересекаются

- **Тот же пользователь.** README Paperclip обращается к человеку с десятками открытых терминалов Claude Code [76]. worfy запускает и показывает sessions Claude Code и Codex CLI.
- **Те же агенты.** Claude Code и Codex есть в обоих продуктах [67].
- **Иерархия работы.** Paperclip: цели → проекты → задачи с подзадачами и blockers; Cases для долгой работы [19][24][47]. worfy: Epics из Tickets.
- **Агент-планировщик.** Paperclip: CEO-агент предлагает стратегию на approval и делегирует; Agent Chat превращает просьбы в задачи [22][45]. worfy: Orchestrator session планирует и раздаёт.
- **Работа без присмотра.** Paperclip: пробуждения по событиям и routines на сервере, круглые сутки; ограниченные повторы; ожидание сброса лимита [38][81][80][136]. worfy: Autopilot запускает Waves, ждёт сброса лимитов подписки и повторяет ошибки API.
- **Счётчики лимитов.** Paperclip: окна квот каждого аккаунта, Window spend, Check usage; строка Usage limit на задаче — в черновике релиза [29][53][80]. worfy: счётчики лимитов и расхода.
- **Permission prompts без человека.** Paperclip: bypass по умолчанию, режимы ACP, правила на действия connectors [66][65][56]. worfy: Autopilot одобряет permission prompts по политике.
- **Worktree, PR и CI.** Paperclip: experimental worktree на задачу; плашки PR и карточки PR с checks [39][24]. worfy: worktree на каждый Ticket, PR с CI badges.
- **Агенты-reviewer-ы.** Paperclip: стадии review с лимитом в 3 раунда и передачей человеку; GitHub review bot с check run [41][55]. worfy: reviewer subagents с review lenses — разными углами проверки.
- **Набор знаний для агента.** Paperclip: skills внедряются в run, библиотека skills, Skill Studio, файлы инструкций агента [36][35]. Своего слоя hooks для пользователя нет; Runner с `homeMode: "preconfigured"` берёт hooks машины [65]. worfy: Harness plugin с rules, skills, subagents и hooks.
- **Журнал работы без присмотра.** Paperclip: Work Timeline, журнал Audit, транскрипты runs [27][28][22]. worfy: Flight Recorder — лента событий автономного запуска; Work track — вся работа проекта по дням и неделям.
- **Другие машины.** Paperclip: окружения по SSH и хосты Runner; `--bind lan` и `--bind tailnet` [49][76]. worfy: Linked machines в локальной сети.
- **Карточки с результатами.** Paperclip: Status Cards и HTML-артефакты, показанные как страницы [46][33]. worfy: Cards, которые агенты строят на Canvas через MCP server.
- **Очередь PR.** Paperclip: очередь PRs в Decisions, плашки статуса PR [31][24]. worfy: PR inbox.

### Где расходятся

- **Форма продукта.** Paperclip — сервер с web UI и PWA для многих людей и многих компаний [76][61][81]. worfy — desktop-приложение на Electron для одного пользователя.
- **Экран.** У Paperclip нет полотна: только web-страницы — список или доска задач, дерево org chart, Timeline, Status Cards [24][35][27][46]. worfy — бесконечный Canvas.
- **Предмет.** Paperclip ведёт «компанию» для любых функций бизнеса; coding — один из случаев [76][1]. worfy — работа coding-агентов.
- **Проверка перед завершением.** У Paperclip нет локального запуска проверок; качество — через стадии review, заявления агента, watchdogs и monitors [104][105][130]. worfy: tests и локальный Gate на каждый Ticket.
- **Изоляция по умолчанию.** Paperclip — общий checkout, worktree experimental [116]. worfy — worktree на каждый Ticket.
- **Лимиты.** Paperclip реагирует на упавший run и не планирует под остаток [136][140]; пользователи просят окна запуска [183]. worfy планирует запуски под лимиты подписки и имеет Eco mode.
- **Права.** Paperclip выключает prompts CLI и проверяет права на своём API и tool gateway [108][57]. worfy одобряет prompts самого CLI по политике.
- **Деньги.** Paperclip: денежные budgets с жёсткой остановкой и резервированием [29][144]. В описании worfy денежных budgets нет; есть счётчики лимитов подписки.
- **Число сред агентов.** Paperclip: около десяти harnesses от разных вендоров и внешние ассистенты [67][50]. worfy: Claude Code и Codex CLI.
- **Где исполняются агенты.** Paperclip: локально, по SSH и в облачных sandboxes восьми и более провайдеров [49][68]. worfy: локально и на Linked machines в LAN.
- **Терминал и браузер.** У Paperclip их для человека нет; есть только терминал для образа sandbox и живые вкладки Browser Use Cloud [49][159][81]. worfy: Terminal с AI-помощником и встроенный Browser с профилями.
- **Продуктовый слой.** У Paperclip нет аналога Product Session, Mind map и критика spec. Ближе всего — approval стратегии CEO, режим Plan и Reflection Coach [20][25][73].
- **Доказательства.** Скриншотов-доказательств с privacy scrub у Paperclip нет; есть skill agent-browser со скриншотами и галерея Artifacts [74][33].
- **Eco mode** — у Paperclip не найден.
- **Чем Paperclip шире:** роли людей и много компаний [61][76]; найм агентов через approval и org chart [30][35]; каталог connectors за tool gateway [52]; каналы чата — Slack, Discord, Teams, Telegram, iMessage, голос [52]; облачные sandboxes [68]; PWA для телефона [81]; шаблоны компаний [85][37].

## Механизмы, которые стоит изучить

1. **Отложить run до сброса лимита — проверка перед стартом.**
   - Что это: функция `deferRunForProviderLimit`, которая решает, запускать ли run, до любой работы с workspace или провайдером [136].
   - Как работает: если runs агента за последние 24 часа падали с `rate_limit` или `quota_exhausted`, новый run отменяется, а повтор назначается на время сброса [136][137]. Время сброса берётся из поля `retryAt` или из текста провайдера — например, из сообщения Codex «try again at …» [138][161]. Если время неизвестно — ожидание 1 час, максимум — 24 часа. Успешный run стирает старые свидетельства [134][137]. Ручные runs, разговоры, восстанавливающиеся runs и пулы аккаунтов проверку обходят [136]. Черновик v2026.1113.0 показывает это на задаче как состояние «Waiting for usage limit reset» и строку вроде «5h 78% · resets 15:40» [80].
   - Чем интересно: одна дешёвая проверка до старта заменяет серию упавших runs; список исключений явный.
   - Источник: [136][137][138][161][80].
2. **Окна квот и пул аккаунтов с выбором по использованию.**
   - Что это: чтение лимитов подписок и распределение задач по нескольким аккаунтам [139][44].
   - Как работает: квота Claude читается с `api.anthropic.com/api/oauth/usage` — окна `five_hour`, `seven_day`, `seven_day_sonnet`, `seven_day_opus`, `extra_usage`; для Codex есть похожее чтение [139]. Страница Costs показывает процент, время сброса и расход внутри окна (Window spend) [29]. Router выбирает аккаунт по кругу или по использованию: аккаунты с 90% и выше пропускаются, на проверку — 15 секунд, данные свежи 60 секунд [44][141]. Задача закреплена за одним аккаунтом. Когда все аккаунты за лимитом, задача показывает «Pool exhausted» и ждёт, не тратя бюджет повторов [44].
   - Чем интересно: закрепление задачи за аккаунтом сохраняет session и кэш, а исчерпание пула не считается ошибкой.
   - Источник: [139][29][44][141].
3. **Допуск пробуждения одной чистой функцией.**
   - Что это: правило, что делать с новым пробуждением, если по задаче уже идёт run [99].
   - Как работает: каждое пробуждение — строка с `idempotencyKey` и счётчиком `coalescedCount` [94]. Функция `decideWakeAdmission` возвращает coalesce (влить в живой run), defer (ждать) или proceed (запускать). Комментарии в очереди можно переупорядочить или отбросить и доставить пачкой [99]. В UI это кнопки Wait, Steer и Interrupt [24].
   - Чем интересно: вся логика гонок пробуждений сведена в одну функцию без I/O, которую легко покрыть tests; кнопки UI прямо соответствуют её исходам.
   - Источник: [94][99][24].
4. **Atomic checkout одним условным UPDATE.**
   - Что это: захват задачи агентом без отдельного lock-сервиса [112].
   - Как работает: один `UPDATE … WHERE status IN (expected) AND (assignee IS NULL OR same) AND <lock free> RETURNING`; нет строки — `409` [112]. Право исполнять (`checkoutRunId`) и живой run (`executionRunId`) хранятся раздельно. При завершении lock очищается, только если всё ещё указывает на этот run (compare-and-clear); устаревший lock чинится, только если run-владелец завершён или пропал [101]. Skill агента запрещает повторять запрос после 409 [100].
   - Чем интересно: гонка двух агентов за одну задачу решается базой за один запрос, а завершение старого run-а не может снять чужой lock.
   - Источник: [112][101][100].
5. **Завершение — типизированный вызов, статус решает сервер.**
   - Что это: в native-режиме агент сообщает итог вызовом tool, а не текстом, и сервер проверяет его [102][104].
   - Как работает: run получает только разрешённые ему semantic actions; права проверяются на каждом вызове [102]. Ход должен закончиться ровно одним `paperclip_finish` или `paperclip_block`; иначе runtime добавляет корректирующий ход [103]. Сервер считает результат недоверенным заявлением: классифицирует доказательства как `accepted`, `missing`, `rejected` или `unverifiable`, выбирает статус чистой функцией и фиксирует его в транзакции [90][104]. Строгий режим требует принятого доказательства для каждого критерия; по умолчанию действует `agent_claim_policy`, которая верит агенту [104].
   - Чем интересно: граница между «агент сказал» и «система приняла» проведена в коде, и строгость можно выбирать.
   - Источник: [102][103][104][90].
6. **Стадии review с перехватом «done» и лимитом раундов.**
   - Что это: execution policy — цепочка review и approval перед завершением задачи [105][41].
   - Как работает: когда исполнитель ставит done, runtime переводит задачу в `in_review` и назначает reviewer-у; исполнитель в стадиях не участвует [105]. «Changes requested» возвращает задачу исполнителю и потом в ту же стадию. Решает только текущий участник, остальные получают `422`; решение требует комментария в том же запросе [105]. После трёх раундов между агентами (`maxReviewRounds`, до 50) review уходит человеку [41]. GitHub review bot превращает оценку в check run «Paperclip Review» с порогом [55].
   - Чем интересно: число раундов между агентами ограничено, и эскалация к человеку встроена в саму политику.
   - Источник: [105][41][55].
7. **Watchdog дерева задач и сигнал тихого run-а.**
   - Что это: агент-проверяющий для остановившейся работы и счётчик тишины [40][130].
   - Как работает: watchdog просыпается, только когда остановились все листья дерева, и проверяет каждую остановку как утверждение: снова открывает работу или подтверждает blocker [40][130]. Run без вывода помечается `suspicious` через 5 минут и `critical` через 15, но не отменяется [101]. Ожидание внешнего события (checks, CI, deploy) — разовое пробуждение `issue_monitor_due`, которое надо ставить заново [101].
   - Чем интересно: остановка дерева задач проверяется отдельным агентом, а не принимается на веру. Пользователи при этом видели, как watchdog каждые 30 секунд плодит дубликаты на застрявшей задаче [181].
   - Источник: [40][130][101][181].
8. **Ограниченное восстановление как отдельные записи.**
   - Что это: восстановление после сбоев с явным владельцем и пределом попыток [101][135].
   - Как работает: брошенная задача получает одно автоматическое пробуждение; если не помогло — `blocked` и действие восстановления, которым владеет board; исполнитель не меняется [101]. Намеренное ожидание без цели чинится 5 раз: сразу и через 60, 120, 240 и 480 секунд, по отпечатку состояния задачи [101]. Действие восстановления хранит тип, владельца и доказательства; UI пишет «Trying again in …» и «Retry available» [24]. Retry продолжает в том же worktree с новой session, если это безопасно, иначе начинает изолированную попытку с подсказками `priorWorkspace`; idempotency key защищает от двойного нажатия [135].
   - Чем интересно: каждый автоматический повтор ограничен, а дальше работа переходит к человеку как видимая запись, а не теряется.
   - Источник: [101][135][24].
9. **Протокол Runner с журналом исходящих событий.**
   - Что это: протокол между сервером и процессом `paperclip-runnerd` на Rust (PRP v1) [90].
   - Как работает: WebSocket на `/api/runner/v1/connect/:runId`; схема описана JSON Schema, реализации на TypeScript и Rust сверяют parity tests [90]. Runner сохраняет каждое событие до отправки, сервер подтверждает накопленный курсор, ID команд идемпотентны — после переподключения события повторяются без повторных последствий [90]. Runner получает не API key, а одноразовый bootstrap ticket, привязанный к компании, агенту, задаче, run-у и артефакту [90]. Исчерпанные лимиты переподключений и времени завершают run с классифицированной ошибкой [90].
   - Чем интересно: обрыв связи между процессом агента и сервером не теряет и не дублирует события; права runner-а сужены до одного run-а.
   - Источник: [90][92].
10. **Очередь Decisions с проверкой устаревания.**
    - Что это: очередь решений, которые агенты предлагают человеку [31].
    - Как работает: если затронутые задачи изменились после предложения, решение помечается «1 target changed since this was proposed». Разрушительный вариант требует ввести идентификатор задачи. Решения без ответа истекают через 7 дней. Очереди разделены: PRs, Plans и Questions [31]. Рядом — Blocked inbox с метками причин и сортировками «Most urgent» и «Longest stopped» [32].
    - Чем интересно: человек видит, что предложение агента могло устареть, прежде чем его принять.
    - Источник: [31][32].
11. **Work Timeline.**
    - Что это: диаграмма Gantt работы агентов [27].
    - Как работает: по линии на агента или автоматизацию; наведение на полосу рисует передачу работы следующему агенту; диапазоны Today, 7 и 30 дней или свой до 31 дня; zoom и minimap [27].
    - Чем интересно: отвечает на вопрос «что происходило ночью» одной картинкой, с передачами между агентами.
    - Источник: [27][81].
12. **Жизненный цикл worktree: очистка, expiry и restore points.**
    - Что это: правила, как workspaces задач создаются и убираются [79][39].
    - Как работает: дочерняя задача всегда получает workspace от базы проекта, а не от неслитых изменений parent [101]. Через час после завершения дерева удаляются восстанавливаемые папки (`node_modules`, `dist`, `target`). По желанию законченные worktrees удаляются через 24 часа и восстанавливаются на точном коммите, если задачу открыли снова. По желанию encrypted restore points сохраняют незакоммиченную работу перед очисткой [79]. Adapters и сам Paperclip никогда не делают push из workspace [39][119].
    - Чем интересно: место на диске освобождается без потери возможности вернуться к задаче.
    - Источник: [79][39][101][119].
