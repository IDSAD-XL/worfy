## Модель работы

### Три слоя продукта

1. **Warp desktop app.** Терминал, который вендор называет ADE — agentic development environment, «среда разработки с агентами». Внутри — встроенный Warp Agent и поддержка сторонних CLI-агентов, например Claude Code и Codex [1][2].
2. **Automation Platform (бывшая Oz).** Запускает облачных агентов по триггерам, по расписанию, из интеграций и через API [1][19]. Новые командные сценарии документация направляет в Factories [8][6].
3. **Warp Factories.** Вендор описывает их как «open, flexible infrastructure for building your own software factory». Software factory у Warp — набор агентов, который сам ведёт задачи команды от запроса до PR. Factories построены на Automation Platform. Каждый run агента фабрики — обычный облачный run [22][1].

### Local, cloud или hybrid

Hybrid. По частям:
- **На машине пользователя.** Агенты работают в окне desktop-приложения. Сторонние CLI (Claude Code, Codex и другие) идут в обычных панелях терминала [52].
- **Цикл встроенного агента идёт на сервере Warp.** Модель вызывается через серверный «multi-agent API» — protobuf поверх SSE (server-sent events, поток событий от сервера к клиенту). Инструменты выполняются на клиенте или в sandbox [128]. Даже со своим ключом (BYOK) запросы проходят через серверы Warp [136].
- **Облако Warp.** Отдельная sandbox на каждый run [38]:
  - Linux — новый Docker-контейнер на каждый run. Архитектура x86-64 или aarch64. Образ по умолчанию — `warpdotdev/dev-base:latest`. Внутри можно запускать Docker и виртуальные машины KVM, например эмулятор Android.
  - macOS — новая VM на Apple Silicon на каждый run. Версии 14, 15, 26 или 27, по умолчанию 26. Установлены Xcode и симуляторы iOS, watchOS и tvOS.
  - Windows — новая VM на каждый run. Только x86-64. Команды настройки пишутся на PowerShell.
- **Self-hosted (Enterprise).** Управляемый worker `oz-agent-worker` держит только исходящее соединение с control plane Warp [41]:
  - Backends: Docker, Kubernetes, Direct (прямо на хосте), Command (передаёт задачу во внешний API заданий) и одноразовый Direct.
  - У Warp остаются данные control plane: конфигурация, метаданные run, logs и биллинг.
  - Transcripts и artifacts можно хранить в своём bucket.
- **Unmanaged.** Команда `oz agent run` внутри своего CI или dev-окружения [6].
- **Handoff.** Разговор можно перенести с машины в облако, из облака в облако и обратно на машину [12].

### Агенты и модели

- **Локальные агенты.** Warp Agent и 16 распознаваемых CLI-агентов: Claude Code, Codex, OpenCode, Amp, Auggie, Copilot CLI, Cursor CLI, Gemini CLI, Droid, Pi, Goose, Antigravity, Hermes, Mistral Vibe, Grok Build и Kiro CLI [52].
- **Облачные harness.** Harness здесь — программа-агент, которая ведёт цикл «модель → инструменты». Документация называет три: Warp Agent (`oz`), Claude Code (`claude`, псевдоним `claude-code`) и Codex (`codex`) [29].
  - Доступ к сторонним harness зависит от тарифа. Админ может отключить harness для всего workspace [29].
  - Источники расходятся в списке. Маркетинговая страница Factories называет ещё Cursor [90]. Документация — только три [29]. В коде есть пути для Gemini, Pi (только через ACP) и OpenCode [128]. Доступны ли они пользователям — не подтверждено.
  - При запуске Oz облачная оркестрация поддерживала только агента Warp. Так ответил инженер Warp на Product Hunt [163]. Claude Code и Codex появились в облаке в мае 2026. Пост в блоге Warp датирован 2026-05-19 и сам называет multi-harness бетой [108]; статья SD Times — 2026-05-20 [165]. На 2026-11-13 строка тарифа Free на странице цен всё ещё говорит «Use any harness in the cloud (beta)» [89].
- **Модели.** Автоматический выбор модели, модели OpenAI, Anthropic, Google, xAI и открытые модели на хостинге Warp; свои routers; свой inference [73][77][74]. Подробности — в разделе «Функции → Модели и inference».
- **Подписки.** Облачные run Claude Code и Codex оплачиваются через API-ключи, а не через подписки Claude или ChatGPT [30][31][74].

### Один пользователь или команда

Продукт ориентирован на команды:
- Factories требуют команду и роль admin или Editor [46].
- Интеграции и общие secrets требуют команду. Self-hosting требует ещё и Enterprise [18].
- Admin Panel задаёт для всей организации autonomy агентов, denylists, redaction, telemetry и расходы [88].
- Enterprise добавляет SSO через Okta, Entra или Google, Analytics API, SOC 2 Type II и zero data retention у провайдеров моделей [87].

Один пользователь без команды получает desktop-приложение, локальных агентов и облачные run через CLI и API [18].

### Платформы

- **Desktop:** macOS, Windows и Linux. Для Linux есть пакеты .deb, .rpm и pacman, каждый для x64 и ARM64. Установка через Homebrew, WinGet или загрузку с сайта. Приложение обновляется само [3].
- **Warp Agent CLI (`warp`).** Отдельная программа: Warp Agent в любом терминале, в том числе по SSH, без установленного приложения [55].
- **Oz CLI (`oz`).** Запускает облачные run, управляет расписаниями, secrets, runners и интеграциями. Используется из скриптов и CI [8][6].
- **Web.** oz.warp.dev и platform.warp.dev [16][27]. Общие sessions открываются в браузере без установки. Changelog называет эту сборку «Warp on Web» и «WASM conversation viewer» [15][4].
- **Телефон — только через браузер.** Страница Runs в Oz web app «also works on mobile devices». Ссылки Remote Control открываются на телефоне [9][54]. Нативного мобильного приложения в документации нет (не подтверждено).
- **IDE.** Маркетинговая страница обещает управление «from web, mobile, terminal, or IDE» [90]. Расширения для IDE в документации не найдено (не подтверждено).
- **Программный доступ:** REST «Warp Platform API» со спецификацией OpenAPI; SDK для Python и TypeScript (`warp-platform-sdk`, `@warp-dot-dev/warp-platform-sdk`); hosted Factory MCP server (MCP — Model Context Protocol, протокол инструментов для агентов) [8][28].

## Функции

Функции сгруппированы по частям продукта. Где поведение известно из кода, а не из документации, это сказано рядом.

### Терминал

- **Поле ввода как в текстовом редакторе.** Обычные сочетания клавиш macOS, многострочная правка, несколько курсоров, режим vim, отдельные блоки для ввода и вывода, автодополнение. «Warpify» включает эти возможности в SSH-сессии. Пользователи хвалят это поле больше всего [150][151][152][153].
- **Классификатор «команда или запрос».** Warp угадывает, что ввёл пользователь: команду shell или запрос к агенту. Пользователи пишут, что он ошибается в обе стороны [152].
- **Агент в новой вкладке.** Новая вкладка по умолчанию открывает агента; это настраивается [152].
- **Настройки в файле TOML** — с апреля 2026 [4][128].
- **Уровни настройки.** От простого терминала до полного ADE [106].
- **Warp Drive.** Общие для команды rules, конфигурации MCP, prompts и workflows [99].

### Warp Agent — встроенный агент

- **Agent Profiles** [60]. Профиль задаёт основную модель, модель для планирования, доступ к инструментам и MCP и autonomy для каждого вида действий.
  - Виды действий: применить diff, читать файлы, составить план, выполнить команду, работать с уже запущенной командой, задать вопрос.
  - Уровни: Agent Decides, Always ask, Always allow, Never.
  - Allowlist и denylist команд — регулярные выражения. Denylist сильнее остальных настроек.
- **Run until completion** (⌘+Shift+I) [60]. Одобряет всё до конца текущей задачи. По умолчанию обходит и пользовательский denylist; отдельная настройка это выключает. Denylist, заданный админом, действует всегда.
- **Планирование.** `/plan` создаёт план — документ с форматированием. Каждая правка агента создаёт новую версию. Есть история версий и выполнение выбранных частей плана [61].
- **Task lists.** Для многошаговых запросов список задач создаётся сам. У пунктов — живые статусы и отметки о выполнении [62].
- **Очередь prompts.** Переключатель авто-очереди, команда `/queue`, панель очереди с перестановкой пунктов. Пока идёт долгая команда, новые prompts встают в очередь сами [67].
- **Fork разговора** с любого места. Fork сохраняет модель и профиль [68].
- **Вопросы агента.** Карточки с вариантами ответа: один или несколько вариантов, ответ «Other», пропуск. Включается разрешением «Ask questions» [69].
- **Full Terminal Use.** Агент подключается к интерактивным программам — psql, vim, gdb, dev-серверам — и читает и пишет в живой PTY (pseudo-terminal, программный терминал) [63].
- **Разговоры в облаке.** Включаются в Settings > Privacy. Разговор доступен на разных устройствах, им можно поделиться по ссылке с правами доступа, его можно смотреть в web и продолжить локально [70].
- **Rules.** `AGENTS.md` (или `WARP.md` для совместимости) в корне репозитория и в подпапках, плюс глобальные rules [65].
- **Skills.** Ищутся в `.agents/skills/`, `.warp/skills/`, `.claude/skills/`, `.codex/skills/`, `.cursor/skills/` и папках других инструментов [64].
- **Interactive code review.** Комментарии к diff собираются пачкой и уходят агенту [71][79].
- **Agents 3.0** (ноябрь 2025) добавил Full Terminal Use, `/plan` для работы по спецификации, interactive code review и интеграции со Slack и Linear [5][103].
- **Подписка ChatGPT для локального Warp Agent.** В changelog — 2026-09-23 [4], пост в блоге — 2026-09-29 [122]. Если OpenAI отклоняет запрос, Warp предлагает Try again, Manage ChatGPT usage или «Continue with Warp credits» [74]. Подписка SuperGrok тоже подключается [76].

### Warp Agent CLI

- **Что это.** Отдельная программа `warp`: Warp Agent в любом терминале, в том числе по SSH, без приложения. Программа сама держит терминальную сессию внутри себя (свой PTY multiplexer) [55]. Вышла 2026-08-04 [115].
- **Чем отличается, по словам Warp.** Инженер Warp на HN: команды идут на переднем плане — `cd`, REPL, SSH без установки чего-либо на удалённой машине [152].

### Сторонние CLI-агенты («universal agent support»)

- **Распознаются 16 агентов** — список выше [52]. Поддержка появилась 2026-04-14 [105].
- **Что работает для всех из списка** [52]:
  - редактор ввода с форматированием (Ctrl-G);
  - inline-комментарии code review, которые отправляются в работающий агент;
  - код как вложение в контекст;
  - метаданные агента в вертикальных вкладках;
  - Tab Configs;
  - Remote Control.
- **Уведомления агента** работают только для Claude Code, Codex и OpenCode, плюс Antigravity через structured notifications [52].
  - Claude Code — через plugin. Ставится кнопкой-чипом в один клик или командой `/plugin install warp@claude-code-warp` [53].
  - Codex — строка `notification_condition = "always"` в секции `[tui]` файла `~/.codex/config.toml` [56].
- **Как работает plugin для Claude Code** [130]:
  - Скрипты hooks шлют JSON через escape-последовательности OSC 777 (служебные последовательности терминала) на адрес `warp://cli-agent`.
  - README перечисляет шесть hooks: SessionStart, Stop, Notification, PermissionRequest, UserPromptSubmit, PostToolUse. В `hooks.json` на коммите `b32182f9` есть ещё StopFailure [130].
  - Событие Stop сообщает о незаконченных фоновых задачах и запланированных пробуждениях. Так Warp отличает «закончил» от «ждёт фоновую работу».
- **Переход к ожидающей сессии.** Shift+Cmd+J переключает на ту сессию Claude Code, которая ждёт ввода (так пишет пользователь) [151].
- **Главное ограничение.** Sessions Claude Code, Codex и других сторонних агентов не попадают ни в Conversation Panel, ни в Agent Management Panel. Их видно только в их панели, в вертикальных вкладках и через Remote Control [52][53].
- **Открытые запросы на GitHub** на 2026-11-13:
  - #14720 — восстанавливать разговоры CLI-агентов (Claude Code и других) по проекту после перезапуска [140];
  - #9295 — показывать Claude Code Agent Teams в разделённых панелях [142];
  - #8579 — свои обёртки (wrappers) для сторонних CLI-агентов, 11 голосов «+1» [141].

- **Появление.** Запись changelog от 2025-06-20: «New Agent Management Panel to monitor, multitask, and intervene across multiple agents», вместе с настройками autonomy и уведомлениями агентов [5]. Пост Warp 2.0 от 2025-06-24 описывает интерфейс управления параллельными агентами с уведомлениями [99].
- **Что в списке.** Локальные интерактивные разговоры Warp Agent и облачные run [9].
- **Вкладки.** «Personal» — всё, что принадлежит пользователю. «All» добавляет run, которыми поделились коллеги; по документации, «right now, this only includes things triggered from integrations» [9].
- **Поля строки** [9]:
  - источник: Interactive, CLI, API, Slack/Linear, Scheduled;
  - статус: Working; Blocked (ждёт ввода или обязательного шага); Canceled (только для интерактивных); Failed/Errored; Success;
  - длительность — только для облачных run.
- **Фильтры:** источник, день, автор, статус [9].
- **Клик по строке.** Облачная строка открывает общую session: prompt, план, команды, logs, результаты. Интерактивная строка открывает локальный разговор [9].
- **Оркестрация.** Локальные дочерние агенты своих строк не получают. Они видны в «orchestration pill bar» над родителем — полоске с живыми значками статуса. Облачные дети получают свои строки. Статус родителя отражает только его собственную работу, поэтому детей нужно проверять по одному [9].
- **Blocked для работы без человека.** Сторонний harness, которому без присмотра понадобился ввод, заканчивает run статусом Blocked, а не ждёт вечно [9][4].
- **Место продукта.** Warp пишет, что это наблюдение за run и sessions, а «not a replacement for full APM, OpenTelemetry» [9].
- **Web-версия.** Страница Runs в Oz web app выполняет ту же роль и работает на телефоне [9].
- Где именно панель находится в окне по текущей документации — не подтверждено.

### Уведомления

- **Виды:** Complete; Request (одобрение, разрешение или простой агента в ожидании); Error [56].
- **Toasts.** Одновременно видно не больше двух. Клик переводит в нужную session [56].
- **Notification mailbox** — открывается значком колокольчика. Фильтры: All tabs, Unread, Errors. Есть «отметить всё прочитанным» и навигация с клавиатуры [56].
- **Другие сигналы.** Значки статуса на вкладках с отметкой «нужно внимание». Системные уведомления ОС, когда Warp в фоне [56].
- **Оркестрация.** Уведомления в приложении приходят только по родительскому разговору; по детям — нет [56].

### Вертикальные вкладки, Tab Configs, worktrees, Code Review

- **Вертикальные вкладки** [80]:
  - для каждой панели: рабочая папка, ветка git, значок статуса агента (в работе, готово, ошибка, отменён, заблокирован), статистика diff, значок PR, точка «не прочитано»;
  - режим «Summary» сводит все панели вкладки в одну сводку;
  - карточка с деталями при наведении; поиск; перетаскивание;
  - меню «+» создаёт вкладки агента, облачные sessions и worktree configs.
- **Tab Configs** [81]:
  - файлы TOML: папка, команды при старте, раскладка панелей, тема;
  - «New worktree config» создаёт config на основе worktree;
  - шаблон `{{autogenerated_branch_name}}` создаёт новую ветку worktree при каждом открытии;
  - config открывается по адресу `warp://tab_config/...`.
- **Git worktrees** распознаются сами. У каждого worktree свой Code Review panel, свой Git chip (значок ветки) и свой индекс кода [78].
- **Code Review panel** [79]:
  - diff: незакоммиченные изменения, сравнение с main или с любой веткой;
  - откат отдельных hunks; diff можно приложить к контексту агента;
  - inline-комментарии собираются пачкой и уходят Warp Agent или поддерживаемому CLI-агенту [71][79].

### Общий доступ и Remote Control

- **Agent Session Sharing** [72]:
  - несколько человек смотрят и правят одну session, у каждого свой курсор;
  - работает из приложения, из браузера и с телефона.
  - Secret redaction (скрытие secrets в выводе) в общих sessions не применяется [86].
- **Remote Control** для сторонних агентов [54][4]:
  - чип `/remote-control` публикует session в облако и копирует ссылку;

  - отозвать доступ или остановить публикацию может только тот, кто опубликовал;
  - вход по QR-коду добавлен 2026-05-27 [4].
- **Всё идёт через облако Warp.** Режима прямой связи по локальной сети не найдено (не подтверждено).

### Automation Platform (бывшая Oz): облачные агенты

#### Запуск run

- **Способы запустить run** [30][16][20][21][19]:
  - Cloud Mode в приложении Warp, с выпадающим списком «Agent harness»;
  - форма «New run» в Oz web app: Quick run от своего имени или сохранённый агент;
  - команда `oz agent run-cloud`;
  - REST API или SDK;
  - расписание cron — каждый запуск по расписанию начинается с нуля с одним и тем же prompt [21];
  - упоминание в Slack, Linear или Jira [19];
  - упоминание `@warp-agent` на GitHub;
  - GitHub Actions через `oz-agent-action` [20].
- **Skills как агенты.** Skill можно запустить как самостоятельного облачного агента — это было в запуске Oz [104].
- **От чьего имени идёт run** [17]:
  - с личным ключом run выполняется от имени пользователя;
  - с API-ключом агента run выполняется от имени облачного агента; в CLI и API это service account (служебная учётная запись);
  - у каждой команды с самого начала есть облачный агент по умолчанию.
- **Что требует команды** [18]:
  - один пользователь без команды может запускать облачных агентов через CLI или API;
  - интеграции, общие secrets команды и self-hosting требуют команду;
  - self-hosting требует ещё и Enterprise.

#### Harness и учётные данные

- **Три harness:** Warp Agent (`oz`), Claude Code (`claude`, псевдоним `claude-code`), Codex (`codex`) [29].
- **Доступ по тарифу.** Сторонние harness доступны не на всех тарифах. Админ может отключить harness для workspace [29].
- **Учётные данные Claude Code в облаке** [30][32]:
  - подходят Anthropic API key, Anthropic Bedrock API key или access key для Bedrock;
  - агенты фабрики могут брать только secrets уровня команды; разовые run — и личные.
- **Учётные данные Codex в облаке** [31][32]:
  - подходит только OpenAI API key;
  - документация: «A local Codex subscription sign-in is not this managed-secret credential». Вход через ChatGPT — «a different authentication path» [32][30].
- **Подписки не оплачивают облачные run.** «A ChatGPT subscription doesn't fund cloud agent runs» [74]. Облачные run Claude Code и Codex идут через оплату API, а не через подписки Claude или ChatGPT [30][31].
- **Оплачиваемое время.** Для Claude Code и Codex в него входит выполнение команд и ожидание ответа модели. Для Warp Agent — только генерация ответа [83].

#### Environments и runners

- **Environment** — окружение облачного run. При запуске sandbox клонирует репозитории, выполняет команды настройки и получает только разрешённые secrets [7]. Oz запускался с окружениями на Docker [104]. Окружения задаются на странице Environments в Oz web app [16]. Подробно о sandbox по ОС — в разделе «Модель работы» [38].
- **Ограничение на настройку.** Если команда настройки завершилась с ненулевым exit code или шла дольше 30 минут, run падает [38].
- **Runner** задаёт ОС, архитектуру, образ, число vCPU и память. На Enterprise — до 32 vCPU и 64 GiB [39]. Runner по умолчанию в примере Warp — 4 vCPU, 8 GB, `ubuntu:24.04` [131].
- **Лимит параллельных run на команду.** Run сверх лимита ждут в очереди [39]. Число в документации не названо (не подтверждено). Заметки здесь расходятся: одна нашла этот лимит на странице про хостинг Warp [39], другая пишет, что лимиты параллельности для облака Warp не документированы.
- **Метаданные run.** До 20 строковых ключей. Они становятся переменными окружения `WARP_METADATA_*`, которые читают скрипты настройки [25].
- **Заранее прогретые sandbox.** Sandbox готовят заранее и держат до назначения run (подробно — во «Внутреннем устройстве») [128]. С 2026-10-22 возобновлённые run берут такие sandbox [4]. Прогретая настройка не получает метаданных конкретного run [25].
- **Жёсткий срок жизни sandbox.** На бесплатном тарифе он фиксирован, на платных настраивается. Когда срок истекает, run получает статус FAILED [128].

#### Self-hosting (Enterprise)

- **Worker `oz-agent-worker`** (Go, MIT) [41][132]:
  - сам открывает соединение WebSocket наружу, входящие порты не нужны;
  - backends: Docker, Kubernetes Job, Direct (общий kernel с хостом), Command (передаёт задачу внешнему оркестратору), одноразовый Direct;
  - `max_concurrent_tasks` ограничивает число задач на одной машине;
  - в каждый контейнер задачи монтируется «sidecar image», который «contains the warp agent binary» [132][40];
  - отдаёт traces и logs в формате OpenTelemetry (OTLP) [132].
- **Worktree на задачу для Direct backend.** Рецепт Warp: один worktree на задачу из общего clone без checkout, создаётся и удаляется hooks настройки. Ветка — `warp-agent/<run_id>`. В примере на хост — `max_concurrent_tasks: 4`. Документация прямо пишет, что так изолируются файлы и ветки, «not the host OS» [42].
- **Где лежат данные.** У Warp — конфигурация, метаданные run, logs и биллинг. Transcripts и artifacts можно держать в своём bucket [41].

#### Оркестрация: родитель и дети

- **Форма.** Один родитель и его дети, ровно один уровень [10]. У каждого ребёнка свой run, свой transcript и своя оплата [10].
- **Где кто работает** [10]:
  - локальный родитель → локальные дети;
  - локальный → облачные;
  - облачный → облачные;
  - облачный → «cloud-local» дети, которые делят sandbox родителя.
- **Разные harness.** Родитель на Warp Agent может запускать детей на Claude Code или Codex, и наоборот [10].
- **Сообщения** [10]:
  - надёжная шина сообщений на сервере; у каждого агента свой inbox;
  - события жизненного цикла: INPROGRESS, SUCCEEDED, FAILED, BLOCKED, ERROR, CANCELLED; родителю не нужно опрашивать детей;
  - законченного ребёнка можно «разбудить» новым сообщением.
- **Описанные схемы:** supervisor/worker, fan-out/fan-in, critic/verifier, review swarm (много рецензентов), DAG, swarm. Warp советует давать каждому агенту свой git worktree [10].
- **Как начать** [11]:
  - `/orchestrate` сначала предлагает разбивку: сколько детей, их prompts и окружения. Пользователь должен её одобрить;
  - `/plan` может содержать блок конфигурации оркестрации с выбором модели, harness, окружения, хоста, параллельности и авторизации;
  - к партии детей или к одному ребёнку можно прикрепить теги метаданных;
  - в API то же делается полем `mode: orchestrate|plan`. Пока человек не одобрил, ничего не запускается; одобрение фиксирует конфигурацию всего run [10][11].
- **Отмена.** Отмена родителя не отменяет детей. Это сделано намеренно [11].
- **Как участвует Claude Code.** В облачные окружения сам ставится plugin `oz-harness-support`. Он через hooks передаёт сообщения родителя в session Claude Code [130]. В README названы skills `oz-finish-task`, `oz-report-pr`, `oz-notify-user`, `oz-upload-file` и `factory-files`. В коде на коммите `b32182f9` есть ещё skill `oz-child-agent-orchestration` [130].

#### Handoff, snapshots, устойчивость

- **Направления handoff** [12]:
  - с машины в облако — fork разговора и snapshot отслеживаемых и неотслеживаемых изменений;
  - из облака в облако — продолжение после конца session, с восстановленным workspace;
  - из облака на машину — «Continue locally» или `/continue-locally`; изменения workspace локально не применяются.
- **Только для Warp Agent.** Перенос с машины в облако работает только для Warp Agent, не для sessions сторонних CLI [12]. Функция появилась 2026-05-18 [4].
- **Частичный перенос.** Если часть изменений не применилась в облаке, Warp сообщает об этом и продолжает с остальным [13].
- **Автоматический handoff при сне Mac.** Если настройка включена и macOS уходит в сон, активный локальный run агента уходит в облако. Это видно в коде; подробности — во «Внутреннем устройстве» [128].
- **Snapshots** [14]:
  - снимаются в конце run и при первом SIGTERM или SIGINT;
  - что снимать, решает скрипт деклараций; по умолчанию — каждый git-репозиторий в workspace.
- **Устойчивость в changelog 2026** [4]:
  - 2026-08-27 — повтор при обрыве соединения посреди потока; run всегда сообщают конечный статус;
  - 2026-09-02 — debug-агент можно запустить в сохранённой session run, у которого упала настройка окружения;
  - 2026-10-15 — периодические checkpoints для handoff во время run;
  - 2026-10-22 — возобновлённые run берут заранее прогретые sandbox.
- **Каталог ошибок.** Ошибки описаны по имени, например `budget-exceeded`, `insufficient-credits`, `environment-setup-failed`, `infrastructure-timeout`, `external-authentication-required` [22].

#### Просмотр и управление run

- **Общая облачная session** [15]:
  - видны все команды, logs, план и task list, artifacts и diffs;
  - пока VM жива, зрители могут писать follow-up и после завершения;
  - когда VM выключилась из-за простоя, «Fork to local» переносит разговор на машину пользователя.
- **Сколько живёт законченная session.** Параметр `idleTimeoutMinutes`: 10 минут по умолчанию, 60 для детей оркестрации [37]. У worker для oz CLI по умолчанию 45 минут [132].
- **Страницы Oz web app** [16]:
  - Runs, Agents, Skills, Schedules, Environments, Secrets, Integrations;
  - быстрые фильтры: All, Mine, Active, Failed, Recurring;
  - у run видны стоимость или credits и artifacts;
  - вкладка «Sub-agents» показывает дочерние run.
- **API** отдаёт состояние run, нормализованный разговор, сырой transcript, artifacts и список потомков по `ancestor_run_id` [11].
- **Запуск Oz** обещал ссылки на sessions и audit trail [104][94].

#### Computer Use и доказательства работы

- **Где работает.** Только в облачных sandbox Warp, «not in local interactive terminal sessions». Скриншоты, клики, ввод текста, видео, встроенный Chromium [57].
- **Настройки по умолчанию** [57]:
  - включён для harness Warp Agent;
  - выключен для Claude Code и Codex: «third-party harnesses don't integrate with Warp's Computer Use tooling»;
  - run из приложения Warp следуют настройке приложения, которая по умолчанию выключена;
  - использует модели Anthropic Claude.
- **Записи экрана** [59]:
  - простой и время «размышлений» вырезаются;
  - на видео вшиты подсказки действий, круги от кликов и следы перетаскивания;
  - набранный текст подписан «typing…», сам ввод не показывается;
  - запись идёт только изнутри sandbox.
- **Вложения в PR** [58]:
  - до 10 скриншотов на PR плюс записи;
  - настройка команды выбирает режим: Link only (по умолчанию; Warp проверяет доступ зрителя), Embed (публичные URL) или Disabled;
  - снимки можно отправить и в Slack, Linear или комментарии.
- **Windows-runners** в облаке записывают видео Computer Use с октября–ноября 2026 [4].

### Warp Factories

#### Понятия

- **Фабрика** собирает примитивы Automation Platform — run, environments, runners, интеграции и secrets — в один измеряемый процесс [7]. Отдельного движка у неё нет.
- **Work item** — один запрос: issue, ветка обсуждения в поддержке, PR, задача по расписанию или задача из Factory MCP. Он сохраняет свою идентичность от приёма до передачи человеку [22][23].
- **Foreman** — агент-координатор фабрики. Документация: «the only default agent that communicates directly with you». К нему обращаются по имени фабрики, например `@payments` [22][24].

#### Агенты по умолчанию и свои агенты

- **Агенты по умолчанию** [24]:
  - Triage — исследует, воспроизводит, оценивает объём;
  - Spec — пишет продуктовую и техническую спецификацию с критериями проверки в draft PR;
  - Implement — пишет код и тесты, гоняет проверки репозитория, собирает визуальные доказательства. Никогда не делает merge;
  - Review — независимая проверка. Её вердикт носит рекомендательный характер.
- **Типы агентов** в определении фабрики: FOREMAN, TRIAGE, SPEC, IMPLEMENT, REVIEW, VERIFY, CUSTOM [37].
- **Свои агенты** описываются отдельно [25]. Поле `spawnableBy` задаёт, кто может запускать агента; по умолчанию — только foreman [37].
- **Разные harness на разных агентов.** Например, Claude Code пишет код, а Warp Agent делает review [29].

#### Этапы и остановки для человека

- **Этапы:** Intake → Triage → (Planning) → Human review → Building → Reviewing → (доработки) → Human handoff → Complete. Foreman может пропускать этапы или возвращать работу назад [23]. Он «picks the shortest path that still meets your quality policy» [23].
- **Завершение.** Work item завершается только после уведомления о merge или подтверждения человека. Одной передачи человеку мало [23].
- **Остановки для человека** [23][24]:
  - по умолчанию — одобрение spec, уточняющие вопросы и merge;
  - одобрение spec и вопросы — это «workflow policy» в редактируемых инструкциях foreman;
  - merge защищён branch protection. «The factory never merges on your behalf».

#### Prompts агентов по умолчанию

Пример из репозитория `warp-factory-examples` [131]:
- review «runs only once per work item»;
- одобрение spec «may come in the form of a written confirmation or approval of the draft PR»;
- foreman передаёт человеку только вопросы, решения, результаты и блокеры;
- модели в примере: foreman — `claude-5-opus-high`, implement — `auto-genius`, review — `gpt-5-6-terra-high`, spec — `gpt-5-6-sol-high`, triage — `grok-4-5-high`.

#### Web-приложение фабрик (platform.warp.dev)

- **Home «Waiting on you»** [26]:
  - личный список, а не лента команды;
  - виды пунктов: Asked question, Answered question, Spec review, PR review (в том числе GitHub review, которые запросили у вас на чужую работу), Blocked, Failed;
  - «Mark as resolved» с отменой (Undo);
  - статусы: Active, Complete, Blocked, Failed. Поиск группирует результаты по Today, This week и All time.
- **Dashboard** [27][33]:
  - всего run, открытых и слитых PR;
  - Autonomy — доля слитых PR, в которые человек не пушил код;
  - PR cycle time с медианой по каждому этапу;
  - Cost per PR — медиана с разбивкой на compute, platform и inference или по размеру PR S/M/L/XL. Warp пишет, что это оценка, а не сумма из счёта;
  - самые дорогие PR, карточки Scorers, последние PR от Self-improvement;
  - метрики, которые зависят от merge, требуют GitHub App или webhook GitLab.
- **Другие страницы** [27]:
  - Runs: хронология, стоимость, вкладка Sub-agents; run можно остановить, оценить или превратить в задачу benchmark;
  - Agents, Automations, Webhooks (журнал доставок, смена secret);
  - редактор определения фабрики — только для фабрик, которыми управляет Warp;
  - Scorers, Self-improvement, Benchmarks;
  - Settings: идентичность, репозитории, автор PR (агент или тот, кто запустил run), модель для анализа, runners, интеграции, удаление.
- **New Chat** отправляет запрос foreman выбранной фабрики [27][46].
- **Правки определения от агентов** приходят как spec review с кнопкой «Approve & merge» [27].

#### Factory-as-code

- **Формат.** Дерево файлов YAML и Markdown с корнем `factory.yaml` [37]:
  - `agents/<name>/agent.md`;
  - `automations/`, `runners/`, `routers/` (routers моделей);
  - `benchmarks/`, `scorers/`, `skills/`, `webhooks/`.
- **Где хранится** [37][27]:
  - у Warp (по умолчанию);
  - в репозитории команды на GitHub (платные тарифы). Merge в `main` применяет изменение, а проверка PR `warp/factory-config` его валидирует;
  - «live-managed» — через API, без файлов.
- **Валидация.** Определение применяется целиком. Если проверка не прошла, остаётся последнее рабочее определение. JSON Schemas и скрипт проверки опубликованы [37].
- **Отдельные поля** [37]:
  - `agentType` — тип агента;
  - `networkPolicy` — списки разрешённых и запрещённых адресов для исходящих соединений;
  - `credentialStrategy` — EXECUTOR или CREATOR (чьими учётными данными работает агент);
  - `restrictFollowupsToStarter` — follow-up может писать только тот, кто запустил run;
  - `selfImprovement`;
  - `agentDefaults` — модель, harness, `workerHost`, `computerUseModel`.
- **Skills фабрики** задаются для одного агента или для всех [25][37].

#### Приём работы и automations

- **Источники** [43]:
  - Slack и Microsoft Teams — упоминание приложения;
  - GitHub — метка фабрики плюс **@warp**;
  - GitLab — упоминание бота в merge request;
  - Azure DevOps;
  - Linear — назначить issue или упомянуть приложение; Jira — назначить или упомянуть;
  - свои webhooks, `POST /factory/{uid}/runs`, Factory MCP, прямые run, расписания.
- **Ограничение.** Одна фабрика не может подключить Linear и Jira одновременно [43].
- **Продолжение разговора.** Ответы в той же ветке продолжают тот же work item. Повторные доставки отбрасываются [43].
- **Фильтры automations** [44]:
  - Slack — беседы, люди, ключевые слова, emoji;
  - GitHub — репозиторий, ветка, пути, метки, люди, review, результаты workflows;
  - Linear — команда, проект, метки, состояние;
  - webhooks — шаблоны по JSON payload;
  - события от ботов по умолчанию пропускаются.
- **Automation** — это провайдер + событие + фильтры. Каждая подходящая automation запускает свой run [44].
- **Результаты CI** приходят как события `check_suite_completed` и `workflow_run_completed` [45].

#### Factory MCP: связь локального агента с фабрикой

- **Endpoint.** Hosted MCP server по адресу `https://app.warp.dev/api/v1/mcp/factory`. Встроен в Warp с 2026-08-18. Облачные run Claude Code и Codex подключаются к нему сами [28][4].
- **Инструменты** [28]:
  - `send_task`, `get_task` (с `start_working=true` возвращает команды для настройки worktree), `list_tasks`, `search_task`;
  - `message_foreman`, `get_conversation`, `complete_task`, `list_notification_routes`;
  - инструменты первичной настройки, вплоть до `create_factory`;
  - `validate_factory_files`.
- **Оговорки** [28]:
  - взять задачу — «doesn't claim, lock, or pause it»;
  - у сервера нет scopes «только чтение» или «одна фабрика»;
  - уведомления в личные сообщения Slack или в issue Linear доставляются без гарантии.

#### Измерение и улучшение

- **Scorers** [34]:
  - LLM-as-judge (модель, которая оценивает результат другой модели) классифицирует законченные run выбранных агентов;
  - настройки: инструкции судьи, модель судьи, метки с баллами, порог прохождения, доля выборки. По умолчанию оценивается 10% run [34][37];
  - любой run можно оценить и вручную.
- **Self-improvement** [35]:
  - запускается после 25 разных непросмотренных неудач или когда самой старой неудаче 7 дней. Порог настраивается от 1 до 50; «Run now» запускает сразу;
  - открывает PR в код приложения или в определение фабрики. В каждом PR есть раздел «Regressions addressed» со ссылками на упавшие run;
  - рецензент назначается по правилу: админы, команда, свой список или никто.
- **«Observer agents».** Так это называют пост о запуске и маркетинговая страница: агенты, которые оценивают run и «open PRs against your factory config» [90][116]. Термин есть и в статье Warp про foreman [118]. В документации Factories его нет; там говорят Scorers и Self-improvement [23][33].
- **Benchmarks** [36][37]:
  - набор задач, у каждой «Correctness criteria» (критерии правильности);
  - конфигурации (harness, модель или router, runner) с повторами; оценивает встроенный Correctness Scorer. В `suite.yaml` можно заранее задать от одной до шести конфигураций [37]; предел для диалога запуска документация не называет [36];
  - задачи можно делать из законченных run.
  - Пост о запуске Benchmarks — 2026-09-03 [119].

#### Доказательства до PR

- **Implement-агент** «Opens a pull request with test and visual evidence». Prompt по умолчанию требует раздел «как проверено» и визуальное доказательство для изменений UI [23][131].
- **Рецепт проверки UI** [48]:
  - запускается меткой `ui-verification`;
  - агент VERIFY на harness Warp Agent собирает PR и проходит его через Computer Use;
  - пишет в PR комментарий: проверенный SHA, наблюдения, ссылки на доказательства, критерии со статусом passed, failed или unverified.
- **Источники расходятся в объёме.** Маркетинговая страница утверждает, что каждый агент снимает скриншот или видео до PR [90]. Документация и prompt по умолчанию требуют визуальное доказательство для изменений UI [23][131].

#### Права доступа

- **Роли.** Factory user (запускает работу), Editor (настраивает) и Admin. Назначать роли можно только на Enterprise; на остальных тарифах каждый участник — Editor [47].
- **Права агента** берутся из его конфигурации и прав провайдера, «never from its instructions» [24].

- **Порядок вклада** (CONTRIBUTING) [128]:
  - каждое изменение начинается с issue;
  - метки готовности идут `ready-to-spec` → `ready-to-implement`;
  - для новой функции нужен PR со spec: `product.md` и `tech.md` в папке `specs/`. В ней 294 записи;

- **Бот в issues.** Бот разбирает каждое новое issue и помечает свой анализ «may be incorrect». Мейнтейнеры зовут `@oz-agent`, чтобы он подготовил PR [145][148]. Issues создаются автоматически из постов в X и Reddit [145][148].

- **Результаты по словам Warp:** фабрики автоматизируют «about 30%» задач самого Warp (2026-08-18) [116]; стоимость PR упала на 70% (2026-10-03) [124]. Независимо не проверено.

## Принципы и подходы

### Философия

- **Ранние принципы (2021).** Восемь принципов продукта. Среди них: встречать разработчиков там, где они уже работают; сохранить силу терминала, но исправить его интерфейс; хорошо работать без настройки; строить ради скорости; строить платформу; строить для команд [95].
- **Три этапа работы с ИИ** по словам Lloyd: автодополнение, затем интерактивные агенты, затем «Automated Development». Работа инженера теперь — «build the thing that builds that product» [111].
- **Внутренняя записка от 2026-06-18** называется «We are now factory engineers, not product engineers» [111].
- **Метрики:**
  - доля изменений, которые прошли полностью автоматически, и их цена [111];
  - эффективность фабрики ≈ выпущенный продукт / (стоимость inference + стоимость времени людей) [111];
  - траты на производство ПО учитываются как себестоимость (cost of goods sold), а не как R&D [111];
  - «human touches per PR» — сколько раз человек вмешался в PR — должно со временем падать [121];
  - порядок внедрения: сначала охват (доля слитых PR, которые прошли через фабрику), потом пропускная способность, cycle time и cost per PR [125].
- **Сначала автоматизация, но без «dark factory».** Dark factory — фабрика, которая работает совсем без людей.
  - Внутри Warp каждая интерактивная session агента считается неудачей, из которой надо извлечь урок [111].
  - Публично Lloyd говорит, что фабрики без присмотра сейчас нереалистичны, а полная автоматизация — не цель [121][125].
  - Это расхождение в словах самого вендора: внутренняя записка требует большего, чем публичные посты.
- **Две работы у инженера.** Продуктовая (вкус, решение, что строить) и «factory engineering» (измерять фабрику, гонять на ней benchmarks, улучшать). Warp учитывает обе в оценке работы сотрудников [121].
- **Облако вместо ноутбуков.** Локальные агенты, которые каждый разработчик выбирает сам, расползаются по расходам, безопасности и управлению. Ответ Lloyd — собрать всё в облачной фабрике, а интерактивную работу вести на удалённых машинах [113][112].
- **Работа публична и измерима по умолчанию.** Lloyd признаёт, что инженерам это бывает неудобно [121].
- **Встречать инженеров в их инструментах.** Работа начинается в Slack или Teams, в Jira или Linear, в GitHub или GitLab. Warp советует не делать новый web-портал главным местом работы [125].
- **Инфраструктура, а не продукт.** Стек фабрики должен быть открытым, составным и описанным в коде — «Terraform for factories». Слои стека: factory-as-code, контекст, compute, inference и измерение [120][126].
- **Суверенитет.** Любая модель и любой harness. Compute можно держать у себя. Zero data retention, и ни один провайдер не обучается на данных клиента [120][116]. Несколько harness нужны потому, что результат агента зависит от пары «harness + модель» [108].
- **Жёсткие остановки для человека:**
  - одобрение spec по умолчанию;
  - фабрика никогда не делает merge;
  - изменения от Self-improvement приходят только как PR [23];
  - foreman только распределяет работу и сам её не выполняет; прав на правку кода и merge у него нет [118].
- **Инструкции — не доступ.** «Changing what an agent is told to do doesn't change what it's able to do». Одобрение spec — правило в prompt. Merge защищает сам репозиторий [24].
- **Проверка — новое узкое место** [106]. На практике:
  - к PR прикладываются доказательства: тесты и визуальное подтверждение [23];
  - записи Computer Use «до» и «после», обрезанные через FFmpeg [127];
  - раунды adversarial review (review, который ищет, как сломать изменение) идут вне ветки обсуждения на GitHub [127];
  - skill `/merge-risk` и многораундовый review; число раундов зависит от размера изменения [127].
- **Открытый цикл разработки** («Open Agentic Development»). Идею пользователя прототипирует агент. Команда её одобряет, Oz её строит, проверяют вместе. Основная команда держит объём, чтобы продукт не разрастался [107].
- **Spec в репозитории.** PRODUCT.md (пользовательские истории и проверяемые инварианты) и TECH.md коммитятся вместе с PR [107][110]. В открытом репозитории Warp такие spec лежат в папке `specs/` [128].

### Ключевые понятия

- **ADE** — agentic development environment, «среда разработки с агентами»; так Warp называет себя с версии 2.0 [99].
- **Warp Drive** — общие для команды rules, конфигурации MCP, prompts и workflows [99].
- **Agent Profiles** — разрешения и модели для каждого агента [99][60].
- **Full Terminal Use** — агент работает внутри интерактивных программ в терминале [5][63].
- **Agent Management Panel** — один список локальных и облачных run с фильтрами по источнику, дню, автору и статусу; показывает родителей и детей и расход. Страница Runs в Oz web app играет ту же роль в браузере [9].
- **Harness** — программа-агент, которая ведёт цикл «модель → инструменты»: Warp Agent, Claude Code, Codex [29].
- **Термины облачных агентов:** Environments (окружения), Skills-as-agents (skill как самостоятельный агент), Schedules (расписания), Handoff (перенос между машиной и облаком), session sharing (общий просмотр) [104][108].
- **Agent Memory** — память агентов, общая для нескольких harness [108][66].
- **Термины Factories** [23][123][119]:
  - work item — одна единица работы от приёма до передачи человеку;
  - foreman — агент-координатор;
  - stage agents — агенты этапов: triage, spec, implement, review;
  - этапы: Intake → Triage → Planning → Building → Reviewing → Human handoff → Complete;
  - evidence (доказательства), handoff (передача человеку);
  - Scorers (LLM-as-judge), Self-improvement, Benchmarks (WarpBench);
  - factory-as-code (`factory.yaml`): агенты, automations, runners, scorers, skills, webhooks;
  - Factory MCP; фильтр «Waiting on you».
- **Только в блоге:** «observer agents» и «control room» [116][118].
- **AI sovereignty / BYO inference** — свой провайдер моделей и свой inference [114].

### Чем подход отличается

- **Фабрика команды, а не агент разработчика.** Единица работы — work item из инструментов команды. Её ведёт конвейер этапов с правилами, а результат меряется бизнес-метриками: autonomy, cycle time, cost per PR [22][23][27].
- **Независимость от harness.** Lloyd хочет, чтобы Warp дополнял Claude Code и Codex, а не конкурировал с ними [168]. Облачные run принимают три harness [108][29].
- **Облако как место работы.** Отдельная sandbox на каждый run, а не машина разработчика [38][113].
- **Оплата по факту.** Usage по ценам API плюс плата платформы за время агента. Lloyd говорит, что Warp уходит из бизнеса перепродажи токенов [89][114]. Warp пишет, что не может конкурировать ценой или дотировать usage [106].
- **Цикл измерения.** Оценка run моделью-судьёй, PR с исправлениями по накопленным неудачам, benchmarks конфигураций на своих задачах [34][35][36].
- **Смена курса за последние годы:**
  - от закрытого кода к открытому [98] → [106]. По словам Lloyd в интервью, одна из главных причин — продукт получился слишком «opinionated», навязывал свой способ работы [168];
  - от своего агента к независимости от агента [168];
  - от локальной работы с человеком в цикле к облаку и автоматизации [99] → [113][111];
  - от продуктовой компании к инфраструктурной; команда пишет, что в основном этот сдвиг сделала [124].

### Слои и жизненный цикл run

- **Пять слоёв** [7]:
  - клиенты: приложение Warp, Oz CLI, web-приложение, dashboard фабрики, клиенты Factory MCP;
  - control plane, которым управляет Warp: координирует run, хранит общую конфигурацию, направляет вызовы моделей и ведёт историю;
  - data plane: transcripts, artifacts и вложения в хранилище Warp;
  - execution plane: sandbox у Warp или worker у клиента;
  - внешние системы.
- **Один жизненный цикл для каждого облачного run**, что бы его ни запустило [7]:
  1. Срабатывает триггер.
  2. Control plane создаёт запись run.
  3. Он определяет конфигурацию: environment, runner, хост, модель и harness.
  4. Создаётся sandbox. Она клонирует репозитории, выполняет команды настройки и получает только разрешённые secrets.
  5. Идёт цикл агента.
  6. Результаты отдаются: ветка, PR и ответ в тот элемент Slack, Linear или Jira, который запустил run.
  7. Transcripts, artifacts и стоимость прикрепляются к записи run.
  8. Команда может смотреть или подключиться.
  9. Снимается snapshot, sandbox удаляется.
- **Фабрика — не отдельный движок.** Она «assembles the Automation Platform's primitives — runs, environments, runners, integrations, and secrets — into one measurable workflow» [7]. Работа каждого агента этапа — обычный облачный run [23].

### Где выполняется run

- **Виды sandbox** [128]:
  - клиент распознаёт Docker Sandboxes и Namespace (облако Warp), а также обычный Docker и Kubernetes (self-hosted). Сервер сообщает платформу в переменной `WARP_ISOLATION_PLATFORM`;
  - комментарий к тому же перечислению говорит, что платформы изоляции «may also include weaker forms of sandboxing such as Git worktrees»;
  - каждая платформа выдаёт токен workload identity. Namespace делает это командой `nsc auth issue-id-token`.
- **Жёсткий срок жизни** [128][51]:
  - сервер передаёт `WARP_SANDBOX_DEADLINE` только для run в Docker Sandbox и Namespace;
  - на бесплатном тарифе срок фиксирован, на платных настраивается; по истечении run становится FAILED [128];
  - отдельно серверная задача очистки завершает run, которые превысили максимум платформы. Это `infrastructure_timeout`, состояние ERROR, без повтора [51].
- **Заранее прогретые sandbox.** Команда `agent run-cloud-standby` готовит sandbox и шлёт heartbeat, пока сервер не назначит ей run. Затем run ставится в тот же процесс [128]. Прогретая настройка не получает метаданных конкретного run [25].
- **Self-hosted worker** [132][40]:
  - сам открывает соединение WebSocket наружу, входящие порты не нужны;
  - типы сообщений: `task_assignment`, `task_claimed`, `task_completed`, `task_failed`, `task_rejected`, `task_cancellation`, `heartbeat` и сообщения `prewarm_*`;
  - backends: Docker, Kubernetes Job, Direct (общий kernel с хостом) и Command (передаёт задачу внешнему оркестратору);
  - `max_concurrent_tasks` ограничивает число задач на машине;
  - в каждый контейнер задачи монтируется sidecar image с бинарником агента Warp.
- **Мощности** [39][131]:
  - у run в облаке Warp есть лимит параллельности на команду; лишние run ждут в очереди [39];
  - runner задаёт ОС, архитектуру, образ, vCPU и память; на Enterprise — до 32 vCPU и 64 GiB [39];
  - runner по умолчанию в примере — 4 vCPU, 8 GB, `ubuntu:24.04` [131].

### Цикл агента

#### Warp Agent (harness `oz`)

- **Где идёт цикл.** Цикл модели работает на сервере за «multi-agent API» (protobuf поверх SSE). Инструменты выполняются на клиенте или в sandbox. Комментарий в коде: «A turn spans many MAA requests (every tool-result round trip is its own)» — каждый ход агента состоит из многих запросов к серверу, по одному на каждый результат инструмента [128].
- **Инструменты** [128]:
  - команды shell, включая работу с долгими командами;
  - чтение и правка файлов, grep и glob, поиск по коду;
  - инструменты и ресурсы MCP, skills, документы;
  - Computer Use и запись экрана, `AskUserQuestion`;
  - инструменты оркестрации `RunAgents`, `SendMessageToAgent` и `WaitForEvents`.
- **Маршрут inference.** Вызовы моделей идут через Warp к провайдерам с условием zero data retention, либо по ключам команды, либо через свой LLM [7].
- **Планирование.** `/plan` создаёт план с версиями. Task lists создаются сами [61][62].

#### Сторонние harness: Claude Code и Codex

- **Контракт обёртки.** Trait `ThirdPartyHarness` задаёт [128]:
  - проверку, что CLI есть в PATH;
  - команду проверки входа (auth preflight);
  - шаблоны ошибок во время работы;
  - данные для resume;
  - `build_runner`, который пишет файлы конфигурации: вход, доверие к папке, system prompt, MCP.
- **Запуск Claude Code** [128]:
  - команда: `claude --session-id <uuid> --dangerously-skip-permissions [--append-system-prompt-file …] [--mcp-config …] < prompt`. Продолжение — с `--resume <uuid>`;
  - драйвер заранее заполняет `.claude.json`: первичная настройка пройдена, диалог доверия к рабочей папке принят, суффикс API-ключа одобрен;
  - драйвер выставляет `skipDangerousModePermissionPrompt`.
- **Запуск Codex** [128]:
  - команда: `codex --dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust "<prompt>"` или `codex resume …`;
  - перед запуском, за feature flag, драйвер проверяет собственный plugin Warp для Codex. Причина в коде: флаг «bypasses hook trust globally», то есть доверяет всем hooks сразу.
- **Документация и код здесь расходятся по полноте.** Документация не описывает, в каком режиме разрешений идут облачные Claude Code и Codex; описан только статус Blocked, когда нужен ввод [9]. Код показывает, что оба CLI запускаются с отключёнными подтверждениями [128].
- **Как драйвер ведёт CLI** [128]:
  - CLI запускается как команда в терминальной session драйвера после настройки окружения. Зритель общей session видит его как обычный блок вывода;
  - другой транспорт — ACP (Agent Client Protocol), через локальный socket. Поток `session/update` переводится в обычный разговор Warp;
  - follow-up, который пришёл посреди хода, идёт через расширение `_session/steering`, если агент его поддерживает. Иначе драйвер отменяет ход и отправляет prompt заново;
  - если адаптера ACP нет, run переходит на PTY и пишет причину в session.
- **Защита вокруг CLI** [128]:
  - проверка входа: `claude auth status --json` или `codex login status`, с таймаутом 30 s;
  - фоновый монитор ищет в выводе harness известные строки ошибок и быстро роняет run — «instead of letting the harness hang»;
  - разговор harness сохраняется каждые 5 минут и в точках сохранения;
  - остановка ограничена по времени: `/exit`, через 1 s — Enter, через 14 s — SIGKILL группы процессов; всего около 15 s.
- **Другие harness.** В коде есть пути для Gemini, Pi (только ACP) и OpenCode [128]. Документация называет только `oz`, `claude` и `codex` [29]. Доступны ли остальные — не подтверждено.

### Декомпозиция и планирование

#### Фабрика: процедура foreman, в которую можно войти с любого шага

- **Процедура.** Foreman — LLM-агент с письменной процедурой. Его prompt по умолчанию опубликован целиком [24][131]:
  1. Проверка адресата: это сообщение для foreman?
  2. Решение о triage.
  3. Решение о spec. Foreman сначала спрашивает пользователя. Агент spec возвращает draft PR, и «the user must approve the spec before implementation can proceed».
  4. Implement.
  5. Review. «The review runs only once per work item». Однозначные замечания возвращаются исполнителю. Неоднозначные публикуются в PR для человека.
  6. Метка на PR и комментарий об авторстве.
  7. Остановка на передаче PR. Завершение — при следующем входе, после уведомления о merge или подтверждения пользователя, что PR влит.
- **Вход с любого шага.** «Work can enter this procedure at any stage»: новый запрос, PR на review, падение CI, уведомление о merge, ответ на вопрос [131]. Foreman «picks the shortest path that still meets your quality policy» [23]. Статья Warp: застрявший run «can be resumed by respawning the foreman against the same work-item state» [118].
- **Передача контекста задана в prompt.** Каждое поручение агенту этапа содержит [131]:
  - запрос дословно;
  - ссылку на issue;
  - ссылку на ветку обсуждения и того, кто попросил;
  - «only the information that the stage needs».
  - Follow-up идёт тому агенту, у которого уже есть контекст, а не новому.
- **Роли и модели.** Значения `agentType`: FOREMAN, TRIAGE, SPEC, IMPLEMENT, REVIEW, VERIFY, CUSTOM [37]. Модели по умолчанию — от разных вендоров (список — в разделе «Функции») [131].
- **Раздача работы** [25][37]:
  - foreman вызывает `run_agents` с `remote: {}` и `agent_run_configs[].agent_identity_uid`;
  - дети наследуют настроенные environment, runner, хост, harness и модель;
  - строковые метаданные (до 20 ключей) становятся переменными `WARP_METADATA_*`;
  - `spawnableBy` ограничивает, кто может запустить агента; по умолчанию — только foreman [37].
- **Приём работы.** Automation = провайдер + событие + фильтры. Каждая подходящая automation запускает свой run. События ботов GitHub по умолчанию пропускаются [44]. Результаты CI приходят событиями `check_suite_completed` и `workflow_run_completed` [45].

#### Оркестрация вне фабрик

- `/orchestrate` или `/plan` в приложении, или `mode: orchestrate|plan` в API. Родитель предлагает число детей, их prompts, окружения и параллельность. Ничего не запускается, пока человек не одобрит; одобрение фиксирует конфигурацию всего run [10][11].
- Описанные схемы: supervisor/worker, fan-out/fan-in, critic/verifier, review swarm, DAG и swarm [10].

### Параллельность и координация

- **Форма.** Оркестрация ровно в один уровень: родитель и его прямые дети. У каждого свой run, свой transcript и своя оплата [10].
- **Где работают дети.** Локально → локально, локально → облако, облако → облако и облако → «cloud-local», когда дети делят окружение родителя. Ребёнок может работать на другом harness, чем родитель [10].
- **Сообщения** [10][128]:
  - надёжная шина сообщений на сервере, один inbox на ID агента. Работает одинаково для всех harness [10];
  - события жизненного цикла идут по той же инфраструктуре: INPROGRESS, SUCCEEDED, FAILED, BLOCKED, ERROR, CANCELLED. Родителю не нужно опрашивать детей [10];
  - на клиенте — поток SSE с фильтром по `run_ids[]` или `ancestor_run_id`, курсор по номеру события для каждого разговора и переподключение через 1, 2, 5 и 10 s [128].
- **Дети, которых можно продолжить:**
  - законченный ребёнок остаётся адресуемым и «will wake up» от нового сообщения [10];
  - законченная session ждёт follow-up `idleTimeoutMinutes`: 10 минут по умолчанию, 60 для детей оркестрации [37]. У worker для oz CLI по умолчанию 45 минут [132];
  - уснувшего ребёнка на Claude Code заново поднимает отдельный слушатель, который только будит session [128].
- **Claude Code как ребёнок.** Plugin `oz-harness-support` ставится сам и доставляет сообщения родителя через hooks [130]:
  - SessionStart запускает слушатель;
  - UserPromptSubmit и PostToolUse подмешивают накопленные сообщения родителя в контекст session;
  - Stop не даёт session закончиться, пока есть недоставленные сообщения;
  - SessionEnd останавливает слушатель;
  - на диске сообщение проходит путь `staged/` → `surfaced/` → `pending-hook-output.json` плюс файл `.ack` (подтверждение доставки) [128];
  - ребёнок отвечает командой `oz run message send …`. Закончить он должен через `oz harness-support finish-task --status success|failure`; `failure` даёт статус BLOCKED, а не FAILED [130].
- **Отмена и статусы.** Отмена родителя не отменяет детей — так задумано [11]. Статус родителя отражает только его работу, поэтому родитель может закончиться успехом при упавшем ребёнке [9].
- **Уведомления** в приложении приходят только по родителю [56][10].

### Изоляция

- **Облако.** Одна sandbox на run. Clones репозиториев удаляются вместе с ней [7]. Дети «cloud-local» делят файловую систему родителя [10].
- **На машине пользователя автоматического worktree на ребёнка нет** [10]:
  - документация предупреждает: «assigning different prompts does not isolate their files»;
  - советует отдельные worktrees и ветки, явное владение файлами и одного агента или человека, который сводит результат.
- **Worktree на вкладку.** Tab Configs могут создать worktree с новой веткой при открытии вкладки [81][128]. Один пользователь хвалит «automatic worktree management» [151]; по документации это создание worktree на вкладку, а не на дочернего агента [81][10].
- **Распознавание worktrees.** У каждого worktree свой Code Review panel и свой индекс кода [78].
- **Self-hosted Direct.** Один worktree на задачу из общего clone без checkout; ветка `warp-agent/<run_id>`; в примере до 4 задач на хост. Изолируются файлы и ветки, «not the host OS» [42].
- **Worktree как слабая изоляция.** Перечисление платформ изоляции в коде прямо называет git worktrees «weaker forms of sandboxing» [128].

### Состояние и память

- **Надёжные записи:**
  - запись run хранится в control plane, transcripts и artifacts — в data plane [7];
  - work item сохраняет идентичность от приёма до передачи человеку [23];
  - в замысле foreman надёжная запись — это issue, PR и закоммиченный файл spec; для мелкой работы без issue записью служит разговор самого foreman [131].
- **Snapshots** [14][128]:
  - в конце run скрипт деклараций пишет строки JSONL вида `repo` или `file`;
  - драйвер выгружает git diff (отслеживаемые изменения плюс неотслеживаемые файлы, которые не в ignore) и содержимое файлов вместе с манифестом `snapshot_state.json` по presigned URL в GCS;
  - неверные строки пропускаются, ошибки выгрузки не роняют run.
- **Checkpoints** — каждые 5 минут плюс случайная задержка до 30 s. Драйвер ждёт безопасной границы, когда ход не идёт, но не дольше 10 минут; потом checkpoint снимается и посреди хода [128].
- **Сигнал остановки.** Первый SIGTERM или SIGINT снимает snapshot до выхода процесса [14].
- **Handoff:**
  - с машины в облако — fork разговора и snapshot workspace. Изменения, которые не применились, перечисляются, остальное продолжается [13];
  - автоматический handoff при сне Mac. Если настройка включена, активный локальный run уходит в облако. Это не происходит, когда разговор — оркестратор с работающими локальными детьми или когда выбрана модель, которую облако не запускает [128].
- **Resume стороннего harness.** Transcript берётся с сервера и записывается туда, где его ищет CLI (`claude --resume`, `codex resume`). Продолжить run на другом harness нельзя — это ошибка [128].
- **Локальные sessions Claude Code после перезапуска Warp** сами не восстанавливаются; это открытый запрос #14720 [140].
- **Skills** [128][25][37]:
  - папки skills Warp подключаются symlink в собственную папку skills каждого harness. Для Codex это `.agents/skills`, исключённая из git [128];
  - skills поддержки harness, например `oz-finish-task`, добавляются, если у транспорта нет шага установки plugin [128];
  - skills фабрики задаются для одного агента или для всех [25][37].
- **Agent Memory** (research preview) [66]:
  - хранилища принадлежат человеку, агенту или команде; агенту подключают хранилище только для чтения или для чтения и записи, с инструкциями на каждое хранилище;
  - память извлекается после окончания разговора и подтягивается в фоне в начале задачи;
  - работает для облачных run разных harness; у каждой записи есть источник, каждое изменение журналируется.
- **Разговоры Warp Agent в облаке** доступны на разных устройствах и продолжаются локально [70].

### Проверка качества

- **Implement-агент** [131]:
  - проверка «mandatory»;
  - исправление бага требует regression test, который падает до изменения и проходит после;
  - агент запускает собственные проверки репозитория — format, lint, build — и тесты затронутого кода;
  - каждый критерий проверки из spec должен пройти. «Never claim that an unverified change passed»;
  - изменения UI требуют визуального доказательства через Computer Use.
- **Spec-агент.** Критерии проверки должны быть «objective, executable, and complete». Каждый называет тест или команду. Для изменений UI по умолчанию нужно видео [131].
- **Review-агент** [131][23]:
  - только сообщает и никогда не пишет в PR. «Do not trust the PR description»;
  - отсутствие визуального доказательства или его несоответствие — блокирующее замечание;
  - вердикты: accepted, revision needed, human decision needed. Вердикт рекомендательный [23].
- **Рецепт агента Verify** (Computer Use; только harness Warp Agent) [48]:
  - берёт точный коммит и сообщает проверенный SHA;
  - помечает результат устаревшим, если head PR сдвинулся во время проверки;
  - никогда не правит код, не одобряет и не делает merge.
  - Снимки сами прикладываются к PR: до 10 скриншотов; по умолчанию — только ссылки, режим embed делает их публичными [58].
- **Merge** фабрика не делает никогда. Это обеспечивают branch protection и права репозитория [24].
- **Измерение после факта:**
  - Scorers: модель-судья классифицирует выборку законченных run (10% по умолчанию) по меткам с порогом прохождения [34][37];
  - Self-improvement собирает неудачи агента в отдельный run, который открывает PR в код приложения или в определение фабрики. Запуск — при 25 непросмотренных неудачах или когда самой старой 7 дней; порог от 1 до 50. В каждом PR есть раздел «Regressions addressed» [35][37];
  - «observer agents» описаны только в блоге: они «score a share of agent runs» и могут открывать PR, которые меняют код фабрики [116]. Документация этот термин не определяет; больше подробностей — не подтверждено;
  - Benchmarks гоняют задачи × конфигурации × повторы и оценивают их встроенным Correctness Scorer, чтобы сравнить качество с ценой [36];
  - Dashboard показывает Autonomy (слитые PR без кода от человека), PR cycle time и cost per PR [33][27].
- **Собственный репозиторий Warp:**
  - skill `cross-platform-cloud-verification` сначала гоняет локальные проверки и только потом запускает детей на runners разных ОС и архитектур, которые находит во время run («cost-conscious») [128];
  - для merge нужно одобрение OWNERS, это проверяет CI [128].
- **Отдельной локальной проверки перед PR нет.** Ближе всего — собственные проверки implement-агента [131].

### Восстановление после сбоев

- **Встроенный агент** [128]:
  - на каждый запрос один `RecoveryBudget`, общий для повторов и resume: `MAX_RECOVERY_ATTEMPTS = 3`. Resume ждёт паузу со случайным разбросом (jitter) и возвращения сети;
  - в облачном драйвере `AUTO_RESUME_TIMEOUT` — 120 s на попытку;
  - почему бюджет общий: раньше одиночный resume попадал «inside the same window of transport resets» во время поэтапного deploy серверов.
- **Повторы на уровне инфраструктуры** [128]:
  - git credentials: при старте повторы через 1, 2 и 4 s; обновление раз в 50 минут;
  - поток событий: переподключение через 1, 2, 5 и 10 s;
  - сохранение transcript и публикация usage — до 3 повторов;
  - сервер ждёт, что агент начнёт работу примерно в течение 10 минут после того, как взял run.
- **Классы ошибок** [128][49][50][51][9]:
  - FAILED — исход задачи: превышен бюджет, мало credits, неверный запрос, упала настройка;
  - ERROR — инфраструктура: сбой потока, внутренняя ошибка, ресурс недоступен;
  - у ошибок API есть флаг `retryable`;
  - BLOCKED — нужен человек. Сторонний harness без присмотра, которому нужен ввод, заканчивается BLOCKED, а не ждёт [9].
- **Changelog 2026** добавил повтор при обрыве потока, гарантированный конечный статус, периодические checkpoints и прогретые sandbox для resume (даты — в разделе «Функции») [4].
- **Застрявший work item** можно продолжить, заново запустив foreman на том же состоянии work item [118].
- **Автоматического повтора упавшего этапа фабрики** в документации нет. Ни подтвердить, ни опровергнуть не удалось (не подтверждено).

### Лимиты и стоимость

- **Лимиты плана для сторонних harness — фатальная ошибка** [128]:
  - для Claude Code ищутся строки «Credit balance too low», «You've hit your» (лимиты session, недели и Opus) и «API Error: Request rejected (429)»;
  - для Codex — «You've hit your usage limit» и «Quota exceeded…»;
  - совпадение даёт `HarnessRuntimeFailureDetected`, и run получает FAILED;
  - логики ожидания сброса лимита в клиентском коде нет. На сервере — не подтверждено.
- **Облачным harness нужны оплаченные API-ключи** в виде managed secrets: ключ Anthropic, учётные данные Bedrock или ключ OpenAI. Вход через ChatGPT — «a different authentication path» [32][30].
- **Подписки.** Подписка ChatGPT «doesn't fund cloud agent runs». Локально, если OpenAI отклоняет запрос, Warp предлагает Try again, Manage ChatGPT usage или «Continue with Warp credits» [74].
- **Ограничители на стороне Warp:**
  - бюджет расходов команды. Когда он исчерпан — HTTP 403 `budget_exceeded`, без повтора; нужно поднять бюджет или ждать нового периода [49];
  - `insufficient_credits`, если на счёте мало средств [50];
  - очередь при лимите параллельности [39] и срок жизни sandbox [128].
- **Учёт:**
  - Warp считает hosted compute, inference от Warp и usage платформы. Внешний inference в итогах Warp отражён не полностью [40][29];
  - usage run Claude Code, Codex и Pi восстанавливается из их transcripts crate `warp_harness_usage` [128];
  - routers выбирают модель по сложности задачи или по описанию в prompt [37].
- **Цены** [83][84][82][85]:
  - платформа — $3 за час работы агента ($0.05 в минуту) для облачных run и для части локальных run на Business со своим inference. Если пользователь сам запускает `claude` или `codex`, платы нет [83];
  - для Claude Code и Codex в оплачиваемое время входит выполнение команд и ожидание модели; для Warp Agent — только генерация ответа [83];
  - compute на Linux — $0.0015 в минуту за единицу; единица — большее из числа vCPU и половины памяти в GB. Пример: 4 vCPU и 8 GB стоят $0.36 в час. Windows — вдвое дороже Linux. macOS — от $4.50 до $16.20 в час [84];
  - usage из тарифа обнуляется каждый месяц без переноса. Купленный usage действует 12 месяцев. Есть месячный лимит расходов команды с автопополнением [82][85].
- **История цен.** В октябре 2025 Warp убрал тарифы Pro, Turbo и Lightspeed и оставил один Build за $20 с credits и BYOK. Warp признал, что старые тарифы были убыточны при полном использовании. «Requests» переименовали в «credits», расход стал виден по каждому разговору [102][101]. По словам пользователей, старый Pro давал 2 500 запросов в месяц, а новый Build — 1 500 credits без переноса [153]. На странице цен от 2026-11-13 Build включает $20 usage [89].
- **Чего нет.** Оценки стоимости до облачного run и потолка расходов на один run нет. Сотрудник Warp ответил, что это требует изменений на сервере, которые сообщество сделать не может [143]. Стоимость PR на Dashboard — оценка, а не сумма из счёта [27].

### Права и безопасность

- **Локальный Warp Agent.** Agent Profiles задают autonomy по видам действий; denylist сильнее allowlist. «Run until completion» по умолчанию обходит пользовательский denylist, но не denylist админа [60].
- **Облачные run идут без человека** [128]:
  - сторонние CLI запускаются с выключенными собственными подтверждениями (флаги — в разделе «Цикл агента»);
  - в режиме ACP разрешается и записывается в журнал всё, о чём спросил бы обычный исполнитель. Отказ получают только команды из denylist и запись в защищённые файлы (`acp/policy.rs`).
- **Поэтому граница безопасности — sandbox и учётные данные с узкими правами:**
  - secrets берутся по allowlist агента. Они выдаются в момент нужды по токену конкретного run или заменяются workload identity federation для облачных учётных данных [7][40];
  - токены GitHub выдаются на задачу, ограничены репозиториями и истекают; драйвер их обновляет. Есть режим `RestrictedInstallation` [128];
  - `credentialStrategy` — EXECUTOR или CREATOR [37];
  - `networkPolicy` сочетает allow и deny, запрет сильнее. Если политика не задана, исходящий доступ не ограничен [37];
  - учётные данные MCP-серверов, к которым Warp ходит как proxy, остаются у Warp [7];
  - redaction secrets на выходе — запасная мера, а не основная [7]. В общих sessions redaction не применяется [86].
- **Инструкции — не доступ.** Одобрение spec — правило в prompt. Merge защищает репозиторий [24].
- **Защита от prompt injection:**
  - prompts рецептов велят считать текст PR недоверенным вводом [48];
  - события ботов по умолчанию пропускаются [44];
  - `restrictFollowupsToStarter` ограничивает, кто может управлять run [37];
  - PR из forks требуют изолированной настройки, которую одобрил человек [48].
- **Factory MCP** не имеет scopes «только чтение» или «одна фабрика» [28].
- **Enterprise и админ:** SOC 2 Type II, zero data retention у провайдеров [87]; Admin Panel для autonomy, denylists, redaction и telemetry [88].
- **Инцидент октября 2026.** Warp сообщил, что злоумышленники через стороннего поставщика добрались до traces агентов и telemetry; верхняя оценка — около 1% пользователей [158][169]. Подробности — в разделе «Что говорят пользователи».

### Человек в цикле и наблюдаемость

- **Остановки по умолчанию:** одобрение spec, уточняющие вопросы, merge [23][24].
- **Очередь Home «Waiting on you»:** вопросы, spec review, PR review, заблокированные и упавшие run [26].
- **Один голос.** С людьми говорит только foreman. Внутренние шаги фабрики он не показывает [131].
- **Управление.** Session sharing даёт следить за идущим или законченным облачным run, писать follow-up и делать fork на машину [15]. Правки определения фабрики от агентов приходят как spec review с «Approve & merge» [27].
- **Agent Management Panel** [9]:
  - локальные разговоры Warp Agent и облачные run; у строки — источник, статус (Working, Blocked, Canceled, Failed, Success) и длительность;
  - фильтры: источник, день, автор, статус;
  - облачные дети — отдельными строками; локальные — только в pill bar над родителем.
- **Уведомления** — только по родителю [10][56].
- **Локальные sessions Claude Code в панели не видны** [52][53]. Они видны в вертикальных вкладках. Уведомления по ним дают hooks plugin (SessionStart, UserPromptSubmit, PostToolUse, PermissionRequest, Stop, StopFailure, Notification), которые шлют escape-последовательности OSC 777 [130].
- **API** отдаёт состояние run, нормализованный разговор, сырой transcript, artifacts и список потомков по `ancestor_run_id` [11].
- **Telemetry worker.** Self-hosted worker отдаёт traces и logs в формате OpenTelemetry (OTLP) [132].
- **Чего нет.** Warp пишет, что это наблюдение за run и sessions, «not a replacement for full APM, OpenTelemetry» [9].

- **Пользователи говорят о терминале и доверии, а не об оркестрации.** Самые оживлённые ветки HN за 2025–2026 — про открытие кода, цены, приватность и CLI-агента [150][151][152][153][154]. Oz и Factories почти не обсуждали независимо:
  - запуск Oz на HN получил 3 балла и 0 комментариев;
  - оба поста HN про Factories — 0 комментариев. Один опубликовал сотрудник Warp [161][150];
  - обзор июня 2026 не нашёл содержательного независимого обсуждения Oz. Обзор вторичный, его автор руководит конкурирующей компанией Tembo [171].
- **Основатель прямо называет позицию компании.** Zach Lloyd на HN: «our business is our agent and orchestrator, not our terminal» [150]. Пользователи в ответ спрашивают, зачем вообще платить Warp. Многие запускают в Warp Claude Code или Codex на подписках, которые оплачивает работодатель [151][152].
- **Самые поддержанные запросы — про контроль, и большую часть Warp уже закрыл.** По числу голосов «+1» на 2026-11-13 [133][134][177]:
  - локальные модели — 1 236 (#4339), открыт с 2024 года;
  - поддержка Linux в WSL (Windows Subsystem for Linux) — 1 016 (#4240), закрыт как выполненный 2025-03-10;
  - свой API-ключ (BYOK) — 514 (#2788), закрыт как выполненный 2025-11-07;
  - работа и пробный период без входа плюс офлайн-режим — 462 (#900), закрыт как выполненный 2024-11-22; вход с тех пор не обязателен [98];
  - возможность выключить AI — 189 (#2808), закрыт как выполненный 2024-12-14;
  - полный офлайн-режим — 115 (#5640), открыт.
- **Доверию мешает история.** Пользователи возвращаются к одним и тем же событиям:
  - старый обязательный вход в аккаунт;
  - telemetry;
  - «Active AI», которая в 2025 году отправляла вывод терминала в модель без запроса [154];
  - ошибка, которая снова включала telemetry; Warp признал её в апреле 2026 [150];
  - утечка traces агентов и telemetry в октябре 2026 [158][159][169].
- **Главная причина уйти — разрастание продукта и постоянные изменения интерфейса.** Худшей точкой стал февральский релиз 2026 года с агентами [138].
- **Product Hunt:** 4.8 по 81 отзыву [164].

### Что ругают (примерно по числу жалоб)

**a) AI навязан терминалу, интерфейс меняется, продукт разрастается.**
- Февральский релиз 2026 года с агентами разозлил людей [138]:
  - заголовки вкладок переименовали с упоминанием Oz;
  - новая вкладка открывалась 5–10 секунд вместо 0.5;
  - скачки CPU и зависшие CLI-программы;
  - элементы AI оставались видны при выключенном AI.
  - Инженер Warp ответил, что ошибки исправлены патчем на следующий день. Автор issue спросил, зачем такой релиз вообще выпустили. Пользователь тарифа за $200 в месяц пригрозил отменить подписку [138].
- Другие жалобы:
  - новая вкладка по умолчанию открывает агента (настраивается) [152];
  - кнопка «+» подталкивает к агенту Warp [151];
  - классификатор «команда или запрос» ошибается в обе стороны [152];
  - большое всплывающее окно с предложением Oz при первом запуске [151];
  - сочетания клавиш и раскладка меняются от релиза к релизу [150][151][153].
- Несколько платящих пользователей удалили Warp из-за этих изменений [151].
- Размер и ресурсы: приложение весит около 850–900 MB [150][152] и занимает больше 1 GB памяти [153]. Warp может зависать на минуты при загрузке CPU выше 100%, пока работает session Claude Code [139].

**b) Цены и credits.**
- В октябре 2025 старый Pro (2 500 запросов в месяц) превратился в Build за $20 с 1 500 credits без переноса [153].
- Пользователь из Канады сообщил о фактическом десятикратном росте цены. Это одно сообщение (не подтверждено) [157].
- Пользователь Business написал, что израсходовал лимит за три дня, после чего агент сломал рабочий код (июль 2025) [155].
- Заголовки issues жалуются на навязчивые уведомления «out of credits» и называют стоимость credits безумной [133].
- У облачных агентов нет оценки стоимости до запуска и потолка расходов на один run. Сотрудники Warp ответили, что это требует изменения на сервере, которое сообщество сделать не может [143].
- Oz web app и desktop-приложение показывают разные суммы credits за один и тот же run [144].

**c) Своя модель и работа без сервера Warp.**
- После открытия кода самым популярным новым issue стал BYOK без тарифа Pro — 150 голосов [135].
- Lloyd объяснил, что harness агента разделён: клиент — открытый код на Rust, сервер — закрытый код на Go. Поэтому BYOK и свои endpoints всё равно идут через серверы Warp [136].
- Самый поддержанный ответ просил вообще не гонять запросы через сервер. Другие написали, что политика компании запрещает туннели вроде ngrok [136].
- BYOK на бесплатном тарифе и свои endpoints, совместимые с OpenAI. Источники расходятся в дате: по issue и обсуждению — 2026-05-22 [135][136], по посту в блоге Warp — 2026-05-20 [109]. После выхода пользователи обнаружили:
  - внутренние proxy LiteLLM не работают, потому что endpoint должен быть доступен из интернета [136];
  - часть бесплатных аккаунтов всё ещё не могла использовать свой ключ [135].
- Fork OpenWarp, работающий только локально (теперь называется Zap), набрал около 2.1 тыс. stars [137].
- Подписки:
  - документация теперь разрешает подписку ChatGPT для агента Warp в приложении;
  - потребительскую подписку Claude — нет [74][75];
  - запрос запускать из агента Warp собственный CLI пользователя с его подпиской остаётся открытым [145].

**d) Приватность и доверие.**
- Наследие обязательного входа всё ещё стоит Warp пользователей. Один ветеран так и не попробовал Warp из-за входа [150].
- Один пользователь написал, что пакет RPM в апреле 2026 всё ещё требовал вход [150]. Другой — что Warp не запускается без сети [151]. Оба сообщения единичные (не подтверждено).
- Пользователь насчитал пять сетевых запросов при старте, в том числе три события telemetry. Warp признал ошибку уровня P0, которая снова включала telemetry, исправил её в PR #9438 и отметил, что в сборке из открытого кода telemetry нет [150].
- Новому пользователю отключили AI за «Terms of Service violation» после одного prompt [150].
- Утечка октября 2026:
  - Warp сообщил, что злоумышленники через стороннего поставщика добрались до traces агентов и telemetry. Верхняя оценка — около 1% пользователей [158][169];
  - в письме одному получателю говорилось, что traces агентов могли содержать секретные ключи. Этот пользователь почти год не пользовался Warp и усомнился в обещаниях zero data retention [159];
  - были ли украдены secrets — не подтверждено [170].

**e) Работа на разных платформах.** Чёрное окно в VM с Ubuntu [150]. На Windows просят поддержку cmd.exe — 137 голосов [133].

### Oz и Factories отдельно

**Как встретили Oz.**
- На Product Hunt Oz получил около 21 голоса. В ветке «Ask Me Anything» было два комментария пользователей: один не понял, куда ушёл его prompt; другой спросил, какие агенты работают. Инженер Warp ответил, что облачная оркестрация тогда поддерживала только агента Warp [163].
- Статьи после запуска только пересказывают. It's FOSS отмечает, что стоимость зависит от credits [166].
- Испаноязычный пользователь X нашёл Oz после обновления и написал, что не будет платить за AI-сервисы. Это видно только во фрагменте поиска [175].

**Утверждения Warp о себе.** Ни одно не проверено независимо.
- Oz пишет 60% PR самого Warp (февраль 2026) [104].
- Warp пользуются 700 000+ разработчиков [94].
- Factories: безымянный VP of Engineering сообщает о стоимости PR от агента на 30% ниже. Кейс говорит о снижении с $80 до $30 за PR. FAQ пишет, что большинство организаций начинают с 20–30% PR, сделанных полностью автоматически [90].

**Warp гоняет Oz на своём репозитории.**
- Бот разбирает каждое новое issue и помечает свой анализ «may be incorrect». Мейнтейнеры зовут `@oz-agent`, чтобы тот подготовил PR [145][148].
- Issues создаются автоматически из постов в X и Reddit [145][148].
- Один обзор пишет, что части контрибьюторов не понравилось, что их вклад идёт через закрытых агентов. Обзор вторичный [173].

**Жалобы пользователей на Oz и Factories в issues.**
- Последний шаг дочернего агента жёстко прописан: push и draft PR. Это противоречит правилам пользователей, которые запрещают незапрошенные операции git [146].
- Skills в папках-symlinks не находятся, и агенты не загружаются [142].
- В фабрике, которой управляют через файлы, нельзя сменить модель-судью встроенного Correctness scorer. API отказывает с «use files», а в схеме файла такого поля нет [147].
- Встроенный сервер Factory MCP перезапускается по кругу после ошибки 403 [147].
- Run получают SUCCEEDED без ответов и transcripts [147].
- Пользователь назвал поддержку Forgejo условием «can't work without it» [147].
- Большинство остальных issues про Factories создали боты Warp. Внешних пользователей, судя по issues, немного [147].

**Доказательство, что работа сделана.**
- В июне 2026 пользователь попросил короткое видео готовой функции, чтобы рецензент видел, что она работает, без повторного запуска. В запросе сказано: session sharing показывает, что делал агент, но не то, работает ли результат [149].
- Страница Factories теперь утверждает, что каждый агент снимает скриншот или видео до PR [90]. Реакции пользователей на это не найдено.

### Claude Code и Codex внутри Warp

- Пользователи ценят значки статуса, уведомления, переход к ожидающей session и code review [151][172]. Пробелы, которые они называют:
  - sessions Claude Code и Codex не видны в Agent Management Panel [52];
  - sessions не восстанавливаются после перезапуска; это issue #14720 [140]. Разработчик сделал fork Warp под названием «Clinch» отчасти ради этого, убрав Oz и telemetry. У fork 7 stars [160];
  - уведомления сломались после обновления Claude Code [142];
  - worktrees, созданные `claude --worktree`, не обновляют в Warp данные о ветке, PR и дереве файлов [142];
  - один пользователь ушёл в другой инструмент, чтобы запускать по агенту на worktree [142];
  - пользователи просят показывать Claude Code Agent Teams в разделённых панелях [142].
- Люди спрашивают, зачем Warp делает своего агента, а не встраивает существующих [152]:
  - пользователи написали, что в Warp Agent CLI нет ничего особенного по сравнению с OpenCode или pi;
  - инженер Warp ответил, что отличие — команды на переднем плане: `cd`, REPL и SSH без установки на удалённой машине;
  - комментаторы добавили, что большинство разработчиков выбирают Claude Code или Codex, чтобы работать по подписке, а не платить за токены.

### Почему приходят и почему уходят

**Приходят ради:**
- поля ввода;
- аккуратного интерфейса и настроек в графическом окне;
- генерации команд из обычного текста;
- управления несколькими вкладками агентов;
- поддержки macOS, Windows, Linux и WSL;
- того, что BYOK теперь бесплатен [150][153][151][135].

**Уходят из-за:**
- навязанного AI и изменений интерфейса;
- разрастания продукта;
- credits;
- telemetry и наследия обязательного входа;
- запретов в компаниях (один пользователь написал, что Warp не одобрен у него на работе) [152][154].

Пользователь HN в ноябре 2026 попробовал opencode, Warp, Orca и другие инструменты и вернулся к обычным Claude Code и Codex [162].

### Альтернативы глазами пользователей

- **Терминалы:** Ghostty, iTerm2, WezTerm, kitty и fish. Часть пользователей нашла Ghostty менее отделанным и вернулась в Warp [150][153][154][155][172].
- **Запуск нескольких агентов:** cmux; Superset (берёт ticket из Linear, создаёт worktree, резервирует порты, открывает браузер и запускает Claude); Orca; Herdr; agentastic [150][151][152].
- **Harness, то есть сами программы-агенты:** Claude Code, Codex, OpenCode и pi [152].

### Что поменяли в главном

- **Закрытый код → открытый** [98] → [106]. В интервью Lloyd назвал одной из главных причин то, что продукт получился слишком «opinionated» [168].
- **Свой агент → независимость от агента.** Lloyd хочет, чтобы Warp дополнял Claude Code и Codex, а не конкурировал с ними [168].
- **Локальная работа с человеком в цикле → облако и автоматизация** [99] → [113][111].
- **AI в комплекте → usage по ценам API и свой inference.** Lloyd говорит, что Warp уходит из бизнеса перепродажи токенов [114].
- **Бренд Oz растворён в Warp Factories.** Пакеты SDK переименованы в `warp-platform-sdk`; Oz CLI местами помечен как legacy [8][2].
- **Продуктовая компания → инфраструктурная.** Команда пишет, что в основном этот сдвиг уже сделала [124].

### Бизнес и рынок

- **Ставка.** Lloyd говорит, что бизнес-ставка — помогать компаниям строить software factories, а не интерактивный агент. Принятие среди разработчиков ведёт к продажам крупным компаниям [168]. Внутренняя записка называет бизнес фабрик единственным бизнесом продуктивности разработки, который будет иметь значение [111].
- **BYOK.** Бесплатен для частных лиц и компаний до 10 человек. Большие компании платят «platform credits» за время активной работы агента [109].
- **Цена.** Warp пишет, что не может конкурировать ценой или дотировать usage [106]. Довод Lloyd: у перепродавцов inference сжимается маржа, а крупные компании хотят свой inference [114].
- **Кому продают — источники расходятся.** TechCrunch (вторичный источник) цитирует Lloyd: Factories нацелены на небольшие компании, которые не могут построить фабрику сами [167]. Блог Warp делает упор на управление и self-hosting для крупных компаний [108][116].
- **Цифры роста от Warp:**
  - около 2 млн запусков агентов в день в июле 2025; выручка выросла в 15 раз с начала года на июль 2025 [100];
  - за 2025 год агенты изменили 3.2 млрд строк, внутри Warp влито 10 000+ PR, поддерживается 20+ моделей [103];
  - цифра ARR не опубликована (не подтверждено).

## Слабые места и чего нет

**Сторонние агенты поддержаны слабее встроенного.**
- Sessions Claude Code, Codex и других CLI не попадают ни в Agent Management Panel, ни в Conversation Panel [52][53].
- После перезапуска Warp они сами не восстанавливаются (#14720) [140].
- Уведомления есть только у Claude Code, Codex, OpenCode и Antigravity [52]. После обновления Claude Code они ломались [142].
- Worktrees, созданные `claude --worktree`, не обновляют в Warp данные о ветке, PR и дереве файлов [142].
- Перенос с машины в облако работает только для Warp Agent [12].
- Computer Use выключен для Claude Code и Codex; рецепт проверки UI работает только на harness Warp Agent [57][48].
- Agent Memory работает только для облачных run [66].

**Подписки и лимиты.**
- Облачные Claude Code и Codex требуют оплаченных API-ключей. Подписки Claude и ChatGPT облачные run не оплачивают [30][31][74].
- Сообщение о лимите плана у стороннего harness — сразу FAILED. Ожидания сброса лимита в клиентском коде нет; на сервере — не подтверждено [128].
- Потребительская подписка Claude для агента Warp не поддерживается [74][75].

**Стоимость и прозрачность.**
- Нет оценки стоимости до облачного run и нет потолка на один run [143].
- Oz web app и desktop-приложение показывают разные суммы credits за один run [144].
- Стоимость PR на Dashboard — оценка, а не счёт [27]. Внешний inference в итогах Warp отражён не полностью [40][29].
- Пользователи жалуются на credits и рост цены после октября 2025 [153][157][155][133].
- На бесплатном тарифе нет usage Warp Agent, а срок жизни sandbox фиксирован [82][128].

**Оркестрация.**
- Только один уровень: родитель и дети [10].
- На машине пользователя нет автоматического worktree для дочернего агента [10].
- Отмена родителя не отменяет детей. Статус родителя не показывает падения детей [11][9].
- Уведомления в приложении — только по родителю [56].
- Последний шаг дочернего агента жёстко делает push и draft PR, даже если правила пользователя это запрещают [146].

**Factories.**
- Всё ещё early access; дата general availability не названа [90][124].
- Review делается один раз на work item, и его вердикт только рекомендательный [131][23].
- Автоматического повтора упавшего этапа в документации нет (не подтверждено).
- Factory MCP: взятая задача не блокируется и не закрепляется; нет scopes «только чтение» и «одна фабрика»; уведомления без гарантии доставки; сервер перезапускается по кругу после 403 [28][147].
- Одна фабрика не может подключить Linear и Jira одновременно [43].
- Run получают SUCCEEDED без ответов и transcripts; в фабрике из файлов нельзя сменить модель-судью Correctness scorer [147].
- Редактор определения в web — только для фабрик, которыми управляет Warp [27].
- Назначать роли можно только на Enterprise [47].
- Внешних пользователей в issues мало, большинство issues про Factories создали боты Warp. Независимых результатов нет [147][161][171].

**Безопасность и доверие.**
- В облаке CLI-агенты работают с выключенными подтверждениями. Без заданной `networkPolicy` исходящий доступ не ограничен [128][37].
- В общих sessions нет redaction secrets [86].
- Общий доступ и Remote Control идут только через облако Warp; прямого режима по локальной сети не найдено (не подтверждено).
- BYOK и свои endpoints всё равно идут через серверы Warp. Внутренний endpoint должен быть доступен из интернета [136].
- Утечка traces агентов и telemetry в октябре 2026 [158][169]; были ли украдены secrets — не подтверждено [170].
- История с обязательным входом, telemetry и «Active AI» продолжает отталкивать людей [150][154].
- Self-hosted Direct изолирует файлы и ветки, но не ОС хоста [42].

**Терминал и клиент.**
- Тяжёлое приложение (около 850–900 MB, больше 1 GB памяти), частые изменения интерфейса, зависания при работе Claude Code [150][152][153][138][139].
- Нет локальных моделей — самый популярный запрос, открыт с 2024 года [134].
- Полного офлайн-режима, возможно, нет: запрос «Full Offline Support» (#5640, 115 голосов) открыт [177]. Lloyd при этом пишет, что функции терминала работают без сервера, а сервер нужен только AI [136]. Источники расходятся (не подтверждено).
- На Windows просят cmd.exe [133].
- Ориентация на команду: Factories, интеграции и общие secrets требуют команду [46][18].

**Наблюдаемость.**
- Всё показано списками и вкладками. Пространственного вида нет. Воспроизведения хода run, кроме transcript и хронологии на странице Runs, нет [9][15][27].
- Warp сам пишет, что это не APM [9].
- Размер лимита параллельных run не документирован (не подтверждено) [39].
- Где Agent Management Panel находится в окне по текущей документации — не подтверждено.

**Платформы.**
- Нативного мобильного приложения и расширения для IDE в документации нет, хотя маркетинг обещает управление «from web, mobile, terminal, or IDE» (не подтверждено) [90].

**Где пересекаются.**
- Оба запускают Claude Code и Codex и показывают их статус, уведомляют о вопросах и дают перейти к ожидающей session [52][56][151].
- Оба делят работу на единицы с собственным жизненным циклом: ticket у worfy, work item у Warp [23].
- Оба держат координатора, который раздаёт работу исполнителям и рецензентам [24][131].
- Оба ставят plugin в Claude Code и используют его hooks [130].
- Оба собирают визуальные доказательства и прикладывают их к PR [58][131].
- Оба держат очередь того, что ждёт человека: PR inbox у worfy, «Waiting on you» у Warp [26].

**Где расходятся.**
- **Где идёт работа.** worfy работает на машине пользователя. Warp ставит на первое место облачную sandbox на каждый run и прямо выступает против агентов на ноутбуках [38][113].
- **Как оплачивается модель.** worfy работает на подписках и планирует run под их лимиты. Warp в облаке требует API-ключи, а сообщение о лимите подписки считает фатальной ошибкой [30][31][128].
- **Для кого.** worfy — один пользователь. Warp — команда: роли, общие secrets, интеграции, метрики команды [46][18][27].
- **Как видна работа.** worfy — Canvas. Warp — вкладки, списки и Dashboard [80][9][27].
- **Как одобряются действия.** worfy — по политике на машине. Warp в облаке выключает подтверждения CLI и полагается на изоляцию и узкие credentials [128][7].
- **Как проверяется результат.** worfy — локальный Gate, CI и рецензенты с разными lenses. Warp — проверки внутри implement-агента, один рекомендательный review и оценка run моделью-судьёй после факта [131][23][34].
- **Чего у Warp нет из списка worfy:** Cards через MCP, встроенный Browser с профилями, Product Session с Mind map, связь машин по LAN, удаление личных данных со скриншотов (последние два — не подтверждено).
- **Чего нет у worfy из списка Warp** (по описанию worfy): облачные sandbox, фабрика как код, оценка run моделью-судьёй, Self-improvement, Benchmarks, работа в браузере и с телефона, оплата по факту для команды [37][34][35][36][16].

## Механизмы, которые стоит изучить

1. **Foreman — процедура, в которую можно войти с любого шага.**
   - Что это. Координатор фабрики — LLM-агент с письменной процедурой из семи шагов, а не код-оркестратор [131].
   - Как работает. Любое событие — новый запрос, PR на review, падение CI, уведомление о merge, ответ на вопрос — снова запускает foreman. Он находит текущий шаг и идёт кратчайшим путём, который ещё соответствует политике качества [131][23]. Состояние работы хранится в issue, PR и закоммиченном spec. Для мелкой работы без issue записью служит разговор самого foreman, а follow-up уходит тому агенту этапа, у которого уже есть контекст [131]. Застрявший run продолжают, запустив foreman заново на том же состоянии work item [118]. Review — один раз на work item: однозначные замечания уходят исполнителю, неоднозначные — человеку в PR [131].
2. **Inbox на агента и пробуждение законченных детей.**
   - Что это. Надёжная серверная шина сообщений: inbox на каждый ID агента и события жизненного цикла [10].
   - Как работает. Родитель получает события, а не опрашивает детей. Законченный ребёнок остаётся адресуемым по ID агента и просыпается от нового сообщения [10]. Отдельно `idleTimeoutMinutes` держит законченную session открытой для follow-up от 1 до 60 минут: 10 по умолчанию, 60 для ребёнка оркестрации [37]. Ограничено ли пробуждение этим окном, документация не говорит (не подтверждено). В Claude Code сообщения доставляет plugin: SessionStart запускает слушатель, UserPromptSubmit и PostToolUse подмешивают сообщения в контекст, Stop не даёт закончить, пока есть недоставленные. На диске сообщение проходит `staged/` → `surfaced/` → `pending-hook-output.json` с файлом `.ack`. Ребёнок заканчивает явной командой `finish-task` со статусом success или failure; failure даёт BLOCKED [130][128].
3. **Общий бюджет восстановления на запрос.**
   - Что это. Один счётчик на повторы и resume: `MAX_RECOVERY_ATTEMPTS = 3` [128].
   - Как работает. Resume ждёт паузу со случайным разбросом и возвращения сети; в облаке — 120 s на попытку. Комментарий в коде объясняет причину: одиночный resume попадал в то же окно обрывов во время поэтапного deploy серверов [128].
4. **Checkpoints на безопасной границе с пределом ожидания и snapshot по сигналу.**
   - Что это. Периодическое сохранение workspace во время run [128][14].
   - Как работает. Таймер — 5 минут от конца предыдущей попытки плюс случайная задержка до 30 s, чтобы агенты не сохранялись одновременно. Потом драйвер ждёт момента, когда ход не идёт, и проверяет это каждые 2 s. Ждёт он не дольше 10 минут, после чего checkpoint снимается и посреди хода: комментарий в коде — «a slightly-inconsistent checkpoint is strictly better than none» [128]. Первый SIGTERM или SIGINT тоже снимает snapshot. Что сохранять, решает скрипт деклараций (строки JSONL `repo` или `file`); по умолчанию — все git-репозитории. Сохраняются diff и неотслеживаемые файлы с манифестом; ошибка выгрузки не роняет run [14][128].
5. **Монитор вывода harness и три класса исхода.**
   - Что это. Фоновый поиск известных строк ошибок в выводе Claude Code и Codex и деление исходов на FAILED, ERROR и BLOCKED [128].
   - Как работает. Строки лимитов — «You've hit your», «Credit balance too low», «API Error: Request rejected (429)», «Quota exceeded» — сразу дают FAILED, чтобы harness не висел. FAILED — исход задачи, ERROR — инфраструктура, у ошибок API есть флаг `retryable`, BLOCKED — нужен человек [128][49][9]. Остановка ограничена по времени: `/exit`, через 1 s Enter, через 14 s SIGKILL группы процессов [128].
6. **Hook Stop, который отличает «закончил» от «ждёт фоновую работу».**
   - Что это. Plugin Warp для Claude Code передаёт события session прямо в терминал через escape-последовательности OSC 777 [130].
   - Как работает. Hooks (SessionStart, Stop, StopFailure, Notification, PermissionRequest, UserPromptSubmit, PostToolUse) шлют JSON на `warp://cli-agent`. Stop сообщает о незаконченных фоновых задачах и запланированных пробуждениях, поэтому вкладка не показывает «готово», пока Claude Code ждёт фоновую работу. Канал — сам терминал, отдельный сервер не нужен [130][52].
7. **Цепочка доказательств от spec до PR.**
   - Что это. Требования к доказательствам на каждом этапе фабрики [131][48].
   - Как работает. Spec называет для каждого критерия тест или команду, для UI — видео. Implement пишет regression test, который падает до изменения и проходит после, гоняет проверки репозитория и не заявляет непроверенное: «Never claim that an unverified change passed». Review не доверяет описанию PR и блокирует при отсутствии визуального доказательства [131]. Verify-агент проверяет точный SHA и помечает результат устаревшим, если head PR сдвинулся [48]. Снимки прикладываются к PR в режиме «только ссылка» с проверкой доступа [58]. В записях вырезан простой, а ввод текста заменён подписью «typing…» [59].
8. **Цикл Scorers → Self-improvement → Benchmarks.**
   - Что это. Измерение качества агентов после факта и автоматические PR с исправлениями [34][35][36].
   - Как работает. Модель-судья оценивает 10% законченных run по меткам с порогом [34][37]. Неудачи копятся. При 25 непросмотренных или когда старейшей 7 дней Self-improvement открывает PR в код или в определение фабрики с разделом «Regressions addressed» [35]. Benchmarks сравнивают конфигурации (harness, модель, runner) с повторами на задачах из прошлых run, чтобы сопоставить качество и цену [36]. В `suite.yaml` можно заранее задать от одной до шести конфигураций [37].
9. **Factory-as-code с проверкой целиком.**
   - Что это. Всё определение фабрики — дерево YAML и Markdown, в том числе в репозитории команды [37].
   - Как работает. Определение применяется целиком. Если проверка не прошла, остаётся последнее рабочее определение. В репозитории это проверяет PR check `warp/factory-config`. JSON Schemas и скрипт проверки опубликованы [37]. Правки определения от агентов приходят как spec review с «Approve & merge» [27].
10. **Личная очередь «Waiting on you».**
    - Что это. Одна страница со всем, что ждёт конкретного человека [26].
    - Как работает. Вопросы, ответы на них, spec review, PR review (включая GitHub review, запрошенные у вас на чужую работу), заблокированные и упавшие run. «Mark as resolved» с Undo. Поиск по Today, This week и All time [26].
11. **Метрики фабрики: Autonomy, cycle time по этапам, cost per PR.**
    - Что это. Dashboard в терминах результата, а не активности агентов [27][33].
    - Как работает. Autonomy — доля слитых PR, в которые человек не пушил код. Медиана cycle time по каждому этапу. Медиана стоимости PR с разбивкой на compute, platform и inference и по размеру S/M/L/XL; список самых дорогих PR. Метрики merge требуют GitHub App или webhook GitLab. Стоимость — оценка, а не счёт [27].
12. **Handoff в облако при сне Mac и заранее прогретые sandbox.**
    - Что это. Работа агента не останавливается, когда ноутбук засыпает [128].
    - Как работает. Если настройка включена, активный локальный run уходит в облако со snapshot workspace. Этого не происходит, если разговор — оркестратор с работающими локальными детьми или если модель недоступна в облаке [128][13]. В облаке прогретые sandbox ждут с heartbeat, пока сервер не назначит им run; с 2026-10-22 возобновлённые run берут их [128][4].
