## Модель работы

**Local / cloud / hybrid: hybrid.**

- Цикл агента выполняется на машине пользователя. Код не загружается в облако Factory и не индексируется там [70].
- Factory всегда хранит метаданные сессий. Синхронизация содержимого сессий — отдельный переключатель `cloudSessionSync` [12][68]. Организация может потребовать, чтобы хранились только метаданные [10][12].
- Работа может идти и в облаке:
  - Droid Computers — постоянные облачные машины Factory; в этой роли можно подключить и свою машину [53][99];
  - Environments — заранее собранные образы для свежих облачных sandbox [55][123];
  - OpenCompute — оркестратор sandbox, который клиент ставит у себя, например в Kubernetes (Private Preview) [56].
- Remote Control подключает собственную машину пользователя через relay Factory. Входящие порты не нужны [54].
- Inference по умолчанию идёт через Factory и считается в лимитах подписки. На плане Free пользователь приносит свою inference: вход через ChatGPT, GitHub Copilot или OpenRouter либо свои ключи и endpoint [3][133].
- Модели со своими ключами (BYOK, bring your own key) работают только локально. Ключи не покидают машину, поэтому такие модели не видны в вебе и в мобильной версии [58].
- Для предприятий есть два варианта [67]:
  - Factory Managed — всё работает у Factory;
  - Factory Private — control plane у Factory, а sandboxes OpenCompute работают в VPC клиента.
- Также доступны on-prem, air-gapped и хранение данных в EU (с 2026-05-14) [1][72][118].

**Агенты и модели.**

- Агент один — Droid. Он работает в разных ролях: обычная сессия, subagent («custom droid»), orchestrator, worker и validator в Missions, агенты в Workstreams [18][32][97].
- Признаков того, что Factory запускает процессы Claude Code или Codex CLI, в прочитанной документации нет. Входа по подписке Claude тоже нет: в полном тексте документации (`llms-full.txt`) вход по чужой подписке описан только для ChatGPT (`credentialSource: "chatgpt-plan"`), GitHub Copilot и OpenRouter [3][64][222].
- Каталог моделей [5]:
  - Anthropic: семейство Claude Fable 5.x, Opus 4.5–5.5 (включая варианты «Fast»), Sonnet 4.5–5.5, Haiku;
  - OpenAI: от GPT-5.2 до GPT-6.1, включая варианты Codex и Fast;
  - Google: от Gemini 3 до Gemini 4;
  - xAI: Grok 4.5–4.7;
  - Droid Core — пул открытых моделей (open-weight): GLM, Kimi, Qwen, DeepSeek, MiniMax, Nemotron, Mistral и другие.
- У каждой модели есть множитель расхода и набор уровней reasoning [5].
- Factory Router (в интерфейсе — «Auto Model») сам выбирает модель под задачу [57].

**Один пользователь или команда.**

- И то и другое. Есть индивидуальные планы (Free, Pro, Plus, Max) и планы для организаций (Teams, Business, Enterprise) [3][4].
- Продажи построены вокруг предприятий: отдельный CRO, руководитель направления госсектора США, партнёрская сеть на $100M [89][112].
- Workstreams пока работают для одного человека. Совместную работу («multiplayer») Factory пообещала 2026-11-04 [128].

**Платформы.**

- Desktop app: macOS (Apple Silicon и Intel), Windows (x64 и ARM64, есть подписанный пакет MSIX), Linux (x64 и ARM64, скрипт установки или пакет `.deb`) [2][7][8][72].
- Веб app.factory.ai в адаптивной вёрстке для телефона. Нативного приложения для iOS или Android не найдено (не подтверждено) [72].
- CLI и TUI `droid`: установка через curl, Homebrew, PowerShell или npm [2][11].
- Headless-режим `droid exec`, Execute API, публичный REST API, SDK для TypeScript и Python [60][61][62][63][155].
- IDE: расширение для VS Code, Cursor и Windsurf; JetBrains и Zed через ACP (Agent Client Protocol — протокол связи редактора с агентом) [59].
- Чаты и трекеры: Slack, Microsoft Teams, Google Chat, Linear, Jira [50].
- CI: GitHub, GitLab, Bitbucket и Azure DevOps через `droid-action` [44].

## Функции

### Тарифы, лимиты и учёт расхода

| План | Цена | Что входит | Источник |
|---|---|---|---|
| Free | $0 | Своя inference: вход через ChatGPT, GitHub Copilot или OpenRouter либо свои ключи и endpoint. В схеме API у custom models есть вариант `credentialSource: "chatgpt-plan"` | [3][64][133] |
| Pro | $20 в месяц | Inference через Factory со скользящими лимитами; desktop, CLI и SDK. С 2026-09-09 — управляемые облачные машины на 5 compute-часов в месяц | [3][72][133] |
| Plus | $100 в месяц | Примерно 5× объёма Pro | [133] |
| Max | $200 в месяц | Примерно 10× объёма Pro | [133] |
| Teams | $60 в месяц за команду + $40 за место | До 10 мест, у каждого места лимиты Pro, общий счёт раз в месяц | [4][133] |
| Business | по запросу | Свои лимиты, SSO, SAML/SCIM, Zero Data Retention, audit log, базовые настройки администратора | [4] |
| Enterprise | по запросу | Сверх Business: неограниченное число мест, выделенные вычисления, отдельный пул inference, on-prem, суб-организации, хранение данных в нужном регионе, SLA | [4] |

- **Три скользящих окна.** Окна на 5 часов, 7 дней и 30 дней считаются независимо. Запрос проходит, только если запас есть во всех трёх. Каждое окно отсчитывается с первого использования и сбрасывается, когда истекло [3].
- **Порядок расхода.** Сначала тратится Standard Usage — основной объём плана. Когда он кончился, есть два пути, а не цепочка: бесплатно перейти на пул Droid Core с отдельным лимитом или купить Extra Usage, чтобы остаться на стандартных моделях. Extra Usage — предоплаченные кредиты от $10 без срока действия [3][133].
- **Где смотреть.** Команда `/limits` в CLI и страница Settings → Usage в app показывают расход и включают Droid Core или Extra Usage [3].
- **Missions** тратят те же окна. Для них нужно включить Extra Usage. Упёршись в лимит, Mission встаёт на паузу [3].
- **Автопереход на Droid Core.** С 2026-04-26 сессия сама переходит на Droid Core, если так задано в настройке перерасхода [72].
- **Лимит посреди сессии.** Текущий запрос доходит до конца. Следующие запросы падают с ошибкой лимита; в `/limits` можно включить Droid Core или Extra Usage и сразу повторить [3]. В CLI это ответ HTTP 402 с названием окна и временем до сброса, например «weekly standard usage limit (resets in 4 days)» [173].
- **Workstreams и лимиты.** На 90% лимита появляется баннер. На лимите агенты стоят до сброса окна; продолжат ли они сами после сброса, страница не говорит. Кнопка «Change models» снижает усилие reasoning или ставит orchestrator и агентам более дешёвую модель. Когда кончился Standard Usage, workstream можно перевести на модели Droid Core с отдельным объёмом или докупить usage [26].
- **Учёт для пользователя:**
  - `/limits` (остатки по группам кредитов), `/cost`, `/stats [period]`, `/context` [11][72];
  - личная страница аналитики (с 2026-03-05) [72];
  - письма на 80% и 100% месячного лимита [12];
  - еженедельная сводка расхода, которую организация может отключить [12].
- **Единица расчёта** — Standard Credits; до марта 2026 она называлась Billable Tokens. У каждой модели свой множитель цены [5][72].
- **Service account** — служебная учётная запись. На индивидуальных планах и Teams есть одна, только для Delegations. На Business и Enterprise их можно создать больше [50].
- **Ваучер.** Страница /teams обещает отобранным заявителям $500 на план Teams [140].

### Модели и маршрутизация

- **Каталог моделей** с множителем расхода и уровнями reasoning у каждой [5]. Модели Anthropic Fable («Mythos-class») требуют, чтобы администратор согласился на хранение данных 30 дней [5].
- **Factory Router («Auto Model»)** [57]:
  - выбирает модель для каждой задачи;
  - при сбое переключается на другого провайдера; вендор заявляет надёжность запросов 99,9%+;
  - администратор задаёт правила маршрутизации и может разрешить или потребовать модели со своими ключами;
  - вендор заявляет 63% общей экономии в production [57].
- **Свои модели (custom models, BYOK)** [58][72]:
  - добавляются в блок `customModels` файла `settings.json`, через `/model` или `/settings` в CLI (с 2026-09-29) или на странице Settings → Custom Models в app;
  - провайдеры: Anthropic, OpenAI (Responses API), любой OpenAI-совместимый chat API, Bedrock, Vertex, локальные серверы Ollama, vLLM и LM Studio;
  - `apiKeyHelper` — скрипт, который выпускает короткоживущие токены;
  - ключи остаются на машине, поэтому BYOK-модели не видны в вебе и мобильной версии.
- **Управление моделью в сессии:**
  - `/fast` включает быстрый режим [11][72];
  - Tab переключает уровень reasoning, Ctrl+N — модель [11];
  - `--spec-model` задаёт отдельную модель для планирования [11];
  - в Missions отдельно выбираются модели worker и validator [17];
  - `modelFallbacks` — карта запасных моделей для каждой модели [12];
  - `legacyModelOverrides` оставляет старую модель вместо автоматического перехода на новую [11].

### Worktrees

**В app** [9]:

- В поле новой задачи есть **New worktree**: выбор базовой ветки, затем «новая ветка» или «существующая ветка».
- Жизненный цикл: **Ephemeral** (может быть удалён автоматически) или **Persistent** (показывается как проект). App запоминает последний выбор для каждого проекта.
- **Setup profiles** — профили подготовки из трёх частей: setup-скрипт, первый prompt для Droid и cleanup-скрипт.
  - Перед запуском скриптов из окружения убираются учётные данные.
  - Переменная `REPO_ROOT_PATH` указывает на основной checkout.
  - Профили можно хранить в репозитории: `.factory/worktree-setups/*.yaml`.
- **`.worktreeinclude`** — список git-ignored файлов (например `.env.local`), которые копируются в каждый новый worktree.
- **Settings → Worktrees:** папка для worktrees (по умолчанию `~/.factory/worktrees`), сколько ephemeral-worktrees хранить (по умолчанию 15), список worktrees с размером, типом и активными сессиями.
- **Автоочистка** удаляет сначала самый давно использованный ephemeral-worktree. Она пропускает worktree, если у него есть [9]:
  - закреплённая, активная или недавно использованная сессия;
  - незакоммиченные или неотслеживаемые файлы;
  - открытый PR;
  - незапушенные коммиты (кроме случая, когда PR уже смержен).
- Очистка уважает git locks, не трогает worktree, который не удалось проверить, и удаляет только checkout, никогда не ветку [9]. С v1.9.0 checkout остаётся, если во время очистки в него пришёл коммит [72].
- Перед ручным удалением app показывает незакоммиченные изменения, неотслеживаемые файлы и незапушенные коммиты [9].

**В CLI** [11]:

- `droid -w [name]` и `droid exec --worktree`. Без имени ветка называется `<текущая-ветка>-wt`. Путь — `<root>/<группа из 8 символов>/<repo>/`.
- В режиме `exec` чистый worktree удаляется при выходе. Грязный остаётся, и его путь печатается.

### Droid CLI и TUI

- **Установка:** скрипт curl, Homebrew cask, PowerShell или npm. Отдельная сборка обновляется сама; `droid update -v <версия>` откатывает на нужную версию. В сборке из npm автообновление выключено [2][11].
- **Команды** [11]:
  - `droid "запрос"`, `--resume`, `--fork`;
  - `droid search` (синоним `find`) — локальный полнотекстовый поиск по сессиям;
  - `droid rules check [--command ...]` — проверить permission rules и посмотреть, что будет с командой;
  - `droid mcp add|remove`;
  - `droid plugin install|update|list|marketplace`;
  - `droid computer register|list|ssh|port-forward`;
  - `droid daemon [--remote-control]`;
  - exit codes: 0 — успех, 1 — ошибка во время работы, 2 — неверные аргументы.
- **Slash commands**, около 50 [11]:
  - сессия: `/sessions`, `/tree` (дерево fork-ов с метками и фильтрами), `/fork`, `/rewind-conversation`, `/compress`, `/context`, `/archive`, `/share` (поделиться с организацией);
  - расход: `/cost`, `/stats [period]`, `/limits`;
  - расширения: `/missions`, `/droids`, `/skills`, `/create-skill`, `/hooks`, `/plugins`, `/mcp`;
  - готовые процессы: `/review`, `/readiness-report`, `/readiness-fix`, `/install-code-review`, `/install-slack-app`, `/setup-incident-response`;
  - интерфейс: `/statusline`, `/themes`, `/vim`, `/language`, `/btw`, `/bug`.
- Slash commands работают и во время хода агента. Команды, которые переписывают сессию, сначала просят подтверждение [11].
- **Ввод во время работы.** Пользователь печатает, пока агент работает. Сообщения в очереди можно вернуть в поле ввода или выбросить [11][160].
- **Клавиши** [11]:
  - `!` — bash mode (shell без AI);
  - Ctrl+T — overlay Mission Control;
  - Ctrl+O — подробный transcript;
  - Ctrl+L — смена уровня autonomy;
  - Shift+Tab — переключение Normal/Spec;
  - двойной Escape — откат (rewind).
- **Отрисовка в терминале:** диаграммы Mermaid рисуются ASCII-графикой (flowchart, sequence, state, class, ER); формулы TeX — символами Unicode [11].
- **Языки TUI:** японский, китайский и корейский (2026-03-05), итальянский (2026-04-28) [72].
- **`droid doctor`** проверяет связь, MCP servers, дубли установки в PATH и полный ход агента [72].

### Headless-режим, API и SDK

- **`droid exec`** — запуск без интерфейса, для скриптов и CI [11][60]:
  - по умолчанию только чтение; `--auto low|medium|high` повышает autonomy; `--skip-permissions-unsafe` убирает вопросы, но правила block всё равно действуют;
  - форматы вывода: `text`, `json`, `stream-json`, `stream-jsonrpc`, а для IDE — `acp` [59]; события `stream-json` — system, message, tool_call, tool_result, completion [60];
  - выбор инструментов: `--only-tools`, `--add-tools`, `--remove-tools`, в том числе отдельные MCP-инструменты;
  - также `--tag`, `--append-system-prompt[-file]`, `--settings` (наложение настроек поверх обычных) и `--mission`;
  - если действие требует autonomy выше разрешённой, запуск завершается с ненулевым exit code, а уже сделанные правки остаются [60];
  - готовые рецепты в документации: автоисправление lint, чистка imports, тексты ошибок, проверка зависимостей и секретов, ночное обновление docs и tests [1].
- **Execute API** — `POST api.factory.ai/api/v0/droid/execute`, ответ 202 [61]. Цель запуска: Environment (свежий компьютер), существующий компьютер или существующая сессия. Ход работы узнают опросом сессии.
- **Публичный REST API** [1][63][132]:
  - ключ Bearer или JWT;
  - группы методов: сессии, компьютеры, environments, CI-automations, wiki, readiness reports, аналитика, организация и service accounts;
  - с 2026-11-11 у каждой операции стабильный ID; события audit организации можно забирать опросом [72].
- **SDK `@factory/droid-sdk`** для TypeScript [62]:
  - запускает тот же harness как подпроцесс Node или подключается к работающему daemon;
  - методы `run()`, `createSession()`, `resumeSession()`, `listModels()`, `listSessions()`, плюс MCP-инструменты внутри процесса.
  - Есть и SDK для Python [155].

### IDE

- **VS Code, Cursor, Windsurf:** расширение передаёт агенту активный файл, выделение, открытые файлы и diagnostics и показывает diff средствами IDE. Управление — командой `/ide` [59].
- **JetBrains (2025.3+):** Droid появляется в AI Chat через реестр ACP. Открытые файлы, выделение и diff пока не передаются [59].

### Режимы, autonomy и безопасность

- **Режимы работы** [27]:
  - **Normal** — обычная сессия;
  - **Spec** — только чтение и план; заканчивается запросом одобрения через инструмент `ExitSpecMode`;
  - **Mission** — долгий многоагентный запуск.
- **Одобрение spec.** Пользователь выбирает уровень autonomy для реализации или отвечает «Proceed with comment» [27][72]. Одобренный spec можно сохранить в Markdown с именем `YYYY-MM-DD-slug.md` [27], скачать или продолжить в новом чате, который начинается с этого spec [72].
- **Где лежит spec — источники расходятся.** Страница Spec mode называет папку `.factory/docs/` в репозитории [27]. Страница настроек CLI называет папку по умолчанию `~/.factory/specs`, она задаётся через `specSaveDir` [12].
- **Уровни autonomy** — Off, Low, Medium, High [28]:
  - у каждой команды и MCP-инструмента есть оценка риска; команда выполняется без вопроса, если её риск не выше уровня сессии;
  - ответ «Allow always» поднимает уровень сессии;
  - `mcpAutonomyOverrides` задаёт уровень отдельным MCP-инструментам [72];
  - subagents наследуют уровень родителя или задают свой;
  - организация ограничивает максимум через `maxAutonomyLevel` [28].
- **Permission rules** [29]:
  - решения `allow`, `ask` или `block` по упорядоченному префиксу команды;
  - в каждое правило встроены тестовые примеры (`match`/`noMatch`);
  - приоритет: block, потом ask, потом allow;
  - уровни правил: организация, проект, папка, пользователь и файл `settings.local.json`.
- **Sandbox ОС** [31]:
  - на macOS — Seatbelt, на Linux и WSL2 — bubblewrap с фильтром seccomp;
  - сеть идёт через proxy со списком разрешённых доменов;
  - режим `per-command` ограничивает каждую shell-команду, режим `whole-process` — весь процесс Droid;
  - по умолчанию запись разрешена только в рабочую папку, чтение — везде, кроме запрещённых путей.
- **Droid Shield** [30]:
  - перед `git commit` или `git push`, которые выполняет Droid, проверяет добавленные строки и блокирует операцию, если находит секреты; включён по умолчанию;
  - версия 2.0 добавляет две дообученные модели (Private Preview): модель «риска» ищет секреты, которые пропустили шаблоны, а модель «понижения» превращает ложные срабатывания в предупреждения.
- **Hooks** [33]:
  - девять событий: PreToolUse, PostToolUse, UserPromptSubmit, Notification (типы `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`), Stop, SubagentStop, PreCompact, SessionStart, SessionEnd;
  - exit code 2 блокирует действие или возвращает агенту обратную связь;
  - плагины используют формат hooks Claude Code (с 2026-02-05) [72];
  - организация может рассылать свои managed hooks [33].
- **Защита от зацикливания** в harness 1.0 [126]:
  - на потоках Anthropic, которыми управляет Factory, 4 минуты тишины считаются обрывом, и запрос повторяется;
  - три хода подряд без вывода останавливают агента;
  - три одинаковых вызова инструмента дают агенту подсказку, шесть — останавливают цикл.

### Многоагентная работа

#### Missions

Mission — долгий многоагентный запуск. Orchestrator планирует, workers делают features (единицы работы), validators проверяют результат.

- **Как начинается** [13]. `/missions` открывает разговор о планировании. В нём определяются features и milestones (группы features, после которых идёт проверка), а также подбираются или создаются skills. После одобрения сессия переходит в **Mission Control**.
- **Масштаб:** примерно от 1 до 500 features [13].
- **Рекомендация к репозиторию:** для лучших результатов — Agent Readiness Level 4 (Optimized) или выше; жёстким условием запуска документация это не называет. Validators проверяют приложение как пользователь, поэтому его нужно уметь запустить и управлять им из скрипта [13].
- **Роли** [97]:
  - orchestrator;
  - по одному worker на feature, каждый в новой сессии; worker сначала пишет tests;
  - validators двух видов: «scrutiny» смотрят код, «user-testing» проверяют работающее приложение.
- **Общее состояние в файлах** [97]: `validation-contract.md` (пишется до любой feature), `features.json`, `services.yaml`, `AGENTS.md` и библиотека знаний, которая растёт по ходу запуска.
- **Порядок:** в основном последовательный. Провал проверки превращается в новую fix feature [97].
- **Проверка и оценка стоимости** [14]:
  - milestones задают, как часто идёт проверка;
  - оценка: число запусков агентов ≈ число features + 2 × число milestones; это нижняя граница;
  - для проверок Factory поставляет `tuistory` и `agent-browser`, чтобы validators управляли web-приложениями, Electron-приложениями и TUI;
  - проверку в стиле QA можно выключить.
- **Mission Control в app** [16]:
  - сверху — прошедшее время и потраченные кредиты;
  - справа — живой журнал хода работы и выбор моделей для orchestrator, worker и validator;
  - экран feature — критерии проверки и коммиты;
  - список workers — вывод терминала и рассуждения каждого;
  - кнопки Pause, re-plan и resume;
  - Mission может работать на Droid Computer;
  - разбивка токенов по workers (2026-04-02) [72].
- **Настройки** [17]:
  - `missionModelSettings.*`, `skipScrutiny`, `skipUserTesting`;
  - `keepSystemAwakeDuringMissions` — по умолчанию включено;
  - политика организации `missionPolicy.restrictedAccess` ограничивает, кто может запускать Missions;
  - headless-вариант — `droid exec --mission`; ему нужен `--auto high`.
- **Данные вендора о запусках** [78][97]:
  - медианная Mission длится около 2 часов; 37% — дольше 4 часов; 14% — дольше суток; самая долгая — 16 дней;
  - медиана обычной сессии — около 8 минут;
  - Mission тратит примерно в 12 раз больше токенов, чем обычная сессия;
  - пример — клон Slack: 16,5 часа, 185 запусков агентов, 778,5 млн токенов.
- **Если что-то пошло не так**, документация советует «поговорить с orchestrator»: поставить его на паузу, описать симптом, попросить переоценить план или отметить feature выполненной. Есть предупреждение о приближении к лимиту повторов feature [13].
- **Дата анонса расходится.** Страница анонса Missions датирована 2025-02-26 [144]. Но в тексте рекомендованы Opus 4.6, Sonnet 4.6, GPT-5.3-Codex и Kimi K2.5 [78]. Changelog впервые упоминает Missions 2026-01-27, поддержку Opus 4.6 — 2026-02-05, флаг `--mission` — 2026-03-05 [72]. Вероятнее всего, анонс вышел в феврале 2026 (не подтверждено).

#### Workstreams (beta, только в app)

Workstream — работа, которая начинается с разговора. Пользователь говорит с orchestrator, а тот раздаёт задачи агентам.

- **Доступность:** планы Pro, Plus, Max и Teams; на Business и Enterprise пока нет [18]. Даты запуска в changelog нет (не подтверждено) [72].
- **Метка beta.** Документация называет Workstreams beta [18]. Но по правилам самой Factory меток только две — «Private Preview» и «Deprecated», а страница без метки считается общедоступной [73].
- **Модель работы** [18][20]:
  - orchestrator распределяет работу, даёт каждому агенту вводные и спрашивает у пользователя решения, которые может принять только он;
  - агенты — обычные сессии Droid; любую можно открыть и написать ей напрямую.
- **Машины** [19][21]:
  - orchestrator работает на свежем облачном компьютере из Environment, на Droid Computer или «Local»;
  - агентов можно отправлять на другие машины;
  - orchestrator выбирает машину по **текстовому описанию каждой машины**, например «есть мобильный репозиторий, Xcode…» [21].
- **Вкладки:**
  - **Agents** — группы Waiting on you, Working и Idle [19][20];
  - **Files** — общая папка, которая синхронизируется между машинами: планы, заметки, передачи работы [22];
  - **PRs** — группы Open, Draft, Closed и Merged; в строке — checks и число комментариев и тредов; у открытого PR есть виды Conversation, Diff, Walkthrough и Validation и кнопки Review и Merge [23];
  - **Automations** — повторяющиеся задания, которые возвращают результат в workstream [25];
  - **Migration** — для команды `/migrate` [20];
  - **Tasks** — исправления CVE, Private Preview [24].
- **Панель действий в Tasks** [24]:
  - у каждой задачи — свои кнопки под её состояние: Approve plan, Merge PR, Retry with guidance;
  - каждое действие несёт версию задачи, которую видел пользователь, поэтому применяется не больше одного раза;
  - если orchestrator не подтвердил действие за 2 минуты, панель предлагает Continue in chat, Send again или Dismiss.
- **`/migrate`** (с 2026-09-26) [20][72]: пользователь и orchestrator договариваются о результате и плане проверки; потом orchestrator работает до конца и сдаёт доказательства. Вкладка **Migration** показывает примерную шкалу прогресса и ленту «сделано / в работе / дальше».
- **Настройки и расход** [26]:
  - бюджет compaction (сжатия контекста) для orchestrator — 500 тыс. токенов по умолчанию;
  - баннер на 90% лимита; на лимите агенты стоят до сброса окна;
  - кнопка «Change models» снижает усилие reasoning или ставит более дешёвую модель; переход на Droid Core или докупка usage — отдельные пути.
- **Обещано:** «multiplayer» задачи и workstreams и совместная работа в app над планами, specs и design docs, которые пишут агенты, — силами команды HumanLayer [128].

#### Custom droids (subagents)

- Описываются в Markdown в `.factory/droids/` или `~/.factory/droids/`. У каждого свой prompt, модель и политика инструментов [32].
- Встроены два: `worker` и `explorer` [32]. Missions добавляют `scrutiny-feature-reviewer` и `user-testing-flow-validator` [32].
- Subagent не может задавать вопросы пользователю и запускать своих subagents [32].
- Subagent останавливается после настраиваемого времени бездействия; по умолчанию 3 минуты с 2026-03-04 [72].
- Работающий subagent можно остановить из его панели в app [72].
- Агентов можно импортировать из Claude Code [32].

### Машины для работы

- **Droid Computers** [53][99] — постоянные облачные машины Factory. Файлы, сервисы и настройки сохраняются между сессиями.
  - Простаивающая машина засыпает и просыпается к следующей сессии [53]. Она восстанавливается из полных снимков файловой системы и памяти [99].
  - Подготовка машины показывает прогресс в реальном времени [53].
  - Страница машины: графики CPU, памяти и диска; версия daemon и кнопка удалённого обновления [53].
  - `droid computer ssh` идёт через relay с ключами Ed25519, которыми управляет Factory, и работает как ProxyCommand для VS Code Remote-SSH. `port-forward` пробрасывает только TCP [53].
  - Машину можно принудительно перезагрузить из сессии [72].
  - Своя машина в роли Droid Computer (BYOM, bring your own machine) бесплатна для всех [99].
- **Delegation pools** [53]:
  - до 20 управляемых машин в одной партии;
  - число параллельных workers на машину — 3 по умолчанию, от 1 до 50;
  - сессия держит слот 30 минут после перехода в простой;
  - на общих машинах Droid работает в своём worktree.
- **Remote Control** [54]:
  - своя машина на Linux, macOS или Windows; регистрация — `droid computer register`, запуск — `droid daemon --remote-control`;
  - соединение только исходящее, через `relay.factory.ai`, для организаций из EU — через `relay.eu.factory.ai`;
  - desktop app регистрирует себя по hostname и показывает переключатель Remote Control.
- **Environments** [55][123] — базовые образы облачных sandbox на основе снимков.
  - Общий доступ — с 2026-10-12 [123].
  - Пересобираются раз в несколько часов; в работу идут только успешные сборки [123].
  - Ими пользуются Delegations, Automations, Missions и Workstreams [55].
- **OpenCompute** [56][67] — оркестратор sandbox, который клиент разворачивает у себя, например в Kubernetes. Private Preview, представлен 2026-10-14 [144]. Это стандартный backend sandbox для развёртываний Factory Private.

### Automations и готовые процессы

**Automations** [39][40]:

- **Триггеры:** расписание (cron или обычными словами), сообщение в Slack, событие GitHub (выполняется в GitHub Actions, включается после merge setup-PR), Webhook.
- **Как создать:** Starters (готовые шаблоны), Guided setups, с нуля или «Create with Droid».
- **Starters** [40]: Ticket to PR (каждые 15 минут), PR Reviewer, Daily Status Digest, Code Health, Error Triage, Slack Bug Fixer, Alert Responder, CI Failure Triage, Review Comment Fixer, Test Coverage, Docs Refresh.
- **Удалённый шаблон.** «PR Babysitter» (шаблон, который следил за PR) удалён 2026-11-06; причина не названа (не подтверждено) [72].
- **Настройки automation** [40]:
  - от чьего имени: от пользователя или от service account;
  - где выполнять: на машине пользователя через desktop app, на Droid Computer, в Environment или в GitHub Actions;
  - видимость: Private или Shared; приватность сессий: Private или Team;
  - модель и reasoning; вместо модели можно указать `cheapest`;
  - «Memory & Evolution» и dashboard «Visualization» для каждого запуска.
- **Файлы на диске** у automation по расписанию — папка `~/.factory/automations/<slug>/` [40]:
  - `HEARTBEAT.md` — prompt, до 256 KiB;
  - `VISUAL.html` — dashboard, который Droid обновляет при каждом запуске;
  - папки `memory/`, `reports/` и `skills/`.
- **Здоровье запусков** [40]:
  - статусы: Creating, Running, Active, Paused, Degraded, Failed;
  - автопауза после пяти неудачных запусков подряд по расписанию, при перегрузке машины, а для automation на своей машине — после 10 дней пропущенных запусков;
  - на своей машине запуск, который не стартовал за 15 минут от назначенного времени, записывается как пропущенный; напоминание приходит раз в день, а когда машина снова на связи, запуски возобновляются сами;
  - письма о сбоях, потом ежедневная сводка;
  - лента событий: запуски, оповещения, доставки webhook; fork; «Edit with session»;
  - на одной управляемой машине — не больше 10 automations и не больше 5 в одну минуту.
- **Из чата:** у Droid есть инструменты CreateAutomation, ListAutomations, ReadAutomation, EditAutomation и DeleteAutomation [40].
- Каждый запуск automation — это сессия, которую можно открыть. Есть уведомления о сбоях и доля успешных запусков за 7 дней [39][120].
- Automation, созданная внутри workstream, отчитывается в этот workstream и работает на его машине [25].

**Loops** — повторяющиеся prompts на уровне сессии.

- Действия: создать, показать список, пауза, продолжить, отменить. Расписание — cron из 5 полей в UTC; можно запустить сразу [160].
- Над полем ввода есть плашка для паузы, продолжения и остановки (2026-09-29) [72].
- Loops работают и на Droid Computers. Changelog даёт для этого дату 2026-11-05 [72] и версию 1.4.0 [72]; что это один и тот же релиз, не проверено.

**Готовые процессы:**

- **Локальное code review.** `/review` проверяет изменения против базовой ветки, незакоммиченные изменения, коммит или работу по своим инструкциям. Находки получают степень от P0 до P3 [43]. Многопроходный `/deep-review` — с 2026-05-28 [72].
- **Code review в CI.** `/install-code-review` настраивает GitHub, GitLab, Bitbucket или Azure DevOps через `droid-action`. Review оставляет inline-комментарии [44].
- **Security review.** Методики STRIDE, OWASP и supply-chain; на PR или полным аудитом. Полный аудит советуют запускать внутри Mission [45].
- **Исправление CVE** (Private Preview) [46]. Внутри workstream listener опрашивает сканер уязвимостей. На каждую задачу — свой droid, который проходит путь от triage к плану, PR, CI и merge после одобрения пользователя. Windows не поддерживается.
- **Automated QA** [41][72]. `/install-qa` создаёт для проекта skill `/qa`. Он собирает доказательства: screenshots, снимки терминала, данные API, видео на GitLab. Настройка «failure learning» решает, что делать с уроками провала: предложить изменения в отчёте, закоммитить их или открыть PR.
- **Плагин Droid Control** [42][156]. Управляет терминалами, браузерами и desktop-приложениями. Команды `/demo`, `/verify`, `/qa-test`. Делает видео «до и после» для PR через Remotion.
- **Incident Response** [47]. Запускается оповещениями из Slack. Делает разбор root cause, PR с исправлением и обновляет runbook.
- **Triage** [48]: приём, классификация, поиск дублей, маршрутизация.
- **AutoWiki** [49][72]. `/wiki` генерирует wiki, `/install-wiki` обновляет её в CI. Wiki можно читать в app; есть синхронизация с GitHub Wiki.
- **CI Steward** в `droid-action` [158]. Ждёт все checks, кратко пересказывает логи упавших jobs и перезапускает flaky- и инфраструктурные сбои в пределах бюджетов.
- **Agent Readiness** [65] — оценка готовности репозитория к работе агентов.
  - Пять уровней: Functional, Documented, Standardized, Optimized, Autonomous.
  - Команды `/readiness-report` и `/readiness-fix`, dashboard организации и API.
  - Уровень открывается, когда пройдено 80% критериев предыдущего уровня [65]. В январском посте правило сформулировано иначе: уровень открывают 80% его собственных критериев [92].
  - Число «pillars» (групп критериев) источники называют по-разному: в документации их девять [65], в январском посте — восемь [92].
  - Число критериев тоже расходится: «60+» в январском посте и «100+ signals» на странице Platform [92][136].

### Delegations: работа из чатов и трекеров

- **Общая настройка** [50]:
  - профиль агента «Apps» хранит модель, свои инструкции, плагины, учётную запись service account и вычисления: Dynamic (свежий Environment на каждый запрос) или Persistent (пул машин);
  - личные сообщения в Slack и Google Chat выполняются от имени отправителя; запросы из каналов и issues — от имени service account.
- **Slack** [51]:
  - `@Factory` в треде берёт весь тред как контекст;
  - результат приходит сообщениями, файлами, артефактами и видео;
  - CI обрабатывает отдельный subagent;
  - **Code channels** — отдельный канал Slack на каждую сессию с репозиторием, веткой и diff; diff, где могут быть секреты, не показывается; каналы архивируются после 7 дней простоя;
  - команды: `!new`, `!connect` (инструкция по SSH на компьютер сессии), `!help`.
- **Linear** [52]:
  - запуск — назначить issue на Factory или упомянуть Factory;
  - Factory переводит issue в In Progress и прикладывает ссылки на PR;
  - есть `!connect`; любой может остановить запуск кнопкой Stop в Linear.
- **Jira, Microsoft Teams, Google Chat:** та же модель; запуск по упоминанию или через меню Agents в Jira [50]. Подробностей сверх обзорной страницы нет (не подтверждено).

### Аналитика и телеметрия

- **Factory Analytics** (Business и Enterprise) [121]:
  - расход по моделям и по пользователям, график концентрации затрат, adoption (активные за день и за месяц), оценка экономии от Router;
  - у каждой карточки метрики есть tooltip с объяснением расчёта;
  - аналитика построена на OpenTelemetry и имеет шесть видов; «autonomy ratio» в ней — число вызовов инструментов на одно сообщение пользователя [95].
- **Agent Effectiveness** [1][66]:
  - throughput — как меняется cycle time с ростом трат на агентов;
  - output — «намерения сессий» (feature, maintenance, bugfix) против целей;
  - attribution — кредиты по сессиям, PR, задачам и проектам;
  - только Enterprise, по умолчанию выключено [66][110].
- **Экспорт:** OpenTelemetry в свой collector [67][71]; audit log [1].
- **Signals** [93]. Раз в день LLM просматривает сессии и ищет признаки трудностей, например «пользователь много раз перефразирует». По найденному заводятся задачи в Linear; Droid их исправляет, человек одобряет PR.
- **Signals — продукт или нет: оценки расходятся.** Одна оценка: Signals — внутренняя система Factory, а не функция продукта [93]. Другая: Signals — один из измерительных продуктов Factory, рядом с Agent Effectiveness [93][110].

## Принципы и подходы

Factory называет себя «agent-native software development platform» — платформой, где агенты планируют, пишут, проверяют, тестируют и выпускают ПО [132]. С выхода Factory 2.0 продукт подаётся как «software factory»: замкнутый цикл разработки, в котором сигналы из работы возвращаются в план [103].

### Как менялась позиция

- **2023 — автономия вместо автодополнения.** Миссия из seed-поста — принести автономию в разработку ПО. Инструменты, которые действуют только по запросу, Factory считает недостаточными. Цель — автоматизировать процессы всей организации. В долгосрочной перспективе разработка ПО должна стать доступным массовым товаром [74].
- **2024 — отдельный Droid на каждую работу:** review, тесты, код, знания, управление проектом, документация [75]. Правило из отчёта Code Droid: у агента должны быть все инструменты, которые есть у инженера [76]. Основатели говорили, что строят продукт поверх frontier-моделей и свои не обучают (вторичный источник) [171].
- **Начало 2025 — сложнее всего всё, кроме кода.** Factory назвала себя «командным центром» всего жизненного цикла: общие треды контекста и процессы команды в виде исполняемых workflows [77]. Политика безопасности закрепила два правила: не допускать необратимых действий и требовать подтверждения человека для действий высокого риска [79].
- **Середина 2025 — agent-native разработка** [81]:
  - агент ведёт внутренний цикл: собрать контекст, спланировать, реализовать, проверить и сдать изменение на review вместе с trace;
  - люди отвечают за архитектуру, ограничения и вмешательство;
  - три условия: запрос настолько точен, что успех можно показать; задачи мелкие; среда проверяет работу автоматически и объективно;
  - метод: explore → plan → code → verify; test first для логических ошибок; визуальный цикл для UI; действия делятся по риску — низкий и средний риск выполняются сами, высокий спрашивает.
- **Linters как исполняемая спецификация** [85]. AGENTS.md объясняет, зачем нужно правило. Правило lint заставляет его соблюдать. Lint без ошибок — это и есть определение «готово».
- **Конец 2025 — общий агент; главное преимущество — harness** [87]. Тезис раунда B: лучшие агенты для разработки будут лучшими общими агентами. Пользователь сам выбирает модель, IDE и интерфейс; headless-режим нужен для автоматизации.
- **Terminal-Bench 2025** [86]. Factory заявила первое место (58,75%) и победу над агентами самих лабораторий на тех же моделях: с Opus — 58,8% против 43,2% у Claude Code, с GPT-5 — 52,5% против 42,8% у Codex CLI. Причиной названо устройство harness: три слоя prompts, мало инструментов со схемами под конкретную модель, короткие timeouts по умолчанию, инструмент списка дел, фоновые процессы только по запросу.
- **2026 — Software Factory (Factory 2.0)** [103]. Продукт описан как цикл: сигналы (баги, разговоры, отзывы, требования) разбираются, планируются, реализуются, тестируются, проходят review и проверку безопасности, выпускаются и наблюдаются, а это порождает новые сигналы. Три принципа:
  - **Model Independence** — ни одна модель не подходит для всего; организация выбирает модели сама или отдаёт выбор router;
  - **Sovereign Intelligence** — клиент решает, где работает система (облако, свои ключи, свой data plane, EU, air-gapped), и владеет системой, которая учится на его сессиях, review и инцидентах;
  - **Continual Learning** — все стадии цикла работают на одном ядре агента, одном router и одном контексте организации; поэтому находка security влияет на code review, а инцидент связывается с PR, который его вызвал.
- **Автономия как путь** [103]: skills → Automations → Droid Computers → Missions. Инженеры строят «фабрики», которые строят ПО. С середины 2026 стандартный абзац пресс-релизов описывает систему, которая работает 24/7, а людей — как «governance layer» (слой надзора и правил) [89][128].
- **Дата Factory 2.0 расходится.** Пост датирован 2026-06-15, а пост о раунде на $5B говорит, что 2.0 объявили в апреле [103][117].
- **Конец 2026 — harness, который улучшает сам себя на многих моделях** [126]. Droid 1.0 настраивается на 20+ моделях. Так Factory отделяет настоящие улучшения от подгонки под особенности одной модели. Во внутреннем цикле Agent Factory агенты предлагают изменения harness с гипотезой, каждое изменение проверяется по семействам моделей, лучшие мержат инженеры.
- **Принцип о людях** из поста о покупке Typedef: AI должен сделать инженеров операторами «фабрик», а не заменить их [127].

### Ключевые принципы и как они устроены

- **Чинить среду, а не агента.** Agent Readiness оценивает репозиторий по группам критериев («pillars»).
  - В январском посте их восемь: стиль и проверки, система сборки, тесты, документация, среда разработки, качество кода, observability, безопасность и governance [92]. В документации — девять [65].
  - Пять уровней: Functional, Documented, Standardized, Optimized, Autonomous. Критерии — pass/fail. Целевой уровень — 3 [92].
  - Каждый новый отчёт опирается на предыдущий; это снизило разброс оценки с 7% до 0,6%. Исправления предлагаются как PR [92].
  - Большинство предприятий начинают с уровня 2 [123]. Для лучших результатов Missions документация советует уровень 4 или выше; `/readiness-fix` закрывает пробелы [13].
- **Отделять работу от оценки** [97]:
  - orchestrator планирует и никогда не проверяет;
  - на каждую feature — новый worker;
  - validators сообщают о проблемах, но не исправляют их;
  - tests пишутся первыми на двух уровнях: worker пишет tests до кода, а orchestrator пишет validation contract из поведенческих утверждений до любой feature;
  - у утверждения есть ID, например `VAL-AUTH-001`; оно проверяется в настоящем браузере и оставляет доказательства — screenshot и лог сети.
- **Validator из другого семейства моделей.** По умолчанию validator берётся из другого семейства моделей, чем исполнитель [113].
- **Скрытый измерительный instrument** (исследование августа 2026) [115]. Validator строит instrument до начала реализации. Исполнитель не видит, что за этой границей, и не может её ослабить. Каждый одиночный агент в исследовании остановился, решив, что закончил. Factory подытоживает так: одиночному агенту не хватало не умения, а стандарта готовности [115].
- **Состояние живёт в файлах, а не в модели.** Missions хранят общее состояние на диске: validation contract, список features, файл сервисов и AGENTS.md. Источник истины — git [78][97].
- **Из доклада о Missions** [150]:
  - передачи работы (handoffs) структурированы и записывают команды с exit codes, незаконченную работу и найденные проблемы;
  - features идут по одной, а исследование и review только на чтение — параллельно;
  - оркестрация — это в основном prompts и skills поверх тонкого детерминированного слоя.
- **Советы для долгих запусков** [147]: долговечное общее состояние; результаты tests считаются устаревшими после изменения кода; явные условия остановки; точное описание блокера ценнее непроверенного заявления о готовности.
- **Контекст — это бюджет.** Factory считает контекст ресурсом, как CPU или память, со слоями памяти пользователя и организации [84]. Deferred Context Engine загружает инструменты и skills только когда они нужны [101]. Пять правил Droid 1.0 [126]: считать каждый токен; не ломать prompt cache; профилировать hot path; отслеживать фоновую работу; всегда иметь следующий шаг.
- **Ограниченная автономия.** В Droid 1.0 зашиты правила для застрявших агентов [126]. Пользователю доступны четыре уровня autonomy с потолком от администратора и три режима работы — Normal, Spec, Mission [27].
- **Маршрутизация моделей — внутри harness.** Router переходит на более сильную модель только при необходимости и переключает провайдеров при сбоях [102]. Аргумент из исследования: внешний gateway не видит prompt cache, а остаться на текущей модели — тоже решение маршрутизации [113].
- **Постоянные машины лучше одноразовых sandbox.** Droid Computers сохраняют зависимости, учётные данные, memories и skills между сессиями, поэтому проблему настройки решают один раз [99]. Позже появились Environments — образы, которые пересобираются по расписанию и выпускаются только после проверки [123].
- **Мерить результат, а не логины.** Страница Software Factory называет метрики [135]: cycle time от сигнала до production; доля смерженной работы, которой не касался человек; MTTR инцидентов; «срок жизни» кода; стоимость одного смерженного PR.
- **Два определения «autonomy ratio».** В Analytics это число вызовов инструментов на одно сообщение пользователя [95]. На странице Software Factory — доля смерженной работы без участия человека [135].
- **Factory разрабатывается с помощью Factory.** Так написано на странице компании [134]. Signals исправляет сам продукт [93]. OpenCompute сделан через Missions [124].
- **Открыты края, закрыто ядро:**
  - Factory вошла в рабочую группу AGENTS.md вместе с OpenAI, Sourcegraph (Amp) и Google [83];
  - Droid читает плагины, skills, hooks и subagents Claude Code [34], работает как ACP daemon для редакторов [72], у него есть SDK для TypeScript и Python [126][155];
  - веса дообученных моделей Droid Shield 2.0 (адаптеры LoRA) лежат на Hugging Face [105];
  - OpenCompute и HumanLayer обещано открыть [124][128];
  - собственные плагины Factory: `droid-control` (с `/demo`, `/verify` и `/qa-test`), `security-engineer`, `code-review`, `autoresearch` [156];
  - сам продукт закрыт; публичный репозиторий говорит «all rights reserved» и служит трекером issues [152].

### Чем подход отличается

- **Независимость от лабораторий.** Factory строит свой harness и продаёт его как альтернативу агентам самих лабораторий. Сравнение с OpenAI dots вышло в день запуска dots [151]. Droid 1.0 сравнивают с Claude Code, Codex, Cursor, OpenCode и Devin на одних и тех же моделях [126]. CEO в интервью подчёркивает, что нужны альтернативы любому одному провайдеру моделей [149].
- **Своя inference.** Factory сама продаёт inference: кредиты, множители моделей и собственные окна лимитов [3][5][72].
- **Облако и корпоративный контроль.** Ставка на облачный парк машин (Droid Computers, Environments, OpenCompute) и на корпоративный контроль: иерархию настроек, потолок autonomy, Factory Private [99][118][123][124].
- **Жёсткое разделение исполнения и проверки:** отдельные validators, другое семейство моделей, скрытый instrument [97][113][115].
- **Продвижение понятия «software factory».** Factory опубликовала его историю: GE в 1960-х, Hitachi в 1969 году, книга Cusumano 1991 года [145]. В sitemap 113 статей, среди них сравнения, датированные на год вперёд, например июньская страница 2026 года о лучших инструментах 2027 года [144][146]. Автор заметок считает это контентной стратегией, чтобы закрепить за собой термин (вывод, не подтверждено).

## Как это устроено внутри

Код Droid закрыт. Описание ниже собрано из документации, инженерных постов и из перечислений и схем внутри опубликованного пакета `@factory/droid-sdk@0.11.0`; кода самого Droid в источниках нет [155][160]. Все цифры — заявления вендора; независимо их никто не проверял.

### Процесс, протокол и производительность

- **Один daemon на много сессий.** С версии 1.0 один процесс daemon держит много сессий, около 20 МБ на сессию. До 1.0 каждая сессия была отдельным процессом примерно на 350 МБ [126].
- **Два runtime в SDK** [157]:
  - Node запускает подпроцесс `droid` и общается с ним по JSON-RPC через stdio;
  - Daemon использует один WebSocket (например `ws://127.0.0.1:37643`), по которому идут многие сессии сразу; когда клиент отключается, сессия продолжает работать.
- **Методы JSON-RPC сервера** [160]: `initialize_session`, `load_session`, `add_user_message`, `interrupt_session`, `kill_worker_session`, `kill_background_process`, `compact_session`, `fork_session`, `execute_rewind`, `get_handoff_summary`, `get_context_breakdown`, `warmup_cache`. Обратные вызовы клиенту: `request_permission`, `ask_user`, `pick_options`, `session_notification`.
- **Около 40 типов уведомлений** из сессии [160]. Примеры: `llm_retry`, `assistant_message_retracted`, `session_compacted`, `child_session_available`, `child_session_settled`, события `mission_*` (в том числе `mission_heartbeat`), `tool_execution_heartbeat`, `tool_execution_phase_changed`, начало и конец hooks, `background_processes_changed`.
- **Ресурсы daemon** [157]:
  - сессии; workspace с проверкой доверия; терминалы;
  - git: `getDiff`, `commit`, `push`, `createPullRequest`, `resolvePullRequestStatuses`;
  - relay, плагины и automations;
  - нестабильная группа: crons, `missions.inspectReadiness`, `semanticDiff`, передача файлов и `softwareFactory` (workstreams, signals, changes, activities, events).
- **Версия протокола** согласуется между клиентом и daemon; сейчас 1.321.0 [160].
- **Неясное место:** что такое «PR layers» (операция `PullRequestLayerManifestOperation` в протоколе), не описано (не подтверждено).
- **Производительность** [126]:
  - CLI работает на Bun 1.4.2;
  - CI отклоняет изменение, если p95 задержки первого нажатия клавиши выше 250 мс;
  - сброс телеметрии и синхронизация сессий вынесены в отдельный процесс; выход из CLI ускорился с 648 мс до 30 мс.
- **Удалённая и headless-работа.** Remote Control соединяется через relay.factory.ai без входящих портов [11][54]. `droid exec` выдаёт text, json, stream-json, stream-jsonrpc или acp [11].
- **Стек desktop app — данные расходятся.** Официальные материалы о внутреннем устройстве стек не называют (не подтверждено). По issues в публичном трекере и другим источникам, приложение построено на Electron [72][153][164][186].

### Цикл агента в одной сессии

- **Инструменты** (ID из SDK) [160]:
  - файлы и shell: LS, Read, Create, Edit, MultiEdit, ApplyPatch, Glob, Grep, Execute;
  - скрипты и план: Script, WaitForScript, TodoWrite (в интерфейсе — «Plan»);
  - пользователь и веб: AskUser, WebSearch, FetchUrl;
  - прочее: GetIDEDiagnostics, StageSettingsChanges, ConnectorSearch, ConnectApp, Task.
- **MultiEdit — источники расходятся.** Changelog за ноябрь–декабрь 2025 сообщает, что инструмент MultiEdit убран, потому что успешных вызовов было около 80% [72]. В списке ID инструментов SDK 0.11.0 он всё ещё есть [160].
- **Редактирование под модель.** Одни модели получают редактор «найти и заменить», другие — редактор diff в формате V4A [86]. Инструментов мало, схемы простые, timeouts по умолчанию короткие. Инструмент плана вычёркивает сделанный шаг и отмечает следующий [86]. Инструмент правки зависит от модели, поэтому harness выбирает модель до сборки запроса [113].
- **Prompts в три слоя** [86]:
  1. описания инструментов;
  2. system prompt;
  3. «system notifications» — вставки ближе к концу разговора, потому что модели сильнее учитывают недавний текст.
- Сессия начинается с фактов о среде, оформленных как вывод shell [86].
- **Script tool — программный вызов инструментов** [126]:
  - включён по умолчанию для топовых моделей;
  - модель пишет JavaScript; скрипт работает в sandbox без собственного доступа к файлам, сети и системе и обращается наружу только через инструменты;
  - независимые вызовы идут одновременно;
  - печатный вывод ограничен; полные результаты пишутся в лог, по которому модель потом может искать;
  - скрипт ждёт максимум 5 минут и возвращает то, что есть; может работать в фоне;
  - WaitForScript проверяет, ждёт или останавливает скрипт, поэтому модели не нужно опрашивать; Droid будит модель, когда фоновая работа закончилась;
  - один Script требует одного одобрения на много вызовов инструментов; SDK советует одобрять его, только если разрешён каждый вызов внутри [157];
  - с v1.9.0 Task (запуск subagent) больше не блокирует другие вызовы внутри Script [72].

Цифры вендора по Script tool [126]:

| Случай | Со Script | Без Script |
|---|---|---|
| Чистка задач в Linear | 312 вызовов инструментов за 2 запроса, около 61 тыс. токенов | по оценке, 36 запросов и 3,1 млн токенов |
| Обход CI | 550 вызовов, по 60 одновременно; в контекст модели попало меньше 0,1% результатов | — |
| Стоимость на Opus 5.5 | на 15% ниже | — |

- **Deferred Context Engine — загрузка по требованию** [101][126]:
  - модель видит компактный индекс возможностей; инструменты-загрузчики вносят нужный элемент в контекст, и дальше он переиспользуется;
  - базовый prompt сократился с 20 887 до 13 055 токенов, а число описаний инструментов, отправляемых сразу, — с 11 до 2;
  - в сессиях с MCP-инструментами входных токенов меньше на 15,1% в среднем, на 39,4% на p90 и на 50,8% при 100+ скрытых инструментах;
  - только 16,6% сессий запускают MCP server и только 5,4% реально вызывают MCP-инструмент.
- **Дисциплина prompt cache** [126]:
  - новые инструменты добавляются в конец запроса;
  - 98% входа читается из cache, 98,6% запросов только дописывают предыдущий;
  - монитор сравнивает каждый запрос с предыдущим и называет, что сломало cache;
  - неудачный запрос повторяется у того провайдера, у которого уже есть cache.
- **Фоновые процессы** — только по запросу. Опасные и тяжёлые команды отфильтровываются; каждый запущенный процесс отслеживается, чтобы его убрать [72][86].
- **Ввод во время работы.** Пользователь пишет, пока агент работает; slash commands выполняются посреди хода [11]. Сообщения в очереди можно вернуть или выбросить [160].

### Планирование и разбиение работы

- **Spec mode** только читает. Инструмент `ExitSpecMode` просит одобрения; при одобрении пользователь выбирает уровень autonomy для реализации [27].
- **Переход из spec в новую сессию.** Среди ответов подтверждения есть `proceed_new_session_{low,medium,high}`, а среди событий — `spec_handoff_session_created` [160]. По названиям похоже, что одобрение может начать реализацию в новой сессии на выбранном уровне. Это вывод только из имён (не подтверждено).
- **Предложить Mission** [157][160]:
  - любая сессия может вызвать `RecommendMission`;
  - `ProposeMission` и `StartMissionRun` доступны только сессиям с ролью orchestrator Mission;
  - оба — типы подтверждений, их одобряет пользователь; принятие пишет `mission_accepted` в журнал Mission.
- **Сначала validation contract** [97]. Orchestrator пишет контракт до того, как определит features. Контракт — нумерованный список утверждений. У каждого утверждения есть ID вида `VAL-AUTH-001`, инструмент проверки (например agent-browser) и вид доказательства (screenshot или сетевой вызов с ожидаемым статусом).
- **Потом features.json** [97][160]. У feature есть поля id, description, status, skillName, preconditions, expectedBehavior, `fulfills` (какие утверждения контракта она закрывает), milestone и workerSessionIds. В общем состоянии также лежат `services.yaml` (как запускать сервисы), AGENTS.md, заметки исследования и база знаний [97].
- **Масштаб и стоимость:**
  - Missions подходят примерно для 1–500 features [13];
  - длинную обычную сессию не стоит превращать в Mission [13];
  - лучше всего на репозиториях уровня Agent Readiness 4 и выше [13];
  - запусков агентов не меньше, чем features + 2 × milestones; это нижняя граница, а не верхняя [14];
  - планировщик пишет для каждого worker цель, предусловия и условия завершения [113].
- **Следующее поколение Missions** (исследование на 24 задачах ProgramBench) [115]:
  - до начала реализации validator строит «instrument» — взвешенные тест-кейсы и правила сравнения вывода;
  - исполнители не видят ни кейсов, ни сырых результатов;
  - validator может расширять instrument, но не ослаблять его;
  - orchestrator разрешает споры и даёт указания на уровне недостающих features;
  - Factory пишет, что эта схема войдёт в следующие Missions; на них открыт лист ожидания [115].
- **`/migrate` в Workstreams** [20][160]. Внутри это флаг «ledger», который после включения не выключается. Шаги:
  1. договориться о результате, объёме и способе проверки;
  2. одобрить план;
  3. выполнить до конца;
  4. сдать доказательства и пометить то, что подтвердить не удалось.
- Вкладка Migration показывает примерный прогресс [20].

### Параллельность и координация

У Factory три слоя.

**Слой 1: subagents («custom droids»)** [32]:

- Инструмент Task принимает `subagent_type`, `prompt`, `complexity` (light, medium или heavy), `run_in_background` и `resume`. `TaskOutput` читает результат. `TaskStop` шлёт SIGTERM, затем SIGKILL.
- Subagents не задают вопросов пользователю и не запускают своих subagents.
- Модель выбирается по цепочке: своя модель droid → маршрутизация по complexity → модель родителя.
- Autonomy droid ограничена максимумом организации.

**Слой 2: Missions:**

- Workers запускает программа, а не модель: по одному на feature, по очереди, каждый с чистым контекстом [97].
- Выполнение последовательное, с точечным параллелизмом внутри features и при проверке. Factory пишет, что это оказалось лучше широкого параллелизма [78]. Пользователь HN, наоборот, жалуется, что Missions идут строго последовательно и без параллельных агентов [202].
- Workers передают работу через git: событие `worker_completed` несёт `commitId` и `repoPath` [78][160]. Получает ли каждый worker свой worktree — неизвестно (не подтверждено).
- На каждом milestone система добавляет два вида validators [97]:
  - **scrutiny validators** смотрят код и траекторию каждого worker и записывают знания;
  - **user-testing validators** проверяют работающее приложение снаружи, как пользователь (black-box), по контракту.
- Validators только сообщают о проблемах. Orchestrator превращает находки в fix features, и milestone проверяется снова, пока не пройдёт [97].
- Сколько уровней управления: одного хватает большинству проектов, два могут помочь большим, а три, по словам Factory, уже похожи на бюрократию [78].
- Модели по ролям на запуске [78]:

| Роль | Модель |
|---|---|
| Оркестрация | Opus 4.6 |
| Реализация | Sonnet 4.6 или Opus 4.6 |
| Проверка | GPT-5.3-Codex |
| Исследование | Kimi K2.5 |

- По умолчанию validator из другого семейства моделей, чем исполнитель [113]. Модель и усилие reasoning задаются по ролям в настройках, флагами `--worker-model` и `--validator-model` или на лету в app [16][17].
- Состояния [160]:
  - Mission: planning, awaiting_input, initializing, running, paused, orchestrator_turn, completed;
  - feature: pending, in_progress, completed, cancelled;
  - итог feature: success, partial, failure.

**Слой 3: Workstreams** (beta; в протоколе называется «Mission V2») [18][160]:

- Orchestrator сам работу не делает [20]. Он даёт вводные каждому агенту, потому что агенты не видят чат пользователя. Он досылает работу, спрашивает о ходе и может прервать текущий ход агента.
- Агенты отчитываются, когда закончили, когда заблокированы или когда что-то меняет план. Пользователя они спрашивают напрямую только о том, на что может ответить только он [20].
- Инструменты: `SpawnAgent`, `ListAgents`, `SendMessage`, `InterruptAgent`, `RenameAgent`, `ArchiveAgent`, `CreateListener` [160].
- У каждого сообщения есть отметка отправителя (в заголовке, который читает модель) и видимость: both, llm_only или user_only [160].
- Машины трёх видов [21]:
  - Environment — свежий облачный компьютер на каждого агента;
  - Droid Computer — один на всех агентов, которых отправили на него;
  - Local — этот компьютер.
- Orchestrator выбирает машину по её описанию. Если модель машину не назвала, берётся машина по умолчанию [21][160].
- Общая папка синхронизируется между машинами [22]. Вкладка PRs показывает checks и виды Conversation, Diff, Walkthrough и Validation [23].
- Как именно Workstreams планирует агентов и что питает listeners, не описано (не подтверждено).

**Пул Droid Computers** [53]: по умолчанию 3 параллельные сессии на машину (от 1 до 50); слот держится 30 минут после перехода сессии в простой; новая работа идёт на наименее загруженную машину; Droid получает указание работать в своём git worktree.

**Delegations** [50]: работа приходит из Slack, Linear, Jira, Teams или Google Chat и выполняется либо на свежем компьютере из Environment, либо в постоянном пуле.

### Изоляция

- **Worktrees** в CLI и app: setup profiles, `.worktreeinclude`, очистка самых давно использованных, удаление только checkout, но не ветки [9][11].
- **Sandbox ОС** [31]:
  - Seatbelt на macOS, bubblewrap с seccomp на Linux и WSL2, сеть через фильтрующий proxy;
  - оборачивает каждую команду или весь процесс; в режиме «весь процесс» Droid не стартует, если sandbox недоступен;
  - по умолчанию запись — только в рабочую папку, сеть — только к доменам из списка;
  - файлы настроек защищены от процессов внутри sandbox.
- **Environments** — образы, собранные заранее и пересобираемые раз в несколько часов. Сборка проверяется и выпускается только при успехе. Пока идёт обновление, сессии работают на предыдущей сборке [55][123].
- **Droid Computers** сохраняют файловую систему и память процессов. Управляемые машины засыпают и просыпаются из снимков. Своя машина пользователя подключается только исходящим соединением [99].
- **Права на Droid Computer.** Входящий трафик на управляемых машинах ограничен правилами iptables, но документация сама предупреждает: у пользователя `factory-user` есть sudo без пароля, и он может эти правила изменить [53]. Сессии работают в домашней папке `factory-user`, поэтому, по всей видимости, это может и агент (вывод).
- **OpenCompute** запускает sandboxes в VPC клиента [124]. Устройство [124]:
  - только исходящие WebSocket-соединения;
  - желаемое и наблюдаемое состояние хранится в Postgres, расхождения исправляет reconciler;
  - неизменяемые сборки;
  - драйверы gRPC с профилем Core и необязательными профилями Suspend, Snapshot и Fork;
  - сделан с помощью Missions за шесть недель; код обещано открыть.
- **Headless.** `droid exec` по умолчанию только читает. Действие выше разрешённой autonomy завершает запуск с ненулевым exit code; сделанные правки остаются [60].
- **`vfs`** — открытый репозиторий Factory: файловая система copy-on-write поверх SQLite. С её помощью живую сессию вместе с незакоммиченной работой переносят на другую машину [54][99][155].

### Состояние и память

- **Состояние Mission живёт вне агентов** — в общих файлах: контракт, features.json, services.yaml, AGENTS.md, заметки и база знаний [97].
- **Журнал хода Mission** — записи определённых типов, которые только дописываются [160]:

| Запись | Что несёт |
|---|---|
| `mission_accepted`, `mission_paused`, `mission_resumed`, `mission_run_started` | у `mission_paused` есть причина |
| `worker_started` | `modelId`; `substitutedFromModelId`, если политика организации запретила закреплённую модель и её заменили |
| `worker_selected_feature` | — |
| `worker_completed` | успех, флаг «вернуть управление orchestrator», коммит, путь к репозиторию, exit code, пройденные validators, handoff |
| `worker_failed` | причина сбоя; причина `unrecoverable_usage_402` ставит Mission на автопаузу; без структурированной причины feature снова ставится в очередь, а управление возвращается orchestrator |
| `worker_paused` | сессия worker и feature |
| `handoff_items_dismissed`, `milestone_validation_triggered` | у `handoff_items_dismissed` — список отказов; у `milestone_validation_triggered` — milestone и feature |

- **Возобновление.** Missions можно ставить на паузу, перепланировать и продолжать, в том числе старые: в Mission Control выполнение продолжается с того места, где остановилось; их можно запускать на Droid Computer [16]. Продолжение запускает пользователь; автоматического продолжения документация не описывает. 2026-09-02 changelog исправил возобновление: Mission на паузе продолжает текущую сессию, а не устаревшую; тогда же появились янтарные индикаторы для Mission, которая ждёт ввода [72].
- **Сессии.** Transcripts — файлы JSONL в `~/.factory/projects/` [33]. Есть resume, fork, `/tree` и `/rewind-conversation`; `droid search` индексирует сессии локально [11]. Rewind может восстановить или удалить файлы. Handoff начинает новую сессию с краткого изложения старой [157].
- **После перезапуска:** с v1.9.0 вызовы инструментов, которые так и не выполнились, помечаются прерванными; с v1.8.0 `droid exec` не забирает сессию, которую держит другая машина [72].
- **CVE Tasks в Workstreams** [24]. Каждое действие пользователя несёт версию задачи, которую он видел, поэтому одно действие не применяется дважды. Orchestrator получает указание отклонять действия над задачами, присланные другими агентами.
- **Файлы инструкций** [36]: AGENTS.md и папки `.factory/`, `.agents/`, `.agent/` на уровне проекта и пользователя; CLAUDE.md принимается как совместимое имя.
- **Skills растут вместе с работой.** `/create-skill` делает fork сессии в Spec mode для нового skill [35]. Missions со временем копят библиотеку skills [78]. Каждый handoff worker содержит `skillFeedback` [160]:
  - следовал ли worker процедуре;
  - отступления: шаг, что сделано вместо него и почему;
  - предложения по изменению skill.
- **Знания и память:**
  - scrutiny validators записывают знания в общее состояние [97];
  - на Droid Computers Droid может записывать memories и skills [99];
  - «Memories» есть среди источников контекста, которые загружаются по требованию [101];
  - Factory пишет о слоях памяти пользователя и организации [84];
  - на странице продукта заявлена «persistent memory» [137], но отдельного хранилища памяти в документации нет; его устройство не описано (не подтверждено).
- **Compaction** — сжатие истории разговора [82]:
  - summaries «якорные» и итеративные: сжимается только кусок, который только что выпал из окна, и он вливается в сохранённую summary;
  - два порога: `T_max` запускает compaction, `T_retained` — сколько контекста остаётся после неё;
  - summary обязана сохранить цель сессии, пошаговый ход работы, список затронутых файлов и подсказки, где что искать;
  - цель — меньше токенов на задачу, а не на один запрос.
- **Оценка compaction самой Factory** [90]. Набор probes (контрольных вопросов) проверяет, что модель помнит факты, артефакты, как продолжить работу и какие решения приняты; судья — GPT-5.2. Баллы: Factory 3,70, Anthropic 3,44, OpenAI 3,35. Хуже всего у всех методов сохраняется список затронутых файлов: 2,45, 2,33 и 2,19.
- **Настройки и изменения compaction:**
  - лимит summary поднят с 8 тыс. до 16 тыс. токенов: треть и больше summaries упирались в старый предел [126];
  - настройки `compactionTokenLimit` и `compactionModel` [12];
  - orchestrator в Workstreams сжимает контекст на 500 тыс. токенов по умолчанию [26];
  - слишком большой запрос теперь сжимается и повторяется; с v1.10.0 сессия на пределе контекста сжимается, а не падает [72].
- **Просмотр контекста:** `/context`, `/compress` и статистика контекста — занято, осталось, предел, точность [11][157].
- **Ранние подходы:** стек контекста из обзоров репозитория, семантического поиска, точечных файловых операций и корпоративных источников (Datadog, Slack, Notion) [84]; в 2024 — системы поиска HyperCode и ByteRank [76].

### Проверка качества

- **Кто решает, что работа верна** [97]. Workers пишут tests первыми, но окончательный вердикт не за ними. Validators отделены, потому что агент оценивает свою работу хуже, чем свежий проверяющий.
- **Схема handoff worker** [160]:
  - `salientSummary`, `whatWasImplemented`, `whatWasLeftUndone`;
  - `verification.commandsRun` — команда, exit code, наблюдение;
  - `verification.interactiveChecks` — действие и что увидели;
  - `tests.added`, `tests.updated`, `tests.coverage`;
  - `discoveredIssues` со степенью blocking, non_blocking или suggestion.
- **Явный отказ от пунктов handoff** [160]. Для отказа от пункта у orchestrator есть инструмент `DismissHandoffItems`. У каждого отказа есть тип (`discovered_issue`, `critical_context` или `incomplete_work`), feature-источник, краткое описание и обоснование; отказы попадают в журнал записью `handoff_items_dismissed`. Обязан ли orchestrator отклонять каждый пункт явно, из SDK не видно (не подтверждено).

Пример Mission — клон Slack, цифры вендора [97]:

| Мера | Значение |
|---|---|
| Время | 16,5 ч |
| Доли времени | реализация 60,5%, проверка 37,2%, оркестрация 2,3% |
| Код | 38,8 тыс. строк, из них 52,5% — tests |
| Покрытие statements | 89,25% |
| Найдено проблем | 81, из них 65 блокирующих |
| Fix features | 21 на 61 implementation feature (34,4%) |
| Раундов проверки на milestone | 2–4 |

- **Эффект скрытого instrument**, цифры вендора [115]: медиана на ProgramBench с Fable 5 — 56,7 у одиночного агента и 89,3 с системой; на задаче gdal — 36% и 90%. Запуск gdal с системой стоил в 14 раз больше кредитов и занял в 13 раз больше времени.
- **Automated QA** [41]:
  - `/install-qa` создаёт QA skill: SKILL.md, config.yaml, шаблон отчёта и по одному sub-skill на приложение;
  - каждый запуск проверяет только приложения, которые задел diff, и собирает доказательства через agent-browser или tuistory;
  - итог — PASS, FAIL или BLOCKED;
  - уроки провала можно предложить в отчёте, закоммитить автоматически или оформить PR.
- **Подготовка приложения к QA в Mission** [14]: одна команда запуска; логи в файлы; умеренный расход ресурсов; программный способ подать ввод.
- **Плагин droid-control** [156]:
  - `/demo`, `/verify` и `/qa-test` — «контракты намерения», которые обязуются выдать конкретные результаты;
  - цикл capture → compose → verify; у каждого запуска свои RUN_ID и RUN_DIR;
  - skill-маршрутизатор загружает только нужные файлы, поэтому плагин занимает в контексте одну запись skill вместо одиннадцати.
- **Review PR в droid-action** [158]:
  - два прохода: сначала кандидаты в находки (до 100 ходов), потом validator (до 40 ходов);
  - текст review собирает код из JSON validator; модель даёт доказательства и текст, но не вёрстку и не числа;
  - тред закрывается только после того, как validator подтвердил исправление;
  - треды, которые закрыл человек, не трогаются;
  - повторные review смотрят только новые коммиты;
  - порог P0/P1/P2 может проваливать check;
  - Droid никогда не ставит Approve и не запрашивает изменения.
- **Устаревший предшественник droid-code-review** [159]: не больше 10 inline-комментариев; находки с низкой уверенностью — в форме вопроса; одна проблема не поднимается дважды; ищет только серьёзные проблемы корректности, конкурентности, ресурсов, неверного использования API, производительности и регрессий.
- **CI Steward** [158]:
  - ждёт все checks, кратко пересказывает логи упавших jobs и перезапускает flaky- и инфраструктурные сбои;
  - три бюджета: `max_retries`, `max_fix_attempts`, `max_runs_per_pr`;
  - конфигурация читается только из ветки по умолчанию, поэтому ветка не может сама выдать себе автоисправление; на PR из forks не работает;
  - вне `fix.scope` инструменты правки не выдаются вовсе, а не спрашиваются;
  - изменения в `protected_paths` откатываются после запуска, и job падает;
  - никогда не пушит в ветку по умолчанию и не делает force-push.
- **Agent Readiness** [65]: 9 групп критериев и 5 уровней; 80% критериев одного уровня открывают следующий.

### Восстановление после сбоев

- **Вызовы моделей:**
  - на потоках Anthropic, которыми управляет Factory, 4 минуты тишины считаются обрывом, и запрос повторяется [126];
  - ответ, который упёрся в жёсткий предел времени, получает не больше 2 попыток [126];
  - частичный ответ удаляется перед повтором; этому соответствует событие `assistant_message_retracted` [126][160];
  - переключение провайдеров и зарезервированная пропускная способность; заявлено 99,9%+ надёжности запросов [57];
  - настройки `modelFallbacks` и `llmRequestTimeout` [12];
  - автоматические повторы при недоступности модели — с июля 2026 [72].
- **Застревание и циклы** [126]:
  - три хода подряд без видимого вывода останавливают цикл;
  - три одинаковых вызова инструмента — подсказка агенту, шесть — остановка;
  - повторы, которые возвращают новые результаты (например, опрос сборки), разрешены;
  - правило проектирования: у застрявшего агента всегда есть следующий шаг — подсказать, повторить, сжать контекст или остановиться.
- **Workers:**
  - worker, который вышел без handoff, получает ошибку `worker_exited_without_handoff`; сбой без причины снова ставит feature в очередь [160];
  - `subagentInactivityTimeout` задаёт, когда worker считается зависшим [12]; timeouts для workers появились в феврале 2026 [72], а timeout бездействия subagents по умолчанию 3 минуты — с 2026-03-04 [72];
  - в API есть `killWorker` [157].
- **Missions.** Причины автоматической паузы имеют фиксированные коды; у паузы, которую поставил пользователь или runner, причины нет [160]:
  - `unrecoverable_usage_402` — лимит или кредиты исчерпаны (ответ HTTP 402); ставится, когда worker упал с этой причиной;
  - `feature_retry_limit_exceeded` — feature превысила лимит повторов;
  - `scope_growth_limit_exceeded` — объём работы вырос сверх лимита.
- App предупреждает, когда feature подходит к лимиту повторов [13]. Значения лимитов не опубликованы (не подтверждено).
- **Соединения** [72]: число попыток переподключения ограничено (v1.3.0); rate limits от connectors пережидаются (v1.10.0).
- **Пробелы, которые Factory признаёт** [24]: агент исправления, который перестал отвечать, автоматически не обнаруживается; CVE-задача помечается «Fix failed», если CI падает после трёх раундов исправлений.

### Лимиты, подписка и стоимость

- **Индивидуальные планы** [3]:
  - три независимых скользящих окна — 5 часов, 7 дней и 30 дней; запросу нужен запас во всех трёх;
  - Droid Core — бесплатный пул открытых моделей со своими лимитами;
  - Extra Usage — предоплаченные кредиты; без него Missions не запускаются; Mission при упоре в rate limit встаёт на паузу;
  - если лимит кончился посреди сессии, текущий запрос завершается, а следующие падают с ошибкой лимита;
  - план Free работает на своей inference пользователя: вход через ChatGPT, GitHub Copilot, OpenRouter или ключи API.
- **Продолжение после сброса лимита.** Источники не противоречат друг другу: ни один не описывает продолжения без пользователя.
  - Документация: Mission на лимите встаёт на паузу [3]; продолжает её пользователь из Mission Control [16].
  - SDK: сбой worker с причиной `unrecoverable_usage_402` ставит Mission на автопаузу, и в журнал пишется `mission_paused` с этой причиной [160].
  - Changelog: 2026-04-28 — «Missions now handle Rate Limit responses gracefully», то есть Missions корректно обрабатывают ответ о лимите; 2026-09-02 — Mission на паузе продолжает текущую сессию, а не устаревшую; 2026-09-08 — первое сообщение после сброса лимита больше не считается превышением [72].
  - Независимый обозреватель видел, как Mission остановилась на пятичасовом лимите и сама не продолжила [162].
  - Workstreams: на лимите агенты стоят до сброса окна; продолжат ли они сами, документация не говорит [26].
  - Итог: автоматическое продолжение Missions и Workstreams после сброса окна не подтверждено.
- **Workstreams** [26]: баннер на 90% лимита; на лимите агенты стоят до сброса окна; совет — сменить модель или перейти на Droid Core.
- **Factory Router** выбирает модель под задачу и переходит на более сильную, когда текущая не справляется [57]. Цифры экономии в разных источниках получены разными методами за разные периоды, поэтому сравнивать их нельзя:

| Источник | Общая экономия | Медианная сессия |
|---|---|---|
| Пост о запуске Router [102] | 20–25% | — |
| Страница Platform [136] | 40%+ | — |
| Пост о маршрутизации внутри harness [113] | 58% | 76% |
| Документация Router и пост о production-экономии [57][119] | 63% | 72,5% |

- Пост о маршрутизации также сообщает: медианная задержка хода упала с 81 до 49 секунд без потерь на 8 production-метриках [113].
- **Смена модели с учётом cache** [113]. Если не учитывать cache, стоимость относительно базовой — 2,12–2,37×. С учётом cache — 0,19–0,28×. Router, слепой к cache, обходился в 2,12 раза дороже на ходах с 61-го по 150-й [113].
- **Размеры Missions:**
  - медиана — около 2 часов против примерно 8 минут у обычной сессии; 14% Missions идут дольше суток; самая долгая — 16 дней [78];
  - в медиане Mission тратит в 12 раз больше токенов при той же скорости расхода — около 45 тыс. токенов в минуту [78];
  - пост о маршрутизации даёт другую медиану: 423 хода в десяти сессиях, около 12 часов; маршрутизация снижает стоимость Mission на 37,8% [113];
  - **медиана длительности Mission в двух постах расходится:** около 2 часов [78] и около 12 часов [113].
- Клон Slack потратил 778,5 млн токенов, из них 744,9 млн — чтение из cache [97].
- App показывает прошедшее время и кредиты [16] и по умолчанию не даёт компьютеру уснуть во время Missions [17].

### Права и безопасность

- **Уровни autonomy** [28]. У команд Execute и MCP-инструментов есть оценка риска: low, medium или high.

| Уровень | Что выполняется без вопроса |
|---|---|
| Off | чтение и команды, разрешённые политикой |
| Low | правки и команды низкого риска |
| Medium | обратимые действия: установки, сборки, локальные коммиты |
| High | действия высокого риска, например push и миграции, если их не остановила проверка безопасности |

- «Allow always» поднимает уровень сессии. Организация задаёт уровень по умолчанию и максимум. Missions требуют High или `--skip-permissions-unsafe` [13][28].
- **Варианты ответа на запрос разрешения** [160]: один раз; всегда; всегда для этого файла; auto-run на выбранном уровне; новая сессия на выбранном уровне; правка; всегда для этих инструментов или этого server; сообщить о ложном срабатывании; отмена.
- **Permission rules** [29]:
  - у правила есть id, решение (allow, ask или block) и префикс из точных токенов команды;
  - в правиле лежат примеры `tests.match` и `tests.noMatch`; правило включается, только если проходят его собственные примеры; примеры только сопоставляются с правилом, но не выполняются;
  - `droid rules check` показывает решение для конкретной команды;
  - порядок источников org > runtime > folder > project > user решает только, чьё определение действует при одинаковом ID; правила с разными ID суммируются, и среди совпавших block сильнее ask, ask сильнее allow;
  - неверное правило пропускается и не превращается в «запретить всё».
- **Hooks** [33]:
  - девять событий с теми же именами, что в Claude Code, плюс фильтр `commandRegex`;
  - exit code 2 блокирует действие; PreToolUse-hook может вернуть решение о разрешении и переписанный ввод;
  - организация может разрешить только managed hooks;
  - набор hooks фиксируется при старте.
- **Droid Shield** [30][69]:
  - сканирует добавленные строки diff при commit и push;
  - версия 2.0 (Private Preview) добавляет модель, которая находит пропущенные сканером секреты, и модель, которая пересматривает срабатывания сканера с замаскированным секретом и может снять ложную тревогу;
  - если diff слишком большой для проверки, Shield блокирует операцию (fail closed).
- **`StageSettingsChanges`** [1]:
  - готовит до 20 изменений настроек; ничего не применяется, пока пользователь не нажмёт Apply;
  - потом изменения применяются по одному, по порядку, без транзакции и с проверкой конфликтов;
  - workers и subagents этим инструментом пользоваться не могут.
  - Индекс документации `llms.txt` содержит инструкции для собственного агента Factory в app — пользоваться `StageSettingsChanges`. Это данные о том, как устроены настройки, а не инструкции для читателя [1].
- **Прочее:** плагины из npm ставятся с `--ignore-scripts` [34]; оценка риска каждой команды экспортируется в OTEL [69].
- **Данные.** Цикл агента выполняется локально; код не загружается и не индексируется в облаке Factory; trace spans не попадают в collector Factory [70].

- **Уведомления.** Hook уведомления о permission prompt не говорит, какой инструмент или команда ждут одобрения. Это ломает dashboards для нескольких сессий [182].
- **Интеграции ACP:**
  - новая ACP-сессия наследует контекст прошлых чатов в том же процессе; в Zed агент «помнит» чужой чат [183];
  - другие ошибки схемы ACP исправили и закрыли примерно за два дня [193].
- **Чего нет по сравнению с Claude Code:** выделения мышью с копированием исходного текста [184], настраиваемых сочетаний клавиш и живого счётчика токенов [153].
- **Настройки не работают:** настройка co-author игнорируется, а агент отказывается коммитить без строки co-author [185]; symlink на AGENTS.md не загружается [195].
- **Поиск секретов.** Droid Shield блокирует коммиты, в которых есть хэши SHA-256 [192].

**Приватность и телеметрия.**

- Desktop app отправил на хост телеметрии Factory 2,4 ГБ в сентябре и 3,0 ГБ в октябре — примерно в 100 раз больше, чем скачал [175].
- По чтению клиентского кода автором issue: данные идут несжатым JSON, а неудачные пакеты отправляются повторно [175].
- Changelog ужесточил отказ от телеметрии 2026-10-10; desktop app учитывает отказ с 2026-11-07 [72]. Issue всё ещё открыт [175].

**GitHub Action для code review.**

- Одна находка опубликована 29 комментариями в 8 reviews [198].
- Шаг validator отправил review четыре раза, и тексты обрезались до заголовков [199].

### Почему приходят и почему уходят

- **Приходят ради:**
  - одной подписки на много моделей [201][204];
  - дешёвого BYOK и открытых моделей [133][206];
  - веры в harness и бенчмарки [86][203];
  - множества поверхностей и headless-режима [201];
  - надёжной репутации вендора [202];
  - акций [163].
- **Сокращают использование или уходят из-за:**
  - тесных пятичасовых лимитов по сравнению с подписками самих вендоров моделей [162];
  - дорогих Missions с посредственным результатом [162];

- **Типичный итог:** обозреватель оставил место за $20 для второго мнения и собирался попробовать Devin [162].
- **Что просят пользователи:**

  - машиночитаемые коды для отказов по содержимому [177];

  - Missions, которые продолжаются сами [162];

### Реальные результаты: заявления вендора и независимые данные

- **Отобранные вендором, со слов клиентов** [138]:
  - Comarch — поставка в 18 раз быстрее;
  - Groq — features в 3 раза быстрее;
  - Chainguard — две недели в одной непрерывной сессии на 6 репозиториях и 80 пакетах;
  - Nav — на 60% меньше переключений контекста;
  - Empower — на 50% быстрее одобрение PR;
  - Tilt — на 40% быстрее реакция на инциденты.
- **Другие заявления вендора:** у Wipro обновление платформы, оценённое в 9–12 месяцев, сделал один инженер за 2–3 месяца [139]; на раунде B заявлены поставка features в 31 раз быстрее, миграции короче на 96,1% и разбор дежурств быстрее на 95,8% [87].
- **Независимые данные:**
  - компания примерно на 2000 разработчиков с доступом к Devin, Factory Droid, Claude Code и Codex и бюджетом €2000 на разработчика в месяц измерила около 7% общего прироста продуктивности от всех AI-инструментов вместе, а не от Droid отдельно [214];
  - Mission обозревателя дала посредственный результат за шестую часть месячного объёма [162].
- **Непроверенное обвинение.** В 2025 на HN утверждали, что Factory отдаёт не те модели, которые указаны. Это проверяли, спрашивая модель, как её зовут; такой способ ненадёжен (не подтверждено) [201].
- **Бенчмарки.** Независимого воспроизведения цифр вендора нет (не подтверждено) [86][126]. В запусках Terminal-Bench 4 для Droid 1.0 задача, где Devin остановился с вопросом, засчитывалась по результату Codex; в среднем так было с 4,7 задачи на попытку [126].

- **Частые релизы:** почти каждый день; 1.7.0 вышел 10 ноября, 1.10.0 — 12 ноября [72].

### Что убрали или переосмыслили

- Много специализированных Droids превратились в один общий Droid с режимами и custom droids [27][72][75][87].
- Инструменты сократили: убран MultiEdit; описаний инструментов в первом запросе — 2 вместо 11; базовый prompt меньше на 37% [72][126].
- Cloud Machines заменены Droid Computers, а их уведомления теперь ведут на Environments. Cloud Templates устарели [72].
- Машины: от одноразовых sandbox — к постоянным машинам, затем — к проверенным образам, которые пересобираются по расписанию [99][123].
- **Цены:**
  - на старте общего доступа (GA) — $40 за команду плюс $10 за активного пользователя в месяц [80];
  - теперь — уровни расхода с тремя окнами, кредиты и множители моделей [3][5][72][133];
  - управляемые Droid Computers стартовали на планах Max, Growth и Enterprise [99] и дошли до Pro 2026-09-09 [72]; плана Growth на странице цен больше нет [133].
- Сняты старая аналитика, модели MiniMax и шаблон PR Babysitter; причина удаления шаблона не названа (не подтверждено) [72].
- Повторяющиеся prompts объединены в один инструмент Loop, который позже стал работать и на Droid Computers [72].
- На пределе контекста теперь идёт compaction вместо ошибки [72].
- Подача сместилась от метрик adoption к ROI и метрикам результата [110][149].

- **Сложные лимиты и счётчики.** Три окна (5 часов, 7 дней, 30 дней), плюс Droid Core и Extra Usage [3]. Пятичасовое окно пользователи называют тесным даже на плане Max [162]. Видимый месячный счётчик не предупреждает о 7-дневном окне [173].
- **Missions на лимите встают на паузу.** Продолжения без пользователя после сброса окна не описывает ни документация, ни changelog, ни SDK; обозреватель видел, что Mission сама не продолжилась (автопродолжение не подтверждено) [3][16][72][160][162]. Changelog пишет только об исправлениях ручного возобновления [72]. Для Missions нужен Extra Usage [3] и уровень autonomy High или пропуск разрешений [13][28].
- **Дорогие Missions:**
  - в медиане в 12 раз больше токенов, чем обычная сессия [78];
  - схема со скрытым instrument — в 14 раз больше кредитов и в 13 раз больше времени [115];
  - проверка заняла 37% времени Mission в примере вендора [97];
  - выполнение в основном последовательное [78][202];
  - `droid exec --mission` может «успешно» завершиться без работы [180].
- **Workstreams:**
  - beta, и их нет на Business и Enterprise [18];
  - нет BYOK, у SpawnAgent нет параметра модели [189];
  - нет обязательного одобрения плана и merge; агент исправления, который перестал отвечать, не обнаруживается [24].
- **Непрозрачные ограничения аккаунтов** (волна 2026-11-12) — без объяснения и апелляции [172]. Фильтр содержимого отвечает 403, навсегда ломает сессию и записывается как ошибка аутентификации [177].
- **Модель меняется без явного решения пользователя:** Auto Model выбирает слабые модели [162]; глобальный переход на Droid Core может молча сменить модель посреди задачи [162]; custom droids не всегда держат закреплённую модель [190].
- **Повторы вслепую.** Рассуждение обрывается на 600 секундах, и тот же запрос повторяется [176].
- **Ресурсы и надёжность:**
  - больше 1,5 ГБ памяти на сессию у обозревателя; исправило ли это Droid 1.0 — не подтверждено [126][162];
  - потерянные результаты subagents из-за ответов 404 [162];
  - низкая доля cache у hosted Gemini [174].
- **Windows:** осиротевшие процессы `git.exe` [186]; карантин transcripts антивирусом [187]; падение на CPU без AVX2 [188]; исправление CVE на Windows не поддерживается [46].
- **Синхронизация между устройствами** работает не для всех сессий [178][179].
- **Расширяемость:**
  - project-scope hooks молча не читаются [181];
  - symlink на AGENTS.md не загружается [195];
  - настройка co-author игнорируется [185];
  - уведомления о разрешениях не называют инструмент [182];
  - контекст протекает между ACP-сессиями [183];
  - Droid Shield ложно срабатывает на SHA-256 [192].
- **Телеметрия:** гигабайты выгрузки в месяц из desktop app [175].
- **Шум в code review:** дубли комментариев, повторные review, чтение только первых 100 комментариев PR [198][199][200].
- **IDE:** в JetBrains не передаются открытые файлы, выделение и diff [59]; ранние отзывы на расширение VS Code отрицательные [163].
- **Цифры только от вендора.** Все бенчмарки и цифры экономии опубликовала сама Factory. В Terminal-Bench 4 задачи, где Devin задал вопрос, засчитаны по результату Codex [126].
- **Права на облачных машинах.** Документация сама предупреждает: на управляемом Droid Computer у `factory-user` есть sudo без пароля, и он может изменить правила firewall [53]. Сессии работают в домашней папке `factory-user`, поэтому, по всей видимости, это может и агент (вывод).

## Механизмы, которые стоит изучить

1. **Validation contract до кода и fix features.**
   - Что это: список проверяемых утверждений о поведении, который orchestrator Mission пишет до того, как определит features.
   - Как работает: у утверждения есть ID (`VAL-AUTH-001`), инструмент проверки (например agent-browser) и вид доказательства (screenshot или сетевой вызов с ожидаемым статусом). Каждая feature в `features.json` перечисляет в поле `fulfills`, какие утверждения закрывает. На каждом milestone validators проверяют контракт. Их находки orchestrator превращает в fix features, и milestone проверяется снова, пока не пройдёт. В примере с клоном Slack на 61 implementation feature пришлась 21 fix feature (34,4%), а каждый milestone сошёлся за 2–4 раунда проверки.
   - Источник: [97][160].
2. **Скрытый instrument и validator из другого семейства моделей** — две отдельные вещи из двух разных постов.
   - Что это: набор взвешенных тест-кейсов и правил сравнения, который validator строит до реализации и прячет от исполнителей.
   - Как работает: исполнители не видят ни кейсов, ни сырых результатов; validator может расширить instrument, но не ослабить; спорные случаи решает orchestrator. В этом исследовании все роли — одна и та же модель с одним уровнем reasoning, так что прирост дало разделение ролей, а не смена модели [115]. Отдельно от исследования: в продукте validator по умолчанию берётся из другого семейства моделей, чем исполнитель [113]. Цифры вендора: медиана на ProgramBench (панель Fable 5) выросла с 56,7 до 89,3; на задаче gdal — с 36% до 90%, но это стоило в 14 раз больше кредитов и в 13 раз больше времени; запуски не уравнивали по compute [115].
   - Источник: [113][115].
3. **Структурированный handoff и явные отказы.**
   - Что это: обязательный JSON-отчёт worker при завершении работы.
   - Как работает: поля — что сделано и что нет, команды с exit codes, интерактивные проверки, добавленные tests, найденные проблемы со степенью и отзыв о skill. Worker без handoff получает ошибку `worker_exited_without_handoff`; сбой без причины возвращает feature в очередь. Для отказа от пункта у orchestrator есть инструмент `DismissHandoffItems`: отказ несёт тип, feature-источник, описание и обоснование и попадает в журнал. Обязан ли orchestrator отклонять каждый пункт, из SDK не видно (не подтверждено).
   - Источник: [160].
4. **Журнал с типами записей и коды причин паузы.**
   - Что это: журнал Mission, в который только дописываются записи фиксированных типов, и закрытый список причин остановки.
   - Как работает: записи `mission_paused` (причина есть только у автоматической паузы), `worker_started` (с `substitutedFromModelId`, если политика заменила модель), `worker_completed`, `worker_failed`, `worker_paused` и другие. Причины паузы: `unrecoverable_usage_402` (лимит или кредиты исчерпаны, ответ HTTP 402), `feature_retry_limit_exceeded`, `scope_growth_limit_exceeded`. Сбой worker с причиной `unrecoverable_usage_402` ставит Mission на автопаузу; сбой без структурированной причины возвращает feature в очередь. Состояния Mission и feature — конечные списки. Heartbeats Mission и инструментов идут в потоке событий.
   - Источник: [13][160].
5. **Правила против зависаний и циклов в harness.**
   - Что это: жёстко заданные пороги в цикле агента Droid 1.0.
   - Как работает: на потоках Anthropic, которыми управляет Factory, 4 минуты тишины — повтор запроса; не больше 2 попыток на ответ, который упёрся в предел времени; частичный ответ убирается перед повтором; 3 хода без вывода — остановка; 3 одинаковых вызова инструмента — подсказка, 6 — остановка, если результаты не меняются. Правило: у застрявшего агента всегда есть следующий шаг.
   - Источник: [126][160].
6. **Окна лимитов, порядок расхода и оценка числа запусков.**
   - Что это: три независимых скользящих окна, цепочка источников объёма и нижняя оценка стоимости Mission.
   - Как работает: запрос проходит, только если запас есть во всех окнах (5 ч, 7 дн, 30 дн); каждое окно скользящее и отсчитывается с первого использования. Сначала тратится Standard Usage. Когда он кончился, можно бесплатно перейти на пул Droid Core с отдельным лимитом или купить предоплаченный Extra Usage, чтобы остаться на стандартных моделях; с 2026-04-26 переход на Droid Core бывает автоматическим, если так задано в настройке перерасхода. При лимите посреди сессии текущий запрос доходит до конца, а следующие получают ошибку HTTP 402 с временем до сброса. В Workstreams баннер появляется на 90%, на лимите агенты ждут сброса, а кнопка «Change models» снижает reasoning или ставит более дешёвую модель. Mission при лимите встаёт на паузу; продолжения без пользователя после сброса не описано. Нижняя оценка числа запусков Mission — features + 2 × milestones.
   - Источник: [3][14][26][72][133][160][173].
7. **Permission rules со встроенными примерами.**
   - Что это: правила allow/ask/block по префиксу команды, в которых лежат собственные тест-примеры.
   - Как работает: правило включается, только если проходят его примеры `tests.match` и `tests.noMatch`; примеры сопоставляются, но не выполняются. `droid rules check` показывает решение для команды. Порядок источников Org > Runtime > Folder > Project > User решает только, чьё определение действует при одинаковом ID. Правила с разными ID суммируются, и среди совпавших block сильнее ask, ask сильнее allow: allow организации и block проекта с разными ID дают block. Неверное правило пропускается и не превращается в «запретить всё». У каждой команды есть оценка риска; она сравнивается с уровнем autonomy сессии и уходит в OTEL.
   - Источник: [28][29][69].
8. **Жизненный цикл worktree.**
   - Что это: профили подготовки и правила безопасной очистки worktrees.
   - Как работает: setup profile — setup-скрипт, первый prompt и cleanup-скрипт; профили лежат в репозитории в `.factory/worktree-setups/*.yaml`. Учётные данные убираются из окружения скриптов. `.worktreeinclude` копирует нужные git-ignored файлы. Очистка удаляет самые давно использованные ephemeral-worktrees и пропускает грязные, незапушенные, с открытым PR или активной сессией. Она уважает git locks и никогда не удаляет ветку.
   - Источник: [9][72].
9. **Действия пользователя с номером версии.**
   - Что это: защита от двойного применения действий в панели задачи.
   - Как работает: каждое действие (Approve plan, Merge PR, Retry with guidance) несёт версию задачи, которую видел пользователь, поэтому применяется не больше одного раза. Если orchestrator не подтвердил действие за 2 минуты, панель предлагает Continue in chat, Send again или Dismiss. Orchestrator отклоняет действия над задачами, присланные другими агентами.
   - Источник: [24].
10. **Выбор машины по описанию и пул слотов.**
    - Что это: распределение работы между машинами без жёстких правил маршрутизации.
    - Как работает: у каждой машины есть текстовое описание, например «есть мобильный репозиторий, Xcode…». Orchestrator читает описания и выбирает машину; если машина не названа, берётся машина по умолчанию. В пуле Droid Computers по 3 слота на машину (настраивается от 1 до 50); слот держится 30 минут после простоя; новая работа идёт на наименее загруженную машину; Droid работает в своём worktree. Планы и заметки синхронизирует общая папка.
    - Источник: [21][22][53][160].
11. **Маршрутизация моделей с учётом prompt cache.**
    - Что это: выбор модели внутри harness, который учитывает цену потери cache.
    - Как работает: harness сравнивает запрос с предыдущим и называет, что сломало cache. Новые инструменты дописываются в конец запроса. Повтор идёт к провайдеру, у которого уже есть cache. Остаться на текущей модели — тоже решение router. По данным вендора, смена модели без учёта cache обходится в 2,12 раза дороже базы на ходах 61–150 и в 2,37 раза на ходах 151–200, а маршрутизация с учётом cache — 0,19–0,28 базы; база — одна frontier-модель на всех ходах, расчёт смоделирован.
    - Источник: [113][126].
12. **Бюджеты CI Steward и здоровье automations.**
    - Что это: ограничения для агента, который сам чинит CI, и состояния для повторяющихся запусков.
    - Как работает: у CI Steward есть бюджеты `max_retries`, `max_fix_attempts`, `max_runs_per_pr`. Он читает конфигурацию только из ветки по умолчанию, вне `fix.scope` не получает инструментов правки, откатывает изменения в `protected_paths` и проваливает job, никогда не пушит в ветку по умолчанию. У automations есть статусы Active, Paused, Degraded и Failed; автопауза после пяти сбоев подряд, а для automation на своей машине — и после 10 дней пропусков; там же запуск, который не стартовал за 15 минут, записывается как пропущенный.
    - Источник: [40][158].
