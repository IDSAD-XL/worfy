## Модель работы

- **Local, cloud или hybrid.** Оба варианта: один и тот же продукт ставят у себя или берут как SaaS.
  - Self-hosted. Daemon — серверный процесс Agor на FeathersJS (Node-фреймворк для REST и событий в реальном
    времени). Он отдаёт REST, Socket.IO и web-интерфейс на React. Пользователи работают в браузере [41][76].
  - Daemon можно запустить на своём ноутбуке: по умолчанию база — SQLite, для одного пользователя. Для команды —
    общий сервер с PostgreSQL [38].
  - Desktop-приложения нет: ни Electron, ни нативного desktop-клиента, ни PWA в коде не найдено [125].
  - Масштабирование self-hosted: несколько daemon-ов active-active на PostgreSQL и Redis за ingress со sticky
    sessions [61]; executors можно запускать как pods Kubernetes [62].
  - Agor Cloud — управляемый сервис. Варианты [2]:
    - hosted Cloud — «available now», open beta;
    - Managed Private Cloud — в AWS-аккаунте клиента;
    - private cloud или on-prem — как enterprise-проект.
  - Пост о private beta 2025 года называл ещё GCP, VPC peering и общий dev-сервер за VPN [10].
  - Заметки расходятся в том, что известно о runtime Cloud. Страница Cloud пишет: каждый workspace — изолированный
    instance со своей базой на автомасштабируемом Kubernetes, с health checks и автоматическим восстановлением [2].
    По заметкам о внутреннем устройстве, runtime Cloud публично не описан (не подтверждено) [22].
- **Агенты и модели.**
  - Своей модели и своего агентного цикла у Agor нет. Пользователь приносит свои ключи и подписки [1][54][65].
  - Шесть harness-ов (агентных программ вендоров), выбор — на каждую session: Claude Code, Codex, Gemini (Beta),
    GitHub Copilot, OpenCode, Cursor (Beta) [1][54].
  - Agor вызывает их через SDK — библиотеки вендоров для запуска агента из кода. CLI он не оборачивает [54][66][88]:
    - Claude — `@anthropic-ai/claude-agent-sdk` 0.3.321; по CHANGELOG 0.28.0 это соответствует Claude Code 2.1.321
      [66][88];
    - Codex — `@openai/codex-sdk` 0.160.0 и `codex app-server` [54][88];
    - Copilot — `@github/copilot-sdk` ^0.2.2 в `package.json` [88]; документация называет SDK technical preview
      v0.2.0 [54];
    - Cursor — `@cursor/sdk` 1.3.0 [66][88];
    - Gemini — `@google/gemini-cli-core` 0.61.0 [88].
  - Бета-инструмент «Claude Code CLI» появился в 0.19.1 и убран в 0.24.0 [66].
  - Модели, которые называет CHANGELOG [66]:
    - Claude: Sonnet 5.5 (по умолчанию, контекст 1M), Opus 5, Opus 5.5, Fable 5.2 (1M), Haiku 5.5;
    - OpenAI: GPT-5.5, GPT-6 Astra, GPT-6 Sol и Luna, GPT-6.1 Sol.
  - Ограничения по вендорам:
    - Gemini — только API keys из AI Studio; модель по умолчанию — gemini-3.8-flash [39][54];
    - Copilot — нужен fine-grained PAT (personal access token GitHub) с правом «Copilot Requests» [54];
    - OpenCode — 75+ провайдеров локально и 180+ провайдеров по API key в hosted workspaces. Локально писать ему
      prompt-ы может только владелец. С 0.24.0 есть managed OpenCode [54][66];
    - Cursor — только автономный режим, без учёта tokens [54][123].
  - Настройки модели: уровни effort low, medium, high, xhigh, max [45]; контекст 200k или 1M переключается посреди
    session [44]; у Claude есть настройка «advisor model» (0.21.2) [66].
  - Вход в провайдеров:
    - API keys [38][60];
    - subscription token Claude из `claude setup-token` (планы Pro, Max, Team, Enterprise), он хранится как
      `CLAUDE_CODE_OAUTH_TOKEN`; или Sign in with Claude там, где он поддержан [60];
    - Codex — `codex login` или Sign in with ChatGPT [38][60]. С 0.23.3 можно импортировать уже имеющиеся
      ChatGPT-учётные данные Codex. С 0.17.3 у каждого пользователя могут быть свои OpenAI-совместимые endpoint-ы
      Codex [66].
  - Каждый пользователь сам выбирает API key или subscription token. Сам Agor учётные данные из окружения не
    подхватывает [60]. Документация советует ключи на каждого пользователя, а не общие [60].
  - Это расходится с ответом maintainer-а от ноября 2025. Тогда несколько пользователей одного сервера не могли
    работать каждый на своём плане Max: либо один общий план, либо у каждого API key [130 #207]. Когда это
    поменялось, в заметках не сказано.
- **Один пользователь или команда.**
  - Команда — главный сценарий: live cursors, комментарии на board, роли, общие sessions [46][58].
  - Один пользователь — режим по умолчанию: SQLite на одной машине [38].
  - В Cloud роли owner, admin, member; в beta — до 5 участников на команду [2][3].
- **Платформы.**
  - Сервер: Linux поддерживается полностью. macOS — только в режиме `simple`, без sandbox [60][117].
  - Нативный Windows не поддерживается. Пакет в npm исключает win32, и с версии 0.26.4 npm отказывает в установке
    [60][66][68]. WSL2 вендор не проверял; пользователям Windows советуют заходить через браузер [60].
  - Клиенты: браузер на компьютере; мобильный workspace (0.26.4); мобильная оболочка с вкладками по адресу `/m`
    (0.27.0) [66].
  - Homebrew formula в репозитории есть, но закреплена на 0.21.0, в homebrew-core не входит, а текущая документация по
    установке о ней молчит. Homebrew как текущий способ установки — не подтверждено [66][71].

## Функции

Функции описаны по документации и коду на коммите `fb6829a` [65]. В скобках — версия, в которой функция появилась,
по CHANGELOG [66]. Документация делит функции на четыре группы: основной workflow, агенты и контекст, командная
работа, продуктовый опыт [40].

### Установка и первый запуск

- **Установка CE.** `npm install -g agor-live`, затем `agor init`, `agor daemon start`, `agor open`. Нужны Node
  ≥ 22.12 и Git [65][68].
- **Docker Compose** — другой путь: `docker-compose.prod.yml` на localhost:3030, с заранее созданным admin и без
  агентов по умолчанию [64].
- **`agor init`** спрашивает, каких агентов поставить; нужен хотя бы один. Потом идут `agor install --sync` и
  `agor doctor` — проверка установки [38]. Там же `agor init` спрашивает про анонимную телеметрию [30].
- **Wizard первого запуска** [38]:
  1. Шаблон teammate (постоянного агента), старт с нуля или пропуск.
  2. Провайдер: Claude (рекомендован), GPT, Gemini или свой endpoint. Учётные данные проверяются сразу.
  3. Просмотр каталога MCP. На этом шаге ничего не подключается.
  4. Готово: создаётся board, и стартует первая session teammate.
- Esc откладывает wizard; вернуться к нему можно из Settings → Profile. Slack настраивается отдельно [38].
- **История wizard.** Пятишаговый wizard появился в 0.23.3, в 0.28.0 его сократили [66]. Из onboarding убрали
  вопросы о цели и роли и длинный список инструментов для подключения. Новое правило: быстро довести пользователя до
  teammate, а инструменты подключать позже, с помощью этого teammate [66][74].
- **Guide «первый teammate»** предлагает пути по ролям: пишет код, ведёт проекты, руководит командой, работает один
  [39].
- **Обновления.** Пакет похудел со 126 до 42 MiB в 0.27.0. С 0.17.1 баннер предупреждает, если версии интерфейса и
  daemon разошлись. 0.28.0 требует offline-миграции базы [66].
- **Телеметрия.** Анонимный ping при установке и необязательная агрегированная статистика использования. Выключается
  `AGOR_TELEMETRY=0` или `DO_NOT_TRACK=1` [30]. В 0.28 добавили продуктовую аналитику, которую настраивает оператор
  установки; она работает на Segment [66].

### Boards

- **Что это.** Board — бесконечное 2D-полотно на React Flow (библиотека графов и полотен для React). В workspace
  может быть много boards [41][42].
- **Объекты на board:** карточки branch, zones, текст, markdown-заметки шириной 300–800 px, apps и artifacts
  [42][127].
- **Навигация и вид:**
  - zoom через Cmd/Ctrl и колесо мыши (0.18.0) [66];
  - порядок слоёв (0.23.2) [66];
  - подсветка активной branch и центрирование на ней (0.21.0) [66];
  - свои CSS-анимации (0.17.0) [66];
  - новые фоны (0.24.3) [66];
  - переключатель тем и редактор своей темы [125].
- **Управление.** Архив boards (0.16.0). Меню «+» Create (0.27.0). С 0.28.0 новые boards приватные [66].
- **Роли на board:** Viewer, Editor, Manager [42].
- **Что показывает.** Board показывает branches, а не списки sessions [77]. Позиции объектов хранятся в
  `board_objects.data = {position:{x,y}, zone_id?}` [114].

### Zones

- **Что это.** Zone — область на board с шаблоном prompt-а. Перенос branch в zone запускает этот шаблон. Документация
  называет zones workflow engine (движком процесса), где положение карточки запускает поведение [42][77].
- **Панель zone:** переименовать, вид, заблокировать, настройки автоматизации, расставить, удалить. Удаление
  открепляет содержимое zone [42].
- **Раскладки:** Free, Row, Column, Grid (0.28.0) [42][66].
- **Что происходит при переносе** [42][107]:
  - по умолчанию — picker: пользователь выбирает новую или существующую session и действие — Prompt, Fork или Spawn;
  - режим «Always new» — всегда новая корневая session с готовым prompt-ом.
- **Prompt** — редактируемый шаблон Handlebars (язык шаблонов с подстановками `{{...}}`) [42]. Шаблоны рендерятся на
  daemon, в сервисе `/templates`; в браузере Handlebars нет [84].
- **Переменные шаблона:** branch (имя, URL issue, URL PR, уникальный id), board, session, environment (URL, статус),
  репозиторий (имя, ветка по умолчанию) [42].
- **Применение.** Документация показывает zones как kanban-конвейер. Пример — zone, которая запускает пять
  reviewer-ов [42]. Ещё пример — zone «Codex review», собранная из URL issue и PR. В демо-данных есть zone «Review»
  [42][121].
- **Zones руками агентов.** Пользователи просят агентов создавать zones и их prompt-ы. Maintainer пишет, что агенты
  раскладывают zones по просьбе и даже сами выбирают цвета [131 #675].

### Branches — карточки на board

- **Что это.** Branch — git worktree или полный clone плюс запись с метаданными. Режим clone появился в 0.21.0
  [43][66]. До 0.21.0 этот объект назывался Worktree; переименовали без слоя совместимости [66].
- **Правило.** Одна branch — одна фича или bug — один PR [77].
- **Где лежит.** Рабочие копии — в `~/.agor/worktrees/<repo>/<name>`, база — `~/.agor/agor.db`, конфигурация —
  `~/.agor/config.yaml` [43][65][76].
- **На карточке** [42][45][55]:
  - дерево sessions — «генеалогия» разговоров;
  - pill (метка) environment;
  - бирюзовая пульсация, когда branch ждёт внимания.
- **Окно деталей** — вкладки General, Sessions, Environment, Files, Schedule [43].
  - Files показывает All files, Changes и Staged, с git-значками (0.26.7) [43][66].
  - Diff viewer появился в 0.16.2 [66].
- **Ссылки.** Поля URL issue и URL PR подставляются в prompt-ы zones [42][43].
- **Готовность.** На медленных файловых системах Agor ждёт готовности branch 45 s по умолчанию, максимум 5 min [43].
- **Архив.** Файлы: не трогать, очистить (`git clean -fdX`, если политика разрешает) или удалить. Метаданные: в архив
  или удалить навсегда [43].
- **Доступ к branch.** Роли Viewer, Collaborator, Manager. Доступ к файлам: none, read или read-write. Terminal
  требует доступа к файлам [43].
- **Порты.** У каждой branch есть монотонный номер `branch.unique_id` внутри репозитория. От него считают порты,
  например `{{add 9000 branch.unique_id}}` [55][81].

### Sessions и деревья sessions

- **Что это.** Session — разговор с агентом, привязанный к branch. Внутри карточки sessions показаны деревом
  [44][77].
- **Fork** копирует контекст до точки fork. Только Claude Code и Codex; Codex — с 0.19.0 [44][66].
- **Spawn** — дочерняя session с чистым контекстом. У неё можно поменять агента, модель, права, MCP servers и
  содержание callback [44].
  - Кнопка «Spawn subsession» не создаёт дочернюю session сама. Она шлёт родительскому агенту служебный prompt с
    требованием вызвать MCP tool `agor_sessions_spawn`. Какой контекст передать ребёнку, решает родительский агент
    [44][108].
- **btw** (0.16.2) — короткий побочный вопрос. Это временный fork: он идёт параллельно, сам уходит в архив, а ответ
  вставляется в родительскую session. Только Claude и Codex [44][66].
- **Callbacks** — отчёт дочерней session родителю: статус, summary, число вызовов инструментов, последнее сообщение.
  Родителя он не блокирует; если родитель занят, callback ждёт в очереди [44]. Режимы Once и Persistent; Persistent
  — с 0.27.0 [44][66].
- **Изменения на ходу.** Посреди session можно сменить модель, effort, права, MCP servers, переменные окружения и
  размер контекста [44].
- **Общие файлы.** Fork и spawn остаются на той же branch: расходится разговор, а не файлы. Документация
  предупреждает о возможных конфликтах в git [44][77].
- Документация сравнивает деревья sessions с subagents Claude Code в отдельной таблице [44].

### Очередь prompt-ов

- Очередью владеет daemon, поэтому prompt-ы не теряются (0.17.3) [66].
- Задачи в очереди можно отменить и переставить (0.26.7) [66].
- Каждый prompt помнит, откуда он пришёл, — prompt provenance (0.27.0) [66].
- Очередь видна прямо в окне разговора [45].

### Восстановление session в интерфейсе

- Интерфейс показывает состояния «соединение прервано» и «идёт очистка». Принудительно снова открыть session можно,
  только набрав слово STOP [44].
- Executor шлёт heartbeat — сигнал «я жив» (0.21.0) [66].
- **Resume** после прерванного хода отправляет новую задачу с фиксированным текстом: «Continue from the interrupted
  task. Inspect the previous task state first, then continue safely.» [78][98][99].
- **Try again** повторяет исходный prompt — только если запуск вообще не начался и prompt набирал тот, кто смотрит
  [78][98][99].
- Если ход упёрся в лимит, Resume появляется только после времени сброса [98].

### История разговора

- Сначала грузятся 10 последних ходов, в памяти держатся 30. Поиск внутри session — по загруженным ходам (0.23.2)
  [44][66].
- Разговоры подгружаются страницами (0.26.5) [66].
- Лимиты: 800 000 байт на запись одного сообщения; 250 KiB на превью diff [44].

### Окно разговора

- **Стоимость.** У каждого prompt-а — tokens (input, output, cache read, cache write) и доллары. Итоги суммируются по
  session [1][45].
- **Контекст.** Подложка показывает заполнение окна контекста; у каждого сообщения есть popover с контекстом [45].
  Это оценка, а не точный счёт [54].
- **Блоки содержимого** [45]:
  - Edit — с diff; Bash — с exit code; MCP — с JSON;
  - изменения git по каждому сообщению, todo-списки прямо в ленте, видимая очередь сообщений, @-автодополнение;
  - рендер через Streamdown, с Mermaid (диаграммы), KaTeX (формулы), Shiki (подсветка кода) и GFM (markdown в
    стиле GitHub).
- **Ввод.** Вложения, вставка скриншотов и файлов любого типа (0.19.1, 0.23.2, 0.26.7), отдельно на каждую session
  [45][66]. Slash-команды с автодополнением (0.14.3) [66].
- **To-do агента** обновляется вживую: у Claude — через его task tools, у Codex — через `update_plan` [45][92].
- **Лимиты (0.16.0).** Блок с текстом `Resets: <time>`. Ход, который упёрся в лимит, пишет
  `<Agent> usage limit reached. Try again after <time>.` [66][125]. Автоматического продолжения нет: пользователь
  пишет снова сам [125].

### Режимы разрешений и approvals

- **Режимы по агентам** [123]:
  - Claude: Manual, Plan, Accept edits, Auto (спрашивает, когда не уверен), Bypass;
  - Codex: Untrusted, On request, On failure, Never ask — в сочетании с sandbox read-only, workspace-write или
    danger-full-access;
  - Gemini: Accept edits, Bypass;
  - OpenCode и Copilot: Manual, Accept edits, Bypass;
  - Cursor: Autonomous.
- **Значения по умолчанию** [102]:
  - Claude — `auto`: решает классификатор модели в SDK, а всё нерешённое уходит в интерфейс Agor;
  - Codex — `allow-all`: sandbox workspace-write, approval never, сеть включена;
  - Gemini и OpenCode — `autoEdit`;
  - Copilot — `acceptEdits`;
  - Cursor — `bypassPermissions`.
- **Карточка approval.** Запрос ждёт решения 10 минут по умолчанию, потом задача получает статус `timed_out`
  [100][101]. Timeout запросов появился в 0.14.0 [66].
- **Remember** сохраняет решение в файлы настроек Claude — project, user или local [100][101].
- Одобрить запрос можно только в интерфейсе, не через MCP [53].
- **Разная глубина по агентам.** Запросы разрешений у Claude — полные, у Codex — базовые, у Gemini нет режима Manual,
  у Copilot и OpenCode — интерактивные, у Cursor их нет совсем [54].

### Environments

- **Что это.** Environment — команды для запуска приложения конкретной branch: start, stop, nuke (снести всё), logs,
  health, URL приложения [55].
- **Варианты.** В файле `.agor.yml` v2 есть именованные варианты (0.17.0). Они рендерятся для каждой branch по кнопке
  Render. Варианты правят admins; запуск варианта требует права «all» на branch [55][66].
- **Logs и health.** Logs разделены на вывод команды и вывод работающего приложения. У health checks есть свой
  жизненный цикл [55]. Успешный Start значит только, что команда отработала, а не что приложение готово [55].
- **Docker.** Быстрый старт на Docker Compose; порты — из шаблонов вроде `{{add 9000 branch.unique_id}}`. В шаблонах
  есть математические helpers [55].
- **Без Docker.** Environments только с webhook (0.21.1) — например, в Cloud, где нет локального Docker [55][66].
- **Готовые интеграции.** Previews на Railway (0.26.9) и GitHub Codespaces. Vercel, Kubernetes и VM описаны как
  возможные, но не проверенные [55][66].
  - Заметки расходятся насчёт Codespaces. Документация Environments называет GitHub Codespaces готовой интеграцией
    [55]. По CHANGELOG, поддержку Codespaces и devcontainers убрали в 0.18–0.19 [66].
- **На карточке** pill environment открывает приложение и даёт start, stop, logs и edit [55].
- **Переменные.** Обязательные переменные окружения можно объявить (0.14.3) [66].
- **Защита.** Перед запуском итоговая команда проверяется по deny list [55]. Start, Stop и Nuke никогда не
  повторяются автоматически [55].

### Terminal

- **Мультиплексор.** Страница о multiplayer пишет, что web-терминал общий через tmux. Guide по установке и код daemon
  используют Zellij (терминальный мультиплексор, как tmux) с 1000 строк scrollback. Страница про tmux устарела
  [46][60][125]. По истории README, tmux заменили на Zellij в ноябре 2025 [72].
- **Доступ.** По умолчанию terminal включён для members и выше. В режиме simple он работает от имени пользователя
  daemon [29]. В 0.17.0 доступ members был спрятан за флагом конфигурации [66].
- **Срок жизни.** Executor web-терминала живёт, пока terminal не закрыт, — в отличие от остальных executors
  [62][122].
- **AI-помощника в terminal нет** [125].

### Artifacts

- **Что это.** Artifacts (0.16.0) — живые приложения Sandpack на board. Sandpack — движок CodeSandbox, который
  собирает и запускает web-приложение прямо в браузере [52][66].
- **Публикация.** Агенты публикуют artifacts через MCP; повторная публикация перезагружает приложение на лету.
  Ручного создания в интерфейсе нет [52].
- **Шаблоны.** static, react, react-ts, vanilla, vanilla-ts. Тип code принимает ещё vue, vue3, svelte, solid и
  angular. До 1000 исходных файлов [52].
- **Доверие.** Значок Yours, Trusted или Untrusted и переключатель «можно взаимодействовать» [52]. Согласие при первом
  использовании (trust-on-first-use) — на один раз, на artifact, на автора или на весь instance (0.18.0) [52][66].
- **Секреты** подставляются в отрендеренное приложение отдельно для каждого зрителя [52].
- **Доступ агента.** Tool `agor_artifacts_query_dom` даёт агенту прочитать DOM своего отрендеренного приложения [52].
- **Прочее.** Экспорт в CodeSandbox, возврат кода в branch, полноэкранный режим (0.21.1) [52][66]. Можно поднять свой
  bundler Sandpack (0.16.2) [66].

### Cards (Beta)

- **Что это.** Cards (0.15.0) — записи не о коде на board, например tickets или leads [26][51][65].
- **Типы.** У типа есть emoji, цвет и необязательная JSON schema. Типы правят в Settings → Cards [51].
- **Поля.** Title, description, note и data. Статус карточки — это zone, в которой она лежит [51].
- **Автоматизация.** Cards не запускают автоматизацию zones [51].
- **MCP tools:** create, update, move, list, archive, delete, bulk create, bulk move [51].
- **Предлагаемые применения:** поддержка, продажи, DevOps, контент, миграции, здравоохранение [51].

### Knowledge

- **Что это.** Knowledge — база markdown-документов с версиями, разложенная по namespaces. Виды документов: doc,
  memory, skill, prompt, guide, decision, bundle, external (0.21.1) [56][66].
- **Поиск.** Текстовый работает всегда. Семантический и гибридный — только с PostgreSQL, pgvector (расширение
  PostgreSQL для векторного поиска) и embeddings OpenAI [56][115].
- **Связи.** Ссылки вида `agor://kb/document/<id>` строят граф; его можно открыть как отдельный вид [56].
- **Прочее.** MCP tools для агентов; архив и восстановление и формат v2 (оба — 0.27.0); экспорт и импорт через CLI в
  формате, удобном для git (0.26.5) [56][66].
- Для teammates Knowledge — основное хранилище памяти и документов. Backup в git Knowledge не включает [47].

### Teammates — постоянные агенты

- **Что это.** Teammate — постоянный агент со своей личностью и памятью. Технически — особая branch, созданная из
  шаблонного репозитория `preset-io/agor-teammate`. Идея взята из OpenClaw — open-source проекта с одним долгоживущим
  личным агентом [11][47][129].
- **Разделение понятий.** Teammate — это «кто»: личность и память. Агент — движок, который выполняет его session
  [47]. Branch — это «где» [13].
- **Board и onboarding.** У teammate свой приватный board. Его первая session выполняет файл `ONBOARDING.md` [47].
- **Файлы памяти:** `SOUL.md`, `IDENTITY.md`, `USER.md`, датированные заметки `memory/YYYY-MM-DD.md`, `BOARD.md`,
  `HEARTBEAT.md` [47][129].
- **Skills шаблона:** каналы gateway, подключение SaaS, управление задачами [129].
  - Skill `task-management` задаёт порядок: поиск в Knowledge → `agor_branches_create` → `agor_sessions_create` с
    brief-ом (цели и как выглядит «готово») → запись причины решения в память → наблюдение через callbacks или board
    [129].
- **Оркестрация.** Teammate управляет другими sessions через MCP server Agor [47].
- **Создание и вид.** Teammates создают в Settings → Teammates. На board это карточки с иконкой робота и синей рамкой
  [47]. Есть каталог teammates (0.26.9) и вид со всеми branches (0.24.4) [66].
- **Когда действует.** Только когда его просят или когда срабатывает расписание; сам по себе не бродит [39].
  Heartbeat — запуск по расписанию, который читает `HEARTBEAT.md`, — делает teammate проактивным [13][25].
- **Heartbeat в шаблоне** запускает `gh pr checks` и двигает branches между zones [129].
- **Чьи учётные данные.** Общий teammate работает с учётными данными того пользователя, который его попросил [13].
- **История имени.** Persisted Agents → Assistants (0.14.0) → Teammates (0.23.3) [66].
- **Витрина.** На главной — AgorClaw, Preset Architect, Princeton, Milchick, Peyton Manning, SRE, Telchar, Saul, Blake,
  Hodor!, Wendy, Bug Basher, DatAgor [1]. Страница roster описывает роли: AgorClaw — оркестратор кода, Princeton —
  reviewer PR, Telchar — патчит CVE, Saul — юрист, Blake — deal desk, Hodor — PM самого Agor, Wendy — конкурентная
  разведка [23].

### Scheduler

- **Что это.** Scheduler (0.10.0) запускает sessions по cron. Одно расписание на branch; визуальный конструктор cron;
  время только UTC [48][66].
- **Запуски.** Каждый запуск — новая session с названием `Scheduled: <branch>` [48].
  - Окно защиты от дублей — 2 минуты.
  - Пропущенное не догоняется: после простоя срабатывает только последний пропущенный слот.
  - Хранятся последние N запусков [48].
- **Настройки расписания.** Агент, модель, режим разрешений и MCP servers. Prompt — шаблон Handlebars с данными
  branch, board и расписания [48].
- **Права.** Создать расписание может только Manager. Расписание работает от имени создателя, и его права
  перепроверяются при каждом запуске [48].
- **Позже добавили.** «Execute now» и `allow_concurrent_runs` (0.17.0); расписания как отдельные объекты с созданием,
  чтением, правкой и удалением (0.21.0) [66].
- **Без человека.** Для запусков без человека документация советует режим разрешений Auto [48].

### Message gateway — каналы из чатов

- **Что это.** Gateway связывает чат с sessions Agor. Сообщение в чате становится prompt-ом, ответ агента
  возвращается в чат [49].
- **Платформы:**
  - Slack — через Socket Mode; появился в 0.12 (2026-02-09) [49][66];
  - Discord — через gateway-соединение Discord; появился 2026-08-25 [49][75 #2524];
  - GitHub и Shortcut — опрос API, без webhooks; Shortcut — с 2026-07-16 [49][75 #1903];
  - Microsoft Teams — HTTPS callback, один tenant Entra. В 0.28.0 стал высокодоступным и вышел из статуса
    Experimental [49][66].
- **Каналы.** Канал направлен на «домашнюю» branch; с 0.28.0 по умолчанию — на teammate [49][66]. В канале задают
  агента, модель, режим разрешений (trust, auto, supervised или manual) и MCP servers [49].
- **Треды и личность.** Каждый тред платформы — одна session. Отправителя сопоставляют с пользователем Agor по email;
  тем, кого сопоставить не удалось, отказывают. Вместо этого можно задать фиксированного пользователя «run as» [49].
  Агент работает от имени того, кто спросил [1].
- **GitHub: настройка.** GitHub App создают через manifest flow в Settings → Gateway или вручную. Права: Contents
  read, Issues и Pull requests read/write, Metadata read. Webhooks выключены [49]. Канал опрашивает выбранные
  репозитории и ищет ключевое слово упоминания — по умолчанию `agor` [49]. В коде интервал опроса по умолчанию —
  15 s [113].
- **GitHub: как это выглядит** [49]:
  1. Кто-то пишет `@agor` в issue или PR.
  2. Agor ставит реакцию «eyes».
  3. Публикует комментарий «Processing» со ссылкой на session.
  4. Заменяет его итоговым ответом от `agor[bot]`.
  - На один PR — одна session. Reviews и inline-комментарии review его не запускают [49].
- **Shortcut** опрашивается каждые 15 s [49].
- **Teams** [49]:
  - на канал — один публичный HTTPS callback, его обслуживает каждый daemon;
  - в личных чатах упоминание не нужно, в группах и каналах — нужно;
  - каждый тред ответов в канале — своя session;
  - длинные ответы режутся на части;
  - доставка с неизвестным исходом помечается «ambiguous» и повторно не отправляется.
- **Команды в чате.** `!stop`, `!skip`, `!stop-clear`, `!help` (0.28.0) работают в Slack, Discord и Teams [66][79].
- **Прочее.** Реакции Slack как prompt-ы и форумы Discord (0.27.0); личные сообщения Discord с историей (0.26.8);
  режим «все публичные каналы» в Discord (0.28.0) [66]. Emoji-реакции приходят как prompt-ы [49]. OAuth-карточки
  Connect появляются и в Slack (0.26.7) [66].
- **Предупреждение.** Документация пишет: канал даёт его участникам власть над агентом, сравнимую с удалённым
  терминалом [49].

### Agor как MCP server

- **Что это.** Встроенный MCP server — endpoint `POST /mcp` с bearer-авторизацией. Его tools повторяют сервисы
  интерфейса и работают с правами того пользователя, от имени которого их вызвали [41][53].
- **Tokens.** Каждая session получает JWT (подписанный token) на 24 часа с ограниченными правами [53]. Внешние агенты
  подключаются к `/mcp` с личным ключом `agor_sk_` (0.16.1; без привязки к session — с 0.21.0) [53][66].
- **Поиск инструментов.** Прогрессивный, через три tool-а: `agor_search_tools`, `agor_get_tool_details`,
  `agor_execute_tool` [53]. С включённым поиском (по умолчанию) `tools/list` показывает только эти три [53][80].
  Всего в коде около 150 разных tool-ов `agor_*` [109][128].
- **Области:** sessions, repos, branches, boards, zones; tasks (отмена, перестановка); environments, cards, artifacts,
  schedules; knowledge, gateway, users [53].
- **Главные tools оркестрации** [53][79][80]:
  - `agor_sessions_create` — новая session в любой branch, можно с persistent callbacks;
  - `agor_sessions_prompt` — режимы `continue`, `fork`, `subsession`, `btw`;
  - `agor_branches_create` — асинхронно; с `waitForReady` ждёт готовности branch;
  - `agor_branches_set_zone` — может запустить триггер zone;
  - `agor_tasks_cancel_queued` и `agor_tasks_reorder_queued` — правка очереди; `agor_sessions_stop` принимает
    `expectedTaskId`.
- **Агент по умолчанию.** Настройка «Primary coding agent» выбирает агента для sessions, созданных через MCP (0.27.0)
  [66].
- **Живой контекст.** Текущий контекст session агент получает через tool `agor_sessions_get_current_context` [91].

- **Live cursors** обновляются примерно каждые 100 ms. Facepile — аватары тех, кто сейчас на board [41][46].
- **Пространственные комментарии** на boards, zones, branches и sessions — с тредами и @mentions [46]. Их можно

- **Чужие sessions.** Писать в чужую session можно, только если это разрешает настройка workspace и есть пакет прав на

### Безопасность CE

- Авторизация на каждый вызов; пароли — bcrypt; секреты — AES-256-GCM; MCP tokens на 24 часа; лимит запроса 10 MB
  [29].
- Встроенного SSO нет. Для SSO и списков разрешённых IP советуют reverse proxy [29].
- Master key нельзя ротировать [29].
- В режиме simple агенты и web-терминалы работают от имени пользователя daemon. Они могут читать его конфигурацию,
  секреты и API keys [29].
- Refresh token живёт от 1 часа до 90 дней, по умолчанию 30 дней (0.28.0). Одноразовые коды запуска (0.21.0).
  Anonymous mode убран (0.19.0) [66].
- CSP и CORS настраиваются. Функция `safeOutboundFetch` не ходит на приватные адреса [84].
- Канал для приватных сообщений об уязвимостях включили через два дня после просьбы внешнего аудитора [130 #1817].

  На вопрос пользователя о CLI для старта sessions из терминала ответил участник сообщества, а не сотрудник: такого
  нет [131 #1440].
- Config-as-code с командой sync (0.16.2); вход в CLI через браузер (0.26.7) [66].
- CLI и интерфейс не ходят в базу напрямую, только через API: принцип API-first с первого дня [41][76].

- Управляемый сервис. Private beta — с 2025-11-23, open beta — с 2026-10-13 [10][22][37].

## Принципы и подходы

### Откуда взялся Agor

- В августе 2025 Beauchemin и Evan Rusackas выпустили Claudette — CLI для разработки Superset. В нём у каждой ветки
  свой git worktree, своё окружение и свои порты Docker [34].
- Beauchemin пишет, что сделал Agor, когда упёрся в предел 5–10 параллельных sessions Claude на Superset. Agor
  обобщил идею Claudette [8].
- Ещё раньше эссе Preset задало экономическую посылку: AI сделал эксперименты дешёвыми, больше всего на результат влияет
  контекст, а команде нельзя зависеть от одной модели [33].
- Первую версию, примерно v0.4, сделали меньше чем за месяц, в основном по вечерам: основатель координировал
  параллельных AI-агентов, которые работали внутри самого Agor. Это заявление основателя [5][133]. README благодарит
  «армию» Claude и Codex [65].
- Хронология: репозиторий создан 2025-10-04, лицензия BSL — 2025-10-13, пост making-of — 2025-10-25, анонс —
  2025-10-26, первая публикация в npm — 2025-10-27 [5][6][65][68][70].

### Исходный тезис (октябрь–ноябрь 2025)

- **Узкое место — процесс, а не код.** Поставку тормозят ожидание review, переключение веток, возня с окружениями и
  координация в Slack — сильнее, чем написание кода [6].
- **Аналогия с Figma.** Figma перевела дизайн из личных файлов в совместную работу на общем полотне в реальном
  времени. Agor хочет сделать то же для разработки [6].
- **Пространственная память.** Основатель считает, что люди лучше помнят, где работа лежит на полотне, чем ищут её в
  прокрутке [6]. В making-of он пишет: списков не хватало, нужно было видеть место и историю [5].
- **Multiplayer прежде всего, но лёгкий.** Presence, cursors, комментарии — ровно столько реального времени, чтобы не
  терять контекст [5][6].
- **Через SDK, а не через CLI.** Agor управляет Claude Code, Codex и Gemini через их SDK. CLI — лишь адаптеры, вывод
  CLI не разбирается [5][6]. Позже основатель уточнил: Agor — оркестратор agentic coding tools, а не сам
  мультимодельный coding-агент [131 #489].
- **Worktree — единица работы.** Одна фича — один worktree со своим dev server и автоматически выделенными портами.
  Позже эту единицу переименовали в Branch [5][6][77].
- **Деревья sessions.** Fork — чтобы распараллелить работу. Spawn — чтобы поручить узкую задачу дочерней session с
  чистым контекстом [5][6].
- **Session знает, где она.** Session знает свой board и worktree и может действовать на Agor через его MCP server
  [5].
- **Платформа, а не GUI** [9]:
  - слои: примитивы → REST и WebSocket API → CLI → типизированный TypeScript client → интерфейсы;
  - предпочтения: постоянное вместо одноразового, наблюдаемое вместо чёрного ящика, продолжаемое вместо одного
    запуска.
- **Context engineering** — подход основателя к контексту [7]:
  - контекст — как код: маленькие связанные markdown-заметки («context nuggets») в папке `context/`;
  - `CLAUDE.md` — глоссарий и карта, а не склад всего подряд;
  - сначала план, потом код. По умолчанию задача решается за один заход по design doc. Раздавать работу
    специализированным агентам — только когда это нужно;
  - не переусложнять оркестрацию.
  - Репозиторий до сих пор так устроен; `CLAUDE.md` — symlink на `AGENTS.md` [65][77]. Design docs для агентов в
    `context/` необычно подробные [76][77][78][79].
- **Эссе об оркестрации** (2025-11-15) описывает семь фаз [8]:
  - Agor — в фазе 5 (инструменты для многих агентов) и в фазе 6 (агенты оркеструют друг друга через MCP);
  - он тянется к фазе 7: supervisor-агенты по расписанию и цепочки запусков по завершению;
  - у фазы 7 есть «runaway problem» — цепочки агентов, которые запускают агентов. Эссе просит ограничений, как
    лимиты в Kubernetes: бюджеты tokens, лимиты параллельности, circuit breakers (автоматическая остановка при
    сбоях);
  - основатель не знал, останется ли оркестрация занятием одного человека или станет командным («group vibe
    coding»).
- **Открытые вопросы** из making-of [5]: сколько автоматизации zones станет шумом; останутся ли полезными отчёты
  sessions; где кончается «приноси свой редактор»; курировать контекст вручную или выводить автоматически. Agor подан
  как правильное решение на сегодня, а не навсегда.

### Ключевые понятия на ноябрь 2026

Пять примитивов [77]:

- **Branch** — рабочая git-папка со своим dev environment: native git worktree или изолированный clone [60][77]. Одна
  branch = одна фича или bug = один PR [77].
- **Board** — 2D-полотно, где branches — карточки, а sessions — дерево внутри карточки [77].
- **Session** — разговор агента; в базе она обязательно ссылается на свою branch [77].
- **Task** — один prompt и его выполнение. В очередь встаёт именно task, если session занята [77].
- **Report** — markdown-сводки, которые пишут агенты. Помечен как «planned/partial» — запланирован или сделан
  частично [77].

Правила сочетания [77]:

- boards показывают branches, а не списки sessions;
- fork и spawn расходятся в разговоре, а не в файловой системе;
- иерархия: board → branch → sessions → tasks → messages.

Другие термины (подробно — в разделе «Функции»):

- **Environment** — `.agor.yml`, именованные варианты, порты на каждую branch [24].
- **Teammate** — постоянный агент на branch с файлами личности и памяти, на фреймворке `agor-teammate`, который
  заимствует идеи OpenClaw [25][47][129].
- **Heartbeat** — запуск teammate по расписанию, который читает `HEARTBEAT.md` [25].
- **Scheduler** — cron в UTC; запуски без дублей; после простоя срабатывает только последний пропущенный [25].
- **Knowledge** — markdown-namespaces с версиями, ссылками и текстовым поиском, плюс необязательный семантический
  [24][25].
- **Message Gateway** — каналы Slack, Discord, GitHub, Shortcut и Teams; session работает от имени сопоставленного
  отправителя [26][66].
- **Artifacts** — живые приложения Sandpack на board [24].
- **Cards (beta)** — записи не о коде, например tickets или leads [26][65].
- **Agor MCP** — тот же API, что у интерфейса, с отдельными учётными данными на каждую session [24].
- **Executor** и режимы выполнения `simple`, `sandbox`, `delegated` [18][27].
- **Термины интерфейса:** attention glow (подсветка внимания), facepile, spatial comments (комментарии, привязанные к
  месту на board), общий terminal branch [26][28].
- **btw** — временный fork; **Home** с разделами Needs you и My work [66].

### Философия 2026: от sessions к teammates

- **Agor vs. OpenClaw** (2026-02-03) [4][11]:
  - OpenClaw — один долгоживущий личный агент. Agor — много короткоживущих агентов параллельно: на полотне, вокруг
    git, для нескольких людей.
  - Настоящей находкой OpenClaw основатель называет цикл агента: личность, память, самоулучшение.
  - Он взвешивал три пути: выпустить готовый фреймворк со своим мнением, оставить только примитивы или сделать и то и
    другое с заменяемыми умолчаниями.
  - Следующий опыт запустил паттерны OpenClaw целиком внутри Agor через Agor MCP, с heartbeat-subsession каждые 30
    минут [12].
- **Teammates** (2026-03-03) [13][131 #675]:
  - teammate — «кто», branch — «где»;
  - память и личность живут в git; heartbeats делают teammate проактивным;
  - общий teammate работает с учётными данными того, кто его попросил.
  - Адрес поста — `agor-assistants`, а имя Teammates в продукте появилось только в 0.23.3 [13][66]. Заметки
    предупреждают: посты блога правили после публикации, на страницах стоит «last updated 2026-11-10», правки видны в
    истории git [10].
- **Agent Modeling 101** (2026-06-15) [14]:
  - решить, какого агента строишь;
  - задать рамки, как у должности. Проверка — одно предложение, где названы команда, вид работы и системы;
  - личность — это стиль работы;
  - переиспользовать контекст через библиотеку с правами доступа («permissioned library»). Антипаттерны —
    бесконтрольный рост числа агентов («agent sprawl») и сваленный без разбора контекст («context landfill»);
  - моделировать процессы, а не возможности. Начинать с повторяющейся проблемы, источника правды только для чтения и
    конкретного результата;
  - работать там, где команда уже работает;
  - доверие растёт через совместную работу, а не через настройки. Шаги автономии: только чтение → черновики → действия
    с одобрением → автономные действия с отчётом после;
  - governance и наблюдаемость — то, что масштабируется;
  - выбрать между «credential borrowing» (агент берёт учётные данные пользователя) и отдельной «agent identity». В
    обоих случаях каждое действие должно прослеживаться до агента, пользователя, session и источника учётных данных;
  - назвать границы одобрения и путь при сбое. Архивировать лучше, чем удалять.
- **Raise a team helper agent** (2026-06-17) [15]: сначала черновики; действия — с одобрением, пока агент не заслужил
  доверия; повторяющаяся работа идемпотентна (повтор не меняет результат); доверие зарабатывается результатами.
- **Ответ на Claude Tag** (2026-06-26) [4][16]:
  - Claude Tag подтверждает, что категория существует;
  - отличия Agor, по словам вендора: устойчивая личность у каждого teammate, свои рамки у каждого, визуальное рабочее
    пространство, много harness-ов;
  - governance подана как форма самого продукта. Slack — лишь один из входов в это пространство.
- **Is the IDE obsolete?** (2026-08-01) [4][17]:
  - контейнер IDE устарел, но её возможности по-прежнему нужны;

  - узкое место теперь — review, и review должен опираться на риск. Просмотр кода становится местом проверки;
  - Agor подан как командный центр над редактором.
  - В январе 2026 основатель описывал 5–10 агентов и ручной перенос worktrees между zones. Работу полностью без
    присмотра он тогда считал невозможной с текущими моделями, но обещал строить Agor так, чтобы её поддержать
    [131 #491].
- **Agent Modeling 201** (2026-10-07) [21]:
  - передавать владение AI постепенно;
  - один именованный агент на «context cluster» — группу связанного контекста;
  - прежде чем добавить агента, спросить, не должен ли эту работу взять уже существующий;
  - держать roster, который поддерживает себя сам; делить контекст на части, а не копировать;
  - нормы общих пространств: работать в тредах, писать одно краткое итоговое сообщение;
  - вводить агентов в работу как новых сотрудников;
  - переводить человека от одобрения каждого действия к наблюдению и вмешательству;
  - агент-менеджер не заменяет структуру (со ссылкой на Project Vend от Anthropic);
  - признание: Preset добавляла агентов слишком быстро, и стало непонятно, кто что делает.

      падающий test;
    - каждое утверждение агента сверяется с git, PR и CI;
    - устойчивая память; merge делает человек;

  - Hodor описывает себя как markdown-файлы в git. Он пишет еженедельные сводки о росте open-source проекта [20].

### Что вендор называет своим отличием

- Один общий board вместо личных терминалов; команда учится вместе. Agor подан как рабочее место для роли «AI
  Enablement Engineer» — человека, который внедряет AI в команде [28][36].
- Branch — точка, где встречаются sessions, environment, prompts и PR [65][75 #1080].
- Нет привязки к одному вендору моделей [27][54][65]:
  - свои ключи или подписка; harness выбирается на каждую session;
  - Agor выключает встроенный multi-agent у Codex, чтобы вся делегация оставалась видимой как sessions Agor.
- Governance [27]:
  - роли board и branch: Viewer, Collaborator, Manager;
  - Manager никогда не получает доступа к чужим sessions и учётным данным;
  - учётные данные пользователей зашифрованы;
  - граница выполнения — где и от чьего имени работает агент — отдельная настройка, не смешанная с правами.
- Стоимость на виду: оценка стоимости у каждого сообщения, сумма по session и счётчик контекста [24][27].

### Чем Agor не является

Документ позиционирования от мая 2026 перечисляет [75 #1080]:

- не только для кода;
- не model gateway (не прокси к моделям);
- не IDE — «приноси свою IDE» в планах;
- не CI/CD;
- не закрытый SaaS.

### Чем подход отличается

Сводка по заметкам; у каждого пункта — источник.

- **Единица работы — branch, а не session.** На одной branch живёт много sessions; fork и spawn делят её файлы
  [44][77].
- **Своего цикла и планировщика нет.** Agor запускает чужие SDK [54][88]. Планировщика или компонента декомпозиции в
  коде не найдено; работу делят сами агенты через примерно 150 MCP tools [109][128].
- **Положение карточки вместо команды.** Перенос карточки в zone запускает prompt [42][77].
- **Надзор без автоматического повтора.** Сбой не повторяется сам; человек выбирает Resume или Try again [78][98].
- **Governance — часть продукта.** Роли, учётные данные на пользователя, audit [16][27][58].
- **Чаты как вход.** С 0.28.0 каналы gateway по умолчанию направлены на teammates [66]; Slack — один из входов в
  рабочее пространство [16].

### Процессы

- **Daemon** [41][76]:
  - один server на FeathersJS, порт по умолчанию 3030;
  - отдаёт REST, Socket.IO и MCP JSON-RPC на `/mcp`;
  - слои: services → repositories → Drizzle ORM (библиотека доступа к базе);
  - CLI и интерфейс в базу не ходят.
- **Хранилище** [76][114][128]:
  - по умолчанию LibSQL/SQLite в `~/.agor/agor.db`;
  - PostgreSQL — для multi-tenant и HA (high availability — работа нескольких копий сервиса);
  - в SQLite-схеме 57 таблиц.
- **Executor** — отдельный процесс из `packages/executor`:
  - выполняет ровно одну задачу и завершается [86];
  - говорит с daemon через Feathers WebSocket; доступа к базе у него нет [41][86];
  - авторизуется короткоживущими подписанными JWT от `SessionTokenService` [41];
  - исключение — executors web-терминала (Zellij): они живут, пока terminal не закрыт [62][122];
  - все изменения git (clone, worktree add/remove) daemon отдаёт executors; себе оставляет только проверки для
    чтения [62][116].
- **Запуск executors:**
  - локальные executors — дочерние процессы daemon, они всегда работают от его пользователя [87];
  - или daemon вызывает шаблон оператора `executor_command_template`. В документации пример —
    `kubectl run … agor-executor --stdin`; JSON с заданием идёт в stdin [62][87].
- **Интерфейсы.** React 18, Vite, Ant Design (набор UI-компонентов), React Flow для board, client Socket.IO и CLI на
  oclif. Все пользуются одним типизированным client [41][76].
- **Realtime** [41]:
  - события created, patched и removed уходят только авторизованным соединениям того же tenant. Рассылки всем
    подряд нет даже как запасного пути;
  - cursors обновляются не чаще раза в 100 ms;
  - браузер никогда не грузит весь workspace.
- **Health endpoints:** `/livez`, `/readyz`, `/health` [41].

### Цикл агента

- **Своего цикла нет.** Agor не поставляет ни модели, ни агентного цикла. Он вызывает SDK harness-ов; выбор — на
  session [54][65].
- **Один процесс на ход.** Каждый prompt становится Task. Task запускает новый процесс executor, тот делает один вызов
  SDK. Непрерывность разговора — через возобновление id разговора в самом SDK (`sdk_session_id`) [89].
  - Claude: fork — `resume` плюс `forkSession: true`; spawn — новый контекст [89].
  - Codex: `startThread` или `resumeThread` плюс `runStreamed()`. Для fork поднимается короткоживущий
    `codex app-server`, он вызывает `thread/fork` и закрывается [54][93][94].
  - OpenCode: процесс `opencode serve` на время одной задачи [128].
  - Cursor: локальный runtime SDK; автономный режим без запросов разрешений; без учёта tokens [54].
- **Как вызывается Claude** (`query-builder.ts`) [89]:
  - system prompt — preset `claude_code`, к нему добавлены статичная «ориентация» Agor и блок с личностью session;
  - `settingSources: ['user','project','local']` — значит, применяются CLAUDE.md и разрешения из файлов настроек;
  - потоковая выдача tokens включена; `/tmp` и `/var/tmp` добавлены как дополнительные папки.
- **Статичный system prompt ради cache.** Ориентацию нарочно держат неизменной, чтобы префикс prompt-а у провайдера
  не менялся и кэшировался на сервере. Живой контекст агент берёт через MCP tool `agor_sessions_get_current_context`
  [91].
- **Инструменты Claude, которые Agor убирает** [90]:
  - `AskUserQuestion` — в Slack он зависал;
  - `ExitPlanMode` — в Agor нет интерфейса plan mode;
  - `EnterWorktree` и `ExitWorktree` — жизненным циклом branch управляет Agor;
  - `ScheduleWakeup` — разговор некому разбудить; вместо него — расписания Agor.
  - Этот список сливается с deny list из `~/.claude/settings.json` пользователя [66][90].
  - Зато Agor принудительно включает `TaskCreate`, `TaskUpdate`, `TaskGet`, `TaskList` — на них держится закреплённый
    to-do list [90].
- **Политика запуска Codex** [92]:
  - встроенный multi-agent выключен (`features.multi_agent=false`). Комментарий в коде объясняет: оркестрация,
    которую Agor поддерживает и может наблюдать, — это его собственные sessions;
  - `update_plan` включён принудительно; plugins выключены, пока пользователь сам их не включит;
  - переменные окружения с учётными данными MCP Agor обнуляются в каждом shell, который запускает Codex.
- **Тихий сброс контекста у Claude** [89]. Если session не обновлялась больше 24 часов или к ней подключили MCP
  server после последней синхронизации с SDK, Agor стирает `sdk_session_id` и начинает в SDK новый разговор. История
  в интерфейсе остаётся, а модель теряет контекст.
- **Когда ход завершён** [78]:
  - ход Claude завершён только сообщением result от SDK;
  - `is_error: true` — сбой, даже если subtype равен `success`;
  - поток, закрытый без result, — сбой, если его не прервали намеренно.
- **Compaction** (сжатие контекста) делают сами SDK. Agor показывает его системными сообщениями вроде
  `Context compacted successfully` [95][96].

### Планирование и декомпозиция

- **Планировщика нет.** Компонента, который планирует или делит задачи, в коде не найдено [128]. Делят работу сами
  агенты через внутренний MCP server — около 150 tools `agor_*` в `apps/agor-daemon/src/mcp/tools/` [109][128].
- **Spawn — через родителя.** Кнопка «Spawn subsession» рендерит служебный prompt: родительский агент обязан вызвать
  `agor_sessions_spawn`. Родитель сам решает, какой контекст передать [44][108].
- **Tools оркестрации** — `agor_sessions_create`, `agor_sessions_prompt`, `agor_branches_create`,
  `agor_branches_set_zone` и tools очереди [53][80]. Подробно — в разделе «Функции».
- **Zones как стадии конвейера.** Zone хранит шаблон Handlebars. Picker даёт выбрать session и действие; «Always new»
  создаёт корневую session и отправляет готовый prompt [42][107]. Шаблоны рендерит daemon [84].
- **Teammates планируют по skill.** Skill `task-management` задаёт шаги: поиск в Knowledge → новая branch → session с
  brief-ом → запись причины решения → наблюдение через callbacks или board [129].
- **Планы — текстом.** Plan mode убран, поэтому планы агенты пишут обычным текстом [90]. To-do агента рисуется
  вживую: task tools у Claude, `update_plan` у Codex [45][92].

### Параллельность и координация

- **Иерархия:** board → branch → sessions → tasks → messages [77].
  - Sessions одной branch делят её файлы и состояние git.
  - Fork и spawn остаются на той же branch: расходится разговор, а не файлы [77]. Документация предупреждает о
    конфликтах git [44].
  - Запрос «fork the worktree too» — отдельный worktree для fork — открыт с 2025-11-26 [130 #374].
- **Правила очереди** [79]:
  - в каждой session одновременно выполняется не больше одной Task;
  - Tasks в очереди — устойчивые строки таблицы `tasks` с полем `queue_position`; их принимают под блокировками
    строк Branch → Session;
  - запустить задачу может только голова очереди, и у такой попытки ровно один победитель.
- **Callbacks** [44][80]:
  - законченная дочерняя session шлёт родителю статус, summary, число вызовов инструментов и, по желанию, последнее
    сообщение; если родитель занят, callback ждёт в очереди;
  - режимы `once` и `persistent`; persistent позволяет цепочки в несколько шагов (C → B → A);
  - callback принимается после того, как задача ребёнка записана в базу. Документация прямо пишет: это не гарантия
    exactly-once (ровно одной доставки) и не восстановление после падения.
- **btw** — временный fork; идёт параллельно, сам уходит в архив и вставляет ответ в родителя. Только Claude и Codex
  [44].
- **Управление очередью.** `agor_tasks_cancel_queued`; `agor_tasks_reorder_queued` требует точной перестановки
  текущей очереди [53][79]. `agor_sessions_stop` принимает `expectedTaskId` — id задачи, которую видел вызывающий
  [53]. В Slack, Discord и Teams есть `!stop`, `!skip` и `!stop-clear` [66][79].
- **Несколько daemon-ов** [61][79]:
  - каждый daemon запускает `SessionQueueWorker`; лидера и аренды (lease) нет;
  - за один проход worker проверяет не больше 250 sessions, потом ждёт около минуты;
  - кто запустит задачу, решает захват строки в базе (claim);
  - scheduler и runtime reconciler — фоновая сверка состояния — устроены так же;
  - по документации, Redis не служит ни блокировкой задач, ни источником прав tenant, ни устойчивым журналом событий
    [61].
- **Лимит параллельности.** Общего лимита на число одновременных executors в конфигурации daemon не найдено [128].
  Внешний launcher может отказать в запуске, выйдя с exit code 75 [62][78]. В Cloud beta — 5 одновременных executors
  на команду [3].

### Изоляция

- **Хранение branch** [61][104]:
  - `worktree` — по умолчанию, обычный `git worktree add`, общий `.git/config` с базовым репозиторием;
  - `clone` — свой `.git`. Комментарий в коде: так закрываются пути утечки учётных данных и настроек между branches.
    Объекты git можно брать из базового репозитория через `--reference`;
  - hosted multi-tenancy требует только clone.
  - Порты считаются от монотонного `branch.unique_id` внутри репозитория [55][81].
- **Режимы выполнения** (`execution.unix_user_mode`) [59][85]:
  - `simple` — границы нет; агент работает от пользователя daemon;
  - `sandbox` — mount namespace через bubblewrap (утилита Linux для sandbox). Branch монтируется для записи, только
    для чтения или не монтируется — по ролям. Соседние worktrees, чужие home-папки и состояние daemon скрыты. У
    каждого пользователя свой постоянный приватный overlay home. Сеть — общая с хостом: документация говорит, что это
    изоляция файлов, а не сети. Если sandbox недоступен, запуск отказывает, а не тихо работает без него; загрузчик
    конфигурации принудительно ставит `fail_if_unavailable: true` [105];
  - `delegated` — внешний launcher оператора получает `{tenant_id}`, `{user_id}`, `{branch_fs_access}` и
    `{branch_sdk_home}`. Документация оговаривает: Agor не берётся доказать изоляцию внешнего launcher.
- **Перепроверка на ходу** [59][78]. Каждый heartbeat executor-а заново проверяет пользователя, задачу, session,
  branch, право на prompt и доступ к файлам.
  - Потеря доступа завершает задачу через защищённый путь остановки.
  - Новый доступ не расширяет уже работающий процесс.
- **Платформы** [60][117]: Linux — с sandbox; macOS — только доверенный режим `simple`, без локального sandbox;
  нативный Windows — не поддерживается, npm-пакет блокирует установку.
- **Почему ушли от пользователей Unix.** До 0.25 Agor сопоставлял пользователей с учётными записями Unix, а branches —
  с группами POSIX, через sudo и ACL (списки доступа). От этого отказались [18]:
  - права POSIX не выражают граф прав Agor без потерь;
  - исправлять владельцев файлов задним числом (рекурсивные chown, chmod, правка ACL) медленно, и это конфликтует с
    идущей работой;
  - сопоставлять UID на общем хранилище трудно;
  - тысячи branches дают тысячи групп.
- **Общие SDK home на branch.** `sdk_home_mode: per_branch` даёт sessions одной branch общее состояние `.claude` и
  `.codex` [59][104].
- **Codex внутри sandbox Agor.** Если executor уже обёрнут sandbox Agor (`AGOR_OUTER_SANDBOX=1`), Codex работает в
  `danger-full-access` внутри него, чтобы не вкладывать bwrap в bwrap. Переменная `AGOR_CODEX_SANDBOX_MODE` нужна
  потому, что `workspace-write` у Codex требует bwrap, а в pods его нет [93].
- **Учётные данные:**
  - каждый пользователь выбирает API key или subscription token; Agor не берёт учётные данные из окружения сам [60];
  - MCP egress gateway (выходной шлюз MCP) даёт executors только непрозрачные разрешения. Headers подставляет daemon
    и перед каждым внешним вызовом заново проверяет права [83];
  - PR #3246 (2026-11-10) привязывает MCP tokens к задаче и убирает их из аргументов командной строки и окружения
    агента [75 #3246].
- **Изоляция tenants** в PostgreSQL — через row-level security (права на уровне строк) [82].
- **Что изучают дальше.** OpenShell, Docker `sbx`, nono.sh и Lima — в открытых issues #1631 и #1684
  [130 #1631, #1684].

### Состояние и память

- **Схема.** «Гибридная материализация»: поля, по которым ищут, — в индексированных колонках, остальное — в JSON. Два
  файла схемы, для SQLite и для PostgreSQL; SQL, зависящий от диалекта, живёт только в них [41][76].
- **Жизненный цикл задачи хранится в базе** [78]:
  - состояния: `queued`, `created`, `dispatching`, `running`, `awaiting_permission`, `stopping`, `completed`,
    `failed`, `stopped`, `timed_out`;
  - конечное состояние неизменно: побеждает первая запись;
  - строка Session — более грубая проекция и одновременно барьер приёма новых задач. Флаг `ready_for_prompt` служит ещё
    и флагом внимания; читать его как «можно писать prompt» нельзя.
- **Позиции на board** — `board_objects.data = {position:{x,y}, zone_id?}` [114].
- **Лимиты записи.** 800 000 байт на запись сообщения executor-ом; 250 KiB на превью diff [44].
- **Контекст агента.** Compaction делают SDK [95][96]. Интерфейс показывает оценку заполнения контекста и tokens с
  долларами на prompt [45][54]. У Claude — варианты контекста 200k и 1M [44][66].
- **Knowledge** — namespaces, версии, ссылки и поиск. Семантический поиск — embeddings OpenAI в pgvector на PostgreSQL
  [91][115].
- **Память teammate** — markdown в его branch плюс Knowledge как основное хранилище. Backup в git Knowledge не
  включает [47].
- **Очередь переживает перезапуск** [78][79].

- **Встроенного нет ничего.** Нет test runner, нет приёма статусов CI (кода для `check_run` и `check_suite` нет), нет
  review-агента, нет merge gate [128].
- **GitHub — это канал чата.** Connector GitHub опрашивает @-упоминания в issues и PR (по умолчанию каждые 15 s) и
  отвечает от имени GitHub App [113].
- **Проверка живёт в prompt-ах** [42][121][129]:

  - heartbeat teammate запускает `gh pr checks` и двигает branches между zones.
- **Health environment.** Daemon опрашивает health URL. Успешный Start не значит, что приложение готово [55].
- **Artifacts.** Агент может прочитать DOM своего приложения через `agor_artifacts_query_dom` [52].
- **Порядок работы как соглашение.** Bug Basher описывает проверки — root cause, reviewer только для чтения, падающий
  test, сверку с git, PR и CI — как свой порядок работы, а не как функцию продукта [19].
- **Review в самом репозитории.** PR Agor размечены labels AI-review по моделям [73].
- **Известная дыра.** Issue #2063 (2026-07-28, открыт): отказ в вызове инструмента внутри subagent не оставляет
  ошибки, и родитель сообщает об успехе [130 #2063].

### Восстановление после сбоев

- **Два отдельных сигнала здоровья** [78][103]:
  - heartbeat обёртки — каждые 10 s; устаревшим считается не раньше чем через 30 s и три интервала;
  - «pulse» от SDK — `sdk_started`, `progress`, `waiting`, `unknown_activity`.
- **Watchdog по умолчанию** [78][103]:
  - режим `observe` — только записывает, что сработал бы;
  - первый прогресс ждут 180 s;
  - у Claude простой после прогресса — до 1 часа;
  - на мягкую остановку — 15 s;
  - на подключение при запуске — 5 min;
  - Cursor к watchdog не подключён.
- **Termination coordinator — один владелец остановки** [78]. Он обрабатывает Stop пользователя, timeout старта,
  потерю heartbeat, сбой здоровья SDK, SIGTERM и SIGINT, отзыв доступа и отказ в запуске.
  - Он записывает в базу состояние `stopping`; executor прерывает SDK и сообщает, что затих.
  - Локальный executor: 250 ms на добровольную остановку, потом проверка, что группы процессов больше нет, потом
    SIGTERM → SIGKILL.
  - Удалённый executor: 15 s плюс необязательная команда очистки от оператора [62].
  - Если остановку подтвердить нельзя, session остаётся закрытой для prompt-ов. Пользователь может нажать «Retry
    cleanup». Последнее средство — владелец или admin набирает `STOP` и выбирает «Reopen anyway»: задача помечается
    failed без доказательства, что процесс завершился [44][78].
  - Метрика `executor.cleanup_failures` считает неудачные очистки [62].
- **Автоматического повтора нет — намеренно.** Инвариант в design doc: надзор не означает автоматического повтора,
  повторной отправки prompt-а или гарантии ровно одного внешнего эффекта [78]. Следствия:
  - приём prompt-а не повторяется даже при deadlock [79];
  - Start, Stop и Nuke environment не повторяются [55];
  - очистка не повторяется [62];
  - пропущенные в режиме HA ответы на запросы разрешений не переотправляются [61].
- **Восстановление руками** [78][98][99]. Resume отправляет фиксированный текст: продолжи прерванную задачу, но
  сначала проверь её состояние. Try again повторяет исходный prompt, только если запуск не начался и prompt набирал
  сам смотрящий.
- **Перезапуск daemon** [78][79]:
  - одиночный daemon отпускает осиротевшие задачи как stopped и помечает, что остановка не проверена;
  - на общем PostgreSQL daemon никогда не считает работу другой копии осиротевшей;
  - очередь переживает перезапуск.
- **Открытые issues о надёжности:**
  - #1809 — supervisor heartbeat помечает занятые, но живые sessions как failed. Issue открыт. По заметкам об
    отзывах, главная причина — token, который истекал через 15 минут, — уже исправлена [130 #1809];
  - #2067 — ходы навсегда висят в «running», если не пришло уведомление о фоновой задаче [130 #2067];
  - #2052 — падение executor-а gateway не доходит до Slack [130 #2052];
  - #2030 — timeout clone оставляет осиротевший процесс git [130 #2030].
- **Как было раньше.** В январе 2026 пользователь упёрся в idle timeout 300 секунд у Claude SDK [130 #505]. Сегодня
  watchdog по умолчанию только наблюдает, а допустимый простой у Claude — 1 час [78][103].

### Лимиты и стоимость

- **События лимитов.** События Claude `rate_limit_event` со статусом `allowed_warning` или `rejected` сохраняются как
  системные сообщения с `resetsAt` и данными об overage (работе сверх лимита). Обычные `allowed` скрыты [95][96].
  Баннер хода — `<agent> usage limit reached. Try again after <time>`; Resume появляется только после времени сброса
  [98].
- **Категории ошибок — только для диагностики.** 429, 5xx/529, бюджет и лимит ходов размечены. Комментарий в коде
  говорит: ни одна категория не даёт права на повтор или на восстановление учётных данных [97].
- **Чего нет в коде:** автоматического ожидания сброса и продолжения, счётчиков использования подписки, лимитов
  бюджета. Искали `resetsAt`, `utilization`, `max_budget` [128].
- **Открытые issues:** #1897 — лимит заканчивает ход, session простаивает, никто не ждёт сброса и не повторяет;
  #2097 — нет счётчика использованной квоты плана на пользователя [130 #1897, #2097].
- **Свои ключи.** Ключи и подписки у каждого пользователя свои; участники команды могут их смешивать [22][58].
- **Стоимость** [45][109][111][118][119]:
  - Claude — `total_cost_usd` из result SDK;
  - Codex — оценка по встроенному снимку цен OpenAI из LiteLLM (библиотека с таблицами цен моделей), потому что SDK
    Codex стоимость не сообщает;
  - сервис `/leaderboard` группирует tokens и стоимость по пользователю, branch, репозиторию, модели и агенту, по
    часам, дням, неделям и месяцам; наружу он выведен через `agor_analytics_leaderboard`.
- Страницу «Settings → Analytics» из документации в коде интерфейса найти не удалось — не подтверждено [45][128].
- **Ограничения на уровне всей системы.** Эссе 2025 года просит бюджеты tokens, лимиты параллельности и circuit
  breakers [8]. Cloud называет «usage tiers & quotas» на команду [2]. Есть ли такие ограничения в CE — не
  подтверждено.

### Права и безопасность

- **RBAC приложения** [58][85]:
  - роли board: Viewer, Editor, Manager;
  - роли branch: Viewer, Collaborator, Manager, плюс доступ к файлам `none`, `read` или `read/write`;
  - новые boards приватные;
  - чтобы писать в чужую session, нужны два разрешения; sessions «execution-home» никогда не бывают общими.
- **Режимы разрешений** — свои у каждого harness; значения по умолчанию — в разделе «Функции» [102].
- **Интерактивное одобрение у Claude** [100][101]:
  - `canUseTool` из SDK → задача и session переходят в `awaiting_permission` → карточка в интерфейсе Agor;
  - ждут 10 минут (`600_000` ms), потом задача — `timed_out`;
  - «Remember» пишет решение в файлы настроек Claude — project, user или local;
  - собственные MCP tools Agor одобряются автоматически. Tools подключённых MCP servers — тоже, если их
    `tool_permissions` не говорят `ask` или `deny`.
- **Дыра для запусков без человека.** Issue #2062 (2026-07-28, открыт): sessions по расписанию в режиме `auto` всё
  равно поднимают запросы на Bash. На instance самой Preset — около 20 в день, и каждый выжидает полные 600 s. Автор
  issue пишет, что в системе нигде нет понятия «к session не подключён оператор» [130 #2062].
- **Безопасность MCP** [53][80]:
  - короткоживущий JWT привязан к session, пользователю, tenant и задаче; передаётся только в header Bearer;
  - блок prompt provenance (откуда пришёл prompt) не считается одобрением человека.
- **Расписания** работают от создателя; его права перепроверяются при каждом запуске [48].
- **Codex** не видит учётных данных MCP Agor в своих shell [92].
- **Web.** CSP и CORS настраиваются; `safeOutboundFetch` не ходит на приватные адреса [84].
- **Режим simple** даёт агентам и терминалам читать конфигурацию, секреты и API keys daemon; master secret не
  ротируется [29].

- Запросы разрешений и picker zone [42][100].
- Формы для секретов и OAuth: значения не попадают в контекст агента, а после заполнения агент продолжает сам

- Уведомлений ОС нет: issue #104 открыт с 2025-11-06 [130 #104].

### Observability

- Метрики StatsD: число запусков и время от запроса до запуска и до подключения [112].
- Datadog APM — только если установлен `dd-trace` [112].
- `AGOR_LOG_FORMAT=json` пишет по строке на каждый вызов log, с id tenant, пользователя, session, задачи и branch
  [66].
- Продуктовая аналитика на Segment [66].
- Health endpoints `/livez`, `/readyz`, `/health` [41].

### Источники событий: scheduler, gateways, environments

- **Scheduler** [48][106]:
  - daemon проверяет расписания каждые 30 s (по умолчанию) индексированным запросом `findDue`;
  - одно расписание на branch; каждый запуск — новая session `Scheduled: <branch>`;
  - защита от дублей — время запуска, округлённое до минуты, плюс уникальный индекс; окно — 2 минуты;
  - после простоя срабатывает только последний пропущенный слот;
  - про `allow_concurrent_runs` заметки пишут: запуск по cron при занятой session молча пропускается;
  - хранится N последних sessions; время — только UTC.
- **Gateways** (Slack, Discord, Teams, GitHub, Shortcut) [49][113]: тред платформы — одна session; отправитель
  сопоставляется по email, или задан фиксированный пользователь «run as»; настройки агента — на канал.
- **Environments** [55]: варианты `.agor.yml` v2 с командами start, stop, nuke, logs, health, app; Handlebars с
  математическими helpers; режим только с webhook; проверка итоговой команды по deny list.

- `docker compose` падает на свежем clone (#248);

- ошибки миграции базы после обновления (#478);

- «Getting started fails»: ошибки clone репозитория не доходили до интерфейса (#862);

**C. Учётные данные git и приватные репозитории** [130]:

- самая обсуждаемая тема пользователей — приватные репозитории (#88). Daemon отключал git credential helpers, и
  пользователям приходилось вписывать personal access token прямо в URL. Один пользователь видел «repo added», хотя
  репозиторий не добавился;
- позже приватные репозитории тихо падали при вызове через MCP (#1126);
- sessions не могут сделать `git push`, даже если token задан на уровне daemon (#2024, открыт);
- clone больших репозиториев обрывается по timeout примерно через 5 минут и оставляет осиротевший процесс git (#2030,
  открыт).

**D. Долгие запуски без присмотра умирают** [130]:

- #2817: первая session teammate упала, потому что Agor потерял связь с executor (процессом, который выполняет prompt

- #1809 (от сотрудника): sessions, которые реально работали, помечались failed. Главная причина — token, который
  истекал через 15 минут, — исправлена.

### Истории неудач

- **17 sessions Ferree на одной branch** [144]. Orchestrator застрял на ошибках разрешений, daemon упал. Ferree
  переключился в yolo. Тогда orchestrator решил, что branches уже есть, и направил все 17 sessions в один worktree.
  Они мешали друг другу: меняли одни и те же файлы и ломали tests. Перенос работы на отдельные branches запустил
  циклы, которые израсходовали его лимит Claude.
- **Зависший ноутбук** [130 #133]. Экземпляр Codex SDK создавался на каждый prompt и не убирался; дочерние процессы
  копились. Исправлено в тот же день.
- **Потерянный prompt** [130 #180]. Сброс интерфейса стёр длинное сообщение, которое пользователь набирал.
- **Убитые долгие сборки и tests** [130 #505, #2006, #2817]: idle timeout SDK 300 секунд, предполагаемый сон Mac,
  потеря связи с executor.
- **Production instance Preset** [130 #3079]. Branches, застрявшие в «deleting», навсегда засоряли boards. Исправление
  сократило один шаг удаления примерно с 5.5 минуты до 15 секунд — в тесте на заранее заполненных данных.

### О каких результатах сообщают

- **Ferree:** недели backlog-а меньше чем за полчаса. Каждое изменение он всё равно смотрит и сливает руками, на
  своей branch [144].
- **Рабочий процесс maintainer-а** [131 #491]: один board на репозиторий; 5–10 агентов параллельно; branches между
  zones он двигает руками; несколько экспериментальных агентов по расписанию. Работать полностью без присмотра, по его
  словам, с нынешними моделями пока нельзя.
- **Как строили.** Agor собран на самом Agor меньше чем за месяц, примерно до v0.4 — заявление основателя [5][133].
- **Внутри Preset (данные вендора):**
  - PR в dbt с тремя core-моделями занял около часа времени reviewer-а [35];
  - анонс Cloud признаёт, что AI teammates всё ещё ошибаются, и советует начинать с некритичной работы [37].

## Пересечение с worfy

Термины worfy в этом разделе — по описанию worfy:

- Canvas — бесконечное полотно, на котором worfy показывает работу агентов.
- Epic — группа связанных Ticket-ов. Ticket — одна задача.
- Orchestrator — session, которая планирует и раздаёт работу.
- Wave — набор Ticket-ов, которые запускаются вместе. Autopilot — запуск Waves без человека.
- Gate — локальный запуск проверок для Ticket.
- Harness — plugin, который приносит в Claude Code rules, skills, subagents и hooks.
- Flight Recorder — история запусков Autopilot. Её собирают из журнала Autopilot, транскриптов, GitHub и логов gate.
- Work track — лента всей работы проекта на машине за день, неделю или месяц: запуски, Waves, turns sessions, запуски
  gate, слитые PR и часы по Epic-ам.
- Product Session — продуктовый советник с живым Mind map и критиком spec.
- Linked machines — машины, связанные по локальной сети.
- Evidence screenshots — скриншоты-доказательства с privacy scrub (удалением личных данных).
- Eco mode — настройка проекта: на Ticket работает меньше агентов, а subagents идут на более дешёвых моделях.

## Механизмы, которые стоит изучить

1. **Два сигнала здоровья и watchdog, который сначала только наблюдает.**
   - Что это: Agor отдельно следит, жив ли процесс-обёртка и идёт ли работа в SDK [78][103].
   - Как работает: heartbeat обёртки — каждые 10 s; устаревшим он считается не раньше чем через 30 s и три интервала.
     Отдельно SDK шлёт «pulse»: `sdk_started`, `progress`, `waiting`, `unknown_activity`. Watchdog по умолчанию в
     режиме `observe` — только записывает, что сработал бы. Пороги: первый прогресс — 180 s, простой Claude после
     прогресса — 1 час, мягкая остановка — 15 s, подключение — 5 min [78][103].
   - Чем интересно: зависший процесс и долгий живой ход различаются по разным сигналам. Пороги можно сначала
     проверить на реальных данных, не убивая работу.
2. **Один владелец остановки и проверка, что процесс правда остановлен.**
   - Что это: termination coordinator — все причины остановки идут через один путь [78].
   - Как работает: координатор пишет в базу `stopping`; executor прерывает SDK и сообщает, что затих. Локально — 250
     ms на добровольный выход, проверка, что группы процессов больше нет, потом SIGTERM → SIGKILL. Удалённо — 15 s и
     команда очистки от оператора. Пока остановка не подтверждена, session закрыта для prompt-ов: «Retry cleanup» или,
     в крайнем случае, `STOP` → «Reopen anyway» с пометкой failed [44][62][78]. Каждый heartbeat заново проверяет
     права, и потеря доступа идёт тем же путём [59][78].
   - Чем интересно: новый prompt не попадает в session, где старый процесс, возможно, ещё пишет в файлы.
3. **Строгий исход хода и ручное восстановление с фиксированным текстом.**
   - Что это: правила, когда ход Claude считается завершённым, и две кнопки восстановления [78][98][99].
   - Как работает: ход завершён только сообщением result; `is_error: true` — сбой даже при subtype `success`; поток
     без result — сбой, если его не прервали. Resume отправляет новый prompt: продолжи, но сначала проверь состояние
     прерванной задачи. Try again повторяет исходный prompt, только если запуск не начался и prompt набирал сам
     смотрящий. Повтор никогда не бывает автоматическим [78][98][99].
   - Чем интересно: исход хода не зависит от догадок, а повторная отправка не дублирует уже сделанные внешние
     действия.
4. **Очередь задач в базе: одна задача на session и захват без лидера.**
   - Что это: устойчивая очередь prompt-ов, которая переживает перезапуск и работает на нескольких daemon-ах
     [61][79].
   - Как работает: не больше одной выполняемой Task на session. Tasks в очереди — строки с `queue_position`, их
     принимают под блокировками Branch → Session; запустить может только голова очереди, и у захвата один
     победитель. Каждый daemon запускает `SessionQueueWorker` без выбора лидера и без lease: до 250 sessions за проход, пауза
     около минуты, запуск решает захват строки в базе. Перестановка очереди требует точной перестановки текущего
     порядка, остановка — `expectedTaskId` [53][61][79].
   - Чем интересно: правка очереди и Stop не задевают задачу, которую пользователь не видел, а гонки решает база.
5. **Callbacks от дочерних sessions.**
   - Что это: отчёт ребёнка родителю без блокировки родителя [44][80].
   - Как работает: ребёнок шлёт статус, summary, число вызовов инструментов и, по желанию, последнее сообщение. Если
     родитель занят, callback ждёт в его очереди. Режимы `once` и `persistent`; persistent позволяет цепочки C → B →
     A. Callback принимается после записи задачи ребёнка в базу; exactly-once документация прямо не обещает [44][80].
   - Чем интересно: оркестратор не опрашивает детей, а получает итог как обычный prompt в свою очередь.
6. **Статичный system prompt ради cache и живой контекст через MCP.**
   - Что это: неизменная ориентация отделена от меняющегося состояния [89][91].
   - Как работает: к preset `claude_code` добавлены статичная ориентация Agor и блок личности session. Ориентацию
     держат неизменной, чтобы префикс prompt-а кэшировался у провайдера. Текущее состояние агент берёт сам, через
     `agor_sessions_get_current_context` [89][91].
   - Чем интересно: cache prompt-а не сбрасывается при каждом изменении состояния приложения.
7. **Снятие инструментов Claude и выключение multi-agent у Codex.**
   - Что это: Agor убирает у агентов функции, которые конфликтуют с его собственными [90][92].
   - Как работает: у Claude сняты `AskUserQuestion` (зависал в Slack), `ExitPlanMode`, `EnterWorktree`,
     `ExitWorktree`, `ScheduleWakeup`; список сливается с deny list пользователя. Принудительно включены
     `TaskCreate`, `TaskUpdate`, `TaskGet`, `TaskList` для to-do. У Codex выключен `features.multi_agent`, включён
     `update_plan`, plugins выключены, переменные с учётными данными MCP обнулены в его shell [66][90][92].
   - Чем интересно: агент не может уйти из своего worktree, задать вопрос, на который некому ответить, или запустить
     невидимых субагентов.
8. **Spawn через служебный prompt родителю.**
   - Что это: кнопка в интерфейсе не создаёт дочернюю session сама [44][108].
   - Как работает: она рендерит шаблон из `spawn-subsession-template.ts`, который велит родительскому агенту вызвать
     `agor_sessions_spawn`. Какой контекст передать ребёнку, решает родитель [44][108].
   - Чем интересно: brief для ребёнка пишет агент, который знает контекст, а не интерфейс.
9. **Zone как триггер: шаблон prompt-а срабатывает при переносе карточки.**
   - Что это: положение карточки на полотне запускает действие [42][107].
   - Как работает: zone хранит шаблон Handlebars с переменными branch, board, session, environment и репозитория. При
     переносе — picker (Prompt, Fork или Spawn) или всегда новая session. Шаблоны рендерит daemon [42][84][107].
     Агенты тоже двигают карточки — через `agor_branches_set_zone` [80].
   - Чем интересно: этапы процесса видны как области полотна, и менять их может сам агент.
10. **MCP с прогрессивным поиском инструментов и token на задачу.**
    - Что это: около 150 tools, видимых через три [53][109][128].
    - Как работает: `tools/list` показывает только `agor_search_tools`, `agor_get_tool_details`,
      `agor_execute_tool`. Token — короткоживущий JWT, привязанный к session, пользователю, tenant и задаче; он идёт
      только в header Bearer, а с PR #3246 не попадает в аргументы и окружение агента. Выходной шлюз MCP сам
      подставляет headers и перепроверяет права перед каждым внешним вызовом. Prompt provenance не считается
      одобрением человека [53][75 #3246][80][83].
    - Чем интересно: большой набор tools не раздувает контекст, а утёкший token работает только в одной задаче.
11. **Формы для секретов вне контекста агента.**
    - Что это: in-conversation widgets [50].
    - Как работает: агент рисует форму для переменных окружения, OAuth или tokens gateway. Значения идут из браузера
      прямо в daemon и в контекст агента не попадают; после заполнения агент продолжает сам [50][91].
    - Чем интересно: агент может попросить секрет, не увидев его.
12. **Учёт событий лимита и цены по данным SDK.**
    - Что это: Agor хранит то, что сообщает SDK, и не выдумывает недостающее [95][96][97][98][118][119].
    - Как работает: `rate_limit_event` со статусом `allowed_warning` или `rejected` сохраняется с `resetsAt` и данными
      overage; Resume появляется после времени сброса. Ошибки 429, 5xx/529, бюджета и лимита ходов размечены только
      для диагностики. Цена Claude — `total_cost_usd` из SDK; цена Codex — оценка по встроенному снимку цен LiteLLM,
      потому что SDK Codex её не сообщает [95][96][97][98][118][119].
    - Чем интересно: время сброса лимита уже приходит в событиях SDK, а для Codex нужна своя таблица цен.
