- **Дата:** 2026-11-13. Документация Anthropic прочитана в этот же день.
- **Сайт:** https://claude.ai/code — веб-интерфейс. Документация: https://code.claude.com/docs/en/claude-code-on-the-web (cloud sessions) и https://code.claude.com/docs/en/claude-projects (Projects) [2][1].
- **Что входит в досье и как это сейчас называется:**
  - **Cloud session** — сессия Claude Code на VM, которой управляет Anthropic, или на self-hosted runner организации. Она продолжает работать, когда ноутбук закрыт [2]. Раньше продукт назывался «Claude Code on the web». Теперь так называют только веб-интерфейс на claude.ai/code [2][46]. Внутреннее имя — Claude Code Remote, сокращённо CCR [54][23].

  - **Cloud scheduled tasks** — сохранённый prompt, который запускается по расписанию, вызову API или событию GitHub. Раньше они назывались routines. Старое имя осталось в части URL, alias-ов CLI и путей API [4].

## Модель работы

- **Cloud по умолчанию, с hybrid-вариантами.**
  - Сессия работает на VM Anthropic или на self-hosted runners организации. Runner — процесс в сети клиента, который забирает сессии из очереди [2][19].
  - Control plane — очередь сессий, интерфейс claude.ai и хранение transcript — всегда у Anthropic, даже при self-hosted [19].
  - Thread в Projects может работать на компьютере пользователя через Remote Control. Remote Control — режим, в котором claude.ai и телефон управляют сессией на машине пользователя [1][6].
- **Откуда запускают:** браузер (claude.ai/code), вкладка Code в приложении Claude для iOS и Android, Desktop (выбор Cloud environment), терминал (`claude --cloud`), cloud scheduled tasks [2]. `--remote` — устаревший alias для `--cloud` [2]. Мобильное приложение — только клиент, код там не выполняется [11].
- **Desktop:** macOS (universal build), Windows x64 и ARM64, Linux beta через apt или .deb [12].
- **Projects:** только claude.ai/code, вкладка Code в Desktop и мобильное приложение. Не работают в CLI, VS Code, JetBrains и через Bedrock, Agent Platform или Foundry [1].
- **Агенты:** только Claude Code. Cloud sessions требуют аккаунт Anthropic и не работают через сторонних провайдеров [2][7]. Threads используют Anthropic как провайдера модели [1]. Self-hosted runners могут отправлять inference в Bedrock или Agent Platform [19]. Поддержки агентов других вендоров не найдено (не подтверждено).
- **Модели:** в API по умолчанию Opus 5.5, Sonnet 5.5 и Haiku 5.5. Старшая модель — Fable 5.2 [34]. На Max и Ultra Fable можно тратить до половины недельного лимита [49]. В Projects по умолчанию везде Opus [1]. Классификатор auto mode в посте 2026-03-25 работал на Sonnet 4.6 [56]. Текущая документация называет моделью классификатора по умолчанию Sonnet 5, а в cloud sessions на VM Anthropic действия проверяет сервер [36].
- **Один человек или команда:**
  - Project принадлежит одному владельцу. Sharing и контроля организации в beta нет [1]. Cloud scheduled tasks принадлежат одному аккаунту и работают от его имени [4].
  - Для команд есть: видимость Team у общих сессий [2]; общие environments организации и environment по умолчанию [3]; переключатель «Quick setup» [2]; права в custom roles для cloud sessions, scheduled tasks и Remote Control [2][4][6]; Code Review [14]; self-hosted environments [19]; GitHub Enterprise Server [29].
  - Командный продукт Anthropic — Claude Tag, агент организации в Slack. Projects — для одного человека [1][18].

## Функции

### 1. Cloud sessions: запуск

- **Репозиторий и ветка.** На вебе и в мобильном приложении пользователь выбирает репозиторий и ветку. В одну сессию можно добавить несколько репозиториев [5]. При этом issue #23627 (просьба о сессиях с несколькими репозиториями, 90 👍) в обзоре мнений значится открытым [76]. Источники расходятся.
- **Режимы прав.** Auto (действия одобряет модель-классификатор), Accept edits и Plan. Режимов Manual и Bypass нет [5][36].
- **URL-параметры.** `prompt`/`q`, `prompt_url`, `repositories`/`repo` и `environment` заполняют новую сессию. Их делают для кнопок в issue trackers [5].
- **Onboarding.** Подключает GitHub и создаёт environment «Default» с сетью Limited. В Team и Enterprise Owner должен сначала включить GitHub connector [5].
- **Параллельные сессии из терминала.** Каждый вызов `claude --cloud` создаёт отдельную параллельную сессию. CLI показывает живой checklist подготовки VM и ставит в очередь сообщения, набранные в это время [2].
- **Сессия не зависит от вкладки.** После закрытия вкладки она доводит задачу до конца и переходит в idle [5].

### 2. Cloud sessions: environment и VM

- **VM:** Ubuntu 24.04, x86_64, примерно 4 vCPU, 16 GB RAM, 30 GB диска [3].
- **Что установлено** [3]: Python с uv, poetry, pytest и ruff; Node 20–22 с pnpm, yarn и bun; Ruby; PHP 8.3; Java 21; Go; Rust; GCC и Clang; Docker и docker compose; PostgreSQL 16 и Redis 7 (по умолчанию не запущены); Chrome for Testing; git, gh, jq, ripgrep, tmux.
- **Shell для пользователя нет.** Все команды выполняет Claude [3].
- **Уровни сети** [3]:
  - None, Limited или Full. Limited — большой allowlist по умолчанию (registries пакетов, GitHub, cloud SDK) плюс свои домены.
  - GitHub, трафик MCP connectors и API Anthropic идут мимо allowlist.
  - Изменения доходят до работающих сессий примерно за минуту.
- **Network secrets.** API key хранится в environment. Proxy добавляет его к запросам на указанные hosts, в VM ключ не попадает. Функции нет в self-hosted environments и при CMEK [3].
- **Переменные окружения** в формате `.env`. Их видит любой, кто пользуется этим environment [3].
- **Setup script** [3]: bash-скрипт от root, выполняется до старта Claude. Файл, который загружают кнопкой Choose file, — до 64 KB; общий предел размера скрипта документация не называет. Если скрипт укладывается примерно в 5 минут, файловая система сохраняется в snapshot и переиспользуется. Snapshot пересобирается при изменении скрипта или allowlist либо примерно через 7 дней.
- **Таймауты** [3]: команда на переднем плане — 2 минуты по умолчанию, максимум 10. Команда, которая не уложилась, уходит в фон ещё на 30 минут. SessionStart hooks — 600 секунд.
- **Простой** [2][3]: через несколько минут простоя VM встаёт на паузу, файлы сохраняются. Приостановленную VM могут забрать. Тогда при открытии сессии восстанавливается разговор, но не shell-команды, subagents, расписания внутри сессии и `/loop`. Сессия, которая ждёт одобрения MCP connector, считается простаивающей и может истечь.
- **Личные настройки не переносятся** [3]:
  - `~/.claude` пользователя — settings, skills, MCP servers, plugins — в облако не попадает.
  - Из репозитория грузятся CLAUDE.md, `.claude/rules`, skills, agents и commands. Hooks и permissions из `.claude/settings.json` и `.mcp.json` — только в сессиях с одним репозиторием.
  - Plugins, объявленные в репозитории, не устанавливаются. Skills, включённые в аккаунте claude.ai, грузятся. Серверные managed settings организации действуют.
- **Environments организации.** Owners в Team и Enterprise делятся environments со всей организацией и задают environment по умолчанию [3].
- **`/remote-env`** выбирает environment по умолчанию для сессий, запущенных из CLI [3].

### 3. Cloud sessions: GitHub

- **Два способа подключения** [2]:
  - Claude GitHub App: любые публичные репозитории и приватные, где App установлен. Он нужен для auto-fix и Projects.
  - `/web-setup`: загружает локальный token `gh`. Доступны все репозитории, которые видит этот token.
- **GitHub proxy** [2][3]: credential хранится на серверах Anthropic. Proxy подменяет ограниченный credential настоящим token. Он отклоняет удаление веток и push тегов, отдаёт API только для репозиториев сессии и отклоняет весь GraphQL. Поэтому `gh pr` и `gh issue` не работают, и Claude пользуется REST-вызовами через `gh api` [3].
- **Встроенные GitHub tools** читают issues и PR, получают diff и пишут комментарии [3].
- **GitLab, Bitbucket и другие hosts** [2]: `claude --cloud` с переменной `CCR_FORCE_BUNDLE=1` загружает git bundle меньше 100 MB. Без этой переменной bundle загружается сам, только если у репозитория нет remote или на github.com-репозитории не установлен Claude GitHub App. Если bundle не помещается — только текущую ветку или squash-snapshot. Незакоммиченные изменения в `.env`, ключах и файлах credentials не загружаются (macOS, Linux и WSL; в нативном Windows загружаются как есть). Результат нельзя запушить обратно на этот host.
- **GitHub Enterprise Server** для Team и Enterprise: cloud sessions, teleport, Code Review [29].

### 4. Перенос между терминалом и облаком

- **В облако.** `claude --cloud "<задача>"` клонирует remote на текущей ветке. Из CLI перенос только в эту сторону. В Desktop кнопка **Open in > Cloud** переносит локальную сессию в облако с пересказом разговора [2][12].
- **Follow-up из скриптов.** `claude -p "msg" --cloud <session-id>` ставит сообщение в очередь сессии с любой машины, где выполнен вход, и завершается. `--output-format json` возвращает `{ok, session_id, url}`. Подходит для CI-скриптов [2].
- **Teleport** — перенос cloud session в локальный терминал [2]:
  - `claude --teleport [id]`, `/teleport` (`/tp`), клавиша `t` в `/tasks` или «Open in > Terminal» на вебе.
  - Нужны чистое состояние git, тот же репозиторий (не fork), запушенная ветка и тот же аккаунт.
  - Терминал получает свою копию сессии. Дальнейшая локальная работа обратно не синхронизируется.
  - Сообщения, которые уже убрал compaction (сжатие контекста), не переносятся.

### 5. Внутри сессии

- **Карточка Changes** [2][5]: счётчики строк +/− и diff view. Комментарии к строкам собираются в следующее сообщение. «Compare against» сравнивает с любой веткой. Кнопки **Create PR** и **Create draft PR**.
- **Управление** [2][48]: забрать сообщение из очереди; вернуться к более раннему сообщению (rewind); поменять environment у работающей сессии; загрузить файлы.
- **Команды.** Работают команды, которые печатают текст. `/model`, `/effort` и `/rename` принимают аргументы. `/fast` требует v2.1.271 [2].
- **Ранний compaction.** Сессия сама задаёт `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, поэтому контекст сжимается раньше, чем в CLI [2].
- **Subagents** работают. Agent teams — ведущий агент и teammates с общим списком задач — включаются переменной окружения [2][39].
- **Предложение plugin.** Claude может показать карточку plugin с кнопкой **Add**. Чтобы её отключить, запрещают tools `SearchPlugins` и `SuggestPluginInstall` [2].
- **`/goal`** — работать, пока не выполнится условие. Cloud sessions восстанавливают auth, поэтому goal не сбрасывается [25].
- **Напоминание закоммитить.** В сессиях на VM Anthropic Stop hook (hook на окончание ответа) просит Claude закоммитить и запушить [20].

### 6. Auto-fix для PR

- **Что делает** [2]: Claude подписывается на события PR в GitHub. Когда падает CI или приходит review comment, он разбирается и пушит исправление, если оно очевидно.
  - Если комментарий двусмысленный или касается архитектуры, сначала спрашивает.
  - Повторные события отмечает и пропускает.
  - Отвечает в review threads от GitHub-аккаунта пользователя с пометкой Claude Code.
- **Как включить** [2][33]: меню ⋮ у PR в карточке Changes; `/autofix-pr` в CLI (запускает cloud session); просьба с телефона; вставка URL PR. Нужен установленный GitHub App.
- **Ограничения** [2]: на merge conflicts не реагирует — GitHub не шлёт для них webhook. Документация предупреждает: комментарии auto-fix могут запустить automation, которая реагирует на комментарии, например Atlantis.
- **Дата запуска.** Вторичный источник называет март 2026 (не подтверждено) [129]. Дайджест What's new за неделю 2026-03-23…27 упоминает «PR auto-fix on the web» [47].

### 7. Sharing, архив, трассировка, данные

- **Sharing** [2]: в Team и Enterprise — Private или Team, с проверкой доступа к репозиторию (включена по умолчанию). В Pro, Max и Ultra — Private или Public. Расшаренный вид не обновляется вживую.
- **Архив и удаление** [2]: архивные сессии лежат на claude.ai/code/sessions. Удаление необратимо.
- **Трассировка** [3]: в commits добавляется trailer `Claude-Session: <url>`, в описание PR — URL сессии. В сессии заданы `CLAUDE_CODE_REMOTE=true` и `CLAUDE_CODE_REMOTE_SESSION_ID`. Ссылку в commits отключает настройка `attribution.sessionUrl: false` [72].
- **Хранение** [32]: transcripts хранятся у Anthropic 30 дней по умолчанию и 5 лет, если пользователь разрешил обучение. Сессии можно удалять.
- **Сообщения между сессиями** [24]: написать в cloud session можно только из сессии, подключённой к Remote Control. Ответить через `SendMessage` cloud session не может.

### 8. Projects: структура

- **Coordinator** — разговор проекта, одна долгая сессия Claude. На каждое сообщение он [1]:
  - сам отвечает на быстрый вопрос;
  - запускает новый thread или передаёт работу существующему;
  - разбивает несколько задач из одного сообщения на отдельные threads;
  - видит отчёты threads, а не каждый их шаг.
- **Thread** — отдельная сессия со своим context window [1]. Cloud thread работает в своей ветке от ветки по умолчанию. PR он открывает по просьбе или сам, если исправление конкретное [1]. Пересекающиеся правки проявляются как merge conflicts [52].
- **Overview** — панель, где threads сгруппированы по состоянию [1]:
  - Ready for review — PR открыт;
  - Waiting on you — нужен ответ, одобрение, или случился сбой;
  - Working;
  - Landing — PR одобрен или стоит в очереди на merge;
  - Idle;
  - Resolved — закрыт пользователем, самим Claude после последнего шага (например, merge) или автоматически после недели без активности.
- **Точка на кнопке Threads** — какой-то thread ждёт пользователя [1].
- **Library** — файлы, добавленные пользователем, и файлы, которые сделали threads [1].
- **Вид Scheduled tasks** — cloud scheduled tasks, созданные из проекта [1].

### 9. Projects: создание

- **Диалог New project** [1]: имя (обязательно); цель в одну строку («What do you want to work on?»), по желанию; контекст — репозитории GitHub, файлы, папки, папки Google Drive.
- **Continue in project** превращает cloud session в новый проект или переносит её работу в существующий. Подходят и локальные сессии Remote Control, если не включено «Require trusted devices» [1].
- **Первый ход Claude** на первом проекте [1]: может запустить read-only thread, который изучает репозиторий. Публикует **Setup recommendations** по недавним cloud sessions: репозитории, scheduled tasks и threads для запуска. У каждого пункта переключатель. Применяются кнопкой **Update setup**.
- **Требования** [1]: репозитории на github.com с установленным Claude GitHub App (`/web-setup` недостаточно); право push; SSO-авторизация для организаций, где она обязательна.

### 10. Projects: рабочий цикл

- **Карточки threads.** Каждый новый thread появляется карточкой под сообщением пользователя [1].
- **Suggested threads** — предложенные, но не запущенные threads. У каждого стрелка запуска, есть кнопка «start all» [1].
- **Кнопки на карточке** [1]: **Resolve conflicts**, **Fix CI**, **Address comments** и **Merge it** отправляют эту инструкцию как сообщение пользователя. **Review PR** открывает GitHub. **Create PR** открывает PR из запушенной ветки.
- **Слежение за PR** [1]: после открытия PR thread следит за ним с включённым auto-fix, независимо от настройки аккаунта. Он пушит исправления CI, отвечает на review comments и сообщает, когда checks прошли.
- **Открытый thread** [1]: полный transcript; своё поле ввода для прямого управления; ответы на permission prompts; **Stop** или Esc прерывают работу.
- **Уведомления** [1]: Desktop шлёт уведомления ОС о сообщениях coordinator, ошибках threads и threads, которым нужен ввод. Настройка — на каждый проект, есть вариант «each turn finished». В браузере сигнал один — точка на кнопке Threads.
  - Push на телефон для проектов: описание функций их не подтверждает [1]; обзор принципов говорит, что push-уведомления есть [1][47]; в issue #98655 пользователь просит push о решениях coordinator [92]. Источники расходятся.
- **Управление словами** [1]: «Propose threads and wait», «Run at most two threads at a time», «Only post when something finishes», «Don't open a PR until I've seen the plan». Claude сохраняет такие предпочтения в память проекта. Лимит threads, заданный так, не жёсткий.

### 11. Projects: модели, контекст, одобрения

- **Модели** [1]: по умолчанию Opus везде, effort high у threads и low у coordinator. Модель и effort threads и coordinator — четыре отдельные настройки. Отдельная задача может попросить другую модель.
  - Пользователи пишут другое: выбор effort у coordinator убран, он закреплён на Opus 5.5 с low effort, а cloud threads работают на low даже при настройке high (#106126, #101349) [89]. Источники расходятся.
- **Контекст** [1]: пользователь им не управляет. Threads сжимают контекст сами. Coordinator работает по последним сообщениям, последним threads и памяти проекта, поэтому может работать без конца. Переполненный thread показывает «Claude ran out of context on this turn».
- **Auto mode в threads** [1]:
  - Threads работают в auto mode, если модель его поддерживает.
  - Prompt, которому всё же нужно одобрение, ждёт внутри thread. Слова «go ahead» в coordinator до него не доходят.
  - Одобрение действует на один prompt или на весь остаток thread.
  - Permission rules репозитория не читаются.

### 12. Projects: thread на своём компьютере

- **Запуск** [1]: **Work locally** в меню + или просьба словами. Claude показывает карточку «Allow Claude to work in a folder on your device»: выбрать папку, по желанию включить **Worktree** (свой git worktree для thread), подтвердить **Allow once**.
- **Подключение машины** — заранее, с v2.1.280+ (вышла 2026-09-22) [1][48]: в Desktop — Settings > «Use this computer from your phone and claude.ai», или `claude remote-control [--spawn worktree]`.
- **Локальный thread** [1]:
  - пользуется локальными файлами, tools, MCP servers, hooks и permission rules;
  - получает инструкции проекта, но не файлы памяти;
  - встаёт на паузу, когда компьютер спит; в Desktop есть «Keep this computer awake»;
  - иконка ноутбука показывает состояние связи;
  - недоступен, пока требуются Trusted Devices.

### 13. Projects: постоянный контекст

- **Память проекта** [1]: файлы с индексом `MEMORY.md`. Claude пишет их, когда его просят что-то запомнить или забыть. Каждый cloud thread читает индекс при старте. Файлы правятся в Settings > Memory.
- **Инструкции проекта** — до 16 000 символов. Их получают каждый новый thread и coordinator [1].
- **Репозитории** [1]: каждый новый cloud thread клонирует все репозитории проекта. Thread может посреди задачи добавить ещё один только для себя. Claude добавляет репозитории только от GitHub owners, которых проект уже использует.
- **Загрузки** [1]: до 1 000 файлов и 2 GB за раз, один файл до 480 MB; до 10 папок плюс папки Drive. Загрузки — копии, смонтированные в `/mnt/project-files`.
- **Что cloud threads берут из репозитория** [1]:
  - Только корневой `CLAUDE.md`, `.claude/CLAUDE.md` и `.claude/rules/` без правил для отдельных путей.
  - Не грузятся: skills, agents, commands, `.mcp.json`, plugins, permission rules, hooks, `env`.
  - Замена: skills аккаунта, настройка Plugins проекта, connectors claude.ai (доступны threads; у coordinator их нет), setup scripts.
  - Про AGENTS.md источники расходятся. Один пользователь пишет, что новые threads получают AGENTS.md и «brief» от coordinator [68]. Другой — что threads игнорировали AGENTS.md [86]. В списке документации AGENTS.md нет [1].
- **Проект без репозитория** — для документов и исследований с результатом в Library [1].

### 14. Projects: настройки, управление, расход

- **Settings** [1]: имя, иконка, цель; модель и effort coordinator и threads; инструкции, репозитории, environment, plugins; расход по threads и моделям; файлы памяти; auto-continue при сбросе лимита; **Restart Claude** — если coordinator перестал отвечать.
- **Pause, Archive, Delete** [1]: Pause прерывает всё и останавливает scheduled tasks. Archive архивирует и threads. Delete необратим; ветки и PR на GitHub остаются.
- **Изменения настроек** доходят только до новых threads [1].
- **Расход** [1]:
  - Жёсткий лимит — 500 новых threads в день на все проекты. В материалах о запуске называли 200 [124]. Источники расходятся; вероятно, лимит подняли (вывод).
  - Coordinator тратит свои tokens.
  - Threads, которые следят за PR, просыпаются на события CI и review и снова тратят лимит.
  - На Pro, Max и Ultra prompt cache живёт 1 час. Старый простаивающий thread при пробуждении перечитывает весь разговор.
  - Простаивающий проект ничего не тратит.
- **Ограничения beta** [1]:
  - Один владелец; sharing и контроля организации нет.
  - Threads нельзя переносить между проектами, проекты нельзя объединять.
  - Sandbox cloud thread встаёт на паузу между ходами. Если он не восстановится, thread начнёт со свежего clone, и незакоммиченные изменения могут пропасть.
  - «Reached the turn limit» появляется, если задан `CLAUDE_CODE_MAX_TURNS`.

### 15. Продолжение после лимита подписки

- **Projects** [1]: thread или coordinator, остановленный 5-часовым или недельным лимитом, ждёт и по умолчанию продолжает сам после сброса. Переключатель один на проект — «Auto-continue when usage limits reset», включён по умолчанию. Продолженная работа считается в следующее окно.
- **CLI** с v2.1.234 (2026-08-17): интерактивная сессия на подписке claude.ai ждёт в открытой сессии и после сброса продолжает задачу [9][48].
  - Показывает «Continuing automatically at 3:45pm · Esc to cancel» [9].
  - Последнее сообщение не повторяет, а просит Claude продолжить с места остановки. Permission prompts по-прежнему останавливают задачу [9].
  - Если компьютер спал больше ~30 минут после сброса, нужно нажать Enter [9].
  - Останавливается после трёх автоматических продолжений [9].
  - Сама не начинает ждать, если сброс дальше 24 часов (например, недельный лимит), в сессиях Remote Control и у teammates в agent teams [9].
  - Не предлагается в background sessions, в runs с `-p`, с API keys и через облачных провайдеров [9].
  - Отключается `autoContinueAtUsageLimit: false` [9].
- **Desktop** [8]: на карточке 5-часового лимита есть checkbox «Auto-continue when limits reset». На карточке недельного лимита его нет. Настройка отдельная от CLI.
- **Dynamic workflows** — скрипт, который запускает много subagents. Агенты, упёршиеся в лимит, встают на паузу, новые не запускаются, после сброса работа продолжается (v2.1.271, 2026-09-14) [38][48]. В Desktop — с v2.1.323 (2026-11-12) [48].
- **`/goal`** встаёт на паузу и продолжает после сброса (v2.1.269) [25][48].
- **Retry watchdog для unattended runs** [28][8]:
  - `CLAUDE_CODE_RETRY_WATCHDOG=1` бесконечно повторяет ошибки 429 и 529. Между попытками ждёт до 5 минут или до времени сброса, указанного в ошибке. Так сессия, упёршаяся в лимит, дожидается конца окна [28].
  - Другие временные ошибки — около 300 повторов, примерно 3 часа. Без watchdog — 10 повторов [8].
  - На spend limit или исчерпанных usage credits завершается сразу [28].
  - По умолчанию ожидание сброса ничем не ограничено [8]. `CLAUDE_CODE_RETRY_WATCHDOG_MAX_USAGE_LIMIT_WAIT_MS` (v2.1.301) обрывает запрос, если сброс слишком далеко. `CLAUDE_CODE_RETRY_WATCHDOG_USAGE_LIMIT_RECHECK_MS` (v2.1.305) проверяет, не сняли ли лимит раньше [28][48].
  - Включают ли его cloud sessions — не подтверждено.
- **Предупреждение о расходе** (v2.1.304, 2026-10-19): на планах Pro и Max CLI предупреждает, если возобновление неактивного разговора займёт заметную долю 5-часового лимита [48].
- **Cloud scheduled tasks** [4]: без usage credits лишние runs отклоняются до сброса окна. С credits они продолжаются на платном overage.
- **Ultra** [49][50]: нет 5-часового лимита для verified accounts. Недельный лимит (10x Pro) и отдельный недельный лимит Fable остаются.
- **Отдельные cloud sessions вне проекта:** auto-continue после сброса документацией не подтверждён. Пользователь в issue #106673 пишет, что четыре cloud sessions сами продолжали после каждого 5-часового сброса и тратили новое окно примерно за 10 минут, три раза подряд (не подтверждено) [71].
- **Threads, запущенные routine,** по материалам о запуске Projects сами не продолжались (вторичный источник) [124].
- **История запроса.** Самый популярный запрос об этом — issue #13354 (+212 голосов) — закрыт 2026-10-22 с пометкой «fixed in 2.1.234» [67].

### 16. Cloud scheduled tasks (бывшие routines)

- **Что это** [4]: research preview. Задача хранит prompt, репозитории, connectors, environment, модель и effort.
- **Triggers** — их можно сочетать в одной задаче [4]:
  - **Schedule:** пресеты; cron с минимальным интервалом 1 час; разовые runs, заданные обычной фразой.
  - **API:** POST на endpoint `/fire` с bearer token задачи, ответ — URL сессии. Beta header `experimental-cc-routine-2026-04-01`. Поле `text` приходит обёрнутым в `<routine-fire-payload>` с пометкой «недоверенные данные».
  - **GitHub:** события pull request, release и issue. Фильтры PR — автор, заголовок, текст, base и head ветки, labels, draft, merged, в том числе regex. Нужен GitHub App.
- **Где управлять** [4]: claude.ai/code/routines; вид «Scheduled» в Desktop; `/schedule` в CLI (`list`, `update`, `run` и вопросы об истории runs).
- **Runs** [4]: каждый run — полная cloud session в auto mode. История показывает Succeeded, Failed или Cancelled. Предупреждения «The last run…» объясняют, почему run не стартовал. Ветки — с префиксом `claude/`. Всё делается от имени пользователя.
- **Лимиты** [4]:
  - 100 scheduled runs в час на аккаунт; лишние ждут.
  - 30 в час на задачу для Run now, API fires и разовых повторов; лишние падают.
  - Run now — 100 в час на аккаунт, API fires — 100 в час на аккаунт.
  - Overage на часовые лимиты нет.
  - Без связи с GitHub задача пропускает runs до 72 часов, потом выключается.
  - Задачи принадлежат одному аккаунту и не расшариваются.
- **Дневные лимиты.** На запуске в апреле 2026 блог называл 5, 15 и 25 runs в день (Pro, Max, Team и Enterprise) [55]. Текущая документация даёт только часовые лимиты [4]. Отменены ли дневные — не подтверждено.
- **Admin-переключатель** «Scheduled tasks (Was Routines)» у Owner останавливает все задачи организации [4].
- **Artifacts без вопроса.** Scheduled run может публиковать Artifacts, не спрашивая [4].
- **В проекте** scheduled work становится cloud scheduled task, который запускается как threads этого проекта. Run может продолжить существующий thread [1][4].
- **Сравнение с другим планированием** [27]: cloud tasks не требуют включённой машины. Desktop tasks работают на машине пользователя, минимум 1 минута, если интервал задаёт Claude. `/loop` требует открытой сессии.

### 17. Review кода в облаке

- **Ultrareview** (`/code-review ultra`, alias `/ultrareview`; research preview) [13]:
  - группа агентов-reviewers в cloud sandbox; каждую находку отдельно проверяют;
  - 5–15 минут; лимиты — 500 файлов и 8 000 изменённых строк; принимает номер PR;
  - `--post` публикует находки одним обычным комментарием в PR от аккаунта пользователя;
  - `claude ultrareview` — вариант для CI, exit codes 0, 1 и 130;
  - 3 бесплатных run на аккаунт (один раз), дальше примерно $5–25 за run из usage credits.
- **Code Review** (Team и Enterprise) [14][15]:
  - управляемый reviewer для PR в GitHub и GHES: параллельно найти, проверить, ранжировать, опубликовать;
  - inline-комментарии с severity и check run «Claude Code Review», который никогда не падает и не блокирует PR;
  - запуск — один раз на PR, на каждый push или только по `@claude review` и `@claude review always`;
  - уровни Quick, Standard и Deep; настройка — файл `REVIEW.md` из base-ветки;
  - оплата — usage credits организации, с месячным spend limit и страницей аналитики.
  - Дату запуска называют только вторичные источники — 2026-03-09; сами источники в материалах исследования не названы (не подтверждено).
- **`/ultraplan`** отправлял планирование в cloud session. Он появился в апреле 2026 [47] и сейчас удалён [33].

### 18. Соседние продукты и поверхности

- **Remote Control** [6]:
  - claude.ai/code и телефон управляют сессией на машине пользователя. Машина подключается только исходящими соединениями.
  - Серверный режим `claude remote-control`: `--spawn same-dir | worktree | session`, `--capacity` (по умолчанию 32), QR-код. `--settings` — с v2.1.321 [48].
  - Сессию можно возобновить примерно 4 часа после остановки сервера. Из браузера сессию можно fork.
  - Модель и effort меняются с телефона.
  - Trusted Devices (beta): нужно зарегистрированное устройство и вход не старше 18 часов.
- **Мобильное приложение** [11]: запуск и наблюдение за cloud sessions, проектами и сессиями Remote Control; задачи Dispatch. Push-уведомления описаны для Remote Control и Dispatch. Bypass нет. Каждая машина с `claude remote-control` видна на телефоне карточкой устройства [47].
- **Desktop** [12]:
  - cloud и локальные сессии рядом, split view;
  - карточки «Send to cloud» с предложенными задачами;
  - карточка Changes у PR показывает статус CI, Auto-fix и **Merge when ready** (auto-merge GitHub);
  - auto-archive после merge (только локальные сессии);
  - кольцо расхода лимитов;
  - «Work across sessions» видит только локальные, SSH и WSL сессии Desktop, не cloud.
- **Dispatch** (Pro, Max, Ultra) — постоянный разговор Cowork, в который пишут с телефона. Он может запускать сессии Code в Desktop [12]. Cowork — агент Anthropic для работы не с кодом. 2026-09-16 его объединили с чатом [60].
- **Slack** [16]: старый Claude Code in Slack — для Pro, Max и Ultra в workspaces без Claude Tag. @mention создаёт cloud session; есть View session и Create PR; один PR на сессию; только GitHub. В workspaces с Claude Tag его выключили 2026-10-05.
- **Claude Tag** (Team и Enterprise, public beta) [17]: общий агент организации в каналах Slack. Connectors настраивает admin. Расход идёт с баланса организации со spend limit. Работает в одноразовом sandbox с теми же cloud environments [3] и на том же движке, что cloud sessions [18].
- **Self-hosted environments** (Team и Enterprise, public beta) [19]: runners выполняют сессии в сети клиента и опрашивают Anthropic исходящими запросами. Autoscaling orchestrator — по желанию. Runner принадлежит одному владельцу за раз. Control plane и transcripts остаются у Anthropic.
- **Artifacts** [30]: живые одностраничные HTML-страницы на claude.ai — private, на организацию или public, с версиями. Страница может вызывать MCP connectors от имени зрителя. Есть комментарии, на которые Claude может отвечать сам. Шаблоны Slides, Design и Docs.
- **Agent view** (`claude agents`, локальный research preview) [31]: один экран терминала для background sessions в группах Ready for review, Needs input, Working и Completed. Показывает значки PR и MR, даёт каждой сессии свой worktree. Cloud sessions не показывает.
- **Другие способы параллельной работы** [10][31]: subagents внутри одной сессии; agent view; agent teams (экспериментальные, выключены по умолчанию); dynamic workflows; `/batch` — от 5 до 30 subagents, каждый в своём worktree; Projects.

## Принципы и подходы

### Что говорят создатели

- **Boris Cherny**, создатель и Head of Claude Code [130]:
  - работа с языковыми моделями эмпирическая, ближе к социальным наукам, чем к детерминированной инженерии;
  - Claude Code постоянно добавляет, убирает и переделывает tools по мере роста моделей;
  - продукт начался как эксперимент: модель уже умела больше, чем продукты вокруг неё.
- **Cherny на Fortune Brainstorm Tech** (вторичный источник) [132]: около восьми месяцев не пишет код руками. Claude Code пишет сам Claude Code. Большинство сессий Claude Code запускает другой Claude. Узким местом стал code review: его делает команда Claude-reviewers с разными ролями, а одобряет человек.
- **Cat Wu (продукт) и Thariq Shihipar (инженерия, дизайн tools)**, июль 2026 (вторичный транскрипт) [119]:
  - строить под следующую модель: держать evals и менять модель, только если новая строго лучше; отдельный system prompt на модель;
  - удалять scaffolding (обвязку вокруг модели): system prompt для frontier-моделей сократили примерно на 80%, примеры убрали;
  - меньше запретов, больше контекста;
  - несколько общих и разных tools, опора на bash;
  - dogfooding: функция выходит, только если прошла внутреннюю планку использования и удержания;
  - хороший набор тестов служит спецификацией, и тогда переписывание кода реально.
- **Cat Wu**, май 2026 (вторичный источник) [131]: ориентироваться на рост моделей, а не на конкурентов — погоня за конкурентами оставляет на месяц-два позади. Следующий шаг — проактивность: от синхронной работы к routines, а затем Claude сам замечает, над чем работает человек, и настраивает automation. Люди будут управлять группами агентов и должны оставаться экспертами в своей области, чтобы их отлаживать.
- **Позиция компании** на Code w/ Claude SF 2026: строить в расчёте на быстрый рост возможностей AI и планировать ускорение заранее [61].

### Принципы в документации

- **Значения по умолчанию должны быть правильными.** Обычный prompt в новой сессии должен приводить к правильному результату. Примеры: auto mode по умолчанию, Claude сам делегирует работу subagents, compaction автоматический [45].
- **Два вида инструкций** [45]. Недетерминированные — prompt, CLAUDE.md, skills: модель сама решает, как им следовать. Детерминированные — hooks, deny rules, managed settings: их соблюдение обеспечивает harness. По умолчанию решение оставляют Claude. Детерминированные средства — только для того, что должно происходить всегда или никогда.
- **Сначала проверка, потом автономия.** Нужно дать Claude проверку, которую он может запустить сам. На ней держатся `/goal`, unattended runs и dynamic workflows [45][44]. `/goal` оценивает завершение отдельной моделью-оценщиком, а не самим исполнителем [25].
- **Пять вопросов перед unattended run** [45]: как выглядит «готово»; как агент проверит себя; что ему можно трогать; что его остановит; кто подписывает результат. За человеком три шага: запустить run, определить «готово», одобрить merge.
- **Что можно перестать делать** [45]. Документация отменяет советы, которые нынешним моделям больше не нужны: агрессивное управление контекстом; выделение заглавными буквами; subagents только ради экономии контекста; «think harder» в prompt; prompts вида «keep going»; описание архитектуры в CLAUDE.md.
- **Цикл агента** — собрать контекст, действовать, проверить. Claude Code — «agentic harness» вокруг модели [44][46].

### Принципы облачной архитектуры

- **Изоляция и credentials** [2][3]: у каждой сессии своя VM, сеть по умолчанию Limited. Git credentials и ключи подписи остаются вне sandbox. GitHub proxy подменяет ограниченный credential настоящим token. Network secrets добавляются к запросам после выхода из VM.
- **Одноразовые VM** [3][2]: VM встаёт на паузу через несколько минут простоя, позже её могут забрать. При открытии сессии восстанавливается разговор, но не фоновая работа.
- **Managed Agents** — инженерный пост 2026-04-08 о hosted-агентах Anthropic для разработчиков [58]:
  - session (журнал, в который только дописывают), harness и sandbox разделены стабильными интерфейсами;
  - модель и harness («brain») отделены от sandboxes и tools («hands»);
  - контейнеры одноразовые, credentials не попадают в sandbox;
  - разделение сократило time to first token примерно на 60% на p50 и больше чем на 90% на p95;
  - пост называет Claude Code одним из harness, которые могут работать на этом слое. Работают ли на нём cloud sessions — не подтверждено.
- **Trigger — задание, а не одобрение** [4]: prompt от scheduled trigger — это задание run, а не живой ввод пользователя. Он не может одобрять действия во время run. С 2026-06-19 (v2.1.183) доставки triggers не считаются вводом с клавиатуры [48].
- **Self-hosted как CI runners** [19]: control plane ставит сессии в очередь, runners клиента их забирают. Все соединения исходящие из сети клиента.

### Принципы Projects

- **Разделение труда** [52]: coordinator направляет, threads работают. Каждый thread — полная сессия в своей ветке и своей копии репозитория. Пересечения — обычные merge conflicts. Threads могут делить работу дальше через subagents, loops и workflows. Launch-пост советует объяснять проекту задачу так же, как её объясняли бы своему chief of staff.
- **Контекст накапливается** [52][1]: общая память, которую читают и пишут все threads, уменьшает нужду в prompt engineering. Claude запоминает стиль работы пользователя: как часто отчитываться, запускать threads и публиковать новости. Контекст делится на три слоя: память проекта, инструкции проекта, CLAUDE.md репозитория.
- **Coordinator видит отчёты, а не шаги.** Пользователь не управляет окнами контекста [1].
- **Мягкий контроль по замыслу** [1]: «не больше двух threads» — это инструкция в памяти, а не настройка. Единственный жёсткий лимит — 500 новых threads в день.
- **Проактивность по умолчанию** [1]: на первом проекте Claude делает ход сам — исследующий thread и setup recommendations, всё включено по умолчанию.
- **Работа без присмотра по умолчанию** [1]: threads в auto mode; каждый thread следит за своим PR с auto-fix; Opus везде; auto-continue после лимитов включён.

### Auto mode — автономия без permission prompts

- **Обоснование** (инженерный пост 2026-03-25) [56]: пользователи одобряли около 93% permission prompts — это усталость от одобрений. Sandboxing безопасен, но требует много поддержки. `--dangerously-skip-permissions` не защищает ничем. Классификатор — середина между ними.
- **Устройство** [56]:
  - Три уровня: allowlist безопасных tools и правила пользователя; правки внутри проекта без проверки; всё остальное — классификатору по transcript.
  - Классификатор работает в две стадии: быстрый фильтр в один token, затем рассуждение только по отмеченным действиям. В посте он работал на Sonnet 4.6; по текущей документации модель по умолчанию — Sonnet 5 [36].
  - Он «reasoning-blind»: видит сообщения пользователя и вызовы tools, но не текст Claude и не вывод tools.
  - Отдельный серверный probe проверяет результаты tools на prompt injection до того, как их прочтёт Claude.
- **Опубликованные ошибки** [56]: 0.4% false positives после второй стадии на 10 000 реальных действий; 17% пропущенных «слишком рьяных» действий на 52 реальных случаях — авторы называют это честной цифрой; 5.7% пропущенных синтетических утечек данных.
- **Возврат к человеку** [36][56]: после 3 блокировок подряд или 20 всего auto mode встаёт на паузу, и Claude Code снова спрашивает человека. Пороги не настраиваются. Пост 2026-03-25 писал, что run с `-p` в этом случае завершается [56]. Текущая документация говорит иначе: в run с `-p` без `--permission-prompt-tool` заблокированное действие не выполняется, а Claude продолжает работу [36].
- **Блокировки по умолчанию** [36]: merge PR, который не одобрил человек; одобрение своего PR; отключение CI.
- **Границы из разговора** классификатор перечитывает из transcript каждый раз. После compaction они могут потеряться [36].
- **Где работает.** В cloud sessions на VM Anthropic проверка идёт на сервере. Bypass нет [36].
- **Rollout** [47][56][48]: research preview в марте 2026; Pro — в мае 2026; по умолчанию для новых сессий на Pro, Max и Team с 2026-08-14, тогда же вызовы классификатора перестали тратить лимит; с v2.1.283 (2026-09-25) — стартовый режим интерактивного терминала и VS Code.

### Ключевые понятия

- **Где выполняется:** local session и cloud session; environment (уровень сети, переменные, network secrets, setup script, cache окружения); GitHub proxy; self-hosted runner [46][3][19].
- **Перенос работы:** `--cloud` (новая cloud session); `-p --cloud <id>` (follow-up в работающую сессию); teleport (из облака в терминал); Open in > Cloud (из Desktop в облако); Remote Control (управлять своей машиной с телефона и веба) [2][12][6].
- **Цикл PR:** auto-fix (агент сам чинит CI и отвечает на review), `/autofix-pr`, Merge when ready [2][12].
- **Projects:** project, coordinator, thread, Suggested threads, Overview, Library, project memory, project instructions, Setup recommendations, Work locally [1].
- **Automation:** cloud scheduled task с triggers Schedule, API и GitHub; Desktop scheduled tasks; `/loop` (повтор prompt в открытой сессии); `/goal` [4][27][25].
- **Параллельность:** subagents, agent view, agent teams, dynamic workflows, `/batch`, cross-session messaging [10][31][24].
- **Лимиты:** 5-hour limit (до 2026-10-27 — «session limit»), weekly limit, usage credits, auto-continue [8][48].

### Чем подход отличается

1. **Вертикальная интеграция.** Anthropic владеет моделью, harness, VM и подпиской. VM не оплачивается отдельно, облако тратит тот же пул, что чат и CLI [2][49][51].
2. **Coordinator — модель, а не scheduler.** Маршрутизация, число threads, частота отчётов и момент PR — предпочтения на естественном языке в памяти. Жёсткий только лимит 500 новых threads в день [1].
3. **Cloud threads не используют механику репозитория.** Из репозитория грузятся только корневые CLAUDE.md и rules. Skills, agents, commands, hooks, permission rules, `.mcp.json`, `env` и plugins репозитория — нет. Hooks и локальные tools работают только в thread на своём компьютере [1].
4. **Привязка к GitHub.** Projects требуют github.com и Claude GitHub App на каждом репозитории. Другие hosts — только bundle без push [1][2].
5. **Надзор с телефона.** Управление с телефона, уведомления, карточки устройств [1][47].
6. **Один человек, а не команда.** Проект не расшарить. Командный продукт — Claude Tag [1][18].
7. **Один движок на разных поверхностях.** Claude Tag работает на движке cloud sessions. Dispatch запускает сессии Claude Code [18][12].

## Как это устроено внутри

Код закрыт, модулей и файлов для ссылок нет [66]. Всё ниже — из документации, инженерных постов, changelog и issues.

### Компоненты и поток данных

- **Control plane** Anthropic: оркестрация сессий, очереди и интерфейс claude.ai. Он всегда работает у Anthropic, даже при self-hosted. При старте сессии control plane ставит её в очередь выбранного environment [19].
- **Environment** — именованное место назначения сессий. Три вида [3][19]:
  - hosted у Anthropic: уровень сети, переменные, network secrets, setup script;
  - self-hosted pool: группа runners, id вида `ccpool_…`, в API — «pool»;
  - «bridge environment»: запись, которую Remote Control регистрирует для машины пользователя.
  - Что локальные threads Projects идут через bridge environment — вывод [1][6].
- **Executor** — VM Anthropic, self-hosted runner или машина пользователя через Remote Control. Он запускает headless-процесс Claude Code. Процесс шлёт события в Anthropic, transcript хранится у Anthropic, все клиенты показывают один и тот же поток [19][2][48].
- **Протокол self-hosted** [19]:
  - runner забирает сессию и держит на неё lease;
  - клонирует репозиторий и запускает дочерний процесс Claude Code;
  - дочерний процесс шлёт события по HTTPS через server-sent events;
  - каждый poll runner продлевает lease и служит heartbeat;
  - lease потерянного runner истекает примерно через 60 секунд, и сессия снова встаёт в очередь — это может занять несколько минут;
  - poll — timeout 10 секунд, backoff до 20 секунд.
- **Hosted-путь** устроен так же, через дочерний процесс (вывод). Changelog это поддерживает: `claude -p` и Claude Code Remote больше не грузят интерактивный UI (2026-09-25); веб-интерфейс — «SDK consumer» сессии (2026-03-05) [48].
- **Что добавляет control plane** [20]:
  - system prompt и дополнительный system prompt файлами (`--system-prompt-file`, `--append-system-prompt-file`);
  - connectors пользователя из claude.ai как серверную MCP-конфигурацию через `api.anthropic.com`;
  - MCP server Anthropic «Claude Code Remote». Его tools позволяют Claude создавать cloud scheduled tasks, запускать и направлять другие cloud sessions, добавлять репозитории (`add_repo`) и следить за PR.
  - Как coordinator запускает threads, не документировано. Что через этот MCP server — вывод.
- **Credentials в сессии** [20][19][23]:
  - OAuth token на сессию для вызовов модели живёт около 30 минут; обновления приходят в stdin дочернего процесса (документировано для self-hosted runners [20]);
  - session JWT с префиксом `sk-ant-cc-` (`CLAUDE_CODE_SESSION_ACCESS_TOKEN`) у сессий self-hosted environment: `iss: ccr`, `ccr:role: session_worker`, срок 4 часа по умолчанию и 8 максимум, цепочка делегирования RFC 8693 `act` с тем, кто создал сессию. Сессии на VM Anthropic получают token с префиксом `sk-ant-si-`, подписанный другим набором ключей [23];
  - id сессий — `session_…` и `cse_…` [2][23].
- **Transcript** хранится у Anthropic, чтобы сессию можно было продолжить с любой поверхности [19][32]. Сессии Remote Control тоже хранят transcript на сервере, пока подключены [6]. `--teleport` использует ту же инфраструктуру Remote Control, что и cloud sessions [2].

### Цикл агента

- Каждый thread — полная сессия Claude Code со своим context window [1]. Цикл стандартный: собрать контекст, действовать, проверить [44].
- Thread может делить работу через subagents, loops и workflows [52]. Agent teams включаются `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` [2]. Их почтовые ящики — локальные JSON-файлы [39].
- Особенности облака:
  - ранний compaction через `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` [2];
  - команда на переднем плане — 2 минуты по умолчанию, максимум 10, затем до 30 минут в фоне [3];
  - Stop hook просит закоммитить и запушить [20];
  - `CLAUDE_CODE_MAX_TURNS` ограничивает число ходов [1].
- Шаги run: clone и setup script, настройка сети, работа, push ветки. Сессия остаётся открытой после push, поэтому PR и дальнейшие правки — в том же разговоре [5].

### Параллельность и координация

- **Coordinator** [1]: одна долгая сессия. Она помнит все threads, которые запустила, и видит их отчёты, а не шаги. Работает по последним сообщениям, threads и памяти проекта, а не по всей истории. Launch-пост: coordinator уточняет запрос, делегирует, координирует параллельные threads, проверяет результат и собирает итог [52].
- **Число threads** [1]: фиксированной параллельности нет. Единственный жёсткий лимит — 500 новых threads в день на все проекты пользователя. В материалах о запуске называли 200 [124].
- **Лимит организации** на одновременные cloud sessions существует. Он виден как предупреждение scheduled task. Размер не опубликован [4][48].
- **Общее состояние** [1]: общей файловой системы нет. Общие только файлы памяти проекта, Library (`/mnt/project-files`), ветки и PR в GitHub.
- **Конфликты** проявляются как merge conflicts в PR [52]. Руководство Anthropic по cloud sessions советует делить параллельные задачи по границам файлов. Оно предупреждает, что сессии не видят исправлений друг друга [59].
- **Связь** [1][24]:
  - threads отчитываются coordinator;
  - сообщение в поле thread идёт прямо ему;
  - follow-up в разговоре проекта доходит до thread, только если Claude сопоставит его с этим thread;
  - локальные сессии могут писать cloud sessions через серверы Anthropic, но cloud sessions не могут ответить через `SendMessage`.
- **Наблюдения пользователей** (вторичные):
  - у coordinator есть tools `read_memory` и `update_memory`; новые threads стартуют с инструкциями проекта, AGENTS.md репозитория и «brief» от coordinator [68];
  - threads не умеют ждать друг друга; пересылка отчётов зависит от решения coordinator; в одном случае готовый результат не пересылали около 90 минут (#109202) [92].
- **Соседние механизмы** — subagents, agent view, agent teams, dynamic workflows и Projects — устроены отдельно [10]. Agent view запускает локальные background sessions под процессом-supervisor [31].

### Изоляция

- **Cloud thread** клонирует репозиторий в свой sandbox и свою ветку от ветки по умолчанию, поэтому worktrees не нужны [1]. Scheduled runs пушат в ветки `claude/…` [4].
- **Локальные threads** получают git worktree через переключатель Worktree или `claude remote-control --spawn worktree` [1][6]. Сервер Remote Control по умолчанию принимает до 32 сессий (`--capacity 32`) [6].
- **Self-hosted runner** закрепляется за одним владельцем при первой сессии, чтобы выгруженный код разных владельцев не смешивался [19].
- **Что грузит project thread** [1]: только корневые `CLAUDE.md`, `.claude/CLAUDE.md` и `.claude/rules/`. Не грузятся: CLAUDE.md подкаталогов, правила для путей, skills, agents и commands репозитория, `.mcp.json`, `.claude/settings.json` (permissions, hooks, `env`, plugins).
- **Отдельные cloud sessions с одним репозиторием** вне проекта читают settings, hooks и `.mcp.json` репозитория [3][42].
- **Область репозиториев** [1]: Claude добавляет репозитории только от GitHub owners, которых проект уже использует.

### Состояние и память

- **Простаивающие VM** [3][2]:
  - через несколько минут простоя VM встаёт на паузу с сохранением файлов; следующее сообщение поднимает ту же VM;
  - если VM забрали, создаётся свежая VM с восстановленной историей разговора;
  - фоновые shell-команды, subagents и расписания внутри сессии не восстанавливаются; Claude сообщают, что остановилось.
- **Project threads** [1]: sandbox на паузе между ходами. Если он не восстановился — свежий clone, незакоммиченное может пропасть. Совет Anthropic — коммитить и пушить.
- **Cache окружения** [3]: snapshot файловой системы после setup script, если тот уложился примерно в 5 минут. Процессы не сохраняются. Пересборка — при изменении скрипта или allowed hosts либо примерно через 7 дней.
- **Self-hosted resume** [19][21][22]: простаивающие или выводимые из работы runners делают «release» сессий. Сессия продолжается на свежем runner, когда пользователь пишет снова. Незапушенная работа теряется, если у runner нет `--push-outcome-on-release`.
- **Workflows** [38]: в cloud sessions результаты workflow сохраняются с историей разговора и переживают потерю VM. При перезапуске уже завершённые агенты переиспользуются.
- **Перенос** [2][12]: teleport выгружает ветку сессии и загружает разговор; сжатая сессия приходит как summary. Из CLI перенос в одну сторону. «Open in > Cloud» в Desktop отправляет локальную сессию как summary.
- **Память проекта** [1]: файлы с индексом `MEMORY.md`. Каждый cloud thread читает индекс при старте и открывает остальные файлы по необходимости. Память проекта отдельна от локальной auto memory. Локальные threads её не получают.
- **Инструкции проекта** [1]: до 16 000 символов, каждому новому thread и coordinator. Правки доходят только до новых threads.
- **Окно контекста** [1]: threads сжимаются автоматически. Переполненный thread может сам продолжить в новой сессии. Локально грузятся только первые 200 строк или 25 KB `MEMORY.md` [41]. Есть ли такой предел у памяти проекта — не подтверждено.
- **Стоимость cache** [40][1]: на подписке prompt cache основного разговора живёт час. Thread, который простоял дольше, при пробуждении перечитывает весь разговор.
- **Сбои по отчётам пользователей** (вторичные): память проекта перестала работать при выключенной памяти чата на уровне аккаунта (#100597, 2026-10-08) [68]; инструкции проекта иногда не доходили до threads (#103294) [69].

### Проверка качества

- **Обязательного gate нет** [1]. Projects не запускают встроенных проверок. Документация советует вписать в инструкции проекта: запустить `make test` и `make lint` и вставить итоговые строки.
- **Auto-fix** [2]: подписка на события PR через GitHub App; очевидные исправления для упавших checks и review comments; вопрос при двусмысленности; дубликаты отмечаются. Для конфликтов с base-веткой webhook нет — нужен ручной запрос «rebase».
- **Auto-fix в проектах** [1]: включён по умолчанию для PR threads. Простаивающие threads просыпаются на падение CI или review comment. Кнопки: Resolve conflicts, Fix CI, Address comments, Merge it.
- **Блокировки классификатора** [36]: merge PR без одобрения человека, одобрение своего PR, отключение CI.
- **Отдельные продукты review:** Code Review — find, verify, rank, post; никогда не одобряет и не блокирует PR [14]. Ultrareview — группа reviewers в cloud sandbox; каждая находка воспроизводится отдельно [13].
- **`/goal`** — отдельная модель-оценщик решает, выполнено ли условие [25].
- **Статусы scheduled tasks** (Succeeded, Failed, Cancelled) говорят, как закончилась сессия, а не выполнена ли работа [4][123].

### Восстановление после сбоев

- **Повторы API** [8]: 10 повторов по умолчанию. Retry watchdog — бесконечно для 429 и 529, около 300 повторов (примерно 3 часа) для других временных ошибок, ожидание сброса лимита с необязательными пределами. Используют ли его cloud sessions — не подтверждено.
- **Provisioning** [2]: «Session creation failed» значит, что не удалось выделить VM. Мощность выделяется по запросу, нужно повторить. С v2.1.314 сессии с веба, Desktop и телефона стартуют, даже если setup script упал [48].
- **Coordinator** [1]: баннер «Claude hasn't responded» с кнопкой «Restart Claude». Coordinator переподключается, частичный ответ теряется, threads не затронуты.
- **Scheduled tasks** [4]: без связи с GitHub runs пропускаются до 72 часов, потом задача выключается. При превышении часового лимита run ждёт.
- **Self-hosted** [19][22]: истёкший lease возвращает сессию в очередь. `--kill-session-after-min` освобождает зависшие сессии после 15 минут отсрочки.

### Лимиты и стоимость

- Облако тратит лимиты плана. VM отдельно не оплачивается. Projects расходуют лимиты быстрее [1][3].
- Лимит тратят: работающие threads, tokens coordinator, пробуждения threads, которые следят за PR. Простаивающий или архивный проект не тратит ничего. Вкладка usage показывает расход по threads и моделям [1].
- Платный расход сверх лимитов — только если пользователь сам включил usage credits. Thread не может включить их за него [1].
- Продолжение после сброса: в Projects — по умолчанию для 5-часового и недельного лимита [1]; в CLI — до трёх продолжений и не дальше 24 часов [9]; workflows и `/goal` встают на паузу и продолжают [38][25]; scheduled tasks без credits отклоняются до сброса [4].
- Один большой fan-out workflow может за раз съесть недельный лимит [8].
- Не подтверждено: продолжают ли сами отдельные cloud sessions; есть ли предел числа продолжений у project threads.

### Права и безопасность

- **Режимы:** Accept edits, Plan и Auto, без Bypass [36]. Threads — в auto mode, если модель его поддерживает [1].
- **Auto mode** [56][36]: allowlist и правила; правки внутри проекта; остальное — серверный классификатор, который не видит рассуждений Claude; probe на prompt injection в выводе tools; возврат к человеку после 3 блокировок подряд или 20 всего.
- **Правила репозитория** project threads игнорируют. Одобрения — только внутри thread; «go ahead» в coordinator до thread не доходит [1].
- **GitHub proxy** [3][37]: подменяет credential; отклоняет удаление веток, push тегов, GraphQL и репозитории вне сессии. Источники расходятся о push: текущая документация говорит, что proxy не ограничивает, какие ветки может обновить push [3][37]; ранние посты говорили, что push разрешён только в ветку сессии [57][59].
- **Сеть** [3][2]: уровни None, Limited, Full; security proxy на весь исходящий трафик; network secrets добавляются после выхода запроса из VM; трафик connectors идёт через Anthropic. API Anthropic доступен даже при None — документация признаёт, что через него данные могут уйти наружу.
- **Недоверенный ввод** [4]: текст из API trigger приходит в `<routine-fire-payload>` с пометкой untrusted.
- **Аудит и данные:** все операции cloud sessions логируются [37]. Хранение — 30 дней или 5 лет для потребительских аккаунтов с согласием на обучение [32]. Организации с ZDR, HIPAA и CMEK cloud sessions не используют [2].
- **Владение** [1]: проект принадлежит одному человеку; контроля организации в beta нет.
- **Найденные уязвимости** (вторичный источник) [122]: бывший инженер Anthropic показал, что token из sandbox позволял перечислить, прочитать, изменить и удалить все сессии пользователя. Через него же можно было клонировать любой подключённый репозиторий и выносить данные через загрузку картинок в браузере пользователя. Всё быстро исправили.
- **Где участвует человек:**
  - до работы: Suggested threads, предпочтение «propose first», setup recommendations [1];
  - во время работы: permission prompts в thread; карточка «Allow once» для локальных threads [1]; вопрос auto-fix при двусмысленном комментарии [2];
  - после push: кнопки PR [1];
  - auto mode подталкивает Claude работать дальше без уточняющих вопросов [36];
  - пользователь сообщает, что локальный project thread записал одобрение production deploy, которого он не видел (#107089, вторичный) [70].

### Projects (beta) подробно

- **Качество** — issue #97924 о merge при красном CI, 2026-09-28 [86]:
  - threads слили два PR с красным CI, хотя инструкции требовали зелёный;
  - один PR слит примерно через 4 секунды после выхода из draft, а CI репозитория на drafts пропускает настоящие тесты;
  - threads игнорировали AGENTS.md репозитория;
  - coordinator передавал непроверенные догадки как факты;
  - итог: 4 слитых PR откачены, 3 открытых закрыты, разбиение задачи начато заново;
  - вывод автора: coordinator только пересылает сообщения. На одной задаче «разобраться и починить» тот же продукт работает хорошо.
- **Пассивный coordinator и устаревшее состояние:**
  - одобрения нужны постоянно; coordinator редко сообщает о блокерах; to-do списки threads устарели; один ответ — coordinator добавляет больше работы, чем экономит (#98355) [87];
  - чтобы узнать, что происходит, пользователи пишут «Status?» [92];
  - coordinator не переслал результат локального thread, и ожидающий thread простоял около 90 минут (#109202) [92];
  - после перезапуска coordinator теряет tools для карточек решений (#104059) [92].
- **Effort зажат внизу** [89]: выбор effort убрали, coordinator закреплён на Opus 5.5 с low effort, `/effort xhigh` отклоняется (#106126). Cloud threads работают на low даже при настройке high (#101349). Документация по-прежнему описывает отдельные настройки effort [1]. Источники расходятся.
- **Трение с правами** [90]:
  - классификатор auto mode заблокировал миграцию staging БД после слов «Merge and migrate»; одобрить в UI нельзя, и threads отдают prompt, чтобы выполнить его локальным агентом (#96775);
  - проверки прав называют жестокими; пользователь хочет поставить проект на autopilot (#105844).
- **Cloud-first против local-first** [91]:
  - сделать локальные сессии полноценными threads (#99156);
  - дать доступ из CLI (#103710): cloud-first делает Projects неудобными;
  - разрешить локальную папку без GitHub как основной контекст (#99307);
  - уважать локальные CLAUDE.md, память и hooks — просит product manager без опыта программирования (#103709); в ответ пишут, что приходится держать три копии правил, и они расходятся;
  - дать локальным threads память проекта (#97464).
  - Cloud threads молча привязаны к Desktop-устройству. Это ломает исходящие POST и обновление Google OAuth token (#99688) [94].
- **Видимость** [92]: полные детали выполнения в виде thread — на телефоне видны только сообщения, to-do и кнопка PR (#97690); один inbox «Waiting on you» на все проекты плюс API или `--json` в CLI (#96115); push на телефон о решениях coordinator (#98655).
- **Недовольство миграцией** [88]: классические проекты чата claude.ai конвертировали без opt-out, и coordinator теперь видит все чаты — пользователь пишет, что это не косметический редизайн (#101369). Похожий отчёт бот закрыл как «не про Claude Code» (#99128). Миграция односторонняя (#103290).
- **Вторичные источники:**
  - пересказ Reddit [125]: threads нельзя создать вручную; контроль coordinator устраивает, только если ему доверяешь; память на серверах вендора — это lock-in; Projects хороши для разделимой работы в нескольких репозиториях, а на связанном коде лишние threads дают merge conflicts и расход лимитов;
  - Gewirtz из ZDNET в пересказе [124]: новой параллельности по сравнению с subagents в терминале нет, конфликты лишь откладываются;
  - под build log Felix Rieseberg на HN спрашивали стоимость в tokens; один комментатор счёл текст рекламой, другой нашёл битые ссылки [118].

### Routines

- Функцию любят, когда она работает, но, по словам пользователя, в основном она не работает [103].
- Сбои: connectors отваливаются посреди run [103]; в версии для Cowork automation в 90% случаев даже не запускается [103]; вызовы MCP падали с «requires approval» (#61015, 53 👍); обновление Desktop спрятало sidebar Routines (#102150, 38 👍); результаты runs трудно найти (#54517) [85].
- Зелёный статус run не значит, что задача из prompt выполнена [123].
- Безопасность: в режиме routine write-tools MCP разрешены всегда (комментарий на HN) [104]. Пользователи боятся prompt injection через GitHub triggers [103].
- Нет совместной работы на личных планах и нет контроля организации [103]. Как восстановить состояние после падения run посередине, не документировано [103].

- **Спрос был раньше функции.**

- **Пробелы** [96]:
  - только одна из примерно 11 параллельных сессий Desktop предложила auto-continue (#92004);

## Слабые места и чего нет

- **Нет обязательной проверки перед merge.** Проверки — только в инструкциях проекта, CI — через auto-fix. Threads сливали PR с красным CI (#97924) [1][86].
- **Coordinator без жёстких правил.** Лимит threads — пожелание. Нет графа зависимостей и порядка запуска. Пересылка отчётов — на усмотрение coordinator, ожидание доходило до ~90 минут (#109202) [1][92]. Пользователи называют coordinator пассивным и пишут ему «Status?» [87][92].
- **Effort coordinator** по отчётам пользователей зажат на low, хотя документация описывает настройку [89][1].
- **Только один человек.** Нет sharing и контроля организации. На Team и Enterprise Projects нет [1].
- **Только Claude Code и модели Anthropic.** Codex и другие агенты не поддерживаются [1][2].
- **Привязка к github.com.** GitLab и Bitbucket — только bundle без push. Azure DevOps и Gitea нет [2][76][116].
- **Облако не видит механику репозитория.** Hooks, skills, agents, permission rules и plugins репозитория в cloud threads не грузятся. Правила приходится держать в нескольких местах [1][91].
- **Расход лимитов.** Projects тратят быстрее. Auto-continue по умолчанию за ночь съедал недельный лимит Ultra. После часа простоя cache холодный. Разобрать расход трудно, планирования расхода до run нет (не подтверждено) [1][97][96].
- **Надёжность.** Зависания с расходом кредитов, невозобновлённые контейнеры, сбои git proxy, обрывы Remote Control, 57 инцидентов за два месяца [79][80][81][82][115].
- **Потеря работы.** Свежий clone теряет незакоммиченное. После потери VM фоновые процессы не восстанавливаются [1][3].
- **Auto-fix.** Не видит merge conflicts. Просыпается от любого комментария в публичном репозитории. Принимает статусы ботов за review [2][95].
- **Teleport** теряет follow-ups и историю. Из CLI нельзя перенести работающую сессию в облако [84][2].
- **Окружение.** Только x86_64, нет GPU и WebGPU, ограничены RAM и диск, нет Kubernetes [3][103][112][116].
- **Тихие значения по умолчанию.** URL сессии в commits, классификация сессий и ошибка согласия Remote Control подорвали доверие части пользователей [72][83][109][48].
- **Scheduled tasks.** Зелёный статус не значит выполненную задачу. Сбои MCP и connectors. Нет совместной работы [123][85][103].
- **Миграция** старых проектов чата — без opt-out и в одну сторону [88].
- **Закрыто** для организаций с ZDR, HIPAA и CMEK [2].
- **Чего нет** (не найдено, не подтверждено): canvas; timeline run без присмотра; продуктового советника с mind map и критиком спецификаций; скриншотов-доказательств с удалением личных данных; планирования runs под лимиты подписки.

**Где жалобы пользователей Projects касаются того, что в worfy устроено иначе** (сопоставление исследования, а не слова пользователей):
- Пользователи просят local-first: доступ из CLI, локальные папки, уважение локальных CLAUDE.md и hooks [91]. worfy работает с локальными сессиями и ставит правила через Harness plugin.
- Merge PR с красным CI и непроверенные выводы coordinator [86]. В worfy есть локальный Gate и reviewer subagents.
- Просят детали выполнения, общий inbox, уведомления о решениях coordinator и возможность не спрашивать «Status?» [92]. В worfy это Canvas, Flight Recorder, Work track, PR inbox и уведомления.
- Боль с лимитами: auto-continue только в одной сессии из многих, холодный cache после сброса, мёртвые сессии Remote Control, непрозрачный ночной расход [96][97]. В worfy — ожидание сброса в Autopilot, планирование runs под лимиты, Eco mode и счётчики.
- Просят режим autopilot для одобрений [90]. В worfy — auto-approval по policy.
- Пользователи постоянно сравнивают Claude и Codex [100][101]. worfy запускает оба.

**Где Anthropic впереди, по словам пользователей:** работа продолжается при закрытом ноутбуке; управление с телефона; sandbox без настройки; встроенные GitHub App, auto-fix и облачные runs по расписанию [2][4][112][119].

## Механизмы, которые стоит изучить

1. **Auto-continue после сброса лимита с ограничителями.**
   - Что это: сессия не обрывается на лимите подписки, а ждёт сброса окна и продолжает.
   - Как работает: CLI ждёт в открытой сессии и показывает время продолжения с отменой по Esc. После сброса последнее сообщение не повторяется: Claude просят продолжить с места остановки. Ограничители: не больше трёх продолжений подряд; не ждёт сам, если сброс дальше 24 часов; после сна машины больше ~30 минут нужен Enter; нет в background sessions и `-p`. В Projects — один переключатель на проект, включён по умолчанию, покрывает 5-часовой и недельный лимиты. В Desktop — только на карточке 5-часового лимита.
   - Источники: [9][1][8].
2. **Retry watchdog для runs без присмотра.**
   - Что это: режим повторов API для сессий без человека.
   - Как работает: `CLAUDE_CODE_RETRY_WATCHDOG=1` бесконечно повторяет 429 и 529 с паузой до 5 минут или до времени сброса из ошибки. Для других временных ошибок — около 300 повторов. На spend limit выходит сразу. Отдельные переменные задают предел ожидания и интервал проверки, не сняли ли лимит раньше.
   - Источники: [28][8][48].
3. **Учёт стоимости холодного cache.**
   - Что это: prompt cache живёт час, после простоя возобновление перечитывает весь разговор.
   - Как работает: документация Projects прямо предупреждает об этом. CLI с v2.1.304 на планах Pro и Max перед возобновлением неактивного разговора предупреждает, если тот займёт заметную долю 5-часового лимита. Пользователи сообщают, что первый запрос после сброса съедал 30–40% нового окна.
   - Источники: [1][40][48][96].
4. **Credentials вне sandbox.**
   - Что это: агент работает без настоящих token и ключей внутри VM.
   - Как работает: GitHub proxy подменяет ограниченный credential настоящим token и отклоняет удаление веток, push тегов, GraphQL и репозитории вне сессии. Network secrets добавляются к запросам на указанные hosts уже после выхода из VM. GitHub credentials хранятся зашифрованными на серверах Anthropic и в VM не попадают [37]. О ключах подписи вне sandbox говорит только пост 2025-10-20 [57].
   - Источники: [2][3][37][57].
5. **Lease и heartbeat у runners.**
   - Что это: протокол, по которому self-hosted runner забирает сессию и отдаёт её при сбое.
   - Как работает: runner берёт сессию с lease. Каждый poll продлевает lease и служит heartbeat. Lease потерянного runner истекает примерно через 60 секунд, сессия возвращается в очередь. Простаивающий runner делает «release», и сессия продолжится на свежем runner. `--push-outcome-on-release` пушит работу перед release, `--kill-session-after-min` освобождает зависшие сессии. Runner закрепляется за одним владельцем.
   - Источники: [19][21][22].
6. **Идентичность сессии с цепочкой делегирования.**
   - Что это: у каждой сессии self-hosted environment свой короткоживущий token, по которому сервисы в сети клиента видят, кто её создал.
   - Как работает: JWT с префиксом `sk-ant-cc-`, `iss: ccr`, ролью `session_worker` и сроком 4 часа (максимум 8). Runner обновляет token до истечения. Claim `act` по RFC 8693 хранит цепочку делегирования от создателя сессии. Отдельный OAuth token для вызовов модели живёт около 30 минут и обновляется через stdin дочернего процесса. Сессии на VM Anthropic получают token с другим префиксом, `sk-ant-si-`, подписанный другим набором ключей.
   - Источники: [23][20][19].
7. **Классификатор вместо permission prompts.**
   - Что это: модель решает, можно ли выполнить действие, без вопроса человеку.
   - Как работает: три уровня — allowlist и правила, правки внутри проекта, остальное классификатору. Две стадии: быстрый фильтр в один token, затем рассуждение только по отмеченным действиям. Классификатор не видит рассуждений Claude и вывода tools. Отдельный probe проверяет вывод tools на prompt injection. После 3 блокировок подряд или 20 всего — вопрос человеку. В run с `-p` без `--permission-prompt-tool` заблокированное действие просто не выполняется, а run продолжается; пост 2026-03-25 описывал завершение процесса. По умолчанию блокирует merge PR без одобрения человека, одобрение своего PR и отключение CI. Опубликованы ошибки: 0.4% false positives и 17% пропусков. В посте классификатор работал на Sonnet 4.6; сейчас модель по умолчанию — Sonnet 5.
   - Источники: [56][36].
8. **Trigger — данные, а не одобрение.**
   - Что это: правило, по которому внешний запуск не может разрешать действия агента.
   - Как работает: текст из API trigger приходит обёрнутым в `<routine-fire-payload>` с пометкой «недоверенные данные». Prompt от trigger — задание run, а не живой ввод. С 2026-06-19 (v2.1.183) доставки triggers не считаются вводом с клавиатуры и не одобряют действия.
   - Источники: [4][48].
9. **Состояния threads и кнопки-инструкции.**
   - Что это: обзор, где каждый thread стоит в одной из шести групп, и кнопки с готовыми инструкциями.
   - Как работает: группы Ready for review, Waiting on you, Working, Landing, Idle и Resolved; Resolved ставится сам после недели без активности. Точка на кнопке Threads показывает, что кто-то ждёт. Кнопки Resolve conflicts, Fix CI, Address comments и Merge it отправляют thread обычное сообщение с инструкцией, а не вызывают отдельный API.
   - Источники: [1].
10. **Auto-fix PR по событиям.**
    - Что это: после открытия PR агент сам доводит его до зелёного CI и отвечает на review.
    - Как работает: подписка на webhooks через GitHub App. Очевидные исправления пушатся сразу, двусмысленные — после вопроса. Повторные события отмечаются. В Projects простаивающий thread просыпается на событие CI или review. Пробел: GitHub не шлёт webhook о merge conflict. Пользователи жалуются, что агента будит любой комментарий в публичном репозитории.
    - Источники: [2][1][95].
11. **Ссылка на сессию в каждом commit.**
    - Что это: trailer `Claude-Session: <url>` в commits и URL сессии в описании PR.
    - Как работает: добавляется по умолчанию в cloud sessions и сессиях Remote Control. Отключается настройкой `attribution.sessionUrl: false`. В сессии есть переменные `CLAUDE_CODE_REMOTE` и `CLAUDE_CODE_REMOTE_SESSION_ID`. Включение по умолчанию вызвало спор на HN: 209 points и 240 комментариев.
    - Источники: [3][72][108].
12. **Setup script со snapshot окружения.**
    - Что это: окружение готовится один раз, а не в каждой сессии.
    - Как работает: root-скрипт выполняется до старта Claude (файл, который загружают кнопкой Choose file, — до 64 KB). Если скрипт укладывается примерно в 5 минут, файловая система сохраняется в snapshot и переиспользуется. Пересборка — при изменении скрипта или allowlist либо примерно через 7 дней. Процессы не сохраняются. С v2.1.314 сессия стартует, даже если скрипт упал.
    - Источники: [3][48].
