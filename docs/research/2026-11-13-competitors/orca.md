## Модель работы

**Где работает: local, с удалёнными режимами на машинах пользователя.**
- Orca — desktop-приложение на машине пользователя. Документация прямо говорит, что это не hosted VPS-продукт: удалённые вычисления всегда идут на машинах и в облачных аккаунтах, которыми управляет пользователь [9][46].
- Есть четыре режима запуска [46]:
  - **Local** — на этой машине.
  - **SSH target** — Orca на ноутбуке запускает git и агентов на хосте по SSH [47].
  - **Remote Orca Server** — сервер (`orca serve`) владеет проектами, worktrees, терминалами, аккаунтами и агентами. Ноутбук, браузер и телефон — только клиенты [48].
  - **Cloud VM / per-workspace environment** — отдельная VM или контейнер на каждый workspace. Их создают скрипты-«recipes» из файла `orca.yaml` у провайдера, которого выбирает и оплачивает пользователь [46].
- Headless-режим: `orca serve` запускает runtime без окна [28]. Серверный пакет для Linux весит около 60 МБ, `.deb` — 190 МБ [48].
- Web-клиент: браузер подключается к runtime так же, как ноутбук или телефон [46]. Часть функций в нём выключена, например плавающий workspace [106].
- Мобильные приложения для iOS и Android — клиенты к desktop или серверу. Они помечены beta [49][183][6].
- Вендор держит только вспомогательные сервисы: вход в аккаунт, Orca Relay для телефона, push-уведомления и публикацию Artifacts [63][72][5].
- В privacy policy упомянуты «Cloud Sandboxes: hosted workspaces». Документация при этом говорит, что Orca не продаёт управляемый VPS-хостинг [5][46]. Есть ли hosted-продукт — не подтверждено.

**Агенты и модели.**
- Своего агента у Orca нет, моделей Orca не хостит. По документации, выбор агента просто запускает процесс в терминале [17].
- Число агентов разное в разных местах: на главной — 27 [1], в README — 34 и «любой CLI-агент» [56], в таблице документации — 40 строк. Одна из них — Claude Agent Teams, режим самого Claude Code [17].
- Около 39 CLI настроены заранее. У каждого своя глубина интеграции: автонастройка, статус, hooks, usage, история сессий, переключение аккаунтов [17].
- Модель выбирается в настройках самого агента. Chat UI добавляет выбор модели и effort [21]. Подробности — в разделе «Функции → Агенты, модели и права».

**Один пользователь или команда.**
- Ядро продукта — для одного пользователя.
- Что есть для команд [12][33][48][2]:
  - общий `orca.yaml` в репозитории;
  - один Remote Orca Server для нескольких клиентов;
  - отзываемые ссылки на наборы skills (документация приводит пример «Team Toolkit»);
  - на странице Enterprise — помощь во внедрении и «organization-level defaults».
- Мест, ролей, SSO, общих dashboards и audit log как отдельного продукта не найдено [2][72].
- В коде есть начала командного облака:
  - скрытый в production dev-only preview входа в «Orca Cloud» [104];
  - PR, добавивший аккаунт (2026-07-09), сразу построил выбор организации, приглашения по email, смену ролей и удаление участников [130];
  - в строках интерфейса есть «Cloud profile» и «Failed to switch organization» [72].
  - Выйдет ли это в продукт — не подтверждено.

**Платформы.**
- macOS: DMG для arm64 и x64, подписаны и notarized [54].
- Windows 10/11, только x64 [6]. Подпись кода — через SignPath [56].
- Linux: AppImage (x64 и arm64), `.deb` и `.rpm`. Сам обновляется только AppImage [54].
- Homebrew cask `stablyai/orca/orca` (и `@rc`), пакет AUR `stably-orca-bin` [56][54].
- На Linux CLI называется `orca-ide`: имя `/usr/bin/orca` уже занято экранным диктором GNOME [27][54].
- Терминал на Windows — PowerShell, CMD или WSL, есть режим администратора [45]. Аккаунты Codex можно держать внутри WSL [19].
- Интерфейс — на 11 языках плюс «System», среди них русский [52].
- Поддержку macOS 12 прекратили (Discussion #38765, 2026-11-06) [178].
- Серверная часть требует Node 24, launcher и CLI остаются на Node 18 [61].

### Workspaces и worktrees

- **Основной сценарий** [10][11]. Добавить репозиторий, нажать + и создать worktree, выбрать агента, смотреть за работой, открыть diff, отправить (ship). Каждая задача получает настоящий `git worktree`, свою ветку, свои терминалы и вкладки браузера.
- **Создание workspace** [11]:
  - идёт в фоне; в sidebar видна строка прогресса с кнопками Cancel и Retry;
  - старт от base ref (ветки по умолчанию для новых worktrees), другой локальной ветки, SHA коммита или удалённой ветки;
  - в диалоге — поля с поиском: Project, «Run on» (локально, SSH-хост, сервер или recipe) и Agent с флажком «Set as default»;
  - в разделе «Advanced» — явное имя ветки и родительский workspace. Вложенность видна только в sidebar и не меняет историю git;
  - в поле имени можно вставить URL GitHub PR, issue Linear, GitLab MR или Jira — workspace свяжется с ним. Для Linear берётся имя ветки, которое предлагает сам Linear [11][39];
  - пустое имя заменяется именем морского существа. Настройка «Auto-Rename Branch From Work» переименовывает ветку, когда агент начал работу [10][52].
- **Заранее подготовленные checkouts.** До 3 штук хранятся в `.orca-preparing` по 5 минут. Подготовка начинается, когда пользователь открывает диалог создания. Подготовленный checkout сбрасывается, если base сдвинулся или цель поменялась [95].
- **Folder workspaces.** Родительскую папку с несколькими репозиториями можно сделать project group с «folder workspaces» — это workspace, который не обязан быть git worktree [11][58].
- **Sidebar** [11]:
  - группировка по проектам;
  - фильтры: скрыть спящие workspaces, workspaces на ветке по умолчанию, созданные automation, созданные из CLI, от других клиентов, с detached HEAD;
  - закрепление workspaces;
  - множественный выбор для массовых archive, sleep и delete;
  - чипы «N children» у родителей; Sleep и Delete можно применить вместе с потомками;
  - непрочитанные workspaces выделены жирным.
- **Workspace board.** Kanban из workspaces по статусам. Статусы можно добавлять, переименовывать и красить; карточки — перетаскивать и закреплять. Опция «Sync board and issue status» меняет статус связанного issue Linear вместе с карточкой [72][52].
- **Worktree checkpoints.** Агент пишет свободный комментарий и статус карточки (todo, in-progress, in-review, completed) командой `orca worktree set --comment … --workspace-status …`. Комментарий виден на карточке [32].
- **Очистка** [11]:
  - Resource Manager → «Clean up workspaces» показывает размер, состояние git, активность и связанный review;
  - если массовое удаление сотрёт ветки с несмерженными коммитами, появляется шаг «Review N Branches»;
  - worktrees, созданные вне Orca (Claude Code, GSD, свои папки), можно показать или скрыть.
- **Что отмечают пользователи:** сон workspace освобождает RAM, а пробуждение возвращает агентов [195]; ветка по умолчанию синхронизируется с remote автоматически; worktrees, созданные агентами, можно скрыть [249].

### Настройка репозитория: `orca.yaml` и `.worktreeinclude`

- **`orca.yaml`** — файл настроек Orca в репозитории. Его можно закоммитить для всей команды [12]:
  - скрипты setup и archive; выбор, запускать агента сразу или ждать конца setup (`setupAgentStartupPolicy: wait-for-setup`);
  - `defaultTabs` — вкладки по умолчанию: заголовки, команды и цвета;
  - `issueCommand` — шаблон команды с подстановкой `{{artifact_url}}`;
  - `environmentRecipes` — recipes для Cloud VM;
  - `worktree.sharedDirectories` — папки из `.gitignore`, общие для всех worktrees через symlink или Windows junction;
  - лимит — 256 KiB на файл. Ошибка YAML или повтор ключа отклоняют весь файл.
- **Переменные окружения скриптов** [12]: `ORCA_ROOT_PATH`, `ORCA_WORKTREE_PATH`, `ORCA_WORKSPACE_NAME` и `CONDUCTOR_ROOT_PATH`. Последняя — псевдоним для setup-скриптов, написанных под Conductor (другое приложение для агентов в worktrees).
- **Как выполняются скрипты** [12]:
  - на macOS и Linux `scripts.setup` идёт в Bash с `set -e`;
  - `scripts.archive` выполняется перед удалением worktree;
  - команды из общего `orca.yaml` проходят через одобрение в Orca; одобрение может опираться на сохранённое доверие.
- **Файлы из `.gitignore` в новом worktree** — три пути [11][12]:
  - личная настройка «Worktree Shared Paths» — clone-копия на APFS, иначе ссылка;
  - `worktree.sharedDirectories` — всегда ссылка;
  - `.worktreeinclude` — список файлов (например, `.env`), которые копируются в каждый новый worktree. Бюджет копирования — 2 GiB и 50 000 записей.

### Статус агентов, внимание и уведомления

- **Значки статуса** [14][25]: working (spinner), needs you (жёлтый «?»), done, blocked или failed, idle и обычный shell.
  - Статус берётся из escape-последовательностей OSC (кодов, которыми программа в терминале задаёт заголовок окна) и из hooks агента.
  - Orca сама ставит агентам status hooks. Hooks находят приложение и после его перезапуска, потому что endpoint записан в файл.
- **Agent Dashboard** (experimental) — Kanban с колонками Needs You / Working / Done / Idle [14]:
  - Idle по умолчанию скрыт; туда попадает агент примерно после 30 минут тишины;
  - на карточке — последнее сообщение агента и значок хоста;
  - вложенные subagents Claude и Codex показаны раскрываемыми дочерними строками;
  - фильтры по проекту, статусу workspace и состоянию PR;
  - открывается в главном окне или отдельным окном (pop-out).
- **Agents feed** — лента событий по всем worktrees, сгруппированная по разговорам: законченные ходы, блокирующие вопросы, новые worktrees с превью ответа. Работающие агенты закреплены сверху [51].
- **Уведомления** [50][52][116]:
  - когда агент переходит из working в idle — системное уведомление, звук и чип;
  - колокольчик в заголовке и badge на иконке в Dock (macOS) считают непрочитанное;
  - свой звук для каждой категории;
  - категории также включают падение PR checks и доступное обновление [52];
  - во время orchestration уведомления от workers отфильтровываются [116].
- **Push на телефон** — через сервисы Apple и Google. На хосте push можно выключить: `ORCA_MOBILE_PUSH_MODE=disabled` [50].
- **Restart chip** появляется после выхода агента [14].
- **«Hand Off to Another Agent»** — новая сессия того же или другого CLI. Её первый prompt — ограниченный по размеру handoff-prompt из старой сессии [14][19].
- **Ручная пометка worktree как непрочитанного.** Neil Parker называл её одним из отличий от cmux [190].

### Восстановление сессий, hibernation и история

- **Session restore** [15]:
  - фоновый daemon владеет процессами терминалов;
  - агенты продолжают работать после Cmd-Q, перезапуска при auto-update и падения приложения; при следующем запуске Orca снова подключается к ним;
  - перезагрузка машины убивает агентов, но раскладка и scrollback возвращаются;
  - «Quit Completely» завершает все сессии. Режима «запустить с чистого листа» нет.
- **Чаты** после выхода или обновления продолжаются автоматически — на новых установках [111].
- **Agent hibernation** (experimental, выключена по умолчанию) [23]:
  - ставит агента на паузу после того, как он закончил, если его вкладка не на экране и его не трогали;
  - порог по умолчанию — 30 минут, можно от 1 минуты до 24 часов;
  - только для CLI, которые умеют resume: Claude, Codex, Gemini, Antigravity, OpenCode, Pi, MiMo, Droid, Grok, Devin, OMP;
  - пропускает panes, где есть незакрытый dispatch orchestration, где терминалом управляет телефон или где ещё живы subagents или teammates;
  - когда пользователь открывает вкладку, агент запускается снова с флагами resume, например `claude --resume <id>`.
- **Agent Session History** (правая панель) [22][108]:
  - читает транскрипты около 18 CLI с диска — например, `~/.codex/sessions` и историю Claude;
  - область: workspace, проект или всё; поиск, сортировка, группировка;
  - в деталях — полный первый prompt;
  - Resume одной кнопкой (`claude --resume`, `codex resume` и аналоги), «Copy resume command», «Open log». Resume работает только из локальных workspaces [22];
  - поиск идёт в фоновом worker и работает на SSH- и серверных хостах [108].

### Chat UI и терминальный режим

- **Два вида** [21][116][113]:
  - «Chat UI» говорит с поддерживаемым агентом напрямую, в структурированном режиме, или показывает транскрипт поверх агента, который работает в терминале;
  - выбор делается для каждого агента («Chat | CLI»). Новые установки по умолчанию открывают Terminal [21];
  - Chat UI вышел из experimental в v1.4.246 [116]. Онбординг сразу спрашивает: Chat или Terminal [113];
  - по changelog, структурированный режим стал режимом Chat UI по умолчанию в v1.4.224 (2026-10-10), а workers могут стартовать как чаты с v1.4.225 (2026-10-14) [7];
  - переключатель вида на вкладке пропал в 1.4.193 без упоминания в release notes; пользователи просили вернуть его [139].
- **Перенос разговора** [21][77]:
  - «Continue in Chat UI» и «Continue with Terminal Agent» копируют разговор, оригинал не меняется;
  - в Session History — «Resume in New Chat» и «Resume in New Terminal»;
  - переключение на лету — Cmd+Shift+J на macOS;
  - переносится ограниченный отрывок: до 8 000 символов на сообщение или блок инструмента, 1 000 — на вход инструмента, 2 000 — на его выход [77].
- **Поле ввода** [21]: `/` открывает slash-команды и найденные skills; можно прикладывать файлы и картинки; черновики переживают переподключение; есть выбор модели, effort и режима. AskUserQuestion и запросы прав показываются карточками с вариантами ответа.
- **Добавлено в октябре–ноябре 2026:**
  - `/btw` — побочный вопрос в отдельной копии (fork) чата, пока исходный чат продолжает работать; `/fork` — копия от последнего ответа [109];
  - fork от любого законченного ответа; `/plan` включает режим Plan у Claude и Codex [110];
  - rewind (откат разговора), продолжение остановленного ответа, закреплённый план агента, цель чата (`/goal`) и показ занятости контекста [111][72];
  - в каждом ходе — изменённые файлы с числом строк и патчами прямо в чате [112];
  - результаты CI для PR, которые чат открыл или куда пушил [109]; карточка на каждый PR, открытый агентом [110];
  - сообщения в очереди и сообщения, которые корректируют текущую работу (steering), сохраняют порядок [109];
  - карточка одобрения у Codex показывает предлагаемые файлы и diff [110].

### Лимиты подписки в чатах

- **Автопродолжение после сброса лимита** — opt-in, только в Chat UI:
  - настройка «Continue chats automatically when a usage limit resets» отправляет «Continue where you left off.» в каждый чат с известным временем сброса [115][72];
  - по коду [100]:
    - проверка идёт каждые 10 с;
    - если аккаунт всё ещё показывает окно израсходованным, Orca ждёт дольше и ждёт свежих данных usage;
    - не больше 5 автопродолжений подряд;
    - если сброс опоздал больше чем на 24 часа, Orca сдаётся;
    - отмена, которую сделал человек, сохраняется после перезапуска;
  - по PR #36873 (merged 2026-11-02): примерно через 15 с после сброса Orca отправляет одно видимое сообщение «continue»; его можно отменить для отдельного чата [133];
  - баг у Codex: чаты не планировались, если последний отчёт usage был ниже 100%. Исправлено к 2026-11-11 (#38890) [151].
  - **Расхождение исследований снято проверкой.** Вывод «такой функции нет» опирался на PR #31241 (merged 2026-11-01): тот прямо исключал автопродолжение из scope [128]. Функцию добавил следующий PR #36873 (merged 2026-11-02). Она вышла в v1.4.247 (2026-11-03) и есть в коде на `main` [133][115][100].
  - Для агентов в терминальном виде такого поведения не найдено (не подтверждено). Автоматический resume терминальных агентов после сброса — открытые запросы #8133, #18799 и #40807 [144][146][147].
- **Когда лимит исчерпан** [128][116][72]:
  - в строке чата три действия: Switch Account (другой аккаунт), Hand Off (другой агент) и «Continue Now», которое появляется только после сообщённого времени сброса [128];
  - диалог Hand Off не предлагает режимы того же CLI: они делят тот же лимит. Если других агентов на хосте нет, диалог так и пишет: «Only Agents sharing the usage limit with {{agent}} are available on this workspace host» [72].

### Orchestration: coordinator и workers (experimental)

- **Понятия** [29]:
  - Run — пространство имён со своим inbox (почтовым ящиком coordinator-а);
  - Task — задача со статусом (pending, ready, dispatched, completed, failed, blocked) и зависимостями; из задач получается граф;
  - Dispatch — одна попытка выполнить задачу в одном терминале;
  - Message — письмо между coordinator-ом и worker-ом;
  - Decision gate — вопрос coordinator-а, который блокирует задачу, пока на него не ответят.
- Функцию нужно сначала включить в Settings [29].
- **Ход работы** [29][64]:
  - coordinator (агент, который раздаёт работу) запускает `orca orchestration worker-start --task … --worktree current|new-child|new-top-level --agent codex [--model --effort]` и заканчивает свой ход;
  - Orca будит coordinator-а, когда worker отчитался, спросил или остановился. Руководство запрещает polling и watch-скрипты.
- **Контракт worker-а** [29]:
  - ровно один `worker_done` с `--outcome succeeded|failed`, кратким итогом, ID задачи и ID dispatch. Два ID нужны, чтобы старый повтор не закрыл чужую попытку;
  - вопросы — через `ask`; ответ приходит письмом;
  - групповые адреса: `@all`, `@idle`, `@codex`, `@claude`, `@worktree:<id>`.
- **Настройки** [72][29]:
  - глубина вложенных workers;
  - автозакрытие законченных workers через 2 минуты, если не отмечено Keep open;
  - «Let coordinators approve worker permission prompts» — coordinator может разрешить запрос прав worker-а, указав причину. Человек всё равно видит Allow и Deny; побеждает первый ответ. Без этой настройки coordinator может только отклонить запрос с причиной.
- **Federated workers.** `--on <host>` запускает worker-а на SSH-хосте или на сопряжённом сервере [29].
- **Версии:**
  - «Orchestrator V3» (v1.4.246) — по словам вендора, заметно экономнее по токенам и надёжнее; работает в CLI и в Chat UI, показывает индикаторы workers [116];
  - с v1.4.251 workers могут запускать своих workers [111];
  - удалённые coordinators на v1.4.257 ещё неактивны [106].
- **Документация расходится с кодом.** Живая страница (2026-11-13) говорит, что панель orchestration и её переключатель «temporarily unavailable», и не упоминает одобрения от coordinator-а. В `main` есть и то, и другое [29]. Панель временно отключили в PR #38045 [126].
- Как это устроено — в разделе «Как это устроено внутри → Параллельность и координация».

### Scheduled automations

- **Создание** — из CLI или со страницы Automations [30]:
  - триггеры: presets (hourly, daily, weekdays, weekly), cron или RRULE (правило повторения из формата iCalendar), с часовым поясом;
  - цель: репозиторий (новый workspace на каждый запуск), существующий workspace или проект на выбранном хосте.
- **Управление запуском** [30]:
  - `--precheck <cmd>` — команда перед запуском; ненулевой exit code пропускает запуск со статусом `skipped_precheck`;
  - grace period для пропущенных запусков;
  - `--reuse-session` продолжает работу в прошлом терминале;
  - дополнительные аргументы агента — только model и effort (и `--add-dir` у Claude);
  - Run now (без precheck), история запусков, Rerun.
- **Таблица на desktop** фильтрует по хосту, включённости, последнему результату и агенту [30].
- **Из changelog:** automations могут идти в чате и сохранять разговор [7]; ими можно управлять с телефона [183]; черновики переживают закрытие мобильного приложения системой [109].

### Review: diff, аннотации, attribution

- **Diff viewer** [34]:
  - общий diff staged, unstaged и untracked изменений относительно start-from ref (точки, от которой ответвился worktree);
  - diff картинок: рядом, swipe, onion skin (наложение с прозрачностью); превью HTML сбоку;
  - трёхсторонний вид конфликтов merge; дерево файлов меняет ширину; базу сравнения можно сменить.
- **Annotate AI Diff** [35]:
  - + в gutter (поле слева от строк) или клавиша `c` на любой строке — и комментарий в Markdown;
  - комментарий остаётся привязан к строке при последующих правках;
  - «Send to agent» отправляет все комментарии одной пачкой, с привязкой к строкам, выбранному или новому агенту;
  - комментарии можно закрывать и отправлять снова.
- **Заметки в Markdown.** В rich Markdown-файлах можно оставлять review-заметки прямо на отрисованном тексте [41].
- **Attribution** [36]: строки, которые написал AI, помечены в gutter. Если человек правит такую строку, пометка снимается. Данные хранятся локально, не коммитятся, их можно экспортировать.

### Commit, push, PR и CI

- **Commit и push** [37]:
  - «Generate with AI» пишет commit message;
  - «Fix with AI» чинит упавший pre-commit hook: агенту велено только исправить, не обходить hooks, не коммитить и не пушить;
  - force-push with lease — отдельное, явно подписанное действие;
  - создание PR или MR с «Generate pull request details with AI»;
  - «Resolve with AI» для конфликтов, плюс Abort merge и Abort rebase;
  - «action recipes» на уровне репозитория задают агента, аргументы и шаблон prompt для каждого AI-действия;
  - чип ветки показывает изменённые строки по группам Source, Tests и Generated.
- **Hosted reviews** [38]:
  - GitHub — глубже всего. GitLab — MR, issues и pipelines, включая логи дочерних pipelines. Bitbucket Cloud — создание PR. Azure DevOps и Gitea — PR в списке;
  - checks, reviews и комментарии открываются прямо в приложении, с ответами и реакциями;
  - «Fix broken checks» отдаёт упавшие checks агенту — названия и ссылки;
  - auto-merge или «Merge when ready» для merge queue;
  - **Stacked PRs** — «Stack this PR above #N» и «Merge through #N · M PRs». Если хоть один слой нельзя смержить, merge стека не начинается.
- **«Resolve N Comments With AI»** запускает агента по выбранным review threads. Потом Orca помечает их resolved, а в тех, которые закрыть не удалось, оставляет ответ [72].
- **Git Graph** — вкладка с ветками, тегами и деталями коммита; checkout, cherry-pick и revert [109][108].
- Отправить review GitHub PR из самого Orca пока нельзя — это открытый запрос #9512 [135].

### Встроенный браузер

Chromium, отдельный на каждый worktree.

- **Основное** [42][121][122]: адресная строка, история, DevTools (можно закрепить в окне), панель загрузок, эмуляция viewport через Chrome DevTools Protocol, правила, какие ссылки открывать в Orca, а какие — в системном браузере.
- **Профили** [44][123][118]:
  - общий, на репозиторий или на workspace; у каждого свой набор cookies;
  - cookies импортируются из Chrome, Edge и Vivaldi, кроме cookies Google;
  - работают passkeys на USB-ключах безопасности.
- **Пароли и расширения.** Менеджер паролей, совместимый с Chrome, хранит пароли в keychain ОС [112]. Расширения из Chrome Web Store — experimental; Bitwarden и 1Password работают [119].
- **Design Mode** [43][55]: клик по элементу страницы отправляет в prompt агента его HTML, вычисленный CSS, обрезанный скриншот и строку исходника, если есть source map.
- **Annotate** — заметки на элементах страницы, которые переживают перезапуск. Агенты читают их через `orca tab annotations` [106].
- **Управление агентом** [27][28][121]: команды `orca snapshot/click/fill/screenshot` со ссылками на элементы вида `@e3`. Курсор и значок на странице показывают, где агент кликает или печатает.
- **Удалённые workspaces.** Страница рисуется на устройстве пользователя, а её трафик идёт через удалённый хост [42].
- По отзыву пользователя, у каждой сессии свои вкладки [249].

### Терминал, раскладка, навигация

- **Терминал** [45][109][115]:
  - xterm.js с рендером на GPU (WebGL) [45][109];
  - Kitty keyboard protocol, буфер обмена через OSC 52 (включён по умолчанию), импорт тем из Ghostty, Warp и Kitty [115];
  - поиск по scrollback, меню действий над ссылкой, «Copy Context»;
  - плавающий глобальный терминал (Cmd+Option+A);
  - Quick Commands — сохранённые команды и prompts агентов; синхронизируются с телефоном;
  - на Windows — PowerShell, CMD или WSL, режим администратора.
- **Раскладка** [13][190]:
  - вкладку можно перетащить к краю pane, чтобы разделить её; разделения вкладываются друг в друга;
  - у каждого worktree своя сохранённая раскладка;
  - вкладки верхнего уровня, а не внутри panes — по словам основателя, одно из отличий от cmux [190].
- **Навигация** [16]: Cmd-P — быстрое открытие файлов; Cmd-J — список последних сессий, сначала те, что ждут человека, с переходом по цифрам.

- **Rich Markdown-редактор**: slash-меню, Mermaid, wiki-ссылки через `[[`, оглавление [41].
- **Просмотрщики**: HTML, Mermaid, PDF, картинки, редактируемые CSV и Jupyter (beta) [41][7].
- **Drag and drop**: файл, брошенный на терминал агента, вставляет свой путь. По SSH файл сначала загружается на хост [41].

### Диктовка

- Модели распознавания речи на устройстве (Parakeet, Whisper, SenseVoice и другие) или транскрипция через OpenAI [52][107].
- Режимы toggle и hold, свой словарь, диктовка на самом телефоне [52][109].

### Удалённая работа

- **SSH targets** [47][7]:
  - импорт из `~/.ssh/config`, проверка host key, jump hosts, Kerberos и FIDO2;
  - Orca ставит на хост свой сервер через подключение пользователя. С версии 1.4.225 такие managed SSH servers включены по умолчанию [7];
  - удалённые терминальные сессии переживают закрытие приложения на ноутбуке;
  - port forwarding с найденными портами;
  - workspace можно открыть в VS Code Remote-SSH, Cursor или Zed.
- **Remote Orca Server** (beta) [48][109][56][46]:
  - сервер владеет проектами, worktrees, терминалами, аккаунтами и агентами; ноутбук, браузер и телефон — только клиенты. Агенты работают, когда ноутбук спит [56][46];
  - сопряжение рекомендуется через Tailscale; у каждого клиента свой отзываемый token;
  - один сервер для нескольких клиентов; чужие workspaces можно скрыть («Hide other-client workspaces»);
  - с v1.4.254: одноразовые коды сопряжения, соединения на «E2EE v2» (новая версия сквозного шифрования), `orca serve` по умолчанию не слушает публичные адреса интернета [109];
  - `orcad` — собственный headless Node-сервер Orca. `orca serve` использует его по умолчанию; на упакованном приложении macOS — сервер desktop-приложения, если не задано `ORCA_SERVE_RUNTIME=orcad` [48].
- **Cloud VM / per-workspace environments** (experimental) [46][107][66]:
  - recipe-скрипты в `orca.yaml` создают, приостанавливают, возобновляют и уничтожают окружение на Vercel Sandbox, Fly, Modal, SSH-хосте или в локальном Docker;
  - провайдера выбирает и оплачивает пользователь;
  - Suspend и Resume видны в интерфейсе [107];
  - skill для recipes требует явного согласия человека перед каждым платным шагом [66].
- **WSL-хосты** появились в сентябре–октябре 2026 [132][7].
- **Порты.** `orca ports` показывает порты, которые слушает workspace [28].

### CLI `orca`, skills, computer use, artifacts, MCP

- **CLI `orca`** [56][27][28]:
  - принцип: всё, что можно сделать в Orca, могут делать и агенты;
  - охватывает репозитории, worktrees, терминалы (`read`, `send`, `wait --for tui-idle`), файлы и diff, браузер, automations, orchestration, аккаунты, хосты, Linear (чтение и запись), artifacts и skills;
  - `--json` даёт машинный вывод.
- **Skills** [33]:
  - `npx skills add https://github.com/stablyai/orca --skill <name>` ставит `orca-cli`, `orchestration`, `orca-computer-use`, `orca-linear`, skills эмуляторов iOS и Android, `orca-per-workspace-env` и `orca-plugin-authoring`;
  - установленный skill — короткий stub: он говорит агенту загрузить полный guide из работающего бинарника (`orca skills get … --reference <name>`). Поэтому флаги в guide не расходятся с версией приложения. Stub также велит предпочитать `--json` и не выдумывать флаги по памяти;
  - встроенный updater переписывает только нетронутые копии, сначала показывает план, а для изменённых копий пишет «You've changed this copy». Папки, которые создал не он, updater не удаляет;
  - своими skills можно делиться по неиндексируемым, отзываемым ссылкам с версиями. Для этого нужен аккаунт Orca. Агент может публиковать такие ссылки только после отдельного разрешения, выключенного по умолчанию.
- **Computer use** (beta) [31]:
  - `orca computer` читает accessibility tree и скриншоты любого desktop-приложения; кликает, печатает, прокручивает и перетаскивает;
  - на macOS действует в фоне и не двигает указатель мыши;
  - блокирует сочетания клавиш выхода, закрытия окна и logout, если их явно не разрешили;
  - секреты можно передавать через stdin.
- **Эмуляторы** — iOS Simulator и Android (через adb) командой `orca emulator` [27][33].
- **Artifacts** — `orca artifacts share` публикует HTML или Markdown как публичную ссылку через аккаунт Orca. Для новых профилей это разрешено по умолчанию [28][106].
- **MCP** — серверы MCP для агентов регистрируются в Settings → Integrations [33][52].

## Принципы и подходы

### Откуда взялся продукт

- **Show HN, 2026-03-27.** Neil Parker опубликовал Orca как «Open Source 'Conductor + Ghostty'» [190]. Его объяснение: команда весь день работает с Claude Code, Codex и Gemini, хотела вести несколько worktrees с несколькими агентами и решила открыть свой внутренний инструмент. Он признал, что похожие программы есть, но эта — своя. Пост набрал 21 point и 10 комментариев [190].
- **Отличия от cmux по словам Neil** [190]:
  - вкладки верхнего уровня, а не вкладки внутри panes;
  - нативная интеграция с GitHub через `gh` CLI;
  - статус агента виден и в неактивных panes;
  - ручная пометка worktree как непрочитанного;
  - кросс-платформенность (cmux работает только на Mac).
- **Product Hunt, около апреля 2026.** В комментарии к запуску Neil писал, что работа с AI стала ощущаться «однопоточной» — по одному агенту за раз. Исследование направления развития нашло на странице запуска 87 upvotes и 45-е место за день [186]. Исследование отзывов нашло статистику запуска только на сайте-агрегаторе и считает её неподтверждённой [187]. Здесь источники расходятся.
- Первый коммит — «Initial commit» из стандартного шаблона Electron/React [57].

### Для кого и чем Orca не является

- **Аудитория** [9]: люди, которые профессионально пишут код и хотят, чтобы AI усиливал их работу, а не заменял их. Предполагается, что пользователь читает diff, следит за коммитами и держит worktree в порядке. No-code инструментом Orca не является.
- **Три «не»** [9]:
  - не модель — подписку Claude, Codex или OpenCode приносит пользователь;
  - не замена git — каждый worktree настоящий;
  - не hosted VPS-продукт.
- **Та же позиция в других местах.** Удалённые режимы всегда используют машины и облачные аккаунты пользователя [46]. Страница Enterprise: Orca не стоит посередине между пользователем и моделью; prompts и код Orca не смотрит и не хранит [2].

### «Built for agents»: CLI как интерфейс агента

- **Позиция главной страницы** [1]: редакторы сделаны для одного человека, который печатает; обёртки над агентами заканчиваются терминалом; Orca — вся среда: worktrees, review, браузер и удалённые хосты в одном приложении. IDE сделана для человека, ADE — для человека и его агентов.
- **Главный принцип** [56][1]: всё, что можно сделать в Orca, агенты тоже могут делать из командной строки — создавать worktrees, запускать workers, управлять браузером и desktop-приложениями, ставить automations.
- **Skills — короткие stubs**, которые загружают guide из работающего бинарника, чтобы инструкции не расходились с версией приложения [33].

### Worktree на задачу и best-of-N

- **Worktree-native** [11]: каждая задача получает свою копию репозитория на диске через `git worktree`. Документация говорит, что именно это делает параллельных агентов безопасными.
- **Основной сценарий — best-of-N** (несколько агентов решают одну задачу, человек выбирает лучший результат) [10]. Страница, которую документация называет самой важной, предлагает запустить Claude Code, Codex и Cursor CLI на одном prompt, выбрать лучший результат, просмотреть diff и отправить. Цикл «add → worktree → agent → watch → diff → ship», по словам документации, и есть весь Orca.

### Автономия по умолчанию; позиция смягчилась

- **Bypass прав по умолчанию** [131]:
  - PR #5145 (2026-06-11) сделал полную автономию агентов поведением по умолчанию;
  - PR #5440 (2026-06-16) добавил глобальный переключатель Yolo / Manual;
  - PR #26116 (2026-10-12) добавил режимы прав для отдельного чата.
- **Обоснование** — worktree и есть sandbox [14]. Более поздняя страница (2026-11-11) говорит обратное и советует Manual [17].
- **Запрос на промежуточные режимы.** Пользователи просили режим Auto из Claude Code и «Approve for me» из Codex (#13081, 22 👍, закрыт 2026-10-20) [140][135]. В коде на `main` появился общий вариант «Approve for me» [72].

### Уважение к соглашениям агентов

- `CLAUDE.md` и `AGENTS.md` принадлежат агенту; Orca их не трогает [25].
- Статус берётся у самих агентов — из OSC-последовательностей и hooks. Свои «Orca-managed hooks» Orca ставит только для статуса working / waiting / done [14][25].
- Нейтральность к провайдерам — правило для contributors: общее поведение не должно зависеть от конкретного CLI-агента, интеграции или git-провайдера [59].
- Orca не обновляет CLI агентов сама. Объяснение команды: интеграция опирается на поведение CLI, и новая версия CLI может её сломать (Discussion #24978, 2026-10-03) [176].

### «First-class» требования и стиль интерфейса

- **Четыре обязательных вопроса к каждой правке** [58]. Список стоит в AGENTS.md — файле инструкций для coding-агентов в репозитории; добавлен 2026-10-20 (PR #31265):
  1. кросс-платформенность;
  2. удалённые хосты;
  3. мобильное приложение;
  4. folder workspaces — нельзя считать, что каждый workspace это git worktree.
- **Внешний вид** [60]: интерфейс монохромный и тихий. Orca в основном показывает чужие инструменты (Monaco, xterm, превью Markdown), поэтому собственный UI должен быть незаметной рамкой вокруг них.
- **Учёт задержек** [60]: если действие быстрое локально и медленное по SSH, видимое состояние загрузки показывается только примерно через 200 мс.
- **Функции включаются по возможностям другой стороны**, а не по номерам версий. Это правило Orchestration v3 [127].

### Как команда выпускает

- **Каждый день.** README говорит, что список функций всегда отстаёт, а настоящий список — changelog [56]. Главная обещает новые функции каждый день [1].
- **Правила репозитория** [58][59]:
  - `main` всегда готов к релизу;
  - PR небольшие и сфокусированные;
  - шаблон PR требует объяснение «ELI5» (простыми словами), Visual Proof (до и после), уровень риска и способ отката;
  - в разделе Review автор вставляет короткий итог review от своего coding-агента.
- **Performance-PR** принимаются, только если выигрыш «бесплатный», очень большой или оправдывает размер изменения и будущую поддержку (Discussion #27143, 2026-10-10) [177].
- **Orca строят с помощью агентов** [181][59][105]:
  - 1 499 слитых PR заканчиваются строкой «Made with Orca 🐋»;
  - шаблон PR просит итог review от агента;
  - бот `buf0-bot` присылает исправления с пометкой «pr-bug-scan validated finding».
- **Triage issues частично ведут агенты** от имени аккаунтов основателей. В одном комментарии maintainer-а сказано, что «этот агент» работает на macOS и не может проверить Windows. Issue о задержке ввода закрыт автоматическим «cannot reproduce», в котором остался незаполненный placeholder шаблона [154].

### Политика тестов

- **Сейчас** AGENTS.md велит не добавлять тесты по умолчанию: тесты малой ценности стоят дороже, чем ловят; если трогаешь такой тест — удали его, а не обновляй [58].
- **История** [58]: 2026-10-27 формулировку «low value» заменили на «negative value» (PR #34507); 2026-11-04 правило ужесточили (PR #37993).
- **Массовое удаление** [181]: с 2026-10-06 по 2026-11-13 слиты 642 PR со словами «low-value test» в заголовке, 640 из них — от аккаунта OrcaWin. В 430 заголовках есть число удалённого, их сумма — около 85 000. Это грубая оценка по заголовкам: где-то число считает test cases, где-то declarations или suites.

### Человек отвечает за результат, автоматизация — opt-in

- Orchestration не закрывает сама workers, которые остановились без отчёта: она сообщает coordinator-у, и ничего не решается автоматически [127].
- Разрешить запрос прав worker-а может только человек — если не включена opt-in настройка для coordinator-ов [29][129].
- PR о лимитах в чатах подчёркивал, что автоматического продолжения не добавляет [128]. Следующий PR добавил его как opt-in (см. «Функции → Лимиты подписки в чатах») [133].

### Чем подход отличается

- **Среда вокруг чужих агентов.** У Orca нет своего агента и своей модели. Ценность — в окружении: worktrees, review, браузер, хосты, телефон [17][9][1].
- **Единица работы — workspace (git worktree)**, а не задача, эпик или проект [11].
- **Ширина охвата:** около 39 агентов, 10 провайдеров usage; desktop, web, телефон, SSH, сервер и cloud VM [17][24][46].
- **Автономия по умолчанию.** Агенты запускаются без запросов прав; контроль — через diff, PR и CI [17][35][38].
- **Orchestration как протокол, а не планировщик.** Orca даёт почту, задачи, dispatch и защиту от повторов, а разбивает работу LLM-coordinator [29][64][82].
- **Ставка на скорость выпуска:** релиз почти каждый день, тесты по умолчанию не добавляются [105][58].
- **Бесплатно и MIT**, без платного тарифа и без объявленной модели монетизации [1][56].

### Процессы и модули

- **Несколько процессов, которые работают вместе** [56][61][63]:
  - Electron-приложение: main process (`src/main`), preload и React renderer;
  - CLI (`src/cli`) и гостевая часть для WSL;
  - мобильное приложение на Expo (`mobile/`);
  - облачный relay (`cloud/`).
- **Terminal daemon владеет всеми PTY** (псевдотерминалами, в которых идут агенты). Поэтому агенты переживают выход из приложения, перезапуск при обновлении и падение; при следующем запуске приложение подключается к тем же процессам [15].
  - Правила для пути socket записаны в собственном `AGENTS.md` daemon-а. Они появились, потому что прежний вариант дал «двадцать три дефекта» за «семь раундов review» [67].
  - Правила: занять приватное имя; попробовать эксклюзивный `link`; доказать, что текущий владелец мёртв, подключившись к нему; затем сделать `rename` одним вызовом. «Не могу определить» никогда не считается «мёртв». Отдельного процесса для уборки нет [67].
- **`orcad`** — собственный headless Node-сервер Orca для `orca serve` [48].
- **`@orca/process-host`** — общий пакет для запуска процессов, ограничения вывода и завершения дерева процессов. Его используют desktop-приложение, headless-сервер, CLI, SSH relay и daemon [68].
- **Версии Node:** серверный код — Node 24, launcher и CLI — Node 18 [61].
- **Как CLI находит runtime** [73]: подключается по Unix socket (named pipe на Windows); endpoint и `authToken` читает из метаданных runtime в папке user-data; отказывается от перенесённого socket, если его папка доступна не только этому пользователю.
- **Связь с телефоном** [63][74]: телефон и desktop открывают исходящие WebSocket-соединения к relay-«cell»; «director» распределяет хосты по cells; отдельный gateway отправляет push через APNs и FCM. Сопряжённые клиенты получают публичные ключи из QR-кода и сами строят шифрование ECDH (обмен ключами на эллиптических кривых) поверх обычных WebSockets.

### Цикл агента: своего нет

- **Orca оборачивает чужие CLI.** По документации, выбор агента просто запускает процесс в терминале [17]. Рассуждение, план и вызовы инструментов — внутри самого агента.
- **Транспорт 1 — терминал** (TUI, текстовый интерфейс агента, в PTY) [75][88]:
  - Orca печатает prompt в PTY и нажимает Enter;
  - потом проверяет, что новый ход действительно начался. Доказательством считается событие hook о начале хода, lifecycle-последовательность агента или вывод после Enter;
  - если начала не видно за 30 с, prompt помечается «stalled» [75];
  - в orchestration dispatch с невидимым началом остаётся активным. Orca не отправляет prompt снова: Enter мог уже дойти [88].
- **Транспорт 2 — структурированный чат** [76]:
  - Claude — через `@anthropic-ai/claude-agent-sdk`, направленный на установленный у пользователя Claude CLI;
  - Codex — через протокол app-server самого Codex;
  - Copilot, Grok, Kimi, OpenCode, OMP и Antigravity — через слой Agent Client Protocol (ACP, открытый протокол связи редактора с агентом) с отдельным «dialect» на агента.
- **По умолчанию — терминал.** Новые установки открывают Terminal [21]. Перенос между чатом и терминалом делает копию с ограниченным отрывком: 8 000 символов на сообщение или блок инструмента, 1 000 на вход, 2 000 на выход инструмента [21][77].
- **Claude Agent Teams** [78][17]: Orca направляет переменную `TMUX` у Claude на `/tmp/orca-claude-agent-teams/`, где tmux-сервер не слушает. Shim tmux (подменная программа с интерфейсом tmux) превращает panes участников команды в обычные panes Orca. Функция выключена по умолчанию.

### Как Orca узнаёт, что делает агент

Три источника пишут в одно хранилище статуса. Приоритет — сверху вниз.

1. **Managed hooks** (высший приоритет) [69][79][25]:
   - hooks каждого агента отправляют POST на HTTP-сервер Orca на loopback: состояние, prompt, имя и вход инструмента, ответ агента, ID сессии у провайдера, модель, subagents [69];
   - для Claude Orca пишет hooks в `settings.json` папки конфигурации Claude. События: SessionStart, UserPromptSubmit, Stop, StopFailure, SubagentStart/Stop, TeammateIdle и PreToolUse. Ещё Orca ставит свой status-line script [79];
   - скрипты hooks перечитывают `{userData}/agent-hooks/endpoint.env` при каждом вызове. Поэтому агент, который работает дольше приложения, попадает в перезапущенную Orca, а не в закрытый порт [25].
2. **OSC 7501, «Program Status Protocol»** [69]:
   - Orca разбирает эту escape-последовательность в выводе PTY;
   - hooks важнее. OSC 7501 берёт верх, если hooks выключены, не установлены или 2 минуты молчат о состоянии, из которого программа уже вышла;
   - поддержка на 2026-10-17: Claude Code с версии 2.1.295, Grok, pi и omp; Codex сообщает только состояние.
3. **Декларативные правила по экрану и заголовку** [80]:
   - JSON-правила для каждого агента. Пример: префикс `✳` в заголовке окна Claude значит idle, но только как «слабый» вывод — нужен ещё и тихий экран;
   - правила скачиваются заново каждые 4 часа из release-asset `agent-state-rules.json` на GitHub. Исправления распознавания выходят без релиза приложения;
   - лимит — 256 KiB. Regex с backreferences, lookbehind или неоднозначными повторяющимися группами отклоняются, чтобы не было катастрофического backtracking (взрывного роста времени проверки regex);
   - подписан ли скачиваемый пакет правил — не подтверждено. Проверки подписи в прочитанных файлах не нашлось.
- **Что видит пользователь:** working, waiting on you, done, blocked/failed и idle; Agent Dashboard и Agents feed [14][51].

### Параллельность и координация

Параллельность в Orca двух видов. Первый — человек сам запускает много агентов в разных worktrees и следит за ними через sidebar, dashboard и feed [10][14][51]. Второй — experimental orchestration, где агент-coordinator раздаёт задачи агентам-workers [29].

#### Модель данных и хранение

- **Пять сущностей** [29]:
  - **Run** — пространство имён и inbox coordinator-а. Сам Run никогда не планирует и не размещает workers;
  - **Task** — spec, зависимости и статус;
  - **Dispatch** — одна попытка задачи в одном терминале. Именно dispatch даёт право отчитаться о завершении;
  - **Message** — письмо между coordinator-ом и workers;
  - **Decision gate** — вопрос, который блокирует задачу, пока на него не ответят.
- **Всё хранится в SQLite**, файл `{userData}/orchestration.db` [81]:

| Таблица | Состояния и ключевые поля |
|---|---|
| `tasks` | pending, ready, dispatched, completed, failed, blocked; `deps` — JSON-массив |
| `dispatch_contexts` | pending, dispatched, completed, failed, `circuit_broken`; плюс `failure_count`, `depth`, `consumer_generation`, `retry_of_dispatch_id`, `last_heartbeat_at` |
| `worker_dispatches` | starting, ready, start_unknown, failed, succeeded, stopping, stop_unknown, stopped, abandoned |
| `messages` | типы: status, dispatch, worker_done, merge_ready, escalation, handoff, decision_gate, question, heartbeat; приоритет normal / high / urgent |
| `deliveries` | outstanding, acknowledged, fenced |
| `worker_terminal_resources` | владение: owned, transferred, user_owned, external, released |
| `decision_gates` | pending, resolved, timeout |

- Ещё есть таблицы relay для работы между машинами и архивы вывода workers. Миграции схемы дошли до v46 [81].

#### Кто разбивает работу на задачи

- **LLM-агент coordinator, а не код Orca.**
- **В коде ещё есть старый встроенный `Coordinator`** [82]:
  - опрашивал состояние каждые 2 с, держал не больше 4 workers одновременно и создавал не больше одного нового терминала за цикл;
  - автоматической декомпозиции у него не было: без готовых задач он падал с «No tasks found…», а комментарий в коде говорит, что задачи надо создавать заранее, пока декомпозиция не реализована;
  - его RPC-методы `orchestration.run` и `runStop` теперь отклоняются как выведенные из работы, с ответом, что никаких изменений не сделано [82][29];
  - команды `orca orchestration run`, `run-stop`, `coordinator-start` и `coordinator-stop` ничего не делают [29].
- **Протоколу coordinator-а учит skill `orchestration`** [64]. Spec задачи должен назвать:
  - цель и само изменение;
  - ограничения и что worker может править;
  - какие доказательства покажут, что задача сделана;
  - считается ли ненулевой exit code провалом.
- **Граф зависимостей.** Задачи получают `--deps`. Skill велит при каждом пробуждении запускать задачи из `task-list --ready` [64]. Когда задача завершается, зависимые задачи становятся ready в той же транзакции БД, если все их зависимости completed [83].

#### Цикл coordinator-а: закончить ход и ждать, пока разбудят

- Coordinator запускает workers и заканчивает свой ход. Orca будит его, когда worker отчитался, спросил или остановился [29].
- **Пробуждение — строка, напечатанная в терминал coordinator-а:** «You have N orchestration messages. Run `orca orchestration check`.» [84]
  - её отправляют, только когда агент в покое или может поставить ввод в очередь;
  - каждый байт и Enter отслеживаются, пока запись не подтверждена [84];
  - coordinator в чате получает каждое письмо целиком, как отдельный ход [64].
- **Чтение почты.** `check` отдаёт самое старое непрочитанное письмо как одну «Delivery» и помечает его обработанным. `--peek` и `--all` читают, не забирая [29].
- **Polling запрещён.** Если скрипт вызовет `check`, он заберёт письмо, и Orca будет нечем будить агента [64].
- **Orchestration v3** (PR #36137, merged 2026-10-30; вышла в 1.4.246) [127][116]:
  - раньше coordinators ждали внутри хода длинными блокирующими вызовами, опрашивали состояние и сами вели учёт;
  - теперь заканчивают ход, а Orca будит их по отчётам workers; законченные workers закрываются сами;
  - замер команды: 27 правильных запусков из 27 против 26 из 27; токены на двух параллельных workers — 232k вместо 351k (−34%).

#### Запуск worker-а и его контракт

- **`worker-start` идёт по этапам** [85]:
  1. синхронно вставить строку dispatch — это занимает терминал;
  2. разместить worker-а: текущий worktree или новый (вложенный в worktree coordinator-а или верхнего уровня), в терминале или в чате; затем setup;
  3. ждать готовности агента — по умолчанию до 60 с: idle TUI или прохождение setup;
  4. записать, какая pane и какой процесс владеют dispatch;
  5. доставить worker-у инструкции («preamble»).
  - При сбое возвращается квитанция с названием этапа: `terminal_create`, `setup_start`, `setup_wait` или `agent_readiness`. Model и effort задаются на каждого worker-а [85][29].
- **Что говорит preamble** [86]:
  - ID задачи и адрес coordinator-а;
  - делать только эту задачу и самому — без subagents и помощников, если задача их не просит;
  - не задавать локальных вопросов вроде AskUserQuestion: coordinator их не видит;
  - отправить ровно один `worker_done` из трёх предложений — что сделано, что найдено, что осталось;
  - ставить `--outcome failed`, если работа не сделана, и не прятать провал в тексте;
  - после отчёта вернуться к idle-prompt и не опрашивать состояние;
  - прямая инструкция пользователя важнее правила про idle.
  - Раздел о своих sub-dispatch появляется, только если глубина вложенности ещё позволяет помощников.
- **Вопросы.** `ask` записывает вопрос и сразу возвращает pending. Worker заканчивает ход; ответ придёт письмом [29].

#### Как повторы не ломают учёт

- **Для завершения нужны два ID** — задачи и dispatch, чтобы старый повтор не закрыл чужую попытку [29].
- **Счётчик поколений.** `consumer_generation` растёт, когда dispatch переназначают на другую pane или процесс. Это отменяет доставки, которые прошлый владелец не подтвердил [81].
- **Кто исполнитель.** Dispatch хранит ключ pane, «incarnation» процесса (номер его запуска), hash launch-token и хост [81][88]. Capability tokens dispatch (`dcap_…`) маскируются в видах терминала [89].
- **Повторные вызовы CLI безопасны.** Каждая мутация хранится по отпечатку вызывающего и ID запроса, вместе с hash payload. Хранилище держит не больше 10 000 строк и не дольше 30 дней [81][87].

#### Обнаружение сбоев и восстановление

- **Сообщения об остановке хода.** Ход worker-а может закончиться как finished, errored или needs-input, пока его dispatch ещё открыт. Тогда Orca сама пишет coordinator-у: причина плюс последнее сообщение агента или отредактированный хвост экрана. Если это запрос прав, он прикладывается [89].
  - Skill: при остановке с причиной — направить worker-а через `send`, остановить и повторить или сказать пользователю; при `exited` или `lost` — повторить или сказать пользователю [64].
  - Жалоба пользователей, что об остановившемся агенте orchestrator не узнаёт и ждёт бесконечно, относится к версиям до Orchestration v3: discussions #26273 и #28601 открыты 2026-10-07 и 2026-10-14 [168]. Сообщения об остановке хода добавила v3 (2026-10-30) [127][89]. Пробел остался, его признаёт сам PR v3: если процесс агента умер, а shell жив, coordinator об этом не узнаёт [127].
- **Circuit breaker после трёх неудач** [90][65]:
  - три неудачных старта в одной цепочке повторов помечают dispatch `circuit_broken` и проваливают задачу;
  - текст отказа говорит, что Orca больше не будет повторять, и велит сообщить пользователю;
  - собственный отчёт worker-а о провале в эти три не входит;
  - skill запрещает обходить breaker новым Run, новой Task или сбросом счётчика. Только по явной просьбе пользователя coordinator может открыть ту же задачу заново, как новую серию.
- **Действовать только по доказательствам** [64][65]: тишина, timeout или liveness «unverifiable» сами по себе не доказывают, что агент вышел, и не разрешают автономное восстановление. `worker-stop` выходит с кодом 1 и состоянием `stop_unknown`, если не может доказать остановку.
- **Проверка устаревшей базы** (найдена только в пути выведенного coordinator-а) [88][86]:
  - dispatch отклоняется, если worktree отстал от base больше чем на 20 коммитов. Комментарий в коде ссылается на реально наблюдавшееся отставание на 168 коммитов;
  - строка `allow-stale-base: true` в spec отключает проверку; реальное отставание показывается worker-у в preamble;
  - применяет ли проверку текущий `worker-start` — не подтверждено.
- **Тупик.** Если все оставшиеся задачи заблокированы и ни одна не идёт, Orca пишет в log «Stuck… Resolve decision gates to continue» [83].

#### Вложенность, другие машины, уборка

- **Глубина вложенности** — 4 по умолчанию. Менять её можно только в интерфейсе: код держит эту настройку вне settings RPC, чтобы workers не могли поднять себе лимит [91].
- **Workers на другой машине.** `--on <server>` запускает worker-а на сопряжённой Orca. Почта между машинами нумеруется и подтверждается в обе стороны. Ответы приходят в почтовый ящик coordinator-а [81][64].
- **Уборка законченных workers.** Их терминалы закрываются через 2 минуты; это включено по умолчанию. Перед закрытием вывод архивируется — как закреплённый transcript, хвост терминала или структурированный журнал. `worker-read` работает и после закрытия терминала [92][81][29].

#### Запросы прав внутри orchestration

- **По умолчанию разрешить может только человек.** Escalation называет запрос; coordinator может отклонить его с причиной [29].
- **Opt-in настройка** «Let coordinators approve worker permission prompts» выключена по умолчанию. Побеждает первый ответ — человека или coordinator-а. Применяет настройку та машина, где идёт worker [29][94].
- **Правила из PR #41306** [129]: одобрение требует причины; проверки, на которые может ответить только человек, остаются за человеком; правил о том, что безопасно одобрять, текст не добавляет — политики одобрения нет.
- **Ответ ограничен:** Orca может выбрать только «allow once» или «reject once», но никогда не постоянное правило [93].

### Изоляция

- **Один git worktree на задачу** [11]: создание в фоне с прогрессом, отменой и повтором; старт от base ref, локальной ветки, SHA коммита или удалённой ветки.
- **Файлы, которые игнорирует git** (зависимости, cache, секреты), попадают в новые worktrees тремя путями: общие пути пользователя, `worktree.sharedDirectories` и `.worktreeinclude` [12]. Подробности — в «Функции → Настройка репозитория».
- **Setup и teardown** — через скрипты `orca.yaml`; `wait-for-setup` держит агента до успешного setup [12].
- **Пул подготовленных checkouts**: до 3 штук на 5 минут, сброс при сдвиге base [95].
- **Worktree — не security sandbox.** Документация говорит об этом по-разному: одна страница — что worktree это изолированная копия, но не security sandbox [17], другая — что задумано, чтобы worktree и был sandbox [14].
- **Настоящая изоляция — VM или контейнер на workspace** по recipe: скрипты create, suspend, resume и destroy, подключение через `orca serve` или SSH [46]. Skill для recipes задаёт «autonomy envelope»: перед каждым платным шагом агент должен получить явное «да» [66].
- **Docker sandboxes для агентов** — открытый запрос #13665 (26 👍) [141].

### Состояние и память

- **SQLite-файлы** [81][96]: `orchestration.db`; `profile-state.db`; `last-status.db` — последний статус из hooks; `ai-vault/session-search.sqlite` — индекс поиска по сессиям; cache GitHub.
- **Hibernation**: выключена по умолчанию; порог 30 минут (от 1 минуты до 24 часов); только для агентов с resume; не трогает агентов с незакрытым dispatch и с живыми subagents или teammates; возвращение — командой resume, например `claude --resume <id>` [23].
- **История сессий** читается из собственных хранилищ агентов (например, `~/.codex/sessions` и история Claude); resume в один клик [22].
- **Память агентов Orca не трогает.** `CLAUDE.md` и `AGENTS.md` принадлежат агенту; Orca читает конфигурацию `.claude/` и `.codex/` каждого репозитория [25].
- **Отдельного долговременного хранилища памяти** в прочитанном коде не найдено. Это отсутствие доказательств, а не доказательство отсутствия.
- **Как контекст переходит между агентами и людьми:**
  - комментарий и статус на карточке worktree (`orca worktree set --comment`) [32];
  - ограниченный отрывок при переносе разговора между чатом и терминалом [77];
  - архив вывода workers [92];
  - индекс поиска по сессиям [96].
- **Skills как stubs.** Установленный `SKILL.md` только говорит, когда использовать Orca и как загрузить полный guide. Бинарник отдаёт guide своей версии (`orca skills get <topic>`); `--reference` загружает один справочный файл, поэтому агент тратит контекст только на то, что читает [33].

### Проверка качества

- **Встроенного test runner, verification gate и reviewer-агентов** в коде и документации не найдено. Проверка приходит из четырёх мест:
  - **доказательства от worker-а** — spec требует их; coordinator их суммирует и перепроверяет только при пробеле или противоречии [64];
  - **review человеком в приложении** — Annotate AI Diff (комментарии к строкам пачкой агенту) и Attribution (какие строки написал AI) [35][36];
  - **hosted CI на PR** — панель Checks, «Fix broken checks», auto-merge, merge queue и merge стека [38];
  - **упавшие commit hooks** — «Fix with AI» отдаёт вывод hook агенту и не просит обходить hooks, коммитить или пушить [37].
- **Свой reviewer у Codex.** У Codex есть reviewer одобрений (`auto_review`); Orca только читает эту настройку [97].
- **В собственной разработке** Orca тесты по умолчанию не добавляют, а малоценные удаляют [58].

### Восстановление после сбоев

- **Процессы агентов отделены от окна.** Daemon держит PTY; агенты переживают выход, падение и обновление приложения; после перезагрузки машины возвращаются раскладка и scrollback [15].
- **Hooks находят перезапущенное приложение** через `endpoint.env` [25].
- **Prompt, который не начал ход,** помечается «stalled» через 30 с; в orchestration его не отправляют повторно вслепую [75][88].
- **Orchestration:** сообщения coordinator-у об остановке worker-а, circuit breaker после трёх неудачных стартов, восстановление только по доказательствам [89][90][64][65].
- **Повторы без двойного эффекта:** журнал кредитов сброса лимита Codex, квитанции мутаций CLI [101][87].
- **Лимиты:** автопродолжение в Chat UI после сброса (opt-in) [100].
- **Известные провалы восстановления** (подробности — в «Что говорят пользователи»): после обновлений оставались работать daemons старых версий (#9138) [156]; фоновые `git`-процессы накапливались до зависаний (#16038, исправлено) [155].

### Лимиты и стоимость

- **Чтение usage.** Для Claude Orca опрашивает `api.anthropic.com/api/oauth/usage` примерно раз в 15 минут, пока окно в фокусе. Показывает время сброса и чип на 80% — примерно для десяти провайдеров [24].
- **Status line Claude как источник лимитов.** Claude 2.1.80 и новее кладёт rate limits в данные status line. Managed status line Orca отправляет их не чаще раза в 15 с. Так Orca обходит опрос usage endpoint, который, по комментарию в коде, отвечает 429 при работе под Orca [98].
- **Аккаунты.** Каждый аккаунт — в своей папке (`CLAUDE_CONFIG_DIR` у Claude, отдельный home у Codex). Переключение ручное; квоты не складываются. При смене работающие сессии Claude следуют настройке ask / restart / keep [20][99].
- **Автопродолжение после лимита — только Chat UI, выключено по умолчанию** [100]: проверка каждые 10 с; после сброса отправляется «Continue where you left off.»; если аккаунт ещё показывает израсходованное окно — ожидание дольше и свежие данные usage; не больше 5 автопродолжений подряд; отказ, если сброс опоздал больше чем на 24 часа; отмена человеком переживает перезапуск.
- **Кредиты сброса лимита Codex** тратятся из Orca; вызовы пишутся в журнал, чтобы повтор не потратил кредит дважды [101][24].
- **Orchestration не смотрит на usage.** Открытый issue #24157 (2026-09-30): `worker-start` и automations запускают worker-а одинаково при 10% и при 99% лимита [150].
- **Автоматический resume терминальных агентов после сброса** — открытые запросы #8133, #18799, #40807 [144][146][147].
- **Heartbeats до v3.** До Orchestration v3 каждый heartbeat worker-а будил coordinator-а на полный ход модели. У пользователя на v1.4.224 так 5-часовое окно уходило примерно за 2.5 часа [168]. v3 (2026-10-30) убрала heartbeats workers: старые записываются как состояние, а не как письмо [127].
- **Стоимость** — оценка по локальной таблице цен, «inferred pricing» [24].
- **Расход лимита зависит от способа запуска.** По замерам двух пользователей, Claude Code в режиме SDK или stream-JSON (так работают вкладки чата Orca) тратит 5-часовое окно в 1.5–2.9 раза быстрее, чем интерактивный CLI на той же работе (не подтверждено) [153].

### Права и безопасность

- **По умолчанию — полный доступ.** Каждый агент запускается со своим bypass-флагом: `--dangerously-skip-permissions` у Claude, `--dangerously-bypass-approvals-and-sandbox` у Codex, `--yolo` у других. Chat UI тоже по умолчанию `full-access` [17][94].
- **Plugin hooks как слой политик** [62]:
  - `agent.launch.before`, `agent.prompt.before`, `agent.tool.before`, `terminal.send`, `workspace.create.before`, `editor.save.before`;
  - каждый может отклонить действие или переписать его;
  - у обработчика 2 с. Медленный, упавший или ошибочный обработчик считается пройденным, если hook не задал `"onError": "deny"`;
  - изменения от plugins пишутся в audit log.
- **Заблокировать вызов инструмента можно только у Claude Code на macOS и Linux.** Его PreToolUse-скрипт ждёт решения Orca до 8 с. Остальные агенты только сообщают о вызовах [69].
- **Вывод исследователя:** любой процесс, запущенный от имени пользователя, может управлять Orca. Доступ к runtime даёт token в файле user-data, а прочитать его может любой процесс того же пользователя, включая агентов [73].
- **Агенты не публикуют ссылки на skills** без отдельного разрешения, выключенного по умолчанию [33].
- **Computer use** блокирует сочетания выхода, закрытия и logout, если их явно не разрешили [31].
- **Remote server:** отзываемый token на клиента, одноразовые коды сопряжения, «E2EE v2», отказ слушать публичные адреса [48][109].
- **Вырезание секретов:** локальная трассировка убирает tokens Anthropic, OpenAI, GitHub, AWS и Slack, JWT, блоки PEM и строки `.env` [102]; хвосты экранов workers в сообщениях coordinator-у тоже редактируются [89].
- **Защиты в работе с git:** «Fix with AI» не обходит hooks; force-push with lease — отдельное действие; массовое удаление веток с несмерженными коммитами требует отдельного шага review [37][11].
- **Обещания Enterprise:** «No silent changes» — каждое изменение агента попадает в worktree и PR; «Audit trail by default» [2].

- На Product Hunt всего три отзыва, все на 5 звёзд и помечены как отзывы основателей. Для мнения пользователей это не источник [187].

### Общий тон

- На HN с июля по ноябрь 2026 отзывы в основном положительные — среди тех, кто запускает много агентов одновременно. Многие называют Orca основным рабочим инструментом или основной ADE [192][194][197][202][207][229].
- Больше всего хвалят удалённые runtime и приложение для телефона [201][202][214][224][225].
- Устойчивое меньшинство считает Orca тяжёлым, медленным, глючным, перегруженным или небезопасным по умолчанию. Несколько человек вернулись к более лёгким Herdr и cmux [208][209][210][216][226].
- Повторяется усталость от категории: такие инструменты считают взаимозаменяемыми [204][210][215]. Двое заметили, что надстройку над несколькими агентами («meta harness») пока используют немногие [221][230].
- В issues на GitHub преобладают запросы опытных пользователей (несколько репозиториев, редактор и language server, несколько аккаунтов и лимиты) и баги производительности и надёжности [136]–[157].

### Что ругают и почему уходят

- **Тяжёлый, медленный, на Electron.**
  - Один пользователь нашёл Orca слишком тяжёлым и медленным и окончательно ушёл на Herdr [210].
  - Другой противопоставил Herdr, написанный в основном на Rust, и Electron в Orca [210].
  - Для кого-то Orca перегружен и избыточен по сравнению с cmux [208].
  - Комментатор YouTube вернулся на Herdr, потому что остальные инструменты едят слишком много памяти [242].
  - Пользователи Herdr называют его намного легче и проще для начала [233].
- **Баги интерфейса и нестабильность.**
  - Пользователь неделю работал в Orca и вернулся на Herdr: кнопки не работали, меню не закрывались. Он собирается вернуться, когда продукт станет стабильнее [216].
  - Зритель Christian Lempa счёл Orca слишком глючным для серьёзной работы: падали computer use, orchestration и сессии [232].
  - Довольный пользователь всё равно теряет соединения с workspaces, и их трудно восстановить [214].
  - У русскоязычного зрителя CLI `orca` перестал работать на следующий день: его блокировал лишний процесс Orca, который не удавалось завершить [235].
- **Слишком много функций и репутация продукта, написанного AI.**
  - Пользователь HN, который сам работает в Orca каждый день, назвал продукт небрежным, перегруженным функциями и с плохим редактором [209].
  - При запуске ранний пользователь благодарил команду за README, написанный не AI [190].
  - Часть triage в issues пишут агенты (см. «Принципы → Как команда выпускает») [154].
- **Слабый редактор.**
  - Ушедший пользователь: правка слишком медленная, нет vim-биндингов и настройки shell по умолчанию [191].
  - Запросы на редактор — среди самых популярных: встроенный VS Code (46 👍), language server (44, 39 и 24 👍), git blame (34 👍), пресеты клавиш из других редакторов (25 👍) [138].
- **Всё начинается с worktree; функции трудно найти.**
  - Даже быстрая правка начинается с создания worktree, а каждый проект надо сначала настроить [211].
  - Другой пользователь полчаса искал вид diff [197].
  - Sidebar трудно читать, когда агентов много и они в нескольких репозиториях [172].
  - Настройка удалённых хостов спрятана и неочевидна [224].
- **Опасные права по умолчанию.**
  - Документация подтверждает, что агенты по умолчанию запускаются с bypass-флагами, и предупреждает, что worktree — не security sandbox [17][52].
  - В июне 2026 пользователи просили перестать запускать агентов в bypass по умолчанию (#5385) [142].
  - В ноябре пользователь HN назвал Orca опасным: всё идёт в bypass, а загнать Orca в sandbox трудно [226].
  - Главный совет одного обзора — переключить на Manual до начала работы [243].
  - Спрос на промежуточный вариант: поддержка промежуточных режимов прав агентов (22 👍, issue закрыт) [140] и Docker sandboxes для агентов (26 👍) [141].
- **Windows (WSL) и headless-установки работают хуже.**
  - Chat UI не работает через WSL [227].
  - Подключение проекта внутри WSL почти стало для зрителя причиной отказаться [233].
  - Установка на headless-сервер не удалась у пользователя HN [198].
  - Онбординг orchestration и computer use на Windows не сработал у другого пользователя [154].
- **Почти ежедневные релизы и регрессии.**
  - 28 стабильных релизов за 30 дней [105]; пользователи просят более медленный, проверенный stable-канал (#37651) [158].
  - Главный минус по одному обзору — приложение меняется почти каждый день [244].
  - Сайт сравнений предупреждает, что подписи в интерфейсе часто меняются [251].
  - Переключатель чат/терминал на вкладке пропал в 1.4.193 без упоминания в release notes, пользователи просили вернуть [139].
- **Утечки памяти и ресурсов** — см. «Истории сбоев» ниже [156][157].
- **Шум уведомлений:** спам и ложные запросы внимания [161].
- **Ввод на корейском и других CJK-языках** — длинные треды с багами [162].
- **Нет работы с несколькими репозиториями.** Это самый популярный запрос [136].
  - Русскоязычный зритель остаётся на Herdr, пока одна задача не сможет охватывать несколько репозиториев с общим контекстом [235].
  - Пользователь HN использует Orca вместе с другим инструментом, потому что ни Orca, ни Herdr не работают с несколькими проектами сразу [199].
- **Усталость от категории.**
  - Пользователи пишут, что таких инструментов очень много [215], что они одинаковые [210] и по сути это один продукт [204].
  - Человек, который ушёл из категории, всегда возвращается к обычным Claude Code и Codex [221].
  - Комментатор Better Stack высмеял канал за то, что каждый новый инструмент там «лучший» (65 лайков) [231].
- **Опасение насчёт условий использования.** Комментатор YouTube считает, что условия Anthropic и Google запрещают программное или удалённое управление их CLI, и пользователи рискуют (не подтверждено) [237].

### Истории сбоев и измеренные результаты

- **Процессы агентов оставались после обновлений** (#9138, открыт) [156]:
  - каждое обновление приложения запускало новый фоновый daemon терминалов и не останавливало старый; у автора работали четыре поколения daemons сразу;
  - интерфейс показывал 8 сессий, а живых процессов Claude Code было около 46. Остановка старых daemons завершила 370 процессов. Swap дошёл до 25 из 26 ГБ;
  - баг воспроизводили на 1.4.204, на 1.4.238 под Windows и на 1.4.245.
- **Зависания из-за git** (#16038) [155]: зависания до примерно 20 минут. Причина, по словам maintainer-а, — неограниченное накопление фоновых процессов `git`, из-за которого одиночная команда шла 50–65 с. Исправлено в PR #16874.
- **Задержка ввода** (#6795) [154]: буквы появлялись через 2–5 с; в треде 55 комментариев. Issue закрыт автоматическим «cannot reproduce», в котором остался незаполненный placeholder шаблона.
- **Другие утечки** [157]:
  - на Linux приложение убито по нехватке памяти примерно через 44 часа;
  - GPU helper терял больше 20 ГБ видеопамяти на Apple Silicon;
  - запасной путь Codex оставлял около 36 ГБ временных папок в день;
  - память daemon-а терминалов постоянно росла;
  - общая жалоба на высокий расход RAM и CPU.
- **Перегрузка мобильного relay** [159][160]:
  - в конце июля 2026 relay перегрузили пользователи — так сказала сооснователь Jinjing (передано из Discord). Self-hosted версию relay обещали, потом отложили;
  - бывший платный клиент Superset готов платить за relay; другие спрашивают, как бесплатный relay может работать долго;
  - ошибки сопряжения и разрывы на iOS через Tailscale остаются открытыми [160].
- **Запуски coordinator-and-workers под присмотром человека.** Пользователь описал сбои, которые повторялись [169]:
  - coordinator правил `main` напрямую;
  - состояние «ready» не значило, что ход worker-а действительно начался;
  - письма доставлялись, но не обрабатывались;
  - workers незаметно расширяли scope задачи;
  - diff только от formatter-а чуть не привёл к откату настоящей работы;
  - бесконечные повторы, когда одна и та же проверка падала снова и снова.
  - Свои меры против этих сбоев он оформил как skills для агентов [169].
- **Замер: команда Codex против команды Pi** [250][205]. Пользователь запустил в Orca две одинаковые команды агентов: spec, design, build и общий reviewer.
  - Время: Codex — 48 минут, Pi — 217.
  - Токены: Codex — 10.8M, Pi — 32.0M.
  - Оценка стоимости по ценам API: $9.24 у Codex и $11.42 у Pi.
  - Оба приложения прошли все 43 скрытых приёмочных теста. Шахматный движок Pi выиграл 18 из 20 партий, 2 свёл вничью.
  - Трения: человек-координатор задерживал работу — около 13 минут времени Pi ушло на ожидание его ответов. Один агент попросил права править за пределами своей фазы.
- **Долгая автономная работа** [201]. У пользователя в каждом репозитории файл правил, а GitHub Action заводит баги из production logs. Одно сообщение в Orca запускает subagents, которые чинят эти баги. Deploy идёт автоматически два раза в день. Управляет он с iPhone.

### Лимиты подписки, работа без присмотра и автопродолжение

Эта тема ближе всего к вопросу, ради которого собиралось исследование: автоматически продолжать работу после 5-часового лимита.

- **Спрос давний и повторяется.**
  - #8133 открыт с 2026-07-10 и перенесён из Discord: найти агента, который остановился на лимите, и продолжить после сброса. Цель — работа агентов ночью без присмотра, особенно на младших планах. Автор приложил PR #8132, который искал сообщения о лимите в выводе терминала [144].
  - #15033 закрыт 2026-10-07 как дубликат. Комментатор там пишет, что остановки бывают в основном на планах за $20 [145].
  - #18799 просит то же для Codex, с аккуратными проверками перед продолжением. Комментатор добавляет, что OpenCode после повторов сдаётся, а не ждёт возврата квоты [146].
- **Спор, где должна жить эта логика.**
  - Часть пользователей считает, что продолжать должен harness самого агента, и oh-my-pi уже так делает [144].
  - Через plugins это не сделать: plugins не читают вывод терминала и не получают событий о лимите и сбросе [145][144].
  - Claude Code сам продолжает сессию после сброса лимита claude.ai с версии 2.1.234 (2026-08-17). Выключается это в `/config` настройкой «Continue automatically at usage limit» [256]. Пользователи писали «не больше двух раз» [144][150], а по changelog 2.1.314 предел — три продолжения подряд без prompt человека [256]. Что это работает только в открытой интерактивной сессии — не подтверждено.
- **Что Orca выпустила.**
  - PR #36873 (merged 2026-11-02) добавил opt-in настройку только для Chat UI. Примерно через 15 с после сброса Orca отправляет одно видимое сообщение «continue»; его можно отменить для отдельного чата [133].
  - Баг у Codex — чаты не планировались, если последний отчёт usage был ниже 100% — исправлен к 2026-11-11 (#38890) [151].
  - Что такое же поведение есть для агентов в терминале, ни один источник не показывает (не подтверждено).
- **Автоматическая смена аккаунта.**
  - #20512 (10 👍, 22 комментария): пользователи с 2–9 аккаунтами пишут, что в Orca уже есть все части, кроме политики, которая их связывает [148].
  - Они пишут свои внешние переключатели аккаунтов и жалуются, что синхронизация credentials в Orca перезаписывает изменения, сделанные снаружи [148].
  - PR #29898 (merged 2026-10-17) после ручной смены перезапускает работающие сессии на новом аккаунте [134].
  - PR #28044 — автоматическое переключение на 90% usage — открыт. В октябре maintainers написали, что изучают вопрос [148][134].
  - Связанные баги [152]: перезапуск непрактичен, когда открыты десятки panes с агентами; работающие panes пропускаются при смене аккаунта; режим Agent Teams теряется при перезапуске; чаты остаются остановленными после смены.
- **Orchestration не учитывает лимиты.**
  - #24157 просит не запускать workers на аккаунте, близком к лимиту, и дать workers отдельное состояние «parked until reset» [150].
  - Без него coordinator не отличит worker-а, который ждёт сброса, от зависшего [150].
  - До Orchestration v3 heartbeats workers будили coordinator-а на полный ход модели. У одного пользователя так 5-часовое окно уходило примерно за 2.5 часа [168]. v3 (2026-10-30) heartbeats workers убрала [127].
  - До v3 orchestrator не узнавал об остановившемся агенте и ждал бесконечно [168]. v3 сообщает coordinator-у об остановке хода worker-а. Не сообщается только смерть процесса агента при живом shell [127][89].
- **Расход лимита зависит от способа запуска.** Двое пользователей измерили, что Claude Code в режиме SDK или stream-JSON (так работают вкладки чата Orca) тратит 5-часовое окно в 1.5 раза (один замер) и в 2.9 раза (другой) быстрее, чем интерактивный CLI на той же работе. Причину они видят в метке entry point, которую сообщает Claude Code; T3 Code, по их словам, обошёл это сменой метки [153]. Не подтверждено.
- **Что хотят дальше:** стоимость каждой задачи на доске workspaces [174][239].

### Бизнес-модель

- **Продукт** бесплатный, MIT, на подписках пользователя. Платного тарифа и цен нет нигде [56][1].
- **Enterprise** [2]: «SOC 2 Readiness» (это не сертификат); «No silent changes» — каждое изменение агента в worktree и PR; «Audit trail by default»; self-hosting на desktop или постоянно работающем сервере; продажи — по email. На вопрос FAQ «Is Orca SOC 2 compliant?» страница отвечает, что Orca «built for SOC 2 readiness»: аудит — это git history, PR и одобренные провайдеры, документы о compliance — по email.
- **Сервисы, которые держит Stably** [63][130][49][52]:

  - push gateway (APNs и FCM);
  - код runtime открыт, а deployment лежит в приватном репозитории `stablyai/orca-cloud`;
  - Relay бесплатный, но требует входа в desktop; телефон в аккаунт не входит;

## Слабые места и чего нет

**Работа без присмотра и лимиты.**
- Нет режима «прогнать пачку задач без человека с учётом лимитов». Orchestration не смотрит на usage и запускает workers одинаково при 10% и при 99% лимита [150].
- Автопродолжение после сброса лимита — только в Chat UI и только opt-in [100][133]. Для агентов в терминале — открытые запросы [144][146][147].
- Автоматической смены аккаунта при лимите нет. Пользователи просят её в нескольких issues; PR открыт с октября [148][149][134].
- Автоматического повтора при ошибках API не найдено (не подтверждено).

**Планирование и проверка.**
- Нет слоя планирования — эпиков, тикетов, волн. Граф задач строит LLM-coordinator по ходу работы [29][64][82].
- Нет локального verification gate и reviewer-агентов. Качество держится на review человеком и hosted CI [35][38][64].
- Orchestration experimental: панель временно отключена, удалённые coordinators неактивны [29][126][106].
- Пользователи описывают сбои запусков coordinator-and-workers: правки в `main`, расширение scope, бесконечные повторы на одной проверке [169].

**Права и безопасность.**
- По умолчанию агенты работают в полном bypass прав. Политики auto-approval нет; coordinator одобряет запросы без правил [17][129].
- Worktree — не sandbox; Docker sandboxes пока только запрос [17][141].
- Заблокировать вызов инструмента можно только у Claude Code на macOS и Linux [69].
- Доступ к runtime — по token в файле пользователя; любой процесс этого пользователя может управлять Orca (вывод исследователя) [73].
- Пакет правил распознавания статуса скачивается каждые 4 часа; проверка подписи не найдена (не подтверждено) [80].

**Стабильность и вес.**
- Electron и большой расход памяти; часть пользователей уходит к более лёгким Herdr и cmux [210][208][242].
- Утечки и зависания: daemons старых версий после обновлений (#9138), утечки памяти и видеопамяти, накопление процессов `git` [156][157][155].
- Релиз почти каждый день и регрессии; пользователи просят медленный stable-канал [105][158][244].
- Тесты по умолчанию не добавляются; по заголовкам PR удалено около 85 000 тестов, грубая оценка [58][181].

**Функции, которых нет или мало.**
- Нет работы с несколькими репозиториями в одной задаче — это самый популярный запрос [136].
- Нет нескольких окон и Jujutsu [137].
- Слабый редактор: нет language server, git blame, vim-биндингов [41][138][191].
- Нет canvas или другого пространственного обзора; при многих агентах sidebar трудно читать [171][172].
- Нет командных функций: мест, ролей, SSO, audit log как продукта [2][72].
- Нет интеграций со Slack, Teams и Discord [5][72].
- Нельзя отправить review GitHub PR из Orca [135].

**Платформы.**
- Windows только x64; Chat UI не работает через WSL; онбординг на Windows ломался [6][227][154].
- Мобильный relay был перегружен; ошибки сопряжения и разрывы на iOS — открытые issues [159][160].

**Документация и процесс.**
- Документация отстаёт от `main` и противоречит себе: про sandbox, про аккаунты, про orchestration [29][14][17][53].
- Triage issues частично ведут агенты; один issue закрыт автоматическим ответом с незаполненным шаблоном [154].
- Шум уведомлений; ошибки ввода на корейском и других CJK-языках [161][162].

**Бизнес.**
- Нет объявленной модели монетизации. Relay бесплатный, а пользователи спрашивают, за счёт чего он будет работать дальше [159][1].
- Метрики пользователей не публикуются; значок «downloads» считает и файлы auto-update [71].

## Пересечение с worfy

worfy здесь — однопользовательское Electron-приложение для macOS (порт на Windows в работе). Оно запускает сессии Claude Code и Codex CLI и показывает их работу на бесконечном Canvas. Термины worfy в таблице: Epic — крупная цель из нескольких Tickets; Ticket — одна задача; Wave — группа Tickets, которые Autopilot прогоняет без присмотра; Gate — локальный запуск проверок перед PR; Harness — plugin, который ставит в Claude Code правила, skills, subagents и hooks.

## Механизмы, которые стоит изучить

1. **Пробуждение coordinator-а строкой в терминале и постоянный почтовый ящик.**
   - Что это: coordinator не ждёт workers внутри своего хода, а заканчивает ход. Orca будит его, только когда пришла почта.
   - Как работает: письма лежат в SQLite. Когда агент в покое или, если Orca его распознаёт, может поставить ввод в очередь, Orca печатает в его терминал одну строку «You have N orchestration messages…» и отслеживает доставку каждого байта и Enter. `check` отдаёт самое старое письмо и помечает его обработанным. Polling запрещён: скрипт забрал бы письмо, которым Orca будит агента. По замеру самой команды в PR Orchestration v3 (по 3 прогона) это дало 27/27 правильных запусков вместо 26/27 и −34% токенов на двух workers.
   - Источники: [84][64][29][127].
2. **Сообщение coordinator-у, когда worker остановился без отчёта.**
   - Что это: событие «ход worker-а закончился, а dispatch ещё открыт».
   - Как работает: Orca видит, что ход завершился как finished, errored или needs-input без `worker_done`, и пишет coordinator-у причину, последнее сообщение агента или отредактированный хвост экрана. При запросе прав прикладывает сам запрос. Skill перечисляет ответы: направить worker-а, остановить и повторить или сказать пользователю. Пробел, который признаёт PR v3: если процесс агента умер, а shell жив, сообщения нет.
   - Источники: [89][64][127].
3. **Завершение ровно один раз: ID dispatch, счётчик поколений, квитанции мутаций.**
   - Что это: защита от того, что старая или повторная попытка закроет не ту задачу.
   - Как работает: `worker_done` несёт ID задачи и ID dispatch. `consumer_generation` растёт при переназначении dispatch и отменяет неподтверждённые доставки. Каждая мутация CLI хранится по отпечатку вызывающего и ID запроса с hash payload (до 10 000 строк, 30 дней), поэтому повтор вызова безопасен.
   - Источники: [29][81][87].
4. **Circuit breaker в коде и в тексте skill; восстановление только по доказательствам.**
   - Что это: предел автоматических повторов.
   - Как работает: три неудачных старта в одной цепочке помечают dispatch `circuit_broken` и проваливают задачу; текст отказа велит сообщить пользователю. Skill запрещает обходить предел новым Run, новой Task или сбросом счётчика. Тишина или timeout не считаются доказательством выхода агента; `worker-stop` без доказательства остановки возвращает `stop_unknown` и код 1.
   - Источники: [90][65][64].
5. **Проверка, что prompt действительно начал ход.**
   - Что это: защита от случая, когда prompt напечатан в TUI, а агент его не принял.
   - Как работает: после ввода prompt и Enter Orca ищет доказательство начала хода — событие hook, lifecycle-последовательность агента или вывод после Enter. Через 30 с без доказательства prompt помечается «stalled». В orchestration такой dispatch не отправляется повторно, потому что Enter мог уже дойти.
   - Источники: [75][88].
6. **Автопродолжение после сброса лимита с ограничителями и выбор при исчерпанном лимите.**
   - Что это: продолжение чата, остановленного лимитом подписки.
   - Как работает: проверка каждые 10 с; после сброса — сообщение «Continue where you left off.». Если usage всё ещё показывает израсходованное окно, Orca ждёт свежих данных. Не больше 5 продолжений подряд; отказ, если сброс опоздал больше чем на 24 часа; отмена человеком сохраняется после перезапуска. При исчерпанном лимите строка чата предлагает Switch Account, Hand Off другому агенту и «Continue Now» после времени сброса. Диалог Hand Off не предлагает режимы того же CLI, которые делят тот же лимит. Аккаунты живут в отдельных папках конфигурации, поэтому могут работать одновременно.
   - Источники: [100][128][72][20][99].
7. **Rate limits Claude из status line вместо опроса usage endpoint.**
   - Что это: источник данных о лимитах без отдельных запросов к API.
   - Как работает: Claude 2.1.80 и новее кладёт rate limits в данные status line. Managed status line Orca пересылает их не чаще раза в 15 с. Комментарий в коде объясняет выбор тем, что опрос usage endpoint под Orca получает 429. Опрос endpoint остаётся запасным путём — раз в 15 минут, пока окно в фокусе.
   - Источники: [98][24].
8. **Статус агента из трёх источников и правила распознавания, которые обновляются без релиза.**
   - Что это: определение working / needs you / done / idle для любого CLI.
   - Как работает: приоритет — hooks агента (POST на loopback), затем OSC 7501 в выводе PTY, затем JSON-правила по экрану и заголовку. Правила скачиваются каждые 4 часа из release-asset; лимит 256 KiB; regex с backreferences, lookbehind и неоднозначными повторами отклоняются. Hooks перечитывают endpoint из файла при каждом вызове, поэтому находят перезапущенное приложение.
   - Источники: [69][80][25].
9. **Skills как короткие stubs с guide, который отдаёт сам бинарник.**
   - Что это: способ держать инструкции для агентов в соответствии с версией приложения.
   - Как работает: установленный `SKILL.md` только говорит, когда применять Orca и как загрузить guide. `orca skills get <topic>` отдаёт guide версии работающего бинарника; `--reference` загружает один справочный файл. Updater переписывает только нетронутые копии, сначала показывает план и не удаляет чужие папки.
   - Источники: [33].
10. **Policy hooks с выбором поведения при сбое и одобрение запросов прав coordinator-ом.**
    - Что это: точки, где plugin может отклонить или переписать действие агента, и правила, по которым coordinator отвечает на запросы прав.
    - Как работает: hooks `agent.launch.before`, `agent.prompt.before`, `agent.tool.before`, `terminal.send`, `workspace.create.before`, `editor.save.before`. У обработчика 2 с; без `"onError": "deny"` медленный или упавший обработчик пропускает действие; изменения пишутся в audit log. Для Claude Code на macOS и Linux PreToolUse ждёт решения до 8 с. Coordinator одобряет запрос worker-а только с причиной, побеждает первый ответ, и ответ — только «allow once».
    - Источники: [62][69][129][93].
11. **Daemon, который держит PTY, и hibernation со строгими условиями.**
    - Что это: процессы агентов живут отдельно от окна приложения; простаивающие агенты засыпают.
    - Как работает: daemon переживает выход, падение и обновление приложения. Владение socket переходит через эксклюзивный `link`, проверку подключением и `rename`; «не могу определить» не считается «мёртв». Hibernation усыпляет законченного агента после 30 минут без внимания — только если CLI умеет resume и нет незакрытого dispatch, живых subagents или управления с телефона.
    - Источники: [15][67][23].
12. **Пул заранее подготовленных worktrees.**
    - Что это: ускорение создания worktree.
    - Как работает: подготовка начинается при открытии диалога создания; до 3 checkouts живут 5 минут в `.orca-preparing`; checkout сбрасывается, если base сдвинулся или цель изменилась. Файлы, которые игнорирует git, приходят через общие ссылки или копией по `.worktreeinclude` с бюджетом 2 GiB и 50 000 записей.
    - Источники: [95][12].
