## Модель работы

- **Где работает агент — hybrid.** Для каждого нового чата пользователь выбирает Local (текущий checkout), Worktree
  (отдельный git worktree) или Cloud (Codex Cloud) [6][8]. Ещё варианты — SSH host и связанный компьютер Mac или PC,
  которым управляют с телефона или с другого desktop [17].
- **Платформы.**
  - macOS: Apple Silicon [1], Intel — с 2026-04-16 [4].
  - Windows: нативно с 2026-03-04 [4]. Установка из Microsoft Store или через `winget`. Агент работает в PowerShell с
    нативным Windows sandbox или, по выбору, в WSL2 [40].
  - Linux: preview с 2026-08-11 [4]. Ubuntu 24.04/26.04, Debian 13, Fedora 43/44, Arch; x64 и ARM64. Computer Use на
    Linux нет, нативный Wayland — экспериментально [41].
  - Mobile: в ChatGPT для iOS и Android есть раздел «Codex» (раньше — «Remote»). Он управляет desktop-хостами и
    задачами Cloud [17][18].
  - Web: ChatGPT в браузере запускает задачи Codex Cloud и ChatGPT Work [19][42].
  - Оболочка, вероятно, Electron: в документации Linux есть флаг Chromium `--ozone-platform=wayland` [41], а команда
    CLI `doctor` считает desktop-приложением процессы `chatgpt.exe` и `electron.exe` [127] (вывод, не подтверждено).
- **Агенты.** Только собственный агент OpenAI — Codex. Способа запустить в приложении агента другого вендора не нашли.
  Вместо этого есть импорт настроек и недавней работы из Claude Code, Claude Cowork и Cursor [44].
- **Один агент на всех поверхностях.** Приложение, CLI и IDE extension берут одну конфигурацию: `config.toml`, MCP
  servers, AGENTS.md (файл с инструкциями агенту в репозитории) [51]. Если проект открыт и в приложении, и в IDE, они
  делят активные чаты и контекст редактора [51].
- **Модели.**
  - Текущие: GPT-6 Astra, GPT-6.1 Sol, GPT-6.1 Terra, GPT-6 Sol, GPT-6 Luna [38][39]. Отдельной линейки моделей
    «-Codex» больше нет, модели общего назначения (вывод: страница моделей прямо этого не говорит, но среди текущих
    моделей «-Codex» нет, а gpt-5.3-codex помечена устаревшей) [39].
  - Выбор — ползунок «Power» с шестью готовыми уровнями и панель Advanced: модель, reasoning effort (сколько модель
    рассуждает), скорость [39]. Reasoning effort — до Max. Уровень «Ultra» ещё и разрешает агенту самому отдавать
    работу subagents (дочерним агентам) [33][39].
  - Старые модели снимают по объявленным датам: GPT-5.4 — 2026-08-31, Spark — 2026-09-14, GPT-5.5 — 2026-10-14 [39].
- **Провайдеры моделей.** Amazon Bedrock документирован для desktop-приложения [4: 2026-06-01]. В `config.toml` можно
  описать свой провайдер; `ollama` и `lmstudio` — встроенные ID [55]. Свои провайдеры именно в приложении — открытый
  запрос #10867 [139]. Что работает в приложении кроме Bedrock — не подтверждено.
- **Один пользователь или команда.** Desktop-приложением пользуется один человек. Командные функции стоят вокруг него:
  общие облачные окружения, общие plugins, Team Tasks, Slack и Teams, политики администратора [20][24][38][60].

## Функции

### Рабочее пространство и чаты

- **Sidebar:** New chat, Pinned, Projects, Recents [2]. Там же могут появиться Scheduled, Code Review, Sites и
  колокольчик Activity [9][14][21][4: 2026-06-02].
- **Composer (поле ввода).** Меню «Add»: файлы и папки, «Attach Google Chrome», Goal, Plan mode и встроенные plugins
  для документов — Documents, PDF, Spreadsheets, Presentations [2]. `@` упоминает файлы, plugins, `@Browser`,
  `@Computer`, `@AppName`; `$` выбирает skill; `/` открывает slash-команды [11][27][29].
- **Projects.** Локальный проект подключает одну или несколько папок (несколько — с 2026-07-23). В основной папке
  стартуют новые чаты; от неё же идут Git-операции и поиск AGENTS.md, skills и `config.toml`. Удалённый проект — только
  одна папка [5][4: 2026-07-23].
- **Чаты без проекта** — с 2026-04-16 [4]. **Quick chat** открывает обычный чат ChatGPT прямо из режима Codex [5].
- **Управление чатами.** Закрепить, переименовать, архивировать; архивировать все чаты проекта разом. Поиск по фразе и
  по имени Git branch (по содержимому и ветке — с 2026-05-29). Перенос выбранных чатов в проект — с 2026-10-01 [5][4].
- **Ветвление.** Fork чата с любого прежнего сообщения — с 2026-03-18 [4]. `/fork` копирует локальный чат в новый
  локальный чат или в новый worktree. `/side` открывает временный побочный чат, не прерывая основной [11].
- **Сообщения вдогонку.** «Steer» добавляет сообщение в текущий ход агента, «Queue» откладывает его до следующего хода;
  что выбрано по умолчанию, задаётся в Settings [52]. Сообщения в очереди можно править и переставлять, drag-and-drop —
  с 2026-02-17 [4].
- **Окна.** Несколько окон; чат во всплывающем окне, которое может быть поверх остальных; значок в menu bar macOS и в
  tray Windows [13][4: 2026-02-12][4: 2026-04-16].
- **Горячие клавиши:** «следующий чат, которому нужно внимание», переход к чатам 1–9, Cmd+P для поиска файла, вкладка
  review [12].
- **Deep links:** `codex://threads/new?prompt=…&path=…&originUrl=…` открывает новый чат; другие ссылки открывают
  настройки, Scheduled, установку plugin и настройку SSH host [12].
- **Темы оформления** — свои, с 2026-03-12; ими можно делиться [4][13].

### Параллельная работа: worktrees и Handoff

- **Где работает чат.** Для нового чата — Local, Worktree или Cloud. Для worktree выбирается стартовая ветка. Это может
  быть текущая ветка с незакоммиченными изменениями — они переносятся [6][8].
- **Managed worktrees** — worktrees, которыми управляет приложение. Лежат в `$CODEX_HOME/worktrees`, папку можно
  сменить в Settings > Worktrees. Стартуют в detached HEAD, то есть по умолчанию веток не создают. При создании может
  запускаться setup script локального окружения [6].
- **Handoff** — перенос чата вместе с его кодом между локальным checkout и его worktree; Git-шаги делает сам Codex.
  Документация называет Local передним планом (foreground), а Worktree — фоном (background). Чат, возвращённый в
  worktree, попадает в тот же worktree, что и раньше [6]. Handoff вышел 2026-03-03; до 2026-02-03 функция называлась
  «Sync» [4].
- **«Create branch here»** превращает worktree в ветку с настраиваемым префиксом, например `codex/`; дальше commit,
  push и PR. Документация объясняет правило Git: ветка может быть checked out только в одном worktree [6].
- **`.worktreeinclude`** — список игнорируемых файлов (например, `.env`), которые копируются в новые managed worktrees.
  `AGENTS.override.md` копируется сам [6].
- **Уборка.** По умолчанию хранятся 15 последних managed worktrees; число меняется, автоудаление можно выключить.
  Worktree не удаляется, пока его чат закреплён или работает, и удаляется при архивации чата. Перед удалением
  сохраняется snapshot, и при повторном открытии чата приложение предлагает восстановление [6]. «Постоянные»
  worktrees создавать больше нельзя [6].
- **Координация чатов** в локальных проектах и worktrees, включая отдельные фоновые чаты по явной просьбе, — с
  2026-05-29 [4].

### Локальные окружения, Git, review и терминал

- **Local environments** хранятся в папке `.codex`, её можно закоммитить. Setup scripts бывают разными для разных ОС и
  запускаются при создании worktree. «Actions» (Run, Build, тесты) стоят в верхней панели и запускаются во встроенном
  терминале [7].
- **Git внутри приложения.** В diff pane можно оставить inline-комментарий для Codex. Stage или revert отдельных
  hunks и файлов, commit, push и создание PR — не выходя из приложения [7]. Настройки Git: префикс веток, политика
  force push, prompts для текстов commit и PR [51].
- **Review pane.** Области: Unstaged, Staged, Commit, Branch и Last turn (только то, что агент изменил в последнем
  ответе). Для проектов из нескольких репозиториев — выбор репозитория [21].
- **`/review`** проверяет изменения против базовой ветки или незакоммиченные изменения. Находки приходят
  inline-комментариями, рабочее дерево не меняется. Запускается в текущем чате или отдельным review-чатом [21]. Для
  review можно задать отдельную модель (`review_model`) [21].
- Markdown и код правятся прямо в приложении; «PR Chat» — с 2026-07-09 [4].
- **Встроенный терминал.** Свой на каждый чат, открывается по Ctrl+`, несколько вкладок [26][4: 2026-04-12]. С
  2026-03-11 Codex читает вывод терминала — например, работающий dev server или упавшую сборку [26][4]. Терминал
  ставится внизу или в правую панель [4: 2026-06-01]. Оверлей «Ask Codex» на выделенном тексте — с 2026-04-12 [4].
- **Внешние редакторы.** Кнопка «Open» отправляет проект в VS Code, Visual Studio, Sublime Text; Zed и TextMate
  добавлены 2026-02-04 [40][4].

### Долгая работа без присмотра

- **Goal mode** — режим цели, запуск командой `/goal`; вышел из статуса experimental 2026-05-21 [4].
  - Текст цели — одновременно первый prompt и критерий готовности [10][11].
  - Строка прогресса над полем ввода: pause, resume, edit, clear и прошедшее время [10][11].
  - Цель сохраняет sandbox и политику одобрений чата и встаёт на паузу, когда нужно решение человека [10].
  - Работа идёт автоматическими следующими ходами. С CLI 0.155.0 (2026-09-17) цель блокируется после трёх пустых
    автоматических ходов подряд [4].
  - Бюджет токенов: `goals.max_goal_token_budget`; токены вложенных subagents идут в бюджет корневой цели
    [55][4: 2026-08-29]. Настраиваемый бюджет — с CLI 0.148.0 (2026-08-18); через app-server цель задаётся вызовом
    `thread/goal/set` с полем `tokenBudget` [104][53].
  - Перед целью советуют `/plan`: агент расспрашивает и превращает ответы в измеримые критерии [10].
- **«Prevent sleep while running»** не даёт компьютеру уснуть, пока идут локальные чаты (macOS и Linux) [13]. Для
  удалённых хостов — отдельная настройка «Keep this Mac awake» [17].
- **Режимы разрешений:** Ask for approval, Approve for me, Full access и Custom (из `config.toml`) [34].
- **Approve for me (Auto-review)** — одобрение по политике.
  - Sandbox прежний (workspace-write), одобрения — по запросу. Но подходящие запросы уходят не человеку, а отдельному
    агенту-ревьюеру [34][35].
  - Приложение показывает решение ревьюера и уровень риска по каждому запросу [4: 2026-04-23].
  - Ревьюер по замыслу запрещает: отправку личных данных и секретов в недоверенные места; поиск учётных данных;
    широкое или постоянное ослабление защиты; разрушительные необратимые действия [35].
  - CLI останавливает ход после 3 отказов подряд или 10 отказов в последних 50 проверках. `/approve` разрешает один
    раз повторить отклонённое действие [35].
  - Несколько запросов одобрения могут быть открыты одновременно — с 2026-02-10 [4]. При входе через ChatGPT
    Auto-review не тратит лимит плана — так сказано в сводке на форуме от 2026-10-06, автор помечен как staff [220].
    В документации этого нет; с какой даты так, не подтверждено.
- **Subagents.**
  - Запускаются по просьбе пользователя или если так велят AGENTS.md или skill [33].
  - У каждого свой thread; панель Subagents показывает Active и Done [33]. У фоновых subagents стабильные значки — с
    2026-05-29 [4].
  - Свои агенты (custom agents) задают свою модель и reasoning effort [33].
  - Пример из документации: review PR, разделённый по линзам — безопасность, пробелы в тестах, сопровождаемость, по
    subagent на каждую [33].
- **Hooks** — свои скрипты на события агента; общая доступность с 2026-05-14 [4].
  - События: SessionStart/End, PreToolUse, PermissionRequest, PostToolUse, Pre/PostCompact, UserPromptSubmit,
    SubagentStart/Stop, Stop, Interrupt, Pre/PostModelRequest [36][118].
  - Hook запускается только после проверки и доверия. Доверие привязано к hash, поэтому изменённый hook снова
    требует проверки [36].
  - Hooks бывают фоновыми, приходят в plugins или навязываются администратором [36].
- **Восстановление.** С 2026-08-19 подходящие локальные чаты, прерванные обновлением приложения, сами продолжаются
  после перезапуска [4]. Каждый провайдер по умолчанию повторяет упавший HTTP-запрос 4 раза, оборванный поток — 5 раз
  [55].

### Scheduled tasks — задачи по расписанию (раньше Automations)

- **Где идут.** Desktop-задачи работают в локальном проекте; в Git-репозитории — в папке проекта или в отдельном
  фоновом worktree (с 2026-02-24) [9][4]. Компьютер должен быть включён, приложение — запущено. Задачи могут
  использовать plugins и skills [9].
- **Два вида.**
  - Standalone: каждый запуск начинает новый чат; одна задача может идти по нескольким проектам [9].
  - Задача в чате (в глоссарии — «Heartbeat»): каждый запуск возвращается в тот же чат с его контекстом. Интервал —
    от минут (активные циклы проверки) до дней и недель. Вышло 2026-04-16 как «thread automations» [9][68][4].
- **Расписание:** свои интервалы или строка iCalendar RRULE (RFC 5545) [9]. Шаблоны и своя модель и reasoning на
  задачу — с 2026-03-12 [4].
- **Вид Scheduled** работает как inbox: запуски с находками (Finding) помечены непрочитанными [9][68]. Отметить
  прочитанным и архивировать пачкой — с 2026-06-18 [4].
- **Кто создаёт.** Агент сам создаёт или меняет задачу из чата; skill тоже может её завести. Пример из документации —
  присматривать за PR, пока замечания review не исправлены [9]. Пользователь же сообщает, что встроенные инструкции
  приложения велят модели не создавать задачи, которые следят за работой до завершения, в том числе за PR [141][142].
  Документация и отчёт пользователя здесь расходятся.
- **Триггеры по событиям** — только в web и mobile: новое письмо Gmail, сообщение Slack, активность PR на GitHub. В
  desktop-приложении их нет [9][4: 2026-08-25]. Совместить событие и расписание в одной задаче нельзя [9].
- **Права.** Задачи идут без присмотра с sandbox по умолчанию и `approval_policy = "never"` (никогда не спрашивать),
  если политика организации это позволяет; иначе — с выбранным режимом разрешений. Действия за пределами sandbox тогда
  просто падают, никого не спрашивают [9]. Как задачи повторяют сбои, документация не говорит [9].

### Удалённая работа: телефон, другие компьютеры, SSH

- **Хост и пульт.** Хост — desktop-приложение на macOS или Windows. Управлять им можно с iOS, Android или с другого
  Mac или PC. Пара создаётся по QR-коду, одна на устройство и хост. Общая доступность — 2026-06-25 [4][17].
- **Что можно с пульта:** начать или продолжить чат, steer, одобрить команды, смотреть diffs, тесты и вывод терминала,
  получать уведомления. Работа идёт на хосте, с его файлами, учётными данными, plugins, browser и Computer Use [17].
- **Связь** через secure relay: хост достижим с авторизованных устройств без открытия в публичный интернет [17].
  Общая локальная сеть не нужна: хост сам держит исходящий WebSocket к `chatgpt.com` (по коду) [112].
- **«Control other devices»** — один desktop управляет другим desktop-хостом [17].
- **iOS-клиент в 2026:** ветка, worktree и setup script (2026-06-09); файловый браузер (2026-06-15); Priority view
  (2026-09-01); очередь prompts, которая синхронизируется с хостом и уходит, даже когда приложение в фоне (2026-09-01);
  setup worktree в Live Activity (2026-09-08); просмотр и остановка фоновых команд и @-упоминание чатов на других
  хостах (2026-10-22); блокировка Face ID (2026-06-02) [4].
- **SSH hosts** берутся из `~/.ssh/config`. На удалённой машине работает Codex app server; чаты читают, пишут и
  запускают команды там [17].
- **Перенос чата между хостами** (с 2026-06-18): Handoff переносит чат и его Git-состояние в worktree на другом хосте.
  Идущий ответ перед переносом прерывается. На обоих хостах нужен тот же репозиторий как проект. В Codex Cloud
  перенести нельзя [17][4].
- **Работа на заблокированном Mac** (только macOS). Computer Use продолжает работать после блокировки: приложение
  ставит authorization plug-in Apple, который ненадолго разблокирует Mac на время хода Computer Use. Все экраны при

- Plugin DigitalOcean создаёт облачный сервер (Droplet) и подключает его как удалённую рабочую среду
  [4: 2026-06-25].

## Принципы и подходы

### Заявленная философия

- **Поручить результат и сохранить контроль через проверку.** Страница «Working with agents» описывает агента как
  модель плюс инструменты плюс ограничения и надзор человека [69].
  - Поручение состоит из четырёх частей: Task, Context, Actions (что агент делает сам, что требует одобрения, когда
    остановиться) и Output [69].
  - Инструкции передают намерение, а разрешения управляют доступом [69].
  - Проверка — часть работы: уверенный текст агента не доказывает успех. Глубину проверки подбирают под цену ошибки,
    а свободу агента расширяют по мере доказанной надёжности на похожих задачах [69].
  - Агенты могут работать дольше и стоить дороже. Просьба в prompt тратить меньше не заменяет лимиты и контроль
    расходов продукта [69].
- **Длинный горизонт: напарник, а не инструмент под присмотром.** Пост Derrick Choi от 2026-02-23 [71]:
  - пример — 25 часов непрерывной работы GPT-5.3-Codex, около 13 млн токенов и около 30 тыс. строк кода;
  - тезис: в agentic coding всё больше решает длительность работы, а не разовая сообразительность;
  - цикл: план → правка → запуск инструментов → наблюдение → исправление → обновление документов → повтор;
  - главный приём — durable project memory: spec, план с проверкой на каждом этапе, runbook и журнал статуса в
    Markdown-файлах, которые агент перечитывает;
  - направление — меньше присмотра, больше поручений с ограничениями.
  - Итоговый пост 2025 года: Codex стал «Software Engineer teammate» и скорее рабочей средой, чем моделью, которой
    пишут prompts [75].
- **Командный центр параллельных агентов.** На запуске продукт описан как командный центр для нескольких агентов,
  параллельной работы и долгих задач [79][4: 2026-02-02]. Сейчас — параллельные проекты, файлы, управление
  компьютером и долгая работа в одном desktop [1].
- **Foreground и background.** Local — передний план, Worktree — фон, Handoff переносит чат между ними. Фоновую работу
  ставят в очередь, а сами остаются в переднем плане; потом чат можно забрать в Local, чтобы проверить [6].
- **Цель — это и prompt, и критерий готовности.** Цель пишут так, чтобы агент сам мог проверить прогресс: Outcome,
  Constraints, Verification [10]. Plan отвечает на вопрос «как подходим к задаче», Goal — «что должно быть правдой в
  конце» [72]. Цель не расширяет доступ агента [10].
- **Телефон — пульт, работа — на хосте.** Thomas Ricouard (2026-06-23): код выполняется там, где ему место, — на Mac,

### Чем подход отличается

- **Вендор владеет всем.** Модель, harness, клиенты (desktop, CLI, IDE, web, iOS, Android), облако и учётная запись
  ChatGPT — у одной компании; лимит общий с ChatGPT Work [1][38].
- **Много мест работы и перенос между ними.** Local, Worktree, хост через relay, SSH host, Cloud; Handoff работает
  везде, кроме переноса в Cloud [8][17]. Облачные задачи идут, пока компьютер спит [19].
- **Нативные sandboxes ОС.** На Windows — без WSL и VM [40]. Одобрения может проверять модель [35].
- **Открытый harness, который встраивают другие.** GitHub, JetBrains и Cisco строят на Codex [73]. Symphony —
  открытая спецификация оркестрации OpenAI поверх app-server [106].
- **Физические и фоновые поверхности.** Codex Micro, Pets, Appshots, голос, Computer History [3][16].
- **Область всё время расширяется.** Browser, Computer Use, документы, Sites; заголовок поста 2026-04-16 — «Codex for
  (almost) everything» [4][86]. С 2026-09-29 — dots [63][57].
- **Позиционирование.** Глоссарий называет Codex агентом OpenAI для задач разработки [68]. Страница dots советует Codex,
  когда нужно строить, отлаживать, тестировать или проверять программы [57]. При этом Codex можно продолжать
  использовать для исследований, документов и презентаций [42].

### Процессы

- **Desktop-приложение — клиент открытого app-server.** Подключается по stdio и представляется
  `clientInfo.name = "Codex Desktop"` [127].
- **Протокол app-server** — JSON-RPC 2.0 без поля `"jsonrpc"` [53]. Транспорты: stdio (JSON по строкам), WebSocket
  (экспериментально), Unix socket или никакого [53]. При переполнении очереди запросов — ошибка `-32001` «Server
  overloaded; retry later» [53][109].
- **Три сущности** [53]: Thread — разговор; Turn — один запрос пользователя и работа агента после него; Item — одно
  сообщение, запуск команды, изменение файла или вызов инструмента.
- **Методы.** Основные: `thread/start|resume|fork|archive|compact/start`, `turn/start|steer|interrupt`, `review/start`
  [53]. Новые семейства по коду: `thread/goal/*`, `thread/queue/*`, `thread/revert` (переписывает только историю, не
  файлы), `thread/timeline/list`, `thread/guardianReview`, `account/rateLimits/read|updated`,
  `account/rateLimitResetCredit/consume`, `environment/add|info|status` [123].
- **Статусы thread:** `notLoaded`, `idle`, `systemError` или `active` с флагами `waitingOnApproval` и
  `waitingOnUserInput` [123].
- **Путь для интеграторов.** `codex mcp-server` объявлен устаревшим 2026-08-24 и удалён 2026-09-05. Интеграторов
  отправляют на app-server, который OpenAI при этом называет экспериментальным [4]. TypeScript SDK запускает CLI
  дочерним процессом и обменивается с ним событиями JSONL [132].
- **Daemon.** `codex app-server daemon start|restart|update|enable-remote-control|bootstrap` держит фоновый app-server с
  pidfile в `CODEX_HOME/app-server-daemon/` [113].
  - Обслуживает SSH hosts, desktop- и mobile-приложения. Проверяет обновления через 5 минут после старта, потом раз в
    час. Команды жизненного цикла выполняются по одной на `CODEX_HOME`. При остановке ждёт `shutdownGraceSeconds`: 60 с
    по умолчанию, от 0 до 300 [113].
  - CLI по умолчанию подключается к общему локальному daemon (`DaemonAutoStart`, stable, включён) [122]. Пользователи
    просят сделать daemon включаемым вручную (#48195) [201].
  - Документация называет хостами для телефона только desktop-приложение на macOS и Windows [17]. У daemon при этом
    есть команда `enable-remote-control` [113]. Поддерживается ли официально хост без desktop-приложения — не
    подтверждено.
- **Раздельное выполнение.** `exec-server` выполняет процессы и файловые операции по JSON-RPC, поэтому цикл агента и
  место выполнения команд могут быть на разных машинах. Удалённый executor регистрируется в реестре окружений и
  подключается обратно через relay с шифрованием Noise. Команды получают переменные `CODEX_THREAD_ID` и
  `CODEX_TOOL_CALL_ID` [120].

### Цикл агента

- **Ход.** `run_turn` повторяет: запрос к модели → если модель просит инструменты, выполнить их и повторить → если
  модель вернула только сообщение, ход окончен [108].
- **На каждом круге** цикл забирает ожидающий ввод пользователя (так работает steer, с 2026-02-05 [4]), доставляет
  сообщения из почтовых ящиков других агентов и решает, нужен ли ещё запрос [108].
- **Связь с моделью** — Responses API по WebSocket [124]. Соединение открывается заранее вызовом `response.create` с
  `generate=false`; дальше переиспользуются соединение и `previous_response_id`; маршрутизация закреплена токеном
  `x-codex-turn-state`. При сбое WebSocket клиент переходит на HTTPS [124][109].
- **Stop hooks** в конце хода могут запретить остановку и вставить prompt продолжения; тогда ход продолжается [108].
- **Инструменты модели** [114]: `unified_exec` на PTY и `apply_patch`; `update_plan`, `request_user_input`,
  `request_permissions`; `view_image`; `tool_search` (MCP-инструменты загружаются, только когда модель их ищет) и сами
  MCP-инструменты; JavaScript «code mode»; `sleep` (просыпается раньше при новом вводе); `get_context_remaining` и
  `new_context_window`; инструменты целей и мультиагентные инструменты.
- **Контекст.** Инструкции проекта (AGENTS.md) обрезаются по бюджету `project_doc_max_bytes`, по умолчанию 32 KiB;
  при обрезке пользователь получает warning, сколько байтов загружено [114][227]. Auto-compaction срабатывает на
  заданном лимите или на 90% окна модели — что меньше [126]. Локальная compaction просит модель написать сводку для
  «другой LLM», которая продолжит работу [126]. У удалённой compaction (`compact_remote_v2`) свой, меньший бюджет повторов [126]. Переход
  на модель с меньшим окном может вызвать compaction до запроса [108].

### Цели и долгая работа (по коду)

- Цель — строка в SQLite, одна на thread. Формулировка — до 4000 символов (сверено с кодом), бюджет токенов — по
  желанию [110].
- **Статусы:** `active`, `paused`, `blocked`, `usage_limited`, `budget_limited`, `complete`. Модель может ставить только
  `complete`, `blocked` и `paused`, причём `paused` — только по просьбе пользователя. Продолжение, `budget_limited` и
  `usage_limited` ставят пользователь или система [110].
- **Автопродолжение.** Когда thread простаивает, а цель `active`, расширение запускает новый ход
  (`turn_trigger: "goal"`) [110]. Prompt продолжения содержит бюджет токенов, требование опираться на текущее
  состояние worktree и внешних систем и подсказку про план, а главное — четыре проверки:
  - проверка прогресса: прошлый ход — это прогресс, проверенное ожидание или отсутствие прогресса;
  - правило блокировки: `blocked` ставится, только если одно и то же препятствие повторилось 3 хода подряд;
  - аудит завершения: каждое требование сверить с доказательствами; слабое доказательство считается «не сделано»;
  - верность цели: не подменять цель более лёгкой.
- **Остановки** [110]:
  - бюджет токенов исчерпан → `budget_limited`, и prompt велит модели закругляться;
  - ошибка хода без повтора или повторы кончились → `blocked`; комментарий в коде объясняет: чтобы автопродолжение не
    крутилось и не жгло токены;
  - ошибка лимита использования → `usage_limited`.
  - Создание и возобновление цели и переходы в `blocked`, `usage_limited`, `budget_limited` и `complete` пишут
    счётчики OpenTelemetry, например `codex.goal.usage_limited`; пауза счётчика не пишет [130][110].
- **Очередь сообщений** (`ext/queue`). Сообщения вдогонку хранятся в SQLite и уходят, только когда thread простаивает.
  Записи других процессов проверяются каждые 10 с. `codex queue --thread <id или имя> --message "<текст>"` добавляет
  сообщение снаружи (позиционный prompt команда не принимает); флаг `--resume` по желанию продолжает thread на
  локальном daemon [121].
- **Сон машины.** Удалённый хост должен не спать; ноутбуку Mac с закрытой крышкой для этого нужен внешний монитор
  [17].

### Параллельность и координация

- **Чаты** — отдельные контексты. Документация не советует двум чатам править одни и те же файлы и предлагает
  worktrees [10].
- **Worktree crate** (`codex-rs/worktree`) [111]:
  - путь — `$CODEX_HOME/worktrees/<4 hex-символа UUID>/<имя репозитория>`; на macOS файл `.metadata_never_index`
    выключает индексацию Spotlight;
  - создание — `git worktree add --detach --no-checkout`, затем `reset --hard`; при сбое частичный checkout
    откатывается;
  - Git защищён: hooks репозитория выключены (`core.hooksPath=/dev/null`), fsmonitor и attribute files выключены, LFS
    smudge пропускается, запросы в терминал выключены, унаследованные переменные `GIT_*` вычищаются;
  - владение: файл `codex-thread.json` в git-папке worktree привязывает его к одному thread ID;
  - настройки в секции `[desktop]`: `git-worktree-root`, `worktree-auto-cleanup-enabled`, `worktree-keep-count`
    (по умолчанию 15);
  - флаг CLI `--worktree` использует тот же корень, но никогда ничего не убирает;
  - кода Handoff, `.worktreeinclude` и snapshots в репозитории нет — он в закрытом приложении.
- **Subagents** [33][114]:
  - встроенные роли `default`, `worker`, `explorer`; свои роли — файлы TOML в `~/.codex/agents/` или `.codex/agents/`;
  - наследуют sandbox и политику одобрений родителя; роль может только урезать права;
  - возвращают родителю сводку; если subagent нужно одобрение, которое некуда показать, действие падает, а ошибка
    уходит родителю;
  - инструменты поколения 1: `spawn_agent` (`fork_context`), `send_input`, `resume_agent`, `wait_agent`,
    `close_agent`; поколения 2: `spawn_agent` (`fork_turns`), `send_message`, `followup_task`, `wait_agent`,
    `list_agents`, `interrupt_agent`, плюс почтовый ящик на агента и выгрузка простаивающих дочерних runtime с
    сохранением состояния;
  - по умолчанию глубина 1 (у дочерних агентов своих детей нет); 6 threads в поколении 1, 4 одновременно в поколении 2;
    ожидание 30 с, минимум 10 с, максимум 1 ч;
  - в открытой сборке поколение 2 выключено, а поколение 1 («Collab», помечено устаревшим) включено [122]; что
    использует приложение — не подтверждено;
  - дерево родитель–потомок хранится в таблице `thread_spawn_edges` [117][134];
  - изоляцию subagents по worktrees документация не упоминает [33].
- **Делегирование между чатами.** Core распознаёт инструменты приложения в пространстве `codex_app`, например
  `create_thread` и `send_message_to_thread`. Аналог в TUI умеет создать, fork, отправить, перечислить, прочитать и
  ждать — до 8 threads и 120 с [129]. Changelog 2026-05-29 добавил координацию threads в локальных проектах и
  worktrees [4].
- **Доска сообщений агентов** — общие каналы обсуждения для дерева агентов с локальным, in-memory, удалённым и MCP
  backend. В разработке, по умолчанию выключена [122][134].
- **Облако.** Каждая задача — своя VM [20]. Клиент поддерживает `best_of_n` и параллельные попытки [131]. На какой
  технологии построены облачные VM — не подтверждено.

### Изоляция, права и безопасность

- **Sandbox.** Режимы: `read-only`, `workspace-write` (по умолчанию для локальной работы), `danger-full-access` [65].
  Реализация: macOS — Seatbelt; Linux и WSL — bubblewrap; Windows — три варианта: `mxc` (нативная изоляция процессов),
  `elevated` (отдельные пользователи sandbox и правила firewall), `unelevated` (урезанный token и ACL) [65][67].
  Команды внутри sandbox наследуют его ограничения [65].
- **Permission profiles** (beta). Встроенные `:read-only`, `:workspace`, `:danger-full-access`; свои правила для
  файловой системы `read`, `write` или `deny`, в том числе с glob. Профили на основе `:workspace` держат `.git`,
  `.agents`, `.codex` и `.aws` только для чтения [66]. Правила доменов работают через managed network proxy: HTTP на
  127.0.0.1:3128, SOCKS5 на 127.0.0.1:8081, списки allow и deny, режим «limited» только для чтения [66][119].
- **Правила команд** — на Starlark: `prefix_rule(pattern, decision=allow|prompt|forbidden, justification, match,
  not_match)` [119].
- **Одобрения.** Tool orchestrator применяет одобрения, выбирает sandbox и повторяет команду после отказа sandbox.
  Повтор с повышением прав требует новой проверки [115].
- **Auto-review изнутри** [35][115]:
  - ревьюер видит сжатую историю и точное ожидающее действие и может запускать проверки только для чтения;
  - тайм-аут проверки — 90 с (сверено с кодом);
  - circuit breaker (автоматический выключатель) прерывает ход после 3 отказов подряд или 10 отказов в последних 50
    проверках; для моделей с пометкой «cyber» — после первого отказа;
  - один ревьюер на родительский thread; параллельные проверки получают fork его контекста;
  - политика — встроенный `policy.md`; его можно заменить локально или конфигом организации [35][126].
- **Обязательный человек.** Правило администратора с `decision = "prompt-user"` требует решения человека даже при
  Auto-review. Если подходящего клиента нет, команда отклоняется. При переподключении клиента ожидающие вопросы
  показываются снова [133].
- **Remote control изнутри** [112]:
  - app-server хоста регистрируется на `chatgpt.com/backend-api/wham/remote/control/server/enroll` и держит
    исходящий WebSocket на `.../wham/remote/control/server`;
  - JSON-RPC клиента приходит в конвертах с `client_id`, `stream_id` и курсорами подтверждения `seq_id`; большие
    сообщения режутся на куски base64;
  - пара — по QR или ручному коду; администратор может выключить remote control.
  - Как устроен сам relay-сервер — не подтверждено.
- **SSH.** Приложение запускает удалённый app-server по SSH через login shell пользователя. Открывать транспорты
  app-server в публичные сети не советуют [17].

### Состояние, память и наблюдаемость

- **История.** JSONL rollouts (журналы сессий) в `sessions/` и `archived_sessions/`. База SQLite с таблицами threads,
  thread_goals, thread_spawn_edges, queued_items, projects, thread_turns и items, remote_control_enrollments,
  guardian_review_feedback [117]. Простаивающий thread выгружается через 60 с после ухода последнего подписчика [53].
- **Memories** (по умолчанию выключены) [45][116]:
  - фаза 1 — модель извлекает из каждого простаивающего thread сырую память и сводку; секреты вычищаются;
  - фаза 2 — sub-agent консолидации без одобрений, без сети и с записью только локально правит `~/.codex/memories`
    (папка под git) по diff рабочей папки;
  - задачи памяти используют leases и повторы с задержкой [116].
- **Наблюдаемость.** Метрики OpenTelemetry по времени ходов, токенам, стоимости, review и целям [130]. Локальные trace
  bundles по желанию (`CODEX_ROLLOUT_TRACE_ROOT`), никуда не отправляются [117]. API `thread/timeline/list` [123]. В
  приложении — Activity view, Pets и системные уведомления [14][15].

### Проверка качества

- **`/review`:** отдельный ревьюер читает выбранный diff — против базовой ветки, незакоммиченное, конкретный commit или
  по своим инструкциям — и файлы не меняет [21].
- **Рубрика review:** у каждой находки приоритет P0–P3 и уверенность от 0 до 1; в конце — общий вердикт «patch is
  correct» или «patch is incorrect» со своей уверенностью [126].
- **Проверка «готово».** Главная встроенная проверка — аудит завершения цели [110]. Ещё — бейджи PR в строках чатов
  [4: 2026-02-27] и облачный review на GitHub [22].
- Отдельного локального gate — обязательного запуска проверок перед сдачей работы — в документации и коде не нашли
  (не подтверждено).

### Восстановление после сбоев

- **Классы ошибок** [109]:
  - повтор с задержкой — ошибки потока, тайм-ауты, ответы 5xx, сбои соединения;
  - повтор, только если сервер сказал, сколько ждать, — перегрузка и нехватка мощности;
  - без повтора — `UsageLimitReached`, ошибки квоты и переполнение окна контекста.
- **Задержка:** 200 мс с удвоением и ±10% jitter; `retry-after` сервера важнее. По умолчанию 5 повторов потока
  (максимум 100) и 4 повтора запроса. Когда повторы кончились, клиент может перейти с WebSocket на HTTPS [109].
- **Потеря сети.** Ход её переживает: переподключение через 5 с, с удвоением до 60 с, без лимита попыток; функция
  stable и включена по умолчанию [109][122].
- **Перезапуск и обновление daemon.** Идущие корневые ходы приостанавливаются: история записывается на диск, ход
  отменяется без финального события. После перезапуска ход продолжается под тем же turn ID, когда thread простаивает.
  Работает только для одного локального окружения [128].
- **Создание worktree** при сбое откатывает частичный checkout [111].

### Лимиты и стоимость: что происходит на 5-часовом лимите

- **Ход в работе** разрешено закончить [38]. **Следующий запрос** падает с `UsageLimitReached`, который не
  повторяется [109]. Сообщение об ошибке содержит время сброса и, в зависимости от плана, совет купить credits или
  повысить план; лимиты расходов workspace дают свои сообщения [109].
- **Активная цель** становится `usage_limited`, и TUI советует `/goal resume` [110]. На iOS с 2026-07-20 можно
  возобновить заблокированный или упёршийся в лимит запуск — вручную [4].
- **Автоматического продолжения по таймеру нет** — ни в открытом runtime, ни в документации [10][38][110].
  Пользователь сообщил (2026-07-12): цель в приложении на macOS стояла в `usageLimited`, время сброса прошло, а новый
  ход не начался, пока он не написал сообщение. Это отчёт пользователя, OpenAI его не подтверждала [135].
- **Телеметрия лимитов.** Заголовки ответа `x-codex-primary-used-percent`, `-window-minutes`, `-reset-at` и такие же
  для второго окна; события WebSocket `codex.rate_limits`. Из них собирается `RateLimitSnapshot`: основное и второе
  окно, credits, контроль расходов, план [125]. Клиенты читают `account/rateLimits/read` и
  `account/rateLimits/updated`: `usedPercent`, `windowDurationMins`, `resetsAt`, `rateLimitResetCredits` [53][123].
- **Как продолжить после лимита:** credits [38]; накопленный сброс — вручную через
  `account/rateLimitResetCredit/consume` (нужен ключ идемпотентности, у сбросов есть срок) [53][123]; сессия с API key
  [38].
- **Детали, из которых можно собрать автопродолжение** (для этого они не документированы): задача по расписанию
  внутри чата, которая будит тот же thread [9][4: 2026-04-16]; `codex queue --thread <id> --message … --resume` и
  `codex exec resume` [54][121]; Stop hooks [108]. Оговорки: задачи по расписанию идут с `approval_policy = "never"`
  [9], а встроенные инструкции, по отчёту пользователя, запрещают задачи «следить до завершения» [141][142].
- Пользователи сделали неофициальные watchdog-инструменты: unsnooze, codex-auto-resume-watchdog, «Codex Auto Resume»
  для Windows, Bellows. Это заявления в комментариях, они не проверены [135].
- **Контроль стоимости:** бюджеты токенов целей [110]; генерация memories пропускает проход, если остаток лимита ниже
  `memories.min_rate_limit_remaining_percent`, по умолчанию 25% [45][227]; app-server раз в 150 с опрашивает
  стоимость хода и отдаёт метрику `codex.turn.cost_microusd` [130]; subagents тратят дополнительные токены [33].

### Планировщик задач

- Планировщик — в закрытом приложении. Администратор может закрыть его настройкой `InAppLocalAutomation`, которую

  переносит незакоммиченные изменения, тоже не подтверждены.

- **Работа без присмотра через сброс лимита.** Goal mode продают для работы «часами и даже днями»
  [4: 2026-05-21]; у пользователей бывают цели на 40 дней [138]. Но на лимите работа встаёт.
  - Открытые запросы ждать сброса и продолжать: #21073 (2026-05-04, 92 👍) [135], #28931 (2026-06-18, 83 👍) [136],
    #43605 (2026-09-07) [137], #31386, #34188, #48392 [140].
  - Когда задача умирает ночью, наработанное пропадает [135].
  - Очередь сообщений на 5-часовом лимите не ждёт: отправляет всё накопленное сразу [178].
  - Просят автоматически применять накопленный сброс при упоре в лимит (#32218) [138] и цели, которые ждут, не тратя
    токенов [179].
  - Комментатор: правильнее продолжать существующую сессию, чем перезапускать ход; в Claude Code это включено по
    умолчанию с выключателем в `/config` [135]. Проверено: changelog Claude Code 2.1.234 обещает автоматически
    продолжать сессию, когда сбрасывается лимит claude.ai [224]. Дата 2026-08-17 подтверждена: в этот день версия
    2.1.234 опубликована в npm [226].
- **Счётчики и планирование.** Недовольство из-за убранного индикатора контекста [150] и просьбы всегда показывать
  5-часовой и недельный лимит [196][197]. Сообщество сделало Codexometer: живая квота, мониторинг sessions, история
  токенов, сравнение моделей. Сотрудники форума попросили у автора стандартные тестовые задачи, потому что часто
  слышат о внезапных изменениях расхода [219].
- **Worktrees и Handoff.**
  - #10599 (2026-02-04, 78 👍): worktrees лежат в `~/.codex/worktrees`, папку не сменить [180]. Документация сейчас
    даёт настройку папки [6], а в коде есть ключ `git-worktree-root` [111]. Заметки исследования здесь расходятся;
    текущий статус issue неизвестен.
  - Сообщение «worktree удалён, чтобы освободить место» появляется на threads, которые ещё в работе [181].
  - Worktrees, созданные вне приложения, не поддерживаются; сотрудник ответил, что приложение для этого не задумано
    [182].
  - Устаревшие временные worktrees мешают вернуться на main [183].
  - После передачи контекста или задачи агент рано останавливается [184].
  - Из-за убранного выбора ветки пользователь всерьёз думает о переходе на Claude Code [153].
- **Задачи по расписанию.** На запуске работали, только пока ноутбук включён [205]. На Windows расписание не
  срабатывает, есть ошибки часовых поясов [185]. Встроенные инструкции отказываются от документированных задач
  наблюдения, например следить за PR по расписанию [141]. Триггеры по событиям просили со ссылкой на Claude Code, где
  они уже есть [186]; потом они вышли в web и mobile [4: 2026-08-25].
- **Remote, mobile, SSH.** Телефону нужен работающий desktop; просят headless Linux hosts [187]. Работающий desktop
  телефон показывает как offline [188]. Ошибки writer lock ломают перенос одного thread между CLI, mobile и desktop
  [190]. Отозванное устройство не может снова создать пару [191]. По сравнению с `/remote-control` в Claude Code
  функцию называют сделанной наспех [189].
- **Автоматические одобрения.** Просят откат к человеку, когда Auto-review отказывает, иначе модель может пытаться
  обойти отказ [192].
- **Видимость действий агентов.** Шифрование сообщений между агентами убрало читаемую запись того, что агенты сказали
  друг другу (138 👍); пользователи хотят сохранить возможность проверки [193]. Из-за скрытых команд пользователь Pro

  нескольких папок вышли 2026-07-23 [4].
- **Codex Cloud.** Голосов мало: у метки `cloud` 5 issues [100]. Главные запросы — несколько учётных записей на один

## Слабые места и чего нет

- **Нет продолжения после сброса лимита.** Цель встаёт в `usage_limited` и ждёт человека [110][135]. Очередь сообщений
  на лимите не ждёт, а отправляет всё сразу [178].
- **Нет планирования под лимиты.** Есть только статические оценки числа сообщений на окно [38]. Расход непрозрачен и
  скачет [147][157][158]; фоновые процессы тратят лимит незаметно [159][160][161].
- **Нет модели задач крупнее чата.** Ни эпиков, ни тикетов, ни пакетов работы; «готово» проверяет сама модель через
  аудит цели [110]. Локального gate не нашли (не подтверждено).
- **Задачи по расписанию ограничены.** Нужны включённый компьютер и запущенное приложение; триггеры по событиям есть
  только в web и mobile; обработка сбоев не описана; без одобрений действия вне sandbox падают [9].
- **Удалённая работа зависит от desktop и облака OpenAI.** Документированный хост — desktop-приложение на macOS или
  Windows [17]; headless-хост просят [187]. Связь идёт через relay OpenAI; режима только локальной сети нет [17].
- **Нет бесконечного canvas.** «Canvas» есть только у генератора изображений [4: 2026-07-30].
- **Один профиль во встроенном browser.** Для настоящих профилей нужно расширение [27][28].
- **Только агент OpenAI.** Другие агенты — только через импорт их настроек [44]; свои провайдеры моделей в приложении —
  открытый запрос [139].
- **Закрытое приложение.** Handoff, snapshots и планировщик не видны в коде [111][122]; внешние PR не принимаются [102];
  app-server официально экспериментален [4: 2026-09-05].
- **Регрессии при обновлениях** [150][152][153][165][166][167].
- **Ресурсы и платформы.** Electron и проблемы macOS [146][168][169][207]; на Windows — зависания, сбои worktrees и
  сообщения об удалении файлов вне проекта [170][171][172][216]; на Linux нет Computer Use, Wayland
  экспериментален [41].
- **Аудит.** Сообщения между агентами зашифрованы [193]; трассы и timeline сделаны для разработчиков, а не как лента
  для пользователя [117][123].
- **Агент продолжает без человека.** Вопросы с таймером уходят без ответа [177].
- **Subagents без изоляции по worktrees** — документация её не упоминает [33].

- **Правила рядом с кодом** — skills, hooks, subagents, plugins [36][37]. Codex принимает форматы plugins Claude [70].
- **Счётчики лимитов, уведомления, встроенные browser и терминал** есть у обоих [4][14][26][27].

- **Codex.** worfy запускает Codex CLI — тот же открытый harness, на котором стоит Codex app [56][73].

### Где расходятся

- **Сброс лимита.** worfy ждёт сброса и продолжает сам. Codex после лимита ставит цель в `usage_limited` и ждёт

## Механизмы, которые стоит изучить

1. **Prompt продолжения цели с аудитом завершения.**
   - Что это: автоматический следующий ход для долгой цели без человека.
   - Как работает: когда thread простаивает, а цель активна, запускается ход; prompt этого хода среди прочего содержит
     четыре проверки: был ли прогресс; `blocked` только после 3 одинаковых препятствий подряд; каждое требование
     сверить с доказательствами, слабое доказательство = не сделано; не подменять цель более лёгкой. С CLI 0.155.0 цель
     блокируется после трёх пустых автоматических ходов.
   - Источник: [110][4: 2026-09-17].
2. **Статусы остановки цели вместо бесконечного цикла.**
   - Что это: отдельные состояния `usage_limited`, `budget_limited` и `blocked`.
   - Как работает: ошибка лимита, исчерпанный бюджет токенов или ошибка без повтора переводят цель в своё состояние, и
     автопродолжение прекращается; каждая такая остановка пишет счётчик OpenTelemetry (пауза — нет). Бюджет считает и
     токены вложенных subagents.
   - Источник: [110][130][4: 2026-08-29].
3. **Auto-review с circuit breaker.**
   - Что это: отдельный агент-ревьюер решает запросы разрешений вместо человека.
   - Как работает: ревьюер видит сжатую историю и точное действие, может делать проверки только для чтения, отвечает
     за 90 с. После 3 отказов подряд или 10 из 50 ход прерывается. После отказа основной агент получает указание не
     обходить запрет. Правило `prompt-user` всё равно требует человека; ожидающие вопросы повторно показываются, когда
     клиент переподключается.
   - Источник: [35][115][133].
4. **Жизненный цикл managed worktree.**
   - Что это: правила хранения и удаления worktrees, привязанных к чатам.
   - Как работает: хранятся 15 последних; не удаляются, пока чат закреплён или работает; удаляются при архивации; перед
     удалением — snapshot с предложением восстановить; `.worktreeinclude` копирует нужные игнорируемые файлы.
   - Источник: [6].
5. **Защищённое создание worktree и файл владения.**
   - Что это: создание worktree без побочных эффектов чужой конфигурации Git.
   - Как работает: `--detach --no-checkout`, затем `reset --hard` с откатом при сбое; hooks репозитория, fsmonitor,
     attribute files и LFS smudge выключены; переменные `GIT_*` вычищены; `.metadata_never_index` против Spotlight;
     `codex-thread.json` привязывает worktree к одному thread.
   - Источник: [111].
6. **Handoff между foreground и background.**
   - Что это: перенос чата вместе с кодом между основным checkout, его worktree и другим хостом.
   - Как работает: Git-шаги делает приложение, учитывая, что ветка может быть checked out только в одном месте; чат
     возвращается в тот же worktree; перед переносом на другой хост идущий ответ прерывается.
   - Источник: [6][17].
7. **Устойчивая очередь сообщений и продолжение хода после перезапуска.**
   - Что это: сообщения и ходы, которые переживают перезапуск процесса.
   - Как работает: очередь лежит в SQLite и отправляется, только когда thread простаивает; другие процессы могут
     добавлять в неё через `codex queue … --resume`. При перезапуске или обновлении daemon ход приостанавливается с
     записью истории на диск и потом продолжается под тем же turn ID.
   - Источник: [121][128][54][4: 2026-08-19].
8. **Повторы по классам ошибок.**
   - Что это: разные правила для разных сбоев.
   - Как работает: сбои потока, тайм-ауты и 5xx — повтор с задержкой от 200 мс; перегрузка — только при `retry-after`;
     лимит, квота и переполнение контекста — без повтора. Потеря сети — переподключение каждые 5–60 с без лимита
     попыток; WebSocket при исчерпании повторов уступает HTTPS.
   - Источник: [109][122][124].
9. **Телеметрия лимитов и накопленные сбросы.**
   - Что это: машиночитаемое состояние лимита для клиентов.
   - Как работает: заголовки `x-codex-primary-used-percent`, `-window-minutes`, `-reset-at` и события
     `codex.rate_limits` складываются в `RateLimitSnapshot`; `account/rateLimits/read` отдаёт `resetsAt`; сброс
     применяется вызовом `account/rateLimitResetCredit/consume` с ключом идемпотентности. Фоновая генерация memories
     пропускает проход, если остаток лимита ниже порога (по умолчанию 25%, по коду [227]).
   - Источник: [125][53][123][45].
10. **Доверие к hook по hash.**
    - Что это: защита от тихой подмены скриптов hooks.
    - Как работает: hook запускается только после проверки человеком; доверие привязано к hash, поэтому любое
      изменение снова требует проверки; администратор может навязать hooks.
    - Источник: [36].
11. **Remote control через relay с курсорами подтверждения.**
    - Что это: управление хостом с телефона без открытия хоста в интернет.
    - Как работает: хост регистрируется и держит исходящий WebSocket к серверу OpenAI; трафик клиента идёт в конвертах
      с `client_id`, `stream_id` и `seq_id`, большие сообщения режутся на куски; пара — по QR, одна на устройство и
      хост; на заблокированном Mac Computer Use разблокирует экран только на время хода.
    - Источник: [112][17][29].
12. **Сигналы внимания по срочности и снимки с вычисткой секретов.**
    - Что это: как показывать много параллельных чатов и как делиться результатом.
    - Как работает: Pets показывает самый срочный статус (needs input → blocked → ready → running), Codex Micro даёт по
      клавише со светом на каждый из шести чатов, Activity view собирает непрочитанные и ждущие чаты. Shared snapshot
      перед загрузкой вычищает известные шаблоны секретов и не берёт вызовы инструментов и вывод shell.
    - Источник: [14][15][16][42].
