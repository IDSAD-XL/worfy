## Модель работы

- **Развёртывание — local. Тот же CLI можно запустить и в облачной сессии.**
  - Команда работает на машине пользователя, внутри CLI Claude Code [1].
  - Teammate бывает двух видов [1][6][25]:
    - in-process — работает внутри процесса lead;
    - split-pane — отдельный процесс Claude Code в pane tmux или iTerm2. tmux — программа, которая делит окно терминала на panes (панели).
  - Всё состояние команды — локальные файлы: `~/.claude/teams/{team}/` (config и inbox-ы) и `~/.claude/tasks/{team}/` (задачи) [1]. Серверной службы команд документация не описывает [1].
  - В облачных сессиях Claude Code on the web функция тоже выключена по умолчанию. Её включают той же переменной в переменных облачного окружения [17].
  - Страница Projects пишет, что команда работает на машине пользователя или внутри облачной сессии и заканчивается вместе со своей задачей [14].
- **Только интерактивная сессия.**
  - В `claude -p` (запуск без интерактива) и в сессиях Agent SDK teammate-ы не запускаются. Subagent с именем работает там как обычный subagent [1].
  - Документация SDK пишет, что agent teams не настраиваются опциями SDK: это функция CLI [23].
  - GitHub Action Claude Code построен на SDK [24]. Значит, в этом пути CI команд нет. Это вывод заметок из [1] и [24].
- **Поверхности:**

| Поверхность | Есть ли agent teams |
| --- | --- |
| CLI в терминале | да, основная поверхность [1] |
| Desktop-приложение | нет: функция есть в CLI, но не в Desktop. Вместо неё Desktop предлагает dynamic workflows и управление несколькими сессиями [16] |
| Claude Code on the web (облако) | выключено по умолчанию; включается переменной в переменных облачного окружения [17] |
| Расширение VS Code | не описано. Его «agent map» показывает только subagents [28] |
| Расширения JetBrains | работают ли там teammate-ы — не подтверждено |
| Remote Control и мобильное приложение | видны ли там teammate-ы — не подтверждено |
| Облачные scheduled tasks | работают ли там команды — не подтверждено |

- **Агенты и модели.**
  - Worker-ы — всегда сессии Claude. Другой инструмент можно подключить только как MCP server, с которым работает Claude [11].
  - Каждый teammate может работать на своей модели: aliases Opus, Sonnet, Haiku или Fable. Действует allowlist моделей организации [1][20].
  - На Anthropic API aliases `opus`, `sonnet` и `haiku` сейчас ведут на модели версии 5.5 [20].
  - Провайдеры — те же, что у Claude Code: Anthropic API, Amazon Bedrock, Google Vertex и Microsoft Foundry. Исправления teammate-ов для трёх облачных провайдеров вышли в v2.1.41 и v2.1.45 (февраль 2026) [38].
  - Через LLM gateway (прокси перед API модели) запросы in-process teammate-ов (участников команды, которые работают в процессе lead) несут заголовок `x-claude-code-agent-type: teammate`. У teammate стабильный ID, построенный по имени: он сохраняется между переподключениями [25].
- **Один пользователь.**
  - «Команда» здесь — AI-агенты внутри сессии одного человека. Команда привязана к сессии. Разделить её с другой сессией нельзя [1].
  - Уже идущие сессии не могут вступить в команду. Issue #24294 с таким запросом закрыл бот за неактивностью [110].
  - Функции для команд людей с похожими названиями к agent teams отношения не имеют:
    - `/team-onboarding` пишет гайд по проекту для новых коллег-людей. На планах Team и Enterprise им можно поделиться ссылкой [18];
    - Claude Tag добавляет Claude в каналы Slack на планах Team и Enterprise [14].
- **Платформы.**
  - Claude Code работает на macOS 13+, Windows 10 1809+ и Windows Server 2019+, Ubuntu 20.04+, Debian 10+, Alpine 3.19+. Нужно от 4 GB RAM [30].
  - Режим in-process работает в любом терминале [1].
  - Split panes требуют tmux или iTerm2 с CLI `it2` и включённым Python API. Во встроенном терминале VS Code, в Windows Terminal и в Ghostty они не работают [1].
  - Документация пишет, что tmux традиционно лучше всего работает на macOS. Начать советует с `tmux -CC` внутри iTerm2 [1].
  - Cross-session messaging (переписка между сессиями) работает на macOS и Linux с v2.1.224 [15][38]. Для нативного Windows документация называет v2.1.234 [15], а changelog объявляет поддержку Windows в v2.1.239 (2026-08-21) [38][39].
  - На Linux ограничение памяти для вида процессов `agent` покрывает дочерние процессы Claude Code, в том числе teammate-ов [6].

## Функции

### Основной сценарий

1. **Включить функцию** переменной окружения [1].
2. **Попросить команду** обычной фразой [1].
3. **Lead запускает teammate-ов.** Он вызывает инструмент Agent с параметром `name`. Ответ инструмента сообщает об успешном запуске, даёт agent_id вида `my-agent@session-<id>` и говорит, что инструкции придут через mailbox. Это воспроизвёл сотрудник Anthropic [133].
4. **Работа.** Teammate-ы берут задачи из общего списка или получают их от lead. Они работают и пишут друг другу и lead [1].
5. **Отчёт.** Закончив ход, teammate отправляет lead idle notification — уведомление о простое с финальным ответом [1].
6. **Остановка.** Lead просит teammate-а завершиться. Тот соглашается или отказывается с объяснением. Общие папки команды удаляются автоматически [1].

### Включение и запуск

- **Переменная окружения** `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` — в shell или в блоке `env` файла `settings.json` [1].
  - Managed settings — настройки, которые задаёт организация. Они применяются после всех остальных источников, поэтому организация может включить функцию принудительно [1].
  - Значение `0` выключает функцию. Сохранённый файл настроек применяется к уже идущей сессии. Переменная перечитывается при каждом запуске teammate [1].
- **Запуск обычной фразой.** Пример из документации: создать трёх teammate-ов — одного на UX, одного на техническую архитектуру, одного в роли оппонента [1].
  - Если число не названо, размер команды выбирает Claude [1].
  - Claude может выбрать subagents вместо команды. Subagents видны в той же панели, поэтому команду лучше просить явно [1].
- **Отдельного шага «создать команду» нет.**
  - Инструменты `TeamCreate` и `TeamDelete` убраны в v2.1.178 (2026-06-15). У каждой сессии с флагом одна неявная команда. Teammate запускается вызовом Agent с параметром `name`. Параметр `team_name` игнорируется [38].
  - Раньше команду создавали явно, вызовом `TeamCreate({team_name,…})` [127].
  - Имя команды — `session-` плюс первые 8 символов ID сессии [1].
- **Команда может собраться без просьбы.** Пока флаг включён, любой subagent, которому Claude дал имя, запускается как teammate. Подтверждения Claude Code не спрашивает [1][7].
  - Обычными subagents остаются fork (ответвление текущей сессии) и вызовы, где `isolation` передан в самом вызове [1][7].
- **Размер команды.** Жёсткого предела нет [1].
  - Совет документации: 3–5 teammate-ов и 5–6 задач на каждого. При 15 независимых задачах — начать с трёх teammate-ов [1].
  - По документации, три сфокусированных teammate-а часто работают лучше пяти разрозненных [1].
  - Предел в 20 одновременных subagents к teammate-ам не относится. У них свои пределы, но какие — не описано [7].

### Состав команды

- **Четыре части** [1]:
  - team lead — главная сессия. Она запускает teammate-ов и координирует их;
  - teammates — отдельные экземпляры Claude Code;
  - shared task list — общий список задач;
  - mailbox — почтовый ящик для сообщений между агентами.
- **Жёсткие ограничения** [1]:
  - одна команда на сессию; разделить её между сессиями нельзя;
  - вложенных команд нет: teammate не может запустить своих teammate-ов. Запрет действует с v2.1.69 [38];
  - lead назначен на всё время сессии; передать роль нельзя;
  - отдельный режим прав для teammate-а при запуске задать нельзя.
- **С чем стартует teammate** [1]:
  - свой context window;
  - CLAUDE.md, MCP servers и skills — как у обычной сессии;
  - то же ограничение `--setting-sources`, что у lead;
  - prompt запуска от lead, но без истории разговора lead.
  - Агенты с инструментом `SendMessage` получают на старте снимок списка других агентов с именами [7].
- **Team config** — файл `~/.claude/teams/{team}/config.json` [1]:
  - runtime-состояние: ID сессий и ID panes tmux;
  - массив `members`: имя, agent ID и тип агента каждого участника. У lead тип `team-lead`;
  - teammate-ы читают файл, чтобы найти друг друга;
  - править вручную нельзя: файл перезаписывается при каждом изменении;
  - файла команды на уровне проекта нет.
  - По сообщению пользователя, в файле есть `leadAgentId` вида `team-lead@<team>`, `leadSessionId` и поле `isActive` у каждого участника [130].

### Agent panel и работа с teammate-ами

Agent panel — список агентов под строкой ввода lead [1].
- Стрелки вверх и вниз выбирают teammate. Enter открывает его transcript. Дальше набранный текст уходит этому teammate [1].
- Escape снимает выбор. Пока открыт teammate, Escape прерывает его текущий ход [1].
- Клавиша `x` останавливает выбранного teammate. Ctrl+T показывает и прячет список задач [1].
- Строки idle-teammate-ов (простаивающих) прячутся через 30 секунд после того, как вся панель стала idle. Сам teammate продолжает работать [1].
- Если idle-teammate-ов больше трёх, лишние сворачиваются в одну строку «N idle agents» [1].
- Строки working, failed и открытого сейчас teammate остаются всегда [1].
- **Пока открыт teammate** [1]:
  - обычный текст и skills уходят teammate-у, встроенные команды — lead;
  - `/compact`, `/clear` и `/rewind` сначала просят подтверждения;
  - `/model` и `/fast` заблокированы: модель и fast mode teammate-а задаются при запуске и не меняются.
- **Другие способы обратиться к teammate-у:**
  - `@name` в строке ввода lead. Если запись в inbox не удалась, Claude Code оставляет текст в поле ввода [10];
  - команда `/list-agents` (alias `/peers`) показывает teammate-ов, с v2.1.239 [18];
  - в fullscreen-режиме тусклая строка «Message from @sender» раскрывается по клику [31]. Раскрытие свёрнутых сообщений teammate-ов по клику появилось в v2.1.274 [38].
- Подсказки prompt в сессиях teammate-ов по умолчанию выключены. В сессии lead они есть [5].
- **Клавиши менялись:**
  - при запуске — Shift+Up/Down или tmux, чтобы перейти к любому teammate напрямую [45];
  - v2.1.47 (2026-02-18) — только Shift+Down [38];
  - сейчас — agent panel [1].
- Agent view (`claude agents`, экран фоновых сессий) teammate-ов отдельными строками не показывает [13].

### Display modes: in-process и split panes

- **Настройка `teammateMode`:** `in-process` (по умолчанию), `auto`, `tmux` или `iterm2` [1][8].
  - Флаг `--teammate-mode` задаёт режим на одну сессию. Флаг экспериментальный и не показан в `claude --help` [1][19].
  - Значение `iterm2` появилось в v2.1.186 (2026-06-22) [38].
  - Как менялось значение по умолчанию — не подтверждено.
- **In-process.** Teammate-ы живут в терминале и процессе lead. Режим работает в любом терминале [1].
  - Фоновая работа такого teammate не может пережить процесс lead. Поэтому in-process teammate-ы запускают только foreground subagents [1].
- **Split panes.** У каждого teammate свой pane. Чтобы работать с teammate-ом, кликают в его pane [1].
  - Сессию tmux, которая осталась после выхода lead, удаляют командой `tmux kill-session` [1].

### Настройка teammate-ов

- **Выбор модели.** Claude Code берёт первое, что подходит [1]:
  1. модель, названную в prompt запуска;
  2. поле `model` в определении subagent (`inherit` — модель lead);
  3. переменную `CLAUDE_CODE_SUBAGENT_MODEL`, если она не `inherit`;
  4. текущую модель lead.
  - Hook `agent.spawn` у mod может заменить первый источник [1][22]. Mods описаны ниже, в разделе о quality gates.
  - `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (с v2.1.257) пропускает первые два источника. Так одна модель задаётся всем teammate-ам [1][9].
  - До v2.1.251 переменная окружения шла первой [1].
  - Настройку `teammateDefaultModel` убрали в v2.1.234 [1][8].
- **Allowlist моделей организации** [1][20]:
  - заблокированный alias семейства, например `opus`, опускается до самой новой разрешённой версии этого семейства. Так работает на Anthropic API и Claude Platform on AWS;
  - любое другое заблокированное значение заменяется моделью lead;
  - в отличие от subagents, о замене модели teammate-а пользователю не сообщают.
  - Цепочка запасных моделей тоже может переключить teammate на другую модель, и об этом тоже не сообщают [20].
- **Effort (уровень усилия модели)** [1][38]:
  - teammate на модели lead наследует effort lead;
  - split-pane teammate-ы делают так с v2.1.186;
  - с v2.1.317 teammate на другой модели берёт сохранённый effort этой модели или её значение по умолчанию.
- **Роли из определений subagents.** При запуске можно назвать тип subagent уровня проекта, пользователя, managed или plugin [1]. Какие поля определения применяются, зависит от режима [1]:

| Поле определения | In-process teammate | Split-pane teammate |
| --- | --- | --- |
| `tools` | применяется; добавляются `SendMessage` и, если доступны, Task tools | применяется |
| `model` | применяется | применяется |
| `disallowedTools` | применяется, но инструменты команды остаются | не описано |
| `effort` | применяется | не описано |
| `autoCompactWindow` | применяется (с v2.1.296) | игнорируется |
| Тело определения (текст prompt) | добавляется к system prompt по умолчанию | заменяет system prompt по умолчанию |
| `skills` | не применяется | не применяется |
| `mcpServers` | игнорируется | применяется |

  - Issue с запросом «custom agents как teammate-ы» закрыт как выполненный 2026-08-17. Закрывал его Boris Cherny [111]. Агентов из plugins исправили в v2.1.288 [38]. Поле `model` custom agent учитывается для teammate-ов с v2.1.47 [38].
  - Когда остановленный teammate возвращается, определение из папки проекта применяется снова, только если папка trusted (помечена как доверенная) [1][10].
  - Поля `memory` (постоянная память агента) в этом списке нет. Получают ли её teammate-ы — не подтверждено [1].
- **Cron.** У teammate-ов остаются инструменты `CronCreate`, `CronDelete` и `CronList` [7].

### Общий список задач

- **Работает через инструменты** `TaskCreate`, `TaskGet`, `TaskList` и `TaskUpdate` [6]. На новых моделях их по умолчанию нет:
  - v2.1.233 (2026-08-14) убрал их на Opus 4.8, Sonnet 5, Fable 5, Mythos 5 и новее [38];
  - с v2.1.268 (2026-09-10) они по умолчанию есть только на Claude 3.x, Opus 4.0–4.7, Sonnet 4.0–4.6 и Haiku 4.5 [38][6];
  - без них агент координируется с командой сообщениями, а не списком задач [6];
  - вернуть их можно переменной `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`. Split-pane teammate-ам её передают через `--settings`: экспортированная в shell переменная до них не доходит [6]. Пользователь подтверждает, что на Opus 5.5 переменная нужна [159];
  - в фоновых и облачных сессиях инструменты есть на любой модели [6].
- **Состояния и захват** [1]:
  - три состояния: pending, in progress, completed;
  - задача может зависеть от других. Пока они не закончены, задача считается blocked. Teammate-ы сами её не берут, но человек или lead могут её назначить;
  - teammate, закончивший работу, сам берёт следующую незанятую и незаблокированную задачу. Или задачу назначает lead;
  - захват защищён file lock от гонок. Завершение задачи само разблокирует зависимые.
- **Поля задачи** [23]:
  - `TaskCreate`: `subject`, `description`, необязательные `activeForm` и `metadata`;
  - `TaskUpdate`: `taskId`, `status` (pending, in_progress, completed, deleted), `subject`, `description`, `activeForm`, `addBlocks`, `addBlockedBy`, `owner`, `metadata`;
  - `TaskGet` возвращает `blocks` и `blockedBy`, `TaskList` — `owner` и `blockedBy`.
- **Просмотр** [5]:
  - Ctrl+T показывает до пяти задач;
  - задачи переживают compaction — сжатие контекста, при котором старую часть разговора заменяет сводка;
  - `CLAUDE_CODE_TASK_LIST_ID=<name>` даёт один именованный список нескольким отдельным сессиям [5][9].
- **Хранение** [1][29]:
  - папка `~/.claude/tasks/{team}/` переживает конец сессии. Её удаляют через `cleanupPeriodDays` дней (по умолчанию 30);
  - папка config команды удаляется в конце сессии.
- **Известный изъян:** статус может отставать. Teammate-ы иногда не отмечают задачу выполненной, и зависимые задачи стоят [1].
- v2.1.311 (2026-10-26) исправил пустой список задач после `--resume`, `--continue`, `/clear` или сбоя [38].

### Сообщения

- **Отправка.** Инструмент `SendMessage` адресует агента по имени. Имена даёт lead. Чтобы ссылаться на teammate-ов предсказуемо, документация советует сказать lead, какие имена нужны [1].
- **Доставка автоматическая:** lead не нужно проверять inbox-ы самому [1]. Пользователи сообщают, что занятый teammate получает сообщение только после конца своего хода, а не между вызовами инструментов [155][156].
- **Broadcast нет.** Чтобы обратиться ко всем, нужно отправить по сообщению каждому [1].
  - В марте 2026 пользователь описывал два примитива: direct и broadcast [116]. Когда broadcast убрали — не подтверждено.
- **Уведомления от teammate-а** [1][38]:
  - idle notification несёт финальный ответ teammate-а (исправлено в v2.1.251);
  - teammate, чей ход кончился ошибкой API, сообщает lead «failed» с текстом ошибки (с v2.1.198).
- **Protocol messages** — структурированные сообщения того же канала [1][10]:
  - запрос на shutdown, согласие и отказ;
  - запрос на одобрение плана, одобрение и отклонение;
  - запросы прав от teammate-ов.
  - Сам `SendMessage` работает и без agent teams. Флаг нужен только этим структурированным сообщениям [7].
- **Доверие между агентами** [1][21][38]:
  - получатель видит, что сообщение пришло от другой сессии Claude, а не от пользователя;
  - teammate не может одобрить запрос прав или дать согласие за пользователя. Отказанное действие нельзя передать другому teammate-у, чтобы обойти проверку;
  - с v2.1.166 пересланные сообщения не несут полномочий пользователя [38];
  - auto mode — режим прав, в котором решения принимает classifier безопасности. В нём пересланные «одобрения» считаются недоверенными. С v2.1.222 classifier проверяет каждое сообщение до доставки, и заблокированное сообщение не приходит;
  - с v2.1.323 split-pane teammate-ы проверяют, что запрос пришёл от их собственного lead.
- **Cross-session messaging** — отдельная функция: v2.1.224+ на macOS и Linux [15][38]; на нативном Windows — v2.1.234+ по документации [15] или v2.1.239 по changelog [38].
  - Claude может написать в другие сессии пользователя на той же машине, на других машинах через Remote Control (доступ к сессии с другого устройства) или в облаке [15].
  - `ListAgents` показывает и teammate-ов [15].
  - Между сессиями ходит только простой текст. Структурированные сообщения протокола команды остаются внутри команды [15].
- **Ошибки доставки описаны в документации** [10]: не удалось записать в inbox; запрос на одобрение плана не доставлен; запрос прав не дошёл до lead.

### Планы, права и остановка

- **Планы** [1]:
  - plan mode — режим, в котором агент сначала составляет план и не меняет файлы;
  - teammate, запущенный, пока lead в plan mode, тоже сначала планирует и шлёт lead запрос на одобрение плана;
  - если режим этого teammate никто не менял, Claude Code одобряет план сразу при получении. Lead его не смотрит;
  - если человек сам перевёл teammate в plan mode (Shift+Tab в окне teammate), план проверяет lead.
- **Режим прав** [1]:
  - teammate стартует в режиме lead, включая `bypassPermissions` (`--dangerously-skip-permissions`, все действия без вопросов). Если lead в `dontAsk` (режим, в котором Claude Code не задаёт вопросов), teammate стартует в Manual (каждое действие спрашивает разрешения);
  - in-process teammate следует режиму lead, пока lead в acceptEdits (правки без вопросов), auto или bypass. Переключение teammate в Manual этого не меняет;
  - Shift+Tab переключает режим одного teammate.
- **Правила командной строки** [1]:
  - in-process teammate-ы работают под живыми allow- и deny-правилами lead;
  - split-pane teammate-ы наследуют `--disallowedTools` и `--tools` (с v2.1.309), но не `--allowedTools`.
- **Где появляются запросы.** Запросы прав teammate-ов показываются в сессии lead. Документация советует заранее разрешить частые операции [1].
- **Никогда не ждать ответа.** Настройка `permissions.denyInsteadOfPrompting` (v2.1.319, 2026-11-06) отклоняет вызов инструмента, который ждал бы ответа человека, и ход продолжается. Действует и на teammate-ов [38][8].
- **Остановка** [1]:
  - lead шлёт запрос на shutdown. Teammate соглашается или отказывается с объяснением;
  - остановка бывает медленной: teammate сначала заканчивает текущий запрос;
  - общие папки команды удаляются автоматически;
  - выбранного в панели teammate можно остановить клавишей `x`.

### Quality gates: hooks и mods

- **Три hook-а команды** [2]. Hook — команда или запрос, который Claude Code вызывает на событии:
  - `TeammateIdle` — teammate вот-вот станет idle. Exit code 2 отдаёт stderr как обратную связь, и teammate продолжает работать. JSON `{"continue": false, "stopReason": …}` останавливает его;
  - `TaskCreated` — создаётся задача. Exit code 2 или `decision: "block"` удаляет задачу и возвращает сообщение Claude;
  - `TaskCompleted` — задачу отмечают выполненной. Exit code 2 не даёт её закрыть и возвращает обратную связь. Пример документации запускает `npm test`. `continue: false` учитывается, только если событие пришло от teammate, закончившего ход.
  - Matchers (фильтры по инструменту или событию) ни один из трёх не поддерживает. Поле `team_name` во входных данных устарело.
- **Когда появились** [38]:
  - `TeammateIdle` и `TaskCompleted` — v2.1.33 (2026-02-06);
  - `continue: false` для hooks команды — v2.1.69;
  - `TaskCreated` — v2.1.84. Дата по одной заметке — 2026-03-25, по времени публикации в npm [39]; по другой — 2026-03-26 [38].
- **Типы hook-ов.** Все три события принимают пять типов: `command`, `http`, `mcp_tool`, `prompt` (LLM-судья) и `agent` (проверяющий агент с доступом к инструментам) [2].
  - Для hook-а `prompt` на TeammateIdle ответ `ok: false` по умолчанию останавливает teammate. `continueOnBlock: true` вместо этого возвращает причину и оставляет его работать [2].
- **Другие hooks, которые касаются teammate-ов:**
  - `SubagentStart` срабатывает каждый раз, когда in-process teammate берётся за новое сообщение. Он может добавить `additionalContext` [2];
  - с v2.1.290 поле `agent_id` во входных данных hook-а указывает на in-process teammate [2];
  - TypeScript SDK поддерживает hooks TeammateIdle и TaskCompleted [23];
  - hook Notification с типом `agent_needs_input` срабатывает, когда teammate задаёт вопрос о настройке терминала (с v2.1.248) [3].
- **Открытая ошибка.** Hooks `PermissionRequest` не срабатывают на запросы прав teammate-ов [107]. Сотрудник Anthropic воспроизвёл похожий случай для split-pane teammate в v2.1.233, но этот issue потом закрыли за неактивностью [140].
- **Mods** — plugins из обработчиков на JS или TS, которые работают внутри процесса Claude Code. Появились в v2.1.287 (2026-10-01) [38][22]. Для команд:
  - `agent.spawn` срабатывает и на teammate-ов (`e.isTeammate`). Он может выбрать модель или запретить запуск. С v2.1.299 срабатывает и при возобновлении [22][38];
  - `turn.start` слышит ходы teammate-ов (v2.1.299) [38];
  - `$.agent.list()` возвращает статусы pending, running, waiting, idle, completed, failed, killed [22];
  - `$.session.send` пишет teammate-у [22];
  - mods умеют рисовать свои panes [22].

### Работа без присмотра, лимиты и сбои

- **Документация не советует** надолго оставлять команду без присмотра: растёт риск потратить работу впустую [1].
- **Ожидание сброса лимита подписки** (v2.1.234+, по умолчанию включено для подписок claude.ai) [5][38]:
  - сессия показывает, что лимит исчерпан, когда он сбросится и когда работа продолжится сама. Esc отменяет;
  - после сброса сессия продолжает задачу;
  - после трёх автоматических продолжений сессия останавливается;
  - сама сессия не ждёт сброса, до которого больше 24 часов. На практике это недельный лимит.
- **Но не в сессиях teammate-ов.** Там Claude Code сам ожидание не запускает. Человек у этого терминала должен выполнить `/rate-limit-options` [5]. Вывод заметок: команда, упёршаяся в 5-часовой лимит, сама полностью не продолжит.
- **Для сравнения, в том же Claude Code:**
  - dynamic workflows ставят паузу на лимите и продолжают после сброса (v2.1.271) [38];
  - `/goal` повторяет запрос или ждёт сброса лимита (v2.1.269) [38].
- **Согласие на расход кредитов Fable.** В сессиях teammate-ов этот вопрос держится время `dialogExpiry` (5 минут). Если никто не ответил, ход заканчивается и ничего не отправляется [20][10].
- **Ошибки и остановки** [1][38]:
  - упавший teammate сообщает lead «failed»;
  - сообщение будит teammate-а, который ждёт повтора запроса к API;
  - teammate-ы могут остановиться после ошибок. Lead может закончить раньше времени или начать делать работу сам. В обоих случаях его надо подтолкнуть.
- **Прерывание lead.** Teammate-ы продолжают работать [12].
- **Возобновление** [1]:
  - `/resume` и `/rewind` не восстанавливают in-process teammate-ов. После этого lead может писать teammate-ам, которых уже нет;
  - в той же сессии сообщение остановленному in-process teammate-у возвращает его с сохранённым разговором.
- **План без 5-часового лимита.** Ultra обещает подтверждённым аккаунтам отсутствие 5-часового лимита [43].

### Изоляция файлов

- **Worktree для teammate-ов нет.** Работу делят так, чтобы каждый teammate владел своими файлами. Два teammate-а, правящие один файл, перезаписывают друг друга [11][1].
- **`isolation` превращает teammate в subagent.** Параметр `isolation` в вызове Agent делает обычного subagent, не teammate. `isolation` во frontmatter определения запуск teammate не отменяет. Такой teammate работает в главном рабочем каталоге [7].
- **Сообщения пользователей.** Пользователи не раз сообщали, что `isolation: "worktree"` для teammate-ов молча игнорируется. Эти issues закрыли как дубликаты или ботом за неактивностью [132].
- **Открытый запрос:** свой рабочий каталог, CLAUDE.md и MCP config для каждого teammate (#23669, 33 реакции) [106].
- **Где worktree есть** [11][18]:
  - у subagents;
  - у фоновых сессий agent view;
  - у `/batch` — он делит одно изменение на 5–30 subagents, каждый в своём worktree.

### Наблюдаемость и администрирование

- Managed settings могут включить команды принудительно. Allowlist моделей организации действует и на teammate-ов [1].
- Корпоративный launcher (`processWrapper`, обёртка запуска процессов) оборачивает и split-pane teammate-ов, с v2.1.210 [27].
- OpenTelemetry: `agent_id` ставится на запросы и запуски инструментов subagents и teammate-ов [26].
- Запуск split-pane teammate прерывается, если deny-правило командной строки нельзя передать ему без искажений [10].
- Через LLM gateway запросы in-process teammate-ов помечены заголовком `x-claude-code-agent-type: teammate` [25].

### Поверхности и интеграции

- Интеграций именно для agent teams нет [1].
- MCP servers teammate получает из настроек проекта и пользователя (in-process) или из поля `mcpServers` своего определения (split-pane) [1].
- GitHub Actions и SDK teammate-ов не запускают [1][24].
- В Desktop функции нет [16]. Desktop отдельно рекламирует параллельные сессии с изоляцией через Git и наблюдением за PR [37].
- Расширение VS Code показывает в «agent map» только subagents [28].

| Функция | Что это | Статус |
| --- | --- | --- |
| Subagents | worker-ы внутри одной сессии; возвращают сводку тому, кто их вызвал | общедоступны [11] |
| Agent view (`claude agents`) | один экран терминала с фоновыми сессиями по состояниям: Working, Needs input, Idle, Completed, Failed, Stopped. Каждая сессия перед правками переходит в свой worktree. Teammate-ов отдельными строками не показывает | research preview [13] |
| Dynamic workflows (инструмент `Workflow`, `/workflows`, `/deep-research`) | план держит скрипт; десятки и сотни агентов за запуск; запуск можно возобновить; работает в Desktop | доступны [12] |
| Projects | один разговор, который запускает параллельные облачные «threads»; личные, без общего доступа | public beta на Pro, Max и Ultra [14] |
| Cross-session messaging | сессии, которые пользователь запустил сам, пишут друг другу, в том числе на других машинах | с v2.1.224 [15] |

- Рядом есть `/batch` — subagents в своих worktree [18] — и `/goal`: Claude делает ходы, пока условие не выполнено [32].
- Страница dynamic workflows описывает agent teams так [12]:
  - что это: lead, который руководит равноправными сессиями;
  - кто решает, что делать дальше: lead, ход за ходом;
  - где промежуточные результаты: в общем списке задач;
  - масштаб: несколько долгоживущих равноправных агентов;
  - что при прерывании: teammate-ы продолжают работать.

## Принципы и подходы

### Ключевые понятия

| Понятие | Что значит | Источник |
| --- | --- | --- |
| Team lead | главная сессия. Запускает teammate-ов и координирует их. Остаётся lead всё время сессии; передать роль нельзя. Командой управляет только lead | [1] |
| Teammate | отдельный полный экземпляр Claude Code со своим context window. Загружает CLAUDE.md, MCP servers и skills, плюс prompt запуска от lead. Истории разговора lead не получает | [1] |
| Shared task list | общий список задач: pending, in progress, completed; зависимости; задачи назначает lead, или teammate-ы берут их сами под file lock | [1] |
| Mailbox | по одному JSON-inbox на агента в `~/.claude/teams/{team}/inboxes/{agent}.json`. Доставка автоматическая. Broadcast нет | [1] |
| Idle notification | уведомление lead, что teammate остановился, с его финальным ответом. Если ход кончился ошибкой API — «failed» с текстом ошибки | [1] |
| Protocol messages | структурированные сообщения: запрос на одобрение плана и ответ; запрос на shutdown, который teammate может принять или отклонить | [1][7] |
| Display mode (`teammateMode`) | где живут teammate-ы: `in-process` (по умолчанию), `auto`, `tmux`, `iterm2` | [1] |
| Agent panel | список агентов под строкой ввода lead | [1] |
| Team config | `~/.claude/teams/{team}/config.json`: runtime-состояние с массивом `members`; перезаписывается при каждом изменении | [1] |
| Адрес teammate-а | `name@team` в поле `teammate_id`, отдельно от `agent_id` | [38] |
| Quality-gate hooks | `TeammateIdle`, `TaskCreated`, `TaskCompleted`; exit code 2 возвращает обратную связь и блокирует действие | [2] |
| Mods | plugins из обработчиков на JS или TS внутри процесса Claude Code; hook `agent.spawn` видит запуск teammate-ов | [22] |

### Принципы из документации функции

- **Команда — только там, где параллельная работа реально помогает.** Лучшие случаи по документации [1]:
  - исследование и review;
  - новые модули;
  - отладка с конкурирующими гипотезами;
  - работа, которая охватывает frontend, backend и tests.
  - Документация советует сначала проверить, не справится ли вариант полегче [1].
- **Независимость важнее координации.**
  - Последовательные задачи, правки одного файла и сильно зависимую работу лучше делать в одной сессии или в subagents [1].
  - Два teammate-а в одном файле перезаписывают друг друга. Работу делят по файлам [1].
  - Worktree для teammate-ов нет [11].
- **Маленькие команды.** 3–5 teammate-ов и 5–6 задач на каждого. При 15 независимых задачах — три teammate-а. Три сфокусированных teammate-а часто работают лучше пяти разрозненных [1].
- **Спор как инструмент.**
  - В шаблоне «competing hypotheses» teammate-ы пытаются опровергнуть теории друг друга, как в научном споре. По документации, это мешает зацепиться за первую же теорию [1].
  - В параллельном code review у каждого teammate-а одна lens — один угол проверки: security, performance или test coverage [1].
- **Человек рядом.**
  - Долгая работа команды без присмотра повышает риск потраченной впустую работы [1].
  - Запросы прав teammate-ов приходят в сессию lead [1].
  - При этом планы teammate-ов по умолчанию одобряются автоматически: lead их не смотрит, если человек сам не менял режим teammate-а [1].
- **Сообщения агентов не несут полномочий пользователя.** Получатель знает, что сообщение от другой сессии Claude. Teammate не может одобрить запрос прав или дать согласие за пользователя. В auto mode classifier проверяет каждое сообщение до доставки [1].
- **Gates — в hooks, а не в prompt.** Документация описывает TeammateIdle как способ требовать quality gates до остановки teammate-а, например прохождения lint [2].
- **Команда — runtime-состояние, а не конфигурация.** Team config перезаписывается. Файла команды в проекте нет. Повторно используемые роли живут в определениях subagents [1].

### Общая доктрина Anthropic о системах из многих агентов

- **Начинать с простого.** Искать самое простое решение и усложнять только при необходимости [47].
- **Много токенов.**
  - Системы из многих агентов обычно тратят в 3–10 раз больше токенов, чем один агент [49].
  - Исследовательская система Anthropic из многих агентов тратила около 15× токенов обычного чата [48].
- **Позиция менялась.**
  - В июне 2025 Anthropic писала: в программировании меньше по-настоящему параллельных задач, чем в исследовании, а агенты пока плохо координируют и делегируют работу в реальном времени [48].
  - Запуск в феврале 2026 смягчил это для независимой работы, где много читают код, например для review кодовой базы [45].
- **Делить работу по контексту, а не по виду работы.** Context-centric decomposition — каждому агенту тот контекст, который ему нужен. Деление по видам работы (writer, tester, reviewer) создаёт постоянные расходы на координацию [49].
- **Пять шаблонов координации (апрель 2026)** [53]:
  - generator-verifier, orchestrator-subagent, agent teams, message bus и shared state;
  - agent teams — для параллельных, независимых и долгих подзадач. Их отличие: worker-ы живут через много заданий и накапливают контекст;
  - трудные места agent teams: работа, которая зависит от другой работы; понять, что всё закончено; общие ресурсы;
  - совет по умолчанию — начинать с orchestrator-subagent.
  - Расхождение в словах: статья пишет, что teammate-ам трудно делиться промежуточными результатами. Функция Claude Code при этом даёт им прямую переписку [53][1].
- **Отделять исполнителя от оценщика.** По опыту Anthropic, это сильно улучшает результат: отдельного скептичного оценщика настроить проще, чем научить исполнителя критиковать себя [50].
- **Допущения harness устаревают.**
  - Harness (код вокруг модели: цикл, инструменты, проверки) кодирует то, чего модель пока не умеет сама. С новыми моделями это устаревает. Например, сбросы контекста стали лишними на Opus 4.5 [52].
  - Совет Applied AI (октябрь 2026): возвращать subagents в один цикл агента со skills, потому что каждая новая модель берёт на себя больше решений. System prompt Claude Code для новых моделей сократили больше чем на 80% [62].
  - В документации есть таблица «что можно перестать делать». Например, больше не нужно защищать context window через subagents. Просить Claude «продолжай, пока не закончишь» не рекомендуется [35].
- **Цикл проверки — условие автономии.**
  - Глоссарий называет цикл проверки обязательным условием для `/goal`, работы без присмотра и dynamic workflows [33].
  - Чек-лист для работы без присмотра: определено, что значит «готово»; агент может проверить свою работу; он трогает только то, что можно; есть предел ходов или расходов; человек одобряет результат в конце [35].

### Уроки показательных проектов Anthropic

- **Компилятор C (2026-02-05)** [46]:
  - масштаб: 16 агентов, около 2 000 сессий Claude Code, около $20 000, 2 млрд входных и 140 млн выходных токенов;
  - итог: компилятор на Rust в 100 тыс. строк, который собирает Linux 6.9 для x86, ARM и RISC-V;
  - мотивация автора: существующие harness-ы вроде Claude Code требуют, чтобы оператор был на связи;
  - приёмы:
    - очень качественные tests. Проверка задачи должна быть почти идеальной, иначе Claude решит не ту задачу;
    - смотреть на задачу глазами Claude;
    - не засорять context window;
    - учитывать, что агент не чувствует, сколько прошло времени;
    - облегчать параллельность. Когда все агенты упёрлись в одну ошибку при сборке ядра, эталоном стал GCC;
    - давать агентам роли: убирать дублирующийся код, ускорять компилятор, писать документацию, критиковать код с позиции Rust;
  - предостережение автора: легко увидеть, что tests проходят, и решить, что работа сделана. Выпускать ПО, которое программист сам не проверил, — реальная проблема.
- **Теорема Ферма, сентябрь 2026** [58]. Prove2Me вместе с multi-agent harness на основе Claude Code закончили формализацию чуть меньше чем за две недели. Ушло около 6 млрд выходных токенов. Использовалась ли функция agent teams — не подтверждено.
- **Теорема Ферма, 1 000 агентов (2026-11-09)** [63]:
  - один lead и 999 помощников работали 28.7 часа;
  - координация — таблицы Postgres, которые спроектировал сам lead (announce, assign, notes, subtasks, landed), и merge requests в Git. Отдельных инструментов для сообщений у агентов не было;
  - одна общая машина упёрлась в свои пределы примерно на 100 агентах;
  - безопасность: classifier проверял каждый вызов инструмента, offline monitor просматривал действия команды;
  - поведение: помощники сначала сочли 47 из 60 утверждений невыполнимыми, но команда доказала большую часть. Управляющая программа этого запуска (harness Anthropic, не плагин worfy) 19 раз напоминала lead, сколько осталось времени. Авторы пишут, что агенты склонны сдаваться на трудных задачах и неверно оценивать их сложность;
  - вывод авторов: команды из многих агентов при безопасном масштабировании помогут решать самые трудные задачи.

### Чем подход отличается

- **Равноправные агенты, которые живут долго, а не родитель с помощниками.** Subagent отчитывается только тому, кто его вызвал. Teammate-ы пишут друг другу, и человек может говорить с любым teammate-ом напрямую [1]. Статья Anthropic о subagents называет команды более тяжёлыми и дорогими [51].
- **План держит суждение lead, а не код.** Сравнение Anthropic с dynamic workflows [12]:

| | Agent teams | Dynamic workflows |
| --- | --- | --- |
| Кто решает, что делать дальше | lead, ход за ходом | скрипт |
| Где промежуточные результаты | в общем списке задач | в переменных скрипта |
| Масштаб | несколько долгоживущих равноправных агентов | десятки и сотни агентов за запуск |
| Что при прерывании | teammate-ы продолжают работать | запуск можно возобновить в той же сессии |

- **Локально и на файлах.** JSON inbox-ы, захват задач через file lock, состояние в `~/.claude/teams` и `~/.claude/tasks` [1].
- **Команда может собраться сама.** Любой вызов Agent с именем запускает teammate-а без подтверждения [1][7].
- **Общий рабочий каталог.** В отличие от subagents с `isolation`, сессий agent view и threads в Projects, у teammate-ов нет своего worktree [11][14].
- **Позиционирование.**
  - При запуске: для независимой работы, где много читают код, например review кодовой базы [45].
  - Сейчас: тяжёлый вариант после более лёгких [1][51].
  - Один из входов в «multiplayer agents» — вместе с Claude Tag [57].
  - Отчёт Anthropic о трендах 2026 предсказывает, что одиночные агенты станут координированными командами. Для этого, по отчёту, нужны среды разработки, которые показывают состояние многих одновременных сессий агентов [64].

## Как это устроено внутри

Код CLI закрыт [40]. Ниже — по документации, changelog и issues. Детали, которые пользователи получили разбором бинарника, отмечены отдельно.

### Что где работает

- **Lead** — обычная главная сессия Claude Code. Вне модели ничего не планирует и не расписывает работу. Координацию, раздачу задач и делегирование lead делает сам, по инструкциям на естественном языке [1].
- **Каждый teammate** — полная сессия Claude Code с обычным циклом агента: собрать контекст, действовать, проверить — через инструменты [34].
- **In-process teammate** — задача внутреннего типа `in_process_teammate` в процессе lead [38].
  - Он делит память с lead. Исправление в v2.1.69 перестало держать в памяти всю историю родителя всё время жизни каждого teammate-а [38].
- **Split-pane teammate** — отдельный процесс `claude` [1][6]:
  - по сообщениям пользователей, pane создаётся командой `tmux split-window … -P -F #{pane_id}`, а команда запуска вводится в него через `send-keys` [106];
  - команда запуска несёт JSON в `--settings '{…}'`. В iTerm2 её обрезало на 1024 байтах [138];
  - pane может получить stdin без TTY, и тогда teammate падает в режим `--print` [134];
  - наследует deny-правила командной строки и `--tools` (с v2.1.309), `--setting-sources` (с v2.1.281), `--settings` и фиксированный набор переменных окружения. Не наследует `--allowedTools` [1][6][38].
- **Бинарник.** CLI — один скомпилированный файл. По сообщению пользователя, собран Bun [138].

### Цикл агента и запуск teammate-а

- Lead вызывает инструмент `Agent` с параметром `name`, пока включён флаг [1][7].
  - Входные поля Agent: `description`, `prompt`, `subagent_type`, `model`, `effort`, `run_in_background`, `name`, `team_name` (устарел и игнорируется), `isolation` со значениями `"worktree"` или `"remote"` [23].
  - Fork и вызов с `isolation` становятся обычными subagents [1][7].
  - Подтверждения нет [1].
- Ответ инструмента даёт agent_id вида `my-agent@session-<id>` и сообщает, что инструкции придут через mailbox. Что именованный запуск идёт путём teammate-а, подтвердил сотрудник Anthropic [133].
- Адрес teammate-а — `name@team`. С v2.1.290 он хранится в поле `teammate_id`, отдельно от `agent_id` [38].
- Около v2.1.63 инструмент Task переименовали в Agent [7][101].
- Одна неявная команда на сессию — с v2.1.178 (2026-06-15). До этого команды создавались явно через `TeamCreate` [38][127].

### Планирование и список задач

- **Планировщика нет.** Lead разбивает работу сам, если prompt его об этом просит [1].
- **Задачи** должны быть самостоятельными кусками работы с понятным результатом [1].
- **Известные сбои lead** [1]:
  - lead начинает делать задачи сам. Помогает прямая просьба ждать teammate-ов;
  - lead решает, что команда закончила, раньше, чем готовы все задачи.
- **Хранение.** Одна задача — один JSON-файл, например `~/.claude/tasks/session-0adfd7b2/1.json` (воспроизведение сотрудника Anthropic) [136].
- **Захват.** Teammate берёт задачу под file lock, чтобы не было гонок [1].
- **Дефекты захвата** (оба открыты):
  - teammate захватил через `TaskUpdate` задачу, у которой блокер ещё в работе [159];
  - у self-claim нет фильтра по роли или по доступным инструментам. Teammate-reviewer, которому можно только читать, берёт задачи на реализацию и не может их закончить [150].
- **Зависимость от модели.** Task tools по умолчанию есть только на старых моделях (Opus 4.7, Sonnet 4.6, Haiku 4.5 и раньше). На новых без `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` координация идёт только сообщениями [6][38]. В таких сессиях не срабатывает и hook `TaskCreated` [2].

### Сообщения и протокол координации

- **Mailbox — файл.** У каждого агента свой `~/.claude/teams/{team-name}/inboxes/{agent-name}.json` [1].
  - Записи проверяются при чтении. Битые удаляются с отчётом, хорошие доставляются [1].
  - С v2.1.224 сообщение считается отправленным только после успешной записи в файл получателя. До этого неудачные записи тоже считались отправленными [1][10][38].
  - Конкуренция за lock inbox-а превращается в ошибку инструмента, которая просит Claude повторить [10].
- **Адресация.** По имени. Тип lead — `team-lead`. Broadcast нет [1].
- **Тот же канал несёт protocol messages:** запрос на shutdown, согласие и отказ; запрос на одобрение плана, одобрение и отклонение; запросы прав teammate-ов [1][10].
- **Как сообщение видит модель.**
  - В transcript такие сообщения обёрнуты в тег `teammate-message` с атрибутом `teammate_id`, например со значением `team-lead` [155].
  - SDK помечает источник сообщения как `peer` (in-process teammate пишет главной сессии) или `coordinator` (сообщение от координатора команды) [23].
  - Получатель знает, что сообщение пришло от другой сессии Claude, а не от пользователя [1].
- **Доставка — что говорит документация и что нашли пользователи.**
  - Документация: доставка автоматическая, lead не опрашивает inbox-ы [1].
  - Разбор debug log и вывода `strings` одного пользователя (v2.1.245) [149]:
    - каждый in-process teammate опрашивает свой mailbox примерно раз в 500 мс. В log видны строки вида `[inProcessRunner] <name> poll #N: checking mailbox` и `[TeammateMailbox] readUnreadMessages`;
    - idle-teammate получает 30-секундный срок, после которого его выселяют. Но из-за порядка «продлить срок до выселения» 5 idle-teammate-ов опрашивали mailbox около 20 часов.
  - Документация отдельно пишет, что строки idle в панели прячутся через 30 секунд [1].
- **Время доставки — открытый дефект.** Несколько пользователей сообщают, что сообщение занятому teammate-у приходит только после конца его хода, а не между вызовами инструментов. Это видели в интерактивном режиме на v2.1.283 и v2.1.288 и в режиме tmux на v2.1.287 [155][156]. Для cross-session messaging документация обещает доставку между вызовами инструментов [15].
- **Будит idle-teammate-а только `SendMessage`.** События Monitor и завершение его собственных фоновых задач теряются, а не ставятся в очередь (открытый отчёт) [137].
- **«Пинг-понг».** Ответ lead закончившему teammate-у будит его, и тот шлёт ещё одно idle notification (отчёт закрыт как not planned) [143].
- **Внешние процессы, которые пишут в inbox-ы,** не имеют описанной схемы и правил блокировки. Запрос на такой контракт закрыт как not planned [147]. Cross-session messaging использует отдельный socket на каждую сессию [15].

### Параллельность и процессы

- Два runtime выбираются настройкой `teammateMode`. Флаг `--teammate-mode` тоже работает, но скрыт в `--help` [1][8].
- Жёсткого предела числа teammate-ов нет [1]. Предел в 20 одновременных subagents на них не распространяется; их собственные пределы не описаны [7].
- Одна команда на сессию. Teammate-ы не запускают своих teammate-ов. Lead не меняется [1].
- Фоновая работа in-process teammate-а не переживает процесс lead [1].
- На Linux ограничение памяти для вида `agent` покрывает дочерние процессы Claude Code, включая teammate-ов [6].

### Изоляция

- **Между teammate-ами нет изоляции файловой системы.** Документация советует делить работу по файлам. Два teammate-а в одном файле перезаписывают друг друга [11][1].
- **`isolation` в определении для teammate-а игнорируется.** Teammate работает в рабочем каталоге главной сессии. `isolation` в самом вызове даёт subagent вместо teammate-а [7].
- **Что получают subagents.** `isolation: worktree` даёт subagent-у временный worktree от ветки по умолчанию. Если subagent ничего не изменил, worktree удаляется [7].
- **Teammate-ы наследуют каталог, CLAUDE.md и MCP config lead.**
  - Свой рабочий каталог для teammate-а просят в issue #23669: 33 голоса, открыт с 2026-02-06 [106]. Одна заметка называет его самым популярным запросом о командах [106]. По подсчётам трёх других заметок, запросы на backends терминалов набрали больше — до 96 реакций у zellij [108].
  - Ошибка в tmux запускала teammate-ов в `$HOME` (v2.1.199; закрыт как not planned) [135].
- **Нет веток и PR для teammate-ов.** Запрос на ветку для каждого teammate-а, взаимный review и слияние под управлением lead открыт [161].
- **Своей sandbox нет.** Контейнеров или VM для команд документация не описывает. В проекте компилятора C изоляцию давали Docker и git, вне функции [46].

### Состояние, возобновление и память

- **Имя команды** — `session-` плюс первые 8 символов ID сессии [1].
- **Что переживает сессию** [1][29]:
  - папка config команды удаляется в конце сессии;
  - папка задач остаётся, пока её не удалит `cleanupPeriodDays` (по умолчанию 30 дней).
- **Что восстанавливает resume** [1]:
  - `/resume` и `/rewind` не восстанавливают in-process teammate-ов;
  - в той же сессии сообщение остановленному in-process teammate-у возвращает его с сохранённым разговором. Его определение применяется снова, только если папка с файлом определения trusted [1][10].
- **Регрессия resume.** С v2.1.178 возобновлённая сессия получала новый пустой список задач: имя команды строилось от нового runtime ID сессии. Диагноз поставил сотрудник Anthropic [136]. Исправлено в v2.1.311 (2026-10-26) [38][39].
- **Teammate-ы без lead.** С v2.1.323 (2026-11-12) split-pane teammate, переживший своего lead, отклоняет его запросы. Одобрения планов после `/clear` или `/resume` надо отправлять заново [38][39].
- **Transcripts.** Transcripts subagents лежат в `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl` [7]. Тот же ли путь у in-process teammate-ов — не подтверждено. Split-pane teammate-ы — полные сессии со своими transcripts [135].
- **Начальный контекст.** Свой context window; CLAUDE.md, MCP servers и skills, как у новой сессии; prompt запуска. История разговора lead не переносится [1]. Агенты с `SendMessage` получают снимок списка других именованных агентов [7].
- **Compaction.**
  - Каждый teammate сжимает свой контекст сам [7][38].
  - Способа, которым lead мог бы запустить compaction у teammate-а, нет. Teammate, у которого примерно через 14 часов кончился контекст, можно было только заменить (запрос закрыт как not planned) [145].
  - Compaction у самого lead стирает его знание о команде. Отчёт об этом открыт с 2026-02-06 [105].
- **Prompt cache.**
  - Запросы in-process teammate-ов живут вне cache главного разговора. Поэтому по умолчанию у них 5-минутный cache, даже на подписке. `subagentPromptCacheTtl: "1h"` продлевает его; запись часового cache API оплачивает дороже [1][8].
  - Промахи cache у teammate-ов исправляли в v2.1.261, v2.1.265, v2.1.277 и v2.1.290 [38].
  - По логам одного пользователя на v2.1.217, доставка сообщения teammate-у иногда полностью перезаписывала cache: 396–513 тыс. токенов [139].
  - Отчёт: teammate-ы вообще не получали часовой cache [128]. Boris Cherny писал, что subagents обычно работают с 5-минутным cache, а главный агент — с часовым [93].

### Проверка качества

- **Три блокирующих hook-а** — `TeammateIdle`, `TaskCreated`, `TaskCompleted`. Ни один не поддерживает matchers; каждый срабатывает на каждом событии [2].
  - TeammateIdle получает `teammate_name`, устаревший `team_name` и `agent_id` (с v2.1.290) [2].
  - TaskCompleted срабатывает в двух случаях: когда `TaskUpdate` отмечает задачу выполненной и когда teammate заканчивает ход с задачами in progress [2].
- **Типы hook-ов:** command, http, mcp_tool, prompt (LLM-судья) и agent (проверяющий агент с инструментами). Для prompt на TeammateIdle `ok: false` по умолчанию останавливает teammate-а; `continueOnBlock: true` оставляет его работать. У hook-а agent поля `continueOnBlock` нет: его `ok: false` всегда возвращает причину teammate-у, и тот продолжает работу [2].
- **Пробелы.**
  - У Stop hook есть поле `stop_hook_active` и предел в 8 продолжений подряд. Во входных данных TeammateIdle такого поля нет. Действует ли предел — не описано [2][23].
  - По отчёту пользователя, TaskCompleted срабатывает на каждом idle для задач in progress, и во входных данных нет поля, которое говорит, что вызвало событие (открыт) [159].
  - TeammateIdle срабатывал для fork с чужим transcript [141]; v2.1.290 это изменил [38].
  - Idle-teammate остаётся «running» в поле `background_tasks` Stop hook (отчёт от 2026-11-13) [164].
- **Review задаётся prompt-ом, а не встроен.** Примеры документации: три reviewer-а teammate-а с lenses security, performance и test coverage; отладка «competing hypotheses» [1].
- **Встроенного шага tests, CI, PR или merge для команд в документации нет** [1][2].

### Восстановление после сбоев

- **На уровне запроса.** Временные сбои — 429 (throttle), ошибки сервера, перегрузка, timeout, обрыв соединения — повторяются до 10 раз с экспоненциальной задержкой [10].
- **Когда ход teammate-а умер.**
  - Teammate сообщает lead «failed» с текстом ошибки [1][38].
  - Сообщение in-process teammate-у, который ждёт повтора, запускает повтор сразу [1].
  - Цепочка запасных моделей может переключить subagent или teammate на другую модель. О переключении teammate-а пользователю не сообщают [20].
- **Восстановление — вручную или силами lead** [1]:
  - teammate-ы могут остановиться после ошибки вместо того, чтобы восстановиться. Документация советует дать им указания или запустить замену;
  - статус задачи может отставать. Надо проверить, сделана ли работа, и поправить статус вручную или подтолкнуть teammate-а.
- **Остановка.** Teammate заканчивает текущий вызов, прежде чем остановиться. Сессии tmux могут остаться без хозяина; их удаляют `tmux kill-session` [1].
- **Дефекты.**
  - Дубликаты: один запуск превращался в 10–151 скрытых копий teammate-а, и все правили файлы (v2.1.90–v2.1.126; закрыт как not planned) [129].
  - Битая запись в mailbox вызывала падение раз в секунду; исправлено в v2.1.207 [38].
  - Lead не обрабатывал уведомления teammate-ов, пока не нажмут Enter (v2.1.116, апрель 2026; закрыт за неактивностью). Есть ли это сейчас — не подтверждено [127].
  - Lead завершался через секунды после того, как teammate согласился на shutdown (v2.1.280, открыт) [152]. В v2.1.304 исправлен похожий выход, когда shutdown одобряет главная сессия. Закрывает ли это отчёт — не подтверждено [38].
  - Shutdown подтверждали, но teammate-ы не завершались [126].
  - В многодневных сессиях auto-updater удалял работающий бинарник, и новые teammate-ы не запускались [144].

### Лимиты и стоимость

- **Модель затрат.**
  - Каждый teammate — полный экземпляр Claude. Расход токенов растёт с числом активных teammate-ов и временем их работы [4][1].
  - Команды тратят примерно в 7 раз больше токенов, чем обычная сессия, когда teammate-ы работают в plan mode [4]. Пост в блоге для разработчиков (сентябрь 2026) повторяет это число [60].
  - Советы: Sonnet для teammate-ов; маленькие команды и короткие prompts запуска; останавливать teammate-ов, потому что каждый активный teammate тратит токены, пока не завершится он сам или сессия [4].
- **Выбор модели** — порядок источников и `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`; allowlist организации подменяет модель [1][9].
- **Бюджета команды нет.** Бюджета на команду, предела токенов или планирования по лимитам документация не описывает. Hook `agent.spawn` у mod может отказать в запуске или выбрать модель; это возможное место для бюджета [22].
- **Лимиты подписки** (5-часовое окно и недельный лимит).
  - **Главная сессия ждёт и продолжает.** С v2.1.234 (2026-08-17) интерактивная сессия на подписке claude.ai ждёт в открытой сессии и сама продолжает задачу после сброса. Включено по умолчанию настройкой `autoContinueAtUsageLimit` [5][8][38][39].
  - После сброса Claude Code просит Claude продолжить задачу. Последнее сообщение пользователя повторно не отправляется. Запросы прав по-прежнему могут остановить работу [5].
  - **Пределы ожидания** [5]:
    - не больше трёх автоматических продолжений;
    - сама сессия не ждёт сброса, до которого больше 24 часов, то есть недельного лимита;
    - если компьютер спал дольше примерно 30 минут, нужно нажать Enter;
    - выход из сессии отменяет ожидание.
  - **Teammate-ы исключены.** В сессиях teammate-ов Claude Code сам ожидание не запускает; человек должен выполнить там `/rate-limit-options` [5]. Lead после сброса продолжит, а teammate-ы, упавшие на лимите, только сообщат «failed» и продолжат, когда им напишут [1]. Будит ли их продолжение lead — не описано.
  - **Где ожидания нет вообще:** фоновые сессии, запуски `-p`, оплата API-ключом и через облачных провайдеров [5]. Само не запускается и под Remote Control [5]; открытый отчёт говорит, что при подключённом Remote Control оно не включается никогда [157].
  - **Dynamic workflows** ставят паузу на лимите и продолжают после сброса: не больше двух раз за запуск и только если сброс ближе 24 часов. Не работает в `-p`, фоновых сессиях, под Remote Control и в сессиях teammate-ов [12]. Для вкладки Code в Desktop документация называет версию v2.1.319, а changelog — v2.1.323 [12][38].
  - **Для работы без присмотра** — переменная `CLAUDE_CODE_RETRY_WATCHDOG=1` [10][9]:
    - бесконечно повторяет ошибки 429 и 529;
    - ждёт сброса лимита плана, если ответ несёт время сброса;
    - ожидание можно ограничить `…_MAX_USAGE_LIMIT_WAIT_MS` (v2.1.301+) и проверять раньше через `…_USAGE_LIMIT_RECHECK_MS` (v2.1.305+);
    - при 429 из-за лимита расходов сразу сдаётся.
    - In-process teammate-ы проходят через эти долгие паузы повтора. v2.1.260 исправил потерю сообщений и пустой transcript in-process teammate-а во время таких пауз [38].
    - Split-pane teammate-ы получают фиксированный набор переменных окружения. Поэтому переменная, экспортированная только в shell, может до них не дойти. Это вывод заметок из [6] (не подтверждено).
  - **Desktop** имеет свой флажок «Auto-continue when limits reset» для 5-часового лимита, но не для недельного [10]. Команд в Desktop нет [16].
  - **Предупреждения.** Одна большая вспышка работы, например fan-out большого workflow, может съесть недельный лимит раньше, чем сбросится 5-часовое окно [10]. Есть предупреждение на 85% и поля `rate_limits` для status line [10].
  - **Согласие на кредиты usage** в сессиях teammate-ов держится `dialogExpiry` (5 минут по умолчанию), затем ход заканчивается без ответа [10][20].
- **Сообщения пользователей о лимитах.** Ошибки 429 и 529 при пяти teammate-ах на Max [123]. Lead в цикле ответов на idle notifications [125]. v2.1.212 перестал дублировать тела `SendMessage` в повторно отправляемой истории [38].

### Права и безопасность

- **Режим прав.** Новый teammate стартует в режиме lead, включая `bypassPermissions`. Lead в `dontAsk` даёт teammate-ам Manual. Отдельных режимов при запуске нет [1]. In-process teammate остаётся в режиме lead, пока lead в acceptEdits, auto или bypass, даже если status bar teammate-а показывает Manual [1].
- **Правила.** In-process teammate-ы — под живыми allow- и deny-правилами lead. Split-pane получают deny-правила командной строки и `--tools`. Если deny-правило нельзя передать без искажений, запуск прерывается [1][10].
- **Куда идут запросы прав.**
  - Документация: запросы teammate-ов появляются в сессии lead [1]. Они идут через mailbox [10][38].
  - Открытые отчёты пользователей говорят иначе:
    - split-pane teammate-ы бесконечно ждут ответа на запрос в своих panes. Lead о них не знает, срока ожидания нет [160];
    - один ждущий запрос в in-process teammate-е задерживал сообщения всех teammate-ов к lead на 5–10 часов [162].
  - Сотрудник Anthropic воспроизвёл случай, когда запрос split-pane teammate-а не доходит до hooks `PermissionRequest` ни в одной из сессий (v2.1.233). Потом отчёт закрыли за неактивностью [140][165].
- **Настройка для работы без человека.** `permissions.denyInsteadOfPrompting` (v2.1.319, 2026-11-06) превращает будущие запросы в отказы; teammate-ы тоже покрыты [8][38].
- **Доверие между агентами** [1][21]:
  - teammate-ы не могут одобрять запросы и давать согласие;
  - отказанное действие нельзя передать другому teammate-у в обход проверки;
  - в auto mode classifier проверяет каждый `SendMessage` — и обычный, и protocol — до доставки (v2.1.222+). Пересланные «одобрения» он считает недоверенными.
- **Укрепление.**
  - С v2.1.323 split-pane teammate-ы проверяют, что запросы правда пришли от их lead [38].
  - Определение вернувшегося teammate-а применяется снова только из trusted папки [1][10].
  - SDK пишет, что поле `from` заполняет сам отправитель и его можно подделать. Только доставка через socket cross-session messaging несёт PID отправителя, проверенный ядром ОС (`verifiedPeerPid`); на Windows этого поля нет [23].

### Где участвует человек

- Нужна интерактивная сессия [1].
- Agent panel: выбор teammate-а, transcript, прямые сообщения, прерывание, остановка, список задач [1].
- Набор текста при открытом teammate-е: обычный текст и skills — teammate-у; встроенные команды — lead; `/compact`, `/clear`, `/rewind` — с подтверждением; `/model` и `/fast` запрещены [1].
- Ответы на запросы shutdown, одобрение планов (по умолчанию автоматическое), запросы прав у lead [1].
- Документация не советует надолго оставлять команду без присмотра [1].

### Наблюдаемость

- **В терминале.** Строки панели показывают working, idle и failed teammate-ов. Idle-строки прячутся через 30 секунд, больше трёх idle сворачиваются в одну строку, failed остаются [1]. Split panes показывают живой вывод каждого teammate-а [1].
- **Окно in-process teammate-а** держит только последние 50 сообщений и не загружает transcript с диска (открытый отчёт) [154].
- **OpenTelemetry.** Spans несут `agent_id` и `parent_agent_id` для subagents и teammate-ов. В log events у in-process teammate-ов `agent_id` нет [26].
- **Программный доступ:**
  - hooks получают `agent_id` (v2.1.290+) [2];
  - `ListAgents` показывает teammate-ов (v2.1.239) [6][38];
  - `$.agent.list()` у mods возвращает статусы pending, running, waiting, idle, completed, failed и killed [22].
- **Ленты событий или replay запуска команды** в документации не найдено.

### Точки расширения

- Определения subagents как роли teammate-ов — уровня проекта, пользователя, managed или plugin [1].
- Hooks команды и hooks, которые касаются teammate-ов [2].
- Mods: `agent.spawn` с `isTeammate` (выбор модели, отказ в запуске; с v2.1.299 — и при возобновлении) и `turn.start` для ходов teammate-ов [22][38].
- Настройки и переменные окружения: `teammateMode`, `subagentPromptCacheTtl`, `CLAUDE_CODE_TASK_LIST_ID` [8][9].

### Файлы на диске

Исходников для ссылок нет: код CLI закрыт [40]. Вот что команда держит на диске:
- `~/.claude/teams/{team}/config.json` — runtime-состояние команды и массив `members`; удаляется в конце сессии [1];
- `~/.claude/teams/{team}/inboxes/{agent}.json` — inbox каждого агента [1];
- `~/.claude/tasks/{team}/` — по одному JSON на задачу, например `1.json`; хранится до 30 дней [1][136][29];
- `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl` — transcripts subagents. Пишут ли сюда in-process teammate-ы — не подтверждено [7].

### Где документация расходится с сообщениями пользователей

1. **Доставка сообщений.** Документация: доставка автоматическая [1]. Пользователи: занятому teammate-у сообщение приходит только после конца хода [155][156].
2. **Опрос mailbox.** Документация: lead не нужно опрашивать [1]. Разбор бинарника: in-process teammate-ы сами опрашивают mailbox примерно раз в 500 мс, а idle-teammate-ы могли делать это часами [149].
3. **Запросы прав.** Документация: появляются в сессии lead [1]. Пользователи: split-pane teammate-ы ждут в своих panes без срока, а один ждущий запрос задерживает сообщения всех [160][162].
4. **Worktree.** Документация: `isolation` во frontmatter для teammate-а игнорируется, в самом вызове — даёт subagent [7]. Пользователи: `isolation: "worktree"` молча не работал [132][118], а teammate, вошедший в worktree, перенёс туда всех агентов сессии [142].
5. **Заблокированные задачи.** Документация: teammate-ы их сами не берут [1]. Пользователь: teammate захватил такую задачу через `TaskUpdate` [159].
6. **Флаг.** Документация: функция выключена по умолчанию [1]. Сотрудник Anthropic: для некоторых аккаунтов флаг всегда включён (не подтверждено) [136].

## Что говорят пользователи

### Общая картина

- Пользователи в целом считают функцию самым удобным встроенным способом запустить несколько сессий Claude, которые общаются между собой. Настраивать почти нечего, оплата входит в подписку [76][94][84].
- На то, что функция не работает, жалуются редко. Жалобы — о четырёх вещах:
  1. она очень быстро тратит токены и лимиты плана [75][87][88][85];
  2. lead хрупкий: его ломают compaction, время доставки сообщений и остановка [105][125][121][156][152];
  3. у teammate-ов общий рабочий каталог, и они перезаписывают друг друга [106][118][89];
  4. нужен человек рядом: teammate-ы останавливаются на запросах прав, а работа с терминалом ограничена [75][87][108][117][109][112][103][115][104][160].
- Самые популярные запросы о командах на GitHub просят новые backends для терминалов (zellij, Ghostty, Windows Terminal, WezTerm), а не более умную координацию [108][117][109][112][103][115].
- Активные пользователи берут функцию для параллельного review, споров и отладки. Тот, кому нужны долгие запуски, несколько репозиториев или агенты разных вендоров, чаще уходит к внешним оркестраторам [89][106][148][76].

### Запуск в феврале 2026

Ветка о запуске на HN набрала 396 points и около 220 комментариев [75]. Основные темы:
- **Сравнение с Gas Town** — оркестратором агентов Steve Yegge. Многие сравнили сразу. Комментаторы назвали схему Anthropic проще: один lead и worker-ы против многих именованных ролей Gas Town. Один предсказал, что победит клон без причуд [75].
- **Шутки о расходе токенов.** Спрашивали, хватит ли плана за $20 на десять минут. Писали, что квота уйдёт за минуты, в основном на сообщения делегирования. Другие отвечали, что функция для компаний на API [75].
- **Хотели работу без присмотра.** Один пользователь хотел, чтобы Claude собрал все нужные разрешения заранее и поставил работу в очередь на ночь. Другой ответил, что без присмотра она по-настоящему не работает [75].
- **Хорошие первые впечатления:**
  - lead продолжает разговор, пока teammate-ы работают [75];
  - пользователь, который вёл четыре сессии вручную, сказал, что с командой узким местом стал он сам: не успевал писать spec и проверять работу [75];
  - reviewer превратил четыре параллельных review-агента в команду, которая обсуждает находки, и назвал результат потрясающим [75].
- **Скептики:**
  - на больших задачах ей нельзя доверять [75];
  - узкое место — проверка, а не оркестрация [75];
  - возможно, это способ продать больше токенов [75];
  - хватает worktree и параллельных сессий [75];
  - вендор модели не должен владеть циклом агента [75].
- **Хотели разные модели**, например lead на Opus и worker-ы на Gemini или Codex. Функция работает только с Claude [75].

**Компилятор C.** В тот же день Anthropic опубликовала проект компилятора C: 16 агентов, около $20 000. Пост называет подход «agent teams», но это собственный harness: цикл на bash, контейнеры Docker и lock-файлы в git, без агента-оркестратора [46]. Ветку на HN (735 points) озаглавили так, будто проект использовал функцию [77]. Комментаторы писали, что успех дали скорее наборы tests, чем схема из многих агентов [77]. По цитате на HN, подзаголовок Ars Technica говорил, что проекту всё равно требовалось глубокое управление человеком [78].

### Что хвалят

- **Параллельный review, споры и отладку.**
  - Reviewer-ы работают командой и перепроверяют утверждения друг друга [75].
  - Skill «red team» использует команду, чтобы критиковать и ранжировать отзывы [84].
  - Показательные случаи самой документации — конкурирующие гипотезы и review с нескольких углов [1].
- **Разбор инцидентов.** Отчёт практика: lead плюс четыре teammate-а — Slack, Datadog, Sentry и review кода через MCP [71]:
  - root cause нашли примерно за 10 минут против оценки 30–45 минут в одиночку;
  - расход — около $8–10 по ценам API против $2–3 для одной сессии;
  - вывод автора: стоит того, когда важно время, но не для мелких проблем.
- **Чистый контекст lead.** Главной пользой пользователи называют то, что основной разговор остаётся маленьким, а тяжёлая по токенам работа идёт в свежих context window [75][90].
- **Ничего не надо настраивать.**
  - Автор собственного mailbox-инструмента признал, что встроенная версия выигрывает уже тем, что её не надо ставить, — в пределах своих возможностей [76].
  - Другой пользователь выбрал Claude Code среди конкурентов отчасти из-за agent teams [84].
  - Третий отметил, что функция входит в подписку и API-ключ не нужен [94].
- **Результаты, о которых пишут пользователи:**
  - сложный модуль Ansible с одной попытки [80];
  - backend для ZFS, перенос сервиса картинок на Go, Rust и Zig, отладка базы данных [85];
  - Wayland-композитор примерно за три недели [85];
  - схема на Bedrock: оркестратор на Opus, worker-ы на Sonnet [91];
  - проект длиной в месяцы. К октябрю 2026 тот же пользователь писал, что agent teams с Opus 5.5 уже по умолчанию достаточно хороши для координации в стиле stand-up [99].
- **Обращённые.** Один пользователь написал, что больше не представляет работу с одним агентом. По его словам, токенов уходит примерно в 10 раз больше, но результат лучше и быстрее [87].

### Что ругают

#### Токены и лимиты плана — самая частая жалоба

- **Числа Anthropic.** Расход растёт линейно с размером команды [1]. В plan mode команды тратят примерно 7× токенов обычной сессии [4]. Anthropic советует Sonnet для teammate-ов, маленькие команды и остановку teammate-ов после работы, потому что idle-teammate тоже тратит токены [4].
- **Числа пользователей:**
  - один prompt запустил 9 и больше агентов и потратил около 1 млн выходных токенов примерно за час [87];
  - около 1 млн токенов за 15 минут; автор предсказал, что цена $200 не удержится [88];
  - лимиты плана Max кончились меньше чем за час [85];
  - два агента Opus параллельно на Max x1 уже упирались в лимиты [85];
  - читатель Show HN не мог запустить больше одного-двух агентов до лимита [92].
- **Расходы на саму координацию:**
  - разбор файлового протокола насчитал idle notifications каждые 2–4 секунды. Автор оценил, что команды стоят примерно вдвое дороже subagents на ту же работу [70];
  - отчёт об ошибке: lead тратил входные токены на подтверждение idle notifications и повторённые назначения задач. Координация, которой хватило бы 6–8 ходов lead, заняла 60–100 [125]. По подсчёту автора, чистые подтверждения уведомлений заняли 13.0% входных токенов командной части сессии, а вместе с ходами, где lead будили сообщения teammate-ов, — 22.2% [125]. Отчёт закрыт ботом как not planned 2026-11-11;
  - остановка на 90 минут сожгла около 15 млн cache-read токенов [124].
- **Дубликаты teammate-ов.** Один запуск превращался в 10–151 скрытых копий. Худшая сессия дошла до 592 экземпляров, 389 одновременно. Автор оценил ущерб примерно в $86 000 по ценам API за 14 недель. Отчёт закрыт как not planned [129].
- **Cache.** Teammate-ы не получали часовой prompt cache [128]. Boris Cherny писал, что subagents обычно на 5-минутном cache, главный агент — на часовом [93]. Сейчас документация предлагает `subagentPromptCacheTtl: "1h"` с более дорогой записью [1].
- **Ошибки rate limit.** 429 и 529 при пяти teammate-ах на Max [123].
- **Обратное мнение.** Автор dashboard-а утверждал, что команды экономнее из-за свежих context window, а установленные plugins и skills могут умножить расход в 5–10 раз [92].

#### Lead — единая точка отказа

- **Compaction стирает команду.** После сжатия контекста lead забывает свою команду. Teammate-ы продолжают выдавать результаты, которые никто не читает, и остаются брошенные файлы. Отчёт открыт с 2026-02-06. Один комментатор назвал это самой частой ошибкой, на которую он натыкается в agent teams [105].
- **Lead ждёт нажатия клавиши.** В режиме in-process lead застревал на ожидании результатов, пока не нажмут клавишу [121].
- **Lead ведёт себя не так.** Делает задачи сам вместо делегирования или заканчивает команду раньше времени. Документация советует сказать ему ждать или продолжать [1][69].
- **Lead завершается после shutdown.** Процесс lead выходил через секунды после того, как teammate согласился на shutdown (v2.1.280, открыт) [152]. Changelog v2.1.304 исправляет похожий выход, когда shutdown одобряет главная сессия. Закрывает ли это отчёт — не подтверждено [38].

#### Время доставки сообщений и дубли работы

- **Сообщения приходят только между ходами.**
  - Проверочные сообщения lead копятся непрочитанными, пока teammate занят. Lead решает, что teammate не отвечает, и запускает дубликаты [122].
  - Поправка, отправленная посреди задачи, приходит только после того, как работа, которую она должна была остановить, уже закончена (открыт, 2026-10-03) [156].
- **Терялись финальные ответы.** До v2.1.251 (2026-08-28) финальные ответы teammate-ов не доходили до lead [38][39].

#### Общий рабочий каталог: конфликты файлов, нет worktree

- **Схема держится на том, что файлы не пересекаются.**
  - Автор конкурирующего инструмента пишет: встроенная схема полагается на file locking, поэтому задачи должны трогать разные файлы, иначе агенты перезаписывают друг друга. Его инструмент даёт каждому worker-у свой git worktree и добавляет проверки [89].
  - Документация согласна: каждому teammate-у — свои файлы [1].
  - Один практик разрешает писать код только lead [72].
- **Worktree для teammate-ов ломается:**
  - teammate-ы игнорировали `isolation: "worktree"`, потому что в команде запуска не было флага. Пользователь видел это ещё в v2.1.168. Закрыт как not planned [118];
  - teammate, вошедший в worktree, молча перенёс туда всех остальных агентов сессии [142];
  - по текущей документации, именованный вызов Agent с `isolation` не запускает teammate-а. Вывод заметок, прямо не сказанный в документации: teammate-а нельзя изолировать в worktree [1].
- **Свой рабочий каталог для teammate-а.** Запрос на свой каталог, CLAUDE.md и MCP config набрал 33 «+1» и всё ещё открыт [106]:
  - комментаторы тратят токены на префиксы `cd`;
  - одна группа бросила agent teams для работы с несколькими репозиториями;
  - pane tmux создаётся без начального каталога.
- **Зрелые кодовые базы.** Пользователи HN замечают, что сквозные функции вызывают конфликты дизайна и ограничивают параллельность [81].

#### Права и работа без присмотра

- **Одобрения копятся.** Пользователи описывают бесконечные одобрения и советуют sandbox с отключёнными запросами прав [85][72]. Один ожидает, что большинство будет запускать команды небезопасно, и говорит, что удобства для разработчика почти нет [87].
- **Режимы наследуются.** Режим прав берётся у lead, включая bypass, и при запуске отдельно не задаётся [1]. Отчёт: teammate-ы всё равно спрашивают разрешение на Bash в bypass, а выборы «always allow» не наследуются (открыт) [114].
- **Запросы, которых никто не видит.** Teammate-ы в panes tmux бесконечно ждали ответа на запросы прав и доверия к папке. Lead об этом не сообщали. Пользователь, который следил с телефона, ничего не видел (открыт, 2026-10-22) [160]. То же с диалогом development channel (открыт, 2026-11-11) [163].
- **Запустилась без спроса и не останавливалась.** Пользователь подал формальную жалобу: команда запустилась без одобрения, и остановить её можно было только убив сессию [119]. В другом отчёте запросы shutdown подтверждались, но teammate-ы не завершались [126].
- **Что добавили позже:**
  - клавиша `x` останавливает выбранного teammate-а [1];
  - v2.1.319 (2026-11-06): `permissions.denyInsteadOfPrompting` отклоняет вызов вместо ожидания ответа [38][39].

#### Терминал, UI и видимость

- **Самые популярные запросы — о panes:** backends для zellij, Ghostty, Windows Terminal, WezTerm и подключаемый протокол backends. Числа реакций — в таблице «Самые популярные запросы» ниже [108][117][109][112][103][115].
- **Неподдерживаемые терминалы.** Документация подтверждает: split panes не работают в терминале VS Code, Windows Terminal и Ghostty [1].
- **Поломки tmux.** Команды ломали пользователям раскладку tmux. Искажённый `send-keys` уронил 2 агента из 4 [76][104].
- **За работой не уследить.** Агенты в tmux двигаются слишком быстро, и пользователь попросил настройку скорости [98]. Другой сказал, что интерфейс на переднем плане недостаточно хорош [87].
- **Dashboards.** Запрос на dashboard запущенных агентов с usage по каждому открыт [113]. Dashboard на hooks набрал 719 звёзд на GitHub [74]. В его ветке подняли ещё одну проблему: агенты докладывают, что исправили ошибку, хотя только заглушили её, и логи этого не показывают [92].

#### Настройка

- **Свои определения агентов.** Сначала жаловались, что teammate-ы — одинаковые клоны: у subagents была специализация без переписки, у команд — переписка без специализации [111]. 2026-08-17 Anthropic сообщила, что teammate-ы могут использовать определения из `.claude/agents/`. Их tools и model применяются, skills и `mcpServers` — частично нет [111][1].
- **Наследование effort и модели.** Ошибки возвращаются; два issue про effort открыты [158].
- **Описание ролей.** Запросы на декларативное описание команды и на хранение ролей в репозитории открыты. Сейчас team config — runtime-состояние, заранее его не написать [148][153][1].

#### Привязка к сессии

- Одна команда на сессию, без вложенности, lead не меняется. `/resume` и `/rewind` не восстанавливают in-process teammate-ов [1].
- Пользователь пишет: команда умирает, когда закрывается терминал; переписки между разными инструментами нет; журнала, который переживает сессию, нет [76].
- Запрос на команды на нескольких машинах закрыт как дубликат [131].
- Инструмент, который защищает команды при compaction, набрал 430 звёзд [74].
- v2.1.311 (2026-10-26) исправил пустой список задач после resume [38][39].
- В многодневных сессиях auto-updater удалял работающий бинарник, и следующие teammate-ы не запускались [144].

#### Hooks как quality gates и их ошибки

- **Проверки вне агентов.** Команды, которые доверяют результату, ставят проверки снаружи. Пример: проверки на Python отказывают в закрытии задачи, пока не прошли tests и критерии приёмки; кодовая база — 71 тыс. строк [83]. Другой инструмент заставляет worker-а доказать завершение, прежде чем брать новую работу [89].
- **Ошибки hooks:**
  - `TaskCompleted` срабатывает на каждом idle teammate-а, а задачу с незаконченной зависимостью всё равно можно захватить (открыт, 2026-10-10) [159];
  - `TeammateIdle` срабатывал для fork с чужим transcript [141]; v2.1.290 это изменил [38];
  - idle-teammate остаётся «running» в `background_tasks` Stop hook (отчёт от 2026-11-13) [164].
- **Нужен общий hook простоя.** Внешний оркестратор Claude Code и Codex попросил hook `SessionIdle`, чтобы будить любую сессию [151].

#### Разбор issues и закрытия ботом

- **Скопления ошибок:**
  - доставка сообщений и запуск в tmux — в первую неделю [38];
  - запросы прав teammate-ов роняли lead — апрель 2026 [38];
  - исправления panes tmux — вплоть до ноября [38].
- **Закрытия ботом.** Многие серьёзные отчёты закрыл как not planned бот неактивности [118][125][129][121]. Пользователи заводят их заново и жалуются на это [156][153]. Отчёт #87647 насчитал больше 6 000 issues с меткой «has repro», которые бот закрыл с марта 2026 [146]. Закрытый issue не значит исправленный.

### Истории неудач

- **Уверенно и неправильно.** В схемах из многих агентов агенты не падают, а спокойно и уверенно делают не то [83].
- **Агенты-оппоненты могут множить ошибки.** Они делают одинаковые ошибки, а ошибка на уровне одобрения расходится дальше [96].
- **Отладка командой стоит денег и опыта.** Один комментатор оценил отладку командой в $1–5 за ошибку и заметил, что разработчик ничему не учится из такого исправления [82].
- **Трудно занять много агентов.** Один пользователь не может загрузить 16 агентов работой, не растрачивая их нарочно, даже с полными agent teams [100].
- **Большие автономные проекты обходились без функции.** Декомпиляция игры на 500 млрд токенов шла через независимые сессии CLI, которые координировались через GitHub issues, Discord и CI, а не через agent teams. Там агент-reviewer принимал плохие отклонения, а агенты пытались обмануть проверку и править проверяющий код [73]. Компилятор C тоже делали на собственном harness [46].

### Почему приходят и почему уходят

- **Приходят:**
  - встроено, ничего не надо ставить [76];
  - входит в подписку [94];
  - хорошо для review и споров [75][84];
  - контекст lead остаётся чистым [90];
  - сильные модели (Opus 4.5 и новее) наконец сделали команды рабочими [85].
- **Уходят или не начинают:**
  - стоимость и лимиты [85][92];
  - настоящее узкое место — проверка [75][81];
  - нужны несколько репозиториев, разные инструменты или несколько машин — это толкает к внешним решениям [76][106][131];
  - некоторым удобнее параллельные сессии в worktree [75];
  - одного-двух агентов с хорошим prompt хватает [81];
  - один разработчик перечислил команды из многих агентов среди того, чем перестал пользоваться [86].

### С чем сравнивают

- **Subagents.** Дешевле, но только отчитываются. Команды дороже, зато агенты переговариваются [1][69][70]. Обычный совет: если агентам не нужно общаться, берите subagents [70].
- **Gas Town и Gas City** (18.8 тыс. звёзд у Gas Town) [74]. Пользователи видят в agent teams более простую массовую версию [75]. Некоторые спрашивают, что Gas City добавляет к шаблонам с subagents [96]. Один комментатор назвал Claude Code первым крупным игроком с оркестрацией агентов в отдельных процессах [96].
- **Самодельные оркестраторы** — worktree, devcontainers, скрипты tmux, CAS, Metaswarm, amux. Их выбирают ради изоляции каждого агента, прав по репозиториям и проверок [89][81].
- **Слои переписки между инструментами** — mcp_agent_mail (2.2 тыс. звёзд), AgentWorkforce relay (1.1 тыс.) [74]. Agent teams видят как mcp_agent_mail, встроенный в runtime, но привязанный к сессии [76].
- **Codex CLI.** Своих agent teams у него нет; `/goal` у Codex появился раньше [97]. Есть мосты, которые делают Codex и другие CLI teammate-ами [95][74].
- **Dynamic workflows Anthropic** (2026-05-28):
  - позиционируются как подход на один-два порядка больше агентов, по фазам [98];
  - пользователь, которому не удалось сделать agent teams надёжными для функций от начала до конца, спросил, заменяют ли их workflows. Anthropic ответила, что workflows помогают и там [98];
  - пользователи путаются в agents, subagents, tasks, teammates, `/goal`, `/loop` и workflows [98];
  - workflows тратят ещё быстрее: у одного пользователя 62 subagents на Opus съели 5-часовой лимит за 18 минут [98];
  - пользователи хотят оркестрацию, не привязанную к одному провайдеру [98].

### Что убрали или упростили

- Явный жизненный цикл команды (v2.1.178) [38].
- Настройку модели teammate-а по умолчанию и поле `team_name` в hooks (устарело) [38][2].
- Delegate mode — по сообщениям пользователей [101]. Он ограничивал lead инструментами координации. Пользователь видел его в v2.1.32 [102]. В текущей документации его нет [1]. Когда его убрали, официально не подтверждено.
- Broadcast. В марте 2026 его описывал пользователь [116]; сейчас документация велит писать каждому получателю отдельно [1]. Когда его убрали — не подтверждено.
- Task tools на новых моделях — теперь по желанию. Документация объясняет, что новые модели ведут многошаговую работу без записанного списка [6].
- **Итог:** на текущих моделях одна из четырёх частей архитектуры — общий список задач — необязательна. Без Task tools агенты координируются сообщениями [1]. Hook `TaskCreated` в таких сессиях не срабатывает [2].

### Сближение с subagents

- Определения агентов можно использовать как teammate-ов [111][1].
- `SendMessage` работает и без agent teams; флаг нужен только сообщениям протокола (shutdown, одобрение плана) [7].
- Subagents и teammate-ы показываются в одной agent panel [1].

### Укрепление и расширяемость

- Укрепили: отчёты о сбоях, ошибки записи в mailbox, наследование deny-правил, проверку, что запрос пришёл от lead, отказ вместо вопроса, когда ответить некому [38].
- Расширили: hooks команды — в феврале и марте, hooks mods для teammate-ов — в октябре [38].

### Другие поверхности росли быстрее

- Agent view (research preview), dynamic workflows (GA), cross-session messaging и Projects (beta) вышли, пока agent teams оставались экспериментом [13][55][15][14].
- Документация о параллельной работе перечисляет пять подходов. Только agent teams помечены как экспериментальные и выключенные по умолчанию [11].
- Документация Desktop отправляет тех, кому нужны команды, к dynamic workflows [16].
- Пост о dynamic workflows называет «agent teams» среди самодельных harness-ов, которые workflows теперь заменяют более естественно [56].
- API Managed Agents для многих агентов даёт subagents, dynamic workflows и модель-советника. Примитива равноправной команды в нём нет [65].
- Планы переименовали: Max 20x стал Ultra, Max 5x — Max [36].

### Интерпретация заметок (не позиция Anthropic)

Одна из заметок считает, что Anthropic переносит оркестрацию в трёх направлениях:
- в код — скрипты workflows;
- в облако — координатор Projects;
- в модель — меньше инструментов harness.

По этой оценке, agent teams остаются экспериментом CLI, который постепенно сливается с именованными адресуемыми subagents. Идея «команды» при этом жива в масштабных исследованиях Anthropic, но там она координируется через базу данных и Git, а не через сообщения [63].

## Слабые места и чего нет

- **Экспериментальная уже девять месяцев.** Выключена по умолчанию. Документация признаёт ограничения в возобновлении, координации задач и остановке [1].
- **Нет изоляции файлов.** Worktree для teammate-ов нет. Работу надо делить по файлам вручную [11][1]. `isolation` превращает teammate-а в обычного subagent [7]. Пользователи сообщают о молча проигнорированном worktree и о переносе всех агентов в чужой worktree [132][118][142].
- **Привязка к одной сессии.** Одна команда, без вложенности, lead не меняется, разделить команду нельзя. `/resume` и `/rewind` не восстанавливают in-process teammate-ов. Config команды удаляется в конце сессии [1].
- **Нет плана дольше сессии.** Нет epic, ticket или очереди. Только папка задач живёт до 30 дней [1][29]. На текущих моделях общий список задач по умолчанию выключен [6][38].
- **Lead — единая точка отказа.** После compaction забывает команду [105]. Делает работу сам или заканчивает раньше [1]. Ждал нажатия клавиши [127][121]. Завершался после shutdown [152].
- **Доставка сообщений.** По отчётам, занятый teammate получает сообщение только после конца хода [155][156]. Это ведёт к дубликатам и запоздалым поправкам [122]. События Monitor не будят idle-teammate-а [137]. Ответы на idle notifications порождают «пинг-понг» [143].
- **Запросы прав.** Могут молча блокировать teammate-а [160][162][163]. Hooks `PermissionRequest` на запросы teammate-ов не срабатывают [107][140]. Отдельный режим прав для teammate-а при запуске не задать [1]. Bypass mode игнорировался [114].
- **Работа без присмотра.** Документация её не советует [1]. Сессии teammate-ов сами не ждут сброса лимита [5]. Планы teammate-ов по умолчанию одобряются без проверки lead [1].
- **Команда собирается без спроса и без подтверждения** [1]. Был случай, когда её можно было остановить, только убив сессию [119]; shutdown не всегда завершал teammate-ов [126].
- **Стоимость.** Около 7× токенов в plan mode [4], рост линейный с числом teammate-ов [1], 5-минутный cache по умолчанию [1][128], дубликаты teammate-ов [129], расходы на уведомления [125][70]. Бюджета команды нет [22].
- **Только терминал.** Нет GUI и нет Desktop [16]. Split panes не работают в терминале VS Code, Windows Terminal и Ghostty [1]. tmux ломается [76][104]. Окно in-process teammate-а держит последние 50 сообщений [154]. Ленты событий и replay запуска в документации нет.
- **Только Claude** — другие агенты только как MCP server [11].
- **Нет PR, CI и merge** для команды [161].
- **Нет в `-p`, Agent SDK и GitHub Actions** [1][23][24].
- **Нет команд на нескольких машинах** [131].
- **Нет декларативного описания команды** [148][153][1].
- **Lead не может сжать контекст teammate-а** [145].
- **Захват задач:** нет фильтра по роли [150]; заблокированную задачу можно захватить, а TaskCompleted срабатывает на каждом idle [159].
- **Нет broadcast** [1]. **Нет режима, в котором lead только координирует,** — delegate mode убран [101][102][1].
- **Замена модели teammate-а молчаливая** — ни allowlist, ни цепочка запасных моделей о ней не сообщают [1][20].
- **Отчёты об ошибках часто закрывает бот**, а не исправление [146][118][125][129].

## Пересечение с worfy

Описание worfy взято из задания на это исследование. Номера источников в этом разделе относятся только к Claude Code agent teams. Здесь только сравнение, без выводов для worfy.

Термины worfy коротко: Epic — набор Ticket-ов; Ticket — одна задача; Orchestrator session — сессия, которая планирует и раздаёт работу; Autopilot — запускает Wave-ы (пакеты ticket-ов) без присмотра: ждёт сброса лимита подписки, повторяет запросы при ошибках API, одобряет запросы прав по политике; Gate — локальный verification run; Harness plugin — rules, skills, subagents и hooks, которые worfy ставит в Claude Code; Flight Recorder — лента событий запуска без присмотра; Work track — вся работа проекта за день или неделю; Cards — карточки, которые агенты строят на Canvas через MCP server; Product Session — продуктовый советник с живым Mind map и критиком spec; Linked machines — машины пользователя в локальной сети; Evidence — скриншоты-доказательства с privacy scrub (удалением личных данных); Eco mode — режим экономии.

| Продуктовая работа | Product Session с живым Mind map и критиком spec | нет; есть пример с teammate-оппонентом [1] | только у worfy |
| Терминал с AI-помощником, встроенный Browser с профилями, Cards на Canvas через MCP server, Evidence-скриншоты с privacy scrub | есть | аналога нет [1] | только у worfy |
| Переписка worker-ов между собой | в описании нет | `SendMessage` по имени между teammate-ами [1] | только у agent teams |
| Прямой разговор человека с любым worker-ом | в описании нет | Enter в agent panel открывает transcript teammate-а, и набранный текст уходит ему [1] | в описании worfy нет |
| Сообщение агента как согласие пользователя | в описании нет | запрещено: сообщения агентов не несут полномочий пользователя, в auto mode classifier проверяет их до доставки [1][21] | заметка о принципах считает, что это правило совпадает с правилом worfy; в описании worfy, по которому идёт сравнение, его нет |

**Где совпадают по сути:**
- Оба продукта — для одного человека, который ведёт много сессий Claude Code на своей машине [1].
- В обоих одна сессия-координатор раздаёт работу другим сессиям Claude Code [1].
- Оба строятся на механизмах самого Claude Code: CLAUDE.md, skills, определения subagents, hooks, MCP servers [1][2].
- Оба ставят проверку на событиях работы агента: у worfy — Gate и hooks Harness, у agent teams — блокирующие hooks команды [2].
- Review с разными lenses есть в обоих [1].
- Ожидание сброса лимита подписки есть в обоих, но у agent teams — только в сессии lead [5].

**Где расходятся по сути:**
- Agent teams — функция терминала внутри CLI; worfy — отдельное desktop-приложение с Canvas [1][16].
- У worfy каждый ticket в своём worktree; у agent teams общий рабочий каталог [11].
- У worfy план живёт в Epic-ах и Ticket-ах; команда agent teams живёт одну сессию [1].
- Autopilot сделан для работы без присмотра; документация agent teams её не советует, а teammate-ы не ждут сброса лимита сами [1][5].
- У worfy результат идёт через PR и CI; у agent teams нет PR, CI и merge [161].
- worfy запускает Claude Code и Codex CLI; agent teams — только Claude [11].
- worfy одобряет запросы прав по политике; у agent teams — режим lead для всех, вопрос в сессии lead или отказ без вопроса [1][8].
- Teammate-ы пишут друг другу напрямую; в описании worfy переписки между worker-ами нет [1].

## Механизмы, которые стоит изучить

1. **Quality gates на событиях команды (`TeammateIdle`, `TaskCreated`, `TaskCompleted`).**
   - Что: проверка, которая не даёт teammate-у остановиться, создать или закрыть задачу, пока условие не выполнено.
   - Как работает: exit code 2 возвращает stderr модели как обратную связь: teammate продолжает работу, задача не создаётся или не закрывается. `{"continue": false, "stopReason": …}` останавливает teammate-а. TaskCompleted срабатывает и на `TaskUpdate`, и когда teammate кончает ход с задачами in progress; пример документации запускает `npm test`. Hook может быть типа `prompt` (LLM-судья) или `agent` (проверяющий агент с инструментами). У `prompt` на TeammateIdle `ok: false` по умолчанию останавливает teammate-а, а `continueOnBlock: true` возвращает причину и оставляет его работать; hook `agent` всегда ведёт себя как `continueOnBlock: true`. Слабые места: нет matchers; у TeammateIdle нет поля `stop_hook_active`, и предел продолжений подряд не описан (у Stop hook он 8); по отчёту, TaskCompleted срабатывает на каждом idle, а во входных данных нет причины.
   - Источник: [2][23][159].
2. **Файловые mailbox-ы с подтверждённой записью и протоколом в том же канале.**
   - Что: обмен сообщениями между сессиями агентов через JSON-файл на каждого агента.
   - Как работает: файл `~/.claude/teams/{team}/inboxes/{agent}.json`. Записи проверяются при чтении: битые удаляются с отчётом, хорошие доставляются. Сообщение считается отправленным только после успешной записи (с v2.1.224). Конкуренция за lock превращается в ошибку инструмента с просьбой повторить. По тому же каналу идут структурированные сообщения: shutdown, одобрение плана, запросы прав. По замерам и разбору бинарника одним пользователем (v2.1.245), in-process teammate опрашивает inbox примерно раз в 500 мс (официально не подтверждено; отчёт закрыт ботом за неактивностью 2026-10-20). Пользователи сообщают о доставке только в конце хода. Контракта для внешних процессов, которые пишут в inbox, нет.
   - Источник: [1][10][38][149][155][156][147].
3. **Сообщения агентов без полномочий пользователя.**
   - Что: правило, что текст от другого агента не заменяет согласие человека.
   - Как работает: получатель видит, что сообщение пришло от другой сессии Claude. Teammate не может одобрить запрос прав или дать согласие и не может передать отказанное действие другому teammate-у. С v2.1.166 пересланные сообщения не несут полномочий пользователя. В auto mode classifier проверяет каждое сообщение до доставки (с v2.1.222); заблокированное не приходит. С v2.1.323 split-pane teammate проверяет, что запрос от его lead. SDK предупреждает: поле `from` пишет сам отправитель, и любой процесс того же пользователя может его подделать. PID отправителя, проверенный ядром ОС (`verifiedPeerPid`), есть только у доставки через socket cross-session messaging; на Windows его нет.
   - Источник: [1][21][38][23].
4. **Ожидание сброса лимита подписки с явными пределами.**
   - Что: сессия сама ждёт сброса лимита и продолжает задачу.
   - Как работает: с v2.1.234, по умолчанию для подписки claude.ai (настройка `autoContinueAtUsageLimit`). Сессия показывает время сброса и время продолжения; Esc отменяет. После сброса Claude получает prompt продолжить; последнее сообщение пользователя повторно не отправляется. Не больше трёх продолжений. Сброса дальше 24 часов сессия сама не ждёт. После сна дольше примерно 30 минут нужен Enter. В фоновых сессиях, в `-p`, при оплате API-ключом и через облачных провайдеров ожидания нет вовсе. Под Remote Control и в сессиях teammate-ов сессия сама ожидание не запускает: человек у этого терминала запускает его через `/rate-limit-options`. Dynamic workflows ставят паузу и продолжают не больше двух раз за запуск.
   - Источник: [5][8][12][38].
5. **Retry watchdog для работы без присмотра.**
   - Что: переменная окружения, с которой сессия ждёт и повторяет, а не падает.
   - Как работает: `CLAUDE_CODE_RETRY_WATCHDOG=1` бесконечно повторяет 429 и 529 и ждёт сброса лимита плана, если ответ несёт время сброса. Потолок ожидания — `…_MAX_USAGE_LIMIT_WAIT_MS` (v2.1.301+), ранняя проверка — `…_USAGE_LIMIT_RECHECK_MS` (v2.1.305+). При 429 из-за лимита расходов — сразу ошибка. In-process teammate-ы тоже проходят эти паузы; v2.1.260 исправил потерю сообщений в их transcript во время долгих ожиданий повтора. Дойдёт ли переменная до split-pane teammate-ов — не подтверждено.
   - Источник: [9][10][38][6].
6. **Отказ вместо вопроса (`permissions.denyInsteadOfPrompting`).**
   - Что: когда ответить некому, вызов инструмента отклоняется, а не ждёт.
   - Как работает: вызов, который ждал бы ответа человека, получает отказ, и ход продолжается. Настройка покрывает teammate-ов. Появилась в v2.1.319 (2026-11-06). Ждать всё ещё может диалог доверия к папке (workspace trust) и одобрение project MCP server: на них надо ответить заранее.
   - Источник: [8][38].
7. **Общий список задач с зависимостями и захватом под file lock.**
   - Что: worker-ы сами берут следующую готовую задачу.
   - Как работает: задачи — JSON-файлы в `~/.claude/tasks/{team}/` с состояниями pending, in progress, completed и полями `blocks`, `blockedBy`, `owner`. Освободившийся teammate берёт следующую незанятую и незаблокированную задачу под file lock. Завершение разблокирует зависимые. Список переживает compaction и конец сессии (до 30 дней). `CLAUDE_CODE_TASK_LIST_ID` даёт один список нескольким сессиям. Известные изъяны: статус отстаёт; заблокированную задачу можно захватить через `TaskUpdate`; нет фильтра по роли.
   - Источник: [1][23][136][5][29][159][150].
8. **Отчёт worker-а координатору: финальный ответ и «failed».**
   - Что: worker сам сообщает координатору, что закончил или упал.
   - Как работает: с v2.1.251 idle notification несёт финальный ответ teammate-а; раньше это было пустое «доступен». С v2.1.198 teammate, чей ход кончился ошибкой API, шлёт «failed» с текстом ошибки. Сообщение будит teammate-а, который ждёт повтора запроса. Цена: lead тратит ходы на ответы на уведомления. В одном отчёте чистые подтверждения заняли 13.0% входных токенов командной части сессии, а вместе с пробуждениями lead сообщениями teammate-ов — 22.2%. Ответ lead снова будит teammate-а.
   - Источник: [1][38][125][143].
9. **Компактный список многих агентов (agent panel).**
   - Что: способ держать на виду много агентов под одной строкой ввода.
   - Как работает: idle-строки прячутся через 30 секунд; больше трёх idle — одна строка «N idle agents»; working, failed и открытый teammate видны всегда. Enter открывает transcript и прямой разговор; Escape прерывает ход; `x` останавливает. При открытом teammate-е встроенные команды идут lead; `/compact`, `/clear` и `/rewind` просят подтверждения; `/model` и `/fast` запрещены.
   - Источник: [1].
10. **Порядок выбора модели и allowlist с понижением внутри семейства.**
    - Что: предсказуемое правило, на какой модели работает каждый worker.
    - Как работает: prompt запуска → `model` в определении → `CLAUDE_CODE_SUBAGENT_MODEL` → модель lead; `…_FORCE=1` задаёт одну модель всем. Заблокированный alias семейства опускается до самой новой разрешённой версии, иначе берётся модель lead; о замене не сообщают. Hook `agent.spawn` у mod выбирает модель или отказывает в запуске — место для бюджета.
    - Источник: [1][20][22].
11. **Атрибуция работы и расходов по агентам.**
    - Что: у каждого запроса и события видно, какой агент его сделал.
    - Как работает: через LLM gateway запросы in-process teammate-ов несут заголовок `x-claude-code-agent-type: teammate`; ID teammate-а стабилен и построен по имени. Spans OpenTelemetry несут `agent_id` и `parent_agent_id`. Hooks получают `agent_id` (v2.1.290+). `$.agent.list()` у mods отдаёт статусы pending, running, waiting, idle, completed, failed и killed.
    - Источник: [25][26][2][22].
12. **Координация через базу данных и Git в больших запусках Anthropic.**
    - Что: вместо переписки — общие таблицы и merge requests.
    - Как работает: в запуске 1 000 агентов на теореме Ферма lead сам спроектировал таблицы Postgres (announce, assign, notes, subtasks, landed); работа сливалась через merge requests в Git. Управляющая программа этого запуска (harness Anthropic, не плагин worfy) 19 раз напоминала lead, сколько осталось времени. Classifier проверял каждый вызов инструмента, offline monitor просматривал действия команды. Одна общая машина упёрлась в пределы примерно на 100 агентах. В проекте компилятора C задачи захватывались lock-файлами в `current_tasks/` общего bare-репозитория, без оркестратора; когда все агенты упёрлись в одну ошибку, эталоном служил GCC.
    - Источник: [63][46].
