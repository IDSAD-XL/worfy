- **Одной фразой:** Swarm — бесплатный self-hosted runtime на Go (один бинарник `swarm`), который запускает LLM-агентов внутри машины состояний, описанной в YAML. Переходы решает детерминированный код, каждое событие пишется в журнал, а run (одно выполнение процесса) можно повторить (replay) или ответвить (fork). GUI нет. Это инфраструктура для долгих бизнес-процессов, а не инструмент для программирования [7][1][28].

## Модель работы

### Local, cloud или hybrid

- **Только self-hosted.** Swarm работает на машине или сервере пользователя. Один бинарник — это и CLI, и сервер (`swarm serve`) [7][31]. Облачного или хостингового варианта не найдено [1][2].
- **Хранилище.** По умолчанию — файл SQLite, ставить ничего не нужно [7][31]. Для production по выбору — Postgres 16 [2][31].
- **Сеть.** Сервер по умолчанию слушает только loopback `127.0.0.1:8081`. Этот один listener отдаёт health, `/v1/rpc`, `/v1/ws` и маршруты MCP [34][42]. В примере конфигурации есть ещё MCP listener на `127.0.0.1:8082` [87]. Чтобы слушать адрес не на loopback, нужен явный файл с токеном [31].
- **Изоляция агентов.** По умолчанию агенты работают в Docker-контейнерах [7].
  - Backend `claude_cli` требует Docker-образ с Claude CLI внутри. Его собирают командой `swarm workspace build --backend claude_cli` [48][61].
  - Backend «host» включается явно и только для локальной разработки. Проект сам называет его доверенным и небезопасным. Claude CLI прямо на хосте не поддерживается [7].
- **Масштаб — одна установка.**
  - Документация пишет, что распределённое выполнение и изоляция нескольких клиентов (multi-tenant) пока вне рамок [45].
  - Swarm не раскладывает flow instances (запущенные экземпляры процессов) по разным машинам [35].
  - Второй `serve` на том же хранилище не становится репликой и не перехватывает работу. Он ждёт блокировку хранилища (standby) [59][9].
- **Webhooks при разработке** [7]:
  - `swarm serve --dev --expose` открывает временный публичный URL через cloudflared quick tunnel. Только для разработки;
  - `--public-webhook-base-url` использует уже имеющийся свой HTTPS-адрес. Публичный listener открывает только `/webhooks/*`;
  - `--dev` при каждом старте заменяет локальное временное хранилище.
- **Конфигурация.** Текущий код читает один файл: `.swarm/swarm.yaml` или файл из `--config` / `SWARM_CONFIG`. Файлы `.env` и глобальный конфиг пользователя он не читает [7]. Документация всё ещё описывает четыре файла, которые сливаются по слоям. Здесь документация отстаёт от кода [34].
- **Секреты.** Команды `swarm secrets set|list|check|rm`. Файл лежит в системной папке конфигурации, по умолчанию `os.UserConfigDir()/swarm/credentials.json` [7][61]. OAuth-подключения к внешним сервисам: `swarm connections connect|callback|status|disconnect` [61][50].

### Агенты и модели

- **Backends** — способы вызвать модель [7][34][66]:
  - `anthropic` — по умолчанию, нужен `ANTHROPIC_API_KEY`;
  - `claude_cli` — Claude Code в headless-режиме, нужен `CLAUDE_CODE_OAUTH_TOKEN` (вход по подписке Claude, а не по API-ключу);
  - `openai_compatible` — ключ и base URL;
  - `openai_responses` — `OPENAI_API_KEY`;
  - mock на Python, без ключей.
- **Модели** задаются псевдонимами `cheap`, `regular` и `frontier`. Для каждого backend псевдоним сопоставлен конкретной модели в `llm.models` [35][59].
- **Codex не поддерживается** [86][59]:
  - в `Dockerfile.workspace` есть аргумент `INSTALL_CODEX_CLI`, но `swarm workspace build` жёстко ставит его в false;
  - backend для Codex нет. OpenAI доступен только через HTTP-адаптеры Responses и Chat Completions [86][7].
- **Версия Claude Code** в образе закреплена — 2.1.87, автообновление выключено [86].
- **Другие провайдеры.** DeepSeek в CHANGELOG упомянут только как источник вспомогательных проверок (advisory evidence) [9]. OpenRouter, Ollama, Bedrock, Azure, Vertex и vLLM отнесены к будущей работе [59].

### Один пользователь или команда

- Одна установка обслуживает одного клиента. Идентификатора организации, клиента или workspace в API нет [57].
- Один bearer token даёт все права. Scopes объявлены, но не проверяются [57].
- Учётных записей, ролей и SSO не найдено.
- Люди участвуют как допущенные операторы (admitted operator principals). Они принимают решения в mailbox — очереди задач для человека. Личность оператора подтверждается через Telegram или WhatsApp [60][61].
- «Role-based routing authority» в README — это права ролей агентов, а не людей [7].
- Маркетинг расходится с документацией. Главная страница обещает изоляцию клиентов (tenant isolation) и тысячи одновременных команд агентов [1]. Документация говорит про одну установку и отсутствие multi-tenancy [45][57].

### Платформы

- Бинарники релизов есть для Linux amd64 (только glibc, без musl и Alpine) и macOS arm64 (smoke test на macOS 15) [12][7].
- Windows, подпись и нотаризация, Homebrew — вне процесса выпуска [9]. Поддержка Windows не подтверждена.

## Функции

Ниже — всё найденное. Термины продукта объяснены при первом упоминании. Сводный словарь — в разделе «Принципы и подходы».

### Описание процессов: flows и контракты

- **Flow package.** Flow — пакет контрактов, единица сборки системы [29][7]. На диске это папка с YAML-файлами: manifest, schema (stages и pins), events, nodes (handlers), agents, tools, policy, state и types, плюс `prompts/*.md` [7][26].
  - Flow instance — один запущенный экземпляр flow. У static flow экземпляр один, у template flow — по одному на каждый ключ [30].
  - Entity — типизированный изменяемый документ, который проходит через flow instance. С июня 2026 у экземпляра одна главная (primary) entity [30][134].
  - В v0.7 файл `entities.yaml` заменён плоским `state.yaml`. Документация всё ещё описывает `entities.yaml` [9].
- **Handler pipeline.** Handler — детерминированный код, который обрабатывает одно событие [29]. По README шаги такие: guard (условие) → accumulate → compute → смена stage, установка gates, запись данных → emit (выпуск новых событий). Всё фиксируется одной транзакцией [7].
  - Условия пишутся на CEL (Common Expression Language). Это строго типизированный язык выражений без полноты по Тьюрингу: бесконечный цикл на нём не написать [7][27].
  - Gate — именованный флаг (boolean) на entity [30].
- **Жизненный цикл (lifecycle)** [47]:
  - stages — именованные шаги; нужен хотя бы один конечный (terminal) stage;
  - decision gates — stage ждёт решения человека;
  - joins — stage ждёт набора результатов;
  - timers на stage (например `after: 48h`) и повторяющиеся timers на node;
  - конечный stage нельзя открыть снова.
- **Сборка из частей (composition).** У flow есть входы и выходы — pins. Родительский flow импортирует дочерние [7]. README и документация называют pins типизированными [7][55]. По спецификации pins теперь — только имена событий, а типы задают схемы событий [59].
- **Параллельная работа** [55]:
  - `fan_out` разбивает список на элементы; верхняя граница — `max_items`;
  - каждый элемент получает свой flow instance со своим агентом, session (одним разговором с моделью) и workspace;
  - join в режиме `barrier` или `stream` собирает результаты, отбрасывает дубликаты и требует timeout;
  - singleton flow (flow в одном экземпляре) владеет общим состоянием и координирует остальных;
  - циклы доработки объявляются через `loops:` с `max_attempts` и обязательным выходом `escape`. Вложенные и неограниченные циклы отклоняются.
  - Документация описывает лимиты sharding: 8 частей на задачу, 12 одновременно, 30 минут на часть [34]. Текущий код отвергает ключ `sharding`: его не использует ни один путь выполнения [94].
- **Compute modules** — детерминированный код для алгоритмической работы, на Python (встроенный интерпретатор CPython-WASI на Wasmtime) или на WASM [52]:
  - модуль закреплён по digest (хешу содержимого);
  - ограничен по gas (счётчику шагов вычисления), памяти и размеру вывода;
  - ввода-вывода нет.
- **Статический анализатор:**
  - `swarm verify` проверяет пакет до запуска [61][53];
  - `--portable` проверяет только структуру [61];
  - `--run <id>` сверяет состояние entities в run с историей их изменений [61];
  - каждая находка называет id проверки и точный путь к полю, чтобы LLM могла исправить её сама [54];
  - документация перечисляет 49 именованных проверок (50 записей: `entity_reader_coverage` указан дважды), ни одну нельзя отключить [56];
  - ошибка уровня error останавливает загрузку сервера. Частичного старта нет [42].
- **Стартовые шаблоны `swarm new <archetype>`.** Здесь исследования расходятся. Одно насчитало три шаблона [65][61], другое — два, по папке `archetypes/` [61]. При написании досье проверен код: в реестре `new_archetype.go` три имени, а `webhook-responder` собирается из встроенного примера Telegram-агента, поэтому своей папки у него нет [62]. Шаблоны [65][61]:
  - `zero-agent-automation` — отправляет сообщение в Telegram, агентов нет;
  - `webhook-responder` — чат-агент в Telegram;
  - `whatsapp-receptionist` — эхо-бот в WhatsApp.
- **Команды осмотра** [61]:
  - `swarm describe` показывает развёрнутый вид контрактов. `--graph` печатает граф жизненного цикла текстом. Подкоманды — `describe routes` и `describe pack`;
  - `swarm packs list|show|import` и `swarm import <provider>` копируют встроенные packs провайдеров в flow;
  - `swarm data import|show|prune` управляет неизменяемыми справочными данными в JSONL с версиями.
- **Bundle CLI.** Bundle — набор файлов контрактов, его id — хеш содержимого [30]. Команды для bundles появились в релизе 1.6.0 [9].
- **Страница для AI-ассистентов.** Отдельная страница документации обращается к LLM-агентам [54]:
  - сначала прочитать `platform-spec.yaml`, затем `openrpc.json`, указатель полей и тесты в `tests/`;
  - добиться, чтобы минимальный flow прошёл `verify`, потом добавлять по одной вещи;
  - исправлять по id проверки и искать образцы grep-ом среди 200+ проверенных conformance bundles — наборов контрактов, по которым проверяют сам runtime;
  - никогда не выдумывать поля и не отдавать flow, который не проходит проверку.
- **Визуального редактора нет:**
  - «Builder · visual canvas» помечен «soon» [1];
  - внутренние Builder и dashboard убраны: issue #2378 удалил JSON-RPC транспорт Builder (закрыт 2026-08-30), issue #2390 — REST-транспорт dashboard (закрыт 2026-10-02) [116];
  - guided composer (сборка flows без ручного YAML) и assembly agent (агент, который превращает просьбу на обычном языке в проверенные правки) есть только в roadmap [13][134][135][136];
  - команды `swarm compose|route|bind|diagnose` описаны как целевой UX, а не текущий CLI [134][135][136].

### Агенты

- **Описание агента в `agents.yaml`** [36][35][59]:
  - `intent` — prompt из Markdown-файла или текстом;
  - `model` — псевдоним `cheap`, `regular` или `frontier`;
  - `subscriptions` — события, которые агент получает;
  - `emit_events` — каждое становится автоматически созданным инструментом `emit_*`;
  - `memory`: `false` — новый разговор на каждую задачу; `true` — один долгоживущий разговор на flow instance;
  - `permissions_bundle` и `manager_fallback` [36]. В спецификации поле называется `permission_bundles` [59];
  - `entity_writes` — узкий, явно выданный список полей entity, которые агент может менять;
  - `max_turns_per_task` — лимит turns (ходов разговора: запрос к модели и её ответ) на задачу;
  - `tools`, `native_tools` и необязательный `mock` [35][59].
- `memory: true` разрешён только в template flows. Иначе загрузка падает с ошибкой, которая объясняет причину [35].
- **Prompts** — файлы `prompts/<role>.md` с подстановками `{{var}}` [36].
- **Инструменты закрыты по умолчанию (default-deny).** Агент может вызвать только [37]:
  - объявленные инструменты типов `platform_builtin`, `mcp` или `http`;
  - свои `emit_*` и созданные для entity инструменты;
  - `read_flow_data`, если он объявил данные flow;
  - встроенные `bash`, `web_search` и `file_io` — все выключены по умолчанию.
  - Здесь источники расходятся. Документация инструментов и страница концепций называют общими для всех агентов `agent_message` и `mailbox_send` [37][35]. По спецификации и коду эти два инструмента убраны, а общим остался `notify_human` [59][90].
- **Глаголы прав** (permission verbs): `configure_routing`, `message_flow`, `human_task_request|decide`, `schedule`, `approve_spend` [37]. В спецификации есть ещё `ask_human` [59].
- **Адресация и изоляция:**
  - агенты обращаются друг к другу по цепочке coordinator → manager → worker [35]. Общего контекстного окна у них нет [7];
  - `/workspace` — личная папка агента или общая для flow instance [35][48];
  - `/data` и `/opt/swarm/contracts` всем доступны только на чтение [48].
- **Действия оператора с работающим агентом** [33][60][61]:
  - `swarm agent list|view|frame|deliveries|diagnose|restart|replay|replay-backlog`;
  - `swarm agent directive <id> "<msg>"` отправляет агенту произвольное указание. Directive направляет агента, но не меняет состояние [30].
- **Разговоры:** `swarm conversation list|view|turn` [61].
- **forkchat.** Копирует один разговор агента в sandbox, и с копией можно переписываться. Такие сессии живут ровно 24 часа [33][60]. Функция появилась в релизе 1.6.0 [9].
- **Контекст** [59][9]:
  - сжатие контекста (compaction) своё у каждого backend. У `claude_cli` сжатием занимается сам Claude Code;
  - память агента переживает обновление контрактов на месте. Следующий turn уже идёт с новым prompt или новой моделью.
- **`ask_human`** — инструмент агента. Он создаёт карточку для человека с тезисами для разговора, сроком и учётом недельного бюджета задач для человека [90][59].

### Запуск и наблюдение

- **Два режима** [42]:
  - `swarm serve` — долгоживущий сервер;
  - `swarm run start` публикует одно событие. В v0.7.1 он только публикует в уже запущенный `serve` и больше не поднимает разовый runtime [7]. Quickstart в документации описывает старое поведение [32].
- **Story feed.** `serve --dev` пишет по одной строке на каждый значимый шаг [43]:
  - что попадает в ленту: опубликовано событие, сделана доставка, агент закончил turn, stage сменился, ждёт решение человека;
  - в терминале — цветные строки (красный только для настоящих сбоев) и живая строка статуса внизу;
  - при выводе в pipe — NDJSON;
  - `--no-feed` выключает ленту.
- **Диагностика:**
  - `swarm run trace <id> -f` следит за run, с фильтрами [43];
  - `swarm run status` объясняет, почему run застрял: называет слой, который блокирует, и причину [43];
  - `swarm run fan-out list` показывает ход fan-out [61];
  - `swarm agent diagnose` — диагностика агента, появилась в 1.6.0 [9].
- **Чтение данных:** `swarm event list|follow|view|publish|replay`, `swarm entity list|view|aggregate`, `swarm logs --follow`, `swarm incidents` [33][43].
- **Сырые ответы CLI** пишутся по агентам в `.swarm/monitor` [87].
- **Health** [42][61]:
  - `/healthz` и `/readyz` работают без токена;
  - `swarm health` — сводка с авторизацией;
  - `swarm doctor` проверяет, всё ли установлено. `--gateway-probe` бесплатно проверяет вход, без вызова модели.
- **Управление** [33][9][42]:
  - `swarm control pause|continue|stop <run>|--all`;
  - `swarm control nuke` — разрушительный сброс, с предпросмотром `--dry-run`;
  - при штатной остановке сервер доделывает уже принятую работу в пределах grace period (по умолчанию 30 с).
- **Состояния run:** running, completed, failed, paused, stalled. Все события одного run связаны общим `run_id`. Сбой handler или агента не роняет run: событие уходит в dead letters [42]. Dead letter — событие, которое после всех повторов отложено в отдельную очередь для разбора [30].
- **Локальный контекст CLI:** `swarm context current|list|prune` и `swarm store status` [61].

### Надёжность, replay, fork и аудит

- **Повторы:**
  - handler — 3 повтора с паузами 1, 2 и 4 с. Перед каждым повтором записи откатываются. Ошибки guard и бизнес-логики не повторяются [41];
  - session агента повторяется один раз, потом уходит в dead letters [41]. В коде то же: `AgentMaxRetries = 1`, `NodeMaxRetries = 3` [78];
  - dead letters проиндексированы, их можно повторить [41].
  - Здесь источники расходятся. По документации конфигурации и workspaces у `claude_cli` по умолчанию timeout 30 минут и 2 повтора [34][48]. По коду timeout по умолчанию — 120 с, а повтор агента — один [69][78].
- **Лимит глубины цепочки.** Событие глубже 50-го звена цепочки уходит в dead letters (`chain_depth_exceeded`). Handler, который его выпустил, всё равно фиксируется [41].
- **Сигнал о зависании.** `platform.run_stalled` срабатывает один раз на каждое зависание, по умолчанию через 300 с [41].
- **Восстановление после падения.** События, которые сохранены, но не доставлены, доставляются снова. Ключи идемпотентности (по ним повторный вызов не выполняется второй раз) не дают выполнить работу дважды [44]. Timers, срок которых наступил во время простоя, срабатывают при восстановлении [47].
- **Replay и fork:**
  - replay событий, replay агента и replay его очереди (backlog) [44][33]. Replay — повторная доставка сохранённого события [30];
  - fork восстанавливает состояние на выбранный момент и продолжает оттуда под новым `run_id` [30][63];
  - по документации `swarm run fork <run> --at-event <id>` работает только на том же bundle контрактов, а fork на новые контракты запланирован, но не включён [44]. Здесь источники расходятся: текущий код принимает `--source <dir>`, а также `--at-start`, `--publication` и `--pin name@vN` [63];
  - главная страница обещает больше: поменять модель, prompt или policy и пересчитать альтернативный ход событий, как `git bisect` для runs агентов [1]. По документации это пока недоступно [44].
- **«Flight recorder» в Swarm** — не отдельная система, а запрос. Это четыре таблицы, соединённые по `run_id` [46][59]:
  - `events`;
  - `entity_mutations` — значения до и после;
  - `agent_turns`;
  - `event_deliveries`.
  - UI для него нет. Отдельный продукт «Flight Recorder» помечен «soon» [1].
- **Mutation log** хранит значения до и после для каждого изменения поля entity [30].

### Человек в контуре (human in the loop)

- **Decision gates** [38][30]:
  - stage ждёт типизированного решения человека;
  - каждый исход объявлен заранее, например «одобрить» или «отклонить с обязательной причиной»;
  - платформа создаёт decision card — карточку решения;
  - по хешу содержимого карточка, показанная на устаревших фактах, становится недействительной;
  - истёкший срок никогда не одобряет автоматически. Карточка уходит на эскалацию или откладывается.
- **Mailbox items** — задачи для человека, которые не блокируют процесс [38]:
  - важность: normal, urgent или critical;
  - к каждой сервер собирает decision sheet — контекст и что произойдёт после решения;
  - решение принимается один раз, повтор того же решения ничего не меняет [39][38].
- **Команды:**
  - документация показывает `swarm mailbox approve|reject|defer` [39];
  - текущий код использует `mailbox list|view|decide <card-id> <option>|defer` [61];
  - API добавляет `acknowledge`, черновики ввода (`begin_input` / `cancel_input`) и `mailbox.subscribe` — поток изменений карточек [60].
- **Напоминания** настраиваются. По умолчанию первое — через 4 часа, затем каждые 24 часа. Через 24 часа карточка становится срочной. Черновик ввода живёт 15 минут [87].
- **Бюджет задач для человека:** недельный лимит (`budget.human_tasks.max_tasks_per_week`), категории задач, автоматическое истечение через 168 часов, настраиваемый день сброса [87][90].
- **Каналы на телефоне:**
  - документация обещает показ карточек в мессенджерах, первым — в Telegram [27][38];
  - pack канала Telegram умеет показывать карточки и кнопки, править сообщения, подтверждать получение и выводить список входящих, на английском и французском [92];
  - WhatsApp подключается сканированием QR-кода на экране «Связанные устройства» (Linked Devices) в WhatsApp. Работает на fork неофициальной клиентской библиотеки [5][92][65];
  - `swarm channel connect|reconnect|rebind|resume|list|status|logout|unbind|revoke-proof` управляет этими аккаунтами [61].
- **Ограничения v0.7:**
  - decision cards через зарегистрированного бота пока работают только из CLI [129];
  - общий inbox решений на уровне установки отложен до v0.8. Это issue #2836 — задача v0.8 про карточки и inbox через зарегистрированных ботов Telegram и WhatsApp [9][129];
  - WhatsApp ещё не прошёл приёмку на физических устройствах [9];
  - живая проверка Telegram с настоящим токеном, по README, не проводилась [7].
- **`notify_human`** — общий для всех агентов инструмент уведомления человека [59][90].

### Бюджет, стоимость и лимиты

- **Журнал расходов (spend ledger).** Одна строка на каждый вызов агента: токены, стоимость, модель. Расходы раскладываются по entity и по actor (исполнителю) [40].
- **Лимиты в долларах.** Месячные лимиты в USD (общий, на entity, системный) задаются в `swarm.yaml`. По умолчанию все три равны 0, то есть выключены [87][73]. Пороги в процентах (например 60 / 80 / 95) — в `policy.yaml` [40]. Месяц — календарный, по UTC [40][73].
- **Уровень throttle:**
  - по документации: одновременно работает меньше агентов, некритичная работа ждёт. На OpenAI-совместимом backend исполнитель может перейти на дешёвую модель [40][34];
  - здесь источники расходятся: по коду throttle только подавляет события, тип которых совпадает с `throttle_suppress_prefixes`. Перехода на дешёвую модель в коде нет [75][34].
- **Уровень emergency.** По документации все sessions агентов встают на паузу и создаётся задача в mailbox [40]. По коду для этой области подавляются доставки агентам, а при emergency на системном уровне — все доставки агентам. Создаётся critical-задача «alert» [75][73].
- **API `agent.usage`** [60]:
  - токены и оценка стоимости по агенту;
  - расход `claude_cli` помечен как оценка;
  - стоимость — защитная оценка, а не данные биллинга провайдера.
- **Ограничение частоты на стороне клиента:**
  - `llm.provider_limits.<backend>` задаёт `rate_limit` (например `30/m`), `max_concurrency` и максимальное ожидание [59][87]. Можно переопределить по модели [72][87];
  - действует и на запуск процессов `claude_cli` [59];
  - если ждать дольше предела, вызов падает с повторяемой ошибкой. В спецификации её код — `rate_limited`, в коде — `llm_provider_rate_limited` класса `platform.connector_failure` [59][71][84];
  - встроенных значений по умолчанию нет [87]. В примере конфигурации: 30 запросов в минуту, ожидание до 30 с, одновременно 2 [64].
- **Устаревший ключ.** Документация показывает `runtime.max_concurrent_agents: 16`. Текущий код этот ключ отвергает: его не исполняет ни один путь [87][94].
- **Лимиты подписки Claude (5-часовое окно).** Кода, который распознаёт лимит подписки или ждёт его сброса, нет. Подробно — в разделе «Как это устроено внутри», подраздел «Лимиты и стоимость» [66][59].

- **Чего нет:**
  - ничего для pull requests, CI, Linear, Jira и GitLab [92];
  - локальных git-коммитов нет [7]. Документация всё ещё описывает действие `artifact_repo_commit`, но в спецификации его уже нет [45][59]. Убрано 2026-09-21 [111].
- **Оговорки WhatsApp (beta)** [65]:
  - сообщения, пропущенные офлайн, повторно не доставляются;
  - скорость отправки не ограничена, а это грозит блокировкой аккаунта WhatsApp.
- **Общие подключения:**
  - HTTP-инструменты [37];
  - внешние MCP servers по HTTP или stdio. Имена их инструментов получают префикс. Недоступный server пропускается при загрузке [49];
  - connector packs можно сгенерировать из OpenAPI-описания [50].
- **MCP наружу.** Документация пишет, что внешние инструменты могут управлять runtime через маршруты `/mcp` и `/tools/` [49]. В коде этот gateway отдаёт набор инструментов каждого агента. Claude CLI подключается к нему через `--mcp-config` [66][85]. Может ли внешний MCP client провести через него целый процесс — не подтверждено.
- **Webhooks из интернета** — через `serve --expose` (cloudflared quick tunnel) или свой HTTPS-адрес (описано в «Модели работы») [7].

### API

- **Транспорт:** JSON-RPC 2.0 на `POST /v1/rpc`, подписки по WebSocket на `/v1/ws` [57].
- **Объём:** 70 методов в пространствах run, event, entity, agent, conversation, mailbox, channel, data, runtime, health и test [60]. Среди них `run.trace`, `run.subscribe_trace`, `run.diagnose`, `agent.diagnose`, `agent.send_directive`, `agent.usage`, `conversation.get_turn`, `runtime.logs` и метод для incidents [60].
- **Авторизация:** bearer token. Любой действующий токен даёт все права, scopes объявлены, но не проверяются. Токен WebSocket проверяется один раз, при подключении [57]. На loopback работает встроенный dev token [42][34].
- **Соглашения:** постраничная выдача по курсору (по умолчанию 50, максимум 500). Ключи идемпотентности хранятся 24 часа для тройки (метод, токен, ключ) [57].
- **Чего нет в v1:** multi-tenancy, ограничения частоты запросов, SLA и массовых методов [57].
- **Подписки могут терять сообщения.** При перегрузке они отбрасывают сообщения и не переживают обрыв соединения [57].
- **Exit codes CLI:** 0, 2–7 и 130 [33].

## Принципы и подходы

### Главное правило

- Слоган главной страницы: «The LLM never runs the system. Agents reason. Code decides. State survives.» [1] По-русски: LLM не управляет системой; агенты рассуждают, код решает, состояние сохраняется.
- **Разделение ролей** [27][28][29]:
  - LLM-агенты рассуждают в маленьких ограниченных sessions и только выпускают события;
  - детерминированные system nodes (узлы с обычным кодом) владеют состоянием, маршрутизацией и правилами;
  - агент предлагает исход, а node решает, что на самом деле меняется. Поэтому агент не может оставить систему в состоянии, о котором он только заявил.
- **Маршрутизация** задаётся объявленными подписками, а не моделью. Условия пишутся на CEL [7][27].
- **Одна транзакция на переход.** Guard, accumulate, compute, запись состояния, gates и данных, emit и необязательное действие фиксируются вместе или не фиксируются вовсе [7][29].
- **Происхождение идей — блокчейн-протоколы.** По Show HN: всё асинхронно, построено на событиях, состояние меняется только через зафиксированные упорядоченные переходы [143]. В обсуждении дизайна есть сравнение с Solidity: определение flow — тип контракта, flow instance — развёрнутый контракт, его главная entity — хранилище контракта [134].
- **Три оговорки к обещанию «LLM не пишет состояние»:**
  - агенты могут писать объявленные поля своей entity через созданные инструменты `save_<entity>_<field>`, в пределах `entity_writes` [35][59];
  - событие, которое выпустил агент, публикуется отдельно, вне атомарной границы handler [59];
  - README разрешает агентам владеть переходами, где нужно суждение [7].

### Swarm как «операционная система»

- Сравнение вендора: ОС не делает программы правильными, она делает их запускаемыми. Она планирует их, изолирует, считает ресурсы, хранит состояние и перезапускает после падения. Swarm заявляет себя таким слоем для агентов [27].
- Вендор признаёт, что детерминированная маршрутизация на YAML становится обычной базой. Своим вкладом он называет всё вокруг маршрутизации [28]:
  - долгоживущую машину состояний на каждую единицу работы;
  - изоляцию вплоть до отдельного workspace у каждого агента;
  - учёт токенов по entity и по исполнителю;
  - людей, которые действуют через ту же цепочку событий, что и всё остальное.
- **Позиционирование.** Для ограниченных задач — обычный workflow runner. Swarm — для систем, которые работают постоянно, переживают падения, координируют агентов днями и должны проходить аудит [1][2][28]. Pipeline для code review сайт приводит как пример задачи для обычных runners [1].

### Шесть заявленных свойств с главной страницы [1]

| Свойство | Обещание |
|---|---|
| Control | Строгие gates проверяют каждый переход |
| Safety | Лимиты стоимости на entity, события с проверкой схемы, изоляция клиентов, статические проверки до deploy |
| Scale | Тысячи одновременных команд агентов |
| Composability | Flows вкладываются друг в друга на любую глубину |
| Observability | Трассируется каждое событие, решение и доллар |
| Determinism | Любой прошлый ход событий воспроизводится точно; изменения контрактов можно проверить на данных production |

### Девять позиций из README [7]

1. Работа — долгоживущая машина состояний.
2. Цикл управления детерминирован.
3. Каждый переход — одна транзакция.
4. Flows — пакеты, которые собираются через входы и выходы (pins).
5. Агенты изолированы: ограниченные sessions; иерархическая адресация (coordinator говорит с managers, managers — с workers, общего контекстного окна нет); отдельный Docker workspace на entity.
6. Выполнение можно воспроизвести (replay).
7. Runs можно ответвить (fork).
8. Люди действуют через долговременный mailbox. Степень автономности настраивается по шагам, а не включается целиком.
9. Система построена от спецификации и рассчитана на то, что её контракты пишут AI-агенты.

Заявленный компромисс: LLM не может перестроить flow во время работы, и эта жёсткость задумана [7][27].

### Честно названные пределы

- **Детерминизм заканчивается на агентах.** Повторно запущенный агент может прийти к другому ответу. Swarm делает детерминированным всё вокруг модели. В тестах mock backend проигрывает заранее заданные turns, поэтому сценарий детерминирован целиком [28].
- **Плохо подходит для** [28]:
  - разовых вызовов LLM;
  - чат-ботов, чья ценность заканчивается ответом;
  - прототипов, которые меняются каждый час;
  - систем, где маршрут должна выбирать модель.
- **Неудобство при исследовании.** Анализатор не даёт загрузить недописанный контракт. Вендор называет это плюсом в production и помехой при исследовании. Совет — сначала набросать вчерне, потом переносить [28].
- **Порядок авторитета.** FAQ обещает отвечать без маркетинга: документация обязательна, спецификация платформы стоит выше документации [2]. Если страница документации расходится со спецификацией, права спецификация [54].

### Почему YAML, а не DSL на Python [2]

- DSL на Python спрятал бы контракты от статического анализатора до запуска. Это ломает подход fail-closed — отказывать, если что-то не проверено.
- YAML — самый маленький формат, который можно проверить без запуска, отрисовать, сгенерировать и написать силами LLM по одной машиночитаемой спецификации.
- Признанная цена — многословность.

### Человек в контуре

- **Решение человека — типизированный объект.** Оно хранится долговременно. Автор flow сам выбирает, на каких переходах нужен человек. Остальное работает автономно [38].
- **Платформа никогда не решает за человека.** Истёкший срок не одобряет: карточка уходит на эскалацию или откладывается, и это видно [38].
- **Issue #1868 — дизайн HITL (human in the loop), 2026-07-08** [106]:
  - цель приёмки: оператор принимает осознанное, типизированное и записанное в аудит решение с телефона меньше чем за 30 секунд, и со временем система спрашивает реже;
  - главная названная проблема — усталость от одобрений (approval fatigue);
  - первое средство — группировать решения по классу;
  - второе средство — graduation: после N одинаковых одобрений одного класса предложить автоматически одобрять этот класс. Предложение оформляется как правка контракта (diff), которую человек проверяет. Правка пишется в журнал, её можно отозвать, её проверяют выборочным аудитом;
  - graduation отложено на вторую фазу.
- **Строгость подтверждения зависит от класса действия** (дизайн authoring в Colony) [141]:
  - действия только на чтение одобряются автоматически, с уведомлением;
  - идемпотентная запись — обычный запрос;
  - неидемпотентная запись (отправка, списание денег) — полная процедура: показать, что pack может делать, и ввести имя flow, чтобы выдать права.

### Расчёт на coding-агентов как авторов контрактов

- Одна машиночитаемая спецификация. Ошибки анализатора называют id проверки и путь к полю. Больше 200 проверенных conformance bundles можно искать grep-ом [7][54].
- Страница документации для LLM-агентов описана в разделе «Функции» [54].
- **Issue #2669 — skill-помощник для Claude Code (2026-10-14, milestone v0.9).** Автор просит однострочного помощника: skill для агента, сначала для Claude Code, который ставит Swarm, пишет flows, запускает их и диагностирует [127]:
  - источник истины — CLI, в самом skill минимум логики;
  - помощник никогда не угадывает написание;
  - работа ждёт заморозки грамматики 2026-12-07.

### Правила UX

- **Issue #1972 — планка UX (2026-07-11).** Работает — ещё не значит готово. Готово — когда посторонний человек справился без помощи [108]. Условия U1–U11 [108]:
  - U1: каждая ошибка, после которой нельзя продолжить, называет исправление как команду, которую можно сразу выполнить;
  - U2: ни один факт не требует чтения исходного кода;
  - U3: статус сообщает наблюдаемое состояние; false-green (сообщение об успехе без успеха) — худшая ошибка;
  - U4: каждый успех печатает следующий шаг;
  - U5: строгость подтверждения зависит от класса действия;
  - U6: термины платформы объясняются там, где появляются впервые;
  - U7: каждый многошаговый процесс можно прервать и продолжить;
  - U8: у каждого интерактивного вопроса есть флаг для неинтерактивного режима;
  - U9: долгие операции показывают прогресс;
  - U10: бюджет времени — часть корректности: от намерения до работающего mock за 60 секунд или меньше;
  - U11: текст для пользователя говорит его словами; внутренний словарь запрещён.
- Дизайн authoring добавляет два правила. На платформе, которая отказывает при сомнении, сообщение об ошибке и есть продукт. Инструмент должен генерировать контракт, а не прятать его [141].

### Правила разработки

- **Никакой совместимости до 1.0.** Принимается только текущий словарь. Нет stubs для удалённых полей, нет codemods и читателей старых форматов [59]. Несовместимое хранилище не загружается, миграций нет [9]. Миграции начнутся с 1.0 [13].
- **Программа восстановления кода (сентябрь 2026)** [119][120]:
  - каждый PR удаляет больше строк production-кода, чем добавляет, или называет инвариант, ради которого строки добавлены;
  - PR ограничен 3000 строк production-кода, кроме PR с меткой `deletion`;
  - выведенный из работы интерпретатор удаляется в том же PR, который его заменяет;
  - исправление называет два расходящихся представления данных и сводит их в одно, а не добавляет проверку их согласованности.
- **Правила для участников.** Работа с высоким риском требует одобренного pre-audit (проверки плана до кода) и proof audit (проверки доказательств до review). Эвристические прослойки совместимости запрещены [10].

### Словарь продукта

- **Flow** — пакет контрактов, единица сборки. README называет его и единицей будущего marketplace [29][7].
- **Flow instance** — один запущенный экземпляр flow. У static flow экземпляр один, у template flow — по одному на ключ [30].
- **Entity** — типизированный изменяемый документ внутри flow instance. По решению июня 2026 у экземпляра одна главная (primary) entity [30][134].
- **Stage** — именованный шаг жизненного цикла. **Gate** — именованный флаг на entity. **Decision gate** — stage, который ждёт решения человека. **Decision card** — типизированная форма, на которой это решение принимают [30].
- **System node и handler** — детерминированный код. Handler — единица выполнения для одного события [29].
- **Agent и session.** `memory: false` даёт session на задачу, `memory: true` — один долгий разговор на тройку (run, агент, flow instance) [30][35].
- **Directive** — сообщение оператора, которое направляет агента и не меняет состояние [30].
- **Model alias** — `cheap`, `regular` или `frontier`, сопоставленный модели конкретного backend [30].
- **Fan-out и join.** Fan-out выпускает по событию на каждый элемент списка. Join ждёт объявленный набор веток, отбрасывает дубликаты и соблюдает срок [30].
- **Timer** — долговременный триггер по времени [30].
- **Pin** — вход или выход flow. Сейчас это только имена событий [30][59].
- **Pack** — пакет интеграции: trigger, connector или channel [30].
- **Bundle** — набор файлов контрактов, его id — хеш содержимого [30].
- **Mailbox** — долговременная очередь задач для человека [30].
- **Mutation log** — значения до и после для каждого изменения поля [30].
- **Flight recorder** — события, изменения, turns агентов и доставки, соединённые по `run_id`. Это шаблон запроса, а не отдельная система [46][59].
- **Replay и fork.** Replay повторно доставляет сохранённое событие. Fork восстанавливает состояние на выбранный момент и продолжает оттуда [30].
- **Dead letter** — куда попадает событие после исчерпания повторов [30].
- **Standing flow** — долгоживущий flow, который отвечает на входящие сообщения [28].
- **Compute module** — sandbox на Python или WASM для алгоритмической работы [52].
- **Durable activity и effect class.** В июльском vision activity — единственный путь к внешнему вводу-выводу, а каждое внешнее действие отнесено к классу риска [138]. Позже встроенные действия платформы лишились замены через activity [59].
- **Capability surface** — что pack может и чего не может. Это показывают человеку, который импортирует pack [138].
- **Archetype** — стартовый шаблон для `swarm new` [61].
- **Hive** — планируемый источник packs. Раньше эту роль должен был играть Colony [126].

### Заявленные отличия и что из них есть на деле

- **Место на рынке.** Swarm ставит себя ближе к системам durable execution (Temporal, Restate, Inngest), чем к библиотекам агентов [28].
- **Таблица сравнения вендора.** Против CrewAI/AutoGen, обычных workflow runners и LangGraph только у Swarm отмечены [28]:
  - бюджеты по entity и по исполнителю с уровнями throttle и emergency;
  - типизированные decision gates;
  - журнал изменений по полям;
  - детерминированные сценарии тестов с заранее заданными turns агентов.
- **Fork для поиска причины.** Главная страница продаёт fork как `git bisect` для runs агентов: поменять одну переменную в точке fork и пересчитать всё, что идёт после. Аудиторам показывают сам run, а не logs [1].
- **Правило расширяемости** (vision, июль 2026) [138]:
  - сторонние расширения не должны ослаблять гарантии runtime;
  - всё, на чём держатся гарантии, остаётся в ядре runtime; всё, что только сочетает готовые примитивы, может быть pack;
  - тест допуска из четырёх проверок: расширение сочетает примитивы, а не даёт новые гарантии; проверяется без запуска; изменение возможностей помещается на один экран; replay либо воспроизводит, либо блокирует каждое внешнее действие.
- **Целевая демонстрация «counterfactual quarter»** (discussion #1709, июль 2026) [135]:
  - fork 90 дней записанных runs на изменённой policy;
  - каждое внешнее действие блокируется, а turns агентов берутся из журнала там, где входы не изменились;
  - результат — отчёт о расхождениях;
  - заявленная уникальная комбинация: детерминированный replay, блокировка внешних действий, журнал turns агентов, контракт как diff, типизированные исходы;
  - в долгой перспективе assembly agent предлагает изменения policy и открывает PR с доказательством.
- **Разрывы между обещаниями и документацией:**
  - fork на новые контракты обещан на главной и в README [1][7]. По документации такой fork пока отклоняется [44]. Fork целого окна runs назван единственным новым примитивом, которого не хватает для демонстрации [135]. Текущий код уже принимает `--source <dir>` [63];
  - главная обещает изоляцию клиентов и тысячи команд агентов [1]. Документация описывает одну установку без распределения и multi-tenancy [45], README в июне говорил то же [8]. Открыт P1 issue #2394 — про сбои по времени в fan-out [117]. Обещание про тысячи команд ничем не подтверждено [1];
  - «Flight Recorder» значит две вещи: существующий шаблон запроса [46] и отдельный будущий продукт [1];
  - пример кода на сайте использует выведенный синтаксис handler [1].

## Как это устроено внутри

### Общая схема

- Bundle контрактов (YAML) проверяет статический анализатор. Затем engine загружает его и запускает цикл событий [7].
- Каждый вход становится типизированным событием. Событие проверяется по схеме, сохраняется и рассылается по объявленным подпискам, никогда — по решению LLM [7].
- Подписчики бывают двух видов [7]:
  - **system nodes** — детерминированные handlers. Каждым событием владеет ровно один node, и только nodes фиксируют состояние;
  - **агенты** — LLM sessions. Они рассуждают и выпускают события обратно в шину событий.
- Главные пакеты (строк Go без тестов, подсчёт исследователя) [95]:
  - `internal/runtime` — около 260 тыс. Крупнейшие подпакеты: `contracts`, `pipeline`, `bus`, `llm`, `manager`, `runforkexecution`, `tools`, `bootverify`, `engine`, `workspace`;
  - `internal/store` — около 182 тыс.
- Спецификация — главный источник: если страница документации расходится с ней, права спецификация [54]. В ней разделы `llm_completion_execution_authority`, `agent_lifecycle_authority`, `permissions_model`, `static_analyzer` и другие [59].

### Детерминированный цикл (system nodes)

- Handler выполняется под блокировкой своей entity (`WithEntityLock`) [76].
- Порядок шагов фиксирован (`OrderedSteps`, `engine/executor.go`, строки 66–86): Loop, Guard, Join, Accumulate, Query, Filter, GroupBy, Reduce, Count, Compute, DataWrites, FanOut, OnComplete, Rules, AdvancesTo, Transform, Emits, Activity, Clear [76].
- Один вызов `CommitEngineMutation` записывает изменение состояния вместе с намерениями выпустить события, activities и fan-out. Это transactional outbox: намерения пишутся в той же транзакции, а рассылаются потом [76]. При конфликте по состоянию вся попытка повторяется с новой загрузки (оптимистичный повтор) [76].
- Фоновый sweeper переотправляет ожидающую работу из outbox каждые 15 с, по 200 штук (`DefaultOutboxSweeperConfig`) [77].
- Событие для entity в конечном состоянии отклоняется до запуска handler [41].
- Анализатор работает при загрузке и в `swarm verify`. Примеры проверок: `single_node_per_event`, `event_cycle_detection`, `entity_writer_coverage`, `memory_scope_validation` [56].
- Flows вкладываются через pins. Template flows создают экземпляр на ключ, singleton flows координируют общее состояние [55].

### Цикл агента

- Runtime-агент — это пара (объявление агента, flow instance) [55]. Каждый работает в своей goroutine и берёт доставки из своего канала строго по одной. Это actor model (`manager/runtime.go`, строки 1840–1870) [89].
- Состояние жизненного цикла хранится в таблице `agents`:
  - с номерами поколения и эпохи — fencing tokens, которые не дают устаревшему процессу перезаписать новое состояние;
  - с обновлением строк через compare-and-set (CAS) — запись проходит, только если строка не изменилась с момента чтения;
  - память процесса — лишь проекция этой таблицы, а не самостоятельный источник истины [59].
- Бюджеты turns [79]:
  - по умолчанию 100 turns на задачу (`agents/agent_llm.go`, строки 69–72). Запасное значение слоя разговора — 25;
  - API backends дают до 8 раундов инструментов за turn (`defaultMaxToolRounds`);
  - превышение даёт `agent_turn_budget_exhausted` или `tool_round_budget_exhausted`;
  - раунд, где все вызовы — «конечные» инструменты (например `emit_*`), завершает задачу.
- Набор инструментов закрыт по умолчанию. Агент видит только [59]:
  - объявленные инструменты;
  - общий `notify_human`;
  - созданные `emit_<event>`;
  - инструменты `read_*` / `save_*` / `update_*` для entity по своей роли;
  - свои встроенные инструменты.
  - Всё прочее отклоняется [59]. `agent_message` и `mailbox_send` выведены из работы [90][59].
- System prompt — авторский intent плюс сгенерированный в конце блок с описанием окружения (environment postamble). Во время работы session источник prompt повторно не читается [59].

### Backend `claude_cli`

- **Выполнение всегда в Docker** [69]:
  - команда: `docker exec -i -e CLAUDE_CONFIG_DIR=/opt/swarm/provider/claude -e SWARM_TOOL_GATEWAY_URL=… -e CLAUDE_CODE_OAUTH_TOKEN=<token> -w <workdir> <container> claude <args>`;
  - host backend для Claude явно не поддерживается [69][7];
  - OAuth token передаётся аргументом `-e KEY=VALUE` в командной строке `docker` на хосте. Из текста ошибок адаптер его вырезает [69].
- **Каждый turn — новая headless session, ответвлённая от предыдущей** (`cli_runtime.go`, строки 387–425) [67]:
  - первый turn: `claude -p --session-id <новый uuid> --output-format json|stream-json --tools <встроенные> --allowedTools <встроенные и MCP> --mcp-config <cfg> --strict-mcp-config --system-prompt … --model …`;
  - следующие turns: `claude -p --resume <подтверждённый head> --fork-session --session-id <новый uuid> …`;
  - id новой дочерней session становится следующим provider head (последней подтверждённой session в цепочке). Head фиксируется через compare-and-set (ожидаемый head → новый) в той же транзакции базы, которая закрывает turn [67][59];
  - если вернулся другой id или файла head нет, turn помечается outcome uncertain — «исход неизвестен» [67];
  - эта цепочка heads и даёт replay и fork разговоров Claude с точностью до turn.
- **Отдельная папка Claude на каждую session** (`workspace/claude_state.go`, строки 159–237) [81]:
  - для каждой session Claude создаётся свой контейнер `<workspace>-claude-<hash>`. Он делит mounts workspace через `--volumes-from`;
  - `CLAUDE_CONFIG_DIR` — именованный Docker volume для sessions с памятью и для доставок, либо `tmpfs` для вызовов без состояния;
  - ключ volume — SHA-256 от (хеш bundle, fingerprint исполнителя, session, вид вызова);
  - скрипт на Node готовит папку и проверяет, что head существует;
  - контейнер одноразовый и удаляется при освобождении.
- **Права** [68][67][66]:
  - режим прав задаётся только переменными окружения. `SWARM_CLAUDE_PERMISSION_MODE` передаётся как `--permission-mode`. `SWARM_CLAUDE_BYPASS_PERMISSIONS=1` добавляет `--dangerously-skip-permissions`;
  - политики одобрения отдельных запросов нет;
  - остальная защита держится на списках `--tools` / `--allowedTools` и строгом MCP config.
- **Инструменты Swarm приходят в Claude через собственный MCP server «tool-gateway».** Каждый turn получает свой токен контекста в заголовке `X-SWARM-Context-Token`. Токен ограничивает, какие инструменты этот turn может вызвать [82][85].
- **Точная проверка набора инструментов.** После каждого turn runtime сравнивает встроенные инструменты, которые Claude сообщил как видимые, с запланированным набором. Расхождение завершает turn как outcome uncertain (`validateClaudeInvocationProviderBuiltins`) [82]. При старте отдельный запуск проверяет видимый набор инструментов [67].
- **Расход и стоимость** берутся из последнего сообщения CLI `type=result`: токены, токены cache, `modelUsage` и `total_cost_usd`. Оценивать токены по числу байтов запрещено [83][59].
- **Timeouts и watchdog:**
  - timeout CLI по умолчанию — 120 с; для агентов без entity действует нижняя граница 300 с [69]. В примере конфигурации — 1 час [87]. Документация называет другие значения по умолчанию — 30 минут и 2 повтора [34][48];
  - watchdog помечает turn как долгий через timeout/4 (в пределах от 30 с до 2 мин) и как «нет вывода» через удвоенное это время [91].
- **Ошибки входа.** Если в выводе есть «not logged in», «please run /login», «authentication required» или «oauth token», ошибка классифицируется как `platform.authentication_required` [69][70].
- **Текст ошибки** Claude CLI обрезается до 240 символов [66].
- **Образ workspace** собран на golang:1.25, с git, Node и клиентом Postgres. По выбору он ставит Claude Code 2.1.87 с `DISABLE_AUTOUPDATER=1` и Codex CLI. Работает от uid 10001 [86].
- **Скорость.** Автор назвал backend `claude_cli` медленным и последовательным, когда пытался нагрузочно проверить параллельность (issue #1449 про нагрузочный тест, 2026-06-23) [101].

### Параллельность и координация

- **LLM-планировщика нет.** Перестроить flow во время работы LLM не может [7].
- **Разбиение задачи объявляется заранее.** Агент выпускает список, а `fan_out` в handler (с `identity` и `max_items`) создаёт экземпляр template flow на каждый элемент — со своим агентом, session и workspace [55]:
  - сбор — join (`barrier` или `stream`) с удалением дубликатов, окнами и обязательным timeout;
  - циклы доработки — `loops:` с `max_attempts` и `escape`; вложенные и неограниченные циклы отклоняются;
  - timers на stages — долговременные переходы.
- **Одна установка.** Swarm не раскладывает flow instances по машинам [35]. Каждым хранилищем владеет один процесс: в Postgres — через advisory lock, в SQLite — через `flock`. Процесс в standby ждёт и никогда не отбирает блокировку [59].
- **Общего лимита одновременных агентов нет.** Валидатор конфигурации отвергает `runtime.max_concurrent_agents` и `sharding`, потому что их не исполняет ни один путь [94]. Документация всё ещё показывает оба ключа [34]. На деле одновременность ограничивают [87][71][74]:
  - `llm.provider_limits` (описан ниже);
  - `max_items` у fan-out;
  - `runtime.fan_out_workers` — по умолчанию 4 на Postgres и 1 на SQLite;
  - последовательная работа каждого агента;
  - лимит бюджета: при заданном лимите в области одновременно допускается один вызов LLM, второй отклоняется [74].

### Изоляция

- **Ровно три mount** у каждой session агента: `/workspace` (чтение и запись), `/data` (только чтение, общий), `/opt/swarm/contracts` (только чтение) [48].
- **Область workspace** — `per-agent` или `per-flow-instance`, задаётся через `workspace_classes` в policy [48]. Контейнеры называются `swarm-agent-<id>` или `swarm-flow-<path>` и несут метки происхождения, например `dev.swarm.run_id` и `dev.swarm.entity_id` [48].
- В коде это долгоживущие контейнеры `sleep infinity` с именованным volume на `/workspace` и необязательной общей сетью [81].
- **Ограничений у контейнеров workspace не найдено:** нет `--cap-drop`, `--read-only` и лимитов памяти и CPU. Ужесточён только контейнер проверки допуска (`--network none --cap-drop ALL --memory 256m --pids-limit 64`) [93]. Compute modules в Docker не запускаются. Они исполняются в Wasmtime внутри процесса runtime (Python — CPython 3.13 под WASI, корень только на чтение), с лимитами fuel (gas) и памяти [52][153]. `--network none` в `worker_execution.go` (строка 189) относится к разовой проверке собранного образа worker, а не к compute modules [93].
- **Host backend** включается явно (`workspace.allow_exec_on_host: false` по умолчанию). Bash на хосте — это полный shell пользователя [87][7].
- **Изоляции на уровне git нет.** Ни worktrees, ни веток в коде нет. Локальных git-коммитов нет [7]. GitHub pack только ставит метки, создаёт issues и комментарии и принимает webhooks. Инструментов для PR и CI нет [92].

### Состояние и память

- **Event sourcing в два слоя** [46]:
  - `events` дописываются до доставки;
  - `entity_mutations` хранят значения до и после и событие-причину;
  - «flight recorder» — соединение `events`, `entity_mutations`, `agent_turns` и `event_deliveries` по `run_id` [46][43].
- **Другие таблицы:** `event_delivery_attempts`, `dead_letters`, `spend_ledger`, `runtime_external_effect_operations/attempts`, `runtime_effect_budget_reservations`, `decision_cards`, `timers`, `flow_instances` и семейство `run_fork_*` [59].
- **Доставки.** Захват доставки сопровождается heartbeat. Доставке агенту дают 1 повтор, доставке node — 3 (`AgentMaxRetries = 1`, `NodeMaxRetries = 3`) [78].
- **Идемпотентность API.** Изменяющие вызовы принимают `idempotency_key`. Ответы хранятся 24 часа для тройки (метод, токен, ключ) [57].
- **Dev-режим.** `serve --dev` заменяет временное хранилище при каждом старте [7].
- **Память агента** [35]:
  - `memory: false` (по умолчанию) — новый разговор на задачу;
  - `memory: true` — один долговременный разговор на тройку (run, агент, flow instance). Разрешён только в template flows, иначе загрузка падает с поясняющей ошибкой.
- **Сжатие контекста есть только у HTTP backends** (Anthropic, OpenAI-совместимый, OpenAI Responses), но не у `claude_cli` [80]:
  - срабатывает около 80% окна контекста, но не выше значения «окно − вывод − 64 тыс.»;
  - оставляет около 16% доступного окна;
  - пишет долговременные контрольные точки с разделами Intent, Essential facts, Completed work, Errors, Pending work, Next action;
  - если маршрут и модель позволяют, используется встроенное сжатие провайдера [80]. Это правило по умолчанию закреплено в issue #2921 (решение о сжатии контекста, закрыт 2026-11-03): сжатие провайдера, иначе сводка платформы [130].
- **У `claude_cli`** контекст ведёт сам Claude Code плюс цепочка `--resume --fork-session` [67].
- **Ротация.** После 3 ошибок разбора ответа (`rotate_on_parse_failures`) session заменяется новой, а её сообщения и контрольные точки сбрасываются [80][87].
- **Обновления.** Память агента переживает обновление bundle на месте. Следующий turn, в том числе продолженный вызов Claude CLI, идёт с новым prompt и моделью [9].

### Проверка качества

Swarm проверяет flows, а не результат работы агентов.

- `swarm verify` — статический анализ без запуска [53].
- `swarm test` — детерминированные сценарии. Они обращаются только к публичному API и проверяют результат после затихания run [53].
- Mock backend на Python проводит turns агентов через настоящий runtime. Внешние действия при этом заблокированы [53][7].
- Conformance suite — 12 уровней, больше 200 bundles [7].
- Traces compute modules сверяются при replay [76].
- **Чего нет:** test-, CI- или PR-проверок результата работы агентов и встроенных reviewer-агентов. Шаг review пользователь сам моделирует как агента плюс ограниченный цикл `loops:` [55].

### Восстановление после сбоев

- **Handlers** — до 3 повторов с паузами 1, 2 и 4 с. Записи откатываются перед повтором. Ошибки guard и бизнес-логики не повторяются [41].
- **Dead letters** имеют тип `failure_type`: `retry_exhausted`, `handler_error`, `target_resolution_failed` или `chain_depth_exceeded`. Их можно повторить [41].
- **Классы сбоев** — закрытый перечень. У каждого класса есть код причины, флаг «можно повторить» и способ исправления, например `platform.outcome_uncertain` и `platform.budget_exhausted` [84].
- **Зависший run** (больше 300 с) выпускает `platform.run_stalled` один раз на каждый набор признаков диагноза [41].
- **После падения процесса** сохранённые, но не доставленные события доставляются снова, с fingerprints идемпотентности [44].
- **Ручные инструменты** [44][7]:
  - `swarm event replay`, `swarm agent replay` и `swarm agent replay-backlog`;
  - `swarm run fork <run> [--at-event|--at-start|--publication] [--source <dir>] [--pin name@vN]` восстанавливает состояние на выбранный момент по журналу изменений под новым `run_id` [63][59];
  - `swarm forkchat` копирует один разговор агента в sandbox [9].
  - Документация о fork на новый bundle пишет, что он сейчас отклоняется [44], а текущий код принимает `--source <dir>` [63].
- **Вызов LLM — не больше одного раза (at-most-once), по замыслу.** Каждый вызов провайдера — долговременная попытка внешнего действия [59]:
  - шаги: разрешение → `MarkLaunched` (фиксируется до старта процесса) → heartbeat → `response_observed` → одна транзакция расчёта, которая пишет расход и освобождает резервы бюджета;
  - при восстановлении попытки, которые уже стартовали, становятся `outcome_uncertain` и повторно никогда не отправляются;
  - повторная отправка провайдеру при восстановлении или replay прямо запрещена спецификацией.

### Лимиты и стоимость

- **Ограничения на стороне клиента.** `llm.provider_limits.<backend>` задаёт `rate_limit: "N/период"` с `rate_limit_max_wait` и `max_concurrency` с `max_concurrency_max_wait`, с переопределениями по модели [72][87]:
  - частота считается скользящим окном в памяти процесса, одновременность — семафором (`provider_admission.go`, строки 190–245) [71];
  - ожидание дольше предела даёт ошибку `llm_provider_rate_limited` [71];
  - лимиты действуют в пределах одного процесса. Они добавлены 2026-07-03 [19];
  - решение перейти от схемы «отправить, получить HTTP 429, повторить с паузой» к заранее рассчитанному темпу запросов в клиенте LLM, включая обёртку `claude_cli`, записано в issue #1457 (про ограничение частоты запросов, июнь 2026) [102].
- **Ошибки провайдера у HTTP backends.** На один turn — одна попытка HTTP. Цикла повторов внутри адаптера нет, заголовок `Retry-After` не учитывается [88]:
  - ответы 4xx — окончательные сбои: 401 — вход, 403 — права, 402 — `provider_credit_exhausted`, 408 — timeout [70][88];
  - 429 по коду статуса считается повторяемым [84];
  - 5xx и ошибки транспорта помечаются outcome uncertain [88];
  - доставка агенту повторяется один раз (база паузы — 1 с), затем уходит в dead letters [41][78].
  - Про 408 CHANGELOG и код согласны. CHANGELOG пишет, что 408 и 429 повторяемы, но автоматической повторной отправки нет [9]. В коде попытка с любым 4xx закрывается как `terminal_failure` и повторно не отправляется. При этом 408 получает класс `platform.timeout`, а 429 — `platform.connector_failure` со статусом 429; каталог сбоев помечает оба как повторяемые [70][84][88].
- **Окна подписки (5 часов, неделя) не обрабатываются вовсе:**
  - поиск по всему репозиторию не находит «usage limit», «limit reached», `rate_limit_event`, `rate_limit_error` и `overloaded_error` [66][67][68][69][70];
  - нет понятия 5-часового или недельного окна, нет разбора времени сброса и нет схемы «подождать сброса и продолжить» [66];
  - спецификация откладывает обнаружение квот конкретного провайдера и динамическую подстройку под провайдера на будущее [59].
- **Что будет при упоре в 5-часовой лимит на `claude_cli`.** Это вывод исследователей, запуском не проверено. Здесь исследования расходятся в деталях:
  - по одному чтению кода CLI завершится с ненулевым кодом (`claude_cli_process_failed`). После старта процесса это оборачивается в `platform.outcome_uncertain`, а каталог сбоев помечает этот класс как неповторяемый: сначала сверить состояние, потом повторять. Применяется ли к нему единственный повтор агента, не прослежено [69][84];
  - по другому — неудачная попытка помечается outcome uncertain, проходит обычные повторы и после них попадает в dead letters [69][104];
  - по третьему — turn упадёт, получит один повтор и окажется в dead letters [66][41].
  - Совпадают все три в главном. Никто не ждёт сброса лимита. Работу возвращает человек через replay события или очереди агента [44]. Сигнал о зависании приходит через 5 минут [41]. Бюджеты в долларах окна подписки не моделируют [40].
- **Автор решает ту же задачу в своём процессе.** Его агент-orchestrator ведёт учёт квоты и ставит работу на паузу и возобновляет её вокруг квот [128]. Работает ли эта оркестрация на Swarm — не подтверждено.
- **Бюджеты — в долларах на календарный месяц UTC** [40][73]:
  - лимиты `global_monthly_cap`, `per_entity_monthly_cap`, `system_monthly_cap`;
  - пороги warning, throttle и emergency в policy (в примере 60, 80 и 95%) [40];
  - пересечение порога выпускает `platform.budget_threshold_crossed`. При emergency создаётся critical-задача alert в mailbox [73];
  - пока область в emergency, доставки агентам в ней подавляются. Emergency на системном уровне подавляет все доставки агентам [75][73];
  - throttle подавляет только события из `throttle_suppress_prefixes`; перехода на дешёвую модель в коде нет, хотя документация его описывает [75][34].
- **Жёсткий резерв бюджета до вызова.** Каждая попытка LLM блокирует строку своей области и резервирует весь оставшийся запас. Если запас не положительный, вызов отклоняется (`completion_spend_budget_exhausted`) [74][59]. Test `no_cap_does_not_serialize` ожидает, что без лимита проходят оба из двух одновременных вызовов, а с лимитом — один. Второй получает `completion_spend_budget_exhausted` (класс `platform.budget_exhausted`, в каталоге сбоев — неповторяемый) [74][84]. Значит, при заданном лимите вызовы LLM в этой области не идут параллельно: лишний вызов отклоняется, а не ждёт очереди. Что runtime делает с таким отказом дальше — не проверено.
- **Circuit breaker (автоматическая остановка) при сбое входа или оплаты.** Сбой входа или HTTP 402 останавливает приём новой работы, пишет в log `runtime_pause_breaker_tripped`, а при сбое входа публикует `platform.auth_required`. Дальше нужен человек [75].
- **Бюджет внимания.** `budget.human_tasks.max_tasks_per_week` ограничивает число карточек от `ask_human` в неделю. По умолчанию 0 — ограничение выключено. День сброса настраивается [87][90].

### Права и безопасность

- **Права инструментов.** Встроенные инструменты платформы проверяют список `permissions` агента (например `approve_spend`, `ask_human`, `schedule`) с необязательными `permission_bundles` [59]:
  - MCP- и HTTP-инструменты разрешает реестр инструментов и хранилище учётных данных; встроенные — поле `native_tools` [59];
  - все права действуют внутри одного flow instance. Flows координируются только событиями [59].
- **API.** Bearer token даёт все права, scopes не проверяются. Токен WebSocket проверяется один раз, при подключении [57]. Listener по умолчанию на loopback, там работает встроенный dev token [42][34].
- **Учётные данные** лежат в файле, по умолчанию `os.UserConfigDir()/swarm/credentials.json`. Управление — командой `swarm secrets` [7].
- **MCP.** Swarm подключает MCP servers, объявленные в policy: http или stdio, с обязательным префиксом; недоступные пропускаются при загрузке [49]. Маршрут `/mcp`, который Swarm открывает сам, — это gateway инструментов агентов [85]. Что через него может внешний MCP client — не подтверждено.
- **Права Claude Code** — только через переменные окружения, вплоть до полного обхода через `--dangerously-skip-permissions` [68].
- **OAuth token Claude** виден в командной строке `docker` на хосте [69].
- **Контейнеры workspace** без `--cap-drop`, `--read-only` и лимитов ресурсов [93].

### Наблюдаемость

- **Story feed** — лента в терминале, описана в «Функциях» [43].
- **Traces.** `run.trace` и `run.subscribe_trace` дают объединённый вид событий, доставок, sessions и turns. `run.diagnose` называет блокирующий слой и причину [43][60].
- **Другие методы чтения:** `agent.diagnose`, `conversation.get_turn`, `runtime.logs`, incidents и health. Подписки WebSocket есть на события, traces, logs и health [60].
- **Сырой вывод CLI** по агентам лежит в `.swarm/monitor` [87].

### Единственная видимая попытка внедрения: fork

- **Что в fork.** В одном из fork есть свои коммиты: 79 коммитов сверх upstream, все от владельца fork, с 2026-10-09 по 2026-10-19. У других fork, которые удалось сравнить, своих коммитов нет [20][149]. Fork добавляет отдельную папку под небольшой pipeline поиска покупателей с намерением купить [149]:
  - flow Swarm, описанный только в YAML: событие приёма переходит в событие «в очереди на review»;
  - инструменты на стандартной библиотеке Python: сбор RSS, оценка, удаление дубликатов в SQLite;
  - отдельный модуль, который вызывает Swarm по RPC с авторизацией и включается явно;
  - файлы deploy для Render.
- **Почему выбрали Swarm** (вывод исследователя из плана внедрения в самом fork) [149]:
  - детерминированный приём данных с прослеживаемостью до источника;
  - replay на отдельном хранилище SQLite;
  - лимиты расхода и стоимости, которые действуют до включения AI-reviewer.
- **Что сработало** (по документам fork): `swarm verify` прошёл; синтетический сценарий прошёл в `swarm test`; 28 тестов на Python прошли в CI [149].
- **Что мешало:**
  - на Render более ранняя сборка работала, а новый старт упал. Блокировка владения при старте сообщила, что уже работает другой `swarm serve`;
  - документы fork объясняют это пересечением rolling deploys на эксклюзивной блокировке Postgres одного процесса;
  - отдельная база Neon Postgres содержала схему Swarm, но ни одного записанного агента и run [149].
- **Итог:**
  - README fork называет его проверенной основой для разработки, а не работающей системой. Живых источников, платящих покупателей и работы по расписанию не показано;

### Как Swarm сравнивают

- **Сравнений от пользователей не найдено** [143][146][147][152].
- **Сравнение вендора** [28]:
  - Swarm ближе к системам durable execution (Temporal, Restate, Inngest), чем к библиотекам агентов;
  - вендор заявляет превосходство над CrewAI/AutoGen, обычными workflow runners и LangGraph по маршрутизации, восстановлению после падения, изоляции, контролю стоимости, одобрениям человека, тестам и аудиту;
  - вендор признаёт, что детерминизм заканчивается на рассуждениях агентов;
  - вендор сам перечисляет плохие применения: разовые вызовы модели, простые чат-боты, быстро меняющиеся прототипы и системы, где следующий шаг решает модель.
- **Единственная внешняя оценка — машинная.** Она повторяет две претензии: тесный рынок и избыточность для простых процессов [147].

- **Большая часть активности — его команда AI-агентов:**
  - 2026-10-17 он передал оперативные решения агентам «lead» и «orchestrator» и велел им не ждать его [128];
  - orchestrator отвечает за параллельные потоки работы, порядок merge и выбор reviewer, за утренние отчёты и отчёты по этапам, за учёт квоты использования и за паузу и возобновление работы вокруг квот [128];
  - решения о продукте, архитектуре и деньгах остаются за ним [128];
  - треды подписаны ролями, например «reviewer-f» [131];
  - issue #1830 просит агента, который построил Empire (самый большой внутренний набор flows автора), проверить дизайн на нём [105];
  - бот Codex оставил 1286 комментариев review в PR [17];
  - значит, около 30 000 комментариев — в основном вывод агентов, а не сообщество (вывод) [16].
- **Lanes.** Метки issues задают lanes — отдельные потоки работы с «Agent A» по «Agent H», от 18 до 187 issues в каждом [14][15]. Issues упоминают lanes с парными reviewers, например «Lane: G (channels), reviewer-g» [129]. Какие инструменты работают в lanes A–H и AI-агенты ли это — не подтверждено.
- **Роли в текстах issues:** orchestrator, lead, reviewer lanes, «rulings» (решения владельца) и «sittings» (сессии с владельцем). Самого maintainer-а агенты называют «the user» [118][126][127][133].
- **Issues от имени агентов.** Пример — заголовок с меткой `[agent-g]` про «proof disposition», с id gates и 54-минутными полными квалификационными runs (`--full`) (issue #2550, 2026-10-03) [122].
- **Codex в процессе:**
  - Codex указан как аудитор (issue #95, 2026-04-05) [96];
  - review от Codex — обязательная проверка перед merge, и merge блокируется, пока у Codex исчерпан лимит (issue #2407 про правила merge) [118];
  - daemon Codex запускает локальные тесты (issue #2666) [125].
- **Claude Code в процессе.** Сентябрьский аудит ссылается на artifact на claude.ai/code. Открыть его не удалось [119][120].
- **Механика процесса:** уровень CI выбирается для каждого PR; есть preflight-квитанции; merge — только rebase [10][15]. Работа с высоким риском требует одобренного pre-audit (плана до кода) и proof audit (доказательств до review) [10].
- **Мелкие проблемы доверия, которые заметит новичок** (наблюдения исследователя):
  - README и LICENSE говорят Apache 2.0, а GitHub и pkg.go.dev лицензию не распознают [3][22][7];
  - первые release notes называли версию спецификации 1.6.0, а сегодняшний README — v0.7.0 [12][7].

## Направление развития

### Происхождение: «Empire»

- **История из Show HN.** Работодатель автора закрылся. Автор давал frontier-моделям трудные задачи распределённых систем, построил автономную «фабрику микро-SaaS» и вынес её runtime в Swarm [143].
- **Empire** — самый большой внутренний набор flows автора [105]. Здесь исследования расходятся. Одно прямо называет Empire пакетом контрактов той самой фабрики [134]. Два других считают это только вероятным выводом: внутренние обсуждения описывают Empire как главную систему автора, но прямо с фабрикой микро-SaaS не связывают (не подтверждено) [13][134][135][136]. Что известно о составе Empire [134]:
  - десять дочерних flows: signal-search, discovery, scoring, lifecycle, holding-devops, treasury, spec-repo, repo-scaffold, validation, operating;
  - только `operating` — template flow, по одному экземпляру на Product.
- **Агенты Empire** [135]:
  - 28 ролей и около 2400 строк prompt-файлов;
  - в YAML контрактов prompts нет;
  - суждения записаны в файлах критериев со стабильными id. Например, роль «factory CTO» отклоняет спецификации со ссылками на id правил.
- **Следы Empire сегодня.** Benchmark M5 в roadmap прослеживает жизненный цикл «OpCo» (operating company — отдельной операционной компании под один продукт) [13]. Пример в документации HITL до сих пор выпускает событие `opco.launched` [38]. Внутренние обсуждения описывают Empire как главную систему из «verticals» (направлений бизнеса) и жизненных циклов OpCo [13][134][135][136].
- **Ранний UI.** В раннем репозитории были dashboard и визуализатор flows [18]. Общий API «Builder» вынесли из сервера dashboard 2026-03-26. Его транспорт удалён 2026-08-30 [18][59][116].
- **Конечная цель.** README говорит, что проект движется к тому, чтобы целые подразделения компаний работали как автономные flows. Июньский README называл разработку, поддержку и операционную работу [7][8].

## Слабые места и чего нет

- **Почти нет пользователей.** 25 звёзд, 31 скачивание, ноль внешних импортёров, около 2 человек в Discord, Show HN без обсуждения [3][12][22][24][143]. Единственная видимая попытка внедрения остановилась без живых данных [149].
- **Один автор.** Весь код, все issues и PR — от одного человека и его агентов [4][15][128].
- **Pre-1.0 без миграций.** Ломающие изменения ожидаются, несовместимое хранилище не загружается [7][9]. Каждое обновление до 1.0 ломало хранилище живой установки и требовало заново подключать WhatsApp [132].
- **Документация отстаёт от кода.** Репозиторий документации последний раз менялся 2026-10-15, код — 2026-11-12 [26][7]. С кодом расходятся:
  - `mailbox approve|reject` — в коде `decide` [39][61];
  - многослойные файлы конфигурации — код читает один файл [34][7];
  - `run start`, который поднимает свой runtime [32][7];
  - `entities.yaml` [9];
  - `artifact_repo_commit` [45][59];
  - `max_concurrent_agents` и `sharding` [34][94];
  - флаг `--abandon-active-runs`, убранный в v0.7 [42][9];
  - ключи `claude_cli` вроде `use_tmux`, которых нет в коде конфигурации [87];
  - общие инструменты `agent_message` и `mailbox_send` [35][90];
  - переход на дешёвую модель при throttle [34][75];
  - оговорка о заблокированных mock-агентах [53][7];
  - отказ в fork на новые контракты [44][63];
  - timeout и число повторов `claude_cli` [34][48][69];
  - версия спецификации в FAQ [2][7];
  - пример кода на сайте с выведенным синтаксисом handler [1].
- **Известная ошибка, описанная в документации.** Правка контрактов и перезапуск на том же хранилище может сломать публикацию событий. Обходной путь — удалить хранилище [42].
- **Новичок не может запустить сложный flow.** Собственный аудит проекта от 2026-08-05: по одной документации новичок довёл сложный flow до успешной проверки, но запустить не смог, и записал около 30 проблем [58]. Issue #1578 про путь от установки до первого запуска открыт [103].
- **Маркетинг обещает больше, чем есть:**
  - тысячи команд агентов и изоляция клиентов против одной установки без multi-tenancy [1][45][57];
  - пересчёт с изменёнными контрактами против документации, где он отклоняется [1][44];
  - Builder и Flight Recorder — только «soon» [1].
- **Нет GUI.** Только CLI, лента в терминале и API [7].
- **Нет git, PR и CI.** Worktrees и веток в коде нет. Локальные коммиты убраны 2026-09-21 без замены. GitHub pack работает только с issues. Linear, Jira и GitLab нет [7][92][111].
- **Проверяется процесс, а не результат.** Нет test-, CI- и PR-проверок работы агентов. Нет встроенных reviewers [53][55].
- **Агенты.** Codex нет [86]. `claude_cli` работает только в Docker и, по словам автора, медленный и последовательный [69][101]. Claude Code закреплён на 2.1.87 без автообновления [86].
- **Лимиты подписки не обрабатываются.** Нет распознавания 5-часового и недельного окон, нет ожидания сброса и автоматического продолжения. Один повтор, затем dead letter. Вызовы с неизвестным исходом никогда не отправляются повторно. Бюджеты — только в долларах [66][59][41].
- **Права Claude Code — только через переменные окружения**, вплоть до полного обхода. Политики для отдельных запросов нет [68].
- **Безопасность:**
  - один токен даёт все права, scopes не проверяются [57];
  - OAuth token Claude виден в командной строке `docker` на хосте [69];
  - у контейнеров workspace нет `--cap-drop`, `--read-only` и лимитов памяти и CPU [93];
  - host backend даёт агенту полный shell пользователя [87].
- **API.** Подписки теряют сообщения и не переживают обрыв. Нет ограничения частоты, SLA и массовых методов [57].
- **Одна установка.** Нет распределения по машинам, второй процесс только ждёт [35][59]. В единственной видимой попытке внедрения rolling deploy на Render упал на эксклюзивной блокировке [149].
- **Платформы.** Нет Windows. Linux — только glibc, macOS — только arm64 [12][7][9].
- **История тихих сбоев** в главных функциях: human in the loop, журнал изменений, fork, записи агентов [99][100][112][123]. Открыты issues про потерянную работу (#2283) и проблемы пилота (#2285) [113][114].
- **WhatsApp на неофициальной библиотеке.** Риск блокировки аккаунта, нет повторной доставки, в production канал тихо отключался (#3011) [65][131]. Приёмку на физических устройствах не прошёл [9]. Живая проверка Telegram с настоящим токеном не проводилась [7].
- **Нет общего лимита одновременных агентов** [94].
- **Нет учётных записей, ролей и SSO** [57].
- **Название трудно найти** в поиске [152].
- **Лицензию не распознают** GitHub и pkg.go.dev [3][22].

### Где пересекаются

- **Долгая работа агентов без человека и запись её истории.** Swarm держит состояние в базе, восстанавливается после падения, ведёт timers и ждёт решений человека [44][47][38]. worfy делает это через Autopilot и Waves.
- **Одно и то же имя «Flight Recorder».** В Swarm так называется шаблон запроса к четырём таблицам и будущий продукт для replay и отладки [46][1]. В worfy — timeline run без человека. Рядом стоит и «Builder · visual canvas» против Canvas в worfy [1].
- **Claude Code как исполнитель.** Swarm запускает headless `claude -p` на каждый turn внутри Docker, со входом по OAuth token подписки, с цепочкой `--resume --fork-session` и своим MCP tool-gateway [67][69][82]. worfy запускает sessions Claude Code и Codex.
- **Человек в контуре.** Swarm зовёт человека через decision cards и mailbox, в том числе в Telegram и WhatsApp [38][92]. worfy — через уведомления.
- **Учёт расхода.** Swarm считает токены и доллары по агенту, entity и исполнителю [40][60]. worfy показывает счётчики лимитов и расхода.
- **Расчёт на Claude Code как на помощника.** Swarm планирует skill для Claude Code, который пишет и запускает flows [127]. worfy поставляет Harness plugin с rules, skills, subagents и hooks.
- **Процесс разработки самого Swarm похож на то, что делает worfy.** У автора есть агент-orchestrator, lanes с reviewer-агентами, review от Codex как условие merge, пауза и возобновление работы вокруг квот [128][118][96][125]. В worfy Orchestrator session планирует работу, reviewer subagents проверяют PR, Autopilot ждёт сброса лимитов.
- **Похожие правила текста.** Правила U3 (статус показывает наблюдаемое состояние, false-green — худшая ошибка) и U11 (слова пользователя вместо внутреннего словаря) [108] совпадают по смыслу с правилами Harness о доказательствах до слова «green» и о простом языке.

### Где расходятся

- **Кто управляет.** В Swarm решает код, а LLM не может перестроить процесс [7]. Swarm прямо критикует системы, которыми управляет LLM: модель выдумывает состояние, контекст переполняется, восстановления после падения нет [28]. В worfy работу планирует Orchestrator — LLM-session.
- **Предмет работы.** Swarm ведёт бизнес-процессы: поддержку, поиск покупателей, ответы в WhatsApp. Работы с git в нём нет [7][61][149]. worfy ведёт работу над кодом в репозиториях.
- **Изоляция и проверка.** В Swarm — Docker-контейнеры и проверка контрактов [48][53]. В worfy — git worktrees, тесты, Gate, CI и reviewer subagents.
- **Лимиты подписки.** worfy ждёт сброса лимитов. Swarm окна подписки не знает и считает только доллары и частоту запросов [59][40][71].
- **Одобрения.** Swarm принципиально не одобряет по timeout, а graduation одобрений только планирует [38][106]. worfy одобряет запросы разрешений автоматически по policy.
- **Интерфейс и платформа.** Swarm — сервер с CLI, без GUI [7]. worfy — desktop-приложение с Canvas.
- **Агенты.** В Swarm нет Codex [86].
- **Чего в Swarm нет совсем:** Terminal с AI-помощником, встроенного Browser с профилями, Cards на Canvas, Product Session с Mind map и критиком спецификаций, PR inbox, Linked machines, Evidence screenshots с privacy scrub, Work track (вся работа проекта за день или неделю) — аналогов не найдено. Из близкого к privacy scrub — только вырезание OAuth token из текста ошибок [69].

## Механизмы, которые стоит изучить

1. **Цепочка ответвлённых sessions Claude Code на каждый turn.**
   - Что это: каждый turn агента — отдельный вызов `claude -p`, ответвлённый от прошлого.
   - Как работает: `--resume <head> --fork-session --session-id <новый uuid>`. Id новой session становится head и фиксируется через compare-and-set в той же транзакции, что и итог turn. Если вернулся другой id или файла head нет, turn помечается outcome uncertain. Так можно сделать replay и fork разговора с точностью до turn. Папка Claude у каждой session своя, в отдельном одноразовом контейнере.
   - Источник: [67][59][81].
2. **Проверка набора инструментов после каждого turn.**
   - Что это: сверка, что Claude видел ровно те встроенные инструменты, которые разрешены.
   - Как работает: после turn runtime сравнивает список видимых инструментов из ответа CLI с планом (`validateClaudeInvocationProviderBuiltins`). Расхождение — сбой turn. При старте отдельный запуск проверяет набор заранее.
   - Источник: [82][67].
3. **Токен контекста на каждый turn для MCP.**
   - Что это: инструменты платформы приходят в Claude через собственный MCP server с ограничением на один turn.
   - Как работает: заголовок `X-SWARM-Context-Token` задаёт, какие инструменты доступны этому turn. `--strict-mcp-config` не даёт подключить другие MCP servers.
   - Источник: [82][85][67].
4. **Вызов LLM как внешнее действие «не больше одного раза».**
   - Что это: каждый вызов провайдера записан как долговременная попытка с явными шагами.
   - Как работает: разрешение → `MarkLaunched` до старта процесса → heartbeat → `response_observed` → одна транзакция расчёта. После падения запущенные попытки становятся `outcome_uncertain` и повторно не отправляются. Сбои описаны закрытым перечнем классов: код причины, флаг «можно повторить», способ исправления.
   - Источник: [59][84].
5. **Резерв бюджета до вызова и circuit breaker.**
   - Что это: деньги резервируются раньше, чем начинается вызов модели.
   - Как работает: лимиты по умолчанию выключены (0) и включаются в конфигурации. Попытка блокирует строку области бюджета и резервирует весь остаток; без остатка вызов отклоняется. Поэтому при заданном лимите второй одновременный вызов в той же области получает отказ `completion_spend_budget_exhausted`, а не ждёт. Пороги warning / throttle / emergency выпускают `platform.budget_threshold_crossed`; при emergency создаётся critical-задача в mailbox. Сбой входа или HTTP 402 останавливает приём новой работы и пишет в log `runtime_pause_breaker_tripped`. При сбое входа ещё публикуется `platform.auth_required`.
   - Источник: [74][75][73][87].
6. **Ограничитель частоты и одновременности на стороне клиента.**
   - Что это: темп запросов задаётся заранее, а не узнаётся по ошибкам 429.
   - Как работает: скользящее окно частоты и семафор одновременности на backend и модель, с максимальным временем ожидания. Действует и на запуск процессов `claude_cli`. Если ждать дольше предела — повторяемая ошибка: `rate_limited` в спецификации, `llm_provider_rate_limited` в коде.
   - Источник: [59][71][72][84][87][102].
7. **Decision cards с хешем фактов и без одобрения по timeout.**
   - Что это: решение человека — типизированная карточка с заранее объявленными исходами.
   - Как работает: карточка, показанная на устаревших фактах, недействительна. Истёкший срок ведёт к эскалации, а не к одобрению. Напоминания — через 4 часа, затем каждые 24 часа. Недельный лимит задач для человека (по умолчанию выключен). Карточки показывают channel packs Telegram и WhatsApp; через бота, зарегистрированного на уровне установки, в v0.7 решать можно только из CLI. Решение принимается один раз.
   - Источник: [38][39][87][90][92][129].
8. **Graduation одобрений и строгость по классу действия (план).**
   - Что это: путь от ручных одобрений к правилу, которое человек проверил.
   - Как работает: после N одинаковых одобрений класса система предлагает автоодобрение как правку контракта. Правка пишется в журнал, отзывается и проверяется выборочным аудитом. Чтение одобряется автоматически с уведомлением, идемпотентная запись — обычным запросом, отправка и списание денег — полной процедурой с вводом имени flow.
   - Источник: [106][141].
9. **Story feed и объяснение, почему run стоит.**
   - Что это: человекочитаемая лента событий и диагноз зависания.
   - Как работает: одна строка на значимый шаг, цвет в терминале (красный только для настоящих сбоев), NDJSON при выводе в pipe, живая строка статуса. `run status` называет блокирующий слой и причину. `platform.run_stalled` приходит через 300 с, один раз на зависание.
   - Источник: [43][41].
10. **Flight recorder как запрос, fork по событию и forkchat.**
    - Что это: история run собирается из обычных таблиц, а не из отдельного журнала.
    - Как работает: таблицы `events`, `entity_mutations` (до и после для каждого поля), `agent_turns` и `event_deliveries` соединяются по `run_id`. `run fork --at-event` восстанавливает состояние под новым `run_id`. `forkchat` копирует один разговор агента в sandbox на 24 часа.
    - Источник: [46][63][33][60].
11. **Ошибки, рассчитанные на исправление агентом.**
    - Что это: сообщения анализатора и CLI, по которым coding-агент чинит контракт без человека.
    - Как работает: каждая находка — id проверки и точный путь к полю. Страница документации для LLM-агентов задаёт цикл: verify → исправить по id → искать образцы grep-ом в 200+ проверенных bundles. Правила UX требуют, чтобы каждая ошибка, после которой нельзя продолжить, называла команду исправления, а каждый успех — следующий шаг.
    - Источник: [56][54][108].
12. **Контрольные точки сжатия контекста и watchdog.**
    - Что это: сжатие разговора по фиксированному шаблону и сигнал о зависшем turn.
    - Как работает: сжатие срабатывает около 80% окна и оставляет около 16%. Контрольная точка имеет разделы Intent, Essential facts, Completed work, Errors, Pending work, Next action. После 3 ошибок разбора ответа session заменяется новой. Watchdog помечает turn как долгий через timeout/4 и как «нет вывода» через удвоенное это время.
    - Источник: [80][91].
