## Модель работы

### Local, cloud или hybrid

Hybrid. Агенты работают на машинах пользователя. Аккаунт, sync и связь между машинами идут через облако Traycer.

- **Три части** [51][56][74]:
  - **Desktop-приложение** — Electron-оболочка вокруг интерфейса на React [89][90].
  - **Host** — фоновый процесс на каждой машине. По документации, он связывает приложение с папками, файлами,
    терминалами, состоянием git и coding-агентами на этой машине [51].
  - **Облако Traycer** — аккаунты, sync Tasks и истории, relay (сервер-посредник между устройствами), лента
    уведомлений и опубликованные копии чатов [51][56][74].
- При первом запуске приложение само скачивает и ставит Host: «Downloading Traycer Host…» [23].
- По умолчанию Host продолжает работать после выхода из приложения. Агенты при этом не останавливаются [64].
- Живая работа идёт на машине, которая её начала. Облако переносит между устройствами Tasks и их историю [51][56].
- Self-hosted облака в документации нет. Dev-сборка из репозитория работает с production-облаком, локальных
  backend-ов нет [90].
- Нужен аккаунт Traycer. Вход — через браузер: GitHub, Google, Apple или одноразовый код на email [75]. Аккаунт
  нужен, даже если работать только на своих подписках. Запрос на offline или self-hosted режим остался без ответа
  [147].
- Приватность [89][77]:
  - код обрабатывается в памяти, не хранится и не идёт на обучение;
  - Privacy Mode включён по умолчанию для командных планов; одиночки включают его сами;
  - запросы к coding-агенту идут прямо к его провайдеру;
  - в release-сборках могут быть включены Sentry (отчёты о сбоях) и PostHog (аналитика);
  - product analytics с выключенным захватом содержимого добавили в 1.1.7 [77].
- Версия 1.0.0 подавалась как local-first: всё хранится локально. С 1.2.0 чаты копируются в облако. Cloud sync
  сейчас есть во всех планах [77][71].
- Cloud sandboxes упомянуты в протоколе и на странице цен, но не в документации. Выпущены ли они (не подтверждено)
  [2][133][135].

  адаптеры примерно для десяти провайдеров [119][120][121].

  - **Chat** — Host управляет провайдером из кода. Есть у всех агентов. Модель, права, thinking effort, fast mode,
    вложения и голос меняются от хода к ходу.
  - **Terminal** — собственный TUI агента в терминале, с фиксированной конфигурацией запуска. Есть только у Claude
    Code, Codex и OpenCode.
- Список моделей Traycer читает во время работы из CLI каждого агента. Фиксированного списка в документации нет
  [34].
- **Несколько аккаунтов на провайдера** («managed profiles») — у Claude Code, Codex, Grok и Antigravity [34][66].
  Несколько аккаунтов появились в Host 1.1.7 [78]. С 1.5.0 profiles синхронизируются между hosts [77]. Технически
  profile — это подмена папки конфигурации провайдера [119].
- **Ограничения по агентам:**
  - Amp и Cursor работают только в Full access; у Devin и Hermes Agent нет режима Supervised [29];
  - часть агентов не принимает сообщения во время хода [34];

- **Claude Code «Ultracode»** — переключатель в чате, который просит у Claude Code его multi-agent режим. Нужен Claude

## Функции

Описание — по документации, changelog и коду клиентов на 2026-11-13. «Ход» ниже — один ответ агента на одно
сообщение (turn).

### Основные объекты

| Объект | Что это |
|---|---|
| **Task** | Главный контейнер одной работы: агенты, панели, artifacts, терминалы, вкладки браузера, файлы, git diff и PR над одной или несколькими папками [25]. |
| **Workspace folder** | Репозиторий или папка, с которой работает Task [25]. |
| **Agent** | Долгоживущая session coding-агента в Task. Агенты образуют дерево «родитель — потомок» [29]. |
| **Artifact** | Долгоживущий документ в Task. Типы: Spec, Ticket, Story, Review, HTML, Canvas, File [47]. |
| **Worktree** | Каждая папка работает в режиме Local, New worktree или Existing worktree [39]. |
| **Host** | Процесс на машине, который запускает агентов [51]. |

- Внутри Task всё ещё называется «epic»: переменная окружения `TRAYCER_EPIC_ID`, namespace протокола `epic.*`, папка
  artifacts `~/.traycer/epics/<task-id>/` [76][136][47].
- В sidebar Task 10 панелей: Agents, Terminals, Browsers, Mobile simulators, Artifacts, Git Diff, Pull Requests, File
  Tree, Sharing, Comments [61].
- Рабочая область Task называется «canvas». Здесь это разделённые панели с вкладками, а не бесконечная доска
  [61][25].

### Встроенные skills: от spec до исполнения

Skill — набор инструкций, который агент выполняет по команде. Встроенные skills выбираются через `$` или `/` в поле
ввода [26][27]. Раньше эти шаги стояли за Epic Mode IDE-расширения [99][26].

| Группа | Skill | Что делает |
|---|---|---|
| Plan | `traycer-epic-brief` | Короткий brief инициативы |
| Plan | `traycer-core-flows` | Пути пользователя и решения по UX, после уточнений с человеком |
| Plan | `traycer-tech-plan` | Архитектурные решения, затем artifacts плана |
| Plan | `traycer-ticket-breakdown` | Artifacts-tickets с зависимостями в папке `tickets/`; правит их, пока человек не одобрит набор |
| Plan | `traycer-revise-requirements` | Проносит изменение требования через продуктовые и технические artifacts и tickets |
| Plan | `traycer-artifact-critique` | Artifact-review со списком пробелов, противоречий и рисков |
| Build | `traycer-execute` | Раздаёт tickets дочерним агентам (подробнее ниже) |
| Build | `traycer-implement` | Инструкция для дочернего агента одного ticket: когда спрашивать, когда решать самому, что сообщать |
| Build | `traycer-autobuild` | Долгая сборка почти без участия человека (подробнее ниже) |
| Review | `traycer-review` | Artifact-review с findings по приоритету |
| Review | `traycer-changeset-walkthrough` | Порядок review готовой работы и список того, что ещё не проверено |
| Decide | `traycer-debate` | Спор нескольких точек зрения, которые одобрил человек, с письменным итогом |
| Maintain | `traycer-housekeeping` | Аудит worktrees; удаляет только те, что одобрил человек |

Источники таблицы: [26][27].

- **Как работает `traycer-execute`** [26][27]:
  - раскладывает tickets по batches (пачкам) по зависимостям;
  - запускает одного дочернего агента на ticket; потомки видны под ним в дереве агентов;
  - после каждого batch проверяет работу против плана;
  - прошедшие tickets помечает Done; на мелкие проблемы заводит fix-up ticket (ticket на доделку);
  - при product drift (отходе от продуктового замысла) останавливает запуск и возвращает решение человеку;
  - ход работы видно в панели Artifacts с фильтром Type = Ticket.
- **Как работает `traycer-autobuild`** [26]:
  1. Агент пишет spec, rubric (критерии оценки) и способ проверить работу.
  2. Человек одобряет все три.
  3. Агент-builder и отдельный агент-evaluator повторяют каждый sprint, пока он не пройдёт проверку.
- **Как работает `traycer-debate`.** Человек одобряет точки зрения и модели. На выходе — artifact на каждый раунд и
  каждую точку зрения плюс итог [26]. В демо вендора агент-mediator собрал четыре точки зрения специалистов. Они
  спорили через сообщения между агентами, ссылались на исходный код и пересматривали свои утверждения. Запуск
  закончился общим выводом [186].
- **Это шаги, а не pipeline** [26]:
  - предлагаемый порядок: brief → core flows → tech plan → tickets → execute → review → walkthrough;
  - любой шаг можно пропустить; Traycer сам их не связывает, и пропущенный skill не ломает ход;
  - документация прямо говорит, что Traycer не запускает шаги автоматической цепочкой: агент пишет artifact, только
    когда работа этого требует, а надёжный способ — выбрать skill вручную.
- **Тексты skills в открытом репозитории нет.** Поиск по `traycer-debate` нашёл только страницу документации.
  Вероятно, тексты лежат внутри закрытого Host (не подтверждено). Поэтому как execute выбирает размер batch, что
  проверяет review и какой формат у rubric (не подтверждено).
- **Обратная связь через комментарии** [27][50]:
  - человек комментирует куски artifact;
  - агенты читают обсуждения из файлов `.comments/<thread-id>.md`;
  - агент закрывает обсуждение, меняя в файле строку `status:`;
  - ответить в обсуждение через этот файл агент не может.
- Свои skills можно добавлять (см. «Настройка провайдеров») [67].

### Панель Agents и поле ввода

- **Дерево агентов** [29][64]:
  - дочерние агенты висят под агентом, который их запустил; агентов можно перетаскивать, чтобы вложить;
  - фильтры: порядок, архивные, интерфейс, свои или чужие;
  - массовый выбор, архивирование и удаление;
  - по желанию — автоархивирование простаивающих агентов.
- **Режимы прав** [29][38]: Supervised, Auto-accept edits, Full access и Auto (experimental).
  - Новые разговоры по умолчанию открываются в Full access — с версии 1.1.2 [24][77].
  - Агенты, созданные из CLI или другим агентом, тоже стартуют в Full access, если создатель не передал
    `--permission-mode` [38].
  - Карточки approval: Approve, Deny, Approve all, Deny all [29].
- **Auto mode — автоматические approvals** [38][71]:
  - judge (модель-судья) одобряет рутинные команды;
  - рискованные, неясные и не уложившиеся по времени команды приходят человеку карточкой approval;
  - сам judge никогда не отказывает;
  - разделы правил: Environment, Always allow, Ask first, Never allow, Notes; правила хранятся в аккаунте;
  - файл репозитория `.traycer/auto-policy.md` может только добавлять ограничения;
  - правка файлов, которые определяют, что запустится потом, всегда спрашивает человека: git hooks, CI workflows,
    manifests, `.claude/settings.json` и подобные;
  - Activity log на каждом host хранит последние 200 решений judge;
  - кто платит за judge: hosted-модель Traycer — тратит credits Traycer даже в чате Claude Code; выбранная модель —
    счёт её провайдера; собственный classifier Claude Code — тогда правила Traycer не действуют;
  - judge на Copilot стоит примерно 60–350 premium requests в час.
- **Во время хода** [29][32][77]:
  - очередь сообщений: переставить, изменить, поставить на паузу;
  - steer (вставить сообщение в идущий ход) — ⌘Enter, у агентов, которые это умеют;
  - над полем ввода — панели «Files changed», «Active agents» и «Background»; Background показывает sub-agents,
    команды, monitors, wakes, инструменты MCP и scheduled jobs Claude Code;
  - агенты запускают долгие команды и получают уведомление, когда команда что-то напечатала или завершилась (1.2.0).
- **Другие действия с агентом** [29][30][31]:
  - fork разговора; fork может работать на другом агенте или на другом host;
  - `/btw` или `/side` — побочный вопрос в fork, не прерывая агента;
  - на вопросы агента есть кнопки «Cross Question» и «A/B Fork»; A/B Fork запускается в новых worktrees, которые
    несут незакоммиченные изменения человека;
  - «Continue as chat» — продолжить завершённый собственный subagent Claude Code или Codex как отдельный чат (1.5.0)
    [77];
  - правка или удаление прошлых сообщений, по желанию с откатом файлов;
  - отмена хода или всего, что изменил агент; artifacts откатываются тоже. Отмена работает только на host, который
    записал изменения [33].
- **Поле ввода (composer)** [29][30]:
  - упоминания через `@`: файлы, папки, worktrees, git diff против ветки или коммита, PR и issues GitHub (нужен
    `gh`), другие Tasks, агенты, терминалы, вкладки браузера, artifacts;
  - индикатор оставшегося контекста с разбивкой и действием «Compact conversation»;
  - вложения до 16 MiB каждое;
  - голосовой ввод с распознаванием на устройстве; ответы можно озвучить голосами устройства.
- **Импорт.** Существующие sessions Claude Code, Codex и OpenCode импортируются как Tasks [23]. Импорт sessions
  Claude Code и Codex появился в 1.3.0 [77].
- **«Traycer memories».** Тур первого запуска предлагает «Traycer memories», общие для всех Tasks. Страницы
  документации нет, поведение (не подтверждено) [23].

### Сообщения между агентами и Agent office

- **Что агент может сделать с другим агентом** [28][76]:
  - создать дочернего агента — в своей Task или в другой Task, которую человек может править, на любом своём host;
  - отправить сообщение — с ожиданием ответа или без;
  - получить список агентов и прочитать их transcripts;
  - переименовать, остановить, архивировать, сделать fork или перенастроить агента;
  - заявить роль (claim a role). Роли агентов по умолчанию выключены [64].
- Всё это доступно как команды `traycer agent create|send|transcript|inbox|configure|fork|stop` и `traycer monitor`
  [76].
- **Правила доставки** [28]:
  - сообщения получают только агенты самого пользователя;
  - на интерфейсе Terminal inbox (входящие) есть только у Claude Code; терминальные агенты Codex и OpenCode могут
    только отправлять, без ожидания ответа;
  - сообщения между hosts идут через облако; сообщение, которое никто не забрал за 24 часа, пропадает;
  - предел размера сообщения — 16 MB.
- **Agent selection guide** [65]. Markdown-файл подсказывает агентам, какой coding-агент, модель и effort выбирать при
  передаче работы. Общий файл — `~/.traycer/agent-selection-guide.md`. Уточнение на репозиторий —
  `.traycer/agent-selection-guide.md`.
- **Agent office** [28] — вид на всех агентов Task и сообщения между ними, по всем hosts:
  - вид «Office»: каждый агент нарисован человеком за столом; hosts — этажи, у агентов верхнего уровня — кабинеты;
    статусы — печатает, ждёт, нужен человек, сбой, в архиве;
  - вид «Graph»: агенты — узлы, сообщения — рёбра;
  - внизу timeline, который проигрывает прошедшее: Play timeline, скорость, Follow live.
- Вид на сообщения агентов (Communication Graph) появился в 1.2.0, вид «office» — в 1.3.0 [77].

### Worktrees

- **Создание** [39][41]:
  - для каждой папки — New worktree: от текущей ветки, от рабочей копии с незакоммиченными изменениями, от другой
    ветки или от удалённой ветки;
  - worktrees лежат в `~/.traycer/worktrees/<owner>__<repo>/<slug>`;
  - префикс веток по умолчанию — `traycer/` [39][64].
- **Setup и teardown** [39][40][41]:
  - скрипты setup и teardown на репозиторий лежат в `.traycer/environment.json`; файл коммитится в репозиторий, в
    нём же можно задать префикс веток;
  - карточка setup показывает Creating, Setting up, Ready или Failed, с кнопкой retry.
- **Worktrees, которые создают сами агенты** [42]: настройка Allow (по умолчанию), Ask first или Never. Она не мешает
  собственным инструментам worktree у coding-агента и прямому `git worktree add`.
- **Уборка** [41][42][43]:
  - «Sweep» удаляет worktrees Task после шага review и оставляет ветки;
  - автоматическая уборка выключена по умолчанию; порог неактивности по умолчанию — 30 дней;
  - worktree удаляется, только если доказано одно из состояний: Landed (работа слита), At base commit (на базовом
    коммите) или Unreferenced (на него ничего не ссылается) и PR нет.

### Review, Git Diff и pull requests

- **Git Diff** [45][46][77]:
  - diff в две колонки или единым списком, правка прямо в diff, diff submodules;
  - stage, commit и discard панель не делает;
  - сравнение на сайте вендора признаёт: комментариев к строкам diff нет [10].
- **Панель Pull Requests** [44]:
  - читает PR через `gh` на host;
  - показывает только PR из веток, над которыми работали чаты этой Task. Это не общий inbox по проектам;
  - в строке PR: сводка checks («3 passed / 1 failing / 2 running»), решение review, число комментариев,
    base ← head;
  - stacked PRs (PR, построенные друг на друге) сгруппированы; они появились в 1.5.2 [77]; фильтр Open, Merged,
    Closed, All;
  - экран PR с вкладками: Overview (что мешает merge), Feedback, Checks, Files, Commits;
  - «Fix in chat» и «Quote» кладут упавший check или комментарий review в поле ввода агента, который делал работу.
    Само ничего не отправляется;
  - строки GitHub Enterprise помечены «Not live».
- Агенты сами открывают PR через `gh` [44][30].

### Artifacts

- **Структура** [47]:
  - artifacts образуют дерево;
  - у Tickets и Stories есть статус: Todo, In Progress или Done; в файле это 0, 1 или 2;
  - specs и reviews — общий контекст для агентов;
  - фильтры: тип, статус, прочитано или нет; отметки о прочтении хранятся на каждом устройстве отдельно;
  - на диске это файлы `index.md` с frontmatter (`kind`, `status`) в `~/.traycer/epics/<task-id>/artifacts/`; агент
    создаёт artifact, создавая там новую папку.
- **История версий** (1.4.0): версии подписаны автором; можно вернуть старую версию и восстановить удалённые
  artifacts [77].
- **HTML artifacts** [49]:
  - интерактивные страницы с версиями («v1 of 3»);
  - комментарии к элементам страницы и «Send to chat»;
  - скачивание ZIP до 64 MB;
  - MCP-серверы тоже могут показывать интерактивные приложения прямо в чате.
- **Canvas artifacts** (1.5.2) [48]:
  - масштабируемая доска из HTML-экранов;
  - «Play» прокликивает пользовательский flow;
  - панель элемента: Design, Code (CSS) и Tweaks;
  - заметки, фигуры, рисование пером и прикреплённые комментарии.
- **Другие форматы:** диаграммы Mermaid, wireframes, файлы (PDF, Word, картинки). Экспорт в Markdown или PDF
  [21][77].

### Длинные запуски и работа без присмотра

Названного режима autopilot или waves в документации нет. Есть отдельные части.

- **Model routing — переключение при лимите или ошибке провайдера** [36][37]:
  - работает только для агентов Chat, никогда для Terminal;
  - по документации включено по умолчанию [36][37]. Issue от 2026-10-13 описывает его как настройку на каждое
    устройство, выключенную по умолчанию [176]. Источники расходятся. Возможно, поведение поменялось между октябрём и
    ноябрём (не подтверждено);
  - порядок шагов: другой аккаунт того же провайдера → равноценная модель другого провайдера → ожидание сброса
    лимита → уведомление человеку;
  - перед каждым переключением идёт отсчёт 15 секунд, его можно отменить; в настройке — от 10 до 15 секунд [37][36];
  - самое долгое ожидание по умолчанию — 6 часов, выбор — от 1 часа до 7 дней;
  - возврат на исходный аккаунт по умолчанию — «Ask me»;
  - в отдельном чате «Wait it out here» оставляет его на своём аккаунте и ждёт;
  - переключение запускает новую session агента из истории чата.
- **Чтобы работа не останавливалась:**
  - «Prevent sleep while running» не даёт машине уснуть, пока агенты работают; выключено по умолчанию [64];
  - Host работает и после выхода из приложения [64].
- **Запуск по расписанию** — `traycer task create … --idempotency-key` плюс свой cron. В документации есть рецепт
  «Start a Task Every Night» [76]. Вендор сам пишет, что расписание — это CLI и cron пользователя [10].
- **Уведомления** [57][58]:
  - уровни: Needs action, Failure, Done, Info (Info выключен по умолчанию);
  - куда: центр уведомлений, отметки на вкладках, уведомления ОС, push на телефон, звуки;
  - hooks на каждом host: запустить скрипт (JSON на stdin, timeout 10 секунд, без повторов) или сделать POST на URL
    с заголовками из переменных окружения;
  - события для hooks: `approval.requested`, `interview.requested`, `browser.human.needed`, `agent.stopped`,
    `agent.stalled`, `workspace.operation.failed`, `host.operation.finished` [58].
- **Home tab** (выключен по умолчанию) [62]: списки «Needs you» и «Running» по всем Tasks, с кнопками Stop и Stop
  all. Появился в 1.4.0 [77].

### Usage, лимиты и стоимость

- **Лимиты подписок** [36]:
  - в status bar — одно значение на провайдера: процент использования и время сброса;
  - ⌘⇧U открывает popover с лимитами всех аккаунтов;
  - Claude Code показывает лимиты session, weekly, по моделям и extra usage;
  - Codex показывает лимиты, credits и ручные сбросы («Use reset»); использованный сброс нельзя вернуть;
  - Cursor, Grok, OpenCode Go, OpenRouter, Hugging Face, Kilo, Kimi и Antigravity показывают свои виды лимитов;
  - баннер предупреждает, когда у аккаунта кончается лимит, и предлагает «Switch to <account>» — по желанию и для
    других чатов Task.
- **Стоимость** [36][77][70]:
  - оценка стоимости и токенов на Task (за 7, 30 или 90 дней, с экспортом картинкой), на чат и по аккаунту;
  - dashboards расхода по агентам, моделям и чатам (1.2.0); dashboard аккаунта фильтруется по host.
- **Не найдено в документации:** планирование запуска заранее под лимиты подписки и режим экономии. Расходом
  управляют только effort на ход и fast mode [36].

### Несколько машин (hosts)

- **Remote hosts** [51][52][53]:
  - любая машина, на которой выполнили `traycer host ensure`, подключается к аккаунту;
  - выбор host задаёт, где пойдёт новая работа;
  - если активный host упал, Traycer переходит на рабочий host и возвращается примерно через 20 секунд после того,
    как выбранный host снова доступен;
  - каждая вкладка привязана к своему host на всё время жизни; чтобы перенести работу, её клонируют [90];
  - если host offline, агент Chat открывается только для чтения из облачной копии; его можно клонировать на другой
    host [56]. Агентов Terminal и обычные терминалы перенести нельзя [51];
  - remote hosts бесплатны на всех планах с 1.3.0 [71][77].
- **Port forwarding** [54][77]:
  - агенты пробрасывают порт dev server, чтобы `localhost:5173` с одной машины открывался на другой;
  - это умеют только агенты Chat, порты 1024–65535;
  - трафик идёт по соединению, которое hosts уже держат;
  - агенты также запускают команды на других машинах пользователя и копируют файлы между ними (1.4.0).
- **Team machines.** Машину можно отдать команде, любой участник может её забрать. Install token позволяет настроить
  машину, на которую никто не входит. Токен одноразовый и живёт час [76][103].

### Встроенные инструменты

- **Browser** [59]:
  - вкладки открываются панелями;
  - один общий профиль с входами на сайты («website sessions»); входы можно импортировать из другого браузера или
    файла cookies;
  - private sessions держат свои cookies;
  - агенты управляют тем же браузером; в строке видно «Driven by» и имя агента;
  - рискованные действия (публичные посты, платежи, удаления) требуют подтверждения человека. Агенты Terminal
    спросить не могут, поэтому им такие действия запрещены;
  - «Annotate page» отправляет отмеченный кусок страницы в чат;
  - пресеты устройств и DevTools;
  - вкладки на другой машине транслируются в панель; на телефоне и в web — только для просмотра.
- **Mobile simulators** (1.5.2) [60]:
  - симуляторы iOS и эмуляторы Android внутри приложения; iOS — только на Mac с Apple silicon;
  - агенты тестируют на них приложения; если устройство занято, агент может поднять отдельную копию;
  - устройства выключаются после простоя;
  - «Save a screenshot» сохраняет снимок экрана устройства.
- **Терминалы, файлы, процессы:**
  - обычные терминалы живут на Host, агенты читают их вывод [76][77];
  - панель File Tree [61];
  - resource monitor показывает CPU и память на каждого агента и процесс, с кнопками stop и kill [55].

### Навигация и интерфейс

- Command palette (⌘K) и поиск по всем чатам на текущей машине (⌘⇧F) [62].
- Поиск по regex в artifacts или коде [62].
- Back и Forward, повторное открытие закрытых вкладок, несколько окон, две вкладки рядом [62][61].
- History: поиск, фильтры, labels, закрепление. Прошлые Tasks ищутся по ветке, папке или номеру PR [63][77].
- Темы (Dracula, Nord и другие), импорт темы VS Code, пресеты раскладки, переназначение клавиш, deep links
  `traycer://`, иконка в system tray [77].
- Публичная status page проверяет каждого провайдера раз в 60 секунд [13][77].

### Настройка провайдеров: MCP, plugins, skills

- У каждого провайдера вкладки: CLI & Args (закрепление версии, аргументы для Terminal), Env, Permissions, MCP,
  Plugins, Skills [66].
- **MCP servers** [68]: глобально или на workspace; удалённые серверы по HTTP или SSE с OAuth, заголовками или
  токеном из переменной окружения.
- **Plugins** [66]: ставятся из npm, по пути на диске, по git URL или как `plugin@marketplace`.
- **Skills** [67]:
  - импорт из `npx skills`, `owner/repo`, git URL или папки; можно написать свой;
  - область действия: только этот провайдер; Personal — все провайдеры на всех hosts пользователя; team — hosts всех
    участников команды;
  - Traycer читает и папку `~/.agents/skills`.
- «Allow native subagents» можно выключить. Тогда агенты передают работу через агентов Traycer, а не через
  собственных subagents провайдера [66].

## Принципы и подходы

### Главная проблема — сохранить замысел человека

- Страница About: контекст теряется между планированием и исполнением. Требования остаются в головах людей. Агенты
  заполняют пробелы в prompt и уходят от исходного замысла [7].
- Разделение труда по Traycer: люди отвечают за замысел, суждение и направление; AI структурирует, расширяет и
  исполняет [7].
- По описанию страницы, инвесторы верят, что разработка будет строиться от замысла («intent-driven»). Tasks подаются
  как место, где невысказанное продуктовое мышление становится общей структурой [7].
- Документация Epic Mode объясняет уход от замысла так же: агенты не стремятся ошибаться, они заполняют пробелы
  [82].
- Пост октября 2025 задал исходный тезис [15]:
  - инструменты уже хорошо пишут код; слабое место — решения, которые принимаются до кода;
  - Traycer — слой планирования и проверки, который добавляет строгость spec и архитектуры до написания кода;
  - пост сравнивает разработку ПО со строительством города: нужны генеральный план и инспекции;
  - пост противопоставлен «vibe coding»;
  - человек всё время сохраняет контроль.

### Spec-driven development по версии Traycer (пост 2026-01-07) [17]

- **Несколько маленьких specs вместо одного большого PRD.** Большая spec упаковывает слишком много решений в один
  документ. Epic — набор маленьких specs: PRD, tech plan, заметки о граничных случаях, wireframes.
- **Структура без жёсткости.** Workflows состоят из команд. Человек может пропустить шаг, разветвиться или
  углубиться. AI подсказывает следующую команду.
- **Выяснять, а не генерировать.** AI задаёт точные вопросы, чтобы неясность превратилась в явные решения.
- **Маленькие исполнимые tickets** — против ошибки «сделать всё сразу».
- **Исполнение любым агентом.** План пишется в Traycer, исполнение — в любом агенте: Cursor, Claude Code, Windsurf
  или свои CLI.
- **Постоянная проверка** против записанного замысла. Она встроена в обычный workflow, а не добавлена в конце.

### Orchestrator, а не исполнитель: внешний цикл (посты 2025-11-26 и 2026-01-29)

- **Внешний и внутренний цикл.** Большинство AI-инструментов работают во внутреннем цикле: сгенерировать, поправить,
  протестировать. Traycer ставит себя во внешний цикл: спланировать, разбить, собрать контекст, проверить. Внутреннюю
  работу делают агенты, которые пишут код [16].
- **Ralph и Bart** [19]:
  - «Ralph loop» — цикл, который упорно повторяет попытки. Память он держит на диске и на каждой итерации заново
    читает состояние. Он подходит для линейной проверяемой работы, но стратегии в нём нет;
  - «Bart» (выпущен как Smart YOLO 2026-02-05) следит за всей системой и перестраивает граф задач: делит, сливает и
    переставляет tickets, обновляет tech plan;
  - Bart проверяет работу постоянно;
  - когда реализация расходится со spec, Bart останавливается и предлагает человеку варианты, а не придумывает
    решение сам. Пост называет это тем, что делает ночные запуски безопасными.
- Документация Smart YOLO говорит то же [83]: он может переписать specs и tickets во время исполнения, запускает
  независимые tickets параллельно и встаёт на паузу при сбое исполнения, пока человек не продолжит.
- Видео о запуске Smart Orchestrator: простые циклы повторов ломаются; orchestrator видит задачу целиком и раздаёт
  работу sub-agents; важнее всего это для ночных запусков [189].

### Набор моделей в 2025, свои агенты пользователя в 2026

- **Серверная схема 2025 года** — набор моделей, по одной на каждую работу [16]:
  - Claude Sonnet 4.5 — планирование и разбиение;
  - GPT-5.1 — проверка, критика и отладка;
  - Grok-4.1-fast — параллельные «scouts» для сбора контекста;
  - GPT-5.1-mini — сводки;
  - parallel.ai — поиск в web.
- **Принципы этой схемы** [16]: своя модель под каждую работу; «думать» отдельно от «собирать» — scouts собирают, но
  не толкуют; раздавать работу параллельно; поддерживать любого агента-исполнителя.
- **Desktop меняет модель оплаты.** Пользователи приносят агентов и подписки, за которые уже платят: всего 22
  агента и провайдера моделей. Собственная inference Traycer — по желанию [1][71][89].
- **Выбор модели переехал в редактируемый файл** — agent selection guide в Markdown [65].
- **Общий контекст между провайдерами.** README обещает переключать модели внутри одного агента так, что контекст
  сохраняется [89].
- Использует ли Host Desktop фиксированный набор моделей (не подтверждено). Материалы о наборе моделей и Smart YOLO
  описывают выведенное расширение [16][19].

### Software factory (пост 2026-10-26) [20]

- **Словарь взят у других:** AFK agent, software factory и dark factory — по определениям Matt Pocock; пирамида
  доверия — у Lauren Tan; «factory engineering» — у Zach Lloyd и Ben Holmes.
- **Рабочее определение Traycer.** Работа приходит по своим триггерам. Агенты доводят её до доказательства. Решения
  принимают люди. Система улучшается с каждым запуском. В отличие от dark factory (фабрики совсем без людей), люди
  участвуют в процессе.
- **Главный риск — comprehension debt** (код, которого никто не понимает). Опасен не плохой код, а больше кода, чем
  кто-либо понимает. Поэтому люди должны проверять доказательства, а не diff.
- **Правило доказательства.** Test доказывает только сам test; продукт доказывает запись работы продукта. Исправлению
  нужен test, который падает на старом коде. Баг сначала воспроизводят в настоящей сборке. Свой код sync Traycer
  проверяет на TLA+ (язык формальных спецификаций с автоматической проверкой моделей).
- **Сначала план.** Планирование в форме интервью, PRD, маленькие tickets, вертикальные срезы. По посту, тридцать
  минут плана экономят часы review.
- **Начинать с малого.** Один триггер, одна работа, потом масштаб.
- **Sandbox и отдельное хранение ключей:**
  - у агентов только токены на чтение;
  - отдельный gateway держит ключи на публикацию и применяет правила, дневные бюджеты и тихие часы;
  - ввод от пользователей, Slack и Sentry — это данные, а не инструкции;
  - LLM-фильтр сообщений молча задержал 40 сообщений, и команда заменила его простыми правилами.
- **Сначала review агентами.** Несколько reviewer-ов-специалистов плюс «blind» reviewer, который видит diff и задачу,
  но не видит рассуждений агента-автора. Изменения распределяются по уровням риска.
- **Агент, открывший PR, владеет им до merge.** Проверка раз в 15 минут напоминает о застрявших PR. Если человек
  пересылает сообщения между двумя агентами, это считается багом.
- **Самоулучшение.** Factory улучшает собственные jobs: 43 из первых 332 слитых PR factory были об этом. Инструкции
  jobs лежат как skills в репозитории, поэтому изменения factory проходят обычный review PR.
- **Измерять то, что выпущено, а не потраченные токены.**
- **За людьми остаются** продуктовые решения, тексты, auth, биллинг, релизы, публичные ответы и всё необратимое.
  Каждое такое решение приходит человеку вместе с рекомендацией.
- **Цифры команды из четырёх человек за 11 дней:** 332 из 675 слитых PR (49%) открыла factory; медиана от открытия до
  merge — 1.6 часа [20].

### Инженерные правила в открытом репозитории

Эти правила AGENTS.md задаёт агентам, которые работают над самим Traycer [90].

- **Ни один test не может требовать retry.** Это решение владельца от 2026-11-03 [90].
- **PR команды в `main` намеренно идут без CI**, кроме сканирования безопасности CodeQL. Тестируется merge в `main`.
  `main` чинят следующими изменениями. Пропущенный набор tests наследует свой последний зелёный результат [90].
- **Модели TLA+ запускаются в CI**, например модель прокрутки transcript чата [106]. В `clients/gui-app/formal/`
  лежат шесть моделей TLA+ о прокрутке чата [136]. Пост о factory говорит о TLA+ для кода sync [20].
- **Тексты для пользователя** должны говорить, что функция делает и чего она стоит человеку, и не рассказывать, как
  она устроена [90].
- **Таблица повторяющихся дефектов**, которые убирает ежедневный проход. В репозитории она помечена словом «slop»
  [90].

### Ключевые понятия

- **Task** — главный контейнер одной работы [25].
- **Workspace folder** — репозиторий или папка, с которой работает Task [25].
- **Canvas tab** — рабочая поверхность, открытая из панели. Это не бесконечное полотно [25].
- **Canvas artifact** — масштабируемая доска HTML-экранов с комментариями и Send to chat [48].
- **Artifacts** — specs, tickets, stories, reviews, HTML-страницы, canvas-доски и файлы. Хранятся с историей версий
  и живут дольше любого разговора [77][26].
- **Built-in skills** — встроенные skills планирования, сборки, review, решения и обслуживания [26].
- **Coding agent, или harness** — агент, на котором работает агент Traycer, через интерфейс Chat или Terminal
  [28][65].
- **Agent-to-agent** — родитель и потомки; любой агент может сослаться на любого. Три отдельные возможности: ссылка,
  чтение transcript и доставка сообщений. У агентов есть inbox [28].
- **Agent roles** — агент заявляет роль, чтобы другие видели, кто за что отвечает [28].
- **Host** — процесс на машине: агенты, терминалы, доступ к файлам. Есть активный host с автоматическим переходом,
  remote hosts и port forwarding [51][77].
- **Режимы прав** — Supervised, Auto-accept edits, Auto (experimental) и Full access, который стоит по умолчанию
  [38].
- **Model routing** — цепочка шагов при лимите или ошибке провайдера [37][36].
- **Другие термины:** Home tab; Sweep — уборка worktrees; side chats — побочные чаты; Interviews — структурированные
  вопросы агента; план Sync; Traycer Inference; Traycer Credits [77][71].
- **Термины расширения:** режимы Plan, Phases, Review и Epic; YOLO и Smart YOLO; Executions; workflows вроде
  Traycer Agile Workflow; model profiles; handoff templates [88][83][82].
- **Термины factory и roadmap:** jobs, triggers, chaining, approvals, shared memory; Tracy — агент factory [4]. В коде
  клиента есть environments, «main bot» и team computers [76][103][104].

### Чем подход отличается

- **Заявленное преимущество** [1][10]:
  - бесплатно и MIT open source, на трёх desktop ОС;
  - 22 агента в одной Task;
  - общие specs и tickets, которые читает каждый агент;
  - сообщения между агентами через Tasks и машины;
  - remote hosts и мобильные приложения в бесплатном плане;
  - sharing Task на любом плане.
- **Единица работы.** Страница сравнения называет единицей Traycer Task: несколько агентов и общий план, по которому
  они работают [10].
- **Выбранный круг конкурентов** (страницы проверены 2026-10-26 — 2026-11-07) [9][11]:
  - Conductor, Orca, T3 Code, Paradev (бывший Superset), Nimbalyst, Emdash, Parallel Code, cmux и Claude Squad;
  - встроенные варианты: Claude Code, Codex в desktop-приложении ChatGPT, окно Agents у Cursor;
  - Vibe Kanban отмечен как закрывающийся.
- **Traycer прямо обращается к пользователям Conductor** [10]. Traycer пишет, что Conductor Cloud закрывается 2026-11-20 и что
  команда Conductor ушла в Meta. Это утверждения Traycer; для Conductor это вторичный источник.
- **Признанные пробелы** [11][10]:
  - нет комментариев к строкам diff; в review и merge, по словам самого Traycer, выигрывает Conductor;
  - нет встроенного scheduler — только CLI и свой cron;
  - нет SSO, SAML и SCIM;
  - cloud sandboxes — платное дополнение.
- **«Open source» с оговоркой.** FAQ сайта называет Traycer полностью open source [1]. AGENTS.md репозитория пишет,
  что Host и облачных backend-ов в репозитории нет [90]. README CLI: Host поставляется отдельным подписанным
  бинарником [92]. Открыты только клиенты, CLI и протокол.

  - отправка отчёта о проблеме — `clients/shared/support/issue-reporter.ts` [107];
  - интерфейс ботов Tracy — `clients/gui-app/src/components/bots` [105].

### Процессы и транспорт

- **Три программы с разными задачами.**
  - Desktop никогда не запускает Host сам. Он читает адрес WebSocket Host из `~/.traycer/host/pid.json`. Дальше
    `gui-app` говорит с HTTP/WebSocket Host на localhost напрямую [91].
  - Источники описывают установку Host с разных сторон. Документация первого запуска: приложение само скачивает
    и ставит Host [23]. Заметки о внутреннем устройстве: процесс Host запускает служба ОС, которую ставит и
    обновляет CLI [69][91].
  - CLI ставит, обновляет и держит Host запущенным как службу ОС [69]. На macOS это login item, которым управляет
    Desktop. На Linux — systemd user service с включённым lingering (служба живёт без входа пользователя). На
    Windows — scheduled task пользователя, который стартует при входе.
  - Перед установкой CLI проверяет бинарники Host по SHA-256 и подписи minisign [79].
  - С CLI 1.2.0 упавший Host перезапускается. С 1.5.3 CLI записывает, как закончил работу прошлый Host: нехватка
    памяти, сбой, остановка или чистый выход [79].
- **Host владеет всем, что привязано к машине** [51]: доступ к папкам и превью файлов, git diff, терминалы, агенты и
  настройки провайдеров, sessions встроенного браузера, проброс портов.
- **Протокол большой.** В `protocol/src` около 600 имён RPC-методов (подсчёт через grep). Крупнейшие namespaces:
  `epic` — 85, `environment` — 73, `host` — 67, `providers` — 57, `agent` — 35, `bot` — 33 [136]. У каждого метода
  своя версия {major, minor}, о ней стороны договариваются при handshake. Версии хранимых записей — отдельная
  система [95].
- **Транспортов только два** [128]: loopback (`local-ws`) и облачный relay. Прямого пути по локальной сети нет.
- **Как работает relay-сессия** [127][128]:
  - один долгоживущий socket к relay несёт канал Noise NK (`Noise_NK_25519_AESGCM_SHA256`) со сквозным
    шифрованием; RPC-вызовы и потоки идут внутри него вместе;
  - потоки файлов и ассетов идут через отдельную очередь BULK, которую ограничивает flow control на credits (квоты
    передачи, не деньги);
  - после переподключения все потоки подписываются заново;
  - если сторона host ненадолго пропала, session ставится на паузу и держит кадры, а не падает.
- **Hosts и переход между ними.**
  - Вкладка интерфейса привязана к одному host на всё время жизни. Чтобы перенести работу, её клонируют; ничего не
    мигрирует [90].
  - Агентов Chat можно клонировать на другой host. Агентов Terminal и обычные терминалы — нельзя [51].
  - Если активный host не отвечает, приложение переходит на рабочий host. Назад оно возвращается, когда выбранный
    host доступен около 20 секунд [51].
- **Remote и team machines** работают на тех же CLI и Host [52]. Install token для team machine одноразовый и живёт
  час [76]. В коде три вида host: Computer, Sandbox и Team machine [135].

### Цикл агента

Своего агентного цикла у Traycer нет. Host управляет CLI и SDK провайдеров.

- **Два интерфейса** [35][34]. Chat — Host ведёт провайдера из кода. Terminal — собственный TUI провайдера в PTY
  (псевдотерминале); только Claude Code, Codex и OpenCode.
- **Адаптеры провайдеров** (по комментариям схем runtime) [119][120][121]:

| Провайдер | Как Host с ним говорит |
|---|---|
| Claude | Типы Agent SDK. Размер контекста — из `getContextUsage().rawMaxTokens`, стоимость — из `SDKResultSuccess.total_cost_usd` |
| Codex | `codex app-server`; id thread берётся из события `thread/started` |
| Grok, Qwen, Kiro, Kimi | ACP (Agent Client Protocol) через stdio: `grok agent stdio`, `qwen --acp`, `kiro-cli acp`, `kimi acp` |
| Droid | `@factory/droid-sdk` |
| Traycer Inference | Сервер OpenCode на пользователя, направленный на облачный route `/inference` |

- **Что несёт запрос на запуск** [119]: harness, модель, режим прав, system prompt, вызовы skills, контекст аккаунта и
  profile. Profile превращается в подмену папки конфигурации провайдера.
- **Один поток событий для всех harness** [119]: ход, текст, рассуждения, вызов инструмента, команда, изменение
  файла, approval, interview (структурированные вопросы), план, todo, subagent, compaction, usage, steer, workflow,
  создание или продолжение session, уведомления провайдера, операции с artifacts.
- **Доставка prompt** [122][32]:
  - первое сообщение проходит состояния pending → preparing → started; если его отозвали, оно возвращается в поле
    ввода;
  - «started» — точка фиксации: после неё сбой — обычная ошибка хода;
  - сообщения, набранные во время хода, встают в очередь и уходят после хода;
  - steer вставляет сообщение в идущий ход;
  - после неудачного хода очередь держит следующее сообщение, пока человек не продолжит.
- **Агенты Terminal: hooks и фоновый monitor.** Traycer ставит свой plugin для Claude Code [112][113][111]:
  - hooks вызывают `traycer agent activity-from-hook` и соседние команды на SessionStart, UserPromptSubmit, Stop и на
    Notification `idle_prompt`;
  - **Stop hook** сообщает фоновые задачи Claude (кроме monitor самого Traycer) и crons session. Так Host понимает,
    значит ли «ход закончен» настоящий простой;
  - **SessionStart hook** считает crons в `<cwd>/.claude/scheduled_tasks.json`;
  - **UserPromptSubmit hook** возвращает роли агентов Task как `hookSpecificOutput.additionalContext`;
  - вызовы hooks несут spawn token и id хода провайдера; CLI заново синхронизирует id session, когда Claude выдаёт
    новый после `/clear` или отката;
  - файл plugin `monitors.json` запускает `traycer monitor` как долгую фоновую команду. Monitor печатает входящие
    сообщения агентов в stdout. Claude Code показывает модели вывод фоновых команд — так модель видит сообщения.
    Monitor подтверждает каждую доставку и меняет свои учётные данные.
- Traycer добавляет агентам Terminal свой контекст: system prompt Traycer, id Task, инструкции по artifacts, skills и
  инструменты общения между агентами [35].
- **Состояния жизни агента** [114][113]:
  - агент работает (running), спит (sleeping) или остановлен (stopped); у сна четыре причины — reaped (снят за
    простой), остановлен человеком, перезапуск, выход процесса;
  - PTY простаивающего агента Terminal снимается; после любого выхода PTY работу можно продолжить;
  - Host снимает агента, только когда есть явные признаки простоя.
- **Замеры пользователя** (вторичный источник) [175]: чат выгружался примерно через 15 секунд после ухода зрителя;
  агент Terminal снимался примерно через 10 минут после отключения; за 5 дней — 91 выгрузка и 302 снятия. Maintainer
  ответил, что цифры совпадают с замыслом: агент спит, только когда ничего не выполняется; выгрузка чата ничего не
  теряет; снятый агент Terminal запускает новый процесс на следующее сообщение [175].

### Планирование и раздача задач

- **Artifacts — это файлы** [47][50]: файл с frontmatter в `~/.traycer/epics/<task-id>/artifacts/`; статус tickets
  и stories хранится как 0, 1 или 2 (Todo, In Progress, Done); комментарии копируются в `.comments/<thread-id>.md`.
  Типы HTML и canvas появились в 1.5.2 [77].
- **Раздача — skill `traycer-execute`**, который выполняет агент, а не фиксированный pipeline [26]. Его шаги описаны
  в разделе «Функции». `traycer-implement` — инструкция для дочернего агента [26].
- Тексты skills не в открытом репозитории. Как execute выбирает размер batch, что проверяет review и какой формат у
  rubric (не подтверждено).
- **Как было в расширении.** Orchestrator внешнего цикла «Bart» следил за системой: делил, сливал и переставлял
  tickets, проверял работу и передавал человеку неясные места [19]. Находки проверки шли агентам по уровню
  серьёзности [84]. Схема 2025 года брала Sonnet 4.5 для плана и GPT-5.1 для проверки [16].

### Параллельность и координация

- **Создание агентов и управление ими** [28][76]:
  - любой агент может создать дочерних; дерево хранит только происхождение агента, а сослаться можно на любого
    агента Task;
  - CLI есть в PATH каждого агента, с переменными `TRAYCER_EPIC_ID` и `TRAYCER_AGENT_ID`;
  - подкоманды: create, send (`--expect-reply`), inbox, transcript, stop (`--cascade`), fork, configure, role.
- **Сообщения** [115][28][76]:
  - каждый агент, который может писать другим, получает от Host одинаковый каталог MCP-инструментов `traycer_a2a`;
  - входящее сообщение обрамляется названием, id и harness отправителя и инструкцией ответить с id ответа;
  - три отдельные возможности: reference (ссылка) — всегда; чтение transcript — для своих агентов на любом своём
    host; receive (получение) — нужен inbox;
  - на Chat все агенты отправляют и получают; на Terminal inbox есть только у Claude Code;
  - агенты Terminal Codex и OpenCode отправляют, но не получают, и другие агенты не могут их создать; их CLI только
    для чтения.
- **Устройство брокера** (по комментариям протокола) [110]:
  - у каждого получателя своя очередь inbox; в протоколе 1.0 она жила только в RAM;
  - запасной механизм — проверка по неактивности. Она шлёт ждущему отправителю уведомление с причиной: turn-ended, exited,
    quiet (watchdog, который только предупреждает), user-stopped, errored (например, лимит), awaiting-input,
    receiver-cancelled;
  - с протокола 1.2 устойчивые id событий и `agent.inbox.ack` дают доставку at-least-once (хотя бы один раз);
  - старые monitors получают подтверждение на стороне сервера, поэтому для них доставка at-most-once (не больше
    одного раза);
  - протокол 1.3 записывает, кто начал остановку агента.
- **Сообщения между hosts** идут через облако [28]. «Queued» значит только, что облако приняло сообщение. Сообщение,
  которое никто не забрал, пропадает через 24 часа. Сообщения больше 16 MB отклоняются.
- **Роли** [117]. Агент заявляет роль в Task, чтобы другие не дублировали работу. Заявка не даёт прав. Рассылка
  смены ролей — best effort: простаивающие агенты читают роли на следующем prompt; сбой рассылки не отменяет заявку.
- **Режим прав потомков.** Agent selection guide велит родителю ставить потомкам `full_access`, если guide
  пользователя не говорит иначе, и не выбирать более строгий режим самому [116]. Агенты из CLI тоже по умолчанию в
  `full_access` [76][38].
- **Граф общения** [118]. Каждая точка захвата добавляет строку в SQLite-лог событий на Host. Autoincrement id служит
  курсором клиента. Интерфейс получает каждое событие ровно один раз и без пропусков относительно курсора.
- Пороги watchdog «quiet» и события `agent.stalled` (не подтверждено).

### Изоляция

- **Контейнера или VM для локальных запусков нет.** Изоляция — git worktrees. Режимы: Local (сама папка), New
  worktree (новая ветка), Existing worktree (worktree, который уже есть на диске) [39].
- **Скрипты из `.traycer/environment.json`** [40]: у setup нет предела по времени, но он отменяется после 5 минут без
  вывода, и агент продолжает работу; teardown получает до 60 секунд, потом worktree удаляется всё равно.
- **Worktrees, которые создают агенты** [42]: настройка на host — Allow, Ask first, Never. Она действует и на
  `traycer worktree create` из shell агента. При Ask first эта команда отклоняется, потому что вызов CLI не может
  спросить человека.
- **Уборка** [132][42][43]:
  - один общий классификатор раскладывает worktrees по состояниям: в работе, на review, осиротел, слит, на базовом
    коммите, без ссылок;
  - этот классификатор используют интерфейс, CLI, Host и skill housekeeping;
  - для удаления без человека нужно «зелёное» состояние, но одного его мало;
  - автоматическая уборка выключена по умолчанию; порог — 30 дней неактивности; один возраст никогда не даёт права
    удалить worktree;
  - история уборки хранится до 90 дней или до 200 запусков;
  - ручной Sweep просит подтверждения.
- **Cloud sandboxes есть только в протоколе** [133][135]:
  - вид host «Sandbox»;
  - egress broker (посредник для исходящего трафика): sandbox не держит учётных данных пользователя и просит секреты
    через инструмент `traycer_secret_request`;
  - биллинг в millicredits.
  - Выпущено ли это (не подтверждено).

### Состояние и память

- **На диске в `~/.traycer/`:** учётные данные CLI, pid и log Host, worktrees, папки artifacts по Tasks
  [76][91][39][47].
- **Записи Task** [126][77]:
  - запись Yjs (библиотека для совместной правки данных) хранит чаты, artifacts и агентов Terminal;
  - карту чатов из неё постепенно выносят; главное состояние чата теперь в строках chat registry (`chat.db`) и
    записях chat-sync;
  - в 1.4.0 хранение перестроили на строки с историей версий; в 1.2.0 добавили sync чатов в облако.
- **Checkpoints** [125][33]:
  - каждый ход пишет manifest с hash каждого файла до и после хода;
  - отклонённые, бинарные и не перехваченные правки отменить нельзя. Отсюда следует, что Host перехватывает правки
    файлов;
  - отмена работает только на host, который записал изменения.
- **Transcripts агентов Terminal** читаются из истории session самого агента, а не из прокрутки терминала. Поэтому
  они переживают закрытие терминала [28].
- **Отдельного долговременного хранилища памяти не найдено.** Агенты делят память через artifacts и через transcripts
  друг друга [26][28]. Что делают «Traycer memories» (не подтверждено) [23].
- **Цепочка sessions** [124]: у каждого чата есть активная цепочка — harness, id session, снимок workspace, последнее
  покрытое сообщение и profile.
- **Смена harness или profile** запускает новую собственную session провайдера. Её заполняют файлом «fake-context»,
  содержимое которого зависит только от transcript до этой точки [124].
- **Якоря продолжения** у harness разные: UUID сообщения у Claude, индекс prompt у Grok, id session у ACP [124]. Так
  чат продолжается после model routing и после возврата на исходный аккаунт [36].
- **Сигналы контекста:** compaction и использование контекста приходят в потоке событий [119]. «Context limit
  reached» routing не обрабатывает [37]. В Host 1.5.0 добавили продолжение собственных subagents провайдера [78], в
  Desktop 1.3.0 — импорт sessions [77].

### Проверка качества

- **Встроенного test runner, CI gate или merge gate нет** ни в документации, ни в протоколе. Проверку делают skills и
  панель PR.
- **Проверки внутри skills** [26]: execute проверяет каждый batch против плана; autobuild использует агента-evaluator
  и rubric; есть skills review и critique; walkthrough перечисляет, что ещё не проверено.
- **Панель PR** [44][45] через `gh` показывает checks и состояние review. «Fix in chat» кладёт вывод упавшего check
  или комментарий review в поле ввода агента. Отправляет человек.
- **Judge Auto mode** проверяет команды до запуска, а не результаты работы [38].
- **Factory самой команды** — это пост о собственном процессе, а не функция продукта [20]: blind reviewer; уровни
  риска; агенты доказывают работу записями экрана и реальным выводом команд; агент-автор PR владеет им до merge, с
  проверкой раз в 15 минут; 332 из 675 PR за 11 дней, медиана 1.6 часа.
- **Формальная проверка интерфейса.** В `clients/gui-app/formal/` шесть моделей TLA+ о прокрутке чата [136].
  Workflow запускает модели TLA+ в CI [106].

### Восстановление после сбоев

- **Retry провайдера** видны как `RETRY_IN_PROGRESS`, `RETRY_RECOVERED` и `RETRY_ENDED`. Текст Codex «Reconnecting
  n/m» разбирается в счётчик попыток [123].
- **Лимиты и сбои провайдера** идут через model routing. После сбоя очередь держит следующее сообщение и не
  отправляет его [32].
- **Спящие агенты** продолжают работу по следующему сообщению или когда открывают их вкладку [114][175].
- **Падения Host:**
  - CLI перезапускает упавший Host [79];
  - с 1.5.2 ходы, оборванные остановкой Host, помечаются как interrupted [77];
  - с 1.5.3 приложение показывает, как закончил работу прошлый Host, включая нехватку памяти [77][79].
- **Переподключение к relay.** Задержка между попытками сбрасывается, только если соединение продержалось какое-то
  время. Потоки подписываются заново [127].
- **Hooks уведомлений** [58]:
  - вызов URL — timeout 5 секунд; два повтора (через 1 и через 5 секунд) при timeout, сетевой ошибке, 429 или 5xx;
  - скрипт останавливается через 10 секунд и не повторяется;
  - повторы не переживают перезапуск Host.
- **Запуск по расписанию** [76]. `traycer task create --idempotency-key` запускает не больше одной Task на ключ за 24
  часа. Документация предлагает ключи вида `nightly-$(date +%F)`. Если параллельный запуск с тем же ключом идёт
  слишком долго, команда выходит с exit code 75.
- **Отчёт пользователя о Host 1.5.2/1.5.3** (вторичный источник) [181]: задержки подтверждений сообщений, рост CPU и
  памяти, падения. Автор винит большую сверку журнала artifacts, которая не пропускает управляющие вызовы.
  Maintainers это не подтвердили (не подтверждено).
- Комментарий в записи supervisor упоминает откладывание запусков без присмотра [134]. Как это работает в продукте
  (не подтверждено).

### Лимиты и стоимость

- **Счётчики по провайдерам** [36]: Claude Code — session, weekly, по моделям, extra usage; Codex — session, weekly,
  по моделям, credits и ручные сбросы; также Cursor, Grok, OpenCode Go и OpenRouter.
- **Пороги предупреждений в коде** [130]:
  - окна 24 часа и короче — предупреждение на 80%;
  - более длинные окна — на 95%;
  - 100% — лимит;
  - при сопоставлении семейств лимитов код склоняется к тому, чтобы считать лимит блокирующим;
  - ответ 429 от endpoint Anthropic `/api/oauth/usage`, после которого идёт штраф на несколько минут, считается
    временной ошибкой чтения.
- **Model routing** — только для агентов Chat; агенты Terminal не переключаются и не ждут [37][36]:
  1. другой аккаунт того же провайдера [36];
  2. равноценная модель другого провайдера по группе уровня — frontier, flagship или standard; выигрывает первая
     подходящая группа в списке; модель без группы никогда не переезжает [131][37];
  3. ожидание сброса, если провайдер сообщил время сброса в пределах самого долгого ожидания; по умолчанию это 6
     часов, максимум — 7 дней [37][36];
  4. уведомление человеку [36].
- **Управление routing** [37][36]:
  - отсчёт перед переключением, который человек может отменить: по умолчанию 15 секунд, настройка — 10–15;
  - когда исходный лимит сбросился, по умолчанию Traycer спрашивает, вернуться ли; можно возвращаться автоматически
    или всегда оставаться;
  - «Wait it out here» держит чат на текущем провайдере и ждёт.
- **Шесть проблем routing никогда не обрабатывает** [37]: context limit reached; провайдер отклонил запрос; провайдер
  не стартовал вовремя; провайдер перестал отвечать; остановилась фоновая работа; session limit reached.
- **Учёт стоимости** [36][77][70]: токены и оценка стоимости на Task (7, 30, 90 дней) и на чат; аналитика usage по
  ходам с 1.2.0; dashboard аккаунта с фильтром по host.
- **Прочее:** код помечает замороженный host как «Out of credits» [135]; judge на Copilot стоит 60–350 premium
  requests в час [38]; «Prevent sleep while running» выключено по умолчанию [64].
- **Не найдено:** планирование запуска под окна лимитов и режим экономии.

### Права и безопасность

- **Четыре режима:** Supervised, Auto-accept edits, Auto (experimental), Full access. Новые разговоры по умолчанию —
  в Full access. Агенты из CLI или от другого агента — тоже, если создатель не задал режим [38].
- **Auto mode изнутри** [38][129][78]:
  - LLM-judge проверяет команды; Host читает настройки в момент решения по approval;
  - judge работает в два этапа — быстрый и глубокий;
  - по умолчанию judge берёт самый низкий effort модели. Комментарий в коде приводит замер на Grok 4.7: 8 секунд на
    low против 14 секунд на effort по умолчанию;
  - judge — либо Automatic, либо выбранная модель. Automatic — это Traycer Inference с откатом на провайдера самого
    разговора;
  - чаты Claude Code могут вместо этого брать classifier самого Claude Code;
  - правила задаются на уровне аккаунта; `.traycer/auto-policy.md` репозитория может их только ужесточить;
  - правки файлов, которые решают, что запустится потом, всегда спрашивают человека: внутренности git и hooks, CI
    workflows, manifests, конфиги сборки и tests;
  - judge сам никогда не отказывает; всё, что он не одобрил, идёт человеку, а агент ждёт [29];
  - log решений остаётся на host и не синхронизируется; секреты из него вычищаются; хранятся 200 последних решений
    [129][38];
  - у записи решения есть флаг `unattended` (без присмотра); hosts, которые оставляют все approvals человеку, всегда
    пишут в нём false [129].
- **Другие меры защиты:**
  - роли не дают прав [117];
  - терминальные агенты Codex и OpenCode получают CLI только для чтения [76];
  - настройка, которая разрешает или запрещает агентам создавать worktrees [42];
  - relay со сквозным шифрованием [127][128];
  - подписанные бинарники Host [79].
- **Собственные approvals провайдеров.** Пользователи просили auto mode Claude Code и режим approve-for-me у Codex.
  Собственная проверка прав Claude появилась в 1.4.0. Reviewer Codex лишил бы Traycer записи команд и снимков для
  отмены, поэтому для Codex остаётся свой judge [162].
- В дизайне sandbox из протокола учётные данные не попадают внутрь sandbox, а трафик идёт через broker [133].
  Выпущено ли это (не подтверждено).

### Где решает человек

- approvals по режиму прав и эскалации от judge Auto mode [38];
- структурированные вопросы агента, с fork для сравнения ответов [31];
- одобрение разбиения на tickets; одобрение spec, rubric и способа проверки у autobuild; одобрение точек зрения
  debate [26];
- остановка execute при product drift [26];
- worktrees в режиме Ask first [42];
- удаления в Sweep и housekeeping [43][26];
- отсчёт routing и вопрос о возврате на исходный аккаунт [36];
- подтверждение ручного сброса лимита Codex [36];
- «Fix in chat» — заполняет поле ввода, но не отправляет [44].

### Наблюдаемость

- **Agent office** [28]:
  - виды Office и Graph по агентам Task и их сообщениям, по всем hosts;
  - состояния: работает, ждёт ответа, нужен человек, в очереди к человеку, простаивает, неудачный ход, неотвеченные
    запросы, в архиве;
  - рёбра сообщений — Request, Reply, Notice и Created, с воспроизведением.

- **Resource monitor** [55]: CPU и память на агента, shell и процесс, со stop и kill.
- **Команды host** [76][79]: `traycer host logs`; `host status` (последнее обновление и кто держит lock обновления);
  `host doctor`.
- **Usage dashboards** [36][70] и **log решений Auto mode** [38].

- Cloud sandboxes, pod «Automations» и Tracy Bots есть только в коде протокола и клиента. Общая доступность не
  подтверждена [133][135][105].
- Пороги watchdog «quiet» и события `agent.stalled`.
- Работа без присмотра сверх `task create` из cron [134].
- Встроенный test gate или CI gate — не найден. Транспорта по LAN в коде нет [128].
- Планирование под лимиты, режим экономии, скриншоты-доказательства с privacy scrub — не найдены.
- Использует ли Host Desktop фиксированный набор моделей [16][19].

### Что ругают

#### Надёжность и потерянная работа

- **Эпоха расширения.**
  - У активного пользователя VS Code падал раз или два в день и уносил идущую многофазную session (сентябрь 2025)
    [144].
  - Отзыв на 3 звезды (март 2026): расширение зависает примерно раз в день, перезагрузка теряет прогресс Epic,
    восстановление тратит оплаченные artifacts [190].
  - Высокая загрузка CPU от расширения — в 2024 и 2025 годах [139].
  - Параллельные окна VS Code давали ошибки блокировки базы данных [142].
- **Запуск Desktop.**
  - Host не стартовал у многих первых пользователей: 92 автоматических отчёта, 80 из них — в июле 2026 [138].
    Типичный случай требовал ручной переустановки CLI до версий 1.1.8/1.1.9 [151].
  - В Индии загрузка Host размером 716 MB с CDN GitHub постоянно обрывалась, а докачки не было. Загрузчик потом
    исправили [152].
- **Потеря данных.**
  - Пользователь часами правил artifact, потом нажал на предложение обновиться. После перезапуска artifact вернулся к
    старой версии. Исправление этого бага было в той самой версии, которая ставилась. Пользователь решил, что работу
    не вернуть (июль 2026) [155].
  - Другие отчёты [165]: Epics пропадали из Recent Work; после перезагрузки все старые logs shell проигрывались
    агенту, и session умирала (исправлено в 1.4.0); сообщения попадали в чужой чат — причина (не подтверждено).

#### Масштаб: Host падает при большом числе агентов

Самые подробные жалобы, в основном от пользователей macOS, сентябрь — ноябрь 2026.

- **39 агентов, около 1 200 папок worktrees.** У Host заканчивалась память. Интервал между падениями сократился с двух
  дней до 31 минуты, потом до 10 минут. Maintainers сказали, что исправление убрало одну утечку, но общий рост heap
  остался: на 1.5.0/1.5.1 hosts падают через 10–70 часов [167].
- **Около 80 агентов примерно в 10 tasks.** После ~11 часов Host держался на 134–166% CPU и 3.9 GB памяти.
  Архивирование агентов ничего не освобождает, помогает только остановка [172].
- **Семь падений Host за день** на Mac Studio со 128 GB при потолке heap около 4.2 GB. Пользователь попросил
  настройку предела памяти [179].
- **Диск.** Папка Host дошла до 32 GB, база чатов одной task — до 13 GB. Сжать базу после удаления чатов нельзя
  [170].
- **Большие epics.** Сотни artifacts вызывали у Host цикл нагрузки на CPU и переподключений. Автор нашёл одну
  причину: редактор artifacts удваивал обратные слеши при каждом сохранении, и файлы разрастались примерно до 5 MB.
  Issue открыт с августа 2026, в нём 20 комментариев [164].
- **Блокеры работы без присмотра.** Команда с ~17 долгими «missions» в 8 tasks перечислила четыре проблемы (ноябрь
  2026, issue открыт) [182]:
  - рост памяти около 50 MiB в минуту и падения по памяти 5–7 раз в день;
  - чтение без постраничной разбивки по 10 646 версиям artifacts;
  - застрявшая облачная очередь исходящих (outbox);
  - очереди сообщений на паузе.
  - Они же намерили 0.14–0.18 TB записи на SSD в день от Host.
- **Отзывчивость.** Другой пользователь подал срочный отчёт об отзывчивости Host вместе со своим patch [181].
- **Worktrees в большом количестве.** Опрос git со стороны Host оставлял устаревшие lock-файлы [166].

- **Квота artifacts.**

    Pro — $25 [202].

  - старые планы с лимитом artifacts переведены на месячные credits 2026-11-01 в размере 1.5 цены плана.
  - Заявленный промо-кредит $100 у пользователя не сработал (ноябрь 2026) [184].

#### Расход токенов в схемах с несколькими агентами

- **Sub-agents наследуют самую сильную модель.** Зритель walkthrough предупредил: если начать с самой сильной модели,
  её наследует каждый sub-agent, и лимит session подписки кончается примерно за 20 минут. Нужно писать prompt выбора
  агента, который отправит механическую работу на дешёвые модели [187].
- **Проверять слабую модель сильной.** Русскоязычный зритель назвал такую схему способом зря тратить токены и
  спросил, почему не взять сразу сильную модель [209].
- **Накладные расходы сообщений между агентами, с замером.** Каждое входящее сообщение несло свежую копию реестра
  ролей — около 8.5 тыс. токенов. За 48 минут это дало около 100 тыс. токенов, примерно 57% роста контекста
  чата-координатора. Maintainers приняли как enhancement отправку только изменений [174].
- **Approvals в debate.** Дочерние агенты не наследовали full access родителя, и debate из нескольких агентов
  заставлял одобрять каждый вызов вручную. В июле 2026 это исправили: агенты теперь сами задают режим прав потомков
  [150].

#### Epic Mode не делал обещанного

- Пользователи, в том числе одна команда, сообщили: агент объявлял, что сначала будет план, а потом сразу начинал
  реализацию — без вопросов и без tickets. Так было на нескольких моделях [148].
- Сотрудники сначала посоветовали Claude Code как более надёжный orchestrator. Потом режим убрали, а не исправили.
  Объяснение сотрудника: «Epic Mode was a prompt variant, not an orchestration engine» [148].
- Замена — явные дочерние агенты, которых пользователь создаёт и которым передаёт работу [148][154].
- **Связанные жалобы:**
  - списки to-do не синхронизируются между агентами: у каждого агента свой список, общие только artifacts [161];
  - агенты OpenCode иногда печатают вызовы инструментов текстом вместо того, чтобы их выполнить [180].

#### «Open source» с закрытым ядром

- Главная называет Traycer бесплатным и полностью open source [1]. Документ для contributors говорит, что в
  репозитории клиенты, CLI и протокол [93]. Dev-скрипт пишет, что Host и облачного backend в репозитории нет, и
  скачивает подписанный бинарник Host [94].
- Пользователи сталкиваются с этим, когда пробуют чинить сами:
  - исправление интеграции с Cursor нельзя выпустить из публичного репозитория [153];
  - чтение rate limit у Kimi живёт в закрытом Host [157];
  - usage токенов по ходам хранится внутри Host, поэтому пользователь не смог сделать дневной счётчик токенов [158];
  - contributor на Windows не нашёл публичного способа собрать Host [173].
- Раньше и в других местах:
  - автор отзыва февраля 2025 хотел, чтобы код был открыт [191];
  - автор на HN противопоставил Traycer свою альтернативу под лицензией Apache [197];
  - зрители YouTube просили по-настоящему открытые инструменты без lock-in [202][204].

#### Накладные расходы и «зачем ещё один инструмент»

- **Слишком медленно для мелких правок.** Зритель заметил: правка hero-блока страницы в Cursor или Lovable занимает
  секунды, а в Traycer — минимум 10 минут плана и исполнения. Другие спрашивали, почему просто не писать prompts
  лучше и стоит ли за это платить [208].
- **Обзоры сходятся:** старт медленнее, контрольных точек больше [211][212][215].
- **Вопрос про Plan Mode.** На Product Hunt спросили, зачем Traycer, если Plan Mode в Claude Code уже отделяет план от
  кода. Ответа команды не видно [192].
- **Вопрос про Cursor.** Зритель спросил, не умеет ли этого уже Cursor [203].

#### Платформы, размер установки, аккаунт

- **Windows пришёл поздно, теперь багов на нём столько же, сколько на macOS.**
  - Desktop 1.0 вышел только для macOS и Linux; установщики Windows появились в 1.1.5 (2026-07-09) [80]. Первые
    зрители жаловались, что есть только Mac или WSL [203].
  - Сейчас у Windows столько же labels багов, сколько у macOS [138].
  - Примеры: setup Host падает на Windows не на английском языке; на одной машине Host может работать только у
    одного аккаунта Windows [177].
- **Размер установки.** Первый запуск без вопроса скачал около 1.5 GB голосовых моделей, и установка выросла
  примерно до 5 GB. Пользователь X возразил, и голос стал ставиться только по желанию [183].
- **Нужен аккаунт** даже со своими агентами. Запрос на offline или self-hosted режим остался без ответа [147].
- **Страх бана.** Зрители опасались, что за использование подписки Claude в стороннем приложении аккаунт забанят или
  посчитают это использованием API [203][209].

#### Удобство orchestration

- **Завершённые дочерние агенты** копились в epics, пока не появились archive и stop [154].
- **Ночные запуски.** Вкладки простаивающих агентов засыпают, когда никто не смотрит, и настройки «не усыплять на
  ночь» нет [175]. Это не то же самое, что «Prevent sleep while running»: та настройка не даёт уснуть машине [64].
- **Общий вид статуса отклонён.** Пользователь попросил один вид: кто работает, кто ждёт меня, что можно закрыть.
  Команда отказала. Она указала на Home tab (с 1.4.0) и сказала, что Traycer не может знать, когда workflow
  закончен [163].
- **Пользователи добавляют свой слой правил.** Одна схема через собственные hooks Claude Code отклоняет приказы
  остановить агента, если пользователь не отдал такой приказ явно. Она же требует отдельный сайт браузера на каждого
  агента [168].
- **Собственные approvals провайдеров.** Пользователи просили auto mode Claude Code и approve-for-me Codex. Проверка
  прав Claude пришла в 1.4.0; для Codex остался judge Traycer [162].
- **Лимиты подписок.** Пользователи переключаются между 5–6 логинами Claude Code. Автоматический переход между
  аккаунтами и моделями, по этому отчёту, настраивается на устройство и выключен по умолчанию [176].
  Документация говорит, что он включён по умолчанию [36][37]. Однажды routing сдался после одной неудачной
  попытки [169]. Настройка «Wait it out here» для отдельного агента появилась в октябре
  2026 [178].
- **Счётчики usage.** Значение за 5 часов показывалось в процентах, а за 7 дней — долей, поэтому недельный расход
  выглядел в 100 раз меньше. Ещё пользователи видели баннер лимита, который нельзя закрыть, и страницу usage,
  которая не загружалась [171].
- **Запускать код, а не только читать его.** В 2025 пользователи просили, чтобы Traycer сам запускал код и tests
  [145]. В недавних тестах поведение всё ещё проверяет человек [214][213].
- **Удалённое управление.** Работу с телефона и с другой машины просили с первых недель Desktop [149]. Traycer
  выпустил remote hosts и мобильное приложение [1][77].

### Почему приходят и почему уходят

- **Приходят:**
  - планирование и проверка на реальном коде, в том числе люди без опыта программирования [190][191][142][196];
  - нет второго счёта за inference: работают подписки, за которые уже платят [203][215][71];
  - одно место для многих агентов — worktrees, сообщения между агентами, remote host и приложение для телефона
    [187][149][1].
- **Уходят или сомневаются:**
  - падение качества и медленная поддержка, закончившиеся отменой подписки [190];
  - квота artifacts — из-за неё один пользователь ушёл на изменённый Ralph loop [207][204];
  - накладные расходы на мелких задачах [208];
  - ради расширения надо держать открытым VS Code — так написал человек в конце 14-дневного trial [141];
  - сбои и потерянная работа [155][144][190];
  - предпочтение open source и инструментов без lock-in [197][202][204];
  - страх бана подписки [203][209].

### Результаты и истории неудач

- **Независимый тест автозапуска «Bart»** (mejba.me, апрель 2026) на dashboard из Next.js 15 и Supabase [213]:
  - Traycer задал 7 вопросов и выдал дерево spec и 14 tickets;
  - первый batch прогнал 4 tickets параллельно примерно за 11 минут;
  - Traycer поймал два несовпадения со spec и одно настоящее противоречие между разделами spec;
  - приложение заработало за 93 минуты, плюс около 40 минут ручных правок — всего около 2.5 часа против примерно 6
    часов на сопоставимую ручную сборку;
  - сбои: параллельность упала 4 → 2 → 1 по ходу batches; регрессия стилей из-за умолчаний, которые spec не
    покрыла; нет защиты от CSRF; нет tests, если spec их не требовала; spec расходилась за три редакции;
  - вывод автора: Traycer лучше всего подходит для работы от пяти tickets, которые могут идти параллельно и
    описываются заранее.
- **dev.to, одно приложение дважды** [211]. Traycer (Epic Mode плюс автозапуск) сделал рабочее приложение с
  граничными случаями. Сборка через Plan Mode в Claude Code вышла со сломанным экспортом и неработающими
  переключателями. Traycer медленнее стартовал; времени автор не привёл.
- **Спонсированный тест автора видео** (Bijan Bowen, пересказ августа 2026) [214]:
  - модель-planner и reviewer в паре с локальным builder Qwen 27B сделали летающий симулятор самолёта; один Qwen
    рабочего управления не сделал;
  - orchestrator один раз нарушил правило «не писать код»;
  - reviewer не мог тестировать в браузере, поведение проверял человек;
  - это один запуск, а не benchmark.
- **Операторы больших наборов агентов** держат одновременно от 17 до 80 агентов, но сталкиваются с повторяющимися
  падениями и зависаниями Host [167][172][182][179].
- **Отзыв на сайте вендора (не проверен).** Founder одной компании пишет, что Epic Mode помог провести большую
  миграцию базы данных, API и платежей за шесть дней [1].
- **Тест конкурента (Augment).** Проверка шла один раз, после исполнения. Поэтому на epic из пяти tickets исправлять
  ошибки приходилось человеку. Планы обрезались на файле в 2 000 строк [216].

### Сравнение с альтернативами

- **Plan Mode в Claude Code:** вопрос на Product Hunt [192]; проиграл Traycer в одном тесте на dev.to [211].
- **Kiro:** на Product Hunt его назвали медленным [192]; фрилансер попробовал его и выбрал Traycer [142]; зритель
  YouTube спросил, лучше ли Traycer [202].

  предлагают как альтернативу в треде об уходе с Cursor [200].
- **Orca и T3 Code** (эпоха Desktop): зрители пишут «то же, что Orca» или «то, чего хотели от T3 Code» [209][187].
- **Ralph loop:** тест Bart и пользователь, который перешёл на Ralph loop [213][207].
- **Другие названия из HN и YouTube:** eforge [197], Runner [199], VS Code Agent Kanban [198], Roo Code [200], fork
  codebuff [202], Serena MCP [202], VSCodium [203].
- **CodeRabbit:** сами авторы Traycer отправляют пользователей туда за review PR [192].
- **Augment Intent:** сравнение, написанное конкурентом [216].

### Что поменялось за 6–12 месяцев

- **Форма продукта.** В 2025 Traycer был plugin, который планирует для других агентов. С июня 2026 это отдельный
  workspace, где работают сами агенты. Причина, по словам вендора: расширение может только то, что позволяет
  редактор, а Traycer хотел держать агентов, терминалы, файлы, diff и планы в одном месте [81][77].
- **Режимы стали skills.**
  - Plan, Phases, Review и Epic превратились в одну Task с artifacts и skills [81][99].
  - Ручное разбиение на фазы ушло: Traycer сам делит работу на шаги или на параллельных sub-agents [81].
  - Переключатель Epic убран 2026-08-06 [77]. По словам сотрудника, Epic Mode был вариантом prompt, а не движком
    orchestration [148].
- **Orchestration переехала внутрь агентов пользователя.** В 2025 планировал и проверял серверный набор моделей
  Traycer [16]. Сейчас агенты пользователя выполняют skills Traycer и общаются друг с другом через инструменты
  agent-to-agent. Команды `traycer agent create/send/transcript/inbox` — это их интерфейс [26][76].
- **Возможностей для работы без присмотра стало больше** [77][38]:
  - в 1.1.2 Full access стал режимом по умолчанию;
  - в 1.4.0 появились Auto mode с judge (всё ещё experimental) и routing с учётом лимитов;
  - фоновые команды уведомляют агентов, когда что-то печатают или завершаются.
- **Совместная работа пересобрана для Desktop.** Sharing досок Epic пришёл в расширение в марте 2026 [88]. В
  Desktop — sharing Task с ролями (состав ролей источники называют по-разному, см. «Sharing и команды») и командный
  sharing на плане Sync [71][10][73].
- **Хранение ушло в облако.** v1.0.0 подавался как local-first. v1.2.0 начал копировать чаты в облако. Cloud sync
  сейчас есть на всех планах [77][71].
- **Лицензия:** Apache-2.0 с 2026-06-22, MIT с 2026-07-15 [96][97].
- **Монетизацию пересматривали три раза** (ниже).
- **Много новых функций за два месяца:** мобильное приложение, браузер, мобильные симуляторы, HTML и canvas artifacts, импорт
  sessions, 22 агента, status page с проверкой каждого провайдера раз в 60 секунд [77][13].
- **Темп.** От v1.0.0 до v1.5.4 — меньше пяти месяцев, с частыми release candidates [80]. В публичном репозитории
  2 595 коммитов с 2026-06-22 [100]. 400 последних слитых PR слиты с 2026-11-02 по 2026-11-13 [101].
- **Ответы на просьбы пользователей — за дни:** archive и stop дочерних агентов, «Wait it out here», голос по
  желанию [154][178][183].

## Слабые места и чего нет

- **Стабильность Host под нагрузкой.**
  - Утечки и рост heap: падения по памяти через 10–70 часов, у больших наборов агентов — 5–7 раз в день [167][182].
  - CPU 134–166% при ~80 агентах; архивирование нагрузку не снимает [172].
  - Папка Host до 32 GB, базу нельзя сжать [170].
  - Цикл нагрузки на CPU и переподключений на больших epics [164].
  - Именно это мешает работе без присмотра, к которой стремятся самые активные пользователи [182][179].
- **Нет встроенной проверки результата.** Нет test runner, CI gate и merge gate. Проверка — skills агентов и панель
  PR [26][44]. Пользователи просили запускать код и tests ещё в 2025 [145]. В недавних тестах поведение всё ещё
  проверяет человек [214][213].
- **Раздача задач — не pipeline.** Skills не связываются в цепочку автоматически. Надёжный способ — выбирать skill
  вручную [26]. Прежний Epic Mode обещал сначала план, а начинал сразу с кода, и его убрали [148].
- **Нет объекта «запуск» для работы без присмотра.**
  - Есть отдельные части: routing для агентов Chat, judge, autobuild и `task create` из cron [37][38][26][76].
  - Встроенного scheduler нет [10].
  - Простаивающие вкладки засыпают, настройки «не усыплять на ночь» нет [175].
- **Routing — только для агентов Chat.** Агенты Terminal не переключаются и не ждут сброса лимита [37]. Один отчёт:
  routing сдался после одной неудачной попытки [169].
- **Небезопасные умолчания.**
  - Новые разговоры и агенты, созданные другими агентами, — в Full access [38][77].
  - Локально агенты работают без контейнера; изоляция — только worktree [39].
  - Sandboxes не выпущены (не подтверждено) [133].
- **Закрытое ядро при заявлении «fully open source».** Host и облако закрыты. Пользователи не могут исправить
  интеграции, получить usage по ходам или собрать Host сами [1][90][153][157][158][173].
- **Обязательные аккаунт и облако.** Без аккаунта Traycer не работает. Offline и self-hosted режимов нет. Связь между
  машинами — только через облачный relay [75][147][128].
- **Слабый review кода в интерфейсе.** Нет комментариев к строкам diff. Git Diff не делает stage, commit и discard
  [10][46].
- **Панель PR — только по одной Task.** Общего inbox нет. Нужен `gh`. GitHub Enterprise — не live [44].
- **Нет собственных интеграций** с Linear, Jira, Slack, GitLab и CI. Есть только hooks уведомлений и обещания
  factory [58][4].
- **Нет планирования под лимиты и режима экономии** [36]. Счётчики usage имели ошибку единиц: недельный расход
  выглядел в 100 раз меньше [171].
- **Цена координации в токенах.**
  - Реестр ролей в каждом сообщении — около 8.5 тыс. токенов, примерно 57% роста контекста координатора [174].
  - Sub-agents наследуют самую сильную модель, и лимит кончается примерно за 20 минут, если не написать guide выбора
    агента [187].
- **Нет SSO, SAML и SCIM** [72][10].
- **Нет общего вида статуса по всем Tasks.** Просьбу отклонили. Есть Home tab, и он выключен по умолчанию
  [163][62].
- **Нет записи всего запуска.** Agent office воспроизводит только сообщения между агентами. Log judge хранит только
  решения по командам [28][38]. Отчёта о работе по дням нет — только History и usage за 7, 30 и 90 дней [63][36].
- **Нет скриншотов-доказательств со scrub.** Есть только «Save a screenshot» у симулятора [60].
- **Нет бесконечного canvas.** «Canvas» в Traycer — это раскладка панелей или тип artifact [61][48].
- **Один профиль браузера** плюс private sessions, а не несколько именованных профилей [59].
- **Windows догоняет.** Он вышел на две недели позже macOS и Linux. Сейчас багов на нём столько же. Host не стартует
  на Windows не на английском языке. На машине работает Host только одного аккаунта Windows [80][138][177].
- **Потеря данных при обновлениях и перезапусках** [155][165].
- **Маленькая команда и почти нет внешнего кода.** Четыре инженера; из последних 1 000 PR внешних — четыре
  [20][102].
- **Мало независимых отзывов.** Независимых обзоров почти нет. Часть оценок в магазинах — от членов команды. Минимум
  одно видео спонсировано. У самого популярного issue 6 голосов [190][191][214][137].

## Пересечение с worfy

Термины worfy в этом разделе:

- Canvas — бесконечное полотно, на котором worfy показывает работу агентов.
- Epic — группа связанных Ticket-ов. Ticket — одна задача.
- Orchestrator — session, которая планирует и раздаёт Ticket-ы.
- Wave — набор Ticket-ов, которые запускаются вместе. Autopilot — запуск Wave-ов без человека.
- Gate — локальный запуск проверок перед PR.
- Harness — plugin, который приносит в Claude Code rules, skills, subagents и hooks.

### Где пересекаются

- **Desktop-приложение на Electron для Claude Code и Codex.** Traycer: Electron, macOS, Windows и Linux; Claude Code
  и Codex — среди 22 агентов [89][34]. worfy: Electron, macOS, Windows в работе; sessions Claude Code и Codex CLI.
- **План → tickets → раздача.** Traycer: artifacts-tickets из `traycer-ticket-breakdown`; `traycer-execute`
  раскладывает их по batches по зависимостям, запускает по агенту на ticket, проверяет batch и останавливается при
  product drift [26]. worfy: Epics из Ticket-ов; Orchestrator планирует и раздаёт.
- **Worktree на задачу.** Traycer: worktree на агента или папку, скрипты setup и teardown, уборка по классификатору
  [39][40][132]. worfy: свой git worktree на каждый Ticket.
- **Работа без человека: лимиты, повторы, approvals.** Traycer: routing с ожиданием сброса лимита (до 6 часов по
  умолчанию), статусы retry провайдера, Auto mode с judge [37][123][38]. worfy: Autopilot ждёт сброса лимитов
  подписки, повторяет ошибки API и одобряет permission prompts по политике.
- **Review агентами.** Traycer: `traycer-review`, `traycer-artifact-critique`, `traycer-changeset-walkthrough`,
  `traycer-debate` [26]. worfy: reviewer subagents с review lenses (разными углами проверки) и критик spec в Product
  Session.
- **PR и CI.** Traycer: панель PR со сводкой checks и «Fix in chat» [44]. worfy: PR с CI badges и PR inbox.
- **Свой plugin внутри Claude Code.** Traycer ставит plugin Claude Code с hooks и фоновым monitor [112][111] и
  добавляет агентам свой system prompt, skills и инструменты [35]. worfy: Harness plugin с rules, skills, subagents и
  hooks.
- **Встроенный браузер, терминалы, уведомления, счётчики лимитов** — есть у обоих [59][76][57][36].
- **Несколько машин.** Traycer: remote hosts через облако, port forwarding, агенты на других машинах [52][54]. worfy:
  Linked machines по локальной сети.
- **Продуктовый слой до кода.** Traycer: `traycer-epic-brief`, `traycer-core-flows`, `traycer-artifact-critique`,
  `traycer-debate` [26]. worfy: Product Session — продуктовый советник с живым Mind map и критиком spec.
- **Наблюдение за работой агентов.** Traycer: Agent office с воспроизведением сообщений на timeline, log решений
  judge, Home tab [28][38][62]. worfy: Flight Recorder (timeline запуска без человека) и Work track (вся работа
  проекта по дням и неделям).
- **Визуальные результаты, которые строят агенты.** Traycer: HTML и canvas artifacts, интерактивные приложения MCP в
  чате [49][48]. worfy: Cards, которые агенты строят на Canvas через MCP server.
- **Учёт расхода.** Traycer: счётчики лимитов по провайдерам, стоимость по Task и чату [36]. worfy: счётчики лимитов
  и usage.

### Где расходятся

- **Экран.** Traycer: панели с вкладками внутри Task; «canvas» — раскладка или тип artifact [61][48]. worfy:
  бесконечный Canvas.
- **Где живёт orchestration.** Traycer: раздача — skill, который агент выполняет по просьбе человека; шаги не
  связаны в pipeline [26]. worfy: Orchestrator session и Autopilot с Waves.
- **Проверка.** Traycer: нет test gate и CI gate; проверяют агенты и человек через PR [26][44]. worfy: tests,
  локальный Gate, PR с CI badges.
- **Запуск без человека как объект.** Traycer: объекта «запуск» нет; запуск по расписанию — CLI и свой cron
  [10][76]; routing только для агентов Chat [37]. worfy: Autopilot запускает Waves, Flight Recorder пишет timeline
  запуска.
- **Учёт лимитов.** Traycer переключает на другой аккаунт и другую модель [37]; планирования под лимиты и режима
  экономии нет [36]. worfy: ожидание сброса, Eco mode и планирование запуска под лимиты подписки.
- **Число агентов.** Traycer: 22 агента и провайдера моделей [34]. worfy: Claude Code и Codex CLI.
- **Один пользователь или команда.** Traycer: sharing Task, план Sync, team computers, боты в Slack
  [73][72][103][105]. worfy: один пользователь.
- **Связь машин.** Traycer: только облачный relay, без LAN [128]. worfy: Linked machines по LAN.
- **Облако и аккаунт.** Traycer требует аккаунт и облако [75][90]. В описании worfy облака нет.
- **Мобильные приложения, симуляторы, импорт sessions.** Есть у Traycer [74][60][23]. В описании worfy их нет.
- **Сообщения между агентами.** Traycer: inbox, роли, сообщения между Tasks и машинами [28][110][117]. Описание worfy
  называет только раздачу от Orchestrator и subagents.
- **Права по умолчанию.** Traycer: Full access по умолчанию [38]. worfy: approvals по политике.
- **Доказательства.** Traycer: только снимок экрана симулятора [60]. worfy: Evidence screenshots с privacy scrub.
- **Терминал.** Traycer: обычные терминалы, вывод которых читают агенты [76]. worfy: Terminal с AI-помощником.
- **Браузер.** Traycer: один общий профиль плюс private sessions [59]. worfy: Browser с профилями.
- **Отчёт о работе по дням.** Traycer: History и usage за 7, 30 и 90 дней [63][36]. worfy: Work track.
- **Код.** Traycer: клиенты открыты под MIT, Host закрыт [89][90]. Лицензия worfy в описании не указана.
- **Направление.** Traycer идёт к командам и к factory, которую запускают триггеры: ошибки, flaky tests, отчёты
  пользователей, красный trunk [4][20]. Autopilot worfy работает по Ticket-ам, которые спланировал человек.

## Механизмы, которые стоит изучить

1. **Цепочка model routing с отменой и возвратом.**
   - Что это: автоматический выход из лимита или ошибки провайдера для агентов Chat [36][37].
   - Как работает:
     - шаги по порядку: другой аккаунт того же провайдера → модель того же уровня у другого провайдера (группы
       frontier, flagship, standard; выигрывает первая подходящая; модель без группы не переезжает) → ожидание
       сброса в пределах лимита ожидания (6 часов по умолчанию, до 7 дней) → уведомление [131][37];
     - перед каждым переключением отсчёт 10–15 секунд, человек может отменить;
     - возврат на исходный аккаунт по умолчанию спрашивает; «Wait it out here» держит один чат на своём аккаунте;
     - новая session заполняется файлом «fake-context» из transcript; якорь продолжения у каждого harness свой
       [124];
     - предупреждения о лимите: 80% для окон 24 часа и короче, 95% для длинных [130];
     - шесть проблем, включая конец контекста и session limit, routing не трогает [37].
   - Чем интересно: ожидание сброса стоит последним шагом после двух переключений, и каждое переключение человек
     может отменить.
   - Источник: [36][37][124][130][131].
2. **Judge Auto mode: правила, которые репозиторий может только ужесточить.**
   - Как работает [38][129]:
     - двухэтапный LLM-judge (быстрый и глубокий) на низком effort;
     - сам никогда не отказывает: всё, что не одобрено, идёт человеку;
     - правила в аккаунте — Environment, Always allow, Ask first, Never allow, Notes;
     - `.traycer/auto-policy.md` в репозитории только добавляет ограничения;
     - правки файлов, которые определяют будущие запуски (git hooks, CI workflows, manifests,
       `.claude/settings.json`), всегда спрашивают;
     - локальный log 200 последних решений с вычищенными секретами; флаг `unattended` в записи решения.
   - Чем интересно: правила одобрения разделены на уровень человека и уровень репозитория, и репозиторий не может их
     ослабить.
   - Источник: [38][129].
3. **Настоящий простой Claude Code определяется через hooks.**
   - Как работает [112][113][114]:
     - Stop hook сообщает фоновые задачи и crons session;
     - SessionStart hook считает crons в `.claude/scheduled_tasks.json`;
     - вызовы hooks несут spawn token и id хода; id session пересинхронизируется после `/clear`;
     - Host снимает агента только при явных признаках простоя.
   - Чем интересно: «ход закончен» и «агент свободен» — разные состояния, и Traycer различает их по данным самого
     Claude Code. Замеры пользователя и ответ maintainer — в [175].
   - Источник: [112][113][114][175].
4. **Inbox агента через фоновый monitor Claude Code.**
   - Как работает [111][110][115][28]:
     - `monitors.json` plugin запускает `traycer monitor`; входящие сообщения печатаются в stdout, а Claude Code
       показывает модели вывод фоновых команд;
     - каждое сообщение обрамлено отправителем и id для ответа;
     - доставка at-least-once с подтверждением `agent.inbox.ack` (с протокола 1.2);
     - проверка по неактивности шлёт ждущему отправителю уведомление с причиной: turn-ended, exited, quiet,
       user-stopped, errored, awaiting-input, receiver-cancelled;
     - сообщения через облако, которые никто не забрал, пропадают через 24 часа.
   - Чем интересно: агент, который ждёт ответа, узнаёт причину, если ответа не будет, и не висит без конца.
   - Цена: копия реестра ролей в каждом сообщении стоила около 8.5 тыс. токенов [174].
   - Источник: [110][111][115][28][174].
5. **`traycer-execute`: batches по зависимостям, проверка batch и остановка на product drift.**
   - Как работает: tickets раскладываются по batches по зависимостям; по дочернему агенту на ticket; после batch —
     проверка против плана; прошедшие tickets — Done; мелкие проблемы — fix-up ticket; отход от продуктового
     замысла останавливает запуск и возвращает решение человеку [26][27].
   - Ограничения: текст skill не опубликован, размер batch (не подтверждено). В независимом тесте прежнего Bart
     параллельность падала 4 → 2 → 1 [213].
   - Источник: [26][27][213].
6. **`traycer-autobuild`: человек одобряет spec, rubric и способ проверки, потом builder и отдельный evaluator.**
   - Как работает: агент пишет spec, rubric (критерии оценки) и способ проверки; человек одобряет; builder и
     evaluator повторяют каждый sprint, пока он не пройдёт [26].
   - Чем интересно: критерий готовности согласован с человеком до начала работы, а проверяет не тот агент, который
     писал код.
   - Источник: [26].
7. **Checkpoint-manifest на каждый ход и отмена.**
   - Как работает: каждый ход пишет manifest с hash каждого файла до и после. Можно отменить ход или всё, что сделал
     агент, вместе с artifacts. Нельзя отменить отклонённые, бинарные и не перехваченные правки. Отмена работает
     только на host, который записал изменения [125][33][29].
   - Источник: [125][33][29].
8. **Общий классификатор worktrees для уборки.**
   - Как работает [132][42][43][40]:
     - состояния: в работе, на review, осиротел, слит, на базовом коммите, без ссылок;
     - один и тот же код у интерфейса, CLI, Host и skill housekeeping;
     - «зелёное» состояние нужно для удаления без человека, но его мало; один возраст никогда не даёт права удалить;
     - автоуборка выключена по умолчанию, порог 30 дней; история уборки — 90 дней или 200 запусков;
     - Sweep оставляет ветки;
     - setup отменяется через 5 минут без вывода, teardown получает 60 секунд.
   - Ограничение: у пользователя накопилось около 1 200 папок worktrees [167].
   - Источник: [132][42][43][40][167].
9. **Agent selection guide в Markdown.**
   - Как работает: файлы `~/.traycer/agent-selection-guide.md` и `.traycer/agent-selection-guide.md` говорят
     агенту, какого агента, модель и effort брать при передаче работы. Guide по умолчанию велит ставить потомкам
     `full_access` [65][116].
   - Чем интересно: это ответ на жалобу, что sub-agents наследуют самую сильную модель и тратят лимит примерно за
     20 минут [187].
   - Источник: [65][116][187].
10. **Идемпотентный запуск по расписанию.**
    - Как работает: `traycer task create --idempotency-key nightly-$(date +%F)` запускает не больше одной Task на
      ключ за 24 часа. Если параллельный запуск с тем же ключом идёт слишком долго, команда выходит с exit code 75.
      Вывод в JSON, exit codes описаны [76].
    - Чем интересно: cron пользователя можно запускать повторно без двойных запусков.
    - Источник: [76].
11. **«Fix in chat» в панели PR.**
    - Как работает: панель читает PR через `gh` и показывает, что мешает merge, checks и feedback. Кнопки «Fix in
      chat» и «Quote» кладут вывод упавшего check или комментарий review в поле ввода агента, который делал работу.
      Отправляет человек [44].
    - Источник: [44].
12. **Правила доказательства из factory самой команды.**
    - Как работает [20]:
      - test доказывает только сам test, продукт доказывает запись работы продукта;
      - исправлению нужен test, который падает на старом коде, а баг сначала воспроизводят в настоящей сборке;
      - blind reviewer не видит рассуждений агента-автора; изменения идут по уровням риска;
      - агент-автор PR владеет им до merge, проверка раз в 15 минут напоминает о застрявших PR;
      - необратимые решения приходят человеку с рекомендацией;
      - ввод из Slack и Sentry — данные, а не инструкции; ключи на публикацию держит отдельный gateway с бюджетами и
        тихими часами.
    - Результат по замеру вендора: 332 из 675 PR за 11 дней, медиана от открытия до merge — 1.6 часа.
    - Источник: [20].
