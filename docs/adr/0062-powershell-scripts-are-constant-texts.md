# 0062 — Скрипты PowerShell worfy — постоянный текст через `-Command`; данные идут в переменных окружения дочернего процесса
Дата: 2026-10-13. Статус: принят.

**Контекст.** Пункт 1 ADR-0057 (окружение агента на Windows) записал, как worfy читает реестр:

> Реестр читается Windows PowerShell по абсолютному пути
> (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive
> -EncodedCommand`, скрыто, timeout 10 с …) … подключ передаётся в base64 — кавычки не нужны.

Тем же способом шёл второй вызов PowerShell — время старта процессов live Session
(`readWindowsProcessStarts`, `src/main/claude-home/registry.ts`): pid вклеивались в текст скрипта.
В последствиях ADR-0057 записан долг: средства защиты могут помечать
`powershell.exe -EncodedCommand`, а передача скрипта через stdin не сделана.

Ticket `worfy-windows/21` измерил эти вызовы на ПК владельца (Windows 11 Pro, Defender включён):

- Скрипт, который PowerShell должен раскодировать из base64, стоит примерно на секунду дольше, когда
  процесс запускает его текст впервые и предок процесса — Electron. Так ведёт себя и
  `-EncodedCommand`, и `FromBase64String` в самом тексте.
- Чтение реестра при старте worfy шло 5,0 s. Время старта для нового набора pid — 2,2 s каждый раз:
  новый набор — новый текст.
- Тот же скрипт текстом через `-Command`, без декодирования, — 0,25–0,33 s всегда.
- Из системного Node разницы в секунду нет.

Числа сняты на одной машине. Измерено условие: декодирование base64 внутри PowerShell под
Electron. Механизм не доказан; кандидат — проверка Defender.

Этот ADR уточняет ADR-0057, пункт 1, — способ передачи скрипта и данных — и снимает долг из его
последствий. ADR-0057 не правится. Остальное в его пункте 1 остаётся в силе: абсолютный путь к
Windows PowerShell, `-NoProfile -NonInteractive`, скрытое окно, timeout 10 s, ключ через .NET
Registry API, вывод в base64 от UTF-8.

Способ выбрал исполнитель Ticket-а 21 — Ticket оставлял выбор ему. Ревью на Mac приняло его
2026-10-13 (PR #269).

**Решение.**

1. **Скрипт — постоянный текст.** Он идёт одним аргументом после `-Command`. `-EncodedCommand` worfy
   не использует.
2. **Данные вызова идут в переменных окружения дочернего процесса.** Окружение дочернего процесса —
   окружение worfy плюс переменные вызова; скрипт читает их как `$env:ИМЯ`. Сейчас их три:
   `WORFY_REGISTRY_HIVE` и `WORFY_REGISTRY_SUBKEY` (чтение реестра), `WORFY_PROCESS_IDS` (время
   старта процессов). В окружение самого worfy и в окружение Session, агентов и Terminal-ов они не
   попадают.
3. **Данные не вклеиваются в текст и не исполняются как код.** Hive выбирается по таблице из двух
   имён. Подключ идёт в `OpenSubKey` строкой. Из списка pid скрипт берёт только то, что состоит из
   цифр.
4. **Входные данные скрипт из base64 не декодирует.** Вывод по-прежнему кодируется в base64: по
   замеру это бесплатно, и вывод остаётся ASCII при любой кодовой странице консоли.
5. **Команду строит одна функция** — `powershellScriptCommand` (`src/main/agent/env.ts`): скрипт,
   данные, окружение. Новый вызов PowerShell идёт через неё.

**Последствия.**

- **Текст доходит до PowerShell без изменений, пока `execFile` зовётся без `shell` и без
  `windowsVerbatimArguments`** (`runFile` в `env.ts`). С `shell` `cmd.exe` обрежет текст на первом
  переводе строки. С `windowsVerbatimArguments` пропадут двойные кавычки. Проверено двумя
  способами: моделью разбора командной строки на Mac и настоящим `powershell.exe` на чистой
  Windows — ручной job «Windows tests», запуск 38333837282.
- **Скрипт не должен читать `$input`.** stdin дочернего процесса — pipe, который Node не закрывает.
- **Текст скрипта виден в командной строке процесса** — в списке процессов и в журналах средств
  защиты. Данных в нём нет: они в окружении дочернего процесса.
- **Потерянная переменная `WORFY_PROCESS_IDS` читается как пустой список.** Скрипт отвечает кодом 0
  и пустым выводом, и worfy считает все спрошенные процессы завершёнными. Пока pid были в тексте,
  такого случая не было. Test на всех системах и код, отличный от 0, — Ticket `worfy-windows/29`.
- **stderr PowerShell при `-Command`, вероятно, простой текст, а не CLIXML.** ADR-0057 и Ticket
  `worfy-windows/09` описывали CLIXML при `-EncodedCommand`. От этого зависит только текст
  сообщения об ошибке чтения реестра. Проверка на ПК — Ticket `worfy-windows/29`.
- **Долг из последствий ADR-0057 снят:** `-EncodedCommand` worfy больше не запускает. Заметка
  ADR-0057 о политике PowerShell transcription остаётся верной: вывод по-прежнему несёт значения
  переменных в base64.
- **Два вызова из других Ticket-ов правило уже выполняли:** helper Terminal-а
  (`src/main/terminal/pty.ts`, PR #239) и список процессов в `scripts/install-stable.mjs` отдают
  скрипт текстом через `-Command`. По замеру Ticket-а 21 они идут 0,45–0,54 s.

## Considered Options

- **Постоянный текст через `-Command`, данные в переменных окружения** (выбрано; варианты (а) и (б)
  Ticket-а 21 вместе). Вызов с новыми данными идёт столько же, сколько повтор, — 0,25–0,33 s. Данные
  не проходят ни через разбор командной строки, ни через разбор кода.
- **Оставить `-EncodedCommand` и сделать текст постоянным.** Отвергнуто: «знакомость» текста не
  переживает перезапуск worfy, и первый вызов каждого запуска стоил бы секунды — 5,0 s на чтении
  реестра по замеру.
- **Данные — аргументами после скрипта.** Отвергнуто: всё, что стоит после `-Command`, PowerShell
  склеивает с текстом и разбирает как код. Подключ с кавычками или `$(…)` пришлось бы экранировать.
- **Скрипт через stdin (`-Command -`).** По замеру 0,22–0,24 s — выигрыш в сотые доли секунды.
  Отвергнуто: многострочный скрипт в этом режиме читается построчно, как в интерактивной консоли
  (Ticket `worfy-windows/09`), и это потребовало бы отдельной проверки.
- **Один долгоживущий процесс PowerShell** (вариант (в) Ticket-а 21). Отвергнуто: граница 1 s на
  вызов выполнена и без него, а он добавил бы состояние — жизнь процесса и разбор его ответов по
  границам.
- **Исправить пункт 1 в самом ADR-0057.** Отвергнуто: принятые ADR правятся только в терминах
  (ADR-0017).
