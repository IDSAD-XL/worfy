# Адрес и изоляция Card — свой origin `worfy-card://<id>.<метка проекта>`

Дата: 2026-10-05. Статус: принят.

Card — исполняемый HTML/JS, написанный агентом.

**Решение.** worfy показывает Card в iframe на своей привилегированной схеме `worfy-card://`
(`standard`, `secure`). У каждой Card свой origin `worfy-card://<id Карточки>.<метка Проекта>`,
где метка — 8 hex-символов хеша пути Project из его id. iframe — `sandbox="allow-scripts
allow-same-origin"`: origin свой, поэтому доступа к окну worfy (file:// или dev-сервер) и к другим
Card-ам нет. Протокол отдаёт только файлы из папки Card с CSP (`connect-src https:`,
`frame-src 'none'`, без форм и плагинов), main не пускает фрейм на чужой origin, не открывает окна
и не даёт web-разрешений.

**Почему записано.** Решение трудно обратимо: origin — ключ хранилищ браузера Card
(localStorage, IndexedDB в userData worfy) и ожидаемый origin в мосте `postMessage` (Ticket 26).
Смена схемы адреса теряет данные Card-ов в этих хранилищах и меняет проверку отправителя.

Источник: Ticket 25 (`.scratch/worfy-mvp/issues/25-рантайм-карточки.md`, раздел «Итог»), PR #15.

## Considered Options

- Весь ключ Project в хосте (`<id>.<ключ>`, как в тексте Ticket-а 25) — отвергнуто: имя папки
  Project с пробелами, заглавными или не-ASCII буквами не проходит в хост без искажения.
- Ключ Project в hex/base32 в хосте — отвергнуто: длинные имена папок не помещаются в метку DNS
  (63 символа), а адрес становится нечитаемым.
- Один origin на все Card-ы с путём `/<проект>/<id>/` — отвергнуто: Card-ы видели бы
  хранилища и DOM друг друга.
- `srcdoc`/`data:` без своего протокола — отвергнуто: opaque origin без своих файлов и без
  контроля заголовков.
- Свой origin на Card с меткой Project из хеша (выбрано).
