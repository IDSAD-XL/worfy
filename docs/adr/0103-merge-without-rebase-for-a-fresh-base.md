# 0103 — PR с зелёным `ci-ok` на своём head вливается без rebase ради свежей базы; сочетание PR проверяет push-run на `main`; частично заменяет ADR-0083, пункт 2
Дата: 2026-11-09. Статус: принят. Epic `worfy-throughput`, Ticket 62 (`.scratch/worfy-throughput/issues/62-merge-queue-или-ci-пачками.md`,
«Итог» и «Решение владельца 2026-11-09»). Вступает в силу с merge PR этого ADR; скрипты Harness догоняют его Ticket-ами
63 и 64.

**Контекст.** ADR-0083, пункт 2: условие merge — зелёный `ci-ok` и отметка `review` `success` на head PR, и «если база с
этого run-а ушла вперёд кодом — rebase, push и новый зелёный `ci-ok`». PR одной Wave (группа Ticket-ов, которые
Orchestrator ведёт параллельно) поэтому вливаются по одному: каждый следующий после первого ждёт rebase и новый run.
Ticket 05 Epic-а `worfy-throughput` назвал это причиной роста Gate → merge на Wave.

Замер Ticket-а 62 — последние 150 влитых PR (#1573…#1722, 2026-11-07 09:03Z … 2026-11-09 08:41Z, 47,6 h), 454 CI run-а;
64 PR с кодом, 86 — только документы:

- head-ов на PR с кодом — медиана 2, p90 3; 21 rebase зелёного head-а (по-видимому, ради свежей базы) стоили 1 823 min CI,
  новый `ci-ok` после такого rebase — медиана 26,3, p90 71,8 min wall;
- из этих 21 run-ов — 18 зелёных, 2 отменены, 1 красный (#1632, test Windows; был ли это skew — несовместимость двух PR,
  каждый из которых зелёный сам по себе, — не различить). Rebase ради свежей базы поймал не больше одного skew-а за 48 h;
- 6 905 min из 13 809 min CI на PR (50 %) ушли на head-ы, которые потом заменили;
- push-run на `main` (CI run на push в `main`) с кодом: 77 run-ов, 158 min CI на run, wall — медиана 36,5, p90 241,6 min
  (очередь macOS runner-ов); красных — 14 из 77 (18,2 %), в основном flaky test-ы macOS;
- зелёный `ci-ok` → merge у PR с кодом — медиана 3,0 min. Wave из 5 PR, готовых почти одновременно: с rebase-ами
  Gate → merge ≈ 105 min (p90 ≈ 290), без них ≈ 15 min.

GitHub merge queue проверила бы сочетание PR до merge, но недоступна: она есть только у репозиториев организации, а
владелец `IDSAD-XL/worfy` — пользователь (`gh api repos/IDSAD-XL/worfy --jq .owner.type` → `User`). Branch protection
`main` требует только `ci-ok`, `strict: false`: свежей базы требует правило проекта, а не GitHub.

**Решение** (владелец, 2026-11-09, ответы «да» на Q1, Q2, Q4, Q5, Q6 по «Итог» Ticket-а 62; вариант B).

1. **Merge без rebase ради свежей базы (Q1).** PR, у которого на его собственном head зелёный `ci-ok` и отметка
   `review` `success` и у которого GitHub не видит конфликта с базой, вливается, даже если `main` с этого run-а ушёл
   вперёд кодом. Rebase, push и новый `ci-ok` ради свежей базы не нужны. Состояние `BEHIND` — не причина ждать.
   Сочетание PR проверяет push-run на `main` после merge: он есть на каждом commit-е `main`.
2. **Rebase — только при конфликте (Q4).** Rebase нужен, только когда GitHub сообщает конфликт: `mergeable`
   `CONFLICTING` или `mergeStateStatus` `DIRTY`. Других исключений нет. Платформенный PR (ADR-0056, пункт 2; в том
   числе PR со скриптами Harness) тоже вливается без rebase: его Windows verdict — job Windows в составе `ci-ok` на его
   собственном head (ADR-0083, пункт 6; ADR-0086 для scope `pc`).
3. **Красный `main` (Q5).** Уточняет ADR-0083, пункт 7, и его поправку 2026-10-29.
   - Виноватый PR — тот, чей squash-commit дал первый красный push-run на `main`: первый по порядку commit-ов `main`
     после последнего зелёного push-run-а. Деления пополам нет.
   - Пока последний push-run на `main` красный, PR с кодом не вливаются; PR только с документами вливаются.
   - Исправление вперёд — не дольше 1 h от красного push-run-а; не успели — revert виноватого PR, со своим зелёным
     `ci-ok`.
   - Упавшие job-ы красного push-run-а повторяются один раз (`gh run rerun --failed`, один повтор на head — правило
     владельца). Если повтор зелёный, сбой — flaky test, а не вина PR: `main` считается зелёным, test идёт в карантин по
     ADR-0083, пункт 3. Для PR правило ADR-0083, пункт 3, не меняется: ручной повтор job-а — не путь к merge PR.
4. **Merge queue — нет (Q2).** Репозиторий не переходит в организацию ради merge queue. Вопрос возвращается, только
   если при этом ADR за одну неделю будет 2 или больше красных `main` от несовместимых PR: красный push-run, у
   виноватого PR зелёный `ci-ok` на своём head, повтор упавших job-ов тоже красный, а исправление касается сочетания
   PR, а не одного из них. Это меряет Ticket 66.
5. **ADR-0083 частично заменён (Q6).** Зелёный `ci-ok` на head каждого PR остаётся условием merge (ADR-0083,
   пункт 2). Уходит только требование rebase и нового `ci-ok`, когда база ушла вперёд кодом. Остальные пункты
   ADR-0083 действуют.

**Последствия.**

- Wave из 5 готовых PR вливается примерно за 15 min вместо примерно 105 min (p90 ≈ 290); CI тратит примерно на
  1 800 min меньше за двое суток такой работы.
- Skew виден после merge, а не до: по замеру — не больше одного на 21 rebase за 48 h. Ответ приходит поздно:
  push-run с кодом — медиана 36,5, p90 241,6 min wall, и к его концу сверху уже влиты другие PR. Поэтому нужен шаг
  поиска виноватого по push-run-ам каждого commit-а и пауза merge PR с кодом, пока `main` красный (Ticket 64).
- Пауза merge задерживает всю Wave: при красном `main` PR с кодом стоят до исправления или revert, до 1 h и дольше,
  если push-run исправления ждёт macOS runner.
- `harness/bin/land` сейчас ждёт на `BEHIND` («the base moved, rebase the PR»), а skill `epic-wave` велит rebase на
  `BEHIND` и на сдвинутую базу. До Ticket-а 63 Orchestrator вливает такие PR руками по этому ADR. `rules-merge.md`
  Profile-а worfy (фраза «база ушла вперёд кодом после run-а — rebase…») правит Orchestrator после merge этого ADR:
  Profile лежит вне репозитория.
- Отметка `review` по-прежнему привязана к SHA (ADR-0067): без rebase head не меняется, и отметку не нужно ставить
  заново или переносить.
- ADR-0056, пункт 6 («второй перед мержем обновляется от свежего main»), в части свежей базы тоже больше не действует;
  merge по одному под общим замком остаётся.

## Considered Options

- **A. GitHub merge queue, пачка 3–5 PR.** Проверяет сочетание до merge, и `main` реже красный. Отвергнуто сейчас:
  нужна передача репозитория в организацию (новый URL, права токена, перенос branch protection), а очередь
  выбивает PR на каждом flaky test-е macOS e2e. Порог возврата — пункт 4.
- **B. Без rebase на PR, сочетание проверяет push-run на `main` (выбрано).** Самый короткий Gate → merge, правки
  только в правилах и скриптах Harness.
- **C. Как сейчас, плюс пропуск CI для PR только с документами.** Пропуск уже работает (`scripts/ci-scope.mjs`), CI
  таких PR — 2 % минут; rebase-ы остаются. Ничего не даёт.
- **CI пачкой: run только на `main` после Wave (`workflow.ci: batch`, ADR-0068).** Буквальная форма «копить коммиты
  и гонять пачками». Отвергнуто: PR теряет Windows verdict на своём head и проверку до ревью, а красный `main`
  ищется заново. B — её мягкая форма: CI на head PR остаётся, пачкой проверяется только сочетание.
