# 0029 — Autopilot ждёт background task-и Orchestrator-а, Stop их не убивает
Дата: 2026-10-06. Статус: принят.

**Контекст.** Первый настоящий прогон Autopilot (Ticket 29 Epic-а worfy-daily) кончил Wave через
85 секунд после старта. Skill `/epic-wave` запустил четырёх implementer-ов tool-ом Agent в фоне и
закончил ход. Ни один implementer ещё не взял Ticket, поэтому правило ADR-0024 «ни один Ticket
Wave не в работе» выполнилось сразу, и прогон остановился с `no-progress`. После остановки
Orchestrator вернулся обычной Session: старая Session закрылась, процесс Claude Code завершился, а
с ним все четыре background task-а. Background task — работа, которую Session запустила и не ждёт
в своём ходе (Subagent с `run_in_background`, workflow-скрипт, Bash с `run_in_background`). Когда
она кончается, Claude Code присылает task-notification и начинает им новый ход Session.

Проверка на настоящем Claude Code 2.1.289 (SDK 0.3.289, модель sonnet, один Bash `sleep 5` в
фоне, фикстура `test/fixtures/sdk-messages/background-tasks.jsonl`) показала:

- `system/background_tasks_changed` приходит в поток SDK без env-флагов. Он идёт перед
  `task_started` задачи и перед `task_updated` / `task_notification` её конца. В нём полный список
  живых задач: уровень, а не фронт.
- После `result` хода и конца задачи Claude Code сам начинает новый ход: `system/init`, ответ,
  `result`. worfy не шлёт для него сообщения.
- `session_state_changed: idle` (с `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1`) пришло сразу после
  первого `result`, пока задача ещё шла. Как признак конца работы Session оно не годится.

ADR-0024 остаётся в силе. Этот ADR заменяет в нём пункты 1 и 2 (когда Wave закончена и как прогон
ждёт), дополняет пункт 4 (новая причина остановки) и пункт 6 (когда Orchestrator возвращается
обычной Session).

**Решение.**

1. **Живые задачи Session.** worfy считает background task-и каждой Session сам, по её событиям
   (`src/shared/agent/background-tasks.ts`):
   - основной источник — `background_tasks_changed`: набор заменяется списком целиком;
   - пока в этом процессе такого события не было, набор собирается из пар `task_started` с
     `is_backgrounded: true` (или `task_updated` с `patch.is_backgrounded: true`) и
     `task_notification` по `task_id`;
   - задачи с `ambient: true` не считаются: это служебные задачи, а не работа;
   - на каждом новом процессе Claude Code и при его смерти набор становится пустым: SDK шлёт
     уровень только при изменении, и после перезапуска задачи старого процесса мертвы.
2. **Wave закончена**, когда выполнено всё сразу:
   - последний ход Orchestrator-а закончился `result` без ошибки и без прерывания;
   - у Session прогона нет живых background task-ов;
   - Session `idle`: после `result` не начался новый ход;
   - в свежем чтении модели workflow ни один Ticket Wave не в работе (правило ADR-0024).

   Ход, который начал task-notification, — тоже ход Wave: его `result` проверяет признак заново.
3. **Ожидание задач.** Ход кончился, а задачи живы: прогон переходит в фазу `tasks`. Строка
   состояния — «Wave 1 · 4 background tasks». Таймер `wave-unfinished` (10 минут ADR-0024) в этой
   фазе не идёт. Каждое событие задач (`background_tasks_changed`, `task_started`,
   `task_progress`, `task_updated`, `task_notification`) перезапускает предел
   `BACKGROUND_STALL_MS` — 60 минут. Если за это время событий задач не было, прогон
   останавливается с причиной `background-stalled`, и `run-stopped` перечисляет живые задачи.
   60 минут — с запасом: implementer ждёт CI одной Bash-командой до 10 минут и повторяет её, а
   зависший Subagent (Ticket 08) держит прогон не дольше часа. Если задач стало 0, а
   task-notification за 2 минуты (`TASKS_GRACE_MS`) не начал ход, признак Wave проверяется без
   этого хода.
4. **Проверяемое правило.** Журнал прогона пишет `background-tasks` при каждом изменении набора.
   `wave-finished` и `run-stopped` с `no-progress` или `no-ready-wave` стоят в журнале только там,
   где последняя строка `background-tasks` перед ними пустая (или её нет).
5. **Stop не убивает задачи молча — отложенный перезапуск, вариант (а).** При любой причине
   остановки, кроме `app-quit`:
   - прогон останавливается сразу: `run-stopped` с причиной и списком живых задач, новые Wave-ы не
     уходят;
   - Orchestrator остаётся Session без человека, пока Session не `idle` и живых задач не 0. Ходы
     от task-notification идут в ней. Набор опустел, а за 30 секунд task-notification не начал
     ход — перезапуск идёт без него;
   - потом Orchestrator перезапускается обычной Session (тот же `resume`), и журнал пишет
     `orchestrator-returned`;
   - keep-awake держится до этого перезапуска: иначе Mac уснёт посреди работы агентов;
   - новый старт Autopilot отклоняется, пока Orchestrator не вернулся: Session без человека с
     живыми задачами нельзя перезапустить, не убив их.
6. **Явного «остановить и убить задачи» нет.** `Query.stopTask` у SDK есть, но кнопка с ним — это
   решение о судьбе чужой работы (implementer посреди merge). Человек, которому нужно убить
   задачи, закрывает приложение: это видно в журнале.
7. **`app-quit`** закрывает процесс Claude Code и задачи неизбежно. `run-stopped` с `app-quit`
   перечисляет живые задачи. Если прогон уже стоял и ждал задач, журнал пишет `tasks-killed` с
   причиной `app-quit` и списком задач.

**Последствия.** Конец Wave по-прежнему зависит только от того, что worfy видит сам: событий своей
Session и файлов Ticket-ов. Протокола со skill-ом нет (ADR-0002). Остановленный прогон может ещё
долго держать Orchestrator без человека и keep-awake, если Subagent завис: журнал называет задачи,
а приложение закрывается как обычно. Задача, о которой SDK не прислал ни одного события, прогон
не держит; задача, чей конец потерян, держит не дольше `BACKGROUND_STALL_MS`, а после перезапуска
процесса — нисколько.

## Considered Options

- **Набор задач из событий Session: уровень `background_tasks_changed`, пары started/finished как
  запасной путь** (выбрано). Событие приходит без флагов, не зависит от формата skill-а и не
  оставляет вечный `running`, если пропущен один фронт.
- **`session_state_changed: idle` как конец работы.** Отвергнуто: Claude Code шлёт его только с
  env-флагом, и на проверке оно пришло сразу после первого `result`, пока фоновая задача шла.
- **Транскрипт Orchestrator-а (`<task-notification>`, дерево Subagent-ов).** Отвергнуто: файл
  догоняет события с задержкой, а зависшие в нём `running` чинит отдельный Ticket 08.
- **Только Ticket-ы «в работе» (ADR-0024 как есть).** Отвергнуто: implementer берёт Ticket через
  минуты после запуска, а ход Orchestrator-а кончается сразу. Проверено первым прогоном.
- **Ждать задачи без предела.** Отвергнуто: зависший Subagent держал бы прогон до утра.
- **Предел от старта ожидания, а не от последнего события задач.** Отвергнуто: Wave из четырёх
  Ticket-ов честно идёт час и больше, и предел пришлось бы ставить на всю ночь.
- **Stop без перезапуска, вариант (б): Orchestrator остаётся Session без человека, пока человек
  сам её не перезапустит.** Отвергнуто: Session человека неопределённо долго живёт в
  `bypassPermissions`, и вернуть её — ещё одно действие человека.
- **Stop сразу вызывает `stopTask` каждой задачи.** Отвергнуто: так Stop убивает работу
  implementer-ов так же, как сейчас, только явно.
