# 0072 — Вердикт Windows «без регресса»: новые test-ы PR красны на Windows по причине, которая уже есть на main; дополняет пункт 2 ADR-0056 и пункты 3–4 ADR-0071
Дата: 2026-10-19. Статус: принят.

**Контекст.** Перед мержем платформенного PR на его head стоит отметка `check/windows` (ADR-0067). Её
ставит Orchestrator на Mac: `success` — по зелёному gate full на Windows-ПК владельца (ADR-0056, пункт 2)
или, для PR без Terminal, окон, e2e и упаковки, по зелёному полному run-у на Windows-runner-е GitHub
(ADR-0071, пункты 3 и 4). Красный прогон — `failure`, PR не мержится.

Пока main сам красный на Windows, это правило ловит PR, которые ничего не ломают. PR добавляет test-ы,
они падают на Windows, но причина — в коде main, а не в PR, и её чинит другой Ticket. Два таких PR
2026-10-19:

- **#496** (`worfy-harness` 27, платный eval-круг): 13 новых test-ов eval красны на Windows. Причины —
  запуск скрипта по `#!`-строке (`spawn` — `ENOENT`), CRLF в файлах фикстуры и путь `pm` реестра Gate в
  форме Git Bash. Чинит их `worfy-windows` 65 (PR #517).
- **#508** (`worfy-link` 32): 6 новых test-ов с настоящим наблюдателем файлов красны на ПК так же, как 7
  старых таких test-ов на main: наблюдатель не сообщает об изменении вовремя (отчёт Session на ПК о head
  `4bce4bf0`, [комментарий PR #508](https://github.com/IDSAD-XL/worfy/pull/508#issuecomment-6255339725)).
  Причину чинит `worfy-windows` 14.

Отложить мерж до починки причины не всегда возможно: починка сама ждёт PR. У `worfy-windows` 65 20 test-ов
`bin/profile` на Windows пропущены с пометкой «Step 4 of worfy-windows ticket 65, after PR #496 merges»
(`test/contract/harness-evals.test.ts:164-169` на ветке `worfy-windows/65`), а новые test-ы #496 красны
из-за причин, которые чинит 65.

**Решение** (владелец, 2026-10-19, вопрос Q-h о #508 и Q-e о #496).

1. Платформенный PR, у которого на Windows красны test-ы, получает `check/windows` `success` с пометкой
   **«без регресса»**, только когда верны все три условия:
   1. **Всё, что зелёное на main, зелёное и на PR.** Сравнение — по именам test-ов: один и тот же набор
      файлов прогоняется на head PR и на main тем же способом — на Windows-runner-е (ADR-0071) или на
      Windows-ПК (ADR-0056).
   2. **Красны только новые test-ы самого PR** — те, которых на main нет.
   3. **У каждой причины есть открытый Ticket**, и комментарий PR, который ставит пометку, называет его
      (эпик и номер).
2. Не выполнено хоть одно условие — `failure`, как раньше. «Не удалось проверить» — без отметки, PR ждёт
   (ADR-0067).
3. **Это запасной путь, а не первый.** Если починка причины может влиться раньше, Orchestrator сначала
   вливает её, делает rebase PR и прогоняет его test-ы на Windows: настоящий зелёный лучше пометки. Для
   2026-10-19 владелец задал порядок (вопрос Q7): #517 (`worfy-windows` 65) — первым; затем rebase #496 и
   run его test-ов на Windows-runner-е; правило этого ADR — только для того, что останется красным.

Не меняются: пункт 1 ADR-0056 (Windows-раннера на PR нет), пункт 5 ADR-0071 (кто проверяется на ПК, а кто
run-ом, решает список путей) и ADR-0067 (отметка привязана к SHA head-а).

**Последствия.**

- Мерж PR не ждёт Ticket-а, который чинит чужую причину, и цикл «A ждёт B, B ждёт A» разрывается.
- На main после такого мержа красных на Windows test-ов больше: к старым добавляются новые test-ы PR.
  Они видны и названы, а не спрятаны. Ticket причины отвечает и за них.
- Сравнение по именам требует двух прогонов одного набора файлов — на head и на main. Это ещё один run
  Windows-runner-а или прогон на ПК; цена — как у одного run-а (ADR-0071).
- Пометка не покрывает регресс в старом коде: если на PR упал test, зелёный на main, — это `failure`.
- Переходное исключение ADR-0056 («Последствия»: падения совпадают со списком Ticket-а 02 `worfy-windows`,
  новых нет) отвечало на другой вопрос — старые красные test-ы. Этот ADR — о новых test-ах PR.

## Considered Options

- **(a) Пометка «без регресса» при трёх условиях** (выбрано).
- **(b) Ждать мержа Ticket-а причины, потом rebase PR и новый прогон.** Отвергнуто как общее правило:
  создаёт круговые ожидания. Пример: у `worfy-windows` 65 20 пропусков `bin/profile` ждут мержа #496, а
  новые test-ы #496 красны из-за причин, которые чинит 65. Как первый шаг, когда починка может влиться
  раньше, остаётся (пункт 3).
- **(c) PR пропускает свои новые test-ы на `win32`.** Отвергнуто: test-ы прячутся, и вернуть их легко
  забыть; красный test с названной причиной виден, пропущенный — нет.
- **(d) Как сейчас: любой красный test на Windows — `failure`.** Отвергнуто: держит PR, который ничего не
  ломает, пока main сам красный на Windows.

## Amendments

- **2026-10-29, ADR-0086** (`worfy-throughput` 30). Контекст «`success` — по зелёному gate full на Windows-ПК (ADR-0056, пункт 2)» для PR со scope `pc` больше не верен: такой PR вливается по `ci-ok`, а ПК проверяет `main` после merge. Правило «без регресса» действует для прицельной проверки ПК у PR, который чинит красный `main` на ПК (ADR-0086, пункт 5), и для gate full на `main`.
