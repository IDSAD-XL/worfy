# 0092 — История Run: два новых события Journal, шкала вычисляется при открытии
Дата: 2026-11-01. Статус: принят. Epic `worfy-flight-recorder`, Ticket 11; spec — `.scratch/worfy-flight-recorder/spec.md`
(«Источники и что меняется в них», «Решения владельца при приёмке», п. 1); решение 01, Q4; решение 04, Q1, Q4, Q7, Q8.

**Контекст.** Flight Recorder показывает Run Autopilot-а шкалой: когда Ticket взят, где ждал, когда кончился. Почти
всё для неё уже лежит в источниках, которые worfy читает: Journal Run-а (`<data dir>/autopilot/<run>.jsonl`), файлы
Ticket-ов, транскрипты Session, GitHub, логи gate. Двух фактов нет нигде. Файл Ticket-а хранит только текущую строку
`Status:`, поэтому история claim → blocked → done во время Run теряется, а у Silent mode и Ticket-ов без PR других
следов нет. Конец хода «Process gate queue» тоже не записан: в Journal есть только `gate-queue` в начале. Кроме того,
Journal не знает, в какую SDK session Orchestrator-а ушла Wave (с worfy-throughput ticket 52 каждая Wave после первой
уходит в новую), кто начал Run и был ли это Run по названным Ticket-ам (ADR-0091).

**Решение.**

1. В Journal два новых вида событий, и только они:
   - `ticket-status` — `ticket`, `state` (`claimed`, `blocked`, `done`, `open`), `statusAt?`, `reason?`
     (`Blocked reason:`), `waits?` (`Waits:`). Пишет Autopilot из своего подписчика `WorkflowHub`: на каждое изменение
     workflow, о котором сообщает watch, он читает модель и пишет строку для каждого Ticket-а Epic-а Run, чей статус
     (состояние вместе с временем, причиной и `Waits:`) отличается от прошлого чтения. Первое чтение — при старте,
     поэтому статус до Run строки не даёт; после `run-stopped` строк нет. Ticket со статусом, который не читается
     (`none`), строки не даёт.
   - `gate-queue-finished` — конец хода «Process gate queue», чем бы он ни кончился; пишется в `endGateQueue` перед
     `run-stopped`.
2. Три необязательных поля в существующих событиях (приёмка, Q1), новых видов они не добавляют:
   `wave-started.session` — id SDK session Orchestrator-а, в которую ушла Wave, то есть имя её транскрипта;
   `run-started.by` — `button`, `command` или `tool`; `run-started.tickets` — названные Ticket-ы, только у Run по
   названным Ticket-ам. Старые строки без этих полей читаются как раньше.
3. В Journal пишет только worfy main. Harness и gate в Journal не пишут и не меняются; исключение observer-а
   (`human-input`, решение 04, Q8) остаётся как было.
4. Шкала Run вычисляется при открытии экрана из источников. Своего индекса spans, кэша и копий источников нет
   (решение 01, Q4): подробности угасают вместе с источниками (логи gate, транскрипты), и экран это показывает.
5. ADR-0002 не нарушен: worfy по-прежнему не пишет статус Ticket-а и не владеет состоянием workflow. Он записывает в
   свой файл в своей папке данных (ADR-0005) то, что прочитал, и не копирует источник (решение 04, Q1).

**Цена.** Две строки `Status:` между двумя чтениями дают одну строку `ticket-status` — последнюю: watch сообщает об
изменении файлов, а не о каждой записи. Последний `done` перед концом Run попадает в Journal, только если watch успел
сообщить о нём до `run-stopped`; иначе его время остаётся в строке `Status:` самого файла Ticket-а. Смена статуса
вне Run не записывается совсем.

## Considered Options

- **Harness пишет события в Journal сам** (`ticket` при claim и done). Отклонено: Journal — файл worfy в его папке
  данных, Harness о нём не знает, и правка Harness задела бы все проекты и ПК (решение 04, Q4, Q7).
- **Индекс spans или копия источников в папке данных** ради долгой памяти. Отклонено: второе хранилище расходится с
  источниками, его надо чистить и мигрировать; вычисление при открытии дешевле (решение 01, Q4; решение 08, Q6).
- **Новый вид события для `session`, `by` и `tickets`.** Отклонено владельцем при приёмке (Q1): это свойства
  существующих событий, и старые читатели их просто не видят.
- **Писать `ticket-status` при каждом чтении workflow** (и после хода, и для бюджета). Отклонено: ticket и spec
  называют подписчика `WorkflowHub`; чтения после хода и так следуют за изменениями файлов, а лишние места записи
  смешали бы историю статусов с логикой цикла.
