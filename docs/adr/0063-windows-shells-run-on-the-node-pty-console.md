# 0063 — На Windows оболочки Terminal идут на консоли из пакета node-pty; main сам отвечает на её запрос и сам узнаёт о выходе оболочки
Дата: 2026-10-13. Статус: принят.

**Контекст.** ADR-0054 (полный порт под Windows) решил, какая оболочка идёт в Terminal на Windows
(пункт 4) и что pseudo-console там — ConPTY, без ветки winpty (пункт 2). На какой консоли node-pty
запускает оболочку, он не решал. По умолчанию это консоль системы; её хост — `conhost.exe`.

Факты ниже — из «Итога» Ticket-а `worfy-windows/22` (PR #280) и трёх кругов его ревью. У фактов о
Windows три пометки. **Замер на ПК** — снято на Windows-ПК владельца (Windows 11 Pro 25H2), Node
24.21.0 из Electron 44.5.1. **Прочитано** — исходники и файлы node-pty 1.1.0; пути `src/win/…`,
`src/windows…`, `lib/…` и `typings/…` — в `node_modules/node-pty`. **Модель на Mac** — JavaScript
node-pty для Windows над подменным native-слоем и xterm.js 6.0.0 с реестром Terminal-ов
(`TerminalRegistry`, `src/main/terminal/pty.ts`). С Mac на Windows ничего не запускалось.

- **Утечка до решения (замер на ПК).** Оболочка, которая вышла сама (`exit`), оставляла свой
  `conhost.exe` до выхода из worfy: 20 выходов — 20 `conhost.exe`.
- **Причина (прочитано, `src/win/conpty.cc`).** Когда оболочка вышла, поток ожидания убирает запись
  о pseudo-console (`:106`) раньше, чем зовёт callback выхода (`:108`). `kill()` после этого записи
  не находит и ничего не закрывает (`:547`, `:549`). Handle pseudo-console в JavaScript не
  попадает: туда идут номер записи, имена двух pipe и pid (`:303`, `:319-321`, `:454`).
- **Новой версии нет.** Стабильного node-pty новее 1.1.0 нет: в npm только `1.2.0-beta.15`
  (проверено на ПК и на Mac — по метаданным pnpm).

Этот ADR уточняет ADR-0054: к его пунктам 2 и 4 добавляет, на какой консоли идёт оболочка. ADR-0054
не правится, оба пункта в силе. Решение 5 ADR-0053 (Terminal показывают все экраны, где он открыт)
в силе и объясняет пункт 3 ниже: вывод получает каждый экран, поэтому консоли отвечает main.
ADR-0057 (окружение агента на Windows) не задет. Способ выбрал исполнитель Ticket-а 22 — Ticket
оставлял выбор ему. Ревью на Mac приняло его 2026-10-13, после трёх кругов.

**Решение.**

1. **На `win32` реестр запускает оболочки с `useConptyDll: true`** (`spawnShellPty`,
   `pty.ts:388-401`). node-pty грузит `conpty\conpty.dll` из папки рядом с `conpty.node`
   (прочитано, `conpty.cc:181`); та запускает `OpenConsole.exe`. Такую консоль node-pty отпускает
   сразу после старта оболочки (`conpty.cc:429-439`), и её хост уходит с последним процессом на
   ней. Замер на ПК: 20 выходов — 0 хостов консоли; оба файла подписаны Microsoft (статус `Valid`)
   и лежат в packaged-сборке вне `app.asar` — шаблон `asarUnpack` `node_modules/node-pty/**`
   (`electron-builder.yml:47-48`). Вызов `spawn` на macOS и Linux не меняется (`pty.ts:389`).
2. **Реестр сам останавливает поток node-pty, который читает вывод консоли, — сразу после
   `kill()`** (`stopOutputWorker`, `pty.ts:429-434`; вызов — `:1045`). На этой консоли `kill()`
   останавливает поток, только когда после него приходит вывод (прочитано,
   `lib/windowsPtyAgent.js:153-160`). Замер на ПК: без остановки 20 оболочек оставляют около 20
   потоков; с ней число потоков процесса держится в пределах 15–17.
3. **На запрос консоли отвечает main.** При старте оболочки консоль шлёт
   `ESC[1t ESC[c ESC[?1004h ESC[?9001h`; `ESC[c` — запрос device attributes. Реестр находит `ESC[c`
   и `ESC[0c` в выводе, пишет в pty `ESC[?1;2c` — так ответил бы xterm.js — и убирает запрос из
   вывода. Его нет ни на экранах, ни в сохранённом выводе — последних 256 KB, которые main отдаёт
   каждому новому view (`src/main/terminal/console-request.ts`; `pty.ts:830-845`). Запрос может быть
   разрезан между двумя кусками: конец куска ждёт следующего до 50 ms. Запрос, который пишет
   программа в оболочке, OpenConsole 1.23 тоже передаёт терминалу (замер на ПК); main отвечает и на
   него.
   - **Без ответа оболочка молчит три секунды** (замер на ПК): приглашение через 3275–3283 ms, с
     ответом — через 274–276 ms; консоль системы не спрашивает — 297–318 ms. Оболочку без экрана
     открывает первый запуск: `gh auth login` (по коду, `src/renderer/shell/FirstRun.tsx:178`).
   - **Ответ экрана оказался дефектом** (первая версия PR #280). Отвечает каждый xterm.js, которому
     достался вывод, в том числе сохранённый. Консоль берёт первый ответ; следующий передаёт
     оболочке как набранный текст (замер на ПК; прочитано в `OpenConsole.exe`). Замер на ПК,
     packaged-сборка: после перезагрузки окна в строке приглашения стоит `[?1;2c`; программа,
     ждавшая одну клавишу, получает ESC. Модель на Mac с ответом из main: три xterm.js на одном
     Terminal — в pty уходит один ответ.
4. **О выходе оболочки реестр узнаёт сам.** На Windows он раз в 500 ms читает у node-pty код
   выхода (`exitCodeKnown`, `pty.ts:415-418`). Через 1 s после чтения, которое нашло код, он
   сообщает о выходе (`pty.ts:852-867`). Событие node-pty, раньше или позже, ничего не меняет.
   Отказ node-pty в `resize` реестр пишет в лог и не бросает (`applySize`, `pty.ts:707-718`).
   - **Почему.** С `useConptyDll` callback выхода только запоминает код (прочитано,
     `src/windowsPtyAgent.ts:224-230`); событие `exit` приходит, когда закрылся вывод консоли
     (`src/windowsTerminal.ts:105-108`). Консоль живёт, пока на ней есть процесс. Замер на ПК:
     оболочка оставила на консоли программу на 30 s и вышла — событие пришло через 30,4 s
     (PowerShell) и 30,1 s (Git Bash); на консоли системы — через 1,1 s. Всё это время Terminal
     считался работающим, а `resize` бросал исключение.
5. **После сообщения о выходе реестр на Windows ничего от этого pty не доставляет** — ни на
   экраны, ни в сохранённый вывод (`pty.ts:812`). Придержанный конец куска уходит до сообщения
   (`:849`, `:861`). Почему: остановка потока из пункта 2 срабатывает через 1 s после последнего
   вывода — каждый новый вывод сдвигает её timer (прочитано, `lib/windowsConoutConnection.js:103-109`,
   `lib/windowsPtyAgent.js:157-159`). До того node-pty читает консоль дальше, а событие вывода не
   называет оболочку. Замер на ПК, packaged-сборка, руками: программа на консоли печатала `tick` каждые
   100 ms; после Restart на экране новой оболочки — 26 строк `tick` и нет её приглашения
   (1 запуск). С правилом — приглашение и вывод команды, строк `tick` нет (2 запуска). Вне Windows
   вывод после выхода без закрытия, как раньше, хранится до следующего открытия (есть test).
6. **Ошибку записи во входной сокет node-pty реестр слушает и пишет в лог, один раз на оболочку**
   (`pty.ts:391-399`). Сам node-pty слушателя `error` не ставит (прочитано,
   `lib/windowsPtyAgent.js:82-87`); без слушателя такая ошибка в main process — необработанное
   исключение. Замер на ПК: одна запись в миллисекунду через момент выхода оболочки даёт `EAGAIN` в
   10 оболочках из 10; на консоли системы — в 0 из 10.
7. **Четыре обращения к приватным полям node-pty; версия закреплена.** Каждое обращение проверяет,
   что поле есть. node-pty стоит ровно на 1.1.0 (`package.json:36`): обновление — отдельное
   решение, перед ним перечитываются все четыре.

   | Поле `_agent` | Что делает реестр | Если поле исчезнет |
   |---|---|---|
   | `_getConsoleProcessList` | подмена пустым списком до `kill()` | лог; pty после `exit` не закрыт |
   | `_conoutSocketWorker.dispose` | вызов после `kill()` | лог; поток остаётся до выхода из worfy |
   | `exitCode` | чтение раз в 500 ms | молча; о выходе сообщает только событие node-pty |
   | `inSocket` | слушатель `error` | молча; ошибка записи — необработанное исключение |

   «Не закрыт»: для оболочки, которая вышла сама, реестр тогда не зовёт ни `kill()`, ни остановку
   потока (`pty.ts:1036`). Первое обращение — из Ticket-а `worfy-windows/10`, для pty на консоли
   системы: там `kill()` запускает helper и спрашивает у него список процессов консоли. К консоли
   оболочки, которая уже вышла, helper подключиться не может, и через 5 s node-pty сам завершил бы
   процесс с pid оболочки (прочитано, `lib/windowsPtyAgent.js:140-149`, `:189-193`). На консоли из
   пакета `kill()` этот метод не зовёт (прочитано, `lib/windowsPtyAgent.js:137-160`).

**Последствия.**

- **Программа, которую оболочка оставила на своей консоли, завершается примерно через 1,5 s после
  выхода оболочки.** Реестр сообщает о выходе и закрывает pty, а с ним консоль (прочитано,
  `lib/windowsPtyAgent.js:155`). Замер на ПК, packaged-сборка: Git Bash, `sleep 25 & exit 4` —
  `exit 4` через 1600 ms; сразу после этого под worfy нет ни `OpenConsole.exe`, ни `sleep.exe`. До
  этого решения, на консоли системы, такая программа жила дальше на хосте консоли, который никто не
  закрывал («Итог» Ticket-а 22).
- **Закрытие Terminal завершает оболочку сразу, через `TerminateProcess`,** с кодом 1 (прочитано,
  `conpty.cc:562-564`), а не событием закрытия консоли. Пишет ли Git Bash историю, не мерили.
- **Объект pseudo-console оболочки, которая вышла сама, node-pty по-прежнему не закрывает.**
  Остаются два handle на каждую такую оболочку (прочитано в коде `conpty.dll`), процесса за ними
  нет. Сколько handle копится у процесса worfy, не мерили (Ticket `worfy-windows/42`).
- **Версия консоли заморожена вместе с node-pty:** OpenConsole 1.23.2510.08001, пока node-pty
  1.1.0. Опция `useConptyDll` в typings помечена `(EXPERIMENTAL)` (`typings/node-pty.d.ts:98-104`).
- **Чистый runner GitHub не судит правки Terminal на Windows:** test-ы с настоящей оболочкой там
  падают и на main (Ticket `worfy-windows/41`). Свидетельство о Windows — ПК владельца.
- **На остальное по-прежнему отвечает каждый экран:** на другие запросы программ (положение
  курсора, цвета) и на focus reports — `ESC[?1004h` шлют на старте обе консоли (замер на ПК). Эти
  ответы считаются вводом и повторяются при показе сохранённого вывода — Ticket `worfy-windows/39`.
- **Падение node-pty при одновременном `kill()`** (код 3221225477) — Ticket `worfy-windows/40`.
  Замер на ПК: по одному разу на каждой из двух консолей.
- **Три обращения из пункта 7, кроме первого, не закреплены test-ом вне Windows.** Это и остальные
  замечания low ревью — Ticket `worfy-windows/42`.
- **Не проверено:** SmartScreen и Defender на установленной сборке (запускалась распакованная
  папка); Windows 10, которую поддерживает ADR-0054; два экрана на одном Terminal одновременно.

## Considered Options

- **Консоль из пакета node-pty, `useConptyDll`** (выбрано; вариант (б) Ticket-а 22).
- **Новая версия node-pty** (вариант (а)). Стабильной нет. В upstream `main` логика та же — это
  прочитано через пересказ двух файлов; сам код upstream не запускался.
- **Закрывать pseudo-console системы самим.** Невозможно: её handle в JavaScript не попадает, а
  `kill()` после выхода оболочки записи уже не находит (прочитано, см. контекст).
- **Завершать оставшийся `conhost.exe` по pid.** Не пробовали: ни Ticket 22, ни его ревью этот
  способ не разбирали. Реестр намеренно закрывает pty по handle-ам node-pty, а не по pid: pid мог
  достаться другому процессу (`pty.ts:1021-1022`). Завершение хоста по pid вернуло бы этот риск.
- **Свой native-вызов** (вариант (в) Ticket-а 22 — «только если (а) и (б) не подошли»). Handle
  pseudo-console из node-pty не выходит, поэтому это правка его native-кода. Не понадобился: подошёл
  (б). Сборка node-pty из исходников на Windows падает, worfy берёт готовый prebuild
  (`scripts/postinstall.mjs:7-9`): свой native-код значил бы и свою сборку.
- **На запрос консоли отвечает xterm.js** — первая версия PR #280. Отвергнуто по замеру пункта 3.
- **Дольше ждать перед сообщением о выходе или отсчитывать секунду от последнего вывода,** как
  node-pty на консоли системы. Не нужно. Замер на ПК (записан в комментарии третьего круга ревью
  PR #280; в «Итоге» Ticket-а 22 его нет): оболочка печатает 200 000 или 500 000 строк и сразу
  выходит — 8 запусков из 8 без потери строки, в том числе с программой на консоли. Последний кусок
  приходит за 20–50 ms до того, как известен код выхода; после сообщения о выходе — ничего.
