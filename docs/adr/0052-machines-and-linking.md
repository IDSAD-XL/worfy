# 0052 — Machine и Linked machine: два worfy связываются по коду в локальной сети
Дата: 2026-10-07. Статус: принят.

**Контекст.** 2026-10-07 владелец попросил второй экран для worfy: работа идёт на Mac, а
интерфейс он открывает на Windows-ПК в той же локальной сети. В разборе запрос вырос. worfy должен
работать на Windows целиком, вместе с агентами (ADR-0054). Если worfy стоит у пользователя на
нескольких компьютерах, пользователь выбирает, на каком из них идёт работа. Оба экрана открыты
одновременно (ADR-0053). Сеть пока только локальная.

Что есть в коде (прочитано, ничего не запускалось):

- worfy знает один компьютер. Renderer говорит с main через мост IPC: preload выставляет
  `window.worfy` (`src/preload/index.ts:29`), renderer берёт его в одной точке — `windowBridge()`
  (`src/renderer/ipc.ts:41`).
- Каналов 91: 72 запроса и 19 событий из main. Все в JSON, со схемами zod
  (`src/shared/ipc/channels.ts:36-42`, ADR-0006). Ответ всегда `{ok: true, value}` или
  `{ok: false, error}` (`channels.ts:76`). Бинарных данных нет: вложения идут base64-строкой
  (`src/shared/agent/attachments.ts:29`). Значит, тот же контракт можно передать по сети без
  потерь.
- main регистрирует handlers одним циклом (`src/main/ipc/index.ts:182`) через интерфейс
  `IpcMainLike` (`:51`), а не через сам `ipcMain`. Сетевой адаптер встаёт в эту точку.
- У моста нет аутентификации. Main проверяет только, что вызов пришёл из кадра самого worfy
  (`event.senderFrame.url`, `src/main/ipc/index.ts:130-131`; правило `isAppUrl`,
  `src/main/index.ts:79-80`). Через мост запускаются shell в Terminal и агенты Claude, то есть
  исполняется код на машине. Сетевой вход без своей проверки отдал бы машину любому в сети.
- Папку Project выбирают нативным диалогом ОС (`dialog.showOpenDialog`,
  `src/main/ipc/projects.ts:45`). Диалог показывает диски той машины, на которой открыт.
- Страница в браузере вместо второго worfy упирается в два места. `crypto.randomUUID()` при
  создании Node-а (`src/renderer/canvas/history.ts:284`) есть только в secure context (HTTPS или
  loopback), а `http://192.168.x.x` им не является. Card показывается на схеме `worfy-card://`
  (ADR-0012; `src/main/cards/protocol.ts:249`; `frame-src worfy-card:` в
  `src/renderer/index.html:5`), а в браузере такой схемы нет.

**Решение.**

1. **Machine** — компьютер с worfy. У каждого Project ровно одна Machine: на ней его папка,
   Session-ы и агенты, worktree и Gate. Один репозиторий, открытый на двух Machine, — два разных
   Project-а; сводит их git, как и сейчас. Machine и Linked machine — новые канонические термины
   (ADR-0017).
2. **Linked machine** — другая Machine, связанная с этой. Связь двусторонняя: после связывания
   каждая из двух Machine — Linked machine для другой. «host» и «client» — роли одного соединения
   (чей Project открыт и откуда), а не виды устройств и не термины. Любой worfy бывает и тем, и
   другим.
3. **Список Project-ов** слева показывает Project-ы всех Linked machine, сгруппированные по
   Machine. У каждой Machine видно состояние: в сети, спит, недоступна. «Add Project» сначала
   спрашивает Machine, потом папку. Папку на Linked machine выбирают просмотром её файлов внутри
   worfy, а не нативным диалогом.
4. **Связывание.** «Link a machine» показывает worfy, найденные в сети через Bonjour (DNS-SD —
   объявление сервисов в локальной сети), и принимает адрес, введённый руками. Вторая Machine
   показывает на своём экране 6-значный код, его вводят на первой. Код одноразовый. После кода
   каждая Machine запоминает сертификат другой и получает токен устройства для входа к ней.
   Machine хранит только хэш выданного ею токена.
5. **Канал — TLS с запомненным сертификатом.** Каждый worfy сам выпускает себе сертификат.
   Доверие держится на сертификате, запомненном при связывании, а не на удостоверяющем центре:
   ставить корневой сертификат на другую машину не нужно. Соединение с другим сертификатом
   отклоняется, такую Machine связывают заново. Соединение — HTTP с переходом на WebSocket
   (upgrade). По нему идёт тот же контракт IPC, и принимающая сторона так же проверяет вход
   схемой (`src/main/ipc/index.ts:135`). Проверку «вызов из кадра worfy» для сетевого вызова
   заменяет проверка токена.
6. **Доступ к своим Project-ам по умолчанию выключен.** Переключатель «Linked machines can work
   with my Projects» по умолчанию выключен. Пока он выключен, Linked machine не работает с
   Project-ами этой Machine: не открывает их Canvas и ничего в них не запускает. Без действия
   пользователя на этой машине worfy сеть не слушает. Когда переключатель включён, Linked machine может в Project-ах всё, кроме действий,
   которым нужен рабочий стол машины Project-а (ADR-0053).
7. **Только локальная сеть.** Доступа из интернета нет: ни проброса порта, ни туннеля, ни
   relay-сервера.
8. **Проверка Host и Origin.** До перехода на WebSocket сервер сверяет заголовок `Host` со
   списком своих имён и адресов. Запрос с заголовком `Origin` веб-страницы он отклоняет. Отказ
   приходит до upgrade. Это защита от страницы в браузере, которая стучится в порт worfy с чужого
   сайта или через DNS rebinding (подмену адреса, на который указывает имя сайта, адресом в
   локальной сети). Проверка покрыта test-ами.
9. **Отзыв — с любой стороны.** Отозванная Linked machine теряет токен и запомненный
   сертификат, её открытые соединения закрываются. Вторая сторона узнаёт об отзыве сразу, если
   соединение открыто, иначе — отказом при следующем входе.
10. **Токены и коды связывания не пишутся в логи** и журналы worfy.

**Последствия.**

- Через worfy по сети теперь можно исполнять код на машине: Terminal и агенты. Защита держится
  на четырёх вещах: доступ выключен по умолчанию, одноразовый код, TLS с запомненным
  сертификатом, токен устройства. Ошибка в любой из них открывает машину Project-а.
- Свой Bonjour-сервис на macOS 15 и новее вызывает запрос разрешения Local Network (Apple
  TN3179). Принимать входящие соединения это разрешение не требует. Обнаружение worfy на Windows
  не проверялось. Имена `.local` Windows 10/11 разрешает встроенным mDNS (по вторичному
  источнику); найдёт ли он сервис worfy — неизвестно. Адрес, введённый руками, работает без
  обнаружения.
- Firewall macOS на Mac владельца выключен (`socketfilterfw --getglobalstate` вернул «disabled»).
  Если его включить, с ad-hoc подписью (`electron-builder.yml:41`) вопрос «Accept incoming
  connections?» будет приходить после каждой пересборки. Это лечит подпись — Epic E4 (подпись,
  нотаризация, внешние пользователи). Как себя поведёт firewall Windows — не проверено.
- Первая проверка связи — dev-сборка и Stable copy на одном Mac, ещё без второго компьютера.
  Значит, Machine нельзя опознавать по имени компьютера, а два worfy на одном Mac не могут делить
  один порт. Папки данных у них уже разные (ADR-0023).
- Epic worfy-link (Linked machines) начинается после закрытия Epic-а worfy-harness (Harness как
  plugin Claude Code) и идёт параллельно с Epic-ом worfy-windows (ADR-0054, ADR-0056). Связь Mac и
  Windows проверяется, когда worfy уже работает на Windows.
- Без Linked machine worfy ведёт себя как сейчас: порт закрыт, в списке только свои Project-ы.
- Ticket-ам Epic-а worfy-link остаётся решить:
  - как Machine опознаёт себя и где хранит id, свой сертификат, запомненные сертификаты и токены;
  - когда открыт порт для связывания, пока переключатель выключен, и видит ли Linked machine в
    это время хотя бы список Project-ов этой Machine;
  - как код подтверждает именно эти два сертификата, чтобы тот, кто встал посередине в момент
    связывания, не запомнился вместо настоящей Machine; срок жизни кода и число попыток;
  - как сервер отличает адрес локальной сети от остальных;
  - кто держит соединение на вызывающей Machine. Направление — main, чтобы токен и сертификаты
    не попадали в renderer;
  - как отличить Machine, которая спит, от недоступной.

## Considered Options

- **Полный worfy на каждой Machine, два worfy связываются** (выбрано). Связь работает в обе
  стороны, на Windows работают и агенты (ADR-0054), renderer тот же, что на машине Project-а.
- **Страница в браузере, которую раздаёт worfy на Mac.** Отвергнуто: владелец хочет, чтобы на
  Windows шла работа с агентами, а не только экран. Кроме того, странице нужен secure context
  (`crypto.randomUUID`, `history.ts:284`; уведомления браузера). Это либо TLS с установкой
  корневого сертификата на Windows, либо polyfill и токен по сети открытым текстом. Card на
  `worfy-card://` пришлось бы раздавать по HTTP с отдельным origin на каждую Card.
- **Тонкий Electron-клиент для Windows: только renderer и сетевой мост.** Отвергнуто по той же
  причине: агентов на Windows нет. Сверх того — своя сборка, расхождение версий клиента и Mac
  после каждого релиза, установка неподписанного exe. Цена почти как у полного порта, пользы
  меньше.
- **host и client как виды устройств, связь в одну сторону (Windows только открывает Mac).**
  Отвергнуто: владелец считает роли абстрактными. С полным портом у Windows свои Project-ы, и Mac
  должен открывать их так же.
- **Один Project на двух Machine (один репозиторий — один Project).** Отвергнуто: папка, агенты,
  worktree и Gate живут на одной машине. Две копии репозитория — два состояния, их сводит git.
- **Нативный диалог выбора папки для «Add Project» на Linked machine.** Отвергнуто: диалог
  показывает диски своей машины, а папка нужна на машине Project-а.
- **Пароль или токен без TLS (HTTP и polyfill `randomUUID`).** Отвергнуто: токен, ввод в Terminal
  и текст Session-ов шли бы по сети открытым текстом.
- **TLS через свой удостоверяющий центр (mkcert) с установкой корневого сертификата на вторую
  машину.** Отвергнуто: лишний шаг установки на каждой машине и ключ центра, который нельзя
  отдавать. Сертификат, запомненный при связывании, даёт ту же проверку без центра.
- **Сетевой доступ включён по умолчанию.** Отвергнуто: через worfy исполняется код на машине.
  Без явного решения владельца машины доступа нет.
- **Доступ из интернета (проброс порта, туннель, relay).** Отложено: пока только локальная сеть.
