# 0112 — worfy отправляет ревью PR только по Submit пользователя
Дата: 2026-11-21. Статус: принят. Решение владельца 2026-11-20, Q2 (а) spec-а `.scratch/worfy-pr-review/spec.md`
(«Submit review из worfy — локальный черновик и один запрос из диалога, который показывает каждый комментарий ровно;
новый ADR»); глубина ревью `max` — Q7 того же раунда. Epic `worfy-pr-review`, Ticket 11.

**Контекст.** ADR-0105, пункт 4, разрешал main только две записи на GitHub: ответ в нити ревью и комментарий в
разговоре PR; отправки review не было. Epic `worfy-pr-review` даёт ревьюить чужие PR во вкладке Pull requests:
черновик ревью лежит на машине пользователя (`<Profile folder>/state/pr-review/`, Ticket 05), его пишет человек
(Ticket 10) или Session Agent review (Ticket 08). Отправка review — запись другого веса: Approve считается в
одобрениях, которые требует правило базовой ветки, и открывает merge чужого кода.

**Решение.**

1. **Одна запись, только по щелчку.** Main отправляет ревью одним `POST /repos/{o}/{r}/pulls/{n}/reviews` и только
   по Submit review (щелчок или ⌘↵; Enter на кнопке не отправляет) в диалоге Finish review
   (`src/renderer/pr-review/FinishReviewDialog.tsx`). Код записи — один модуль, `src/main/github/pr-review-submit.ts`.
   Канал `prReview.submit` — `local`: Linked machine его не вызывает ни при каком уровне доступа.
2. **Уходит ровно показанное.** Диалог держит Summary, событие и каждый комментарий так, как они показаны. Main
   перечитывает файл черновика и отказывает, если показанного комментария там больше нет; тело запроса —
   `{commit_id, event, body, comments}`, комментарии в виде `payload` черновика, без добавлений. Убранный в диалоге
   комментарий не уходит; в файле `submitted` остаются только ушедшие.
3. **Всегда с событием.** Comment, Approve или Request changes выбирает человек; диалог всегда открывается на
   Comment, `suggestedEvent` агента — только строка «The agent suggests: …». Запрос без `event` (pending review на
   GitHub) main не делает никогда. Approve и Request changes на своём PR — отказ (автор PR сравнивается с аккаунтом).
4. **Порядок: проверить → отметить → один POST.** Черновик, чей Submit GitHub не подтвердил, сначала ищет его на GitHub
   (пункт 6), и только потом — проверки ниже.
   - `review-draft-lint` над текстами (следы workflow, подпись ИИ, личные данные, длина); находка — отказ, ни одного
     запроса. `lint.json` Team reviewer-а Project-а — с флагом `--untiered` (у черновика человека нет tier-ов: каждому
     тексту наибольшая длина файла); без `lint.json` — длины шаблона. Без флага `--rules` по-прежнему требует tier-ы.
   - Head PR перечитывается. Сдвинулся с открытия диалога — отказ без записи; диалог говорит «Your comments are on
     <a>; the head is <b>.» и предлагает Submit on <a>.
   - Каждый комментарий проверяется по diff-у GitHub на своём коммите: на изменённой строке, `start_line` в той же
     hunk, что `line`. Не так — отказ всего Submit-а, ни одного запроса: такой комментарий GitHub отверг бы целиком
     вместе с ревью.
   - Пока Session Agent review пишет черновик, Submit отказывает.
   - Черновик получает `state: 'submitting'`, затем один POST, затем `submitted` и `reviewUrl`; PR inbox читает PR
     снова (chip одобрений).
5. **`commit_id` — коммит, на котором стоят строки.** `commit_id = anchoredOn ?? startedOn`: если комментарии
   перенесены на новый head (`anchoredOn`, Ticket 10), их строки — строки этого коммита. Spec
   (`.scratch/worfy-pr-review/spec.md:528`) называет `startedOn`; поправка записана там же.
6. **Без второго POST.** Автоматического повтора нет. Отметка `submitting` хранит время (`submittingAt`). Ответ 5xx,
   обрыв сети или timeout gh — черновик остаётся с «GitHub did not confirm the review: <причина>» и с ушедшими
   текстами. Пока так (или пока висит `submitting`, оставленный обрывом), тексты заперты: Review mode их не правит,
   диалог открывается на ушедших событии, Summary и комментариях, main отказывает Submit-у других текстов. Следующий
   Submit до всех прочих проверок читает `GET …/pulls/{n}/reviews` и ищет ревью этого аккаунта на том же
   `commit_id` с тем же `body`, в любом состоянии, данное не раньше отметки минус 2 минуты на расхождение часов, и с
   теми же комментариями к строкам (`GET …/reviews/{id}/comments`: путь и текст каждого). Нашёл — только отмечает
   `submitted`. Не нашёл — черновик снова обычный, и Submit идёт дальше как новый. Ответ 4xx (кроме 408) — GitHub
   отказал, ревью нет: причина GitHub в диалоге, черновику возвращаются комментарии, какими они были до отметки
   (убранный в диалоге снова в черновике).
7. **Только аккаунтом Profile-а.** Запрос идёт с токеном `github.account` Profile-а Project-а; Profile без него —
   отказ, как у Send (ADR-0105). gh-логин машины не используется.
8. **Чего main не делает:** resolve нитей, re-request review, dismiss, merge, продолжение pending review,
   начатого на github.com.

**Что меняется в прежних ADR.** ADR-0105, пункт 4: третья запись — отправка review по этому ADR. ADR-0002:
исключение «main пишет» расширено той же записью. Обе поправки дописаны в `## Amendments` этих ADR.

**Последствия.**

- Contract test `test/contract/pr-review-submit.test.ts` на gh stand-in проверяет: ни одной записи без щелчка, на
  находке lint-а, на сдвинутом head и на комментарии вне diff-а; ровно один POST с телом байт в байт; повтор без
  второго POST.
- Если у пользователя висит pending review, начатый на github.com, GitHub может отказать в новом ревью; worfy
  показывает причину GitHub и pending review не трогает. Как именно отвечает GitHub — не проверено на тестовом
  репозитории (Ticket 11, пункт 8).
- Fine-grained токен без «Pull requests: write» — отказ GitHub с его причиной в диалоге.

## Considered Options

- **Main отправляет показанное по Submit, один POST** (выбрано, Q2 (а)).
- **Pending review на GitHub, отправка на сайте.** Не выбрано: запись на GitHub до щелчка, забытый pending review
  висит, а пользователь уходит из worfy в браузер.
- **Session отправляет ревью по просьбе.** Не выбрано: шаг публикации держит модель; Agent review может одобрить чужой
  код без человека.
- **Отправить остальные комментарии, а не попавшие на изменённые строки пометить «Not posted»** (так было в
  прототипе). Не выбрано: GitHub отвергает весь review с одним таким комментарием, а молча выкинутый комментарий
  меняет смысл ревью; человек убирает или переносит его сам.
- **`commit_id = startedOn` всегда** (как в spec). Не выбрано: после переноса на новый head строки комментариев —
  строки `anchoredOn`, и на `startedOn` GitHub поставил бы их не туда.
