# 0104 — Один Ticket может охватывать несколько репозиториев Project-а: по worktree и PR в каждом, один verdict, `done` после всех merge-ей; частично заменяет ADR-0045, пункт 1
Дата: 2026-11-09. Статус: предложен. Epic `worfy-multi-repo-ticket`; spec — `.scratch/worfy-multi-repo-ticket/spec.md`
(черновик для владельца); основание — Ticket 80 Epic-а `worfy-polish`. Вступает в силу, когда владелец примет spec;
до этого действует пункт 1 ADR-0045 без изменений.

**Контекст.** ADR-0045, пункт 1: «Один Ticket — один репозиторий… У Ticket-а одна ветка, одно worktree и не больше
одного PR». Функция через несколько репозиториев — цепочка Ticket-ов со связью `Blocked by`. Вариант «Один Ticket —
несколько PR» владелец тогда отверг: на одну строку `Status:` приходилось бы несколько веток, вердиктов Gate и CI,
`ticket done --pr N` принимает один PR, а Ticket закрывался бы только после merge-ей в разных репозиториях.

На практике цепочка Ticket-ов хуже для правки, которая задевает библиотеку и её потребителя: ревьюер каждого PR видит
половину правки и не может проверить стык; Ticket потребителя ждёт полного цикла Ticket-а библиотеки (две Wave
подряд); «Готово, когда» и доказательства функции лежат только во втором Ticket-е; API библиотеки фиксируется до
того, как написан вызывающий код. 2026-11-09 владелец попросил снять ограничение («да» — заменить пункт 1). Два PR
по-прежнему неизбежны: у GitHub нет PR через несколько репозиториев.

**Решение** (предложено; вопросы Q1–Q8 spec-а — за владельцем, ниже — рекомендованные ответы).

1. **Ticket Project-а над несколькими репозиториями может назвать несколько репозиториев** — по строке `Repo:` на
   каждый, имена из `_resolved.repos`. Порядок строк — порядок merge-а: сначала то, от чего зависят другие.
2. **Одна ветка — одно имя во всех репозиториях** (строка `Branch:` одна). Ключ ветки — пара (repo, branch).
3. **По worktree и по PR на каждый репозиторий.** Строки `PR:` несут имя репозитория: `PR: <repo>#N`. Описание каждого
   PR ссылается на остальные PR правки и называет порядок merge-а; в Silent mode — только ссылкой GitHub на PR, без
   имени Epic-а, номера Ticket-а и других следов workflow (ADR-0042).
4. **CI — у каждого PR свой; факт CI Ticket-а — сумма**: красный любой PR — красный Ticket.
5. **Один verdict ревью на Ticket**, на набор head-ов всех его PR. Отметка `review` ставится на head каждого PR. Новый
   head любого PR снимает verdict всего Ticket-а.
6. **Merge — по порядку строк `Repo:`, и каждое начало этого порядка — рабочее состояние** всех репозиториев:
   implementer делает ранние PR совместимыми со старыми потребителями, ревьюер это проверяет. Правку, которую так не
   разбить, `land` вливает целиком, только когда все PR зелёные. Если влита часть, Ticket остаётся `claimed` и
   доделывается в том же Ticket-е; revert влитого PR — решением владельца.
7. **`done` — когда влиты все PR из строк `Repo:`.** Нового статуса нет: частично влитый Ticket — `claimed`, а
   «влит 1 из 2» видно по фактам PR. `ticket done` с неполным набором PR отказывает.

**Что меняется в прежних ADR.** ADR-0045, пункт 1, в части «у Ticket-а одна ветка, одно worktree и не больше одного
PR» заменён пунктами 1–7 выше для Ticket-а с несколькими строками `Repo:`. Цепочка Ticket-ов со связью `Blocked by`
остаётся допустимой, а для правки, которую нельзя ни разбить на рабочие шаги, ни влить разом, — нужной. Пункты 2–4
ADR-0045 (Node Ticket-а показывает его репозиторий; Project над несколькими репозиториями — всегда Silent mode; финиш
зависит от прав) в силе. ADR-0018 (Project — папка с workflow) не меняется.

**Последствия.**

- Ticket с одной строкой `Repo:` или без неё работает как сегодня: одна ветка, одно worktree, `PR: #N`,
  `ticket done --pr N`. Сам worfy — Project из одного репозитория, для него ничего не меняется.
- Меняются `harness/bin/ticket`, `epic-status`, `land`, `wave-brief`, модель Ticket-а и стадии Pipeline в worfy,
  Pipeline board, Ticket Node и тексты skill-ов `ship-ticket` и `epic-wave` — Ticket-ы 01–07 Epic-а.
- Пока не влиты Ticket-ы, которые учат читателей новому формату, Ticket-ы с несколькими `Repo:` не пишутся: старые
  `epic-status` и worfy берут одну строку `Repo:` и одну `PR:`.
- Половина правки в `main` двух репозиториев становится обычным промежуточным состоянием. Её безопасность держится на
  проверке ревьюером, что каждое начало порядка merge-а работает.

## Considered Options

- **Несколько `Repo:`, одна ветка, `PR: <repo>#N`, merge по порядку с рабочими префиксами** (предложено).
- **Всё или ничего: ни одного merge-а, пока не зелёные все PR, потом все подряд.** Не выбрано правилом по умолчанию:
  окно половины правки всё равно есть (merge второго может упасть), и вариант не работает, когда CI потребителя видит
  библиотеку только из её `main`. Остаётся исключением для правки без рабочих префиксов.
- **Независимые PR в любом порядке.** Отвергнуто: половину правки ничто не закрывает.
- **Своя ветка на каждый репозиторий.** Не выбрано: правка одна, и ключ (repo, branch) не требует второго имени.
- **Новый статус `merging` для частично влитого Ticket-а.** Не выбрано: его пришлось бы учить `ticket`, `epic-status`,
  worfy и skill-ы, а факт виден по PR.
- **Оставить ADR-0045, пункт 1** (цепочка Ticket-ов). Не выбрано владельцем 2026-11-09 по причинам из «Контекста».
