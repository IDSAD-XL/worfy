# 0104 — Один Ticket может охватывать несколько репозиториев Project-а: ветка и PR в каждом, один verdict, стадия release, `done` после всех merge-ей; частично заменяет ADR-0045, пункт 1
Дата: 2026-11-09. Статус: предложен. Epic `worfy-multi-repo-ticket`; spec — `.scratch/worfy-multi-repo-ticket/spec.md`
(черновик; решения владельца 2026-11-09, Q0–Q8, в нём записаны); основание — Ticket 80 Epic-а `worfy-polish`; критика —
`docs/product/critic/worfy-multi-repo-ticket-2026-11-09.md` (Split). Вступает в силу, когда владелец примет spec; до
этого действует пункт 1 ADR-0045 без изменений.

**Контекст.** ADR-0045, пункт 1: «Один Ticket — один репозиторий… У Ticket-а одна ветка, одно worktree и не больше
одного PR». Функция через несколько репозиториев — цепочка Ticket-ов со связью `Blocked by`. Вариант «Один Ticket —
несколько PR» владелец тогда отверг: на одну строку `Status:` приходилось бы несколько веток, вердиктов Gate и CI,
`ticket done --pr N` принимает один PR, а Ticket закрывался бы только после merge-ей в разных репозиториях.

Для правки, которая задевает библиотеку и её потребителя, цепочка Ticket-ов хуже: ревьюер каждой стороны видит
половину правки и не может проверить стык; API библиотеки фиксируется до того, как написан вызывающий код; «Готово,
когда» и доказательства функции лежат только во втором Ticket-е; на Pipeline board — две карточки одной правки.
2026-11-09 владелец попросил снять ограничение. Два PR по-прежнему неизбежны: у GitHub нет PR через несколько
репозиториев.

Единственный сегодня Project над несколькими репозиториями работает так: одна рабочая папка без worktree
(`parallel: single`), PR открываются только после ревью агентов, вливают люди команды (`workflow.merge: null`), а
потребитель видит библиотеку только через выпущенную версию (диапазон версий в `package.json`, публикация по tag-у).

**Решение** (владелец, 2026-11-09, ответы Q0–Q8 spec-а).

1. **Ticket Project-а над несколькими репозиториями может назвать несколько репозиториев** — по строке `Repo:` на
   каждый, имена из `_resolved.repos`. Порядок строк — порядок merge-а: библиотека первой, потребители после неё.
2. **Одна ветка — одно имя во всех репозиториях** (строка `Branch:` одна). Ключ ветки — пара (repo, branch).
3. **По PR на каждый репозиторий; строки `PR:` несут имя репозитория**: `PR: <repo>#N`. PR ничего не говорят друг о
   друге — ни ссылки, ни фразы. Связь PR живёт только в файле Ticket-а в Workflow folder и на Pipeline board worfy.
4. **Один verdict ревью на Ticket**, на набор head-ов веток (а после открытия — PR) всех его репозиториев. Отметка
   `review` ставится на head каждого. Новый head любого снимает verdict всего Ticket-а.
5. **CI — у каждого PR свой; факт CI Ticket-а — сумма**: красный любой PR — красный Ticket, кроме CI потребителя,
   который ждёт release (пункт 6).
6. **Release библиотеки и подъём версии у потребителя — стадия Ticket-а.** Ветка потребителя несёт подъём версии;
   строка `Release:` файла Ticket-а называет tag или опубликованную версию, которой она ждёт. PR потребителя остаётся
   draft, пока release нет; Board показывает «waits for release <version>». worfy только ждёт и замечает release; сам
   release — шаг команды. В каталоге стадий Pipeline появляется стадия `release`.
7. **Каждый PR безопасен сам по себе.** Изменение библиотеки обратно совместимо: старые потребители после её merge-а и
   release работают. Implementer делает так, ревьюер проверяет.
8. **Частично влитый Ticket остаётся в работе** и чинится вперёд в том же Ticket-е. Нового статуса нет: Board
   показывает «1/2 merged». worfy никогда не предлагает revert влитого PR — это решение владельца или команды.
9. **`done` — когда влиты все PR из строк `Repo:`.** `ticket done` с неполным набором PR отказывает.

**Что меняется в прежних ADR.** ADR-0045, пункт 1, в части «у Ticket-а одна ветка, одно worktree и не больше одного
PR» заменён пунктами 1–9 выше для Ticket-а с несколькими строками `Repo:`. Цепочка Ticket-ов со связью `Blocked by`
остаётся допустимой. Пункты 2–4 ADR-0045 (Node Ticket-а показывает его репозиторий; Project над несколькими
репозиториями — всегда Silent mode; финиш зависит от прав) в силе. ADR-0018 (Project — папка с workflow) не меняется.
Merge остаётся за тем, кто вливает в Project-е сегодня.

**Последствия.**

- Ticket с одной строкой `Repo:` или без неё работает как сегодня: одна ветка, `PR: #N`, `ticket done --pr N`. Сам
  worfy — Project из одного репозитория, для него ничего не меняется.
- Меняются `harness/bin/ticket`, `epic-status`, `wave-brief`, каталог стадий Pipeline (`release`), модель Ticket-а и
  стадии в worfy, Pipeline board, Ticket Node и тексты skill-ов `ship-ticket` и `epic-wave` для `parallel: single`
  через несколько checkout-ов — Ticket-ы 01–07 Epic-а.
- `land` через несколько репозиториев и `parallel: worktrees` через несколько репозиториев не делаются: ни один Project
  над несколькими репозиториями сегодня не даёт агенту вливать. Это отдельное решение, когда такой Project появится.
- Пока не влиты Ticket-ы, которые учат читателей новому формату, Ticket-ы с несколькими `Repo:` не пишутся.
- Выигрыша во времени до merge-а потребителя нет: между merge-ами стоит release. После release потребитель может
  получить новый head (lockfile) и новое ревью этой дельты.

## Considered Options

- **Несколько `Repo:`, одна ветка, `PR: <repo>#N`, стадия release, PR без ссылок друг на друга, merge — как в
  Project-е сегодня** (выбрано владельцем 2026-11-09).
- **Ссылка на соседний PR и порядок merge-а в описании каждого PR.** Отвергнуто владельцем (Q6):
  «подозрительно и ненадёжно — лучше держать на машине».
- **`land` вливает PR Ticket-а по порядку `Repo:`** (черновик spec-а, Ticket 06). Отложено (Q0, Split; критика,
  возражение 1): в единственном Project-е над несколькими репозиториями вливают люди.
- **Всё или ничего: ни одного merge-а, пока не зелёные все PR.** Не выбрано: потребитель не может позеленеть до
  release библиотеки.
- **Своя ветка на каждый репозиторий.** Не выбрано (Q2): правка одна.
- **Новый статус `merging` для частично влитого Ticket-а.** Не выбрано (Q4): факт виден по PR.
- **Автоматический revert влитого PR, если второй не вошёл.** Не выбрано (Q7): revert — решение владельца или команды.
- **Оставить ADR-0045, пункт 1** (цепочка Ticket-ов). Не выбрано владельцем 2026-11-09 по причинам из «Контекста».
