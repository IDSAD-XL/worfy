# 0037 — Внутренность рамки Epic-а раскладывает ELK в Web Worker renderer-а; Layout хранит на Epic только смещение рамки и `collapsed`
Дата: 2026-10-07. Статус: принят.

**Контекст.** Места Ticket-ов в рамке Epic-а считала своя функция `layoutEpic`
(`src/renderer/canvas/epic-layout.ts`): колонка — уровень зависимостей, внутри колонки «сначала
ready, потом номер». Пересечения Edge-ей Blocked by никто не уменьшал, а сами Edge-и были кривыми
React Flow по умолчанию от handle к handle: Edge через уровень (Level 1 → Level 3) проходил через
Ticket-ы средней колонки. Ticket-ы и Node-ы Subagent-ов перетаскивались, их смещения лежали в
Layout (ADR-0011: `data["offset:<NN>"]` в Node-е `epic-frame`; Node `subagent-tree` с
`offset:<key>`). Владелец 2026-10-07 решил (spec.md Epic-а worfy-week, решения 15–17, 28, 29):
Edge-и ортогональные, по коридорам между колонками, в обход Ticket-ов; порядок в колонке — с
минимизацией пересечений, ready отмечен chip-ом, а не местом; Ticket-ы и деревья Subagent-ов не
перетаскиваются, их сохранённые смещения снимаются один раз; раскладку считает ELK в Web Worker,
до ответа видны прежние места. Решение принято вместе с Ticket-ом 03 Epic-а worfy-week.

**Решение.**

1. **Зависимость `elkjs` 0.12.0** (ELK — Eclipse Layout Kernel, перевод на JavaScript через GWT) —
   в `dependencies` с точной версией. Лицензия пакета — «EPL-2.0 OR GPL-3.0-or-later»; worfy берёт
   его на условиях EPL-2.0. EPL-2.0 — слабый copyleft на уровне файлов: код `elkjs` мы не меняем и
   поставляем как есть, отдельным модулем сборки, исходники остаются у Eclipse; на остальной код
   worfy условия EPL-2.0 не распространяются. Install-скриптов у пакета нет (`npm view elkjs@0.12.0
   scripts` — только скрипты сборки самого пакета), `allowBuilds` не меняется. Размер: пакет
   распакованный — 8,0 MB; в сборку попадает один файл `lib/elk.bundled.js` — 1,6 MB, 469 KB
   gzip, — и только в chunk worker-а раскладки, не в главный chunk renderer-а.
2. **Внутренность рамки раскладывает ELK, алгоритм layered.** Колонку Ticket-у задаёт наш уровень
   зависимостей, а не слои ELK: колонки Done (стопка или колонка), Level 1…N, Needs attention
   передаются ELK разбиением (`elk.partitioning.activate`, номер колонки в `partition`). ELK
   упорядочивает Ticket-ы внутри колонок с минимизацией пересечений и прокладывает Edge-и
   ортогонально (`elk.edgeRouting: ORTHOGONAL`) от правого handle блокера к левому handle
   блокируемого. Промежутки — не меньше прежних `COLUMN_GAP` и `ROW_GAP`; ширина рамки по
   заголовку — прежняя. ELK получает только Edge-и вперёд, между разными колонками. Edge внутри
   одной колонки (done → done в открытой стопке, цикл в Needs attention) и Edge назад (из Needs
   attention на уровень) прокладывает наша функция: по коридору справа от блокера, через
   промежуток колонки у блокируемого, по коридору слева от него, — тоже ортогонально и в обход
   Ticket-ов. Точки маршрута лежат в раскладке рамки относительно её угла; тип Edge-а
   `routed` (`src/renderer/canvas/edge-types/RoutedEdge.tsx`) рисует путь отрезками со
   скруглёнными углами, сдвиг рамки сдвигает маршрут без нового расчёта.
3. **ELK считает в Web Worker renderer-а** — один worker на окно, отдельный файл сборки (не
   `blob:`: CSP `script-src 'self'`, renderer грузится с `file://`). Запрос — на каждый Epic, у
   которого изменились входы раскладки (Ticket-ы, их состояния и блокеры, `collapsed`); ответ на
   устаревший запрос отбрасывается. Пока ответа нет, рамка показывает прежние места: последний ответ
   ELK для этого Epic-а, а до первого ответа — синхронный `layoutEpic` (порядок по номеру, Edge-и
   без маршрута, напрямую от handle к handle). Ответ заменяет места целиком, без анимации. Один
   запрос считает обе формы рамки — со свёрнутой и с открытой стопкой done: высота с открытой
   стопкой нужна колонке рамок как запас (ADR-0032, пункт 2), и раскрытие стопки не ждёт worker.
   В test-ах (jsdom, Worker-а нет) тот же модуль раскладки вызывается напрямую с ELK без worker-а.
4. **Кто размещает Derived Node-ы.** Внутренность рамки — ELK (пункт 2). Колонку рамок на плоскости
   по-прежнему считает правило ADR-0032 (`stackFrames`, `frameColumnX`), теперь с размерами рамок из
   ответа ELK. Дерево Subagent-ов раскладывает его источник (`sources/subagents.ts`) и сдвигает
   целиком от Node-ов Layout-а, как решил Ticket 28 Epic-а worfy-daily.
5. **Дополнение к ADR-0011: Layout хранит на Epic только смещение рамки (`x`, `y` Node-а
   `epic-frame`) и `data.collapsed`.** Ключи `data["offset:<NN>"]` (смещения Ticket-ов) и Node-ы
   `subagent-tree` (смещения Node-ов Subagent-ов) больше не пишутся и не читаются. Ticket-ы и Node-ы
   Subagent-ов не перетаскиваются (`draggable: false`), выделение Ticket-а остаётся. Рамка
   по-прежнему перетаскивается целиком за заголовок.
6. **Сохранённые смещения снимаются один раз, в main, при чтении `layout.json`**
   (`src/main/layout/upgrade.ts`, вызов из `LayoutStore`). Из каждого Node-а `epic-frame` убираются
   ключи `offset:*`, Node-ы `subagent-tree` удаляются; `x`, `y` и `collapsed` рамки остаются. Если
   что-то убрано — одна строка в лог на Project и запись файла; если нет — файл не переписывается.
   Нормализация идемпотентна и в историю ⌘Z не попадает.
7. **Ready — chip-ом, а не местом.** Ready Ticket получает chip «Ready» и цвет ready из F-SPEC;
   пунктирная рамка `ready-wave` вокруг ready Ticket-ов уходит, chip колонки «Ready wave · N»
   остаётся.
8. **Типы Edge-ей — точка расширения.** Тип Edge-а — файл в `src/renderer/canvas/edge-types/`,
   найденный так же, как типы Node-ов (`extensions.ts`); `Canvas.tsx` передаёт их React Flow один
   раз.

**Цена.**

- +1,6 MB в сборке приложения (chunk worker-а) и ещё одна зависимость с лицензией EPL-2.0, которую
  надо помнить при смене условий распространения worfy.
- Раскладка асинхронна: после смены статуса Ticket-а рамка какое-то время показывает прежние места,
  при первом открытии Project-а — синхронную раскладку по номеру, и затем места меняются скачком.
- Пользователь больше не может подвинуть Ticket или Node Subagent-а; сделанные раньше смещения
  теряются при первом запуске новой версии без возможности отмены.
- Высота рамки и колонки зависят от ELK: длинный Edge (через уровень) раздвигает Ticket-ы средней
  колонки, рамка может стать выше, чем при раскладке по строкам.
- Маршруты Edge-ей внутри одной колонки и назад прокладывает наш код, а не ELK: пересечения среди
  них не минимизируются.

Источник: Ticket 03 Epic-а worfy-week (`.scratch/worfy-week/issues/03-elk-раскладка-рамок-epic-ов.md`),
решения владельца 2026-10-07 №15–17, 28, 29 (`.scratch/worfy-week/spec.md`). ADR-0011 остаётся в
силе, кроме смещений Ticket-ов (пункт 5); ADR-0032 остаётся в силе целиком.

## Considered Options

- **Своя эвристика порядка и свой обход Node-ов.** Не выбрано: минимизация пересечений (barycenter
  с перестановками) и ортогональная маршрутизация с разведением параллельных отрезков в коридоре —
  это заново написать то, что ELK уже делает и проверил; на рамках Auction ручная эвристика
  оставляла бы пересечения, а маршрутизатор — слипшиеся отрезки.
- **dagre.** Не выбрано: умеет layered и порядок с минимизацией пересечений, но не маршрутизирует
  Edge-и ортогонально в обход Node-ов — Edge через уровень по-прежнему шёл бы сквозь Ticket-ы, и
  маршрутизатор пришлось бы писать самим. Колонку по нашему уровню dagre тоже не держит.
- **ELK в main process.** Не выбрано: модель workflow и раскладка рамок живут в renderer
  (ADR-0011); ELK в main — это IPC туда и обратно на каждую смену Epic-а и расчёт, который блокирует
  event loop main, где идут Layout, Session-ы и Agent SDK. Main размер рамок не знает и знать не
  должен (ADR-0032, пункт 4).
- **ELK в главном потоке renderer-а.** Не выбрано: расчёт большой рамки занимает десятки миллисекунд
  и больше; в главном потоке он рвёт кадры при каждой смене статуса и ломает бюджет
  `test/e2e/epic-frame.spec.ts` (медиана ≥ 55 fps, самый долгий кадр ≤ 100 ms) — решение 29
  владельца.
- **ELK в Web Worker renderer-а** (выбрано, пункт 3).
