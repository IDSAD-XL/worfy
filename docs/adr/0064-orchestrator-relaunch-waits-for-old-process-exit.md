# 0064 — Relaunch Orchestrator-а ждёт выхода старого процесса Claude Code
Дата: 2026-10-15. Статус: принят.

**Контекст.** Relaunch — перезапуск Session Orchestrator-а (главной Session Project-а) с другим
режимом: без человека на время прогона Autopilot и снова с человеком после него. Старый процесс
Claude Code закрывается, новый продолжает ту же сохранённую сессию через `--resume`. До этого ADR
`Orchestrators.relaunch` закрывал старую Session и в том же синхронном шаге запускал новую.
`Session.close()` зовёт `close()` у запроса SDK и не ждёт выхода процесса. SDK 0.3.289 после
`close()` закрывает stdin процесса, через 2 s шлёт SIGTERM, ещё через 5 s — SIGKILL. Значит, старый
процесс мог до 7 s писать транскрипт той же сессии рядом с новым. Хуже всего это при Force stop
(ADR-0050): ход, который не кончился за `HALT_TURN_MS`, ещё идёт в старом процессе. Правило «два
процесса не пишут один транскрипт» в worfy уже было (`SessionRegistry.start` отклоняет `resume`
живой Session), но закрытая Session переставала считаться живой до выхода своего процесса.
Владелец решил 2026-10-12: перед relaunch дождаться выхода старого процесса, по таймауту — SIGKILL
(Ticket `worfy-week/20`).

Этот ADR дополняет ADR-0050: тот решил, что Force stop отдаёт Orchestrator сразу и закрытие
процесса уносит всё, что пережило interrupt; этот задаёт порядок «выход старого процесса, затем старт
нового». ADR-0050 остаётся в силе как есть.

**Решение.**

1. **worfy запускает Claude Code сам и видит его выход.** `sdkQueryFactory`
   (`src/main/agent/app-registry.ts`) передаёт SDK опцию `spawnClaudeCodeProcess` — функцию
   `watchedSpawn` (`src/main/agent/options.ts`). Она повторяет запуск SDK по умолчанию
   (`ProcessTransport.spawnLocalProcess`, SDK 0.3.289): те же command, args, cwd, env и abort
   signal, которые передаёт SDK, три pipe, `windowsHide: true`, без веток по платформе. stderr
   декодируется как UTF-8 и идёт в обработчик Session, как шёл. О выходе процесса SDK узнаёт после
   закрытия stderr, но не позже 200 ms после выхода, как в SDK. Сам процесс уходит в Session
   (`QueryRequest.spawned`).
2. **`Session.exited(ms)`** ждёт выхода всех процессов Session. Сначала — запуска, который ещё
   идёт: процесс появится, когда factory ответит. Не вышел за `EXIT_WAIT_MS` — worfy шлёт SIGKILL и
   ждёт ещё `KILL_EXIT_MS` (2 s). Если процесс жив и после этого — предупреждение в лог, и relaunch
   идёт дальше: Orchestrator не должен зависнуть навсегда. `Session.close()` остаётся синхронным.
3. **`EXIT_WAIT_MS` = 7,5 s** (`src/main/agent/session.ts`, рядом с `HALT_TURN_MS`). SDK шлёт свой
   SIGKILL через 7 s после `close()` — на macOS после SIGTERM, на Windows без него. SIGKILL worfy
   приходит позже, поэтому путь мягкого выхода SDK не сокращается ни на одной ОС. Он добивает
   процесс, которому SDK не помог.
4. **Relaunch ждёт выхода старого процесса.** `Orchestrators.relaunch` закрывает старую Session,
   зовёт её `exited()` и сразу регистрирует новую Session с этим ожиданием
   (`SessionRegistry.start(…, after)`). Новая Session живёт с первого мгновения: экран показывает
   её как `starting`, очередь старой переходит в неё, как раньше (`handOverQueue`, `adoptQueue`).
   Процесс Claude Code она запускает, только когда ожидание кончилось. Процесс вышел сразу —
   задержки нет.
5. **Пока идёт ожидание**, отправленное Orchestrator-у сообщение ложится в очередь новой Session и
   уходит в новый процесс, когда тот готов. Старая Session закрыта и сообщений не берёт. Второй
   relaunch закрывает новую Session до её старта: та не запускает процесса, а следующая ждёт её
   `exited()`, то есть выхода того же старого процесса. Закрытие Project-а в это время тоже не
   запускает процесса; старый всё равно получает SIGKILL по таймауту.
6. **Все пути relaunch** — `setUnattended`, `giveBackNow`, отложенный relaunch после хода и задач
   (`relaunchIfFree`) — идут через `relaunch`. `setUnattended` и `giveBackNow` отвечают после старта
   нового процесса. Поэтому строка `orchestrator-returned` журнала прогона и ответ `forceStop`
   приходят после выхода старого процесса, а не после его закрытия.

**Последствия.**

- Force stop может стать дольше: до 15 s `halt` и до 7,5 s (плюс 2 s после SIGKILL) ожидания
  выхода. Всё это время кнопка показывает «Stopping…».
- Старт и конец каждого прогона Autopilot тоже ждут выхода простаивающего процесса. Сколько
  настоящий Claude Code выходит после закрытия stdin, test-ы не меряют: там подставной процесс.
- Запуск Claude Code теперь в коде worfy, для всех Session, а не только для Orchestrator-а. Обновление
  SDK, которое меняет свой запуск по умолчанию, надо сверять с `watchedSpawn`.
- Сообщение ошибки выхода от SDK больше не содержит хвоста stderr: SDK собирает его только в своём
  запуске. Session по-прежнему дописывает свой хвост stderr к ошибке, так что текст ошибки на экране
  не беднеет.
- На Windows поведение меняется: worfy теперь ждёт выхода процесса и может послать ему SIGKILL
  (на Windows Node завершает процесс через TerminateProcess). Такой PR вливается после gate full на
  Windows-ПК (ADR-0056).

## Considered Options

- **Свой `spawnClaudeCodeProcess`, повторяющий запуск SDK** (выбрано). Публичная опция SDK; worfy
  получает `ChildProcess` с событием `exit`, `exitCode` и `kill`.
- **Узнать о выходе, не подменяя запуск.** У `Query` SDK нет ни pid, ни события выхода; опция
  `onProcessSpawned` есть только во внутреннем коде `sdk.mjs`, в публичных типах (`sdk.d.ts`) её нет.
  Можно было бы найти pid в `~/.claude/sessions/<pid>.json` по id сессии и опрашивать
  `kill(pid, 0)`. Отвергнуто: запись появляется после старта процесса, pid может быть переиспользован,
  а опрос — чтение `~/.claude` по таймеру.
- **Постоянная пауза перед стартом нового процесса** (например, 7 s). Отвергнуто: каждый переход
  Autopilot стал бы на 7 s дольше, а процесс, который не вышел, всё равно мог бы жить.
- **Без живой Session на время ожидания** (новая Session создаётся после выхода старого процесса).
  Отвергнуто: у экрана не было бы id Session, и сообщение, отправленное в это время, получало бы
  отказ «The Session is not running» вместо места в очереди.
- **Править ADR-0050.** Отвергнуто: принятые ADR не правятся (правило проекта).
