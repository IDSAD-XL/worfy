# 0096 — записи о падениях и повтор поодиночке командой; меняет ADR-0086, пункты 2–4
Дата: 2026-11-05. Статус: принят. Вступает в силу с merge PR этого ADR и обновлением Harness на машине, где
идёт gate full (`pnpm install:stable`, Replace Harness). После merge правятся `rules.md` Profile-а worfy на обеих
машинах — у каждой свой (ADR-0042), только по слову владельца: на Mac — Orchestrator, на ПК — Session на ПК.

**Контекст.** По [ADR-0086](0086-pc-gate-full-once-per-wave.md) красный gate full на `main` на ПК сначала
проверяют на flaky test: Session на ПК повторяет упавшие test-ы поодиночке руками (пункт 3), сообщает SHA, код
выхода и строку вердикта (пункт 2), а при подтверждённой регрессии открывает issue `pc-main-red` с отчётом в теле
(пункт 4). Отчёт — текст: «19 failures, all green alone», «60 failed in 15 files under a game». bridge-Session
(Session на Mac, которая передаёт сообщения между Orchestrator-ом и Session на ПК) пересказывает его, и
Orchestrator по памяти решает, что flaky, а что регрессия, и повторялся ли flaky test раньше — а от этого зависит
запись в карантин (ADR-0083, пункт 3).

Epic `worfy-failures` ([spec](../../.scratch/worfy-failures/spec.md)) дал для этого данные и команды. Красный
gate пишет запись на каждый упавший test — test, шаг gate, SHA, компьютер и платформу, время, первую строку
ошибки после очистки, команду повтора поодиночке — в папку состояния gate, вне репозитория (ADR-0005). CLI
Harness `gate-failures` (`harness/bin/gate-failures`) умеет:

- `rerun [--run <id> | --last] [--file <path>] [--limit N] [--dry-run]` — гоняет каждый упавший test run-а
  отдельно на том же SHA и пишет файл повтора. Отказ (exit 3), если HEAD не равен SHA run-а, дерево грязное, run
  импортирован или с другого компьютера. Playwright test-ы идут последними, под замком e2e и после проверки
  экрана, когда Profile задаёт `workflow.e2e_lock`. Коды выхода: 0 — все зелёные поодиночке, 2 — хоть один
  красный, 3 — повторять нечего, отказ или test без команды повтора (и ни одного красного).
- `export [--run <id> ...] [--since <days>] [--out <file>]` — записи этого компьютера вместе с их файлами
  повтора как текст частями до 60000 символов; перед выводом проверяет личные данные и при находке отказывает
  (exit 2).
- `import <file> | - | --gh <owner/repo> (--issue N | --pr N)` — кладёт чужие записи в `imported/`; с `--gh`
  читает тело и комментарии issue или PR и берёт только те, чей автор — `github.account` Profile-а.
- `report [--days N] [--computer <name>] [--json]` — по записям многих run-ов и обеих машин: flaky, стабильно
  красные, без повтора, run-ы «под нагрузкой» и кандидаты в карантин и в Windows exception.

`node scripts/quarantine-suggest.mjs` превращает кандидатов `report --json` в записи формата
`test/quarantine/<id>.json` — печатает, никогда не пишет.

**Решение** (владелец, 2026-11-04, ответы на Q1–Q3 spec-а `worfy-failures`: Q1 — А и В как запасной путь, Q2 — А,
Q3 — да).

1. **Повтор поодиночке — команда, а не ручной прогон** (меняет ADR-0086, пункт 3). Красный gate full на ПК —
   Session на ПК сразу после него, на том же SHA и в том же worktree, запускает
   `gate-failures rerun --last` (самый новый красный run этого worktree). Замок e2e и проверку экрана `rerun` берёт
   сам, когда задан `workflow.e2e_lock`; руками их не берут. Повтора внутри run-а gate по-прежнему нет, вердикт
   gate не меняется (Q2, вариант А; решение владельца 2026-10-28 о карантине).
   - Код 0 — все повторённые test-ы зелёные поодиночке: flaky test под нагрузкой. `main` красным не считается,
     только если в выводе `rerun` нет строки `step without tests, not rerun: <step>`. Такой строкой `rerun` называет
     упавший шаг без test-ов (lint, typecheck, сборка) и ничего для него не запускает, поэтому с ней `main` красный,
     как при коде 2. Повтор, суженный `--file`, таких строк не печатает; тогда решает строка самого gate
     `--- failure records: <file> (<n> tests, <m> steps without tests)`: `<m>` больше 0 — красный.
   - Код 2 — хоть один test красный и поодиночке: регрессия, `main` красный на ПК (пункт 4 ADR-0086).
   - Код 3 — повтор ничего не подтвердил зелёным: упал шаг без test-ов (lint, typecheck, сборка), у test-а нет
     команды повтора, или `rerun` отказал. Это считается как код 2. Отказ из-за дерева (HEAD не тот SHA, грязное
     дерево) сначала устраняют и повторяют `rerun`.
   - Долгий повтор (десятки e2e test-ов) можно сузить `--file` и `--limit`; `--dry-run` печатает список и оценку
     времени без запуска. Неповторённый test остаётся «без повтора» и flaky не считается.
2. **Отчёт Session на ПК несёт блок export** (дополняет ADR-0086, пункт 2). Как прежде — SHA, код выхода и строка
   вердикта gate full. После красного — ещё код выхода `rerun` и блок `gate-failures export --run <id>`, где
   `<id>` — id красного run-а `<tag>/<run>` (первое слово первой строки вывода `rerun`); файлы повтора этого run-а
   export берёт сам. При отказе `rerun` печатает только `gate-failures rerun: <причина>` в stderr; тогда `<id>` —
   первое слово строки этого run-а в выводе `gate-failures list`: самой новой строки с первыми 12 знаками
   проверенного SHA и без пометки `imported` (список идёт от новых к старым). Такой строки нет — gate записей не
   сохранил (его отчёт кончается `--- failure records: not saved, <why>`): блока нет, отчёт говорит, что записи не
   переданы. Куда идёт блок (Q1, вариант А):
   - красный `main` — в issue `pc-main-red` (тело или комментарий);
   - зелёный повтор (flaky) — комментарием в PR, чей merge-коммит проверял gate full (в Wave — последний влитой
     PR Wave);
   - запасной путь (вариант В) — текст блока в сообщении между Session-ами, когда комментарий GitHub оставить
     нельзя.
   Длинный export — несколько частей; каждая — отдельным комментарием. Репозиторий публичный: export сам
   отказывает при личных данных (exit 2), и такой блок не публикуется — отчёт говорит, что записи не переданы.
3. **Issue `pc-main-red` — отчёт gate плюс блок export** (дополняет ADR-0086, пункт 4). Условие открытия, метка,
   команды `gh label create` и `gh issue create`, закрытие только зелёным gate full — как в ADR-0086. Список
   упавших test-ов `file:line` в теле остаётся: он нужен прицельной проверке PR-исправления (пункт 5 ADR-0086).
4. **Orchestrator на Mac читает записи, а не пересказ.** Получив отчёт ПК, он запускает
   `gate-failures import --gh IDSAD-XL/worfy --issue N` (или `--pr N`; для сообщения — `gate-failures import -`
   или файл), затем `gate-failures report --days 14`. Первые три строки отчёта — в отчёт Wave (вне Wave — в отчёт
   Session, которая влила PR). Кандидатов в карантин печатает `node scripts/quarantine-suggest.mjs`; запись в
   `test/quarantine/` делает человек или Orchestrator по `rules-merge.md` Profile-а, как сейчас, а не команда.
   «Повторяется» из ADR-0086, пункт 3, теперь считает `report`: flaky в двух разных run-ах (другой SHA или другой
   компьютер) за 14 дней (Q4 spec-а).

Что остаётся в силе: ADR-0086, пункты 1 и 5–8, и в пунктах 2–4 всё, что выше не названо: когда и на каком SHA
запрашивается gate full на ПК, что такое зелёный gate full, единственное место состояния красного `main` — issue с
меткой `pc-main-red`, кто его открывает и закрывает.

**Последствия.**

- Решение «flaky или регрессия» принимает код выхода `rerun` вместе со строками `step without tests` его вывода,
  а не пересказ; Orchestrator видит записи ПК в
  своём `report` вместе с записями Mac.
- Отчёт Wave с PR со scope `pc` получает три строки `report`; кандидат в карантин виден без памяти о прошлых Wave.
- Блок export лежит в публичном репозитории. Очистка при записи и проверка при export ловят пути, имя
  пользователя, hostname, UUID, токены; имя, которое test сам печатает в сообщении без пути, они не ловят (риск 4
  spec-а).
- Повтор e2e долгий (до часа на 60 test-ов); пока он идёт, замок e2e на ПК занят.
- Skill `epic-wave` (раздел 4, «A check that answers on the main branch after the merge») описывает `rerun`,
  `export`, `import`, `report` в общем виде; `rules.md` Profile-а worfy на обеих машинах получает тот же порядок
  после слова владельца. До этого Session на ПК со старым Harness повторяет test-ы по ADR-0086, пункт 3, как
  написано, — оба пути дают один вердикт.

## Considered Options

- **Записи ПК на Mac — через Linked machine (worfy Link)** (Q1, вариант Б). Отвергнуто: нужен новый вызов Link и
  код worfy, а Harness CLI сам Link не умеет.
- **Только сообщение между Session-ами** (Q1, вариант В как основной). Отвергнуто как основной путь: следа в
  репозитории нет, доставка не подтверждается. Оставлен запасным.
- **Gate сам повторяет упавшие test-ы в конце красного run-а** (Q2, вариант Б). Отвергнуто: каждый красный run
  дольше, а повтор нужен не всегда.
- **Gate зеленеет, если все упавшие test-ы зелёные поодиночке** (Q2, вариант В). Отвергнуто: против решения
  владельца 2026-10-28 — повтора внутри run-а нет, вердикт gate честный.
- **Поправка только на ПК, без строк `report` в отчёте Wave** (Q3, вариант «только ПК»). Отвергнуто: без
  `import` и `report` на Mac решение о карантине снова опирается на пересказ.
- **Переписать пункты 2–4 ADR-0086.** Отвергнуто правилом `rules-adr.md` Profile-а: текст принятого ADR не
  переписывается, изменение — новый ADR и датированный раздел `## Amendments` в ADR-0086.
