# 0114 — Assistant — Session приложения над всеми Project-ами машины: MCP-сервер `worfy-app`, шесть границ, закрытый список действий в main, пункты в папке данных Project-а, проверка источников через connectors claude.ai
Дата: 2026-11-25. Статус: принят.

Epic `worfy-assistant`, Ticket 01; spec — [`.scratch/worfy-assistant/spec.md`](../../.scratch/worfy-assistant/spec.md),
принят владельцем 2026-11-20 из черновика Product Session
[`docs/product/proactive-runtime/drafts/worfy-assistant.md`](../product/proactive-runtime/drafts/worfy-assistant.md).
Решения владельца — карта [proactive-runtime](../product/proactive-runtime/map.md), вопросы 01–13, и spec, раздел
«Решения владельца (карта proactive-runtime, 2026-11-20)», пункты 1–22; права —
[вопрос 01](../product/proactive-runtime/issues/01-что-агент-делает-сам.md), устройство —
[вопрос 07](../product/proactive-runtime/issues/07-где-живёт-агент.md), внешние источники —
[вопрос 12](../product/proactive-runtime/issues/12-как-читать-внешние-источники.md). Критика —
[`docs/product/critic/worfy-assistant-2026-11-20.md`](../product/critic/worfy-assistant-2026-11-20.md) (Split);
владелец 2026-11-20 («Все верно») отклонил возражение 1 и принял возражения 2 и 3 (spec, решение 21). Этот ADR
записывает то, что решил spec; новых решений в нём нет. Значения, которые spec оставил открытыми, названы в разделе
«Что остаётся открытым» вместе с Ticket-ом, который их задаёт.

**Контекст.** С 2026-08-21 по 2026-11-20 работа стояла 28 раз, и сигнал об этом лежал непрочитанным от 4 часов до
14 дней ([история простоев](../product/proactive-runtime/research-история-простоев.md)). По всем Project-ам worfy
показывает только счётчики («N busy · N PR need you · N waits») и утренний digest PR; пометка `quiet` молчащего хода
видна только в самой Session; что уже уведомлено, main помнит только в памяти; остановка Run-а Autopilot-а — только
toast; Auto-continue после ошибки API или сброса Limits продолжает только Orchestrator (решение 3 Epic-а
`worfy-retry`). Внешних источников, кроме GitHub, worfy не читает. Все MCP-серверы worfy привязаны к одному Project-у
через cwd Session, общей шины событий в main нет.

Владелец решил завести Assistant — агента worfy, по одному на машину, над всеми Project-ами этой машины. Он замечает,
что работа стоит или ждёт пользователя, объясняет почему, готовит следующий шаг, в пределах, заданных пользователем,
сам делает внутренние обратимые действия worfy, регулярно проверяет Slack и Jira в work hours пользователя, знакомится
с пользователем и отвечает на вопросы о самом worfy. Код Assistant не пишет, Epic-и в очередь не ставит, вовне ничего
не публикует. Всё опционально, включая самого Assistant-а (решение 7); у нового пользователя и у того, кто обновил
worfy, он выключен (решение 10).

**Решение.**

1. **Три слоя** (spec, «Решение»).
   - **Ядро внимания — код main без модели.** Собирает события всех Project-ов машины как пункты, а не счётчики, хранит
     их между перезапусками, само замечает, что «ничего не произошло», решает, будить ли модель, и сразу выполняет
     действия закрытого списка (пункт 4).
   - **Session Assistant-а** (пункт 2).
   - **Исполнители прежние:** Orchestrator, Session-ы, Autopilot с диалогом пользователя, pr-follow, pr-reply.

2. **Assistant — Session приложения** (решение 11, вариант c вопроса 07; spec, «Session Assistant-а»).
   - Session Claude Code, новая на каждое пробуждение. Память между пробуждениями — файл состояния: обязанности,
     открытые предложения, обязательства, правила из оценок пользователя, ответы пользователя.
   - cwd — папка данных worfy вне всех Project-ов: `CLAUDE.md` и hooks Project-ов не грузятся. На Canvas Project-ов
     этой Session нет.
   - Для Harness это третий вид Session: новое значение `WORFY_SESSION_KIND` (сейчас есть `product`,
     `src/main/vendors/claude/options.ts`) и свой файл правил.
   - Рассуждает сильная модель; Haiku 5.5 только сортирует текст внешних источников (пункт 6).
   - Будит Session ядро: срочное — сразу (работа стоит и закрытый список не помог; Run остановился), несрочное — пачкой
     в work hours, утром — сводка, и когда пишет пользователь. Перед каждым автоматическим пробуждением — проверка
     Limits (обобщённая проверка Terminal AI, порог 5-часового окна 80 %) и дневной предел пробуждений (решение 13).
   - Assistant на Codex — не в этом Epic-е: у Codex нет одноразового вызова.

3. **MCP-сервер `worfy-app`** (spec, «MCP-сервер `worfy-app`»). Session Assistant-а получает только его.
   - Привязан к приложению, а не к cwd Session: нынешние серверы worfy вне Project-а не работают.
   - Чтение: Project-ы и машины, пункты журнала, workflow Project-а, нити PR, хвост Session, Run Autopilot-а, Limits,
     поиск и чтение описаний функций worfy (`docs/features`, которые кладутся в сборку).
   - Предложения: создать, обновить, снять. У Prepare — точный текст будущей Session.
   - Действия — только те, что разрешает режим обязанности, и только через функции main, у которых есть свои проверки:
     например, pr-follow отказывает, пока идёт Autopilot, а `autopilot_start` всегда открывает диалог.
   - Чужой текст помечен как данные, с источником и автором. Секретов в ответах нет.

4. **Закрытый список действий — в main, без модели** (решения 1 и 13, вариант C вопроса 01; spec, «Закрытый список
   действий»).
   - Сам Assistant делает только внутренние обратимые действия из этого списка, всё остальное предлагает.
   - Действия: разбудить простаивающий Orchestrator фиксированным сообщением, которое просит проверить и продолжить
     остановленные Subagent-ы; продолжить Session на Canvas после сброса Limits.
   - Текст действия задаёт main, а не Assistant.
   - Каждое действие — строка журнала Assistant-а с пунктом, который его вызвал.
   - Список расширяется только кодом.
   - Ticket 08, который его строит, начинает с причины простоя 2026-11-13 (возражение 3 критика): 5-часовой лимит
     остановил трёх implementer-ов, и Auto-continue Orchestrator-а, который был в main с 2026-11-07, их не продолжил.

5. **Шесть границ в коде** (решение 9, «Принимаю все 6»; spec, «Границы»).
   1. У Assistant-а только tools `worfy-app`: нет Bash, записи файлов и сети.
   2. Чужой текст приходит к нему только как данные, с источником и автором.
   3. Сам Assistant делает только действия из закрытого списка, и их текст задаёт main. Session с текстом, который
      написал Assistant, стартует только по щелчку пользователя, и пользователь видит этот текст до старта.
   4. Наружу — только существующий щелчок Send.
   5. Project-ы второй машины Assistant только читает.
   6. Каждое действие пишется в журнал вместе с пунктом, который его вызвал, и с like и dislike пользователя.

6. **Проверка внешних источников — через connectors claude.ai** (решение 19, вариант В вопроса 12; spec, «Проверка
   источников через connectors claude.ai»).
   - Пользователь подключает Slack и Jira в claude.ai. Своих token-ов для этих источников у worfy нет. Какие connectors
     подключены, main узнаёт без вызова модели — из списка MCP-серверов, который Claude Code уже отдаёт worfy.
   - Одна проверка — один одноразовый вызов Haiku 5.5 (thinking включено всегда). В вызове только read tools одного
     connector-а: ни tools Claude Code, ни `worfy-app`, ни настроек Project-а. Образец изоляции — narrator Live summary.
   - Рецепт источника говорит вызову, что искать («что касается пользователя» с прошлой проверки) и какие tools
     разрешены. В этом Epic-е два рецепта: Slack и Jira.
   - Выход — структурированные пункты: источник, id, автор, время, ссылка, короткий текст, касается ли пользователя,
     срочно ли, к какому Project-у или Ticket-у относится. main проверяет форму; ответ, который проверку не прошёл,
     пунктом не становится и пишется в журнал.
   - Session Assistant-а и тут видит только tools `worfy-app`: пункты источников приходят к ней как данные, с
     источником и автором.
   - Интервал — у каждого типа проверки свой (Slack — около 10 минут, Jira — раз в час), проверки, отмеченные
     пользователем, спят вне work hours (решение 5). Один планировщик проверок в main; настройки — в настройках машины,
     их каналы IPC `local`, как у настроек Limits и Link.

7. **Где хранятся пункты** (spec, «Ядро внимания (main)»).
   - Пункты журнала лежат в папке данных Project-а на его машине — `<Project data folder>` в `WORFY_DATA_DIR`
     (ADR-0005), не в репозитории Project-а.
   - У пункта есть источник, Project, предмет (PR, Ticket, Session, Run, сообщение источника), вид, время начала,
     ревизия, состояние (новый, просмотрен, отложен, снят, закрыт, устарел) и обязанность.
   - Дедупликация — по источнику, id и ревизии; склейка — по предмету за день.
   - После запуска worfy ядро догоняет то, что пропустило. Пока Mac спит или worfy закрыт, проверки не идут.

8. **Две машины** (решение 6). Assistant каждой машины отвечает за её Project-ы; Project-ы второй машины он видит через
   Link только для чтения (ADR-0066).

**Что это решение меняет и чего не меняет в прежних.**

- **ADR-0105 не меняется.** Ответ в PR публикует только main по щелчку Send пользователя; у Assistant-а нет пути к
  отправке ответа в PR (граница 4).
- **ADR-0058 этот ADR не меняет.** Переход одноразовых вызовов на Haiku 5.5 и правило «thinking не отменяет
  Suggestion» записал Ticket `worfy-polish` 135 (Amendment ADR-0058 от 2026-11-20). Проверка источников опирается на
  него.
- **Решение 3 Epic-а `worfy-retry`** («Повтор только у Orchestrator-а», `.scratch/worfy-retry/spec.md`) меняется для
  Session-ов на Canvas: их после сброса Limits продолжает Assistant по режиму обязанности. Меняет поведение Ticket 08;
  в остальном решение 3 остаётся как было.
- **ADR-0100 не меняется** (решение 8): Epic-и в очередь ставит владелец, Assistant только предлагает.
- **ADR-0021** (allowlist MCP-серверов Project-а) не меняется: Session Assistant-а работает вне Project-ов с одним
  сервером `worfy-app` (граница 1). Урок ADR-0021 — с 634 tools у Haiku второй ход падал с «Prompt is too long» — причина первого шага Ticket-а 11 (ниже).
- **ADR-0002 и ADR-0005 не меняются.** Действия Assistant-а идут только через функции main с их проверками (пункт 3),
  пункты лежат в `WORFY_DATA_DIR` (пункт 7).

**Что остаётся открытым** (spec значения не задал; задаёт названный Ticket).

- Можно ли оставить в одноразовом вызове один connector и только его read tools, и сколько места в контексте займут
  tools connector-ов, — первый шаг Ticket-а 11. Если ограничить вызов нельзя, Ticket 11 останавливается и возвращается
  к владельцу с вариантами; тогда пункт 6 этого ADR пересматривается Amendment-ом.
- Через что connector Claude ходит в Slack и что одобряет admin workspace Slack — не проверено (spec, «Риски»). Ticket-а
  для этого spec не назначает; первыми connector Slack вызывают Ticket-ы 11 и 12.
- Значение `WORFY_SESSION_KIND`, имя и путь файла правил и файла памяти, какая именно сильная модель рассуждает —
  Ticket 10.
- Имя файла пунктов в папке данных Project-а и запись о нём в инвентарь ADR-0005 — Ticket 03.
- Дневной предел пробуждений (значение по умолчанию) и способ оценки доли Assistant-а в окнах Limits — Ticket 05; на
  экране процент помечен как оценка.
- Разброс интервалов проверок и work hours по умолчанию — Ticket 04; интервалы рецептов Slack и Jira в пределах
  решения 5 — Ticket-ы 12 и 13.
- N для паузы обязанности (сколько проигнорированных предложений или dislike подряд) и N минут для правила «CI
  основной ветки красный» по умолчанию — Ticket 07; оба пользователь меняет в настройках (Ticket 15).
- Причина, по которой 2026-11-13 Auto-continue Orchestrator-а не продолжил работу, — Ticket 08.

**Последствия.**

- В main появляется шина событий для Assistant-а (ядро внимания) и один планировщик проверок источников.
- Каждая проверка источника — вызов модели на подписке пользователя: Slack раз в 10 минут за 10 рабочих часов — 60
  вызовов в день. Против цены — счётчики token-ов по каждому вызову, дневной предел и проверка Limits (решение 20).
- Против prompt injection из Slack, Jira и PR — шесть границ: чужой текст для Assistant-а только данные, а действовать
  он может только закрытым списком, текст которого задаёт main.
- Gmail и Google Calendar, Assistant на Codex, доставка на телефон, Assistant для команды — не в этом Epic-е (spec,
  «Не в этом Epic-е»).

## Considered Options

**Что Assistant делает сам** (вопрос 01).

- A — только замечает и объясняет. B — ещё готовит следующий шаг, работу запускает пользователь. Не выбраны
  (решение 1).
- **C — B плюс внутренние обратимые действия из закрытого списка. Выбран** (решение 1).
- D — C плюс сам выбирает работу и ставит Epic-и в очередь. Отклонён: запрет на Epic-и, которые worfy ставит в очередь
  сам, остаётся (решение 8, ADR-0100).

**Как читать Slack и Jira** (вопрос 12).

- А — свой HTTP-клиент в main: API token Jira, internal app Slack и `search.messages`. Рекомендовал советник; владелец
  отклонил: много ручных шагов, internal app Slack может не разрешить admin.
- Б — общее Slack app worfy со входом через PKCE. Не выбран (решение 19). Факты из вопроса 12: app вне Marketplace
  получает 1 запрос в минуту на `conversations.history` (правило Slack 2025-05-29), refresh token-ы PKCE живут 30 дней.
- **В — connectors claude.ai через одноразовый вызов модели. Выбран** (решение 19).
- Г — MCP-клиент в main. Не выбран (решение 19).

**Где живёт Assistant** (вопрос 07).

- **Новая Session приложения на каждое пробуждение и файл памяти (вариант c). Выбран** (решение 11).
- Код в main без Session («самая дешёвая альтернатива» советника: уведомления и Auto-continue для всех Session-ов без
  модели). Не выбран как целое: закрывает часть простоев, но не объясняет, не связывает событие с работой и не готовит
  шаг. Его части вошли в ядро внимания и закрытый список.

**Один Epic или два** (возражение 1 критика: Slack и Jira — во второй Epic). Отклонено владельцем: путь к Slack и Jira
решён (вариант В), условие самого критика для одного Epic-а выполнено (решение 21).
