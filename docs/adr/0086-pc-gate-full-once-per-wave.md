# 0086 — PR со scope `pc` вливается по `ci-ok`, а gate full на Windows-ПК идёт на `main` после Wave; меняет ADR-0056, пункт 2, ADR-0071, пункт 4, ADR-0072 и ADR-0083, пункт 6
Дата: 2026-10-29. Статус: принят. Вступает в силу с merge PR этого ADR. После merge правятся `rules.md` Profile-а
worfy на обеих машинах — у каждой свой (ADR-0042): на Mac его правит Orchestrator, на ПК — Session на ПК,
которая и открывает и закрывает issue `pc-main-red` (пункты 4 и 6).

**Контекст.** Платформенный PR, для которого `node scripts/windows-verdict-scope.mjs <base> <head>` из
checkout-а `main` печатает `pc` (Terminal, окна, меню, уведомления, `test/e2e/**`, упаковка — список
`PC_ONLY` скрипта), по ADR-0083, пункт 6, ждёт gate full на Windows-ПК владельца на своём head. ПК гоняет
такие PR по одному, и каждый стоит в очереди: Windows-Ticket от конца работы до merge — 2,5 h против 0,6 h у
прочих (аналитика 2026-10-27). Сам gate full на ПК долгий: на #975 — 2925 s (`[gate] time (full)`: `test`
1273 s, `test:e2e` 1440 s, `test:package` 150 s). Под нагрузкой полного прогона в нём краснеют test-ы, которые
поодиночке зелёные (2026-10-29: 7 и 13 таймаутов в двух прогонах подряд, ни один не воспроизвёлся отдельно).
ПК бывает занят или на паузе по слову владельца, и тогда PR со scope `pc` не вливаются совсем.

С #958 job `windows-e2e` — `pnpm test:e2e` на Windows-runner-е в 4 shard-ах — входит в `ci-ok` и решает его
(`NON_BLOCKING` в `scripts/ci-ok.mjs` пуст; job добавлен в #921 как не решающий). e2e на Windows больше не
проверяет только ПК: их проверяет runner у каждого PR, которому нужны e2e. Только на ПК остаётся то, чего
runner не видит: настоящий Terminal (ConPTY, PowerShell, `node-pty`), окна, меню и уведомления на рабочем
столе с настоящим экраном, упакованное приложение на Windows и test-ы, которые runner пропускает
(`test/windows-runner.ts`).

**Решение** (владелец, 2026-10-28, решение 7 раздела «Решения владельца 2026-10-28: процесс» spec-а
`worfy-throughput`; Orchestrator, 2026-10-29, ревью #989).

1. **PR со scope `pc` вливается так же, как любой PR с кодом:** зелёный `ci-ok` и отметка `review`
   `success` на head (ADR-0083, пункт 2), если `main` не красный на ПК (пункт 4). Отметка `check/windows`
   (ADR-0067) — `success` на head, где `ci-ok` зелёный; отчёт Wave помечает такой PR «ПК — после Wave»: по
   пометке видно, что ПК этот head не проверял. Сама отметка (`ticket mark`) описания не несёт. gate full на ПК
   на head PR не нужен и не запрашивается.
2. **ПК гоняет `GATE_SCOPE=all` gate full на `main` после merge PR со scope `pc`.**
   - В Wave — один раз после Wave, в которой влит хотя бы один такой PR, на SHA последнего merge Wave.
     Запрашивает Orchestrator в конце Wave. Wave без PR со scope `pc` gate full на ПК не запрашивает.
   - Вне Wave (PR влит skill-ом `ship-ticket` сам по себе) — сразу после merge, на merge-коммит этого PR.
     Запрашивает Session, которая его влила.
   - Запрос без отчёта заменяется следующим: один gate full на более новом SHA `main` отвечает за оба.
   - Session на ПК сообщает SHA, код выхода и строку вердикта gate. Зелёный — код 0 и строка
     `[gate] green (full)`.
3. **Красный gate full — сначала один повтор упавших test-ов** Session-ом на ПК, поодиночке, на том же SHA:
   проверка на flaky test. Автоматического повтора внутри run-а нет (решение владельца 2026-10-28 о
   карантине). Зелёные поодиночке test-ы — flaky test под нагрузкой: отчёт со списком и кодами выхода, а
   повторяется — запись в карантин по ADR-0083, пункт 3; `main` красным не считается. Снова красный —
   регрессия, и `main` красный на ПК.
4. **Красный `main` на ПК — открытый issue GitHub с меткой `pc-main-red`** в репозитории `IDSAD-XL/worfy`.
   Открывает его Session на ПК, когда повтор подтвердил регрессию: в заголовке SHA, в теле отчёт gate (код
   выхода, строка вердикта, упавшие test-ы `file:line`). Сначала она создаёт метку:
   `gh label create pc-main-red --repo IDSAD-XL/worfy --force --color B60205 --description "main is red on the PC gate full"`
   (`--force` не падает, если метка уже есть), потом —
   `gh issue create --repo IDSAD-XL/worfy --label pc-main-red`. Issue без метки чтение ниже не находит и
   принимает красный `main` за зелёный. Это единственное место состояния: его видят все Wave всех epic-ов и
   merge без Wave. Перед merge любого PR со scope `pc` Session, которая вливает, читает
   `gh issue list --repo IDSAD-XL/worfy --label pc-main-red --state open`: есть открытый — PR не вливается и
   ждёт. Прочие PR вливаются как обычно: их условие — `ci-ok` (ADR-0083, пункт 7, про красный `ci-ok` на
   `main` не меняется). Запрошенный, но ещё не прогнанный gate full на `main` merge не держит.
5. **Исключение — PR, который чинит этот красный.** Его описание называет issue `pc-main-red` как то, что он
   чинит, — без слова GitHub, которое закрывает issue при merge (`Fixes`, `Closes`, `Resolves`): закрыть
   issue может только зелёный gate full (пункт 6). Такой PR — исправление вперёд или revert виноватого PR —
   вливается по зелёному `ci-ok`, отметке `review` и прицельной проверке ПК на своём head: упавшие test-ы из
   отчёта issue, зелёные — `check/windows` `success` на этом head.
6. **`main` снова зелёный на ПК**, когда Session на ПК отчиталась зелёным gate full на merge-коммите
   исправления или на более позднем SHA `main`. Запрашивает его Session, которая влила исправление, сразу
   после merge. Зелёный — Session на ПК закрывает issue комментарием с отчётом; красный — issue остаётся, и
   цикл повторяется с пункта 3.
7. **Срок — 1 h на исправление вперёд** от открытия issue, как у красного `ci-ok` на `main` (ADR-0083,
   пункт 7). Не влит за 1 h ни один PR-исправление — Orchestrator вливает revert виноватого PR по пункту 5.
   Виноватого ищут среди PR со scope `pc`, влитых после последнего зелёного gate full на ПК; Session на ПК
   называет тех, чьи файлы задевают упавшие test-ы. Автоматического revert нет (решение 7): revert вливает
   Orchestrator руками.
8. **Какие пути дают `pc`, по-прежнему решает список `scripts/windows-verdict-scope.mjs`**, а не этот ADR.
   gate full на ПК остаётся и инструментом Session на ПК — для разбора сбоя и проверки своих правок.

Что остаётся в силе: ADR-0056, пункты 3–6; ADR-0067; ADR-0071, пункты 1 и 5; ADR-0072 для прицельной проверки
пункта 5 («без регресса» сравнивает её с `main`); ADR-0083, кроме пункта 6 в части «PR со scope `pc` ждёт
gate full на ПК на том же head».

**Последствия.**

- PR со scope `pc` не ждёт ПК, пока `main` не красный на ПК: путь до merge — как у прочих PR, ПК нужен раз в
  Wave, а не на каждый такой PR.
- Пока ПК занят или на паузе, а `main` красный на ПК, issue `pc-main-red` никто не закрывает, и PR со scope
  `pc` стоят до возвращения ПК: исправлению вперёд и revert-у нужна прицельная проверка ПК (пункт 5), а снять
  красный может только зелёный gate full на ПК (пункт 6). Это не хуже прежнего порядка, где при паузе ПК
  стоял каждый PR со scope `pc`, но этот ADR такой случай не решает.
- Регрессия Terminal, окон, меню или уведомлений на Windows попадает в `main` и видна после Wave, а не до
  merge. Цена — до 1 h исправления вперёд и gate full на ПК после него, пока новые PR со scope `pc` стоят.
- Отметка `check/windows` `success` у PR со scope `pc` больше не значит «ПК проверил этот head»: это говорит
  пометка в отчёте Wave, а проверку ПК — отчёт о gate full на `main`.
- Skill `epic-wave` (раздел 4, «Checks before merge») получает пункт о Check, который отвечает на основной
  ветке после merge, а skill `ship-ticket` (шаг 9) — запрос такого Check после merge вне Wave. Что этот Check —
  `windows` для scope `pc` и где состояние красного `main`, говорят `rules.md` Profile-а worfy.
- Первая Wave с PR со scope `pc` — приёмка: PR влит до gate full на ПК, gate full на `main` после Wave и его
  вердикт записаны в «Итог» Ticket-а `worfy-throughput` 30.

## Considered Options

- **Как было: gate full на ПК на head каждого PR со scope `pc` (ADR-0083, пункт 6).** Отвергнуто: очередь на
  ПК и 2,5 h до merge. При паузе ПК такие PR стояли всегда; по выбранному порядку они стоят, только если
  `main` красный на ПК (раздел «Последствия»).
- **gate full на ПК раз в Wave, состояние красного `main` — в decision log или отчёте Wave.** Отвергнуто
  (ревью #989): decision log есть только у Wave Autopilot-а, Wave другого epic-а и merge без Wave его не
  видят.
- **Состояние — строка в `rules.md` Profile-а или в `HANDOFF.md` на `main`.** Отвергнуто: `rules.md` лежит
  вне репозитория на каждой машине своё, а строка в `HANDOFF.md` требует PR на открытие и на снятие.
- **Открытый issue с меткой `pc-main-red` (выбрано).** Одно место для всех Session и Wave, открыть и закрыть —
  одна команда `gh`, без PR.
- **Запрет без исключения для исправления.** Отвергнуто (ревью #989): исправление регрессии Terminal, окон,
  меню или уведомлений трогает пути `PC_ONLY`, само имеет scope `pc` и попадало бы под запрет.
- **Автоматический revert по красному gate full на ПК.** Отвергнуто решением 7: revert — решение
  Orchestrator-а, по сроку пункта 7.
