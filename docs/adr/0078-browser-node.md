# 0078 — Browser Node: `<webview>` с хранилищем на Browser profile, Live и Asleep с пределом, исполнение на Machine Project-а, свой MCP server через CDP
Дата: 2026-10-19. Статус: принят.

**Контекст.** Проекты владельца — чаще всего веб-приложения и сайты с ролями: admin, moderator,
user. Проверить Ticket глазами каждой роли сейчас можно только вне worfy: руками в своём браузере
или Playwright-тестом, который знает лишь заранее написанные сценарии. Владелец хочет Node с
браузером Chromium на Canvas, в котором Claude ведёт себя как живой пользователь, под сохранённым
входом нужной роли, и чтобы висящие браузеры не ели ресурсы и не тормозили Canvas.

Что есть в коде сегодня:
- Browser Node нет. В отложенном списке `docs/roadmap.md` — «Dock со встроенным браузером», то
  есть панель вне Canvas, а не Node.
- Card показывается в `<iframe>` на своём origin `worfy-card://` (ADR-0012). Отдельного постоянного
  хранилища кук на iframe не бывает.
- `webviewTag` в окне не включён (`src/main/window.ts:84-92`), session partition-ов (отдельных
  хранилищ кук и данных сайтов) в `src/main` нет.
- Canvas монтирует только видимые Node (`onlyRenderVisibleElements`,
  `src/renderer/canvas/Canvas.tsx:543`). Для Terminal и Card это работает; браузер при каждом pan
  терял бы страницу. Усыпления живых Node нет нигде.
- MCP server-ы Session собираются на запуск Session (`src/main/agent/options.ts`) из встроенного
  `worfy-canvas` и `.mcp.json` Harness, с фильтром по списку в Profile (ADR-0021).
- Terminal и агенты Project-а исполняются на его Machine, Linked machine их только показывает
  (ADR-0052).

**Решение** (владелец, 2026-10-19, четыре раунда вопросов: «со всем согласен», «13–17 да», раунд по ревью — пункты 11–16).

1. **Зачем.** Browser — для исследовательской проверки Ticket-а глазами разных ролей и для действий
   по просьбе в чате. Итог проверки — найденные проблемы и Playwright-тесты, которые Session по ним
   пишет. Регрессионным набором в CI Browser не становится: прогон Claude медленный,
   недетерминированный и дорогой.
2. **Термины.** Node — **Browser**, сохранённый вход под одной ролью — **Browser profile**
   (`CONTEXT.md`). Слова «карточка» и «профиль» заняты Card и Profile.
3. **Хост — `<webview>`.** Он живёт в DOM: zoom Canvas его масштабирует, Node и меню перекрывают
   его как обычный элемент. У каждого Browser profile своё постоянное хранилище
   (`partition="persist:…"`). Main включает `webviewTag` и проверяет каждое подключение в
   `will-attach-webview`: без preload, без `nodeIntegration`, только partition-ы Browser profile-ов.
4. **Управление — свой MCP server worfy через CDP** (Chrome DevTools Protocol, у Electron —
   `webContents.debugger`), а не расширение Claude in Chrome. Session видит действия «открыть URL,
   кликнуть, напечатать, screenshot, прочитать страницу, консоль, сеть». Пользователь видит те же
   действия вживую. Server попадает в список MCP server-ов Profile, как любой другой (ADR-0021).
5. **Browser profile.** Принадлежит Project-у, лежит на Machine, в репозитории следов нет
   (ADR-0005). Вход в аккаунт делает только пользователь руками; Session-ы приходят уже со входом и
   паролей не видят. Создавать Browser profile может только пользователь. У Browser profile есть
   список origin-ов (например `http://localhost:3000`, `https://staging.example.com`): переход
   Session за его пределы отклоняется с понятной ошибкой, пользователь руками ходит куда угодно.
   Один Browser profile может быть открыт в нескольких Browser-ах сразу, куки у них общие.
6. **Live и Asleep.** Asleep — последний screenshot, URL и прокрутка; процесс страницы закрыт,
   хранилище остаётся на диске. Browser засыпает, если он вне экрана дольше ~30 с, если zoom Canvas
   ниже уровня читаемого текста, или ~5 мин без фокуса и без действий Session. Просыпается по клику
   или по вызову инструмента Session и загружает сохранённый URL заново. Пороги — в Settings.
7. **Предел Live.** Одновременно Live не больше N Browser-ов (по умолчанию 3, в Settings). При
   открытии N+1-го засыпает тот, к которому дольше всех не обращались. Browser, которым сейчас
   управляет Session, не засыпает.
8. **Кто ведёт.** Session может открыть Browser под существующим Browser profile. Пока она его
   ведёт, на Browser плашка «Claude управляет»; клик или ввод пользователя забирает управление, и
   Session получает ответ «пользователь перехватил».
9. **Где исполняется.** Browser работает на Machine своего Project-а, как Terminal и Session.
   Linked machine показывает поток кадров (CDP `Page.startScreencast`, кадры приходят событием `Page.screencastFrame`) и передаёт ввод. Browser profile
   поэтому один, с какого бы экрана ни шла работа. Поток кадров — отдельный Ticket после базового
   Browser.
10. **Autopilot.** Агенты Wave проверяют acceptance criteria Ticket-а в Browser без человека, но
    только под Browser profile-ами с флажком «доступен Autopilot». Такой Browser считается в
    пределе Live и входит в Family Ticket-а. Нет нужного Browser profile или вход протух — агент не
    входит сам, а пишет в отчёт «нужен вход под <роль>» и продолжает без UI-проверки.
11. **Жизнь после Session.** Browser, открытый Session-ой, уходит с Canvas вместе с ней в любом
    случае: автоархив (ADR-0076), Hide, Remove. Browser profile остаётся. Session, которая не
    архивируется (pinned, Keep), держит свой Browser. Restore Session из архива Browser не
    возвращает: его дёшево открыть заново. Browser, открытый пользователем, живёт, пока
    пользователь его не закроет.
12. **Слой Live Browser-ов вне списка Node-ов.** Canvas выключает Node вне экрана для всего Canvas
    сразу (`onlyRenderVisibleElements`), и вернуть отрисовку одному Node нельзя. Поэтому
    `<webview>` Live Browser-ов рисуются отдельным слоем внутри той же системы координат Canvas, а
    Node Browser — рамка, к которой слой привязан. Уход с экрана страницу не убивает; её усыпляют
    правила пункта 6. Так Session может вести Browser вне экрана, в том числе в Autopilot. Первый
    Ticket Epic-а — прототип слоя с проверкой отображения (pan, zoom, перекрытие Node-ов, drag);
    если он не пройдёт, запасной вариант — засыпать сразу при уходе с экрана и вести только
    видимый Browser.
13. **Family.** Browser, открытый Session-ой, входит в её Family по связи «открыт этой Session», а
    через неё — в Family её Ticket-а. Browser, открытый пользователем, ни в какую Family не входит.
14. **Read only.** Для Linked machine с уровнем Read only (ADR-0066) кадры и ввод Browser — `write`,
    как вывод Terminal. Такая машина видит только рамку Browser с именем Browser profile, без
    картинки и без снимка спящей страницы.
15. **Несохранённая форма и занятый предел.** Перед сном main через CDP спрашивает, есть ли у
    страницы обработчик `beforeunload` («Leave site?»). Если есть, Browser не засыпает и
    показывает метку «несохранённые изменения». Если все N Live заняты — формой или Session-ой —
    Browser, который открывает пользователь, открывается сверх предела с предупреждением, а Session
    получает ошибку «все Live Browser-ы заняты» и ждёт.
16. **Одна живая страница на все экраны.** Project может быть открыт в нескольких окнах и на
    Linked machine-ах (ADR-0053), Layout у них общий. Live Browser живёт ровно в одном окне — там,
    где с ним работали последним. Остальные экраны показывают кадры этой страницы и пересылают ей
    ввод тем же механизмом, что и Linked machine (пункт 9). Правила сна (пункт 6) смотрят на все
    экраны: Browser засыпает, только если его не видно ни на одном.
17. **Не в v1.** Вход Browser profile в Playwright-тесты (`storageState`) не отдаём: тесты
    логинятся сами через fixture-ы проекта. Dock со встроенным браузером не делаем; позже он сможет
    показывать тот же Browser.

**Последствия.**
- Включается `webviewTag` — новая поверхность атаки. Защита держится на `will-attach-webview` и
  на том, что guest-страница не получает preload worfy.
- Electron в документации не рекомендует `<webview>` и может менять его поведение между версиями.
  Обновление Electron проверяет Browser отдельным e2e-тестом.
- Каждый Live Browser — отдельный процесс Chromium, примерно 100–300 МБ; предел N — главный рычаг.
- Пробуждение перезагружает страницу. Форму, о которой страница не предупреждает через
  `beforeunload`, сон теряет; worfy её не видит, потому что preload в страницу не ставится.
- Отдельный слой Live Browser-ов — главный риск по отображению: страница рисуется не внутри Node,
  а над ним, и порядок перекрытия с другими Node-ами, отставание при pan и drag, обрезка по краю
  рамки надо проверить прототипом до остальной работы (пункт 12).
- Session через Browser выполняет действия в веб-приложении под чужой ролью. Список origin-ов и
  вход только руками пользователя — граница, которую нельзя ослаблять ради удобства.
- Решения 4 и 9 вместе означают: CDP-сессия всегда открывается на Machine Project-а; на Linked
  machine нет ни кук, ни CDP-сессии — она получает кадры и отправляет ввод, а исполняет его
  Machine Project-а.
- Browser — нейтральный тип Node по цвету, как Card и Terminal (ADR-0077, пункт 2: больше типов
  цветом не кодируется).

## Considered Options

- **`WebContentsView`.** Отвергнуто: нативный слой поверх окна, zoom Canvas его не масштабирует, он
  всегда поверх Node и меню, координаты пришлось бы двигать при каждом pan.
- **Offscreen rendering в картинку внутри Node.** Отвергнуто: дорого по CPU на каждом кадре.
- **`<iframe>`, как у Card.** Отвергнуто: нет отдельного постоянного хранилища на роль, и многие
  сайты запрещают показ во frame-е (`X-Frame-Options`).
- **Claude in Chrome в настоящем Chrome с `--user-data-dir` на Browser profile.** Отвергнуто:
  браузер живёт вне Canvas, нужна установленная Chrome и расширение с native messaging, за раз
  подключается один браузер. Electron поддерживает расширения Chrome лишь частично.
- **Browser на экране Linked machine с синхронизацией кук.** Отвергнуто: dev server Project-а
  слушает `localhost` своей машины, и с другой машины до него не достучаться; синхронизация кук
  ломается на сессиях, привязанных к устройству, CSRF-токенах и одновременном входе.
- **Claude логинится сам по учёткам из fixture-ов.** Отвергнуто как поведение по умолчанию: пароли
  попали бы в транскрипт, а на production Claude учётные данные не вводит.
- **Без предела Live, только сон по таймеру.** Отвергнуто: пять Browser-ов на экране — пять
  процессов Chromium одновременно, Canvas тормозит.
