# 0032 — Колонка рамок Epic-ов обходит Node-ы на плоскости; main размещает Node-ы без размера рамок
Дата: 2026-10-06. Статус: принят.

**Контекст.** Рамки Epic-ов и Ticket-ы — производные Node-ы (ADR-0011): renderer считает их из
модели workflow (`src/renderer/canvas/epic-layout.ts`), Layout хранит на Epic один Node
`epic-frame` со смещением рамки от её автоматического места и `w = h = 1`. Стопка рамок
(`stackFrames`) начиналась в (0, 0), что бы там ни лежало. Main ставит свои Node-ы — Orchestrator,
HANDOFF, New session — правилом `placeNewNode` (`src/main/layout/place.ts`): точка (40, 40), если
её не занимает Node на плоскости, иначе под всеми такими Node-ами; рамки при этом не видны, их
размера в Layout нет. Orchestrator main открывает у каждого активного Project-а, поэтому рамки
ложились на Orchestrator и HANDOFF почти везде (Ticket 10 Epic-а worfy-daily). Ticket-ы приходят из
`epic-status` асинхронно, после того как Orchestrator уже поставлен, — в момент размещения рамок
ещё нет; у Auction Orchestrator и HANDOFF уже сохранены в (40, 40).

Два вопроса Ticket-а 10: кто знает размер рамок, когда main ставит новый Node; как рамки обходят
Node-ы, которые уже стоят.

**Решение.**

1. **Рамки встают в свою колонку (вариант «г»).** Все рамки — одна колонка с общим левым краем `x`;
   внутри неё порядок и промежутки прежние (`FRAME_GAP`), сверху `y = 0`. `x` — первое место
   слева направо, начиная с 0, где полоса шириной самой широкой рамки, от `y = −FRAME_GAP` и
   неограниченно вниз, с отступом `FRAME_GAP` по бокам, не задевает ни одного Node-а на плоскости.
   Кандидаты — 0 и правый край каждого Node-а плюс `FRAME_GAP`; последний всегда свободен.
   Полоса неограниченна по высоте, поэтому рост рамки — раскрытие стопки done, новый Ticket, новая
   рамка ниже — идёт вниз внутри колонки и ни на что не надвигается. Колонка сдвигается вправо,
   только когда Node на плоскости встаёт в неё сам (его поставили или перетащили) или когда растёт
   ширина самой широкой рамки.
2. **Node на плоскости — одно правило для main и renderer.** Видимый (`hidden = false`),
   незакреплённый на экране (`pinned = false`) Node не производного вида
   (`src/shared/layout/derived.ts`). Оба читают его из `src/shared/layout/derived.ts`.
3. **Колонка пересчитывается при каждой смене Layout и модели workflow.** Ticket-ы, пришедшие после
   Orchestrator-а, и рамки, выросшие после того, как main поставил Node, обходят его так же, как при
   первом открытии.
4. **Main размера рамок не знает (ни «а», ни «б», ни «в»).** `placeNewNode` и `placeNear`
   (`create_card`, `create_note` без x, y) не меняются: новый Node встаёт по-старому — в (40, 40),
   если она свободна, — а колонка рамок уходит из-под него при ближайшем пересчёте. Контракт
   `create_card` и `create_note` с явными x, y не меняется.
5. **Сохранённые Layout-ы не переносятся (вариант «д» не нужен).** Orchestrator и HANDOFF у Auction
   остаются в (40, 40): уходит колонка рамок, а она не хранится. Layout Project-а при открытии не
   меняется.
6. **Ручное смещение рамки — поверх колонки.** Смещение пользователя, как и раньше, отсчитывается от
   автоматического места (ADR-0011) и в расчёт колонки не входит. Рамку, которую пользователь сам
   положил на Node, worfy не сдвигает и Node из-под неё не уносит.

**Цена.**

- Рамки двигаются без участия пользователя: когда в колонку встаёт новый Node (Card рядом с
  Session-ом, Node, перетащенный пользователем), вся колонка прыгает вправо от него. Рамка со
  смещением пользователя прыгает вместе с колонкой.
- У Project-а с Orchestrator-ом в (40, 40) рамки начинаются правее него, а не в (0, 0); при узком
  окне и viewport по умолчанию видна только левая часть колонки.
- Node, на который пользователь сам перетащил рамку, остаётся под ней (пункт 6).
- Производные Node-ы других источников (дерево Subagent-ов, ADR-0011) колонка не учитывает: их нет
  в Layout.

Источник: Ticket 10 Epic-а worfy-daily (`.scratch/worfy-daily/issues/10-рамки-epic-не-на-node-ах.md`).
Решение принято исполнителем Ticket-а без владельца как обратимое: оно меняет только расчёт
положения рамок в renderer.

## Considered Options

Кто знает размер рамок, когда main ставит новый Node:

- (а) Main сам считает `layoutEpic`, перенесённый в `src/shared`. Не выбрано: Orchestrator ставится
  до того, как пришли Ticket-ы, и у Auction уже сохранён в (40, 40), — main всё равно не может
  обойти рамки, которых ещё нет, и колонка из пункта 1 нужна в любом случае. Модель workflow и
  расчёт рамок стали бы зависимостью размещения в main.
- (б) Renderer сохраняет настоящие w, h рамки в Layout. Не выбрано: размер рамки производный и
  меняется при каждой смене статуса Ticket-а — это запись в `layout.json` на каждое изменение
  workflow, против ADR-0011; и та же гонка с Ticket-ами, пришедшими позже.
- (в) Размещение новых Node-ов переходит в renderer. Не выбрано: Orchestrator и HANDOFF main
  создаёт без окна; пришлось бы переносить создание Node-ов из main.
- Никто — колонка рамок уходит от Node-ов сама (выбрано, пункт 4).

Как рамки обходят Node-ы, которые уже стоят:

- (г) Колонка рамок, не пересекающая Node-ы на плоскости (выбрано, пункт 1).
  - Колонка левее самого левого Node-а — пример из Ticket-а. Не выбрано: Orchestrator стоит в
    (40, 40) у каждого Project-а, и рамки целиком уходили бы в отрицательные `x`, за левый край
    viewport по умолчанию.
  - Полоса только на высоту стопки. Не выбрано: раскрытие стопки done удлиняет полосу, она задевает
    Node ниже, и колонка прыгает в сторону от щелчка пользователя.
- (д) Рамки остаются от (0, 0), Node под рамкой переносится из-под неё операцией `move`. Не
  выбрано: worfy двигал бы Node-ы пользователя и сохранял это в Layout при каждом росте рамки;
  Ticket предлагал «д» только для остатка — Node-а под рамкой со смещением пользователя, — а этот
  остаток пользователь создаёт сам (пункт 6).
