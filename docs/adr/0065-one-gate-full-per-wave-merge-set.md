# 0065 — Один gate full на набор готовых PR Wave
Дата: 2026-10-16. Статус: принят.

**Контекст.** До этого ADR каждый PR с кодом перед мержем проходил свой путь: rebase на свежий main,
`GATE_SCOPE=all` gate full на ветке (около 11,5 min), потом CI на Linux заново — rebase меняет head
PR. Правило записано в `rules.md` Profile-а worfy («Перед мержем любого PR с кодом — … gate full на
ветке после rebase»). ADR-0056, пункт 6, добавляет: «За раз вливается один PR. Второй перед мержем
обновляется от свежего main, и его проверки идут заново: CI на Linux, а для платформенного PR — ещё и
gate full на Windows». Каждый следующий PR Wave ждёт rebase, gate full и CI предыдущего — около 30
min на PR. Замер Epic-а `worfy-throughput` (раздел «Откуда» его spec-а): шаг Gate → merge — четверть
всего времени Ticket-а, и вся она — эта очередь. GitHub обновления ветки перед мержем не требует: у
main нет branch protection и rulesets, а CI идёт и на push в main (`.github/workflows/ci.yml`).

**Решение.** Готовые PR Wave вливаются набором после одного gate full на общем дереве. Механика — скрипт
Harness `harness/bin/wave-gate` (команды `check` и `merge`), включает её поле Profile-а
`workflow.merge_gate: "wave"`; путь замка e2e — поле `workflow.e2e_lock`.

1. **Набор.** PR Wave с вердиктом `VERIFIED` и зелёным CI на head, в порядке мержа. `wave-gate check`
   записывает SHA `origin/main` как базу, во временном worktree от неё делает `git merge --squash` и
   commit каждого PR по порядку — как squash-мерж GitHub — и записывает дерево после каждого PR
   (дерево префикса). PR с конфликтом выходит из набора с причиной `DIRTY` и идёт назад implementer-у
   на rebase, как раньше.
2. **Один gate full на набор вместо rebase и gate full на каждый PR.** `GATE_SCOPE=all` gate full идёт
   один раз, на дереве всего набора, под замком e2e. PR набора перед мержем не перебазируется.
   Красный прогон повторяется на том же дереве: зелёный повтор — набор зелёный, упавшие test-ы первого
   прогона записываются как flaky test. Красный и при повторе — деление пополам по префиксам порядка
   мержа: самый короткий красный префикс называет виноватый PR; префикс перед ним — зелёный, и
   вливается только он. Всего прогонов gate full — не больше 2+⌈log₂ N⌉. «Не удалось проверить»
   (код 3, «ничего не прогналось», остановка сигналом) — не зелено, мержа нет.
3. **CI на Linux заново перед мержем не нужен.** CI зелёный на head каждого PR набора, а сам мерж
   запускает CI на push в main.
4. **Гарантия дерева на каждом мерже.** `wave-gate merge` под замком главной ветки: перед первым мержем
   `origin/main` должен совпасть с базой набора — иначе ни одного мержа («base moved»), набор
   проверяется заново. После каждого `gh pr merge --squash --match-head-commit <head>` дерево main
   сверяется с деревом проверенного префикса; первое несовпадение — стоп: дальше никто не вливается,
   причина и номер PR — в файле состояния и в отчёте Wave, затем gate full на main.
5. **Платформенные PR и `needs-mac-gate` — вне набора, по-старому.** Gate full на Windows заново после
   rebase (ADR-0056, пункт 6) остаётся только для PR вне набора. Платформенный PR (ADR-0056, пункт 2;
   флаг ставит Orchestrator) и PR Session на Windows-ПК с меткой `needs-mac-gate` в набор не входят:
   они вливаются по одному, с rebase, своим gate full и, для платформенного, вердиктом Windows. Так же
   идут PR, которые набор вывел (`DIRTY`, виноватый), и PR, готовый после начала проверки, — он ждёт
   следующего набора.
6. **Красный CI на main после мержей набора.** Новых мержей нет. Orchestrator открывает revert
   squash-коммита первого красного push-run-а (`git revert`); revert-PR идёт по-старому — вне набора,
   со своим gate full; Ticket отменённого PR — в круг доработки. Revert, а не правка вперёд: дерево
   main возвращается к проверенному префиксу, и следующий набор проверяется на известной базе.
7. **Долгий прогон.** Проверка набора не помещается в один вызов Bash: skill запускает `wave-gate
   check` в фоне. Каждый законченный шаг сразу записан в файл состояния; повторный запуск после
   обрыва Session-и продолжает с первого незаконченного шага и не повторяет готовые прогоны gate.
   Ушедший `origin/main` сбрасывает состояние: набор проверяется заново.

Поле `workflow.merge_gate`: `null` или нет поля — Harness gate перед мержем не требует (как у других
Project-ов); `"each"` — прежнее правило worfy, gate full на каждый PR после rebase; `"wave"` — этот
ADR. На `local-green` Project-ы поле не действует: у них свой порядок локального мержа.

Этот ADR уточняет ADR-0056, пункт 6, и правило `rules.md` Profile-а worfy о gate full перед мержем;
ADR-0056 не меняется. Правку `rules.md` и `profile.json` Profile-а worfy делает Orchestrator после
мержа Ticket-а `worfy-throughput` 01.

**Последствия.**

- Wave из N PR без красного PR вливается после одного gate full вместо N. Один красный PR задерживает
  соседей на 1+⌈log₂ N⌉ прогонов (повтор и деление); при 10 PR — до шести прогонов вместе с первым,
  всё равно меньше десяти.
- Flaky test на прогоне деления (не на первом и не на повторе) может назвать виноватым не тот PR:
  прогоны деления не повторяются, иначе их больше 2+⌈log₂ N⌉. Цена — один PR зря уходит в доработку и
  вливается со следующим набором.
- Squash-мерж GitHub и локальное слияние могут дать разные деревья. Тогда сверка дерева останавливает
  мерж на первом несовпадении, и main проверяет gate full.
- Платформенные PR и PR с `needs-mac-gate` не ускоряются: их путь прежний.
- Сам `wave-gate` — скрипт Harness, значит его PR платформенный и вливается по-старому, с вердиктом
  Windows.

## Considered Options

- **Gate full на каждый PR после rebase (как было).** Просто и проверяет ровно то, что ляжет в main.
  Цена — очередь: около 30 min на PR, Σ Gate → merge Wave 1 `worfy-polish` — 611 min. Остаётся как
  `merge_gate: "each"` и для PR вне набора.
- **Один gate full на набор с повтором и делением пополам (выбрано).** Один прогон на здоровую Wave;
  виноватый находится за ⌈log₂ N⌉ прогонов; сверка базы и дерева на каждом мерже держит main равным
  проверенному префиксу.
- **Merge queue GitHub.** Делает то же на стороне GitHub, но проверку в очереди гоняет CI GitHub, а
  gate full с e2e и собранным `.app` идёт только на macOS. Нужен macOS-раннер — запрещено ценой
  (правило владельца: Actions только на Linux).
