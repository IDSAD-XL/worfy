# 0056 — Проверка Windows и две Session-и: без Windows-раннера на PR, gate full на ПК владельца перед мержем платформенных PR, общение через репозиторий
Дата: 2026-10-07. Статус: принят.

**Контекст.** После закрытия Epic-а E3 `worfy-harness` («Harness как часть worfy») над одним
репозиторием worfy параллельно идут два Epic-а (решение Q12). `worfy-link` («Linked machines»,
ADR-0052 и ADR-0053) ведёт Session на Mac. `worfy-windows` («Windows-порт», ADR-0054 и ADR-0055) ведёт
Session на Windows-ПК владельца. Нужно решить две вещи: чем проверяется код на Windows и как две
Session-и на разных машинах не мешают друг другу.

Факты:

- CI на PR идёт только на Linux: job `check`, `runs-on: ubuntu-latest`
  (`.github/workflows/ci.yml:25-26`). Job `full-macos` запускается только вручную, через
  `workflow_dispatch` (`ci.yml:61-62`).
- Цена минуты GitHub Actions: Linux $0.006, Windows $0.010, macOS $0.062 (документация GitHub,
  actions-runner-pricing). Правило владельца: Actions держать дешёвыми. CI на PR — только Linux,
  e2e и сборка приложения — локально перед мержем, macOS-раннеров на PR нет.
- Gate: `gate.sh fast` — проверка для Ticket-а, `gate.sh full` — всё, руками или при закрытии Epic-а
  (`harness/hooks/gate.sh:9-10`). Исходы — «зелено», «красно» или «не удалось проверить», и
  последнее зелёным не считается.
- Session-и на двух машинах друг друга не видят. Worktree, замки worktree (`worktree-lock`),
  Background task-и и Profile (ADR-0042: Profile целиком лежит на машине) у каждой свои. Общее у
  них — только репозиторий на GitHub: main, ветки, PR, файлы Ticket-ов, `HANDOFF.md`.
- Wave по определению (`CONTEXT.md`) не содержит Ticket-ов с общими файлами, но смотрит только на
  свой Epic. Skill `epic-wave` уже берёт список открытых PR с их файлами
  (`gh pr list --state open --json …,files`, `harness/skills/epic-wave/SKILL.md:69`). Но ищет в нём
  только занятые номера ADR и состояние мержа (`mergeStateStatus`), а не общие файлы с Ticket-ами
  своей Wave.
- Linked machines в это время только строятся в `worfy-link`, и опереться на них Session-и не
  могут.

Решения владельца 2026-10-07 по вопросам Q12, Q23 и Q25 Session проектирования «Несколько машин и
порт под Windows».

**Решение.**

1. **Windows-раннера на PR нет (Q23).** CI на PR остаётся только на Linux.
2. **Платформенный PR мержится после gate full на Windows-ПК владельца (Q23).** Платформенный PR —
   тот, что меняет поведение на Windows: PR Epic-а `worfy-windows` и PR другого Epic-а, который
   трогает код с ветками по платформе, скрипты Harness или упаковку. Перед мержем такого PR на
   Windows-ПК идёт `gate full`. Его итог — строка вердикта Gate и код выхода — входит в отчёт
   Ticket-а. «Не удалось проверить» — не зелено, и PR не мержится. Переходные исключения — пока
   Gate не на Node и пока test-ы не починены под Windows — в «Последствиях».
3. **Ручной job «Windows»** в `ci.yml` по образцу `full-macos`: только `workflow_dispatch`, на PR
   не запускается. Это дополнительная проверка на чистой Windows по запросу; прогон на ПК из
   пункта 2 он не заменяет. Что он гоняет, решает Ticket Epic-а `worfy-windows`, который его
   добавляет.
4. **Session-и общаются через репозиторий (Q25).** Прямого канала между ними нет. Каждая Session
   ведёт только свой Epic. Всё, что ей нужно знать о второй, она читает из репозитория: Status
   Ticket-ов, открытые PR и их файлы, main, `HANDOFF.md`.
5. **Перед каждой Wave — проверка открытых PR второго Epic-а (Q25).** Session берёт открытые PR
   второго Epic-а и списки их файлов и сравнивает с файлами Ticket-ов своей Wave. Ticket с общим
   файлом в Wave не берётся, пока тот PR не влит, — по тому же правилу, по которому в Wave не
   бывает Ticket-ов с общими файлами. Пересечение и отложенный Ticket называются в отчёте Wave.
6. **Мерж в main по очереди (Q12).** За раз вливается один PR. Второй перед мержем обновляется от
   свежего main, и его проверки идут заново: CI на Linux, а для платформенного PR — ещё и gate
   full на Windows.

**Последствия.**

- Расходы на Actions не растут. PR проверяет только Linux, Windows — ПК владельца, а ручной job
  стоит $0.010 за минуту и запускается только по запросу.
- Мерж платформенного PR ждёт включённого Windows-ПК владельца. PR Session Mac, который оказался
  платформенным, тоже ждёт прогона на Windows, и это связывает две Session-и.
- Регрессию на Windows из PR, который не сочли платформенным, CI не поймает: её увидит следующий
  gate full на Windows. Обратное направление закрывает «Готово, когда» Epic-а `worfy-windows`:
  gate full на Mac зелёный.
- Нужен ли gate full на Mac перед мержем каждого PR Session Windows, этот ADR не решает. Сегодня
  такой PR на PR-уровне проверяет только Linux CI.
- Пока Gate не переписан на Node (ADR-0055), gate full на Windows может не работать. До того первые
  Ticket-ы порта дают вердикт командами проверки Project-а с кодами выхода, и отчёт говорит, что
  Gate не запускался.
- Пока не влит Ticket Epic-а `worfy-windows`, который чинит test-ы под Windows (gate full на Windows,
  сейчас Ticket 14), gate full на Windows может быть красным из-за этих test-ов. До его мержа
  платформенный PR мержится, если падения `pnpm test` на Windows совпадают со списком упавших
  test-ов, который записал Ticket 02 того же Epic-а (репозиторий ставится и запускается на Windows),
  и новых падений нет. С мержа того Ticket-а — только зелёный gate full на Windows.
- Пока worfy под Windows не собран, Session на Windows идёт в Claude Code без worfy. Как на ПК
  ставится Harness до установщика worfy, решает Ticket 01 Epic-а `worfy-windows` (проверка фактов
  на живой Windows и правка Ticket-ов порта).
- На Windows-ПК нужны свой Profile worfy (ADR-0042) и вход `gh` в аккаунт GitHub Project-а: hook
  берёт `GH_TOKEN` командой `gh auth token -u <account>` (ADR-0048). Это шаг владельца.
- Проверки пункта 5 сегодня нет: список открытых PR у skill-а `epic-wave` есть, сравнения их файлов
  с Ticket-ами Wave нет. Где она будет жить — в skill `epic-wave` или в расчёте Wave у worfy, —
  этот ADR не решает.
- `HANDOFF.md` — один файл на репозиторий. Обе Session-и правят его в своих PR, и конфликт решает
  та, что мержит второй.
- Autopilot на Mac и Autopilot на Windows идут одновременно, каждый над своим Epic-ом. Запрет
  ADR-0053, пункт 9 (один Autopilot на Epic одного репозитория, с тем же `origin`, на все Machine),
  им не мешает.

## Considered Options

- **Без Windows-раннера на PR; gate full на ПК владельца перед мержем платформенных PR; ручной job;
  общение через репозиторий** (выбрано).
- **Windows-раннер на каждый PR (`windows-latest` в job на `pull_request`).** Отвергнуто (Q23):
  правило владельца — не добавлять на PR дорогих раннеров. Минута Windows в 1,7 раза дороже
  минуты Linux, а сборку и e2e приложения то же правило держит локально.
- **Проверять Windows только в приёмке Epic-а.** Отвергнуто: регрессии копились бы до конца Epic-а,
  и искать их пришлось бы по всем PR сразу.
- **Прямой канал между Session-ами: сообщения, общая папка, Linked machines.** Отвергнуто (Q25):
  Linked machines только строятся в `worfy-link`, а репозиторий уже общий для обеих машин и хранит
  историю.
- **Не смотреть чужие PR, решать конфликты при мерже.** Отвергнуто (Q25): конфликт находится,
  когда Wave уже сделала работу, и переделывать приходится готовый PR.
- **Долгая ветка порта, влитая в main в конце.** Отвергнуто (Q12): мерж в main идёт по очереди, по
  PR. Одна большая ветка дала бы один большой мерж, и поломки Mac от порта всплыли бы только в
  конце.
- **Epic-и по очереди: сначала Linked machines, потом порт.** Отвергнуто (Q12): Epic-и идут
  параллельно, каждый на своей машине.
