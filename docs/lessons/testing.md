# Test-ы

## Круг доработки вносит дефекты: каждое новое поведение — под test, который краснеет на мутанте

За ночь круг доработки не раз сам вносил дефект: `NoteNode` (Ticket 05), watcher транскриптов
(Ticket 13), уведомления (Ticket 21). Правка по находке ревью — такой же новый код, как первый.
Каждое новое поведение доработки покрывать test-ом и проверять, что test краснеет на мутанте этой
правки. В асинхронном коде (watcher, debounce, таймеры, IPC) перед отчётом продумать гонки: что
будет, если событие придёт между двумя `await`, если файл удалят, пока идёт чтение, если ответ
придёт после закрытия.
Проверка: проверки нет: требование к кругу доработки — текст агентов и skill-ов, test его не сверяет.
Источник: worfy-mvp/05, worfy-mvp/13, worfy-mvp/21.

## Сбой проверочной команды — это «не знаю», а не «нет»

Когда код спрашивает внешнюю команду, жив ли процесс (`ps`), есть ли файл или ветка, у ответа три
значения: да, нет, не знаю. Ненулевой код выхода, таймаут или пустой вывод — это «не знаю», если
команда не сказала «нет» явно (у `ps -p` — код 1 и пустой stdout без сигнала). Сведённое к «нет»,
временное «не знаю» становится необратимым действием: Session объявляется закрытой, её Subagent-ы — `error`.
Test-ом проверять все три ветки, включая подставной `ps`, который падает или висит.
Код: `processState` в `src/main/claude-home/registry.ts`, его вызов в `src/main/claude-home/subagents.ts`.
Проверка: test/contract/claude-home-subagents.test.ts:382 — `ps` не ответил, `processState` отвечает `unknown`;
Session и Subagent-ы в том же случае — соседние test-ы файла; зависший `ps` test не проверяет.
Источник: worfy-daily/08, круг доработки PR #45.

## Любой внешний процесс из main — с env из `agentEnv()`; test-ы из терминала этого не ловят

Почему у `.app` из Finder другой `PATH` и откуда берётся окружение login shell —
[ADR-0007](../adr/0007-claude-code-launch-environment.md). Обобщение: не только Claude Code, а любой
внешний скрипт или CLI, который запускает main (`~/.claude/bin/profile`, `gh`), получает env
из `agentEnv()` (`src/main/agent/env.ts`), а не `process.env`. Test-ы и `pnpm dev` идут из терминала
с полным `PATH` и такой дефект не покажут: test проверяет, что runner получил переданный env, а
ручная проверка идёт на `.app`, открытом из Finder. У приложения не только другой `PATH`, но и
другой аккаунт gh (без `GH_TOKEN` агента), поэтому вывод внешнего CLI сверяют в окне приложения, а не
своей командой (worfy-daily/17, PR #73).
Проверка: test/contract/harness-script-wiring.test.ts:111 — Harness-скрипты из main получают env из
`agentEnv()`, места вызова — test-ы ниже в файле; для `gh` и прочих CLI общего test-а нет.
Источник: worfy-daily/06, круг доработки PR #43.

## Форму ошибки Electron сначала фиксировать e2e на настоящем Electron, потом писать правило

Правило по `code` или `errno` ошибки Electron, написанное по документации, может не совпасть
с тем, что отдаёт Electron на деле. Прерванная загрузка `file://` в Electron 44.5.1 приходит как
`{code: 'ERR_FAILED', errno: -2}`, а не `ERR_ABORTED`/-3, и правило `loadWasAborted` её не узнало.
Порядок: e2e, который на настоящем Electron воспроизводит событие и записывает его форму; потом
правило под эту форму. e2e, который не воспроизводит событие (два `loadURL` в одном тике дают
`null`), ничего не доказывает — проверить, что он краснеет без правки.
Код: `src/main/window.ts` в PR #48 (не влит).
Проверка: test/e2e/window.spec.ts:102 — e2e на настоящем Electron фиксирует прерванную загрузку как
`ERR_FAILED -2`.
Источник: worfy-daily/15, PR #48.

## Снимок окна worfy не содержит vibrancy macOS — сверять с F-SPEC цвет token-а

Нативный vibrancy окна не попадает в PNG ни через `page.screenshot()`, ни через
`BrowserWindow.capturePage()`, ни после смены `nativeTheme.themeSource`. Без подложки
полупрозрачный CSS-слой боковой панели (alpha 204–209) показывает в PNG фон просмотрщика, и сверка
с F-SPEC находит расхождение, которого в окне нет. Другие способы съёмки не искать: снимать через
`snapshotThemes`, она подкладывает непрозрачный token `--sidebar`. На снимке сверять цвет token-а;
сам vibrancy поверх рабочего стола проверяет человек в окне приложения.
Код: `test/e2e/snapshots.ts`.
Проверка: test/e2e/snapshots.spec.ts:90 — боковая панель на PNG непрозрачна (alpha 255): `snapshotThemes`
подкладывает token.
Источник: worfy-daily/18, PR #75.

## Текст, который живёт только в `title`, снимок не доказывает

Подсказка (`title`, tooltip) появляется только при наведении, в PNG её нет. Если два случая
различаются только текстом подсказки, их снимки выходят одинаковыми и ничего не доказывают: в
Ticket-е 01 `worfy-week` снимки «нет аккаунта» и «нет входа» совпали побайтно, и ревью вернуло
Ticket на круг доработки. Как узнать: заявленного текста не видно на PNG глазами, или хэши снимков
разных случаев совпадают. Что делать: вывести текст на снимок (панель, которую вставляет сам spec,
с подписью, что это не часть приложения) или положить рядом `.txt` с дампом DOM или данных из того
же запуска.
Проверка: проверки нет: правило для автора снимков; ни один test не сравнивает снимки разных случаев.
Источник: worfy-week/01, PR #81.

## Одноразовую правку данных пользователя проверять на минимальность: сколько тронуто против сколько должно

Код: `test/unit/free-place.test.ts:201`, `src/shared/layout/free-place.ts`.
Проверка: test/unit/free-place.test.ts:201 — список сдвинутых Node сверяется с заранее известным.
Источник: worfy-week/04, PR #88.

## Test, который ходит в сеть git к github.com, отключает credential helper

На ПК владельца в `~/.gitconfig` стоит `credential.https://github.com.helper = gh auth git-credential`
(его пишет `gh auth setup-git`). Поэтому каждый `git fetch` или `git push` к github.com запускает настоящий
`gh` — пару `get` и `store` — с учётной записью владельца. Ночью 2026-10-19 процессы `gh.exe` на ПК были от
этого helper-а, не от test-ов. Но test, который делает сетевую операцию git с remote на github.com,
запустил бы настоящий `gh` тем же путём. Что делать: такой test задаёт `GIT_CONFIG_GLOBAL` (временный файл
или `/dev/null`) или передаёт git `-c credential.helper=`. Как узнать: `gh` или `gh.exe` в списке процессов во
время `pnpm test`, хотя ни один test не зовёт `gh` по имени.
Проверка: проверки нет: test-а, который ловит сетевую операцию git без `GIT_CONFIG_GLOBAL`, нет; для прогонов eval то же проверяет test/contract/harness-evals.test.ts:512.
Источник: Session на Windows-ПК, 2026-10-19.

## Test, который запускает только что написанный исполняемый файл, ждёт очередь проверки macOS

- macOS проверяет каждый новый исполняемый файл перед его первым запуском (XprotectService, по одному
  файлу за раз). Замер 2026-10-22: 130–300 ms на новый файл без нагрузки, ссылка (symlink) на уже
  проверенный файл — 4–11 ms; при load 6 — до 4,9 s на файл (worfy-polish 30). В gate full новые файлы
  многих test-ов стоят в одной очереди, и test, у которого их два-три, упирается в свой timeout.
- `test/contract/harness-evals.test.ts` писал stub `claude` заново в каждом test-е — теперь ссылка на
  `test/fixtures/eval-stub/claude.cjs`. Копию git делает сам `scripts/eval-run-env.mjs` (`gitCopy`): она
  новая в каждом запуске `eval-harness.mjs`, и это две проверки на test (обёртка и `git-core/git`).
- `test/unit/install-stable.test.ts` — одна подписанная копия `/bin/sleep` на файл, в test-ах ссылки на неё.

Как узнать: test пишет или копирует файл и сразу его запускает; красный только в gate full, отдельно
зелёный. Что делать: stub — файл в `test/fixtures/`, в test-е ссылка на него; `ps` показывает
программу под путём ссылки.
Проверка: проверки нет: правило держится review; test, который ловит новый исполняемый файл в test-е, не написан.
Источник: worfy-polish/30, worfy-polish/34.
